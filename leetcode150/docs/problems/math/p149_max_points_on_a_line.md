# 149. Max Points on a Line

- Difficulty: Hard
- LeetCode: https://leetcode.com/problems/max-points-on-a-line/
- Official Group: Math
- Pattern Group: Math
- Patterns: math

## First-Principles Explanation

### 1. What Is the Problem Really Asking?

You are given a list of 2D points:

```text
points[i] = [x_i, y_i]
```

The task is to return the largest number of points that lie on one straight line.

For example:

```text
points = [[1, 1], [2, 2], [3, 3]]
```

All three points lie on the same diagonal line:

```text
y = x
```

So the answer is:

```text
3
```

The line does not have to be horizontal, vertical, or pass through the origin. It can be any infinite straight line in the plane.

So the real problem is:

> Among all possible straight lines determined by the input points, find the line that contains the most input points.

A crucial geometric fact makes the problem finite:

> Any two distinct points determine exactly one straight line.

That means we do not need to search through infinitely many possible lines. We only need to reason about lines created by pairs of input points.

---

### 2. Start From the Brute Force Idea

The most direct solution is:

1. Pick every pair of points.
2. Treat that pair as defining a candidate line.
3. Count how many points lie on that line.
4. Keep the largest count.

Conceptually:

```python
best = 1

for i in range(n):
    for j in range(i + 1, n):
        count = 0
        for k in range(n):
            if points[k] lies on the line through points[i] and points[j]:
                count += 1
        best = max(best, count)
```

This is correct because every optimal line containing at least two points is generated by choosing any two points on that line.

But it costs:

```text
O(n^3)
```

There are `O(n^2)` pairs, and for each pair we scan all `n` points.

The deeper question is:

> If we fix one point, can we group all other points by the line they form with that fixed point?

Yes. That reduces the repeated work.

---

### 3. Fix One Anchor Point

Choose one point as an anchor:

```text
anchor = points[i]
```

Now compare it with every later point:

```text
points[j], where j > i
```

Every point `points[j]` forms a line with the anchor.

If several points form the same line with the anchor, then they must all have the same direction from the anchor.

For example, with anchor `[1, 1]`:

```text
[2, 2] gives direction (1, 1)
[3, 3] gives direction (2, 2)
[4, 4] gives direction (3, 3)
```

These raw direction vectors differ, but they all represent the same slope:

```text
1 / 1 = 2 / 2 = 3 / 3
```

So from the anchor's point of view, the problem becomes:

> Count how many other points have each distinct slope relative to this anchor.

If the most common slope from this anchor appears `m` times, then the line through the anchor with that slope contains:

```text
m + 1
```

points, because the anchor itself is also on the line.

---

### 4. Why Slope Is the Right Invariant

A line through a fixed anchor is determined by its direction.

For two points:

```text
anchor = (x1, y1)
point  = (x2, y2)
```

The direction vector is:

```text
dx = x2 - x1
dy = y2 - y1
```

The slope is usually written as:

```text
dy / dx
```

Two points are on the same line through the anchor exactly when their direction vectors are scalar multiples of each other.

For example:

```text
(1, 1), (2, 2), (10, 10)
```

all describe the same direction because they reduce to:

```text
(1, 1)
```

This reduced direction is the invariant we want:

> For a fixed anchor, all points on the same line must produce the same normalized slope key.

The challenge is representing that slope safely.

---

### 5. Do Not Use Floating-Point Slopes

A tempting key is:

```python
slope = dy / dx
```

But floating-point values are a poor representation for exact geometry.

For example, these rational slopes may not be represented exactly:

```text
1 / 3
2 / 6
333333 / 999999
```

Mathematically they are equal, but floating-point rounding can make equality checks fragile.

Also, vertical lines have:

```text
dx = 0
```

so `dy / dx` would divide by zero.

Instead, store the slope as a pair of integers:

```text
(normalized_dy, normalized_dx)
```

This keeps the comparison exact.

---

### 6. The Normalized-Slope Invariant

For each pair of points, compute:

```text
dx = x2 - x1
dy = y2 - y1
```

Then reduce the pair by the greatest common divisor:

```text
g = gcd(abs(dx), abs(dy))
dx = dx / g
dy = dy / g
```

For example:

```text
raw direction (2, 2)  -> gcd = 2 -> normalized (1, 1)
raw direction (4, 4)  -> gcd = 4 -> normalized (1, 1)
raw direction (6, 9)  -> gcd = 3 -> normalized (2, 3)
```

But reducing by `gcd` is not quite enough. We also need a consistent sign convention.

These pairs describe the same slope:

```text
(1, 1)
(-1, -1)
```

And these also describe the same slope:

```text
(1, -1)
(-1, 1)
```

If we allow both representations, equal lines may be counted separately.

A common convention is:

```text
Keep dx positive whenever possible.
If dx is negative, multiply both dx and dy by -1.
```

Then:

```text
(-1, -1) becomes (1, 1)
(-1,  1) becomes (1, -1)
```

Vertical lines need special handling because `dx = 0`. Every vertical line through the anchor should use the same key:

```text
(1, 0)
```

Horizontal lines can similarly use:

```text
(0, 1)
```

With these rules, every slope has one canonical representation.

That is the key invariant:

> For a fixed anchor, two points are counted in the same bucket if and only if the line from the anchor to each point has the same canonical normalized slope.

---

### 7. Detailed Algorithm

Handle small inputs first:

```text
If n <= 2, return n.
```

Any one or two points are always collinear.

Then:

1. Initialize `answer = 1`.
2. For each anchor index `i`:
   - Create an empty hash map `slope_count`.
   - Compare the anchor with every point `j > i`.
   - Compute `dx` and `dy`.
   - Normalize `(dy, dx)` into a canonical slope key.
   - Increment that key's count.
   - The line represented by that key contains `slope_count[key] + 1` points, including the anchor.
   - Update `answer`.
3. Return `answer`.

Why only compare with `j > i`?

Because when `i` is the anchor, points before `i` were already considered as anchors in earlier iterations. For finding the maximum, it is enough that each line eventually gets counted from one of its points as anchor with the remaining points after it.

For example, if a line contains points at indices:

```text
2, 5, 8, 9
```

When `i = 2`, the algorithm sees `5`, `8`, and `9`, so it counts all four points on that line.

---

### 8. Pseudocode

```python
from collections import defaultdict
from math import gcd


def max_points(points):
    n = len(points)
    if n <= 2:
        return n

    best = 1

    for i in range(n):
        slopes = defaultdict(int)
        x1, y1 = points[i]

        for j in range(i + 1, n):
            x2, y2 = points[j]
            dx = x2 - x1
            dy = y2 - y1

            if dx == 0:
                key = (1, 0)       # vertical line
            elif dy == 0:
                key = (0, 1)       # horizontal line
            else:
                g = gcd(abs(dx), abs(dy))
                dx //= g
                dy //= g

                if dx < 0:
                    dx = -dx
                    dy = -dy

                key = (dy, dx)

            slopes[key] += 1
            best = max(best, slopes[key] + 1)

    return best
```

The key is written as `(dy, dx)` because slope is usually read as `dy / dx`. The order does not matter as long as the implementation is consistent.

### 9. Walkthrough of Example 1

Input:

```text
points = [[1, 1], [2, 2], [3, 3]]
```

Start with:

```text
best = 1
```

Use `[1, 1]` as the anchor.

Compare with `[2, 2]`:

```text
dx = 2 - 1 = 1
dy = 2 - 1 = 1
normalized slope = (1, 1)
```

Update:

```text
slope_count[(1, 1)] = 1
line count = 1 + anchor = 2
best = 2
```

Compare with `[3, 3]`:

```text
dx = 3 - 1 = 2
dy = 3 - 1 = 2
gcd = 2
normalized slope = (1, 1)
```

Update the same bucket:

```text
slope_count[(1, 1)] = 2
line count = 2 + anchor = 3
best = 3
```

No later anchor can beat `3`, so the final answer is:

```text
3
```

### 10. Walkthrough of Example 2

Input:

```text
points = [[1, 1], [3, 2], [5, 3], [4, 1], [2, 3], [1, 4]]
```

The answer is `4` because these four points lie on the same line:

```text
[1, 4], [2, 3], [3, 2], [4, 1]
```

They all lie on:

```text
y = -x + 5
```

Now see how the algorithm finds it.

Use `[1, 4]` as anchor. In the original array this point appears last, so if we only scan `j > i`, this specific anchor has no later points. But the same line will be counted earlier from one of its earlier indexed points.

Use `[3, 2]` as anchor.

Compare with `[4, 1]`:

```text
dx = 1
dy = -1
normalized slope = (-1, 1)
```

Compare with `[2, 3]`:

```text
dx = -1
dy = 1
```

After enforcing `dx > 0`:

```text
dx = 1
dy = -1
normalized slope = (-1, 1)
```

Compare with `[1, 4]`:

```text
dx = -2
dy = 2
gcd = 2
reduced = (-1, 1)
```

After enforcing `dx > 0`:

```text
dx = 1
dy = -1
normalized slope = (-1, 1)
```

The same slope bucket receives three other points:

```text
slope_count[(-1, 1)] = 3
```

Including the anchor `[3, 2]`, the line contains:

```text
3 + 1 = 4
```

So the algorithm records:

```text
best = 4
```

### 11. Correctness

We prove that the algorithm returns the maximum number of points on one line.

#### Lemma 1: For a fixed anchor, points on the same line through the anchor produce the same normalized slope key.

If two points lie on the same line through the anchor, their direction vectors from the anchor are scalar multiples of each other. Dividing each vector by the greatest common divisor removes the scalar factor, and the sign convention chooses one canonical orientation. Therefore both points produce the same normalized slope key.

#### Lemma 2: For a fixed anchor, points with the same normalized slope key lie on the same line through the anchor.

If two points produce the same normalized slope key, their reduced direction vectors are identical after canonical normalization. Therefore their original direction vectors are scalar multiples of the same vector. Since both vectors start at the anchor, both points lie on the same straight line through that anchor.

#### Lemma 3: For each anchor, the algorithm correctly counts the largest line that uses that anchor and any later-indexed points.

By Lemma 1, every later point on the same line through the anchor increments the same slope bucket. By Lemma 2, every point in one bucket is truly on that same line. Therefore each bucket count plus one for the anchor equals exactly the number of counted points on that line.

#### Lemma 4: Every optimal line is considered completely by some anchor.

Take any line with the maximum number of input points. Among the points on that line, choose the one with the smallest index. When the algorithm uses that point as the anchor, all other points on the same optimal line have later indices, so they are all scanned and counted in the same slope bucket.

#### Theorem: The algorithm returns the correct answer.

By Lemma 3, every candidate count the algorithm records is the true number of points on some line. By Lemma 4, the globally optimal line is fully counted during the iteration for its smallest-indexed point. Therefore the maximum recorded count equals the maximum possible number of collinear points.

### 12. Complexity

Let:

```text
n = number of points
```

The algorithm chooses each point as an anchor and compares it with later points:

```text
(n - 1) + (n - 2) + ... + 1 = O(n^2)
```

Each comparison performs constant-time arithmetic plus a `gcd` call. If coordinates are bounded by `C`, `gcd` costs `O(log C)`.

So the time complexity is:

```text
O(n^2 log C)
```

In typical LeetCode analysis, coordinate size is treated as bounded, so this is often written as:

```text
O(n^2)
```

For each anchor, the hash map can store up to `O(n)` distinct slopes.

Space complexity:

```text
O(n)
```

### 13. Common Pitfalls

#### Using floating-point slopes

Avoid:

```python
slope = dy / dx
```

Floating-point equality can be unreliable, and vertical lines divide by zero. Use normalized integer pairs instead.

#### Forgetting vertical lines

For vertical lines:

```text
dx = 0
```

All vertical directions from the same anchor must map to the same key, such as:

```text
(1, 0)
```

#### Forgetting horizontal lines

For horizontal lines:

```text
dy = 0
```

Normalize them to one key, such as:

```text
(0, 1)
```

Otherwise `(0, 1)` and `(0, -1)` may be counted separately.

#### Inconsistent signs

These represent the same slope:

```text
(1, -1)
(-1, 1)
```

Pick one convention and apply it every time.

#### Counting only the other points

A slope bucket counts points other than the anchor. The actual line count is:

```text
slope_count[key] + 1
```

Do not forget the anchor.

#### Duplicate points

The original LeetCode constraints for this problem use unique points in modern versions. If duplicate points are allowed in another version, they need special handling because `(dx, dy) = (0, 0)` has no slope. In that variant, count duplicates separately for each anchor and add them to every slope bucket for that anchor.

---

### 14. First-Principles Summary

The problem looks like it asks us to search over infinitely many geometric lines, but two facts reduce it to a finite counting problem:

```text
1. Any two points determine one line.
2. For a fixed anchor point, each line through that anchor is determined by its slope.
```

So the algorithm fixes one anchor at a time and groups every other point by the normalized slope from the anchor.

The normalized slope is the essential invariant:

```text
same normalized slope from the same anchor
<=> same line through that anchor
```

Once that invariant is represented exactly with integer pairs, the rest of the problem becomes hash-map counting.
