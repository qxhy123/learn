# 07 为一个任务创建分支

## 场景

你正在 `main` 上收到一个小任务：修改登录页文案。你不想直接在主干上实验，也不想让未完成工作挡住下一次同步。目标是创建一个短生命周期任务分支，完成可 review 的小提交，并能解释 HEAD、当前分支和主干分别站在哪里。

## 学习目标

完成本章后，你应该能够：

1. 用“可移动引用”解释分支，而不是把分支理解成项目副本。
2. 从干净主干创建任务分支，并验证 HEAD 已附着到新分支。
3. 在任务分支上提交改动，并用历史图解释分支如何向前移动。
4. 在切换分支前判断工作区是否安全，避免覆盖未提交改动。

## 观察点

开始前先固定观察面板：

```bash
git status -sb
git branch --show-current
git log --oneline --graph --decorate --all -n 8
```

你需要确认三件事：

- `git status -sb` 没有未提交改动，或者你明确知道这些改动要留在哪个分支。
- 当前分支是你准备从哪里开始任务的基线，通常是 `main` 或团队约定的集成分支。
- 历史图中当前分支和基线指向同一个提交，或者你能解释它们为什么不同。

一个干净起点通常像这样：

```text
## main
* a1b2c3d (HEAD -> main, origin/main) docs: update guide
```

## 命令

创建并切换到任务分支：

```bash
git switch -c feature/login-copy
```

再次观察：

```bash
git status -sb
git branch --show-current
git log --oneline --graph --decorate --all -n 8
```

此时你应该看到 HEAD 附着在 `feature/login-copy`，而 `main` 仍停在原来的提交上。做一次小改动后：

```bash
git diff
git add docs/login.md
git commit -m "docs: clarify login copy"
```

提交后再看历史图，重点观察：

- 新提交只让当前分支向前移动。
- `main` 没有自动跟着移动。
- HEAD 仍通过当前分支间接指向最新提交。

## 实验

Lab ID：`LAB-BRANCH-TASK-01`

实验步骤：

1. 在练习仓库确认 `main` 干净。
2. 执行 `git switch -c feature/readme-note`。
3. 修改一个文档文件，先看 `git diff`，再提交。
4. 用历史图记录 `main` 与任务分支的分叉位置。
5. 切回 `main`，确认任务分支提交不会出现在当前工作区。

预期结果：学习者能解释“分支只是一个会移动的名字”，并能说明为什么新提交没有改变 `main`。

## 常见错误

- **把分支当成完整目录副本。** 分支主要是提交引用，Git 复用对象，不会复制整个项目。
- **在脏工作区直接切分支。** 如果目标分支会覆盖当前改动，Git 可能拒绝；如果不拒绝，也会让你难以判断改动归属。
- **长期保留任务分支不合并。** 短任务分支越久不同步，后续冲突和 review 成本越高。
- **分支名只写 `fix` 或 `test`。** 好的分支名应表达任务边界，例如 `fix/session-timeout`。

## 危险提示与恢复路径

`git switch -f <branch>` 会强制切换分支并可能丢弃工作区改动。除非你已经确认这些改动不需要保留，否则不要使用。

恢复路径：

1. 如果只是切换被拒，先运行 `git status -sb`，不要加 `-f`。
2. 想保留改动：提交到当前分支，或在后续中断工作章节学习 `stash`/`worktree`。
3. 已经强制丢弃后，若改动没有进入暂存区或提交，Git 通常无法可靠恢复；这就是本章要求先观察的原因。

## 验收

你应该能回答：

1. 当前 HEAD 是直接指向提交，还是附着在某个分支上？
2. 任务分支提交后，`main` 为什么没有移动？
3. 切换分支前为什么要先看 `git status -sb`？
4. 如果任务做到一半需要临时切回主干，你会先检查什么？
