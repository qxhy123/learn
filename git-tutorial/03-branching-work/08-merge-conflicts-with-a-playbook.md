# 08 用 playbook 解决合并冲突

## 场景

你在任务分支上完成了改动，准备把它合并回主干。与此同时，主干也改了同一段内容。Git 无法替你判断哪个业务意图更正确，于是把仓库停在“冲突待解决”的中间状态。

本章目标不是让你记住所有冲突类型，而是建立一套稳定 playbook：先观察、再理解双方意图、再编辑结果、最后确认合并完成。

## 学习目标

完成本章后，你应该能够：

1. 区分快进合并、普通三方合并和冲突合并。
2. 在冲突发生时识别工作区、暂存区和合并状态分别发生了什么。
3. 按固定顺序解决冲突，而不是凭感觉删除标记。
4. 在无法判断业务语义时安全中止合并。

## 状态观察

合并前观察：

```bash
git status -sb
git log --oneline --graph --decorate --all -n 12
```

你要先判断：

- 目标分支是否干净。
- 被合并分支从哪里分出。
- 当前合并可能是快进，还是两边都已有新提交。

冲突发生后立即观察：

```bash
git status
git diff --name-only --diff-filter=U
```

如果存在未合并路径，说明仓库还处于合并中间状态。此时不要急着提交，也不要随意切分支。

## 命令

从主干合并任务分支：

```bash
git switch main
git merge feature/login-copy
```

遇到冲突时使用 playbook：

```bash
git status
git diff --name-only --diff-filter=U
# 打开冲突文件，理解双方意图，编辑成最终结果
git diff
git add <resolved-file>
git status
git commit
```

如果你发现自己无法判断正确结果：

```bash
git merge --abort
```

`--abort` 会尝试回到合并开始前的状态。它不是失败，而是保留判断权，避免把错误业务结果提交进历史。

## 冲突文件如何阅读

典型冲突文件会出现三类标记行：`<<<<<<< HEAD` 表示当前分支片段开始，`=======` 分隔双方内容，`>>>>>>> feature/login-copy` 表示被合并分支片段结束。

处理时不要只问“保留当前分支还是被合并分支”，而要问：

1. 当前分支为什么这样改？
2. 被合并分支为什么那样改？
3. 最终结果是否同时满足两个改动背后的需求？
4. 是否需要补充测试或文档说明新的合并语义？

## 实验

Lab ID：`LAB-BRANCH-CONFLICT-01`

实验步骤：

1. 从同一个提交创建 `feature/a` 和 `feature/b`。
2. 让两个分支修改同一文件同一行。
3. 回到 `main`，先合并 `feature/a`，再合并 `feature/b`。
4. 冲突发生后，记录 `git status` 和未合并文件列表。
5. 编辑成一个同时表达两边意图的结果，`git add` 后再次观察状态。
6. 完成提交，用历史图解释 merge commit 的父提交。

预期结果：学习者能说清楚“冲突是人工判断点”，并能识别合并未完成时 Git 的保护状态。

## 常见错误

- **把冲突当成仓库损坏。** 冲突只是 Git 无法自动决定业务结果。
- **只删除冲突标记。** 删除标记不等于语义正确，最终文件必须能运行、能解释。
- **没看 `git status` 就提交。** 可能还有未解决文件，或者你并没有真正 staged 最终结果。
- **用整文件覆盖解决冲突。** 这很容易把另一边的有效改动一并删除。

## 危险提示与恢复路径

危险动作：在冲突中用 `git checkout --theirs`、`git checkout --ours` 或编辑器按钮“一键接受全部”。这些动作在某些场景有效，但它们绕过了语义判断。

恢复路径：

1. 不确定时先运行 `git merge --abort` 回到合并前。
2. 已经 `git add` 但尚未提交：继续编辑文件，然后重新 `git add`。
3. 已经提交了错误合并：不要在共享主干上直接重写历史，后续恢复模块会用 `revert -m` 处理合并提交回滚。

## 验收

你应该能回答：

1. 快进合并为什么不会产生新的 merge commit？
2. 冲突发生时，工作区和暂存区为什么会处于中间状态？
3. `git merge --abort` 适合在什么时机使用？
4. 为什么解决冲突的核心不是“选一边”，而是“构造正确最终结果”？
