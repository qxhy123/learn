# 17 Tags, Releases and Hotfixes

## 场景

团队需要知道某个版本到底来自哪个提交，线上故障需要从已发布版本切出 hotfix。靠“应该是 main 上某个位置”无法支撑审计、回滚和自动化发布；Git 标签和维护分支能把发布点变成稳定坐标。

## 学习目标

- 区分会移动的分支和应保持稳定的标签。
- 创建、检查并推送附注标签。
- 从发布标签切出 hotfix 分支，修复后生成 patch 版本标签。
- 处理错误标签时先判断是否已推送和是否被自动化依赖。

## 观察点

发布前至少检查：

```bash
git status -sb
git branch -vv
git log --oneline --graph --decorate --all -n 16
git tag --list --sort=version:refname
```

关注：

- 工作区是否干净。
- 标签要指向的提交是否已经通过测试。
- 当前提交是否在预期分支上。
- 同名标签是否已经存在，是否已经推送。

## 命令与判断

### 创建正式发布标签

```bash
git tag -a v1.2.0 -m "Release v1.2.0"
git show v1.2.0
git push origin v1.2.0
```

正式发布优先使用附注标签，因为它携带说明、作者和日期，更适合审计。

### 从标签切 hotfix

```bash
git switch -c hotfix/v1.2.1 v1.2.0
# 修复、测试、提交
git tag -a v1.2.1 -m "Release v1.2.1 hotfix"
git push origin hotfix/v1.2.1 v1.2.1
```

修复完成后，还需要按团队策略把补丁合回主干，避免下个版本丢失 hotfix。

### 查看标签指向

```bash
git show --stat v1.2.0
git log --oneline --decorate v1.2.0 -n 5
```

## 风险提示

标签一旦推送并被发布系统使用，就不应随意移动。删除并重建远端标签可能导致：

- 不同机器看到不同的发布坐标。
- CI/CD 对同名版本产出不一致。
- 回滚、审计和事故复盘无法对齐。

如果标签打错：

1. 先判断是否已推送：`git ls-remote --tags origin v1.2.0`。
2. 若未推送，可以本地删除重打：`git tag -d v1.2.0`。
3. 若已推送，优先发布新版本号或按团队流程公告、冻结自动化，再处理远端标签。

## 实验

Lab：`LAB-RELEASE-HOTFIX-TAG-01`

1. 在练习仓库做一个可发布提交，创建附注标签 `v1.0.0`。
2. 用 `git show v1.0.0` 验证标签内容和指向。
3. 从 `v1.0.0` 切出 `hotfix/v1.0.1`，提交一条修复。
4. 打 `v1.0.1` 标签，并把 hotfix 合回 main。
5. 模拟本地打错标签，在未推送前删除并重打；记录如果已推送会多出哪些协作步骤。

## 常见错误

- 把标签当成可以随意前移的分支。
- 打标签前没有确认工作区干净和测试结果。
- 发布 hotfix 后忘记合回主干。
- 用同一个版本号覆盖不同提交，让自动化和人工记录失去可信度。

## 验收

你应该能解释：

- 为什么标签适合表示发布点，分支适合表示持续开发线。
- 为什么正式发布推荐附注标签。
- 从发布标签创建 hotfix 的完整路线。
- 已推送错误标签为什么不是一个纯本地问题。
