# 第 11 章：设计查询、存储边界与失败路径

## 当前问题

一旦数据被持久化，产品面对的就不再只是“有没有值”，而是“怎么查、在哪查、查不到怎么办、写失败怎么办”。如果这些问题全散在界面层里，应用会很快变得脆弱。

## 核心机制

查询和存储边界的关键是职责分离。View 层只应该提出界面需要什么和用户做了什么；查询与读写策略则应该在更稳定的边界里表达。失败路径同样如此：有些错误属于局部输入问题，有些则是持久化层失败，二者不应该被压成同一种“出错了”提示。

## 在 FocusList 里的落点

在 `FocusList` 里，这一步会让你第一次真正感受到产品工程的重量。搜索条件、过滤视角、项目列表、任务详情都在依赖查询，而用户保存或同步失败时也需要被合理告知。做好这一层之后，UI 层会变轻，因为它终于不再假装自己既是界面，又是查询引擎，又是错误处理中心。

## 常见误区

一个典型错误是把查询写成 View 内部的一堆条件判断，让每个屏幕都偷偷实现一遍数据逻辑。另一个错误则是为了避免重复而过早发明一层抽象，但没有解释清楚失败由谁负责。边界设计最怕的不是文件多，而是职责说不明白。

## 本章小结

查询、存储和失败路径一旦被放到正确边界，`FocusList` 就具备了继续抽出共享核心的前提。因为你终于能看见什么是 UI 关心的事，什么是更稳定的产品规则。
