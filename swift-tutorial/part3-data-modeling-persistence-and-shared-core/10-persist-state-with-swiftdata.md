# 第 10 章：使用 SwiftData 持久化状态

## 当前问题

没有持久化时，`FocusList` 仍然像一个会话内产品：应用一关，用户的工作上下文就跟着消失。到这里，产品已经足够真实，开始值得把状态保存下来。

## 核心机制

`SwiftData` 在这套教程里的意义不是“学会另一个框架”，而是让你第一次面对持久化对产品结构的影响。数据从内存进入存储之后，错误、恢复、查询成本和模型演化都会成为真正问题。持久化并不会让架构自动更好，它只会把原本模糊的边界放大出来。

## 在 FocusList 里的落点

`FocusList` 进入持久化阶段后，用户创建的任务和项目不再只是临时数组，而开始拥有长期存在的产品意义。这个变化会逼你重新思考：哪些状态值得写入存储，哪些仍然应该留在界面层，哪些失败应该在用户层面被看到。

## 常见误区

最常见的错误是把所有状态一股脑持久化，仿佛“能存就应该存”。另一个错误是把存储失败看成技术细节，不给产品设计任何恢复路径。持久化最怕的不是 API 不会写，而是你根本没想清楚什么该保存、为什么该保存、出错时谁负责解释。

## 本章小结

持久化让 `FocusList` 从“应用演示”走向“产品数据”。从这一章开始，数据流讨论不再只是内存中的所有权，还包括长期状态如何进入、离开和重新回到用户面前。
