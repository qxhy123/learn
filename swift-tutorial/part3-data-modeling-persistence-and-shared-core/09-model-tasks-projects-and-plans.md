# 第 9 章：建模任务、项目与计划

## 当前问题

当产品开始出现项目、标签、筛选和更多状态时，早期够用的临时模型会迅速显得脆弱。名字不清、字段随意、关系模糊的模型会直接拖垮后面的持久化、查询和共享核心抽离。

## 核心机制

建模不是把现实世界原封不动搬进代码，也不是为了未来所有可能性把模型堆到最复杂。你需要的是一套能支撑当前产品行为、又能被查询和存储清楚表达的结构。好的模型能解释为什么一个字段存在，也能解释为什么某些字段现在不该存在。

## 在 FocusList 里的落点

对于 `FocusList`，任务、项目和计划的区别必须逐渐清楚。任务是具体动作，项目代表更大的工作容器，而计划描述的是用户如何组织时间或关注。把这三者拆明白，产品层的很多混乱都会自动减少，因为 UI 不再被迫承担建模缺失留下的烂摊子。

## 常见误区

常见误区之一是为了“以后也许有用”过早引入复杂关系；另一个误区是完全不建模，把多个概念混进一个结构里，表面上方便，后面一到查询和持久化就全部爆炸。建模的关键不是复杂，而是边界和命名足够稳定。

## 本章小结

Part 3 的起点不是存储 API，而是模型判断。只有当任务、项目和计划的职责被讲清楚，后面的 `SwiftData`、查询边界和 `FocusCore` 才会有稳固的落脚点。
