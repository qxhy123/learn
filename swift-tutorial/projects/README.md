# Projects：FocusList 项目主线

## 为什么项目目录不是附赠代码区

这套教程的正文和项目目录是绑在一起的。正文负责解释“为什么这样做”，项目目录负责回答“这件事在代码里到底落在哪里”。如果没有 `projects/`，你很容易再次把 Swift 学成一堆抽象概念；如果只有 `projects/` 没有正文，你又会很难知道每一步为什么现在值得做。

## FocusList 这条主线里有什么

你会反复遇到三个表面：

- `FocusListApp`：用户真正面对的应用
- `FocusCore`：逐步抽出来的共享模型与规则
- `focusctl`：建立在共享核心之上的轻量 CLI

它们不是三个独立项目，而是同一条产品线的三个观察角度。前半段你主要从 App 角度学习，Part 3 以后逐步看见核心边界，Part 4 以后再用 CLI 和测试把工程闭环补齐。

## 这个目录该怎么读

- `projects/focuslist/starter/`：你每一章真正动手修改的起点
- `projects/focuslist/checkpoints/`：每个阶段应该达到什么状态，以及为什么下一阶段会继续变化
- `projects/focuslist/final/`：课程收尾时，你应该能描述出的最终产品形态

最有效的读法通常是：先改 starter，再用 checkpoint 校验当前阶段是否成立，最后用 final 判断自己对整条主线的理解是否闭环。

## 做项目线时要持续验证什么

每推进一个 Part，至少重复三件事：

1. 构建 starter，确认系统仍然健康
2. 重新走一遍关键用户路径
3. 解释这次改动怎样改变了产品结构或工程边界

如果你只关注“新增了什么功能”，而不检查这三件事，项目线就很容易再次退化成示例集合。
