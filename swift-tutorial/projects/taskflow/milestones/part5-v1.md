# TaskFlow Part 5 Milestone: v1

## Part 5 结束时，`TaskFlow v1` 代表什么

Part 5 的终点不是“已经做完一个成熟 app”，而是 `TaskFlow` 已经从 SwiftUI 概念练习进入了第一代真实客户端形态。`TaskFlow v1` 至少意味着：

- 任务列表可以作为 SwiftUI 集合界面被表达
- 新增任务有了明确输入入口
- 状态、`Binding`、可观察模型之间的职责开始清楚
- 列表、表单、导航已经能组织最小 app 流程
- 这些结构建立在共享任务核心之上，而不是 UI 私有规则之上

这就是 v1 的教学价值。它证明 SwiftUI 基础已经落地到项目，而不是停在 API 认识层。

## 此时 `TaskFlow` 复用了哪些共享能力

Part 5 的 milestone 应能明确看见这条连续性：

- 共享任务模型继续来自 `TaskCore`
- 任务行、详情和筛选等 UI 结构围绕同一任务领域展开
- SwiftUI 线新增的是交互形式，不是新领域规则

这让 `TaskFlow` 成为共享核心的第一个图形客户端，而不是对前面项目线的替换。

## v1 与 CLI 线的区别

到了这个里程碑，读者应能清楚区分两种客户端：

- CLI 线解决命令组织、文本输出与脚本友好
- SwiftUI 线解决列表、输入、导航与 app 状态反馈

二者的差异是交互表面差异，不是任务语义差异。共享核心因此变得更有现实意义。

## v1 还没有彻底解决什么

Part 5 结束时，有些问题已经被引出，但还没有在架构层彻底做实：

- app 级数据流如何跨多个 feature 协调
- 持久化与共享模型如何进入 app
- 异步更新、preview 与测试如何构成长期演进路径

这也是为什么 Part 6 紧接着要进入 data flow 与 architecture，而不是在 v1 处草草收尾。

## 如何使用这个 milestone

如果你读完 Part 5 再回来看这个文档，应该能确认一件事：`TaskFlow` 已经不再是“会画出任务列表的 SwiftUI demo”，而是共享任务领域上的第一代 app client。下一里程碑的重点，不再是基础 View 组合，而是让这条 app 线真正具备架构成长能力。
