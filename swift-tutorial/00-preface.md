# 前言：如何使用这套 FocusList Swift 教程

## 为什么这套教程要从 App 开始

很多 Swift 教程的默认结构是：先花很长篇幅讲语法，再找一个小项目做收尾。这种方式的问题是，读者很容易把语法学成彼此孤立的知识点，一进入真实 App 就重新失去方向。你会背 `struct`、`enum`、`protocol`，却说不清为什么某个状态应该留在 `View`，为什么某个规则该进入共享核心。

这套教程反过来做：先给你一个真实 App，然后只在当前产品确实需要的时候引入相应的 Swift 和 SwiftUI 能力。这样做的好处是，所有语言和工程决策都能立刻回到 `FocusList` 的真实问题上；代价是你必须接受自己不是在背语法清单，而是在学习一整套产品工程判断。

## 默认读者是什么水平

我默认你已经会一门别的语言，知道基本的函数、类型、模块、测试和命令行。你不需要我解释 for 循环是什么，但你很可能需要重新建立这些判断：

- 为什么 SwiftUI 的 `View` 不是“永久存活的小对象”
- 为什么 `@State` 不该变成“所有数据都往里塞”的桶
- 为什么 `FocusCore` 应该在 Part 3 才出现
- 为什么并发问题常常先表现为状态所有权问题

如果你是完全零基础，仍然能读，但会比较吃力；更适合先找一套基础编程入门材料，再回来沿着这条产品主线推进。

## 环境要求

### 最低要求

- 一台能运行较新 Xcode 的 Mac
- 命令行里可以使用 `swift`
- 基本会用 `git status` 和 `rg`

### 建议验证一次

```bash
swift --version
xcodebuild -version
```

你不需要一开始就把所有工具链细节都弄明白，但至少要确认环境不是坏的。因为整套教程里，App 代码、共享核心、测试和验证脚本都会依赖这套基础开发环境。

## 推荐学习方式

### 1. 先读问题，再看代码

每章开头都会先说明当前产品为什么卡住、为什么必须引入新能力。不要直接跳去抄代码；先知道这段代码解决的是什么问题，后面的判断才会稳。

### 2. 跟着 starter 改，而不是只看 final

`starter/` 的意义是让你面对一个还不够强的系统，再一步步把它推成更好的版本。你当然可以看 `final/`，但那只能帮助你对齐结果，不能代替过程。

### 3. 每完成一个 Part 就做 lab

章节会让你“局部看懂”，labs 才会逼你把这些能力重新拼起来。别把它当选做题，它们是避免你高估自己理解程度的主要机制。

### 4. 把失败也当学习材料

如果你改坏了 starter、测试没过、某个状态放错了，这些都不是“偏离教程”，而是最接近真实工程学习的部分。Swift 和 SwiftUI 真正难的地方，往往都藏在这些错里。

## 技术栈约定

主线默认使用现代 Swift 技术栈：

- `Swift 6`
- `SwiftUI`
- `Observation`
- `SwiftData`
- `Swift Testing`
- Swift Concurrency

这不意味着旧栈完全不存在，而是说这套教程的主叙事不会被“兼容所有历史写法”拖住。如果你需要和更旧的项目打交道，等主线走稳之后再回头补差异，会轻松得多。

## 这套教程刻意不做什么

为了把主线讲透，这里不做几件事：

- 不把 UIKit 或 AppKit 做成平行课程
- 不把服务端 Swift 扩展成另一条主线
- 不把语法点写成百科目录
- 不为了“显得高级”过早堆很多抽象层

你学完这套教程后，当然可以继续深入这些方向，但这里的目标非常明确：先把你带到“能独立做现代 SwiftUI 产品”的层级。
