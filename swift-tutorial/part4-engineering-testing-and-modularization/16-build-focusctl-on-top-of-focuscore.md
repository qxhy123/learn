# 第 16 章：在 FocusCore 之上构建 focusctl

## 当前问题

如果共享核心只被 App 自己使用，很多读者仍然会把它理解成“给 SwiftUI 服务的内部整理”。要真正证明共享规则的价值，需要第二个入口。

## 核心机制

`focusctl` 的意义不在于做成一个复杂命令行工具，而在于让你看见同一套领域行为如何脱离 UI 继续成立。CLI 不是主产品，但它是极好的工程镜子：任何仍然偷偷依赖界面状态的规则，在这里都会立刻暴露。

## 在 FocusList 里的落点

通过 `focusctl`，你可以把任务打印、统计、批量切换等行为理解为共享核心能力，而不是 App 事件处理函数。它让 `FocusCore` 的边界被真正证明，也让测试和验证脚本更容易只围绕稳定规则工作。

## 常见误区

最常见的误区是把 CLI 做得过大，好像要再写一个完整产品；另一个误区则是为了省事把 UI 层的字符串和流程原样搬到 CLI 里。`focusctl` 的任务只有一个：证明共享核心值得存在，不要把主线焦点从 App 身上抢走。

## 本章小结

Part 4 到这里结束时，教程已经不只是“一个有界面的 App”。它开始像一个真正的产品代码库，拥有共享核心、测试、工作区和第二个入口。后面的并发和可靠性讨论也因此有了更稳的地基。
