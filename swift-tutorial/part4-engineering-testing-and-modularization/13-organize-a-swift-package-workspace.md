# 第 13 章：组织 Swift Package 工作区

## 当前问题

到了 `FocusCore` 出现之后，产品不再只是一个应用 target 的故事。如果包结构仍然混乱，测试、CLI 和共享逻辑会一起变得含糊。Part 4 的起点，就是把产品线整理成一个有边界、有依赖关系的工作区。

## 核心机制

`SwiftPM` 在这里的价值不是“学会另一套命令”，而是让你明确哪些代码应该一起演化，哪些不应该。包结构不是技术层分类，而是职责层分类：`FocusListApp` 负责用户表面，`FocusCore` 负责共享规则，`focusctl` 负责第二个入口。只要这三者的依赖方向被讲清楚，后面的测试和扩展才会有稳定基础。

## 在 FocusList 里的落点

把 `FocusList` 推进成工作区后，很多模糊地方会自动暴露出来：某些原本偷放在 UI 里的规则应该迁走，某些领域操作如果对 CLI 和 App 都成立，就不该继续只存在于某个页面事件里。工作区结构的意义，是强迫你把这些边界说清楚。

## 常见误区

最常见的误区是把包拆得过细，把目录结构当成功。另一个误区则是因为担心复杂度，继续把所有东西放在同一个 target 里。真正的判断标准是：边界是否有清楚责任，依赖方向是否可解释，修改某块代码时影响面是否还能被控制。

## 本章小结

工程化的第一步不是多写脚本，而是让代码的组织方式和产品责任一致。`SwiftPM` 让 `FocusList` 从一个会增长的应用，变成一个能被维护的工作区。
