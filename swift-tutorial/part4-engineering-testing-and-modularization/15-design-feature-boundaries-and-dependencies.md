# 第 15 章：设计功能边界与依赖关系

## 这章处理的是“未来还能不能改”

只要产品继续生长，边界和依赖一定会成为主问题。功能边界设计得差，后果通常不是当下立刻报错，而是几周后每改一处都牵一大片。所以这一章的目标不是画一张漂亮架构图，而是让你学会用修改成本来判断边界是否合理。

## 先把依赖方向说死

对 `FocusList` 这条产品线，一条最基本也最有价值的规则就是：

```text
FocusListApp  --->  FocusCore
focusctl      --->  FocusCore
FocusCore     -/->  FocusListApp
```

只要你允许最后一条反向箭头出现，后面所有模块化收益都会被吃掉。因为一旦核心依赖 UI，它就再也不是稳定中心，只是换个名字的页面私货。

## 用“变化原因”划边界

判断某段代码该属于哪一层，一个非常实用的问题是：它为什么会变化？

- 因为产品规则变了？更可能属于 `FocusCore`。
- 因为页面布局或平台体验要调整？更可能属于 `FocusListApp`。
- 因为命令格式或终端输出要变？更可能属于 `focusctl`。

例如：

- “完成任务时是否允许自动归档”是产品规则。
- “macOS 侧栏图标用哪一个 SF Symbol”是平台表达。
- “CLI 输出要不要带状态前缀”是命令行表面。

把这些不同变化原因的代码塞进一个文件，后面维护一定会痛。

## 功能边界也存在于 App 内部

不要以为边界只发生在 target 之间。`FocusListApp` 自己也需要边界。一个实用布局可以是：

```text
FocusListApp/
  Root/
  Features/
    Inbox/
    Projects/
    Settings/
  SharedUI/
```

这里的判断很简单：

- 某个页面自己的状态和视图，放在对应 feature 下。
- 多个页面共用的纯展示组件，放在 `SharedUI/`。
- 页面之间共享的业务规则，不要偷放在 `SharedUI/`，而应该回到 `FocusCore`。

## 最容易犯的两个错

### 错误 1：为了“减少重复”把太多逻辑塞进共享组件

共享 UI 组件应该共享显示结构和交互协议，而不是把核心业务判断也藏进去。

### 错误 2：为了“核心更强大”把页面私有状态塞进 `FocusCore`

例如当前 sheet 是否打开、哪个 tab 被选中，这些都是 UI 暂态，不应该上升成共享依赖。

## 一次边界审计

拿一个真实动作来审查最有效，例如“编辑一条任务”：

1. 页面负责弹出编辑器和持有草稿。
2. 核心负责校验、更新和查询。
3. CLI 如果也支持编辑，只复用核心，不复用页面。

只要这三点里有一条说不清，功能边界就还没真的成立。

## 本章小结

边界设计的价值不是抽象看起来更高级，而是让以后每次修改都更可预测。真正的高阶工程判断，常常就体现在你有没有能力让依赖方向长期保持单向。
