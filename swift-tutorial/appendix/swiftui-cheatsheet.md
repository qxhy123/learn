# SwiftUI 速查

这份速查服务于 Part 5 与 Part 6，也会在 Part 8 做 capstone 时继续有用。它不试图替代 SwiftUI 文档，而是把本教程反复强调的那些“最容易写错、最值得反复检查”的状态、视图、数据流提醒压成一页。

## 第一原则

1. `View` 首先是状态描述，不是业务逻辑仓库。
2. 先分清状态拥有权，再决定用哪个 property wrapper。
3. UI 可以表达客户端差异，但不应重写共享领域规则。
4. 看不懂刷新问题时，优先检查 identity、ownership、observation，而不是乱加强制重建。

## 常见状态工具

| Tool | 什么时候用 | 不该怎么用 | 一句话判断 |
| --- | --- | --- | --- |
| `@State` | 当前 View 自己拥有的短期可变状态 | 用来保存整个 app 的共享真源 | “我拥有它，所以我负责改它。” |
| `@Binding` | 子 View 需要读写父层拥有的状态 | 把所有状态都暴露成双向绑定 | “我能改它，但我不拥有它。” |
| `@Observable` | 需要让模型变化驱动 View 刷新 | 把任何数据对象都先做成可观察模型 | “这是状态拥有者，而不是纯数据传输值。” |
| `ObservableObject` | 旧版或现有项目仍在使用的可观察模型模式 | 与新观察系统混成一团、概念不清 | “老模式仍可用，但要知道自己为何仍在用。” |
| `@Environment` | 少量、稳定、跨层共享上下文 | 把任意依赖都藏进环境，导致来源不明 | “这是广域上下文，不是万能全局变量。” |
| `@AppStorage` | 简单偏好值与用户设置 | 拿来替代完整持久化层 | “适合轻设置，不适合核心业务数据。” |

## State Ownership Checklist

每遇到一份状态，先问：

1. 谁创建它？
2. 谁拥有它？
3. 谁允许修改它？
4. 哪些 View 只是展示它？
5. 这个状态是 feature state，还是 app state？

只要这五个问题答不清，后面就很容易出现：

- 双向绑定泛滥
- 预览和真机逻辑分叉
- UI 刷新看似随机

## 常见数据流模式

### 模式 1：本地输入状态

适合：

- 文本框输入
- 开关切换
- 临时编辑草稿

推荐：

- 用 `@State` 保存临时值
- 在提交动作时才进入共享模型

不要：

- 一边输入一边无条件写回共享真源

### 模式 2：父拥有、子编辑

适合：

- 父视图维护筛选条件
- 子视图负责编辑和展示

推荐：

- 子视图拿 `Binding`

不要：

- 让子视图偷偷复制一份“看起来一样”的本地状态，除非你明确需要编辑缓冲

### 模式 3：共享模型驱动多个界面

适合：

- 任务列表
- 跨页面共享筛选
- 异步加载状态

推荐：

- 用一个清楚的 observable app model 或 feature model 持有真源

不要：

- 每个页面各维护一份平行事实

## View 拆分提醒

你应该拆 View，当且仅当：

- 它已经承担多个不同责任
- 它的输入 / 输出边界可以说清楚
- 拆出来后更容易预览、复用或测试

你不该拆 View，只因为：

- “组件化看起来更专业”
- 一个 `HStack` 也想变成独立文件
- 想把复杂度从一处搬到十处

## 列表与身份（identity）提醒

看到列表刷新异常时，优先检查：

1. 你的数据是否有稳定 identity
2. 你是否在不同层偷偷复制并替换了对象
3. 你是不是在试图用 `id(UUID())` 掩盖状态流问题

速记：

- identity 清楚，SwiftUI 才知道什么是“同一个项”
- identity 混乱，刷新就会看起来像随机

## 导航提醒

导航不是“从 A 页跳到 B 页”的命令式按钮表，而是状态的一部分。

设计时先问：

- 当前选择是什么？
- 当前路径是怎么得出的？
- 返回后，列表和详情读的是不是同一个真源？

如果你无法回答，就说明导航状态仍然漂着。

## Preview 提醒

Preview 的作用：

- 检查结构
- 检查状态组合
- 快速看布局和交互路径

Preview 不是：

- 真机替代品
- 平行实现
- “为了能显示，临时塞一套完全不同的依赖”

最稳做法：

- 用和运行时一致的 model / dependency 入口
- 只替换数据内容与依赖实现

## 异步 UI 提醒

异步工作要优先放进 model / store / coordinator，而不是直接塞进任意 View 闭包。

当你写 `.task`、`refreshable`、按钮动作时，先问：

- 这只是触发点，还是我正在把业务逻辑塞进视图？
- loading / success / failure 是否都回到了可观察状态？

## 常见症状与优先排查方向

| 症状 | 优先怀疑什么 | 第一反应不该是什么 |
| --- | --- | --- |
| 数据变了但界面没更新 | observation 或 identity 边界错了 | 乱加 `id(UUID())` |
| 输入框内容反复被覆盖 | 临时编辑态和共享真源混在一起 | 继续增加更多 binding |
| Preview 能跑、真机不对 | preview 依赖路径和运行时分叉 | 觉得“Xcode Preview 就是不准” |
| 两个页面数据不同步 | 没有 single source of truth | 给每页都加一个 store |
| View 代码越来越胖 | 业务逻辑与 UI 描述没有分开 | 一口气拆成十几个空组件 |

## Part 5 和 Part 6 的重点差别

Part 5 主要关心：

- SwiftUI 心智模型
- `@State` / `Binding`
- list / form / navigation 的最小闭环

Part 6 主要关心：

- app state
- persistence
- async UI updates
- preview / test double / app architecture

如果你在 Part 5 就想一次做完整架构，通常会学乱；如果到了 Part 6 还只会写局部状态，系统也长不起来。

## 最后一句速记

写 SwiftUI 时，遇事先问“这是谁的状态”，再问“这个 View 怎么画”。顺序反过来，系统很快就会开始漂。
