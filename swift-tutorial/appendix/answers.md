# 练习与综合实验答案

这份答案不是完整 solution dump。教程里的 drills 和 labs 设计，本来就是为了逼你自己做判断。如果把每题都写成标准代码答案，你最容易学到的反而是“怎样抄出看起来对的 Swift”，而不是“为什么这个设计在当前 part 合理”。因此这里给的是 selected guidance：关键思路、常见误区、最低合格标准，以及你应该能说出来的判断。

## 如何使用本页

- 先自己完成章节 drills 或 part-level lab。
- 卡住时先回头读本 part 的 `Project Handoff` 与项目 README。
- 只有在你已经写出一个版本、但不确定判断是否稳时，再看这里。

## Part 1 `TaskCLI Lite v1`

### 代表题：为什么 `Command` 应该先用 `enum`

合格答案应至少包含：

- `enum` 能让命令集合显式且有限。
- 相比散落在多个字符串判断里，`enum` 更容易集中解析错误。
- 这一步已经在建立“命令是数据”的直觉，为 Part 2 建模做准备。

常见弱答案：

- “因为 Swift 推荐 enum。”
- “因为以后方便扩展。”

这两句不算错，但没有说出本教程真正关心的点：**状态和分支必须先被命名清楚。**

### 代表题：为什么 Part 1 不直接上持久化

合格判断：

- 当前阶段主要验证语言闭环，而不是 I/O 工程化。
- 如果一开始把文件系统、错误恢复、异步写入都引进来，会稀释值语义、控制流、函数拆分这些基础主题。
- `TaskCLI Lite v1` 故意保持内存态，不是简化现实，而是控制教学顺序。

### Part 1 Lab 提示

如果你做 Part 1 lab 时发现：

- 所有逻辑都还堆在 `main.swift`
- `Optional` 被你用成“失败大口袋”
- `Task` 仍然只是字符串拼接产物

那说明你还停留在“脚本能跑”，没有真正进入“最小程序设计”。

## Part 2 `TaskCLI Lite` 建模强化阶段

### 代表题：为什么不先从 `class` 开始

最低合格答案：

- 任务记录首先更像值，而不是共享身份对象。
- 值语义让测试与状态推理更稳定。
- “以后可能会复杂”不是现在就选 `class` 的理由。

更强答案还会补充：

- 当一个类型的第一需求是“合法值 + 显式状态变化”，`struct` 更顺手。
- 如果未来真的出现共享身份压力，再转向 `class` 更诚实。

### 代表题：什么时候该引入 protocol

合格判断：

- 只有当变化点已经真实存在，而且抽象能隔离那个变化点时。
- 为了 mock、为了“更像架构”、为了不喜欢具体类型，这些都不是好理由。
- protocol 会压扁语义时，宁可先保持具体类型。

### Part 2 Lab 提示

如果你的错误类型最后都被重新压成 `Bool`，或 protocol 名字是 `TaskManagerProtocol` 这种双重空洞命名，说明你引入的是抽象外形，不是抽象判断。

## Part 3 `TaskCore + TaskCLI v1`

### 代表题：为什么测试要先锁 `TaskCore`

合格答案应指出：

- core behavior 的稳定性比 CLI 文本外观更关键。
- CLI 文本会变化，但领域 contract 不应轻易漂移。
- 如果先把大量精力花在 CLI 输出快照上，很容易忽略真正的行为边界。

### 代表题：为什么要拆成 `TaskCore + TaskCLI`

最低合格标准：

- `TaskCore` 负责领域模型和核心状态变换。
- `TaskCLI` 负责参数、命令、输出。
- 拆分不是为了文件好看，而是为了让依赖方向正确。

### Part 3 Lab 提示

你应该能在 1 分钟内说清楚任意一个类型为什么在 `TaskCore` 或 `TaskCLI`。如果你只能说“感觉放这里比较自然”，说明边界还没立住。

## Part 4 `TaskCore + TaskCLI` 运行时强化

### 代表题：什么时候该改成 `async`

合格判断：

- 只有真正触及挂起点、等待外部资源或异步边界时，才需要 `async`。
- 纯逻辑函数保持同步通常更清楚、更易测。
- “以后也许会异步”不是今天把整条调用链都改掉的理由。

### 代表题：为什么 actor 不是默认答案

答案至少要包括：

- actor 解决的是共享可变状态隔离，不是“所有并发代码都更高级”。
- 如果问题根本不是共享状态，而是错误建模、快照传播或 UI 读旧值，硬上 actor 可能只是在绕开真正问题。

### Part 4 Lab 提示

如果你能说出“取消发生时，系统在哪个状态点仍然保持一致”，说明你已经开始理解可靠性；如果你只能说“任务取消了，所以没事”，说明还不够。

## Part 5 `TaskFlow v1`

### 代表题：为什么 SwiftUI 不是“写页面”教程

合格判断：

- SwiftUI 的核心是状态到界面的声明式映射。
- View 不该偷偷拥有业务规则。
- `TaskFlow v1` 是 `TaskCore` 的 client，不是平行世界。

### 代表题：`@State` 和 `@Binding` 怎么区分

最低合格答案：

- `@State` 表示这个 View 拥有这份短期可变状态。
- `@Binding` 表示这个 View 能修改一份不由自己拥有的状态。
- 当你分不清拥有权时，通常已经在制造数据流混乱。

### Part 5 Lab 提示

如果你需要频繁用“强制刷新”技巧，通常不是 SwiftUI 的问题，而是 identity、observation 或 ownership 边界没想清楚。

## Part 6 `TaskFlow` 架构强化

### 代表题：什么叫 single source of truth

合格答案：

- 一份关键状态只有一个权威来源。
- 其他地方要么读它、要么映射它、要么绑定它，但不应各自维护平行事实。
- 在 `TaskFlow` 里，这通常直接决定 preview、test、持久化是否一致。

### 代表题：为什么 preview 不是“为了演示随便造一套数据”

更强判断：

- preview 应复用真实的状态入口方式和依赖表面。
- 它可以用 fake data，但不应绕开真实 contract。
- 否则 preview 和运行时会变成两套平行系统。

## Part 7 `Capstone` 预备重设计

### 代表题：什么时候该用 `any`，什么时候该用 `some`

合格答案的方向：

- 需要隐藏具体类型、且不关心其进一步静态关系时，`any` 可用。
- 想保留静态类型信息，但不想公开具体实现时，优先考虑 `some`。
- 如果这两个都让 API 更难懂，回到具体类型可能更强。

### 代表题：为什么 macro 不是架构工具

合格判断：

- macro 能消机械样板，不能替你做边界判断。
- 如果关键语义被生成物藏起来，调用虽然更短，理解却更弱。
- 教程里对 macro 的态度应是克制使用，而不是迟到的炫技补偿。

## Part 8 `Capstone`

### 代表题：Capstone 的 minimum success bar 应写什么

合格答案至少应可验证地覆盖：

- 核心 contract 清楚
- CLI 只是翻译层
- `TaskFlow` 不再补核心空白
- 关键失败面有验证
- 至少一条跨客户端场景闭环成立

不合格写法：

- “架构更优雅”
- “代码更现代”
- “体验更完整”

这些都太空，不能作为 capstone 成功标准。

### 代表题：为什么毕业路线图不是“继续学更多 API”

强答案应指出：

- 教程训练的是系统判断，不是 API 收藏。
- 下一步应按方向深入，例如并发、SwiftUI、系统 API、包设计，而不是跟热点乱跳。
- 真正的毕业不是“学完”，而是知道以后该怎样继续学。

## 最后提醒

如果你读这页时最失望的一点是“为什么不给标准代码答案”，那通常说明你现在最需要练的，正是本教程最想训练的能力：**在具体约束下做 Swift 判断，而不是记一份看起来正确的实现。**
