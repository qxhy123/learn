# 常见问题

## 为什么教程不从 `class` 开始

因为本教程默认读者已经会别的语言，而这些语言里很多会让你形成“对象 = 类”的起手式。Swift 不是不能用 `class`，但如果一开始就把所有模型写成引用类型，你会更难建立值语义、复制直觉、`mutating` 可见性、测试隔离这些 Swift 的核心判断。

更直接地说：任务记录在教程前中段首先更像值，不像共享身份对象。先从 `struct` 开始，不是为了政治正确，而是为了让默认建模更接近问题本身。

## 为什么教程不从 protocol 开始

因为 protocol 在 Swift 里很强，也很容易被滥用。很多初学者一旦知道 protocol 存在，就会把它当作“更工程化”的象征：先抽一个 protocol，再说后面怎么实现。本教程刻意反过来做：

- 先把具体模型和责任说清楚
- 再判断变化点是否真实存在
- 最后才决定是否需要抽象边界

如果协议先行，读者很容易学成“名词工程”，不知道抽象到底在隔离什么。

## 为什么 SwiftUI 要到 Part 5 才出现

因为 SwiftUI 不是独立王国。它建立在语言、建模、包边界、失败面和运行时判断之上。如果一开始就把 SwiftUI 当入口，很多人会学成：

- 会拼 View
- 会抄 property wrapper
- 不会解释状态拥有权
- 不会判断共享核心应该在哪里

本教程希望你先知道 Swift 工程本体是什么，再进入 SwiftUI。这样 `TaskFlow` 才是 `TaskCore` 的 client，而不是一门突然换题的新课。

## 为什么教程不一开始就用 `swift-argument-parser`

因为教程前半段的重点不是“最快做出一个更像真实工具的 CLI”，而是让你真正看懂命令解析、usage、错误翻译和入口责任。太早引入命令框架，会把很多本应亲手理解的表面藏进库约定里。

这不代表 `swift-argument-parser` 不好；只是它不该替代前期学习 CLI 语义的过程。

## 为什么教程一直强调 `TaskCLI Lite -> TaskCore + TaskCLI -> TaskFlow -> Capstone`

因为连续项目线能防止知识碎片化。每学一个新主题，你都能回答：

- 这个能力在改善项目的哪一段
- 当前项目为什么要在这里变化
- 这个变化如何通向下一阶段

如果每章都换一个 demo，你会更容易“这一章懂了，下一章重置”。本教程要避免的正是这种假熟练。

## 为什么 Part 3 才开始强调 SPM 和 package boundary

因为在此之前，你首先需要知道语言里的值、可变性、函数、模型、失败和抽象到底在表达什么。没有这些前置判断，package boundary 很容易退化成“目录拆分美学”。Part 3 才进入 SPM，是为了让边界有真实压力来源。

## 为什么教程仍然使用 XCTest，而不是直接转向 Swift Testing

原因有两个：

1. 教程当前项目表面已经围绕 XCTest 组织，继续使用它能保持前后连续。
2. XCTest 仍然是 Apple 平台工程里非常常见、非常真实的测试表面，尤其在性能测试、UI 测试与现有项目维护里仍然重要。

这不意味着 Swift Testing 不值得学，而是说本教程优先保证系统连续性。等你完成本教程，再去比较两套测试表面，会更有判断力。

## 为什么 SwiftUI 部分不顺手扩展到 server-side Swift

因为这会把教程目标打散。server-side Swift、Vapor、后端数据库、网络部署、认证授权，这些都是真问题，但它们属于另一条学习主线。如果在当前教程里硬加进去，会让原本围绕语言、CLI、core、SwiftUI、系统设计的主线失焦。

教程避免 server-side expansion，不是说它不重要，而是因为：

- 它需要不同的项目压力
- 它会引入不同的基础设施复杂度
- 它会模糊当前“共享核心 + 多客户端”这条主线

## 为什么高级 Swift 没有被写成“炫技专栏”

因为高级 Swift 真正难的不是记住更多语法，而是知道什么时候不用。`some`、`any`、associated type、type erasure、result builder、macro 都很强，但一旦脱离具体系统边界，只会快速扩大 API 表面和认知负担。

Part 7 的价值，不是让你觉得“我终于学到高级招式”，而是让你知道高级工具只有在服务 contract 和边界时才值得进入代码库。

## 为什么 capstone 不等于“把所有想法一次做完”

因为真正的毕业项目不是功能清单，而是系统收束。Part 8 最重要的是：

- 盘点现状
- 定义 minimum success bar
- 收紧共享 contract
- 统一 CLI / core / UI 语义
- 证明验证链闭环

如果 capstone 变成“想到什么就顺手加”，那你学到的还是 feature accumulation，不是系统判断。

## 我已经会一点 Swift，可以直接跳到 SwiftUI 或高级部分吗

可以跳读，但不建议跳过前四部分后再自信进入 Part 5 之后。更稳妥的办法是：

- 先读 `swift-tutorial/README.md` 的八部分地图
- 找出自己真正缺的是语言、建模、SPM、并发，还是 SwiftUI 心智模型
- 按缺口补读整 part，而不是只扫一个关键词章节

你会一点 Swift，不等于你已经有稳定的 Swift 判断。

## 教程为什么这么强调“中文负责解释，英文保留 API 和术语”

因为这样最利于长期迁移。纯中文翻译会丢掉社区和文档对接能力，纯英文又会让很多细微判断被匆匆略过。最稳的做法是：

- 中文解释概念、取舍、错误模式
- 英文保留类型名、协议名、命令名、framework 名

这样你既能在教程里真正想明白，也能回到官方文档和真实项目里继续工作。
