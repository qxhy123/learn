# 第 2 章：理解 View、状态与重新渲染

## 当前问题

很多初学者会把 SwiftUI 的 `View` 误解成一个会永久保存内部状态的对象，于是很容易在“我改了值，为什么界面没按我想的那样动”这里卡住。要继续写 `FocusList`，必须先建立正确的重新渲染直觉。

## 核心机制

`View` 更像一个随状态重新求值的描述，而不是命令式 UI 世界里的长期存活对象。`@State` 负责本地 UI 状态，`@Bindable` 则让可观察模型的字段能被表单、输入框和开关直接绑定。真正重要的不是记住所有包装器，而是判断：这份状态究竟属于当前界面，还是属于会被多个界面共享的产品模型。

## 在 FocusList 里的落点

在 `InboxView` 中，新增任务输入框的草稿文本属于局部 UI 状态，所以它留在 `View` 内部；任务列表本身属于产品状态，所以它来自 `FocusStore`。这个区分非常关键，因为它决定后面我们能否平稳地把 `FocusList` 长成一个产品，而不是让所有状态都挤在一起互相污染。

## 常见误区

一个常见误区是把所有东西都塞进 `@State`，结果局部状态和应用状态混成一团。另一个误区是刚接触可观察模型就试图引入更多包装层，用新名词掩盖状态放错地方的事实。状态设计的第一原则不是“显得高级”，而是“谁拥有它、谁改变它、谁依赖它”能否说清楚。

## 本章小结

这一章的核心不是包装器列表，而是重新渲染和所有权直觉。只要你能稳定地区分局部 UI 状态与共享产品状态，`FocusList` 后面的数据流和边界设计就会容易很多。
