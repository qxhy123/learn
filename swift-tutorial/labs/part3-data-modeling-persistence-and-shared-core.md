# Part 3 Lab：整理模型、存储与 FocusCore 边界

## 场景

Part 3 之后，`FocusList` 已经不再只是前端界面练习。你现在要面对的是更真实的数据问题：模型是否站稳、哪些状态应该持久化、失败时用户是否还能继续工作，以及 `FocusCore` 为什么必须在这个阶段出现。

## 开始前检查

在 starter 里重新跑一次：

```bash
cd swift-tutorial/projects/focuslist/starter
swift test
swift run focusctl
```

确保你当前的共享核心和 CLI 基线都还正常。

## 任务一：找出一条已经该进入 FocusCore 的规则

在 App 代码里挑一处仍然散落在页面层、但已经明显会被多个表面复用的规则。例如：

- 任务标题校验
- 查询筛选规则
- 编辑提交时的字段清洗

把它移动到 `FocusCore`，并写下理由：为什么它现在已经不是某个页面的私有细节。

## 任务二：设计一次持久化失败后的恢复路径

选一个具体场景，例如“编辑任务后保存失败”。给出一条完整路径：

1. 页面如何保留草稿
2. 存储边界如何上抛错误
3. 用户看到什么反馈
4. 用户如何继续完成原本动作

### 验收点

- 失败不会被误报成正常空状态
- 草稿不会因为失败而丢失
- 你能说清哪个层负责反馈，哪个层负责存储

## 任务三：划清持久化状态与交互状态

把当前系统里的状态分成两列：

- 应该持久化的
- 只属于当前会话或当前页面的

至少列出六项，再解释两项最容易搞混的边界。例如：

- 搜索词通常不该持久化
- 任务标题、项目归属和完成状态通常应该持久化

## 通过标准

这次 lab 只有在下面三点都成立时才算完成：

- 你能指出 `FocusCore` 为什么现在才出现，而不是更早
- 你给出了一条具体失败场景的恢复路径
- 你能清楚区分模型、存储边界和页面交互状态
