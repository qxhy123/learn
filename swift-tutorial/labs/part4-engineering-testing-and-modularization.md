# Part 4 Lab：把产品推进成真正的代码库

## 场景

Part 4 的主线不是“继续堆功能”，而是把已经有的产品能力压进更可靠的工程结构里。这个 lab 会同时检查三件事：你的测试是不是在锁定行为，你的依赖方向是不是清楚，以及 `focusctl` 是否真的是共享核心的第二表面。

## 任务一：先写一条失败测试，再补最小实现

挑一个当前还没被测试保护、但很容易在重构时被改坏的规则，例如：

- 空白标题不能新增
- 未知任务 ID 不会改坏状态
- 项目查询只返回该项目任务

先写失败测试，再补最小实现让它通过。

### 验收点

- 测试名描述的是行为，不是内部实现
- 实现变化后，这条行为仍应成立
- 你能解释为什么这条测试值得优先写

## 任务二：找一段代码，把它放回正确 target

在 `FocusListApp` 和 `FocusCore` 之间做一次边界归位：

- 如果某段规则已经明显属于共享核心，把它移入 `FocusCore`
- 如果某段 UI 暂态被错误塞进核心，把它移回 App

重点不是“移动文件”，而是解释它为什么应该和哪一层一起变化。

## 任务三：扩展 `focusctl`，但不复制业务逻辑

给 CLI 加一个小能力，例如：

- 输出任务总数
- 支持只列出未完成任务
- 增加一个简单命令参数

实现时必须复用 `FocusCore`，不能在 `focusctl` 里重写任务查询或校验逻辑。

## 通过标准

只有同时满足这三点，这次 lab 才算完成：

- 你的测试锁定了真实行为
- 你能解释当前依赖方向和边界归位理由
- CLI 的新增能力建立在共享核心之上，而不是复制业务逻辑
