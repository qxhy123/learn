# Part 4 综合实验：把 `TaskCore + TaskCLI` 从能跑推到可信

## 对应部分与项目阶段

- 对应部分：Part 4 `part4-concurrency-performance-and-reliability`
- 对应项目阶段：`TaskCore + TaskCLI` 运行时强化阶段
- 关联章节：第 16 章到第 20 章

Part 4 不是为了“终于上高级特性”。它真正解决的问题是：当系统开始接触异步、取消、共享状态、复制成本、内存与失败面时，你还能不能说清楚代码为什么安全、为什么脆、为什么当前选择合理。这份 lab 的目标，是让你真正拥有 runtime judgment，而不是只会写 `async` 关键字。

## 使用方式

建议把每个任务都当成一次运行时事故演练。遇到一个问题时，不要先问“怎么写更炫”，而要先问：

1. 状态在哪里被拥有？
2. 并发边界在哪里被收紧？
3. 失败会怎样传播？
4. 取消会不会让系统停在半截？

## Integrated Exercises

### 综合练习 1：把核心操作改造成可异步但可解释的流程

挑一个最适合异步化的路径，例如：

- 从磁盘读写任务
- 批量导入
- 外部同步占位接口

要求：

- 用 `async` / `await` 改写调用链。
- 明确区分同步纯逻辑与异步边界。
- 保留清楚的错误语义，不要把所有失败都压成 `nil` 或 `print`。

写一段说明：

- 为什么不是“所有函数都改成 async”。
- 哪些函数在 Part 4 仍然应保持同步纯函数。

### 综合练习 2：为共享可变状态建立隔离策略

请选择一种真实风险场景，例如：

- 同时有两个命令尝试更新任务存储
- 一个后台刷新和一个前台完成操作并发发生

然后设计你的隔离策略。可以是 actor，也可以是更小范围的串行边界，但必须解释：

- 为什么这个位置需要隔离
- 为什么这个位置不该继续裸露可变共享状态
- `Sendable` / isolation 在这里帮你防住了什么

### 综合练习 3：给可靠性写出“可取消、可恢复、可验证”的路径

挑一条异步命令链，补齐下面三件事：

- 用户取消时系统如何停止
- 中途失败时状态如何保持一致
- 测试如何证明这条路径没有悄悄吞掉失败

请输出一张简单表格：`Event` / `Expected Behavior` / `Verification`.

## Debugging Tasks

### 调试任务 1：并发写入导致任务列表丢更新

症状：

- A 命令完成任务
- B 命令几乎同时新增任务
- 最终结果只保留其中一方

你的任务：

- 判断这是数据竞争、隔离缺失，还是“最后写入覆盖前写入”。
- 说明为什么“偶现”不等于“可以忽略”。
- 给出一个最小可解释修法，而不是立刻把整个系统改成全 actor 宫殿。

### 调试任务 2：异步 API 成功了，但 UI / CLI 读到旧状态

弱代码常见于：

- 更新发生在后台，但展示层读的是旧快照
- mutable state 被复制了多份，但作者没意识到

你需要解释：

- 这是 isolation 问题、snapshot 问题，还是 ownership 问题。
- 你会怎样把“读什么、改什么、谁负责发新值”写清楚。

## Refactoring / Design Tasks

### 设计任务 1：给失败面做一次运行时分层

把你当前系统的失败分成三层：

- 领域失败（domain failure）
- I/O 或系统失败（system failure）
- 用户可见失败（user-facing failure）

然后说明：

- 哪一层该在 `TaskCore` 命名
- 哪一层该在 `TaskCLI` 翻译
- 哪一层不该直接泄漏给最终用户

### 设计任务 2：做一次“性能不是玄学”的最小审查

请挑两段你怀疑可能有复制成本或不必要内存压力的代码，例如：

- 大数组频繁拷贝
- 字符串反复拼接
- 为了“安全”到处 `map` 新数组

你不需要做花哨 benchmark，但要写出：

- 你怀疑的成本点是什么
- 你准备用什么最小测量方式验证
- 如果没有数据支持，为什么不该先做激进优化

## Challenge Tasks

### 挑战 1：为批量导入加入可取消进度流

设计一个 API，让调用方能：

- 启动导入
- 观察进度
- 在中途取消
- 在完成或失败后得到明确结果

可以考虑 `AsyncSequence`、回调桥接，或更简单的事件流，但一定要解释为何这个选择适合当前项目规模。

### 挑战 2：为运行时加一条“慢路径”测试

构造一个故意慢、故意易失败的依赖替身，验证：

- 超时 / 取消时系统是否保持一致
- 错误是否仍能被正确翻译
- 测试是否会因为并发调度差异变成脆弱快照

## 退出标准

完成这份 lab 后，你至少应能说明：

- 为什么 Part 4 的项目名仍然是 `TaskCore + TaskCLI`，但系统已经不再只是 package engineering。
- 为什么并发、性能、可靠性不是三张独立清单，而是共享状态设计的三个侧面。
- 为什么一个 runtime upgrade 应首先收紧 contract，而不是只增加并发语法。

## 复盘问题

1. 你哪里最容易把“能异步”误当成“应该异步”？
2. 你的取消语义是显式 contract，还是碰巧没崩？
3. 如果 `TaskFlow` 要复用当前核心，你现在哪些 runtime 承诺已经足够稳，哪些还不够？
