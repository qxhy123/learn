# Part 5 综合实验：让 `TaskFlow v1` 像一个 SwiftUI 客户端，而不是会动的截图

## 对应部分与项目阶段

- 对应部分：Part 5 `part5-swiftui-foundations`
- 对应项目阶段：`TaskFlow v1`
- 关联章节：第 21 章到第 24 章

Part 5 把你带进 SwiftUI，但顺序是刻意晚的。因为如果没有前四部分的语言、建模、包边界和运行时判断，SwiftUI 很容易被误学成“声明式语法 + 组件拼装”。这份 lab 的目标，是让你把 `TaskFlow v1` 建成一个真正站在共享任务核心之上的客户端，而不是把 UI 当成新的业务起点。

## 使用方式

做这份 lab 时，请强迫自己反复回答：

1. 这个 View 描述的是状态，还是在偷偷持有业务逻辑？
2. 这个 `@State` / `@Binding` / observable model 的拥有权是否清楚？
3. 这个 `TaskFlow v1` 真的是 `TaskCore` 的 client 吗？

## Integrated Exercises

### 综合练习 1：把 `TaskFlow v1` 的主界面收束成清楚的状态图

设计一个最小主界面，至少包含：

- 任务列表
- 新增任务入口
- 标记完成动作
- 空态（empty state）或无数据提示

要求：

- 用最少但清楚的状态驱动界面变化。
- 让 View 自己只描述显示，不负责定义任务规则。
- 写出一段解释：为什么 `TaskFlow v1` 的首要目标是建立 SwiftUI 心智模型，而不是立刻做大 app。

### 综合练习 2：把输入链路做成真正的 binding 流

请实现一个新增任务流程，明确区分：

- 临时输入状态
- 提交动作
- 提交后的清理或错误展示

要求：

- 使用 `@State` 存输入，使用 `Binding` 传递必要编辑能力。
- 不要把整个 store 无脑下传给每个子 View。
- 如果你用了 `@Observable` 或 `ObservableObject`，要说明它拥有的到底是 feature state 还是 app state。

### 综合练习 3：用列表、表单与导航建立一条最小完整交互

你至少需要让用户能：

- 看列表
- 点进详情或编辑页
- 在表单里修改状态
- 返回后看到一致结果

这个练习的重点不是页面数量，而是验证：

- 状态流是否单向可解释
- 导航是否围绕任务语义，而不是围绕随机页面跳转

## Debugging Tasks

### 调试任务 1：列表更新了，子视图却没刷新

常见症状：

- 父视图数据变了
- 子视图还显示旧值
- 作者开始乱加 `id(UUID())` 强迫刷新

你的任务：

- 解释问题是 identity、state ownership 还是 observation 边界错误。
- 指出为什么“强制重建 View”通常是在掩盖数据流问题。
- 给出一个更强修法，强调数据从哪来、谁负责变更、谁负责观察。

### 调试任务 2：表单输入一边打字一边被覆盖

典型原因：

- 表单直接绑定到会在外部刷新重置的源数据
- View model 在不合适时机回写值

请说明：

- 为什么编辑态经常需要临时本地 state。
- 为什么不是所有字段都该双向直接绑到共享模型。

## Refactoring / Design Tasks

### 设计任务 1：拆出真正的 View 边界

请审查你的 `TaskFlow v1`，把过大的根视图按职责拆开，例如：

- list section
- row view
- editor form
- empty / error / loading view

但请同时克制：

- 不要因为“组件化看起来高级”而把一个简单 `HStack` 也拆成单独文件。
- 每次拆分都要回答：这个 View 的输入是什么，输出或副作用是什么。

### 设计任务 2：写一份状态拥有权清单

为主要状态写一张表：

`State` / `Owner` / `Reason`

至少覆盖：

- 当前任务数组
- 当前筛选条件
- 新任务标题输入
- 当前导航选择
- 当前错误提示

## Challenge Tasks

### 挑战 1：为 `TaskFlow v1` 增加筛选条

支持：

- all
- pending
- done

要求：

- UI 切换不要复制三份列表逻辑。
- 筛选条件的位置要合理，不要随手塞进最顶层所有 View。
- 写出说明：为什么这个功能一加，就开始暴露 Part 6 的 app data flow 问题。

### 挑战 2：做一个“看似小、实则考验心智模型”的批量完成按钮

功能：一键把当前筛选结果标记为完成。

你需要判断：

- 这个动作是 View 层行为，还是共享核心动作？
- UI 应怎样反馈结果而不把业务逻辑藏在按钮闭包里？
- 如果未来要接异步持久化，这个表面是否还站得住？

## 退出标准

做完这份 lab 后，你应该能明确说出：

- 为什么 Part 5 的项目阶段名是 `TaskFlow v1`。
- 为什么 SwiftUI View 首先是状态描述，不是业务逻辑容器。
- 为什么现在最重要的是 state / binding / navigation 的可解释性，而不是 UI 花样。
