# Part 2 Lab：把 FocusList 做得更像产品

## 场景

经过 Part 2 的正文后，`FocusList` 已经不再只是一个最小任务列表。它开始拥有项目、标签、编辑流、筛选和搜索。但也正因为这样，系统很容易滑向另一个极端：页面越来越多，结构却越来越模糊。这个 lab 的目的，就是强迫你把“功能增长”重新收束成“产品结构”。

## 开始前检查

先在 starter 上确认当前基线可用：

```bash
cd swift-tutorial/projects/focuslist/starter
swift test
swift build --product FocusListApp
```

## 任务一：抽一个真正值得复用的任务行

从 `Inbox` 和项目详情入口里挑出重复的任务展示骨架，抽成一个 `TaskRow`。它至少应该能表达：

- 完成状态
- 标题
- 项目或标签摘要

但它不应该偷偷拥有全局状态，也不应该自己决定保存或删除规则。

### 验收点

- 调用方仍然清楚知道点击后会触发什么行为
- 抽出后条件分支没有比原来更多
- 你能解释它为什么属于复用 UI，而不是共享业务逻辑

## 任务二：修正一次搜索或筛选状态放错位置的问题

在当前实现里挑一个状态做归位：

- 如果它只对当前页面有效，却被错误升成共享状态，把它降回局部。
- 如果它需要跨入口保留，却被错误塞在局部 `@State`，把它提到更高层。

### 你要回答的问题

- 这个状态在用户心智里是临时输入，还是产品视角？
- 它切换页面后是否应该保留？
- 它是否影响共享规则，还是只影响当前页面阅读方式？

## 任务三：做一次产品一致性审计

从用户视角完整走一遍：

1. 从侧栏进入 `Inbox`
2. 搜索某条任务
3. 进入编辑流
4. 保存后切到 `Projects`
5. 再返回原入口

把过程中发现的两个产品结构问题写下来，例如：

- 某个入口像临时补丁
- 某个空状态讲不清当前视角
- 某个筛选条件保留或丢失得不合理

## 通过标准

这次 lab 只有同时满足下面条件才算通过：

- 组件抽取减少重复，没有制造更深耦合
- 你能清楚解释搜索/筛选状态的所有权
- 你能指出 `FocusList` 目前仍然不像成品的两个地方，并给出下一步整理方向
