# Labs：分部综合实验

## labs 不是“课后题”，而是整合训练

章节正文会帮你看懂某一个局部能力，例如状态所有权、查询边界、测试策略或者并发取消。labs 的作用更接近真实工程：把几个能力同时压到你面前，逼你在一个连续工作流里做判断。

所以做 lab 时，最重要的不是“最终能跑”，而是你能不能同时解释：

- 这份状态为什么放在这里
- 这个失败为什么要由这一层解释
- 这个组件为什么值得抽，或者为什么不该抽
- 这个入口和整个产品地图是什么关系

## 推荐做法

每个 Part 结束后，按这个顺序推进：

1. 先回顾对应 Part 的章节目标。
2. 在 `projects/focuslist/starter/` 上亲手改代码。
3. 用 checkpoint 文档检查当前阶段目标是否真的达成。
4. 最后再看 appendix 里的速查和答案索引。

如果你先看答案，lab 的价值会直接减半。因为这些实验最重要的部分就是你亲自做边界判断。

## 每个 lab 都应该留下什么

建议你至少保留三类产物：

- 一次真实代码改动
- 一段对状态/边界/失败面的解释
- 一份手动验证记录

这样你复盘时看到的就不只是结果，而是判断过程。

## 做到什么程度才算通过

每个 lab 的最低通过线都一样：

1. 代码层面完成了要求的改动。
2. 你能解释为什么这份改动比至少一个替代方案更合适。
3. 你能说明这份改动怎样改变了 `FocusList` 的产品体验或工程稳定性。

如果只做出了“看起来能工作”的版本，却解释不清边界和代价，那次实验就还没真正完成。
