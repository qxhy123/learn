# Part 2 综合实验：把 `TaskCLI Lite` 推到可建模的边缘

## 对应部分与项目阶段

- 对应部分：Part 2 `part2-type-system-and-modeling`
- 对应项目阶段：`TaskCLI Lite` 建模强化阶段，目标是为 `TaskCore + TaskCLI` 做迁移准备
- 关联章节：第 6 章到第 10 章

Part 2 的关键，不是学会更多关键字，而是从“能写几段 Swift”跨到“能判断一种建模是否稳”。所以这份 lab 不要求你直接做成 `TaskCore + TaskCLI`，而要求你把 `TaskCLI Lite` 推到一个诚实的边界：它还能继续长，但哪些责任已经必须重新命名、重新切边界，你应该看得很清楚。

## 使用方式

完成这份 lab 时，请一直记住一句话：**Part 2 还在训练建模判断，不是在奖励你滥用抽象。**

做题时请优先回答三个问题：

1. 这个状态应该是谁拥有？
2. 这个失败应该怎样命名？
3. 这个抽象到底在隔离变化，还是只是在制造名词？

## Integrated Exercises

### 综合练习 1：把任务模型从“字段容器”升级为有语义的值

把你的 `Task` 从单纯字段集合升级到更强版本：

- 有明确初始化器，拒绝空标题或全空白标题。
- 有能表达业务意图的方法，例如 `markDone()`、`rename(to:)`。
- 至少有一个 computed property，用来表达对外可读语义，而不是技术细节。

写出你的判断：

- 哪些规则应该放在 `Task` 里，哪些不该。
- 为什么“有方法”不等于“应该改成 `class`”。
- 你的初始化器是在建立合法值，还是在替后续逻辑补洞。

### 综合练习 2：为命令执行建立最小失败模型

请定义一个 `enum` 失败类型，例如 `TaskCLIError` 或 `TaskStoreError`，覆盖至少这些场景：

- 重复添加任务
- 找不到要完成的任务
- 标题非法
- 命令参数不合法

然后完成两件事：

- 让核心操作通过 `throws` 或 `Result` 之一表达失败。
- 写一段说明：为什么这里的重点不是“两个都用”，而是根据调用链选择一个更合适的表面。

### 综合练习 3：为变化点画边界，但不要先抽象一切

给系统加入一个“渲染”变化点，例如终端输出、测试用字符串输出、未来 UI 展示。

要求：

- 先写出一个具体类型，再判断是否真的需要 protocol。
- 如果你决定引入 protocol，要明确这个 protocol 隔离的变化是什么。
- 如果你决定不引入 protocol，也要说明为什么当前还不值得。

## Debugging Tasks

### 调试任务 1：引用共享导致测试互相污染

假设有人把 `Task` 或 `TaskStore` 改成 `class`，测试里出现这种现象：

- 测试 A 改过的状态，会影响测试 B。
- 两个变量看似各自持有数据，实际指向同一实例。

你需要完成：

- 解释这是值语义 / 引用语义问题，而不是“XCTest 不稳定”。
- 说明在当前任务领域里，哪些类型更应保持 `struct`。
- 只有当你真的认为某个类型该是 `class` 时，才给出理由。

### 调试任务 2：协议抽象让错误类型消失

观察一个弱设计：

```swift
protocol TaskManaging {
    func add(_ title: String) -> Bool
}
```

问题是：原本清楚的失败原因全被压成 `Bool`。

你的任务：

- 指出这个 protocol 为什么让语义变弱。
- 给出更强版本，可能是 `throws`、`Result`，或先不用 protocol。
- 说明“为了 mock 而抽 protocol”为什么在 Part 2 很容易把设计带偏。

## Refactoring / Design Tasks

### 设计任务 1：把“TaskManager”式命名清理成领域语言

如果你代码里已经出现这些名字，请重命名并解释：

- `TaskManager`
- `TaskHelper`
- `TaskProcessor`
- `TaskProtocol`

要求：

- 名字要体现责任，不要体现模糊权力。
- 删除无意义中间层优先于新增抽象层。
- 写出一段简短说明：你的命名变化如何帮助 Part 3 未来拆出 `TaskCore`。

### 设计任务 2：为 Part 3 预演模块边界

现在还不真正改 package，只做纸面设计：

- 哪些类型未来应进入 `TaskCore`
- 哪些逻辑应留在 CLI 入口
- 哪些失败类型应由 core 暴露，哪些由 CLI 翻译

请把结果写成一个三栏表：`Name` / `Belongs To` / `Why`。

## Challenge Tasks

### 挑战 1：为过滤与排序设计可增长 API

增加如下需求，但不要做过度框架化：

- 查看 only done
- 查看 only pending
- 按标题排序

要求：

- 尝试用泛型或策略型 API，但只在它真的减少重复时才用。
- 明确说明为什么这里不需要 `Any` 驱动的“万能过滤器”。
- 如果你引入 protocol with associated type，要解释它到底让什么关系变清楚了。

### 挑战 2：设计一个“批量导入”接口

输入是一组标题字符串，输出是“成功导入的任务 + 失败原因”。

这个练习的重点不在 I/O，而在：

- `throws` 不一定适合批量部分成功场景
- `Result` 也不一定要包住一整个数组
- 你如何设计返回值，才能把失败当作值而不是当作日志

## 退出标准

做完这份 lab，你应该能清楚回答：

- 为什么 Part 2 还不急着先上 `class`、先上 protocol、先上“大架构”。
- 为什么 `TaskCLI Lite` 在这个阶段最需要的是建模强度，而不是功能数量。
- 为什么下一步自然会走向 `TaskCore + TaskCLI`，而不是继续在 executable 里硬撑。

## 复盘问题

2. 你的错误类型是在帮助调用者判断，还是只是在换一种方式打印字符串？
3. 如果明天开始 Part 3，你会先拆哪条边界，为什么不是别的边界？
