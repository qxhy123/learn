# 第 21 章：重构功能图谱

## 收尾阶段最危险的，不是缺功能，而是历史负担

教程做到最后，系统通常会留下两类东西：

- 早期为了推进学习而接受的临时写法
- 中期为了功能增长而产生的重复和过宽边界

如果你直接带着这些东西去做发布准备，系统会看起来“什么都有”，但一继续改就会痛。所以 Capstone 第一章不是继续加功能，而是重新绘制当前系统的功能图谱。

## 什么叫功能图谱

这里说的不是 PRD 列表，而是当前系统里这些关系：

- 哪些入口是一级产品结构
- 哪些功能依赖共享核心
- 哪些页面只是某条工作流的辅助面
- 哪些状态链路已经宽到不容易解释

只要这张图谱你自己都说不清，后面的收尾动作就只会变成局部修修补补。

## 先用“删不删得掉”判断价值

一个很有效的重构问题是：如果我删掉这段结构，系统会损失什么？

- 如果答案是“损失一个清楚的产品能力”，说明它有价值。
- 如果答案是“只是历史上为了图省事留下的中间层”，那它很可能该收掉。

例如，一个只转发参数却不增加语义的 wrapper view，往往就是可以删掉的复杂度；而一个把项目任务查询统一封装的边界，则通常值得保留。

## 重构顺序要从最难解释的地方开始

别随机挑文件修。一个更稳的顺序是：

1. 最难解释的状态链路
2. 最胖的 `View`
3. 散落在页面里的共享规则
4. 已经没有用户价值的入口或组件

按这个顺序做，收益最大，因为你先解决的是系统里最影响理解的部分。

## 这一步通常不是“加层”，而是“收层”

Capstone 阶段的好重构，经常表现为这些动作：

- 删除重复 helper
- 把页面内复制的查询归回核心
- 缩小状态拥有范围
- 给入口重新命名或重新归组

如果你在这里又不断发明新协议、新容器、新管理器，通常是在把旧复杂度换成新复杂度。

## 一次功能图谱审计

拿 `Inbox` 到 `Project Detail` 再到 `Task Editor` 这条路径做检查：

1. 哪一层持有了真正需要共享的状态？
2. 哪些页面只是展示同一套核心规则？
3. 有没有只为中转而存在的视图或模型？
4. 有没有已经不再属于一级导航的入口还占着显眼位置？

把这些问题答一遍，你会很快知道该删什么、该收什么。

## 本章小结

重构功能图谱的目的不是让代码显得更优雅，而是让产品结构和工程结构重新变得容易解释。一个能持续维护的系统，结尾阶段通常都要经历这一步。
