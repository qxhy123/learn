# 第 22 章：加固测试、预览与无障碍

## 这三件事决定“能做”能不能变成“能交付”

开发者最容易在最后阶段犯的错，就是继续沉迷新功能，而忽略三个真正影响交付质量的面：

- 测试是否保护了关键行为
- 预览是否让你能快速看见复杂状态
- 无障碍是否让产品对不同用户都可用

它们不会直接让功能表变长，但它们决定现有功能能不能被放心保留。

## 先把测试补到真正危险的地方

Capstone 阶段不需要把所有东西都测成白盒。更有效的做法是把测试补到这些位置：

- 核心规则最容易被重构破坏的地方
- 失败路径最容易被忽略的地方
- 批量操作和边界输入

这类测试的价值，比再多十条“正常路径只是跑了一遍”的测试高得多。

## 用 Preview 把复杂状态显出来

对 SwiftUI 来说，Preview 最有价值的时刻不是展示“正常列表”，而是快速检查那些真实用户经常遇到、但你平时不想每次手动构造的状态：

```swift
#Preview("Empty Inbox") {
    InboxView(store: .emptyState)
}

#Preview("Search Results") {
    InboxView(store: .searchHeavySample)
}
```

你真正要训练的是：每当某个界面需要经常手动构造才能观察，就应该考虑给它一个专门 Preview。

## 无障碍不是“最后加几个 label”

在 `FocusList` 里，至少要检查：

- 完成按钮是不是只有图标，没有可读名称
- 标签和项目摘要会不会被 VoiceOver 读成一串噪音
- 空状态、错误提示和成功反馈是否都能被辅助技术感知

例如，一个任务行至少应该像这样补充语义：

```swift
Image(systemName: task.isDone ? "checkmark.circle.fill" : "circle")
    .accessibilityLabel(task.isDone ? "Completed task" : "Incomplete task")
```

这不是“锦上添花”，而是让产品不只服务于鼠标和手指操作。

## 一次质量加固清单

完成这一章后，逐项检查：

1. 关键共享规则是否有行为测试。
2. 复杂 UI 状态是否有可复用 Preview。
3. 图标按钮、状态提示、空状态是否都有清楚可读语义。

如果这三项中你只做了第一项，产品仍然只是“对开发者友好”，还谈不上真正完成。

## 本章小结

测试、Preview 和无障碍对应的是三种成熟度：敢改、看得见、用得上。能把这三条一起补稳，才说明你已经开始从“会做功能”切到“会交付产品”。
