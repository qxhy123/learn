# 第 23 章：为发布准备 FocusList

## 发布准备是一次系统视角的回头看

到了这一章，最不该做的事情就是继续埋头加功能。发布前真正要完成的是一次系统检查：这个产品在正常路径、异常路径、首次启动、双平台表达和长期维护上，是否都已经说得通。

这也是区分“能写功能”和“能带产品交付”的地方。

## 先跑一份发布前检查单

对 `FocusList` 来说，一份够用的检查单至少包括：

- 首次启动路径是否清楚
- 默认数据或空状态是否可理解
- 搜索、筛选、编辑、批量操作是否都有清楚反馈
- 失败后是否能恢复，而不是把用户扔回起点
- `iOS` 和 `macOS` 是否都像各自平台上的自然应用

这份清单的作用不是一次性消灭所有问题，而是逼你从“最近在写哪段代码”切到“用户今天第一次打开会看到什么”。

## 把验证命令收成稳定流程

发布前不要靠记忆力。至少把这类命令重新跑一遍：

```bash
bash swift-tutorial/scripts/verify_layout.sh
bash swift-tutorial/scripts/verify_parts.sh
bash swift-tutorial/scripts/verify_projects.sh
bash swift-tutorial/scripts/verify_appendix.sh
bash swift-tutorial/scripts/verify_focuslist_starter.sh
bash swift-tutorial/scripts/verify_focuscore_focusctl.sh
```

这里的意义不是“显得严谨”，而是让发布准备从主观感觉变成客观证据。

## 别忽略那些看起来“不算功能”的细节

发布前最容易漏掉的通常不是大逻辑，而是这些：

- 危险操作有没有足够明确的反馈
- 设置默认值是否一致
- 空状态文案是不是仍然贴合当前产品
- CLI 和 App 是否都反映同一套规则

这些问题单看都不大，但聚在一起就会严重影响成品感。

## 一次最后的路径演练

请按真实用户流程走一遍：

1. 首次进入应用。
2. 新建一条任务并归入项目。
3. 搜索它、编辑它、完成它。
4. 触发一次可恢复的失败。
5. 切换到另一平台重复一遍核心路径。

如果这条流程里还有明显让你停下来解释“这里其实是因为内部实现这样”的地方，就说明产品还没准备好交付。

## 本章小结

发布准备不是装饰层，而是一次系统级复盘。你越能在这个阶段用产品和工程双重视角重新看系统，越接近真正的高阶工程师状态。
