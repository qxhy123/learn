# 第 7 章：加入筛选、搜索与界面组织

## 当前问题

当任务、项目和标签都开始出现之后，用户不再只需要“看全部”，而需要更快地定位关注点。筛选和搜索看起来像高级功能，但它们其实是信息结构是否健康的直接压力测试。

## 核心机制

筛选和搜索不只是多一个输入框。它们会逼你重新思考：哪些状态是临时查询状态，哪些是可分享的产品状态，哪些入口应该留在侧栏，哪些应该是页面内局部交互。换句话说，这一章真正讲的是界面组织，而不只是搜索 API。

## 在 FocusList 里的落点

`FocusList` 在这一阶段开始从“几个页面”变成“有主次、有入口层级的产品”。搜索和筛选必须嵌入已有导航结构，而不是像插件一样粘在某个角落。这样做的结果，是用户能按自己的注意力切换视角，而开发者也能看见未来的查询和持久化压力。

## 常见误区

最容易犯的错是把搜索和筛选都做成局部 View 的私有状态，结果一换页面条件就丢。反过来，把所有查询条件都升成全局状态也会让产品异常笨重。判断标准始终是：这份状态需要谁共享，能否被解释，切换上下文时是否应该保留。

## 本章小结

当搜索和筛选被正确放进产品结构后，`FocusList` 才真正拥有了“用户可以主动组织注意力”的能力。这一步也在提前暴露后面一定会碰到的查询与持久化问题。
