# 第 20 章：打磨 iOS 与 macOS 体验

## 跨平台真正难的是“同一个产品，不同的表达”

很多“跨平台”教程最后会停留在一句空话：一份代码跑两个平台。真实产品远不止这个层次。`iOS` 与 `macOS` 的共同点，应该集中在模型、规则和产品目标；它们的差异，则集中在交互节奏、信息密度和输入方式。

如果你强迫两边界面完全一样，最后通常不是统一，而是双输。

## 先明确哪些东西必须共享

对 `FocusList` 来说，应该尽量共享的是：

- `FocusCore` 的模型和规则
- 查询与筛选语义
- 任务完成、编辑、搜索这些产品能力本身

而更适合按平台调整的是：

- 导航方式
- Toolbar 布局
- 快捷操作入口
- 列表密度与空白留白

这意味着跨平台设计不是“复制页面”，而是“共享产品中心，分化表达层”。

## 用导航差异举最直接的例子

同样是浏览任务：

- 在 `macOS` 上，分栏和常驻侧栏通常更自然。
- 在 `iOS` 上，推进式导航和更聚焦的单列阅读通常更顺手。

因此你可能会写出类似这种平台化入口：

```swift
#if os(macOS)
NavigationSplitView {
    SidebarView(store: store)
} detail: {
    DetailView(store: store)
}
#else
NavigationStack {
    InboxView(store: store)
}
#endif
```

这里的重点不是条件编译本身，而是你已经承认：平台差异是真实存在的，应该在表达层处理，而不是硬压回共享核心。

## 平台打磨不仅是导航

还要继续看这些细节：

- `macOS` 是否提供键盘快捷键、右键菜单、更多信息密度。
- `iOS` 是否减少视觉噪音、保证单手操作路径合理。
- 相同空状态文案在两边是否都成立。
- 编辑流在大屏和小屏上是否都自然。

这些问题不会自动被“一套 SwiftUI 代码”解决，必须由你主动审视。

## 一次双平台体验检查

完成这一章后，至少走一遍：

1. 在 `macOS` 上，用键盘和侧栏完成一天常用路径。
2. 在 `iOS` 上，用推进式导航完成同样路径。
3. 比较两边哪个步骤显得别扭或啰嗦。
4. 只把真正属于表达层的问题留在平台分支，别把产品规则拆开。

## 本章小结

跨平台做得好，不是因为两边长得一模一样，而是因为它们共享同一个产品中心，却都像自己平台上的自然应用。能做到这点，你才算真正开始理解 Apple 平台工程。
