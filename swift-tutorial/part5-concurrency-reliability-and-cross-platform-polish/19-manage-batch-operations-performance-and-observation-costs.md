# 第 19 章：管理批量操作、性能与 Observation 成本

## 功能越全，结构问题越会被性能放大

前面几部分里，很多结构问题还能躲过去，因为数据量小、交互路径短。一旦你开始做批量操作、异步刷新和更复杂的列表，性能和 Observation 成本会把所有边界问题一起放大。这个阶段最重要的认知是：SwiftUI 产品里的性能问题，常常先是状态结构问题，然后才是算法问题。

## 批量操作会暴露影响面

先看一个最朴素的批量完成：

```swift
func completeTasks(ids: [UUID]) {
    for id in ids {
        toggleCompletion(id)
    }
}
```

这段代码的语法没什么难度，但它立刻带来三个检查题：

1. 这次操作会触发多少次观察更新？
2. 哪些页面其实并不关心这次变化，却被一起刷新了？
3. 有没有比“逐条切换”更适合的核心操作表达？

如果这三个问题你没想过，批量功能一上线，产品就很容易变得迟钝。

## Observation 成本通常来自“拥有得太高”

最常见坏味道不是“算法太慢”，而是：

- 一个大 `store` 持有了太多和当前页面无关的状态。
- 派生结果每次渲染都重新计算。
- 页面既看共享状态，又自己拼很多重复过滤逻辑。

遇到这类问题，先别急着写缓存。先回头问：这份状态是不是被拥有得太高了？这块派生结果是不是应该提炼成共享查询，而不是在多个页面重复算？

## 给批量选择也划清边界

批量操作通常还会引入一组新的页面级状态：

```swift
@State private var selectedTaskIDs: Set<UUID> = []
@State private var isPerformingBatchAction = false
```

这里有个很关键的判断：

- “当前哪些任务被选中”通常是页面交互状态。
- “批量完成任务时应该怎样改变任务集合”通常是核心规则。

如果你把两者混掉，后面很容易一边做页面切换、一边丢选择状态、同时又不敢重构核心逻辑。

## 如何做一次性能排查

不要一上来就开一堆优化开关。先按这个顺序查：

1. 哪次用户动作触发了最大范围的刷新？
2. 刷新的页面里，哪些其实根本不需要重算？
3. 是状态边界过宽，还是派生结果重复计算？
4. 只有在前三条明确后，再考虑局部缓存或算法优化。

这条顺序很重要，因为过早上缓存通常只会把结构问题藏得更深。

## 本章小结

批量操作和性能不是“高级附加题”，而是系统结构的一次压力测试。只要你能先用状态拥有范围和影响面去看问题，Observation 成本通常就不会失控。
