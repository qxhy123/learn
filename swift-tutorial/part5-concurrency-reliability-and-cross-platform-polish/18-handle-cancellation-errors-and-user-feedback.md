# 第 18 章：处理取消、错误与用户反馈

## 取消、失败、空状态绝不能混成一团

异步工作一出现，系统里就不再只有“成功”与“失败”两种情况。至少还会多出：

- 用户主动取消
- 页面切换导致任务自然失效
- 临时网络或存储失败
- 正常但为空的结果

这些语义如果在 UI 上长得一模一样，用户很快就会迷路。工程上也一样难维护，因为每一层都不知道自己面对的到底是什么。

## 先把加载状态建成真正的状态机

一个很好的起点不是 scattered flags，而是把页面状态集中表达：

```swift
enum LoadState<Value> {
    case idle
    case loading
    case loaded(Value)
    case empty
    case failed(String)
}
```

然后再明确规定取消不属于 `failed`。很多时候，取消更接近“这次工作不再需要”，而不是“系统出了错”。

## 区分“谁取消了谁”

在 `FocusList` 里，取消可能至少来自三类场景：

1. 用户主动点了取消按钮。
2. 用户继续输入，旧搜索任务被新任务取代。
3. 页面离开，当前异步工作被系统停止。

这三种取消不一定都需要给用户同等强度的反馈。一个很实用的规则是：

- 用户主动取消：通常给轻量确认或直接安静结束。
- 任务被新任务取代：通常不提示。
- 真正错误：才提示用户可重试或需要注意。

## 错误文案要描述产品影响

不要让界面只显示“Operation failed”。更有价值的反馈应该告诉用户影响是什么、下一步能做什么。例如：

```swift
catch {
    state = .failed("Could not refresh tasks. Your current list is unchanged.")
}
```

这段话虽然短，但它把最重要的信息带出来了：

- 哪个动作失败了。
- 当前已有数据是否还安全。
- 用户是否需要重新操作。

## 保存失败时，不要把用户工作一起丢掉

拿“编辑任务并保存”做例子。一个正确的失败路径通常是：

1. 用户修改草稿。
2. 点击保存。
3. 写入失败。
4. 页面提示失败原因。
5. 草稿仍然保留，方便用户重试。

如果写入失败后你直接把编辑器关闭、草稿丢掉，用户感受到的就不是“系统帮我处理错误”，而是“系统把我的工作吞掉了”。

## 一次反馈审计

完成这一章后，逐条审查：

1. 取消是否被误报成错误。
2. 空状态是否被误报成失败。
3. 失败提示是否说明了影响和下一步。
4. 失败后用户是否还能继续当前工作，而不是被迫从头开始。

只要这四点里有两点做不到，可靠性就还停留在“代码里写了 catch”而不是“产品真的可恢复”。

## 本章小结

可靠性不是异常处理代码行数多，而是状态语义足够清楚。取消、失败和空状态分开之后，`FocusList` 才会真的像一个能让人放心使用的产品。
