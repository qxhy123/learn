## 学新知 intro（7~10 张卡，按章灵活）
典型卡序（按内容取舍）：
1. **这一关解决什么问题** — 先讲真实场景/痛点（如「pull 时冲突了不敢动」），而不是先甩命令。
2. **先看状态** — 这类操作前该观察什么（`git status`/`git diff`/`git log`/分支/远程），状态告诉你什么。
3. **命令与它改了哪一层** — 关键命令逐个讲，每个都点明改的是工作区/暂存区/提交/引用/远程哪一层。
4. **为什么这样做** — 用「为什么…？因为…」自问自答，讲清这个做法/命令背后的道理与取舍（如「为什么 `git restore --staged` 而不是 `git reset`」）。**这是最该深的一张卡，不能省。**
5. **命令示例** — `body` 里放 bash/git 命令围栏（见代码规则），照原章节写，能体现本关要点。
6. **常见错误与恢复路径** — 危险动作必须说明风险 + 怎么补救（reflog/restore 等）。这是本教程特色，务必保留。
7. **验收 / 小结** — 一句话：学完这关你应该能判断/做什么。

## 口吻：正常、清楚的专业表达（务必照 ✅）
同一意思三档对照：
- ❌ **论文腔**：「定义 2.1：暂存区可形式化为索引快照……」「综上所述，证毕」
- ❌ **太大白话 / 俚语**：「这玩意儿说白了就是……」「猛敲 reset 一把梭」「硬刚冲突」
- ✅ **正常**：「为什么撤销暂存优先用 `git restore --staged` 而不是 `git reset`？因为 `restore` 语义明确、只动暂存区，不会误改工作区文件；而 `reset` 一个命令能动好几层，新手容易连带把改动也弄丢。」

要点：用「为什么…？因为…」组织推理；用词正经（工作区、暂存区、提交、分支引用、远程跟踪、快进合并）；不用编号定义体，也不用俚语；命令第一次出现用一句白话点一下它干什么。深度不能因为口吻变白而下降。

## 代码硬规则（违反会导致前端代码块渲染破裂）
- 命令/代码只放卡片 `body` 或 `tip`（按 Markdown 渲染、支持围栏）。`steps`/`title`/`prompt`/选项 只支持**行内** `code`（如 `` `git status` ``）。
- ` ```bash ` 起、` ``` ` 收。**代码内部不能有空行**（空行会把代码块切断）；不要 Tab。命令行可带 `# 注释` 说明每步改了哪一层。
- JSON 字符串里换行写 `\n`。命令照原章节写，单段 ≤ ~20 行。**正文里不要裸写 `$`**（shell 提示符 `$`、变量 `$1` 只能出现在代码围栏里）。

## 题目 questions（每关 10~12 道，考理解不考记忆）
schema：
- `{"type":"choice","prompt","options":[...],"answer":0,"explain"}`（answer 是 0 基下标）
- `{"type":"input","prompt","accept":["git restore","restore"],"explain"}`（accept 列全写法；可问命令/子命令/参数/术语）
- `{"type":"judge","prompt","answer":true,"explain"}`
- `{"type":"match","prompt","left":[...],"right":[...],"explain"}`

深度题方向：给一个场景问「该先看什么状态/该用哪个命令」、某命令**改了哪一层**（工作区/暂存区/提交/引用/远程）、区分相似命令（`reset --soft/--mixed/--hard`、`merge` vs `rebase`、`fetch` vs `pull`、`restore` vs `checkout` vs `reset`）、判断一个危险操作能否恢复（如「`reset --hard` 后还能用 reflog 找回吗」）、判断常见误解对错。
均衡：choice ≤ 6；judge、match 各 ≥ 1；input ≥ 2。每题都写 `explain`。

### 配对题铁律
`right[i]` 必须是 `left[i]` 的正确答案，**按下标对齐存放，绝对不要把 right 打乱**（前端会自己随机显示）。写完每道 match 逐项核对 left[i] ↔ right[i]。（很适合 命令 ↔ 它改的层 / 命令 ↔ 作用 的配对。）

## 排版
命令 / 子命令 / 参数 / 文件名用反引号；Git 课用不到 `$...$` 公式，不要裸写 `$`；命令首次出现给一句中文解释。
