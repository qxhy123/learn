把**已有**的《领域驱动设计（DDD）从零到高阶教程》章节改写成 App 的关卡。一章 = 一关。忠实浓缩原章节的概念、动机、模式、代码、易错点，**不要另造内容**。两条总要求：**深度够**（把每个概念/模式为什么存在、解决什么问题掰细），**口吻正常**（不论文腔、不俚语，见下）。

## 输入
- prompt 会告诉你：单元号、负责的章节（给 .md 绝对路径）、输出文件。
- 逐章 Read 它的 .md 全文，吃透：这章讲什么概念、为什么需要、怎么落地（含 Python 代码/建模示例）、和相邻概念的区别、易错点、小结。

## 输出
- Write 到指定文件（如 `_build/ddd/u1.json`），内容是**关卡数组**，顺序与给定章节顺序一致。每关：`{ "title", "subtitle", "intro": [...卡片...], "questions": [...] }`，**不写 id**。合法 JSON。
- `title`：`第N章中文名`（如 `限界上下文`、`聚合`）。`subtitle`：一句话点出本关主题。

## 学新知 intro（7~10 张卡，按章灵活）
典型卡序（按内容取舍）：
1. **这一章在解决什么** — 一段话点出本章主题 + 它针对的真实痛点（如「为什么大型系统需要划分限界上下文」）。
2. **核心概念** — 把本章关键概念讲清（定义 + 一句白话 + 一个贴近业务的例子）。
3. **怎么落地 / 建模** — 如何在设计/代码里体现；用 `steps` 写建模流程或用代码示例。
4. **为什么这样做** — 用「为什么…？因为…」自问自答，讲清这个概念/模式背后的动机与取舍（如「为什么聚合要通过根访问」「值对象为什么不可变」）。**这是最该深的一张卡，不能省。**
5. **代码 / 建模示例** — `body` 里放 Python 代码围栏（见代码规则），照原章节写，体现本关要点（如实体 vs 值对象的类设计）。
6. **关键对比 / 边界**（按需）— 如 实体 vs 值对象、聚合边界怎么划、领域服务 vs 应用服务、CQRS 读写分离（很适合配 match 题）。
7. **易错点 / 误区** — 列表 3~6 条，照原章节常见坑（如贫血模型、聚合过大、把技术概念当领域概念）。
8. **小结** — 一句话收束本关要记住的东西。

## 口吻：正常、清楚的专业表达（务必照 ✅）
同一意思三档对照：
- ❌ **论文腔**：「定义 5.1：限界上下文是一个语义边界，可形式化为……」「综上所述，证毕」
- ❌ **太大白话 / 俚语**：「这玩意儿说白了就是一坨……」「随便圈个边界糊上去」
- ✅ **正常**：「为什么同一个『商品』在不同上下文里要建成不同的模型？因为销售上下文关心的是价格和库存，而物流上下文关心的是重量和体积——硬塞进一个『万能商品类』，只会让两边的规则互相打架。」

要点：用「为什么…？因为…」组织推理；用词正经（限界上下文、聚合根、不变量、通用语言、防腐层）；不用编号定义体，也不用俚语；术语第一次出现给中英对照 + 一句白话。深度不能因为口吻变白而下降。

## 代码硬规则（违反会导致前端代码块渲染破裂）
- 代码只放卡片 `body` 或 `tip`（按 Markdown 渲染、支持围栏）。`steps`/`title`/`prompt`/选项 只支持**行内** `code`。
- ` ```python ` 起、` ``` ` 收。**代码内部不能有空行**（空行会把代码块切断）；用 4 空格缩进、不要 Tab。
- JSON 字符串里换行写 `\n`。代码照原章节写，体现要点，单段 ≤ ~24 行。**正文里不要裸写 `$`**。

## 题目 questions（每关 10~12 道，考理解不考记忆）
schema：
- `{"type":"choice","prompt","options":[...],"answer":0,"explain"}`（answer 是 0 基下标）
- `{"type":"input","prompt","accept":["聚合根","Aggregate Root"],"explain"}`（accept 列全中英写法；可问术语/模式名）
- `{"type":"judge","prompt","answer":true,"explain"}`
- `{"type":"match","prompt","left":[...],"right":[...],"explain"}`

深度题方向：给一个业务场景问「该用什么概念/模式来建模」、区分相似概念（实体 vs 值对象、聚合根 vs 普通实体、领域服务 vs 应用服务、编排 vs 编排 Saga）、判断一个设计是好是坏（如贫血模型、聚合过大）、判断常见误解对错、为什么某规则这样定（聚合一个事务只改一个）。
均衡：choice ≤ 6；judge、match 各 ≥ 1；input ≥ 2。每题都写 `explain`。

### 配对题铁律
`right[i]` 必须是 `left[i]` 的正确答案，**按下标对齐存放，绝对不要把 right 打乱**（前端会自己随机显示）。写完每道 match 逐项核对 left[i] ↔ right[i]。（很适合 概念 ↔ 定义、模式 ↔ 解决的问题 的配对。）

## 排版
术语 / 模式名 / 代码标识用反引号或中英对照；DDD 课用不到 `$...$` 公式，不要裸写 `$`。

## 自检（写文件前）
- 卡数 7~10、含「为什么这样做」深度卡；代码无空行无 Tab；口吻对照 ✅（无定义/定理体、无俚语）。
- 每关 10~12 题、类型均衡、每题有 explain、答案 / 下标亲自核对；每道 match 逐项对齐。
- 合法 JSON、关卡顺序与给定章节一致。
