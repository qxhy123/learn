## 学新知 intro（7~10 张卡，按章灵活）
典型卡序（按内容取舍）：
1. **这一章在解决什么** — 一段话点出本章主题 + 它针对的真实可靠性 / 工程痛点。
2. **核心概念** — 把本章关键概念 / 架构讲清（定义 + 一句白话 + 贴近工程的例子）。
3. **机制 / 怎么搭** — 这层 Harness 怎么实现；可用 `steps` 写流程或用代码示例。
4. **为什么这样设计** — 用「为什么…？因为…」自问自答，讲清架构 / 做法背后的动机与权衡（如「为什么评估要离线+在线两条线」「为什么多 Agent 要隔离上下文」）。**这是最该深的一张卡，不能省。**
5. **代码示例** — `body` 里放 Python 代码围栏（见代码规则），照原章节写，体现本关要点（评估流水线 / Harness 骨架等）。
6. **关键对比 / 权衡**（按需）— 如 离线 vs 在线评估、单 Agent vs 多 Agent、Guides vs Sensors（很适合配 match 题）。
7. **易错点 / 反模式** — 列表 3~6 条，照原章节常见坑。
8. **小结** — 一句话收束本关要记住的东西。

## 口吻：正常、清楚的专业表达（务必照 ✅）
同一意思三档对照：
- ❌ **论文腔**：「定义 6.1：评估 Harness 可形式化为一个三元组……」「综上所述，证毕」
- ❌ **太大白话 / 俚语**：「这玩意儿说白了就是个壳子……」「随便糊个评估」
- ✅ **正常**：「为什么不能只靠人工抽查来评估 Agent？因为人工抽查既不可复现、也无法回归——今天改了 prompt，你没法自动确认昨天能过的用例今天还能过。评估 Harness 就是把"判断好坏"这件事固化成可重复运行的流水线。」

要点：用「为什么…？因为…」组织推理；用词正经（评估 Harness、可复现、回归、可观测性、护栏、上下文隔离）；不用编号定义体，也不用俚语；术语第一次出现给中英对照 + 一句白话。深度不能因为口吻变白而下降。

## 代码硬规则（违反会导致前端代码块渲染破裂）
- 代码只放卡片 `body` 或 `tip`（按 Markdown 渲染、支持围栏）。`steps`/`title`/`prompt`/选项 只支持**行内** `code`。
- ` ```python ` 起、` ``` ` 收。**代码内部不能有空行**（空行会把代码块切断）；用 4 空格缩进、不要 Tab。
- JSON 字符串里换行写 `\n`。代码照原章节写，体现要点，单段 ≤ ~24 行。**正文里不要裸写 `$`**（shell 变量等只能在代码围栏内）。

## 题目 questions（每关 10~12 道，考理解不考记忆）
schema：
- `{"type":"choice","prompt","options":[...],"answer":0,"explain"}`（answer 是 0 基下标）
- `{"type":"input","prompt","accept":["回归测试","regression"],"explain"}`（accept 列全中英写法；可问术语 / 模式 / 工具名）
- `{"type":"judge","prompt","answer":true,"explain"}`
- `{"type":"match","prompt","left":[...],"right":[...],"explain"}`

深度题方向：给一个工程场景问「该用哪种 Harness / 哪个评估指标 / 哪种编排」、区分相似概念（离线 vs 在线评估、单 vs 多 Agent、Guides vs Sensors、回归 vs 单元测试）、判断一个设计是好是坏（反模式）、判断常见误解对错、为什么某权衡这样取。
均衡：choice ≤ 6；judge、match 各 ≥ 1；input ≥ 2。每题都写 `explain`。

### 配对题铁律
`right[i]` 必须是 `left[i]` 的正确答案，**按下标对齐存放，绝对不要把 right 打乱**（前端会自己随机显示）。写完每道 match 逐项核对 left[i] ↔ right[i]。
