## 学新知 intro（7~10 张卡，按章灵活）
典型卡序（按内容取舍）：
1. **这一章在解决什么** — 一段话点出本章主题 + 为什么需要它 / 解决什么痛点（如「为什么 JS 需要 TS」）。
2. **核心概念 / 语法** — 把本章最关键的语法/类型讲清（定义 + 一句白话解释 + 最小示例）。
3. **机制 / 怎么用** — 用法细节、类型推导规则、编译期 vs 运行期等；可用 `steps` 写流程。
4. **为什么这样设计** — 用「为什么…？因为…」自问自答，讲清这个特性背后的取舍（如「为什么用 `unknown` 而不是 `any`」「泛型解决了什么」）。**这是最该深的一张卡，不能省。**
5. **代码示例** — `body` 里放 TypeScript 代码围栏（见代码规则），照原章节写，能体现本关要点。
6. **关键对比 / 要点**（按需）— 如 `interface` vs `type`、`unknown` vs `any`、`unknown` vs `never`、各 Utility Type 的效果（很适合配 match 题）。
7. **易错点 / 误区** — 列表 3~6 条，照原章节常见坑（如类型擦除、结构化类型、装饰器执行顺序）。
8. **小结** — 一句话收束本关要记住的东西。

## 口吻：正常、清楚的专业表达（务必照 ✅）
同一意思三档对照：
- ❌ **论文腔**：「定义 3.1：结构化子类型关系可形式化为……」「综上所述，证毕」
- ❌ **太大白话 / 俚语**：「这玩意儿说白了就是……」「类型瞎标一通」「随便 any 一下糊过去」
- ✅ **正常**：「为什么尽量别用 `any`？因为 `any` 会让类型检查直接对这块代码"闭眼"，你就失去了 TypeScript 最大的价值——在编译期帮你抓错。需要"暂时不知道类型"时，优先用 `unknown`，它逼你先收窄再使用。」

要点：用「为什么…？因为…」组织推理；用词正经（类型推导、结构化类型、类型收窄、编译期）；不用编号定义体，也不用俚语；术语第一次出现用一句白话点一下。深度不能因为口吻变白而下降。

## 代码硬规则（违反会导致前端代码块渲染破裂）
- 代码只放卡片 `body` 或 `tip`（按 Markdown 渲染、支持围栏）。`steps`/`title`/`prompt`/选项 只支持**行内** `code`。
- ` ```typescript ` 起、` ``` ` 收（或 ` ```ts `）。**代码内部不能有空行**（空行会把代码块切断）；用 2 空格缩进、不要 Tab。
- JSON 字符串里换行写 `\n`。代码照原章节写，可看懂、能体现要点，单段 ≤ ~24 行（长示例拆成相邻多个围栏或多张卡，每个围栏内不留空行）。

## 题目 questions（每关 10~12 道，考理解不考记忆）
schema：
- `{"type":"choice","prompt","options":[...],"answer":0,"explain"}`（answer 是 0 基下标）
- `{"type":"input","prompt","accept":["readonly","Readonly"],"explain"}`（accept 列全写法；可问关键字/类型/工具类型名/编译选项）
- `{"type":"judge","prompt","answer":true,"explain"}`
- `{"type":"match","prompt","left":[...],"right":[...],"explain"}`

深度题方向：给一段 TS 代码问「能否通过类型检查 / 推导出什么类型 / 报什么错」、区分相似概念（`interface` vs `type`、`unknown` vs `any`、`type` 别名 vs 类、`enum` vs union）、选对工具类型（`Partial`/`Pick`/`Omit`/`Record`…）、判断一个「常见误解」对错（如"TS 的类型在运行时还在"）、为什么某设计这样取舍。
均衡：choice ≤ 6；judge、match 各 ≥ 1；input ≥ 2。每题都写 `explain`。

### 配对题铁律
`right[i]` 必须是 `left[i]` 的正确答案，**按下标对齐存放，绝对不要把 right 打乱**（前端会自己随机显示）。写完每道 match 逐项核对 left[i] ↔ right[i]。

## 排版
代码 / 类型 / 关键字 / 标识符用反引号；TS 课基本用不到 `$...$` 公式，不要裸写 `$`；术语首次给中英对照（如 类型守卫 type guard）。
