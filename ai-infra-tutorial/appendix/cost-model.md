# 附录L：AI Infra 成本模型

> 成本模型不是财务表格，而是工程决策工具。它要回答三个问题：钱花在哪条链路、哪个变量最敏感、优化会不会牺牲稳定性和交付速度。

## 1. 成本口径

AI Infra 成本建议先拆成四层：

1. **训练成本**：GPU hours、失败重试、checkpoint、数据 IO、实验管理和工程等待。
2. **推理成本**：prefill、decode、batching、KV Cache、弹性扩缩、量化和副本冗余。
3. **平台成本**：空闲率、碎片率、多租户公平性、控制面、观测、安全和运维自动化。
4. **风险成本**：发布事故、质量回退、安全事件、恢复时间和机会成本。

生产环境不要只看账单总额。账单只能说明钱已经花掉，成本模型要能解释为什么花掉，以及下一次如何少花或花得更稳。

## 2. 通用公式

### GPU 小时成本

```text
GPU 成本 = GPU 数量 * 运行小时 * 单 GPU 小时价格
有效 GPU 成本 = GPU 成本 / 有效利用率
```

这里的有效利用率不是 `nvidia-smi` 上的瞬时 GPU utilization，而是能转化为业务或训练进度的利用率。例如训练看 tokens/sec、step time、MFU；推理看 tokens/sec、请求完成数、SLO 内吞吐。

### 单位产出成本

```text
训练每 B token 成本 =
  总训练成本 / 训练 token 数 * 1e9

推理每 1M token 成本 =
  总推理成本 / 输出和输入 token 总数 * 1e6

每成功请求成本 =
  总推理成本 / 成功完成请求数
```

不同团队比较成本时必须先统一口径：是否包含失败重试、checkpoint 存储、数据预处理、评测、灰度冗余和平台摊销。

### 失败放大系数

```text
失败放大系数 =
  (成功运行 GPU hours + 失败浪费 GPU hours) / 成功运行 GPU hours
```

如果一次训练计划需要 10,000 GPU hours，但因为 NCCL timeout、数据坏样本、checkpoint 恢复失败浪费 2,000 GPU hours，失败放大系数就是 1.2。此时优化稳定性可能比优化 kernel 更划算。

## 3. 训练成本模型

训练成本的核心不是“用了多少卡”，而是“多少 GPU hours 转化成了有效 token 和可恢复进度”。

### 主要成本项

| 成本项 | 计算方式 | 工程关注点 |
|--------|----------|------------|
| GPU hours | `GPU 数量 * wall-clock hours` | step time、MFU、通信等待、straggler |
| 失败重试 | `失败次数 * 已消耗 GPU hours` | checkpoint 间隔、恢复语义、弹性训练、故障隔离 |
| checkpoint | `写入频率 * checkpoint 大小 * 存储单价` | sharded checkpoint、增量写入、异步写入、保留策略 |
| 数据 IO | `读取量 * 存储/网络单价 + 等待时间 GPU 成本` | dataloader、缓存、对象存储吞吐、并行文件系统 |
| 评测与实验 | `评测 GPU hours + 人工等待时间` | 评测抽样、早停、实验去重、指标门禁 |

### 训练成本公式

```text
训练总成本 =
  训练 GPU hours 成本
  + 失败重试 GPU hours 成本
  + checkpoint 存储和 IO 成本
  + 数据读取和预处理成本
  + 评测成本
  + 平台摊销
```

### 示例：一次 64 卡训练

假设：

- 64 张 GPU，单价 3 美元/GPU hour
- 计划训练 72 小时
- 中途失败 2 次，分别浪费 6 小时和 4 小时
- checkpoint 每 2 小时写一次，每次 2 TB，保留 10 份

```text
计划 GPU 成本 = 64 * 72 * 3 = 13,824 美元
失败重试成本 = 64 * (6 + 4) * 3 = 1,920 美元
失败放大系数 = (64*72 + 64*10) / (64*72) = 1.139
```

如果把 checkpoint 间隔从 2 小时缩短到 30 分钟，失败损失会下降，但 checkpoint IO 和存储会上升。正确决策要比较：

```text
缩短 checkpoint 后节省的失败 GPU 成本
  是否大于
新增 checkpoint IO 成本 + 新增 step 抖动成本
```

### 训练优化优先级

1. 先降低失败放大系数：修复 NCCL timeout、坏数据、恢复失败、驱动不一致。
2. 再提升有效吞吐：数据管道、通信拓扑、batch、并行策略、kernel。
3. 最后压缩存储与评测成本：checkpoint 保留策略、评测抽样、实验合并。

## 4. 推理成本模型

推理成本由 token 形态决定。prefill 消耗计算，decode 受内存带宽和 KV Cache 影响，长上下文和高并发会把成本从“每请求”变成“每 token + 每秒占用显存”。

### Prefill 与 Decode

```text
请求成本 =
  prefill token 数 * prefill 单 token 成本
  + decode token 数 * decode 单 token 成本
  + 请求排队和调度成本
  + KV Cache 占用成本
```

prefill 更像批量矩阵计算，容易通过 batching 提升吞吐；decode 每步生成少量 token，容易被 KV Cache、batch shape、内存带宽和调度开销限制。

### Batching 成本

```text
有效 batch 收益 =
  batch 后 tokens/sec 提升
  - 排队延迟增加
  - 长尾请求拖慢
  - OOM/evict 风险
```

生产上不要只追求最大 batch。面向在线服务时，应按 SLO 分层：高优先级请求保 latency，批量请求吃吞吐，长上下文请求单独限流或隔离。

### KV Cache 成本

```text
KV Cache 近似显存 =
  层数 * batch size * sequence length * hidden size * 2(K,V) * bytes_per_element
```

真实引擎会受分页、block size、碎片、prefix cache、并行策略影响。容量规划时至少要用请求 token 分布，而不是只用平均上下文长度。

```text
KV 占用成本 =
  KV Cache 占用 GB * 占用秒 * GPU 显存机会成本
```

长上下文请求即使 QPS 不高，也可能长期占用显存，挤掉更多短请求。

### Autoscaling 成本

```text
在线服务成本 =
  基础副本成本
  + 峰值冗余成本
  + 扩缩容滞后成本
  + 冷启动成本
```

LLM 推理副本冷启动慢，权重加载和 cache warmup 贵。自动扩缩容不能只看 CPU 或 QPS，至少要看：

- waiting queue
- prefill/decode token rate
- KV Cache 水位
- p95/p99 latency
- replica load skew
- 冷启动时间

### 量化收益

```text
量化净收益 =
  GPU 成本下降
  + 吞吐提升收益
  - 质量下降成本
  - 工程维护成本
  - fallback/双轨发布成本
```

量化不是免费优化。生产上要把质量评测、长尾 case、安全策略、回滚路径和多模型兼容性计入成本。

### 示例：两种推理配置

| 配置 | GPU | 单价 | 吞吐 | 月运行 | 月成本 | 单位 token 成本 |
|------|-----|------|------|--------|--------|-----------------|
| FP16 | 8 | 3 美元/小时 | 80k token/s | 720 小时 | 17,280 美元 | 约 0.0042 美元/1M token |
| INT8 | 4 | 3 美元/小时 | 70k token/s | 720 小时 | 8,640 美元 | 约 0.0024 美元/1M token |

如果 INT8 让质量指标下降，导致 3% 请求需要重试或人工兜底，就必须把重试 token、用户体验和人工成本计入净收益。

## 5. 平台成本模型

平台成本的核心是资源不能被完美切分。GPU 集群常见浪费来自空闲、碎片、排队策略和多租户博弈。

### 空闲率

```text
空闲率 = 空闲 GPU hours / 总可用 GPU hours
空闲成本 = 空闲 GPU hours * 单 GPU 小时价格
```

空闲不一定都是坏事。在线服务需要冗余，训练集群需要维护窗口，关键业务需要预留容量。问题是空闲是否有明确目的。

### 碎片率

```text
碎片率 =
  无法被当前任务形态使用的剩余 GPU / 总 GPU
```

例如集群里有很多 1-2 张零散 GPU，但主力训练任务需要 8 卡同机或 64 卡同拓扑，这些零散资源对训练就是碎片。降低碎片的手段包括队列整形、gang scheduling、MIG/MPS、任务规格标准化和离线填谷。

### 多租户公平性

成本优化不能只看全局利用率。一个租户长期占用便宜时段或高质量拓扑，会让其他租户排队，最终变成组织成本。

```text
租户有效成本 =
  租户使用资源成本
  + 租户造成的排队成本
  + 租户占用稀缺拓扑的机会成本
```

公平性策略要明确：

- 配额是硬限制还是软限制
- 抢占是否允许，恢复成本由谁承担
- 高优先级任务是否需要更高 chargeback
- 低优先级任务能否填谷
- 共享平台成本如何摊销

## 6. 成本反模式

1. **只看 GPU 利用率**：GPU utilization 高不代表有效产出高，可能是在做无效重试或被长尾 batch 拖住。
2. **只看账单不看失败**：失败重试、恢复失败和灰度事故经常比单次优化节省的钱更大。
3. **平均 token 决策**：KV Cache、p99 latency 和 OOM 都由分布尾部决定，平均值会误导容量规划。
4. **过度追求满载**：在线服务没有冗余会放大发布和流量突刺风险。
5. **量化只算 GPU 节省**：质量下降、回滚、双轨验证和兼容维护都是真成本。
6. **训练和推理混用同一成本口径**：训练关注完成时间和失败放大，推理关注 SLO 内 token 成本。
7. **忽略拓扑机会成本**：高质量 NVLink/IB 拓扑被低优先级任务占用，会让关键训练排队。
8. **成本优化绕过治理**：手工改配置、跳过评测或绕过准入，短期省钱，长期制造事故成本。

## 7. 决策检查清单

### 训练成本

- 本次训练的目标产出是什么：token、checkpoint、模型版本还是评测结论？
- GPU hours 中有多少是有效 step，有多少是等待、失败和恢复？
- 最近失败的根因是否会在更大规模上放大？
- checkpoint 间隔是否按恢复成本和 IO 成本共同决定？
- 数据 IO 是否让 GPU 等待？等待成本是否高于缓存成本？
- 是否有早停、实验合并或小规模验证，避免大规模无效训练？

### 推理成本

- 成本按请求、输入 token、输出 token 还是 SLO 内成功请求计量？
- prefill 和 decode 的瓶颈分别是什么？
- batching 提升吞吐后，p99 是否仍在 SLO 内？
- KV Cache 是否按 token 分布尾部做容量规划？
- autoscaling 是否考虑冷启动、权重加载和 cache warmup？
- 量化收益是否扣除了质量下降、重试和回滚成本？

### 平台成本

- 空闲容量是浪费、冗余、维护窗口还是业务预留？
- GPU 碎片是否来自任务规格、队列策略还是拓扑约束？
- 多租户 chargeback 是否反映稀缺拓扑和优先级？
- 低优先级任务是否能填谷，且可被安全抢占？
- 成本指标是否能按团队、模型、任务、版本和环境归因？
- 成本优化是否仍满足安全、发布门禁和审计要求？

## 8. 最小落地指标

一个可运营的 AI Infra 成本面板至少应包含：

- 训练：GPU hours、tokens/sec、MFU、失败放大系数、checkpoint IO、恢复成功率。
- 推理：每 1M token 成本、prefill/decode token rate、KV Cache 水位、batch size 分布、SLO 内成功率。
- 平台：空闲率、碎片率、队列等待时间、租户配额使用率、抢占次数、拓扑占用。
- 治理：按模型/版本/团队/环境归因的成本，异常增长告警，发布前后成本 diff。

成本模型要和发布、容量规划、故障复盘放在一起使用。只有能解释工程行为的成本，才值得进入决策。
