## 第1章：什么是 AI Infra

### 第1题：用你自己的话说明 AI Infra 与“训练一个模型”有什么区别

**思路**

- 这道题的关键不是复述定义，而是区分“一个模型任务”和“一整套持续运行系统”。
- 可以从目标、对象、时间尺度、失败处理、团队协作五个维度回答。

**参考答案**

“训练一个模型”更像是一个局部任务，它关注的是：

- 数据是否准备好了
- 训练代码能否跑通
- loss 是否下降
- 最终指标是否达标

而 `AI Infra` 关注的是围绕这个模型任务的一整条链路是否能长期、稳定、可治理地运行，包括：

- 数据如何进入和版本化
- 训练任务如何调度与恢复
- 模型制品如何注册、评测、发布和回滚
- 推理服务如何扩缩容、限流和观测
- 多团队如何共享 GPU、配额和预算

可以用一个简单对比说明：

| 维度 | 训练一个模型 | AI Infra |
|------|--------------|----------|
| 目标 | 得到一个效果可接受的模型 | 让模型从实验到生产形成稳定闭环 |
| 时间尺度 | 一次实验或一批实验 | 长期持续运行 |
| 关注对象 | 模型、数据、训练脚本 | 资源、任务、数据、制品、服务、治理 |
| 失败处理 | 人工重跑 | 自动恢复、回滚、限流、审计 |
| 协作方式 | 个人或小组实验 | 多团队共用平台与规则 |

所以更准确地说，训练模型是 AI 工作负载中的一个环节，而 AI Infra 是承载整条工作负载生命周期的系统能力。

**延伸提醒**

- 如果一个团队只能“训练出模型”，但无法稳定发布、回滚和治理，它还没有真正拥有 AI 基础设施。

### 第2题：画出一个包含业务层、模型层、平台层、资源层的系统分层图

**思路**

- 这道题考察的是分层意识。
- 重点不是画得多复杂，而是每一层有清晰职责，并且上下游关系明确。

**参考架构**

```text
业务层
  - 产品接口
  - 用户请求
  - SLA / 成本目标

模型层
  - 训练逻辑
  - 推理逻辑
  - 评测逻辑

平台层
  - 训练任务编排
  - 模型仓库
  - 发布与回滚
  - 监控、告警、审计
  - 队列、配额、权限

资源层
  - GPU / CPU
  - 内存 / 显存
  - 网络
  - 存储
  - 容器运行环境
```

**参考答案**

一张合格的分层图至少要表达两个关系：

1. **职责关系**：业务层关心用户价值，模型层关心效果，平台层关心工作流和治理，资源层关心容量和带宽。
2. **依赖关系**：上层依赖下层提供能力，下层并不知道上层业务细节。

如果进一步补充，可在每层边上标注典型问题：

- 业务层：接口超时、结果不稳定、成本超标
- 模型层：效果退化、评测不过、模型版本冲突
- 平台层：队列拥塞、回滚困难、工件找不到
- 资源层：GPU 不够、网络慢、存储吞吐低

### 第3题：如果一个推理服务超时变多，你会优先从哪三层开始排查？为什么？

**思路**

- 这道题不要求“唯一顺序”，而是要求给出合理排障顺序。
- 最好的回答不是“从最底层开始”，而是“从最有可能解释现象的层级开始”。

**参考答案**

我会优先看这三层：

1. **平台层**
2. **资源层**
3. **模型 / 依赖链路层**

原因如下：

#### 第一步：先看平台层

因为超时往往先体现在：

- 队列等待时间升高
- 某个版本刚刚灰度
- 路由策略变化
- 副本数不够或扩容失败

这些都是平台层直接可见的问题，而且能最快缩小范围。

#### 第二步：再看资源层

如果平台层显示请求在排队或副本忙不过来，就要检查：

- GPU 利用率和显存是否打满
- 节点是否有冷启动
- 网络是否有抖动
- 下游存储或索引是否变慢

#### 第三步：最后看模型 / 依赖链路层

如果平台和资源看起来都正常，就要怀疑：

- 模型版本变大了
- prompt / 上下文长度变长
- 下游向量库、重排器、特征服务变慢
- 某个模型输出长度失控

**一个实用排障顺序**

```text
先看 queue wait -> 再看 GPU / 显存 / 副本 -> 再拆 downstream / model
```

### 第4题：为什么说“开源组件拼起来”不等于“拥有 AI 平台”？

**思路**

- 这题考察“组件”和“平台能力”的区别。
- 关键在于：平台不仅是功能集合，更是规则、状态和治理的统一系统。

**参考答案**

开源组件只能提供局部能力，例如：

- Kubernetes 负责通用编排
- MLflow 负责实验记录或模型仓库
- vLLM 负责 LLM 推理
- Prometheus 负责监控指标

但真正的平台还必须解决这些“组件之间”的问题：

- 训练任务输出如何自动进入模型仓库
- 评测结果如何影响发布门禁
- 推理版本如何与模型版本、镜像版本、索引版本绑定
- 多团队如何共享配额、权限和预算
- 出事故后如何回滚、审计和复盘

可以说：

> 组件解决“某一段能做什么”，平台解决“整条链路如何稳定协同”。

所以如果只是把开源工具堆在一起，但没有统一的身份、状态、规则和流程，系统仍然会停留在“工具集合”，而不是“平台”。

## 第2章：算力、存储与网络

### 第1题：为什么说 AI 系统吞吐通常由最慢的一段决定？

**思路**

- 这题本质是木桶效应。
- 回答时要把“单点性能”和“端到端吞吐”区分开。

**参考答案**

AI 系统通常是一条串联链路，例如训练场景：

```text
存储读取 -> CPU 预处理 -> H2D 拷贝 -> GPU 计算 -> 梯度同步
```

在这种串联系统里，哪怕某一段非常快，只要其中一段明显更慢，整体吞吐仍会被这段限制。

粗略写法可以是：

$$
\text{effective throughput} \approx \min(\text{storage},\text{transfer},\text{compute},\text{network})
$$

举例：

- 如果 GPU 理论吞吐很强，但数据加载只能每秒供应 100 个样本，那么整体吞吐就不会超过 100。
- 如果单机算得很快，但多机梯度同步太慢，那么整体 step time 仍然会被通信拖长。

**结论**

所以端到端优化必须先找到最短板，而不是只优化最显眼的那一段。

### 第2题：对象存储、SSD、主存、显存分别适合放什么类型的数据？

**思路**

- 这题考察分层存储意识。
- 回答时要把“容量 / 延迟 / 带宽 / 用途”一起说清楚。

**参考答案**

| 层级 | 适合放什么 | 原因 |
|------|------------|------|
| 对象存储 | 原始数据、长期 checkpoint、模型仓库 | 容量大、成本低，但延迟高 |
| SSD / NVMe | 热点训练数据、本地缓存、临时中间结果 | 吞吐高，适合热路径缓存 |
| 主存 | dataloader 缓冲、预处理结果、运行中间态 | 延迟低，适合 CPU 侧快速访问 |
| 显存 | 模型权重、激活、batch 数据、KV Cache | 最接近 GPU 计算，带宽最高但最贵最稀缺 |

**一个合理分层示意**

```text
对象存储：存“长期和大”的东西
SSD：存“近期会重复用”的东西
主存：存“马上要处理”的东西
显存：存“此刻正在算”的东西
```

### 第3题：为什么网络既会影响训练吞吐，也会影响线上推理时延？

**思路**

- 关键是说明网络不仅存在于“分布式训练”。

**参考答案**

网络会影响训练吞吐，因为训练里有：

- 多机数据读取
- 分布式梯度同步
- 参数广播
- checkpoint 写远端存储

网络也会影响线上推理时延，因为推理链路通常不是单进程孤立运行，而会调用：

- 网关
- 特征服务
- 向量检索
- 重排器
- 下游安全过滤

所以网络在训练里更常体现为“吞吐下降或扩卡失效”，在推理里更常体现为“尾延迟恶化”。

### 第4题：请把一个训练 step 拆成至少 5 个时间段，并思考哪个最容易成为瓶颈

**思路**

- 这题要给出时间拆解和瓶颈判断方法。

**参考答案**

一个训练 step 可以拆成：

$$
t_{\text{step}} =
t_{\text{load}} +
t_{\text{preprocess}} +
t_{\text{h2d}} +
t_{\text{forward}} +
t_{\text{backward}} +
t_{\text{optim}} +
t_{\text{sync}}
$$

如果是单机，可以先忽略 `t_sync`；如果有 checkpoint 或日志，也可再加：

- `t_checkpoint`
- `t_logging`

**哪个最容易成为瓶颈？**

- 在早期系统里，常见是 `t_load` 或 `t_preprocess`
- 在大模型训练里，常见是 `t_h2d`、`t_backward` 或 `t_sync`
- 在多机训练里，`t_sync` 非常容易被低估

**排查建议**

先画这个时间分解，再用 profiler 或日志验证每一项占比，而不是凭感觉判断。

## 第3章：从模型实验到生产系统

### 第1题：为什么说“模型能跑起来”不等于“模型可以交付”？

**思路**

- 区分实验成功和交付成功。

**参考答案**

“模型能跑起来”只说明：

- 训练脚本可执行
- 有一组结果
- 在某个数据集或样例上看起来有效

但“模型可以交付”还意味着：

- 可复现：别人能用同样数据和配置重现结果
- 可发布：模型包、镜像、依赖和配置都能进入线上系统
- 可回滚：线上出问题时能快速切回上一版本
- 可观测：知道系统和模型是否退化
- 可治理：权限、成本、配额、审计都可控

所以交付成功比实验成功多了一整套平台和治理要求。

### 第2题：请画出一个从数据到训练、评测、发布、推理、反馈的完整链路

**参考架构**

```text
数据采集
  -> 清洗 / 去重 / 标注
  -> 数据版本
  -> 训练 Job
  -> checkpoint / 日志 / 指标
  -> 离线评测
  -> 模型注册
  -> staging 部署
  -> 灰度发布
  -> 在线推理
  -> 监控 / 用户反馈 / 人工审核
  -> 数据回流
  -> 下一轮训练
```

**参考答案**

这条链路最重要的不是节点数量，而是“每个节点都留下可追踪状态”：

- 数据有版本
- 训练有 job id
- 模型有 registry 版本
- 发布有灰度记录
- 线上有观测和反馈

只有这样，这条链才不是一次性的，而是真正的闭环系统。

### 第3题：与普通后端服务相比，模型发布多了哪些关键步骤？

**参考答案**

模型发布通常比普通代码发布至少多出这些步骤：

1. 离线评测
2. 回归集检查
3. 模型 / tokenizer / 配置一致性校验
4. 模型包注册
5. 质量灰度观察
6. 线上业务指标验证

也就是说，模型发布不只是“接口能不能通”，还要回答“结果是否仍然有业务价值”。

### 第4题：你的团队如果现在还处于“训练脚本 + 手工部署”阶段，最先应该补哪类平台能力？

**思路**

- 这题不是让你列全平台，而是选“第一块最值钱的能力”。

**参考答案**

优先补 **训练输出与模型发布之间的最小闭环**，也就是：

- 统一训练 Job 入口
- 统一保存 checkpoint / 配置 / 日志
- 简单模型注册表
- 简单离线评测门禁

原因是：

- 这是从“人肉交付”到“可重复交付”的第一步
- 比直接做复杂调度平台更快见效
- 没有这一步，后面的灰度、回滚和治理都无从谈起

**最小闭环示意**

```text
训练脚本
  -> 统一输出目录
  -> 评测结果
  -> 模型注册
  -> staging 服务
```

## 第4章：GPU 与加速器

### 第1题：为什么 GPU 选型不能只看峰值算力？

**参考答案**

因为峰值算力只说明“理论上最多能算多快”，不能说明：

- 模型能不能放下
- 数据能不能喂满
- 多卡能不能高效通信
- 线上冷启动和缓存是否合适

至少还要同时看：

- 显存容量
- 显存带宽
- 互联拓扑
- 驱动和软件栈兼容性
- 单位成本

所以选型应看“有效算力”，而不是只看“理论算力”。

### 第2题：训练和推理在硬件诉求上最大的差异是什么？

**参考答案**

训练更关注：

- 大显存
- 高带宽
- 多卡互联
- 长时间吞吐稳定

推理更关注：

- 单位成本吞吐
- 冷启动速度
- 显存复用
- 并发管理
- 尾延迟控制

简化理解：

> 训练更像“持续重负载生产”，推理更像“有波峰波谷的在线服务”。

### 第3题：用“算得动、放得下、喂得满、连得快”分析一个你熟悉的模型场景

**示例场景：13B LLM 在线推理**

**思路**

用四个问题拆解：

1. 算得动吗：单卡吞吐是否够
2. 放得下吗：权重 + KV Cache 是否能放进显存
3. 喂得满吗：请求量是否足以形成高效 batch
4. 连得快吗：如果多卡分片，互联是否足够

**参考答案**

- **算得动**：若请求量高且上下文中等，单卡 Tensor Core 吞吐通常足够支撑一部分流量
- **放得下**：13B 权重若用 FP16 很吃显存，再叠加 KV Cache，单卡可能放不下，需要量化或多卡
- **喂得满**：如果流量稀疏、请求长度差异大，实际利用率未必高
- **连得快**：如果模型分片到多卡，PCIe-only 环境可能导致 decode 受通信拖累

**结论**

这个场景下，最关键的不是单纯“算力高不高”，而是“显存和调度是否匹配”。

### 第4题：如果你的平台同时有 A100 80G 和 H200，哪些任务更适合优先放到 H200？

**参考答案**

更适合优先放到 H200 的通常是：

- 长上下文推理
- KV Cache 压力很大的在线服务
- 显存容量直接决定能否落地的 70B 级或多模态模型
- 需要减少跨卡切分、尽量单卡承载的任务

A100 80G 仍然非常适合：

- 常规训练
- 中等上下文在线服务
- 更看重吞吐 / 成本平衡而不是超大显存的任务

所以这里的判断重点不是“新卡一定更好”，而是：**哪类任务真的会被更大 HBM 容量和更高带宽直接解锁。**

## 第5章：内存、互联与 IO

### 第1题：为什么很多 AI 系统优化要从“数据怎么走”开始，而不是从“算子怎么写”开始？

**参考答案**

因为在很多实际系统里，计算并不是第一瓶颈。
更常见的问题是：

- 数据加载太慢
- 小文件太多
- H2D 拷贝过多
- 远端依赖过长
- checkpoint 回写拖慢训练

如果数据根本没能高效到达 GPU，再优化 kernel 往往没有明显收益。

### 第2题：PCIe、NVLink、RDMA 分别更影响哪些场景？

**参考答案**

| 技术 | 主要影响场景 |
|------|--------------|
| PCIe | CPU 和 GPU 之间的数据拷贝、设备接入 |
| NVLink | 同机多 GPU 训练、张量并行、大模型分片推理 |
| RDMA | 多机训练通信、低 CPU 参与的数据传输 |

可以这样记：

- PCIe：主机到设备
- NVLink：设备到设备（同机）
- RDMA：机器到机器

### 第3题：如果你的集群要从单机 8 卡扩到 4 个节点，你会优先比较哪些互联数字？

**参考答案**

我会优先比较四类数字：

1. **节点内 GPU 互联带宽**：NVLink / NVSwitch 到底多快，决定同机内 TP / PP 是否划算。
2. **节点间网络带宽**：例如 200Gb/s、400Gb/s IB / RoCE，决定跨机 AllReduce 上限。
3. **单机到网卡的拓扑**：GPU 到 NIC 是否走合理 PCIe / NUMA 路径，决定跨机通信的真实损耗。
4. **存储写入带宽**：如果训练还要频繁写 checkpoint，写盘路径也会和训练通信竞争。

简单说，扩到 4 节点后要看的已经不是“某个数字大不大”，而是：

- 节点内快不快
- 节点间快不快
- GPU 到 NIC 顺不顺
- 训练和存储会不会互相抢带宽

### 第4题：什么时候你会接受 TCP，而不是继续为 RoCE / RDMA 增加运维复杂度？

**参考答案**

当以下条件成立时，我会接受 TCP：

- 集群规模不大
- 训练任务以单机或少量多机为主
- 通信不是主瓶颈
- 团队当前更缺稳定运维，而不是极限通信性能

也就是说，如果你的主要目标还是：

- 先把平台跑稳
- 先把业务闭环跑通
- 当前 AllReduce 规模还不大

那么继续为 RoCE / RDMA 付出很高运维复杂度，未必划算。

更激进的高速互联通常在这些场景更值得：

```text
多机训练已成主流
通信开销明显吃掉扩卡收益
平台已经有能力维护更复杂的网络栈
```

### 第5题：为什么“并行文件系统做热层、对象存储做冷层”通常比只靠对象存储更适合训练集群？

**参考答案**

因为训练热路径同时要求：

- 稳定高吞吐读取
- 大量并发 worker 访问
- checkpoint 的持续大带宽写入

对象存储更擅长：

- 大容量
- 低成本
- 冷数据长期保存

但它对训练热路径常见的随机读取、小文件元数据访问和高并发写入并不友好。
所以更稳妥的工程分层通常是：

```text
对象存储：冷层、归档层
并行文件系统：热层、训练读写主路径
本地 NVMe：局部热点缓存
```

这样做的本质，是把“容量最优”和“训练 I/O 最优”拆开。

## 第6章：CUDA、运行时与算子执行

### 第1题：为什么大量小 kernel 往往会降低整体效率？

**参考答案**

因为每个 kernel launch 都有固定开销。如果一个任务被拆成大量很小的 kernel，就会出现：

- launch 开销占比变高
- 设备执行被频繁切碎
- 内存访问难以形成高效模式
- 调度和同步点变多

所以“很多小 kernel”常常意味着：

> 设备大部分时间不在做高价值计算，而在做频繁切换和等待。

### 第2题：同步点为什么会破坏计算与拷贝重叠？

**参考答案**

如果本来可以并行进行：

- 下一批数据拷贝
- 当前批次计算

但在中间插入同步点，那么系统就会强制等待上一阶段完全结束后再继续。
结果就是：

```text
原本：拷贝 || 计算
加入同步后：拷贝 -> 等待 -> 计算
```

也就是说，同步点会把本可以重叠的链路串行化。

### 第3题：在什么情况下应优先调用成熟库而不是自己拼很多算子？

**参考答案**

当问题属于高频通用算子时，应优先考虑成熟库，例如：

- GEMM
- 卷积
- 标准 attention
- 通信原语

原因是成熟库通常已经优化了：

- kernel 选择
- 内存布局
- 硬件适配
- 稳定性和边界处理

只有当：

- 现有库完全不支持
- 你的数据形状非常特殊
- 性能瓶颈已明确指向这一点

才值得投入自定义实现。

### 第4题：如果你发现 attention kernel 很快，但整体 step 仍然不快，你会继续检查哪一层？

**参考答案**

我会优先继续看“attention 之外的整条 step 链路”，尤其是：

1. 数据加载和 CPU 预处理
2. H2D 拷贝与 stream 重叠情况
3. 反向传播里其他算子是否更慢
4. 同步点、日志和 checkpoint 是否插入停顿
5. 通信或 optimizer step 是否在拖总时间

这道题想强调的是：**单个热点 kernel 很快，不等于整步就快。**

优化时一定要回到：

```text
load -> h2d -> forward -> backward -> optim -> sync
```

整条时间线看占比，而不是盯住一个“已经很快的局部”。

## 第7章：单机训练系统

### 第1题：为什么说多机训练前必须先掌握单机训练基线？

**参考答案**

因为多机训练会叠加更多变量：

- 通信
- 调度
- 节点差异
- checkpoint 分片

如果单机基线都不清楚，你根本无法判断：

- 多机性能差是通信问题，还是单机本来就没优化好
- loss 不稳定是并行问题，还是单机配置问题

一个合格的单机基线至少包括：

- step time
- 样本吞吐
- 显存占用
- GPU 利用率
- 数据加载时间占比

### 第2题：写出一个训练 step 的时间拆解式，并说明哪一项最容易被忽视

**参考答案**

$$
t_{\text{step}} =
t_{\text{load}} +
t_{\text{preprocess}} +
t_{\text{h2d}} +
t_{\text{forward}} +
t_{\text{backward}} +
t_{\text{optim}}
$$

最容易被忽视的通常是：

- `t_load`
- `t_preprocess`
- `t_checkpoint`（如果存在）

因为很多人天然只盯前向和反向，但真实系统常常先被供给链拖慢。

### 第3题：如果 GPU 利用率周期性掉到很低，你会优先怀疑什么？

**参考答案**

优先怀疑：

1. 数据加载断续
2. CPU 预处理跟不上
3. H2D 拷贝过慢
4. checkpoint / eval / logging 周期性插入

这是典型的“供给链锯齿”症状，而不一定是 GPU 算子本身有问题。

### 第4题：以 LLaMA 13B 为例，为什么只看参数显存会低估真实训练显存？

**参考答案**

因为 LLaMA 13B 的 BF16 参数显存大约只是 `26 GB` 量级，但训练时还要再叠加：

- 梯度
- 优化器状态
- 激活
- 临时 buffer
- 碎片

如果使用 Adam，一套优化器状态本身就可能再吃掉 `100 GB+` 的量级；再加上激活显存和运行时临时 buffer，真实训练开销会远大于“只放下权重”。

所以很多 13B 模型会出现这种现象：

- 推理能单卡勉强放下
- 训练却需要 AMP、激活重计算、状态分片或直接上多卡

这道题真正想说明的是：**训练显存预算必须按“参数 + 梯度 + 优化器 + 激活”整体估，而不是只看参数表。**

### 第5题：为什么 `nvidia-smi` 看起来很忙，不代表 MFU 一定高？

**参考答案**

因为 `nvidia-smi` 更接近“设备忙不忙”的信号，而 MFU（Model FLOPs Utilization）更接近“设备在做多少有效模型计算”的信号。

设备很忙，可能是因为：

- 等通信
- 做 H2D 搬运
- 被小 batch 和碎 kernel 切碎
- 被 checkpoint / pipeline bubble 干扰

这时 GPU utilization 可能很高，但真正落在模型有效 FLOPs 上的比例并不高。

所以工程上要区分：

- **Utilization**：卡是不是在忙
- **MFU**：忙出来的那部分有多少是有效训练吞吐

前者适合巡检，后者更适合评估训练系统优化是否真的有效。

## 第8章：数据并行

### 第1题：为什么数据并行扩展到多机后收益常常变差？

**参考答案**

因为扩卡带来的不是只有新增算力，还会引入新增通信。
多机时，AllReduce 和同步开销会增加，而且网络拓扑也更复杂。

收益变差的常见原因：

- `t_allreduce` 占比上升
- per-device batch 太小
- 数据供给跟不上
- 节点异构导致慢节点拖全局

### 第2题：ring all-reduce 中，梯度量和设备数如何影响通信成本？

**参考答案**

一个常用近似式是：

$$
\text{bytes per rank} \approx 2 \times \frac{N-1}{N} \times G
$$

其中：

- `N` 是设备数
- `G` 是梯度总字节数

这意味着：

- 梯度越大，通信成本越大
- 设备越多，协调越复杂
- 如果网络跟不上，新增设备带来的收益会越来越小

### 第3题：扩展效率下降时，你会优先从哪三类因素排查？

**参考答案**

优先看三类：

1. **通信因素**：AllReduce 占比、网络拓扑、NCCL 异常
2. **供给因素**：数据加载、CPU 预处理、H2D 拷贝
3. **训练配置因素**：batch、学习率、梯度累积、异构节点

这是因为效率下降未必完全是网络问题，也可能是你把单机瓶颈一起扩到了多机。

### 第4题：如果一个作业已经通信占比很高，checkpoint 策略为什么也要跟着改？

**参考答案**

因为这时训练 step 里已经存在一块很重的“全局停顿”成本：

- AllReduce / 同步本身就在拖长 step
- 如果 checkpoint 还是高频、同步式写盘，就会把停顿继续叠加上去

结果通常是：

- step 抖动更明显
- 有效训练吞吐下降
- 故障恢复收益不一定能抵掉保存开销

所以当通信已经很重时，checkpoint 策略也要一起重算，例如：

- 降低保存频率
- 切到异步 checkpoint
- 先写热层再后台转冷层

这道题想说明的是：checkpoint 不是独立模块，它会直接和通信成本一起决定真实 step time。

## 第9章：模型并行与流水并行

### 第1题：为什么数据并行无法解决“模型放不下单卡”的问题？

**参考答案**

因为数据并行默认每张卡都持有一份完整模型。
它解决的是“吞吐扩展”，不是“单卡内存不够”。

如果模型本身就放不下单卡，再复制多份只会更糟。

### 第2题：请解释张量并行和流水并行分别在“切什么”

**参考答案**

- **张量并行**：切层内部的矩阵计算
- **流水并行**：按层段切模型

简单理解：

```text
张量并行：切单层内部
流水并行：切层与层之间
```

### 第3题：ZeRO Stage 1/2/3 的区别是什么？为什么它和 TP / PP 是互补关系？

**参考答案**

三者的区别在于“切掉哪一部分冗余训练状态”：

| 方案 | 主要切分对象 | 典型收益 | 典型代价 |
|------|--------------|----------|----------|
| ZeRO Stage 1 | Optimizer state | 先把优化器状态显存压下来 | 参数和梯度仍然全量保留 |
| ZeRO Stage 2 | Optimizer state + Gradients | 进一步降低反向阶段显存 | 通信更多，反向链路更复杂 |
| ZeRO Stage 3 | Optimizer state + Gradients + Parameters | 单卡状态占用最低 | gather / shard 和恢复流程最复杂 |

它和 TP / PP 是互补关系，而不是替代关系：

- TP / PP 解决的是“单层算不动”或“整模放不下”的结构性切分问题
- ZeRO / FSDP 解决的是“训练状态冗余太重”的显存问题
- 超大模型训练里，经常同时存在“算子太大”和“状态太重”两类约束，所以需要叠加使用

一个常见组合是：

```text
TP / PP 负责切模型结构
ZeRO / FSDP 负责切训练状态
DP 负责做吞吐扩展
```

### 第4题：如果你的模型已经用了 TP 和 PP，checkpoint 设计为什么还要跟着调整？

**参考答案**

因为 TP / PP 会改变“状态分散在哪些设备上、如何重新拼回完整模型”。

这会直接影响 checkpoint 的四个方面：

1. **保存粒度**：是每卡各写自己的 shard，还是聚合后再写。
2. **恢复方式**：恢复时是否要求相同并行拓扑，还是支持重分片加载。
3. **写入耗时**：并行切分越复杂，写盘前 gather / 同步 的成本越高。
4. **元数据要求**：必须记录 TP / PP 拓扑、stage 映射、rank 到 shard 的对应关系。

所以当你已经用了 TP 和 PP，checkpoint 不能再只被当成“存一个模型文件”，而是要被当成“存一套分布式训练状态拓扑”。

平台侧常见做法是：

- 分片保存训练状态
- 额外记录拓扑与版本元数据
- 同时保留一份更易分发的推理权重导出物

### 第5题：为什么 128K+ 上下文训练通常要开始讨论 Context Parallelism？

**参考答案**

因为当序列长度继续拉长时，attention 相关的激活和 KV 开销会迅速放大，问题不再只是“参数放不放得下”，而是“长上下文本身的中间状态放不放得下”。

这时只靠：

- 数据并行
- 张量并行
- 流水并行

往往还不够，因为它们主要解决的是模型结构或训练状态的切分问题，不直接把超长序列本身拆开。

Context Parallelism 的价值就在于：

- 直接沿序列维度切 attention 计算
- 让每张卡只持有一段上下文相关状态
- 用额外通信换长上下文可训练性

所以一旦进入 `128K+` 训练，平台往往就要从“切模型”升级到“连上下文也一起切”。

## 第10章：内存优化、检查点与恢复

### 第1题：为什么训练阶段的显存占用远不止模型参数本身？

**思路**

- 训练显存既有静态状态，也有运行时状态。
- 回答时先把账本拆开，后面几题就会顺很多。

**参考答案**

训练阶段的显存通常至少包括：

- 参数本体
- 梯度
- 优化器状态
- 激活
- 临时 / 通信 buffer

粗略可写成：

$$
M_{\text{train}} \approx M_{\text{params}} + M_{\text{grads}} + M_{\text{optim}} + M_{\text{acts}} + M_{\text{temp}}
$$

这就是为什么训练比推理更容易 OOM。推理时很多状态根本不存在，训练却要把“学会更新自己”所需的上下文一起装进显存。

**延伸提醒**

- 很多团队高估了权重、低估了激活和优化器状态。

### 第2题：假设参数使用 BF16、优化器使用 Adam，请粗略说明为什么参数相关状态可能达到“参数本体数倍”。

**思路**

- 题目要的是数量级直觉，不是精确到实现细节。
- 按“一个参数要存几份状态”来算最直接。

**参考答案**

对一个参数，常见账本大致是：

- BF16 参数：`2 bytes`
- BF16 梯度：`2 bytes`
- Adam 一阶矩 `m`：`4 bytes`
- Adam 二阶矩 `v`：`4 bytes`
- 某些实现还保留 FP32 master weight：`4 bytes`

所以参数相关状态可能达到：

```text
12-16 bytes / param
```

而参数本体自己只有 `2 bytes`。这就是为什么即使模型权重只占 14 GB，完整训练状态也能轻松上到数倍。

**延伸提醒**

- ZeRO / FSDP 的价值之一，就是把这些状态分片掉，而不是让每张卡都背全量。

### 第3题：激活重计算的收益和代价分别是什么？它更适合哪类瓶颈场景？

**思路**

- 这是典型的“算力换显存”。
- 最好同时回答收益、代价和适用场景。

**参考答案**

收益：

- 降低激活显存占用
- 支持更大 batch、更长序列或更大模型

代价：

- 反向需要重跑部分前向，step time 增加
- 图更复杂，调试和定位性能问题更难

它更适合明显是显存瓶颈、而不是算力瓶颈的训练，比如长上下文训练或激活占用很高的模型。

**延伸提醒**

- 如果作业本来就算不满 GPU，再做重计算只会进一步拖慢吞吐。

### 第4题：为什么使用 ZeRO / FSDP 后，checkpoint 设计不能再停留在单文件思维？

**思路**

- 关键不在“文件几个”，而在“状态已经分散”。

**参考答案**

ZeRO / FSDP 下，参数、梯度、优化器状态都可能分散在不同 rank 上。checkpoint 需要解决的问题变成：

- 每个 shard 由谁保存
- 恢复时怎样聚合或重新映射
- world size 变化后怎么兼容
- 哪个版本才算完整提交

所以它更像“带 manifest 的分布式快照”，而不是一个单一模型文件。

**延伸提醒**

- 只导 full state dict 虽然简单，但在大模型上很可能让保存过程本身成为瓶颈。

### 第5题：`torch.save`、SafeTensors、分布式 checkpoint 各更适合什么场景？

**思路**

- 没有唯一最优，关键看目标是“恢复训练”还是“安全发布”。

**参考答案**

| 方案 | 更适合什么场景 | 主要短板 |
|------|----------------|----------|
| `torch.save` | 单机实验、快速原型、最小接入成本 | 强依赖 Python / pickle，安全性和跨环境兼容性一般 |
| SafeTensors | 发布权重、模型交换、推理加载 | 更像安全权重格式，不等于完整训练状态 |
| 分布式 checkpoint | FSDP / ZeRO / 多机训练恢复 | 接入复杂，但最适合保存分片训练状态 |

如果目标是继续训练，就优先关心状态是否完整；如果目标是安全下发权重，就优先关心格式安全和加载稳定性。

**延伸提醒**

- “能加载权重”不等于“能无缝恢复训练”。

### 第6题：为什么训练 checkpoint 和部署权重包不应混为一谈？

**思路**

- 训练恢复和线上发布服务的是两种完全不同的目标。

**参考答案**

训练 checkpoint 面向“从中断点继续训练”，通常包含：

- 模型参数
- 优化器 / scheduler 状态
- RNG state
- 数据游标
- 当前 step

部署权重包面向“稳定推理或发布”，通常更关注：

- 已验收权重
- tokenizer / config
- 推理元数据
- 版本、来源和校验信息

把两者混在一起的问题是：训练包太重、不适合分发；部署包又缺少恢复训练的关键状态。

**延伸提醒**

- 成熟平台通常会同时维护 `train state` 和 `deployable artifact` 两条工件线。

### 第7题：设计一个适合长训练任务的 checkpoint 保存与清理策略。

**思路**

- 要同时回答保存频率、保留策略和防半成品机制。

**参考答案**

一个最小可执行策略可以是：

```yaml
checkpoint_policy:
  every_n_steps: 1000
  every_n_hours: 2
  keep_recent: 3
  keep_daily: 2
  keep_best_by_eval: 2
  manifest_required: true
  latest_pointer: separate
  cleanup_only_after_commit: true
```

设计理由是：

- 按 step 和按墙钟双触发，避免长 step 时恢复点过稀
- 最近版本保证快速恢复
- 日级和 best 版本兼顾回滚与评测
- `latest` 与实际文件分离，防止半写入污染
- 清理只删除已提交成功的旧版本

**延伸提醒**

- 长训练不要只按 step 存，因为 step 一变慢，实际可丢失时间会突然变大。

### 第8题：为什么异步 checkpoint 虽然减少阻塞，却会增加系统复杂度？

**思路**

- 收益是减少训练线程停顿，复杂度则转移到了后台状态管理。

**参考答案**

异步 checkpoint 能减少主训练循环的阻塞，但同时引入：

- 后台写入失败如何回报主训练器
- 多个未完成 snapshot 如何排序与取消
- 存储跟不上时如何做背压
- 恢复时如何识别哪些版本是完整提交的

所以它不是“白拿性能”，而是把问题从前台阻塞换成后台一致性和并发控制。

**延伸提醒**

- 没有 manifest 和 commit 标记的异步 checkpoint，恢复时最容易踩坑。

### 第9题：什么情况下自动重试有意义，什么情况下自动重试只会放大问题？

**思路**

- 把故障分成瞬时性和确定性，判断就很容易。

**参考答案**

适合自动重试的情况：

- 瞬时网络抖动
- 节点短暂失联
- 对象存储偶发超时
- 可从 checkpoint 安全恢复的 preemptible 中断

不适合自动重试的情况：

- 稳定 OOM
- 配置错误
- 数据损坏
- 代码 bug
- checkpoint 本身已坏

前者重试能穿过偶发故障；后者重试只是重复烧资源。

**延伸提醒**

- 好的重试策略是“按错误类型分流”，不是“失败就重跑”。

### 第10题：为什么弹性训练对 checkpoint 的要求比普通重试更高？

**思路**

- 普通重试通常假设拓扑不变，弹性训练不保证这一点。

**参考答案**

普通重试一般默认：

- world size 不变
- rank 拓扑不变
- 只是原 worker 重新拉起

弹性训练则可能：

- 掉几台机器后缩容继续跑
- 之后再扩容回来
- 让 rank 重新分配

因此 checkpoint 需要支持：

- shard 重新映射
- rendezvous 元数据恢复
- world size 变化后的加载
- 数据游标和随机性的一致性重建

这就是为什么弹性训练更依赖带元数据的分布式 checkpoint，而不是简单文件重读。

**延伸提醒**

- 如果 checkpoint 没记并行策略和 shard 布局，弹性恢复通常只是口号。

## 第10b章：对齐训练与后训练基础设施

> **编号映射说明**：本节练习已于 2026-05 改用 `练习 10b-N（基础/进阶/设计）` 形式，与正文练习题一一对应。原"第 1 题 ... 第 17 题"对应当前 `练习 10b-1 ... 练习 10b-17`。基础题 = 10b-1 至 10b-6，进阶题 = 10b-7 至 10b-13，设计题 = 10b-14 至 10b-17。

### 练习 10b-1（基础）：post-training 和 alignment training 的关系是什么？为什么不能把两者完全等同？

**思路**

- 关键是集合关系，而不是两个词谁包含谁。

**参考答案**

更合适的关系是：

```text
pretraining
  -> post-training
       -> alignment training
```

其中：

- `post-training` 是预训练之后的一整条塑形流程，常见包括 SFT、偏好优化、安全整形、工具使用整形、评测放行
- `alignment training` 是其中一个重要子集，重点在让模型行为更符合偏好、规则和产品约束

不能完全等同的原因是：

- 并不是所有 post-training 都在做偏好对齐
- 某些蒸馏、格式整形、领域适配也属于 post-training
- alignment 也不只等于 RLHF

**延伸提醒**

- 如果把 post-training 直接缩成“PPO / DPO”，会漏掉大量真实工程环节。

### 练习 10b-2（基础）：为什么 PPO 的基础设施形态不能简单等同于 pretraining？至少列出 3 个维度的差异。

**思路**

- 负载形态、模型数量、时间结构三条线最容易答完整。

**参考答案**

PPO 和 pretraining 至少有三类关键差异：

1. 负载类型不同
   pretraining 主要是训练负载；PPO 同时混合 rollout 推理、reward 打分和训练更新。

2. 模型角色不同
   pretraining 常以单模型为中心；PPO 通常至少涉及 policy、reference、critic、reward model 多角色协同。

3. step 结构不同
   pretraining 常是 `forward -> backward -> step`；PPO 先 rollout，再打分，再算优势，再更新，链路更长。

所以 PPO 的瓶颈往往不只在训练卡，还在 rollout 引擎、RM 吞吐和多模型状态管理。

**延伸提醒**

- 训练卡很强但 rollout 很慢时，PPO 一样会整体跑不动。

### 练习 10b-3（基础）：用 LLaMA-7B bf16 全量训练粗估 policy 的参数、梯度、Adam optimizer 显存，为什么会接近 84GB？

**思路**

- 这题直接按份数相加即可。

**参考答案**

7B 参数量在 BF16 下可粗估为：

- 参数：`7B × 2 bytes ≈ 14 GB`
- 梯度：`7B × 2 bytes ≈ 14 GB`
- Adam 一阶矩：`7B × 4 bytes ≈ 28 GB`
- Adam 二阶矩：`7B × 4 bytes ≈ 28 GB`

合计约：

```text
14 + 14 + 28 + 28 = 84 GB
```

这还没算激活和临时 buffer，所以 84GB 只是 policy 训练状态的地板，不是完整峰值。

**延伸提醒**

- 这就是为什么全量 PPO 很容易先被显存而不是算力卡住。

### 练习 10b-4（基础）：DPO 的偏好对数据一般包含哪些字段？为什么 chosen/rejected 必须来自同一个 prompt？

**思路**

- 先写最小字段，再解释同 prompt 的因果意义。

**参考答案**

一个最小 DPO 偏好样本通常包含：

- `prompt`
- `chosen`
- `rejected`
- 数据版本 / 来源
- 可选元数据，如任务标签、采样参数、标注人信息

`chosen` 和 `rejected` 必须来自同一个 prompt，因为 DPO 学的是“在同一条件下，哪个回答更被偏好”。如果 prompt 不同，模型学到的就混进了任务差异，偏好信号会被污染。

**延伸提醒**

- prompt 模板和采样参数也应进 lineage，否则偏好对质量很难排查。

### 练习 10b-5（基础）：Reward Model 适合和训练节点共置还是独立服务？请分别说明模型大小、吞吐和显存余量对决策的影响。

**思路**

- 没有统一答案，要按资源约束判断。

**参考答案**

共置更适合：

- RM 较小
- 打分频率不高
- 训练卡有显存余量
- 团队想先用最短路径验证

独立服务更适合：

- RM 较大或调用频繁
- rollout 量大，打分容易成为瓶颈
- 训练卡显存已经紧张
- 需要独立扩缩容和熔断保护

本质判断是：你更怕“多一段网络跳转”，还是更怕“训练卡被 RM 挤爆”。

**延伸提醒**

- RLHF 里的 RM 往往不是“一个小模块”，而是训练内环里的推理子系统。

### 练习 10b-6（基础）：如果一个 PPO 作业要支持恢复，checkpoint 至少应额外保存哪些状态？

**思路**

- PPO 恢复的是过程，不是单个模型。

**参考答案**

除了 policy 权重，至少还应保存：

- critic / value model 权重与 optimizer 状态
- policy optimizer 状态
- rollout buffer 或其边界信息
- KL controller、reward normalization 等运行中控制器状态
- 当前 global step、数据游标、RNG state

否则恢复出来的只是一个“像原来 policy 的模型”，不是原本那条 PPO 训练轨道。

**延伸提醒**

- rollout buffer 如果无法完整恢复，至少要能从明确边界安全重采样。

### 练习 10b-7（进阶）：假设你要在 8×H100 80GB 上给 7B 模型做全量 PPO，按 policy ~84GB、critic ~84GB、ref ~14GB、RM ~14GB、KV Cache ~10-60GB 估算总账本，并说明为什么总显存够不代表不会 OOM。

**思路**

- 先算 aggregate，再解释为什么 aggregate 不等于 per-GPU placement。

**参考答案**

粗略总账本是：

```text
policy   ~84 GB
critic   ~84 GB
ref      ~14 GB
RM       ~14 GB
KV Cache ~10-60 GB
-------------------
合计约 206-256 GB
```

8×H100 80GB 的总 HBM 是 `640 GB`，aggregate 看似放得下，但这不等于每张卡都放得下，因为还要考虑：

- 模型切分方式
- 激活、通信 buffer、临时张量
- KV Cache 的热点分布
- allocator 碎片
- rollout 与更新阶段的瞬时峰值

所以真实风险往往不是总和爆掉，而是某个 rank 的局部峰值先 OOM。

**延伸提醒**

- 显存预算一定要做到“按角色、按阶段、按卡”三层。

### 练习 10b-8（进阶）：某团队有 20 万条高质量 chosen/rejected 偏好对、没有稳定 RM、只有 SFT 训练平台。它应优先选 DPO、PPO 还是 GRPO？说明理由和风险。

**思路**

- 先看现有资产，再看最小实现路径。

**参考答案**

最应优先选 `DPO`。

理由是：

- 已经有高质量 preference pairs，正好匹配 DPO 输入
- 没有稳定 RM，做 PPO 的关键前提不成立
- 只有 SFT 平台，DPO 最容易复用现有训练栈

不优先选 PPO 的原因：

- 还要补 RM、rollout、critic、多模型恢复等整套基础设施

不优先选 GRPO 的原因：

- 它更适合有可程序化或可批量评估 reward 的任务，而不是纯人工偏好对资产

主要风险是：

- 偏好数据覆盖不足时，DPO 容易把离线偏好学死
- 没有在线探索，某些交互式任务提升有限

**延伸提醒**

- 很多团队的现实路线是 `SFT -> DPO -> 再决定是否值得补 PPO / GRPO`。

### 练习 10b-9（进阶）：GRPO 相比 PPO 省下了 critic，但代价是"每个 prompt 要采样 16-64 个 response"。在什么样的任务和硬件配置下，GRPO 会比 PPO 更划算？反过来什么情况下不划算？

**思路**

- 对比的是“省显存”和“增采样成本”两本账。

**参考答案**

GRPO 更划算的场景：

- 任务有便宜、稳定、可程序化的 reward
- 单条 response 可高效批量评估
- rollout 推理吞吐强，但训练显存偏紧
- 希望避免 critic 带来的额外复杂度

不划算的场景：

- reward 本身昂贵或需要复杂 judge
- 推理吞吐不足，16-64 次采样会把成本放大得过头
- 任务结果高度开放，组内相对比较不稳定
- GPU 紧缺到连大 batch rollout 都做不起

**延伸提醒**

- GRPO 省掉的是 critic，不是 rollout 账单。

### 练习 10b-10（进阶）：你发现训练中 reward 越来越高但人工抽查觉得质量变差了。这是什么现象？在基础设施层面应该怎样提前预警？

**思路**

- 先识别现象，再给平台层监控。

**参考答案**

这通常是 `reward hacking` 或 `reward over-optimization`：模型越来越会讨好当前奖励信号，但不一定越来越符合真实质量。

平台应至少同时看：

- reward 曲线
- 人工抽检或 judge win-rate
- KL 偏离
- 响应长度分布
- refusal / safety 指标

如果出现“reward 上升，但 win-rate、抽检或安全指标下降”，就应触发告警、暂停放量或回退到更稳的 checkpoint。

**延伸提醒**

- 单看 reward 曲线就放行，是后训练里最常见的误判之一。

### 练习 10b-11（进阶）：KL 系数调得过大或过小分别会带来什么模型行为和系统指标变化？平台应如何监控和自动干预？

**思路**

- 题目要同时说行为和指标变化。

**参考答案**

KL 系数过大时：

- 模型被 reference 拉得太紧
- 输出更保守、更像原模型
- reward 提升慢，训练可能接近停滞

KL 系数过小时：

- 模型更容易漂离 reference
- reward 可能先冲高，但行为更不稳定
- 容易出现长度膨胀、风格漂移、安全退化

平台应监控：

- 平均 / P95 KL
- reward
- win-rate
- 输出长度
- 安全指标

自动干预可以做成：

- KL 超上限时上调系数或减小学习率
- KL 长期过低且 reward 停滞时适度下调系数
- 越过硬阈值时停止训练并保留最近稳定点

**延伸提醒**

- KL controller 最好和 checkpoint 一起保存，否则恢复后行为会突然变样。

### 练习 10b-12（进阶）：rollout 长度从 512 增加到 2048，会如何影响 KV Cache、RM 打分吞吐、step time 和 checkpoint 频率？

**思路**

- 长度扩 4 倍后，很多成本会近似线性放大。

**参考答案**

把 rollout 从 `512` 拉到 `2048`，常见影响是：

- KV Cache 近似放大到 `4x`
- RM 打分 token 数显著增加，吞吐下降
- rollout 和更新的 step time 都会变长
- 如果 checkpoint 仍按 step 保存，墙钟意义上的恢复点会变稀

因此通常要同步：

- 收紧并发或 batch
- 改成按墙钟和按 step 双触发 checkpoint
- 重新评估 RM 服务批大小和超时

**延伸提醒**

- rollout 变长时，先出问题的往往是 KV Cache 和临时缓冲，不一定是权重。

### 练习 10b-13（进阶）：对同一批 rollout，选择"全量打分"和"流式打分"分别会怎样影响 RM 服务的吞吐、尾延迟、重试语义和训练器复杂度？

**思路**

- 这题适合做维度对照。

**参考答案**

| 方案 | 吞吐 | 尾延迟 | 重试语义 | 训练器复杂度 |
|------|------|--------|----------|--------------|
| 全量打分 | 更容易做大 batch，吞吐高 | 最慢样本拖尾更明显 | 失败时常要重做整批 | 更简单 |
| 流式打分 | 批处理效率较弱 | 更平滑，可边到边出 | 可按样本或小块重试 | 需要处理增量结果和乱序 |

工程上没有绝对更好，取决于你更看重 GPU 利用率还是恢复语义与尾延迟。

**延伸提醒**

- RM 一旦跨机部署，流式方案通常更容易和背压机制配合。

### 练习 10b-14（设计）：你的团队现在只有 4 张 A100 80GB，想做 7B 模型的对齐训练。给出一个从 SFT → 偏好优化 → 上线的完整路线图，说明每一步选什么算法、为什么。

**思路**

- 资源有限，路线必须现实，不要一上来全量 PPO。

**参考答案**

更可执行的路线通常是：

1. `SFT`
   先用 LoRA 或 QLoRA 打出稳定基线，成本最低。

2. `DPO`
   如果已有 preference pairs，优先做 DPO，因为最能复用现有 SFT 栈。

3. `离线评测 + shadow`
   先验证质量和稳定性，再进入真实流量环境。

4. `必要时再评估 GRPO / PPO`
   只有当任务存在明确可验证 reward，且 DPO 提升不够时，再考虑更重的方案。

5. `canary 上线`
   新老版本并存，保留快速回滚。

**延伸提醒**

- 对 4 张 A100 来说，最大的风险通常不是算法落后，而是基础设施复杂度先把自己拖垮。

### 练习 10b-15（设计）：设计一个 PPO 多模型 checkpoint 恢复策略：如何组织 policy、critic、reference、RM、rollout buffer、KL controller 和数据游标？恢复时应做哪些一致性校验？

**思路**

- 题目要的是恢复协议，不是目录美观。

**参考答案**

一个最小组织方式可以是：

```text
ckpt/
  step-12000/
    manifest.json
    policy/
    critic/
    reference/
    reward_model/
    optimizers/
    rollout/
    controllers/
    dataloader_state.json
```

`manifest.json` 至少记录：

- global step
- 各子模型版本、hash、并行策略
- rollout buffer 边界
- KL controller / reward norm 状态
- 数据游标与 RNG state

恢复时应校验：

- 所有子目录是否来自同一 step
- 文件 hash 与 manifest 是否一致
- world size / parallel config 是否兼容
- tokenizer、prompt 模板、数据版本是否匹配
- rollout buffer 是否完整；不完整则回退到安全边界

**延伸提醒**

- `reference` 一旦版本漂移，训练语义也会漂。

### 练习 10b-16（设计）：设计一个 LLM-as-judge 评测 pipeline：从 checkpoint 产生到 quick-eval、judge 打分、门禁、失败样本回流，说明每一步记录哪些版本信息。

**思路**

- 重点在版本可追溯，而不是流程多花哨。

**参考答案**

一个最小 pipeline 可以是：

```text
checkpoint 产出
-> 导出 deployable artifact
-> quick-eval 小样本冒烟
-> judge 批量打分
-> 门禁决策
-> 失败样本回流数据池
```

每一步至少记录：

- 被评模型版本 / hash
- tokenizer 与 prompt bundle 版本
- judge 模型版本与 judge prompt 版本
- 评测集版本
- 采样参数
- 时间戳、运行任务 ID

这样分数变化时，才能分清是被评模型变了，还是 judge、数据集、prompt 规则变了。

**延伸提醒**

- judge 本身也是模型，必须像生产依赖一样治理版本漂移。

### 练习 10b-17（设计）：某团队声称他们"用 DPO 完全替代了 PPO，效果一样还更省钱"。结合本章内容，你会问他们哪些问题来判断这个结论是否可靠？

**思路**

- 重点不是反驳，而是验证比较是否公平。

**参考答案**

我会先问：

- 比的是什么任务，是否需要在线探索或长期交互？
- DPO 和 PPO 用的是同一套评测集、同一套 judge 吗？
- 成本是否把数据标注、评测和运维都算进去了？
- 是否比较了稳定性、安全性和长度控制，而不只是平均分？
- 结论是一轮实验，还是多 seed、多版本后的稳定结果？
- “效果一样”是所有场景都一样，还是只在当前离线分布上一样？

只有这些问题都回答得住，“完全替代”才可能成立。

**延伸提醒**

- 很多“更省钱”的结论，省掉的其实只是没被记账的那部分成本。

## 第10c章：Fine-Tuning 基础设施与多 Adapter 服务

### 第1题：为什么 fine-tuning 任务不应该和 pretraining 任务共用同一资源队列？

**思路**

- 关键不是模型名字，而是任务形态差异。

**参考答案**

因为两者的资源曲线差异很大：

- pretraining：长作业、大 GPU、固定拓扑、对中断极敏感
- fine-tuning：短作业、高频提交、资源粒度更碎、通常更能接受排队或抢占

如果塞进同一队列，常见后果是：

- 长任务把短任务压住
- 短任务把大作业切碎
- 一个调度策略无法同时满足两类目标

所以更合理的做法是拆队列、拆配额、拆 SLA。

**延伸提醒**

- FTaaS 追求的往往是周转效率，而不是单任务极限吞吐。

### 第2题：LoRA 和 QLoRA 的平台意义分别是什么？它们分别改变了训练侧和服务侧的哪些成本结构？

**思路**

- 题目要求同时回答训练侧和服务侧。

**参考答案**

LoRA 的平台意义是：把“全量微调”改成“只训练少量增量参数”，训练侧直接降低显存和 GPU 规模要求。

QLoRA 更进一步：把 base model 也压到更低精度，训练侧能在更小显存上跑更多作业。

它们对成本结构的影响是：

- 训练侧：显存门槛下降，更多作业能复用中小 GPU
- 服务侧：更容易形成“base model 常驻 + adapter 动态切换”的 Multi-LoRA 形态

**延伸提醒**

- QLoRA 降的是训练门槛，不等于线上服务一定要采用相同精度。

### 第3题：从平台角度看，为什么说 adapter 是“一等制品”，而不是训练脚本顺手导出的一个小文件？

**思路**

- 小文件和低治理要求不是一回事。

**参考答案**

adapter 虽然小，但它仍然直接决定模型行为，所以平台必须把它当成一等制品来管理：

- 要有版本号和来源
- 要绑定 base model、tokenizer、prompt 模板
- 要经过评测和门禁
- 要支持回滚、审计和权限控制

如果只是把它当成一个小文件，最后会出现“文件在，但不知道适配哪个 base、有没有验收、能不能上线”的治理真空。

**延伸提醒**

- 小文件不等于低风险，行为变化照样可能很大。

### 第4题：画出一个 FTaaS 的任务状态机，并解释为什么 `training succeeded`、`evaluation passed`、`deployable` 必须是三个不同状态。

**思路**

- 本质是在区分“训练成功”“质量合格”“可交付”。

**参考答案**

一个最小状态机可以是：

```text
queued
-> scheduled
-> running
-> training_succeeded
-> evaluation_passed
-> registry_registered
-> deployable
-> deployed
```

三者必须分开的原因是：

- `training succeeded`：只是训练过程没报错
- `evaluation passed`：说明质量和安全门禁过了
- `deployable`：说明兼容性、元数据、注册流程都完成了

把它们揉成一个状态，平台就无法精确定位失败位置，也无法定义清晰门禁。

**延伸提醒**

- 很多线上事故正是把“训完了”误当成“能发布了”。

### 第5题：训练完成后，为什么还要插入自动评测、兼容性检查、registry 注册和服务热加载，而不是直接把 adapter 交给业务方使用？

**思路**

- 训练完成只证明产物存在，不证明可用。

**参考答案**

中间步骤的作用分别是：

- 自动评测：确认质量、安全、稳定性
- 兼容性检查：确认 base model / tokenizer / prompt 版本匹配
- registry 注册：给产物正式身份、元数据和权限
- 服务热加载：验证线上加载路径和回滚路径

如果直接把 adapter 丢给业务方，平台就失去版本治理和上线门禁。

**延伸提醒**

- FTaaS 真正交付的不是一个文件，而是一份“可上线的已验收变体”。

### 第6题：如果某个 FTaaS 任务因为节点重启而失败，控制面应如何区分“自动重试”与“直接失败”的条件？

**思路**

- 先区分基础设施瞬时故障和任务本身不可恢复。

**参考答案**

适合自动重试的条件：

- 失败原因明确是节点中断、pod 驱逐、瞬时网络故障
- 最近 checkpoint 完整可用
- 重试不会造成重复写 registry 或重复发布

适合直接失败的条件：

- 稳定 OOM、配置错误、数据损坏
- 没有可恢复 checkpoint
- 已超过重试上限

控制面最好把错误原因标准化成可机判类型，而不是只看退出码。

**延伸提醒**

- 没有错误分类的自动重试，通常只是自动烧钱。

### 第7题：请基于公式 `总显存 ≈ base_model_size + N × adapter_size + concurrent_requests × kv_cache_per_request`，说明在 Multi-LoRA 场景下为什么只盯 adapter 文件大小会低估显存风险。

**思路**

- 题目给了公式，重点是指出哪一项才是大头。

**参考答案**

只看 adapter 文件大小会低估风险，因为：

- base model 常驻显存通常是最大固定项
- 并发请求的 KV Cache 会随上下文和输出长度剧烈波动
- adapter 虽小，但数量多后也会叠加

所以真正把系统推向 OOM 的，常常是“常驻 base + 突发 KV + 热层 adapter”叠在一起，而不是某一个 adapter 文件太大。

**延伸提醒**

- 平台如果只给 adapter 配额，不给并发和 KV 配额，风险仍然不可控。

### 第8题：假设一个 base model 常驻占 18 GB，单个 adapter 为 120 MB，GPU 热层放 40 个 adapter，同时有 24 个并发请求、每个请求平均消耗 180 MB KV cache。粗略估算总显存占用，并讨论是否还需要额外安全余量。

**思路**

- 先套公式，再解释为什么这个结果不能当硬上限。

**参考答案**

粗略估算：

- base model：`18 GB`
- adapter：`40 × 0.12 GB = 4.8 GB`
- KV Cache：`24 × 0.18 GB = 4.32 GB`

合计约：

```text
27.12 GB
```

但线上仍应预留额外安全余量，因为还没算：

- allocator 碎片
- 临时张量
- 热切换瞬间双份 adapter
- 请求长度波动带来的 KV 峰值

工程上通常还会留 20-30% 余量。

**延伸提醒**

- 容量规划最好用 P95 / P99 KV 占用，而不是平均值。

### 第9题：Multi-LoRA 中 adapter 数量上限为什么不只由显存决定，还会被切换延迟和路由复杂度约束？

**思路**

- 题目要把静态容量和动态控制面成本分开。

**参考答案**

即使显存放得下，adapter 数量也还会受到两类限制：

1. 切换延迟
   adapter 越多，冷加载、热切换、预取和驱逐的复杂度越高，尾延迟更难稳住。

2. 路由复杂度
   请求需要准确命中对应 adapter，版本、租户、权限、A/B 分流都会让路由规则膨胀。

所以 adapter 上限不只是“还能塞几个文件”，而是“还能不能在目标 SLA 下正确切换”。

**延伸提醒**

- 很多 Multi-LoRA 服务先撞上的不是 OOM，而是切换抖动和错路由。

### 第10题：设计一个 adapter 热加载 / 热卸载策略，说明 LRU 驱逐与预加载分别解决什么问题，各自可能带来什么副作用。

**思路**

- 这是缓存题，要同时说收益和副作用。

**参考答案**

一个可行策略是：

- 热层保留近期最常用 adapter
- 新请求到来时，如果目标 adapter 不在热层，则触发加载
- 低热度 adapter 按 LRU 驱逐
- 对预期热点版本提前预加载

其中：

- `LRU` 解决热层空间有限时的自动淘汰
- `预加载` 解决大促、灰度或已知热点流量的冷启动

副作用分别是：

- LRU：可能误驱逐周期性热点，导致抖动
- 预加载：可能把不该常驻的版本提前占满显存

**延伸提醒**

- 热加载策略最好接入租户级流量预测，而不是只看全局热度。

### 第11题：为什么 base model 升级后，已有 LoRA adapter 往往需要重新训练或重新验收？请从“权重空间绑定”角度解释。

**思路**

- 关键词就是“权重空间绑定”。

**参考答案**

LoRA 学到的是“相对于某个 base 权重空间的增量”。当 base model 升级后：

- 底层权重分布变了
- 激活路径和表征空间可能也变了

于是旧 adapter 不再是“在同一空间里的微调”，而可能变成“打在另一张底图上的补丁”。结果可能是效果下降、风格漂移或评测失真。

**延伸提醒**

- “同一家族的小版本应该没事”是很危险的侥幸心理。

### 第12题：如果平台要做 base model 灰度升级，为什么更稳妥的方式是让新旧 base 并存，而不是直接原地替换？请说明流量分割和回滚策略。

**思路**

- 原地替换会让灰度、回滚和定位同时变难。

**参考答案**

新旧 base 并存更稳妥，因为它允许：

- 按租户或按比例做分流
- 同时保留旧 adapter 兼容路径
- 一旦异常快速回切

常见策略是：

- 先 shadow 验证
- 再对低风险租户做 1-5% canary
- 观察质量、延迟、错误率
- 再逐步扩量

如果直接原地替换，一旦出问题，很难分清是 base 升级、adapter 兼容还是路由逻辑造成的。

**延伸提醒**

- 更稳妥的治理单元通常是“新 base + 重新验收过的 adapter 组合”。

### 第13题：设计一个 adapter A/B 测试流程，说明离线评测、shadow、canary、扩量和回滚各自的作用。

**思路**

- 这题适合按阶段说明每一步的职责。

**参考答案**

一个最小流程可以是：

1. 离线评测
   先筛掉明显退化版本，控制实验成本。

2. Shadow
   在线复制真实请求但不影响用户，验证稳定性和日志完整性。

3. Canary
   给少量真实流量，验证真实用户分布下的质量与延迟。

4. 扩量
   按阈值逐步增加流量，避免一次性放大风险。

5. 回滚
   保留旧 adapter 热备，一旦指标越线快速切回。

**延伸提醒**

- A/B 测试里最重要的不是分了多少流量，而是实验单元和版本绑定是否清楚。

### 第14题：当 registry 里积累了数千个 adapter 后，你会如何设计 adapter 清理策略？请同时考虑审计留存、热度分布、租户权限和对象存储成本。

**思路**

- 清理策略不是简单按时间删，要按状态分层。

**参考答案**

更合理的策略通常是分层保留：

- 线上活跃版本：强保留，不自动删
- 历史上线版本：保留审计元数据和可恢复副本
- 从未上线且长时间低热度版本：进入冷层或删除
- 被合规要求留存的版本：单独锁定

同时需要：

- 按租户隔离删除权限
- 保留最小审计记录，即使对象文件被冷归档
- 对热层和冷层分别计费与配额

目标不是“删得最多”，而是“把高价值版本留在快路径，把低价值版本留在可追溯低成本路径”。

**延伸提醒**

- 清理策略应先定义“什么不能删”，再谈“什么可以删”。

## 第11章：数据管道

### 第1题：为什么数据管道问题常常会被误判成模型问题？

**参考答案**

因为很多症状最终都体现在模型结果上：

- loss 波动
- 线上效果下降
- 训练吞吐下降

但根因可能其实是：

- 切分规则变了
- 清洗逻辑变了
- 回流断了
- 样本格式变了

所以数据管道问题经常伪装成“模型训练变差”。

### 第2题：训练和在线特征管道在目标上有什么根本差异？

**参考答案**

训练管道更看重：

- 吞吐
- 分片
- shuffle
- 版本稳定

在线特征管道更看重：

- 低延迟
- 一致性
- 权限控制
- 热点缓存

所以训练管道更像批处理系统，在线特征管道更像低延迟服务系统。

### 第3题：设计一个包含回流环节的数据流图

**参考架构**

```text
原始日志 / 文档
  -> 清洗 / 去重 / 脱敏
  -> 标注 / 样本化
  -> 训练集 / 验证集 / 测试集
  -> 训练任务
  -> 模型上线
  -> 用户请求 / 用户反馈 / 人工审核
  -> 回流样本池
  -> 下一轮训练
```

**参考答案**

这条数据流的关键不是画出来，而是标明：

- 哪一步产生版本
- 哪一步产生标签或审核结果
- 哪一步是回流入口

只有这样，回流才不会只是“日志堆积”，而是真正进入再训练闭环。

### 第4题：为什么“先让数据能用”不等于“数据管道已经设计好”？

**参考答案**

“能用”通常只说明：

- 当前任务能读
- 当前样本能训练

但“设计好”还意味着：

- 可追踪
- 可回流
- 可切分
- 可扩展
- 可审计

一个能临时跑通的脚本，不等于一个可持续的数据系统。

### 第5题：如果对象存储里的训练样本有数十亿条，你会优先选择顺序读取、随机读取还是流式读取？为什么？

**参考答案**

大多数情况下我会优先考虑**流式读取或顺序化后的大块读取**，而不是直接做高频随机读。

原因是数十亿条样本意味着：

- 元数据规模巨大
- 小对象访问成本高
- 随机读取很容易把远端存储和网络打碎

更稳妥的工程路径通常是：

- 先把数据组织成适合顺序扫描的大 shard
- 再通过流式 dataset 在 worker 侧做局部打乱

也就是尽量把“随机性”留在计算侧，而不是强迫对象存储做海量随机 I/O。

### 第6题：请为一个文本训练管道设计最小的数据质量验证表，至少包含 3 类检查。

**参考答案**

一个最小表可以这样设计：

| 检查类型 | 例子 | 目的 |
|------|------|------|
| Schema 检查 | 字段是否齐全、编码是否正确 | 防止样本直接读崩 |
| 统计分布检查 | 长度分布、语言分布、标签比例 | 发现数据漂移 |
| 异常样本检查 | 空文本、重复样本、乱码、超长样本 | 防止脏数据放大 |

如果再往前走一步，还可以把这些检查接入：

- 训练前门禁
- 定期回流巡检
- 数据版本发布记录

### 第7题：为什么在线特征系统特别需要 point-in-time correctness？

**参考答案**

因为在线特征系统最容易出现“今天看到的数据，偷偷包含了昨天预测时本不该知道的信息”。

如果没有 point-in-time correctness，就会出现：

- 训练时看到了未来信息
- 离线评测很好看
- 线上真实效果却明显变差

所以它的本质，是保证：

> 任意时刻拿到的特征，只能依赖该时刻之前真实可见的数据。

这既影响模型正确性，也影响评测是否可信。

## 第12章：制品、模型与检查点管理

### 第1题：为什么 checkpoint 不适合直接当生产模型包？

**参考答案**

因为 checkpoint 的目标是恢复训练，它通常包含：

- 模型参数
- 优化器状态
- scheduler 状态
- 当前训练步数

而生产模型包更需要：

- 轻量、可加载的权重
- 推理配置
- tokenizer
- 版本元数据

直接把 checkpoint 用于线上通常会带来：

- 体积大
- 无用状态多
- 配置和部署边界不清

### 第2题：一个模型版本的最小元数据应该包含哪些字段？

**参考答案**

建议至少包含：

```yaml
model_name: reranker
model_version: 2026-04-11-rc1
dataset_version: support-v3
code_revision: abc1234
training_job_id: train-20260411-007
eval_report_id: eval-20260411-002
image: reranker-serving:2026-04-11-rc1
status: staging
```

这些字段能把“模型来自哪里”“能不能上线”“出了问题怎么回滚”都串起来。

### 第3题：为什么模型状态管理必须进入平台控制面？

**参考答案**

因为状态会直接影响：

- 谁能发布
- 哪个版本能被流量命中
- 哪个版本还能回滚
- 哪些工件可以清理

如果状态只存在于文档或群消息里，平台就没法自动执行门禁、回滚和审计。

### 第4题：举一个“文件都在但无法回滚”的失败案例

**参考答案**

一个典型案例：

- 老模型权重还在
- 但老 tokenizer 已被覆盖
- 老镜像已被清理
- 索引或 prompt 模板已经升级

结果是：

- 文件都没丢
- 但系统无法恢复为“旧的完整运行态”

**结论**

回滚依赖的是一组彼此兼容的制品，而不是单个文件。

### 第5题：如果团队同时用对象存储和 registry，各自应该保存什么信息？

**参考答案**

更常见的职责分工是：

| 位置 | 更适合保存什么 |
|------|----------------|
| 对象存储 | 大文件本体，如 checkpoint、权重、评测产物、日志包 |
| Registry / 控制面 | 版本状态、元数据、依赖关系、审批状态、发布标签 |

可以把它理解为：

- 对象存储负责“放东西”
- registry 负责“告诉平台这些东西是什么、现在能不能用”

如果把两者混在一起，平台很容易出现：

- 文件在，但状态不清
- 版本存在，但依赖缺失

### 第6题：请画出一个“训练结束到正式发布”的最小制品流转链路。

**参考答案**

一个最小链路可以写成：

```text
训练完成
  -> 产出 checkpoint / 导出权重
  -> 评测任务
  -> registry 登记版本与状态
  -> staging 部署
  -> 灰度发布
  -> full rollout
```

关键不是画得多复杂，而是每一步都要留下：

- 制品 ID
- 评测结果
- 当前状态
- 回滚指向

这样发布链路才是“平台可执行”的，而不是“人脑记得住”的。

## 第13章：特征、向量与缓存

### 第1题：为什么 embedding 模型升级后，通常不能只替换线上模型而不重建索引？

**参考答案**

因为向量索引中的向量就是由旧 embedding 模型生成的。
如果直接换线上 embedding 模型而不重建索引，就会出现：

- query 向量和文档向量不在同一分布空间
- 检索相似度失真
- 召回结果质量下降

所以 embedding 模型版本和索引版本必须绑定治理。

### 第2题：在线特征缓存为什么既能提升性能，也可能制造一致性问题？

**参考答案**

收益：

- 减少重复计算和远端访问
- 降低延迟
- 降低下游服务压力

风险：

- 读到过期值
- 训练和线上特征定义不一致
- 某些用户画像更新滞后

所以缓存不仅是性能问题，也是正确性问题。

### 第3题：解释“缓存命中不能绕过权限边界”这句话

**参考答案**

意思是：

- 即使某个检索结果或文档已经缓存在系统里
- 系统仍然必须重新确认当前用户是否有权限访问它

否则就会出现：

- A 用户本不该看到某文档
- 但由于缓存命中，系统直接返回了结果

这在企业知识库、RAG 和搜索系统里是非常危险的越权风险。

### 第4题：请设计一个最小的向量索引元数据结构

**参考答案**

```yaml
vector_index:
  name: docs-prod
  version: 2026-04-11
  embedding_model: text-embed-v4
  source_dataset: kb-2026-04-11
  chunk_policy: title-paragraph-v2
  build_job: reindex-20260411-003
  status: active
```

这个结构至少解决四件事：

- 索引来自哪份数据
- 用什么 embedding 生成
- 用什么 chunk 规则切分
- 当前是否可被线上服务使用

### 第5题：HNSW、IVF、PQ 三种 ANN 方法分别更适合什么工程取舍？

**参考答案**

可以把三者理解成三种不同的优先级：

| 方法 | 更偏向什么 | 常见代价 |
|------|------------|----------|
| HNSW | 高召回、低延迟、在线检索体验好 | 内存占用高，构建和更新成本不低 |
| IVF | 先粗分桶，再桶内搜索，适合更大规模数据集 | 需要调聚类参数，召回率和延迟依赖分桶质量 |
| PQ | 极致压缩、降低内存和存储成本 | 距离是近似值，召回率通常最容易受损 |

如果你的优先级是：

- 先追求检索质量和交互时延，通常先看 HNSW
- 先追求大规模可扩展性，通常看 IVF
- 先追求成本和容量压缩，通常看 PQ 或 IVF + PQ

### 第6题：什么时候应该做索引全量重建，而不是增量更新？

**参考答案**

以下情况通常更适合全量重建：

- embedding 模型换了，向量分布整体发生变化
- chunking 策略换了，文档切分边界整体变化
- 距离度量或索引参数体系改了
- 删除 / 更新比例已经高到让增量修补变得不再可靠

增量更新更适合“少量新增文档或局部修订”，全量重建更适合“索引语义边界整体变化”的场景。

### 第7题：prefix cache 的 key 为什么必须包含租户与工具上下文？

**参考答案**

因为 prefix cache 命中的前提，不只是“前几个 token 一样”，还包括这段前缀在业务语义和权限边界上也必须等价。

如果 key 里不包含：

- 租户标识
- 工具启用状态
- system prompt / policy 版本

就可能出现：

- 不同租户错误复用同一段前缀
- 不同工具权限上下文混用
- 看起来命中了缓存，实际却复用了不该复用的执行环境

所以 prefix cache 的 key 设计，本质上既是性能问题，也是隔离问题。

## 第14章：在线推理架构

### 第1题：为什么在线推理架构不能只看模型执行时间？

**参考答案**

因为完整请求延迟通常是：

$$
t_{\text{request}} =
t_{\text{queue}} +
t_{\text{preprocess}} +
t_{\text{model}} +
t_{\text{downstream}} +
t_{\text{postprocess}}
$$

如果你只看 `t_model`，就会漏掉：

- 队列等待
- 检索 / 特征调用
- 冷启动
- 路由和后处理

这也是为什么很多线上超时，并不是模型 kernel 慢，而是系统链路慢。

### 第2题：网关、路由层和模型副本池分别解决什么问题？

**参考答案**

| 组件 | 主要职责 |
|------|----------|
| 网关 | 统一入口、鉴权、限流、基础日志 |
| 路由层 | 按模型版本、租户、上下文长度分流 |
| 模型副本池 | 真正加载模型并执行推理 |

如果少了路由层，很多灰度、版本切换和长短请求分流都很难做；如果少了副本池治理，扩容和缓存策略就很难稳定。

### 第3题：为什么尾延迟比平均延迟更能决定用户体验？

**参考答案**

用户感受到的通常是“偶发特别慢”而不是“平均还不错”。
平均延迟掩盖了最差那批请求，而这些请求往往正是：

- 高峰期请求
- 长上下文请求
- 依赖链路异常请求

所以线上推理更应该盯：

- P95
- P99
- queue wait time

而不是只盯平均值。

### 第4题：如果一个 RAG 服务变慢，你会先从哪几段时间开始拆解？

**参考答案**

建议先拆成：

```text
queue
-> embedding
-> retrieval
-> rerank
-> prompt build
-> llm prefill
-> llm decode
-> postprocess
```

然后优先看：

1. `queue`：是不是副本不够或批处理策略变化
2. `retrieval / rerank`：是不是下游依赖慢
3. `prefill / decode`：是不是 prompt 变长、输出变长或 KV Cache 打满

这是 RAG 推理最常见的三段瓶颈。

### 第5题：为什么冷启动问题不能只靠 autoscaling 解决？

**参考答案**

因为 autoscaling 解决的是“多起几个副本”，而冷启动的核心痛点是：

- 权重加载慢
- CUDA context 初始化慢
- 编译 / 预热慢

如果扩容动作本身就要花很久，等到流量上来再扩，用户已经先感受到排队和超时了。

所以冷启动通常要和这些策略一起看：

- warm pool
- 预热请求
- 镜像与权重预置
- 更早的扩容触发条件

### 第6题：vLLM、Triton Inference Server 和 KServe 分别更适合什么平台诉求？

**参考答案**

| 系统 | 更适合什么诉求 |
|------|----------------|
| vLLM | LLM 在线生成吞吐、continuous batching、共享 GPU serving |
| Triton Inference Server | 多后端、多模型统一托管，希望把不同框架装进同一运行层 |
| KServe | Kubernetes 原生发布、灰度、Autoscaling 和平台统一入口 |

可以把它们理解为三个不同层次：

- vLLM 更偏 LLM 运行时
- Triton 更偏多后端推理服务层
- KServe 更偏平台交付层

### 第7题：什么情况下值得把 prefill 和 decode 拆到不同资源池？

**参考答案**

通常在以下情况更值得考虑：

- 长短请求混跑导致 TTFT 抖动明显
- prefill 和 decode 的资源诉求已经明显不同
- 有能力承担额外 KV handoff 和路由复杂度

如果请求都很短、规模不大，或者网络 / KV 传输层还不成熟，强行拆分往往只是把复杂度提前。

### 第8题：TTFT、TPOT、ITL 这三个指标互相有什么关系？如果 TPOT 正常但 ITL 的 P99 很差，说明什么？

**思路**

- 先把三个指标定义清楚，再解释它们可能分离的原因。

**参考答案**

- `TTFT`：首 token 时间，通常包含排队、prefill、首个 decode 步
- `TPOT`：后续 token 平均耗时
- `ITL`：相邻两个 token 之间的真实间隔，更贴近用户流式体验

如果 `TPOT` 正常但 `ITL P99` 很差，通常说明问题不在平均 decode 算力，而在：

- 调度抖动
- 队列切换不均
- 网络 / streaming flush 抖动
- 某些请求被长请求或重试阻塞

也就是说，系统“平均能生成得很快”，但“偶发卡顿”仍然严重。

**延伸提醒**

- 流式产品里，ITL 的尾延迟往往比平均 TPOT 更接近真实体验。

### 第9题：一个 LLM 服务的 QPS 从 100 提升到 200，但用户投诉变多了。你会看什么指标来判断问题？为什么 "goodput" 可能比 "QPS" 更能说明问题？

**思路**

- QPS 只是吞进来了多少请求，不代表用户真正拿到了多少合格结果。

**参考答案**

我会优先看：

- 成功率 / 超时率 / 中止率
- P95 / P99 TTFT 与 ITL
- queue wait
- 每请求输出 token 和完成率
- 429 / fallback / retry 比例

`goodput` 比 `QPS` 更有解释力，因为它关注的是“在目标 SLO 内成功完成的有效请求”。如果 QPS 翻倍，但大量请求超时、被降级或中途取消，平台只是更忙了，不是更好了。

**延伸提醒**

- 线上扩容评估时，最好把 `goodput / GPU-hour` 作为核心指标之一。

### 第10题：Chunked prefill 和完整的 prefill/decode 解耦架构相比，各自适合什么场景？

**思路**

- 这题不是谁更先进，而是谁更适配当前复杂度。

**参考答案**

`Chunked prefill` 更适合：

- 请求长度差异明显，但还不想引入完整 KV handoff
- 需要在同一资源池内缓解长 prompt 对短请求的阻塞
- 平台希望先用较小复杂度拿到一部分收益

完整 prefill/decode 解耦更适合：

- prefill 与 decode 资源诉求已经高度分化
- 规模足够大，值得为独立资源池和 KV handoff 付出复杂度
- 团队有能力治理额外链路、状态和观测

**延伸提醒**

- 很多团队的现实路线是先 chunked prefill，再决定是否走到完全解耦。

### 第11题：你的路由层目前做简单 round-robin。估算一下，如果切到 prefix-aware 路由，对一个大量复用 system prompt 的 chatbot 服务，吞吐大概能提升多少？为什么？

**思路**

- 题目要估算，不是精确承诺。
- 关键取决于 prefill 在总成本里的占比，以及共享前缀复用率。

**参考答案**

如果这个 chatbot 服务里：

- system prompt 高度复用
- prefill 约占总算力的 30-40%
- prefix-aware 路由能把前缀命中率拉到 60-70%

那么端到端吞吐常见能提升约 `20-40%`，极端情况下更高。

原因是路由把相同前缀尽量送到已有 cache 的副本，减少了重复 prefill。吞吐提升不会等于命中率本身，因为 decode、下游调用和排队仍然存在。

**延伸提醒**

- 如果请求大多是一次性长上下文、共享前缀很少，prefix-aware 路由收益会明显变小。

### 第12题：设计一个"自动降级"规则集：当 GPU 池使用率超过 85%、向量库 P99 > 500ms、单租户 burst 超出配额时，分别应该触发什么动作？

**思路**

- 降级规则的关键是“动作要对应瓶颈”。

**参考答案**

一个最小规则集可以是：

- GPU 池使用率 `> 85%`
  - 降低 `max_new_tokens`
  - 暂停高成本特性，如 best-of-N 或长上下文档位
  - 将低优请求路由到更小模型

- 向量库 `P99 > 500ms`
  - 缩短检索超时
  - 启用缓存结果或降级到无检索回答
  - 对低优流量暂时关闭 rerank

- 单租户 burst 超出配额
  - 进入租户限流队列或直接 429
  - 不允许其占用共享 warm pool
  - 记录审计并通知租户侧

**延伸提醒**

- 自动降级最好是可解释的，让租户知道“为什么被降了、降成什么”。

### 第13题：你所在团队的 LLM 服务冷启动要 90 秒。领导说"那就一直开 10 个 warm 副本兜底"。从成本和 SLA 角度，怎么评估这个决策是否合理？有哪些替代方案？

**思路**

- 这题要同时看峰值保护收益和闲时成本。

**参考答案**

评估这个决策时，我会看：

- 冷启动期间到底造成了多少 SLO 违规
- 峰值流量是否真的需要 10 个常驻热副本
- 低谷时这 10 个副本会空转多久
- warm pool 成本是否低于用户损失或人工兜底成本

替代方案包括：

- 按时段保留动态 warm pool
- 提前预测扩容，而不是被动扩容
- 缩短权重加载与预热链路
- 按模型 / 租户等级分层保温

**延伸提醒**

- “一直开更多副本”通常是最简单、也最昂贵的冷启动补丁。

### 第14题：某同事说"把模型换成 TensorRT-LLM 能快 2x，我们直接换吧"。从本章提到的运营维度（发布、回滚、排障、观测、灰度），你会问哪些问题来决定是否该换？

**思路**

- 题目重点不是性能真假，而是运营代价。

**参考答案**

我会先问：

- 新引擎和现有流式、tool use、长上下文能力是否完全兼容？
- 编译产物和运行时参数怎样进入发布流程？
- 灰度时能否和现有引擎并存、按流量切换？
- 回滚时是切路由就行，还是要重新构建 / 预热？
- 观测和 profiling 能力是否足够，排障会不会比现在更难？
- 团队是否已有运维经验，还是每次问题都要靠少数专家救火？

如果这些问题回答不稳，单看“快 2x”还不够做迁移决策。

**延伸提醒**

- 推理引擎迁移是平台变更，不只是模型变更。

## 第15章：批处理、调度与 KV Cache

### 第1题：为什么批处理策略会直接影响用户延迟？

**参考答案**

因为批处理的核心做法是“先等一会儿，再一起算”。
所以总延迟通常可写成：

$$
t_{\text{request}} = t_{\text{wait for batch}} + t_{\text{batch compute}}
$$

批次越大，计算效率可能越高；但如果等待过久，用户体验会变差。
因此批处理天然是吞吐和延迟之间的权衡器。

### 第2题：Prefill 和 Decode 为什么应该区别对待？

**参考答案**

因为它们的资源形态不同：

- Prefill 更像大块并行计算
- Decode 更像小步增量生成

Prefill 更容易吃算力和带宽；Decode 更容易受调度粒度和 KV Cache 影响。
如果把它们完全当成一种负载处理，系统很容易在某一侧失衡。

### 第3题：KV Cache 为什么既是性能利器，也是显存压力来源？

**参考答案**

收益：

- 避免每步重算全部历史上下文
- 明显降低 decode 重复计算

代价：

- 显存占用随层数、上下文长度、并发数增长

粗略估算：

$$
M_{\text{kv}} \approx 2 \times L \times H \times T \times B \times \text{dtype\_bytes}
$$

所以 KV Cache 同时在做两件事：

- 降计算
- 升显存压力

### 第4题：Continuous batching 相比固定 batch 在工程上解决了什么问题？

**参考答案**

固定 batch 的问题是：

- 不同请求长度差异大
- 短请求要等长请求
- 已完成请求还占位置

Continuous batching 解决的是：

- 动态回收已完成请求槽位
- 动态接纳新请求
- 在 decode 阶段持续维持较高利用率

也就是说，它把“静态组批”升级成了“运行中调度”。

### 第5题：为什么 128K 长上下文场景下，KV Cache 可能先于权重成为显存瓶颈？

**参考答案**

因为权重大小通常是相对固定的，而 KV Cache 会同时随这些维度增长：

- 层数
- hidden size
- 上下文长度
- 并发请求数

当上下文从 `8K` 拉到 `128K` 时，这部分运行时状态会被迅速放大，所以即使模型权重已经量化，显存也可能先被 KV Cache 吃满。

### 第6题：Speculative decoding 和 MoE 调度分别会给运行时带来什么额外复杂度？

**参考答案**

Speculative decoding 会引入：

- 草稿模型与目标模型的协同
- 验证失败后的回退逻辑
- 吞吐与命中率的动态波动

MoE 调度会引入：

- expert 路由不均衡
- 局部热点 expert 过载
- expert 并行与显存管理的额外复杂度

前者更像“多模型协同验证”，后者更像“同一模型内部的负载不均衡治理”。

### 第7题：如果采用 prefill / decode 解耦，为什么 KV handoff 会成为新的瓶颈点？

**参考答案**

因为解耦之后，prefill 不再在同一实例里直接把缓存交给 decode，而是要把整段 KV 状态传出去。

这会把新问题暴露出来：

- KV 体积大
- 传输带宽要求高
- handoff 延迟会直接进入首 token 延迟链路

所以解耦不是“白拿收益”，而是把内部资源竞争转换成了外部状态传输问题。

### 第8题：用本章 §15.3 的公式估算：Llama 3 8B（32 层，GQA 8 头，head_dim=128），单请求 32K 上下文、bf16，KV Cache 多大？如果并发 16 个请求呢？

**思路**

- 题目是数量级估算，用近似值即可。

**参考答案**

按公式粗估：

$$
M_{kv} \approx 2 \times L \times H_{kv} \times d_{head} \times T \times dtype\_bytes
$$

代入：

- `L = 32`
- `H_kv = 8`
- `d_head = 128`
- `T = 32768`
- `bf16 = 2 bytes`

得到单请求大约：

```text
2 × 32 × 8 × 128 × 32768 × 2 bytes
≈ 4 GiB
```

并发 16 个请求时，大约就是：

```text
4 GiB × 16 ≈ 64 GiB
```

这说明长上下文场景下，KV Cache 完全可能先于权重成为显存主项。

**延伸提醒**

- 这还没算碎片、临时 buffer 和实际调度冗余。

### 第9题：一个服务观察到 prefix cache 命中率只有 5%。可能的原因是什么？分别要怎么排查？

**思路**

- 命中率低不一定是缓存实现差，也可能是请求形态不适合。

**参考答案**

常见原因包括：

- system prompt 经常变化，前缀本来就不复用
- 请求没有做规范化，导致看似相同的前缀实际 key 不同
- 路由不是 prefix-aware，相同前缀没被送到同一副本
- TTL / 驱逐过于激进，热点缓存被频繁踢掉
- key 设计带入了过多噪声字段

排查时可依次看：

- 前缀复用率分布
- cache key cardinality
- 路由日志
- eviction / TTL 指标
- 命中率按租户、模板、前缀长度分桶后的结果

**延伸提醒**

- 命中率低时先确认“有没有共享前缀”，再谈缓存算法优化。

### 第10题：Chunked prefill 和 DistServe 类完全解耦方案相比，各自的适用场景和代价是什么？

**思路**

- 一种是中等复杂度优化，一种是架构级拆分。

**参考答案**

`Chunked prefill` 更适合：

- 想缓解长 prompt 阻塞，但还不想引入完整 KV handoff
- 请求规模中等，追求较小改造成本

代价是：

- 只能部分缓解 prefill 对 decode 的干扰
- 资源隔离粒度有限

DistServe 类完全解耦更适合：

- prefill 和 decode 资源诉求已经明显不同
- 规模足够大，值得做独立资源池
- 团队能治理额外链路和状态复杂度

代价是：

- KV handoff 成本
- 调度与观测复杂度大幅增加

**延伸提醒**

- 不要为了“更先进的架构”提前承担自己还用不到的复杂度。

### 第11题：为什么 speculative decoding 在高并发下可能反效果？解释其中的算力账。

**思路**

- 关键是草稿模型不是免费的。

**参考答案**

speculative decoding 在高并发下可能反效果，因为它引入了额外草稿生成成本：

- 草稿模型要先跑一遍
- 目标模型还要做验证
- 接受率不高时，大量草稿算力会被浪费

当系统已经高并发时，这些额外计算会和主模型争抢 GPU、显存和调度槽位，结果可能是：

- 平均吞吐没上去
- 尾延迟反而变差

**延伸提醒**

- speculative decoding 的收益高度依赖接受率和并发形态，不能默认“必赚”。

### 第12题：设计一个 vLLM 参数调优的步骤清单：从打开服务、跑压测、到稳定上线，每一步调哪个参数、观察什么指标？

**思路**

- 这题适合按阶段回答，不求穷尽所有参数。

**参考答案**

一个最小步骤清单可以是：

1. 启动基线
   先固定模型、并行度、`max_model_len`。看能否稳定启动、显存水位是否合理。

2. 低并发压测
   调 `gpu_memory_utilization`、`max_num_seqs`。看 TTFT、TPOT、OOM、KV 使用率。

3. 中高并发压测
   调 `max_num_batched_tokens`、连续 batching 相关参数。看 goodput、P95/P99 延迟、queue wait。

4. 打开缓存特性
   启用 prefix cache 或相关路由。看命中率、prefill 时间、显存波动。

5. 稳定性验证
   长时间压测，观察错误率、重试、显存碎片、冷启动行为。

**延伸提醒**

- 调参数时不要同时改太多项，否则很难知道收益来自哪一步。

### 第13题：你的 LLM 服务遇到一个场景：高峰期 P99 TTFT 飙到 10 秒，但 P50 还很正常。结合本章的调度机制，列出至少 5 个可能的原因，以及排查顺序。

**思路**

- P50 正常、P99 飙升通常意味着长尾调度问题，而不是普遍算力不足。

**参考答案**

可能原因包括：

1. 少量超长 prompt 把 prefill 阶段拖长
2. prefix cache 命中率在高峰期下降
3. 某些副本路由倾斜，出现热点节点
4. GPU 显存逼近上限，触发更激进的驱逐或 admission 失败
5. autoscaling 或 warm pool 跟不上峰值
6. 某个租户 burst 抢占了共享队列

建议排查顺序：

1. 先看 queue wait 和 admission failure
2. 再看长 prompt 占比与 prefill 时间
3. 再看 cache hit / eviction
4. 再看路由倾斜与租户分桶
5. 最后看扩容与副本健康

**延伸提醒**

- P50 正常说明系统基线没坏，优先盯长尾样本和分桶指标。

### 第14题：某团队声称通过自研调度器比 vLLM 快 30%。基于本章内容，你会问哪些问题来判断这个"30%"是否可信、是否可迁移？

**思路**

- 要确认比较是否公平、结果是否能迁移到你的流量形态。

**参考答案**

我会先问：

- 对比是在同一硬件、同一模型、同一请求分布上做的吗？
- “快 30%”指的是吞吐、TTFT、TPOT，还是 goodput？
- 是否包含了长上下文、流式输出、缓存命中波动等真实场景？
- 错误率、OOM、排障成本有没有一起比较？
- 自研调度器是否要求特定流量形态或特定模型才成立？

如果这些问题都没回答清楚，这个 30% 很可能只是某个窄场景的 benchmark 数字。

**延伸提醒**

- 可迁移的收益，必须建立在可复现的工作负载定义上。

## 第16章：量化、编译与推理引擎

### 第1题：为什么量化收益常常和模型类型、硬件类型绑定？

**参考答案**

因为量化效果取决于三件事是否匹配：

1. 模型是否对精度敏感
2. 硬件是否对目标低精度格式有高效支持
3. 引擎是否能稳定执行该量化路径

所以相同量化策略在不同模型或硬件上，收益和风险差异会很大。

### 第2题：编译优化和量化分别更偏向解决什么问题？

**参考答案**

- **量化**：更偏向减少显存占用和带宽压力
- **编译优化**：更偏向减少执行开销、优化 kernel 和内存布局

量化主要改“表示”，编译主要改“执行计划”。

### 第3题：推理引擎和框架直接推理各自适合什么场景？

**参考答案**

| 方式 | 更适合什么 |
|------|------------|
| 框架直接推理 | 调试、实验、模型快速验证 |
| 专用推理引擎 | 高吞吐、批处理、缓存管理、多租户线上场景 |

如果你还处于快速迭代模型阶段，框架更灵活；如果你要长期托管线上流量，专用引擎通常更合适。

### 第4题：如果吞吐提高了但排障更困难，是否一定值得？为什么？

**参考答案**

不一定值得。
要综合判断：

- 提升的吞吐值不值得额外复杂度
- 质量是否退化
- 灰度和回滚是否更难
- 排障时间是否显著增加

一个好的原则是：

> 线上优化必须同时通过“性能收益”和“可运维性”两道门。

### 第5题：PTQ 和 QAT 在平台接入流程上最大的区别是什么？

**参考答案**

最大的区别在于：**PTQ 主要改变发布前的离线处理流程，QAT 会改变训练流程本身。**

具体看：

| 方案 | 平台接入重点 |
|------|--------------|
| PTQ | 准备校准集、离线量化、评测量化后模型、接入目标引擎 |
| QAT | 在训练阶段就加入伪量化节点，训练、评测、导出和部署链路都要配合 |

所以 PTQ 更像“上线前新增一个压缩步骤”，QAT 更像“把量化目标前置到训练管线里”。

### 第6题：为什么权重量化后，KV Cache 仍可能是长上下文服务的主瓶颈？

**参考答案**

因为权重量化主要压缩的是“模型参数”，而长上下文服务经常被“运行时缓存”主导。

当上下文长度和并发一起上来时，KV Cache 的占用会随着：

- 层数
- hidden size
- token 长度
- 并发请求数

持续增长。即使权重已经从 BF16 压到 INT4 / FP8，KV Cache 仍可能继续占据大头显存。

所以工程上常见结论是：

- 权重量化解决“模型放得下”
- KV Cache 优化解决“长上下文跑得稳”

两者要一起看，不能互相替代。

### 第7题：为什么编译产物应该被当成一份带 shape contract 的制品来管理？

**参考答案**

因为很多编译优化都隐含假设：

- 输入 shape 范围
- batch 上限
- dtype
- 某些静态图约束

如果不把这些条件一起记录下来，就会出现：

- 线下编译好的产物在线上遇到新 shape 失效
- 推理速度和稳定性与预期不一致
- 回滚时不知道该切回哪一份编译产物

所以编译产物不应被当成“一个裸文件”，而应被当成：

```text
模型版本 + 编译参数 + shape contract + 目标硬件
```

一起治理的制品。

### 第8题：一个 7B 模型在 A100 上做 decode（batch=1），是 memory-bound 还是 compute-bound？量化成 int4 预期能加速多少？如果 batch 开到 64 呢？

**思路**

- 先判断瓶颈，再谈量化收益。

**参考答案**

对 7B 模型在 A100 上做 `decode, batch=1`，通常更接近 `memory-bound`，因为每步只生成一个 token，算子规模小，更多在搬权重和读 KV。

这时量化成 int4 的预期收益常见是 `1.3x-2x`，前提是：

- 引擎对 int4 路径优化成熟
- 反量化开销没有吃掉收益

如果 batch 开到 64，系统会更靠近 compute 利用区间，量化收益通常会缩小，常见更像 `1.1x-1.4x`，因为这时不再只是带宽瓶颈。

**延伸提醒**

- 量化收益不是常数，它会随 batch、上下文长度和引擎实现变化。

### 第9题：你的服务要支持 128K 长上下文，硬件是 H100 80GB。给出一个量化组合（W / A / KV 精度），并解释为什么这个组合合理。

**思路**

- 长上下文服务里，KV 精度和权重精度一样重要。

**参考答案**

一个相对稳妥的组合可以是：

- `W4`
- `A16`
- `KV FP8`

理由是：

- 权重做 `W4`，优先压缩常驻权重占用
- 激活保留 `A16`，避免 prefill / decode 过程精度波动过大
- KV 用 `FP8`，因为 128K 场景下 KV Cache 常常是最大运行时成本

这个组合的目标不是追求最激进压缩，而是在长上下文容量和质量稳定性之间取平衡。

**延伸提醒**

- KV 精度是否可接受，必须用长上下文任务而不是短 benchmark 验证。

### 第10题：TensorRT engine 文件的 shape contract 具体包含哪些维度？发布时这些信息应该如何管理？

**思路**

- shape contract 的本质是“这份 engine 适用什么输入空间”。

**参考答案**

典型 shape contract 至少应包含：

- batch 范围
- 最大 input length
- 最大 output length / total sequence length
- beam width 或并行生成配置
- dtype
- tensor parallel / pipeline parallel 配置
- 目标硬件与驱动约束

发布时，这些信息不应藏在文件名里，而应作为 registry 元数据进入控制面，并参与：

- 路由匹配
- 发布门禁
- 灰度与回滚

**延伸提醒**

- 没有 shape contract 的 engine，很容易在线上碰到“能启动但某些请求不能跑”的事故。

### 第11题：你的团队想从 vLLM 换到 TensorRT-LLM 追求极致性能。列出换之前需要评估的至少 5 个非性能因素。

**思路**

- 平台迁移看的是总拥有成本，不只是 benchmark。

**参考答案**

至少要评估：

1. 功能兼容性：流式输出、长上下文、tool use、cache 特性是否齐全
2. 发布复杂度：engine 构建、版本管理、shape contract 管理是否可控
3. 回滚路径：能否与现有引擎并存、快速切回
4. 观测与排障：profiling、日志、错误定位是否成熟
5. 运维门槛：团队是否有足够经验维护新栈
6. 生态依赖：量化、并行、硬件支持是否匹配现有模型

**延伸提醒**

- 对平台方来说，“能否稳定运维”常常比“峰值更快”更重要。

### 第12题：为什么 "benchmark 报告 XX 比 YY 快 3x" 这种结论常常难以直接复用？设计一个严谨的引擎对比测试方案。

**思路**

- benchmark 不可复用，通常是因为工作负载定义不一致。

**参考答案**

这种结论难以直接复用，常见原因是：

- 硬件、驱动、模型版本不同
- prompt 长度、输出长度、并发不同
- 一个测 warm case，一个测 cold case
- 指标口径不同，吞吐和 goodput 混在一起

更严谨的对比方案应固定：

- 同一硬件 / 驱动 / CUDA 栈
- 同一模型和量化版本
- 同一请求分布、上下文长度和并发档位
- 同一观测指标：TTFT、TPOT、throughput、goodput、错误率、显存
- 多轮重复测试，分别记录 cold / warm 情况

**延伸提醒**

- 平台选型最好基于自己的真实流量回放，而不是只看公开 benchmark。

### 第13题：你的服务目前是 bf16 Llama 3 70B，QPS 100，P99 TTFT 2s，P99 TPOT 80ms。领导要求成本降 40%。基于本章内容，给出至少三套不同的优化路径，说明各自的收益、风险、运维代价。

**思路**

- 这题考察的是“同一目标，三种路径”。

**参考答案**

可以考虑三条路径：

1. 量化路径
   例如从 bf16 降到 FP8 / INT4。
   收益：显存和带宽下降，副本密度提升。
   风险：质量回退、引擎兼容性问题。
   运维代价：需要额外评测和制品管理。

2. 运行时路径
   例如优化 batching、prefix cache、prefill/decode 分层。
   收益：不改模型即可提升 goodput。
   风险：收益依赖流量形态。
   运维代价：需要更强观测和调度治理。

3. 路由路径
   让一部分简单流量走更小模型或蒸馏模型。
   收益：最直接地降低平均成本。
   风险：路由错误会伤质量。
   运维代价：需要多模型治理和灰度策略。

**延伸提醒**

- 真正落地时，通常是三条路组合，而不是押单一路线。

### 第14题：某算法同事声称用一个新的 INT4 方法，精度损失比 GPTQ 还小，并给出了 MMLU 分数对比。作为平台方，你会问哪些问题决定要不要推动上线？

**思路**

- 单个离线分数远远不够决定平台上线。

**参考答案**

我会先问：

- 这个 INT4 路径支持哪些硬件、哪些引擎？
- 除了 MMLU，长上下文、指令跟随、安全任务表现如何？
- TTFT、TPOT、吞吐、显存收益具体是多少？
- 是否需要特殊校准集、特殊构建流程？
- 失败时的回滚路径和兼容性怎样？
- 团队是否有能力长期维护这条量化栈？

只有当质量、性能、制品治理和回滚都回答清楚，平台才值得推动上线。

**延伸提醒**

- 平台评估量化方法时，永远要把“可运维性”与“离线精度”一起看。

## 第17章：多租户与成本治理

### 第1题：为什么推理平台一旦服务多个团队，就必须考虑多租户治理？

**参考答案**

因为这时平台不再只是技术系统，而变成资源分配系统。
它必须回答：

- 谁优先
- 谁保底
- 谁能借闲置资源
- 谁为账单负责

没有多租户治理，就会演变成“谁更会抢资源，谁就赢”。

### 第2题：单位请求成本为什么不能只看模型大小？

**参考答案**

因为成本至少还受这些因素影响：

- 上下文长度
- 输出长度
- batch 利用率
- cache 命中率
- 副本空转时间
- 下游依赖调用成本

所以同一个模型，在不同流量形态下，单位请求成本可能差很多。

### 第3题：公平性和利用率为什么会冲突？

**参考答案**

如果极度追求利用率，平台倾向于：

- 尽量填满 GPU
- 长任务也不轻易中断

这会让高优先级短任务体验变差。
如果极度追求公平，则可能：

- 保留很多配额不借出去
- 导致资源闲置

所以平台必须在两者之间做政策取舍，而不是追求某个单一最优值。

### 第4题：请为 3 类租户设计一套简单的 GPU 与优先级策略

**参考答案**

```yaml
tenant_policy:
  core_online:
    priority: high
    reserved_gpu: 8
    burst_gpu: 16
    preemptible: false
  internal_product:
    priority: medium
    reserved_gpu: 4
    burst_gpu: 8
    preemptible: false
  research_experiment:
    priority: low
    reserved_gpu: 0
    burst_gpu: 6
    preemptible: true
```

**思路**

- 核心在线业务要保底且不可抢占
- 一般产品业务可保底但可限制峰值
- 实验业务尽量利用空闲资源，并允许被抢占

### 第5题：如果两个租户共享同一组 GPU，哪些指标最能帮助你识别 noisy neighbor？

**参考答案**

最有用的通常不是单个平均值，而是租户维度的对照信号，例如：

- 每租户 P95 / P99 延迟
- queue wait time
- GPU 显存占用与 active sequences
- cache hit ratio 变化
- 某租户突发流量与另一租户尾延迟的相关性

如果一个租户流量一上来，另一个租户的尾延迟和排队时间就跟着恶化，这通常就是 noisy neighbor 的强信号。

### 第6题：按 GPU·时、按 token、按请求三种 chargeback 模型分别会激励租户做什么优化？

**参考答案**

| 计费方式 | 更容易激励什么 |
|------|----------------|
| 按 GPU·时 | 提高资源利用率、减少空转和过度保留副本 |
| 按 token | 控制上下文长度、输出长度和无效思考 token |
| 按请求 | 压缩请求次数、合并调用、减少碎片流量 |

所以 chargeback 不只是记账方式，也是在塑造用户行为。

### 第7题：为什么 warm pool 既是 SLA 工具，也是成本放大器？

**参考答案**

因为 warm pool 的好处很直接：

- 预留热副本
- 降低冷启动抖动
- 保护首 token 延迟

但代价也同样直接：

- 这些副本即使空闲也在持续占用 GPU
- 流量低谷时容易变成高成本保底容量

所以 warm pool 的关键不是“开不开”，而是：

- 保留多少
- 在什么时段保留
- 与真实流量和 SLO 如何联动

### 第8题：用 §17.4a 的粗略 TCO 算法：你的团队需要 16 张 H100，预计使用 2 年，平均利用率 65%。估算 Cloud 按需、Cloud 3 年预留、On-Prem 三种路径的大致总成本。哪个最划算？

**思路**

- 用章节里的数量级即可，不要把粗算伪装成精算。

**参考答案**

按文中粗略口径：

- On-Prem 约 `$2.5 / GPU-hour`
- Cloud 按需约 `$4 / GPU-hour`
- Cloud 3 年预留约按需的 `50-60%`

则 16 张 H100、2 年、65% 利用率时：

- Cloud 按需
  `16 × 8760 × 2 × 0.65 × $4 ≈ $729K`

- On-Prem
  如果按固定年度 TCO 计费，16 卡大约是 8 卡示例的两倍，约 `$360K / 年`，2 年约 `$720K`

- Cloud 3 年预留
  纸面单价可能最低，粗略约 `$600K` 上下，但它要求更长承诺周期；对只看 2 年需求的团队，第三年的承诺风险必须算进去

所以纯账面上“预留”最便宜，但在“两年期、65% 利用率”这个前提下，更稳妥的判断往往是：`Cloud 按需` 与 `On-Prem` 接近，是否值得上 3 年预留要看你能否吃满承诺期。

**延伸提醒**

- TCO 判断里，时间周期和利用率曲线往往比单价更决定结论。

### 第9题：你发现平台 GPU utilization 从 40% 涨到 70%，但单位 token 成本没降反而略涨。按 §17.4 的诊断流程，你会按什么顺序排查？

**思路**

- 利用率上涨不代表在做更有价值的工作。

**参考答案**

我会按这个顺序排查：

1. `goodput` 是否同步上升，还是只是忙在重试、长尾或低价值流量
2. 输入 / 输出 token 长度是否变长
3. prefix cache、retrieval cache 命中率是否下降
4. warm pool、空转副本、双版本并存是否增加
5. 下游依赖成本是否被放大，例如向量库或 rerank

如果 GPU 更忙，但有效产出没有同步上升，单位 token 成本完全可能不降反升。

**延伸提醒**

- GPU utilization 应和 `useful tokens per GPU-hour` 一起看。

### 第10题：某租户每月预算 $1000，但第 20 天就用掉了 $950。设计一套"软着陆"降级策略，让他在月底前还能用基本功能但不爆预算。

**思路**

- 软着陆的目标不是“一刀切停服”，而是逐层缩功能。

**参考答案**

一个可执行的策略可以是：

- 达到 80% 预算
  通知租户，并默认关闭高成本特性，如长上下文、best-of-N

- 达到 95% 预算
  将默认模型切到更小版本，限制 `max_tokens`，降低 burst 配额

- 达到 100% 预算
  保留核心低成本能力，实验流量返回 429 或排入低优队列

这样月底前租户还能保留基本功能，但不会继续无上限透支。

**延伸提醒**

- 最好的软着陆是“提前可预期”，而不是最后几天突然断电。

### 第11题：你的平台有一个大户占了 50% 的 GPU 用量，另有 200 个小户共用剩下 50%。这两群租户的治理策略应该有什么不同？

**思路**

- 题目要的是差异化治理，而不是一刀切。

**参考答案**

对大户，更适合：

- 独立资源池或更强保留配额
- 更细粒度 chargeback
- 单独容量规划和灰度策略

对 200 个小户，更适合：

- 共享池
- 简化计费与限流规则
- 更强的噪声隔离和默认降级策略

原因是：大户决定容量，小户决定平台的共享治理复杂度。两者用同一套策略，通常会两头都不满意。

**延伸提醒**

- 多租户治理里，“按体量分层”往往比“人人同权”更现实。

### 第12题：某算法同事说"把 warm pool 从 10 砍到 2，每月能省 $30K"。作为平台方，你会看哪些指标来判断这个决策的风险？

**思路**

- 这题不是反对省钱，而是量化风险。

**参考答案**

我会重点看：

- 冷启动时间
- 峰值流量到来速度
- P95 / P99 TTFT
- 过去因冷启动导致的超时 / 失败比例
- 时段分布，看 10 个 warm 副本是否真的长期空转

如果高峰期 arrival burst 很陡、冷启动很慢，直接从 10 砍到 2 可能把省下的 GPU 钱换成 SLA 事故。

**延伸提醒**

- 更稳妥的做法通常是“按时段逐步下调”，而不是一次性砍到位。

### 第13题：你所在平台目前的成本治理只有"每月账单"一个数字，团队想推进精细化。给出一个从 0 到 1 的 6 个月路线图：分别要接入哪些埋点、建立哪些流程、推动哪些政策变化？

**思路**

- 路线图要同时覆盖数据、流程和政策三层。

**参考答案**

一个 6 个月的最小路线可以是：

1. 第 1-2 个月
   接入 GPU-hour、token、租户、模型版本、下游调用等基础埋点。

2. 第 3-4 个月
   建立按租户 / 模型 / 请求类型的成本看板，接入预算告警和异常分析流程。

3. 第 5 个月
   推出基础 chargeback 规则，如预算阈值、长上下文单独计费、warm pool 单独记账。

4. 第 6 个月
   把预算阈值、限流、自动降级接进控制面，形成闭环。

**延伸提醒**

- 成本治理如果只停在看板，就还不算治理。

### 第14题：有人建议"把所有租户的 GPU 都合成一个共享池，利用率最高"。从本章内容出发，列出这种做法的至少 5 个潜在问题。

**思路**

- 共享池追求的是利用率，但治理风险会被一起放大。

**参考答案**

潜在问题至少包括：

1. noisy neighbor 更严重
2. 长上下文和高 burst 租户会拖垮共享池尾延迟
3. 回滚和灰度时更难隔离风险
4. 预算和 chargeback 更难解释
5. 关键租户无法获得稳定保底容量
6. 单一池子出问题时影响面更大

所以“全共享”常常是局部利用率更高、整体治理更差。

**延伸提醒**

- 对平台来说，最优目标通常是“足够高的利用率 + 可解释的隔离”，而不是纯粹最高利用率。

### 第15题：设想你的平台即将迎来一个新大户（流量占当前总量的 30%）。从容量规划、配额、chargeback、发布隔离等角度，你会在正式接入前做哪些准备？

**思路**

- 题目要的是接入前准备，而不是出问题后的补救。

**参考答案**

正式接入前，我会先做：

- 容量规划：重算高峰期 GPU、warm pool、下游容量
- 配额设计：给新大户明确保底与 burst 上限
- chargeback：单独核算其 GPU、token 和关键下游成本
- 发布隔离：让其先进入独立灰度池，避免新租户直接污染共享池
- 观测准备：提前建租户级 dashboard 和 noisy neighbor 监控

这样新大户上线后，平台不会在最脆弱的时候同时学习“怎么接”和“怎么救火”。

**延伸提醒**

- 大户接入本质上是一次平台容量与治理策略的再基线化。

## 第18章：容器与运行时

### 第1题：为什么训练镜像和推理镜像的优化目标不同？

**参考答案**

训练镜像更关注：

- 依赖完整
- 调试工具
- 数据处理工具链
- 编译 / 扩展能力

推理镜像更关注：

- 体积小
- 启动快
- 安全面更小
- 运行路径更稳定

所以两者目标不同，通常不适合长期复用同一个镜像。

### 第2题：容器能启动但 GPU 不可用时，你会从哪几层排查？

**参考答案**

建议从这几层排查：

1. 宿主机驱动是否正常
2. 容器运行时是否正确暴露 GPU
3. 设备插件是否正常注册资源
4. 镜像内 CUDA runtime / 框架版本是否匹配

可以用一个简单顺序记：

```text
驱动 -> runtime -> device plugin -> image / framework
```

### 第3题：请设计一个 AI 镜像的最小分层结构

**参考答案**

```text
base-os
  -> cuda-runtime
    -> framework-runtime
      -> team-common-libs
        -> project-code
```

**设计理由**

- 底层稳定层变化少
- 团队公共依赖可统一治理
- 项目代码更新不会重复构建全部底层

### 第4题：为什么 AI 镜像治理必须和宿主机驱动治理一起看？

**参考答案**

因为镜像里的 CUDA runtime 和框架最终仍然要跑在宿主机驱动之上。
如果两边版本矩阵不兼容，就会出现：

- 镜像能起，但 GPU 不工作
- 性能异常
- 某些功能缺失

所以 AI 镜像治理不是纯镜像问题，而是“镜像 + 驱动 + 运行时”的组合治理。

## 第19章：Kubernetes for AI

### 第1题：为什么说 Kubernetes 是 AI 平台底座，而不是 AI 平台本身？

**参考答案**

Kubernetes 擅长解决：

- 容器编排
- 资源声明
- 服务发现
- 基本扩缩容

但它并不天然理解：

- 模型评测门禁
- 训练恢复语义
- KV Cache 管理
- 多租户 GPU 策略
- 模型质量和发布治理

所以它是底座，不是完整 AI 平台。

### 第2题：训练任务和推理服务分别更适合哪些 K8s 对象？

**参考答案**

- 训练任务：`Job`、`CronJob`、训练类 `CRD / Operator`
- 推理服务：`Deployment`、`StatefulSet`、专用 serving 控制器

原因是训练更偏一次性批任务，推理更偏长期在线服务。

### 第3题：GPU 为什么在 K8s 里不能被简单当成“另一个 CPU”？

**参考答案**

因为 GPU 是：

- 离散资源
- 型号差异大
- 拓扑差异大
- 显存强约束资源

而 CPU 更像通用可切分资源。
GPU 调度常常需要额外语义，例如：

- 卡型选择
- 多卡拓扑
- gang scheduling

### 第4题：请写出一个需要额外调度语义的 AI 场景，说明为什么原生资源对象不够

**参考答案**

场景：**8 卡分布式训练任务必须一次性拿到同一节点池、同一拓扑上的 8 张卡。**

为什么原生对象不够：

- 原生资源请求只表达“我要 8 张 GPU”
- 但表达不了“这 8 张必须拓扑相近、必须同时到位、必须一起启动”

这就是为什么很多 AI 平台需要额外的调度器、CRD 或 gang scheduling 语义。

## 第20章：队列、配额与自动扩缩容

### 第1题：为什么 AI 任务比普通 Web 服务更依赖队列治理？

**参考答案**

因为 AI 任务往往：

- 更长
- 更吃 GPU
- 更依赖资源形状
- 更容易因优先级差异产生冲突

普通 Web 请求通常来了就处理，AI 任务更像“稀缺资源上的排产问题”。
所以队列治理在 AI 平台里是核心体验层，不是附属功能。

### 第2题：如果推理服务冷启动很慢，自动扩容策略应如何调整？

**参考答案**

应做三类调整：

1. **提前扩容**：不要等 P99 已经爆炸才扩
2. **保留预热副本**：维持最小热池
3. **多指标触发**：结合 queue wait、pending requests、GPU 水位，而不是只看 CPU

**示意策略**

```yaml
scale_out_if:
  queue_wait_p95_ms: "> 150"
  pending_requests: "> 50"
  gpu_utilization: "> 70%"
min_replicas: 3
warm_pool: enabled
```

### 第3题：配额和优先级冲突时，平台应该如何解释决策？

**参考答案**

平台必须给出透明解释，例如：

- 你所在租户当前已用满保底配额
- 当前请求优先级低于核心线上队列
- 当前借用资源已被回收给高优先级业务

最好让这类信息直接体现在：

- 调度事件
- 队列看板
- 审计日志

否则平台会被用户理解成“黑箱”。

### 第4题：为什么训练场景下的 autoscaling 往往不如推理场景直接？

**参考答案**

因为训练任务常常要求：

- 固定卡数
- 固定拓扑
- 长时间连续运行

而新扩出来的节点不一定能马上满足当前作业的拓扑条件。
所以训练更常见的是“集群容量扩展”，而不是推理那种基于请求的细粒度 HPA。

## 第21章：可观测性与容量规划

### 第1题：为什么 GPU 利用率高不一定代表用户体验好？

**参考答案**

因为高 GPU 利用率只说明设备很忙，不说明：

- 请求有没有在排队
- P99 延迟是否恶化
- 下游依赖是否变慢
- 模型输出是否仍然高质量

一个推理系统完全可能出现：

- GPU 90%+ 利用率
- 用户却感受到更慢和更多超时

所以必须结合队列、延迟和质量指标一起看。

### 第2题：设计一个推理服务的最小指标面板

**参考答案**

建议至少包含：

1. 请求量 / token 量
2. P50 / P95 / P99 延迟
3. queue wait time
4. GPU 利用率
5. 显存占用
6. active sequences / batch tokens
7. cache hit ratio
8. 单位请求成本或每千 token 成本
9. 关键模型质量指标

**最小 dashboard 逻辑**

```text
入口压力
  -> 队列
  -> 模型执行
  -> 成本
  -> 质量
```

### 第3题：容量规划时为什么要考虑故障冗余？

**参考答案**

因为现实中必须假设：

- 某些节点会挂
- 某些可用区会有故障
- 某些副本会被回滚或重建

如果容量规划只按“正常状态刚刚够用”来算，任何一次节点故障都会让系统进入超载。

因此容量规划应至少包含：

- 正常容量
- 峰值容量
- 故障冗余容量

### 第4题：如果平均流量稳定，但 P99 延迟突然恶化，你会优先看哪些指标关联？

**参考答案**

优先看：

1. queue wait time
2. 长请求 / 长上下文占比
3. 下游检索 / 特征依赖延迟
4. cache hit ratio
5. GPU 显存是否接近上限

因为 P99 恶化通常说明某一类边缘请求开始拖尾，而不是平均流量本身上升。

## 第22章：评测、发布与故障处理

### 第1题：为什么 AI 发布不能只看“接口没报错”？

**参考答案**

因为 AI 发布除了系统可用性，还必须看：

- 模型质量是否退化
- 是否误答、幻觉或引用错误
- 成本是否大幅上升
- 安全或权限边界是否被突破

接口 200 只能说明“服务返回了”，不能说明“返回得对、返回得值”。

### 第2题：请为一个 RAG 服务设计最小灰度发布流程

**思路**

- 这道题不是让你写“一个上线步骤列表”而已，而是要体现 RAG 系统比普通模型发布多了索引、检索质量和引用正确性的额外风险。
- 所以答案应同时覆盖离线验证、线上小流量验证、回滚准备和关键观测指标。

**参考答案**

**参考架构 / 流程**

```text
新模型 / 新索引
  -> 离线评测
  -> staging 验证
  -> 1% 灰度
  -> 观察系统指标 + 检索质量 + 用户反馈
  -> 10% 灰度
  -> 全量
  -> 保留旧版本回滚窗口
```

**关键检查点**

- 检索召回是否退化
- 引用是否正确
- P95 / P99 是否恶化
- 单请求成本是否异常上升

**参考答案**

一个最小可执行的 RAG 灰度发布流程应至少包含四段：

1. **离线验证**：先在固定问答集和检索集上比较新旧版本，确认召回、引用正确率和响应成本没有明显退化。
2. **staging 验证**：把“模型 + 索引 + prompt 配置”作为一组完整版本部署到预发布环境，验证依赖、权限和日志链路。
3. **小流量灰度**：先让极小比例真实流量进入新版本，重点观察系统指标、检索质量和用户反馈。
4. **逐步放量与可回滚保留**：在确认没有系统退化、质量退化和权限问题后逐步放量，同时保留旧版本一键切回路径。

这道题真正想强调的是：RAG 灰度对象从来不是“只有模型”，而是“模型 + embedding / 索引 + prompt / 配置 + 路由规则”的组合版本。

### 第3题：为什么 AI 系统的回滚往往不只是回滚模型文件？

**参考答案**

因为一个版本往往同时绑定：

- 模型权重
- tokenizer
- prompt 模板
- 索引版本
- 推理镜像
- 路由策略

如果只回滚模型文件，而其他对象仍是新版本，系统仍可能处于不一致状态。

### 第4题：举一个事故复盘最终应沉淀成平台能力的例子

**参考答案**

例子：某次模型灰度后发现引用错误率显著上升，原因是新索引版本与旧 embedding 模型不一致。

如果只是复盘写文档，问题还会再发生。
更好的平台化沉淀应是：

- 发布前强制校验 embedding 模型版本与索引版本一致
- 不一致则禁止进入灰度流程

也就是说，好的复盘最终要把“人工经验”变成“系统规则”。

## 第23章：安全、隔离与治理

### 第1题：为什么 AI 平台的安全面比普通在线服务更宽？

**参考答案**

因为 AI 平台除了接口本身，还要保护：

- 训练数据
- 模型权重
- 向量索引
- 日志与反馈
- GPU 资源
- 镜像供应链
- prompt / 上下文数据

这比普通在线服务多了更多状态对象和更多可能泄露的内容。

### 第2题：RAG 系统为什么特别容易出现权限越界问题？

**参考答案**

因为 RAG 会把“检索到的文档内容”拼进模型上下文。
如果检索或缓存阶段权限控制做错，就可能：

- 把用户无权访问的文档检索出来
- 进一步在回答中泄露给用户

所以 RAG 的权限边界不是单点 API 权限，而是：

检索权限 + 文档权限 + 缓存权限 + 输出过滤

### 第3题：请写出一个最小治理配置中必须包含的 4 类规则

**参考答案**

至少应包含：

1. **身份规则**：谁能提交任务 / 调模型 / 发版本
2. **资源规则**：谁最多能占多少 GPU / 队列 / 副本
3. **数据规则**：谁能访问哪些数据、索引、日志
4. **审计规则**：关键操作必须留痕

可以写成：

```yaml
governance:
  identity: required
  quota: enforced
  data_access: least_privilege
  audit_log: mandatory
```

### 第4题：举一个“治理停留在文档里”最终会失败的场景

**参考答案**

场景：

- 文档里写着“生产模型发布前必须过评测门禁”
- 但发布系统没有强制检查
- 某次紧急上线直接绕过评测
- 最终把有缺陷的模型推到线上

这就是典型的“规则存在，但系统不执行”。
治理只有进入平台控制面，才真正有效。

### 第5题：如果模型权重文件使用 `pickle` 序列化，存在什么安全风险？SafeTensors 为什么更适合进入平台默认格式？

**参考答案**

`pickle` 的核心风险不是“文件大”，而是**反序列化时可能执行任意 Python 对象构造逻辑**。这意味着如果权重文件来源不可信，加载动作本身就可能变成代码执行入口。

在平台里，这个风险会被进一步放大，因为权重文件常常会被：

- 自动下载
- 自动分发到多个训练 / 推理节点
- 在 CI、评测、发布链路里重复加载

所以问题不只是“某个研究同学的本地脚本有风险”，而是“整条平台供应链都可能被带毒制品污染”。

SafeTensors 更适合作为平台默认格式，主要因为：

1. **格式边界更窄**：它只表达张量数据和必要元信息，不依赖通用对象反序列化。
2. **更利于校验**：平台更容易对文件内容、大小、哈希和元数据做验证。
3. **更适合自动化链路**：在模型注册、扫描、分发和加载阶段更容易做标准化治理。

所以平台工程上的结论通常不是“绝不允许任何 `pickle` 文件存在”，而是：**默认格式应优先选择 SafeTensors 这类更窄、更可验证的格式，确需使用 `pickle` 时必须提高来源校验和隔离级别。**

## 第25章：AI Agent 与推理时计算基础设施

### 第1题：从基础设施视角看，Agent 和 Thinking Model 分别会怎样改变会话持续时间、token 消耗可预测性和并发模型？

**思路**

- Agent 改变的是执行流程，Thinking Model 改变的是单次推理内部计算。
- 两者都会让容量规划更难预测。

**参考答案**

Agent 会把一次请求变成一个长会话工作流，里面可能有：

- 多次模型调用
- 工具调用
- 中间状态保存
- 失败重试与停止条件判断

Thinking Model 则会让单次模型调用内部消耗更多 reasoning tokens，token 消耗更难提前预测。

对基础设施的影响是：

- 会话持续时间变长
- token 和 GPU-second 分布长尾变重
- 并发不能再只按短请求 QPS 估算
- 需要 session 级预算、trace、回退和限流

**延伸提醒**

- Agent 不是“多轮 prompt”，而是带状态、预算和停止条件的执行系统。

### 第2题：给定 1,000 个并发 agent session、平均每个 session 6 次模型调用、每次调用平均 1.5 秒 GPU 时间，估算总 GPU-second 需求，并说明还缺哪些容量假设。

**思路**

- 直接乘法算总需求，再说明为什么这还不是容量规划。

**参考答案**

总 GPU-second 需求为：

```text
1000 sessions × 6 calls/session × 1.5 GPU-second/call = 9000 GPU-second
```

如果希望在 60 秒内处理完这批会话，理论上需要约：

```text
9000 / 60 = 150 GPU
```

但还缺这些假设：

- session 到达分布
- 每次调用的 token 长度分布
- 是否能 batch
- 工具调用等待是否占 GPU
- 重试率和失败率
- 目标 P95 / P99 延迟

**延伸提醒**

- 总 GPU-second 是容量下限，不是线上副本数。

### 第3题：为什么 agent 容量规划不能只用 `QPS x request latency`？请和传统在线推理调度做对比。

**思路**

- 传统推理请求通常边界清楚，Agent session 边界更长、更动态。

**参考答案**

传统在线推理里，一个请求通常对应一次模型调用，`QPS × latency` 可以粗略估并发。

Agent 不适合这样算，因为一个 session 可能包含：

- 多次模型调用
- 工具调用等待
- 验证和重试
- 中间状态持有
- 不同分支路径

所以 Agent 容量规划更应看：

- session 并发
- 每 session 模型调用数
- GPU-second
- tool wait time
- 失败重试成本

**延伸提醒**

- Agent 平台的基本单位更像“会话工作流”，不是单个 HTTP request。

### 第4题：Chain-of-Thought、Best-of-N sampling、Tree search / beam search、Verifier-guided generation 分别会把成本放大到哪里？

**思路**

- 分清 token 放大、候选放大、搜索分支放大和验证放大。

**参考答案**

| 方法 | 成本放大位置 |
|------|--------------|
| Chain-of-Thought | reasoning tokens 变多，单次调用更长 |
| Best-of-N | 多个候选并行或串行生成，采样成本近似乘以 N |
| Tree search / beam search | 多分支探索，状态和模型调用次数一起放大 |
| Verifier-guided generation | 额外验证模型 / 规则调用，以及失败后的再生成 |

这些方法本质上都是用更多推理时计算换更高成功率，但放大的资源类型不同。

**延伸提醒**

- 不同放大方式应接不同预算阈值，不能只用一个 `max_tokens` 管全部。

### 第5题：如果一个请求允许 `max_thinking_tokens=8,000`，但租户剩余预算只够 4,000 个 reasoning tokens，你会如何设计截断和降级策略？

**思路**

- 预算不足时不应默默超支，也不应直接粗暴失败。

**参考答案**

一个可执行策略是：

- 将本次请求的 reasoning 上限降到 `4,000`
- 在 prompt / system policy 中明确要求简化推理路径
- 禁用高成本策略，如 Best-of-N、tree search
- 如果任务仍不能在预算内完成，返回 partial result 或请求用户升级预算

同时要记录：

- 原始请求预算
- 实际下发预算
- 是否触发降级
- 输出是否为 best-effort

**延伸提醒**

- 预算降级必须可审计，否则租户很难理解质量为什么下降。

### 第6题：请为一个“数学求解 agent”设计最大步数、最大工具调用数、`per_request_gpu_second_budget` 和回退策略。

**思路**

- 数学求解任务适合较高推理预算，但仍要有硬停条件。

**参考答案**

一个最小策略可以是：

```yaml
agent_policy:
  max_steps: 12
  max_tool_calls: 6
  max_retry_per_tool: 2
  per_request_gpu_second_budget: 25
  fallback:
    - if verifier_failed_twice: switch_to_direct_solution
    - if budget_exceeded: return_partial_with_uncertainty
    - if tool_timeout_repeats: disable_tool_and_finish_best_effort
```

关键是把“继续思考”和“必须停止”都变成控制面规则。

**延伸提醒**

- 数学 agent 最怕无限修正，所以 verifier 和预算阈值必须成对出现。

### 第7题：为什么 verifier-guided generation 需要把生成队列和验证队列分开限流？

**思路**

- 生成和验证是两类不同资源池，混在一起容易互相拖垮。

**参考答案**

如果不分开限流，可能出现：

- 生成端产出大量候选，把验证端打爆
- 验证端变慢后，生成端继续堆积无效候选
- 一个高预算任务挤占其他短请求

分开限流后，平台可以分别控制：

- 生成模型 GPU 预算
- verifier GPU / CPU 预算
- 候选队列长度
- 失败重试次数

**延伸提醒**

- verifier 不是免费裁判，它本身也是生产资源。

### 第8题：Agent session 如何映射到 vLLM / TRT-LLM 请求？为什么长 session 不应该直接等同于一个超长推理请求？

**思路**

- Agent session 是控制面概念，推理引擎请求是运行时调用。

**参考答案**

一个 Agent session 通常会映射成多次 vLLM / TRT-LLM 请求：

```text
session
  -> plan call
  -> tool call
  -> observe call
  -> verify call
  -> final call
```

长 session 不应该直接等同于一个超长推理请求，因为：

- 工具调用期间不应占着 GPU decode 槽位
- 中间状态可能需要压缩或摘要
- 每一步都可能有不同模型、预算和超时
- 失败恢复需要从步骤边界重试

**延伸提醒**

- 把整个 session 塞成一个超长上下文，往往会把 KV Cache 和调度都拖垮。

### 第9题：Tool calling 沙箱至少应该限制哪些资源？请说明超时、权限、网络和文件边界各自防止什么风险。

**思路**

- 工具调用是 Agent 系统最容易产生副作用的地方。

**参考答案**

沙箱至少应限制：

- 超时：防止工具长时间挂起，占用 session 和 worker
- 权限：防止越权访问凭据、生产系统或敏感 API
- 网络：防止任意外连、数据外泄或 SSRF 类风险
- 文件边界：防止读写不该访问的路径，污染宿主环境
- CPU / 内存：防止单个工具调用耗尽机器资源

**延伸提醒**

- 工具权限应该按任务最小化，而不是按 agent 全局放开。

### 第10题：多 Agent 并发运行时，怎样做租户级资源隔离，避免一个高预算 session 挤占其他短请求？

**思路**

- 关键是按租户和任务类型做预算与队列隔离。

**参考答案**

可以组合这些手段：

- 租户级并发上限
- 每 session GPU-second 预算
- 短请求和长 agent session 分队列
- 高预算任务只能使用专用或低优池
- verifier、tool worker、生成模型分别限流

这样一个高预算 session 即使还没耗尽自己预算，也不能无限占用共享队列。

**延伸提醒**

- Agent 多租户隔离必须管“过程资源”，不仅是最终 token 数。

### 第11题：长 context 与 Ch 15 的 KV Cache 有什么关系？prefix caching 和 KV 生命周期管理分别解决什么问题？

**思路**

- 长 context 会直接放大 KV Cache，缓存策略是缓解但不是消除。

**参考答案**

长 context 会让 KV Cache 随上下文长度、层数和并发一起增长。Agent 又常常有长会话历史，所以 KV 管理会成为核心瓶颈。

两类机制解决的问题不同：

- prefix caching：复用相同前缀，减少重复 prefill
- KV 生命周期管理：决定哪些 KV 保留、转移、驱逐或压缩，避免长会话无限占显存

**延伸提醒**

- prefix cache 的 key 必须包含租户和工具上下文，否则可能出现隔离问题。

### 第12题：如果一个 agent 系统成功率更高，但单位成本翻了 4 倍，你会如何判断它是否应该上线？

**思路**

- 成本翻倍不是自动否决，关键看增量收益能否覆盖增量成本。

**参考答案**

我会先判断：

1. 成功率提升是否真的带来业务收益
2. 成本上涨是否可被转化率、留存或人工替代节省覆盖
3. 是否可以只对高价值请求启用 agent 模式
4. 有没有更低成本替代方案

如果收益只出现在低价值场景，就不应全量上线。更常见的策略是：

- 分层路由
- 对复杂任务启用
- 设置预算上限
- 保留普通模型 fallback

**延伸提醒**

- Agent 上线决策应看 `incremental value / incremental cost`，不是只看成功率。

### 第13题：设计一个 Agent 成本预测面板，至少包含 token、GPU-second、工具调用、session 时长和失败重试成本。

**思路**

- 面板要能解释“钱花在哪里”，而不是只展示总成本。

**参考答案**

一个最小面板应包含：

- input / output / reasoning tokens
- GPU-second，按模型和步骤拆分
- 工具调用次数、耗时、失败率
- session 总时长和步骤数
- 重试次数和重试消耗
- 单租户、单任务类型、单版本分桶成本

同时应提供：

- P50 / P95 / P99
- 每成功任务成本
- 每失败任务浪费成本

**延伸提醒**

- Agent 成本面板必须能按步骤 drill down，否则很难定位哪个环节在放大成本。

### 第14题：Agent 执行失败后，哪些步骤适合自动重试，哪些步骤应该直接返回 partial result 或转人工？为什么？

**思路**

- 按“是否幂等、是否可恢复、是否有副作用”判断。

**参考答案**

适合自动重试的步骤：

- 瞬时模型超时
- 幂等工具查询
- verifier 临时失败
- 可从明确 step 边界恢复的中间生成

不适合盲目自动重试的步骤：

- 有外部副作用的工具调用，如下单、发邮件、改配置
- 已经多次验证失败的推理路径
- 预算即将耗尽的长任务
- 涉及高风险权限或敏感数据的操作

这些情况更适合返回 partial result、请求用户确认或转人工。

**延伸提醒**

- 自动重试必须避开非幂等副作用，否则会把小故障放大成事故。

## Part 0：体系结构基础新增练习参考答案

> 本节补齐 Batch 1 中 Part 0 四章新增练习题。题号与正文中的 `0a-*`、`0b-*`、`0c-*`、`0d-*` 对应，答案以判题要点为主。

### 0a CPU 微架构

**0a-1：CPI 估算**

理想 5 段流水线稳定后 CPI 接近 1，但真实 CPI 要加上 stall。估算时可写成 `CPI = 1 + 分支停顿 + cache miss 停顿 + 数据依赖停顿 + 结构冲突停顿`。如果 20% 指令访存、L1 miss 率 5%、miss penalty 30 cycles，仅 cache 项就约 `0.2 x 0.05 x 30 = 0.3` CPI。

**0a-2：识别冒险**

RAW 是后一条读前一条尚未写回的值；WAR/WAW 多见于乱序机器里的名字依赖；控制冒险来自分支路径未知；结构冒险来自多个指令争同一硬件资源。答案应说明具体依赖、会造成什么等待，以及 forwarding、stall、renaming 或预测分别能缓解哪一类。

**0a-3：假依赖**

假依赖不是数据语义必须等待，而是多个逻辑变量复用了同一个寄存器名。Register renaming 把架构寄存器映射到不同物理寄存器，消除 WAR/WAW，使 CPU 可以让无关指令并行执行。

**0a-4：ROB 的必要性**

ROB 让指令可以乱序执行、顺序提交。没有 ROB，异常、分支回滚和精确状态会很难保证；有 ROB 后，错误路径结果可以丢弃，正确路径结果按程序顺序变成可见状态。

**0a-5：BTB 与方向预测**

方向预测回答“分支走不走”，BTB 回答“跳到哪里”。方向预测对了但 BTB miss，取指仍可能停顿；BTB 有目标但方向错，流水线会取错路径并在分支解析后 flush。

**0a-6：Cold path**

AI 服务的异常分支、低频 tokenizer 规则、罕见 schema、工具调用错误路径常常缺少分支历史和 i-cache 热度。冷路径第一次触发时可能同时遇到分支误预测、指令 cache miss、数据 cache miss 和动态加载开销，所以尾延迟会比平均值敏感。

**0a-7：向量宽度**

SIMD 理论加速约等于一次能处理的元素数，例如 AVX2 256-bit 可同时处理 8 个 int32 或 4 个 double。但真实收益受内存带宽、对齐、分支、尾部处理、gather/scatter 和 decode/encode 逻辑限制。

**0a-8：Tokenizer SIMD**

适合 SIMD 化的 tokenizer 热点通常有连续字节扫描、ASCII 分类、查表、delimiter 搜索等特征。不适合的情况包括复杂 Unicode 状态机、频繁分支、随机访问、短字符串占多数。应先用 profiling 找热点，再用向量化报告和 benchmark 验证。

**0a-9：Cache line 浪费**

如果每次只读 8B，但硬件搬运 64B cache line，空间局部性差时有效带宽只有 1/8。结构体数组中只访问少数字段时，SoA 往往比 AoS 更容易提高 cache line 利用率。

**0a-10：关联度冲突**

多个热点地址若映射到同一 cache set，即使总 working set 小于 cache 容量，也可能反复驱逐。判断方式包括改变数组 stride、padding、对齐或数据布局后 miss 率明显变化。

**0a-11：MESI 状态转移**

单核独占写入通常从 E 到 M；其他核读取该 line 后变成 S；某核要写共享 line 时，需要让其他副本 Invalid。频繁跨核写同一 line 会造成 invalidation storm，这就是伪共享的硬件根源。

**0a-12：Counter 布局**

多 worker counter 应让每个线程写独立 cache line，例如按 64B 或更保守的硬件 destructive interference size padding。最终汇总时再读所有 counter，避免每次更新都让其他 core 的 cache line 失效。

**0a-13：完整排查 Runbook**

先固定数据、batch、worker 数和 CPU 频率，记录吞吐与 p95/p99；用 `perf stat` 看 IPC、cache miss、branch miss、context switch；用 `perf record` 找热点；用 `perf c2c` 查伪共享；再做 worker 数、NUMA 绑定、padding、预取和 tokenizer SIMD 的对照实验。结论必须来自 A/B 数字，而不是单次观察。

**0a-14：Tokenizer Host Bottleneck**

如果 GPU 计算很快但 step 间隔被 tokenizer 卡住，应拆 input pipeline：读取、解压、tokenize、collate、H2D。优化路径包括离线预 tokenization、批量 tokenizer、SIMD/多进程、减少 Python GIL 热点、NUMA 绑定、pinned memory 和 overlap。最终看 GPU idle time 是否下降，而不只看 tokenizer microbenchmark。

### 0b 内存、虚拟内存与 IO

**0b-1：虚拟地址翻译**

CPU 先用虚拟地址查 TLB；命中后直接得到物理页框，未命中则走页表遍历。连续虚拟地址不保证物理连续，大数组随机访问可能同时放大 cache miss 和 TLB miss。

**0b-2：Page Cache 判断**

第二轮 dataset 更快通常是 Page Cache 命中。可通过 drop caches 前后对比、观察 `cached`/`buff/cache`、`vmtouch`、`mincore`、磁盘 `iostat` 和进程吞吐验证。不能把第二轮速度当作冷启动存储吞吐。

**0b-3：Dirty page 估算**

脏页阈值约为可回写内存乘以 `vm.dirty_ratio` 或 `dirty_bytes`。checkpoint 写入先进入 Page Cache 时，短时间看似很快，但达到阈值后会被 writeback 节流，尾延迟突然升高。

**0b-4：THP 观察**

检查 `/sys/kernel/mm/transparent_hugepage/enabled`、`/proc/meminfo` 中 AnonHugePages，以及 `perf` 的 TLB miss。THP 可降低 TLB 压力，但 page collapse、split 或 compaction 可能制造延迟尖峰；低延迟服务需谨慎。

**0b-5：NUMA locality**

应让 DataLoader worker、内存分配、GPU 所属 PCIe root complex 尽量落在同一 NUMA node。可用 `numactl --hardware`、`nvidia-smi topo -m`、`numastat` 验证；跨 socket 会降低 H2D 和内存读取吞吐。

**0b-6：PCIe 带宽**

PCIe 带宽由代际和 lane 数决定，例如 x16 约等于 x8 的两倍。估算时要扣除编码和协议开销，并检查是否因拓扑、共享 switch、BIOS 配置或设备降速实际跑在较低 lane/速率。

**0b-7：fork 与 copy-on-write**

fork 后父子进程先共享物理页，任一方写入才复制。它节省启动内存，但 DataLoader worker 若修改大对象，会触发大量 COW，导致内存暴涨和 page fault。

**0b-8：`io_uring` 适用性**

`io_uring` 适合大量异步文件或 socket IO、需要减少 syscall/上下文切换的场景。若瓶颈在磁盘本身、应用 CPU 处理、对象存储尾延迟或同步语义，换 `io_uring` 不会自动解决。

**0b-9：Pinned memory 副作用**

Pinned memory 能提高异步 H2D 拷贝效率，但过多 page-locked 内存会挤压可回收内存、影响 Page Cache 和系统调度。应设置上限，并观察内存压力、H2D 带宽和训练吞吐。

**0b-10：Topology 推理**

看 GPU、NIC、NVMe 分别挂在哪个 CPU root complex 下。理想路径是 GPU 和 NIC/NVMe 在同一 socket 或同一 PCIe switch 附近；跨 UPI/QPI 的路径会增加延迟、降低带宽，并影响 RDMA/GPUDirect。

**0b-11：8 GPU DataLoader 亲和方案**

按 GPU 拓扑把 worker 绑定到同 NUMA node 的 CPU core，数据预取 buffer 在本地内存分配，启用合理的 `pin_memory`，避免所有 worker 抢同一磁盘或同一锁。每张卡应有独立或均衡的数据队列，并记录每卡 input wait。

**0b-12：Checkpoint 写入策略**

大 checkpoint 可采用分片写临时文件、并发写入、校验、`fsync` 文件和目录、最后原子 rename/manifest 切换。要限制脏页堆积，避免训练进程在 writeback 阶段被长时间阻塞。

**0b-13：低延迟推理 IO**

低延迟控制面优先减少阻塞 syscall、连接抖动和内存分配；socket 可用 epoll/io_uring，权重和配置应预加载或 mmap 后预热。不要让首次请求承担 page fault、模型加载、TLS 建连和动态编译成本。

**0b-14：训练机房 NUMA 与 PCIe 拓扑健康检查 SOP**

下面是 8 项必检点，每项给出"检查命令 / 期望值 / root cause / 修复路径"。修复路径都按"临时缓解 + 最终修复"两步给出。

| # | 检查项 | 检查命令 | 期望值 | 异常 root cause | 临时缓解 → 最终修复 |
|---|---|---|---|---|---|
| 1 | NUMA node 拓扑 | `numactl -H`；`lscpu \| grep NUMA` | 双路机器看到 2 nodes，每 node 内存均衡（差 ≤ 2 GB） | BIOS 关闭 NUMA / 单内存通道故障 | 临时：避免单 socket 调度；最终：BIOS 打开 NUMA + 工单换内存条 |

### 0c 文件系统与存储内核

**0c-1：VFS 路径**

一次文件读取大致经过路径解析、dentry/inode、权限检查、Page Cache 命中判断、文件系统方法、block layer、设备驱动。VFS 提供统一抽象，具体 ext4/XFS/ZFS 决定底层元数据和数据布局。

**0c-2：write 成功的含义**

`write()` 成功通常只表示数据已进入内核缓冲或提交给底层路径，不等于持久落盘。崩溃一致性需要 `fsync`、目录同步、rename 协议和校验/manifest 配合。

**0c-3：ext4 journal**

ext4 journal 主要保护元数据一致性；不同模式对数据是否进入 journal 有差异。它能提升崩溃恢复确定性，但 checkpoint 大文件频繁提交可能带来额外写放大和尾延迟。

**0c-4：XFS 适配**

XFS 擅长大文件、并发写和大目录场景，B+tree 元数据结构适合扩展。AI checkpoint 和大 shard 写入常适合 XFS，但小文件极多时仍需关注目录、inode 和元数据压力。

**0c-5：对象存储语义**

对象存储适合不可变 shard、checkpoint 归档和大规模分发，但不是 POSIX 文件系统。目录、append、rename、fsync、权限和一致性语义都不同，应用应使用 manifest 和分片上传协议。

**0c-6：IOPS 换算**

小随机 IO 吞吐约等于 `IOPS x block_size`。例如 50k IOPS、4KB 随机读约 200MB/s；同一设备顺序读可能有数 GB/s，所以小文件训练很容易被 IOPS 而不是带宽限制。

**0c-7：Page Cache 误判**

若 benchmark 第二次明显更快，且磁盘 `iostat` 读吞吐下降、Page Cache 增加，说明测到的是内存缓存。应分别测 cold cache、warm cache 和真实训练混合负载。

**0c-8：`O_DIRECT` 取舍**

`O_DIRECT` 可减少 Page Cache 污染和双份拷贝，但要求对齐，可能降低小 IO 合并能力。它也不自动等价于持久化，仍需考虑 flush、barrier、fsync 或设备缓存策略。

**0c-9：小文件瓶颈**

大量小文件会放大 open/stat/list、inode、目录锁和 MDS 压力。解决方向包括 shard/tar/webdataset、合并索引、预取、减少目录列表、并行文件系统 MDS 扩容或本地缓存。

**0c-10：ZFS dataset 仓库**

ZFS 适合需要快照、校验、压缩和可回滚 dataset 的场景。代价是 COW 写放大、ARC 内存占用和 sync 写策略复杂；训练热路径需验证尾延迟和内存竞争。

**0c-11：Checkpoint 发布协议**

推荐写入 `tmp/step-id/rank-*`，每个分片写完校验并 fsync，生成 manifest，fsync 目录，最后用原子 rename 或提交 manifest 标记可见。恢复只读取完整 manifest 指向的分片，清理未完成临时目录。

**0c-12：混合存储架构**

本地 NVMe 做热缓存和临时 spill，并行 FS 做训练热层和 checkpoint 最新 N 份，对象存储做归档和跨集群分发。控制面负责生命周期、校验、预热和回收，避免用户手工搬文件。

**0c-13：Stripe 策略**

大 checkpoint 分片应按 rank 数、OSS 数和目标吞吐设置 stripe，避免所有 rank 写同一 OST 或同一目录热点。小文件不应盲目加大 stripe，应先减少文件数或优化 MDS 压力。

**0c-14：200TB checkpoint 仓库文件系统选型**

按题目给出的 6 维权重（吞吐 0.25 / 尾延迟 0.10 / 一致性 0.20 / 快照 0.15 / 容量成本 0.20 / 运维 0.10）对五个候选打分（1-5 分），并给出加权总分：

| 维度（权重） | ext4 | XFS | ZFS | Lustre | WekaFS |
|---|---:|---:|---:|---:|---:|
| 持续吞吐（0.25） | 2 单机受限 | 3 单机较好 | 3 CoW 写放大 | 5 stripe 易扩 | 5 NVMe 全闪 |
| 尾延迟（0.10） | 4 简单可控 | 4 同上 | 2 ARC/sync 抖动 | 3 MDS 偶发抖动 | 4 设计低延迟 |
| 一致性（0.20） | 3 journal | 3 journal | 5 CoW + checksum | 4 分布式锁 | 4 强一致 |
| 快照/版本（0.15） | 1 需 LVM | 1 需 LVM | 5 内建 | 3 依赖产品 | 4 内建 snap |
| 容量成本（0.20） | 5 最便宜 | 5 同上 | 4 需大内存 | 2 HPC 硬件 | 1 商用 NVMe 贵 |
| 运维复杂度（0.10） | 5 最简单 | 4 简单 | 3 需 ZFS 经验 | 1 需 HPC 专人 | 2 厂商支持必备 |
| **加权总分** | **3.05** | **3.30** | **3.65** | **3.50** | **3.70** |

加权决策：WekaFS（3.70）与 ZFS（3.65）最高，但 WekaFS 在"容量成本 0.20"和"运维 0.10"两个高权重项被压低；考虑团队"不能新招 HPC 专人"的硬约束，**最终推荐 ZFS（单池 raidz2，配 SLOG + L2ARC）做主仓库**，理由：(a) 一致性 + 内建快照覆盖了 0.35 的总权重；(b) 写放大可通过 `recordsize=1M`、关闭 `atime`、`compression=zstd-3`、`sync=standard` 调优；(c) 14 天滚动窗口正好契合 ZFS snapshot；(d) 团队不需要 HPC 经验。建议分层架构：

- **L0 训练节点本地 NVMe（XFS）**：写临时 checkpoint，30 分钟后 rsync/zfs send 到 L1。
- **L1 ZFS 主仓库（200TB raidz2）**：保留最新 14 天 + 每日 snapshot；对外通过 NFS/RDMA 暴露给恢复任务。
- **L2 对象存储归档**：保留每周一份 + 关键模型里程碑，做跨 region 副本。

**会换选的三种条件：**

1. **单 checkpoint 体积翻倍（→ 100GB+/rank、聚合吞吐 ≥ 25 GB/s）**：换 **WekaFS** 或 **Lustre**；ZFS 单池吞吐瓶颈会让 step 间隔超出预算。
2. **加入"GPU 直挂 RDMA 读取"需求**：换 **WekaFS**（原生支持 GPUDirect Storage）或 Lustre + DAOS；ZFS 的 ARC 路径无法绕过 host memory。
3. **TCO 上限砍半到 $0.025/GB·月**：换 **XFS + 对象存储分层**（XFS 做最近 3 天热层，其余全部归档到 S3 IA / Glacier），放弃内建快照换成 manifest + immutable key 协议。

### 0d 网络协议栈基础

**0d-1：`send()` 到发包路径**

典型路径是用户态 buffer、syscall、socket buffer、TCP/IP 协议栈、qdisc、网卡驱动、DMA ring、NIC 发包。若启用 offload，分段、校验和等部分工作可下推到 NIC。

**0d-2：三次握手为什么不是两次**

三次握手让双方都确认自己发送和接收能力可用，并同步初始序列号。两次无法让服务端确认客户端已收到服务端的 SYN-ACK，也更难处理旧连接报文干扰。

**0d-3：MTU 对包数影响**

同样 1GB 数据，MTU 1500 会产生远多于 MTU 9000 的包数。包数越多，CPU 中断/轮询、协议栈处理、交换机转发和队列管理开销越高；但 jumbo frame 必须端到端一致。

**0d-4：Receive window 与 congestion window**

Receive window 是接收端还能收多少，防止把接收端 buffer 打爆；congestion window 是发送端根据网络拥塞估计能发多少，防止把网络路径打爆。吞吐受二者较小者限制。

**0d-5：5 个网络排查命令**

可列 `ip addr/route`、`ss -tinp`、`ethtool -S`、`tcpdump`、`ping`/`tracepath`、`iperf3`、`nstat`、`ibstat`、`ib_write_bw`。答案应说明每个命令看链路、路由、连接、包、吞吐或 RDMA 哪一层。

**0d-6：RSS 影响多核收包**

RSS 把不同 flow 分配到多个 RX queue，再由不同 CPU core 处理。未配置好时，所有流量集中到单队列/单 core，会出现单核软中断打满但总 CPU 和网卡带宽未满。

**0d-7：CUBIC 与 BBR**

CUBIC 主要按丢包和窗口增长行为调节，适合传统互联网默认场景；BBR 估计瓶颈带宽和 RTT，可能改善高带宽时延积链路。选择时要看公平性、队列延迟、丢包模型和与网络设备策略的兼容。

**0d-8：RDMA Write 生命周期**

应用注册内存，建立 QP，提交 RDMA Write WR 到 send queue，HCA 通过 DMA 读取本地内存并经网络写入远端注册内存，完成后在 CQ 产生 WC。数据路径绕过远端 CPU，但控制面仍需建连、权限和内存注册。

**0d-9：RoCE v2 为什么需要 ECN/PFC**

RoCE 对丢包敏感，丢包会造成性能急剧下降。PFC 用 pause 降低特定优先级丢包，ECN 用拥塞标记促使端侧降速；二者配置不当会导致 pause storm、拥塞扩散或吞吐不稳。

**0d-10：判断 NCCL fallback 到 socket**

看 `NCCL_DEBUG=INFO` 日志中的 NET/IB、NET/Socket、GID、HCA 选择和拓扑；用 `nccl-tests` 对比预期 RDMA 带宽。若带宽接近 TCP、日志显示 Socket 或找不到 IB device，通常是 fallback。

**0d-11：32 节点训练网络验收清单**

至少覆盖链路速率、MTU、ECN/PFC、无错误计数、GPU-NIC 拓扑、单链路 RDMA bw/lat、跨 rack all-reduce、NCCL 多消息大小、故障告警和交换机拥塞指标。验收要覆盖不同节点组合，而不是只测两台。

**0d-12：推理服务 control plane IO 模型**

低到中等并发可用成熟 HTTP server + epoll；高并发、长连接、流式响应可关注事件循环 backpressure 和 flush 延迟；`io_uring` 只有在 syscall/上下文切换成为明确瓶颈时才值得引入。

**0d-13：GPU 与 NIC 亲和放置**

调度时优先让 GPU 使用同 socket、同 PCIe switch 或拓扑最近的 NIC，并让 CPU worker 绑定到相同 NUMA node。多 rail 集群应让每张 GPU 走预期 rail，避免跨 socket 绕路和 rail 不均衡。

**0d-14：AI 训练集群网络配置交付清单**

下面是 8 个维度的交付清单，每项均覆盖"检查命令 / 期望值 / 错误时影响 / 责任角色"四列。

| 维度 | 检查命令 | 期望值 / 配置目标 | 错误时的影响 | 责任角色 |
|---|---|---|---|---|
| 1. NIC 固件 / driver | `ethtool -i ens5f0`；`ofed_info -s` | 与厂商 LLM training reference matrix 一致；MOFED 5.8+ / firmware 与 H100 RDMA 推荐版本对齐 | RDMA QP 创建失败、CQE syndrome 异常、driver crash | 系统/网络组 |
| 2. PFC | `mlnx_qos -i ens5f0`；交换机 `show priority-flow-control` | 仅在 RoCE priority（如 3）启用 PFC；其他 priority 关闭，端到端一致 | 全局 pause storm；非 RoCE 流被反压；HOL blocking 拖垮控制面 | 网络组 |
| 3. ECN + DCQCN | `mlnx_qos -i ens5f0 --trust dscp`；交换机 `show qos red-thresholds` | ECN 在 RoCE priority 启用；WRED min/max ≈ 150KB / 1.5MB（按 buffer 调）；DCQCN 默认参数 | DCQCN 收不到拥塞信号 → 只能等 PFC 触发；尾延迟暴涨 | 网络组 + 训练平台 |
| 4. MTU | `ip -d link show ens5f0`；`ping -M do -s 8972 <peer>` | NIC 9000、VLAN/bond 9000、overlay 头部预留后 ≥ 8950 | RoCE 大包分片 → 吞吐折半；连接频繁断开 | 网络组 |
| 5. RoCE QoS（DSCP/802.1p） | `cma_roce_tos -d mlx5_0`；交换机 `show qos dscp-mapping` | DSCP 26 → priority 3 → traffic class 3；端到端映射一致 | RoCE 流量与存储 / 控制流共用同一队列，相互踩踏 | 网络组 |
| 6. `NCCL_TOPO_FILE` | `cat $NCCL_TOPO_FILE`；NCCL 启动日志 `Topology` 段 | XML 描述 GPU/NIC/NVLink/PCIe 真实拓扑；NCCL 选 ring/tree 与拓扑匹配 | NCCL 选错 transport 或绕远 → AllReduce 慢 30%-50% | 训练平台 |
| 7. IB `sm_priority`（或 RDMA CM） | InfiniBand：`ibstat`；`smpquery`；RoCE 替代：`rdma link show`、`rdma resource show` | IB：每子网仅一台 active SM、priority 一致；RoCE：N/A，但需配 RDMA CM GID index 和路由权重一致 | 多 SM 抢主→ fabric 抖动；GID index 选错 → RoCE handshake 失败 | 网络组（HPC 团队） |
| 8. libfabric provider | `fi_info -p verbs`；`fi_info -p efa` | 训练用 verbs（RoCE/IB）；AWS EFA 节点用 efa；同节点不混用 shm 之外的多 provider | provider mismatch → NCCL fallback socket，带宽掉到 1/10 | 训练平台 |

**三段验收节奏：**

| 时间窗 | 验收项 | hard / soft gate |
|---|---|---|
| 上线前 7 天 | 1. 固件版本 audit；2. 全节点 MTU 端到端 ping；4. PFC/ECN 配置；6. `NCCL_TOPO_FILE` 与 `nvidia-smi topo -m` 一致 | 全部 **hard gate** — 任一不通过禁止入池 |
| 上线当天 | nccl-tests AllReduce/AllGather 跨全部节点；`ib_write_bw` pair-wise；libfabric provider check；冷启动后 NCCL_DEBUG=INFO 抽样 | nccl-tests bus bandwidth ≥ 期望 80% 为 **hard gate**；其余 soft gate（带 caveat 上线 + 24h 内整改） |
| 上线后 30 天 | DCQCN/ECN mark 趋势；PFC pause 帧速率；RoCE 重传计数；NCCL p99 step time；交换机 buffer occupancy | **soft gate**：进入持续观测仪表盘；若任一指标连续 3 天恶化 → 触发 incident review |

判分要点：必须 (a) 区分 hard / soft gate（不能全部 hard，否则永远上不了线）、(b) 把 #2/#3/#4 三项识别为 RoCE 训练最常见故障来源、(c) 给出可执行的 `mlnx_qos` 与交换机侧命令、(d) 在 IB sm_priority 一项里识别"RoCE 集群无 SM"并给出 RDMA CM 替代验证方法。
