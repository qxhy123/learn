# 附录H：AI Infra 面试与自测评分 Rubric

> 本附录提供一套通用评分模板，用来校准第26章题库和第27章模拟面试。它不替代具体题目的标准答案，而是判断一个回答是否具备可复用的系统推理能力。

## 1. 通用五步框架

任何 AI Infra 面试题都可以先按五步组织答案：

1. **识别资源**：先说清瓶颈候选项，至少覆盖 GPU/SM、HBM/KV Cache、CPU、网络、存储、调度队列、制品和权限边界。
2. **画链路**：把请求、训练 step、发布流程或供应链路径画成端到端链路，标出控制面、数据面和观测面。
3. **给证据**：用指标、日志、trace、profile、审计记录、版本差异或复现实验支持判断，避免只凭经验下结论。
4. **定方案**：给出短期止血、根因修复和长期治理方案，并说明取舍：吞吐、延迟、稳定性、成本、安全或交付速度。
5. **说 rollback**：明确什么情况下回滚，回滚对象是什么，如何验证回滚成功，以及如何避免回滚放大风险。

这个框架适用于 GPU 利用率低、NCCL timeout、KV OOM、发布回滚、安全供应链等题。题目不同，资源和链路不同，但评分关注点一致：候选人是否能从现象走到证据，再从证据走到可执行决策。

## 2. 1-5 分评分标准

| 分数 | 标准 | 典型表现 |
|------|------|----------|
| **1 分** | 只会背名词或给单点建议 | 把问题归因到某个组件；没有资源分类、链路图、证据或 rollback；容易把“重启”“扩容”“换框架”当万能解 |
| **2 分** | 能说出部分资源和常见原因 | 能列 GPU、显存、网络等关键词，但链路不完整；证据停留在“看监控”；方案缺少优先级和失败预案 |
| **3 分** | 及格：能按资源和链路排查 | 能区分训练/推理/平台/安全题的关键路径；能提出基本指标和止血动作；rollback 仍偏笼统 |
| **4 分** | 良好：能用证据驱动方案 | 能把指标、日志、profile、版本和配置变更串起来；能说明方案取舍、验证方式和风险边界 |
| **5 分** | 优秀：能兼顾诊断、设计和治理 | 能主动缩小影响面，提出可操作实验，给出分阶段方案、rollback 条件、复盘改进和组织协作方式 |

## 3. 答案结构模板

### 优秀答案结构

1. 先复述约束和影响面：业务 SLO、规模、资源、版本、最近变更和不可接受风险。
2. 按“识别资源”列出最可能的 3-5 个瓶颈候选项，并说明优先级。
3. 用“画链路”描述端到端路径，标出可能阻塞点和观测位置。
4. 用“给证据”说明要看哪些指标、日志、profile 或审计记录，以及如何排除反例。
5. 用“定方案”分成止血、修复、治理三层，并说明代价。
6. 用“说 rollback”定义触发条件、回滚粒度、验证指标和回滚后的复盘项。

### 及格答案结构

1. 能先分类问题，不直接跳到工具或命令。
2. 能说出主要资源和主链路。
3. 能列出至少 3 个有效证据来源。
4. 能给出一个可执行止血方案和一个后续修复方向。
5. 能说明需要准备 rollback，但回滚细节可能不完整。

### 危险答案结构

1. 一上来就断言根因，且没有证据。
2. 只说“加机器、重启、调参数、升级版本”，不说明影响面和副作用。
3. 把训练题、推理题、发布题、安全题都套同一个答案。
4. 忽略控制面和数据面的边界，把高风险逻辑放进热路径。
5. 不提 rollback，或认为 rollback 等于简单退回旧版本。

## 4. 场景化使用

### GPU 利用率低

- 识别资源：GPU SM、HBM 带宽、CPU dataloader、H2D、存储读取、网络等待、batching。
- 画链路：数据读取 -> CPU 预处理 -> H2D -> kernel -> 通信/同步 -> checkpoint 或返回。
- 给证据：GPU utilization、SM occupancy、memcpy、dataloader wait、CPU perf、storage throughput、profiler timeline。
- 定方案：先确认是数据饿死、同步等待还是 kernel 低效，再分别调 worker、pin memory、batch、算子或拓扑。
- 说 rollback：调大 batch、worker 或 fused kernel 后要能退回基线配置，并验证吞吐、错误率和显存水位。

### NCCL timeout

- 识别资源：IB/RoCE、NIC、PCIe/NVLink、rank 拓扑、DNS/容器网络、防火墙、straggler。
- 画链路：rank 启动 -> rendezvous -> NCCL 建链 -> collective -> timeout -> elastic/retry。
- 给证据：NCCL debug log、rank 卡点、`NET/IB` 或 `NET/Socket`、接口错误计数、拓扑映射、最近节点或镜像变更。
- 定方案：先隔离坏 rank/坏节点，确认网络 fallback，再修复驱动、MTU、GID、拓扑调度或版本兼容。
- 说 rollback：回滚镜像、驱动、NCCL 参数或调度策略时，要验证同规模最小复现和完整训练 step。

### KV OOM

- 识别资源：权重显存、KV Cache、batch、context length、prefill/decode 比例、并发、fragmentation。
- 画链路：gateway -> scheduler -> prefill -> KV block 分配 -> decode -> evict/free。
- 给证据：请求 token 分布、KV block 使用率、waiting queue、OOM 日志、batch shape、prefix cache 命中率。
- 定方案：短期限流/缩短 max tokens/降低并发，后续调度分层、PD 分离、分页策略、模型并行或容量规划。
- 说 rollback：任何 batching、cache 或 max context 调整都要有旧配置回退，并用 p99、OOM 率、拒绝率验证。

### 发布回滚

- 识别资源：模型制品、配置、路由、评测门禁、灰度流量、依赖服务、观测指标。
- 画链路：registry -> staging -> canary -> production -> telemetry -> rollback。
- 给证据：版本 diff、离线评测、线上质量采样、错误率、p99、成本、审计记录。
- 定方案：先冻结扩量或切回稳定版本，再定位是模型、prompt、engine、配置还是依赖问题。
- 说 rollback：说明回滚粒度是流量、模型、配置、镜像还是数据版本，并验证用户影响已恢复。

### 安全供应链

- 识别资源：镜像、模型权重、数据集、依赖包、Secrets、SBOM、签名和 admission policy。
- 画链路：构建 -> 扫描 -> 签名 -> registry -> 部署准入 -> 运行时审计。
- 给证据：SBOM、cosign/Sigstore 记录、漏洞扫描结果、来源证明、权限审计、异常下载或加载日志。
- 定方案：阻断未知来源制品，隔离受影响版本，补签名/扫描/准入策略，修复长期发布门禁。
- 说 rollback：回到已签名、已扫描、已验证的制品版本，并确认权限、镜像和模型权重都同步回退。

## 5. 面试官追问模板

### 资源与链路

- 你现在假设的瓶颈是哪一种资源？还有哪两种资源可能伪装成同样现象？
- 如果让你画链路，哪个节点是控制面动作，哪个节点是数据面热路径？
- 这个问题在训练、推理、平台岗视角下，优先级会如何变化？

### 证据与排除

- 你会先看哪 3 个指标？每个指标能排除什么，不能排除什么？
- 如果这些指标互相矛盾，你会做什么最小复现实验？
- 最近一次变更可能来自代码、配置、模型、镜像、调度还是依赖服务？你如何验证？

### 方案与取舍

- 你的止血方案会牺牲吞吐、延迟、成本、安全还是用户体验？
- 这个方案在 10 倍流量或 10 倍模型规模下还成立吗？
- 哪个方案最容易上线，哪个方案最能解决根因，为什么不是同一个？

### Rollback 与治理

- rollback 的触发阈值是什么？由谁决策？
- 你回滚的是流量、配置、镜像、模型权重、数据版本还是调度策略？
- 回滚成功要看哪些指标？回滚后还需要补哪些门禁或自动化？
