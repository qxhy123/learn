# 第5章：内存、互联与 IO

> AI 系统的很多性能问题，不是“算子不够快”，而是数据从来没有以正确的方式进入正确的地方。

> **关联章节**：本章内容与 [第4章](./04-gpu-and-accelerators.md) 的硬件选型、[第8章](../part3-training-infra/08-data-parallel.md) 的通信扩展效率密切相关。很多“GPU 不够快”的问题，最后都能追到搬运链路。

## 学习目标

完成本章学习后，你将能够：

1. 理解 HBM、DRAM、SSD、对象存储在 AI 系统中的分工
2. 理解 PCIe、NVLink、RDMA 等互联为什么重要
3. 识别单机和多机场景中的典型 IO 与带宽瓶颈
4. 用“数据搬运链路”视角分析性能问题
5. 理解为什么很多优化本质上是在减少搬运次数
6. 理解集群拓扑与并行文件系统为什么会决定大规模训练上限

## 正文内容

### 5.1 AI 系统的真实问题通常是“数据怎么走”

以训练为例，数据通常会经历：

```text
对象存储 / 文件系统
  -> 本地磁盘缓存
  -> CPU 内存
  -> GPU 显存
  -> 计算
```

以 LLM 推理为例，状态通常会经历：

```text
模型权重
  -> 主机内存
  -> GPU 显存
  -> KV Cache 更新
  -> 输出 token
```

这意味着 AI 系统的性能，往往不是“一个阶段算得多快”，而是“整条搬运链路有没有形成稳定供给”。

### 5.2 一张最重要的层次图

可以把 AI 系统的数据驻留层级粗略理解成：

| 层级 | 典型介质 | 容量 | 延迟 | 带宽 | 典型用途 |
|------|----------|------|------|------|----------|
| 远端持久层 | 对象存储、冷数据仓 | 大 | 高 | 中 | 原始数据、长期归档、跨集群共享 |
| 共享热存储 | 并行文件系统、训练集群共享文件层 | 中大 | 中 | 中高 | 训练热数据、checkpoint 热层、集群共享模型缓存 |
| 本地磁盘 | NVMe / SSD | 中 | 中低 | 高 | 训练缓存、热点模型、shuffle 临时数据 |
| 主存 | DRAM | 中 | 低 | 很高 | dataloader、预处理、中间缓存 |
| 显存 | HBM / GDDR | 小 | 更低 | 极高 | 权重、激活、KV Cache |

理解这张表有两个工程意义：

1. 容量越大的层，往往越慢
2. 越靠近计算设备，容量越贵也越稀缺

所以平台设计经常是在“容量大但慢”和“容量小但快”之间做分层。

### 5.3 PCIe、NVLink、RDMA 到底在解决什么

#### PCIe

CPU 和 GPU 之间最常见的通道。它决定：

- 主机到设备（H2D）拷贝速度
- 多 GPU 通过主机转发时的带宽

#### NVLink / NVSwitch

主要用于 GPU 与 GPU 间高速通信。它对以下场景非常重要：

- 多卡训练
- 张量并行
- 大模型分片推理

#### RDMA / 高速网卡

多机训练或远端高速服务访问时常见。它能降低 CPU 参与和数据复制开销，对大规模训练集群尤为重要。

你可以把它们理解成不同层级的“高速公路”：

- PCIe：CPU 和设备之间
- NVLink：设备和设备之间
- RDMA：机器和机器之间

把抽象概念落到数字上，会更容易判断瓶颈位置：

| 互联 | 典型带宽 | 常见范围 | 更影响哪些场景 |
|------|----------|----------|----------------|
| PCIe 3.0 x16 | 16 GB/s | CPU <-> GPU | 旧机器 H2D / D2H、数据回传 |
| PCIe 4.0 x16 | 32 GB/s | CPU <-> GPU | 目前大量训练节点的基础链路 |
| PCIe 5.0 x16 | 64 GB/s | CPU <-> GPU | 新一代主机侧高带宽拷贝 |
| NVLink 3 | 600 GB/s | GPU <-> GPU | A100 代 8 卡训练、张量并行 |
| NVLink 4 | 900 GB/s | GPU <-> GPU | H100 / H200 代高频同步 |
| InfiniBand NDR | 400 Gb/s（约 50 GB/s） | 机器 <-> 机器 | 多机数据并行、分布式 checkpoint |

注：PCIe 以上数字常用 `x16` 单向口径，NVLink 常用单 GPU 聚合双向口径，InfiniBand 常用端口线速口径。口径不同，但足以帮助你建立数量级直觉。

> **参考数量级（仅供建立直觉，实际值因硬件和配置差异较大）**
>
> | 场景 | 典型值 | 说明 |
> |------|--------|------|
> | 1 GB H2D 拷贝走 PCIe 4.0 x16 | 理论下限约 31 ms | 实际还会受 pinned memory、NUMA 和调度影响 |
> | 1 GB GPU-GPU 传输走 NVLink 4 | 理论下限约 1-2 ms | 更适合频繁激活 / 梯度交换 |
> | 10 GB 数据跨机走 NDR 400G | 理论下限约 0.2 s | 真正训练中还会叠加协议和同步开销 |
> | 跨节点以太网未做 RDMA 优化 | 常见比 IB 慢一截 | 会直接体现在第8章的扩展效率上 |

### 5.4 一个简单的时间拆解

如果一个训练 step 的时间可以写成：

$$
t_{\text{step}} = t_{\text{load}} + t_{\text{h2d}} + t_{\text{compute}} + t_{\text{sync}}
$$

那么你会发现，优化往往有三种路径：

1. **减少数据量**：压缩、缓存、量化、更好的格式
2. **提高带宽**：更快互联、更高吞吐存储、更少中间复制
3. **重叠执行**：让数据准备和计算并行，而不是串行

这三种路径几乎覆盖了很多性能优化的本质。

### 5.5 为什么“减少搬运”经常比“优化计算”更划算

很多任务的痛点不是计算量太大，而是：

- 数据格式碎片化
- 小文件过多
- 频繁跨总线搬运
- 热点状态频繁回写
- 远端依赖调用过多

一个非常重要的工程直觉是：

> 任何不必要的数据复制、跨设备同步和远端访问，都会在规模化时被放大。

所以很多优秀系统设计都会优先考虑：

- 数据是否能预热到更近的层
- 状态是否能留在设备端
- 是否能批量搬运，减少小块传输
- 是否能减少往返次数

### 5.6 RDMA、RoCE 与 TCP 怎么选

对平台工程来说，三者不是“谁先进就用谁”，而是网络目标、预算和运维能力的平衡。

| 方案 | 带宽 / 延迟 | 成本 | 部署复杂度 | 适用场景 |
|------|-------------|------|------------|----------|
| InfiniBand RDMA | 最高 / 最低 | 高 | 中高 | 大规模多机训练、强同步集群 |
| RoCE v2 | 高 / 低 | 中 | 高 | 需要以太网承载 RDMA，但团队能调 PFC / ECN |
| TCP over Ethernet | 中 / 较高 | 低 | 低 | 小规模训练、控制面、对性能不极端敏感的业务 |

快速判断可以这么做：

- **先要极致训练效率**：优先看 InfiniBand RDMA
- **已有强以太网基础设施**：可评估 RoCE，但必须接受调参成本
- **规模不大、以稳为先**：TCP 仍然是最便宜的默认值

### 5.6a 集群网络拓扑决定多机训练上限

到了 32、64、256 卡规模后，真正决定扩展上限的往往不只是单块网卡，而是整张网络怎么组织。

先把单机和跨节点链路关系说清楚：

```text
单机内：
  GPU <-> NVLink / NVSwitch <-> GPU
   |                              |
 PCIe                          PCIe
   |                              |
  NIC                          NIC

跨节点：
  NIC <-> InfiniBand / RoCE fabric <-> NIC
```

GPU 之间的梯度、激活或 KV cache 搬运，单机内优先走 NVLink / NVSwitch；跨节点时要从 GPU 经 PCIe 到 NIC，再进入 InfiniBand 或 RoCE 网络。这里的关键不是“有 RDMA 就够了”，而是 GPU、NIC、交换机和拓扑是否匹配。

在 8 卡节点里，NVSwitch 让 GPU 间通信更接近一张高带宽背板。到了多机训练，NCCL 会把 AllReduce 拆成单机内 reduce、跨节点 exchange、单机内 broadcast 等阶段。跨节点阶段一旦走到慢 rail、跨 pod 或拥塞链路，整轮 AllReduce 都会被最慢的一段拖住。

常见拓扑可以粗略分成三类：

```text
Fat-tree / Clos:
  Leaf -- Spine -- Leaf
   |               |
 Node            Node

Rail-optimized:
  rail-0: node0-GPU0/NIC0 -- ToR-0 -- node1-GPU0/NIC0
  rail-1: node0-GPU1/NIC1 -- ToR-1 -- node1-GPU1/NIC1
  rail-N: ...

Dragonfly / Dragonfly+:
  group A == high-radix global links == group B
     |                                  |
   local fabric                       local fabric
```

Fat-tree / Clos 追求任意节点间尽量接近等价带宽。平台调度更轻松，因为大多数 rank placement 都能获得相近网络路径；代价是 spine、leaf 和布线成本高。

Rail-optimized topology 则更贴近 AI 节点形态：每个 GPU 或一组 GPU 绑定一张 NIC，再把同编号 NIC 接到同一条 rail。它能降低交换机规模和布线复杂度，但要求通信库、rank placement 和并行策略理解 rail。比如 8 卡节点有 8 张 NIC 时，理想情况是 GPU0 的跨节点流量走 NIC0/rail0，GPU1 走 NIC1/rail1；如果 AllReduce ring 把大量流量压到少数 rail，或者 rank 跨 rail 绕行，就会出现网卡没满、step time 却变慢的情况。

Dragonfly / Dragonfly+ 更常见于超大 HPC 或超大 AI 集群，用较少全局链路连接多个 group，降低超大规模网络成本。它不是默认答案，因为调度需要理解 group locality：跨 group 作业过多时，全局链路会变成瓶颈。

| 拓扑 | 典型规模 | 收益 | 代价 | 适用场景 | 失败条件 |
|------|----------|------|------|----------|----------|
| Fat-tree / Clos | 数百到数千卡 | 任意节点间带宽更均衡，AllReduce、参数同步和 checkpoint 流量更容易调度 | 交换机层级、端口和布线成本高，扩容需要整体规划 | 通用大规模训练，多租户训练平台，通信模式经常变化的集群 | oversubscription 过高、spine 层拥塞、ECMP 哈希不均导致部分 rank 变慢 |
| Rail-optimized | 数十到数百卡，或按 pod 扩展到更大 | 成本和布线更可控，GPU-NIC 对应关系清晰，适合 NCCL 拓扑感知优化 | 对 rank placement、NIC 亲和性和 NCCL 配置更敏感，跨 rail 绕行会拖慢同步 | DP + TP 为主、节点形态一致、作业规模相对固定的训练集群 | GPU 到 NIC 亲和性错配、某条 rail 拥塞或故障、AllReduce ring 没有均匀使用多 rail |
| Dragonfly / Dragonfly+ | 数千卡以上 | 用较少全局链路支撑超大规模，成本和跳数更可控 | 调度、故障隔离和拓扑感知更复杂，平台团队需要更强网络运维能力 | HPC / 超大 AI 集群，作业能按 group 做 locality-aware placement | 跨 group 流量比例过高、全局链路热点、调度器不了解 group 边界 |

多 rail 对 AllReduce 的影响尤其明显。AllReduce 不是简单“总网卡带宽相加”，而是取决于通信分片能否均匀铺到多张 NIC、多条 rail 和多层交换机上：

- 如果每个 GPU 有独立 NIC，通信库可以把不同 GPU 的跨节点流量并行送到不同 rail，聚合同步带宽更接近线性增长。
- 如果多个 GPU 共享一张 NIC，或者 GPU 到 NIC 要跨 NUMA / PCIe switch，单机内 NVLink 很快，但跨节点阶段会被 NIC 或 PCIe 根复合体限制。
- 如果 rail 之间没有足够横向带宽，跨 rail rank 放置会让本来应该直达的流量绕行，AllReduce tail latency 会变差。
- 如果 RoCE 网络的 PFC / ECN 没调好，轻微拥塞也可能表现为 NCCL timeout，而不是清晰的网络告警。

平台侧真正关心的是 placement：

- 通信密集的 rank 尽量落在同一节点、同一交换机、同一 rail 或同一 dragonfly group
- 先放满 8 卡节点，再放满 32 卡 pod，最后扩到 256 卡 superpod
- 尽量让同一作业使用同型号 GPU、同速 NIC、同代交换机和同样的链路层配置
- 对 rail-optimized 集群，调度器要知道 GPU/NIC 亲和性，不能只看“还有几张 GPU 空闲”

这也是为什么很多集群会按 8 卡节点 -> 32 卡 pod -> 256 卡 superpod 分层设计。
作业放置不对，即使网卡标称带宽够，扩展效率也会在 [第8章](../part3-training-infra/08-data-parallel.md) 里提前掉下来。

训练里的网络故障也不一定表现为“网挂了”，更常见的是：

- NCCL timeout
- 某几个 rank 长时间等待
- step time 周期性抖动
- 某节点变成 straggler

所以监控不能只看链路 up/down，还要看训练视角下的等待时间。

### 5.6b 并行文件系统：训练热层，不是对象存储替代品

对象存储适合冷数据和长期保留，但训练现场经常需要一个更靠近计算层的“热层”：

- dataloader 的并发随机读取
- 大批 checkpoint 的并发写入
- 多节点共享同一份热点数据

这时常见选择是并行文件系统。

| 系统 | 类型 | 核心优势 | 更适合什么场景 |
|------|------|----------|----------------|
| Lustre | 并行文件系统 | 顺序吞吐高，HPC 生态成熟 | 大规模训练数据读取 |
| GPFS / Spectrum Scale | 并行文件系统 | 企业级管理与一致性较强 | 企业训练集群 |
| WekaFS | 并行文件系统 | 延迟更低，随机 IO 更友好 | 混合训练 / checkpoint 热层 |
| 对象存储 | 对象 | 容量弹性好，跨区域复制方便 | 冷数据、长期归档、模型仓库 |

更实用的做法通常不是二选一，而是分层：

| 层级 | 放什么 | 为什么 |
|------|--------|--------|
| 并行文件系统 / 本地 NVMe | 当前训练集、最近 checkpoint、热点样本 | 吞吐高、恢复快 |
| 对象存储 | 原始数据、历史 checkpoint、模型发布包 | 成本低、容量大、便于归档 |

如果把所有数据都直接从对象存储读，常见问题会是：

- 小文件和随机读取放大延迟
- checkpoint 高并发写入时吞吐不稳
- 训练和恢复都依赖远端网络

所以在平台工程里，对象存储更像冷层，真正贴近训练主路径的往往是并行文件系统或 NVMe 缓存。这一点会直接影响 [第10章](../part3-training-infra/10-memory-checkpointing-and-recovery.md) 的 checkpoint 频率设计。

### 5.7 IO 瓶颈的典型表现

#### 训练场景

- GPU 利用率锯齿化
- dataloader worker 很忙
- step time 波动大
- checkpoint 写入时出现明显抖动

#### 推理场景

- 模型冷启动慢
- 请求延迟受模型加载和缓存未命中影响
- RAG 文档检索后还要远程拉取元数据，造成尾延迟

#### 多机场景

- 扩卡后吞吐提升远不如预期
- 跨节点同步比例升高
- 某一台机器成为“木桶短板”

### 5.8 常见误区

#### 误区一：显存不够就一定是模型太大

不一定。也可能是：

- batch 太大
- 激活保留太多
- KV Cache 回收策略差
- 数据在设备侧重复保留

#### 误区二：IO 问题只是数据读取慢

不对。主机到设备拷贝、checkpoint 回写、远端依赖访问也都属于 IO 链路。

#### 误区三：只要上更快硬件，搬运问题就会消失

不对。如果链路层级和访问模式不合理，再快硬件也会被错误使用方式浪费。

## 本章小结

| 主题 | 关键点 |
|------|--------|
| 内存层级 | 越靠近计算层越快，但容量越稀缺 |
| 互联 | PCIe、NVLink、RDMA 分别负责不同范围的数据搬运 |
| 集群拓扑 | 放置策略和网络分层会决定多机训练的扩展上限 |
| 存储热层 | 并行文件系统 / NVMe 更适合作为训练与 checkpoint 的热层 |
| 性能优化本质 | 很多优化不是减少计算，而是减少搬运或重叠搬运 |
| 瓶颈识别 | 训练抖动、扩卡失效、冷启动慢都可能是 IO / 互联问题 |

2. PCIe、NVLink、RDMA 分别更影响哪些场景？
3. 如果你的集群要从单机 8 卡扩到 4 个节点，你会优先比较哪些互联数字？
4. 什么时候你会接受 TCP，而不是继续为 RoCE / RDMA 增加运维复杂度？
5. 为什么“并行文件系统做热层、对象存储做冷层”通常比只靠对象存储更适合训练集群？
