1. 第一性原理拆解：构建一个 AI 平台

拆 — 不可化简的问题

剥离 Kubernetes、model registry、feature store、gateway、queue、observability 这些名字以后，AI 平台要解决的不可化简问题只有一个：组织里有多种 AI 工作负载、多类用户和有限资源，它们都在持续变化，但业务仍然要求模型从数据到训练、评测、发布、观测、回滚形成可解释、可重复、可治理的交付闭环。所谓平台，不是把工具堆在一起，也不是给每个团队发一个统一入口页，而是把人、代码、数据、模型、资源、请求、风险放进同一套因果链路里，让每一次训练为什么排队、每一个模型为什么能上线、每一次故障为什么能回滚、每一笔 GPU 成本为什么属于某个租户，都有证据可查。

这也是本章和前面章节的关系：前面每章都在解决一个局部瓶颈，例如 GPU 显存、通信拓扑、checkpoint 恢复、推理 batching、租户隔离、可观测性和安全治理；本章要做的是把这些局部机制重新组合成平台级判断。平台工程师面对的不是“该不该用某个组件”，而是“在当前组织规模、模型类型、资源预算和风险边界下，哪些约束必须被产品化，哪些灵活性应该留给用户”。如果这个问题没有先拆清楚，平台很容易变成两种失败形态：要么只是 UI 包装，底层数据版本、模型版本、评测结果和发布记录互相断裂；要么过早大一统，把研究、微调、RAG、在线推理这些差异很大的工作负载强行塞进同一种流程，最后既不敏捷，也不可治理。

推 — 从这个问题如何推导出每个机制

从“有限资源上的可治理交付闭环”出发，平台机制会自然出现。首先，资源是有限的，所以必须有资源池、队列、配额、优先级和抢占规则，否则训练任务、批处理任务和在线服务会彼此挤占，SLA 只能靠人工协调。其次，用户真正想提交的不是 Pod，而是训练、评测、发布、推理服务这类任务，所以平台需要任务级 API，把底层容器、镜像、节点选择、存储挂载、网络策略翻译成可审计的工作流。再次，模型输出能不能被信任，取决于输入证据链是否完整，因此需要数据版本、代码版本、实验追踪、checkpoint、模型 registry 和评测门禁，把“这个模型从哪里来”回答清楚。

继续往后推，模型上线之后风险会从“能不能训练出来”转成“能不能稳定服务业务”。因此平台必须包含推理网关、灰度、回滚、SLO、日志、指标、trace、质量采样和成本归因；没有这些，训练平台再强，也无法解释线上延迟上升、命中率下降或成本突增。再往组织层面推，多团队共享平台必然带来差异：研究团队要灵活，业务团队要稳定，平台团队要可维护，安全团队要审计。于是平台边界不能只靠统一组件，而要靠统一证据、统一控制点和分层抽象：资源层保证可调度，运行层保证可执行，工作流层保证可追踪，运营层保证可治理。

工程边界也由此确定：中型团队的第一版平台不应追求全自动、全场景、全自研，而应先把一条端到端链路打通，例如训练 Job → checkpoint → registry → 评测 → staging → 灰度 → 回滚 → 反馈，再围绕这条链路逐步扩展。平台成熟的标志也不是功能列表更长，而是关键动作可以被解释：谁提交了任务、用了哪份数据、跑在哪个资源池、生成了哪个制品、通过了什么评测、为什么被允许发布、线上出了问题该回滚到哪里、成本属于哪个业务单元。

2. 学习目标

完成本章学习后，你应该能把前 23 章的资源、运行时、训练、数据、推理、可靠性和治理知识重新组合成一个平台方案，而不是只罗列组件。

系统设计能力
围绕业务目标、团队规模、资源约束和风险边界，设计一个可落地的中型 AI 平台蓝图。
平台取舍能力
解释统一性与灵活性、利用率与 SLA、建设速度与长期治理之间的冲突，并给出明确取舍。
  • 把训练、数据、推理、平台、治理串成完整蓝图。
  • 围绕目标业务、团队规模与资源约束做系统设计。
  • 识别平台设计中的关键取舍：统一性 vs 灵活性、利用率 vs SLA、建设速度 vs 长期治理。
  • 形成从需求 → 架构 → 运行规则 → 风险控制的表达能力。
  • 设计一个适合中型团队的 AI 平台最小闭环。
结课视角：真正理解 AI Infra 的标志，不是记住多少组件名，而是能把资源、训练、推理、治理重新组装成一个可解释、可落地、可演进的系统。

3. 先定义平台要解决什么

平台设计最容易犯的错误，是一开始就讨论组件：要不要上 Kubernetes，要不要自建 model registry，要不要接向量数据库，要不要做统一网关。这些问题都重要，但它们是第二层问题。第一层问题应该是平台到底服务谁、哪类工作负载最关键、哪种约束最敏感、当前组织最痛的瓶颈在哪里。

问题为什么先问会影响的设计
平台主要服务训练、推理，还是两者兼有？训练看吞吐、恢复和排队；推理看延迟、SLA 和流量治理。资源池划分、队列规则、服务模板、观测指标。
主要租户是谁？算法团队、业务团队、平台团队和外部客户对灵活性、稳定性、审计的要求不同。身份模型、API 抽象、权限边界、支持流程。
最敏感的是延迟、成本、交付速度还是合规性？不同目标会把同一套技术选型推向不同方向。抢占策略、灰度规则、预算阈值、发布门禁。
现在最痛的是排队、部署、回滚、观测还是账单？第一版平台应该优先闭合真实痛点，不应追求全功能清单。MVP 范围、里程碑、平台产品顺序。
边界提醒：如果这些约束没有先写清楚，平台设计很容易变成名词堆砌，最后每个组件都“有”，但没有一条链路能解释模型如何可靠上线。

4. 中型团队的最小 AI 平台蓝图

你可以把一个中型团队的 AI 平台抽象为一条端到端交付链路。开发者入口不是门户本身，而是任务进入平台的控制面；数据、训练、实验、制品、评测、发布、推理和观测必须在证据链上相互连接。

开发者入口
  -> 数据与特征管理
  -> 训练任务提交
  -> 实验追踪与制品管理
  -> 评测与发布门禁
  -> 在线推理网关
  -> 可观测性 / 审计 / 成本面板

背后的基础设施包括 GPU / CPU / 存储 / 网络资源池、容器与运行时、队列配额优先级与抢占规则、对象存储与模型仓库、索引存储、推理引擎与服务路由，以及监控、日志、trace、质量评测与审计系统。关键在于：这些不是平铺组件，而是一条端到端交付链路。

  D --> E[模型 registry]
  E --> F[评测与发布门禁]
  F --> G[staging 与灰度]

最小平台判断：第一版不需要覆盖所有模型形态，但必须至少让一条高价值链路从训练到上线可追踪、可恢复、可回滚、可审计。

5. 平台 API 设计原则

平台 API 值得单独讲，因为很多平台一开始把底层资源对象直接暴露给用户，结果用户学会的是“怎么申请 GPU Pod”，而不是“怎么提交训练、评测、发布任务”。健康的平台 API 应屏蔽节点选择、调度插件、Pod 模板这些底层细节，同时保留可审计、可回滚、可配额的控制点。

更好的 API 入口不够好的 API 入口背后的平台原则
提交训练任务直接申请一组裸 Pod用户面向任务，平台面向资源翻译。
创建评测运行让用户自己拼 Job、PVC、环境变量把标准工作流做成产品接口。
发布模型版本让用户手工改 Deployment 和路由隐藏调度细节，保留治理钩子。
API 层级用户看到的对象平台内部翻译必须留下的证据
训练TrainJob、数据版本、镜像版本、资源档位队列、GPU 节点、Pod、存储挂载、分布式启动提交人、租户、代码版本、数据版本、资源用量、checkpoint。
评测EvaluationRun、baseline、评测集、门禁策略批处理 Job、指标采集、报告生成、审批钩子模型版本、评测集版本、指标、阈值、审批结果。
发布ModelRelease、目标环境、灰度比例路由、Deployment、网关、流量分配、回滚点发布人、准入结果、灰度记录、线上指标、回滚记录。
控制面原则：平台 API 不是把 Kubernetes 换个名字暴露出去，而是把组织认可的训练、评测、发布和推理规则固化成可执行边界。

7. 设计顺序与最小闭环

一个实用设计顺序是：先明确业务目标，再画核心链路，随后找最稀缺资源，定义任务调度规则，最后把发布、回滚、观测和账单接上。这个顺序背后的原则是先保证平台能形成闭环，再追求高级自动化。

  1. 业务目标：要支持哪些模型和工作流。
  2. 核心链路：数据怎么流，请求怎么流。
  3. 最稀缺资源：GPU、网络、存储、工程人力哪个最紧张。
  4. 任务调度规则：谁优先，谁保底，谁可抢占。
  5. 发布与回滚：模型如何上、如何下、如何止损。
  6. 观测与账单：谁看得到，谁解释得清。
sequenceDiagram
  participant U as 用户
  participant P as 平台控制面
  participant Q as 队列与资源池
  participant T as 训练任务
  participant R as Registry
  participant E as 评测门禁
  participant G as 推理网关
  participant O as 观测与成本
  U->>P: 提交 TrainJob 和数据版本
  P->>Q: 资源准入与排队
  Q->>T: 分配 GPU 并启动任务
  T->>R: 写入 checkpoint 与模型版本
  R->>E: 触发评测运行
  E->>P: 返回门禁结果
  P->>G: staging / 灰度发布
  G->>O: 上报延迟 质量 token 成本
  O->>P: 放量 回滚 或反馈再训练
闭环步骤平台必须保证失败信号
用户提交训练 Job身份、租户、资源申请、数据版本明确。任务能跑，但没人知道谁提交、用了哪份数据。
训练运行与 checkpoint日志、指标、失败恢复、制品写入统一系统。任务失败后只能人工翻机器和临时目录。
模型进入 registry权重、tokenizer、配置、代码、数据和评测元数据绑定。只有一个文件名，无法解释模型来源。
评测与发布门禁与 baseline 对比，记录质量、延迟、安全和成本结果。上线靠口头确认或临时 notebook 截图。
灰度、观测、回滚流量可控，指标可见，回滚点明确。线上异常后不知道该降级、回滚还是扩容。
MVP 边界：最小闭环不等于简陋脚本。它可以功能少，但关键证据不能断：数据、代码、模型、评测、发布、线上指标和成本要能串起来。

8. 平台设计中的关键取舍

平台设计不是把所有“最佳实践”同时打开。每个组织都要面对统一性、灵活性、利用率、SLA、建设速度和长期治理之间的冲突。成熟的平台设计会把这些冲突显式化，而不是隐藏在默认参数里。

取舍偏向左侧的收益偏向右侧的收益中型团队建议
统一性 vs 灵活性统一镜像、Job 模板和 registry 提升治理。研究和业务团队能快速试新模型、新依赖、新链路。统一关键边界：身份、数据版本、模型 registry、评测门禁、发布记录；保留实现细节弹性。
利用率 vs SLAGPU 压得更满，单位成本更低。在线服务有余量，训练排队更可预测。按工作负载分层经营：在线保底，训练可抢占，批处理填谷。
建设速度 vs 长期复杂度快速解决当前痛点。减少后期迁移、权限混乱和证据断链。围绕最痛问题建设最小闭环，避免全场景大一统，也避免完全无规范。
严重风险：如果平台把所有 GPU 都压满当作唯一目标，在线推理的 p99、突发容量和故障恢复会被牺牲；如果完全不管利用率，平台成本会很快失控。

9. 平台能力分层

你可以把平台能力分成四层：资源层、运行层、工作流层、运营层。这个分层的好处是，需求进入平台时可以先判断它到底是在补资源问题、运行问题、工作流问题，还是运营治理问题。

层级核心能力典型问题平台产物
第 0 层：资源层GPU / CPU / 存储 / 网络，节点池，拓扑，镜像基线。资源是否足够，拓扑是否适合训练，存储是否拖慢吞吐。资源池、节点标签、容量规划、基础镜像。
第 1 层：运行层容器运行时，训练任务抽象，推理服务模板，队列与配额。任务如何启动、排队、隔离、重试和抢占。TrainJob、InferenceService、队列策略、配额规则。
第 2 层：工作流层数据版本、实验追踪、模型 registry、评测门禁、发布与回滚。模型从哪里来，是否值得上线，出了问题回到哪里。数据集版本、模型版本、评测报告、Release 记录。
第 3 层：运营层可观测性、审计、成本归因、SLA / SLO、incident response。平台是否能解释质量、延迟、故障、安全和成本。SLO 面板、审计日志、账单面板、事故复盘。

排查提示：一个“训练慢”的需求可能落在资源层，也可能落在运行层或工作流层；不要在没定位层级前直接换调度器或重写平台。

10. 平台最容易失败的地方

平台失败通常不是因为缺少某个热门组件，而是因为端到端证据链、发布运营能力或业务差异被忽视。

只做 UI，不做底层证据链
界面很漂亮，但模型版本、数据版本、评测结果、回滚路径都不连通。这种平台很快会沦为另一个入口页。
只重训练，不重发布和观测
训练能力很强，但上线和运营能力弱。模型很多，真正稳定跑在线上的很少，每次发布都像人工冒险。
只追求统一，不尊重业务差异
推荐、RAG、分类、生成服务对延迟、批处理、缓存、隔离的要求差异很大。平台应统一边界和治理规则，而不是强迫所有工作负载使用同一套最优解。
失败形态早期信号修正方向
UI 包装型平台页面能提交任务，但数据、模型、评测、发布记录互不关联。先补证据链和 registry 元数据，而不是继续扩页面。
训练孤岛型平台训练任务很多，线上发布仍靠手工脚本和临时审批。把评测门禁、staging、灰度、回滚接入训练产物。
一刀切型平台研究团队绕过平台，业务团队抱怨流程太重。统一身份、制品、评测、审计，放开模型实现和局部流程差异。
平台产品判断：用户绕过平台不一定是用户不规范，也可能说明平台抽象没有覆盖真实任务，或者把底层复杂度转嫁给了用户。

11. 演进路线图与多集群

一条务实路线通常分成四个阶段：规范化、闭环化、平台化、高阶化。核心不是越快越好，而是每一阶段都能解决真实问题，并为下一阶段留下可演进的接口和证据。

阶段重点建设完成标志
阶段一：规范化统一训练 Job 入口、统一镜像基线、统一模型与数据命名。任务和制品不再靠个人约定命名，能基本追踪来源。
阶段二：闭环化实验追踪、registry、发布门禁、监控与回滚。一个模型能从训练到灰度再到回滚形成完整记录。
阶段三：平台化队列、配额、租户隔离、服务模板、成本归因、incident 流程。多团队共享资源时，平台能解释优先级、成本和故障边界。
阶段四：高阶化多地域、RAG / 向量基础设施、智能调度、自动容量与质量优化。平台能跨集群经营容量，并围绕质量、成本和 SLA 自动优化。

当平台规模继续扩大，单集群设计会逐步碰到边界：不同区域的时延、数据主权、容量池差异和故障域都会开始主导架构。

挑战为什么会出现平台侧常见处理
统一调度视图资源分散在多个集群，单集群队列不再够用。做上层全局控制面，底层按集群执行。
数据就近与合规数据、模型和索引跨区复制成本高，还可能受合规约束。按区域放置数据和模型副本，尽量本地训练 / 本地服务。
Checkpoint / 制品跨区同步大模型 checkpoint 太大，跨区同步慢且贵。区分热恢复副本与冷备副本，减少全量同步频率。

  C --> B[区域 B 集群]
  C --> D[区域 C 集群]

多集群原则：这类平台通常不追求“所有集群像一个集群一样透明”，而是追求统一入口、局部自治、跨区故障可解释。

12. 结课后的两种能力

学完本教程后，你应该形成两种核心能力：诊断能力和架构能力。诊断能力让你看到训练或推理问题时，能判断是算力问题、存储问题、网络问题还是调度问题，是资源不足、资源浪费还是规则设计出了问题。架构能力让你面对一个 AI 业务需求时，能从资源、链路、平台、治理、风险这些维度组织方案，而不是只会堆组件名。

诊断能力
把表面症状映射到资源、运行、工作流和运营层级，快速判断下一步应该查 GPU、数据、通信、调度、推理网关、评测还是治理证据。
架构能力
把业务目标翻译成平台边界，明确资源经营方式、任务抽象、发布门禁、观测指标、成本归因和安全审计。
看到的问题诊断视角架构视角
GPU 利用率低数据加载、CPU 预处理、通信等待、batch 策略、队列规则。是否需要分层资源池、数据缓存、训练模板和容量面板。
线上 p99 抖动KV Cache、batching、下游检索、节点抢占、网关限流。是否需要在线保底资源、灰度策略、SLO 和降级规则。
模型质量回退数据版本、Prompt、检索索引、模型版本、评测集覆盖。是否需要评测门禁、registry 元数据和线上质量采样。
账单不可解释租户标签、token 统计、GPU 小时、对象存储、向量库成本。是否需要配额、成本归因、预算告警和资源回收。

13. 本章小结与练习题

构建 AI 平台的核心不是组件清单，而是让组织在有限资源、多租户、多工作负载和持续变化的模型链路中，仍然能解释每一次训练、发布、故障、回滚和成本。

维度关键问题
目标平台到底服务谁、解决什么痛点。
资源稀缺资源是什么，如何组织。
工作流从数据到训练到发布到推理是否闭环。
治理是否可观测、可回滚、可审计、可归因。
演进是不是围绕真实瓶颈逐步建设。

练习题

  1. 为一个 3 个团队共享 GPU 的平台画出高层架构图。
  2. 如果你的业务以在线推理为主，平台设计的优先级应如何调整？
  3. 试用本教程的框架分析一个你熟悉的 AI 系统。
  4. 请为一个中型团队写出 AI 平台的三阶段建设路线图。
练习要求：不要只画组件框图。每个方案都要说明任务如何提交、资源如何准入、模型如何评测、发布如何回滚、成本如何归因。
