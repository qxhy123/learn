1. 第一性原理拆解：特征、向量与缓存

拆 — 不可化简的问题

剥离 Feature Store、Embedding、Vector DB、RAG、Cache 这些工具名以后，本章真正面对的是一个不可化简的问题：AI 应用不能只依赖模型权重本身，它还必须在请求发生时拿到正确、及时、可授权、可复现的外部状态。这个状态可能是用户最近 5 分钟行为统计，可能是一段企业文档被 embedding 后的向量，可能是某个 query 的检索结果，也可能是 LLM 已经算过的公共 prompt 前缀。只要这些状态与模型一起决定输出，平台就不能把它们当作旁路优化；它们就是线上推理路径的一部分。

这个问题难在四个约束同时成立。第一，外部状态比模型权重变化更快：文档会更新，权限会变化，商品会下架，用户行为每秒都在写入。第二，模型只能消费有限上下文和有限延迟预算：RAG 不能把整座知识库塞进 prompt，推荐系统也不能对全量候选做精排。第三，相似性搜索不是数据库等值查询：embedding 空间、chunk 规则、ANN 索引和 reranker 共同定义了查到什么，其中任一版本变化都会改变结果。第四，缓存会把历史结果带到未来：它能降低延迟，也能把已经删除、已经越权、已经过期的数据继续送进模型。

因此，本章不是在罗列几类存储组件，而是在回答一个平台工程问题：当模型输出依赖外部状态时，怎样设计一条从数据产生、特征计算、向量化、索引构建、检索、重排、上下文组装到缓存失效的闭环，使得性能提升不会破坏一致性，召回优化不会破坏权限边界，增量更新不会制造不可解释的混合版本。这个问题比“选哪个向量库”更底层，因为向量库只是其中一个执行组件；真正需要被治理的是外部状态的生命周期。

推 — 从这个问题如何推导出每个机制

从“模型需要外部状态”出发，第一步会推导出特征。特征是把业务世界压缩成模型可用字段的过程：用户画像、实时计数、商品属性、会话上下文都属于这一类。它带来的第一个机制是 point-in-time correctness：训练样本只能看到样本时间点之前存在的特征，线上服务也必须明确 freshness SLA，否则训练和线上看到的世界不是同一个世界。只要这个契约不成立，模型质量分析就会变成猜测，因为你无法判断问题来自模型、数据、时间窗口还是服务实现。

当外部状态是非结构化文本、图片、音频或长文档时，结构化字段不够用，于是需要 embedding。embedding 把对象映射到向量空间，但这个空间由模型版本、tokenizer、预处理和归一化共同定义；模型一换，向量含义就变了。由此自然推出向量索引：如果每次 query 都全量比较千万或十亿级向量，延迟和成本都不可接受，所以需要 ANN 用少量召回损失换取可用的 P95/P99 延迟。HNSW、IVF、PQ 的差别，本质是在内存、构建时间、召回率、更新成本之间移动。

非结构化文档通常又太长，不能直接整篇 embedding 或整篇塞进 LLM。于是推导出 chunking：固定长度切分让索引规模可预测，段落和句子切分保留文档结构，语义切分追求更自然的边界。chunk policy 一旦变化，索引行数、召回粒度、rerank 候选和缓存 key 都会变化，所以它必须成为版本化配置，而不是 ingestion 脚本里的隐式常量。

状态会变化，因此还必须推导出增量更新与全量重建的边界。文档少量新增、元数据变化、热数据修补通常可以增量；embedding 模型、chunk 规则、距离度量、清洗规则变化时，向量空间或文档边界已经改变，继续增量修补会得到一个不可解释的混合索引。平台需要双索引灰度、golden queries 回归和可回滚切换，而不是直接覆盖生产索引。

最后，延迟和成本压力会推导出缓存。缓存可以存在于在线特征、embedding、检索结果、文档元数据、prefix cache 和单请求 KV Cache 多个层次。它们共同的工程问题是 cache key 必须覆盖版本、权限和上下文。尤其是 RAG 与企业知识库中，缓存命中不能绕过 ACL；prefix cache 如果包含检索结果、用户画像或 policy 条件，就不再是纯静态前缀，必须把租户、用户授权、工具定义、tokenizer 版本和索引版本纳入 key。否则缓存越有效，泄露和过期的风险越大。

3. 为什么这一层越来越重要

很多现代 AI 系统并不是一个模型吃原始输入直接输出结果。检索、推荐、RAG 和在线特征场景进入生产以后，平台管理的就不再只是模型权重，而是一整套特征、embedding、索引、缓存的状态系统。

  • 在线特征：把实时行为、业务上下文和用户画像提供给模型。
  • embedding 向量：把文本、图片、文档等对象放进可比较的向量空间。
  • 向量检索：在大规模候选中用近邻搜索找到可能相关的对象。
  • reranker 特征：用更贵但更精细的模型压缩候选集。
  • 多层缓存：降低重复计算、检索、预填充和元数据读取成本。
embedding 来自模型，索引依赖 embedding，缓存又依赖索引和访问模式。任何一层版本漂移，都会改变模型最终看到的上下文。

4. 特征、embedding、向量索引分别是什么

特征

特征通常是结构化或半结构化输入，可能来自用户画像、商品属性、实时行为统计和业务上下文。特征平台的核心不是“把字段读出来”，而是保证同一份定义在训练、回放、在线服务中具有一致语义。

Embedding

Embedding 是把文本、图片、文档等映射到向量空间后的表示。它通常由某个特定模型版本生成，并受到 tokenizer、预处理、归一化、截断策略和语言分布影响。

向量索引

向量索引是为了高效近邻检索而组织的结构，可能包含向量本身、文档 ID、元数据过滤条件、分区与分片信息。它不只是文件，而是线上服务状态。

5. 一致性与版本管理

现实中常见的错误不是系统挂了，而是不一致：训练使用的是一套特征定义，线上使用的是另一套；embedding 模型更新了，但索引没重建；文档已经删除，但向量索引还保留旧记录；cache 命中了旧数据，导致线上结果滞后。这种问题麻烦在服务表面正常，指标不一定立刻异常，但模型质量会逐步漂移。

定位原则：如果 RAG 结果变差，先确认模型版本、embedding 版本、chunk policy、索引版本、metadata filter 和缓存 key，而不是直接调 prompt。

一个向量索引至少应该绑定 embedding 模型版本、文档或数据版本、chunk 规则版本、构建时间和构建任务 ID。

vector_index:
  name: docs-prod
  embedding_model: text-embed-v4
  source_dataset: kb-2026-04-10
  chunk_policy: title-paragraph-v2
  distance_metric: cosine
  build_job: reindex-20260410-003

6. 向量数据库怎么选

向量数据库的核心差异不在能不能存 embedding，而在索引类型、过滤能力、部署模式、更新方式和可运营规模。选型时要同时看数据规模、查询 QPS、更新频率、metadata filter、P95/P99 延迟目标和团队运维能力。

7. ANN 搜索与距离度量

精确搜索最直接，但向量规模一旦达到千万级，平台通常就会转向 ANN（Approximate Nearest Neighbor）索引，用可控召回损失换更低延迟和更低成本。

方法核心思路优势代价适用判断

HNSW图索引近邻跳转延迟低、召回高内存占用较大，构建和更新成本较高百万到亿级、交互式 RAG、内存预算充足

PQ压缩向量后近似比较显著节省内存精度损失更明显，调试复杂十亿级或内存受限场景，通常与 IVF 组合

8. 缓存在这里到底缓存什么

缓存不只是普通意义上的把结果存一下。在 AI 系统里，缓存可能覆盖在线特征、embedding 结果、检索结果、文档元数据、prefix cache 和 KV Cache。收益通常是更低延迟、更少重复计算、更低下游压力；代价通常是新鲜度下降、版本一致性变难、权限边界更复杂。

Embedding cache输入到向量的编码结果输入内容、模型版本、tokenizer、预处理版本减少重复 embedding 计算模型升级后旧向量误用
Retrieval cachequery 对应召回结果query、过滤条件、权限上下文、索引版本降低向量库和 rerank 压力文档删除或 ACL 变化后仍返回旧结果
Prefix cache公共前缀激活 / KV 状态system prompt、模板、工具定义、租户、tokenizer减少 prefill 计算不同租户或不同工具上下文混用

安全边界：缓存命中不能绕过权限检查。只要缓存结果包含文档、特征、用户态或 policy 条件，权限上下文就必须进入 key 或进入命中后的强校验。

9. Chunking 策略会改变检索质量

在 RAG 场景里，切分规则会直接影响索引规模、召回粒度和后续生成质量。chunk 大小不是越小越好：chunk 太小，召回更细但上下文不完整，索引行数和 rerank 成本上升；chunk 太大，单条召回包含更多噪声，LLM 上下文预算被浪费。

策略优势风险适用场景失败信号
固定长度切分实现简单，吞吐稳定，索引规模可预测可能截断语义边界早期原型、结构松散文档命中文本经常缺前后文，答案引用半句话
段落 / 句子级切分更贴近原始结构，可保留标题和层级长度差异大，短段落噪声多文档排版规整的知识库长段落召回后超上下文，短段落缺实体解释
语义级切分检索相关性通常更好，边界更自然构建成本更高，规则更复杂高质量 RAG、问答系统切分模型不稳定导致重建频繁、线上结果漂移

工程上常见做法是先用 300-800 token 的 chunk 建基线，再根据问答日志调节；相邻 chunk 可以保留 10%-20% overlap，用来减少边界信息丢失，但 overlap 会线性增加索引规模和重复召回。

chunk_policy:
  id: title-paragraph-v2
  max_tokens: 600
  overlap_tokens: 90
  split_order: [heading, paragraph, sentence]
  keep_metadata: [doc_id, title, section, acl, updated_at]
版本判断：chunk policy 应视为索引版本的一部分。它一变，召回结果、rerank 候选、上下文质量和缓存命中模式都会跟着变。
评估单位：不要只看平均 chunk 长度，还要看每篇文档 chunk 数量、索引膨胀倍数、重复召回率、答案引用完整率和上下文 token 利用率。

10. 增量更新 vs 全量重建

索引更新不是永远都能做增量。一个可操作的判断是：当向量含义变了，就不要试图只修局部。文档少量新增、删除或元数据更新通常可以增量；embedding 模型、chunk 规则、索引算法、距离度量、清洗规则变化时，应该全量重建。

场景更适合的策略原因注意事项
文档少量新增或删除增量更新写入成本低，业务中断小删除要同步清理向量、元数据和检索缓存
元数据更新通常增量不改变向量语义，只改变过滤或展示字段ACL、租户、可见性字段必须立即生效
embedding 模型变更全量重建向量空间整体变化，旧索引不可比需要双索引灰度和召回质量对比
chunk 规则变更全量重建文档边界变化会影响全部召回旧 chunk 的缓存结果不能继续复用
大规模脏数据修复视比例决定，通常倾向全量增量修补容易留下历史碎片修复比例高于阈值时直接重建更可控
索引算法或距离度量变更全量重建索引结构和排序含义变化先用离线 golden queries 做回归
flowchart LR
  D[源数据变更] --> T{变化类型}
  T -- 新增/删除少量文档 --> I[增量写入或 tombstone]
  T -- 元数据/ACL 更新 --> M[同步更新 filter 字段并失效缓存]
  T -- embedding 模型变化 --> R[全量重建新索引]
  T -- chunk/清洗/距离度量变化 --> R
  R --> B[后台构建 blue/green 索引]
  B --> Q[golden queries 回归]
  Q --> S{召回 延迟 ACL 是否达标}
  S -- 是 --> C[按租户或流量切换]
  S -- 否 --> F[保留旧索引并修正构建参数]
  I --> V[记录索引版本和变更任务]
  M --> V
  C --> V
生产做法：新索引在后台构建，完成后用固定查询集比较召回率、延迟、权限过滤和答案质量，再按租户或流量比例切换。切换后保留旧索引一段时间，便于回滚和解释线上质量波动。
更新优先级：不要把 ACL 更新排在普通文档更新后面；权限字段变化应按安全事件处理，缓存失效优先级高于召回质量优化。

11. 混合搜索与 RAG 工程决策路径

很多生产系统不会只做纯向量搜索，而是把关键词检索和向量检索并联，再做 rerank。关键词检索补精确命中，向量检索补语义召回，RRF 适合把两路排序先做稳健合并，cross-encoder reranker 再负责最后的排序收敛。

query
  -> BM25 / keyword retrieval
  -> vector retrieval
  -> RRF / merge
  -> cross-encoder rerank
  -> top-k context
层次目标常见输入规模不应该承担的职责
粗召回快速找到可能相关的候选top 50-1000不负责最终事实判断和复杂权限补救
合并 / 去重融合 BM25、向量、业务规则top 50-300不把明显无权或过期内容带到后面
rerank用更贵模型做精排top 20-100不负责扩大召回范围
上下文组装控制 token、引用和顺序top 3-20不修改文档含义或隐藏来源
flowchart TD
  A[文档进入] --> B[清洗 / 解析]
  B --> C[chunk]
  C --> D[embedding]
  D --> E[索引写入]
  E --> F[缓存失效]
  G[查询进入] --> H[改写 / 归一化]
  H --> I[权限和过滤条件]
  I --> J[BM25 召回]
  I --> K[向量召回]
  J --> L[RRF / merge / 去重]
  K --> L
  L --> M[rerank]
  M --> N[上下文组装]
  N --> O[生成]
  P[golden queries] --> Q[召回评估]
  Q --> R[rerank 评估]
  R --> S[答案评估]
  S --> T[索引或策略灰度]
决策点推荐做法失败条件
embedding 模型版本固定模型、tokenizer、预处理版本，并写入索引元数据模型升级后旧向量和新向量混查，排序含义失真
冷热数据热数据放高性能索引和短 TTL 缓存，冷数据可用低成本索引或归档重建所有数据同等服务导致成本过高，或冷数据召回延迟不可控
检索缓存cache key 包含 query、过滤条件、权限上下文、索引版本文档删除、ACL 变化后仍命中过期结果
召回 topK先保证召回覆盖，再交给 rerank 压缩topK 太小导致 reranker 没有正确答案可排
Prefix cache只缓存严格相同的静态前缀或完整授权上下文不同租户、不同 ACL、不同检索结果共享同一前缀
边界提醒：如果 reranker 经常把低相关内容排到前面，问题未必在 reranker；也可能是 chunk 太大、候选集太小、metadata filter 过严，或 embedding 模型与查询语言不匹配。

12. 权限、Prefix Cache 与 KV Cache

在 RAG、检索、企业知识问答场景里，一个常见风险是：用户无权访问某文档，但缓存或索引没有正确执行权限过滤，最终回答引用了本不该暴露的信息。这说明向量与缓存系统不是单纯性能组件，还承担了安全边界。

对象缓存的是什么更常见于哪一层典型命中条件主要风险
Embedding cache文本 / 图片到向量的编码结果检索与特征层输入内容、模型版本、预处理版本相同模型升级后旧向量误用
Retrieval cachequery 对应的召回结果检索编排层query、过滤条件、权限上下文相同文档变更后结果过期
Prefix cache已算过的公共前缀激活 / KV 状态LLM serving 入口附近system prompt、模板、工具定义、tokenizer 结果一致错把不同租户或不同工具上下文命成同一份前缀
KV Cache单请求 decode 过程中的历史 key/valueLLM decode 运行时同一个活跃请求持续生成显存占用、碎片和回收复杂

平台上最容易混淆的是后两者：prefix cache 更像跨请求复用公共前缀，KV Cache 更像单请求内复用历史状态。前者关注命中键设计，后者关注显存生命周期管理，后续会在 第 15 章 继续展开。

收益口径：Prefix Caching 的收益要用 prefill token 占比衡量，而不是只看请求数命中率。公共前缀越长、越稳定、越能被路由到同一缓存域，收益越明显。
禁止共享的情况：如果前缀里已经包含检索结果、用户画像或会话态、policy / safety 条件、同租户内不同用户的授权差异，这些维度必须进入 cache key；做不到时应只缓存严格静态的公共前缀。

13. 在线特征为什么容易出现 point-in-time 错误

在线特征最危险的问题，往往不是缺数据，而是拿到了不该在那个时刻看到的数据。对平台来说，point-in-time correctness 不是研究细节，而是特征服务的契约。如果契约不成立，后面的向量索引、缓存命中和线上质量分析都会失真。

场景错误表现常见补救
训练样本回放训练时读到了样本时间之后才产生的统计特征以样本事件时间做特征快照
实时聚合延迟线上特征比训练定义晚到几分钟甚至几小时明确 freshness SLA，并允许降级到较旧窗口
回填修数离线修正后没同步线上 cache / feature store回填完成后触发 cache 失效与索引重建
多模态预处理升级图片裁剪、OCR 或 tokenizer 变化，但 key 没变把预处理版本写进特征和缓存 key
sequenceDiagram
  participant E as 事件流
  participant F as Feature Store
  participant T as 训练样本回放
  participant O as 在线服务
  E->>F: 写入用户行为 t0
  T->>F: 以样本事件时间读取 <= t0 的特征
  O->>F: 以当前请求读取满足 freshness SLA 的特征
  F-->>T: point-in-time snapshot
  F-->>O: online feature value
  Note over F,O: 回填或预处理升级必须触发缓存失效
契约写法：每个在线特征都应声明事件时间、窗口、允许延迟、缺失降级策略、回填触发器和 cache key 版本。

14. 工程建议、工具与小结

工程建议

  • 特征定义必须版本化。
  • embedding 模型变化要和索引构建一起治理。
  • 缓存命中不能绕过权限检查。
  • 在线与训练的特征含义要保持一致。
  • 向量索引要像模型包一样具备元数据和生命周期状态。
  • 向量库选型要同时看规模、QPS、更新频率、过滤条件、延迟目标和运维能力。
  • RAG 的 chunk、embedding、索引、缓存和 rerank 必须共享版本边界。
  • prefix cache 的 key 至少要覆盖模板、租户、工具定义和 tokenizer 版本；若前缀含检索结果、用户态或 policy 条件，这些授权相关维度也必须进入 key。
  • 共享前缀场景里，路由层应尽量把相同前缀请求送到同一实例，否则 prefix cache 的理论收益很难兑现。
  • 在线特征要明确 freshness SLA 与 point-in-time 契约。
