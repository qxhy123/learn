1. 第一性原理拆解：Tokenization 与 Dataset 格式

拆 — 不可化简的问题

把所有工具名和格式名拿掉。训练一个语言模型，本质上是在做什么？给定一段文本 "the cat sat"，模型的每个训练步接收的是一串整数，比如 [1169, 3797, 6435]，然后预测序列的下一个整数，通过与标签的差距计算梯度。不是字符，不是字节，是词表索引。这就是不可化简的第一个约束：模型只消费离散整数序列，文本是连续字符，中间必须有映射层。这个映射层叫 tokenizer。

tokenizer 看起来是一个简单的查表工具。但当训练语料从 1GB 膨胀到 1TB 再到 100TB 时，这个"查表"就变成了工程问题：谁来做、什么时候做、做完的结果存在哪里、怎么让 N 个训练节点的 M 个 DataLoader worker 稳定、无重复、可恢复地读取这些整数？

第二个不可化简的约束：GPU 需要固定形状的 batch，但文本长度天然参差不齐。一句话 20 个 token，一篇论文摘要 512 个 token，一篇长文 8192 个 token。如果用 padding 对齐到最大长度，短文本大量浪费算力。如果限制最大长度，长文本只能截断，信息丢失。工程解决方案是 sequence packing：把多条文档的 token 流拼接填满一个固定长度的序列，用 attention mask 或 document boundaries 区分边界。这本来是个聪明的方案，但它引入了第三个约束：packing 改变了每条文档参与梯度的方式，影响 loss 的数值语义。

第三个约束：存储格式决定读取效率。1TB 文本经过 tokenizer 处理后变成约 2800 亿整数（1TB / 3.5B/token，int32 存储约 1.1TB 原始，压缩后约 400-560GB）。这些整数怎么存？存成 JSON 文件一行一个样本？存成 Parquet？存成二进制流？格式选择直接决定：随机访问 vs 顺序读取的成本、分布式训练的 shard 分配方式、能否流式训练、磁盘占用与读取带宽的比值、训练中途 crash 重启后能否从断点续训。

四个约束叠加：tokenizer 映射层 × 序列形状约束 × packing 语义问题 × 存储格式效率——任何一个处理不当，都会导致训练效率损失、loss 数值不准或者训练不可恢复。这才是本章要解决的不可化简问题。

推 — 从这个问题如何推导出每个机制

从"文本到整数的映射"推出 tokenizer 算法的必然选择。最朴素的映射是字符级：每个字符一个 ID。词表小但序列太长，注意力复杂度 O(n²)。另一个极端是词语级：词表可能几百万甚至更多，泛化差，OOV 问题严重。折中就是子词（subword）：词表可控（32K 到 256K），序列长度居中，对 OOV 和多语言都有更好的覆盖。BPE 从字节出发，把高频相邻单元合并，迭代直到词表达到目标大小。这个算法是统计驱动的，因此 tokenizer 需要在训练语料上先"训练"出 merge rules，再用这些 rules 对新文本编码。

从"tokenizer 需要在大语料上训练"推出 SentencePiece 和 Tiktoken。BPE 的原始实现是 Python，在 TB 级语料上速度太慢。SentencePiece 把 BPE/Unigram 的训练和推理都做成 C++ 库，速度提升数十倍，支持多语言字节级处理。Tiktoken 用 Rust 实现编码推理路径，在单线程编码吞吐上通常是纯 Python 实现的 5-10 倍。HuggingFace Tokenizers 库把训练和推理都用 Rust 实现，支持并行批量编码。

从"GPU 需要固定 batch shape"推出 sequence packing：把文档 token 首尾相接，打包进固定长度窗口（如 2048 或 4096 tokens），GPU 每个 step 消费相同形状的 batch，无 padding 浪费。问题随之而来：两个不同文档的 token 被放进同一个窗口，默认 causal attention 会跨文档——这叫跨文档 attention 污染。解决方案是 document boundary mask，或者 Flash Attention 的 cu_seqlens 参数。

从"packing 改变 loss 语义"推出 token-level vs sample-level 损失的区分。不 packing 时，一条文档算一个 loss 贡献，长短文档权重相同（sample-level）。Packing 时，loss 是在整个 packed sequence 上按 token 平均，长文档自然获得更多 token，权重更大（token-level）。两者在数学上不等价，必须明确选择并保持一致。

从"TB 级整数序列如何存储"推出格式选择：JSONL 调试方便但效率差；Parquet 列式压缩好支持查询；MosaicML Streaming .mds 专为分布式 LLM 训练设计，支持随机访问、断点续训、multi-rank 分配；WebDataset .tar 适合流式读取多模态数据；litdata .bin 类似 .mds 设计。

从"多节点训练"推出 sharding 策略：切成多个 shard，每个 DataLoader rank 读取不同 shard，互不重叠。Shard 大小 64MB-1GB 是合理区间。训练中断后重启需要 deterministic shuffle（同 seed 同 rank 产生同序列），以及 step 级别的 checkpoint 记录已消费样本位置。

2. BPE、SentencePiece、Tiktoken：算法与实现对比

2.1 BPE：从字节出发的统计合并

BPE（Byte-Pair Encoding）由 Sennrich et al. 2016 引入 NLP 领域，核心思想：从字节级词表（256 个初始符号）出发，反复统计训练语料中相邻 token pair 的频率，将最高频 pair 合并为一个新 token，迭代直到词表达到目标大小（如 50,257）。BPE 产生一组有序的 merge rules，编码时按顺序应用这些 rules。GPT-2、GPT-4 使用 byte-level BPE：先把文本转为 UTF-8 字节，再做 BPE，天然支持任意 Unicode 字符，无 OOV。

2.2 SentencePiece：语言无关的 C++ 实现

SentencePiece（Google, 2018）的关键贡献：不依赖预分词（直接从原始文本含空格做 BPE 或 Unigram LM），全 C++ 实现比 Python BPE 快约 20x，把空格作为特殊符号 ▁ 纳入词表使编码与分词边界无关，支持 Unigram LM 概率模型。LLaMA、Gemma、Mistral 均使用 SentencePiece。

spm_train \
  --input=corpus.txt \
  --model_prefix=tokenizer \
  --vocab_size=32000 \
  --character_coverage=0.9995 \
  --model_type=bpe \
  --num_threads=32

2.3 Tiktoken：Rust 驱动的编码推理

Tiktoken（OpenAI）不做 tokenizer 训练，只做推理（编码）。Rust 实现核心编码逻辑，Python binding 调用；使用预计算的 BPE merge table 高效编码；批量编码时利用 Rust 的并行安全性，多线程加速。在单线程 ASCII 文本编码上，比 HuggingFace tokenizers 的 Python 路径快约 3-5x。

3. Tokenizer 训练：词表大小、特殊 Token 与兼容性

3.1 词表大小的工程考量

词表大小（vocab size）是 tokenizer 最核心的超参，影响面宽：词表越大，同样文本用更少 token 表示（序列更短，注意力计算更省），Embedding 矩阵更大（显存开销），多语言效率更高。对于 attention 是 O(n²) 复杂度的模型，序列长度增加的代价比 Embedding 矩阵增大的代价更敏感。

词表大小典型模型Embedding 矩阵 (dim=4096, BF16)多语言覆盖序列效率
32KLLaMA-1/2, Mistral~512 MB亚洲语言较弱序列偏长
50KGPT-2, RoBERTa~800 MB英语为主中等
65KLLaMA-3~1.0 GB改进多语言中等
100KGPT-4 (cl100k_base)~1.6 GB较好多语言序列较短
256KGemma-2~4.0 GB强多语言序列最短
经验法则：英语为主的预训练，32K-65K 是合理区间；强多语言需求，100K+ 较适合；代码为主，50K-100K 并做 byte-fallback 通常效果好。

3.2 特殊 Token 设计

特殊 token 是 tokenizer 与模型结构之间的接口，一旦确定后更改会破坏所有下游模型权重中的 Embedding 矩阵。如果 tokenizer 词表变化（增删 token），对应位置的 Embedding 需要重新初始化或迁移，pre-trained 权重对这些 token 的语义理解会丢失。

常见特殊 token 类别：
- BOS (beginning of sequence): <s>, <|startoftext|>
- EOS (end of sequence): </s>, <|endoftext|>
- PAD: <pad> (packing 场景可能不需要)
- UNK: <unk> (byte-level BPE 通常不需要)
- SEP: <sep> (多段分隔)
- MASK: <mask> (MLM 任务)
- 任务特定: <|user|>, <|assistant|>, <|system|> (chat 模型)
兼容性陷阱：tokenizer 版本必须严格锁定，与模型 checkpoint 一起版本化管理。推理服务加载模型时，必须同步加载匹配的 tokenizer，不能跨版本混用——词表大小变化会导致 Embedding 矩阵维度不匹配，直接 crash 或产生静默错误。

4. Tokenization 性能：SIMD 优化、Rust 实现、批量并行

4.1 编码推理的性能瓶颈

tokenization 的主要计算开销来自：(1) Regex pre-tokenization——按 pattern 切分文本，Python regex 是瓶颈；(2) BPE merge 过程——反复查找并合并最高优先级 pair，O(n log n) per word；(3) 词表查找——hash map 查找 token 字符串对应 ID。

4.2 SIMD 与 Rust 优化路径

Tiktoken 和 HuggingFace Tokenizers 的 Rust 实现利用 SIMD 快速扫描 ASCII 字节（检测非 ASCII，决定是否走 fast path）、批量字节级 BPE 预处理、向量化 hash 计算。Rust 内存模型提供零拷贝（直接在原始字节切片上操作）、无 GC（避免 Python GIL 和 GC pause）、线程安全（Tokenizer 对象 Send + Sync，可无锁并行）。

4.3 大规模并行 Tokenization 工程实践

from tokenizers import Tokenizer
from multiprocessing import Pool

def tokenize_chunk(args):
    tokenizer_path, texts = args
    tokenizer = Tokenizer.from_file(tokenizer_path)
    # encode_batch 内部用 Rust 多线程
    encodings = tokenizer.encode_batch(texts)
    return [e.ids for e in encodings]

# 进程级并行（绕过 GIL）
with Pool(processes=32) as pool:
    results = pool.map(tokenize_chunk, chunks)
工程边界：单机 32 core，使用 Rust tokenizer，处理 1TB 文本（UTF-8）大约需要 4-8 小时。使用 64 节点的 Spark/Ray 集群，可压缩到 30-60 分钟。tokenization 的瓶颈通常先在 IO（从对象存储读取文本）而非 CPU，需要 IO 与 CPU 并行流水。

5. Sequence Packing：从文档到训练序列

5.1 为什么需要 Packing

自回归语言模型训练需要固定 shape 的 batch：[batch_size, seq_len]。但自然语言文档长度分布极不均匀——典型 Web 文本 25th percentile 约 50 tokens，95th percentile 约 3000 tokens。如果不 pack，直接 pad 到 max_len，对于 seq_len=4096、平均文档 200 token 的场景，padding 比例高达 95%，几乎所有显存和计算都在做无用功。

5.2 Sequence Packing 实现

def pack_sequences(token_lists, seq_len):
    """Greedy sequence packing"""
    packed, current = [], []
    for tokens in token_lists:
        if len(current) + len(tokens) <= seq_len:
            current.extend(tokens)
        else:
            if current:
                packed.append(current)
            current = tokens[:seq_len]  # 超长截断
    if current:
        packed.append(current)
    return packed

5.3 Document Boundary 与 Attention Mask

Packing 后的问题：默认 causal attention 中，后一个文档的 token 可以 attend 到前一个文档，引入跨文档 attention 污染。有两种解决方案：

方案一：document boundary mask

def build_doc_mask(doc_ids, seq_len):
    """同文档内 causal，跨文档屏蔽"""
    mask = (doc_ids.unsqueeze(0) == doc_ids.unsqueeze(1))
    causal = torch.tril(torch.ones(seq_len, seq_len, dtype=torch.bool))
    return mask & causal

方案二：Flash Attention 的 cu_seqlens 接口（推荐）

from flash_attn import flash_attn_varlen_func
# cu_seqlens: [0, len_doc1, len_doc1+len_doc2, ...]
cu_seqlens = torch.tensor([0, 450, 900, 1200, ...], dtype=torch.int32)
output = flash_attn_varlen_func(q, k, v, cu_seqlens, cu_seqlens, max_seqlen, max_seqlen)
工程边界：document boundary mask 需要额外 O(seq_len²) 显存存放 mask 矩阵（seq_len=4096 时约 16MB/sample）。Flash Attention 的 cu_seqlens 方式没有额外显存开销，是大规模预训练的推荐方案。

6. Sample-level vs Token-level 损失：Packing 如何影响 Loss

6.1 数学定义

Sample-level loss（不 packing 时的自然定义）：每个文档先在文档内按 token 平均，再跨文档平均。长文档和短文档权重相同。

Token-level loss（packing 时的自然定义）：所有 token 等权，长文档自然获得更多权重。

场景Loss 行为实践影响
文档长度均匀分布两种 loss 几乎等价无明显区别
混合短文档（新闻）和长文档（书籍）Token-level 偏向长文档模型可能对长格式过拟合
代码预训练（文件长度差异大）Token-level 权重偏向大文件小函数、短脚本学习不足
指令微调（prompt + response）需要只对 response 计算 losspacking 后需精确 loss mask
def compute_loss_with_mask(logits, labels, loss_mask):
    """loss_mask: 1=计算 loss（response token）, 0=忽略（prompt token）"""
    loss = F.cross_entropy(
        logits.reshape(-1, vocab_size),
        labels.reshape(-1),
        reduction='none'
    )
    loss = (loss * loss_mask.reshape(-1)).sum() / loss_mask.sum()
    return loss
工程陷阱：如果混合使用了不同 loss 计算方式（如预训练用 token-level，微调用 sample-level），会导致 loss scale 的突变，使学习率等超参失效。必须在整个训练流程中保持 loss 语义一致，并在 loss 数值上加入规范化（per-token loss logging）。

8. Sharding 策略：大小、Token 数、Doc 数与 Hash

8.1 四种 Sharding 策略对比

策略切分依据优势劣势适用场景
按文件大小每 N MB 一个 shard实现简单，shard 大小均匀shard 内 token 数不均多模态、混合格式数据
按 token 数每 N token 一个 shardtoken 数均匀，step 数可预测需要先 tokenize 再统计文本预训练（首选）
按文档数每 N 个文档一个 shard实现简单shard 大小不均文档数量均匀的数据集
按 hash文档 ID hash 到 shard确定性分配，易 lookup不保证均匀跨 split 追踪同一文档
经验法则：大规模语言模型预训练推荐按 token 数 sharding，每 shard 含约 10M token（约 20-80MB，取决于压缩和整数宽度）。1TB 语料约产生 1000-5000 个 shard，DataLoader 分配均匀，step 数估算准确。

8.2 Shard 大小的工程边界

flowchart LR
    Small["Shard 太小\n小于 16MB"] -->|代价| SmallCost["open/stat 开销大\n对象存储请求数多\nTLS 握手频繁\n调度元数据开销高"]
    Large["Shard 太大\n大于 2GB"] -->|代价| LargeCost["失败重试代价大\n难以均匀分配\n局部 shuffle 灵活性差"]
    Good["推荐区间\n64MB-1GB"] -->|优势| GoodBenefit["存储看到连续大读取\n10-10000 worker 均匀分摊\n失败重试代价可接受\nshard 间 shuffle 统计随机"]

8.3 多节点 Rank 分配示意

def get_shards_for_rank(all_shards, rank, world_size, epoch, seed):
    """确定性地为每个 rank 分配 shard"""
    rng = random.Random(seed + epoch)
    shuffled = list(all_shards)
    rng.shuffle(shuffled)
    return shuffled[rank::world_size]  # 每个 rank 取 1/world_size 的 shard

关键设计要求：(1) Deterministic——相同 seed + epoch + rank 产生相同 shard 序列；(2) No overlap——不同 rank 的 shard 集合不重叠；(3) Full coverage——所有 shard 恰好被某个 rank 覆盖；(4) Resume-friendly——checkpoint 时记录 epoch + step，重启时跳过已消费 shard/sample。

9.2 Shuffle 策略的两级设计

完全随机 shuffle 在大规模分布式训练中代价极高（需要全局通信或随机 IO）。实践中采用两级 shuffle：

Level 1 Shard-level shuffle：打乱 shard 顺序，只需打乱 shard ID 列表，代价极低，确保不同 rank 在不同 epoch 看到不同 shard 顺序。

Level 2 Shard-internal shuffle：在读取每个 shard 时，对 shard 内部样本做局部 shuffle，只需 shard 内部 index 随机化，代价与 shard 内 sample 数成正比。

10. AI Infra 视角：Tokenizer 离线预处理 vs 在线服务化

10.1 离线预处理 vs 在线 Tokenization

维度离线预处理在线 Tokenization
执行时机训练前一次性处理训练时 DataLoader 动态处理
存储需求需额外存 token ID 数组（~1.1TB/TB 文本）只存原始文本
训练时 CPU 开销几乎零（只做数组读取）显著（tokenize 占 DataLoader 时间）
灵活性低（换 tokenizer 需重新处理）高（随时换 tokenizer）
确定性强（token ID 固定）依赖 tokenizer 版本
适用场景大规模预训练（100B+ tokens）实验性训练、小数据集（< 10B tokens）
大规模预训练的标准做法：离线预处理。把 tokenization 作为独立的 ETL 阶段，输出存储为 .mds 或 .bin 格式。训练时 DataLoader 只做 IO + 类型转换，CPU 几乎空闲，不会成为 GPU 瓶颈。

10.2 推理侧 Tokenizer 服务化

flowchart LR
    Client["客户端 / API\n原始文本"] -->|HTTP/gRPC| TokSvc["Tokenizer Service\nRust/C++ 实现\n多副本部署"]
    TokSvc -->|token IDs| InfSvc["推理服务\nvLLM / TensorRT-LLM"]
    TokSvc -->|缓存命中| Cache["Redis / 本地 LRU\n热门 prompt 缓存"]
    Cache -->|cache hit| TokSvc
    InfSvc -->|输出 token IDs| DeTok["Detokenizer Service"]
    DeTok -->|原始文本| Client

Tokenizer 服务化的优势：推理服务无需加载 tokenizer 权重，更专注 GPU 计算；可独立扩容；对热门 prompt 可缓存 token 结果（固定系统 prompt 命中率可达 80%+）；版本管理集中。

工程边界：tokenizer 服务化增加网络 RTT（通常 < 1ms，但 P99 可能 3-5ms）。对延迟极敏感的链路，可把 tokenizer 和推理服务部署在同一进程或同一节点，避免网络跳数。对 prefill 密集型工作负载，tokenizer 延迟通常不是瓶颈。

11. Worked Example：1TB 文本端到端 Tokenize + Pack + Shard 为 MosaicML Streaming 格式

11.1 场景设定

  • 输入：1TB 原始文本（混合 Web 文本、书籍、代码），存储在 S3，约 500 亿 Unicode 字符
  • Tokenizer：LLaMA-3 tokenizer（128K 词表，SentencePiece-based），平均约 3.5 字节/token
  • 目标序列长度：4096 tokens
  • 目标格式：MosaicML Streaming (.mds)，10M tokens/shard
  • 训练集群：64 个 H100 节点，每节点 8 卡（512 GPU）

11.2 Step 1：规模估算

原始文本：1TB = 10^12 字节
平均字节/token = 3.5
估算 token 总数 = 1TB / 3.5B ≈ 286B tokens ≈ 280B tokens

存储计算（uint32 存储 token ID，词表 128K 需要 4 字节）：
280B tokens × 4 bytes/token = 1.12TB（未压缩）

使用 zstd 压缩（典型压缩比 2-3x）：
压缩后约 400-560 GB

Shard 数量（10M tokens/shard）：
280B / 10M = 28,000 个 shard

每 shard 大小：
未压缩：10M × 4 bytes = 40MB/shard
压缩后：约 15-20MB/shard

11.3 Step 2：并行 Tokenization 作业

import ray
from tokenizers import Tokenizer

@ray.remote(num_cpus=4)
class TokenizerWorker:
    def __init__(self, tokenizer_path):
        self.tokenizer = Tokenizer.from_file(tokenizer_path)

    def process_file(self, s3_path):
        texts = self._read_s3_jsonl(s3_path)
        encodings = self.tokenizer.encode_batch(texts)
        return [e.ids for e in encodings]

# 64 个 worker 并行处理
workers = [TokenizerWorker.remote("s3://model/tokenizer.json") for _ in range(64)]
# 预计处理时间：~3-4 小时（瓶颈在 S3 读取 IO）

11.4 Step 3：Packing + 写入 .mds

from streaming.base import MDSWriter
import numpy as np

def pack_and_write(token_lists, output_dir, seq_len=4096):
    columns = {"tokens": "ndarray:int32", "doc_ids": "ndarray:int32"}
    buffer, doc_buffer = [], []
    doc_id = 0

    with MDSWriter(out=output_dir, columns=columns, compression="zstd") as writer:
        for tokens in token_lists:
            tokens = tokens + [eos_token_id]  # 文档分隔
            doc_ids = [doc_id] * len(tokens)
            doc_id += 1

            while tokens:
                space = seq_len - len(buffer)
                buffer.extend(tokens[:space])
                doc_buffer.extend(doc_ids[:len(tokens[:space])])
                tokens, doc_ids = tokens[space:], doc_ids[space:]

                if len(buffer) == seq_len:
                    writer.write({
                        "tokens": np.array(buffer, dtype=np.int32),
                        "doc_ids": np.array(doc_buffer, dtype=np.int32),
                    })
                    buffer, doc_buffer = [], []

11.6 端到端总结

  • 输入：1TB 原始文本（S3）
  • 处理：~3-4 小时（64 节点 Ray 集群并行 tokenization + packing）
  • 输出：~490GB .mds 格式（S3），280B tokens，28,000 shard
  • 训练：64 节点 × 8 H100 = 512 GPU；全局 batch = 4096 × 8 × 512 ≈ 16M tokens/step；280B / 16M ≈ 17,500 steps = 1 epoch
  • 读取吞吐：13.8 GB/s（远超训练计算瓶颈，GPU 不等数据）
  • DataLoader CPU 占用：20%（GPU 利用率稳定 90%+）
关键结论：正确的 tokenization 流水线（离线预处理 + .mds 格式 + 按 token 数 sharding）使 DataLoader CPU 占用降至 20%，读取吞吐 13.8 GB/s 远超典型训练步的计算时间，GPU 利用率稳定 90%+。如果使用 JSONL + 在线 tokenization，DataLoader CPU 成为瓶颈，GPU 利用率可能跌至 60% 以下。
