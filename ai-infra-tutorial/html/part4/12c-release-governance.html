第 12c 章 · 制品版本治理与发布门禁

模型发布不是"把文件推上去"，而是一条从训练完成到线上流量的证明链——证明这个版本足够安全、足够正确、足够兼容，并且出了问题可以在 5 分钟内找到上一个确定可用的版本。版本治理是把离散的模型文件变成可追溯、可回滚、可审计的平台对象的工程基础设施。

1. 第一性原理拆解：制品版本治理与发布门禁

拆 — 不可化简的问题

剥离 GitOps、ArgoCD、MLflow、SemVer、SBOM、4-eyes approval 这些词之后，本章要解决的不可化简问题只有一个：模型的线上版本必须可追溯、可回滚、可审计，任何错误的 promotion 都会污染线上服务并影响真实用户。

先定位问题的严重性。普通软件的发布失败通常是"接口报 500"或"构建失败"，发现成本低，自动回滚代价也低。模型的发布失败经常是"接口返回 200，但回答质量退化了 8%"，或者"新 tokenizer 对某类输入的处理方式悄然改变，下游 parsing 逻辑出现边界错误"。这类故障在 A/B 实验数据积累到足够的统计显著性之前，通常是不可见的——但它已经在影响真实用户。更危险的是，如果发布流程允许手工覆盖元数据或跳过评测报告，团队可能在根本不知道"线上跑的是什么"的情况下继续操作。

从这个核心问题展开，会推出四个第一性约束：不可变性（一旦发布就不能就地修改，修复必须是新版本）、完整性（发布单元包含权重、tokenizer、配置、评测报告、签名的绑定整体）、门禁驱动（promotion 每步由机器可执行的门禁条件控制，失败自动阻断）、可回滚性（任意时刻可在 5 分钟内回到上一个确认可用版本）。这四个约束相互依赖：没有不可变性，版本号就不可信；没有完整性，回滚就是残缺的；没有门禁，不可变性只是仪式；没有可回滚性，整个治理体系只是纸面上的保证。

推 — 从这个问题如何推导出每个机制

从"不可变性"必然推导出版本号策略：版本号必须能唯一且确定地标识一个制品的内容状态。这就引发 SemVer vs date-based vs hash-based vs 业务对齐版本之间的设计权衡。哈希天然保证内容不可变但对人类不友好；SemVer 表达兼容性契约但模型"兼容"定义比 API 更模糊；日期版本可读但不表达语义破坏。

从"完整性"必然推导出发布单元（Release Bundle）的概念：registry 必须把所有组成部分绑定为一个原子对象。这进一步推出兼容性门禁：必须自动校验新版本的 tokenizer、API schema、input/output shape 是否与上一个生产版本后向兼容。一个常见陷阱是：tokenizer 词表文件哈希没变，但 normalizer 配置变了，导致某些 Unicode 输入的 tokenize 结果不同——这种变化不会触发接口层面的 schema 变更检查，但会造成下游静默错误。

从"门禁驱动"必然推导出多层评测门禁：离线评测（核心指标、回归样本、safety 测试）、在线采样（灰度期间 LLM-as-judge、人工抽检）、业务指标（任务完成率、满意度信号）。每层门禁有固定阈值，低于阈值自动阻断。还推出统计显著性要求：两版本指标差异必须超过最小可检测效果量（MDE），否则"通过"可能只是噪声。从"可回滚性"必然推导出promotion 状态机，使回滚成为显式的状态转换事件，而不是手工操作文件。从"审计"必然推导出审批流和不可删除的审计日志。从"出了问题"必然推导出发布预算与 kill switch：超过错误预算阈值自动回滚，不等待人工决策。

2. 版本号策略：为什么这个问题没有唯一答案

模型版本号的设计必须服务于两个相互矛盾的目标：人类可读（让工程师、PM、安全团队能快速判断版本关系）和机器可验证（让 CI/CD、registry、serving platform 能用版本号做自动化决策）。

策略示例优势劣势推荐场景
SemVer 2.1.0, 3.0.0-rc1 表达兼容性契约，MAJOR=破坏性变更 "兼容"对模型输出语义比对 API 更难定义 对外暴露 API 的模型服务
Date-based 2026-05-03, 20260503-r2 可读性强，自然表达时间顺序 不表达兼容性，同一天可能有多个版本 快速迭代的内部模型
Hash-based sha256:a3f2c8... 内容可验证，天然不可变 对人类完全不可读 供应链安全场景，通常与其他策略叠加
业务对齐版本 gpt-4o-2025-05, reranker-v3 对产品和业务最友好 技术细节不透明，容易产生"v3 改了什么"的混乱 对外发布的产品模型
推荐组合：业务版本号 + 内部 date-based + 内容 SHA256 三层组合。例如：对外叫 reranker-v3，内部注册为 reranker-2026-05-03-rc1，artifact 存储时用 sha256:a3f2c... 做内容完整性锚定。三层各司其职，互不干扰。
关键原则：版本号一旦发布，禁止重用（no tag reuse）。如果 2026-05-03-rc1 因评测失败被废弃，下一次发布必须用新版本号（如 2026-05-03-rc2），即使内容改动极小。版本号是追溯链条的锚点，重用会让整个审计体系失效。

2.1 版本号与不可变制品的关系

不可变制品（Immutable Artifact）原则是版本号策略的执行保障：

  • 对象存储层：模型文件写入包含版本号或哈希的路径，禁用覆盖 API
  • Registry 层：版本记录一旦写入不能删除或修改，只能标记为 deprecated
  • Serving 层：严格通过版本号引用模型，禁止"latest"指针指向变化的内容
# 正确做法：内容哈希锚定
artifact:
  uri: s3://models/reranker/2026-05-03-rc1/model.safetensors
  sha256: a3f2c8d1e9b4f7a6c2d0e5f8b3a1c4d7e9f2b5a8c1d4e7f0b3a6c9d2e5f8b1
  immutable: true

# 错误做法：指向 mutable 路径
artifact:
  uri: s3://models/reranker/latest/model.safetensors  # "latest" 随时可能变化

3. Promotion 状态机：模型版本的生命周期

模型版本从诞生到退休，经历一条有明确转换条件的状态链路。每个状态代表该版本被允许做的事、接收的流量，以及触发的后续动作。

stateDiagram-v2
    [*] --> draft : 训练完成，注册模型包
    draft --> validated : 离线评测全部通过
    draft --> rejected : 任意门禁失败
    validated --> staging : 兼容性+性能门禁通过
    staging --> canary : 人工审批+staging 观测期通过
    canary --> production : 灰度观测期通过+在线门禁通过
    canary --> staging : 在线指标退化，自动回滚
    production --> deprecated : 新版本上线，启动 sunset 流程
    rejected --> [*] : 废弃，归档
    deprecated --> [*] : 依赖清零后下线
状态含义允许流量转换触发条件
draft 已注册，未评测 无 训练完成后自动创建
validated 离线评测通过 无（仅内部测试） 离线门禁全部通过
staging 兼容性和性能已验证 仅内部测试流量 兼容性门禁 + 性能门禁通过
canary 小比例生产流量验证 1%—20% 生产流量 人工审批 + staging 观测期通过
production 全量生产流量 100%（或分租户满载） 在线门禁通过 + 正式审批
deprecated 新版本已上线，开始 sunset 无（旧请求继续至迁移完成） 新版本 production + deprecation 流程启动
rejected 评测或门禁失败 无 任意必过门禁失败
状态流转必须有审计日志：每次状态变更都应记录操作者（人工或自动化）、时间戳、触发原因、关联门禁报告 ID。这是事后追溯"谁在什么时候、凭什么把这个版本推到 production"的唯一证据。

4. 多层评测门禁体系

评测门禁分三层，每层回答不同问题，覆盖不同时间窗口。任意层失败都会阻断 promotion，且不允许人工 override（安全门禁绝对不允许）。

flowchart TD
    A[新版本注册] --> B[离线评测门禁]
    B -->|通过| C[兼容性+性能门禁]
    B -->|失败| X1[自动拒绝 rejected]
    C -->|通过| D[staging 观测]
    C -->|失败| X2[自动拒绝 rejected]
    D -->|审批通过| E[canary 发布]
    E --> F[在线评测门禁]
    F -->|通过| G[业务门禁]
    F -->|失败| Y1[自动回滚 staging]
    G -->|通过| H[production promotion]
    G -->|失败| Y2[暂停放量，人工介入]
    H --> I[production 持续监控]
    I -->|SLO 破坏| Z[kill switch 回滚]

4.1 第一层：离线评测门禁

在 canary 之前必须完成，覆盖以下检查项：

门禁项必过指标对比基准统计要求
传统 ML 任务指标 Accuracy、F1、AUC、NDCG、Recall@K（分类/排序/检索任务） 上一个 production 版本 不低于 baseline 的 (1 − δ)，δ ≤ 2%
LLM 通用知识 / 推理 MMLU、MMLU-Pro、BBH、AGIEval 上一个版本 + 公开 LLM 排行榜 关键 subset（如 MMLU STEM、BBH causal）不能下降
LLM 数学推理 GSM8K、MATH、AIME 上一个版本 不低于 baseline，注意 fixed prompt 模板
LLM 代码 HumanEval、HumanEval+、MBPP、LiveCodeBench、SWE-bench 上一个版本 必须沙箱执行验证
LLM 指令跟随 / 对话 MT-Bench、AlpacaEval 2.0、Arena-Hard、IFEval 上一个版本 用 GPT-4 / Claude 作 judge，固定 judge 版本，swap A/B 顺序消除 position bias
RAG 系统 Ragas、TruLens、RAGChecker 上一个版本 与 retrieval index 版本绑定
Agent 系统 GAIA、AgentBench、SWE-bench、τ-bench 上一个版本 多步任务完成率 + 工具调用成功率
业务 Golden Set 业务场景的事实正确性、合规性 50-500 条标注样本 不允许 high-criticality case 退化
回归集 已知 bad case 集合的错误率 ≤ 阈值 固定的 bad case 集 不允许新增已知类型错误
Safety 测试 ToxiGen、AdvBench、HarmBench、PromptBench + 有害输出率 ≤ 0.1%、PII 泄漏 = 0、prompt injection 防御成功率 最严格的 safety baseline 不能低于 baseline，零容忍 PII
成本测试 平均输出 token 数、推理时长、reasoning token 消耗 上一个版本 成本 regression ≤ 5%
传统 NLG（仅翻译/摘要任务） BLEU、ROUGE、BERTScore 上一个版本 仅这两类任务保留，其他 LLM 任务不再使用
不要把 BLEU / ROUGE 当 LLM 主评测指标。它们对开放式问答、推理、代码、Agent 任务与人评相关性很低（多份研究 Pearson < 0.3）。继续把它们当 release gate，会出现"分数没退化但用户感受明显变差"或"分数大幅退化但实际质量没变"两种错误信号。LLM 评测必须用上面表格里的 benchmark 矩阵。
LLM-as-judge 工程化要点：(1) 固定 judge 模型版本（judge 升级会引入 0.5-1 分系统漂移）；(2) swap A/B 顺序两次取均值消除 position bias；(3) 长度归一化或显式提示约束，避免 length bias；(4) 用人工样本周期校准 judge，确保一致性 > 0.8；(5) judge 成本可观（GPT-4 1000 题约 $20-50），release gate 通常 sample 200-500 题做 daily run，full set 做 weekly。
release gate 最小组合（任何 LLM 模型上线前必跑）：MMLU + GSM8K + HumanEval + MT-Bench + 业务 Golden Set + Safety benchmark。前 4 项可用 lm-evaluation-harness（EleutherAI）或 OpenCompass 在 1-2 小时跑完。
统计显著性：若两版本指标差异小于最小可检测效果量（MDE = 0.5σ），认为差异不显著，视为通过（避免因噪声拒绝等效版本）。若差异超过 MDE 且低于阈值，则阻断。评测报告必须包含置信区间和样本量。

4.2 第二层：在线评测门禁（Canary 阶段）

信号类型具体指标采集方式告警阈值
硬性质量信号 错误率、超时率、OOM 率 metrics + log 超过 baseline 的 2× 触发告警
软性质量信号 LLM-as-judge 质量分、人工抽检通过率 随机采样 + judge model 低于 baseline 的 95% 触发暂停
安全信号 有害输出率、越权输出率 安全过滤层 metrics 任何 > 0.1% 立即回滚
成本信号 每请求 token 消耗、推理延迟 tracing 成本上升 > 10% 触发评审
按切片观察：在线采样必须按租户、场景、输入长度分桶，不能只看整体平均。整体平均可能掩盖某类用户严重受损的情况——长 prompt 用户的输出质量退化，可能被大量短 prompt 用户的正常结果平均掉。

5. 兼容性门禁：最容易被忽视的一类

兼容性问题通常不会产生 500 错误，而是产生"静默错误"：输出格式变了但没有 exception，tokenizer 边界行为变了但解码结果只在极少数输入上出错。这类故障往往在影响用户数天后才被发现。

flowchart LR
    subgraph 兼容性检查项
        A[Tokenizer 兼容性] --> A1[词表版本一致\n特殊 token 映射不变\nbos/eos/pad 不变]
        B[API Schema 兼容性] --> B1[请求响应字段不缺失\n枚举值不缩减\n可选字段有默认值]
        C[Output Shape 兼容性] --> C1[logits 维度\nembedding 维度\n结构化输出格式]
        D[Preprocessor 兼容性] --> D1[图像归一化参数\n文本截断策略\n特殊字符处理]
    end
兼容性维度检查方法失败后果严重程度
Tokenizer 词表 比对 tokenizer 配置哈希，对同一组样本做 encode-decode roundtrip 下游 parsing 错误、embedding 不匹配 严重
特殊 token 映射 校验 bos、eos、pad、sep 的 ID 是否与上一版本一致 序列截断错误、对话格式错乱 严重
API 请求 schema OpenAPI diff，检查字段删除、类型变更、枚举缩减 调用方 400 错误 严重
API 响应 schema 对同一组测试输入比对输出格式，检查字段结构 调用方解析失败 中等
Embedding 维度 数值检查输出 tensor shape 下游向量库 insert 失败 严重
Output shape（生成模型） 对边界输入（最大长度、特殊格式）做端到端测试 截断、格式错误 中等
工程边界：兼容性检查不能只靠"schema 看起来没变"，必须用真实样本做端到端验证。一个常见陷阱是：tokenizer 的词表文件哈希没变，但 normalizer 配置变了，导致某些 Unicode 输入的 tokenize 结果不同。这种变化不会被 schema diff 工具发现，只能通过端到端 roundtrip 测试发现。

6. 性能门禁：防止 Throughput 和 Latency Regression

性能门禁的目标不是"越快越好"，而是"不能比上一个版本差"。模型量化、架构调整、服务框架升级之后，性能可能因为各种原因出现隐性 regression。

性能门禁项检查方法Regression 阈值触发行动
Throughput (tokens/s) 固定 batch 大小下的 token 生成速率 低于上一版本 95% 阻断 promotion
Latency P50/P99 固定请求集的端到端推理延迟 P99 超过上一版本 110% 阻断 promotion
Memory Footprint 固定 batch 下的峰值显存占用 超过上一版本 105% 告警 + 人工评审
Time-to-First-Token (TTFT) streaming 场景下首 token 延迟 超过上一版本 115% 告警
KV Cache 命中率 相同 prefix 请求集下的缓存命中率 低于上一版本 90% 告警
性能测试基准固定化：性能门禁的测试集（请求分布、batch 大小、序列长度分布）必须是固定的、版本化的，不能每次测试都用不同输入，否则比较没有意义。测试集本身应该作为 artifact 被 registry 管理。

7. 安全门禁

安全门禁保证新版本不会引入或放宽对有害内容的生成限制。安全门禁失败时，不允许任何人工 override。

安全检查项测试集通过条件失败处置
恶意 prompt 拒绝率 固定的 red-team 测试集（越狱、角色扮演、间接注入） 拒绝率 ≥ 上一版本 × 98% 立即阻断，无豁免
PII 泄漏率 包含 PII 数据的测试集 泄漏率 = 0（零容忍） 立即阻断
有害输出率 人工标注的有害内容分类集 ≤ 0.1% 立即阻断
越权输出率 权限边界测试集（跨租户、跨角色） = 0 立即阻断
Prompt Injection 防御 结构化 injection 攻击集 防御率 ≥ 上一版本 阻断
安全门禁必须独立执行：安全测试集不能与普通评测集合并，不能因为"整体质量够好"而豁免安全门禁失败。安全门禁失败时，不允许任何人工覆盖（override）——无论情况多紧急，均无例外。

8. 自动化 Release Pipeline

一个典型的 release pipeline 把所有门禁串联成可自动执行的工作流，确保人工操作只在关键决策点（审批）介入，其余全部机器执行并留存记录。

    participant Gate as 门禁引擎
    participant Approval as 审批系统

8.1 常用实现方案对比

9. 审批流：谁有权力把模型推到 Production

flowchart TD
    A[promotion 申请] --> B{风险等级}
    B -->|低风险 patch\n指标无破坏性变化| C[单人审批\n任意 senior engineer]
    B -->|中风险 minor\n有指标变化但在容差内| D[双人审批\nEM + tech lead]
    B -->|高风险 major\n接口变更或安全策略变更| E[4-eyes rule\n至少 2 人独立审批\n含安全团队]
    B -->|紧急热修复| F[紧急审批流\n1 人审批\n24h 内补报告]
    C --> G[记录审批人+时间戳+审批时版本报告快照]
    D --> G
    E --> G
    F --> G
    G --> H[promotion 执行]
审批模式适用场景要求风险
单人审批 低风险变更，patch 级别 审批人必须看完评测报告 审批人可能有偏见或疏忽
双人审批 中风险变更 两人独立查看，意见一致才通过 审批效率降低
4-eyes rule 高风险变更 任意两人不能来自同一团队 审批周期长，需提前规划
紧急审批流 生产故障紧急修复 单人可通过，但必须在 24h 内补充完整文档 滥用风险，必须有审计告警
审计不可删除：审批记录必须写入不可删除的审计日志，包含：审批人、审批时间、版本号、关联评测报告 ID、审批意见。这些记录不仅用于内部追溯，也是安全合规和外部审计的基础。审计日志本身应该有完整性保证（如哈希链或签名）。

10.2 Kill Switch 执行流程

flowchart LR
    A[production 监控] --> B{指标超阈值?}
    B -->|自动触发| C[kill switch 执行]
    B -->|人工触发| C
    C --> D[流量立即切回上一版本]
    D --> E[新版本状态变为 staging]
    E --> F[发送告警+创建 incident ticket]
    F --> G[保留现场快照\n评测报告 metrics traces]
Kill Switch 设计原则：
  • 独立于正常 CD 流程，CD 故障时仍可执行
  • 单命令执行，运维工程师点击一个按钮即可触发
  • 执行时间 SLA：流量 100% 切离新版本 ≤ 30s
  • 触发后自动通知 on-call 工程师和相关负责人
  • 回滚目标版本必须在 promotion 之前确认存在且可服务

11. 与 Ch 22 灰度发布的协同

本章（12c）和第 22 章分别负责 release pipeline 的不同层面，必须配合但不能混淆。

维度本章（12c）负责第 22 章负责
关注点 Release-time governance：版本合法性、门禁通过、审批、不可变性 Traffic shaping：流量切分比例、观测信号、放量节奏
时间窗口 Promotion 之前（pre-flight checks）+ 状态机管理 Canary 期间（in-flight monitoring）
核心问题 "这个版本有资格进入 production 流量" "这个版本在真实流量下是否表现正常"
失败处理 阻断 promotion，版本状态回到 staging/rejected 暂停放量或自动回滚，通知 on-call
产出 经过审批的 production promotion 事件 灰度观测报告、放量决策
协同接口：12c 的 promotion 状态机是 Ch 22 灰度发布的前提——只有 staging 状态的版本才能进入 canary 流量；在线观测结果回流到 12c 的门禁系统，决定是否继续放量或回滚。两者通过 Model Registry 的状态字段和事件总线解耦通信。

12. 模型 Deprecation：版本退休流程

    dateFormat  YYYY-MM-DD

    新版本 canary           :2026-05-01, 7d

    旧版本迁移期            :2026-05-08, 60d

    旧版本下线              :milestone, 2026-07-22, 0d
    section 依赖扫描
    扫描下游依赖            :2026-05-08, 3d
    发送迁移通知            :2026-05-11, 1d
    依赖清零确认            :2026-07-20, 2d

12.1 Deprecation 流程步骤

  1. 依赖扫描：扫描所有引用当前 production 版本的系统（API 调用方、实验 baseline、评测集 reference、serving route）
  2. 发布 deprecation 通知：包含下线时间、新版本迁移指南、联系人
  3. 迁移期（通常 30—90 天）：旧版本继续服务，新版本并行运行
  4. 只读模式（下线前 14 天）：旧版本禁止新增流量路由，仅服务已有流量
  5. 依赖清零确认：确认所有依赖已迁移到新版本
  6. 下线：旧版本标记 retired，artifact 进入归档（长期保留，但不可路由流量）
归档 ≠ 删除：已 deprecated 的模型版本 artifact 必须继续保留在对象存储中，保留期限按合规要求决定（通常 1—3 年）。归档版本仍然可以用于审计、法律取证和历史评测对比，但不能路由生产流量。

13.7 假设失败场景：阶段 2 兼容性门禁失败

  1. 版本状态更新为 rejected
  2. 发送告警给模型团队，附详细 diff
  3. 创建 bug ticket，关联版本号和失败报告
  4. 阻断所有后续 promotion 步骤

13.8 每个 Gate 的通过/失败决策标准汇总

Gate通过条件失败后行动可否人工 override
离线评测核心指标、回归集、safety 全通过→ rejected否（safety 绝对不可）
兼容性tokenizer/schema/shape 全兼容→ rejected否
性能throughput/latency/memory 无 regression→ rejected技术类可人工评审
人工审批符合风险等级的审批人数批准等待本质上就是人工
在线门禁硬性/软性/安全/成本指标全在阈值内→ staging 回滚否（安全指标绝对不可）
业务门禁任务完成率、SLA 达成暂停放量可，需记录原因

14. 练习

12c-1（基础）：不可变性原则
解释为什么模型 artifact 一旦发布就不能就地修改。如果团队发现一个刚发布的模型有一个小 bug，正确的处理流程是什么？版本号如何变化？新版本需要重新过哪些门禁？
12c-2（基础）：版本号策略
对比 SemVer、date-based、hash-based 三种版本号策略，分别说明各自最适合的场景。在 AI Infra 实践中，为什么通常需要组合使用而不是选一种？给出一个具体的三层组合方案。
12c-3（基础）：Promotion 状态机
画出模型版本的 promotion 状态机，标注每个状态转换的触发条件。为什么 canary 状态的回滚目标是 staging 而不是 rejected？canary 阶段的版本处于 staging 和 production 之间，如果此时 kill switch 触发，应该回滚到哪个版本？
12c-4（进阶）：Tokenizer 兼容性
设计一个 tokenizer 兼容性检查方案，需要覆盖哪些具体检查项？哪种兼容性失败最容易被忽视但后果最严重？给出一个具体的失败案例（如 normalizer 配置变更导致 Unicode 处理差异）。
12c-5（进阶）：统计显著性
离线评测门禁中的"统计显著性"要求是什么意思？如果两个版本的 NDCG@10 差异为 0.3%，但样本量只有 100，该如何判断是否通过？给出计算最小可检测效果量（MDE）的框架。
12c-6（进阶）：审批流设计
对比单人审批、双人审批和 4-eyes rule 三种审批模式。在什么情况下紧急审批流是合理的？如何防止紧急审批流被滥用（至少给出 3 种控制机制）？
12c-7（进阶）：Kill Switch
设计一个 kill switch 机制，要求：触发条件（自动 + 人工）、执行时间 SLA（如何保证 30s 内完成）、自动通知链路、执行后版本状态如何恢复。如果 CD 系统本身故障，kill switch 如何仍然可用？
12c-8（进阶）：按切片观察
在线评测门禁中，为什么必须按切片（租户、场景、输入长度）观察，而不是只看整体平均值？给出一个具体的例子说明平均值掩盖了问题的情况（如某类长 prompt 用户质量退化但被短 prompt 均值稀释）。
12c-9（设计）：多模型并发 Release
设计一个完整的 release pipeline，支持：(a) 多个模型并发发布不相互干扰；(b) 支持紧急热修复快速通道；(c) 所有门禁结果可查询和回放；(d) 支持按租户粒度的 canary。给出架构设计和关键模块说明。
12c-10（设计）：Deprecation 系统
设计一个模型 deprecation 系统，需要：自动扫描下游依赖、生成迁移通知、跟踪迁移进度、在依赖清零后自动触发下线。给出系统架构和关键 API 设计。依赖扫描需要覆盖哪些维度（API 调用方、实验 baseline、评测集 reference 等）？
12c-11（综合）：事故复盘与流程改进

12c-12（开放）：全自动发布的边界
