1. 第一性原理拆解：Checkpoint 工程化

拆 — 不可化简的问题

剥离 PyTorch DCP、FSDP、DeepSpeed、TorchSnapshot、Lustre、S3 multipart 这些工具名之后，Checkpoint 工程化要解决的不可化简问题是：训练任务故障一定会发生，恢复时间和数据安全直接决定训练成本，而保存和恢复的代价又与训练吞吐相互博弈。

"一定发生"不是夸张。一台 H100 的年度平均故障间隔（MTBF）大约 1–3 年，但一个 512 卡集群在时间维度上的"期望故障间隔"按卡数反比压缩，达到每几天一次的量级。加上调度器抢占、NCCL hang、存储断联、Xid 错误、驱动崩溃，任何超过数天的训练任务都必须假设"中途一定会断"。断了之后，损失的进度等于最后一次 checkpoint 到故障点之间的 token 数，这不是"几步训练"，而是真实的 GPU 小时数和云计算费用。一个 512 卡 H100 集群每小时算力成本约 $25,000–$40,000，直接等于一小时 checkpoint 频率对应的"最坏进度损失"的货币价值。

同时，保存 checkpoint 本身也有代价：同步保存期间所有 GPU 空转，异步保存会占用 CPU 和本地盘带宽。175B 模型在 512 卡上，每次同步 checkpoint 可能需要 5–15 分钟的等待，相当于每小时吞吐损失 8–25%。因此 checkpoint 频率、保存延迟、存储后端、异步实现之间存在一个必须显式建模的博弈，而不是靠经验值随手设一个"每 1000 步"。

这个问题还有第二层不可化简：分布式训练的 checkpoint 不是"一个文件"，而是 N×rank 的分片状态集合，包含模型参数分片、优化器状态分片、RNG 状态、sampler 进度、scheduler 状态、并行布局 metadata。这些必须全部对齐、全部校验、整体原子提交，才算一个"可恢复版本"。任何一个 rank 的分片缺失、损坏或版本不对齐，整个 checkpoint 都无法 true resume。

推 — 从这个问题如何推导出每个机制

从"保存有代价 + 故障一定发生"推出频率决策模型：最优 checkpoint 间隔 T* 是在进度损失期望值和保存开销之间取极小值，与集群故障率（λ）、单次保存延迟（t_save）和保存期间吞吐损失（η）共同决定。

从"保存期间 GPU 空转"推出异步 checkpoint：把状态复制到 CPU 内存后立即恢复训练，后台在 CPU 上执行序列化和写盘。这把 GPU 阻塞时间从"序列化+写盘"压缩为仅"内存 copy"（~10–30 秒），代价是 CPU 内存必须额外保留一份训练状态。

从"N 卡分片状态"推出sharded checkpoint：每个 rank 独立保存自己持有的分片，不 gather 到 rank 0，不存全量权重。这使写入带宽线性扩展（N 个 rank 并发写），避免 rank 0 成为瓶颈，但恢复时如果 rank 数发生变化（扩容/缩容/换卡），必须能重新 reshard——这是 DCP 设计中最复杂的部分。

从"半成品 checkpoint 比没有 checkpoint 更危险"推出manifest + 原子提交：先写到 tmp 目录，所有 rank 写完后，rank 0 写 manifest，最后执行 rename（POSIX）或 finalize（S3 multipart），使整版 checkpoint 原子对外可见。

从"rank 数可能变化"推出DCP 的 planner/writer/reader 设计：Planner 负责决定哪些 tensor 由哪些 rank 写/读，解耦物理 rank 布局和逻辑 state；storage_writer/storage_reader 负责把 planner 决策翻译成实际 I/O；metadata 记录每个分片的 key、shape、dtype、offset，使恢复时不依赖原始 rank 数。

从"保留多少 checkpoint"推出retention 策略：训练过程中保留 rolling N 个最近、K 个 milestone，以及 best（按验证集 loss）。三类用途不同：rolling 用于快速恢复、milestone 用于消融实验和复现、best 用于最终发布。删除老 checkpoint 时必须查 registry 状态，防止删除仍被引用的版本。

2. Checkpoint 的层级结构

大模型 checkpoint 工程化的第一步是弄清楚"checkpoint"在不同层次的含义。

2.1 Framework 层：PyTorch state_dict

最基础的 checkpoint 单元是 PyTorch 的 state_dict，包含模型参数、optimizer 状态、scheduler、RNG 状态、sampler 进度、step、tokens seen、tokenizer hash 和 code commit。

只保存模型权重不是 checkpoint：如果 optimizer.state_dict() 缺失，恢复后 Adam 的一阶和二阶矩归零，相当于重新热身，loss 曲线出现明显跳变。这是 warm start，不是 true resume，在成本上与重新训练无本质区别。

2.2 Distributed 层：全量 vs 分片

分布式训练下每个 rank 只持有参数的一个分片（FSDP sharding、ZeRO Stage-2/3），不存在"完整的 state_dict"。

方式写入并发单 rank 写入量（175B BF16）rank 数变化支持
全量（rank 0 gather）1~1.05 TB支持（但 rank 0 瓶颈）
Sharded（per rank）N=512~2.1 GB需 reshard
Hybrid（per node）节点数=64~16 GB/node部分支持

2.3 Storage 层：POSIX vs 并行 FS vs 对象存储

三种后端的语义差异决定了写入协议完全不同（详见 §0c 文件系统）：

存储后端适合场景原子性保证checkpoint 协议
本地 POSIX（ext4/xfs）单节点、临时 stagingrename() 同 FS 原子write to tmp → fsync → rename → fsync(parent)
并行 FS（Lustre/GPFS）多 rank 共享写、集群 NASPOSIX rename 语义同 POSIX，注意 MDS 元数据并发
对象存储（S3/GCS/OSS）长期归档、跨地域multipart + finalizemultipart upload → manifest PUT → marker key
S3 没有 rename：S3 的"rename"是 copy + delete，不是原子操作。把 POSIX checkpoint 协议直接移植到 S3 会出现 tmp 目录 key 存在但 manifest 未写入的中间状态。正确协议：所有分片 multipart upload 完成 → 写 manifest JSON（含所有分片 key、checksum、size）→ 写 checkpoint_latest marker key 指向该版本。

3. 同步 vs 异步 Checkpoint

3.1 同步保存的代价

同步 checkpoint 流程：all-reduce/step 完成 → 所有 rank 停下来 → 序列化 state_dict → 写盘 → 所有 rank 确认写完 → 继续训练。

GPU idle 时间 = 序列化时间 + I/O 时间。175B BF16 参数 ~350 GB，FP32 Adam 状态 ~700 GB，共 ~1.05 TB。若 Lustre per-rank 写带宽约 2 GB/s，512 rank 并发，per-rank 写入量 ~2.1 GB，纯 I/O 约 1 秒，但序列化（safetensors 编码）和等待最慢 rank 的尾延迟往往让实际阻塞超过 60–300 秒。

3.2 异步 Checkpoint：DCP Async 模式

sequenceDiagram
    participant T as 训练线程
    participant C as CPU 内存 (pinned)
    participant W as 后台写线程
    participant S as 存储后端

    T->>C: copy tensors to CPU pinned memory (~20s)
    Note over T,C: GPU 立即恢复训练
    T-->>T: 继续 forward / backward
    C->>W: 触发后台写任务
    W->>S: serialize + write shards
    W->>S: write manifest
    Note over W,S: 与训练完全并行执行
方式GPU 阻塞时间CPU 内存额外占用实现复杂度
同步（blocking）序列化 + I/O（1–10 分钟）无低
异步（DCP async）仅 CPU copy（10–30 秒）1 份训练状态中
异步 + 压缩仅 CPU copy压缩后约 50%高
异步 checkpoint 的 OOM 风险：async copy 会在 CPU 内存中持有训练状态的完整副本。175B BF16 + FP32 Adam ~1.05 TB，若节点 CPU DRAM 小于此量级，async 模式会 OOM。需评估节点 CPU DRAM 容量（通常 512 GB–2 TB/节点）并限制并行 checkpoint 任务数（通常上限 1–2 个）。
越大的集群越需要异步 checkpoint：1024 卡同步 checkpoint 每小时损失吞吐可达 38%，有效训练时间只有 62%。异步 checkpoint 是大规模训练的基础设施要求，不是可选优化。

4. DCP 原理：Planner、Writer、Reader、Metadata

PyTorch Distributed Checkpoint（torch.distributed.checkpoint，简称 DCP）是 PyTorch 2.x 推荐的分布式 checkpoint 方案，核心设计在于将"哪些数据由谁写/读"（planner）与"数据怎么写到存储"（writer/reader）解耦。

4.1 DCP 架构

flowchart TD
    A[训练状态\nstate_dict] --> B[SavePlanner\n拆解 WriteItem 列表]
    B --> C[StorageWriter\n并发写分片]
    C --> D[(存储后端\nLustre / S3)]
    D --> E[metadata.json\n逻辑 key → 物理 offset]

    F[(存储后端)] --> G[StorageReader\n按需 seek 读取]
    G --> H[LoadPlanner\n分配 tensor 到新 rank]
    H --> I[训练状态\n恢复完毕]

    subgraph 保存路径
        A --> B --> C --> D
    end
    subgraph 恢复路径
        F --> G --> H --> I
    end

4.2 Planner 的逻辑 key 解耦设计

SavePlanner 把 state_dict 中的每个 tensor 拆解成 WriteItem 列表，每个 item 包含：tensor 逻辑 key（不依赖 rank）、storage key（物理文件/prefix）、写入的字节范围（offset + length）、tensor metadata（shape、dtype、stride）。

关键：逻辑 key 与物理 rank 解耦。同一个逻辑参数（如 transformer.layer.0.attn.weight）在不同 rank 数配置下可以有不同的物理分片，但 planner 记录的是逻辑 key 和 byte range，不记录"rank N 写了哪些"。这是 DCP 能支持 reshard 的根本原因。

4.3 Reshard：rank 数变化时的处理

flowchart LR
    subgraph 原始 512 rank
        direction TB
        R1[rank 0 shard A]
        R2[rank 1 shard B]
        R3[... ...]
        R512[rank 511 shard ZZ]
    end
    subgraph metadata.json
        M[key → offset → length\n与 rank 无关]
    end
    subgraph 恢复 256 rank
        direction TB
        N1[新 rank 0\n加载 shard A+C+...]
        N2[新 rank 1\n加载 shard B+D+...]
    end
    R1 --> M
    R512 --> M
    M --> N1
    M --> N2
Reshard 的边界条件：Tensor Parallel 和 Pipeline Parallel 的分片布局不是 DCP 内置的，需要 planner 的自定义 transform_state_dict 钩子处理。如果 TP size 或 PP size 同时改变，还需要额外的参数重组逻辑，不是 DCP 开箱即用能处理的。

一个完整的 checkpoint 元数据不只是 step 和版本号，而是把"恢复时需要的所有判断条件"全部记录：

7. 原子提交：POSIX vs 对象存储

7.1 POSIX 原子提交协议

sequenceDiagram
    participant R as 所有 Rank
    participant T as ckpt_tmp_step52000/
    participant F as ckpt_step52000/
    participant P as parent dir

    R->>T: 写 rank_N.pt 到 tmp 目录
    R->>T: fsync(rank_N.pt)
    Note over R: barrier：等所有 rank 写完
    R->>T: rank 0 写 manifest.yaml
    R->>T: fsync(manifest.yaml)
    R->>F: rename(tmp → 正式目录)
    R->>P: fsync(parent dir)
    Note over F: 整版 checkpoint 原子对外可见
    R->>F: 更新 latest 软链接
    R->>F: fsync(软链接所在目录)

关键点：(1) rename() 在同一文件系统内是原子操作（POSIX 保证）；(2) 必须 fsync(parent dir) 才能保证目录项在断电后持久化；(3) 跨挂载点 rename 不是原子操作，不能跨 NFS 挂载做 checkpoint。

7.2 对象存储原子提交协议

sequenceDiagram
    participant R as 所有 Rank
    participant S as S3 Bucket
    participant M as Manifest Key

    R->>S: multipart upload rank_N.pt (每 part 100–200 MB)
    R->>S: complete_multipart_upload（服务端原子）
    Note over R: barrier：等所有 rank upload 完成
    R->>M: rank 0 PUT manifest.json（含所有分片 key + sha256）
    R->>S: rank 0 PUT ckpt_latest = "step52000"
    Note over S: marker key 写入后，版本对外可见
S3 版本化可防止覆盖：开启 S3 Bucket versioning 后，即使 manifest 被意外覆盖，旧版本仍可恢复。建议在 checkpoint bucket 上开启 versioning 并设置 Object Lock，防止误删。
LIST prefix 不是事务边界：不要用 s3 ls s3://bucket/ckpt_step52000/ 判断 checkpoint 是否完整，LIST 看到的文件可能来自多个并发写入操作的混合状态。必须用 manifest 的存在性和内容作为完整性判断。

8. Checkpoint 频率决策模型

8.1 从故障率反推最优频率

设 λ = 集群故障率（次/小时），T = checkpoint 间隔（小时），t_save = 每次 checkpoint 耗时（小时）。期望进度损失成本：

E[loss] = λ × C × T²/2

对 T 求导取极小值，近似最优间隔：

T* = sqrt(2 × t_save / λ)
场景λ（次/小时）t_save（分钟）T*（分钟）吞吐损失
512 卡 H100（同步）0.21044~23%
512 卡 H100（异步）0.20.510~5%
1024 卡 H100（同步）0.41539~38%
1024 卡 H100（异步）0.40.55~10%

8.2 频率决策表

9. Retention 策略

flowchart TD
    CK[新 checkpoint 写入] --> R[Rolling 保留\n最近 N 个]
    CK --> M[Milestone 保留\n固定 step 快照]
    CK --> B[Best 保留\n最低 val loss]

    R --> DEL1[超出 N 个时\n删除最老 rolling ckpt]
    M --> ARCH1[永久保留\n可归档到冷存储]
    B --> DEL2[新 best 出现\n降级旧 best]

    DEL1 --> CHK[检查 Registry\n是否被引用]
    CHK --> SKIP[仍在引用\n跳过删除]
    CHK --> EXEC[无引用\n执行删除]
保留类型数量触发删除条件绝对不删条件
Rolling最近 3–5 个超出数量仍有 eval job 引用
Milestone固定 step 快照（100K/200K/...）不自动删除永久保留
Best1–3 个新 best 出现已发布到 production
不要按文件年龄删除 checkpoint：age-based 删除会同时误删 milestone 和 best checkpoint。必须按类型 + registry 引用状态做决策，否则可能删掉唯一能恢复的版本。

9.1 磁盘估算（175B 示例）

175B BF16（~350 GB）+ FP32 Adam（~700 GB）= ~1.05 TB/ckpt。保留最近 5 个 rolling + 5 个 milestone + 1 个 best = 11 个，磁盘占用：11 × 1.05 TB ≈ 11.55 TB（仅 checkpoint，不含日志和 eval 结果）。

10. Selective Checkpoint 与 LoRA Delta

类型保存内容大小（175B）用途
Full checkpoint所有参数 + optimizer + RNG~1.05 TBTrue resume
权重 only仅模型参数（BF16）~350 GB推理 / 评测
LoRA delta仅 LoRA 参数（A/B 矩阵）~50–500 MBSFT/RLHF 快速保存
Activation checkpoint中间激活（不持久化）取决于 recompute 策略节省显存
LoRA delta checkpoint 注意事项：保存 LoRA delta 时，必须同时记录 base model 版本 hash，否则 delta 和 base 不对应，恢复后权重损坏。RLHF 多模型 checkpoint 场景（Policy + Reward + Reference 模型同时训练）需要在 manifest 中记录所有模型的 step 对应关系，保证三个模型状态一致。

11. 大模型 Checkpoint 实践：100B+ 规模

11.1 并行上传设计

175B 模型在 512 卡上，每次 checkpoint 后向 S3 上传约 1.05 TB：每个 rank 独立上传自己的分片（~2.1 GB/rank），512 rank 并发上传，每个 rank 并发 4 个 multipart part，有效并发 2048 个 upload stream。若 S3 带宽约 50 GB/s，上传时间约 21 秒（理论），加上序列化和 manifest 写入，实际约 30–60 秒。

并行上传的工程关键：(1) 每个 rank 上传自己的分片，不让 rank 0 聚合；(2) 使用 multipart upload，每 part 100–200 MB，允许失败重传；(3) upload 失败后有重试队列，不是整版 checkpoint 重新开始；(4) manifest 只在所有分片 upload 成功后才写入。

11.2 网络带宽与时间估算

操作数据量（175B FP16+FP32 Adam）理想时间（50 GB/s）实际时间
同步写 Lustre（512 rank 并发）1.05 TB~21 s60–300 s
异步写 Lustre（CPU copy）GPU 阻塞仅 copy10–30 s（GPU block）后台继续 60–300 s
上传 S3（512 rank 并发）1.05 TB~21 s30–60 s
Integrity check（sha256）per rank ~2.1 GBper rank ~2 s并发，整体 5–10 s

11.3 文件系统选型对 Checkpoint 的影响

文件系统Checkpoint 写入性能元数据开销推荐角色
ext4/xfs（本地 NVMe）高（3–7 GB/s/node）低异步 checkpoint 的 CPU-side staging
Lustre高（聚合 100s GB/s）MDS 是瓶颈集群共享 checkpoint 主存储
GPFS/Spectrum Scale高，小文件更优低替代 Lustre 的企业选择
NFS低（~1 GB/s）高不推荐大规模 checkpoint
S3/GCS中（弹性）无 POSIX长期归档，不做训练时主存储

12. Resume 策略

策略从哪个 checkpoint 恢复适用场景
from-last最新提交的 checkpoint故障后自动恢复（最常见）
from-bestval loss 最低的 checkpoint过拟合后回退
from-step N指定 step 的 checkpoint消融实验、分支训练
from-scratch不加载 checkpoint重新训练
resume 后必须验证训练语义：恢复后的前几个 step，应检查 loss 是否平滑衔接（不出现突变）、global step 是否正确、学习率是否按 scheduler 继续（不从头 warmup）、data sampler 是否从正确位置继续（不重复或跳过）。这些检查应该是自动化脚本，而不是人工目测 loss 曲线。

13. 与 Model Registry 集成

flowchart LR
    A[checkpoint 写入完成\nmanifest committed] --> B[注册到 Registry\n含 step / val_loss / metadata]
    B --> C{触发评测 job\n验证集 ppl / 基准集}
    C --> |通过| D[状态: validated\n标记为候选]
    C --> |失败| E[状态: failed\n保留但不升级]
    D --> F{发布门禁\n人工审批或自动}
    F --> |通过| G[状态: staging\n灰度流量]
    G --> H[状态: production\n全量]
    H --> |需回滚| B
checkpoint 转模型包：validated 状态的 checkpoint 可以被转换为"模型包"：提取纯权重（BF16，去掉 optimizer state），打包 tokenizer、config、推理适配层，发布到 serving registry。转换不应直接修改 checkpoint 本身，而是派生出一个独立的 model package artifact。详见 第 12 章 · 制品管理。

14. Worked Example：175B / 512×H100 端到端 Checkpoint 流水线

14.1 场景设定

参数值
模型175B LLaMA-3 变体，BF16 权重
集群512 × H100-80GB，64 节点 × 8 卡
并行配置TP=8, PP=4, DP=16
BF16 权重大小175B × 2 bytes = 350 GB
FP32 Adam 状态175B × 4 bytes = 700 GB（一阶+二阶矩）
总 checkpoint 大小~1.05 TB
训练速度~3,500 tokens/s/GPU × 512 = 1,792,000 tokens/s
checkpoint 频率每 60 分钟（约 6.4B tokens）
故障率 λ~0.2 次/小时（512 卡集群经验值）

14.2 端到端流程

Step 1：触发异步 checkpoint（training step 完成后）

# 每 N step 或每 T 秒触发
if should_checkpoint(step, last_ckpt_time):
    # GPU 阻塞：把所有 tensor copy 到 CPU pinned memory
    cpu_state = copy_to_cpu(model, optimizer, scheduler)  # ~20s
    # 启动后台任务，训练立即恢复
    ckpt_future = async_ckpt_pool.submit(
        save_checkpoint,
        cpu_state,
        step=step,
        tokens_seen=tokens_seen,
    )
    training_resumes()  # GPU 立即继续

GPU 阻塞时间：约 20–30 秒（CPU pinned memory copy，带宽约 30–50 GB/s）。

Step 2：后台序列化 + 写 Lustre

DCP SavePlanner 把 state_dict 拆成 512 个 WriteItem，每个 rank 写约 2.1 GB 到 ckpt_tmp_step52000/rank_XXXX.pt，Lustre stripe count=64，有效写带宽约 2 GB/s/rank，序列化+写盘约 60–120 秒（与训练并行）。

Step 3：Barrier + Manifest + POSIX rename

dist.barrier()  # 所有 rank 写完后 barrier
if rank == 0:
    manifest = compute_manifest(ckpt_tmp_dir)  # 计算所有分片 sha256
    write_manifest(manifest, f"ckpt_tmp_step{step}/manifest.yaml")
    fsync(manifest_file)
    os.rename(f"ckpt_tmp_step{step}", f"ckpt_step{step}")
    fsync(parent_dir)
    update_symlink("latest", f"ckpt_step{step}")

Step 4：并行上传 S3（Lustre → S3 归档）

512 rank 并发启动 S3 multipart upload，每个分片约 2.1 GB，分成 21 个 100 MB part。有效上传带宽：64 节点 × 25 Gbps ≈ 200 GB/s，上传时间约 5.25 秒（理论），实际约 20–40 秒。上传完成后 rank 0 写 S3 manifest + marker key。

Step 5：Integrity Check

# 每个 rank 验证自己的分片
local_sha256 = sha256(f"ckpt_step{step}/rank_{rank:04d}.pt")
assert local_sha256 == manifest["shards"][rank]["sha256"]

# rank 0 验证所有 S3 分片 ETag
if rank == 0:
    for shard in manifest["shards"]:
        verify_s3_etag(shard["key"], shard["md5"])

Step 6：更新 Registry + 触发 Eval

if rank == 0:
    registry.register(
        checkpoint_id=f"ckpt-step-{step}",
        step=step,
        tokens_seen=tokens_seen,
        val_loss=eval_result.loss,
        manifest_s3_path=f"s3://ckpt-bucket/ckpt_step{step}/manifest.yaml",
        status="committed",
        tags=["rolling"],
    )
    eval_queue.submit(checkpoint_id=f"ckpt-step-{step}")

Step 7：Retention 清理

rolling = registry.list(tags=["rolling"], sort="step")
if len(rolling) > 5:
    oldest = rolling[0]
    if not registry.is_referenced(oldest.checkpoint_id):
        delete_checkpoint(oldest)
        registry.mark_deleted(oldest.checkpoint_id)
