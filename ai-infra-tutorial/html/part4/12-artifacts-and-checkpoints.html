1. 第一性原理拆解：从文件到平台对象

拆 — 不可化简的问题

剥离 MLflow、Weights & Biases、S3、Model Registry、checkpoint manager 这些工具名之后，本章要解决的不可化简问题只有一个：训练和发布会产生很多文件，但平台真正需要管理的不是“文件存在”，而是“某个结果是否有完整证据链，能否恢复、验证、发布、回滚和审计”。文件系统只能回答路径下有没有字节；对象存储只能告诉你某个 key 是否存在；训练框架只能在局部上下文里知道某些 tensor、optimizer state 和 step 是否被写出。可是生产系统关心的是另一类问题：这个模型版本从哪份数据、哪段代码、哪个镜像、哪个训练任务而来？它的 checkpoint 能否 true resume？它的模型包是否包含 tokenizer、推理配置、签名和评测报告？它是否通过门禁，是否允许进入 staging，是否可以被生产流量路由，是否能在事故中作为回滚候选？

这个问题之所以不可再拆，是因为 AI 系统的输出天然是离散的、多副本的、跨系统流转的。一次训练可能每隔一小时写出 checkpoint，每个 checkpoint 又由多个 rank、多个 shard、多个 metadata 文件组成；一次发布可能需要权重、tokenizer、vocab、config、镜像 digest、部署 manifest、评测报告、安全扫描结果和审批记录同时匹配。一个 70B checkpoint 可以达到数百 GB 到数 TB；一次线上事故可能要求平台在 5 分钟内定位上一个 production 模型包并确认它和配置、tokenizer、镜像、评测报告彼此兼容。如果只是把结果按日期扔进 bucket，团队看似保存了所有文件，实际上无法证明哪个版本完整、哪个版本通过门禁、哪个版本可以恢复，甚至无法证明线上跑的模型是不是训练报告里说的那一版。

因此，制品管理的第一性问题不是容量，而是判定性。容量回答“放不放得下”，判定性回答“这个版本是不是一个可用对象”。平台需要把一堆离散文件提升为可查询、可比较、可流转、可治理的 artifact。这个 artifact 不只是路径集合，而是带有元数据、状态、血缘、校验、权限、审计和生命周期的控制面对象。只有当平台能基于这些对象自动触发评测、发布、回滚和清理时，训练输出才真正进入工程系统。

推 — 从这个问题如何推导出每个机制

如果结果需要证明来源，就必然需要元数据。代码 revision、数据集版本、训练 job id、配置、step、rank 分片、镜像 digest、评测报告、安全扫描结果和审批记录必须绑定到同一个 artifact 版本，否则训练、评测和部署之间只能靠人工猜测。没有元数据时，“当前线上跑的是哪个版本”会退化成查目录名；“它比上一版好在哪里”会退化成翻聊天记录；“能否回滚”会退化成临时下载一批旧文件试运行。

如果结果需要恢复，就必然要区分 checkpoint 和模型包。Checkpoint 面向训练恢复，必须保存模型参数、优化器状态、scheduler、当前 step、随机数状态、sampler 进度和并行分片布局；模型包面向部署，必须保存可加载权重、tokenizer、模型签名、推理配置、依赖环境和版本元数据。把两者混用会同时伤害训练和发布：恢复时发现缺 optimizer 或 RNG 状态，部署时发现包过大、依赖过重、包含训练态私有结构，甚至 serving runtime 无法加载。

如果结果需要自动发布，就必然需要生命周期状态。draft、validated、staging、production、deprecated 不只是标签，而是发布系统、权限系统、路由系统、审计系统和清理系统共同消费的控制面字段。一个版本从 draft 进入 validated，意味着它通过了固定评测和一致性检查；进入 production，意味着流量路由和审计记录已经落地；进入 deprecated，意味着它不能再被新流量选中，但可能仍要保留一段时间用于回滚和复盘。

如果结果需要跨系统流转，就必然需要 registry 或 metadata plane。对象存储适合保存大对象，但它不知道某个目录是否代表完整版本；CI/CD 不天然知道哪个 checkpoint 通过评测；Serving 平台不应靠人工表格判断 tokenizer 是否匹配。Registry 把“字节”提升成“对象”，提供索引、关联、状态、权限和审计。底层存储解决另一层问题：POSIX FS 适合临时 staging；并行文件系统适合集群共享的大 checkpoint；对象存储适合归档和分发。故障后恢复可信，还要依赖 manifest、校验和、临时文件、原子 rename、父目录 fsync、对象存储 immutable key、评测门禁和回滚候选选择。整章的机制因此都从同一件事推出：平台必须把训练输出从“文件集合”变成“有判定边界的版本对象”。

2. 学习目标与核心判断

模型训练不是只产生一个最终权重文件；真正需要平台管理的，是一整组能证明结果来源、支持恢复并支撑发布决策的工件。完成本章学习后，你应该能够区分 checkpoint、模型包、评测报告、配置和日志等不同制品，理解为什么工件管理是训练和发布之间的桥梁，并设计一套可追踪的模型版本与状态管理方式。

关联章节：本章讨论的 checkpoint、模型包和回滚链路，与 第 10 章的训练恢复机制直接相连；恢复能否成功，取决于制品是否被平台正确登记和保留。
训练侧
关注 step、rank、optimizer state、RNG、sampler、并行布局，以及 checkpoint 是否完整可恢复。
发布侧
关注权重、tokenizer、推理配置、镜像、评测报告和审批记录是否属于同一个版本。
平台侧
关注索引、状态、权限、审计、清理和回滚候选选择是否能自动执行。
核心判断：模型“可下载”不等于模型“可发布”；checkpoint“存在”不等于 checkpoint“可恢复”。平台必须让这些判断从人工经验变成系统字段和门禁规则。

3. 什么算制品

AI 平台中的制品通常包括 checkpoint、最终模型包、tokenizer / vocab、评测报告、训练配置、实验日志、embedding 索引、推理镜像与部署清单。它们共同构成了“模型是怎么来的、现在能不能上线、失败后能不能恢复”的证据链。

制品主要消费者回答的问题
Checkpoint训练平台、恢复逻辑训练能否从某个 step 正确继续？
模型包Serving 平台、发布系统模型能否被加载、路由和回滚？
Tokenizer / vocab训练、评测、推理输入输出切分是否和权重匹配？
评测报告发布门禁、模型治理版本是否比 baseline 更好且满足安全要求？
训练配置与日志复现、排障、审计版本从什么配置和环境产生？
镜像与部署清单CI/CD、Serving 编排运行环境和发布拓扑是否可复现？

如果这些制品只是散落在对象存储里，那么平台就很难回答线上跑的是哪个版本、它对应哪次训练、它是否通过评测，以及出故障后该回滚到哪一个版本。

    A[训练任务] --> B[Checkpoint]
    A --> C[训练配置和日志]
    A --> D[评测候选]
    D --> E[评测报告]
    B --> F[模型包构建]
    C --> F
    E --> G[Registry版本对象]
    F --> G
    G --> H[Staging发布]
    H --> I[Production]
    I --> J[回滚候选]

4. Checkpoint 和模型包的边界

Checkpoint 面向训练恢复，往往包含模型参数、优化器状态、scheduler 状态、当前 step / epoch、随机数状态、sampler 进度和并行分片布局。模型包面向部署，通常更关注可加载权重、推理配置、tokenizer、模型签名、版本元数据和依赖环境。

对象目标典型内容混用后的问题
Checkpoint训练恢复参数、优化器、scheduler、step、RNG、sampler、shard layout拿去部署时包过大、依赖训练框架内部结构、serving 无法加载
模型包部署与回滚权重、tokenizer、config、签名、镜像 digest、评测与发布元数据拿去恢复时缺 optimizer、RNG、数据进度，loss 曲线不可解释
设计原则：成熟平台会把“训练恢复资产”和“部署资产”视为相关但不同的对象：它们共享血缘和版本关系，但生命周期、保存频率、权限、清理策略和消费者都不同。

    A[训练状态] --> B[Checkpoint]
    A --> C[模型导出]
    B --> D[恢复训练]
    B --> E[评测候选选择]
    C --> F[模型包]
    E --> F
    F --> G[Serving加载]
    F --> H[灰度发布]
    F --> I[生产回滚]
    B -. 不直接作为生产包 .-> G

5. 最小版本元数据

一个可运营的 artifact 版本至少要把模型名、版本、数据集版本、代码 revision、训练任务、评测报告、镜像和状态绑定在一起。没有这类元数据时，你无法可靠回答当前线上跑的是哪个版本、它对应哪次训练、它是否通过评测，以及它能否快速回滚。

artifact:
  model_name: reranker
  model_version: 2026-04-10-rc1
  dataset_version: support-v3
  code_revision: abc1234
  training_job: train-20260410-001
  eval_report: eval-20260410-001.json
  image: serving-reranker:2026-04-10-rc1
  status: staging
字段为什么需要缺失风险
dataset_version证明训练输入来源效果变化无法解释，复现困难
code_revision绑定训练代码与导出逻辑同名权重可能来自不同实现
training_job串起日志、指标、checkpoint 和审批排障时只能靠人工查找
eval_report支撑发布门禁与 baseline 对比上线变成未验证发布
image锁定推理运行环境权重正确但 runtime 不兼容
status作为控制面状态发布、清理、回滚规则无法自动化
最小而不是随意：元数据字段不需要一开始就覆盖所有治理需求，但必须足以跨越训练、评测、部署和回滚四个系统边界。

6. 生命周期状态

一个模型版本至少可以有 draft、validated、staging、production、deprecated。这些状态不是形式化文档，而是平台控制面的一部分。它们直接影响谁能发布、哪个版本能被流量路由、哪个版本能被回滚选中、哪些工件可以清理。

stateDiagram-v2
    [*] --> draft: 训练或导出完成
    draft --> validated: 离线评测通过
    draft --> deprecated: 评测失败或人工废弃
    validated --> staging: 发布门禁通过
    staging --> production: 灰度放量完成
    staging --> deprecated: 灰度失败
    production --> deprecated: 新版本替换且保留窗口结束
    deprecated --> [*]
状态允许动作禁止动作
draft补充 metadata、触发评测、删除临时失败版本直接接生产流量
validated进入 staging、生成发布候选绕过镜像和配置一致性检查
staging灰度、压测、回滚演练被清理系统删除
production接生产流量、作为回滚基线无审计修改关键文件
deprecated保留审计、在窗口后归档或清理成为新发布候选
严重风险：把生命周期状态写在人工表格里，等于让发布系统、路由系统和清理系统各自猜测真相。事故时最容易出现“旧版本被清掉了”或“未评测版本被路由了”。

7. Registry 的真正价值

很多人会问：“对象存储里已经有文件了，为什么还需要 registry 或管理系统？”原因在于管理系统解决的不只是“放文件”，而是索引、关联、状态、权限和审计。也就是说，制品管理系统的价值是让“文件”变成“平台对象”。

索引
按模型、版本、状态、训练任务、数据集和评测结果快速查找。
关联
把训练、评测、部署、反馈、回滚和审计串成证据链。
状态
让发布系统消费 validated、staging、production 等控制面字段。
权限
控制谁能读、谁能发、谁能改状态、谁能删除长期保留版本。
审计
记录谁在什么时候把哪个版本推进到哪个状态。
清理
基于状态、引用和保留策略清理，而不是只按文件年龄删除。
flowchart LR
    A[对象存储中的字节] --> B[Manifest与校验和]
    B --> C[Registry版本对象]
    D[训练元数据] --> C
    E[评测报告] --> C
    F[镜像和部署清单] --> C
    C --> G[发布系统]
    C --> H[回滚系统]
    C --> I[审计系统]
    C --> J[清理系统]

8. 文件都在但无法回滚

这类事故通常来自 checkpoint 和模型包命名不一致、线上版本没有记录对应评测结果、镜像版本和模型版本脱节、回滚时发现 tokenizer 或配置文件不匹配。它说明一个重要事实：回滚不是“把旧文件拷回来”，而是让一整组彼此兼容的制品重新组成一个可运行系统。

失败模式：如果 production 只记录了 s3://models/reranker/latest/，而不是不可变版本、manifest、镜像 digest 和评测报告，那么 latest 被覆盖后，所谓“回滚”可能回到一个从未评测过的组合。
表面现象真实缺口平台修复
旧权重还在 bucket不知道对应 tokenizer 和 config模型包 manifest 绑定全部运行资产
有 checkpoint缺 optimizer / RNG / sampler，不能 true resumecheckpoint schema 和校验规则
评测报告存在没有绑定模型 digest 和数据版本评测报告引用不可变 artifact id
镜像可以拉取镜像与权重版本脱节发布候选绑定 image digest
目录名看似是旧版目录可被覆盖或半写入immutable key + manifest 提交
回滚候选选择：优先选择最近一个 production 或通过灰度的 validated 版本，并要求模型包、tokenizer、config、镜像、评测报告和审批记录全部可校验。

9. 存储后端怎么选

制品管理首先是对象治理，其次才是“放在哪里”。更稳妥的理解是：底层存储和上层 registry / metadata plane 是两层不同能力，前者负责放大文件，后者负责版本、状态和审计。

层优势局限适用规模
本地 NFS / NAS接入简单，训练集群共享方便跨地域差、扩容与审计能力弱小团队、单机房
对象存储（S3 / GCS / MinIO）容量弹性大，适合 checkpoint 和模型包归档目录语义弱，需额外做索引和状态管理中大规模平台
Artifact Registry / Metadata Plane（MLflow、W&B 等）自带版本、状态、实验关联本身通常仍要依赖对象存储或共享存储承载大文件需要审计与门禁的团队

平台上常见的组合是：大文件放对象存储，元数据和生命周期状态放 registry。这样既保留了弹性容量，也能让发布系统直接消费“哪个版本可用”的控制面信息。

flowchart TB
    A[训练集群本地或并行FS] -->|快速写入checkpoint| B[临时staging区]
    B -->|校验通过| C[对象存储归档]
    C -->|immutable URI和checksum| D[Registry]
    D --> E[评测系统]
    D --> F[Serving平台]
    D --> G[清理与保留策略]
    E -->|状态更新| D
    F -->|发布记录| D
边界提醒：不要让 serving 平台直接扫描对象存储目录选择模型。它应该消费 registry 中经过门禁的版本对象，否则会把目录命名、上传顺序和人工约定当成发布协议。

10. Checkpoint 文件系统语义

Checkpoint 写入比普通制品上传更接近文件系统语义问题，底层差异可参考 §0c 文件系统与存储内核。POSIX FS 适合写临时文件、fsync(file)、同目录 rename() 成正式文件，再 fsync(parent dir)；工程边界是 write() 成功不等于落盘，rename() 成功不等于父目录已持久化，跨挂载点 rename 也不是原子替换。

并行文件系统适合多 rank 写 10GB-100GB 级 shard，通过 stripe 聚合带宽，但小文件、频繁 stat/open、单目录并发会打 MDS。对象存储适合归档和跨地域保留，但 S3/OSS 不是 POSIX：没有本地 fsync，rename 往往是 copy+delete，LIST prefix 不能当事务边界；可靠协议应改成 immutable key + manifest。

后端适合放什么关键语义工程边界
本地 POSIX FS临时 staging、单节点 checkpointfsync、同 FS rename 原子可见节点丢失会丢本地副本，需异步归档
并行 FS多节点共享 checkpoint、大 shardstripe 聚合带宽、POSIX 路径语义MDS 和小文件是上限，需压测目录并发
对象存储长期归档、发布分发、跨区域保留PUT 完成、multipart、manifest非 POSIX，不能依赖 rename/fsync/list 事务
sequenceDiagram
    participant R as Rank/Writer
    participant S as Staging FS
    participant O as Object Store
    participant M as Registry
    R->>S: 写临时 shard
    R->>S: fsync(file) 并 rename
    R->>S: fsync(parent dir)
    R->>O: 上传 immutable shard key
    R->>O: 上传 manifest 和 checksum
    O->>M: 登记 manifest URI
    M->>M: 校验齐全后标记 committed
提交协议：不要把“最后一个文件出现”当作完成信号。可靠做法是先写不可变 shard，再发布 manifest，由 registry 校验后推进状态。

11. 制品与 CI/CD 集成

制品真正发挥作用，是在训练结束后继续沿着评测、审批和发布链路流动，而不是停留在某个 bucket 目录中。从平台工程角度看，关键不是自动化步骤多，而是状态流转要稳定。

训练完成
  -> 注册 checkpoint / 模型包
  -> 触发离线评测
  -> 写入版本状态与报告
  -> 发布系统读取 validated 版本
  -> 灰度 / 全量 / 回滚
阶段平台动作产出
训练结束上传制品并登记元数据可查询版本
自动评测运行基准集、生成报告validated 候选
发布门禁检查签名、配置、镜像一致性staging 或拒绝
正式发布流量切换与留痕production 版本
flowchart LR
    A[训练完成] --> B[注册制品]
    B --> C[离线评测]
    C --> D{门禁通过?}
    D -- 否 --> E[保持draft或deprecated]
    D -- 是 --> F[validated]
    F --> G[staging部署]
    G --> H{灰度健康?}
    H -- 否 --> I[回滚或废弃]
    H -- 是 --> J[production]
    J --> K[审计与保留]
工程边界：如果 CI/CD 不认识制品状态，训练、评测、发布就仍然是三套松散流程；一旦出故障，排障和回滚会重新退回手工比对文件名。

12. 工程建议与常见工具

  • 训练输出路径、评测结果、模型注册必须可关联。
  • Checkpoint 保存策略要和恢复流程一起设计。
  • 模型“可下载”不等于模型“可发布”。
  • 老工件必须有清理和归档规则。
  • 发布系统应直接消费工件状态，而不是靠人工表格同步。
概念常见工具 / 命令备注
模型与实验注册MLflow Model Registry、Weights & Biases Artifacts管理版本、状态和关联关系
大文件与对象存储同步aws s3 cp/sync、mc cp适合 checkpoint / 模型包上传归档
制品打包Hugging Face Hub、safetensors适合发布可加载模型资产
流水线编排GitHub Actions、Argo Workflows用于训练完成后的评测与状态流转
落地顺序：先统一不可变版本 ID、manifest、关键 metadata 和状态字段；再接入自动评测、灰度发布、审计和清理。没有稳定对象模型时，工具越多，证据链反而越分散。

13. 最低限度的制品分层

即使没有复杂平台，也建议至少区分 checkpoint、模型包、评测报告、配置和部署清单。这能显著减少后续恢复、审计和回滚时的混乱。

artifacts/
  checkpoints/
  model-packages/
  eval-reports/
  configs/
  deployment-manifests/
目录最低要求后续演进
checkpoints/包含 step、manifest、shard 校验和接入 checkpoint manager 和保留策略
model-packages/绑定权重、tokenizer、config、签名接入 model registry 和 serving 平台
eval-reports/引用不可变模型版本和评测集版本成为发布门禁输入
configs/保留训练和推理配置快照纳入审计与差异比较
deployment-manifests/记录镜像、资源、路由和环境接入灰度与回滚自动化
小团队策略：没有 registry 时，也至少用不可变目录名、manifest、checksum、状态文件和变更记录模拟控制面；不要让 latest 成为唯一事实来源。
