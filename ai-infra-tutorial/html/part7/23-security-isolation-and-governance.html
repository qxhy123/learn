1. 第一性原理拆解：安全、隔离与治理

拆 — 不可化简的问题

剥掉 Kubernetes、Vault、cosign、Trivy、OPA、SafeTensors 这些工具名以后，本章真正要解决的不可化简问题是：AI 平台把高价值资产、可执行产物、外部输入和多租户资源放进同一条自动化流水线里，任何一个边界被绕过，损失都可能从一次请求扩大成数据泄漏、模型泄漏、算力滥用或供应链污染。 传统 Web 服务的安全边界通常围绕 API、数据库和用户会话展开；AI 平台多出训练数据、RAG 语料、embedding 索引、模型权重、checkpoint、prompt 模板、Notebook 环境、训练镜像、推理镜像和日志样本。它们既是"数据"，又常常驱动"执行"：模型文件会被加载，Notebook 会拉取密钥，RAG 检索结果会影响工具调用，缓存结果可能跨租户复用，镜像层和 Python 依赖会在生产 Pod 里运行。因此本章开头的判断是：AI 平台的风险从来不只在"服务会不会挂"，还在"数据、模型、权限、成本和审计是否会一起失控"。

安全回答"什么不能被未授权访问或篡改"；隔离回答"故障和越权能否停在边界内"；治理回答"规则能否被平台自动执行、度量、追溯和修正"。这三个问题的结合，构成了 AI 平台区别于传统 Web 平台安全设计的核心。普通 Web 平台的"安全"主要在接口层；AI 平台的安全必须覆盖从数据入口到模型加载到推理输出到日志留存的全链路。

推 — 从这个问题如何推导出每个机制

从"资产流动必须可控"出发，首先必然推出身份与最小权限。训练任务、在线服务、评测流水线、数据处理 Job 和 Notebook 不能共享一个万能账号，因为共享账号让审计失效，也让单点泄露变成全平台泄露。于是需要服务身份、租户身份、短生命周期凭证、RBAC / ABAC、按数据集和模型仓库粒度授权。继续往下推，凭证本身变成高价值资产，所以需要 Secrets 管理：Secret 不能进代码、不能进镜像、不能进长期明文环境变量；它应按身份、租户、用途和 TTL 在运行时注入。

从"模型和 checkpoint 既是资产也是可执行输入"出发，必然推出模型安全。如果平台允许任何人把外部 .pt、.bin、.ckpt 权重直接 torch.load 到共享训练或推理环境，边界就已经被突破，因为 Python pickle 的目标是恢复对象，不是验证安全数据格式。于是需要模型准入、格式约束、哈希校验、签名、隔离转换、SafeTensors 默认化，以及加载阶段的低权限沙箱。RAG 和 Agent 又把外部文本接入模型决策，因此权限检查必须进入检索、上下文拼装、缓存 key、工具调用和日志脱敏链路。

从"生产运行的是构建产物而不是源码意图"出发，必然推出供应链安全。镜像、Python 依赖、CUDA 库、模型权重和评测数据都可能被篡改或漂移；如果部署系统只认 tag，不验证签名和 provenance，就无法区分官方构建、开发者本地构建和恶意上传。于是需要依赖锁定、SBOM、Trivy 扫描、cosign 签名、SLSA provenance、准入控制和例外流程。

LLM 服务面临的安全威胁还有一类传统 Web 没有的维度：自然语言本身成为攻击面。攻击者不需要发送畸形字节，只需构造能操纵模型行为的文本，就可能绕过访问控制、泄露敏感数据或让模型执行未授权操作。因此还必须推导出 Prompt Injection 防护、Jailbreak 缓解、Guardrails 体系和红队 CI 集成。

最后，从"多租户共享昂贵资源"出发，必然推出资源与故障隔离：GPU 配额、队列优先级、限流、预算、租户标签、日志隔离、索引隔离和故障域划分，都是为了让单个团队的实验、错误配置或滥用行为不拖垮公共平台。治理闭环则把这些机制串起来：规则定义、平台执行、指标与审计、异常发现、策略调整。没有闭环，安全规则会逐渐变成不可验证的口头约定。

2. AI 平台的攻击面比普通服务更宽

一个普通在线服务的关键安全面通常集中在：API 接口、数据库、用户认证。AI 平台则往往还包括训练数据、模型权重、checkpoint、镜像和依赖供应链、向量索引、prompt 模板、日志中的用户输入与模型输出。这意味着：哪怕服务本身没有宕机，平台也可能在数据泄漏、权限越界或供应链污染上出问题。

传统 Web 服务攻击面

  • API 接口
  • 数据库
  • 用户认证 / Session
  • 前端 XSS / CSRF
  • 网络层

AI 平台额外攻击面

  • 训练数据 / RAG 语料
  • 模型权重与 checkpoint
  • 镜像层与 Python 依赖
  • Notebook 执行环境
  • prompt 模板与 Agent 工具调用
  • 向量索引与检索缓存
  • 日志（含用户输入 / 模型输出）
边界提醒：AI 平台的权限设计不能只盯"谁能访问 API"，还要管谁能读训练数据、谁能下载模型、谁能构建索引、谁能看到完整日志。缺少其中任何一项，权限控制都是不完整的。

3. 数据与模型安全

主要模型安全威胁

平台不只是在保护"服务接口"，还在保护模型文件、训练数据和推理链路本身。下面这些威胁在 AI 平台里很常见，而且很多都发生在"加载模型"或"接入外部内容"这种容易被忽视的环节。

威胁典型方式平台侧防护思路失败条件
pickle 反序列化攻击直接对未知来源权重执行 torch.load，加载 .pt、.bin、.ckpt 时触发任意代码执行默认禁用不受信任的 pickle 权重；优先使用 SafeTensors；把权重转换放到无网络、低权限的隔离环境生产或共享训练环境可以直接 torch.load 外部下载的权重
模型中毒（data poisoning）恶意样本混入训练集、增量反馈集或 RAG 语料数据源分级、训练集审计、关键任务回归评测、标注链路留痕训练数据来源不明，或语料变更后没有回归评测就上线
模型提取（model extraction）通过 API 批量探测和蒸馏输出行为强鉴权、按租户限流、异常调用检测、输出策略限制、水印或蜜罐样本单个调用方可长期高频采样而不触发限流或审计
Prompt 注入用户输入或检索文档诱导模型泄露系统提示词、越权调用工具输入分层、检索内容净化、工具调用白名单、输出审查、上下文隔离模型可直接按外部文档指令调用高权限工具，或泄露系统提示词
严重风险：对平台来说，重点不是"承诺彻底消灭风险"，而是把这些高风险路径做成默认拒绝、默认隔离、默认审计。没有默认安全，安全规则会逐渐退化为纸面文档。

为什么 torch.load 风险高，SafeTensors 为什么更适合默认化

torch.load 底层依赖 Python pickle。pickle 的设计目标是恢复 Python 对象，不是安全传输格式，所以加载未知来源文件时，本质上是在执行对方提供的反序列化逻辑。

格式典型加载方式安全特征平台建议
Pickle / PyTorch 原生权重torch.load(...)可在反序列化时执行任意代码，不适合作为不受信任输入仅允许来自受信任构建链路；默认不直接进入生产推理
SafeTensorssafetensors loader只描述张量数据，不执行 Python 对象反序列化逻辑作为平台默认权重交换格式，更适合签名、校验和复现
工程边界：SafeTensors 只收窄"加载权重时执行任意 Python 代码"的风险，不保证模型没有后门、没有训练数据泄漏，也不保证输出安全。外部模型进入平台时，最小准入链路应包括来源登记、哈希记录、格式检查、隔离转换、基础评测和责任人确认；不应允许 notebook 直接把任意权重挂进生产模型仓库。

4. Secrets 管理：Vault 与 K8s Secret

AI 平台里的 secrets 往往比普通服务更多，因为训练、评测、拉取模型、访问数据库、调用外部大模型和对象存储都可能需要凭据，而且很多作业还是短生命周期 Pod。默认原则应该非常明确：

Secrets 不入镜像、不入代码、不入环境变量明文。环境变量经常通过 kubectl describe、错误栈、调试页面、进程转储和日志系统扩散出去。更稳妥的做法是运行时按任务注入，走文件挂载、sidecar 渲染或短时凭证。
Secret 类型AI 场景举例推荐注入方式失败条件
模型下载 TokenHuggingFace Token、私有模型仓库凭证Vault 动态注入、云 Secret Manager 临时读取、按 Pod 挂载文件Token 被写入基础镜像、公共 notebook 模板或共享环境变量
外部 API KeyOpenAI / Anthropic / 第三方检索 API KeyVault、云 Secret Manager、K8s Secret + External Secrets Operator 同步到运行时多个团队共享一个长期 API Key，或 Key 出现在日志与报错里
数据库 / 向量库凭证Postgres、MySQL、Milvus、pgvector、RedisVault 动态账号、短时密码、最小权限 DB 账户所有服务共享 root 账号，或凭证写死在 Helm values / notebook

Vault 实际工作机制

Vault 用 Auth Methods 验证身份，用 Secret Engines 存放或动态生成凭据，用 Lease & TTL 绑定凭据生命周期。

Auth Method适用工作方式
KubernetesK8s PodPod 用挂载的 ServiceAccount JWT 调 Vault 登录 API，Vault 用 K8s TokenReview API 验签 → 返回 Vault token
AppRoleCI/CD、传统 VMrole_id（半公开）+ secret_id（机密，每次轮换）换 Vault token
JWT/OIDCOAuth 集成把第三方 IdP 的 JWT/OIDC token 换 Vault token
AWS/Azure/GCP IAM云上 workload用 cloud metadata service 的 instance identity 换 Vault token

动态 secret 是 Vault 最有价值的功能：每次请求 /v1/database/creds/<role>，Vault 现场创建一个临时数据库账号，附带 lease_id 和 TTL。Pod 退出或 lease 到期后，Vault 自动 revoke，数据库账号消失——凭据和 client 生命周期绑定，无需轮换计划。

K8s Secret 在 etcd 中的实际存储

重要认知：K8s Secret 默认只是 base64 编码，不是加密。任何拿到 etcd 备份的人都能直接读所有 Secret。生产环境必须配置 EncryptionConfiguration（aescbc/aesgcm 或 KMS provider），并把 etcd 备份严格隔离。etcd 加密只对之后写入的 Secret 生效，已存在的 Secret 仍是明文，需要触发重写。

kubelet 注入路径：Pod 调度到节点后，kubelet 从 API Server 拿 Secret（API Server 调 KMS 解密），把明文 Secret 写到 tmpfs（内存文件系统，不落磁盘），再 mount 到容器路径。envFrom Secret 在 Pod 启动时一次性读入，Secret 改了不重启 Pod 则继续用旧值——这是 envFrom 最大的隐患。

常见事故发生方式平台侧预防
Secret 泄露到日志应用启动打印环境变量、异常栈回显请求头日志脱敏、启动脚本禁止 env 输出、敏感字段统一 redact
Secret 硬编码到 notebook为了图快把 Key 写进 .ipynb、.py 或示例配置预提交扫描、仓库 secret scanning、最小示例不带真实凭据
Secret 打进镜像在 Dockerfile ARG / ENV、构建缓存或基础镜像中固化凭据构建阶段禁用真实 Secret，改为运行时注入；镜像扫描检查敏感字串

5. 供应链安全加固

AI 平台往往依赖大量镜像、Python 包和系统库。供应链加固的目标不是"把流程变重"，而是让关键产物能被追溯、验证和复现。对 AI 平台来说，供应链不只包括镜像和 Python 包，也包括模型权重、checkpoint、基础数据处理镜像和 notebook 依赖。

控制点最小做法失败条件
镜像签名验证使用 cosign 对基础镜像和业务镜像签名，并在部署前校验签名任意来源的镜像只要 tag 对得上就能部署
依赖锁定使用 requirements.lock、poetry.lock、uv.lock 等锁定解析结果pip install -r requirements.txt 每次解析结果可能不同
漏洞扫描在 CI 和镜像入库阶段运行 Trivy，对基础镜像和依赖做扫描漏洞扫描只出报告不阻断，或扫描结果无人处理
构建 provenance采用 SLSA 思路记录构建来源、构建器、输入和产物 provenance产物来源不明，无法区分官方构建与手工上传
模型与权重准入把模型文件也纳入签名、哈希校验、来源登记权重来源不明，或外部模型可绕过准入直接进入训练/推理集群

三者分工不能互相替代：Trivy 暴露已知漏洞和配置风险；cosign 让产物在部署前可验证"确实由可信身份签过"；SLSA provenance 描述"由哪个源码、哪个构建器、哪个流水线输入生成"。有签名但没扫描的镜像可能带着 Critical 漏洞；扫描通过但没有签名的镜像可能被替换；签名和扫描都有但没有 provenance 的产物，事后仍很难解释来自哪个提交。

flowchart LR
  A[源码 / Dockerfile / 依赖锁文件] --> B[CI 构建]
  B --> C[生成 SBOM]
  C --> D[Trivy 扫描镜像与依赖]
  D --> E{漏洞阈值通过?}
  E -- 否 --> F[阻断发布并记录豁免申请]
  E -- 是 --> G[cosign 签名镜像与模型产物]
  G --> H[生成 SLSA provenance]
  H --> I[推送制品仓库 / 模型仓库]
  I --> J[集群准入验证签名和 provenance]
  J --> K[部署训练 / 推理工作负载]
最佳实践：第一阶段目标不是追求最高 SLSA 等级，而是做到生产产物"不可手工绕过、可验证、可追溯"。先把未签名镜像、未登记模型和无锁文件依赖挡在生产外。latest tag、临时 notebook 镜像、本地手工 build 和外部模型直传都应视为绕行路径；紧急例外必须有 TTL、责任人、审计记录和事后补签/补扫描。

OPA、Gatekeeper、Kyverno：把策略变成集群默认行为

策略执行需要接入 Kubernetes admission webhook 链路。MutatingAdmissionWebhook 先执行（可改对象，如注入 sidecar、加 label），ValidatingAdmissionWebhook 后执行（只能 allow/deny）。OPA Gatekeeper 和 Kyverno 的 policy violation 在 Validating 阶段返回 deny。

维度OPA GatekeeperKyverno
学习曲线高（Rego 是新语言）低（K8s 工程师都会写 YAML）
表达能力极强（图灵完备）中（针对 K8s 场景够用）
Mutation 支持有限（主要做 validation）强（YAML 原生）
可移植性跨 K8s/Terraform/Envoy/CICDK8s only
选型建议：新团队、policy 量少、纯 K8s 场景选 Kyverno，开箱即用；已有 OPA 体系、跨平台 policy（CICD + Terraform + Envoy）、复杂逻辑选 OPA Gatekeeper。failurePolicy 必须配 Fail（安全优先），同时给 webhook 配 HA（≥2 replicas + PDB）避免 webhook 抖动导致整个集群 admission 卡死。

6. 隔离层次与治理闭环

AI 平台里的隔离至少有四层，很多平台只做了第一层，后面三层依然靠约定维持，这通常是不够的。

四层隔离

  1. 身份隔离：谁能提交任务、访问模型、调用服务
  2. 资源隔离：谁最多能占多少 GPU、显存和队列容量
  3. 数据隔离：谁能访问哪些数据集、索引、日志
  4. 故障隔离：一个租户或模型故障不会拖垮全平台

治理闭环

治理不是加几条审批流就结束，它需要闭环：

规则定义 → 平台执行 → 指标与审计 → 异常发现 → 策略调整

如果缺少"平台执行"和"审计证据"，治理最终仍会变成人工流程。

平台默认原则：治理要变成平台默认规则，而不是"大家记得遵守"。审批只是治理的一部分，真正关键的是规则是否能被执行和审计。

7. RAG 与多租户场景的特别风险

RAG 特别容易出的问题包括：用户检索到了本不该访问的文档；缓存复用了不该共享的结果；向量索引版本和权限规则不同步。这些问题和 第 13 章 的向量索引、缓存设计直接相连：检索快不代表权限就对，cache hit 更不能绕过租户和文档级别授权。

flowchart LR
  USER[用户请求] --> AUTH[鉴权网关\n身份验证]
  AUTH --> CACHE{缓存命中?}
  CACHE -->|命中| PERM_CHECK[权限二次检查\n缓存 key 含租户 ID]
  CACHE -->|未命中| RETRIEVAL[向量检索\n带租户过滤]
  RETRIEVAL --> DOC[文档片段\n含来源和权限级别]
  DOC --> CONTEXT[上下文拼装]
  PERM_CHECK -->|通过| CONTEXT
  PERM_CHECK -->|越权| BLOCK[拒绝返回]
  CONTEXT --> LLM[LLM 推理]
  LLM --> OUTPUT[脱敏输出\n日志打标]
多租户常见问题：一个租户刷爆推理资源；低优先级实验拖慢高优先级服务；成本无法归因，治理无从下手。解决方案：按租户配额、优先级队列、限流和预算告警，同时把租户标签纳入所有可观测信号。

8. Prompt Injection、Jailbreak 与 Guardrails

LLM 服务面临的安全威胁和传统 Web 服务有一个根本性差异：攻击面在于自然语言本身。攻击者不需要发送畸形字节序列，只需构造能操纵模型行为的文本，就可能绕过访问控制、泄露敏感数据或让模型执行未授权操作。

Prompt Injection 是结构性安全漏洞：模型无法原生区分"平台指令"和"用户输入"，更无法识别"检索内容里的伪装指令"。这不会随着模型变聪明自动解决，必须在系统架构层引入防护。

Prompt Injection 分类

Direct Injection用户直接输入中公开聊天机器人被用户探测系统提示词
Indirect InjectionRAG 检索文档高攻击者控制的网页被爬入知识库，嵌入"忽略前述指令"
Stored Injection写入数据库极高用户评论字段包含注入指令，被客服系统读取时激活

9. 对外 API 安全

LLM 服务对外暴露 API 时，面临 LLM 特有的 token 消耗计量、API Key 泄露高危化（调用成本极高）和模型提取攻击等挑战。

API Key 泄露在 LLM 场景的代价远高于普通服务：一个泄露的 LLM API Key 可让攻击者用你的配额做大规模模型提取（每分钟消耗百万 token）、产生大额账单。发现泄露后的黄金响应窗口通常不超过 15 分钟。

Token-level Quota（LLM 特有）

普通 API 按请求数计量，LLM 必须额外按 token 计量。一个短请求（10 tokens）和一个长请求（100K tokens）在资源消耗上有 4 个数量级的差距。推荐用 Redis 滑动窗口实现 token quota，记录 prompt_tokens（已知）+ max_completion_tokens（预估上限），窗口结束后清理过期记录。

10. LLM 数据合规

LLM 服务在数据层面面临多重合规要求，覆盖训练数据 PII、用户推理日志保留期、跨境数据流和模型记忆攻击防护。

推理日志保留期合规对照

法规适用范围推理日志要求违规代价
GDPR（欧盟）处理欧盟居民个人数据不得超过业务目的所需时间；默认 30-90 天，需告知用户最高 2000 万欧元或年营业额 4%
PIPL（中国）处理中国境内个人信息须在隐私政策中声明；一般要求不超过 180 天最高 5000 万元或年营业额 5%
HIPAA（美国医疗）医疗相关数据医疗对话日志按 PHI 处理，6 年保留义务最高 190 万美元/年
CCPA（加州）处理加州居民数据用户可请求删除其历史对话日志每次违规最高 7500 美元
跨境数据传输合规红线：GDPR 明确禁止将欧盟居民个人数据传输到"充分性保护决定"以外的国家，除非签署标准合同条款（SCC）。将 EU 用户请求路由到美国 GPU 集群推理，可能已构成违规。技术控制：Region-pinned 推理 + 数据本地化日志。

DP-SGD：差分隐私训练原理

DP-SGD 通过 per-sample gradient clipping（限制单样本最大影响）+ Gaussian 噪声注入，提供 (ε, δ)-DP 保证：对任意相邻数据集（仅差一个样本），算法输出分布的差异被 e^ε 倍上限和小概率 δ 兜底。ε 越小隐私越强，代价是模型精度下降（ε=8 约 -2~3pp；ε=3 约 -5~8pp）。训练时间增加 30-100%，显存需求翻倍。

攻击DP-SGD 防护效果
Training Data Extraction(ε=8, δ=10⁻⁵) 把成功率从 ~5% 降到 < 0.1%
Membership Inference(ε=8) 把 advantage 从 > 0.3 降到 < 0.05
Model ExtractionDP 不直接防护，仍要 rate limit

11. Pickle 攻击与模型权重运行时安全

供应链签名解决"谁构建了这个权重、是否被篡改"，但签名不能防止运行时加载路径上的威胁。PyTorch 的 .pt、.bin、.ckpt 文件默认使用 Python pickle 格式，其 __reduce__ 机制允许被序列化的对象在反序列化时执行任意 Python 代码。

torch.load 是高风险操作：对不受信任来源的 .pt / .bin / .ckpt 文件执行 torch.load() 等同于执行对方提供的代码。文件大小正确、名字正确都不能作为安全依据，因为 pickle payload 通常只需几 KB，可以嵌入任何大小的文件头部。
安全维度torch.load(f)torch.load(f, weights_only=True)safetensors.load_file(f)
代码执行风险极高（任意 __reduce__）低（仅白名单类型）无（纯数据格式）
PyTorch 版本要求所有版本2.0+（2.4+ 推荐，默认将改为 True）需安装 safetensors 库
跨语言支持Python onlyPython onlyPython / Rust / C++ / JS
推理部署推荐不推荐可接受（受信任内部 checkpoint）首选

12. 常见误区与工程建议

常见误区

  • 误区一：内网系统就不需要细粒度权限——内网平台同样会面临误操作、过度权限和供应链问题。
  • 误区二：安全会伤害效率，应尽量后置——后置安全通常意味着以后要用更高成本返工。
  • 误区三：治理等于审批——审批只是治理的一部分，真正关键的是规则是否能被执行和审计。
  • 误区四：K8s Secret = 加密——默认只是 base64，etcd 加密和 RBAC 缺一不可。

工程建议

  • 默认最小权限，而不是默认放开
  • 默认记录关键动作审计信息
  • 对模型、索引、镜像、prompt 模板都建立版本和责任归属
  • 把成本标签、权限标签、租户标签纳入平台元数据
  • 安全测试纳入 CI，每次模型 / Prompt 变更自动触发红队评测

常见工具速查
