1. 第一性原理拆解：评测、发布与故障处理

拆 — 不可化简的问题

剥离模型名、评测框架、A/B 平台、灰度工具和事故流程之后，本章真正处理的是一个不可化简的问题：一个会被数据、prompt、配置、检索、路由和负载共同改变行为的系统，如何在不确定性中被证明"值得上线"，并且在证明失败时把影响面限制住。普通软件发布的最小问题通常是"新代码是否按预期执行"；AI 系统发布的最小问题更复杂，因为同一段服务代码在不同模型权重、system prompt、few-shot、retrieval top-k、安全策略、缓存状态和用户输入分布下，会表现为不同产品。

它可能不报 500，却回答错；可能 p95 延迟正常，却在高价值租户的长尾场景里幻觉率上升；可能离线评测过线，却在线上因为请求分布变化、缓存污染或工具调用失败而退化。这是 AI 发布不可简化的根本原因：行为空间太大，任何单一门禁都无法覆盖全部风险，必须把多层证据串成闭环。

因此，"把新版本推上去"从来不是发布的全部；真正困难的是：你如何证明它该上线、出了问题如何回滚、事故后如何避免再次发生。证明上线需要证据链，包括离线评测、回归样本、安全测试、成本预算、线上灰度观测和实验结论。限制影响面需要控制链，包括版本登记、流量切分、放量阈值、自动告警、降级策略和可执行回滚。避免再次发生需要学习链，包括事故证据保留、影响范围定位、根因归类、门禁补强和平台能力沉淀。

评测、发布与故障处理不是三个孤立动作，而是同一个闭环：上线前减少未知，上线中限制损失，上线后把损失转化为下一次发布的约束。这个闭环必须同时在系统层（错误率、延迟、成本）、质量层（幻觉率、安全拦截、引用准确）和业务层（用户投诉、租户影响）三个维度同时运转，缺少任何一个都意味着证据不完整。工程师必须理解：灰度是控风险的手段，A/B 是比方案的手段，两者回答不同的问题，不能互换，也不能省略。

推 — 从这个问题如何推导出每个机制

从"行为不可完全由代码决定"出发，首先必然推导出离线评测。如果模型、prompt、检索和安全策略都可能改变输出，那么发布前必须把核心任务、回归样本、高风险样本和成本约束固定成可重复的门禁。门禁的意义不是证明系统完美，而是挡住已知坏版本，避免团队靠主观印象上线。接着会推导出 Release Bundle：AI 发布单元不能只包含镜像 tag 或模型文件，还要绑定模型版本、prompt 版本、few-shot 集、retrieval 配置、安全策略、路由规则和缓存维度；否则事故发生时无法回答"线上到底是什么组合"。

从"离线数据不能完全代表线上流量"出发，必然需要灰度发布（canary rollout）。灰度不是仪式，而是在 1%、5%、20% 这些有限流量窗口里验证真实请求、真实租户、真实负载和真实成本是否稳定。因为 AI 退化常常不是硬错误，所以灰度期间还必须有质量采样：在线 metrics 负责发现延迟、错误率、OOM、单位 token 成本等硬信号；真实请求 replay、LLM-as-judge 和人工抽检负责发现幻觉、引用错误、越权输出和长尾退化。质量采样必须按租户、场景、prompt / 配置版本、风险等级切片，否则平均值会掩盖受损人群。

从"想知道哪个版本更好"和"想控制上线风险"是两类问题出发，必然要区分 A/B 测试和灰度发布。灰度回答"这个版本能否安全扩大影响面"，A/B 回答"两个方案哪个在统计上更优"。两者可以串联，但不能混用：先用灰度证明不会把系统搞坏，再用 A/B 在稳定分流和 guardrail metrics 下比较效果。最后，从"任何证明都可能失败"出发，必然推导出回滚和事故响应。回滚必须先于发布存在，并且按 bundle 整体回退；事故响应不能只看 500，还要覆盖质量、成本、安全和租户影响。复盘也不是写报告，而是把事故反向转化为新的评测集、告警规则、灰度阈值、runbook 和平台自动化。

3. AI 发布为什么比普通代码发布更难

普通服务发布主要关注功能正确、接口兼容和系统稳定。AI 发布额外叠加了三个维度的不确定性：

系统发布

镜像、依赖、配置、扩缩容规则。出错通常表现为明显的 HTTP 错误或服务不可用。

模型发布

模型权重、tokenizer、量化配置、推理引擎版本。影响可能滞后出现，且不一定报错。

质量实验

prompt、few-shot、检索配置、安全策略。退化常表现为幻觉、越权、长尾错误，不会触发系统告警。

这意味着 AI 发布必须同时看成功率（系统稳定）、质量信号（模型不退化）和成本变化（单位 token 成本未异常）三条证据链。任何一条断开，都可能导致用户体验下降但技术指标看起来正常。

误判风险：p95 延迟达标、错误率为零，并不等于这个版本可以上线。AI 系统里，质量退化和成本异常可以在"系统指标全绿"的情况下悄悄发生。

4. 离线评测是第一道门

上线前至少应回答四个问题：核心指标是否不低于基线；回归样本是否全部通过；关键安全测试是否通过；延迟与成本是否仍在预算内。

最佳实践：门禁的意义不是证明系统完美，而是挡住已知坏版本。离线门禁应该覆盖业务核心任务、已知失败样本、安全边界测试和成本预算上限，缺少任意一项都会让团队在事故后发现"其实离线已经有信号"。

一个简单门禁配置示例：

gates:
  offline_eval:
    ndcg_at_10: ">= 0.72"
    regression_failures: "== 0"
  serving_eval:
    p95_latency_ms: "<= 120"
    gpu_mem_gb: "<= 36"
  safety_eval:
    harmful_content_rate: "== 0"
    refusal_accuracy: ">= 0.95"

没有门禁时，团队很容易退化为"看起来不错就上线"。有门禁但不覆盖安全和成本时，回归质量可能过线但幻觉率已上升。门禁必须和 Release Bundle 绑定：同一个 bundle 通过的门禁结果不能被另一个 bundle 复用。

门禁类型回答什么问题常见指标失败动作
核心质量效果是否达到基线NDCG、F1、准确率、BLEU不发布，回评测
回归集已知良好样本是否仍然通过regression_failures == 0不发布，定位退化
安全测试是否有高风险输出有害内容率、越权率、拒答准确率强制阻断，不可豁免
成本预算单位请求成本是否在预算内avg_tokens、p95_latency_ms、gpu_mem不发布，优化后重测

5. 灰度发布的真正目标

灰度不是为了"显得专业"，而是在有限风险下验证：真实流量表现、质量是否稳定、长尾请求是否异常、成本是否明显变化。灰度阶段真正看的不是"新版本有没有起起来"，而是 第 21 章 里那组跨层信号：延迟、错误率、成本、质量、租户影响面是否同时稳定。

flowchart LR
  A[离线门禁] --> B[Staging]
  B --> C[1% Canary]
  C --> D{硬阈值触发?}
  D -- 是 --> R[按 release bundle 回滚]
  D -- 否 --> E[5% Canary]
  E --> F[Replay / Judge / 人工抽检]
  F --> G{切片质量退化?}
  G -- 是 --> S[停止放量并定位]
  G -- 否 --> H[20% Canary]
  H --> I[受控 A/B]
  I --> J{主指标提升且 Guardrail 正常?}
  J -- 是 --> K[全量发布]
  J -- 否 --> T[终止实验或回退]

A/B 测试 vs 灰度发布

这两个词常被混用，但目的不同。平台如果分不清两者，很容易把实验问题和稳定性问题搅在一起。

维度灰度发布A/B 测试
核心目标控风险，验证稳定性和可回滚性比较效果，验证哪个版本更优
流量切法按 1%→5%→20% 逐步放量，按版本逐级放量对实验单元做随机分流，避免偏差误认为模型效果
主要看什么系统指标、质量底线、成本异常、是否能快速回滚效果提升、统计显著性、业务指标变化
什么时候先做每次上线都应先做只有需要比较方案优劣时才做
放量决策到达观察窗口且未触发回滚阈值才继续放量样本量足够、差异达到统计显著且 guardrail metrics 未变坏才扩实验
A/B 实验纪律：随机分流应固定在用户/租户/会话级；提前定义主指标、MDE 和显著性标准；不论主指标是否提升都要盯住 guardrail metrics；只要 guardrail 越过回滚阈值，立即停止实验。

灰度期间的质量采样

很多 AI 退化不会直接变成 500，而是慢慢体现在错误回答、引用错乱、越权内容或成本异常上。灰度必须同时运行四种采样：

  1. 在线指标：成功率、超时率、p95/p99 延迟、平均 token、单位请求成本、用户投诉率
  2. 离线 Replay：把灰度窗口保留的真实请求回放到新旧版本，防止线上噪声掩盖退化
  3. 人工抽检：优先抽高价值租户、高风险场景、失败重试、含工具调用或敏感问答的样本
  4. LLM-as-judge：让独立 judge prompt 对新旧回答打分，评估相关性、引用准确率、拒答合规性
灰度阶段质量采样动作重点判断常见放行条件
1%在线指标全量监控；高风险请求全留样；人工抽检最新输出是否出现明显安全、幻觉、越权、格式崩坏问题没有触发硬回滚阈值，且人工抽检未发现严重错误
5%在线指标持续看；抽样做离线 replay；LLM-as-judge 批量对比新旧输出是否存在持续性质量退化，是否只在某些租户/场景恶化系统指标稳定，切片后的质量指标未明显变差
20%扩大抽样面；补长尾任务与大客户样本；保留黄金请求的新旧输出对照长尾任务、分租户、分场景、分 prompt 模板是否都可接受异常都能解释且有处置方案，回滚路径仍然畅通
采样切片原则：分租户（防止大客户数据分布被平均稀释）、分场景（FAQ/复杂推理/工具调用/RAG/多轮各自看）、分 prompt/配置版本、分风险等级。安全敏感任务和普通任务不能按同一阈值放行。

6. 回滚必须先于发布存在

很多团队的回滚方案，其实是在事故发生后才临时想。正确顺序应该是：先有稳定的上一个版本；先有路由切回机制；先明确索引/配置/prompt 是否也要一起回退；再发布新版本。

严重风险：如果发布时没有确认回滚路径畅通，事故发生后就只能在压力下临时拼凑回滚方案。对于 RAG 或 LLM 系统，问题不只来自模型，还可能来自向量索引、prompt 模板、reranker 和安全规则，这些都必须纳入回滚范围。

Prompt 与配置也属于发布单元

在生产 LLM 服务里，prompt 不是"运营文案"，而是影响行为边界的配置代码。它和模型、索引一样，都应该进入版本登记、灰度发布和一键回滚流程。如果 guard rail 或工具白名单配错，影响面往往和模型回归一样大（安全边界参考 第 23 章）。

对象为什么要版本化灰度/回滚要求
system prompt直接决定角色、约束和输出风格不允许控制台热改，和模型版本一起灰度
few-shot 示例集示例变化会改变回答偏好和格式需要记录样本来源、更新时间和责任人
guard rails / safety filters决定输入输出过滤、越权拦截、工具白名单小流量验证误杀和漏拦截，再全量
检索/路由配置top-k、reranker、fallback 直接影响质量与成本和索引、模型一起打包发布

Release Bundle 示例配置：

release_bundle:
  model: "llm-prod@2026-04-18"
  system_prompt: "assistant-prod@v12"
  few_shot_set: "citation-rag@v4"
  safety_policy: "guardrails@v7"
  retrieval_config: "search-prod@v9"
工程边界：prompt registry 和配置中心可以提供编辑、审核、diff、签名和查询，但生产请求只应引用不可变版本 ID。Feature Flag 可以选择已登记 bundle 的流量比例，不能直接承载任意 prompt 文本热更新。紧急修复也应生成新 bundle 并留下审批记录。

7. AI 事故不只有 500 错误

AI 事故常见表现不限于系统错误，还包括：延迟突增、成本突增、回答质量明显下降、幻觉率上升、权限泄漏或安全策略失效。因此 incident 触发条件不能只看系统错误率，还应包含质量告警和成本异常。

系统层事故

  • 错误率超过阈值
  • p95/p99 延迟突增
  • OOM / GPU 故障
  • 服务不可用

质量/安全层事故

  • 幻觉率上升
  • 安全拦截率异常（误杀或漏拦截）
  • 越权输出
  • 引用错误、格式崩坏
  • 成本每千 token 翻倍
stateDiagram-v2
  [*] --> 正常服务
  正常服务 --> 异常检测 : 告警触发（系统/质量/成本）
  异常检测 --> 快速降级 : P0 安全事故
  异常检测 --> 影响范围确认 : P1/P2 质量或成本事故
  影响范围确认 --> 回滚决策 : 已知版本问题
  影响范围确认 --> 定位阶段 : 原因不明
  回滚决策 --> 执行回滚 : 按 bundle 整体回退
  定位阶段 --> 执行回滚 : 定位到版本问题
  定位阶段 --> 降级限流 : 无法立即修复
  执行回滚 --> 服务恢复
  快速降级 --> 服务恢复
  降级限流 --> 服务恢复
  服务恢复 --> 证据保留
  证据保留 --> 复盘
  复盘 --> [*] : 沉淀平台能力

8. 事故响应流程

AI 事故响应的核心不是流程图本身，而是三个关键能力：知道当前线上是什么版本；知道哪些租户受影响；能在几分钟内执行回滚。

发现异常
  -> 确认影响范围（哪些租户、哪些场景、哪些版本）
  -> 决定降级 / 限流 / 回滚（按严重程度）
  -> 保留证据（日志、trace、版本信息、请求样本）
  -> 恢复服务
  -> 复盘并加门禁
证据保留是复盘的基础：灰度窗口应保存可重放样本集，至少包含请求元数据、命中的 release bundle、旧版本输出、新版本输出、judge 结果和人工结论。事故发生后，团队才能快速回答"是模型变了，还是 prompt/检索/安全策略变了"。

9. 从事故反推平台能力

每次事故都应倒逼平台补能力。一个成熟平台，不是"没有事故"，而是"事故会沉淀成平台能力"。

事故现象暴露的平台短板应补充的能力
回滚慢，需要手动切流量版本注册或路由切换能力不足自动化 bundle 回滚 + 路由切换 runbook
质量下降但告警没发现质量观测面不够，只看系统指标在线质量采样 + LLM-as-judge 告警
定位困难，不知道是哪个组件的问题trace/日志/元数据没打通request_id 关联模型版本、prompt 版本、检索版本
事故复盘发现离线已有信号离线门禁覆盖不全把事故样本加入回归集，补强门禁
同类事故重复发生没有把事故转化为自动化守护补告警规则 + 灰度阈值 + 自动化 analysis template

10. 常见误区

误区一：离线评测通过就等于可以全量上线。离线数据不代表真实流量。离线门禁只挡住已知坏版本；灰度才能验证真实请求、真实租户、真实负载。
误区二：灰度只看系统指标。AI 发布还必须看质量指标和成本变化。p95 达标但幻觉率上升，仍然是发布失败。
误区三：回滚只是切模型版本。很多系统还要同时回滚配置、索引、prompt 和路由规则。按 bundle 整体回退才是正确姿势。
误区四：A/B 测试可以替代灰度。灰度回答"能否安全扩大影响面"，A/B 回答"哪个方案更优"。混用这两者会导致把实验问题和稳定性问题搅在一起，出了事故不知道原因。

11. Argo Rollouts / Flagger 实际工作机制

理解 Argo Rollouts 如何实现 traffic split、如何自动判断 metric、如何 promote/rollback，灰度才能从"运行就行"变成"可解释、可调试"。

Argo Rollouts 基本结构

用 Rollout CRD 替代 Deployment，引入 strategy.canary 声明式描述灰度阶段：

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: llm-router
spec:
  replicas: 10
  strategy:
    canary:
      canaryService: llm-router-canary
      stableService: llm-router-stable
      trafficRouting:
        istio:
          virtualService:
            name: llm-router-vs
      steps:
        - setWeight: 1                  # 1% 流量到 canary
        - pause: {duration: 10m}
        - analysis:                     # 跑指标分析
            templates:
              - templateName: success-rate
              - templateName: ttft-p95
        - setWeight: 5
        - pause: {duration: 30m}
        - analysis:
            templates:
              - templateName: success-rate
              - templateName: ttft-p95
              - templateName: ttft-p99
        - setWeight: 25
        - pause: {duration: 1h}
        - setWeight: 100

traffic split 实现机制

TrafficRouting 后端怎么改流量比例
Istiocontroller patch VirtualService.spec.http[].route[].weight，Istio Pilot 推送给 Envoy sidecar
SMI TrafficSplitcontroller 改 TrafficSplit.spec.backends[].weight，Linkerd/其他 mesh 实现
nginx-ingresscontroller 改 Ingress annotation nginx.ingress.kubernetes.io/canary-weight
ALB Ingresscontroller 改 ALB target group weight
Service mesh agnostic通过 Service selector 调整 stable/canary Pod 数量比例（粒度粗，不推荐生产）

Analysis Template 自动判断 metric

apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: ttft-p95
spec:
  metrics:
    - name: ttft-p95
      interval: 1m
      successCondition: result[0] < 1500          # P95 < 1500ms
      failureLimit: 3                              # 连续 3 次失败就 fail
      provider:
        prometheus:
          address: http://prometheus:9090
          query: |
            histogram_quantile(0.95,
              sum(rate(llm_ttft_seconds_bucket{
                service="llm-router",
                version="canary"
              }[2m])) by (le)
            ) * 1000
生产实战要点：AnalysisTemplate 的 query 必须按 version label 区分 canary vs stable；failureLimit 不能太低（建议 3-5）；pause 阶段必备，让流量稳态再 analyze；LLM canary 副本建议至少 3-5 个才做 analysis（防止 Prometheus rate 噪声大）。LLM 推理 metric 通常需要更长 window（5-10 min）才稳定，interval: 1m 偏短。

Flagger 与 Argo Rollouts 的主要差异

  • Flagger 是 service mesh native（Istio/Linkerd/AppMesh），不支持 ingress controller
  • Flagger 自己创建 primary 和 canary Deployment（不像 Rollouts 用一个 Rollout 资源管所有 Pod）
  • Flagger 内置 load test webhook（在分析期间主动打流量到 canary，让 metric 有足够样本）
  • Flagger 的 metric provider 选择更多：Prometheus、Datadog、New Relic、CloudWatch
对话场景特别注意：mesh weight 是 per-request 随机，同一用户每次请求可能落到不同版本，导致用户体验不一致。需要 mesh + header-based routing（如 consistent-hash on user_id）才能保证会话粘性。

12. LLM-as-judge 的偏差与校准

直接用 GPT-4 当 judge 不做校准是常见错误，结论可能偏向系统性。以下是主要偏差类型：

偏差表现严重程度
Position bias让 judge 比较 (A, B) 时偏好第一个或最后一个，不论实际质量严重——很多 judge 偏好第一个 60-70%
Verbosity bias偏好更长的回答，即使内容差中——简单 prompt 可缓解
Self-preference bias用 GPT-4 当 judge 评 GPT-4 输出，得分系统性高于其他 model严重——同 family 模型不能互评
Sycophancyjudge 可能配合 prompt 暗示而非客观评判严重——不能把"哪个更好"暗示放 prompt
Refusal asymmetryjudge 可能偏好不拒答的版本，即使拒答更安全严重——安全场景必须人工校准

Position bias 校准：双向比较

# 错误方式：单方向比较
score_A_vs_B = judge.compare(question, response_A, response_B)

# 正确方式：双向比较
def fair_compare(question, A, B):
    s_AB = judge.compare(question, A, B)  # A 在前
    s_BA = judge.compare(question, B, A)  # B 在前

    if s_AB == "A wins" and s_BA == "B wins":
        return "tie"  # judge 仅按位置选——结果不可信
    if s_AB == "A wins" and s_BA == "A wins":
        return "A wins"  # 两次方向都选 A，可信
    ...
实测结论：双向比较后 30-40% 的"获胜"会变成 tie，说明这部分判断完全是 position bias。生产中 judge benchmark 的 win-rate 数字必须用双向校准过的。

校准（Calibration）流程

1. 抽 500 条业务真实样本（覆盖各场景）
2. 人工标注：response_A vs response_B 哪个更好
3. 用 judge 跑同样的样本对
4. 算 agreement rate：
   - human-judge agreement: 人工和 judge 一致的比例
   - cohen's kappa: 排除偶然一致后的一致性系数
5. 阈值：
   - kappa > 0.6: judge 可用作初筛
   - kappa > 0.8: judge 可用作主判断（仍要抽样 5% 人工复核）
   - kappa < 0.4: judge 不可信，找别的判断方法
生产 judge 设计 checklist：judge prompt 使用 chain-of-thought + 明确 rubric；Position 双向校准是默认行为，不是可选项；judge 模型与生产模型不同 family；每月跑一次 calibration 样本（kappa 下降 > 0.1 时重新设计）；judge 结果只作为 P50 quality 信号，安全/refusal 类判断必须人工。

与灰度结合的 AnalysisTemplate

# Argo Rollouts AnalysisTemplate
- name: judge-quality
  interval: 30m                   # judge 调用贵，跑得疏
  successCondition: result[0] >= 0.55   # judge win rate >= 55%
  failureCondition: result[0] < 0.45    # < 45% 视为退化
  provider:
    web:
      url: http://judge-service/canary-vs-stable
      method: POST
      jsonBody: '{"window": "30m", "samples": 100}'
      jsonPath: "{$.win_rate}"

注意 successCondition 不应该是 > 0.5——judge 噪声 + position bias 残留让 50/50 是合理 baseline，要求"显著优于 stable"才通过会过严。
