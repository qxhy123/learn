1. 第一性原理拆解：可观测性与容量规划

拆 — 不可化简的问题

把 Prometheus、Grafana、OpenTelemetry、Jaeger、DCGM、SLO 这些工具名拿掉，本章的不可化简问题只有一个：AI 系统把昂贵资源、随机负载和不完全可预测的模型行为压缩成用户看到的一次响应，工程师必须在响应变坏之前知道哪里偏离、为什么偏离、会烧掉多少可靠性和成本余量。训练会被一个慢 worker 拖住整组 GPU，推理会被少量超长 prompt 撑满 KV Cache，RAG 会因为检索抖动让 LLM 看起来"变慢"，灰度会因为质量退化但延迟正常而误判成功。它们的共同点不是"缺监控面板"，而是系统内部状态不能被单个指标直接观察。

可观测性不是把所有事件全量存下来。全量存储会撞上三个硬边界：tokens/s、requests/s、训练 step 事件和 GPU 指标形成吞吐压力；tenant、model_version、adapter_id、trace_id、job_id 等维度组合制造 cardinality 爆炸；日志、trace、指标的存储和查询本身也会消耗预算。容量规划也不是简单问"需要几张 GPU"，而是把流量分布、token 长度、SLO、错误预算、发布窗口、故障冗余和成本归因放进同一张账本。看不见的系统会变成靠运气维护的系统；看得见但不能解释成本和风险的系统，也不算真正可观测。

推 — 从这个问题如何推导出每个机制

如果系统状态不能直接观察，第一步必然是选择信号。Metrics 用低成本聚合回答"趋势是否异常"，Logs 用结构化字段回答"这次请求发生了什么"，Traces 用跨服务上下文回答"时间花在链路哪一段"。三类信号要靠 request_id、trace_id、tenant_id、model_version、job_id 关联，否则只有 GPU utilization，看不出 queue wait；只有错误日志，看不出 SLO burn；只有 trace，看不出容量趋势。

信号一旦被采集，就会推导出采样和 cardinality 治理。全量 trace 最有解释力，但成本不可控；head-based sampling 成本稳定，却可能错过慢请求；tail-based sampling 能保留错误和尾延迟，却要求 Collector 缓冲完整链路。维度越细，定位越快，但把 user_id、prompt_hash、trace_id 放进 metrics label 会让时间序列按请求级爆炸。因此必须提前定义哪些字段允许做 metrics label，哪些只能进入日志或 trace attribute，哪些必须 hash、截断或脱敏。

当信号可以解释当前状态后，下一步是把状态变成决策边界。SLI/SLO 把"好请求"的定义写清楚，错误预算把可靠性余量量化，burn-down 暴露预算消耗速度。AI 服务还必须同时看质量和成本：99.99% 可用、P95 达标，但 grounded rate 下降或 cost_per_1k_tokens 翻倍，业务仍然失败。容量规划把边界反推成资源需求；LLM serving 必须拆分 prefill 和 decode 两段独立建模，因为两者算力特性完全不同——prefill 是 compute-bound，decode 是 memory-bandwidth-bound，用统一 R 公式会在长输出场景低估 70% 以上。成本归因把总账拆回 tenant、model、region、endpoint、job，才能把"GPU 很贵"变成可执行的优化决策。

LLM 服务还需要专属指标体系：TTFT（Time To First Token）刻画用户感知等待，TPOT（Time Per Output Token）刻画流式输出顺滑度，Goodput 区分有效吞吐与无效消耗，KV Cache 利用率、Prefix Cache 命中率、Queue depth 串联从资源到体验的完整链路。DCGM Exporter 提供比 nvidia-smi 更细粒度的流式 GPU 指标，其中 DCGM_FI_PROF_PIPE_TENSOR_ACTIVE 才是 LLM 计算效率的核心指标，而非 GPU_UTIL。OpenTelemetry gen_ai.* 语义约定让跨框架的 LLM trace 互操作；Spot GPU 的云平台中断通知（AWS 2 分钟、GCP 30 秒）要求可观测系统提前感知并触发 drain + checkpoint。

2. 三种主要观测信号

2.1 可观测性不只是监控面板

一个成熟的可观测系统至少能回答三类问题：发生了什么（哪个指标、哪个租户、哪个模型异常）；为什么发生（上游流量变化、资源饱和、调度问题还是模型版本变更）；接下来怎么办（扩容、回滚、限流、降级还是继续观察）。可观测性不是"把指标都采上来"，而是让系统证据足够支持诊断。

2.2 Metrics

适合回答：当前系统是否在偏离正常范围，趋势是上升还是下降，是否应该触发告警或扩容。典型指标：GPU 利用率、显存占用、queue wait time、tokens/s、P95/P99 latency、请求错误率。

2.3 Logs

适合回答：这次失败到底是哪一步出错，哪个模型版本在服务这个请求，某次作业为什么退出。日志的关键不是多，而是可关联：request_id、trace_id、model_version、tenant_id、job_id。

2.4 Traces

在 AI 系统中，trace 特别适合多段链路：

网关 → 鉴权 → embedding → 向量检索 → rerank → LLM → 安全过滤

如果没有 trace，很多尾延迟问题会被粗暴归到"模型太慢"，而真正慢的可能是检索或上游回源。

2.5 采样策略

策略决策时机适合场景代价 / 风险
Head-based sampling请求入口处决定高吞吐稳定路径、成本敏感服务成本可预测，但可能漏掉慢请求和偶发错误
Tail-based sampling链路结束或超时后决定错误请求、P99 慢请求、关键发布窗口诊断价值高，但 Collector 内存、CPU 和网络成本更高
Adaptive sampling按租户、endpoint、错误率动态调整流量峰谷明显或多租户平台规则复杂，统计口径会变化
Log sampling / 分级按事件级别和字段保留高频 INFO、低频 WARN/ERROR、审计日志缺少 trace_id 时仍难关联
工程边界：采样不能作为财务、审计和安全证据的唯一来源；采样 trace 不能直接计算真实错误率或延迟分位数，真实 SLI 应来自请求计数器和 latency histogram。tail-based Collector 必须有内存、队列和降级上限。

2.6 Cardinality 治理：维度不是越细越好

Cardinality 指标签或字段可能出现多少不同取值。常见错误是把"定位时有用的字段"全部放进 metrics label。

指标设计维度取值示例风险
llm_request_latency{tenant,model,endpoint}200 × 20 × 30 = 120,000 序列需要容量评估
再加入 status_code,region× 6 × 5 = 3,600,000 序列存储和查询压力明显上升
再加入 user_id× 1,000,000 users请求级爆炸
再加入 trace_id每请求近似唯一metrics 退化成昂贵日志系统

治理原则是分层：低基数字段放在 metrics label（如 tenant_tier、model_family、endpoint、region、status_class）；中高基数字段放在 logs/traces attribute（如 tenant_id、model_version、adapter_id、job_id）；请求唯一字段（如 request_id、trace_id）只用于关联。

告警和容量面板应基于低基数、稳定口径的指标；事故排查再通过 exemplars、trace_id 和日志下钻。新增 metrics label 应评审取值数、增长和保留周期。

2.7 Prometheus TSDB 与 cardinality 的实际成本

Prometheus 数据模型：每个唯一 (metric_name, label_set) 组合是一条 time series。TSDB 给每条 series 分配独立的 in-memory chunk（active chunk，2 小时一切）+ 落盘 block 索引。每条 series 约 1-2 KB active memory；100 万 series ≈ 1-2 GB 内存。

维度健康范围危险阈值
Active series< 5M> 10M（OOM 风险）
Ingestion rate< 500K samples/s> 1M samples/s
Query latency P99< 5s> 30s（用户感知卡）
Retention15-30 天> 90 天（block 过多影响 compaction）
内存2-32 GB> 64 GB（GC 抖动）
HA 与长期存储：单机 Prometheus 是 SPOF。生产用 Thanos / Cortex / Mimir：Thanos sidecar 模式将 2h 落盘 block 上传到 S3/GCS；Cortex / Mimir 横向扩展 ingester / store-gateway / compactor / querier；VictoriaMetrics 单二进制，资源消耗通常低于 Cortex。Prometheus pull 模型通过 service discovery 找 target，target 不需要知道 Prometheus 在哪。

2.8 Histogram 与 histogram_quantile() 的实际机制

Classic histogram 中每个 bucket 是一条独立 series（cumulative count），N 个 bucket 边界 = N+1 条 series（含 +Inf）。histogram_quantile 在 bucket 内做线性插值（假设样本均匀分布）。bucket 选错时 P99 误差可达 5-10x。

bucket 选择规则：必须围绕 SLO 目标密集（守 100ms P99 SLO，bucket 必须有 80/100/125/160ms）；跨数量级用对数尺度；+Inf bucket 装 1% 以上数据时 P99 不可估；每个 bucket 是一条 series，控制在 8-15 个。精度盲区：样本量 < 1000 时 P99 不可信；+Inf 装 1% 以上时 P99 一定不准。

2.10 W3C Trace Context：跨进程的 trace 怎么传

traceparent: 00-{trace_id}-{parent_span_id}-{flags}
例：00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
协议怎么传
HTTP/1.1 / HTTP/2加 traceparent header
gRPC加 metadata（与 HTTP/2 header 类似）
Kafka加 message header（key=traceparent）
数据库SQL comment（/* traceparent='...' */），Postgres 14+ 自动捕获
baggage 风险：baggage 自动随 trace context 传播，附到所有下游 span。把 user_id 放 baggage 会让所有 span 的 metrics 爆炸——只传 tenant_id、environment 这种低 cardinality 的字段。异步任务（Celery、消息队列）需要手动注入 baggage，这是 trace context 丢失的常见 bug 源。

3. AI 系统应该看哪些指标

资源面

  • GPU utilization
  • GPU memory used
  • CPU / memory
  • network tx/rx
  • disk / object storage throughput

任务面（训练）

  • step time
  • dataloader time
  • all-reduce time
  • queue length / pending jobs
  • checkpoint duration

服务面（推理）

  • requests/s
  • tokens/s
  • active sequences
  • prefill latency
  • decode throughput
  • cache hit ratio

业务 / 质量面

  • 离线评测指标
  • 线上反馈分数
  • 召回 / 重排质量
  • 人工审核通过率
  • 成本 / 请求
AI 服务即使资源和延迟都正常，也可能因为模型行为退化而业务失败。必须同时覆盖资源、任务、服务、质量、成本五层，才算真正可观测。

4. SLI / SLO 框架与错误预算

4.1 最小 SLI / SLO 框架

slis:
  availability_ratio: successful_requests / total_requests
  p95_latency_ms: observed end-to-end p95 latency
  answer_grounded_rate: grounded_answers / sampled_answers
  cost_per_1k_tokens_usd: total_cost_usd / (processed_tokens / 1000)
slo:
  availability_ratio: ">= 99.9%"
  p95_latency_ms: "<= 2500"
  answer_grounded_rate: ">= 0.90"
  cost_per_1k_tokens_usd: "<= 0.35"
为什么 AI 服务的 SLO 不能只有延迟和可用性：如果只有系统 SLO 没有质量 SLO，平台很容易把"快速返回错误答案"误当成成功。grounded rate 下降或 cost_per_1k_tokens 翻倍，业务仍然失败。AI 服务必须同时定义系统、质量和成本三类 SLO。

4.2 错误预算 burn-down

SLO 的价值不在于写出"99.9%"，而在于把可靠性余量变成可执行规则。30 天 availability SLO 为 99.9% 时，错误预算是 0.1%，约 43.2 分钟不可用时间。如果 6 小时内因新模型版本不可用 12 分钟，就烧掉 27.8% 月预算。

信号含义典型动作
30 天预算剩余 < 25%本月余量不足冻结非必要发布
6 小时 burn rate > 2x预算消耗过快降低灰度比例
1 小时 burn rate > 10x快速事故回滚、限流或降级
质量 SLO burn-downgrounded rate 等下降暂停模型/Prompt 发布
成本 SLO burn-downcost_per_1k_tokens 超预算收紧上下文、启用缓存或配额
工程边界：错误预算不能替代事故判断。低流量服务需要最小样本数门槛；质量 SLO 依赖采样评测；成本 burn-down 受账单延迟影响。预算规则要和 第 22 章 的灰度、回滚和事故流程绑定。

5. 容量规划：把流量和资源联系起来

5.1 基础公式

假设某模型单 GPU 的稳定吞吐约为 R tokens/s，请求平均 token 总量为 Tavg，目标 QPS 为 Q，则所需 GPU 数量近似为：

gpus_required ≈ (Q × T_avg) / (R × target_utilization)

例：平均 1200 token/请求，目标 20 QPS，单 GPU 12000 tokens/s，利用率 70%：20 × 1200 / (12000 × 0.7) ≈ 2.86，即至少 3 张 GPU，还没算冗余和峰值抖动。

5.2 prefill / decode 分离建模（LLM serving 必做）

单 R 公式在 LLM serving 上经常严重失真：prefill 是 compute-bound（同一 H100 上可达 30K-50K tokens/s），decode 是 memory-bandwidth-bound（batch=1 时只有 50-100 tokens/s，差距 300-1000×）。用平均 R 算容量，长 prompt + 长输出场景会严重低估，短 prompt + 短输出会严重高估。

正确做法：拆成 prefill_gpu_seconds + decode_gpu_seconds 两条独立账本，再求和：

prefill_gpu_seconds_per_req = T_prompt / R_prefill
decode_gpu_seconds_per_req = T_output / R_decode
gpus_required ≈ Q × (prefill_gpu_sec + decode_gpu_sec) / target_utilization
场景T_promptT_outputQ单 R 估算分离建模误差
短问答（chatbot）20010050 QPS1.8 GPU1.6 GPU单 R 略高估 13%
长 RAG（典型）800050010 QPS10.1 GPU5.6 GPU单 R 高估 80%
长输出（reasoning）50080005 QPS5.1 GPU18.2 GPU单 R 严重低估 72%
Agent 多轮2000+工具800/步×5步2 QPS1.4 GPU4.8 GPU单 R 低估 71%
真实 LLM 业务的 prompt / output 长度分布几乎都是双峰甚至多峰：容量规划必须按桶分别建模——把总流量切成 4-6 个 (prompt_len, output_len) 桶，每桶单独算 prefill/decode，再求和。否则少数 long-context 请求会把 P99 拉到 SLO 之外。
参考数量级（仅供建立直觉）：交互式 LLM 服务稳态 GPU 利用率目标 55-75%；稳态显存水位 70-85%；默认 Trace 采样比例 1-10%；关键发布窗口额外容量余量 20-30%。

6. LLM 特有指标体系

LLM 推理服务的失败模式和传统微服务不同：HTTP 200 返回了，但用户已经等了 4 秒才看到第一个字；tokens/s 的吞吐看起来很高，却有 15% 的请求因超时被放弃；GPU 利用率 85%，但实际上一半时间在排队。必须用 LLM 专属指标体系才能准确刻画这些失败模式。

6.1 TTFT：Time To First Token

定义：从请求进入系统到用户看到第一个生成 token 的端到端耗时。TTFT = T_network-in + T_queue + T_prefill。

场景P50 目标P99 目标说明
交互式对话（chat）< 300 ms< 2 s超过 2s 用户感知明显等待
Copilot / IDE 补全< 200 ms< 800 ms键入停顿后补全必须足够快
RAG 问答< 500 ms< 3 s含检索耗时，P99 更难控制
后台批量处理< 5 s< 30 s非交互，侧重吞吐而非延迟
 
histogram_quantile(0.99,
  sum(rate(llm_ttft_seconds_bucket[5m])) by (le, model, endpoint)

TTFT 的 P99 对长尾请求极其敏感。单个超长 prompt 在 prefill 阶段会阻塞同一 worker 的其他请求的 TTFT。Chunked prefill 和 P/D 解耦（见 第 15 章）是减少 TTFT 长尾的主要手段。Admission queue wait 时间是 TTFT 升高的最直接先行信号。

6.2 TPOT：Time Per Output Token

定义：每生成一个 output token 的平均耗时，等同于 ITL（Inter-Token Latency）。Decode 阶段是 memory-bandwidth-bound，70B 模型在单 H100 上理论最低 TPOT 约 40ms/token。

场景P99 目标说明
交互式流式输出< 50 ms/token约 20 token/s，接近人类阅读速度
代码生成< 30 ms/token用户关注代码完整性，流速要快
高并发推理< 100 ms/token并发越高，batch 越大，TPOT 受 HBM 带宽限制上升

6.3 Goodput vs Throughput

Goodput = Throughput × success_rate × slo_compliance_rate。一个系统在高负载时，原始 throughput 看起来很高，但如果 30% 的请求因为 TTFT 超时被客户端放弃，这些 tokens 消耗了 GPU 算力但没有产生业务价值。Goodput 才是应该用来做容量规划和成本核算的分母。

7. DCGM Exporter 详细指标映射

DCGM（Data Center GPU Manager）是 NVIDIA 官方的 GPU 监控和管理框架，比 nvidia-smi 提供更高频、更细粒度的流式指标，以 100ms-1s 可配置频率流式采集，适合送入 Prometheus 做长期监控和告警。nvidia-smi 是采样快照（默认 1s 粒度），适合临时排障。

DCGM 指标物理含义典型用途常见误用
DCGM_FI_DEV_GPU_UTILSM 在采样窗口内"有 kernel 在执行"的时间占比判断设备是否被使用误用为"GPU 算力被充分利用"
DCGM_FI_DEV_FB_USED已使用显存（MB）显存容量规划、OOM 预警—
DCGM_FI_DEV_FB_FREE剩余可用显存（MB）触发 admission 限流—
DCGM_FI_PROF_DRAM_ACTIVEHBM 总线活跃周期占比（0-1）真实内存带宽利用率与 GPU_UTIL 混淆
DCGM_FI_PROF_PIPE_TENSOR_ACTIVETensor Core 执行周期占比（0-1）矩阵乘法实际利用率被忽视，是 LLM 性能的核心指标
DCGM_FI_DEV_NVLINK_BANDWIDTH_TOTALNVLink 总带宽（MB/s）多 GPU 通信瓶颈排查—
DCGM_FI_DEV_XID_ERRORS硬件 XID 错误计数硬件故障检测只在任务失败后才看
DCGM_FI_DEV_GPU_UTIL 的严重误用：GPU_UTIL 的定义是"该采样窗口内，是否有至少一个 kernel 在执行"，并不区分 SM 中活跃 warp 的数量。一张 GPU 上只有 1% 的 SM 在跑 1 个 warp，GPU_UTIL 也会报告 100%。LLM decode 阶段（batch=1 时）常出现 GPU_UTIL 接近 100% 但 Tensor Core 利用率不足 30% 的情况。以 GPU_UTIL 作为性能瓶颈的唯一判断依据，会导致错误的扩容和优化决策。推荐用 DCGM_FI_PROF_PIPE_TENSOR_ACTIVE 作为 LLM 计算效率的核心指标。该值 < 30% 说明矩阵乘法严重不足，通常意味着 batch size 太小（decode memory-bound）或调度器效率低下。

  A[DCGM Exporter] --> B[Prometheus]
  B --> C{指标类型}
  C --> D[DEV_GPU_UTIL\n设备有 kernel 执行]
  C --> E[PROF_PIPE_TENSOR_ACTIVE\nTensor Core 真实利用率]
  C --> F[PROF_DRAM_ACTIVE\nHBM 带宽利用率]
  C --> G[DEV_XID_ERRORS\n硬件错误计数]
  D --> H[误用：不代表计算充分]
  E --> I[LLM 性能核心指标]

8. OpenTelemetry LLM Trace 规范

OpenTelemetry 社区在 2024 年开始为生成式 AI 场景制定 gen_ai.* 语义约定，目标是让不同 LLM 框架（vLLM、LangChain、LlamaIndex、Bedrock SDK 等）产生结构一致、可互操作的 trace 数据。

Attribute类型含义是否敏感

Tail-based sampling 的核心价值：异常请求（超时、错误、P99 以上慢请求）无法被 head-based 采样可靠捕捉。Tail-based Collector 在请求完成后根据 latency、status_code、SLO 违反情况决定是否保留完整链路，适合 LLM 服务的尾延迟排查。

9. 成本可观测性

传统 SRE 体系很少把成本列为核心可观测维度，但 LLM 服务中成本是和延迟、可用性同等重要的第一公民：一次 agent 工具循环失控可以消耗数百美元；reasoning model 的隐藏 token 成本可以让账单翻 3-5 倍；某个 tenant 的上下文长度从 2K 涨到 64K 会让该 tenant 的成本暴增 10 倍以上。

成本层次计算公式用途
per-GPU-hourgpu_count × hours × gpu_price/hr基础设施成本规划
per-requestcost_per_1k_prompt × prompt_tokens/1000 + cost_per_1k_completion × completion_tokens/1000请求级成本归因
per-token（分 prompt/completion）prompt: ~$0.5-3/M tokens；completion: ~$1.5-15/M tokensAPI 计费和内部 chargeback
Reasoning Token 的隐性成本：Claude 3.7 Sonnet thinking、OpenAI o1/o3、DeepSeek-R1 等 reasoning model 会在生成最终答案前，先内部产生大量"思考 token"（thinking/reasoning tokens）。这些 token 通常在 API 响应中不可见，但会计入实际计算成本。监控只看 completion_tokens 而忽略 thinking_tokens，成本归因严重低估。必须额外采集 gen_ai.usage.thinking_tokens span attribute。

9.1 归因维度与 Showback vs Chargeback

归因维度适合回答的问题注意事项

model_family / model_version哪个模型版本成本异常高基数版本放离线明细
endpoint / workflow哪条业务链路最贵RAG、agent、chat 分开看
region / cluster是否受地域和碎片影响结合 GPU 型号和折扣
request_shape_bucket长请求对成本的贡献比例用 bucket，不用原始输入

  A[LLM Engine 日志\n含 token 用量] --> B[Fluentd / Kafka]
  B --> C[离线 ETL\n每小时聚合]

工程边界：在线成本通常是估算，不等于云账单或财务结算；归因维度必须和 cardinality 治理一致，高基数字段进入离线明细或账单流水，不进入 Prometheus 热路径；共享成本需要明确分摊规则。Showback（展示成本，不扣费）适合成本意识建设阶段；Chargeback（按用量转移成本）适合成熟多租户平台。

10. PyTorch Profiler 与 Nsight 工程集成

GPU 级性能问题（如 Tensor Core 利用率低、HBM 带宽瓶颈、kernel 调度延迟）无法靠 DCGM 指标完全定位，需要 profiler 提供 kernel 级别的详细时序信息。

with torch.profiler.profile(
    activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
    schedule=torch.profiler.schedule(
        wait=10,     # 前 10 step 不采集（等系统稳定）
        warmup=5,    # 第 11-15 step 采集但不记录
        active=20,   # 第 16-35 step 正式采集
        repeat=1,
    ),
    on_trace_ready=torch.profiler.tensorboard_trace_handler(output_dir),
    record_shapes=True,
    with_stack=False,   # 生产关闭（开启时 overhead 可达 2-5x）
    with_flops=True,
) as prof:
    for step, batch in enumerate(dataloader):
        outputs = model(**batch)
        loss.backward()
        optimizer.step()
        prof.step()     # 必须调用，驱动 schedule 状态机
参数值含义
wait=1010 步profiler 存在但不记录，让系统进入稳态
warmup=55 步profiler 开始追踪但丢弃数据，减少 profiler 自身启动 overhead
active=2020 步正式记录的 step 数，需覆盖足够多的批次
repeat=11 轮完成一个 wait+warmup+active 周期后停止
ncu --set full 的 overhead 警告：会采集所有可用的硬件计数器，需要多次重放 kernel，overhead 通常为 5-50 倍正常运行时间。绝对不能在生产服务上使用 --set full。正确工作流：在隔离的测试节点上，用相同模型和代表性输入运行单次推理脚本，再用 ncu 分析。

11. Spot / Preemptible GPU 中断处理

Spot / Preemptible GPU 实例通常比按需实例便宜 60-90%，但随时可能被云平台回收。可观测性系统必须能感知中断事件并触发自动响应。

云厂商实例类型通知方式通知提前量注意事项
AWSSpot InstanceEC2 IMDS + CloudWatch Events2 分钟轮询 IMDS 每 5 秒一次；也可订阅 EventBridge
GCPPreemptible VMACPI G2 soft-off + metadata server30 秒通过 shutdown-script 捕捉；极短，必须预先 checkpoint
AzureSpot VMScheduled Events API30 秒（驱逐）/ 5 分钟（维护）轮询 metadata 每 10 秒；类型为 Preempt 时触发
GCP 30 秒的严峻挑战：30 秒内完成 checkpoint 对大模型几乎不可能（70B 模型 checkpoint 通常需要数分钟）。GCP 场景下，必须使用更频繁的异步 checkpoint 策略（每 10-15 分钟一次），并接受最多 15 分钟的计算损失。

12. 常见误区、最小 Dashboard 与本章小结

12.1 常见可观测性误区

误区一：GPU 利用率高就说明系统健康。不对。GPU_UTIL 只反映"是否有 kernel 在执行"，不反映计算是否充分利用。可能队列很长，用户已经在排队等待。应用 DCGM_FI_PROF_PIPE_TENSOR_ACTIVE 来判断 LLM 计算效率。
误区二：指标很多就说明可观测。不对。没有 request_id / tenant_id / model_version 关联，很多指标没有解释力。可观测性是让系统证据足够支持诊断，而不是面板数量多。
误区三：容量规划只看平均流量。不对。AI 业务对长度分布、峰值突发、故障余量都很敏感。LLM 的 prefill 和 decode 必须分开建模，长输出场景用单 R 公式会低估 70%+。

12.2 建议的最小 Dashboard

一个 LLM / RAG 服务最小可用面板至少可以包含：

  1. 请求量与 token 量（按 tenant、model_version、region 切分）
  2. P50 / P95 / P99 延迟（TTFT + TPOT + TTL）
  3. queue wait time 和 queue depth
  4. GPU 利用率（PIPE_TENSOR_ACTIVE）与显存占用
  5. active sequences / KV Cache 利用率
  6. Prefix cache hit rate
  7. Goodput / Throughput 比率
  8. 成本 / 请求或成本 / 1k tokens
