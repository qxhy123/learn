1. 第一性原理拆解：为什么算力、存储与网络必须一起看

拆 — 不可化简的问题

很多 AI 系统问题看起来发生在模型层，真正的瓶颈却早已在算力、存储和网络之间决定了上限。成熟的 AI 工程分析，不是先问“模型还能不能再优化”，而是先问：数据有没有按时送到？算力有没有被喂饱？通信有没有拖住整体？系统有没有被最慢的一段卡死？

把所有术语先拿掉，只保留不可化简的问题：一个 AI 任务要把输入数据变成输出结果，必然要经历“取数、搬运、计算、同步、保存或返回”这些物理动作。每个动作都占用一种有限资源：存储负责把字节交出来，CPU 和内存负责解码、拼 batch、调度和缓存，PCIe / NVLink 负责把数据送到设备，GPU 负责高密度矩阵计算，网络负责跨机器同步或跨服务调用。只要其中一段供给速度低于后续消费速度，后续资源就会等待；只要其中一段尾延迟变大，端到端体验就会被拉长。这个问题不能被“更大模型”“更强 GPU”“更多机器”单独解决，因为系统吞吐不是某个部件的最大值，而是依赖链路上可持续供给能力的最小值。

因此，本章的核心不是背诵“算力、存储、网络”三个名词，而是建立一个资源守恒视角：计算不会凭空发生，GPU 每算一次都需要权重、激活和输入数据已经在正确的显存位置；分布式训练每推进一步都需要各 rank 的梯度或参数状态达到一致；在线推理每返回一个 token 都要经过队列、模型服务、下游服务和客户端连接。所谓“GPU 利用率低”，本质上是昂贵计算单元处在等待状态；所谓“扩卡收益差”，本质上是新增计算能力被通信、同步、慢节点或调度开销吃掉；所谓“p99 很差”，本质上是某些请求走到了更慢的存储、网络或队列路径。先把这些物理约束看清楚，后面的机制才有意义。

推 — 从这个问题如何推导出每个机制

从“端到端结果必须穿过一条有限资源链路”出发，可以自然推出本章的每个机制。第一，既然 GPU 是高吞吐但高成本资源，就必须区分理论算力、可利用算力和系统级有效算力：规格表上的 TFLOPS 只是上限，真实吞吐还要乘以 utilization 和 scaling efficiency。于是我们需要理解 batch size、算子形状、显存带宽、kernel launch、CPU 调度和多卡同步如何让 GPU 被喂饱或饿住。

第二，既然计算前必须有数据，就必须讨论存储层级和读取模式。容量只回答“放不放得下”，不能回答“能否稳定按 1GB/s、10GB/s 或更高速度供给”。大量小文件会把吞吐问题变成元数据问题；远端对象存储会把读取问题变成网络往返和尾延迟问题；checkpoint 会把训练推进问题变成写入带宽、fsync 语义、分片合并和恢复时间问题。所以本章会把数据加载、数据打包、热冷分层、本地 NVMe 缓存、checkpoint 写回放在同一条链路里看。

第三，既然训练和推理都要搬运数据，就必须讨论 CPU 内存到 GPU 显存之间的 Host-to-Device 路径。样本从磁盘进入 Page Cache，再进入用户态 buffer，经过解码、增强、batch 拼接，最后通过 pinned memory 和 DMA 进入 GPU；NUMA 拓扑又会决定 CPU、内存、GPU、NIC 之间是不是走了本地路径。如果 pinned memory 没开、batch 太碎、worker 绑错 NUMA node，即使存储和 GPU 都很强，H2D 仍然可能成为关键路径。

第四，既然多卡和多机任务需要共同推进，就必须讨论网络。数据并行需要 AllReduce，张量并行需要高频中间结果通信，Pipeline 并行需要 stage 之间传激活，MoE 需要 all-to-all token dispatch。在线推理虽然不一定做梯度同步，但会跨网关、路由、向量库、reranker、数据库、外部工具和日志系统；每个服务的 p99 都可能叠加成用户感知的卡顿。于是“网络”不只是带宽，还包括延迟、抖动、拓扑、重试、超时、拥塞和尾延迟放大。

第五，既然所有资源都可能重叠工作，也可能互相等待，就需要关键路径和木桶效应。训练 step 不能只看 forward / backward，要拆成 load、preprocess、h2d、forward、backward、sync、update、checkpoint；推理请求不能只看模型执行，要拆成 queue、tokenize、prefill、decode、postprocess、downstream、return。只有把时间拆开，才能判断优化 tokenizer 省 2ms 是否值得，或者减少 AllReduce 50ms 是否比换更强 GPU 更有效。

2. 学习目标

资源边界
区分算力、存储、网络在 AI 系统中的职责边界，并理解它们为什么不是平行名词。
链路拆解
把训练 step 和推理请求拆成可观测的时间段，用关键路径判断优化优先级。
瓶颈识别
识别 GPU 利用率低、step time 抖动、扩卡收益差、TTFT 高、p99 高背后的资源原因。
工程习惯
建立“先看资源，再看模型；先拆链路，再谈优化”的排查习惯。

3. 先建立一个总图：AI 系统不是只有模型

很多初学者理解 AI 系统时，会把注意力集中在模型本身：

输入 -> 模型 -> 输出

但在真实工程里，模型只是系统链路中的一段。更真实的视角是：

数据 / 请求
   ↓
存储系统
   ↓
CPU / 内存 / 数据预处理
   ↓
GPU 显存
   ↓
GPU 计算
   ↓
网络通信 / 下游服务
   ↓
结果写回 / 响应返回

工程提醒：模型越大、数据越多、并发越高，系统问题就越不像单纯的模型问题，而越像资源调度、数据供给和尾延迟治理问题。

4. 算力、存储、网络不是平行名词，而是一条链路

以训练为例，一个 batch 的最简路径通常是：

存储 -> CPU 内存 -> 数据解码 / 预处理 -> GPU 显存 -> 前向计算 -> 反向计算 -> 梯度同步 -> 参数更新 -> checkpoint 写回

以推理为例，一次请求的最简路径通常是：

入口请求 -> 网关 -> 路由 -> 队列 -> tokenizer -> 模型加载 / 缓存 -> GPU prefill -> GPU decode -> 后处理 -> 响应返回

如果是 RAG 应用，推理链路还会更长：

用户问题 -> 网关 -> query rewrite -> embedding 模型 -> 向量检索 -> 文档召回 -> rerank -> prompt 拼接 -> LLM 推理 -> 输出流式返回
第一判断：系统吞吐近似受 min(计算吞吐上限, 存储供给上限, 网络供给上限) 约束。它不是严格数学模型，但非常适合作为工程排查入口。
概念含义AI 系统中的例子
总工作量整个系统所有模块加起来做了多少事情数据读取、解码、前向、反向、同步、写 checkpoint
关键路径决定一次任务完成时间的最长依赖链GPU 等数据、AllReduce 等最慢机器、请求排队等待

优化系统时，不能只看某个局部模块有没有变快，而要看它是否在关键路径上。一次推理总延迟 200ms，如果 tokenizer 只有 3ms，把它优化到 1ms 只能省 2ms；如果 GPU decode 或下游检索各占几十毫秒，优先级通常更高。

5. 算力在 AI 系统里到底意味着什么

第一层：芯片理论计算能力

指标含义常见场景
FLOPS每秒浮点运算次数通用计算能力描述
TFLOPS每秒万亿次浮点运算GPU 规格表常见指标
Tensor Core 吞吐专门执行矩阵乘的硬件单元吞吐深度学习训练 / 推理
INT8 / FP16 / BF16 / FP8 吞吐不同数值精度下的计算能力推理量化、混合精度训练

第二层：可利用计算能力

真实任务能否把芯片吃满，取决于 batch 是否足够大、张量形状是否适合硬件、算子是否高效、内存访问是否连续、数据是否及时送到设备、CPU 是否成为调度瓶颈。

常见现象：GPU 理论很强，但利用率只有 20% - 40%。这时不要立刻判断 GPU 不行，更可能是 GPU 没有被喂饱。

第三层：系统级有效算力

有效算力 = 理论算力 × 利用率 × 扩展效率
表现真正含义典型处理方向
单卡跑不动设备本身计算或显存不够换更强 GPU、混合精度、模型压缩、ZeRO、offload
GPU 利用率低设备没有被喂饱优化 dataloader、增大 batch、缓存数据、融合算子
扩卡收益差设备之间协同效率差优化通信、调整并行策略、减少同步频率、改善网络拓扑

计算密集型、访存密集型与通信密集型

类型主要瓶颈例子
计算密集型矩阵乘法速度Transformer 中的大型 GEMM
访存密集型显存带宽 / cache 命中LayerNorm、embedding lookup、部分小 batch 推理
通信密集型网络带宽和延迟分布式 AllReduce、参数切分、MoE 路由

一个直觉指标是 计算强度 = 计算量 / 数据搬运量。计算强度高，通常更容易吃满算力；计算强度低，就容易被内存带宽限制。

6. 存储为什么经常被低估

AI 工程师很容易直觉性地盯着 GPU，但存储问题常常才是第一瓶颈。因为数据要先到，训练和推理才有东西可算。

层次典型介质特征常见用途
冷存储对象存储、数据湖、归档存储容量大、便宜、延迟高原始数据、历史 checkpoint、离线归档
热存储本地 SSD、NVMe、并行文件系统吞吐高、延迟较低、成本较高训练缓存、局部热点模型、临时数据集
主存DRAM延迟低、容量有限dataloader、预处理、中间缓存
显存HBM / GDDR带宽极高、容量昂贵权重、激活、梯度、KV Cache
分布式缓存Redis、Memcached、Feature Store 缓存访问快、需要一致性策略在线特征、热文档、路由元数据

读取模式比容量更关键

对象存储很便宜，不代表训练时直接读就足够。训练还要看吞吐、延迟、小文件数量、随机读取、解压解码、多机并发读取、checkpoint 写入是否干扰读取。

大量小文件会把读取问题变成元数据问题。训练数据经常被打包成 WebDataset tar shards、TFRecord、Parquet、LMDB、Arrow 或自定义二进制 shard，目标是减少随机访问，把细碎 IO 变成更适合训练的顺序读取和批量读取。

数据加载链路

远端存储 / 本地磁盘
  -> 文件读取
  -> 解压
  -> 解码
  -> 数据增强
  -> batch 拼接
  -> pinned memory
  -> Host-to-Device 复制
  -> GPU 显存
瓶颈点表现可能原因
文件读取慢dataloader 等待远程存储延迟高、小文件太多
CPU 解码慢CPU 使用率高，GPU 等待图片 / 视频解码过重
数据增强慢worker 忙不过来augment 太复杂，worker 数不足
H2D 慢GPU 计算前等待pinned memory 未使用，batch 太碎
cache 不命中step time 抖动热数据没有缓存，远端存储波动

Page Cache / NUMA 如何影响数据到 GPU

训练数据从文件系统读出时，通常先经过 Linux Page Cache。热数据命中时 t_load 会下降；内存不足、checkpoint 写入产生大量脏页回写、数据集工作集远大于可用内存时，Page Cache 会频繁失效，表现为 step time 抖动、IO wait 升高或 major page fault 增加。完整机制可继续阅读 §0b。

机制影响点典型症状工程边界
Page Cachet_load、重复读取、checkpoint 写回干扰epoch 初慢后快、周期性 IO 抖动适合热数据；不能把它当稳定缓存
pinned memoryt_h2d、异步 H2D 重叠GPU compute 前等待、H2D copy 时间高过量 pin 会挤压 Page Cache
NUMA affinityCPU 预处理、H2D、GPU / NIC 路径同型号节点吞吐差异、跨 socket 带宽下降需要结合拓扑绑定
边界提醒：pin_memory=True 只是让 Host 内存适合 DMA 和异步复制，不自动保证 dataloader worker、内存分配、GPU、NIC 都在正确 NUMA 路径上。

checkpoint 也是存储问题

大模型 checkpoint 可能包含模型权重、optimizer state、scheduler state、dataloader state、random seed、分布式 rank 状态和 ZeRO / FSDP 分片状态。文件可能达到几十 GB 到几百 GB。常见优化是异步 checkpoint、分片 checkpoint、先写本地 NVMe 再后台上传对象存储、降低保存频率、只保存必要状态或使用增量 checkpoint。

7. 网络为什么不只是“把包发过去”

在 AI 系统里，网络至少影响三类事情：训练数据读取、分布式训练通信、在线推理调用链路。因此，网络既可能影响训练吞吐，也可能影响线上尾延迟。

数据并行梯度 AllReduce和模型参数 / 梯度规模相关
张量并行中间激活 / partial result高频、低延迟要求高
Pipeline 并行stage 之间传激活与 micro-batch 和层切分相关
ZeRO / FSDP参数、梯度、optimizer state 分片通信通信复杂度高

在线推理经常不是只有一次模型调用。LLM 应用可能经过客户端、API 网关、鉴权、限流、prompt 组装、模型服务、向量库、reranker、工具调用、数据库、日志系统和流式响应。一个下游服务平均 20ms 不一定可怕，可怕的是 p99 可能是 500ms，并且会被重试和串联调用放大。

严重风险：没有超时、熔断和降级的 RAG / Agent 链路，少数慢依赖会把整体 p99 拉到不可接受的范围，甚至通过重试放大负载。

8. 三类资源如何形成“木桶效应”

现实中的 AI 系统瓶颈通常长这样：GPU 算力强但数据加载慢；模型放得下显存但多机同步太慢；在线推理单实例很快但扩容慢、冷启动重；checkpoint 写入太慢导致训练周期性卡顿；KV Cache 占满显存导致并发上不去；网络 p99 抖动导致整体服务 p99 被放大。

算力桶板很高
存储桶板中等
网络桶板较低
=> 系统出水速度仍然取决于最短那块板
问题说明
GPU 是否在等数据？如果是，先查存储和 dataloader。
GPU 是否在等通信？如果是，先查 AllReduce、拓扑、并行策略。
请求是否在排队？如果是，先查容量、并发、batching、限流。
延迟是否集中在下游？如果是，先查向量库、数据库、工具调用。
p99 是否远高于 p50？如果是，先查抖动、重试、热点、GC、冷启动。
阶段常见瓶颈说明
数据准备存储、CPU、ETL数据清洗、格式转换、去重、切分
预训练GPU、网络、checkpoint大规模并行、长时间训练、容错
微调显存、数据加载数据量较小但实验频繁
离线评测调度、存储、推理吞吐大量模型版本和数据集组合
在线推理显存、KV Cache、尾延迟并发、流式输出、SLA
RAG 应用向量库、rerank、网络多服务链路叠加
Agent 应用工具调用、外部 API不确定性和长链路放大

9. 一个简单的定量分析框架

面对训练或推理吞吐问题时，先问四个量：每个样本 / 请求大约需要多少计算？需要搬多少数据？每秒能提供多少带宽？链路里哪一段最容易抖动？

训练 step 拆解

step time ≈ t_load + t_preprocess + t_h2d + t_forward + t_backward + t_sync + t_update + t_checkpoint
符号含义常见瓶颈
t_load从存储读取数据远程 IO、小文件、元数据
t_preprocess解码、清洗、增强CPU 不够、worker 不够
t_h2dCPU 到 GPU 拷贝PCIe、pinned memory、batch 太碎
t_forward前向计算GPU 算力、算子效率
t_backward反向计算显存、重计算、梯度规模
t_sync梯度 / 参数同步网络、拓扑、并行策略
t_updateoptimizer 更新optimizer state、显存带宽
t_checkpoint保存状态存储写入、分片合并

推理延迟拆解

request latency ≈ t_queue + t_tokenize + t_prefill + t_decode + t_postprocess + t_downstream + t_return
符号含义说明
t_queue排队时间并发高时显著增加
t_tokenize分词时间prompt 很长时不可忽视
t_prefill处理输入 prompt与输入 token 数相关
t_decode逐 token 生成与输出 token 数相关
t_downstream下游调用向量库、数据库、工具、外部 API
t_return返回给客户端网络、流式传输、客户端连接
LLM 推理关键指标：TTFT 决定用户多久看到模型开始回答，TPOT 决定模型输出是否流畅。

带宽与显存估算

4MB × batch size 256 = 1024MB ≈ 1GB
目标 step time 500ms => 至少需要 2GB/s 稳定数据供给
训练显存 ≈ 参数 + 梯度 + optimizer state + 激活 + 临时 buffer
推理显存 ≈ 模型权重 + KV Cache + 临时 buffer

有时模型能加载进显存，但并发一高就 OOM。这不是模型加载问题，而是 KV Cache 和运行时状态随上下文长度、并发数一起增长。

10. 训练场景中的典型瓶颈

GPU 利用率锯齿化

表现为 GPU 利用率一会儿 90%，一会儿 10%，step time 忽快忽慢。常见原因包括 dataloader worker 不足、数据在远程对象存储上、小文件太多、CPU 解码或数据增强太慢、batch 构造复杂、没有预取、H2D 没有和计算重叠。

单卡很快，多卡变慢

表现为 1 卡正常，8 卡没有明显加速，16 卡以后速度反而下降。常见原因包括 AllReduce 通信太重、batch size 切得太小、多机网络带宽不足、节点间拓扑差异大、慢卡或慢节点拖住整体、checkpoint 多 rank 写入冲突。

checkpoint 导致周期性卡顿

表现为每隔 N step 训练突然卡住几十秒甚至几分钟。排查时分别记录 checkpoint 前后耗时、本地写入和远端上传耗时；优化方向包括降低保存频率、异步保存、分片 checkpoint、避免所有 rank 同时写同一个元数据热点。

flowchart TD
  A[训练变慢] --> B{GPU 利用率低?}
  B -->|是| C[查 load/preprocess/H2D/batch]
  B -->|否| D{单卡快多卡慢?}
  D -->|是| E[查 AllReduce/拓扑/慢 rank]
  D -->|否| F{周期性卡顿?}
  F -->|是| G[查 checkpoint/日志/GC/定时任务]
  F -->|否| H[做端到端 profile]
  C --> I[小文件打包/本地缓存/预取/pinned memory]
  E --> J[NCCL 配置/通信重叠/并行策略]
  G --> K[异步或分片 checkpoint]
训练排查顺序：先看 GPU utilization 曲线是否周期性掉下去，再看 CPU、dataloader 等待、存储吞吐、H2D 时间、通信时间和每个 rank 的耗时差异。

11. 推理场景中的典型瓶颈

首 token 慢

用户提交问题后很久才看到第一个 token，但开始输出后速度还可以。常见原因是请求排队、prompt 太长、prefill 时间长、模型冷启动、tokenizer 或 prompt 拼接慢、RAG 检索 / rerank 慢、上游网关或鉴权慢。

输出 token 慢

第一个 token 不慢，但后续一个字一个字慢慢出来。常见原因是 decode 阶段算力不足、batch 调度不合理、KV Cache 压力大、显存带宽瓶颈、输出太长、量化或 kernel 实现不佳。

并发一高就 OOM

单请求正常，并发高时显存爆掉。常见原因是 KV Cache 随并发和上下文增长、batch 太大、没有限制 max context length、长短请求混排、没有显存池化或分页管理。

平均延迟正常，p99 很差

大多数请求很快，但少数请求极慢。常见原因包括下游服务偶发抖动、冷启动、缓存击穿、大 prompt 或超长输出、网络重试、GC 或资源争抢、长请求阻塞短请求。

现象优先检查典型优化
TTFT 高queue、tokenize、prefill、RAG控制 prompt、缓存上下文、并行 RAG、减少冷启动
TPOT 高decode、batch、KV Cache、显存带宽continuous batching、量化、KV 管理、限制输出长度
并发 OOMKV Cache、上下文长度、batch 上限paged attention、长短请求分级、并发上限
p99 差慢依赖、冷启动、缓存击穿、重试超时、熔断、降级、端到端 trace

14. 工程案例

为什么 GPU 很强，训练还是慢？

某团队用 8 张 GPU 训练图像模型，GPU 利用率只有 35% 左右。监控显示 GPU utilization 周期性从 90% 掉到 10%，CPU utilization 接近 100%，step time 波动很大，存储读取是大量小文件随机读取。

对象存储 -> 小图片读取 -> CPU 解码 -> 数据增强 -> batch -> GPU

真正瓶颈不是 GPU，而是小文件远程读取、CPU 解码和数据增强。团队把小文件打包成 shard，将热数据缓存到本地 NVMe，增加 dataloader worker，简化部分 CPU 数据增强，使用 pinned memory 并开启预取，最终 GPU 利用率和 step time 稳定性明显改善。

为什么 RAG 应用平均很快，但用户仍然觉得卡？

某 RAG 问答系统平均响应时间只有 1.2 秒，但用户反馈经常卡住。进一步看指标：

p50: 1.0s
p90: 2.5s
p99: 12s

链路拆解后发现少数文档从远程存储加载非常慢：

用户问题
  -> embedding: 80ms
  -> 向量检索: 120ms
  -> 文档加载: 50ms - 8s 不等
  -> rerank: 200ms
  -> LLM: 700ms - 2s

优化方向是给文档加载增加缓存、设置远程存储超时、对慢文档降级、给检索链路做 trace、单独监控 p99、将热门文档放到热存储。

案例结论：GPU 慢不一定是 GPU 的问题；平均延迟好不代表用户体验好。系统慢，先看链路最短板和尾延迟来源。

15. 常见误区与优化原则

误区：GPU 利用率低，就是 GPU 不行
正确问法：GPU 是在计算，还是在等待？如果在等待，它等的是数据、通信，还是队列？
误区：对象存储够大，就足够做训练存储
正确问法：数据是大文件顺序读，还是小文件随机读？多机并发读是否稳定？
误区：网络只影响分布式训练
正确问法：请求链路跨了多少服务？每个服务的 p99 是多少？有没有重试和超时放大？
误区：平均延迟低，用户体验就好
正确问法：慢请求来自哪里？是长 prompt、长输出、冷启动、下游抖动，还是排队？
误区：扩卡一定能提升训练速度
正确问法：新增 GPU 带来的计算收益，是否大于新增通信代价？
误区：显存能放下模型，就能支撑高并发
正确问法：模型权重占多少？KV Cache 在目标并发和上下文长度下占多少？

资源优化的基本原则

  1. 先定位瓶颈，再优化；没有测量，就没有优化。
  2. 优先补短板，不要继续抬高已经足够高的桶板。
  3. 让资源重叠工作：CPU 预处理下一批，GPU 计算当前 batch，网络异步同步，后台写 checkpoint。
  4. 把随机访问变成大块、顺序、批量、可预取的访问。
  5. 控制尾延迟：超时、熔断、降级、缓存、限流、长短请求隔离、热点预加载。
  6. 把成本当成资源指标：单位 token 成本、单位样本训练成本、单位 QPS 成本、失败重跑成本、存储和网络成本。
成本风险：一个更快但贵很多的方案，不一定是更好的方案；AI Infra 优化必须同时看效果、延迟、稳定性和成本。

本章最重要的思想：AI 系统不是模型孤岛，而是一条资源链路。算力、存储、网络共同决定上限。优化前先拆链路，拆完再找最短板。

练习题

  1. 为什么说 AI 系统吞吐通常由最慢的一段决定？请用水管或木桶模型解释。
  2. 对象存储、SSD、主存、显存分别适合放什么类型的数据？
  3. 为什么网络既会影响训练吞吐，也会影响线上推理时延？
  4. 请把一个训练 step 拆成至少 8 个时间段，并说明每段可能的瓶颈。
  5. 为什么 GPU 利用率低不一定说明 GPU 性能差？
  6. 什么是 TTFT？什么是 TPOT？它们分别影响用户的什么体验？
  7. 一个推理服务 p50 为 800ms，p99 为 9s。你会如何排查？
  8. 某 LLM 服务模型权重可以放进显存，但并发升高后 OOM。请分析可能原因。

参考答案要点

  • 吞吐由最慢的一段决定，因为后续阶段必须等待前面阶段提供输入，整体吞吐无法超过最慢阶段的稳定供给能力。
  • 对象存储适合原始数据和归档；SSD / NVMe 适合训练热数据和临时缓存；主存适合 dataloader 队列和中间缓存；显存适合权重、激活、梯度和 KV Cache。
  • 网络在训练中负责数据读取、梯度同步、参数广播、分布式 checkpoint；在推理中负责网关、模型服务、向量库、数据库、工具调用和流式响应。
  • 训练 step 可拆成 load、preprocess、h2d、forward、backward、sync、update、checkpoint。
  • GPU 利用率低说明 GPU 没有持续计算，原因可能是数据加载慢、CPU 预处理慢、H2D 慢、通信等待、队列等待、batch 太小或算子调度低效。
  • TTFT 是首 token 时间，决定用户多久看到模型开始响应；TPOT 是每个输出 token 的生成时间，决定输出是否流畅。
