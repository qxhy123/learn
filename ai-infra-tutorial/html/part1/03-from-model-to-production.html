1. 第一性原理拆解：从模型实验到生产系统

拆 — 不可化简的问题

把“模型上线”“MLOps”“LLMOps”“Model Registry”“CI/CD”“灰度发布”这些名字先拿掉，本章真正要处理的不可化简问题只有一个：一个由数据、代码、参数、随机性和运行环境共同生成的函数，怎样才能从一次偶然成功的实验，变成可以被多人、多个系统、多个版本、长期、低风险地使用的生产能力。实验里的模型不是普通二进制程序。普通后端服务的行为主要由代码决定，而模型行为同时受训练数据、切分方式、标注口径、特征逻辑、tokenizer、训练超参、checkpoint、推理引擎、prompt、RAG 索引、线上流量分布共同影响。也就是说，模型不是一个孤立文件，而是很多状态变量在某个时间点的合成结果。只要其中一个变量没有被记录，后来看到的线上质量、延迟、成本或安全问题就可能失去因果解释。

AI 系统最大的工程鸿沟，通常不在“模型写出来”，而在“模型要被稳定交付”。从第一性原理看，这句话背后的根因是：实验追求发现一个有效信号，生产追求把这个信号变成可重复、可审计、可替换、可止损的服务。实验阶段允许手工选择数据路径、临时改一行参数、用截图记录指标、把 checkpoint 放在个人目录，因为它的主要对象是“我此刻能否证明想法成立”。生产阶段面对的对象是真实用户和业务系统，错误不再只是训练失败，而可能是错误答案、隐私泄露、成本暴涨、p99 延迟超标、召回质量下降、旧能力回归、灰度流量污染反馈数据。于是，任何生产链路都必须回答四个基本问题：它从哪里来，凭什么上线，出事如何发现，坏了如何退回。

这个不可化简问题还有一个容易被忽略的维度：模型交付不是一次性动作，而是闭环。一次发布改变线上行为，线上行为又改变后续数据，后续数据再改变下一轮模型。推荐、风控、搜索、RAG、大模型 Agent 都有这种反馈结构。只要反馈没有被观测和治理，系统就会从“可解释的工程系统”退化成“看起来在运行但无法归因的黑箱”。因此，本章的主线不是把 notebook 包成 API，而是把一个会随时间漂移的统计系统纳入工程控制面：让每次训练、评测、注册、部署、观测、反馈都有稳定接口、版本边界和决策证据。

推 — 从这个问题如何推导出每个机制

从“模型是多状态变量合成结果”出发，第一步必然是版本化。因为模型质量无法只靠 checkpoint 解释，所以需要记录代码版本、数据版本、配置版本、镜像版本、随机种子、tokenizer 版本和评测集版本；这就推导出数据版本管理、实验管理、Artifact Store 和 Model Registry。没有这些机制，所谓复现只能依赖人的记忆，任何线上回归都很难定位到是哪一个变量改变了。第二步是任务化和调度化。只要训练不再是个人机器上的手动脚本，就必须把训练过程描述成一个 job：资源规格、镜像、入口命令、输入数据、输出路径、日志和指标都要被平台接管；这就推导出训练任务平台、GPU 队列、资源配额、失败重试和 checkpoint 保存。

第三步是评测门禁。模型从实验进入生产，不能只问离线 accuracy 是否提升 0.5%，还要问 Golden Set 是否回归、线上相似流量是否通过、p95/p99 延迟是否满足 SLA、单请求成本是否在预算内、安全策略是否被破坏。于是，评测层不是训练脚本末尾打印的一行指标，而是发布前的决策系统。第四步是制品化。生产服务不能依赖“某个目录里有一个 best.pt”，而需要把权重、配置、tokenizer、pre/post-processing 代码、runtime 依赖、签名、血缘元数据打成可追踪制品。只有制品边界清楚，部署层才能选择 staging、blue-green、canary、shadow、rollback 这些发布策略。

第五步是服务化和观测化。模型一旦变成 API 或批处理服务，就必须面对吞吐、队列、batching、显存、冷启动、超时、降级和多租户隔离。线上质量又不能只靠系统指标判断，因为 200 OK 也可能返回错误答案，所以需要同时观测 latency、error rate、token/s、GPU utilization、输入分布、输出质量、人工反馈、业务指标和成本。第六步是反馈闭环。线上样本、用户标注、失败 case、漂移信号会成为下一轮训练和评测的输入；如果没有反馈治理，坏数据会污染训练集，灰度实验会污染指标解释，prompt 或索引变更会被误认为模型变更。由此可以看到，本章所有机制并不是工具清单，而是从同一个不可化简问题逐层推导出来的控制结构：先让来源可追踪，再让执行可重复，再让上线有证据，再让运行可观测，最后让反馈可治理。

2. 学习目标与核心问题

完成本章学习后，你应能理解 notebook、训练脚本、训练任务、模型制品、推理服务之间的演化关系，并能说清一个 AI 项目从实验到生产通常要补齐哪些基础设施层。

四个层级
区分“模型能跑”“模型可复现”“模型可交付”“系统可运营”。
端到端链路
用系统视角描述数据、训练、评测、注册、部署、推理、监控和反馈。

学习这一章时，不要只问“模型怎么部署”，更应该问：“一个模型从实验结果变成可持续运行的生产系统，中间要经过哪些工程化转化？”

转变实验阶段生产阶段
使用者研究员 / 算法工程师自己团队、业务系统、真实用户
目标验证想法是否有效稳定、低延迟、低成本地提供服务
关注点指标、样例、loss、accuracy可复现、可发布、可回滚、可观测、可治理
运行方式手动运行、临时代码自动化流水线、服务化、平台化
风险处理出错就重跑出错要降级、回滚、告警、止损
一句话总结：实验是证明模型可能有用，生产是证明模型可以被可靠地使用。

3. 从 notebook 到生产，真正增加了什么

一个最初的 AI 项目通常从几段实验代码开始：

读数据
  -> 数据预处理
  -> 定义模型
  -> 训练模型
  -> 查看评测指标
  -> 保存 checkpoint

在 notebook 或本地脚本阶段，工程师关心数据能不能读进来、模型能不能收敛、指标有没有提升、某几个 case 是否变好、checkpoint 能不能保存。这时系统启动快，但通常只适合单人、单机、低频、手工分析、无严格 SLA 的探索。

新增能力解决的问题典型组件
数据版本管理这次训练到底用了哪份数据Dataset Registry、数据快照、数据血缘
实验管理哪次实验用了什么参数、结果如何Experiment Tracking、Metric Logger
训练任务调度训练不能只靠手动跑脚本Job Scheduler、K8s、Slurm、Ray、Argo
资源管理GPU/CPU/内存/存储不能随便抢Resource Quota、队列、优先级
模型制品管理checkpoint 不能散落在个人目录Model Registry、Artifact Store
自动评测不能只看训练集 lossOffline Eval、Regression Test、Golden Set
灰度与回滚新模型出问题要能快速止损Canary、Shadow、Blue-Green、Rollback
线上观测线上效果、延迟、错误要可见Metrics、Logs、Tracing、Dashboard
反馈闭环线上数据反哺下一轮迭代Feedback Store、Retraining Pipeline

AI Infra、MLOps、LLMOps 不是互相割裂的概念，而是同一条生产化链路上的不同关注层：AI Infra 更偏算力、存储、网络、调度和推理集群；MLOps 更偏数据、训练、评测、注册、发布、监控；LLMOps 更偏 Prompt、RAG、Agent、Embedding、向量库、人工反馈和安全治理。

4. 从 notebook 到生产的四个演化阶段

阶段 0：notebook 实验
数据路径写死，参数写在 cell 里，结果截图发群，checkpoint 存在本地。目标是快速证明想法可能有效。
阶段 1：训练脚本化
train.py、config.yaml、requirements.txt、固定输出目录。目标是从交互式实验变成可重复运行的任务。
阶段 2：训练任务平台化
用户提交训练配置，平台分配 GPU，拉取代码和数据，启动容器，记录日志和指标，保存 checkpoint，触发评测任务。
阶段 3：模型交付生产化
训练完成后自动评测、注册制品、staging 验证、灰度发布、线上观测，并能放量或回滚。
python train.py \
  --config configs/resnet50.yaml \
  --dataset s3://bucket/datasets/v3 \
  --output ./outputs/exp_2026_04_24
训练任务需要记录的信息示例
代码版本git commit hash
数据版本dataset_v2026_04_20
配置版本config/resnet50_lr1e-4.yaml
镜像版本training-image:2026.04.24
资源规格8 x A100 80GB
随机种子seed=42
输出制品checkpoint、tokenizer、config、日志
阶段判断：训练脚本化只解决“能重复启动”，平台化才开始解决“可追踪、可协作、可恢复、可审计”。

5. 一个端到端 AI 生产闭环

一个典型 AI 项目从实验到生产，可以抽象成数据采集、清洗标注、数据版本化、样本构造、训练任务、离线评测、模型制品注册、staging 部署、灰度发布、线上推理、监控日志 trace、用户反馈、人工标注、线上样本回流、重新训练、重新评测、重新发布。

flowchart TD
  A[数据采集与清洗] --> B[数据版本化]
  B --> C[训练任务]
  C --> D[离线评测与回归测试]
  D --> E{质量门禁}
  E -->|通过| F[模型制品注册]
  E -->|失败| B
  F --> G[Staging 部署]
  G --> H[Shadow 或 Canary]
  H --> I[线上推理]
  I --> J[监控 日志 Trace 反馈]
  J --> K{是否异常}
  K -->|是| L[回滚 降级 止损]
  K -->|否| M[反馈样本治理]
  M --> B

这条链路有两个关键特点：第一，它不是单向流程，而是闭环。模型表现会随着数据分布、用户行为、业务规则、外部环境变化而变化；第二，它不是单版本系统，而是多版本并存系统。生产环境里通常会同时存在多个数据集、特征工程、模型、tokenizer、prompt、向量索引、推理镜像和服务配置版本。

对象可能同时存在的版本
数据集train_v1、train_v2、golden_set_v3
模型model_v12、model_v13、model_v14_canary
Tokenizertokenizer_v1、tokenizer_v2
Promptprompt_v8、prompt_v9
向量索引index_2026_04_01、index_2026_04_20
推理镜像inference-server:1.8、inference-server:1.9
服务配置batch_size=8、batch_size=16
版本风险：当线上效果变差时，必须知道到底是哪一个版本变了：模型、数据、特征逻辑、tokenizer、prompt、索引、推理框架，还是流量分布。

6. “能跑”与“可运营”的差异

一个 notebook 里的模型能跑，不代表它已经是一个可运营系统。可运营至少意味着输入输出稳定、运行环境稳定、结果可复现、版本可追踪、发布可控制、故障可定位、质量可观测、成本可估算、权限可治理、出错可回滚。

能力层级含义判断标准
能跑代码在某个环境下能执行作者本人能跑通
可复现别人用同样配置也能得到接近结果数据、代码、参数、环境可追踪
可交付模型可以进入标准发布流程有评测、有制品、有版本、有审批
可运营模型能长期稳定服务真实用户有监控、告警、灰度、回滚、成本治理
模型制品：model_v17
代码版本：commit 8f3a21c
数据版本：dataset_v2026_04_20
配置版本：config_v12
训练镜像：training:2026.04.24
离线评测：通过
staging 测试：通过
灰度策略：5% -> 20% -> 50% -> 100%
回滚目标：model_v16
监控指标：latency、error_rate、quality_score、cost_per_request
交付判断：可交付的核心不是“模型文件存在”，而是这个模型文件背后的来源、质量证据、运行方式和风险控制都清楚。

7. 生产化后，AI 系统到底由哪些部分组成

生产中的 AI 系统通常不是“模型 + API”，而是由数据层、训练层、评测层、制品层、部署层、推理层、观测层、反馈层、治理层组成。

flowchart LR
  A[数据层] --> B[训练层]
  B --> C[评测层]
  C --> D[制品层]
  D --> E[部署层]
  E --> F[推理层]
  F --> G[观测层]
  G --> H[反馈层]
  H --> A
  I[治理层 权限 审计 成本] -.-> A
  I -.-> B
  I -.-> D
  I -.-> F
  I -.-> G
数据层
回答模型从哪里学来，管理原始数据、清洗数据、标注数据、训练/验证/测试集、Golden Set、线上反馈样本和数据质量报告。
训练层
把本地命令变成平台 job，包含资源申请、队列排队、任务重试、日志采集、指标记录、checkpoint 和失败归因。
评测层
判断模型是否值得上线，覆盖质量、回归、性能、安全和成本。
制品层
把模型从一个文件变成有身份、有来源、有证据、有生命周期的资产。
部署与推理层
把模型变成线上可调用服务，处理路由、batching、缓存、限流、降级、扩缩容和多版本共存。
观测与反馈层
记录系统指标、模型质量、链路诊断信息，并把线上样本治理后带回训练和评测。
model_v17/
  model.safetensors
  config.json
  tokenizer.json
  preprocessor.json
  eval_report.json
  serving_config.yaml
  requirements.txt
  metadata.json

其中 metadata.json 应记录模型名、版本、创建时间、代码版本、数据版本、训练任务、评测报告、base model、owner 和审批人。没有这些信息，制品就只是文件，不是生产资产。

8. 为什么模型交付要额外引入评测与发布

普通后端服务发布主要关注功能是否正确、接口是否兼容、性能是否稳定、错误率是否可控。模型发布还要额外关注模型质量是否退化、离线评测是否可信、评测集是否被污染、线上流量分布是否变化、局部场景是否变差、延迟和成本是否升高、输出是否符合安全规范、是否可以快速回滚。

评测类型关注问题示例指标
质量指标（传统 ML）模型是否有效Accuracy、AUC、NDCG、Recall@K、人工评分；翻译/摘要可用 BLEU/ROUGE
质量指标（LLM 推荐）大模型主流任务的真实质量MMLU / MMLU-Pro / BBH（知识推理）+ GSM8K / MATH（数学）+ HumanEval / SWE-bench（代码）+ MT-Bench / AlpacaEval 2.0 / Arena-Hard（指令跟随）+ Chatbot Arena（真人偏好）。BLEU/ROUGE 在 LLM 主流任务上与人类质量判断相关性低（多份研究 Pearson < 0.3），不应作为主指标
RAG / Agent 专用检索系统、Agent 系统的端到端质量Ragas / TruLens / RAGChecker（RAG）；GAIA / AgentBench / τ-bench（Agent）
回归测试新模型是否把旧模型做对的东西做错Golden Set、关键场景 case、行为约束
性能指标是否满足线上服务约束p50/p95/p99、QPS、GPU 利用率、TTFT、TPOT、ITL、token/s
安全合规是否越界或违规ToxiGen / AdvBench / HarmBench / PromptBench；隐私泄露、违规内容、越权工具调用、prompt injection 防护
成本指标效果收益是否值得付出单请求成本、token 成本、GPU 小时、缓存命中率
BLEU / ROUGE 在 LLM 时代的边界：仍适用于翻译、抽取式摘要等"答案空间小、词面重叠合理"的场景；但对话、推理、代码、Agent 这些主流 LLM 任务上 BLEU/ROUGE 与人评相关性低，应改用任务 benchmark + LLM-as-judge + 业务 Golden Set 的分层组合。LLM-as-judge 工程化要点：固定 judge 模型版本、swap A/B 顺序消除 position bias、长度归一化避免 length bias、人工样本周期校准（一致性 > 0.8）。
是否上线 = 质量达标
        AND 回归测试通过
        AND 延迟可接受
        AND 成本可接受
        AND 安全合规通过
        AND 有回滚方案
stateDiagram-v2
  [*] --> Trained: 训练完成
  Trained --> OfflineEval: 离线评测
  OfflineEval --> Rejected: 门禁失败
  Rejected --> Trained: 修复或重训
  OfflineEval --> Registered: 门禁通过
  Registered --> Staging: 注册候选模型
  Staging --> Shadow: 影子流量
  Shadow --> Canary: 小流量灰度
  Canary --> FullRelease: 逐步放量
  Canary --> Rollback: 指标异常
  FullRelease --> Observing: 线上观察
  Observing --> Rollback: 质量/成本/延迟异常
  Observing --> [*]
上线风险：没有评测门禁、灰度和回滚的模型上线，本质上是在生产环境里做盲测。

9. 模型发布和普通代码发布有什么不同

维度普通代码发布模型发布
主要变化对象代码逻辑参数、数据分布、模型结构、Prompt、索引
正确性判断单元测试、集成测试离线评测、人工评测、线上实验
输出稳定性通常确定性更强可能概率性、非确定性更强
质量风险功能 bug整体退化、局部退化、偏差、幻觉
版本依赖代码和配置代码、数据、模型、tokenizer、特征、索引、prompt
回滚对象服务版本服务版本 + 模型版本 + 数据/索引/prompt 版本
线上监控错误率、延迟、资源还要看质量、漂移、安全、成本

所以模型交付系统要比普通 CI/CD 多一个核心能力：质量证据管理。每次发布都必须能回答为什么这个模型可以上线、在哪些评测集上通过、比当前线上版本好在哪里、在哪些场景可能更差、如果出问题回滚到哪个版本、谁批准了这次发布。

10. 生产环境中的四类典型问题

结果不可复现

现象是上周训练的模型效果很好，这周重新跑就不行了。常见原因包括数据变了但没有版本记录、代码分支变了但没记录 commit、随机种子不同、依赖库版本变化、训练配置被手动改过、预处理逻辑变化、评测集被更新或污染。解决思路是记录代码、数据、配置、随机种子、训练镜像和完整实验元数据。

离线效果好，线上效果差

离线 AUC 提升 2%，上线后点击率没有提升甚至下降，可能来自评测集不代表线上流量、训练数据泄漏、线上特征和离线特征不一致、用户行为受模型结果反向影响、线上系统延迟或超时、长尾场景退化、指标提升与业务目标不一致。

新模型质量提升，但成本不可接受

准确率提升 1%，但推理成本增加 5 倍，延迟增加 3 倍，可能来自模型过大、上下文过长、batch 策略不合理、没有缓存、检索 / rerank 链路过重、简单请求也使用强模型。解决方向包括单请求成本核算、按请求难度分层路由、缓存、量化、蒸馏、上下文控制和成本门禁。

线上出问题但无法回滚

新模型上线后大量用户投诉，但不知道应该回滚哪个版本，通常是旧模型没有保留、推理配置没有版本化、prompt 没有版本化、向量索引已覆盖、服务和模型绑定不清、没有流量切换能力、没有回滚演练。

止损优先：线上事故处理中，先确认回滚目标、流量切换、降级策略和用户影响范围，再进入细节归因。

11. LLM 应用生产化的特殊问题

如果系统是传统分类、排序、检测模型，生产化重点通常是数据、训练、评测、部署、监控。大模型应用链路更复杂，往往包括意图识别、Prompt 模板、上下文拼接、RAG 检索、Tool Calling、LLM 生成、安全过滤、结果格式化和用户反馈。

sequenceDiagram
  participant U as 用户
  participant G as 网关
  participant P as Prompt服务
  participant R as RAG检索
  participant L as LLM推理
  participant T as 工具/下游系统
  participant O as 观测反馈

  G->>P: 鉴权 限流 构造上下文

  R-->>P: 文档片段与引用
  P->>L: prompt + context
  L->>T: 可选工具调用

  L-->>G: 生成答案

  G-->>U: 返回结果
对象为什么要版本化
Prompt / System Message小改动可能显著影响输出和行为边界
工具 schema参数定义变化会影响工具调用
RAG 文档与向量索引知识和索引构建方式变化会影响召回
Embedding 模型 / Reranker向量空间和排序变化会影响上下文质量
采样参数temperature、top_p 会影响稳定性
Safety Policy决定哪些内容被拦截
LLM 发布原则：不要只把“模型”当作版本对象，而要把“模型 + Prompt + 工具 + 检索 + 安全策略 + 配置”当作整体版本对象。

12. AI 生产系统中的关键角色分工

角色主要关注点
算法工程师 / 研究员模型结构、训练策略、指标提升
数据工程师数据采集、清洗、标注、质量、血缘
MLOps 工程师训练平台、制品管理、评测流水线、发布流程
AI Infra 工程师GPU 集群、调度、存储、网络、推理性能
后端工程师API、业务系统集成、权限、稳定性
SRE / 运维工程师监控、告警、容量、故障响应
产品 / 业务负责人业务目标、用户体验、上线策略
安全 / 合规团队隐私、安全、审计、风险控制

生产化最大的挑战之一，是让这些角色共享同一套事实：模型版本是什么、数据版本是什么、评测结果是什么、当前灰度比例是多少、线上延迟是多少、线上质量是否退化、如果出问题回滚到哪里。

平台价值：平台不是为了炫技，而是为了让复杂协作变得可控。

13. 一个团队常见的演进路线

阶段特征主要风险下一步重点
阶段 0：个人实验notebook、本地脚本结果不可复现脚本化、配置化
阶段 1：脚本协作train.py、手动部署版本混乱、依赖混乱实验追踪、数据/模型版本管理
阶段 2：平台训练训练任务平台、制品仓库评测不系统、发布不规范自动评测、模型注册、发布门禁
阶段 3：生产闭环灰度、监控、回滚、反馈平台复杂度上升成本治理、质量治理、自动化运营
阶段 4：规模化治理多团队、多模型、多业务线权限、审计、成本、标准化挑战平台产品化、自助化、统一规范

本教程的目标不是让每个团队马上跳到阶段 4，而是让你知道自己现在在哪一阶段、当前最大的工程风险是什么、下一步最值得补的能力是什么。

当前状态最先补的能力不建议一开始就做的事
只有 notebook脚本化、配置化、固定数据路径直接搭复杂平台
有训练脚本实验追踪、数据版本、模型输出规范盲目做全自动训练平台
有训练平台自动评测、模型注册、制品管理只堆 GPU 不管交付流程
有推理服务灰度、回滚、监控、告警直接全量发布新模型
有完整链路成本治理、权限治理、质量闭环放任团队各自造轮子

14. 一个模型进入生产前的检查清单

数据检查
训练、验证、测试版本明确；训练集与测试集没有泄漏；时间窗口正确；线上目标流量覆盖充分；标注质量经过抽检；数据处理代码有版本记录。
训练检查
代码版本、配置、随机种子、训练镜像、资源配置、训练日志、checkpoint 和任务复现方式明确。
评测检查
离线主指标达标；分场景指标没有明显退化；回归测试、Golden Set、性能压测、安全测试、成本评估通过；与当前线上版本有对比报告。
制品检查
模型文件、tokenizer、preprocessor、config、serving config、eval report、model card、owner、rollback target 完整。
发布检查
staging 部署成功；集成测试通过；灰度策略明确；监控面板和告警规则已配置；回滚路径已验证；发布审批完成。
观测检查
QPS、错误率、超时率、延迟、模型版本、prompt 版本、质量采样、线上 badcase、成本归因均可见。
门禁底线：如果没有 rollback target、监控面板和观察窗口，不应该进入全量发布。

15. 案例与排查路径

为什么“模型效果好”仍然可能上线失败

客服问答模型离线评测准确率很高，上线后体验很差，可能因为线上数据分布和离线评测不一致、推理延迟过高、RAG 知识库检索失败、灰度和回滚机制缺失、监控只看到 HTTP 200 而看不到用户不满意。

为什么“买更多 GPU”不一定解决问题

训练慢时扩卡不一定带来线性吞吐，可能因为数据加载成为瓶颈、多机通信成本上升、batch size 和模型结构不适合扩展、checkpoint 写入拖慢训练、调度和资源碎片化。

flowchart LR
  A[线上症状] --> B{主要表现}
  B -->|延迟升高| C[流量 队列 batching GPU 下游依赖]
  B -->|质量下降| D[模型 Prompt 检索 数据分布 评测覆盖]
  B -->|训练变慢| E[数据读取 CPU预处理 H2D GPU通信 checkpoint]
  B -->|成本升高| F[token 模型版本 缓存 工具调用 重试 空闲资源]
  C --> G[版本变更与证据链]
  D --> G
  E --> G
  F --> G
  G --> H[止损 回滚 容量调整 或重训]
排查原则：看到一个现象，不只在现象所在层排查，而是沿着整条链路寻找因果关系。

16. AI Infra 建设的最小可行版本

小团队不需要一开始就搭复杂平台，可以先做一个最小闭环。

闭环至少包括
最小训练闭环固定代码仓库、配置文件管理、数据版本记录、训练日志、checkpoint、指标记录、实验结果对比
最小评测闭环固定评测集、baseline 模型、自动评测脚本、评测报告、上线门槛
最小发布闭环模型版本号、制品保存位置、staging 验证、灰度或手工放量、回滚版本、发布记录
最小观测闭环QPS、p50/p95/p99、错误率、GPU/CPU/内存、模型版本、Prompt 版本、线上 badcase
最小成本闭环每日调用量、平均 token 数、GPU 使用时长、模型 API 成本、项目维度成本归因、异常成本告警
建设顺序：先闭合训练、评测、发布、观测、成本的最小链路，再逐步平台化、自动化和治理化。
