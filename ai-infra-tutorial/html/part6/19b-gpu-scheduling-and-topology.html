1. 第一性原理拆解：GPU 调度与拓扑感知

拆 — 不可化简的问题

GPU 调度的不可化简问题是：AI 任务需要的不是任意 N 张 GPU，而是一组满足型号、显存、切分方式、驱动、拓扑、网络和租户策略约束的设备集合。

一个小模型推理副本可能只需要任意 1 张 L4。一个 70B 推理服务可能需要同机 8 张 H100，并且最好在同一个 NVSwitch domain。一个 64 卡训练任务不仅需要 8 台各有 8 张空闲卡的节点，还需要 RDMA fabric 可达、NCCL 可寻、机架分布、CPU/GPU/NIC locality 和一致的软件版本。表面上这是"数量调度"，实际上是多维约束的组合优化。

Kubernetes 默认调度器擅长处理 CPU、内存和扩展资源数量。GPU 通过 Device Plugin 暴露为 nvidia.com/gpu 或 MIG profile 资源后，调度器能知道"节点还有几个设备可分配"。但这个数量不自动表达以下任何一个事实：

  • GPU 型号和显存大小（L4 ≠ H100）。
  • MIG profile 与整卡的区别（mig-1g.10gb 不等于 gpu: 1）。
  • GPU 之间是否有 NVLink / NVSwitch 高速互联。
  • GPU、CPU、NIC 是否在同一个 NUMA locality。
  • 跨节点是否有 RDMA，NCCL 是否会走正确网卡和 rail。
  • 节点 driver、container toolkit、CUDA 镜像是否兼容。
  • 这个租户是否允许使用该卡型和节点池。

这意味着 GPU 调度实质上是信号工程和策略工程的组合：把硬件事实、软件基线、网络拓扑和组织策略，转换成调度器、准入系统和用户都能理解的约束语言。数量只是第一层信号，型号、拓扑、网络、版本是第二层，租户权限和运维状态是第三层。只盯着数量，就会出现"集群有 80 张 H100 但任务 Pending"或者"能调度但吞吐只有预期 55%"的典型问题。

推 — 从这个问题如何推导出每个机制

从"GPU 要被 kubelet 和调度器看见"推出 GPU Device Plugin。它把节点 GPU 注册为 Kubernetes extended resource，通过 ListAndWatch/Allocate 接口持续汇报设备状态并在容器启动时注入设备信息。没有 Device Plugin，调度器完全看不到 GPU 的存在。

从"驱动、容器工具链、device plugin、监控组件要持续一致"推出 GPU Operator。没有 Operator，不同节点的 driver 版本漂移、toolkit 缺失、MIG 配置不刷新是常态。Operator 把这些组件作为 Kubernetes 资源持续管理，是节点 GPU 软件栈的运维控制面。

从"一张物理卡要被切成多个硬件隔离实例"推出 MIG（Multi-Instance GPU）。MIG 使多租户场景可以在单张 GPU 上获得硬件级隔离，但只支持有限的 profile，并会产生形状不匹配的碎片问题。

从"节点硬件事实要进入 Kubernetes 调度语言"推出 Node Feature Discovery（NFD） 和节点标签。NFD 自动发现 CPU、PCI、GPU、内核、网络等特征并打标签，是把物理事实变成调度信号的桥梁。

从"GPU 节点不能被普通 CPU Pod 占满"推出 taint/toleration。GPU 节点加 taint，只有显式声明 toleration 的 Pod 才能进入，是节点准入控制的第一道门。

从"任务要落在特定卡型、节点池、机架或网络域"推出 nodeSelector、node affinity、pod affinity、pod anti-affinity 和 topology spread constraints。不同机制解决不同粒度的选择问题：affinity 选节点，topology spread 控制副本分布，pod affinity 实现 co-location。

从"数量正确不等于性能正确"推出 NUMA、NVLink、RDMA locality 的建模和排障。调度只选节点，不自动选最优数据路径。跨 NUMA 的 CPU-GPU 拷贝变慢，跨 PCIe 的 GPU-GPU allreduce 比 NVLink 慢 5-10 倍，RDMA 走错网卡让 NCCL 退化到 TCP。这些路径问题都必须通过拓扑建模、标签、准入规则和诊断工具来治理。

从"gang scheduling 需要所有 worker 同时拿到资源才有意义"推出 Scheduling Framework 扩展点、Volcano PodGroup 和 scheduler-plugins CoScheduling。kube-scheduler 1.19+ 的 11 个扩展点允许自定义调度逻辑。Volcano 在自己的 Allocate 流程里整体调度，CoScheduling 在 Permit phase 等待所有 Pod 到齐后一起放行。

从"NUMA-aware scheduling 需要 CPU、内存、GPU、NIC 在同一 NUMA"推出 Topology Manager + Hint Provider 机制。kubelet 在 admission 阶段通过四个 Hint Provider 求交集，决定分配哪个 NUMA 的资源。但 Topology Manager 不是 scheduler，它在节点已选定后才工作，如果 NUMA 已被占满，Pod 会被反复 reject，需要 scheduler-plugins 的 NodeResourceTopology plugin 配合在 Filter 阶段感知 NUMA，形成完整的 NUMA-aware 调度方案。

2. 概念先说清楚

GPU Device Plugin 是什么，不是什么

GPU Device Plugin 是 kubelet 的设备插件。它把节点上的 GPU 注册为 Kubernetes extended resource，例如 nvidia.com/gpu。它负责向 kubelet 汇报设备列表和健康状态，并在容器启动时返回需要注入的设备信息。随后 NVIDIA container toolkit 和容器运行时把 /dev/nvidia*、driver library、环境变量等注入容器。

Device Plugin 不负责训练框架调优，不负责 NCCL 拓扑选择，也不保证申请到的多张 GPU 具备理想互联。默认调度器看到的主要是资源名和数量，Device Plugin 提供的 GetPreferredAllocation 只影响节点内设备选择，跨节点选择仍需调度层协作。

GPU Operator 是什么，不是什么

GPU Operator 是节点 GPU 软件栈的运维控制面。它管理的典型组件包括：NVIDIA driver / driver manager、NVIDIA container toolkit、NVIDIA device plugin、DCGM exporter、MIG manager、GPU feature discovery（GFD）、validator 和节点健康检查组件。

GPU Operator 解决"节点基线一致"和"组件持续管理"。它不是容量规划器，不替代队列系统，也不会自动把一个 64 卡训练任务放到最优拓扑上。软件栈正常 ≠ 调度策略正确。

MIG 是什么，不是什么

MIG（Multi-Instance GPU）把支持的 NVIDIA GPU（如 A100、H100）切成多个硬件隔离实例。在 Kubernetes 中这些实例暴露为不同扩展资源，例如 nvidia.com/mig-1g.10gb、nvidia.com/mig-3g.40gb。MIG 碎片的本质是资源形状不匹配：一个需要 nvidia.com/mig-7g.80gb: 1 的 Pod 不能用四个 1g.10gb 拼出来。

MIG 不是显存超卖，也不是任意比例切片——只能使用硬件支持的 profile。MIG 适合小模型推理、Notebook、开发环境和强隔离多租户；不适合需要整卡显存、大规模 GPU-GPU 通信或频繁改变切分形状的任务。碎片治理是 MIG 最主要的运维挑战。

4. 原理：底层机制如何工作

Scheduling Framework：kube-scheduler 的 11 个扩展点

kube-scheduler 1.19+ 的实际架构是 Scheduling Framework——一个有 11 个扩展点的 plugin 系统。所有自定义 GPU 调度器（Volcano、scheduler-plugins、Yunikorn）都基于这套机制。理解这套，"Volcano 是替换 default scheduler 还是扩展它"这种问题才有答案。

sequenceDiagram
  participant PQ as PendingQueue
  participant SF as Scheduling Framework
  participant Node as 候选节点
  participant KB as Kubelet

  PQ->>SF: QueueSort — 决定 Pod 处理顺序（FIFO 或自定义优先级）
  SF->>SF: PreFilter — 预处理 Pod，缓存信息供 Filter 用
  SF->>Node: Filter — 判断节点能否放下（资源/taint/affinity）
  Note over SF: PostFilter 仅在 Filter 全部失败时触发（默认抢占）
  SF->>Node: Score — 0-100 打分（NormalizeScore 归一化）
  SF->>Node: Reserve — 选定节点后预留资源
  SF->>SF: Permit — gang scheduling 在此 wait/allow/deny
  SF->>SF: PreBind — 实际 bind 前最后准备（如 PV provisioning）
  SF->>KB: Bind — 写 Pod.spec.nodeName 到 API Server
  SF->>SF: PostBind — metrics、event 副作用

Volcano vs scheduler-plugins vs default scheduler

形态实现方式部署影响范围

多 scheduler 共存同集群跑多个 scheduler binary，按 schedulerName 分流各自独立必须保证不会同时 schedule 同一个 Pod

Topology Manager + Hint Provider：NUMA-aware 调度的实际机制

一台节点有 2 个 CPU socket（每 socket 一个 NUMA node），GPU 0-3 挂在 socket 0、GPU 4-7 挂在 socket 1，NIC 0 在 socket 0、NIC 1 在 socket 1。Pod 申请 1 GPU + 8 CPU + 32GB memory + 1 NIC，应该让这四类资源都在同一个 NUMA——否则跨 socket QPI/UPI 访问会让性能掉 10-30%。default scheduler 不解决这个，它只看节点级 allocatable。

flowchart TD
  A["kubelet admission 收到 Pod after schedule"] --> B["CPU Manager: GetTopologyHints\n→ socket=0 的 8 个 CPU\n→ {NUMANodeAffinity: 0001, Preferred: true}"]
  A --> C["Memory Manager: GetTopologyHints\n→ {0001, true}, {0010, true}"]
  A --> D["Device Manager (NVIDIA GetPreferredAllocation)\n→ GPU-0 在 socket 0\n→ {0001, true}"]
  B --> E["Topology Manager 求 mask 交集\n0001 ∩ 0011 ∩ 0001 = 0001 (socket 0)"]
  C --> E
  D --> E
  E --> F{"Policy 决策"}
  F -- "none（默认）" --> G["不调用 TM，走简单路径"]
  F -- "best-effort" --> H["有交集用，没有也允许调度"]
  F -- "restricted" --> I["没交集 → admission reject → Pending"]
  F -- "single-numa-node" --> J["必须单 NUMA 内可满足"]

Topology Manager Scope 两种模式：container（默认，每个容器独立算 hint，多容器 Pod 可能分到不同 NUMA）和 pod（整个 Pod 当一个单元算，所有容器在同一 NUMA，多 GPU 训练通常用这个）。

生产 kubelet 配置示例：

# kubelet config
topologyManagerPolicy: single-numa-node
topologyManagerScope: pod
cpuManagerPolicy: static       # CPU Manager 必须是 static 才能 NUMA-aware
memoryManagerPolicy: Static    # 同上
reservedSystemCPUs: "0,1"      # 保留给系统
关键陷阱 — Topology Manager 不是 Scheduler：它在 kubelet admission 阶段工作，决策已经晚了——节点已经被 default scheduler 选好。如果该节点 NUMA 已被占满，single-numa-node policy 会拒绝该 Pod，Pod 重新进入调度循环可能再次落到同一节点又被拒，形成死循环。解决方案是同时使用 scheduler-plugins 的 NodeResourceTopology plugin，让 scheduler 在 Filter 阶段就感知 NUMA，这是生产 NUMA-aware 调度的完整方案。此外，只有 Guaranteed QoS 的 Pod（CPU/memory request == limit、整数 CPU）才会被 NUMA-aware 处理。

PodGroup / Gang Scheduling 实现原理

两种主流实现：

方案 1：Volcano PodGroup（独立 scheduler 路径）

apiVersion: scheduling.volcano.sh/v1beta1
kind: PodGroup
metadata:
  name: train-job-pg
spec:
  minMember: 8              # 必须 8 个 Pod 都能 schedule 才整体 admit
  minResources:
    nvidia.com/gpu: 64      # 8 worker x 8 GPU
  queue: train-prod
---
# Pod 通过 annotation 关联到 PodGroup
metadata:
  annotations:
    scheduling.volcano.sh/group-name: train-job-pg

Volcano gang plugin 工作流程：PodGroup 进入 Inqueue → scheduler Allocate 阶段尝试给所有 Pod 找节点 → 能找到 minMember 个可放置的位置则 batch bind 所有 Pod；找不到则回滚已分配的临时 reservation，PodGroup 回到 Pending。要么全部 bind，要么都不 bind。

方案 2：scheduler-plugins CoScheduling（Permit phase 等待）

不需要独立 scheduler binary，在 default scheduler 框架上加 CoScheduling plugin，利用 Scheduling Framework 的 Permit phase：Pod 完成 Filter+Score → Reserve（占节点资源）→ Permit（wait）。直到 gang 内所有 Pod 都到 Permit，一起 Allow，原子地写 nodeName。超时未满足则触发 Reject，释放 reserve，重新进入 PendingQueue。

维度Volcanoscheduler-plugins CoScheduling
实现独立 scheduler binarydefault scheduler + plugin
资源占用风险scheduler 自己管 reservation 状态Reserve phase 已占节点资源，等待期间其他 Pod 看不到
大 gang 场景适合（>32 Pod，PodGroup-level reservation）大 gang + 资源紧张时反复 reject-retry，吞吐差
弹性训练支持 minMember < total（弹性）需要额外配置
部署复杂度需要 PodGroup CRD + Volcano controllers替换 scheduler image + 配置 plugin

NFD 和 GPU Feature Discovery 工作原理

NFD 由 master + worker 组成。NFD-worker（DaemonSet，每节点一个）每 60s 扫描节点 CPU cpuid、PCI 设备（lspci 识别 NVIDIA GPU / Mellanox NIC）、内核模块、文件系统，上报给 NFD-master，master 通过 NodeFeatureRule CRD 转换为 node label。GPU Feature Discovery（GFD）是 NFD 之上的 GPU 专用扩展，调用 NVML 获取卡型、显存、CUDA capability、MIG 状态、driver 版本并打标签：

nvidia.com/gpu.product=NVIDIA-H100-80GB-HBM3
nvidia.com/gpu.memory=81920
nvidia.com/gpu.count=8
nvidia.com/cuda.driver.major=535
nvidia.com/mig.strategy=single
NFD 工程要点：更新延迟（默认 60s 扫一次，硬件变化后标签可能 1-2 分钟才更新）、静态 fact vs 动态状态（NFD/GFD 暴露节点静态特性，GPU XID 错误、ECC failure 等健康状态必须通过 DCGM Exporter + Node Problem Detector + custom controller 单独治理）、标签漂移（手动标签会被 NFD 覆盖，用 ai.local/ 前缀区分）。

观测面

最小观测面必须覆盖六个层次：

  • 节点：GPU allocatable、device plugin Ready、driver 版本、MIG 状态、节点标签。
  • Pod：Pending events、分配节点、容器内 nvidia-smi、环境变量、runtimeClass。
  • GPU：利用率、显存、功耗、温度、ECC、XID、PCIe replay、NVLink counters。
  • 训练：step time、samples/s、allreduce time、NCCL logs、重试次数。
  • 网络：IB/RoCE link、GID、MTU、PFC/ECN、丢包、NCCL transport。
  • 存储：模型加载时间、checkpoint 写入时间、吞吐和延迟。

治理

GPU 治理要覆盖：namespace / 队列级 GPU 配额；卡型和节点池权限；整卡池与 MIG 池比例；优先级、抢占、gang scheduling 或队列准入；维护 taint、节点 drain、烧机验证；成本归因（租户、项目、作业、模型版本）；空闲检测（分配了 GPU 但利用率长期为 0 的任务要告警或回收）。

NUMA locality

NUMA 描述 CPU socket、内存和 PCIe 设备之间的距离。GPU、NIC、本地 NVMe 往往挂在某个 PCIe root complex 下，离某个 CPU socket 更近。跨 NUMA 访问代价：

  • dataloader 线程在远端 NUMA 分配内存，CPU→GPU 拷贝变慢。
  • GPU 和 RDMA NIC 跨 NUMA，GPUDirect RDMA 路径变差。
  • CPU offload 或参数卸载跨 socket，尾延迟变高。

诊断命令：lscpu、numactl --hardware、nvidia-smi topo -m。工程动作：开启 CPU Manager static policy 和 Topology Manager；为大训练预留整节点；配置 topologyManagerPolicy: single-numa-node + topologyManagerScope: pod；同步使用 NodeResourceTopology scheduler plugin 避免 admission 死循环。

NVLink / NVSwitch locality

NVLink 和 NVSwitch 决定 GPU-GPU 带宽。Tensor parallel、pipeline parallel、FSDP、allreduce 都受影响。典型错配：同样申请 8 张 GPU，有的节点是 HGX NVSwitch，有的只是 PCIe GPU；两个 4 卡推理 Pod 分别占用互联不理想的 GPU 组合；节点被碎片化后大任务拿不到完整 NVLink domain。诊断：nvidia-smi topo -m + NCCL_DEBUG=INFO nccl-tests。工程动作：把 HGX/NVSwitch 节点单独成池；大模型推理和训练使用整节点调度；通过准入系统拒绝不满足 topology profile 的提交。

RDMA locality

跨节点训练依赖 RDMA fabric。Kubernetes Pod 网络能通，不代表 NCCL 走了正确 RDMA 路径。常见问题：NCCL 退化到 TCP；选错 HCA 或 GID；MTU 不一致；RoCE PFC/ECN 配置不正确；多 rail 没有对齐；GPUDirect RDMA 未生效。

诊断命令：

NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET
ibstat
ibv_devinfo
rdma link
NCCL 退化到 TCP 的代价：NCCL 使用 TCP socket transport 时，跨节点带宽通常只有 IB/RoCE 的 1/5 到 1/10，延迟上升数倍。64 卡训练的 allreduce 时间可能从毫秒级变成秒级，直接让吞吐崩溃。必须通过 NCCL_DEBUG=INFO 验证每次训练的 transport 选择，而不是假设 RDMA 一定生效。工程动作：用节点标签表达 rdma=true、rail、rack、fabric；在训练镜像里固化 NCCL 和 RDMA 诊断工具；提交前做准入校验；运行前做短 nccl-tests。

Checklist

  • device plugin DaemonSet 是否 Ready？
  • 节点 capacity/allocatable 是否包含预期 GPU 或 MIG resource？
  • GPU Operator 管理的 driver、toolkit、device plugin、DCGM 是否版本一致？
  • GPU 节点是否加 taint，GPU Pod 是否有对应 toleration？
  • 任务是否请求了正确卡型、MIG profile、节点池和 RDMA 标签？
  • required affinity 是否只表达硬约束？
  • 多卡任务是否需要整节点、NVLink domain、同机 8 卡或 gang scheduling？
  • 训练任务是否需要 RDMA rail、rack、zone 等拓扑信号？
  • 推理副本是否通过 anti-affinity 或 topology spread 分散故障域？
  • NCCL 日志是否显示使用预期 NIC、transport 和 GPU 拓扑？
  • GPU 利用率、显存、XID、ECC、温度是否纳入告警？
  • MIG 池和整卡池比例是否有容量规划和 defrag 机制？
最小可用状态（MVP）定义：device plugin Ready + node allocatable 正确 + GPU 节点有 taint + GPU Pod 有 toleration + 卡型标签由 GFD 自动生成 + NCCL 日志确认走 RDMA + DCGM 指标可查。达到以上七点，才算 GPU 调度基线就绪。

10. Worked Example：64 卡 H100 训练为什么 Pending 又跑不快

团队提交一个 64 卡训练任务，期望 8 个 worker，每个 worker 申请 8 张 H100：

resources:
  limits:
    nvidia.com/gpu: 8
nodeSelector:
  gpu.nvidia.com/model: H100

集群看起来还有 80 张 H100 空闲，但任务 Pending。排查发现：

  1. 只有 5 台节点完整空闲 8 张卡，其余节点每台只剩 2 到 4 张——作业每个 worker 需要单节点 8 卡，不能拆到多台节点。
  2. 其中 2 台完整节点缺少 ai.local/rdma=true 标签，平台准入不允许进入分布式训练队列。
  3. 另有 1 台节点带 maintenance=true:NoSchedule taint，Pod 没有 toleration。

关键结论："集群总空闲 GPU 数"没有意义。调度需要的是"8 个满足 H100、整节点、RDMA、非维护状态的节点"，当时只有 2 台满足全部条件，gang scheduling 无法满足 minMember=8。

修复后任务能调度，但吞吐只有预期的 55%。继续排查：

最终处理动作

  1. 队列准入改为按 topology profile 统计可用完整节点，而不是按 GPU 总数。
  2. 修正 RDMA 标签来源，标签由自动发现和网络验证共同生成。
  3. 将 H100 训练池设置为整节点调度，减少碎片。
  4. 标准化 NCCL 版本和 NCCL_IB_HCA 配置。
  5. 在作业启动前运行短 nccl-tests，失败则不进入长训练。
本例的核心教训：Pending 问题看调度证据（affinity、taint、标签、gang），性能问题看 topology 和通信证据（NCCL transport、NUMA topo、NVLink、存储）。数量只是第一层信号。工程师必须能沿证据链从症状追到根因，而不是凭感觉猜。这个例子体现了 19b 的核心：GPU 调度的核心不是让 Pod 写上 nvidia.com/gpu，而是把设备数量、型号、显存、MIG、节点基线、NUMA、NVLink、RDMA、租户权限和运维状态变成可调度、可观测、可解释的信号。
