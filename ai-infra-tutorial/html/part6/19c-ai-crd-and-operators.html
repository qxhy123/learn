1. 第一性原理拆解：AI CRD 与 Operator

拆 — 不可化简的问题

Pod、Job、Deployment 是 Kubernetes 的通用抽象，足以表达"运行一组容器"的语义。但 AI 平台上的高层任务远不止"一组容器"这么简单。以一个 64 卡 PyTorch 训练任务为例，它至少包含以下无法被通用对象表达的约束：

  • 角色：master、worker，可能还有 evaluator、parameter server、launcher，每个角色有不同的资源需求和生命周期。
  • 拓扑：每个 worker 几张 GPU，是否要求整机，是否要求同 rack 或同 IB fabric 的 gang 调度。
  • 协议：rendezvous 地址、rank、world size、NCCL 网卡、端口——这些必须在 Pod 启动前注入，而不是每次手工管理。
  • 生命周期：初始化、等待所有 rank 就绪、训练主循环、周期性 checkpoint、失败重启、成功归档——每个阶段对观测和决策的要求都不同。
  • 失败语义：单个 worker 失败时，非 elastic 训练要全局 restart，elastic 训练只要缩容重新 rendezvous，而不是简单重启一个 Pod。
  • 观测语义：用户应该看到"等待 8 卡 gang 调度 (InsufficientGPU)"，而不是"某个 Pod Pending"——这是两层完全不同的诊断信息。

同理，RayJob 不是一个普通 Job，MPIJob 不是一堆 worker Pod，KServe InferenceService 也不是一个 Deployment。它们都有各自的控制面语义——模型版本、流量切分、revision、runtime env、driver 状态等。如果把这些语义分散在脚本、CI 模板、平台后端和人工 runbook 里，系统就会变得不可恢复（失败后不知道从哪恢复）、不可解释（用户看不到有意义的状态）、不可审计（谁改了什么无从追溯）。

不可化简的问题是：如何把 AI 任务的高层语义声明为稳定 API，并持续把真实集群状态推进到期望状态。这个问题的"持续"二字是关键——不是"一次性生成 YAML"，而是面对节点重启、Pod 驱逐、镜像拉取失败、PVC 等待绑定、用户修改副本数、服务 revision 切流量等所有真实世界变化，系统仍然能自动收敛。

推 — 从这个问题如何推导出每个机制

从"用户应该提交高层语义"推出 CRD。CRD（CustomResourceDefinition）让 Kubernetes API 增加 PyTorchJob、RayJob、MPIJob、InferenceService 等资源类型，使 AI 平台的领域概念成为可 kubectl get、可 RBAC 管控、可 API 版本化的一等对象。

从"真实世界持续变化"推出 Operator。节点会重启，Pod 会失败，镜像会拉取失败，PVC 会等待绑定，用户会修改副本数，服务 revision 会切流量。一次性生成 YAML 不能处理这些变化，必须有控制器持续监听对象变化、比较期望状态与真实状态、执行修正动作。

从"期望状态和真实状态必须分离"推出 spec 与 status 的边界。spec 是用户或平台声明的目标；status 是控制器观察到的结果。控制器不应偷偷修改 spec 来表达运行状态，否则声明式 API 的边界就被破坏——用户的意图和系统的观测会混在一起，无法区分。

从"删除也有语义"推出 finalizer。删除训练任务时可能要清理临时 Service、外部 Ray cluster、云端 endpoint、模型缓存或 checkpoint lease。Kubernetes 的普通垃圾回收只认识集群内对象，不认识外部资源。finalizer 让控制器可以在删除前执行自定义清理，确保不泄漏外部资源。

从"底层对象必须有归属"推出 ownerReference 和 label selector。Operator 创建的 Pod、Service、ConfigMap、Job、Revision 必须能被反查、清理和聚合状态。ownerReference 启用 Kubernetes 的级联垃圾回收；稳定 labels 让 Prometheus、日志系统、成本系统能对任意维度聚合。

从"AI 任务有阶段"推出状态机与 conditions。单个 phase=Running 不够，平台还要表达 Admitted、PodsCreated、RendezvousReady、ModelLoaded、TrafficReady、CheckpointRestored 等细粒度条件，让用户和自动化系统能做精确决策而不是凭猜测。

从"多个控制器协作同一对象"推出 Server-Side Apply（SSA）。HPA 改 replicas、Operator 管 spec、用户手动 edit——三者同时修改同一个 Deployment 时，传统 Update 全量覆盖会让彼此的修改互相覆盖。SSA 用 field manager 机制让每个控制器只声明自己负责的字段，冲突时显式协商而不是静默覆盖。

从"Operator 重启不能丢事件"推出 List-Watch + Informer Cache + Workqueue。Operator 基于 client-go 的 Reflector List+Watch 机制，用 ResourceVersion 保证断线续传不丢事件；Informer Cache 在内存中维护对象副本，所有 Get/List 操作 O(1) 且不打 API Server；Workqueue 对同对象多次变化去重、失败指数退避、防雪崩。

从"CRD API 需要演化"推出 Conversion Webhook 和版本矩阵。CRD 从 v1alpha1 升级到 v1 时，集群里可能同时存在两个版本的对象。Conversion Webhook 让 API Server 在客户端请求版本和存储版本不同时自动转换，保证旧对象可读、新控制器可处理。

2. 概念先说清楚

CRD 是什么，不是什么

CRD（CustomResourceDefinition）向 Kubernetes API 注册一种新的资源类型。注册后，用户可以像操作 Pod 一样操作自定义对象：

kubectl get pytorchjobs -n train
kubectl describe rayjob -n ml batch-embed-v3
kubectl get inferenceservice -n serving reranker -o yaml

CRD 是 API 扩展机制，不是调度器，不是工作流引擎，也不是模板语言。CRD 本身只负责让 API Server 接受、校验、存储和返回这种对象。没有控制器时，一个 CRD 对象只是 etcd 里的声明，不会自动创建 Pod。

Custom Resource、Controller、Operator 的区别

名称关注点例子

Operator 不是高级 Helm：Helm 渲染发生在提交前，Operator 控制发生在运行中。真正的 Operator 必须面对失败、重试、并发、删除和状态漂移。Helm chart 跑完就退出，Operator 持续运行。

Custom Resource 的字段结构

字段归属含义
metadataKubernetesname、namespace、labels、annotations、finalizers、ownerReferences
spec用户或平台期望状态：副本数、镜像、资源、模型路径、重启策略
status控制器观察状态：phase、conditions、replica status、revision、失败原因

spec 是输入，status 是输出。用户改 spec，控制器改 status。把运行时状态写进 spec 会破坏声明式 API 的边界——用户无法区分哪些是自己的意图，哪些是系统注入的运行时信息。

Reconciliation Loop 的本质

观察对象变化
  -> 读取期望状态：CRD spec
  -> 读取真实状态：Pod、Service、Job、Revision、PVC、外部系统
  -> 计算差异
  -> 创建、更新、删除或等待
  -> 写 status、记录 event、导出 metric
  -> 决定是否重新入队

这个循环必须是幂等的。同一个对象可能被重复 reconcile（每 10 分钟 resync 一次）；一次 reconcile 也可能执行到一半失败。正确实现的控制器不依赖"刚才那一步一定成功"，而是每次都从 API Server 重新读取事实。

Finalizer 与 OwnerReference 的边界

ownerReference 用于 Kubernetes 内部对象的级联删除。PyTorchJob 创建的 worker Pod 带上 ownerReference 后，删除 PyTorchJob 时，垃圾回收器可以自动删除这些 Pod。

finalizer 用于删除前置清理，阻止对象立刻从 API Server 消失，直到控制器完成清理并移除 finalizer。适合清理 Kubernetes 垃圾回收器看不到的东西：外部负载均衡器、云端 endpoint、对象存储临时目录、checkpoint lock、Ray runtime env 缓存等。

不要滥用 finalizer：finalizer 是删除协议，不是生命周期状态机。不要用 finalizer 做普通状态流转，也不要把所有底层对象都用 finalizer 管起来。finalizer 清理失败会让对象永久卡在 Terminating，必须写 event 和 condition 说明原因。

4. 原理：Reconciliation、状态机与对象语义

controller-runtime 内部架构：从 API Server 到 Reconcile

理解这五层架构，才能回答"为什么我的 Operator 偶尔漏处理事件"、"为什么 reconcile 看到的对象比刚 update 的旧"、"resync 是什么"这些实际问题：

flowchart TD
  A["API Server\nList + Watch"] -->|ResourceVersion 续传| B["Reflector\n启动 List 全量\nWatch 持续增量"]
  B -->|Add/Update/Delete events| C["DeltaFIFO\n同对象多次更新合并\n只留最新"]
  C -->|Pop deltas| D["Informer Cache\nthread-safe 本地 store\nGet/List O(1) 不打 API Server"]
  D -->|EventHandler 回调| E["Workqueue\n去重 ns/name key\n指数退避 + 全局令牌桶"]
  E -->|Get 阻塞直到 key available| F["Reconciler.Reconcile\n从 Cache 读对象\n算 desired vs actual\nPatch/Apply 到 API Server\n返回 Requeue / RequeueAfter"]

每一层解决一个具体问题：

  • Reflector List+Watch + ResourceVersion：保证不丢事件。watch 连接断了，下次 watch 用 lastResourceVersion 续传。没有对应历史时（API Server 默认保留 5min 历史）返回 410 Gone，Reflector 触发重新 List。
  • DeltaFIFO 合并：对象在短时间内被改 100 次，FIFO 里只有 1 个最新对象等着 reconcile，避免 watch 风暴导致 reconcile 排队爆炸。
  • Informer Cache 的强一致幻觉：cache 永远略晚于 API Server，所以 Reconcile 拿到对象后必须用 ResourceVersion 防 conflict——Update() 时 K8s 比对 ResourceVersion，cache 旧的就 reject，Reconciler 把请求重新入队。
  • Workqueue 的限速：默认用 ItemExponentialFailureRateLimiter（指数退避，5ms 起跳，1000s 封顶）+ BucketRateLimiter（10 qps + 100 burst 全局令牌桶），防单对象失败雪崩，也防全局打爆 API Server。

Periodic Resync：Operator 自愈的隐形机制

DeltaFIFO 默认启用 Resync（典型 10 分钟）。每 10 分钟，Informer 遍历全部缓存对象、对每个对象触发一次 fake update event，把它们重新塞进 workqueue 走 reconcile。这是 Operator 的"隐形自愈"：

  • Reconcile 失败用尽 retry：原本对象就再也不会被处理了。Resync 让它有机会重新尝试。
  • 外部状态漂移：底层 Pod 被手动删了、Service 被覆盖，Operator 没收到事件。Resync 让 Operator 定期对账。
  • bug 导致 status 没写：Resync 让 Operator 有机会重新算 status。
生产建议：Resync period 太短（< 1min）会让 controller CPU 飙高；太长（> 1h）让自愈变慢。默认 10min 是经验值。看到 controller_runtime_reconcile_total metric 数字远大于实际事件数是正常的——含 resync。

Server-Side Apply（SSA）：多控制器协作

问题：HPA 改 spec.replicas，用户手工 kubectl edit 改 replicas，Operator 全量 Update——三者同时修改会让彼此的修改互相覆盖。

SSA 的解法：每个 client 用 field manager 名字（如 "torchjob-controller"）声明"我对哪些字段负责"。API Server 跟踪每个字段的 owner，发生冲突时返回 Conflict 让 client 决定怎么处理。

// controller-runtime 风格
err := client.Patch(ctx, obj, client.Apply, &client.PatchOptions{
    FieldManager: "torchjob-controller",
    Force:        false,  // 冲突时报错；true = 强制接管
})
生产规则：Operator 一律用 SSA Patch，不用 Update。Operator 只声明自己负责的字段，不要把整个对象 apply。Force=true 谨慎使用——只在有"我有权接管"的判断后才用。CRD 启用 subresources.status: {} 后，status 更新走独立 endpoint，不触发 spec 的 SSA 冲突。

Conversion Webhook：multi-version CRD 的工作机制

CRD 从 v1alpha1 升级到 v1 时，集群里可能同时有两个版本的对象。Conversion webhook 让 API Server 在客户端请求版本和存储版本不同时自动转换：

sequenceDiagram
  participant Client
  participant API as API Server
  participant Webhook as Conversion Webhook

  Client->>API: GET pytorchjob (请求 v1)
  API->>API: 存储版本是 v1，etcd 里是 v1alpha1 格式
  API->>Webhook: ConversionReview {desiredAPIVersion: v1, objects: [v1alpha1格式]}
  Webhook-->>API: ConversionResponse {convertedObjects: [v1格式]}
  API-->>Client: 返回 v1 格式对象
失败场景后果排查方式
Webhook service 不可达（pod 死了）整个 CRD 不可用，所有操作返回 5xxkubectl describe crd 看 status.conditions；保证 webhook 高可用 + PDB
Webhook 返回错误（panic、bug）同上webhook pod 日志
caBundle 过期同上用 cert-manager 自动轮换
Conversion 函数有 bug客户端拿到错对象，调度等下游链路出错round-trip 单测（v1→v1alpha1→v1 应等于原对象）

Leader Election：实际机制

Operator 多副本用 coordination.k8s.io/v1 的 Lease 对象作为分布式锁。只有持有 Lease 的副本执行 reconcile，其他副本进入 standby。

# training-system 下的 Lease 示例
apiVersion: coordination.k8s.io/v1
kind: Lease
metadata:
  name: training-operator-leader
  namespace: training-system
spec:
  holderIdentity: "training-operator-7d8f6c9-xkj2p"
  leaseDurationSeconds: 15   # leader 多久不续就失效
  renewTime: "2026-05-05T10:23:45Z"
  leaseTransitions: 3        # 历史切换次数

三个时间参数关系：RetryPeriod(2s) < RenewDeadline(10s) < LeaseDuration(15s)。RenewDeadline 比 LeaseDuration 短，确保旧 leader 在被认为过期前就主动放弃，防止两个 leader 短暂共存（split brain）。

Leader Election 不能替代乐观并发：切换瞬间可能有重叠操作。所有 reconcile 操作必须基于 ResourceVersion 做乐观并发，不能假设独占。用 kubectl get lease -n training-system 监控当前 leader；leaseTransitions 增长率反映 leader 抖动情况。

AI Operator 状态机

stateDiagram-v2
  [*] --> Created : CRD 保存，controller 首次观察
  Created --> Admitting : 加 finalizer，提交 Workload/PodGroup
  Admitting --> Pending : queue/gang 准入通过，创建底层对象
  Pending --> Initializing : 关键 Pod 启动，运行 init/rendezvous/模型加载
  Initializing --> Running : 关键角色就绪
  Running --> Restarting : 可恢复失败（按策略）
  Restarting --> Running : 从 checkpoint 恢复
  Running --> Succeeded : 任务达到成功条件
  Running --> Failed : 不可恢复或超过重试预算
  Succeeded --> [*]
  Failed --> [*]
  Created --> Terminating : 用户删除
  Admitting --> Terminating
  Pending --> Terminating
  Running --> Terminating
  Terminating --> [*] : finalizer 清理完成

Spec、Status、Conditions

一个有工程质量的 CRD status 应该回答三个问题：当前阶段是什么、卡住或失败的直接原因是什么、系统下一步是否会自动处理。

status:
  observedGeneration: 7   # 对应 metadata.generation，判断 status 新鲜度
  phase: Pending
  conditions:
    - type: Admitted
      status: "False"
      reason: InsufficientGPU
      message: "queue train-prod needs 64 nvidia.com/gpu, currently 48 fit the topology"
      lastTransitionTime: "2026-05-05T10:20:00Z"
    - type: PodsCreated
      status: "False"
      reason: WaitingForAdmission
  replicaStatuses:
    Worker:
      desired: 8
      active: 0
      failed: 0

observedGeneration 很关键。如果用户刚修改 spec，而 controller 还没处理，metadata.generation 会大于 status.observedGeneration。平台 UI 和自动化系统应据此判断 status 是否新鲜，不要把"正在收敛"误报为"稳定运行"。

5. 常见 AI CRD 的语义

TorchJob / PyTorchJob

TorchJob 表达 PyTorch 分布式训练。核心不是"创建多个 Pod"，而是表达 PyTorch 分布式语义：

  • pytorchReplicaSpecs：Master、Worker 等角色及其 replicas、Pod template、资源请求。
  • runPolicy：cleanPodPolicy、backoffLimit、ttlSecondsAfterFinished、suspend。
  • 环境变量和启动命令：master address、rank、world size、backend、NCCL 参数。
apiVersion: kubeflow.org/v1
kind: PyTorchJob
metadata:
  name: train-reranker
  namespace: train
spec:
  runPolicy:
    cleanPodPolicy: Running
    backoffLimit: 3
  pytorchReplicaSpecs:
    Master:
      replicas: 1
      restartPolicy: OnFailure
      template:
        spec:
          containers:
            - name: pytorch
              image: registry.local/ml/reranker-train:cuda12.4-v42
              command: ["torchrun"]
              args: ["--nnodes=8","--nproc_per_node=8","--rdzv_backend=c10d",
                     "--rdzv_endpoint=$(MASTER_ADDR):29400","train.py"]
              resources:
                limits:
                  nvidia.com/gpu: 8
    Worker:
      replicas: 7
      restartPolicy: OnFailure
      template:
        spec:
          containers:
            - name: pytorch
              image: registry.local/ml/reranker-train:cuda12.4-v42
              resources:
                limits:
                  nvidia.com/gpu: 8
必须接入 Gang 调度：生产中，TorchJob 必须和 Kueue、Volcano 或其他 gang scheduler 集成。否则 8 个 worker 可能只启动 5 个，训练卡在 rendezvous 永久等待，占用 GPU 但不产出任何训练进度。

RayJob

RayJob 表达"提交一个 Ray driver，并在 RayCluster 上运行"。对象关系：

RayJob
  -> RayCluster
       -> head Pod + head Service
       -> worker Pods
  -> submitter / driver Job

排障时不能只看 Pod。Pod Running 只是 Ray runtime 在跑，不代表 driver 成功，也不代表 Ray task 没有失败。Operator 应把 driver 状态、RayCluster 状态和 Kubernetes 状态都写到 status。

MPIJob

MPIJob 表达 launcher + worker slot 的启动模式，常用于 Horovod、OpenMPI、传统 HPC 风格训练。典型结构：

MPIJob
  -> launcher Pod (mpirun / mpiexec)
  -> worker Pods (slots / GPU resources)

MPIJob 最常见的失败是 launcher 先启动，worker 未齐，随后连接超时。成熟 Operator 会通过 init、状态检查或调度集成降低这类问题。

InferenceService / KServe

KServe 的 InferenceService 表达在线模型服务，通常把服务拆成 predictor、transformer、explainer，通过 Knative、Deployment、Service、Ingress/Gateway、autoscaler 等底层对象运行。

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: reranker
  namespace: serving
spec:
  predictor:
    model:
      modelFormat:
        name: pytorch
      runtime: vllm-runtime
      storageUri: s3://model-registry/reranker/v42
      resources:
        limits:
          nvidia.com/gpu: 1

生产语义包括：模型加载（storageUri、model agent、local cache）、Runtime（Triton/TorchServe/vLLM/自定义）、Revision（每次变化生成新 revision）、Traffic split（灰度/金丝雀/回滚）、Autoscaling（基于并发/QPS/延迟/GPU 指标）。

InferenceService 不是薄包装：它的价值在于把模型版本、流量、readiness、runtime 和弹性策略变成模型服务控制面。Ready=True 也不等于延迟达标——模型加载完成和服务质量是两个不同维度。

LeaderWorkerSet（LWS）：大模型多机推理

LWS 专为"一组 Pod 共同服务一个推理副本"的场景设计——典型如 vLLM / SGLang / TRT-LLM 把 70B-405B 模型用 TP+PP 切到多机多卡推理。每个推理副本由 1 个 leader Pod + N-1 个 worker Pod 组成，所有 Pod 必须 gang 启动、共享 NCCL/RDMA bootstrap、一起 ready 才能接流量。

字段含义与 vLLM 对应
replicas推理副本数（每个副本是一组 leader+worker）vLLM 副本数
leaderWorkerTemplate.size单副本内 Pod 总数（leader + worker）TP × PP × DP / GPUs_per_pod
restartPolicy: RecreateGroupOnPodRestart任一 Pod 重启则整组重启必选，否则 NCCL 状态不一致
rolloutStrategy副本级滚动升级策略不能像 Deployment 按 Pod 滚
startupPolicy: LeaderReadyleader 模型加载完再起 worker避免 worker 空等
替代方案不适合大模型多机推理的原因
Deployment + Service没有 gang 语义；Pod 个体重启会让 NCCL 链路死锁
StatefulSet提供有序启动，但缺少"组级 ready"和"组级重启"语义
Job / JobSetJob 假设跑完即结束；推理是长服务
RayCluster强依赖 Ray runtime，不适合 vLLM 之外的引擎
LWS专为"长生命周期 + 组级语义 + 滚动升级"设计，vLLM/TRT-LLM/SGLang 多机推理官方推荐路径
LWS 已进入 Kubernetes SIGs 官方路径（kubernetes-sigs/lws v0.4+），并被 NVIDIA / vLLM / Anyscale / Google 官方文档作为大模型多机推理推荐 CRD。如果你在裸 K8s 上做 70B+ 模型多机推理且没用 LWS，意味着你正在自己重新实现 gang 启动、组级重启、组级滚动这些已经被解决的问题。
LWS + Volcano/Kueue 是叠加关系，不是替代：调度层（Volcano PodGroup / Kueue Workload）确保副本"一组 Pod 同时拿到 GPU"；LWS 确保"已分配的 Pod 一起启动且组级管理"。两者通常一起用。

版本矩阵与 API 版本策略

不要只写"支持 Kubernetes 1.29"。对 AI 平台而言，更重要的是"PyTorchJob v1 + Kueue x.y + H100 CUDA 12.4 + NCCL 2.x + driver branch + operator 版本"的组合是否验证过。

阶段API 版本策略
实验v1alpha1快速迭代，不承诺长期兼容
试生产v1beta1字段基本稳定，允许小幅调整
生产稳定v1强兼容，变更需要迁移和公告

发布策略

  1. 发布 CRD schema，但不立即启用新行为。
  2. 发布 admission webhook，先以 audit 或 warn 模式验证策略。
  3. 滚动升级 Operator，观察 reconcile error、workqueue depth、status update conflict。
  4. 对少量 namespace 或 queue 启用新字段。
  5. 扩大灰度，更新平台 UI 和文档。
  6. 固化版本矩阵和回滚手册。

观测

Operator 观测至少包含：

  • 日志：reconcile 开始/结束、对象 namespace/name、generation、错误、重试原因。
  • Events：面向用户的关键状态变化，例如 WaitingForGPU、ImagePullFailed、RevisionReady。
  • Metrics：reconcile duration、error count、queue depth、requeue count、status update conflict、managed objects。
  • Status：phase、conditions、observedGeneration、replica status、failure reason。
  • AI 领域指标：训练 job 运行时长、失败重启次数、checkpoint 恢复次数、Ray driver 状态、InferenceService revision ready 延迟、模型加载耗时、流量切换状态。

RBAC 与安全治理

  • 只能 watch/list/get 自己管理的 CRD 和底层对象。
  • 只能 create/update/delete 自己 namespace 或目标 namespace 下的对象。
  • status 更新使用 /status 子资源权限。
  • 不要给 cluster-admin 作为默认安装方式。
  • Admission 校验镜像来源、GPU 请求、queue、priority、hostPath、privileged。
  • 为不同团队划分 namespace、queue、quota 和 service account。

9. 反模式与 Checklist

常见反模式

反模式后果修正
把 Operator 写成 YAML 渲染器Pod 漂移、失败、删除后无法恢复实现真正 reconcile，按实际状态收敛

生产 Checklist

  • CRD 顶层字段是否表达 AI 语义，而不是简单复制 Pod template？
  • spec 与 status 的边界是否清楚？是否启用了 status subresource？
  • status 是否包含 observedGeneration、conditions、reason、message？
  • reconcile 是否幂等，是否能处理重复事件和中途失败？
  • 底层对象是否有 ownerReference、稳定 labels 和可查询 selector？
  • finalizer 是否只处理删除清理，且幂等、可超时、可重试？
  • 失败策略是否区分可恢复、不可恢复和需要人工介入？
  • 是否接入 queue/gang/priority/quota，而不是让多 worker 训练裸跑？
  • Operator 是否有最小 RBAC、leader election、metrics、events 和告警？
  • CRD 升级是否测试旧对象、新对象、回滚和 conversion？
  • Operator 是否用 SSA Patch，而不是全量 Update？
  • 平台 UI 是否基于 conditions 展示原因，而不是只展示 phase？

10. Worked Example：8 节点 PyTorch 训练的控制面设计

场景

团队要训练一个 reranker，需求如下：

  • 8 个节点，每节点 8 张 H100，总计 64 GPU。
  • 必须所有 worker 同时启动，否则 rendezvous 会超时。
  • 允许节点故障后从最近 checkpoint 全局重启，最多 3 次。
  • 训练结束后保留失败 Pod 证据，成功后清理运行中 Pod。
  • 平台要在 UI 上展示"等待队列准入""等待 GPU""训练中""从 checkpoint 恢复"等状态。

设计决策

需求设计
PyTorch 分布式语义使用 PyTorchJob（kubeflow.org/v1）
64 GPU 整体准入接入 Kueue Workload 或 Volcano PodGroup，gang=8×8
全局失败恢复failurePolicy 设置为 AllWorkers restart，配合 checkpoint
状态展示Operator 写 conditions，平台聚合 Pod events
删除清理ownerReference 清理 Pod，finalizer 释放 queue admission 和 checkpoint lease

控制路径

flowchart TD
  A[用户提交 PyTorchJob] --> B[Admission Webhook\n注入 queue/labels/tolerations/runtimeClass]
  B --> C[Training Operator\n创建 Kueue Workload / PodGroup]
  C --> D{Queue 准入?}
  D -->|等待| E[status: Admitting\nQueueAdmitted=False\nWaitingForGangResources]
  D -->|准入通过| F[Operator 创建 master+worker Pod\n+ rendezvous Service]
  F --> G[Scheduler 绑定全部 8x8 Pod\ngang 必须全部成功]
  G --> H[Pod 启动 torchrun\nrendezvous 完成]
  H --> I[Operator 写 Running\nPodsReady=True]
  I --> J{Worker 失败?}
  J -->|节点故障| K[全局 restart\n从 checkpoint 恢复]
  K --> H
  J -->|重试超限| L[status: Failed\n保留 Pod 证据]
  I -->|训练完成| M[status: Succeeded\n清理 Running Pod]

Status 设计示例

status:
  observedGeneration: 3
  phase: Admitting
  conditions:
    - type: QueueAdmitted
      status: "False"
      reason: WaitingForGangResources
      message: "requires 8 nodes with 8 H100 each in queue h100-prod"
    - type: PodsReady
      status: "False"
      reason: NotCreated
    - type: CheckpointReady
      status: "True"
      reason: LatestCheckpointFound
      message: "s3://checkpoints/reranker/v42/step-18400"

故障演练：部分 worker Pending

故障：5 个 worker Running，3 个 worker Pending，训练卡在 rendezvous。

kubectl get pod -n train -l training.kubeflow.org/job-name=reranker-v42 -o wide
kubectl describe pytorchjob -n train reranker-v42
kubectl get events -n train --sort-by=.lastTimestamp

根因：没有 gang 准入，调度器先绑定了部分 Pod，剩余 3 个 Pod 因 GPU 形状不足 Pending。对 PyTorch 非 elastic 训练而言，部分启动没有业务意义。

处理：

  1. 为任务创建 Workload/PodGroup，要求 8 个 8-GPU worker 整体准入。
  2. 未准入前不创建训练 Pod，或让 Pod 处于 gated 状态。
  3. status 写 QueueAdmitted=False，reason 为 WaitingForGangResources。
  4. 释放已占用但无法成组的 Pod，避免 GPU 被半个任务长时间占住。
核心结论：AI Operator 的职责不是少写 YAML，而是把训练语义传递给调度、状态、恢复和治理系统。一个能正确表达"等待 gang 准入"而不是"Pod Pending"的 status，就能让平台 UI 显示有意义的信息，让运维人员快速定位问题，让自动化系统做出正确决策。
