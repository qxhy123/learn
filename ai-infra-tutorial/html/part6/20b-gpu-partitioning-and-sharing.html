第 20b 章 · GPU 资源切分与共享

GPU 共享不是把一张卡"变多"，而是在隔离、性能确定性、碎片化和利用率之间重新签合同：同一批硬件，面对大训练、小模型推理、开发 notebook 和多租户在线服务，需要完全不同的资源形状、隔离等级和 SLA 承诺。平台的职责，是把这组离散、异构、昂贵且带拓扑约束的设备，表达成可调度、可配额、可计费、可观测、可解释的资源形状。

1. 第一性原理拆解：GPU 资源层

拆 — 不可化简的问题

GPU 资源层要解决的问题是：一组离散、异构、昂贵且带拓扑约束的设备，如何被表达成平台可调度、可配额、可计费、可观测、可解释的资源形状。

CPU 可以相对连续地按 core 和 memory 分配。GPU 不行。影响 GPU 可用性的因素非常多，而且这些因素交织在一起，无法简单叠加：

第一，型号差异：H100、A100、L40S、L4 的算力、带宽、特性和价格完全不同。H100 有 NVLink4、SXM5、FP8 支持，L4 是 PCIe 卡、定位推理省电。把两者当作同一种资源，会导致训练任务被调度到 L4 上，推理服务占满 H100，完全颠倒。

第二，显存规格：40GB、80GB、94GB 不是同一种资源。70B 模型全精度需要 140GB，必须多卡或 80GB 以上的卡。把显存不加区分地纳入同一配额，用户拿到资源却跑不起来，让平台解释困难。

第三，拓扑约束：同机 8 卡之间有 NVLink/NVSwitch，跨机只有 IB/RoCE，性能相差 5-10 倍。一个 8 卡训练作业如果分散到 8 台不同机器，AllReduce 会极慢，甚至不如单机单卡。拓扑是资源形状的重要维度，不是附加属性。

第四，切分语义：整卡、MIG、MPS、time-slicing 的隔离边界、性能承诺和故障范围完全不同。整卡提供完整显存和计算资源的独占；MIG 是硬件级固定切片，隔离但不灵活；MPS 是进程共享 CUDA 上下文；time-slicing 只是轮流占用。把这四种混在一个 nvidia.com/gpu: 1 资源名下，调度器和用户都看不清"我实际得到了什么"。

第五，软件栈版本：驱动、CUDA、Container Toolkit、device plugin、NCCL、推理 engine 版本，任何一层不匹配都可能导致任务无法启动、性能异常或隐式降级。资源形状不只是硬件，还包括软件环境的保证。

第六，状态差异：是否已经拉好镜像、加载权重、构建 engine、预热 KV cache，对"从接到请求到真正服务"的路径长度影响很大。冷节点和热节点在同一资源池里，外部看起来都是空闲，但实际扩容时间差几分钟。

第七，租户边界：跨租户共享和同团队共享的风险不同。一个 MPS 进程的显存峰值异常，可能影响同 GPU 的另一个团队的服务。隔离不只是性能问题，也是安全和 SLA 问题。

把这七条约束放在一起，平台不能只暴露 nvidia.com/gpu: 1。它必须回答"这 1 个 GPU 到底是什么型号、什么显存、什么切分方式、什么隔离等级、什么性能承诺、什么故障边界"。这就是 GPU 资源层不可化简的问题：资源形状的产品化表达。

推 — 从这个问题如何推导出每个机制

每一个 GPU 资源机制都不是凭空发明的，而是从上面的约束中自然推导出来的。理解推导过程，才能理解为什么去掉任何一个机制都会让系统在某个边缘情况下失效。

从"大训练和大模型需要完整显存、拓扑和性能确定性"推出整卡池。整卡是保护完整性的手段，不是低利用率的代名词。在没有更好工具之前，整卡是大作业的安全底线。识别哪些负载需要整卡，哪些可以进入共享池，是资源层设计的第一步。

从"小模型长期独占整卡会浪费，但又需要真实的隔离而不是任务互扰"推出 MIG。MIG 在硬件层面切分 GPU，每个实例有独立的 SM、L2 slice 和 HBM segment，隔离强度接近整卡，但允许一张卡承载多个负载。但 profile 是固定的，不能任意比例——这不是软件限制，而是 GPU 内部硬件结构的直接结果。

从"同信任域的轻量进程想共享 CUDA 上下文，降低 kernel 提交开销"推出 MPS。MPS 让多个 CUDA 进程通过同一个 server 进程调度 GPU，Volta+ 还支持 SM 配额限制，接近"软 MIG"。但显存仍然共享，一个进程崩溃可能污染同卡所有客户端。

从"开发、教学和低优先级任务只需要先跑起来，不在乎稳定性"推出 time-slicing。time-slicing 由 device plugin 把 1 张物理 GPU 虚报成 N 个资源，多 Pod 轮流使用。它没有任何隔离，但大幅提高资源可获得性——是最轻量的共享方式，也是承诺最弱的。

从"模型冷启动慢，权重加载和 engine 构建昂贵"推出 warm pool。warm pool 不增加总容量，而是通过长期占用一部分容量，换取启动路径的缩短，从而提升扩容响应速度。热到哪一层（节点/镜像/权重/engine）决定了扩容速度，也决定了维护成本。

从"资源形状越来越多，账面空闲和可调度空闲分裂"推出 bin packing 和碎片化治理。当集群里同时有整卡、MIG、MPS 和 warm pool，总空闲 GPU 数已经没有意义，必须按形状管理可用性。保留关键形状不是浪费，是预防碎片。

从"共享会带来互扰，不同租户对互扰的容忍度不同"推出隔离等级、性能确定性和准入策略。跨租户必须有明确的隔离边界；共享池必须有明确的 SLA 降级声明；MPS 和 time-slicing 不应对跨租户场景作强承诺。

2. 概念先说清楚

整卡池是什么，不是什么

整卡池把物理 GPU 作为最小分配单元。一个 Pod 获得一张或多张完整 GPU，通常通过 nvidia.com/gpu 或平台定义的 ResourceFlavor 表达。

整卡池不是低利用率的同义词。对于多卡训练、大模型推理、强 SLA 在线服务、长上下文、RDMA/NVLink 敏感任务，整卡池是保护性能确定性和拓扑完整性的必要手段。

MIG 是什么，不是什么

MIG（Multi-Instance GPU）是 NVIDIA 部分数据中心 GPU 支持的硬件切分能力。它把一张物理卡切成若干固定 profile，每个实例拥有相对隔离的显存、计算资源和故障边界。

MIG 不是显存超卖，也不是任意比例切片。它只能使用硬件支持的 profile。切分形状如果与业务需求不匹配，会产生比整卡更难解释的碎片。

MPS 是什么，不是什么

MPS（Multi-Process Service）让多个 CUDA 进程共享同一 GPU 上下文，降低上下文切换和提交开销，改善轻量 kernel 并发。

MPS 不是强隔离多租户。它更适合同团队、同信任域、可容忍互扰的任务。跨租户使用 MPS 时，一个进程的显存峰值、异常 kernel 或错误可能影响同卡其他进程。

Time-slicing 是什么，不是什么

Time-slicing 通过时间片让多个工作负载轮流使用同一张 GPU。它通常由 device plugin 配置表达，把 1 张物理 GPU 虚报成 N 个可分配资源。

Time-slicing 不是性能承诺。它适合 notebook、教学、开发、demo 和低优先级实验，不适合 P99 延迟、吞吐和抖动有明确 SLA 的生产推理。

Warm pool 是什么，不是什么

Warm pool 是预热容量或预热状态：热节点、热镜像、热权重、热 engine、热副本、热 KV cache。它缩短从"需要扩容"到"可以接流量"的路径。

Warm pool 不是 GPU 切分方式，也不增加总容量。它用长期占用成本换启动速度。

控制路径

运维系统把节点划入不同 GPU 池，例如 h100-full、h100-mig-small、l40s-dev-shared。GPU Operator、device plugin、MIG manager、MPS 组件在节点上安装并暴露资源。NFD 或 GPU feature discovery 给节点打上型号、显存、MIG、拓扑和软件版本标签。平台把用户请求转换成 ResourceFlavor。队列和配额层决定租户是否有资格使用该 flavor。调度器根据资源数量、节点标签、污点、亲和、拓扑和 gang 条件选择节点。kubelet 调用 device plugin 分配设备，runtime 注入 /dev/nvidia* 和驱动库。观测系统采集 GPU util、显存、错误、XID、MIG 使用、共享倍率和 throttling。

4. 原理：切分与共享如何工作

整卡：保护完整性

整卡调度的核心价值是完整性：完整显存（大模型权重、KV cache 和训练 activation 不被硬切）、完整计算资源（SM、Tensor Core、带宽不被固定切片）、完整拓扑（多卡作业可以获得同机、同 NVLink/NVSwitch 域的 GPU）、完整故障边界（同卡没有其他租户任务互扰）。

整卡的代价是小模型可能低利用率。治理方向不是简单共享所有卡，而是识别哪些负载需要整卡，哪些负载可以进入 MIG 或共享池。

MIG 的硬件分区机制：为什么是这些 profile

MIG 只能使用固定 profile，这不是软件限制，而是硬件结构决定的。以 H100 SXM 80GB 为例：

H100 GPU 内部:
  ┌─────────────────────────────────────────────────────────┐
  │  144 个 SM（Streaming Multiprocessor）                  │
  │  组织成 8 个 GPC（GPU Processing Cluster），每 GPC 18 SM │
  │                                                         │
  │  L2 cache: 50MB，分成 8 个 slice，每 GPC 一个           │
  │                                                         │
  │  HBM3: 80GB                                             │
  │                                                         │
  │  GPU Engine + PCIe DMA + 通用控制单元 (1 份固定开销)    │
  └─────────────────────────────────────────────────────────┘

一个 GI（GPU Instance） = 1+ 个 GPC 的连续切片 + 对应比例的 L2 slice + 对应比例的 HBM。每个 GI 有独立的 memory controller path 和 L2 slice，物理上不共享——这是"硬件级隔离"的物理含义。一个 CI（Compute Instance） = GI 内的 SM 子集，多个 CI 共享同一 GI 的 memory，但 SM 独占。

H100 的 GPC 是 8 个，但 1 个 GPC 给 GPU engine 和系统用，用户可分配的最多 7 个 GPC。这就是为什么最多 7 个 1g.10gb 实例：

ProfileGPC 数L2 (MB)HBM (GB)最多实例数等效算力比例
1g.10gb16.251071/7 ≈ 14%
1g.10gb+me16.25107同上，带 media engine
2g.20gb212.52032/7 ≈ 28%
3g.40gb318.754023/7 ≈ 42%
4g.40gb4254014/7
7g.80gb750801整卡

为什么不能任意切分：L2 cache 必须按 slice 整数倍分配（每 GPC 一个 slice）；HBM 控制器在 GPC 边界路由，跨 GPC 的访问会绕远路；SM 调度器的硬件实现假设连续 GPC，跨 GPC 的非连续切片性能不可预测；NVIDIA 只验证了固定 profile 的隔离强度，任意切分会让性能/隔离不可保证。

MIG 碎片的本质：集群里有节点全部切成 1g.10gb，总共 280 个实例。突然来一个 3g.40gb 请求——虽然总算力够，但没有任何节点上有连续 3 个未占用的 GPC。这就是 MIG 的碎片：profile 错配比"显存不够"更难定位。诊断用 nvidia-smi -L 查看每个 GPU 上的 MIG profile 分布和占用。

MIG 重切命令序列（必须先停所有用该 GPU 的进程）：

nvidia-smi mig -dci   # destroy all CI
nvidia-smi mig -dgi   # destroy all GI
nvidia-smi mig -cgi 19,19,19,19,19,19,19  # create 7 个 1g.10gb (profile id 19)
nvidia-smi mig -cci   # auto-create CI

时序：destroy + create 大约 5-10 秒，但期间所有该 GPU 的进程必须停——这就是为什么 MIG 重切要走维护窗口。

MPS：共享 CUDA 执行通道

MPS 通过一个控制 daemon 协调多个 CUDA 进程共享 GPU。节点启动 nvidia-cuda-mps-control daemon，它 fork 出 per-GPU 的 nvidia-cuda-mps-server，持有该 GPU 的 CUDA context。应用进程作为 CUDA client，设置 CUDA_MPS_PIPE_DIRECTORY，所有 CUDA call 通过 named pipe 转发给 MPS server 调度。

Pascal 之前的 MPS 是软件 time-slicing 的高级版：所有 client 共享单一 GPU stream context，靠软件 stream interleaving 调度。一个 client 跑 long kernel 期间其他 client 等待，互扰严重。

Volta+ 的 MPS 支持硬件 multi-context concurrent execution，每个 client 可以配置 SM 配额：

export CUDA_MPS_ACTIVE_THREAD_PERCENTAGE=50
./my_cuda_app

GPU 硬件层面把该 client 的 thread block 限制在 50% 的 SM 上——不是靠时间错峰，是 SM 资源真正分配。这是 Volta+ MPS 与 Pascal MPS 的根本区别——Volta MPS 接近"软 MIG"，但显存仍然共享，隔离不如 MIG 强。

Time-slicing：Device Plugin 的虚报机制

Time-slicing 的实现原理非常直接：Device Plugin 在 ListAndWatch 里对单个物理 GPU 报告 N 份虚拟 device ID：

# /etc/nvidia-device-plugin/config.yaml
sharing:
  timeSlicing:
    resources:
      - name: nvidia.com/gpu
        replicas: 4   # 1 张物理 GPU 报告成 4 个 nvidia.com/gpu

4 个 Pod 各申请 nvidia.com/gpu: 1 都能调度上去，但全部看到同一张物理 GPU（同一 UUID），CUDA context 各自独立，完全靠 GPU 硬件本身的 time-slicing（CUDA context switch）轮转。

time-slicing 没有任何隔离：4 个 Pod 共享显存（nvidia-smi 在每个 Pod 内都看到整张 80GB）、共享 SM、共享 L2、共享 PCIe 带宽。一个 Pod cudaMalloc 80GB 会让其他 Pod 的 cudaMalloc 失败。哪个 Pod 跑大 kernel 就占满 GPU，其他 Pod 的 kernel 排队。可以设 replicas: 16 让一张 GPU 报成 16 份——但 16 个 Pod 一起跑性能极差。

生产建议：使用 rename 把 time-slicing 资源改名，与整卡池隔离：

sharing:
  timeSlicing:
    resources:
      - name: nvidia.com/gpu
        replicas: 4
        rename: nvidia.com/gpu.shared   # 改资源名，避免和整卡混

还可以与 MPS 配合，让 4 个 client 走 MPS 路径，比纯 time-slicing 强（有 SM 配额、有显存软上限），但仍然是同信任域才推荐：

sharing:
  mps:
    resources:
      - name: nvidia.com/gpu
        replicas: 4
        memSlicePercentage: 25   # 每 client 显存上限 25%

Warm pool：热的是路径，不是容量

推理扩容慢常常不是没有 GPU，而是启动路径长：

节点加入 -> 镜像拉取 -> 权重下载 -> engine 构建 -> 显存分配 -> 预热 -> readiness
Warm pool 对象缩短什么成本
热节点节点 provisioning空闲节点费用
热镜像image pull镜像缓存和更新治理
热权重weight download磁盘、网络、版本一致性
热 engineTensorRT / vLLM 初始化版本和硬件绑定
热副本readiness 到接流量GPU 常驻成本
热 KV / 预热请求首批请求抖动预热流量和状态管理
最佳实践：Warm pool 必须按模型、卡型、MIG profile 和版本管理。一个 H100 整卡热副本不能替代 3g.40gb MIG 热副本。热到哪一层需要和业务谈清楚：只热节点不热权重，扩容时间下降有限。

5. 资源形状：从硬件到平台 SKU

资源形状是平台对 GPU 可用性的产品化表达。它不只是数量，还包括：GPU 型号和显存、是否整卡/MIG/MPS/time-slicing、单节点 GPU 数量和拓扑、驱动/CUDA/NCCL/推理 engine 版本、是否允许跨租户共享、是否可抢占/spot/warm，以及计费倍率和配额归属。

ResourceFlavor 设计示例

Flavor资源适合负载隔离SLA
h100-80gb-full-nvlinkH100 80GB 整卡，同 NVLink 域8 卡训练、70B 推理强强
h100-80gb-full-singleH100 80GB 单整卡中大模型推理、单卡训练强强
h100-mig-1g.10gbMIG 小切片7B 小模型、embedding、notebook强中
a100-mig-3g.40gbMIG 中切片中等模型推理强中
l40s-mps-teamMPS 同团队共享轻量实验、低风险批处理中弱弱
l4-timeslice-devtime-slicing开发、教学、demo弱无强承诺
h100-warm-70b热权重 / 热副本70B 在线扩容强强

配额和计费

资源形状必须进入配额和计费，否则平台会出现"账面公平、实际不公平"：1 个 H100 整卡不能与 1 个 L4 time-slice 等价；1 个 3g.40gb MIG 不能与 1 个 1g.10gb MIG 等价；热副本消耗 GPU 即使没有流量，也应计入容量成本；MPS/time-slicing 的计费需要表达共享倍率和性能承诺缺失。

计费建议：MPS/time-slicing 常见做法是用计费单位乘以共享系数，例如 4 倍 time-slicing 的一份 = 0.25 整卡当量，并在计费单上注明 best-effort。每个 flavor 都进入配额、计费和审计，是平台可信任的基础。

发布路径

  1. 盘点现有 workload 的显存峰值、GPU util、吞吐和延迟。
  2. 先拆出整卡保护池，避免 MIG 或共享策略破坏关键大作业。
  3. 选择单一低风险池试点 MIG 或 time-slicing。
  4. 用 ResourceFlavor 和 quota 显式暴露新资源形状。
  5. 接入 DCGM、应用指标和队列指标，观察性能互扰。
  6. 配置回滚：MIG 重切窗口、节点 cordon/drain、迁移计划。
  7. 再扩大到生产推理或多租户场景。

7. Bin Packing 与碎片化治理

碎片化定义

碎片化不是"GPU 利用率不高"，而是：账面上有空闲容量，但没有某个工作负载所需的完整资源形状。

例子：4 台 8×H100 节点，总空闲 10 张 GPU：

节点空闲 GPU当前占用对 8 卡训练是否可用
node-a35 张被推理副本占用不可用
node-b26 张被实验任务占用不可用
node-c4已切 MIG profile不可用
node-d17 张被训练占用不可用

用户说"还有 10 张空闲卡"，平台说"没有 1 台完整 8 卡节点"，两者都对。差异在资源形状。

Bin packing 的目标

Bin packing 不是把每张卡都塞满，而是保留关键形状：对 8 卡训练，保留完整 8 卡节点；对 70B 推理，保留成对或成组整卡；对小模型推理，把相近 profile 放到 MIG 池；对开发任务，优先填共享池，不污染整卡训练池；对可抢占任务，优先填将来可回收的位置。

flowchart LR
  A[新任务到达] --> B{任务类型}
  B --> C[8卡训练] --> D[检查 full-train 池完整节点]
  B --> E[小模型推理] --> F[优先调度到 mig-small 池]
  B --> G[开发 Notebook] --> H[调度到 shared-dev 时间片池]
  B --> I[70B 在线] --> J[检查 full-online 或 warm-online]
  D -->|无完整节点| K[Pending / defrag 窗口]
  F -->|无合适 profile| L[等待或重切窗口]
  H -->|超出限额| M[拒绝 / best-effort 排队]
  J -->|无 warm 副本| N[冷启动路径]

策略对照

策略适合风险
compact 小任务保留完整节点单节点热点和故障影响集中
spread 在线副本降低故障域风险破坏整卡训练形状
按卡型拆池避免性能误配池过细降低利用率
按 MIG profile 拆池profile 可审计需求变化时难借用
低峰 defrag回收碎片，恢复大形状需要 checkpoint 和维护窗口
reserved full nodes保护大训练窗口闲时看起来利用率低
碎片治理动作清单：建立 pending by flavor 和 available shape 看板；定义关键形状，例如 8xh100-full-node；小任务默认 compact 到非关键节点；借用任务必须可抢占，方便 defrag；定期复盘 MIG profile 分布，避免长期错配；对训练高峰前做预整理，释放完整节点；把碎片成本纳入队列策略，而不是只看 GPU util。

常见反模式

反模式现象修复方向

Checklist

  • GPU flavor 覆盖型号、显存、整卡/MIG/MPS/time-slicing、拓扑和 SLA。
  • 多卡训练池保留完整节点，并与小任务隔离。
  • MIG profile 来自真实显存画像，不是硬件最大切分能力。
  • MPS 限定同信任域，并限制同卡进程数和显存。
  • Time-slicing 标注 best-effort，不承诺强 SLA。
  • Warm pool 明确热到节点、镜像、权重、engine 还是副本。
  • 每个 flavor 都进入配额、计费、审计和看板。
  • 看板展示 pending by flavor 和关键形状可用数。
  • 有 MIG 重切、节点 drain、defrag 的维护窗口。
  • XID、ECC、显存、共享倍率和 cold start 都可观测。

11. Worked Example：从整卡浪费到资源形状治理

初始状态

一个团队有 64 张 H100：20 个 7B 小模型各占 1 张整卡（平均 GPU util 15%）、4 个 70B 服务各占 2 张整卡（扩容冷启动 8 分钟）、研究团队每天提交 8 卡训练（p95 等待超过 2 小时）、notebook 用户经常申请整卡，运行 10 分钟后空闲。

诊断

指标状态解释
平均 GPU util45%不算高，但不能说明容量健康
总空闲 GPU12看起来有空闲
完整 8 卡节点0训练 Pending 的直接原因
7B 显存峰值13GB不需要 H100 整卡
70B cold start权重 4m + engine 3m + readiness 1mwarm pool 应热到 engine
notebook 使用峰值短、空闲长适合共享池

改造步骤

  1. 把 3 台 8 卡节点划入 h100-full-train，小任务不得进入。
  2. 把 2 台节点划入 h100-full-online，承载 70B 服务。
  3. 把 2 台节点划入 h100-mig-small，按 1g.10gb 和 2g.20gb 承载 7B。
  4. 用 4 张 GPU 做 h100-warm-70b，预加载权重和 engine。
  5. 剩余 4 张 GPU 做 h100-dev-shared，time-slicing 给 notebook。
  6. 队列侧把 dev-shared 标记为 best-effort 和可抢占。

12. 本章小结

主题关键点
整卡保护显存、拓扑、隔离和性能确定性
MIG硬件固定切分（GPC 粒度），适合稳定小规格强隔离场景
MPS同信任域多进程共享，Volta+ 支持 SM 配额，不适合默认跨租户
Time-slicingdevice plugin 虚报资源，提高开发可获得性，不提供强性能承诺
Warm pool缩短冷启动路径，不增加总容量
资源形状GPU 平台应调度、配额、计费 flavor，而不是抽象 GPU 数
Bin packing目标是保留关键形状，不是盲目塞满
