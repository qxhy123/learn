1. 第一性原理拆解：队列、配额与自动扩缩容

拆 — 不可化简的问题

剥离 Kubernetes、Volcano、Kueue、HPA、KEDA、MIG、MPS 和 GPU Operator 这些工具名之后，本章要解决的不可化简问题只有一个：有限、离散、异构、启动慢的计算资源，如何在多租户同时竞争时，被持续分配给正确的工作负载，并且让用户知道为什么是这个结果。AI 平台里的 GPU 不是普通 CPU core。它昂贵、数量有限、卡型不同、显存不同、拓扑不同；训练任务常常需要 4 卡或 8 卡一起到位，推理服务又常常需要副本常驻、权重预热和稳定延迟。资源不是一桶可以随便舀的水，而是一组带形状的零件：一张 H100 80GB、一个 3g.40gb MIG slice、一台 8 卡 NVLink 节点、一个已加载 70B 权重的热副本，它们在调度器眼里并不等价。

这就带来三个硬约束。第一，需求到达是随机的，资源释放是离散的。平均 GPU utilization 为 60% 不代表用户马上能拿到 8 张相邻 GPU，因为空闲卡可能分散在不同节点、不同卡型或不同 MIG profile 中。第二，公平不是自然发生的。没有配额，强势团队会长期占住稀缺资源；配额过硬，资源又会被锁在暂时不用的队列里。第三，弹性不是瞬时发生的。在线推理扩一个副本，可能要经历调度、镜像拉取、权重加载、KV cache 预热和 readiness；离线训练扩容更麻烦，因为一个正在跑的 64 卡作业通常不能随便插入 8 张新卡。队列、配额、抢占、GPU 切分和 autoscaling，本质上都是在这些硬约束之间做可解释的取舍。

从平台体验看，这个问题还包含一个经常被低估的维度：解释性。用户看到的只是任务 Pending、服务扩不起来、线上 P99 变差、低优先级作业被中断，但平台内部的真实原因可能是配额耗尽、优先级不够、拓扑形状不完整、MIG profile 不匹配、冷启动仍在进行、指标触发处于 cooldown，或者高优任务正在回收借用配额。一个成熟平台不能只给出“调度失败”或“资源不足”的泛化错误，而要把排队规则、配额边界、抢占条件和扩容状态产品化表达。否则，即使调度器算法是正确的，用户也会把它感知成随机、偏袒和不可控。

推 — 从这个问题如何推导出每个机制

既然资源稀缺且请求会同时到达，平台首先需要队列：把“谁先等待、等待多久、按什么规则进入候选集”显式化。先来先服务会让大租户或长作业占住集群，所以必须引入配额：给团队、业务线或环境一个可审计的上限和保底。配额解决“谁最多能占多少”，但生产推理和实验训练不能完全同权，于是出现优先级。如果低优先级任务已经占满资源，高优先级任务仍然只能等待，所以还需要抢占。抢占不是按钮，而是一份恢复契约：只有任务能 checkpoint、能重入队、能解释损失，抢占才是工程机制；没有恢复契约的抢占，只是把资源压力转化成重复计算和用户抱怨。

再往下推，GPU 资源不是单一维度。一个任务可能吃 8 GPU、256 vCPU 和 1TB 内存，另一个任务只吃 1 GPU 但占 80GB 显存。只按 GPU 数或作业数谈公平会失真，所以需要 DRF（Dominant Resource Fairness）这类多资源公平思想：看每个队列在自己最紧张资源上的占比。资源的离散形状又会推导出碎片化治理：调度器不仅要算剩余数量，还要保留整节点、同卡型、同 MIG profile、同拓扑的可运行形状。为了提高小模型和开发任务的可获得性，平台会进一步引入整卡、MIG、MPS、Time-Slicing 等共享方式。最后，当排队指标或在线延迟持续恶化时，平台才会触发自动扩缩容，但扩容只能补未来容量，不能立即消除冷启动、配额僵硬、拓扑碎片和模型加载这些现实成本。

因此，本章所有机制可以按一条因果链理解：队列负责把竞争显式化，配额负责给竞争设边界，优先级负责表达业务价值，抢占负责在边界冲突时执行纠偏，DRF 负责避免多资源公平失真，GPU 形状治理负责避免“账面有卡但不可运行”，autoscaling 负责在未来容量不足时增加供给。它们不是互相替代的功能，而是控制面的不同层次。只做 HPA 不做队列，扩容慢时仍然会排队；只做配额不做借用，低峰资源会闲置；只做优先级不做抢占，高优任务仍可能被低优任务卡住；只看 GPU utilization 不看资源形状，就会误判容量。

3. 为什么 AI 平台比普通服务更依赖队列

普通 Web 服务里，很多请求只占用 CPU 和少量内存，请求结束就释放。而 AI 平台里的许多任务具有不同特征：占用 GPU 这类离散而昂贵的资源，任务持续时间可能很长，多卡任务必须一次性拿到完整资源形状，任务之间优先级差异很大。因此，AI 平台不能只依赖“谁先来谁先跑”，而必须明确谁可以排队等待、谁必须保底、谁可以被抢占、谁在高峰期应该被限流。

在线推理
用户请求持续到达，模型副本需要常驻，扩容涉及调度、权重加载、预热和 readiness。排队时间会直接进入 P95 / P99 延迟。
离线训练
训练任务生命周期长，多卡 gang 一次性到位，失败恢复依赖 checkpoint。排队不只是等待，也影响实验迭代速度和 GPU 预算。
工作负载普通服务常见资源形态AI 平台资源形态为什么需要队列
短请求服务CPU / 内存可细粒度复用推理副本占用 GPU 与显存请求高峰会转化成 queue wait 与 tail latency
批处理任务可拆分、可重试、资源相对通用训练可能需要同卡型、多卡、同拓扑必须等待完整可运行形状，而不是任意空闲卡
实验任务通常容忍延迟可能抢占高端 GPU 或本地 SSD需要低优先级队列和可抢占策略
边界提醒：队列不是附属功能，而是平台公平性和效率的核心机制。没有队列，用户只会看到“随机 Pending”；没有解释，队列越复杂越像黑盒。

4. 队列、配额、优先级与抢占

这四件事经常一起出现，但逻辑上不同。队列回答任务按照什么顺序等待和被调度；配额回答某个团队或租户最多能占多少资源；优先级回答资源紧张时谁先执行；抢占回答高优先级任务来了，是否可以中断低优先级任务。没有配额的高优先级系统会被强势租户垄断；没有抢占的优先级系统在高峰期往往形同虚设。

概念回答的问题常见平台对象设计失败时的症状
队列谁在等待、按什么顺序进入候选集Queue、ClusterQueue、PodGroup、JobQueuePending 原因不可解释，长作业或大租户挤压其他人
配额谁最多能占多少，谁至少有保底ResourceQuota、Queue quota、部门预算太松导致垄断，太硬导致闲置不能借用
优先级资源冲突时谁先被满足PriorityClass、SLA class、业务等级实验流量压住生产流量，或者低优队列长期饥饿
抢占是否允许高优任务中断低优任务PreemptionPolicy、drain、checkpoint 恢复没有恢复契约时，抢占变成重复成本和投诉

5. 一个简单的排队视角

如果系统单位时间到达任务数为 lambda，单位时间服务能力为 mu，那么当 lambda < mu 时队列通常可控；当 lambda 接近 mu 时等待时间会急剧增加；当 lambda > mu 时系统必然积压。这就是为什么平台不能只看平均利用率。即使平均利用率看起来正常，短时间高峰也可能造成严重排队。

低负载
lambda 远小于 mu，排队主要来自冷启动、配额或资源形状不匹配。
临界区
lambda 接近 mu，微小流量尖峰也会放大等待时间。
过载
lambda 大于 mu，没有限流、降级或扩容时积压必然增长。
flowchart TD
  A[需求到达 lambda] --> C{lambda 与 mu 的关系}
  B[服务能力 mu] --> C
  C -- lambda 小于 mu --> D[队列可控]
  C -- lambda 接近 mu --> E[等待时间陡增]
  C -- lambda 大于 mu --> F[积压持续增长]
  E --> G[在线推理 P95/P99 恶化]
  E --> H[离线训练 Pending 增加]
  F --> I[限流 降级 扩容 抢占]

对在线推理而言，这会表现为 queue wait time 上升、P95 / P99 延迟恶化。对离线训练而言，这会表现为作业长时间 Pending，用户抱怨“平台有卡但我任务跑不起来”。

6. 配额的真正价值与 DRF 公平调度

很多人把配额理解成“限制使用”。更准确地说，配额在做三件事：防止强势租户垄断资源，给关键业务保底，为预算和容量规划提供边界。配额设计不好，平台会在两种极端之间摇摆：太松时资源被吃光，太死时资源闲着也借不出来。因此很多成熟平台还会加入“保底 + 可借用”的策略。

工程原则：配额最好同时表达 reserved、limit 和 borrow 三个语义。reserved 保证关键队列最低容量，limit 防止强势租户吃光全局，borrow 让低峰闲置资源能临时被使用。

为什么“只看优先级”不够？因为 AI 平台不是单资源系统。一个队列可能主要吃 GPU，另一个队列可能主要吃 CPU / 内存。只按优先级或作业数排序，很容易把某一类资源长期挤爆。DRF 关注的是：谁占用了自己最稀缺的那类资源最多。这样定义公平，比“谁先来”或“谁权重大”更适合多资源集群。

机制更适合解决什么主要短板
简单优先级明确保核心业务先跑难处理多资源公平
纯配额上限防止单租户吃光资源闲置资源借用不灵活
DRF同时考虑 GPU、CPU、内存等多资源公平实现和解释成本更高

假设一个资源池有 100 张 GPU、1000 vCPU、2000GB 内存，三个队列当前占用如下：

工程边界：DRF 的前提是资源可计量且需求可信。GPU、CPU、内存容易计量，网络带宽、本地 SSD IOPS、KV cache 峰值很难准确声明；一旦用户低报 request，DRF 会奖励“写小 request、实际 burst”的负载。

7. 抢占不是万能按钮

抢占可以显著改善高优先级任务的响应，但它必须与任务特性绑定。推理服务通常不适合粗暴抢占，因为中断服务实例会直接影响用户请求，更常见的是限流、重新路由、优先保障核心租户。训练任务更有可能被抢占，但前提是有可恢复 checkpoint、平台知道如何重新入队、用户清楚任务被抢占的规则。没有恢复机制的抢占，只是在制造重复成本。

对象是否适合抢占推荐动作风险
核心在线推理副本通常不适合保留池、限流、路由切换、优先级队列直接中断会放大用户可见错误
低优批推理适合可重试队列、幂等输出、预算限流重复计算和队列回填
长训练任务有条件适合周期性 checkpoint、重入队、损失审计checkpoint 太稀疏会浪费大量 GPU 小时
开发实验任务适合低优先级、Time-Slicing、可抢占池用户体验不稳定，需要清晰预期
严重风险：不要把抢占当成容量规划的替代品。抢占只能重新分配已有容量，不能解决长期供给不足；没有 checkpoint 和审计的抢占还会让平台失去信任。

8. 自动扩缩容的边界

在线推理

自动扩缩容适合流量波动明显、模型副本可快速启动、有清晰延迟或队列指标的服务。但它的难点在于模型很大、冷启动慢、显存预热成本高、token 长度变化剧烈。因此，在线推理的 autoscaling 通常不能只看 CPU 使用率，而要看 queue length、queue wait time、active sequences、GPU / 显存水位和 token throughput。

离线训练

训练任务的 autoscaling 更受限制，因为一个作业可能要求固定卡数，多卡任务对拓扑敏感，扩出来的新节点可能来不及参与当前作业。所以训练场景更常见的是“集群层扩容”，而不是服务式的细粒度 HPA。

场景适合的扩缩容粒度主要指标关键限制
交互式在线推理服务副本 / 热池queue wait、P99、active sequences、token throughput冷启动和 KV cache 预热
批量离线推理队列 worker / GPU 池backlog、deadline miss、GPU 利用率输出幂等与重试成本
多机训练集群节点池pending jobs、gang 可满足率、队列等待作业固定卡数和拓扑约束
边界提醒：扩容只能补未来容量，不能让正在冷启动的副本立刻承接流量，也不能把碎片化的 GPU 自动拼成完整 8 卡节点。

9. GPU 资源碎片化

平台工程里更准确的说法是：账面有容量，不等于调度器手里有可用形状。最典型的情况是：集群看起来还有很多空闲 GPU，但这些资源被切散到不同节点、不同卡型、不同显存规格、不同 MIG slice，或者被各个队列的硬配额锁住，结果需要 8 卡训练、80GB 显存推理、固定 MIG profile 的任务都拿不到真正可运行的资源。

看一个具体例子：集群有 4 台 8xH100 80GB 节点，总计 32 张 GPU。当前空闲 10 张，账面空闲率 31.25%。但节点分布如下：

节点空闲 GPU已占用形状对 8 卡训练是否可用
node-a35 张被在线推理副本长期占用不可用，缺 5 张同节点 GPU
node-b26 张被低优先级训练占用不可用，缺 6 张同节点 GPU
node-c44 张被切成 MIG 1g.10gb不可用，profile 和整卡语义不匹配
node-d17 张被实验任务占用不可用，缺 7 张同节点 GPU

一个需要 8 x H100 80GB + NVLink 的训练作业会 Pending，虽然监控面板显示还有 10 张 GPU 空着。调度器不是不会数数，而是这些 GPU 无法拼成作业要求的形状。

碎片来源平台上会看到什么现象为什么会浪费可用资源
不同 GPU 型号混部A100、H100、L40S 都有空闲，但作业仍 Pending作业镜像、算子、吞吐预期往往绑定卡型
显存大小不一致40GB 卡空着，80GB 需求作业排队约束首先是显存，不是 GPU 数量
MIG slice 粒度固定还剩很多 1g.10gb，但 3g.40gb 服务扩不起来错误切片会制造二次碎片
长短任务混排短推理作业频繁插队，长训练作业一直等完整拓扑长作业需要连续且稳定的资源窗口
队列 quota 过硬某队列空着 GPU，另一队列排爆资源被锁在暂时不用的边界里
flowchart LR
  A[账面空闲 10 GPU] --> B{能否形成目标形状}
  B -- 同节点8卡不足 --> C[8卡训练 Pending]
  B -- MIG profile不匹配 --> D[大显存推理扩不起来]
  B -- 卡型显存不一致 --> E[SKU 不可替代]
  B -- quota锁住空闲 --> F[跨队列不能借用]
  C --> G[关键指标: 可用8卡节点数]
  D --> H[关键指标: 可用MIG profile数]
  E --> I[关键指标: SKU级空闲容量]
  F --> J[关键指标: borrowable quota]
工程边界：碎片化不可能被完全消除。过度 compact 会造成热点；过度预留会降低利用率；频繁迁移会放大 checkpoint、镜像拉取和缓存失效成本。平台要优化的是“关键形状的可获得性”，而不是只追求总 GPU 空闲数。

10. GPU 虚拟化：整卡、MIG、MPS 与 Time-Slicing

当平台开始面对“小模型很多、租户很多、整卡经常浪费”的局面，就会讨论 GPU 切分。但切分提高的是利用率，不一定提高稳定性，因此要和 第 18 章 的运行时暴露、第 19 章 的调度资源一起看。四种常见方式的差别，不在于“能不能共享”，而在于共享发生在硬件层、驱动层还是调度层。

方式工作方式隔离程度更适合什么场景不适合什么场景
整卡调度一个工作负载独占整张卡最强多卡训练、大上下文推理、强 SLA 在线服务小模型常驻导致整卡长期低利用
MIG硬件级切分 GPU，显存和部分计算资源按 profile 固定分配强多租户小模型推理、需要保底的共享集群动态负载变化很大、需要灵活伸缩显存形状
MPS多进程共享同一 GPU 上下文，提升并发提交效率弱同团队轻量推理、实验型多进程任务跨租户隔离、强故障域隔离、严格性能承诺
Time-Slicing / Sharing调度器或 device plugin 以时间片方式让多个 workload 轮流使用 GPU很弱开发环境、教学环境、低优先级批处理延迟敏感服务、长时间高负载训练
判断条件更适合的方式
任务需要稳定吞吐、显存峰值高、故障不能互相影响整卡或 MIG
希望把一张高端卡分给多个固定小服务，并且要配额化管理MIG
同一团队的多个轻量进程想共享同一张卡，提高提交并发MPS
只是为了让更多人先启动任务，容忍明显性能抖动Time-Slicing / Sharing
version: v1
flags:
  migStrategy: mixed
不要误用：MIG 不是动态弹性万能解。它把一张卡变成多个固定 SKU，如果 profile 设计错了，平台只是把整卡碎片化换成 MIG profile 碎片化。

11. 调度与配额策略：公平性和利用率的拉扯

当 GPU 已经被拆成多个 SKU，调度策略就决定了平台是在追求“更满”，还是追求“更公平”，还是在尽量保护关键业务。实践里通常不是单一算法取胜，而是组合拳。

策略平台收益代价失败条件
Bin packing / compact scheduling把小任务塞进少量节点，保留完整拓扑给 4 卡 / 8 卡大任务局部热点更明显，单节点故障影响更集中不区分卡型、显存和拓扑，只做数量打包
Gang scheduling保证多卡训练一次性拿齐资源，避免半启动半等待等待时间可能更长，调度器更复杂没有提前预留或紧凑摆放，大作业会长期饥饿
Priority + preemption关键在线服务或紧急训练可以快速拿到资源被抢占任务需要 checkpoint / 重试能力没有恢复机制时，抢占只会放大浪费
Borrowing quota闲时把保底配额借给别的队列，提高总体利用率回收时要处理驱逐、延迟上升和借用争议缺少回收规则或冷却时间
DRF 倾向的公平调度在 GPU、CPU、内存并存时更公平可解释性差，实现更重业务优先级远比资源公平更重要时会过于机械

一个常见的平台工程做法是：用 bin packing 和按卡型 / MIG profile 拆池来压低碎片；用 gang scheduling 保护多卡训练的最小可运行形状；用 priority / preemption 给关键业务开快车道，但只对可恢复任务生效；用保底 + 可借用 quota 平衡公平性和利用率；用 DRF 思路做多资源公平校正，而不是单独依赖它。

优化目标：平台工程师真正要优化的不是“GPU 利用率”这一个数字，而是关键队列等待时间、大任务完整形状可获得性、闲置容量可借用性这三个指标的组合。

12. 一个 autoscaling 触发框架

scale_out_if:
  queue_wait_p95_ms: "> 200"
  gpu_utilization: "> 75%"
  pending_requests: "> 100"
scale_in_if:
  queue_wait_p95_ms: "< 20"
  gpu_utilization: "< 35%"
  cooldown_minutes: 10

这类规则的重点不是语法，而是扩容触发不应只依赖单个指标，缩容要有冷却时间，长短请求混杂时需要更细的分层策略。

场景典型值说明
已有热副本的在线扩容反应时间10-30 秒主要消耗在调度和 readiness，而不是权重加载
大模型冷启动后新副本真正可接流量1-5 分钟常包含镜像拉取、权重加载、显存预热和 engine 初始化
交互式推理队列等待告警阈值P95 50-200 ms超过后用户通常已明显感知排队
离线训练队列等待 SLO5-30 分钟取决于队列等级和业务优先级，而不是统一常数
flowchart TD
  M[指标采集] --> Q[queue_wait_p95]
  M --> G[gpu_utilization]
  M --> P[pending_requests]
  M --> T[token_throughput]
  Q --> D{扩容条件同时满足?}
  G --> D
  P --> D
  T --> D
  D -- 是 --> O[Scale out]
  D -- 否 --> W[继续观测]
  O --> C[冷启动与readiness]
  C --> R[新副本接流量]
  R --> S{缩容条件与cooldown满足?}
  S -- 是 --> I[Scale in]
  S -- 否 --> W
参考数量级：这些值仅用于建立直觉，实际阈值会受模型大小、镜像体积、权重缓存、集群基线和用户延迟预算影响。

13. 常见故障模式

模式一：平台整体利用率不低，但关键任务一直排队

问题可能在配额分配僵硬、大量资源被低优先级长任务占住、多卡拓扑碎片化。此时不要只看总 GPU utilization，而要看可用 8 卡节点数、关键队列 pending time、可借用配额和低优任务可抢占比例。

模式二：自动扩容触发了，但用户体验没改善

问题可能是冷启动太慢、扩出的节点拿不到模型和热 cache、真正瓶颈不在副本数，而在检索或上游依赖。此时要把扩容事件、readiness 时间、模型加载时间和请求 trace 连起来看。

模式三：平台解释不清为什么某任务被抢占

问题通常是调度规则不透明、审计日志不足、配额与优先级设计没有产品化表达。抢占事件必须包含触发者、被抢占者、优先级差异、配额状态、恢复路径和预计损失。

故障现象优先检查纠偏动作
“有卡但跑不起来”卡型、显存、拓扑、MIG profile、gang 可满足率拆 SKU、保留完整节点、compact 低优任务
P99 高但 GPU 不满queue wait、KV cache、active sequences、检索依赖分层队列、限制长上下文、扩热副本
高优任务仍等待抢占策略、checkpoint 能力、borrow quota 回收启用可恢复抢占，明确回收冷却时间
缩容后立刻反弹cooldown、预测窗口、冷启动时间延长 cooldown，区分热池和冷池容量
排障底线：不要用“资源不足”结束诊断。AI 平台的资源不足必须继续拆成数量不足、形状不足、配额不足、优先级不足、冷启动不足或指标误判。

学习路线

  1. 先用队列视角理解等待时间：把在线推理的 queue wait 和离线训练的 pending time 统一看成稀缺资源竞争的外显指标。
