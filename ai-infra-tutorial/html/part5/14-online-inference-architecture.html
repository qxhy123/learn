1. 第一性原理拆解：在线推理架构

拆 — 不可化简的问题

在线推理架构要解决的不可化简问题，不是“如何把模型挂到一个 HTTP 端口后面”，而是：在请求不可预测、计算昂贵、状态沉重、用户等待有上限的条件下，怎样让每一次调用都尽量在承诺的时间内交付有用结果。第一次做模型服务的团队，最容易把在线推理理解成“带 GPU 的 Flask 服务”：写一个接口接 HTTP 请求，把模型 load 到显存，前向跑一次返回结果。这个心智模型在 demo 上完全够用，因为 demo 里的请求少、输入短、没有灰度、没有租户、没有下游依赖，也不需要解释为什么某个用户等了 12 秒。但生产系统的物理现实更硬：一个 70B 模型的单个副本可能占用多张 GPU；一次长 prompt prefill 会吞掉大量算力；decode 阶段会把 KV Cache 留在显存里；RAG 链路还会调用 embedding、向量库、rerank、安全过滤和工具服务。于是“模型推理”只是一条请求链路中的一段，服务是否可用取决于这条链路里最慢、最抖、最不可控的那几跳。

从第一性原理看，在线推理比传统 Web 服务难，不是因为入口协议特殊，而是因为它把四类约束叠在了一起。第一是成本约束：GPU 秒很贵，副本不是可以随便复制的廉价进程，扩容会带来显存、权重加载、warm pool 和缓存命中率的代价。第二是时间约束：用户不关心平均值，只关心自己这一次是否卡住；聊天场景的 TTFT 可能要压到 500 ms 内，TPOT 超过 150 ms/token 就会明显卡顿。第三是状态约束：KV Cache、prefix cache、会话亲和、模型版本和预热状态都决定了“同一个请求路由到不同副本”会有不同成本。第四是质量约束：HTTP 200 只能说明系统返回了字节，不能说明回答正确、安全、相关或可用。因此本章的核心不是记住某个 serving 框架，而是建立一种拆链路的直觉：一次请求的时间去哪了，尾延迟由哪一跳主导，哪些状态必须亲和，哪些失败必须在控制面里有自动动作。

推 — 从这个问题如何推导出每个机制

如果不可化简的问题是“按时交付有用结果”，第一个必然机制就是请求生命周期拆解。只有把端到端时间拆成 queue / preprocess / model / downstream / postprocess，再把 LLM 的 model 拆成 prefill / decode，平台才知道该扩 GPU、限流、优化检索、改 tokenizer，还是调整 batch。第二个必然机制是入口与路由分层。网关负责鉴权、限流、租户识别和基础日志；路由层负责模型版本、长短上下文、优先级、灰度、prefix-aware 亲和和 SLO-aware 选择副本。二者分离，是因为“谁可以进来”和“进来后去哪一个副本最合适”是两个不同问题。

第三个必然机制是副本池与缓存治理。模型副本不是无状态 worker：它有权重、CUDA context、allocator、KV Cache、prefix cache 和 warmup 状态。Round-robin 在普通 Web 服务里可能足够，在 LLM serving 里却可能摧毁 prefix cache 命中率，让同一 system prompt 的请求反复 prefill。第四个必然机制是尾延迟治理。输入长度可以差 100 倍，输出长度也可能被 max_tokens 顶满；如果只看平均延迟，最慢 1% 用户会被隐藏。于是指标必须从 QPS 扩展到 P50/P95/P99、TTFT、TPOT、ITL、E2EL 和 goodput。Goodput 的意义是把 SLO 纳入吞吐：超时完成的 token 不再被当作有价值的产出。

第五个必然机制是资源形态分离。Prefill 更偏 compute-bound，decode 更偏 memory-bandwidth-bound，还会长期占用 KV Cache。长上下文和短请求混在同一池里时，长 prefill 会把短请求的首 token 和后续 token 都拖慢，所以会推导出 chunked prefill、长短分流，甚至 prefill/decode disaggregation。第六个必然机制是冷启动、熔断和降级控制面。权重加载、运行时初始化、CUDA graph 捕获、缓存预热都需要时间，副本 ready 不等于可以立即接流量；下游抖动或 GPU 池饱和时，也不能靠人工临时决定是否关闭 rerank、切小模型、截短上下文或返回 429。这些策略必须是可配置、可观测、可演练的规则。最后，质量观测必然独立存在，因为模型可能“健康地生成垃圾”：系统指标、链路 trace、输出评测、灰度发布和回滚门禁要一起构成在线推理的运营闭环。

2. 在线推理到底在处理什么

一个在线推理系统最常见的工作流是：

客户端请求
  -> 网关
  -> 路由与鉴权
  -> 预处理
  -> 模型执行
  -> 后处理
  -> 返回结果

如果是 RAG 或多模型组合，这条链会继续延长：

客户端
  -> API 网关
  -> 意图识别 / 路由
  -> embedding
  -> 向量检索
  -> 重排
  -> LLM 生成
  -> 安全过滤
  -> 返回
常见误解：“模型执行时间”通常只是总延迟的一部分。平台工程里最危险的做法，是把模型执行时间误当成整个服务延迟。
链路段典型耗时工程含义
网关 + 鉴权约 5 ms通常不是均值大头，但会进入端到端 P99
Embedding 调用约 80 msRAG 场景的独立依赖，需要单独埋点
向量检索约 40 ms索引、过滤条件和租户隔离会改变尾延迟
重排模型约 120 ms可成为降级开关，不能和主模型混为一谈
LLM prefill约 300 ms受输入 token、prefix cache 和 batch 策略影响
LLM decode约 900 ms常是总耗时大头，也最受输出长度影响
安全过滤 + 后处理约 55 ms影响质量和合规，不能随意省略

  C[Client] --> G[API Gateway]
  G --> R[Intent / LLM Router]
  R --> E[Embedding]
  E --> V[Vector DB]
  V --> K[Rerank]
  K --> L[LLM Replica]
  L --> S[Safety Filter]
  S --> O[Response]
  R -. metrics .-> M[Metrics / Traces]
  L -. tokens .-> M
  V -. latency .-> M

这张链路图给出两个工程启示：LLM 确实常占大头，但不是全部；尾延迟的组成可能和平均延迟完全不同。平均 1500 ms 的服务，P99 可能是 8000 ms，而且多出来的 6500 ms 不一定在 LLM，而可能在 embedding 抖动、向量库扫全表，或者某个租户的长 prompt 把 decode 拖慢了。

3. 一次请求的时间拆解

可以用一个非常实用的式子来理解：

t_request = t_queue + t_preprocess + t_model + t_downstream + t_postprocess
t_model   = t_prefill + t_decode

这个拆解的工程意义很直接：如果 t_queue 高，问题可能在扩容、队列或批处理；如果 t_downstream 高，问题可能在检索、特征或向量库；如果 t_model 高，才更可能是模型执行本身、显存或 batch 策略。

指标全称含义典型目标
TTFTTime to First Token请求到第一个 token 返回的时间聊天场景 < 500 ms，代码补全 < 100 ms
TPOTTime per Output Token除第一个 token 外，平均每个 token 耗时< 100 ms 流畅，> 150 ms 明显卡顿
ITLInter-Token Latency两个相邻 token 之间的时间间隔用于抓局部抖动
E2ELEnd-to-End Latency从请求到最后一个 token 完成由用例决定
TTLTTime to Last Token同 E2EL有些文档用 TTLT 区分于 TPOT
读速直觉：人类阅读速度约 250 词/分钟，按 1.3 token/词换算约 5 token/秒，也就是约 200 ms/token。TPOT 做到 100 ms 以下，用户通常会感觉输出足够流畅。

传统 QPS/TPS 在 LLM 服务里有缺陷：它把超时请求也算进去了。一个系统每秒完成 1000 个请求，但如果其中 400 个已经超过客户端超时，真正有价值的只有 600 个。Goodput 把 SLO 纳入计算：

Goodput = 满足所有 SLO 的请求数 / 总请求数 * 吞吐
容量判断：扩容决策不要只看 QPS 曲线，要看 goodput 曲线。加大 batch 可能提高完成量，却让更多请求超出 TTFT 或 TPOT SLO。

4. 网关、路由和模型副本各自解决什么问题

网关
统一入口，负责鉴权、限流、基础路由、请求日志和租户识别。租户标记会进入下游 chargeback，详见 第 17 章。
路由层
负责模型版本、灰度、长短上下文分流、高低优先级分流、prefix-aware 路由和 SLO-aware 副本选择。
模型副本
真正加载模型权重并执行推理。副本数量、预热方式、缓存策略和设备选择直接决定吞吐与尾延迟。

Prefix-aware 路由是一个常被忽略的优化点：把带相同 system prompt 的请求尽量送到同一副本。现代 serving 引擎支持 prefix cache，已经 prefill 过的 prefix 会留在 KV Cache 中，后续带相同 prefix 的请求可以跳过这部分 prefill。这个收益只有在路由让“对的请求进对的副本”时才能拿到。

flowchart TD
  G[API Gateway
auth / rate limit / tenant] --> R[LLM Router]
  R -->|prod traffic| A[Pool A
stable version]
  R -->|canary 5%| B[Pool B
new version]
  R -->|shadow| C[Shadow Pool
offline eval]
  R -->|same prefix hash| A
  A --> KA[(KV / Prefix Cache)]
  B --> KB[(KV / Prefix Cache)]

  A --> O[Streaming Response]

路由边界：简单 round-robin 在 LLM serving 中上限很低。它可能均衡了请求数，却摧毁 prefix cache 命中率、打散会话状态，并把长上下文请求混入短请求池。

更进一步的策略是基于预测延迟选择副本。简单的 queue depth、memory pressure 都是代理指标，不直接告诉你“这个副本能不能按时完成这个请求”。大多数平台不一定要立刻上 ML 路由，但要知道传统负载均衡器无法同时兼顾 TTFT、TPOT、prefix hit 和租户优先级。

5. 为什么在线推理的核心不是平均延迟，而是尾延迟

用户不会感知“平均一次请求很快”，用户感知的是偶发慢请求、高峰期超时、首次请求冷启动和某些路径特别慢。一个请求依赖多个下游时，总尾延迟往往由最慢的那一跳决定。因此模型服务里的很多设计目标不是把平均值做低，而是控制尾部风险。

P50:    150 ms
P90:    350 ms
P95:    800 ms
P99:   3500 ms
P99.9: 15000 ms

P99 是 P50 的 23 倍，在 LLM 服务里很常见，因为输入长度差异可以轻易达到 100 倍。报告指标要带分位数，不要只有平均；P99 不是偶然噪声，它对应真实的最慢 1% 用户；P99.9 在大流量服务里也要看，因为每天 1000 万请求的服务，P99.9 的长尾就是 1 万个用户。

尾延迟来源典型触发诊断方法
冷启动新副本拉起时接到第一批流量看请求 timestamp 是否和副本 ready 时间接近
长 prompt prefill某个请求 prompt 特别长按输入 token 数分桶看延迟
长 decode输出被顶满 max_tokens按输出 token 数分桶看延迟
下游抖动向量库、检索、rerank 偶发慢把每一跳的延迟单独埋点
队列堆积瞬时 QPS 尖峰看 queue time 和 concurrency
Noisy neighbor共享 GPU 的其他租户占满 decode 槽按租户分桶看 P99
反模式：遇到 P99 问题，先去优化模型推理内核。通常更有效的第一步，是按长度、租户、版本、依赖路径分桶，先判断是所有请求都慢，还是某一类请求很慢。

6. 在线推理与传统 Web 服务的不同

AI 推理服务与传统 Web 服务有共同的入口、日志、限流和发布问题，但它多了几类特别难的约束：计算更重、输入更不规则、缓存更复杂、质量观测更难、发布更重。

维度传统 Web 服务LLM 推理服务
单请求资源CPU 毫秒级GPU 秒级
请求同质性高极低，输入输出长度可有 100x 差异
状态大多无状态KV Cache、prefix cache、sessions
冷启动< 1 秒10 秒到数分钟
发布滚动秒级分钟级
质量闭环HTTP 状态码通常足够输出内容要单独评估
副本成本几美元/副本/天几十到上千美元/副本/天
核心差异：传统服务通常可以把副本视为便宜、无状态、快速滚动的进程；LLM 副本则是昂贵、有状态、冷启动重、发布慢的资源容器。

8. Prefill / Decode 解耦架构

当长上下文 prefill 和持续 decode 同时落在同一副本池时，常见结果是 prefill 抢走大量算力，decode token 级调度被拉长，短请求被长上下文请求拖慢。根因是两者计算特征不同：prefill 更偏 compute-bound，decode 更偏 memory-bandwidth-bound，并长期占用 KV Cache。

阶段瓶颈类型好的硬件特征
Prefillcompute-bound，算力密集高 FLOPS、高带宽
Decodememory-bandwidth-bound，访存密集高 HBM 带宽、大显存
sequenceDiagram
  participant C as Client
  participant R as Router
  participant P as Prefill Pool
  participant K as KV Store / Transfer
  participant D as Decode Pool
  C->>R: request with long prompt
  R->>P: schedule prefill
  P->>K: write KV state
  K->>D: handoff KV
  D-->>C: stream decoded tokens
  R-->>R: adjust routing by TTFT / TPOT
维度一体化副本Prefill / Decode 解耦
优势实现简单，状态本地化资源池可独立扩缩，长 prompt 更不容易拖垮 decode
代价难针对两类负载分别调优需要 KV 传输、状态一致性与更复杂路由
更适合中小规模、请求形态较稳定长上下文、高并发、请求长度差异极大
选型建议：先试 chunked prefill，再考虑完整解耦。chunked prefill 不把 prefill 和 decode 拆到不同机器，而是在同一次 forward 里把大 prefill 切成小块，和 decode token 混在一起跑。

完整解耦通常取决于三个信号：t_prefill 是否显著挤压 decode token 吞吐；长上下文流量是否和短请求共享同一资源池；平台是否有能力管理远端 KV 状态与跨池排障。相关方案包括 DistServe、Mooncake、Splitwise，它们共同回答的是如何把 prefill 的高算力路径和 decode 的高显存路径拆开，同时控制 KV handoff 代价。

9. 多模态 serving 为什么更像组合服务

多模态请求不是简单“把图片也喂给 LLM”，它通常会在链路里新增编码器、预处理和更大的前缀状态。图像 resize、patch 化、音频分帧、OCR、视觉编码器版本和跨模态对齐，都会进入容量、缓存和发布边界。

维度纯文本 LLM多模态模型
预处理tokenizer 为主图像 resize、patch 化、音频分帧、OCR 等
Prefill 成本主要由 token 长度决定还受视觉 token、音频帧数影响
缓存键prompt 模板、tokenizer 版本还要包含图像预处理、视觉编码器版本
运行时瓶颈decode、KV Cache 常更突出prefill、带宽、跨模态对齐常更突出
缓存边界：如果多模态预处理、视觉编码器版本和 tokenizer 版本没有纳入缓存键，prefix cache、检索 cache 和模型版本很容易同时失效。

常见架构选择是编码器与生成器分开扩缩，对大图和长音频单独限流，并把预处理版本纳入缓存与发布元数据。多模态 serving 更像组合服务，而不是单个模型 API。

10. 模型服务框架对照

不同 serving 框架的差别，不只是吞吐 benchmark，而是它们把哪些运行时问题内置到了平台层。

框架核心定位优势更适合的场景
vLLM面向 LLM 的高吞吐服务continuous batching、PagedAttention、prefix cache、chunked prefill 成熟大模型在线生成服务
SGLang面向复杂生成的 serving 引擎RadixAttention、结构化生成、工具调用编排Agent、tool-use、结构化输出
TensorRT-LLMNVIDIA 深度优化引擎对 NVIDIA GPU、量化和 kernel 优化支持强追求极致性能的 NVIDIA 环境
TGIHugging Face 系推理服务集成度高，生态广快速部署 HF 模型

请求是 LLM 为主吗？
├── 否：Triton 或 KServe
└── 是
    ├── 需要 tool-use / agent / 结构化输出：SGLang
    ├── NVIDIA 硬件 + 极致性能 + 接受重运维：TensorRT-LLM
    ├── 平衡且活跃的生态：vLLM
    └── 本地开发 / 边缘：Ollama / llama.cpp
选型原则：先问是追求极限吞吐，还是追求统一托管能力；两者很少能同时做到最优。并发模式也会改变 benchmark 结论。

11. 冷启动与预热

推理服务的冷启动通常不是单一步骤，而是三段叠加：权重加载、运行时初始化、首次执行优化。权重要从对象存储或本地盘搬到进程和显存；CUDA context、allocator、依赖连接要初始化；CUDA graph、kernel autotune 和缓存路径也可能在首次执行时触发。

12. 熔断与降级

当下游依赖抖动或模型池接近饱和时，在线推理不能只靠“多加副本”兜底，还要有明确的保护动作。

机制作用常见触发条件
熔断器暂停访问异常下游，避免放大故障检索服务错误率升高、超时持续上升
排队上限防止请求无限堆积队列长度、排队时长超过阈值
降级响应返回简化结果或切换低成本模型GPU 池饱和、关键依赖不可用
超时回退保护整体 SLA非核心后处理或检索链路超时
Admission control拒绝无法按 SLO 完成的请求预测延迟超过 SLO

降级不是一个动作，而是一组可选择的行为。按破坏性从小到大：关闭非核心增强，切小模型，截短上下文，减少 max_tokens，返回缓存或模板回复，最后拒绝请求。

演练要求：降级策略要定期演练。如果线上从来没真正触发过降级，它在事故时多半不会按预期工作。

在多租户环境下，这些策略还会和优先级耦合在一起。高优先级流量通常拥有更高的排队预算和更晚的降级阈值；相关治理逻辑会在 第 17 章 展开。

13. 工程建议

  • 用请求时间拆解定位瓶颈，不要先假设模型执行最慢。
  • 路由策略要显式区分模型版本、上下文长度和租户优先级。
  • 尽量做 prefix-aware 路由，不要让 prefix cache 白费。
  • 当 t_prefill 与 t_decode 的资源特征明显分化时，先试 chunked prefill，再考虑完整解耦。
  • 冷启动要作为容量模型的一部分，而不是仅在故障时考虑。
  • 多模态请求要把预处理、编码器和生成器一起纳入容量与缓存设计。
  • 熔断、排队上限和降级策略要写入控制面，而不是靠人工临时切换。
  • 指标要看分位数 P50/P95/P99，不要只看平均。
  • goodput 比 QPS 更诚实，因为它考虑了 SLO。

学习路线

  1. 先把一次请求拆成 queue、preprocess、model、downstream、postprocess。
  2. 再把 LLM model time 拆成 prefill、decode，并建立 TTFT、TPOT、ITL、E2EL、goodput 的指标习惯。

  4. 最后用冷启动、降级、灰度和回滚规则检查控制面是否完整。
