1. 第一性原理拆解：多租户与成本治理

拆 — 不可化简的问题

把 Kubernetes namespace、GPU 调度器、预算看板、FinOps 名词和云厂商折扣先拿掉，多租户与成本治理要解决的不可化简问题只有一个：有限且昂贵的 GPU 时间，必须在多个会互相影响、价值不同、风险不同的请求之间分配，并且分配结果要能被解释、约束和纠偏。GPU 不是一个抽象的“弹性资源”，它是每秒都在折旧或计费的物理设备；一次 LLM 请求也不是一个均匀的 HTTP 调用，而是输入 token 的 prefill、输出 token 的 decode、KV Cache 显存占用、下游检索、rerank、安全检查、日志采样和可能的重试共同组成的资源轨迹。只要多个团队、多个模型版本、多个 SLA 档位进入同一个资源池，就必然出现四个事实：资源在时间上有波峰波谷，按峰值隔离会贵，按平均共享会抖；请求的成本差异极大，1K prompt 和 32K prompt 对算力、显存、排队和缓存亲和性的压力不是线性可替代的；业务价值不同，核心生产流量和一次临时批评测不应在高峰期拥有相同抢占权；账单如果不能归因到租户、版本和具体行为，就不会改变任何人的使用方式。

因此，本章不是在讲“怎么给每个团队分一个 namespace”，也不是在讲“月底如何导出一张报表”。它要回答的是：当一个共享推理平台被真实组织使用时，如何让每个租户知道自己能用多少、超用会发生什么、为什么被限流、为什么账单变贵、什么时候应该用 Cloud、On-Prem 或 Spot，以及什么指标能证明 GPU 时间确实转化成了有价值的 token。推理系统真正进入平台阶段的标志，往往不是 QPS 上去了，而是多个团队、多个模型、多个优先级同时进入同一个资源池后，系统还能保持可解释和可控。第一性原理地看，阶段 4 的困难不在服务能不能跑，而在平台必须把技术约束、业务优先级和经济激励合成一套可执行规则。

推 — 从这个问题如何推导出每个机制

从“昂贵 GPU 时间要被多人共享”出发，首先会推出 quota。没有配额，每个租户都会按自己的峰值和局部最优申请资源，最后共享池退化成谁先占谁赢。仅有 quota 还不够，因为空闲资源如果不能借用，整体利用率会很差，所以需要 reserved + burst：保底容量保证可预测性，burst 容量利用空闲水位。只要允许 burst，就会遇到高峰争用，于是需要 priority 和 preemption：线上核心流量能压过实验流量，低优任务可被抢占、降级或排队。再继续往下推，会出现 isolation。隔离不是越强越好，而是成本与稳定性的交换：独占池、MIG、专用 warm pool 能降低 noisy neighbor 风险，但会增加 idle tax；完全混部能提高平均利用率，却可能让长上下文租户拖垮其他租户的 P99。因此平台必须把资源池分层：核心业务强隔离，中等业务共享池，实验和离线流量进入可抢占池。

成本治理也不是外接报表，而是从共享资源必然推导出来的控制能力。GPU-hour 是最容易采集的成本单位，但它无法解释为什么同样一万次请求，有的租户贵十倍；所以要拆到输入 token、输出 token、KV Cache GB·s、下游依赖调用、warm pool 分摊和隔离溢价。这个拆解导出 chargeback：不是为了财务惩罚租户，而是让租户看见长输出、低 cache hit、过度保留容量和高 SLA 要求如何变成钱。chargeback 一旦存在，就会反过来影响行为，所以计费模型本身也是平台政策。最后，“便宜”本身也要拆开。Cloud 按需便宜在风险低和弹性强，On-Prem 便宜在长期高利用率下的 GPU-hour 摊销，Spot / Preemptible 便宜在可中断任务能接受回滚。它们不是三种单价，而是三种风险分配方式。类似地，GPU utilization 也不是最终目标：SM Active 高只能说明设备忙，MFU、useful tokens / GPU-hour 和 goodput 才能说明这份忙是否转化成有效产出。

3. 为什么推理系统会走向多租户

刚开始时，很多模型服务是单租户的：一个模型、一组副本、一个团队维护。但只要模型数量增加，就会自然出现多模型共享 GPU、不同团队共享集群、同一模型不同版本同时在线、不同用户群体有不同 SLA。此时问题不再只是“跑得动”，而是谁先用资源、谁可以抢占、谁为成本负责、谁的请求可以被限流或降级。

静态资源分配撑不住
A 团队高峰期不够用，B 团队低峰期空转；按峰值切分会把账单固定在高位。
共享池没有优先级
实验流量可能压住线上核心流量，没有规则驱动的优先级就只能靠人工协调。
成本无法归因
月底只有总账单，无法追溯哪次流量尖峰、哪个模型版本或哪类请求特征导致成本上升。

  C --> D[多优先级与多SLA]

4. 多租户真正管理的对象

多租户不是简单“每个团队一个 namespace”。真正需要管理的是资源边界、优先级、隔离、成本归因和发布边界。这意味着多租户本质上是一组规则，不只是资源切片。

维度强隔离（各自独立集群）强共享（混部）
利用率低，每个池按峰值留冗余高，波峰波谷互补
可预测性高，互不干扰低，有 noisy neighbor 风险
成本高，冗余多低，复用好
安全高需要额外机制
运维多套基础设施一套但更复杂

成熟平台通常不是全隔离或全共享，而是分层：核心业务和高优租户用专用保留池，中等业务进入共享主池加配额，实验、离线、低优流量进入 Spot 或 preemptible 池。

边界提醒：隔离是稳定性的价格。把所有租户合成一个共享池可能提高平均利用率，但也可能把少量长上下文请求、cache miss 或低优批任务的影响扩散到关键业务。

5. 单位请求成本与成本放大器

一个粗略但实用的成本模型是：单请求成本约等于实例每秒成本乘以请求占用时间，再除以有效请求数。对于 LLM，常常需要进一步拆成输入 token、输出 token、KV Cache、下游依赖和冗余成本。

GPU 固定成本 = GPU 数 × 小时单价 × 运行小时
有效 token 单价 = GPU 固定成本 / useful tokens
单请求成本 = prefill 成本 + decode 成本 + KV Cache 成本 + 下游成本 + 冗余成本
租户账单 = 请求成本求和 + 保底容量分摊 + SLA / 隔离溢价
成本项粗略单价用量请求成本
Prefill 输入 token$0.30 / 1M tokens4K$0.0012
Decode 输出 token$1.20 / 1M tokens1K$0.0012
KV Cache 占用$0.00002 / GB·s8 GB × 6s$0.0010
检索 / rerank / 日志固定估算1 次$0.0020
SLA / idle 分摊请求侧加成 20%-$0.0011
单请求合计--约 $0.0065
放大器为什么会贵平台上的典型动作
长上下文 prefill占用大量算力和带宽，且未必能被 cache 命中把长上下文单独分层计费或限流
长输出 decodedecode 槽位被持续占用，压低共享池吞吐对 max output length 做档位治理
Warm pool / 空转副本为 SLA 保留容量，低峰期没有有效产出用时段策略、共享池或延迟回收控制 idle tax
低命中缓存重复跑 embedding、检索、prefix 计算持续跟踪 cache hit、prefix hit、重复请求比
下游依赖检索、OCR、rerank、工具调用都会计入单次成本把全链路依赖费用并入 chargeback
不要线性外推：prompt 从 2K 扩到 32K，prefill 时间、KV Cache 占用和排队影响可能远超 token 数的线性增长。容量规划必须做分档压测。

6. Cloud、On-Prem 与 Spot 的 TCO 判断

Cloud、On-Prem 和 Spot 不是单价表里的三个数字，而是三种风险分配方式。Cloud 按需把容量风险交给云厂商，On-Prem 把长期利用率风险留给自己，Spot / Preemptible 用供应不稳定换折扣。

场景Cloud 按需Cloud 预留On-Prem推荐判断
新业务探索，流量每周变化 2-3 倍成本高但风险低容易承诺过早采购风险高先 Cloud 按需
稳定线上池，预计 12 个月都在 60%+单价偏高折扣和弹性平衡需要机房能力Cloud 预留优先
长期百卡级，70%+ 使用 3 年长期成本偏高可作为过渡摊销后有优势进入 On-Prem TCO 论证
季节性高峰，平时低谷明显高峰能扛，低谷可关承诺容量可能浪费低谷折旧浪费Cloud 按需 + Spot
数据不能出本地机房受区域和合规限制同左控制力强On-Prem 或专有云
Spot 风险典型表现缓解策略工程边界
实例被回收机器在通知后消失checkpoint、drain、双池路由没有 checkpoint 的任务不应上 Spot
容量不可得某区域或机型突然拿不到卡多 AZ、多实例族、保底池兜底模型必须支持多机型镜像和性能校准
冷启动放大节点频繁进出，模型反复加载镜像预拉取、权重本地缓存大模型加载超过分钟级时收益会被吃掉
抢占风暴同一池子大量实例同时消失按池限额、分散采购、限速迁移Spot 占比过高会把平台变成不稳定系统

工程边界：TCO 表只能支持容量决策，不能替代压测。On-Prem 的每 GPU-hour 看起来低，不代表单位 token 成本一定低；Cloud 也不能只看按需价，GPU 缺货、跨区流量、镜像拉取和存储快照都会改变实际成本。

7. GPU utilization 高不等于有效产出高

很多团队看到 DCGM 或 nvidia-smi 面板上的 SM Active 接近 90%，就以为 GPU 已经被充分利用。这个判断经常过于乐观。GPU 可以一直在跑 kernel，但这些 kernel 可能受访存、同步、碎片化 batch、无效重算或低价值流量限制，没有把理论 FLOPs 转化成有效模型计算。

指标粗略定义回答的问题它不能回答什么
GPU utilization / SM ActiveGPU 上有多少时间至少有 kernel 在跑设备忙不忙工作是否接近理论峰值、是否有业务价值
MFU实际模型有效 FLOPs / GPU 理论峰值 FLOPs模型计算是否高效token 是否有用、SLO 是否满足
HFU硬件实际执行 FLOPs / 理论峰值算术单元是否充分使用重算、padding、无效请求是否有价值
useful tokens / GPU-hour满足质量与策略要求的 token / GPU 小时每张卡最终产出了多少有效 token单个租户的尾延迟和公平性
goodput在 SLO 内完成的有效请求或 token产出是否既有效又准时资源是否被长期过载
MFU ≈ model_flops_per_token × generated_or_processed_tokens_per_second
      / GPU_peak_flops

例如:
MFU ≈ 140 TFLOPs/token × 2500 tokens/s / 989000 TFLOPs/s ≈ 35%
面板建议：至少同时摆 GPU utilization、MFU、useful tokens / GPU-hour、goodput。单看任何一个指标都会被代理目标误导。

8. 公平性、配额与优先级策略

多租户调度不是简单数学最优，而是平台政策问题。极度追求利用率，会让低优长请求霸占资源、高优短请求等待变长；极度追求公平，又会让资源空着不敢借给别人，整体单位成本升高。

公平模型规则优点缺点
Strict quota每个租户固定份额，超出直接拒可预测、公平空闲资源浪费
Weighted fair按权重分配，可借用空闲利用率好抢占逻辑复杂
Priority-only高优先级完全优先实现简单低优容易饿死
Reserved + burst每人保底 + 超用限制平衡参数调优难
Market-based内部计价，租户按钱竞价经济激励强组织成熟度要求高
配额维度控制什么适用场景
GPU 卡数副本容量上限容量规划
QPS / RPM每分钟请求数防突发
输入 token / 分钟长上下文流量控制prefill 密集型租户
输出 token / 分钟decode 占用长输出租户
并发请求数单租户最多 inflight防占满 decode 槽位
预算成本上限超出触发降级

9. Chargeback 与成本归因

成本治理如果只停留在“本月 GPU 花了多少钱”，平台就无法推动租户优化行为。更实用的做法，是把成本拆到租户、业务线、请求特征和模型版本。chargeback 的目的不是财务记账，而是让租户看到自己的长上下文、低命中率、低利用率行为如何变成真实成本。

10. Noisy Neighbor 与隔离

多租户共享 GPU 时，常见麻烦不是某个租户完全把服务打挂，而是它持续把别人的尾延迟拉高。有效信号通常不是平均延迟，而是某个租户到来后，其他租户的 P95/P99 是否突变。

干扰模式典型表现常见隔离手段
长请求占满 decode 槽位高优先级短请求 P99 恶化时分调度、优先级抢占
大上下文请求吃满显存其他租户 admission 失败显存配额、上下文长度分层
热租户持续冲高流量整体队列抖动独占池、限流、空分隔离
新租户 prefix cache miss整体 cache 命中率下降prefix-aware 路由隔离
对每个租户 T，每 5 分钟计算：
  ΔP99(T) = P99 latency of other tenants WITH T's traffic
           - P99 latency of other tenants WITHOUT T's traffic

如果某租户持续 ΔP99 > threshold:
  → 标记为 noisy neighbor candidate
  → 分析长 prompt 占比、并发数、cache hit、版本变更
  → 动作：降级、独占池、加配额硬顶、按成本加价
治理风险：LLM 服务里的租户分布通常更极端，Top 1% 租户可能占 40%-60% GPU 用量。对大户和小户一刀切，往往对大户太松、对小户太紧。

11. 把成本规则变成控制面动作

如果成本治理只停留在看板，它就无法反过来改变平台行为。更实用的做法是把预算、SLA 和容量策略直接接进控制面，让成本治理从解释账单变成提前塑造账单。

控制动作作用典型触发条件
长上下文单独路由避免少量超长请求拖垮共享池输入长度超过某个档位
租户预算阈值预算逼近时自动降级模型或降低 burst日 / 周 / 月预算到达阈值
Cache 观测联动命中率下滑时优先查模板变化与热键失效命中率突然下降、成本突然上升
Warm pool 分层只为高 SLA 租户保留热副本高优租户需要稳定首 token 延迟
Preemptible 池让实验流量承接空闲容量低优任务允许被抢占
自动切小模型预算紧或容量紧时切量化版预算 > 80%、GPU 池 > 90%

多租户里的发布与回滚还会多出额外复杂度：不同租户对新版本容忍度不同，回滚成本对大户不均等，新老版本单位成本不同，多版本并存期间容量可能翻倍。多版本并存是多租户平台的隐形税，必须限制并存时长并按版本拆账。

12. 工程建议、误区与小结

工程建议

  • 配额、优先级和限流策略要能被路由层与调度层直接执行。
  • 分层资源池：核心业务独占，中等业务共享，实验流量进入 Spot 或 preemptible 池。
  • 成本归因至少覆盖 GPU 时间、token、KV Cache 和关键下游调用。
  • 按租户、请求特征、模型版本和时间段都要能切分，不能只有总账单。
  • 不要只追求平均利用率，要把关键租户的尾延迟预算一起纳入治理目标。
  • TCO 评估要每季度复查，随规模变化调整 Cloud / On-Prem / Spot 组合。

常见误区

误区更准确的判断
多租户就是资源切分真正困难的是优先级、回滚、限流和成本归因
单位请求成本只和模型大小有关上下文长度、batch、利用率、缓存命中率都直接影响成本
只要利用率高，平台就运营得好高利用率可能牺牲关键业务延迟和公平性
Cloud 一定比 On-Prem 贵TCO 取决于利用率曲线、承诺周期和运维能力
Spot 应该全上生产主路径不能承受被收走的供应风险
Chargeback 只是财务工作它是政策设计，会诱导不同的租户行为
本章小结：多租户治理的核心不是把 GPU 切开，而是把资源、优先级、隔离、成本和控制面动作连成闭环。平台要追的不是“GPU 很忙”，而是满足业务约束的单位有效产出成本更低。
