1. 第一性原理拆解：请求、状态与有限 GPU

拆 — 不可化简的问题

剥掉 vLLM、TensorRT-LLM、PagedAttention、DistServe、Mooncake 这些名字，本章面对的不可化简问题只有一个：大量到达时间、输入长度、输出长度和优先级都不同的请求，要共享少量昂贵 GPU；每个请求还会在生成过程中制造持续增长的状态。在线推理不是一次矩阵乘法，而是一条长时间占用资源的工作流。用户输入的 prompt 先触发 prefill，系统要把已有上下文一次性读入模型并生成第一批 KV；之后 decode 每次只前进一步，但每一步都要读取模型权重和历史 KV。于是一个请求不只是"算一次"，而是"先大块算，再反复小步算，并持续占显存"。

这和离线训练的直觉不同。训练中一个 global batch 的形状相对固定，吞吐目标可以压过单个样本延迟；在线服务中，一个 128 token 的短问答和一个 32K token 的长文档请求可能同时进入同一副本。若调度器把它们当成相同任务，短请求会被长 prefill 拖住，decode step 会被大 prompt 阻塞，KV Cache 会被少量长上下文占满，最终表现为 TTFT、ITL、TPOT 和 P99 同时恶化。GPU 利用率看起来很高，也可能只是忙在低价值的重算、搬运和排队上。

因此，本章不是在介绍某个框架的参数，而是在回答一个资源组织问题：如何把一批不规则请求切成适合 GPU 执行的计算单元，同时让每个请求的 KV 状态可分配、可迁移、可复用、可回收，并且让延迟指标仍然可控。批处理解决"单请求浪费 GPU"；continuous batching 解决"一批请求长短不同"；KV Cache 解决"历史上下文不能反复重算"；PagedAttention 解决"KV 状态不能靠连续大块显存管理"；chunked prefill 和 P/D 解耦解决"prefill 与 decode 资源形态冲突"；speculative decoding 解决"decode 每步只产一个 token 的串行性"。它们都不是孤立技巧，而是同一个物理约束被一层层逼出来的结果。

推 — 从这个问题如何推导出每个机制

第一步推导 batching。GPU 的强项是大矩阵和高并行度，单请求 decode 往往 batch=1、算子很小、HBM 反复读权重，SM 会空等。于是系统必须把时间上接近的请求合并，让一次 forward 里有更多 token 和序列，摊薄 kernel launch、调度和权重读取成本。但固定 batch 会遇到第二个问题：LLM 输出长度未知，短请求结束后槽位空着，长请求继续拖住整批。于是 continuous batching 成为必然：每个 decode iteration 重新组 batch，完成的请求释放槽位，新请求补进来。

第二步推导 prefill/decode 分离。LLM 请求不是均匀计算。Prefill 处理整段 prompt，通常更接近 compute-bound；decode 每次只生成一个 token，更容易受 HBM 带宽、KV Cache、调度粒度和活跃序列数限制。如果把 32K prompt prefill 和大量短请求 decode 放在同一条队列，长 prefill 会把 decode 的 ITL 拉长。轻量解法是 chunked prefill，把长 prompt 切成 512 或 1024 token 的小片，夹在 decode step 之间执行；重型解法是 Prefill-Decode Disaggregated，把 prefill pool 和 decode pool 拆开，分别扩缩容，但要承担 KV handoff、双队列背压和失败恢复。

第三步推导 KV Cache。自回归生成中，第 N+1 个 token 需要看前 N 个 token。如果每一步都重算全历史，计算量会随上下文长度爆炸；所以必须缓存每层 attention 的 K/V。KV Cache 把重复计算换成显存占用，问题从"算不动"转成"放不下、管不好"。在 70B、长上下文、高并发场景，KV 显存可能比权重更先成为 admission 上限。连续分配又会带来碎片和过度预留，于是 PagedAttention 把 KV 切成固定 block，用 block table 映射逻辑上下文和物理显存；同样的 block 机制又自然支持 prefix cache，让相同 system prompt、few-shot 模板和 RAG 前缀复用 KV。

第四步推导指标。平均吞吐或平均 GPU utilization 不足以判断服务是否好。用户先感知 TTFT，再感知 token 是否稳定吐出；对流式输出，ITL（Inter-Token Latency）往往比总耗时更贴近体验；对平台，goodput 比 raw throughput 更重要，因为违反 SLO 的 token 不应算作有效容量。调度器的目标也因此不是"永远最大 batch"，而是在显存、吞吐、TTFT、ITL/TPOT、公平性和成本之间找到稳定工作点。这意味着调度参数调优必须以 goodput 达峰为停止条件，而不是 raw QPS 达峰。

2. 为什么批处理是推理系统的第一性问题

GPU 适合高吞吐批量计算。如果请求一个个独立执行，GPU 很可能无法高效利用。一张 H100 的 bf16 峰值是 ~990 TFLOPS，但一个 7B 模型跑单请求 decode（batch=1）时，算力利用率通常只有 1–3%——因为 decode 是 memory-bandwidth-bound，绝大部分时间在从 HBM 读权重，计算单元空等。

Batch size7B decode 吞吐（tokens/sec）GPU 算力利用率每 token 成本
1~50~1%高
8~300~5%中
32~900~15%低
128~2500~35%很低
256~3500~45%最低

7B 模型在 H100 的典型数量级；具体数字和模型、序列长度、kernel 版本相关。Batch 从 1 提到 128，吞吐能升约 50 倍，单位成本降约 50 倍。

批处理不是免费午餐：批越激进，t_batch_compute 越经济，但 t_queue 往往上升。吞吐和延迟的矛盾从第一步就出现。

Batching 的演进史

flowchart TD
  SB[Static batching

  DB -->|LLM 输出长度不定，仍有槽位浪费| CB[Continuous / Iteration-level batching

实践建议：对大多数团队来说，continuous batching 是必选项，chunked prefill 是默认开启，disaggregated 是"大规模长上下文业务才考虑"的选项。

Continuous Batching 工作原理

核心思想：每一步 decode 结束后，完成的请求立刻出队，队列里的新请求立刻顶上。没有"等一整个 batch 跑完"的概念。

sequenceDiagram
  participant Q as 请求队列
  participant S as 调度器
  participant G as GPU forward
  Q->>S: 请求 A,B,C,D 到达
  S->>G: step 1: batch [A,B,C,D]
  G->>S: A 完成
  S->>Q: 释放 A 槽位
  Q->>S: 新请求 E 入队
  S->>G: step 2: batch [B,C,D,E]
  G->>S: C 完成
  Q->>S: 新请求 F 入队
  S->>G: step 3: batch [B,D,E,F]

几乎所有现代 LLM 服务都应该开 continuous batching。vLLM、TensorRT-LLM、TGI、SGLang 都默认打开。如果你的服务还在用 static batching，通常能立刻拿到 2–10x 的吞吐提升。

3. Prefill 与 Decode 的本质区别

阶段更像什么常见瓶颈硬件偏好影响的 SLO
Prefill批量矩阵计算算力、带宽高 FLOPS GPUTTFT
Decode小步增量生成调度、KV Cache、显存大显存 + 高 HBM 带宽ITL / TPOT
一个长 Prompt 能拖死一池 Decode：假设 7B 模型：短 prompt（100 token）prefill ~10 ms；长 prompt（32K token）prefill ~2000 ms（约 200x 放大）；单 token decode ~20 ms。一个 32K prefill 独占 GPU 2 秒，期间约 100 个其他 decode token 被延迟，短请求的 TTFT 和 TPOT 同时被污染。这就是"prefill/decode 争用是 LLM 服务最常见的尾延迟来源"。

变长序列在 Forward 里的 Attention 实现

Continuous batching 的工程门槛：同一次 forward 里不同请求的序列长度不一样。现代方案是 variable-length packed batch——把多个序列首尾相接打成一个 1D tensor，用 cu_seqlens（cumulative sequence lengths）数组标记边界：

3 个序列长度分别是 50, 200, 4000:
  packed_tokens: [seq0_token0, ..., seq1_token0, ..., seq2_token0, ...]
  cu_seqlens:    [0, 50, 250, 4250]
  total_tokens:  4250

FlashAttention 的 varlen 接口（flash_attn_varlen_func）直接消费此格式：kernel 内部用 cu_seqlens[i] 和 cu_seqlens[i+1] 算出第 i 个序列的范围，完全没有 padding，也没有跨序列 attention 泄漏。

对于 chunked prefill，同一 batch 里有两类工作：prefill chunk 内部做 causal self-attention；decode 部分用当前 1 个 query token attend 整个历史 KV（按 block_table 间接寻址）。vLLM / FlashAttention V3 的 flash_attn_with_kvcache 在单一融合 kernel 里处理两类，无需分别 launch 两个 kernel。

接口演进：FlashAttention V1 只支持 fixed-length batch（要 padding），V2 引入 varlen 接口，V3 才彻底融合 prefill + decode。这条接口演进直接决定了 vLLM、TRT-LLM、SGLang 在 continuous batching 上的可行性。某些自定义 attention 实现没跟上，开 chunked prefill 会回退到慢路径甚至错误。

4. KV Cache 为什么重要

自回归生成中，第 N+1 个 token 需要看前 N 个 token 的 K/V。如果每一步都重算全历史，计算量随上下文长度平方爆炸。KV Cache 的核心思想：把历史 token 的 key/value 保留在显存里，后续 decode 只计算新增 token。

粗略显存估算式：

M_kv ≈ 2 × L × n_kv_heads × d_head × dtype_bytes × T × B

L：层数，n_kv_heads：KV 头数，d_head：head 维度
T：上下文长度，B：并发请求数，2：K 和 V 各一份

MHA、GQA、MLA：KV Cache 的架构级差异

机制典型模型KV Cache 相对规模说明
MHA（Multi-Head）GPT-3、LLaMA 11x每个 head 独立 K/V
MQA（Multi-Query）Falcon、PaLM~1/N所有 head 共享一套 K/V
GQA（Grouped-Query）LLaMA 2/3、Mistral~1/G（典型 1/4–1/8）每 G 个 head 共享 K/V
MLA（Multi-Latent）DeepSeek V2/V3、R1~1/10 ～ 1/40K/V 压到低维 latent，推理时展开
MHA/GQA 公式套到 MLA 上是错的：MLA 不存独立的 K 和 V 头，而是把所有 head 压缩成一个共享的低维 latent vector，加上一小段单独的 RoPE 分量。直接套 MHA 公式会高估 KV 占用 10–40 倍，导致副本数多配、admission 提前拒绝、容量规划严重偏差。

MLA 正确公式：M_mla_kv/token = L × (d_kv_latent + d_rope) × dtype_bytes
DeepSeek-V3 示例（61 层，BF16）：正确约 70 KB/token；错误套 MHA 约 4 MB/token——高估约 56 倍。

KV Cache 在显存里的物理布局

主流引擎两种 layout：

  • vLLM PagedAttention 默认：[num_layers, 2, num_blocks, block_size, num_kv_heads, head_dim]——K 和 V 在最外层就分开，各为独立大 tensor。一个 block 内 16 个 token 的某个 head 的 head_dim 维度连续，刚好是 attention kernel 算 QKᵀ 时沿 head_dim 做点积所需的访存模式。
  • TRT-LLM BLOCK_HND：[num_blocks, num_layers, 2, num_kv_heads, block_size, head_dim]——外层先按 block，便于 paged attention plugin 一次拿到整个 block 内所有 layer 的 KV。

K 和 V 要分开存的原因：attention 分两步（S = QKᵀ/√d 用 K，O = softmax(S)·V 用 V），交错存时读 K 期间每两个连续元素跳过一个 V，HBM coalescing 减半。分开存每步只读自己需要的，coalescing 完美。

block_size = 16 的工程权衡：太小（4）时 block_table 长、查表延迟主导；太大（128）时内部碎片明显、短请求浪费。16 刚好和 FlashAttention K/V tile 大小（典型 64–128）能整数对齐，一次 attention block 处理 4–8 个 KV block，间接寻址开销均摊。

4b. Worked Example：LLaMA-70B 推理容量规划

问题：一个线上聊天服务要上 LLaMA-70B 类模型，目标是 100 QPS、P99 TTFT < 500 ms、P99 TPOT < 50 ms/token。典型请求是 3072 input tokens + 512 output tokens，按 4K resident context 做 admission。需要多少副本、多少 GPU？

项取值说明
AttentionGQA，8 个 KV heads，head_dim=128不是 64 个 query heads 全量存 KV
权重精度BF16约 70B × 2 bytes = 140 GB
单副本配置4 × H100 80 GB，TP=4一个 replica 是一个 4 卡 TP group
GPU 单价$3.5/GPU-hour仅 GPU 租用，不含 CPU/网络/存储

第一步：算单请求 KV Cache

M_kv/token = 2 × L × n_kv_heads × d_head × dtype_bytes
           = 2 × 80 × 8 × 128 × 2 = 327,680 bytes ≈ 320 KiB/token

4K context 单请求 KV = 4096 × 320 KiB = 1.25 GiB（整个 TP replica）
TP=4 时单 GPU：1.25 GiB / 4 = 0.3125 GiB/GPU/request

第二步：算单副本最大并发

可用预算（80GB × 90%） = 72 GB
权重 shard（140GB / TP=4） = 35 GB
Runtime 预留               = 8 GB
留给 KV Cache             ≈ 29 GB
→ 理论并发 ⌊29 / 0.3125⌋ = 92 requests/replica

为满足 TPOT < 50 ms，decode batch 应按约 64 个活跃序列规划（batch=64 时 step latency 约 42 ms），给 P99 留余量。

第三步：算 token 需求与副本数

prefill demand = 100 × 3072 = 307,200 input tokens/s
decode demand  = 100 × 512  =  51,200 output tokens/s

N_prefill = ⌈307,200 / 28,000⌉ = 11 replicas
N_decode  = ⌈51,200 / 1,500⌉  = 35 replicas

按 70% 目标利用率留尾延迟余量：
N_replica = ⌈max(11,35) / 0.70⌉ = 50 replicas
→ 50 × 4 H100 = 200 H100
→ 200 × $3.5 × 24 × 30 ≈ $504,000/month
敏感性分析：把 resident context 从 4K 提到 32K，KV Cache 线性放大 8 倍，单副本并发从 92 降到约 11；同时 prefill demand 也放大约 10 倍。长上下文容量规划不能简单说"把 max context 从 4K 开到 32K"，它意味着更严格的 admission、更激进的 prefix cache 和可能独立的长上下文池。

容量规划顺序：先把 QPS 拆成 input token demand 和 output token demand，再算 KV 显存并发上限，最后用 P99 SLA 决定可接受的利用率和批处理工作点。

5. Continuous Batching 与调度器

一个简化版 continuous batching 调度器的伪代码：

while service_is_running:
    collect newly arrived requests
    move ready requests into prefill queue
    run as much prefill as memory allows

    move prefilled requests into decode queue
    build current decode batch from active requests
    run one decode step

    remove finished requests
    recycle freed KV blocks

调度器真正解决的问题不是"如何把请求放进队列"，而是哪些请求先进、哪些可被延后、显存还够不够、KV block 怎么回收、是否允许长请求饿死短请求。

情况调度器要做什么
新请求到来但 KV 显存不够要么拒绝（admission）、要么抢占（preempt）一个已在跑的请求
超长 prompt 进来chunked prefill 切片，或独占一次 forward
多个请求带相同 system promptprefix cache 命中，共享前缀的 KV
某 decode 请求已跑 500 token，显存告急抢占它（swap 或 recompute），还是杀掉重跑
有抢占历史的请求恢复用 recompute 还是 swap-in？哪个更快？

Preemption：当显存不够时，谁先被踢出去

策略机制开销适合场景
Swap preemption把被抢占请求的 KV 从 GPU 挪到 CPU 内存几十毫秒（PCIe 传输）显存和内存都够，但 GPU 显存紧张
Recompute preemptionKV 直接丢掉，恢复时重算 prefill几百毫秒到秒级（看 prompt 长度）内存不够、或 prompt 不长；prefix cache 让重算更便宜
prefix cache 不仅是吞吐优化，还是让 preemption 变便宜的关键机制。prefix cache 命中时，recompute 能跳过大部分计算，使 swap 和 recompute 的代价差距大幅缩小。vLLM V1 默认采用 recompute 策略。

vLLM 关键调度参数

5b. Admission Control 与公平调度

Admission control 的定义：在请求真正占用 GPU/KV 资源前，根据当前队列、显存、SLO、租户配额和请求预算，决定接收、排队、降级还是拒绝。没有 admission control 的系统会在高峰期接收所有请求，队列越来越长，很多请求已经不可能在客户端超时前完成，但 GPU 仍在为它们计算——QPS 看起来高，goodput 反而下降。

量为什么重要典型动作
输入 token 数影响 prefill 时间和初始 KV 分配超长请求进长上下文队列或拒绝
当前 queue time直接污染 TTFT超过预算返回 429/503
active sequences决定 decode batch 和 ITL达到上限后只允许高优先级进入
KV free blocks决定是否会 OOM 或 preempt低于阈值收紧 admission
prefix cache hit 预测命中高的请求成本更低给共享 prefix 请求更低准入成本

Admission 反模式

反模式现象修复方向
只按 QPS 限流100 个 100-token 请求和 100 个 32K 请求被视为一样按 input/output tokens、KV blocks 和租户维度限流
只在 gateway 限流gateway 不知道 GPU 队列和 KV 状态gateway 做粗限流，router/model server 回报实时容量

公平调度策略对比

策略做法优势风险

6. PagedAttention 在解决什么

如果 KV Cache 需要按连续显存预分配，会造成显著浪费：请求长度未知、已完成请求释放后留下碎片、高并发下显存利用率下降。PagedAttention 的思路类似操作系统分页：

  subgraph 逻辑视图
    L0[token 0-15] --> L1[token 16-31]
    L1 --> L2[token 32-47]
    L2 --> L3[token 48-...]
  end
  subgraph 物理KV显存
    B102[block 102]
    B17[block 17]
    B88[block 88]
  end
  BT[Block Table
R → 102, 17, 88, ...]
  L0 --> BT
  BT --> B102
  BT --> B17
  BT --> B88

PagedAttention Block 的关键性质

性质含义影响
固定粒度分配KV 按 block 分配，不按请求最大长度一次性连续分配减少外部碎片和过度预留
逻辑连续、物理离散attention 通过 block table 找到对应 KVruntime 需要高效查表和 kernel 支持
引用计数prefix cache 共享的 block 可被多个请求引用回收必须等所有引用释放
Copy-on-write共享 prefix 分叉后，新 token 分配新 blockprefix 共享不会污染其他请求
Evictionblock 不够时可驱逐低价值缓存 block驱逐策略影响 prefix hit 和 TTFT
PagedAttention 效果：传统系统浪费 60–80% 的 KV Cache 显存，vLLM 把浪费降到 4% 以下。同样显存可以跑 3–5 倍更多的并发请求，这是 vLLM 相对 HF Transformers 能达到 24x 吞吐的核心原因之一。

6b. Prefix Cache：降 TTFT 的关键优化

PagedAttention 有个意想不到的副产品：不同请求可以共享 KV block。如果两个请求有相同的 system prompt，它们的前 N 个 token 的 KV 完全一样，PagedAttention 可以让两个请求共享同一批 physical KV block，只有 prompt 分叉后才各自分配新 block。

两个巨大收益：显存节省（高复用的 system prompt 只需存一份）；TTFT 近乎归零（后续相同 prefix 的请求直接跳过 prefill 部分）。

Prefix Cache 失效条件

失效原因例子排查方式
模板有动态字段system prompt 里拼了时间、request id、用户名对 prefix 做 token hash，比较首个不同 token
tokenizer 不一致canary 版本 tokenizer 配置变化记录 tokenizer version 和 prompt hash
消息顺序不稳定tool schema、few-shot 示例顺序随机固定序列化顺序，做 canonicalization
路由随机同 prefix 被打散到不同副本prefix-aware 或 session-aware routing
cache 容量不足热 prefix 被长请求挤出观测 eviction，按 prefix 统计 hit/miss
多租户隔离出于隐私不能跨租户共享在租户内共享，公共模板单独标记
工程建议：同时记录两个 hash：raw_prompt_hash 和 token_prefix_hash。真正决定 KV 复用的是 token 序列一致，而不是字符串看起来相似。Prefix cache 应该默认开启，但要配合 prefix-aware 路由（见 第 14 章），否则命中率会被随机路由拉低。

Chunked Prefill：轻量的 P/D 冲突缓解

Chunked prefill 在同一次 forward 中把 prefill 切片和 decode token 混在一起：长 prompt 的 prefill 不再"霸占"一次 forward，decode 请求能持续推进，TTFT/TPOT 都稳定，实现代价远低于完整的 P/D 解耦。

vLLM V1、TensorRT-LLM、SGLang 都已经默认开启或推荐开启。chunk_size 参数默认约 512 token，大多数场景不需要动。

P/D 解耦架构新增的工程挑战

问题一体化副本里较弱解耦后为什么会变重要
KV handoff 延迟状态本地传递需要跨进程甚至跨机器搬运
双队列背压通常只有单队列prefill 快、decode 慢时会堆积中间状态
容量配比单池统一扩缩prefill 池和 decode 池要分别做容量规划
失败恢复副本级重试即可需要处理"prefill 成功、decode 未接住"的半完成状态
资源异构全用同一种卡可以给 prefill 用 compute-heavy 卡，给 decode 用 memory-heavy 卡

KV Handoff：解耦架构里最被低估的难点

70B 模型、8K prompt 的 KV 数据量大约是 10–20 GB 级别：

传输路径有效带宽10 GB 的传输时间
NVLink（同机）~300 GB/s~30 ms
IB 200Gbps（跨机）~25 GB/s~400 ms
以太网 25GbE（跨机）~3 GB/s~3300 ms

对比：一个 decode 步大约 20 ms。如果 KV 传输慢于 decode 一步的时间，解耦的收益可能被传输吃掉。P/D 解耦对网络的要求很高，通常要求 IB 及以上，且支持 GPU-Direct RDMA。

P/D 解耦首先是 SLO 隔离与弹性扩缩方案，其次才可能是降本方案。若流量主要是短 prompt、短输出，或副本内 chunked prefill 已经能把 TTFT/ITL 压住，解耦增加的网络、metadata 和故障恢复复杂度通常不划算。若业务是 16K–128K 长上下文、RAG 模板高度复用，解耦才更可能体现价值。

8. Speculative Decoding 简述

核心思路：先让一个更小、更快的草稿模型生成候选 token，再由目标大模型批量验证；验证通过的部分直接接受，不通过的部分再回退重算，且理论上保持目标模型分布。

sequenceDiagram
  participant S as Scheduler
  participant D as Draft model / Head
  participant T as Target model
  participant C as Client
  S->>D: generate k candidate tokens
  D-->>S: draft tokens t1..tk
  S->>T: verify candidates in one target forward
  T-->>S: accept prefix length a
  alt a > 0
    S-->>C: stream accepted tokens
  else reject first token
    S->>T: sample one target token
    T-->>S: fallback token
    S-->>C: stream fallback token
  end
  S->>S: update KV and schedule next step

几种投机解码变体

变体草稿来源典型加速复杂度
Draft model单独训练的小模型（如 1B 对 70B）2–3x中
EAGLE从目标模型的 hidden state 直接预测2–4x高
n-gram / suffix用请求自身的 prefix 做 n-gram 预测1.5–2x低
Medusa在目标模型上加多头预测2–3x中（需改模型）
隐藏成本：投机解码的吞吐收益来自降低 decode 步数，但代价是每步计算量变大（要验证多个候选）。低并发、decode 瓶颈时收益大（GPU 利用率低，多算一些没成本）；高并发、已经填满 batch 时收益小甚至反效果（GPU 已经满了，再塞更多计算只是排队）。

上线前要先压测 accepted tokens/step，而不是只看论文里的加速倍数。生产上至少观测：draft_latency_ms、verify_latency_ms、acceptance_rate、accepted_tokens_per_step、fallback_rate 和 ITL P99。

9. MoE 模型的调度特殊性

MoE 模型把调度问题进一步放大：不同 token 会路由到不同 expert，导致负载不均衡和显存分布都更难预测。

问题体现平台影响
Expert 负载倾斜热门 expert 被打满，冷门 expert 空闲吞吐不稳、尾延迟抖动
Token routing 波动同 batch 内 token 走向不同设备通信和同步成本上升
显存分布不均expert 状态与 cache 不均衡admission control 更复杂

MoE Token Dispatching 三个阶段

flowchart TD
  A[原始 batch: token_i → expert_j,k] --> B[Permute 阶段
单卡内按目标 expert 排序分桶]
  B --> C[All-to-all 阶段
每卡同时发出/接收 N_rank 个 bucket]
  C --> D[Compute 阶段
单卡内 expert 计算 grouped GEMM]
  D --> E[反向 All-to-all
结果送回原 token 所在卡]
  E --> F[反向 Permute
还原 token 顺序]

两个隐性瓶颈：(1) All-to-all 通信开销——DeepSeek-V3 671B 一次 forward 有约 120 次 all-to-all，在 200Gb IB 上叠加可能 50–100 ms，可能比 attention + GEMM 加起来还多；(2) Load imbalance——实际 router 不均匀，hot expert 收到的 token 可能是均值的 3–5x，慢的 expert 决定整个 step 的 latency。

MoE 的基础设施复杂度至少是 dense 的 2x。调度增加一层"按 expert 重新分配 token"，通信从纯 TP 的 all-reduce 变成 EP 的 all-to-all，capacity policy 是新的失效维度。如果团队还没把 dense 模型的 serving 做稳，不建议立刻上 MoE。MoE 跨机 EP 几乎不可行——这是为什么 DeepSeek 推理通常用单机 8 卡 EP 而不是 16 卡跨机。

MoE 常见工程对策

对策解决什么代价
Expert parallelism（EP）把不同 expert 放到不同 GPU需要 all-to-all 通信
Capacity factor限制每个 expert 每批最多接收多少 token可能丢 token，精度受损
DeepEP kernel极致优化 all-to-all，重叠通信和计算需要特定 kernel 支持
Expert 预热冷 expert 也要预热，避免首批请求慢warmup 更长

10. OOM、碎片与尾延迟排障

LLM 调度排障要先分清三类问题：算不动、放不下、排不好。算不动通常表现为 prefill/decode step 变慢；放不下表现为 OOM、preemption、swap、KV free blocks 下降；排不好表现为 P99 抖动、某些租户饥饿、goodput 下降。

11. 工程建议与误区

必选项（几乎总是开）

  • Continuous batching
  • PagedAttention（vLLM、TensorRT-LLM 都默认）
  • Prefix cache（enable_prefix_caching=True）
  • Chunked prefill（enable_chunked_prefill=True）

按场景选

  • 长上下文多 + 短请求混部 → chunked prefill（优先）或 P/D 解耦（大规模）
  • 低并发、长输出 → speculative decoding
  • 高并发相同 system prompt → prefix-aware routing + prefix cache
  • 128K+ 上下文 + 大模型 → KV Cache 量化、GQA/MLA 架构

监控必看

  • Prefill 时间 vs Decode 时间的比例
  • Prefix cache 命中率（应按租户和长度桶分列）
  • KV block 利用率和碎片率
  • Preemption 次数（过高说明 admission 过激进）
  • 按输入/输出长度分桶的 P99 延迟
  • Goodput（满足 SLO 的吞吐）

常见误区

误区一：LLM 推理优化就是换一个更快算子

不对。很多收益来自请求组织和缓存管理，而不是单个 kernel。vLLM 相对 HF Transformers 的 24x 吞吐，主要来自 PagedAttention + continuous batching，而不是算子本身。

误区二：KV Cache 只有收益，没有代价

不对。它在降低计算量的同时，把显存管理难度推到了前台。高并发 + 长上下文时，KV 显存可能比权重更先顶爆。

误区三：批处理越大越好

不对。在线服务还必须承担用户等待时间和尾延迟。goodput 而非 raw QPS 才是优化目标。

误区四：Speculative decoding 一定带来加速

不对。高并发下 GPU 已满，再塞更多验证计算只是排队，可能反而降低 goodput。

误区五：Prefix cache 只对相同 prompt 有用

不对。只要 prefix token 序列相同就能共享，常见场景包括：相同 system prompt 的多租户服务、few-shot 批量任务、代码补全 continuation。

误区六：看平均 GPU 利用率就知道调度好不好

不对。平均 95% 可能是"GPU 忙在做低价值的 cache miss 重算"。要看具体工作构成（prefill vs decode 占比、preemption 频率）。
