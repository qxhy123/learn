1. 第一性原理拆解：MoE 训练为什么是独立子学科

拆 — 不可化简的问题

dense 模型把"参数 = 容量 = FLOPs"绑定在一起。每加宽一个 FFN，每个 token 都要读完整 FFN 权重，训练 FLOPs 和激活路径线性变重。MoE 的核心是把容量最大的 FFN 拆成多个 expert，让每个 token 只激活 N 个 expert 中的 K 个；模型总参数随 expert 数增长，但每 token FLOPs 只随 K 增长。

这不是免费扩容。只要 routed experts 分布在不同 GPU，router 选择出来的 token 就必须被物理搬到 expert owner 上，前向至少有 dispatch 与 combine 两次 All-to-All；反向还要反向通信；dropless 实现还要用 alltoallv/flex dispatcher 处理可变 token 数。MoE 的生产问题因此不是“加一个 router”，而是把训练系统从算力主导改写成路由调度、通信重叠、buffer 峰值、expert checkpoint 和 EP group 故障共同主导。

  • token dispatch：router 的 top-K 结果变成 per-expert payload plan，触发 All-to-All 或 AllToAllV。
  • load balance：router 是学出来的，天然不会保证 256 个 expert 负载均匀；坍缩会让热门 expert straggle/OOM，冷 expert 空转。
  • capacity / dropless：fixed capacity 会 drop 或 overflow；dropless 不默认丢 token，但把问题变成 buffer peak、load skew、alltoallv bytes 和 fallback 事务语义。
  • incast 网络：All-to-All 是 N x N 通信，多个 sender 同时打向同一 receiver 时会放大交换机 buffer 与拥塞控制问题。
  • checkpoint reshape：checkpoint 从 layer x tensor shard 变成 layer x expert x tensor shard；loss-free bias、load EMA 和 overflow counters 也要作为训练状态保存。
  • 故障爆炸半径：一个 expert owner 的 kernel failure 或 buffer OOM 会让整个 EP group 停在同一个 dispatcher 边界。

推 — 从这个问题如何推导出每个机制

为什么 sparse FFN？ Transformer FFN 占参数和 FLOPs 的大头，但每个 token 并不需要读完所有 FFN 容量。把 FFN 拆成 N 个 expert 并只激活 K 个，可以让容量增长与每 token FLOPs 部分解耦。

为什么 top-K + gate weight？ topk_idx 是离散 membership，不对“选中哪个 expert”直接求导；主 loss 的连续梯度主要通过 selected gate weight 和 expert output 回到 router / expert。

为什么 shared expert？ routed experts 如果完全独立，会重复学习公共语言能力。DeepSeek-V2/V3 风格把 shared expert 作为每个 token 都经过的公共基线，把 routed experts 留给差异化专家化。

为什么 Expert Parallelism？ 以 DeepSeek-V3 形态估算，单个 routed SwiGLU expert/layer 约 3 x 7168 x 2048 ~= 44M 参数；256 个 expert/layer 约 11.3B，58 个 MoE layer 接近 650B routed expert 参数。把 experts 切到不同 GPU 是自然切法，但这必然引入 token dispatch。

为什么 fixed-capacity 与 dropless 分道？ fixed-capacity 预分配 buffer，超出 token drop 或 overflow，简单但损失训练信号；dropless 按真实 token 数动态打包、alltoallv 发送、可变长度 combine，不默认丢 token，但需要更强的 buffer、fallback 和事务语义。

为什么 load balance loss 与 loss-free balancing？ aux loss 用概率分布约束负载，但会污染主 loss 梯度；loss-free balancing 用 expert 级 bias 控制器调节未来路由，不把均衡目标直接混入主 loss。

为什么 DeepEP overlap？ dispatch + combine 可以占 step time 的 30-50%。DeepEP 类 kernel 把通信拆 chunk，与 grouped expert GEMM 交错，使通信尾部尽量被计算覆盖。

3. Expert Parallelism (EP)：把 expert 切到不同 GPU

3.1 为什么 EP 必然出现

params_per_expert_per_layer ~= W_gate + W_up + W_down
                              ~= 3 × H × I

H = 7168, I = 2048  =>  3 × 7168 × 2048 ~= 44M
256 routed experts/layer => 44M × 256 ~= 11.3B
58 MoE layers => 11.3B × 58 ~= 656B routed expert params
切法切什么问题
TP切单个 expert 内部 hiddenexpert 多且 GEMM 小，TP overhead 大
PP把不同层的 MoE block 放不同 stage只解决层数，不解决单层 expert 太多
DP/FSDP复制 expert 或切状态复制会放大 HBM；状态切分不解决 token dispatch
EP把不同 expert 放不同 GPU自然切法，但必然要 All-to-All / AllToAllV

3.2 EP 的 rank mesh

world_size = DP × PP × TP × EP × CP
rank coordinate = (dp_rank, pp_rank, tp_rank, ep_rank, cp_rank)
EP group        = 固定 (dp_rank, pp_rank, tp_rank, cp_rank)，跨 ep_rank
expert_per_rank = N_experts / EP_size              # 不考虑 ETP 时

有些系统使用 MoE Parallel Folding：attention / shared FFN 使用 dense mesh，routed FFN 使用 expert mesh。它不是说 EP 不占 GPU，而是同一批 physical ranks 在不同子模块中解释成不同 mesh 维度。配置文档必须明确是在严格 mesh 还是 folding 视图下讨论。

4. All-to-All 通信：MoE 的真正瓶颈

4.1 All-to-All 的体积账本

dispatch wire bytes (per rank, per MoE layer, per microbatch)
  ~= local_tokens_per_moe_rank_per_microbatch
      × topK
      × (hidden / ETP)
      × dtype_bytes
      × remote_fraction
      × padding_or_dropless_overhead
口径说明
logical payloadtoken hidden 向量本身，不含 headers、indices、alignment
wire bytes链路上传输的字节，包含 padding / alltoallv metadata / alignment
per-rank egress / send+recv / aggregate三者不能混用；设计评审必须标明口径
microbatch vs global batchAll-to-All 在每个 PP microbatch、每个 MoE layer 发生

严格 mesh 示例：global batch=1024 seq, seq=4096, DP=2, PP=4, TP=4, EP=64, microbatches=4, topK=8, hidden=7168, ETP=1, BF16。单个 DP 副本每 step 约 2.1M tokens；拆成 4 个 microbatch 后，每个 EP rank 本地约 8192 tokens。若负载近似均匀，单 layer dispatch egress wire bytes / rank 约 0.9-1.2GB；dispatch+combine 的 forward send+recv / rank 约 3.6-4.8GB。

工程含义：把 global batch tokens 直接除以 EP 得到"单次 All-to-All 体积"通常会把单 collective 估大一个 microbatch 或 DP 因子。MoE 通信账本必须先定 mesh、microbatch、ETP 和 per-rank/aggregate 口径。

5. Gate Routing：让 router 学会公平分配

5.1 标准 top-K softmax router

logits = x @ W_gate
probs  = softmax(logits, dim=-1)
topk_val, topk_idx = topk(probs, K)
gates  = topk_val / topk_val.sum(-1)

topk_idx 是离散 membership，autograd 不会学习“把第 K+1 个 expert 慢慢变成第 K 个 expert”；gates 是连续权重，主 loss 可以沿 selected gate weight 回到 router logits。

设计选择说明风险
Softmax 在 top-K 之前概率含义清晰membership 仍不可微
Softmax 在 top-K 之后只对 selected logits 归一化未选 logits 没有主 loss gate 梯度
sigmoid + biasDeepSeek-V3 风格需要 checkpoint bias/controller state
K=1/2/8通信与覆盖度的不同折中K 越大，buffer 和 alltoallv 压力越高

5.2 Router reproducibility

  • 浮点累加顺序：router logits/统计建议 FP32。
  • top-K tie-breaker：相同分数时按 expert id 固定排序。
  • dropout / 噪声：需要 fixed seed 或保存 router plan。
  • recompute：forward/backward/replay 必须复用同一 topk_idx/topk_weight 或完全可复现的 metadata。

5.3 Load balance loss（aux loss）

f_i = (1/T) Σ_t 1[token_t selects expert_i]
P_i = (1/T) Σ_t softmax(logits_t)[i]
L_aux = α · N · Σ_i f_i · P_i

aux loss 简单，但它把“负载均衡”目标直接加入优化目标，可能与主 loss 的专家化方向冲突。

5.4 DeepSeek-V3 的 auxiliary-loss-free balancing

score_i = sigmoid(logits_i) + b_i
TopK by score, gate = sigmoid(logits) (only TopK)
b_i 由控制器动态调整：load_i > 平均 -> b_i 减小；load_i < 平均 -> b_i 增大
维度aux lossloss-free balancing
实现loss 项训练循环外控制器
主 loss 梯度污染有无
工程复杂度简单需要 bias/load EMA 状态
checkpoint不需要额外状态必须保存 controller state

5.5 Router 的梯度路径语义

y_t = Σ_{i in S_t} g_{t,i} · Expert_i(x_t)
S_t = TopK(score_t, K)
信号 / 状态是否可微工程含义
topk_idx / membership否forward 保存，backward 复用；不要把 top-K membership 叫可微
selected gate weight是主 loss 回到 selected logits / router weight
selected expert output是只有被选 expert 收到该 token 的 expert-path grad
unselected expert output否dead expert 需要 aux / bias / exploration 解决
f_i hard load counter否作为 aux 系数或监控状态，不能给 membership 传梯度
loss-free bias不是 autograd 参数属于训练状态，影响未来路由，必须 checkpoint

6. Capacity Factor、Token Drop 与 Dropless MoE

6.1 两类容量策略

capacity_per_expert = ceil(capacity_factor × tokens_per_batch × K / N_experts)
路径代表token 溢出行为主要监控
fixed-capacity + dropGShard / Switch / 部分 Mixtral 实现超出 capacity 的 token drop、overflow 或 padding 到固定槽位drop_rate、overflow_count、padding waste
dropless + alltoallvDeepSeek-V3 风格大 MoE不默认丢 token，按真实目的 expert 动态发送max/avg load、buffer peak、alltoallv bytes、straggler、overflow fallback
工程边界：DeepSeek-V3 风格不要写成 capacity_factor=1.25 + token drop。更准确的说法是 dropless routing + flex dispatcher / alltoallv，fallback 触发应当按 incident 处理。

  FailClosed --> Replay: whole EP group selects fallback
  Replay --> Route: explicit replay same microbatch

合法异常处理只有 fail closed 与显式 replay：任一 rank 发现 mismatch、OOM、timeout 或 expert failure，先让整个 EP group 停在同一边界，丢弃未 commit 的 partial output；然后全 group 用同一个 fallback policy 重放同一个 microbatch，并复用 router seed 或保存的 topk_idx/topk_weight。

7.4 一层 MoE 的完整 runtime trace

1. Router
   logits -> score -> topk_idx, topk_weight
2. Expert ownership
   expert_id -> owner_ep_rank, local_expert_id
3. Plan
   histogram(owner_ep_rank) -> send_counts[dst_rank]
   exchange counts -> recv_counts[src_rank]
   prefix_sum -> send_offsets / recv_offsets
4. Stable pack
   payload = token hidden shard
   metadata = (src_rank, src_token_id, kth, expert_id, local_expert_id, gate)
   sort: dst_rank -> expert_id -> src token order -> kth
5. Dispatch
   alltoallv / DeepEP dispatch(payload, send_counts, send_offsets)
6. Expert compute
   grouped GEMM counts = tokens_per_local_expert
7. Combine
   send expert output back; token owner aggregates y += gate * expert_output
8. Backward
   reuse forward handle / permutation / combine metadata
Stable pack 是可复现性的核心。pack 顺序、tie-breaker 或 prefix offsets 在 forward/backward/recompute 之间变了，combine index 就会错位，常见表现不是 crash，而是 loss 慢慢变坏。

Plan 按 routed copy 计数，不按原 token 计数；每个 token 有 K=2 份 hidden copy。dispatch 后，owner rank 按 local expert 分组做 grouped GEMM；combine 按 (src_rank, token, kth) 发回原 token owner 并做 gate weighted sum。Backward 不重新发明路由计划，而是复用 forward 保存的 counts、offsets、pack permutation 和 combine metadata。

8.2 Reshape：EP=64 → EP=32 的恢复

reshape 类型难度备注
EP=64 → EP=32（ownership remap）容易新 rank 拥有更多完整 expert；不是把 expert tensor 相加
EP=64 → EP=128（ownership remap）容易新 rank 拥有更少完整 expert；不是把 expert tensor 拆半

256 expert → 320 expert（增殖）难新 expert 初始化策略未定，常见做法是复制 + 加噪

EP degree 改变时，通常改的是 expert_id -> owner_ep_rank：例如 old expert 17 -> ep_rank 4, local_expert_id 1，new expert 17 -> ep_rank 2, local_expert_id 5，但 experts.17.w_gate / w_up / w_down 的 shape 不变。只有改变 ETP、TP shard 规则、expert FFN hidden/intermediate，或剪枝/增殖 expert 时，才需要真正 reshape expert tensor；把 EP reshape 写成“把 expert tensor 拆半/合并”会导致 checkpoint 工具错误处理 optimizer slots。

恢复模式允许条件默认策略

9.3 Router gradient noise

top-K membership 不可微，未选 expert 没有该 token 的 expert-path gradient。常见症状包括 router 在前 1k step 几乎不动、dead expert 长期不被选中、expert 梯度方差大。缓解方式包括 noisy top-K、探索扰动、router lower lr、热身阶段强制均匀路由，以及 loss-free bias 控制器。

排障原则：MoE loss spike 第一时间看的不是普通 lr 或 global grad，而是 per-expert load、drop/fallback、router entropy、buffer peak 和 alltoallv tail。

12.2 Expert placement 与 node-limited routing

无论训练还是推理，expert_id -> node/gpu 都不是简单取模就完事。placement 同时决定通信 locality、load skew 和 straggler；训练 checkpoint 中的 expert_id -> owner_ep_rank 是训练 owner，不等于推理 placement，转换工具要生成新的 serving manifest。

最小 placement manifest 应显式记录：

expert_placement:
  layer_id: 3
  ep_group_id: dp0_pp1_tp0_cp0
  policy: node_limited_round_robin_v1
  experts:
    - expert_id: 0
      node_id: node000
      gpu_id: 0
      ep_rank: 0
      local_expert_id: 0
    - expert_id: 1
      node_id: node000
      gpu_id: 1
      ep_rank: 1
      local_expert_id: 0
策略做法适用场景风险
round-robin by expert_idowner = expert_id % EPbaseline，易复现热门 expert 可能集中到同一节点或 rail
node-balanced placement先按 node 分桶，再在节点内按 gpu 轮转训练 EP group 跨多节点需要 topology-aware rank map
replicated hot experts热门 expert 多副本，router 或 dispatcher 选最近副本推理、小 batch训练 optimizer 同步复杂，不是默认训练路径
straggler-aware remap根据 load EMA / layer timer 周期性交换 expert owner长训中消除 tail rank会改变 checkpoint ownership，必须在 step 边界做

node-limited routing 的思路是：router 先产生全局 score，但 dispatch plan 可以把候选 expert 限制在少数节点内，降低跨节点 A2A：

for each token t on node n:
  candidate_nodes = topM_nodes(score_t, placement, M)
  candidate_experts = experts_on(candidate_nodes)
  S_t = topK(score_t over candidate_experts)

这不是免费优化：限制候选节点会改变模型可表达性和 load balance。训练里如果使用 node-limited routing，必须把 candidate_nodes 规则视为 router 语义的一部分，checkpoint 和评估都要一致；推理里可以更激进，因为目标是低延迟和 locality。

send plan 应由 placement 派生，而不是在通信层猜：

topk_idx[token,k] -> expert_id
expert_id -> (node_id, gpu_id, ep_rank, local_expert_id)
ep_rank -> send_counts[ep_rank] += 1

如果发现 straggler，重排流程要在算法层闭环：

  1. 收集每层 tokens_per_expert、tokens_per_rank、dispatch/combine time、expert GEMM time。
  2. 把 expert 分成 hot / cold / normal，按 layer 单独处理，不要全局平均。
  3. 在同一 EP group 内交换 hot expert 与 cold expert 的 owner，优先跨节点/跨 rail 打散。
  4. 在 step 边界广播新 placement version，更新 router/dispatcher/checkpoint manifest。
  5. 若要 true resume，先把 optimizer slots 跟随 expert_id 一起迁移，再允许 optimizer step。

placement 的核心原则是：expert_id 是语义身份，rank/gpu 只是 owner。所有 send_counts、checkpoint shard、optimizer slot、load EMA 和 loss-free bias 都必须跟 expert_id 对齐，而不是跟当前 rank 对齐。

训推差异：训练的 EP=64、dropless/fallback、DeepEP normal mode 不能直接等同于推理路径。推理更关注 tail latency、KV cache locality、expert hotness 和小 batch dropless。

top-K 上限K 越大通信与 buffer 越大；K=8 已是高压配置
dropless不是没有容量问题，而是把 drop 转成 buffer peak、fallback 和 straggler 问题
router 数值logits、bias、统计建议 FP32，top-K tie-breaker 固定
DeepEP优化 dispatch/combine，不替代 framework router/dispatcher/checkpoint
MoE checkpoint必须含 expert 映射、ETP shard、router、shared expert 和 controller state
推理路径与训练 placement 分离，需要 serving manifest
