1. 第一性原理拆解：数据并行

拆 — 不可化简的问题

剥离 DDP、NCCL、ZeRO、bucket 这些工具名之后，本章面对的不可化简问题只有一个：训练一个模型需要反复用大量样本估计同一组参数的更新方向，而单个加速器在单位时间内能处理的样本数有限；如果复制计算者来提高样本吞吐，就必须付出让所有复制者重新达成一致的代价。数据并行不是“把脚本复制到多张卡上”这么简单，它是在两个物理事实之间做交换：一边是 GPU 对不同样本的前向和反向天然可并行，另一边是参数更新必须基于同一个全局梯度，否则每张卡很快就会训练成不同模型。只要训练算法仍然假设同步 SGD / Adam 这类全局一致的更新语义，同步梯度就不是可选优化，而是保持数学含义的必要步骤。

这也是很多团队第一次真正面对“通信现实”的地方。单机阶段的主要矛盾通常是算子是否高效、显存是否够、DataLoader 是否稳定；一旦进入数据并行，step 时间里多了一段不做模型计算却必须完成的工作：把每张卡上的梯度聚合，再把聚合结果发回所有卡。卡数越多，样本吞吐潜力越高，但同步路径也越长；模型越大，梯度字节数越大；跨节点越多，网络带宽、延迟、拥塞、拓扑和慢节点都会进入训练主循环。更麻烦的是，扩卡还会改变 batch 语义：固定 per-device batch 会放大 global batch，固定 global batch 又会压小每卡计算量，使通信占比上升。因此，本章真正要建立的不是“会启动多卡训练”，而是能回答：复制多少计算者以后，额外同步代价是否仍然低于新增算力收益？

推 — 从这个问题如何推导出每个机制

从“复制计算者提升吞吐，但必须保持参数一致”出发，第一个必然机制是数据切分和模型复制：每个 rank 拿不同 batch 分片，保留同一份模型，独立完成 forward / backward。第二个机制是梯度聚合：本地梯度只是局部样本的估计，必须通过 AllReduce 变成全局平均梯度；ring、tree、double binary tree 等算法本质上都是在不同消息大小、设备数和拓扑下，平衡带宽利用率与启动延迟。第三个机制是通信与计算重叠：如果等所有层反向结束后再同步全部梯度，GPU 会在 step 尾部纯等网络；于是 DDP 会把梯度组织成 bucket，让较早产生的梯度先开始 AllReduce，目标是把通信藏进 backward 时间里，只留下尽量短的 tail。

接着会推导出扩展效率这个指标。单看 8 卡吞吐没有意义，必须和 1 卡基线相比，判断新增卡数带来的吞吐是否接近线性；还要区分 strong scaling 和 weak scaling，因为前者固定任务总量，后者固定每卡工作量，回答的是两个不同问题。再往下会出现 batch 定义和梯度累积：为了让每卡算得足够久、摊薄同步成本，你可能想增大 per-device batch；但优化算法看到的是 global batch，过大可能影响收敛，于是梯度累积、LR scaling、warmup 都进入系统设计边界。通信成为瓶颈后，又会推导出 bucket 调参、混合精度通信、梯度压缩：先减少碎消息和尾部等待，再考虑用 BF16/FP16、quantization、sparsification 或 PowerSGD 减少传输字节，但这些近似会把系统问题重新带回收敛风险。最后，当“每张卡保留完整模型、梯度、优化器状态”这个前提不再成立，就会推导出 FSDP / ZeRO：它们仍属于数据并行家族，但把原来冗余保存的训练状态切分，从“同步梯度”扩展到“按需聚合参数和状态”。所以本章的逻辑链不是工具罗列，而是：吞吐不足导致复制，复制导致一致性，同步导致通信，通信导致 overlap / 压缩 / 拓扑调优，内存冗余导致 sharding。

3. 数据并行的核心思想

在数据并行中，每张卡持有一份完整模型，但处理不同的数据分片。一个 step 的基本流程是：各卡各自前向和反向，得到本地梯度，通过通信把梯度聚合，然后各卡更新到相同参数。用更抽象的话说，数据并行做的是：复制模型，切分数据，同步梯度。

flowchart LR
  A[全局 batch] --> B[Sampler 切分]
  B --> R0[Rank 0: 模型副本 + 数据分片]
  B --> R1[Rank 1: 模型副本 + 数据分片]
  B --> Rn[Rank N: 模型副本 + 数据分片]
  R0 --> G0[本地梯度]
  R1 --> G1[本地梯度]
  Rn --> Gn[本地梯度]
  G0 --> AR[AllReduce 平均梯度]
  G1 --> AR
  Gn --> AR
  AR --> U0[各 rank 执行相同 optimizer.step]
  U0 --> M[参数重新一致]

它的优势是模型逻辑改动小、框架支持成熟、调试链路短，是大多数训练集群的第一种并行方式。它的代价是通信成本会随着规模上升越来越明显，内存不会自动变多，每卡一份完整参数、梯度和优化器状态，存在大量冗余。

DDP 在做什么，不在做什么

DDP 做的事DDP 没做的事
每个 rank 保留一份完整模型副本让模型本体跨卡切分后放入显存
每个 rank 处理不同数据分片解决 DataLoader 本来就跟不上的问题
在反向传播过程中同步梯度减少完整优化器状态的每卡冗余
让参数在每个 step 后重新一致解决序列长度导致的激活 OOM

一个容易忽略的事实：DDP 下每卡内存不会下降

组成占用说明
模型权重（bf16）2 GB1B 参数 × 2 字节

关键边界：经典 DDP 擅长的是“同一个模型已经能在单卡稳定训练，如何通过复制副本提升样本吞吐”。如果模型或训练状态单卡放不下，继续加 DDP 卡不会解决问题。

4. 一个 step 的时间分解

数据并行下，一个 step 可以粗略写成：

t_step = t_forward + t_backward + t_allreduce + t_optim

如果 t_allreduce 占比越来越高，说明作业已经进入通信主导区间。这时要问梯度量有多大、网络拓扑怎样、通信能否和计算重叠，以及继续扩卡是否仍然值得。

真正影响体验的是重叠得怎么样

真实 DDP step 往往不是先 backward 完再统一 allreduce，而是在反向传播逐层产生梯度时，DDP 把梯度放进 bucket，一些 bucket 一边生成一边开始通信。更接近工程现实的近似是：

t_step ≈ t_forward + max(t_backward, t_allreduce_overlap) + t_tail + t_optim

Profiler 读法：如果 step 尾部有长 NCCL tail，平均 GPU utilization 往往看不出来；必须看时间线、per-rank step time 和 AllReduce 与 backward 的重叠区间。

一个简单的通信占比心算

通信时间 ≈ gradient_bytes × 2 × (N-1) / N / bandwidth
计算时间 ≈ FLOPs / (GPU_peak × 利用率)
通信占比 ≈ 通信时间 / (计算时间 + 通信时间)

举例：7B 模型的 bf16 梯度约 14 GB，8 卡 NVLink 节点内有效带宽约 300 GB/s，通信时间约 14 × 2 × 7/8 / 300 ≈ 0.08 秒。如果换到跨节点 InfiniBand 且有效带宽约 25 GB/s，同样通信约 1 秒，overlap 不到位就会直接拖垮 step。

5. AllReduce 为什么会成为瓶颈

AllReduce 的本质是把多个设备上的梯度聚合，并把聚合结果再分发回去。在一个粗略的 ring all-reduce 模型里，每个参与者大约要传输：

传输量 ≈ 2 × (N - 1) / N × gradient_bytes

梯度越大，通信越贵；设备越多，协调越复杂；网络越慢，扩卡收益越差。所以数据并行不是“卡越多越快”，而是“卡越多越依赖通信栈”。

Ring 和 Tree：NCCL 为什么会选不同算法

算法特点更适合
Ring AllReduce带宽利用率高，延迟随 N 线性增长大消息、小 N
Tree AllReduce延迟随 log(N) 增长，带宽利用率稍差小消息、大 N
Double Binary Tree在带宽与延迟之间折中大规模集群常见
为什么 bucket 有价值：小梯度不一定比大梯度同步快，因为小消息下 latency 和 collective 启动开销可能超过数据传输。把碎梯度合成 bucket，通常比一个个发更快。

6. 扩展效率怎么理解

一个常见指标是扩展效率：

scaling efficiency = T_N / (N × T_1)

其中 T_1 是单卡吞吐，T_N 是 N 卡吞吐。如果效率接近 1，说明扩卡较健康；如果效率快速下滑，通常说明通信开销过大、数据供给跟不上、per-device batch 太小，或节点异构导致木桶效应。这里的 T_1 最好来自 第 7 章 已经稳定的单机基线，否则指标会失真。

强扩展和弱扩展不要混着看

实验方式固定什么更适合回答什么问题常见陷阱
强扩展 strong scalingglobal batch 和任务总量同一个任务能否更快做完每卡 batch 变小，通信占比上升
弱扩展 weak scalingper-device batch加卡后吞吐能否线性增长global batch 变大，优化行为也会变

看 tokens/sec 比看 steps/sec 更稳

指标含义为什么更稳
tokens/sec每秒处理的 token 数和 step 定义解耦
samples/sec每秒处理的样本数适合非文本任务或样本长度稳定场景
TFLOPS/GPU每卡实际算力利用直接反映计算饱满度
MFU实际 FLOPs / 理论峰值跨硬件对比更可靠
指标口径：“8 卡 90% scaling efficiency”本身还不够，必须追问 global batch 是否变了、每卡 batch 是否太小、数据链路是否仍然稳定。

7. 为什么大 batch 不是免费午餐

为了提高数据并行效率，很多人会想到增大 batch。大 batch 往往能减少同步相对占比，但也会改变优化行为、收敛路径、学习率策略和显存压力。因此平台和算法团队需要协作，而不是简单地“为了扩卡效率把 batch 无限做大”。

global batch 到底怎么算

B_global = B_per-device × N_devices × N_accum
  • 扩卡后如果保持 B_per-device 不变，B_global 会随设备数线性变大。
  • 如果想保持 B_global 不变，就必须缩小 B_per-device 或减少累积。
  • B_per-device 太小，会让单卡计算不饱满、通信占比变大。

梯度累积：想要大 batch 又没那么多卡

梯度累积的本质是用时间换空间：把一个大 batch 拆成若干 micro-batch，分多次前向/反向但不立刻更新，最后再一次性 optimizer.step()。

for i, batch in enumerate(loader):
    is_accum_step = (i + 1) % accum_steps != 0
    ctx = model.no_sync() if is_accum_step else nullcontext()
    with ctx:
        loss = model(batch) / accum_steps
        loss.backward()
    if not is_accum_step:
        optimizer.step()
        optimizer.zero_grad()
常见翻车：忘了 no_sync() 包装累积阶段的反向，结果每个 micro-batch 都触发 AllReduce，8 卡 accum_steps=4 下每 step 做了 4 次同步，吞吐可能比不用累积还低。

LR scaling 规则

规则含义何时使用
Linear scalinglr_new = lr_base × (B_new / B_base)中等 batch 扩展
Square-root scalinglr_new = lr_base × sqrt(B_new / B_base)更保守，大 batch 下更常用
Warmup 变长大 batch 初期更不稳定扩卡后 loss 早期抖动明显

8. 梯度压缩与通信优化

当通信开始主导 step 时间时，常见优化主要有三类：梯度压缩减少传输字节数，混合精度通信用更低精度传梯度或 bucket，Gradient Bucketing 把梯度按桶组织并尽早启动通信。

手段在解决什么适用条件常见代价
梯度压缩减少传输字节数网络较慢、模型大、收敛可重新验证可能影响收敛稳定性，排障复杂
混合精度通信用 FP16 / BF16 传梯度或桶训练已稳定、框架支持成熟精度和数值排查更复杂
Gradient Bucketing让梯度一准备好就尽早通信反向传播较长、希望 overlap桶大小不合适会适得其反

梯度压缩：省带宽不是免费的

方法基本思想典型带宽收益收敛风险工程边界
Quantization梯度从 FP32/BF16 压到更低 bit2x-32x量化噪声，训练早期更敏感优先从 BF16/FP16 通信开始
Sparsification只传 Top-K 或超过阈值的梯度5x-100x梯度方向偏差和索引开销需要 error feedback buffer
PowerSGD对二维梯度矩阵做低秩近似4x-50xrank 太小会拖慢或破坏收敛必须做同 token 数 A/B
压缩比不等于 step 加速比：如果原本通信已经被 backward overlap 掩盖，或者 step 里还有 DataLoader、checkpoint、慢 rank 抖动，压缩带来的端到端收益可能只有几个百分点。

为什么 bucket 大小会影响扩展效率

bucket 倾向好处代价
更小更早启动通信，更容易和反向重叠通信调用更碎，latency 开销更明显
更大更容易吃满带宽，调用次数更少启动通信更晚，尾部等待更长
flowchart TD
  A[发现 step 变慢] --> B{NCCL tail 明显吗}
  B -->|否| C[先看 DataLoader / checkpoint / kernel / 慢 rank]
  B -->|是| D{消息碎还是尾部大}
  D -->|小消息多| E[调大 bucket 或减少 collective 次数]
  D -->|尾部大| F[调小关键 bucket / 检查梯度生成顺序]
  E --> G[验证 overlap 和 tokens/sec]
  F --> G
  G --> H{通信仍是主瓶颈}
  H -->|是| I[尝试 BF16/FP16 comm hook]
  H -->|否| J[保留配置并记录实验元数据]
  I --> K[再评估 PowerSGD / quantization / sparsification]

DDP 常见优化开关

参数 / 开关作用适用场景
bucket_cap_mb控制 bucket 大小最基本的调优旋钮
gradient_as_bucket_view=True让梯度直接指向 bucket 内存，省一次 copy大多数 DDP 任务
static_graph=True声明计算图每步一致，允许更激进优化模型结构固定时
find_unused_parameters=True容忍部分参数不参与反向有动态分支，但有性能代价
DDP comm hooks自定义梯度通信逻辑通信瓶颈已被 profiler 证明时
调优顺序：不要一开始就追求激进压缩；先把 bucket、overlap 和拓扑利用率做好，压缩应被当成通信已被证明为主瓶颈后的近似算法变更。

9. NCCL 调优要点

NCCL 很少是“装好就结束”的组件。出现扩展效率异常时，至少要检查通信初始化、网卡路径、GPU / NIC 拓扑、collective 算法、跨节点链路和每个 rank 的健康度。

项目作用常见用途
NCCL_DEBUG=INFO打印通信初始化和错误信息首次排障、确认拓扑和超时位置
NCCL_DEBUG_SUBSYS=ALL更细粒度子系统日志深度排障
NCCL_IB_DISABLE=1禁用 InfiniBand 路径隔离 IB / RoCE 相关问题
NCCL_SOCKET_IFNAME=eth0指定网卡接口避免走错网卡或管理网
NCCL_P2P_DISABLE=1禁用 GPU P2P排查 NVLink / PCIe 问题
NCCL_ALGO=Ring/Tree强制算法选择实验用，生产一般让 NCCL 自选
nvidia-smi topo -m查看 GPU / NIC 拓扑判断通信路径是否符合预期

常见故障信号

信号更可能的问题第一检查动作
初始化阶段 hang网卡接口、rank 配置、端口或拓扑异常看 NCCL_DEBUG=INFO 和网卡绑定
只有跨节点效率明显掉交换网络、NIC 或跨机链路瓶颈区分机内和机间通信占比
某个 rank 总比别的慢慢节点、NUMA、CPU 绑核或热降频看 per-rank step time 和节点健康度
偶发 timeout网络抖动、IB / RoCE、驱动栈问题对齐日志与网络事件时间点
step 末尾总卡一大段通信 overlap 不足，bucket 或拓扑不理想看 profiler 时间线里的通信尾巴
第一个 step 特别慢NCCL 初始化、cuBLAS 预热、buffer 分配不要把 step 0 算进平均
排障原则：不要把所有慢都归结成“网络不好”。很多时候是某个 rank 先慢了，网络 collective 只是把这个慢同步放大给所有人看见。

典型案例：跨节点从 90% 掉到 60%

  1. 先区分机内机外通信：单节点 8 卡仍有 92% 效率，说明问题在跨节点。
  2. 看 NCCL log：发现 NCCL 选了 Ring 算法，跨节点走 IB。
  3. 跑 nccl-tests：2 节点 all_reduce_perf 带宽只有 IB 理论值的 40%。
  4. 检查 NIC：ibstat 显示一个节点的 NIC 链路速率配置错了。
  5. 修复后：效率恢复到 88%。

11. 数据并行的边界：什么时候需要 FSDP / ZeRO

经典 DDP 有一个硬约束：模型、梯度和优化器状态必须能塞进一张卡。当这个前提不成立时，要么上模型并行（见 第 9 章），要么把数据并行升级成 FSDP / ZeRO。

FSDP 和 ZeRO 的核心观察是：DDP 下每张卡都存一份完整权重、梯度、优化器状态，其中存在大量冗余；如果把这些状态切分到不同卡上，只在需要时临时聚合，就能大幅省内存。

阶段切分什么内存节省通信开销对应 FSDP
ZeRO-0不切无基线DDP / NO_SHARD
ZeRO-1优化器状态约 4x（Adam 下）约等于 DDP—
ZeRO-2优化器状态 + 梯度约 8x约等于 DDPSHARD_GRAD_OP
ZeRO-3优化器状态 + 梯度 + 参数随 N 线性下降约 1.5x DDPFULL_SHARD
flowchart LR
  A[DDP: 每卡完整参数/梯度/优化器] --> B[ZeRO-1: 切优化器状态]
  B --> C[ZeRO-2: 再切梯度]
  C --> D[ZeRO-3 / FSDP FULL_SHARD: 再切参数]
  D --> E[forward/backward 时按需 all-gather 参数]
  E --> F[内存下降，通信和 checkpoint 复杂度上升]

DDP、FSDP、ZeRO 的选择

场景推荐理由
模型 + 训练状态能放下单卡DDP最简单，吞吐最高
模型能放下但优化器状态顶不住ZeRO-2 / FSDP SHARD_GRAD_OP通信和 DDP 相当，内存显著节省
模型本身放不下单卡ZeRO-3 / FSDP FULL_SHARD参数也切分，内存随 N 下降
超大模型（100B+）ZeRO-3 + TP + PP单一策略不够，要组合
模型不大但 batch 想开很大DDP + 梯度累积不为“新技术”付额外复杂度
FSDP 不是免费加内存：checkpoint 变复杂、wrap policy 很关键、第一个 step 更慢、forward/backward 需要额外 all-gather，调试也比 DDP 难。上线前必须有分片 checkpoint 的保存恢复流程。

12. 什么时候不该优先做数据并行

以下情况继续做数据并行，可能只是把本来就没解决的问题放大：单卡训练还没稳定，模型根本放不下单卡，数据读取已经是第一瓶颈，网络条件很差，per-device batch 已经小到喂不饱单卡，或 checkpoint / 评测 stall 频繁。

反模式典型表现后果正确做法
单卡没调好就扩单卡 MFU 20%，直接上 8 卡问题被放大先把单卡调到可接受水平
为扩卡无限放大 batch只追求扩展效率，不管收敛模型训不收敛或精度掉和算法团队同步 LR scaling
跨节点用普通以太网25 GbE 集群训 10B+ 模型通信占比过高换 IB 或换并行策略
忘了 no_sync()梯度累积下每 micro-batch 都同步通信多了 N 倍正确包装 accum 阶段
把第一个 step 算进平均报告吞吐“不稳”误判为框架 bug丢掉前 N 步
模型放不下却坚持 DDP不断 OOM retry训练根本跑不起来切 FSDP 或上 TP
只看 GPU utilization“卡利用率 95%”可能主要在 memcpy 或等待看 MFU 和 tokens/sec
严重风险：当通信停顿和 checkpoint 写盘停顿叠加时，step 抖动、超时和恢复成本会一起放大。checkpoint 策略需要跟随并行策略调整，不能沿用单卡默认值。

小结

主题关键点
数据并行本质复制模型，切分数据，同步梯度
