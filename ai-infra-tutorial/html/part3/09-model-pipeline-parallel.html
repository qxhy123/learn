1. 第一性原理拆解：为什么会有模型并行与流水并行

拆 — 不可化简的问题

剥离 Data Parallelism、Tensor Parallelism、Pipeline Parallelism、ZeRO、FSDP、Sequence Parallelism、Context Parallelism 这些术语，本章真正面对的不可化简问题只有一个：一个训练 step 需要保存和计算的状态超过了单个物理设备的容量与带宽，系统必须把状态、计算和通信同时拆开，并且拆完之后仍然保持数学等价和工程可恢复。数据并行在 第 8 章 中解决的是“同一个模型副本如何吃更多样本”，它默认每张 GPU 都能放下完整参数、梯度、优化器状态和必要激活。一旦 7B、70B、405B 模型叠加 BF16 参数、FP32 master weights、Adam 一阶二阶动量、activation checkpointing、长上下文 attention workspace 后超过单卡或单节点容量，复制模型就从扩展手段变成了障碍。

这个问题不能只用“显存不够”概括。显存只是第一层硬约束；第二层是计算单元是否闲置，第三层是 GPU 之间的链路能否承受同步，第四层是 checkpoint、恢复、故障定位是否还能解释清楚。一个策略如果让模型能放下，但每层都跨慢速网络 AllReduce，吞吐可能比小规模训练还差；另一个策略如果利用率很高，但 checkpoint 无法在 rank 重排后恢复，就不适合平台化运行。模型并行的本质不是“把模型分到多张卡”，而是在容量、带宽、延迟、调度复杂度和恢复复杂度之间做约束求解。

因此，本章的学习目标不是记住某个框架参数怎么写，而是建立工程决策直觉：什么时候先用纯 DP，什么时候把层内矩阵切成 TP，什么时候按层段切成 PP，什么时候用 ZeRO / FSDP 切训练状态，什么时候因为序列长度太长而叠加 SP / CP，以及什么时候不应该继续叠加并行维度。读这一章时要一直追问：我切掉的是哪一种重复？新引入的是哪一种通信？这个通信发生在节点内还是跨节点？它会不会改变 checkpoint 的组织方式？当一个 rank 掉线或恢复时，系统还能不能知道每个 shard 属于谁？

推 — 从这个问题如何推导出每个机制

从“单卡装不下完整训练副本”出发，第一种直接推导是状态分片。参数、梯度、优化器状态存在大量副本，ZeRO / FSDP 就是把这些重复状态切开，让每张卡只保存一部分；但它没有自动切开单层 GEMM 的计算，也没有自动降低 attention 对超长序列的压力。于是第二种推导是张量并行：如果某一层的权重矩阵或 attention projection 太大，就沿 hidden dimension、head 或矩阵行列把单层计算拆给多张 GPU。TP 的收益是降低单层参数和计算峰值，代价是每层都可能出现 AllReduce、AllGather 或 ReduceScatter，所以它天然应该优先放在 NVLink / NVSwitch 这类节点内高速互联里。

如果单层通过 TP 能放下，但整个网络层数太多、单节点仍然无法承载完整模型，就会推导出流水并行：把 Transformer 层段切成多个 stage，不同 micro-batch 像工厂流水线一样依次通过 stage。PP 解决的是“整网太深、整模太大”，但它引入 pipeline bubble，因为流水线填充和排空阶段总有设备暂时没有活干。micro-batch 数 m 越少、stage 数 p 越多，bubble 越明显，因此 PP 必然引出 1F1B、Interleaved Pipeline、Zero Bubble 等调度优化。它们不是新的容量机制，而是在容量已经被 PP 解决后，进一步减少空闲槽。

当模型能放下后，还要解决吞吐扩展，这自然回到数据并行：把已经由 TP / PP / ZeRO 组成的“一个模型副本”复制多份，每份吃不同 batch，再同步梯度。大规模训练常见的 DP x PP x TP 不是为了炫技，而是因为三个维度分别切样本、层段和层内计算。长上下文又会推导出另一个分支：TP 主要切 hidden，PP 主要切 layers，ZeRO 主要切训练状态；当 context 从 8K 拉到 128K+，真正爆掉的可能是 token 维度上的激活、KV 和 attention workspace。Sequence Parallelism 在 TP 组内切非 attention 路径的 sequence 激活，Context Parallelism 切 attention 所需的 context / KV 流动。二者的共同点是补“序列维度”的短板，不是替代 DP / TP / PP。

工程上，机制推导的顺序也给出选型顺序：先问完整训练形态单卡能否放下；不能，再问单节点高速互联内能否通过 TP 或 FSDP 放下；还不能，再问模型是否适合按层切 PP；最后再根据长上下文、吞吐目标和 checkpoint 约束叠加 SP / CP / DP。边界很明确：每增加一个并行维度，rank 拓扑、通信域、日志归因、性能画像、checkpoint shard 数量都会变复杂。平台工程师的任务不是默认选择最复杂的组合，而是找到能满足容量和吞吐目标的最小复杂度组合。

2. 为什么数据并行不够了

数据并行默认每张卡都要装下一份完整模型。当模型已经放不进单卡时，就必须改思路：不是复制模型，而是把模型切开。典型触发条件包括参数规模过大、中间激活太大、序列长度太长、单卡显存无法容纳目标训练形态。

数据并行的假设
每个 rank 保存完整参数、梯度、优化器状态和必要激活；扩展方式是复制模型副本并增加样本吞吐。
模型并行的触发
完整副本已经无法放入单卡或单节点，扩展方式必须转向状态、层、张量或序列维度的切分。
压力来源症状优先考虑
参数 / 梯度 / 优化器状态空 batch 也接近 OOMZeRO / FSDP
单层 GEMM / attention projection某些层峰值特别高Tensor Parallelism
整网层数 / 激活单节点仍无法承载完整网络Pipeline Parallelism
超长 context / KVsequence 拉长后显存和时间急剧上升SP / CP
边界提醒：“能启动”不等于“适合纯 DP”。如果必须靠极小 micro-batch 才能放下，GPU 利用率和全局 batch 约束可能已经要求重新评估并行策略。

3. 张量并行：切层内部的计算

张量并行的思路是把同一层里的矩阵计算切到多张卡上。例如，一个大矩阵乘法可以按列或按行分片，让多张卡共同完成。它能解决单层参数太大问题，对超大线性层特别有效；代价是通信频繁、对互联带宽和延迟敏感、实现与调试复杂。也就是说，张量并行把一部分“显存问题”换成了“通信问题”。

flowchart LR
  X[输入激活 X] --> A[列切 Linear: W1 shards]
  A --> G1[AllGather 或局部拼接]
  G1 --> F[激活函数 / Attention]
  F --> B[行切 Linear: W2 shards]
  B --> R[AllReduce / ReduceScatter]
  R --> Y[输出激活 Y]
切分方式常见对象通信直觉工程要求
列并行MLP 上投影、QKV 投影输出分片，后续可能需要 gatherhidden/head 数可整除 TP size
行并行MLP 下投影、输出投影部分和需要 AllReduce高带宽、低延迟互联
Attention head 切分多头注意力按 head 分摊计算head 数可整除，kernel 支持良好
经验规则：TP 组大小通常优先选 2、4、8，并尽量限制在同一 NVLink / NVSwitch 域内；跨节点 TP 是高阶优化，不应作为默认起点。

4. 流水并行：按层切模型

流水并行把模型的不同层段放到不同设备，让不同 micro-batch 像流水线一样流过这些阶段。

Stage 1 -> Stage 2 -> Stage 3 -> Stage 4

它的优点是层次切分更符合 Transformer 结构，每张卡只承担部分层；难点是会出现 pipeline bubble，micro-batch 调度更复杂，前后阶段可能负载不均。Embedding、loss head、MoE router 或局部层结构差异，都可能让某个 stage 成为全局 step time 的瓶颈。

sequenceDiagram
  participant S1 as Stage 1
  participant S2 as Stage 2
  participant S3 as Stage 3
  participant S4 as Stage 4
  S1->>S2: micro-batch 1 forward
  S1->>S2: micro-batch 2 forward
  S2->>S3: micro-batch 1 forward
  S3->>S4: micro-batch 1 forward
  S4-->>S3: micro-batch 1 backward
  S3-->>S2: micro-batch 1 backward
  S2-->>S1: micro-batch 1 backward
流水线视角：PP 不是把一个 batch 一次性塞进所有 stage，而是把 batch 切成多个 micro-batch，让 stage 在时间轴上交错工作。

5. 什么是 Pipeline Bubble

在流水并行中，前几个 step 里后续 stage 还没工作，结束阶段里前面 stage 又可能空闲，这些空闲区间就是 bubble。一个常见近似理解是：

pipeline utilization ≈ m / (m + p - 1)

其中 m 是 micro-batch 数，p 是 pipeline stage 数。这个式子的直觉很重要：micro-batch 太少，bubble 占比高；stage 太多，流水线填满更慢。所以流水并行并不是“切得越细越好”。

stage 数 pmicro-batch 数 m近似利用率判断
41684.2%通常可接受，仍需看负载均衡
8853.3%bubble 很明显，需优化调度或减少 stage
83282.1%更容易填满，但显存和 batch 约束更重
严重风险：为了降低 bubble 盲目增加 micro-batch，可能破坏全局 batch、梯度累积、激活显存和收敛假设。流水线调度必须和训练数学约束一起设计。

6. 为什么大模型训练通常是混合并行

现实中，超大模型训练很少只用一种并行方式，更常见的是组合：数据并行做样本吞吐扩展，张量并行解决单层过大，流水并行解决整体层数过多，参数 / 状态切分进一步降低显存压力。这意味着平台需要处理的不只是某一种策略，而是不同组之间的 rank 组织、不同通信域、不同 checkpoint 方式和不同恢复逻辑。

平台关注点：TP x PP x DP = GPU 总数 只是算术成立；真正落地还要把 TP 放进高速互联域，把 PP stage 放在稳定拓扑上，并让 DP 同步路径可预测。

7. ZeRO 系列与 FSDP

ZeRO 的核心思想不是“换一种模型并行”，而是把训练状态按不同粒度分片，减少每卡持有的冗余状态。

方案主要分片什么典型收益主要代价
ZeRO Stage 1Optimizer state先降优化器显存实现简单，但参数和梯度仍全量保留
ZeRO Stage 2Optimizer state + Gradients进一步降梯度占用通信更多，反向路径更复杂
ZeRO Stage 3Optimizer state + Gradients + Parameters最大幅度降低单卡状态占用通信、checkpoint、恢复都更复杂
PyTorch FSDP常被视作官方 ZeRO-3 风格实现PyTorch 原生集成较好仍需认真处理 shard、state dict 和恢复流程

工程上最重要的判断是：ZeRO / FSDP 与 TP / PP 是互补关系，不是替代关系。当模型既放不下单卡，又不想把所有层硬切给 TP / PP 时，ZeRO / FSDP 往往是第一补充手段。但一旦进入状态分片，checkpoint 就不能再按“单文件全量模型”思路设计，通常要转向 第 10 章 §10.6 的分布式 checkpoint 方案。

状态分片直觉：ZeRO / FSDP 降低的是每卡“持有多少训练状态”，不自动解决单层计算峰值、pipeline bubble 或超长 context attention 的序列压力。

8. Interleaved Pipeline 与 Zero Bubble 简述

传统 1F1B 已经能降低部分 bubble，但 stage 负载仍可能不均。进一步优化时，常见两个方向：Interleaved Pipeline 让一个设备承担多个更细的虚拟 stage，降低空闲比例；Zero Bubble 系列思路尽量把前向、反向和权重更新空隙压到更低。

思路在解决什么工程代价
Interleaved Pipeline让一个设备承担多个更细的 stage，降低空闲比例调度更复杂，stage 划分更难
Zero Bubble 系列思路尽量把前向、反向和权重更新空隙压到更低依赖更复杂的调度与实现细节

Interleaved Pipeline 可以理解成“把原来每张卡只放一个大 stage，改成每张卡放多个更细的小 stage，再交错执行”。它解决的本质问题是传统 stage 太粗，导致 bubble 比例和负载不均同时存在。Zero Bubble 的目标更激进，它会把 backward 中的输入梯度、权重梯度、权重更新等步骤拆成更细的 micro-op，然后重新编排，让原本会闲着的 stage 去做能够提前执行的工作。

flowchart LR
  A[GPipe: 先全 forward 再 backward] --> B[1F1B: forward/backward 交替]
  B --> C[Interleaved: 每设备多个虚拟 stage]
  C --> D[Zero Bubble: 拆分 B/W micro-op 填充空闲槽]
  D --> E[更高利用率\n更高调度和排障成本]
平台判断：当训练团队开始讨论 Interleaved 或 Zero Bubble，通常说明传统流水线利用率已经成为明确瓶颈；平台侧至少要能观测 bubble、stage time 和 straggler。

9. Sequence Parallelism 与 Context Parallelism

当上下文长度从 4K、8K 拉到 32K、128K 甚至更长时，只靠 TP / PP / ZeRO 往往还不够，因为激活和 attention 的 KV 开销会随着序列长度迅速放大。

技术切分什么主要在解决什么更依赖什么常见通信
Tensor Parallelism隐藏维度 / 权重矩阵单层参数或计算过大NVLink / NVSwitch每层 AllReduce
Sequence Parallelism序列维度中的非 attention 部分降低 LayerNorm、Dropout 等激活占用通常要配合 TPAllGather / ReduceScatter
Context Parallelismattention 的序列维度让长上下文 attention / KV 不必全压在单卡高速 GPU-GPU 或跨节点互联环形 KV 传递 / All-to-All

Megatron-LM 风格的 SP 首先要解决一个容易被忽略的问题：即便已经做了 TP，激活也不一定真的被切小。TP 主要切权重矩阵和隐藏维度上的 GEMM；但 LayerNorm、Dropout、Residual Add 这类按 token 做的操作，很多实现里仍然会在 TP 组内每张卡各自保留完整序列激活。SP 的做法是在 TP 组内部再按 sequence 维度切一刀，每张卡只保留自己那段 token 的非 attention 激活。

CP 则是另一个层级的问题：当上下文来到 128K、256K 甚至更高时，attention 本身就已经大到不能再把整条序列塞进单卡。它把 context 维度切到多张卡，每张卡只持有一段 token / context block，并通过跨卡通信逐段交换或重排 K/V。Ring Attention 更像“Q 留在本地，K/V 沿环逐跳传递”；Ulysses 一类方案更像先把 token / head 的布局重新分发，再运行 attention kernel。

flowchart TD
  A[长上下文训练压力] --> B[非 attention 激活重复]
  A --> C[attention / KV / workspace 过大]
  B --> D[SP: TP 组内切 sequence 激活]
  D --> E[AllGather / ReduceScatter]
  C --> F[CP: 切 context block]
  F --> G[Ring KV 或 All-to-All 重排]
  E --> H[更低单卡激活峰值\n更复杂通信]
  G --> H
不要混淆：SP/CP 是补“序列维度显存”短板，不是替代 DP/TP/PP。没有长序列压力时，盲目开启 CP 可能只是在增加通信成本。

分支首选方案工程边界
单卡放得下纯 DP不要过早引入 TP / PP 的额外通信和调度复杂度
状态冗余是主因ZeRO-3 / FSDP + DPcheckpoint 变成 shard 化 state dict，恢复链路先设计
单层太大TP 节点内 + DP 跨节点TP size 要整除 hidden / head，并尽量不跨慢速网络
单节点仍放不下TP + PP + DP确认 micro-batch 足够、层切分均衡、首尾 stage 不拖慢
超长上下文在原组合上叠加 SP / CP需要专门 attention 实现和序列维度通信预算
参考数量级：TP 组大小常见 2-8 卡，PP stage 常见 2-8 段，DP 组大小取决于吞吐和全局 batch，CP 组大小常从 2-4 起步并用于 128K+ context。

12. 如何把决策树落地成第一版方案

如果不想一开始就精确求最优解，可以按下面的顺序落地：

  1. 先判断单卡能不能放下完整训练副本；能放下就从纯 DP 起步。
  2. 放不下时，优先看单节点 NVLink / NVSwitch 内能否通过 TP 装下。
  3. 单节点还不够，再决定是走 TP + PP + DP，还是走 ZeRO-3 / FSDP + DP。
  4. 如果 context 已经到 128K+，把 CP 当成额外维度，而不是最后临时补救。

真实选择还要继续检查设备互联、软件栈支持、团队调试能力、checkpoint 与恢复复杂度。TP 和 CP 都高度依赖拓扑；Megatron-LM、DeepSpeed、FSDP 的能力边界不同；越复杂的混合并行越依赖经验；并行维度一多，恢复链路会一起变复杂。

flowchart LR

  B --> C[并行拓扑]
  C --> D[小规模验证]
  D --> E[吞吐 / MFU / bubble 压测]
  E --> F[checkpoint 保存与恢复演练]
  F --> G[放大到目标规模]

14. 工程建议与常见工具

  • 先用单机和小规模配置验证切分逻辑，再放大规模。
  • 任何并行策略都要同时考虑训练路径和 checkpoint / 恢复路径。
  • 当 TP / PP 已经很重时，再叠加 ZeRO / FSDP 前要先确认通信预算。
  • 决策时不要只问“能不能跑”，要问“出故障后能不能恢复”。

15. 常见误区、小结与练习

常见误区

模型并行只是“分到多张卡”
不对。它重塑了通信模式、同步点和故障处理逻辑。
流水线切得越细越高效
不对。切得太细会增加 bubble 和调度复杂度。
张量并行只要显存够就行
不对。它对互联和通信延迟极其敏感。
上了 ZeRO / FSDP 就不需要模型并行
不对。状态分片无法替代所有层级切分需求。

本章小结

并行方式解决的问题主要代价
张量并行单层参数或计算过大高频通信
流水并行整体模型太深、单卡放不下bubble 与调度复杂度
ZeRO / FSDP冗余状态过重通信、checkpoint 与恢复更复杂
Sequence / Context Parallelism长上下文激活或 KV 过大序列维度通信更重
混合并行同时解决吞吐与显存问题系统复杂度最高

练习题

  1. 为什么数据并行无法解决“模型放不下单卡”的问题？
  2. 请解释张量并行和流水并行分别在“切什么”。
  3. ZeRO Stage 1/2/3 的区别是什么？为什么它和 TP / PP 是互补关系？
  4. 如果模型已经用了 TP 和 PP，checkpoint 设计为什么还要跟着调整？
  5. 为什么 128K+ 上下文训练通常要开始讨论 Context Parallelism？
