# 第13章：特征、向量与缓存

> 进入检索、推荐、RAG 和在线特征场景后，平台管理的就不再只是模型权重，而是一整套“特征 / embedding / 索引 / 缓存”的状态系统。

> **关联章节**：本章的缓存命中、索引权限和租户隔离问题，与 [第23章](../part7-reliability-security/23-security-isolation-and-governance.md) 的安全治理直接相关；缓存层如果绕过鉴权，会把检索系统变成数据泄露面。

## 学习目标

完成本章学习后，你将能够：

1. 区分特征、embedding、向量索引和缓存的职责
2. 理解训练与在线服务之间的数据一致性问题
3. 认识向量系统中的版本、更新和权限边界
4. 学会分析缓存收益与失效风险
5. 设计一个基础的向量与特征治理方案

## 正文内容

### 13.1 为什么这一层越来越重要

很多现代 AI 系统并不是“一个模型吃原始输入直接输出结果”这么简单。
它们常常还会依赖：

- 在线特征
- embedding 向量
- 向量检索
- reranker 特征
- 多层缓存

这意味着，平台不仅要管理模型，还要管理围绕模型运行的一整套状态。

### 13.2 特征、embedding、向量索引分别是什么

#### 特征

通常是结构化或半结构化输入，可能来自：

- 用户画像
- 商品属性
- 实时行为统计
- 业务上下文

#### Embedding

是把文本、图片、文档等映射到向量空间后的表示。
它通常由某个特定模型版本生成。

#### 向量索引

是为了高效近邻检索而组织的结构，可能包含：

- 向量本身
- 文档 ID
- 元数据过滤条件
- 分区与分片信息

它们之间的关系非常紧密：

> embedding 来自模型，索引依赖 embedding，缓存又依赖索引和访问模式。

### 13.3 一致性问题为什么难

现实中常见的错误不是“系统挂了”，而是“不一致”：

- 训练使用的是一套特征定义，线上使用的是另一套
- embedding 模型更新了，但索引没重建
- 文档已经删除，但向量索引还保留旧记录
- cache 命中了旧数据，导致线上结果滞后

这种问题最麻烦的地方在于：

- 服务表面看起来是正常的
- 指标可能也不立刻异常
- 但模型质量会逐步漂移

### 13.4 向量系统里的版本管理

一个向量索引至少应该绑定：

- embedding 模型版本
- 文档 / 数据版本
- chunk 规则版本
- 构建时间
- 构建任务 ID

例如：

```yaml
vector_index:
  name: docs-prod
  embedding_model: text-embed-v4
  source_dataset: kb-2026-04-10
  chunk_policy: title-paragraph-v2
  build_job: reindex-20260410-003
```

没有这些信息时，RAG 与检索系统的问题几乎无法可靠定位。

### 13.5 向量数据库怎么选

向量数据库的核心差异，不在“能不能存 embedding”，而在索引类型、过滤能力、部署模式、更新方式和可运营规模。选型时要同时看六个维度：

- 数据规模：万级、百万级、十亿级对应完全不同的索引和分片策略
- 查询 QPS：离线检索、交互式问答、高并发推荐召回的瓶颈不同
- 更新频率：按天批量、分钟级增量、秒级写入会影响索引构建方式
- 过滤条件：租户、权限、时间、业务标签等 metadata filter 是否是强需求
- 延迟目标：P50 体验、P95 / P99 稳定性和 tail latency 治理成本
- 运维能力：团队是否能承担分片、压缩、备份、扩容、版本升级和故障恢复

| 方案 | 部署模式 | 典型规模 | 适合场景 | 工程边界 / 失败条件 |
|------|----------|----------|----------|----------------------|
| FAISS / 本地索引 | 嵌入式 / 单机 | 万级到百万级 | 离线评测、本地 RAG、小流量内部工具 | 不适合多租户权限、频繁增量、跨节点扩展和高可用服务 |
| Chroma | 本地 / 单机 | 千级到百万级 | Demo、教学实验、RAG 原型 | 规模、并发和运维治理开始变复杂时应迁移 |
| pgvector | PostgreSQL 扩展 | 万级到千万级 | 已有 PG 团队、中小规模检索、需要事务一致性 | 高 QPS、复杂 ANN 调优、海量向量和重过滤会压垮主库 |
| Milvus | 自托管 | 百万到十亿级 | 自建检索平台、海量文档库、多索引类型探索 | 需要较强运维能力；小团队容易被集群、分片和升级成本拖住 |
| Qdrant | 自托管 / 托管 | 十万到亿级 | 过滤条件重、追求性能和可控性的服务 | 超大规模分片和复杂混合搜索需要额外架构设计 |
| Weaviate | 自托管 / 托管 | 十万到亿级 | schema 管理、知识库、RAG 原型到中规模服务 | 对极致低延迟或极简存储模型的场景可能偏重 |
| 云向量库 / Pinecone | 托管服务 | 百万到亿级以上 | 快速上线、运维人手少、业务优先验证 | 成本、数据驻留、厂商锁定和高级调优空间是主要边界 |
| Elasticsearch / OpenSearch hybrid | 自托管 / 托管 | 百万到亿级 | 关键词强、过滤强、需要 BM25 + 向量混合搜索 | 纯向量海量召回未必最省成本；ANN 参数和集群负载要单独压测 |

可以把选择压缩成一条决策路径：

```text
先判断规模：
  < 100 万向量，低 QPS，单团队使用 -> FAISS / Chroma / pgvector
  100 万到 1 亿向量，生产 RAG -> Qdrant / Weaviate / Milvus / 云向量库
  > 1 亿向量或多租户平台 -> Milvus / 云向量库 / 分片化 OpenSearch hybrid

再判断检索形态：
  强关键词、强过滤、审计查询多 -> Elastic / OpenSearch hybrid
  纯语义召回为主，过滤较轻 -> 专用向量库
  已有 PG 且规模可控 -> pgvector

最后判断组织能力：
  没有搜索 / 存储 SRE -> 优先云向量库
  需要数据驻留、深度调参、可控成本 -> 自托管 Milvus / Qdrant / Weaviate
```

一个常见失败模式是只按 benchmark QPS 选型，却忽略权限过滤、更新频率和 P99。RAG 系统里真正压垮平台的，往往不是“查不到向量”，而是“高选择性过滤后召回不足”“索引重建追不上数据更新”“缓存命中绕过了权限边界”。

### 13.6 ANN 搜索与距离度量

精确搜索最直接，但向量规模一旦达到千万级，平台通常就会转向 ANN（Approximate Nearest Neighbor）索引，用可控召回损失换更低延迟和更低成本。

| 方法 | 核心思路 | 优势 | 代价 | 适用判断 |
|------|----------|------|------|----------|
| 精确搜索 | 全量比较所有向量 | 召回最准 | 延迟和成本随规模快速增长 | 小规模、离线评测、作为 ANN 召回基线 |
| HNSW | 图索引近邻跳转 | 延迟低、召回高 | 内存占用较大，构建和更新成本较高 | 百万到亿级、交互式 RAG、内存预算充足 |
| IVF | 先粗分桶，再桶内搜索 | 易扩展到大规模数据 | 召回依赖聚类质量和 probe 参数 | 大规模数据、可接受调参和轻微召回损失 |
| PQ | 压缩向量后近似比较 | 显著节省内存 | 精度损失更明显，调试复杂 | 十亿级或内存受限场景，通常与 IVF 组合 |

距离度量的选择也会影响效果与实现：

| 度量 | 常见用途 | 选型提示 |
|------|----------|----------|
| 余弦相似度 | 文本 embedding 最常见 | 适合只关心方向接近程度 |
| L2 距离 | 视觉、几何类向量 | 适合向量模长本身有意义时 |
| 内积 | 推荐、召回打分 | 常用于未归一化向量或 MIPS 场景 |

平台上更重要的不是追求单一最好算法，而是明确三件事：可接受的召回率下限、目标延迟窗口、索引可承受的内存成本。HNSW、IVF、PQ 本质是在三角权衡中移动：

| 优先目标 | 常见选择 | 需要付出的代价 |
|----------|----------|----------------|
| 召回率和低延迟 | HNSW，提高 efSearch / 图连接数 | 内存更高，构建更慢，更新更贵 |
| 大规模和可分片 | IVF，提高 nprobe 或分区质量 | 召回依赖聚类，参数不当会漏召 |
| 低内存和低存储成本 | PQ / IVF-PQ | 排序精度下降，通常需要 rerank 修正 |

粗略决策是：百万级以内先用精确搜索或 HNSW 建基线；百万到亿级优先 HNSW 或 IVF，看内存和延迟目标；十亿级或内存压力明显时再引入 PQ，并用更大的候选集和 reranker 抵消压缩损失。

### 13.7 缓存在这里到底缓存什么

缓存不只是普通意义上的“把结果存一下”，在 AI 系统里常见的缓存包括：

- 在线特征缓存
- embedding 结果缓存
- 检索结果缓存
- 文档元数据缓存
- prefix cache / KV Cache

缓存的收益通常是：

- 更低延迟
- 更少重复计算
- 更低下游压力

代价通常是：

- 新鲜度下降
- 版本一致性变难
- 权限边界更复杂

### 13.8 Chunking 策略会改变检索质量

在 RAG 场景里，切分规则会直接影响索引规模、召回粒度和后续生成质量。

| 策略 | 优势 | 风险 | 适用场景 | 失败信号 |
|------|------|------|----------|----------|
| 固定长度切分 | 实现简单，吞吐稳定，索引规模可预测 | 可能截断语义边界 | 早期原型、结构松散文档 | 命中文本经常缺前后文，答案引用半句话 |
| 段落 / 句子级切分 | 更贴近原始结构，可保留标题和层级 | 长度差异大，短段落噪声多 | 文档排版规整的知识库 | 长段落召回后超上下文，短段落缺实体解释 |
| 语义级切分 | 检索相关性通常更好，边界更自然 | 构建成本更高，规则更复杂 | 高质量 RAG、问答系统 | 切分模型不稳定导致重建频繁、线上结果漂移 |

chunk 大小不是越小越好。chunk 太小，召回更细但上下文不完整，索引行数和 rerank 成本上升；chunk 太大，单条召回包含更多噪声，LLM 上下文预算被浪费。工程上常见做法是先用 300-800 token 的 chunk 建基线，再根据问答日志调节；相邻 chunk 可以保留 10%-20% overlap，用来减少边界信息丢失，但 overlap 会线性增加索引规模和重复召回。

RAG 平台应把 chunk 规则写成可版本化配置，而不是散落在 ingestion 脚本里：

```yaml
chunk_policy:
  id: title-paragraph-v2
  max_tokens: 600
  overlap_tokens: 90
  split_order: [heading, paragraph, sentence]
  keep_metadata: [doc_id, title, section, acl, updated_at]
```

从平台角度看，chunk policy 应视为索引版本的一部分，因为它一变，召回结果和缓存命中模式都会跟着变。

### 13.9 增量更新 vs 全量重建

索引更新不是永远都能做增量。更稳妥的判断方式如下：

| 场景 | 更适合的策略 | 原因 | 注意事项 |
|------|--------------|------|----------|
| 文档少量新增或删除 | 增量更新 | 写入成本低，业务中断小 | 删除要同步清理向量、元数据和检索缓存 |
| 元数据更新 | 通常增量 | 不改变向量语义，只改变过滤或展示字段 | ACL、租户、可见性字段必须立即生效 |
| embedding 模型变更 | 全量重建 | 向量空间整体变化，旧索引不可比 | 需要双索引灰度和召回质量对比 |
| chunk 规则变更 | 全量重建 | 文档边界变化会影响全部召回 | 旧 chunk 的缓存结果不能继续复用 |
| 大规模脏数据修复 | 视比例决定，但通常倾向全量 | 增量修补容易留下历史碎片 | 修复比例高于阈值时直接重建更可控 |
| 索引算法或距离度量变更 | 全量重建 | 索引结构和排序含义变化 | 先用离线 golden queries 做回归 |

可以把它理解为一个平台判断题：当“向量含义”变了，就不要试图只修局部。

生产系统通常用双索引过渡：新索引在后台构建，构建完成后用一组固定查询集比较召回率、延迟、权限过滤和答案质量，再按租户或流量比例切换。切换后还要保留旧索引一段时间，便于回滚和解释线上质量波动。

### 13.10 混合搜索

很多生产系统不会只做纯向量搜索，而是把关键词检索和向量检索并联，再做 rerank。

```text
query
  -> BM25 / keyword retrieval
  -> vector retrieval
  -> RRF / merge
  -> cross-encoder rerank
  -> top-k context
```

这种混合架构的价值在于：关键词检索补精确命中，向量检索补语义召回，RRF（Reciprocal Rank Fusion）适合把两路排序先做稳健合并，cross-encoder reranker 再负责最后的排序收敛。

召回和重排的边界要明确：

| 层次 | 目标 | 常见输入规模 | 不应该承担的职责 |
|------|------|--------------|------------------|
| 粗召回 | 快速找到可能相关的候选 | top 50-1000 | 不负责最终事实判断和复杂权限补救 |
| 合并 / 去重 | 融合 BM25、向量、业务规则 | top 50-300 | 不把明显无权或过期内容带到后面 |
| rerank | 用更贵模型做精排 | top 20-100 | 不负责扩大召回范围 |
| 上下文组装 | 控制 token、引用和顺序 | top 3-20 | 不修改文档含义或隐藏来源 |

如果 reranker 经常把低相关内容排到前面，问题未必在 reranker；也可能是 chunk 太大、候选集太小、metadata filter 过严，或 embedding 模型与查询语言不匹配。

### 13.11 RAG 工程决策路径

RAG 不是“接一个向量库”就结束。一个可运营的 RAG 平台至少要把 ingestion、embedding、索引、召回、重排、缓存和权限串成同一个版本化系统。

```text
文档进入：
  清洗 / 解析 -> chunk -> embedding -> 索引写入 -> 缓存失效

查询进入：
  改写 / 归一化 -> 权限和过滤条件 -> 召回 -> 合并 -> rerank -> 上下文组装 -> 生成

质量回路：
  golden queries -> 召回评估 -> rerank 评估 -> 答案评估 -> 索引或策略灰度
```

关键判断如下：

| 决策点 | 推荐做法 | 失败条件 |
|--------|----------|----------|
| embedding 模型版本 | 固定模型、tokenizer、预处理版本，并写入索引元数据 | 模型升级后旧向量和新向量混查，排序含义失真 |
| 冷热数据 | 热数据放高性能索引和短 TTL 缓存，冷数据可用低成本索引或归档重建 | 所有数据同等服务导致成本过高，或冷数据召回延迟不可控 |
| 检索缓存 | cache key 包含 query、过滤条件、权限上下文、索引版本 | 文档删除、ACL 变化后仍命中过期结果 |
| embedding cache | key 包含输入内容、模型版本、预处理版本 | 复用旧模型向量，导致召回漂移 |
| 索引重建 | 模型、chunk、距离度量、清洗规则变化时走全量重建 | 用增量补丁修语义变化，留下不可解释的混合索引 |
| 召回 topK | 先保证召回覆盖，再交给 rerank 压缩 | topK 太小导致 reranker 没有正确答案可排 |
| rerank 边界 | reranker 只在候选集内精排，候选生成仍靠召回层 | 期待 reranker 弥补漏召，线上质量随机波动 |
| Prefix cache | 只缓存严格相同的静态前缀或完整授权上下文 | 不同租户、不同 ACL、不同检索结果共享同一前缀 |

冷热数据还会影响索引更新：热文档适合分钟级增量和短 TTL 检索缓存；冷文档适合批量重建、低频压缩索引和更长缓存。不要让冷数据的重建任务挤占热数据写入，也不要让热数据为了追求全量一致性而长期等待离线批处理。

### 13.12 权限问题为什么容易被忽略

在 RAG、检索、企业知识问答场景里，一个常见风险是：

- 用户无权访问某文档
- 但缓存或索引没有正确执行权限过滤
- 最终回答引用了本不该暴露的信息

这说明向量与缓存系统不是单纯性能组件，还承担了安全边界。

### 13.13 Prefix Cache 和 KV Cache 不是一回事

它们都会减少重复计算，但作用层次并不相同：

| 对象 | 缓存的是什么 | 更常见于哪一层 | 典型命中条件 | 主要风险 |
|------|--------------|----------------|--------------|----------|
| Embedding cache | 文本 / 图片到向量的编码结果 | 检索与特征层 | 输入内容、模型版本、预处理版本相同 | 模型升级后旧向量误用 |
| Retrieval cache | query 对应的召回结果 | 检索编排层 | query、过滤条件、权限上下文相同 | 文档变更后结果过期 |
| Prefix cache | 已算过的公共前缀激活 / KV 状态 | LLM serving 入口附近 | system prompt、模板、工具定义、tokenizer 结果一致 | 错把不同租户或不同工具上下文命成同一份前缀 |
| KV Cache | 单请求 decode 过程中的历史 key/value | LLM decode 运行时 | 同一个活跃请求持续生成 | 显存占用、碎片和回收复杂 |

平台上最容易混淆的是后两者：
prefix cache 更像“跨请求复用公共前缀”，KV Cache 更像“单请求内复用历史状态”。前者关注命中键设计，后者关注显存生命周期管理，后续会在 [第15章](../part5-serving-infra/15-batching-scheduling-and-kv-cache.md) 继续展开。

如果前缀足够稳定，尤其是在 system prompt / 模板高度重复的场景里，prefix cache 才常有机会节省约 30%-50% 的 prefill 计算。但这类收益高度依赖请求分布和调度器命中策略：相同前缀的请求应尽量被路由到同一实例或同一缓存域，否则前缀虽然相同，缓存却散落在不同副本上。

如果这段前缀里已经包含：

- 检索结果
- 用户画像或会话态
- policy / safety 条件
- 同租户内不同用户的授权差异

那么这些维度也必须进入 cache key；如果做不到，就宁可只缓存严格静态的公共前缀，而不要做“看起来命中率更高、实际越权风险更高”的共享。

### 13.14 在线特征为什么容易出现 point-in-time 错误

在线特征最危险的问题，往往不是缺数据，而是“拿到了不该在那个时刻看到的数据”。

| 场景 | 错误表现 | 常见补救 |
|------|----------|----------|
| 训练样本回放 | 训练时读到了样本时间之后才产生的统计特征 | 以样本事件时间做特征快照 |
| 实时聚合延迟 | 线上特征比训练定义晚到几分钟甚至几小时 | 明确 freshness SLA，并允许降级到较旧窗口 |
| 回填修数 | 离线修正后没同步线上 cache / feature store | 回填完成后触发 cache 失效与索引重建 |
| 多模态预处理升级 | 图片裁剪、OCR 或 tokenizer 变化，但 key 没变 | 把预处理版本写进特征和缓存 key |

对平台来说，point-in-time correctness 不是研究细节，而是特征服务的契约。如果契约不成立，后面的向量索引、缓存命中和线上质量分析都会失真。

### 13.15 工程建议

- 特征定义必须版本化
- embedding 模型变化要和索引构建一起治理
- 缓存命中不能绕过权限检查
- 在线与训练的特征含义要保持一致
- 向量索引要像模型包一样具备元数据和生命周期状态
- 向量库选型要同时看规模、QPS、更新频率、过滤条件、延迟目标和运维能力
- RAG 的 chunk、embedding、索引、缓存和 rerank 必须共享版本边界
- prefix cache 的 key 至少要覆盖模板、租户、工具定义和 tokenizer 版本；若前缀含检索结果、用户态或 policy 条件，这些授权相关维度也必须进入 key
- 共享前缀场景里，路由层应尽量把相同前缀请求送到同一实例，否则 prefix cache 的理论收益很难兑现
- 在线特征要明确 freshness SLA 与 point-in-time 契约
