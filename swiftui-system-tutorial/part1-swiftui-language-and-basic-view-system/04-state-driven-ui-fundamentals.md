# 第4章：状态驱动界面的第一原则

## 为什么现在讲状态

到这里，你已经知道：

- `App` 在声明应用结构
- `View` 在通过组合描述界面
- 基础组件在表达文本、图标和动作入口

但你还没有真正回答这个问题：

**界面为什么会变化？**

如果这一步讲不清，后面所有交互都会退化成“点一下就临时改点东西”。SwiftUI 最核心的稳定性来源，恰恰不是控件多高级，而是：**状态变化驱动界面描述重算。**

## 从一个较弱起点开始：把界面变化写成手工 patch

最弱的 UI 思维通常是这样的：

1. 用户点了按钮
2. 我去把某块文案改掉
3. 我去让某块区域显示 / 隐藏
4. 我再顺手改一下别的地方

在命令式 UI 里，这种思路很常见；在 SwiftUI 里，如果你还这么想，代码会迅速变得又能跑又说不清。比如你可能写出这种思路：

```swift
Button("Toggle Filter") {
    // 想象中这里“直接改界面”
}
```

问题在于，真正应该变化的不是“界面片段”，而是**驱动界面的状态**。例如：

- 当前是否只显示最近活跃白板
- 当前是否正在创建新白板
- 当前选中了哪一个白板

只要这些状态建模清楚，UI 就会自然跟着变。否则你写的永远是局部补丁。

## `@State`：当前 View 自己拥有的本地可变状态

SwiftUI 最基础的状态工具是 `@State`。它适合放那些：

- 由当前 View 自己拥有
- 生命周期主要绑定当前 View
- 不需要跨很多层共享

例如 `BoardFlow` 首页如果临时加入一个本地筛选开关：

```swift
@State private var showOnlyLargeBoards = false
```

这个状态就很适合留在首页或某个局部 view 内。因为它表达的是：

- 当前这块界面的显示偏好
- 它不是整个 app 的跨层真源
- 它也不是文档持久化的一部分

这就是本教程会反复强调的状态所有权意识：**不是所有会变的数据都该往同一个地方塞。**

## 更强的方向：先想状态归谁，再想界面怎么跟着变

写 SwiftUI 时，一个特别稳的思考顺序是：

1. 这份状态是什么？
2. 谁拥有它？
3. 谁允许修改它？
4. 哪些 View 只是消费它？
5. 变化之后哪些界面描述会一起跟着重算？

对 `BoardFlow` 首页来说，哪怕只是最基础版本，也已经能区分几类状态：

- 文档内容：白板标题、白板列表
- 本地 UI 状态：某个筛选开关、某段临时输入
- 派生状态：例如“是否存在最近白板”“是否应该显示空态文案”

派生状态尤其重要。它通常不应该再被单独存一份，而应从已有事实推出。例如：

```swift
let hasBoards = !document.boards.isEmpty
```

这类值如果再被你复制成另一份可变状态，后面就会开始真假难辨。

## SwiftUI 的“刷新”本质上是描述重算，不是你手工重绘

为什么说 SwiftUI 状态驱动的关键不在于“有个包装器语法”，而在于你理解了刷新机制？

因为一旦驱动 `body` 的状态变化，SwiftUI 会重新评估相关描述，并决定哪些界面结果要更新。你真正写的是：

- 当前状态
- 由当前状态导出的界面描述

而不是：

- 找到某个 label
- 改掉它的文字
- 再刷新一下那块视图

如果你一直把 SwiftUI 想成“自动帮我调用 reload 的框架”，那你还是站在命令式老思路里，只是披了声明式语法外衣。

## `BoardFlow` 在本章的落点

虽然 starter 当前还保持很小，但本章之后你应该已经能用状态视角解释它：

- `document` 不是 UI 随手拼出来的文案集合，而是驱动首页的输入事实
- 首页以后如果出现筛选、搜索、选择、弹出表单，这些都应先想状态归属
- View 的任务是消费状态并表达结构，而不是直接藏业务补丁

这一步很关键。因为 Part 2 一进入表单、列表、导航和可观察模型，如果状态意识不牢，教程很快又会退回“组件会用，但系统会乱”的老路。

## 双语关键词

- state：状态
- local state：局部状态
- derived state：派生状态
- source of truth：事实源
- recomputation：重算
- state ownership：状态所有权

## 常见错误

### 1. 把界面变化理解成“手工改 UI”

这会让你永远在补丁层思考，而不是在状态层思考。

### 2. 把任何会变的数据都塞进 `@State`

`@State` 适合本地拥有状态，不是万能状态仓库。

### 3. 派生值也额外存成可变状态

能从事实推出来的，就别再制造第二份事实。

### 4. 不区分文档状态和临时 UI 状态

对 `BoardFlow` 这种后面要变成文档型创作工具的项目，这个区分越早越重要。

## English Recap

SwiftUI updates do not come from manual UI patching. They come from state changes that cause the relevant view descriptions to be re-evaluated. In `BoardFlow`, the key habit is to decide who owns each piece of state before deciding how the UI should react.
