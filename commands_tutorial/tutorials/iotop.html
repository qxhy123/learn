iotop 深度教程：AI Infra 场景下的进程级 IO 观测与排障

iotop 是 Linux 上按进程/线程查看磁盘 IO 的交互式工具。它特别适合 AI Infra 排障：判断训练卡顿到底是 dataloader 读不动、checkpoint 写爆盘、swap 触发、日志过量、还是某个容器/后台任务抢占了存储带宽。本教程从内核 IO 记账模型讲起，覆盖权限、列含义、交互模式、batch 采样、容器 caveat、与 iostat/pidstat/lsof 的边界，以及面向训练任务的实战流程。

AI Infra进程级 IO读写带宽SWAPINIO waitdataloadercheckpointbatch 模式容器限制生产排障
一句话理解： iotop 不是看“哪块盘忙”，而是看“哪个进程正在造成块设备 IO 压力”；它把 Linux task IO 记账以类似 top 的方式实时呈现。
最重要原则： 先用只读观测定位进程，再结合 iostat 看设备饱和、pidstat 做时间序列、lsof 找文件路径；不要只凭瞬时带宽就杀进程或调整训练参数。

1. iotop 解决什么问题

AI 训练或推理服务出现吞吐下降时，GPU 利用率低不一定是 GPU 问题。常见根因包括样本文件读取慢、远程文件系统抖动、checkpoint 同步写入、日志或 tensorboard 事件文件暴增、数据预处理进程占满盘、以及内存不足导致 swap。iotop 的价值是把“系统 IO 忙”拆到进程/线程维度。

适合回答
哪个 PID/TID 正在读写磁盘？训练进程是不是读数据读不动？checkpoint 写入是否压住整机？
不适合单独回答
具体哪块盘饱和？队列深度是多少？文件系统延迟多高？这些要结合 iostat、fio、存储监控。
AI Infra 视角
先把 IO 压力归因到进程，再映射到 job、container、dataset、checkpoint 目录或后台维护任务。
# 典型入口：只显示正在发生 IO 的任务
sudo iotop -o

# 非交互采样 5 次，每秒一次，便于贴到工单或日志
sudo iotop -b -o -d 1 -n 5
边界提醒： iotop 显示的是内核能归因到 task 的 IO 记账。页缓存命中、网络文件系统、某些 overlay 层和异步写回可能让读数与应用体感不完全一致。

心智模型：iotop 是进程归因工具；设备是否饱和、文件路径是什么、容器是谁，需要用其他工具补齐。

2. 安装、版本与环境前提

多数发行版软件仓库提供 iotop。传统实现依赖 Python 与 taskstats；部分系统还提供 iotop-c，是 C 语言重写版本，启动更轻、兼容性可能不同。生产环境以发行版包为准，避免在节点上随意安装未知来源脚本。

系统安装命令说明
Debian/Ubuntusudo apt-get install iotop常见云主机和训练节点可直接安装。
RHEL/CentOS/Rockysudo dnf install iotop老系统可能使用 yum 或需要 EPEL。
Archsudo pacman -S iotop也可能提供 iotop-c 包。
容器镜像不建议只在业务容器内安装通常需要宿主机权限和完整 /proc 视图。
# 查看版本和帮助
iotop --version
iotop --help

# 如果系统提供 iotop-c，也先确认参数兼容性
iotop-c --help 2>/dev/null || true
环境前提： iotop 需要 Linux 内核的 per-task IO accounting 支持，并通常要求 root 权限或足够 capability。

3. 权限与内核配置

运行 iotop 最常见失败原因是权限不足或内核未开启任务 IO 记账。AI 集群上，普通用户经常只能看到自己的进程，无法观察整机租户、容器 runtime、缓存预热任务或后台同步进程。

检查项命令期望
是否 rootid -u0 可看到完整系统视图。
内核配置grep TASK_IO_ACCOUNTING /boot/config-$(uname -r)CONFIG_TASK_IO_ACCOUNTING=y。
进程 IO 文件head /proc/self/io能看到 read_bytes、write_bytes 等字段。
容器可见性ls -ld /proc/1 /proc/self容器内可能只看到本命名空间。
# 推荐以 sudo 运行，先只读观察
sudo iotop -o

# 如果报错，可以先检查内核是否暴露 /proc IO 记账
cat /proc/self/io

# 常见内核配置检查
zgrep TASK_IO_ACCOUNTING /proc/config.gz 2>/dev/null || \
  grep TASK_IO_ACCOUNTING /boot/config-$(uname -r)
权限安全： 不要为了运行 iotop 给业务容器长期授予 --privileged。更安全的做法是在宿主机、调试节点或受控的 node debug 会话中观测。

4. 界面列含义：DISK READ、DISK WRITE、SWAPIN、IO

iotop 的列不是“累计文件大小”，而是采样窗口内按 task 归因的速率和等待占比。理解每列含义，才能避免把缓存、异步写回或短暂尖峰误判为稳定瓶颈。

列含义AI Infra 解读
TID/PID任务或进程 ID，视线程显示模式而定。多 worker dataloader 常表现为多个 Python 子进程/线程。
PRIOIO 调度优先级或 best-effort 类别。通常不是第一排障入口，除非确认 IO scheduler 支持且策略被修改。
USER进程所属用户。可快速区分训练用户、root 后台任务、日志代理或容器 runtime。
DISK READ采样窗口内归因到该 task 的读速率。dataloader 或预处理任务高读速率，GPU 利用低，常指向输入管线。
DISK WRITE采样窗口内归因到该 task 的写速率。checkpoint、日志、缓存生成、数据解压可能造成写峰值。
SWAPIN任务等待 swap-in 的时间比例。训练内存超限、page cache 被挤压、batch 太大时要警惕。
IO任务等待 IO 完成的时间比例。高 IO% 且 GPU 空闲，说明任务经常阻塞在存储路径上。
COMMAND命令行。映射到训练脚本、DataLoader worker、压缩/同步/日志进程。
读数解释： DISK WRITE 高不一定表示物理盘立即同步写入；page cache 和 writeback 会改变时间归因。对存储设备饱和度要再看 iostat -xz。

流程图：交互式 iotop 的一次排障循环

交互式排障不要停在“看到一个 PID 很高”；要把 PID 连接到文件路径、设备、job/container 和业务阶段。

5. 交互式使用与常用快捷键

最常用启动方式是 sudo iotop -o：只显示当前有 IO 的任务，降低噪声。不同版本快捷键可能略有差异，生产节点上可以按 ? 查看帮助。

操作作用使用建议
sudo iotop显示所有任务。适合初次观察，但噪声较多。
sudo iotop -o只显示有 IO 的任务。AI 节点排障首选。
Left/Right切换排序列。在读、写、IO% 之间快速切换。
r反转排序。确认低值/高值边界。
o切换只显示活跃 IO。观察短时尖峰时很有用。
p切换线程/进程聚合显示。多进程 dataloader 需要留意 TID/PID 语义。
q退出。只读观测，无需清理。
# 2 秒刷新一次，降低终端抖动
sudo iotop -o -d 2

# 只观察某个用户的训练任务
sudo iotop -o -u trainuser

6. 只看活跃 IO：定位谁在读写

-o 是日常排障最实用的参数。训练节点上进程很多，直接看全量列表会被 idle 进程淹没。先用 -o 找活跃 PID，再用 ps、lsof、readlink /proc/PID/cwd 做映射。

# 找出当前正在制造 IO 的任务
sudo iotop -o -d 1

# 记录 PID 后，看完整命令行
ps -fp 12345
tr '\0' ' ' < /proc/12345/cmdline; echo

# 看进程工作目录和打开的文件
readlink -f /proc/12345/cwd
sudo lsof -p 12345 | head -50
读高
关注 dataset 路径、解压/预处理、cache miss、远程 FS、随机小文件读取。
写高
关注 checkpoint、日志、样本缓存生成、临时目录、对象存储同步 agent。
IO% 高
任务经常阻塞等待 IO，可能拖低 GPU pipeline。
瞬时尖峰
单次刷新不够，要用 batch 模式采多次或结合 pidstat -d。

7. AI 训练 dataloader 读瓶颈

Dataloader 读瓶颈的典型表现是 GPU 利用率周期性掉到低位，训练 step time 抖动，iotop 中 Python worker、数据解码进程或缓存预热进程持续高读速率/高 IO%。

观察流程

# 1. 训练运行时观察有 IO 的任务
sudo iotop -b -o -d 1 -n 20 | tee /tmp/iotop.train.log

# 2. 找到高 READ 的 PID 后映射到命令
ps -fp 12345
readlink -f /proc/12345/cwd

# 3. 看它正在打开哪些数据文件
sudo lsof -p 12345 | grep -E '/dataset|/data|\.tar|\.parquet|\.jpg|\.npy' | head
现象可能原因验证方式常见修复方向
多个 worker 低速随机读海量小文件、元数据开销高。lsof 看文件类型，iostat -xz 1 看 await。打包为 tar/webdataset/LMDB，预热本地 NVMe。
读速率很高但 GPU 仍空闲解码/CPU transform 慢，不是纯 IO。同时看 CPU、py-spy、dataloader profiling。增加 worker、优化 transform、缓存解码结果。
远程挂载读抖动NFS/对象存储网关/分布式 FS 抖动。看网络、挂载客户端日志、存储监控。本地缓存、分片、错峰预热。
只有 rank0 读高数据分片或采样策略不均衡。按 PID 映射 rank/local_rank。修正 sampler、shard 规划和数据布局。
判断技巧： 如果 iotop 读高但 iostat 设备不忙，可能是页缓存或网络文件系统路径；如果两者都高且 await 升高，才更像块设备瓶颈。

8. checkpoint 与日志写瓶颈

大模型训练经常周期性写 checkpoint。写入阶段如果阻塞训练主线程，iotop 会看到 Python、torchrun、deepspeed、rsync、tar、压缩进程或日志 agent 的 DISK WRITE/IO 突增。

# 采样覆盖至少一个 checkpoint 周期
sudo iotop -b -o -d 2 -n 120 | tee /tmp/iotop.ckpt.log

# 观察 checkpoint 目录增长
watch -n 2 'du -sh /mnt/nvme/exp/checkpoints 2>/dev/null; ls -lh /mnt/nvme/exp/checkpoints | tail'

# 映射写文件
sudo lsof -p 12345 | grep -E 'checkpoint|ckpt|\.pt|\.safetensors|events.out'
同步 checkpoint
训练 step 卡住，主进程写高。优先评估异步保存、减少保存频率、分片和本地落盘。
日志过量
event 文件、JSONL、debug dump 写高。检查日志级别、flush 频率和 tensorboard 图片/直方图。
后台同步
rsync、rclone、对象存储 sidecar 抢 IO。需要限速、错峰或调整同步策略。
不要直接删除： 看到 checkpoint 写高不代表可以删文件。先确认训练恢复策略、保留策略、rank 写入方式和实验追踪要求。

信息图：SWAPIN、IO% 与训练吞吐的关系

SWAPIN 是内存压力信号，IO% 是等待 IO 的时间信号；两者都可能通过 dataloader 链路让 GPU 挨饿。

9. SWAPIN、IO wait 与内存压力

SWAPIN 高说明任务等待换入被换出的内存页。AI 训练中，这往往来自 batch 太大、DataLoader worker 太多、CPU cache/样本缓存过大、多个 job 共享节点、或 page cache 与匿名内存竞争。

# iotop 看到 SWAPIN 或 IO% 高后，立刻看内存和 swap
free -h
vmstat 1 10

# 看目标进程内存
grep -E 'VmRSS|VmSwap|Threads' /proc/12345/status

# 如果是 cgroup v2，可查看容器/作业内存事件
cat /sys/fs/cgroup/<path>/memory.current 2>/dev/null
cat /sys/fs/cgroup/<path>/memory.events 2>/dev/null
信号组合倾向判断下一步
SWAPIN 高 + free 显示 swap 使用高内存不足或 cgroup 过紧。降 batch/worker/prefetch，增加内存，检查泄漏。
IO% 高 + iostat await 高设备或远程存储延迟高。迁移数据、限速写入、调整并发。
IO% 高但设备不忙可能是锁、网络 FS、容器层或应用级等待。结合 strace、应用日志、存储客户端指标。
操作安全： 不要在共享训练节点上随意执行 swapoff -a 或清 page cache。那是全局破坏性操作，可能让其他任务 OOM 或抖动。

10. batch 模式与可复现采样

交互式界面适合现场观察，batch 模式适合留证据、写入工单、对齐训练 step timeline。核心参数是 -b 非交互、-d 刷新间隔、-n 采样次数、-o 只输出活跃 IO。

# 每秒采样一次，共 60 秒
sudo iotop -b -o -d 1 -n 60 | tee /tmp/iotop.$(date +%Y%m%d-%H%M%S).log

# 每 5 秒采样一次，覆盖长 checkpoint 周期
sudo iotop -b -o -d 5 -n 120 > /tmp/iotop.long.log

# 只看指定用户，减少多租户节点噪声
sudo iotop -b -o -u trainuser -d 1 -n 30

轻量解析示例

# 找出日志中出现频率最高的命令片段，适合快速归因
awk '/K\/s|M\/s|G\/s/ {cmd=$0; sub(/^.*[0-9.]+ [KMG]\/s[[:space:]]+[0-9.]+ [KMG]\/s[[:space:]]+[0-9.]+ %[[:space:]]+[0-9.]+ %[[:space:]]+/, "", cmd); print cmd}' /tmp/iotop.long.log | \
  sort | uniq -c | sort -nr | head
采样建议： 覆盖完整业务周期。Dataloader 问题通常要覆盖多个 step；checkpoint 问题至少覆盖一次保存；后台同步问题要覆盖同步窗口。

11. 容器、Kubernetes 与命名空间 caveat

在容器内运行 iotop 经常得到不完整视图：PID namespace 只看到容器内进程，权限不足无法访问 taskstats，overlayfs 写入归因复杂，宿主机 page cache/writeback 让读数和容器内文件路径不完全一致。AI 平台排障时，优先在宿主机或 node debug 环境中观察。

场景风险建议
普通业务容器内跑 iotop看不到宿主机其他进程，权限常不足。在宿主机或受控 debug pod 中运行。
Kubernetes podPID、mount、cgroup 命名空间影响映射。用 kubectl debug node 或平台侧节点工具。
overlayfs容器层写入与宿主机实际路径不同。结合 container runtime、crictl inspect、cgroup 路径。
多租户节点只看容器内部会漏掉邻居任务。宿主机按 PID/cgroup 映射到 pod/job。
# 宿主机上从 PID 找 cgroup，映射到容器或 pod
cat /proc/12345/cgroup

# containerd 环境可结合 crictl 查询
sudo crictl ps | head
sudo crictl inspect <container-id> | grep -E 'pid|sandbox|io.kubernetes'

# systemd/cgroup 视图
systemd-cgls --no-pager | head -80
平台建议： 如果团队频繁排 AI 作业 IO，最好把 iotop batch 采样、iostat、cgroup 映射封装成只读诊断脚本，而不是让每个用户进宿主机手工操作。

iotop 是入口，不是终点。设备级、文件级、时间序列和目录增长需要其他工具补证。

12. iotop vs iostat/pidstat/lsof/du

工具回答的问题强项盲区
iotop哪个进程/线程正在制造 IO？进程归因直观，适合现场排障。不直接告诉你设备队列、具体文件路径、长期趋势。
iostat -xz哪块设备饱和，延迟多高？设备级利用率、await、队列深度。不能直接归因到进程。
pidstat -d某些 PID 的 IO 随时间如何变化？时间序列清晰，适合记录。现场交互归因不如 iotop 快。
lsof进程打开了哪些文件？把 PID 连接到 dataset、checkpoint、日志路径。不显示实时带宽。
du/ncdu哪个目录占空间或增长？空间排查。不代表当前 IO 压力。
strace进程系统调用卡在哪里？能看到 read/write/open/fsync 等调用。开销和噪声较高，生产慎用。
# 组合拳：进程归因 + 设备验证 + 文件路径
sudo iotop -o -d 1
iostat -xz 1
sudo lsof -p 12345 | head -80
pidstat -d -p 12345 1 20

13. 生产排障工作流

生产环境的关键不是“看到高 IO 就立刻处理”，而是形成可验证假设。下面流程适合训练节点、推理节点、数据预处理节点和共享开发机。

  1. 确认症状：GPU 利用低、step time 抖动、checkpoint 超时、节点负载高、磁盘告警。
  2. 用 sudo iotop -b -o -d 1 -n 30 采证据，记录时间窗口。
  3. 记录高 IO PID/TID、USER、COMMAND，并用 ps 映射完整命令。
  4. 用 lsof -p 或 /proc/PID/fd 找 dataset/checkpoint/log 路径。
  5. 用 iostat -xz 1 判断是否真实设备饱和。
  6. 映射到 job/container/pod/rank，确认是不是目标任务或邻居任务。
  7. 提出最小修复：限速、错峰、调 worker、改本地缓存、降低 checkpoint 频率、迁移数据。
  8. 再次采样验证，比较修复前后吞吐和 IO 指标。
输出证据模板： “在 14:03-14:04，PID 12345 python train.py 持续 DISK READ 500-800 MB/s、IO 70% 左右；lsof 指向 /mnt/nfs/dataset；同时 iostat 显示 nvme1n1 await 正常但 NFS 客户端日志有重传，因此倾向远程 FS 抖动。”

14. 常用命令模板

现场观察

# 只看活跃 IO，1 秒刷新
sudo iotop -o -d 1

# 指定用户
sudo iotop -o -u trainuser

# 拉长刷新间隔，观察 checkpoint 峰值
sudo iotop -o -d 5

可复现记录

# 30 秒证据
sudo iotop -b -o -d 1 -n 30 | tee /tmp/iotop.30s.log

# 10 分钟低频证据
sudo iotop -b -o -d 10 -n 60 | tee /tmp/iotop.10m.log

# 同步记录设备状态
(iostat -xz 1 30 > /tmp/iostat.30s.log) &
sudo iotop -b -o -d 1 -n 30 > /tmp/iotop.30s.log

进程映射

# PID 到命令、工作目录、文件
PID=12345
ps -fp "$PID"
tr '\0' ' ' < "/proc/$PID/cmdline"; echo
readlink -f "/proc/$PID/cwd"
sudo ls -l "/proc/$PID/fd" | head
sudo lsof -p "$PID" | head -80

排障图：从 iotop 异常到安全处置

安全处置原则：证据先于动作；低风险调参先于破坏性操作；共享节点上任何杀进程、删文件、关 swap 都需要明确责任边界。

15. 常见误判与安全注意事项

误判 1：把瞬时尖峰当瓶颈
单次刷新可能只是 checkpoint 或预读。用 -b -n 覆盖完整周期。
误判 2：只看 iotop 不看设备
进程读写高不等于设备饱和。用 iostat -xz 验证 await、util、队列。
误判 3：容器内读数代表整机
容器内可能看不见邻居任务和宿主机 writeback。
误判 4：SWAPIN 高只怪磁盘
SWAPIN 更多是内存压力信号，要同时看 free、vmstat、cgroup memory。
误判 5：看到日志写高就删日志
日志可能是实验追踪或审计要求。先限频、轮转、压缩或调整级别。
误判 6：高写入一定来自当前进程
异步 writeback、overlayfs 和 page cache 会改变归因边界。
高风险操作清单： kill -9 训练进程、删除 checkpoint、清理 page cache、swapoff、卸载文件系统、直接改容器 runtime 配置，都必须先确认影响范围和回滚方式。

16. 故障速查表

现象优先检查常用命令下一步
GPU 利用低，Python worker 读高dataloader、数据布局、远程 FS。sudo iotop -o、lsof -p PID优化分片、本地缓存、减少小文件随机读。
每隔 N 分钟训练卡顿checkpoint 周期。sudo iotop -b -o -d 2 -n 120异步保存、降低频率、独立写盘、限速同步。
SWAPIN 高内存超限、cgroup、worker/prefetch。free -h、vmstat 1、/proc/PID/status降内存占用、调 batch/worker、排查泄漏。
IO% 高但读写速率不高高延迟、小 IO、远程 FS、fsync。iostat -xz 1、strace -p PID降低 fsync 频率、改存储路径、联系存储侧。
容器内看不到高 IO 进程PID namespace、权限、宿主机邻居任务。cat /proc/PID/cgroup、crictl ps到宿主机或 node debug 视角排查。
磁盘空间增长快checkpoint、日志、缓存目录。du -xh --max-depth=2、lsof +L1清理策略、日志轮转、保留最近 N 个 checkpoint。

17. 练习任务

下面练习尽量在测试机或临时目录中完成，不要在共享生产节点制造大量 IO。

练习 1：制造可控读写并观察

# 在临时目录制造一个小文件，避免影响生产盘
mkdir -p /tmp/iotop-demo
dd if=/dev/zero of=/tmp/iotop-demo/blob bs=1M count=256 status=progress

# 另一个终端观察
sudo iotop -o -d 1

# 读取测试文件
dd if=/tmp/iotop-demo/blob of=/dev/null bs=4M status=progress

练习 2：batch 采样并写报告

# 采样 10 秒
sudo iotop -b -o -d 1 -n 10 > /tmp/iotop.demo.log

# 查看是否记录到 dd 或其他 IO 任务
grep -E 'dd|python|tar|rsync' /tmp/iotop.demo.log | head

练习 3：把 PID 映射到文件

# 找到 PID 后
PID=12345
ps -fp "$PID"
sudo lsof -p "$PID" | head -50
readlink -f "/proc/$PID/cwd"
练习目标： 能从 iotop 的一行输出，走到“谁、在读写什么、是否让设备饱和、是否影响训练”的完整判断链路。
