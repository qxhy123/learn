这份教程围绕 Linux 命令 tshark 展开，面向训练集群、推理服务、GPU 节点互联、存储网络、API 网关和远程无头服务器。它不是简单列参数，而是从“抓包或读取 pcap → 解码协议 → 用显示过滤器缩小问题 → 抽取字段或 JSON → 形成可复现证据”这个心智模型出发，系统讲清 CLI Wireshark、capture filter 与 display filter、-T fields、JSON、环形缓冲、远程采集、NCCL/API 调试、隐私安全以及 tshark 与 tcpdump 的边界。

一句话理解： tshark 是 Wireshark 的命令行形态：它既能在服务器上抓包，也能离线读取 pcap/pcapng，并用 Wireshark 的协议解码器和显示过滤器把网络现象转成可查询字段。

1. tshark 是什么，为什么 AI Infra 需要它

tshark 是 Wireshark 套件中的命令行分析器。相比只看连接状态的 ss、只测吞吐的 iperf3、只抓包粗看的 tcpdump，tshark 的强项是“解码”：它能把 pcap 里的二进制报文解析成 IP、TCP、TLS、HTTP、DNS、gRPC/HTTP2 等协议字段，再用显示过滤器和字段抽取形成结构化证据。

它擅长什么
远程服务器抓包、离线读取 pcap、Wireshark display filter、协议字段提取、JSON 输出、环形缓冲、批量网络证据生成。
它不擅长什么
不能替代交换机遥测、eBPF 全链路观测、应用日志、NCCL debug 日志或 GPU/RDMA 专用计数器。
AI Infra 典型问题
worker 是否连到正确 master？API 连接是否复用？TLS 握手是否失败？DNS 是否慢？NCCL 控制连接是否走错网卡？
# 查看版本和可用协议支持
tshark -v

# 列出接口
tshark -D

# 离线读取 pcap，先看前 20 个包摘要
tshark -r incident.pcapng -c 20

# 从 pcap 中抽取 TCP 会话的五元组和时间
tshark -r incident.pcapng -Y 'tcp' -T fields \
  -e frame.time_relative -e ip.src -e tcp.srcport -e ip.dst -e tcp.dstport
边界提醒： tshark 看到的是采集点上经过的包。没抓到不等于不存在，可能是接口选错、offload、镜像口方向、容器 namespace、权限或过滤条件导致。

2. 核心模型：抓包、解码、过滤、抽取、证据

tshark 的工作流可以拆成五步：选择数据来源、解码协议、应用显示过滤器、抽取字段或 JSON、形成可复现证据。现场抓包时，前两步的选择决定了后续所有分析是否可信。

抓包或读包
live capture 用 -i，离线 pcap 用 -r。两者不要混淆。
过滤和抽取
-Y 用协议字段缩小范围，-T fields 或 -T json 输出证据。
复现和审计
结论必须保留命令、采集点、过滤条件、时间窗口和字段含义。
# 同一个 pcap 可以反复离线分析
tshark -r incident.pcapng -Y 'tcp.analysis.flags'
tshark -r incident.pcapng -Y 'dns or tls.handshake'
tshark -r incident.pcapng -T fields -e frame.time_relative -e ip.src -e ip.dst

tshark 的核心价值不是“看到包”，而是把包解码成可过滤、可抽取、可审计的字段。

3. 安装、权限与版本确认

服务器上通常安装 tshark 而不是完整 GUI Wireshark。抓 live interface 需要抓包权限；离线读 pcap 通常不需要 root。生产环境建议用最小权限授予抓包能力，而不是长期以 root shell 操作。

# Debian / Ubuntu
sudo apt-get update
sudo apt-get install -y tshark

# RHEL / CentOS / Rocky / Alma
sudo dnf install -y wireshark-cli

# 确认版本、插件路径和库
tshark -v

# 列出接口，不抓包
tshark -D

# 查看支持的协议和字段，常用于确认字段名
tshark -G protocols | head
tshark -G fields | grep -E '\b(http.request.method|tcp.analysis.retransmission)\b'
主题建议原因
权限优先用系统包提供的 dumpcap capability 或抓包组避免每次用 root 运行复杂过滤和导出命令
版本在工单里记录 tshark -v不同版本协议解码、字段名、JSON 格式可能有差异
接口用 tshark -D、ip -br addr、ip route get 对照AI 节点常有管理网、训练网、存储网、容器网桥
时间确认 NTP/chrony 同步跨节点 pcap 对齐依赖时间戳可信
安全提醒： 抓包权限接近读取网络明文的能力。不要随意给所有用户持久授权；多租户集群应走审计流程和临时授权。

4. 选择接口与第一条抓包命令

第一条命令不要追求复杂。先列接口，再做限量抓包，确认能看到目标流量。高速网卡、容器网络、Bond、VLAN、RoCE 网络和 Kubernetes 节点都可能让“应该抓哪张接口”变成关键问题。

# 只列接口
tshark -D

# 抓 eth0 上前 20 个包并打印摘要
sudo tshark -i eth0 -c 20

# 抓 10 秒，写入文件；-a 是停止条件
sudo tshark -i eth0 -a duration:10 -w /tmp/sample.pcapng

# 限制包长，只保留每包前 128 字节，降低敏感 payload 风险
sudo tshark -i eth0 -s 128 -a duration:10 -w /tmp/headers-only.pcapng

# 只抓某个主机和端口，避免全量抓包
sudo tshark -i eth0 -f 'host 10.10.20.12 and tcp port 443' \
  -a duration:30 -w /tmp/api-443.pcapng
-i
选择接口。不要默认相信 any；它方便但可能丢失链路层细节，且多接口流量混在一起。
-c/-a
限制包数、时长、文件大小。生产抓包必须有停止条件。
-s
snaplen，限制每包保存长度。只看头部时可显著降低敏感内容暴露。
高流量提醒： 在 100G/200G/400G 链路上全量抓包可能丢包、打满磁盘或影响 CPU。先用 capture filter 缩小范围，再决定是否扩大。

流程图：capture filter 与 display filter 的执行位置

capture filter 在保存前丢弃包，display filter 在已有包上筛选。前者省资源但不可逆，后者适合离线反复分析。

5. capture filter 与 display filter 的区别

-f 使用 libpcap/BPF capture filter，语法接近 tcpdump，在抓包阶段执行；-Y 使用 Wireshark display filter，在解码后执行。AI Infra 现场抓包通常先用 -f 限流量，再用 -Y 精确分析。

维度capture filter：-fdisplay filter：-Y
执行时机抓包前/写入前读取和解码之后
语法BPF：host 1.2.3.4 and tcp port 443Wireshark：ip.addr == 1.2.3.4 && tcp.port == 443
优点降低 CPU、磁盘、隐私风险字段丰富，可按协议语义筛选
风险过窄会永久错过证据不能减少现场保存的包量
适合生产 live capture离线 pcap 分析、字段抽取
# 抓包时只保存目标主机 443 流量
sudo tshark -i eth0 -f 'host 10.10.20.12 and tcp port 443' \
  -a duration:30 -w /tmp/api.pcapng

# 离线只显示 HTTP 5xx 响应
tshark -r /tmp/api.pcapng -Y 'http.response.code >= 500'

# 离线只看 TCP 重传、乱序、重复 ACK 等分析事件
tshark -r /tmp/api.pcapng -Y 'tcp.analysis.flags'
记忆法： -f 负责“抓不抓进文件”，-Y 负责“从已有包里显示什么”。

6. 读取 pcap：离线分析比现场试错更安全

成熟的排障流程通常是：现场抓一个受控 pcap，然后离线反复过滤和抽取字段。这样能避免在事故窗口不断改命令，也能保留可复盘证据。

# 读取 pcap 摘要
tshark -r incident.pcapng

# 只看前 50 个包
tshark -r incident.pcapng -c 50

# 按时间相对值输出，便于对齐应用日志
tshark -r incident.pcapng -t r

# 只显示指定时间窗口内的包
tshark -r incident.pcapng -Y 'frame.time_relative >= 10 and frame.time_relative <= 20'

# 保存过滤后的子集，便于分享最小证据
tshark -r incident.pcapng -Y 'ip.addr == 10.10.20.12 and tcp.port == 443' \
  -w focused-api-443.pcapng
先保留原始 pcap
过滤导出子集前保留原文件，避免分析误删上下文。
再做最小化分享
对外分享前用 -Y、-s、脱敏或字段表减少敏感内容。
最后写命令证据
结论里附 tshark 命令，别人可以复算。

7. 显示过滤器：IP、端口、TCP、HTTP、TLS、DNS

Wireshark display filter 是 tshark 的核心能力。它不是普通正则，而是基于协议字段的布尔表达式。字段名可以通过 tshark -G fields 查询，也可以在 Wireshark GUI 中点字段复制。

目标过滤器说明
某个 IPip.addr == 10.10.20.12源或目的任一方向匹配
某个 TCP 端口tcp.port == 443源端口或目的端口任一方向匹配
只看连接建立tcp.flags.syn == 1 and tcp.flags.ack == 0客户端发起 SYN
TCP 问题tcp.analysis.retransmission or tcp.analysis.lost_segment重传或疑似丢段
HTTP 失败http.response.code >= 500API 服务 5xx
TLS 握手tls.handshake证书、SNI、版本、握手异常
DNS 慢查询dns结合时间字段和 query/response 字段分析
# 连接失败相关：SYN、RST、重传
tshark -r incident.pcapng -Y 'tcp.flags.syn == 1 or tcp.flags.reset == 1 or tcp.analysis.retransmission'

# 查看访问某个推理 API 的 HTTP 请求
tshark -r api.pcapng -Y 'http.request and ip.addr == 10.10.20.12'

# 只看 TLS Client Hello，常用于确认 SNI 和版本
tshark -r tls.pcapng -Y 'tls.handshake.type == 1'

# DNS 查询和响应
tshark -r dns.pcapng -Y 'dns.qry.name contains "svc.cluster.local" or dns.flags.response == 1'
协议识别提醒： HTTP/2、gRPC、TLS 内部 payload、非标准端口协议可能需要额外解码设置；如果字段不存在，先确认协议是否被正确识别。

8. 字段抽取：-T fields 与 CSV/TSV

-T fields 把 pcap 变成表格，是自动化分析最常用的输出方式。用 -e 指定字段，用 -E 控制表头、分隔符、重复字段处理和引用方式。

# 抽取 TCP 五元组和相对时间，默认 tab 分隔
tshark -r incident.pcapng -Y 'tcp' -T fields \
  -e frame.time_relative -e ip.src -e tcp.srcport -e ip.dst -e tcp.dstport -e tcp.len

# 输出 CSV，带表头，适合导入表格或分析脚本
tshark -r api.pcapng -Y 'http.request or http.response' -T fields \
  -E header=y -E separator=, -E quote=d \
  -e frame.time_epoch -e ip.src -e ip.dst -e http.request.method \
  -e http.host -e http.request.uri -e http.response.code

# 抽取 TCP 分析事件
tshark -r incident.pcapng -Y 'tcp.analysis.flags' -T fields \
  -E header=y -E separator=, -E quote=d \
  -e frame.number -e frame.time_relative -e ip.src -e ip.dst \
  -e tcp.stream -e tcp.analysis.retransmission -e tcp.analysis.lost_segment \
  -e tcp.analysis.out_of_order -e tcp.analysis.duplicate_ack
选项作用常用写法
-T fields字段表输出-T fields -e ip.src -e ip.dst
-e指定一个字段-e frame.time_epoch
-E header=y输出表头便于 CSV 被人读懂
-E separator=,CSV 分隔符含逗号字段时配合 quote=d
-E occurrence=f多值字段只取第一个避免一格里出现多个重复值
工程建议： 工单里优先贴字段表和命令，而不是只贴 pcap 截图；字段表更容易 grep、diff、排序、脱敏和复现。

9. JSON/Elastic 输出：给脚本和平台用

tshark 支持 -T json、-T ek 等结构化输出。JSON 适合一次性脚本和少量包；Elastic/Kibana 形式适合接入日志平台。大 pcap 输出 JSON 会非常大，建议先用 -Y 缩小范围。

# 输出 JSON，先限制前 10 个包
tshark -r incident.pcapng -c 10 -T json

# 只导出 TCP 分析事件的 JSON
tshark -r incident.pcapng -Y 'tcp.analysis.flags' -T json > tcp-analysis.json

# 只导出指定协议层，减少 JSON 体积
tshark -r api.pcapng -Y 'http' -T json -j 'frame ip tcp http' > http.json

# Elastic/Kibana 风格输出
tshark -r incident.pcapng -Y 'dns or http or tls' -T ek > packets.ek.json
什么时候用 -T fields
需要稳定列、汇总统计、CSV、低体积、便于脱敏和人工审阅。
什么时候用 -T json
需要保留层级结构、字段较多、后续由脚本解析，或要给平台做结构化索引。
体积提醒： JSON 可能比 pcap 大很多。不要对全量生产抓包直接导出 JSON；先过滤，再抽层，再压缩。

信息图：生产抓包的限流与环形缓冲设计

环形缓冲适合“等故障复现”：磁盘占用可控，只保留最近 N 个文件。

10. 写入文件、包长限制与环形缓冲

生产抓包最怕两件事：抓太多敏感 payload，或把磁盘打满。-s、-a、-b 是必须掌握的安全边界。

# 限时 60 秒，限制每包 128 字节，只抓目标端口
sudo tshark -i eth0 -s 128 -f 'tcp port 443' \
  -a duration:60 -w /var/tmp/tshark/api-443.pcapng

# 文件达到约 100 MiB 后停止
sudo tshark -i eth0 -s 128 -f 'host 10.10.20.12' \
  -a filesize:102400 -w /var/tmp/tshark/host.pcapng

# 环形缓冲：每个文件约 100 MiB，最多 10 个文件
sudo mkdir -p /var/tmp/tshark
sudo tshark -i eth0 -s 128 -f 'host 10.10.20.12 and tcp port 443' \
  -b filesize:102400 -b files:10 -w /var/tmp/tshark/api-ring.pcapng

# 采集后确认文件大小
ls -lh /var/tmp/tshark
选项用途生产建议
-w file.pcapng写入 pcapng 文件保留原始证据，离线再分析
-s 128每包只保存前 128 字节多数 TCP/IP/TLS 头部排障足够，payload 风险更低
-a duration:6060 秒后停止适合明确复现窗口
-a filesize:N文件达到 N KiB 后停止防止单文件过大
-b filesize:N -b files:M环形缓冲适合等待偶发问题
磁盘警告： 不要在根分区长时间抓包。用 df -h 确认空间，优先写到临时数据盘，并设置文件数和大小上限。

11. 远程与无头抓包：SSH、容器、Kubernetes

AI 集群节点往往没有 GUI。tshark 适合在远程服务器、容器宿主机和临时 debug 环境中做受控采集。关键是明确采集点：宿主机接口、Pod namespace、Service 路径、NAT 前后看到的五元组可能完全不同。

# 远程节点上抓 30 秒，然后拉回本地
ssh gpu-node-17 "sudo tshark -i eth0 -s 128 -f 'tcp port 29500' \
  -a duration:30 -w /tmp/rdzv.pcapng"
scp gpu-node-17:/tmp/rdzv.pcapng .

# 通过 SSH 流式保存到本地文件，避免远端磁盘占用
ssh gpu-node-17 "sudo tshark -i eth0 -s 128 -f 'host 10.10.20.12' -w -" \
  > gpu-node-17.pcapng

# 在容器所在宿主机确认 veth、cni、bond、物理网卡
ip -br link
ip route get 10.10.20.12

# Kubernetes：进入临时 debug 容器后抓包，具体权限取决于集群策略
kubectl debug node/gpu-node-17 -it --image=nicolaka/netshoot --privileged
tshark -D
宿主机抓包
适合看真实出入节点的流量、NAT 后地址、物理接口、Bond/VLAN。需要理解容器流量如何经过宿主机网络栈。
容器内抓包
适合看应用视角的地址和端口。受 capability、镜像工具、namespace 限制，可能看不到宿主机物理接口。
SSH 流式提醒： -w - 输出的是二进制 pcapng，不能和普通文本日志混在一起；远端命令不要额外打印提示信息到 stdout。

12. AI 训练网络：NCCL、Rendezvous 与 API 调试

很多分布式训练问题不是一条命令能定性。tshark 在这里的角色是补齐网络侧证据：连接是否建立、是否频繁 RST、是否重传、是否走错网卡、rendezvous 端口是否被访问、控制面是否被 DNS/TLS/API 卡住。

NCCL 与 torchrun rendezvous

# 抓 torchrun rendezvous 端口，只看头部，限时 60 秒
sudo tshark -i eth0 -s 128 -f 'tcp port 29500' \
  -a duration:60 -w /tmp/rdzv-29500.pcapng

# 离线查看哪些节点连接 master:29500
tshark -r /tmp/rdzv-29500.pcapng -Y 'tcp.port == 29500' -T fields \
  -E header=y -E separator=, -E quote=d \
  -e frame.time_relative -e ip.src -e tcp.srcport -e ip.dst -e tcp.dstport -e tcp.flags.syn -e tcp.flags.reset

# 查看重传、乱序、零窗口等 TCP 分析事件
tshark -r /tmp/rdzv-29500.pcapng -Y 'tcp.analysis.flags' -T fields \
  -E header=y -E separator=, \
  -e frame.time_relative -e ip.src -e ip.dst -e tcp.stream \
  -e tcp.analysis.retransmission -e tcp.analysis.zero_window -e tcp.analysis.out_of_order

API、对象存储与控制面

# 推理服务 API 入口，先只抓目标客户端和服务端
sudo tshark -i eth0 -s 256 -f 'host 10.20.1.50 and tcp port 8000' \
  -a duration:30 -w /tmp/infer-api.pcapng

# 如果是明文 HTTP，可抽取 method、host、uri、状态码
tshark -r /tmp/infer-api.pcapng -Y 'http.request or http.response' -T fields \
  -E header=y -E separator=, -E quote=d \
  -e frame.time_epoch -e ip.src -e ip.dst -e http.request.method -e http.request.uri -e http.response.code

# TLS 场景下至少确认 SNI、握手版本和 alert
tshark -r /tmp/infer-api.pcapng -Y 'tls.handshake or tls.alert' -T fields \
  -E header=y -E separator=, -E quote=d \
  -e frame.time_relative -e ip.src -e ip.dst -e tls.handshake.extensions_server_name -e tls.alert_message.desc
NCCL 边界： tshark 能帮助判断 TCP/IP 控制连接、socket fallback、路由和重传；RDMA verbs、RoCE PFC/ECN、GPU Direct RDMA 性能仍需结合 ibv_devinfo、ib_write_bw、ethtool、交换机计数器和 NCCL 日志。

用例图：AI Infra 中 tshark 放在哪个排障层

遇到 NCCL/API 问题时，不要只抓包；把 pcap 与应用日志、socket 状态、网卡/交换机计数器放在同一时间线上。

13. HTTP/gRPC/API 排障与延迟证据

推理服务、模型网关、向量数据库、对象存储和控制面 API 的问题常表现为“慢、偶发 5xx、连接重置、请求重试”。如果是明文 HTTP，tshark 可以直接抽 method、URI、状态码；如果是 TLS，只能看到握手、SNI、连接层事件，除非有合法的解密材料和授权。

# 明文 HTTP：请求和响应字段
tshark -r api.pcapng -Y 'http.request or http.response' -T fields \
  -E header=y -E separator=, -E quote=d \
  -e frame.time_epoch -e tcp.stream -e ip.src -e ip.dst \
  -e http.request.method -e http.request.uri -e http.response.code

# 按 TCP stream 追踪同一连接摘要
tshark -r api.pcapng -Y 'tcp.stream == 7'

# HTTP2/gRPC 常见字段，能否解析取决于是否明文 h2c 或已解密
tshark -r grpc.pcapng -Y 'http2' -T fields \
  -E header=y -E separator=, \
  -e frame.time_relative -e tcp.stream -e http2.streamid -e http2.header.name -e http2.header.value

# 看连接复用与关闭：FIN/RST
tshark -r api.pcapng -Y 'tcp.flags.fin == 1 or tcp.flags.reset == 1' -T fields \
  -E header=y -E separator=, \
  -e frame.time_relative -e ip.src -e ip.dst -e tcp.stream -e tcp.flags.reset -e tcp.flags.fin
分析技巧： API 延迟不要只看单包时间。先按 tcp.stream 归组，再把请求、响应、重传、零窗口、RST 放在同一条时间线里看。

14. DNS、TLS 与证书握手排障

AI 平台常依赖对象存储、镜像仓库、模型仓库、服务发现、Kubernetes DNS 和外部 API。DNS 或 TLS 问题会伪装成“模型下载慢”“推理服务偶发超时”“worker 拉取配置失败”。

# DNS 查询和响应字段
tshark -r dns.pcapng -Y 'dns' -T fields \
  -E header=y -E separator=, -E quote=d \
  -e frame.time_epoch -e ip.src -e ip.dst -e dns.qry.name -e dns.a -e dns.flags.rcode

# TLS Client Hello：看 SNI 和 TLS 版本
tshark -r tls.pcapng -Y 'tls.handshake.type == 1' -T fields \
  -E header=y -E separator=, -E quote=d \
  -e frame.time_relative -e ip.src -e ip.dst \
  -e tls.handshake.extensions_server_name -e tls.handshake.version

# TLS alert：定位证书、协议版本、握手失败等线索
tshark -r tls.pcapng -Y 'tls.alert_message' -T fields \
  -E header=y -E separator=, -E quote=d \
  -e frame.time_relative -e ip.src -e ip.dst -e tls.alert_message.desc
现象tshark 线索下一步
首次请求很慢DNS 响应延迟、重试、多次 NXDOMAIN查 CoreDNS、上游 DNS、缓存、搜索域
TLS 连接失败TLS alert、握手中断、SNI 不符合预期查证书链、域名、代理、TLS 版本策略
API 偶发 resetRST 发起方向、发生在请求前还是响应中查服务端日志、LB idle timeout、连接池
大量重传tcp.analysis.retransmission、duplicate ACK查链路错误、队列、拥塞、MTU、交换机

15. tshark vs tcpdump vs Wireshark

三者不是互斥关系。tcpdump 轻量、到处都有，适合快速抓包；tshark 适合服务器上的协议解码和结构化输出；Wireshark GUI 适合人工深挖复杂会话。

工具优势劣势AI Infra 用法
tcpdump轻量、普遍、BPF 过滤强、抓包稳定协议字段解码和结构化输出弱现场快速抓 pcap：tcpdump -i eth0 -s 128 -w x.pcap
tsharkWireshark 解码器、display filter、字段/JSON 输出资源开销更高，字段名需学习无头服务器分析、自动化抽字段、离线复盘
Wireshark GUI交互分析、Follow Stream、图形化时间线不适合无头生产节点和自动化下载最小 pcap 后本地深挖
eBPF/平台观测低侵入、持续观测、关联进程/容器不一定保留原始包和协议细节长期监控与告警，tshark 用于抽样证据
# 常见组合：tcpdump 负责现场轻量抓，tshark 负责离线字段抽取
sudo tcpdump -i eth0 -s 128 -w /tmp/inc.pcap 'host 10.10.20.12 and tcp port 443'
tshark -r /tmp/inc.pcap -Y 'tcp.analysis.flags' -T fields \
  -e frame.time_relative -e ip.src -e ip.dst -e tcp.stream -e tcp.analysis.retransmission
选型原则： 现场压力越大，抓包命令越应该简单、可控、低风险；复杂过滤和解码尽量离线做。

16. 隐私、安全与合规边界

pcap 经常包含内部 IP、主机名、DNS 查询、HTTP header、Cookie、Authorization token、URL 参数、用户数据甚至模型请求内容。AI Infra 场景还可能暴露租户、任务名、数据集路径、对象存储 key、推理 prompt 或业务调用模式。

抓包前
明确授权、时间窗口、接口、过滤条件、保存路径、保留周期和谁可以读取。默认加 -s 限制 payload。
抓包中
使用 -a/-b 限制时长和大小；不要在共享终端滚动输出大量明文协议内容。
分享前
优先分享字段表、统计摘要和过滤后的最小 pcap；必要时脱敏 IP、域名、URL、token、用户名。
归档后
把 pcap 当敏感数据处理：权限控制、加密存储、过期删除、审计下载。
# 更安全的抓包：限头部、限时间、限主机、限端口
sudo tshark -i eth0 -s 128 -f 'host 10.10.20.12 and tcp port 443' \
  -a duration:30 -w /var/tmp/tshark/minimal.pcapng

# 分享字段表而不是原始 pcap
tshark -r /var/tmp/tshark/minimal.pcapng -Y 'tcp.analysis.flags or tls.alert_message' -T fields \
  -E header=y -E separator=, -E quote=d \
  -e frame.time_epoch -e ip.src -e ip.dst -e tcp.stream -e tls.alert_message.desc \
  > /var/tmp/tshark/minimal-evidence.csv
合规警告： 不要为了排障擅自解密 TLS、抓完整 payload、跨租户抓包或外发 pcap。需要解密或全量 payload 时，必须有明确授权和数据处理方案。

排障流程图：tshark 结果不符合预期时怎么查

tshark 排障的常见失败不是命令写错，而是采集点、过滤层级、权限或协议识别假设错了。

17. 常见坑与排障流程

坑 1：把 -f 和 -Y 混用
-f 'tcp port 443' 是 BPF；-Y 'tcp.port == 443' 是 Wireshark 字段表达式。
坑 2：接口选错
多网卡、Bond、VLAN、容器网桥和 hostNetwork 会改变采集点看到的地址。
坑 3：全量抓包无停止条件
缺少 -a/-b 可能打满磁盘，缺少 -s 可能暴露 payload。
坑 4：字段名不存在
版本不同、协议未识别、TLS 未解密或非标准端口都会导致字段为空。
坑 5：把 TCP 分析字段当绝对真相
tcp.analysis.* 是基于采集点看到的包推断，丢包采集点可能产生误导。
坑 6：忽略 offload
TSO/GRO/LRO 可能让包长和分段看起来不像线上真实线速包。必要时结合 ethtool -k 判断。
坑 7：时间不同步
跨节点 pcap 如果时钟漂移，延迟和先后顺序判断会错。
坑 8：共享敏感 pcap
pcap 不是普通日志；优先分享字段表和最小化子集。

排障模板

# 1. 证明接口和权限没问题：短抓包摘要
sudo tshark -i eth0 -c 20

# 2. 证明目标流量经过此接口：先用宽一点的 capture filter
sudo tshark -i eth0 -s 128 -f 'host 10.10.20.12' -a duration:10 -w /tmp/check.pcapng

# 3. 离线逐步收窄 display filter
tshark -r /tmp/check.pcapng -Y 'ip.addr == 10.10.20.12'
tshark -r /tmp/check.pcapng -Y 'ip.addr == 10.10.20.12 and tcp'
tshark -r /tmp/check.pcapng -Y 'tcp.analysis.flags'

# 4. 查字段是否存在
tshark -G fields | grep -F 'tcp.analysis.retransmission'

# 5. 导出字段表作为证据
tshark -r /tmp/check.pcapng -Y 'tcp.analysis.flags' -T fields \
  -E header=y -E separator=, -E quote=d \
  -e frame.time_relative -e frame.number -e ip.src -e ip.dst -e tcp.stream

学习路线

  1. 先理解抓包点、接口、pcap、capture filter 与 display filter 的区别。
  2. 掌握 -r、-w、-i、-f、-Y、-T fields。
  3. 用 tshark -G fields 学会查字段名，不要靠猜。
  4. 在测试环境练习 DNS、TCP、HTTP、TLS、重传和 RST 的字段抽取。
  5. 生产只做受控抓包，离线做复杂过滤和 JSON/CSV 生成。
