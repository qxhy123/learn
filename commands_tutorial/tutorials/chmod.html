chmod 深度教程：从 Linux 权限模型到安全批量授权

这份教程按常用命令 chmod 讲解。它不是“777 能解决一切”的速查表，而是从 Linux 文件权限的主体、动作和对象模型出发，系统讲清楚：u/g/o/a、r/w/x、符号模式与数字模式、文件和目录权限差异、递归修改的安全边界、setuid/setgid/sticky 特殊位、umask、与 chown/setfacl 的边界，以及真实排障方法。

一句话理解： chmod 修改的是文件或目录的“访问模式”：谁可以读、写、执行或进入它；它不改变文件归属者，也不授予不存在的路径访问能力。
最重要原则： 先用 ls -l、namei -l、find 看清当前权限和影响范围，再执行 chmod；递归修改前务必 dry-run，不要用 chmod -R 777 作为排障捷径。

1. chmod 是什么，解决什么问题

chmod 是 change mode 的缩写，用来修改 Unix/Linux 文件模式位。模式位决定用户在访问文件系统对象时能否读、写、执行，或者能否进入目录、列出目录、创建和删除目录项。

它能做什么
给脚本添加执行权限，限制配置文件读取范围，开放 Web 静态文件读取权限，保护私钥，配置共享目录特殊位。
它不能做什么
不能改变所有者或所属组，不能绕过父目录权限，不能替代服务自身的认证授权，也不能修复错误的 SELinux/AppArmor 策略。
它的本质
修改 inode 上的权限位：普通位是 rwx，特殊位是 setuid、setgid、sticky。
# 给当前用户添加脚本执行权限
chmod u+x deploy.sh

# 只允许所有者读写私钥
chmod 600 ~/.ssh/id_ed25519

# 让目录对所有者完全可用，对组和其他用户只可进入和读取
chmod 755 /var/www/static

# 查看修改结果
ls -l deploy.sh ~/.ssh/id_ed25519
ls -ld /var/www/static
关键区别： chmod 修改“能做什么”；chown 修改“谁是所有者/所属组”；setfacl 增加更细粒度的访问控制列表。

信息图：Linux 权限模型总览

chmod 只改对象上的模式位；一次访问是否成功，还取决于进程身份、父目录链路和额外安全机制。

2. 从 ls -l 读懂权限字符串

ls -l 的第一列通常像 -rwxr-xr--。第 1 个字符表示文件类型，后 9 个字符分成三组，分别对应所有者、所属组、其他用户。

$ ls -l script.sh report.txt
-rwxr-xr-- 1 alice dev  812 Apr 25 10:00 script.sh
-rw-r----- 1 alice dev 4096 Apr 25 10:01 report.txt

# 拆解 script.sh
# -     普通文件
# rwx   owner: alice 可读、可写、可执行
# r-x   group: dev 可读、不可写、可执行
# r--   other: 其他用户只可读
位置示例含义
第 1 位-、d、l普通文件、目录、符号链接等对象类型
第 2-4 位rwx所有者权限，也就是 u
第 5-7 位r-x所属组权限，也就是 g
第 8-10 位r--其他用户权限，也就是 o
读权限时先看主体： 你要问的不是“这个文件有没有 x”，而是“当前进程会按 owner、group 还是 other 那一组权限判断”。

3. r/w/x 在文件和目录上的含义

同样是 r、w、x，在普通文件和目录上含义不同。很多 Permission denied 的根源，是把目录的 x 误解成“执行目录”。

权限普通文件目录
r read读取文件内容，例如 cat file列出目录项名称，例如 ls dir。没有 x 时通常只能看到名字，不能读取元数据
w write修改文件内容，前提是能打开文件写入创建、删除、重命名目录项，通常还需要目录 x
x execute/search把文件作为程序或脚本执行进入或穿越目录，例如 cd dir、访问 dir/file
目录只有 r 没有 x
可能能看到文件名，但不能进入目录，也不能可靠读取文件属性。
目录只有 x 没有 r
不能列出目录，但如果知道文件名且文件本身允许，可以访问具体文件。私有发布目录常见这种模型。
# 目录可进入但不可列出：知道文件名才可访问
chmod 711 /srv/dropbox

# 文件可执行不代表路径可执行；父目录也必须有 x
namei -l /srv/app/bin/run.sh
目录写权限很敏感： 如果用户对目录有 w+x，通常就能删除或重命名其中的目录项，即使他没有对应文件的写权限；sticky 位可以改变共享目录中的删除规则。

4. chmod 基本语法

chmod [选项] MODE FILE...

# MODE 可以是符号模式
chmod u+x script.sh
chmod go-rwx secret.txt

# MODE 也可以是数字模式
chmod 755 script.sh
chmod 600 secret.txt
选项作用安全提示
-R递归修改目录树先用 find 预览范围；尽量区分文件和目录
-v显示每个被处理对象批量操作时有助于审计
-c只显示发生变化的对象比 -v 更少噪声
--reference=FILE复制参考文件的权限适合同类文件对齐权限
# 复制 template.conf 的权限给新文件
chmod --reference=template.conf generated.conf

# 显示发生变化的权限修改
chmod -c u+rw report.txt
跨平台提示： GNU coreutils 的 chmod 支持 --reference；macOS/BSD 环境可能不支持。脚本要面向目标系统测试。

流程图：符号模式如何表达“给谁改什么”

符号模式适合表达“增量变化”：只改需要变化的位，保留其他权限不动。

5. 符号模式：u/g/o/a 与 + - =

符号模式由三部分组成：用户类别、操作符、权限。用户类别省略时，行为会受 umask 影响；为了脚本清晰，建议显式写出 u、g、o 或 a。

符号含义例子
u所有者 userchmod u+x script.sh
g所属组 groupchmod g+w shared.txt
o其他用户 otherchmod o-r private.txt
a全部，相当于 ugochmod a+r README.md
+添加权限chmod g+rw file
-移除权限chmod go-w file
=精确设为chmod u=rw,go= file
# 给所有者添加执行权限，不影响读写位
chmod u+x build.sh

# 组成员可读写，其他用户没有任何权限
chmod g+rw,o-rwx report.csv

# 精确设置：所有者读写，组只读，其他无权限
chmod u=rw,g=r,o= settings.ini

# 多个子句从左到右执行
chmod u+rw,g-w,o-rwx file.txt
= 是覆盖式： chmod g=rx dir 会让组权限精确变成 r-x，组原有的 w 会被清掉。

6. 数字模式：八进制权限

数字模式把 r、w、x 映射成 4、2、1，再分别对 owner、group、other 三组求和。755 就是 owner=7、group=5、other=5。

权限数值含义
r4读取文件内容或列出目录项
w2写入文件内容或修改目录项
x1执行文件或进入目录
-0没有该权限
数字权限常见含义
7rwx完全权限
6rw-文件可读写，不可执行
5r-x可读和可进入/执行，不可写
4r--只读
0---无权限
# rwxr-xr-x：常见可执行程序或公开目录
chmod 755 app

# rw-r--r--：常见公开文本文件
chmod 644 README.md

# rw-------：私钥、令牌、敏感配置
chmod 600 .env

# rwxrwx---：团队共享目录或脚本
chmod 770 team-bin
计算方法： rwx = 4+2+1 = 7，r-x = 4+1 = 5，rw- = 4+2 = 6。

对照图：数字模式与权限矩阵

数字模式适合设置完整目标状态；符号模式适合做局部增量修改。

7. 符号模式 vs 数字模式

模式优势风险适合场景
符号模式表达意图清楚，只改指定权限位省略用户类别时可能受 umask 影响；复杂组合要仔细读“给用户加执行权限”“移除其他用户写权限”
数字模式目标状态明确，审计容易覆盖所有普通权限，可能误清已有位私钥 600、目录 755、文件 644
# 增量修改：保留其他位，只给所有者加执行权限
chmod u+x script.sh

# 目标状态：明确要求最终就是 rwxr-xr-x
chmod 755 script.sh

# 复制权限：用参考文件避免手算
chmod --reference=known-good.conf new.conf
实践建议： 单个明确对象用数字模式很直观；在不确定原权限的批量环境里，优先用符号模式做最小变更。

8. 递归修改：-R 的安全用法

chmod -R 会递归处理目录树，影响范围通常比你直觉更大。尤其不要把同一个数字权限同时套给文件和目录：文件通常不该都有执行权限，目录通常需要 x 才能进入。

高危命令： chmod -R 777 . 会让所有用户读、写、执行/进入当前目录树。它可能暴露密钥、允许篡改代码、破坏部署安全边界。

推荐流程：先预览，再分类型修改

# 1. 预览将被处理的对象
find /srv/app -maxdepth 3 -print

# 2. 预览权限现状
find /srv/app -maxdepth 3 -printf '%m %u:%g %p\n' 2>/dev/null

# 3. 目录和文件分开设置
find /srv/app -type d -exec chmod 755 {} +
find /srv/app -type f -exec chmod 644 {} +

# 4. 只给确实需要执行的脚本加 x
find /srv/app/bin -type f -name '*.sh' -exec chmod 755 {} +

使用大写 X 做条件执行位

# X 只给目录加 x，或给原本已有任意执行位的文件加 x
chmod -R a+rX /srv/static

# 常用于发布静态资源：文件可读，目录可进入
chmod -R u=rwX,go=rX /srv/static
X 的价值： 它避免把普通文本、图片、配置文件全部变成可执行文件，同时能保证目录可进入。

9. 文件与目录的常见权限配方

场景推荐权限说明
普通公开文本文件644所有者可写，其他用户只读
可执行脚本或程序755所有者可写，所有人可读和执行
私钥600只有所有者可读写，SSH 常要求这样
个人私有目录700只有所有者能进入和列出
公开静态目录755其他用户可进入和读取，不可写
团队共享目录2770组可协作，setgid 让新文件继承目录组
临时共享目录1777所有人可写，但 sticky 限制删除他人文件，例如 /tmp
# Web 静态站点常见基线
find /var/www/site -type d -exec chmod 755 {} +
find /var/www/site -type f -exec chmod 644 {} +

# SSH 私钥和配置
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
chmod 644 ~/.ssh/authorized_keys
权限不是越大越省事： 如果服务账号只需要读取文件，就不要给写权限；如果文件不是程序或脚本，就不要给执行权限。

信息图：setuid、setgid、sticky 三个特殊位

特殊位改变权限语义，尤其 setuid 可能扩大执行身份，必须比普通 chmod 更谨慎。

10. setuid、setgid、sticky 特殊位

普通权限是三位数字，例如 755。特殊位会出现在第四位，例如 4755、2770、1777。在 ls -l 中，它们通常显示为 s、S、t、T。

特殊位数字常见显示作用
setuid4-rwsr-xr-x可执行文件运行时使用文件所有者的有效 UID
setgid2drwxrws---目录中新建文件继承目录所属组；可执行文件还有运行组身份语义
sticky1drwxrwxrwt共享可写目录中，用户通常只能删除自己拥有的文件
# 团队共享目录：组协作，新文件继承 shared 组
sudo chgrp shared /srv/shared
sudo chmod 2770 /srv/shared

# 临时目录语义：所有人可写，但不能随意删除他人文件
sudo chmod 1777 /srv/tmp

# 移除 setuid/setgid/sticky
chmod u-s risky-binary
chmod g-s shared-dir
chmod -t tmpdir
setuid 警告： 不要给脚本随意设置 setuid；许多系统会忽略脚本 setuid，二进制 setuid 也必须经过安全审计，因为漏洞会直接变成提权入口。

11. umask：默认权限从哪里来

chmod 修改已有对象；umask 影响新建对象的默认权限。可以把 umask 理解为“默认要扣掉哪些权限”。

对象理论最大默认权限常见 umask实际结果
普通文件666022644
目录777022755
普通文件666077600
目录777077700
# 查看当前 shell 的 umask
umask

# 临时设置更私密的默认权限
umask 077
touch token.txt     # 通常得到 600
mkdir private-dir   # 通常得到 700

# 在脚本里局部设置，并显式 chmod 关键文件
old_umask=$(umask)
umask 077
touch secret.env
chmod 600 secret.env
umask "$old_umask"
文件默认通常没有 x： 新建普通文件的最大默认权限一般是 666，所以不会因为 umask 000 自动变成可执行文件。

12. chmod vs chown vs setfacl

权限问题不一定由 chmod 解决。先判断问题是“身份错了”“模式位错了”，还是“传统三组权限表达不够”。

命令修改对象适合问题例子
chmod权限模式位当前 owner/group/other 权限不合适chmod 640 app.conf
chown所有者和所属组文件归属错误，导致进程落到 wrong permission classsudo chown app:app app.conf
chgrp所属组只需改变协作组sudo chgrp deploy release.tar
setfacl访问控制列表 ACL三组权限不够，需要给特定用户或组额外权限setfacl -m u:bob:r file
# 服务账号无法读配置：先看身份和归属
id nginx
ls -l /etc/myapp/app.conf

# 如果所有者/组错了，chown/chgrp 比 chmod 更正确
sudo chown root:nginx /etc/myapp/app.conf
sudo chmod 640 /etc/myapp/app.conf

# 如果只想额外授权给 bob，ACL 更精确
setfacl -m u:bob:r /srv/reports/monthly.csv
getfacl /srv/reports/monthly.csv
不要用 chmod 掩盖归属错误： 如果服务本应以 app 组读取文件，正确修复通常是 chgrp app file && chmod 640 file，而不是把文件改成 644 或 666。

权限排障的顺序是：谁在访问、访问哪个对象、父目录是否允许穿越、是否存在 ACL/SELinux/mount 限制。

13. 生产排障：Permission denied 怎么查

排障时不要先猜 chmod 数字。先确认进程真实身份和路径上每一层权限，再决定是改模式位、改所有者、改组、改 ACL，还是改服务配置。

# 1. 当前用户和组
id

# 2. 文件自身权限、所有者、组
ls -l /srv/app/config.yml
stat /srv/app/config.yml

# 3. 父目录链路权限，定位哪一层缺 x
namei -l /srv/app/config.yml

# 4. ACL 可能改变传统权限判断
getfacl /srv/app/config.yml 2>/dev/null

# 5. 服务进程实际用户
ps -o user,group,comm -p "$(pgrep -n nginx)"

典型修复

# 服务 nginx 需要读取 root 拥有的配置
sudo chown root:nginx /etc/myapp/app.conf
sudo chmod 640 /etc/myapp/app.conf
sudo chmod 750 /etc/myapp

# 脚本不能执行：先确认内容和解释器，再加执行权限
head -1 deploy.sh
chmod u+x deploy.sh
./deploy.sh
父目录链路很常见： 目标文件是 644 仍可能无法读取，因为路径中的某个父目录缺少 x，导致无法穿越到目标文件。

14. 常见错误与安全反模式

错误 1：用 777 解决所有问题
这会把排障问题变成安全问题。先定位拒绝发生在哪一层。
错误 2：递归给所有文件加 x
chmod -R 755 会让配置、图片、文本都可执行；用 find 分开处理或使用 X。
错误 3：忽略目录 x
目录 x 是 search/进入权限；没有它就无法访问目录下已知文件。
错误 4：把 chmod 当 chown 用
归属错了应修 owner/group，而不是给 other 放开权限。
错误 5：随意设置 setuid
setuid 二进制需要安全审计，脚本 setuid 通常不可依赖。
错误 6：忘记 ACL 或 SELinux
ls -l 后有 + 可能表示 ACL；SELinux 上下文也可能拒绝访问。
错误 7：对符号链接理解错误
多数系统 chmod 影响链接目标而不是符号链接本身；排障时看真实目标。
错误 8：在错误目录执行 -R
执行前用 pwd、find ... -maxdepth 和版本控制确认范围。
# 反模式：不要这样做
chmod -R 777 .
chmod -R 755 /srv/app

# 更安全：先看，再按类型修改
pwd
find /srv/app -maxdepth 2 -printf '%m %p\n' 2>/dev/null
find /srv/app -type d -exec chmod 755 {} +
find /srv/app -type f -exec chmod 644 {} +
find /srv/app/bin -type f -exec chmod 755 {} +

15. 练习路线与检查清单

第一阶段：读懂权限

  • 用 ls -l 拆解 -rw-r-----、drwxr-xr-x、drwxrwxrwt。
  • 解释 owner、group、other 哪一组会用于当前用户。
  • 说清目录 x 与文件 x 的差异。

第二阶段：安全修改

  • 用符号模式完成 u+x、go-rwx、g+rw。
  • 用数字模式设置 600、644、755、750。
  • 用 find 分别设置目录和文件权限，不使用 chmod -R 777。

第三阶段：工程化排障

  • 用 namei -l 找出父目录链路缺失的 x。
  • 用 chown/chgrp 修复归属，而不是放开 other。
  • 理解 setgid 共享目录和 sticky 临时目录的使用边界。

练习环境

# 创建临时练习目录
tmp=$(mktemp -d)
cd "$tmp"
mkdir -p project/bin project/conf shared tmpdir
printf '#!/bin/sh\necho hello\n' > project/bin/hello.sh
printf 'token=secret\n' > project/conf/app.env

# 设置合理权限
chmod 755 project project/bin
chmod 750 project/conf
chmod 755 project/bin/hello.sh
chmod 600 project/conf/app.env
chmod 1777 tmpdir

# 观察结果
find . -maxdepth 3 -printf '%M %m %p\n' 2>/dev/null

修改前检查清单

  1. 我是否确认了当前目录和目标路径？
  2. 我是否知道访问进程的用户和组？
  3. 我是否用 ls -l、stat 或 namei -l 看过现状？
  4. 如果使用 -R，我是否先用 find 预览范围？
  5. 我是否区分了文件和目录权限？
  6. 我是否避免了不必要的 777、666、setuid？
  7. 我是否能解释每一位权限为什么需要？

  • man 7 inode：Linux inode、文件类型、权限位与特殊位说明。
  • ACL 相关手册：getfacl(1)、setfacl(1)，用于传统三组权限不足的场景。

建议阅读顺序：先掌握 ls -l 权限字符串，再掌握文件/目录上 r/w/x 的不同含义，随后学习符号模式、数字模式、递归安全、特殊位和 ACL 边界。
