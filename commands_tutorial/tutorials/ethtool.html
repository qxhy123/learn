ethtool 深度教程：AI Infra 网卡链路、队列、卸载与性能排障

这份教程面向 AI Infra、训练集群、推理集群、RoCE/RDMA 网络和高速以太网节点，系统讲解 Linux 命令 ethtool。重点不是死记参数，而是建立“网卡接口 → 驱动/固件 → 物理链路 → 队列/中断 → 内核卸载 → 统计计数 → NCCL/RDMA 现象”的排障模型，覆盖链路速率/双工、驱动固件、ring buffer、offload、channels、stats、NCCL/RDMA 性能线索、变更安全，以及与 ip、ss、rdma、mlxlink 的边界。

AI InfraNIC 链路Speed/DuplexDriver/FirmwareRing -g/-GOffload -k/-KChannels -l/-LStats -SNCCL/RDMA生产安全
一句话理解： ethtool 是 Linux 网卡的“低层体检和调参工具”：它能查看链路、速率、驱动、固件、队列、offload 和硬件统计，也能修改部分 NIC 行为。

1. ethtool 是什么

ethtool 用于查询和配置 Linux 网络接口的硬件与驱动参数。它比 ip addr、ip link 更贴近 NIC 本身，适合回答“这块网卡以什么速率连上了交换机、用什么驱动和固件、队列是否够、offload 是否打开、硬件是否在丢包”等问题。

它擅长什么
检查链路状态、速率、双工、自协商、驱动/固件、ring、channels、offloads、coalesce、NIC 私有统计。
它不擅长什么
不显示 socket 队列、TCP 会话、路由策略、RDMA QP 细节、交换机端口内部状态或 NCCL collective 算法。
它的本质
通过内核和驱动接口读取或设置 NIC 参数；能看到很多硬件线索，但解释这些线索需要结合 ip、ss、rdma、mlxlink、NCCL 日志和交换机遥测。
# 查看接口链路、速率、双工、自协商
ethtool eth0

# 查看驱动、固件、PCI 总线信息
ethtool -i eth0

# 查看 ring buffer 上限和当前值
ethtool -g eth0

# 查看 offload 开关
ethtool -k eth0

# 查看 NIC 私有统计
ethtool -S eth0
权限提醒： 只读查询通常普通用户可运行；修改链路、offload、ring、channels、coalesce 通常需要 sudo，并且可能瞬断或影响线上流量。

信息图：ethtool 在 AI Infra 网络栈中的位置

ethtool 不是 NCCL/RDMA 专用工具，但它能快速确认 NIC 层是否存在明显基线问题。

2. 安装、权限与接口识别

使用 ethtool 前先确认目标接口。AI 节点常同时有管理网、业务网、存储网、RoCE 网和容器虚拟网卡，误查接口会直接导致错误结论。

# Debian / Ubuntu
sudo apt-get update
sudo apt-get install -y ethtool

# RHEL / CentOS / Rocky / Alma
sudo dnf install -y ethtool

# 确认版本
ethtool --version

# 列出接口摘要，先排除 lo、docker、veth、cni 等虚拟接口
ip -br link
ip -br addr

# 看访问目标 IP 会走哪张网卡
ip route get 10.20.30.40
对象示例AI Infra 含义
物理网卡eth0、ens5f0、enp193s0f0np0通常是 ethtool 的主要目标
bond/teambond0需要同时看 bond 逻辑接口和 slave 物理口
VLANbond0.100ethtool 常应下钻到底层物理接口
容器接口veth*、cali*、cni*更多是网络命名空间和 CNI 问题，不代表 NIC 硬件
实用习惯： 先用 ip route get <peer_ip> 找实际出口，再对出口接口和底层物理接口分别运行 ethtool。

3. 链路、速率、双工与自协商

ethtool DEV 是第一条必跑命令。它能快速判断接口是否连上、链路速率是否降级、双工是否异常、自协商是否符合预期。高速训练网络中，100G 接成 25G、200G 接成 100G、链路反复 flap 都会直接影响 NCCL 和存储吞吐。

# 查看链路基础状态
ethtool ens5f0

# 只看关键字段
ethtool ens5f0 | egrep 'Speed|Duplex|Auto-negotiation|Link detected|Port|Transceiver'

# 只判断是否有 carrier
cat /sys/class/net/ens5f0/carrier
cat /sys/class/net/ens5f0/operstate
字段正常含义异常线索
Speed当前协商速率，例如 100000Mb/s低于预期，可能是线缆、模块、交换机端口、FEC、端口 profile 或分叉模式问题
Duplex高速以太网一般应为 Full半双工在现代数据中心几乎不应出现
Auto-negotiation是否自协商两端配置不一致会导致链路不上或速率异常
Link detected物理链路是否检测到no 表示先查光模块、线缆、交换机端口和网卡状态
变更警告： 修改 speed、duplex、autoneg 可能导致链路重协商甚至中断。除非明确知道交换机端配置，否则不要在生产流量接口上直接强制速率。
# 只读记录当前状态
ethtool ens5f0 > /tmp/ens5f0.link.before.txt

# 如果必须变更，先确认维护窗口和交换机端配置
# 示例：启用自协商。执行后可能短暂断链。
sudo ethtool -s ens5f0 autoneg on

# 示例：强制 100G 全双工。仅在明确两端都支持且需要时使用。
sudo ethtool -s ens5f0 speed 100000 duplex full autoneg off

4. 驱动、固件、总线与 NIC 身份

ethtool -i DEV 用来确认网卡由哪个驱动管理、驱动版本、固件版本、PCI 总线位置。AI 集群中，固件版本不一致、驱动版本混杂、网卡插槽/NUMA 位置不同，都可能造成节点间性能差异。

# 查看驱动、固件、总线
ethtool -i ens5f0

# 结合 PCI 设备信息
lspci -s 0000:ca:00.0 -vv

# 看接口到 NUMA 节点的归属
cat /sys/class/net/ens5f0/device/numa_node

# 记录网卡身份
printf 'iface=%s\n' ens5f0
ethtool -i ens5f0
cat /sys/class/net/ens5f0/address
字段用途排障价值
driver内核驱动名，例如 mlx5_core、ice、i40e判断是否使用预期驱动，是否支持目标功能
version驱动版本或内核集成版本与已知问题、发行版内核、OFED/厂商驱动版本关联
firmware-versionNIC 固件版本同型号节点应尽量一致；异常节点先对比固件
bus-infoPCI 地址用于映射 NUMA、PCIe 拓扑和物理槽位
AI 节点建议： 把 ethtool -i 输出纳入节点验收基线；同一训练池内的 NIC 型号、固件和驱动差异应可解释。

5. 端口定位、模块与光电链路线索

链路问题常来自物理层：插错口、线缆质量、光模块兼容性、交换机端口 profile、FEC、分叉模式。ethtool 能辅助定位接口对应的物理端口，并读取部分模块信息。

# 让网口 LED 闪烁 10 秒，用于机房定位端口
sudo ethtool -p ens5f0 10

# 读取模块 EEPROM 信息，是否支持取决于驱动和权限
sudo ethtool -m ens5f0

# 查看支持和广告的链路模式
ethtool ens5f0 | sed -n '/Supported link modes:/,/Advertised pause frame use:/p'
插错口
用 -p 闪灯，比只看接口名更可靠，尤其是多口 NIC 和多张 NIC 的 GPU 服务器。
模块异常
-m 可提供厂商、波长、序列号、温度等线索，但并非所有驱动都开放完整信息。
速率降级
对比 supported、advertised、link partner advertised，判断两端是否都宣告了目标速率。
边界提醒： FEC、SerDes、交换机侧误码和端口 profile 往往需要交换机命令或厂商工具确认；ethtool 只能提供主机侧的一部分证据。

流程图：ring、offload、channels 的安全调参路径

ring、offload、channels 都可能影响性能，也都可能引入副作用；先建立假设再改。

6. Ring buffer：-g / -G

ring buffer 是网卡与驱动之间的收发描述符队列。RX ring 太小可能在突发流量下出现丢包；TX ring 太小可能影响发送排队。增大 ring 有时能减少 burst drop，但也可能增加排队延迟和缓存占用。

# 查看 ring 最大值和当前值
ethtool -g ens5f0

# 典型输出包含 Pre-set maximums 和 Current hardware settings
# 先保存当前值，便于回滚
ethtool -g ens5f0 > /tmp/ens5f0.ring.before.txt

# 示例：把 RX/TX ring 调到 4096。执行前确认驱动支持和维护窗口。
sudo ethtool -G ens5f0 rx 4096 tx 4096

# 回滚到原值示例
sudo ethtool -G ens5f0 rx 1024 tx 1024
现象可能相关验证方式
短时间突发丢包RX ring、CPU 中断处理、交换机微突发对比 -S 中 rx drop/missed/errors 与业务时间线
吞吐不稳ring、channels、IRQ、NUMA、拥塞调 ring 前后做相同 iperf3/NCCL microbenchmark
延迟尾部变差过深队列、coalesce、上游拥塞同时观察 p99/p999 延迟，不只看吞吐
调参边界： ring 不是越大越好。训练流量追求吞吐时可考虑增大；低延迟推理流量需要更谨慎地评估排队延迟。

7. Offload：-k / -K

offload 把部分网络处理交给 NIC 或内核聚合路径，常见包括 checksum、TSO、GSO、GRO、LRO、RX/TX VLAN offload。AI Infra 中，offload 通常有助于降低 CPU 开销，但某些排障、抓包、虚拟化、隧道或低延迟场景需要临时关闭。

# 查看所有 offload 开关
ethtool -k ens5f0

# 保存基线
ethtool -k ens5f0 > /tmp/ens5f0.offload.before.txt

# 示例：临时关闭 GRO，用于验证聚合对抓包/延迟观察的影响
sudo ethtool -K ens5f0 gro off

# 回滚
sudo ethtool -K ens5f0 gro on

# 示例：查看常见 offload
ethtool -k ens5f0 | egrep 'tcp-segmentation|generic-segmentation|generic-receive|large-receive|rx-checksumming|tx-checksumming'
开关常见作用注意事项
rx-checksumming/tx-checksumming校验和卸载抓包中看到 checksum 异常不一定是真错，可能是卸载导致
tso/gso发送大包分段卸载通常降低 CPU 消耗；关闭后 CPU 压力可能明显上升
gro/lro接收侧聚合提升吞吐但可能影响包级可见性和延迟分析
rx-vlan-offload/tx-vlan-offloadVLAN 标签处理卸载与虚拟化、抓包、交换配置一起分析
生产警告： 不要为了“抓包更直观”长期关闭 offload。关闭后可能把 CPU 打满，让 NCCL、数据加载或推理服务性能更差。

8. Channels 与队列：-l / -L

channels 表示 NIC 可用的 RX/TX/combined 队列数量。高速网卡依赖多队列、RSS 和 IRQ 分布把流量并行分摊到多个 CPU 核。队列太少时，100G/200G/400G 链路可能因为单核软中断或队列瓶颈跑不满。

# 查看队列上限和当前配置
ethtool -l ens5f0

# 保存当前值
ethtool -l ens5f0 > /tmp/ens5f0.channels.before.txt

# 示例：设置 combined 队列数。需要结合 CPU 核数、NUMA 和 IRQ 亲和性。
sudo ethtool -L ens5f0 combined 16

# 查看网卡队列目录
ls /sys/class/net/ens5f0/queues

# 查看中断分布
grep -i ens5f0 /proc/interrupts
combined
许多驱动用 combined 表示一组 RX/TX 队列，常见于多队列网卡。
队列数不是越多越好
过多队列可能增加调度和缓存开销，还要看实际流数、CPU 核数和中断亲和性。
与 RSS 联动
多队列要靠 RSS hash 把不同 flow 分散，否则仍可能集中到少数队列。
NCCL 线索： 多连接、多 rail、多个 rank 并发通信时，channels/RSS/IRQ 分布不合理会表现为某些 CPU 核 softirq 高、吞吐上不去或方向不对称。

9. 统计计数：-S

ethtool -S DEV 输出驱动暴露的 NIC 私有统计。不同厂商字段差异很大，但它是判断硬件层是否丢包、错误、拥塞、队列溢出、pause、buffer 不足的重要入口。

# 查看全部 NIC 统计
ethtool -S ens5f0

# 过滤常见异常关键字
ethtool -S ens5f0 | egrep -i 'drop|discard|error|crc|miss|timeout|pause|overflow|buffer|retry|retrans|ecn|pfc'

# 间隔观察计数是否增长
watch -n 1 "ethtool -S ens5f0 | egrep -i 'drop|discard|error|crc|miss|pause|pfc|ecn'"

# 做测试前后快照
ethtool -S ens5f0 > /tmp/ens5f0.stats.before.txt
# run iperf3 / nccl-tests / workload
ethtool -S ens5f0 > /tmp/ens5f0.stats.after.txt
diff -u /tmp/ens5f0.stats.before.txt /tmp/ens5f0.stats.after.txt
计数类型可能含义下一步
crc、symbol、phy error物理链路、线缆、模块、交换端口问题查交换机端口错误、换线/模块、看 FEC 和链路 flap
rx_missed、rx_no_buffer、drop接收侧处理不过来或队列/缓冲不足看 ring、channels、IRQ、CPU softirq、burst
pause、pfc、ecn拥塞控制或无损网络相关信号结合 RDMA、DCQCN/PFC、交换机队列水位排查
tx_timeout、reset驱动、固件或硬件异常查 dmesg、驱动版本、固件、PCIe AER
解释提醒： -S 字段不是标准化 API。不要跨不同驱动硬套字段含义；先看驱动文档或厂商说明。

10. Interrupt moderation：-c / -C

coalesce 控制网卡中断合并策略。合并更多包再中断可以降低 CPU 开销、提高吞吐；更快中断可以降低延迟但增加 CPU 压力。训练吞吐型流量和在线推理低延迟流量的偏好可能相反。

# 查看当前中断合并参数
ethtool -c ens5f0

# 保存当前值
ethtool -c ens5f0 > /tmp/ens5f0.coalesce.before.txt

# 示例：设置 RX/TX usecs。执行前先确认目标延迟和 CPU 余量。
sudo ethtool -C ens5f0 rx-usecs 16 tx-usecs 16

# 回滚示例，使用你环境中的原始值
sudo ethtool -C ens5f0 rx-usecs 8 tx-usecs 8
吞吐优先
适度中断合并可降低 CPU 中断频率，让大流量更平稳。
延迟优先
过度合并会推高尾延迟，在线推理或控制面请求需要谨慎。
CPU 饱和
如果 softirq 高、单核满，coalesce 可能缓解，但不替代队列和 IRQ 亲和性治理。
验证指标
同时看吞吐、重传、p99/p999、CPU、-S drop，而不是只看单一指标。

11. RSS、队列映射与 CPU/NUMA

ethtool 可以查看部分 RSS hash 配置和 indirection table。AI 服务器通常有多 NUMA、多 GPU、多 NIC，网络中断落在远端 NUMA 或少数 CPU 核上，会造成链路看似正常但应用吞吐低。

# 查看 RSS hash indirection table
ethtool -x ens5f0

# 查看指定协议的 hash 字段，支持取决于驱动
ethtool -n ens5f0

# 查看接口所在 NUMA 节点
cat /sys/class/net/ens5f0/device/numa_node

# 查看 IRQ 分布和 CPU softirq
grep -i ens5f0 /proc/interrupts
mpstat -P ALL 1

# 查看队列对应的 RPS/XPS 配置
for q in /sys/class/net/ens5f0/queues/rx-*; do echo "$q"; cat "$q/rps_cpus"; done
问题表现检查
RSS 没有分散多流量仍集中到少数队列ethtool -x、/proc/interrupts、队列统计
IRQ 亲和性不合理单核 softirq 高，吞吐方向不对称irqbalance、smp_affinity、NUMA 绑定
NIC/GPU 跨 NUMARDMA 或数据加载吞吐差lstopo、nvidia-smi topo -m、PCI bus-info
实践建议： ethtool -L 只解决队列数量问题；队列是否真正被 CPU 和流量均匀使用，还要继续看 RSS、IRQ、NUMA 和业务连接分布。

对照图：NCCL/RDMA 慢时 ethtool 能提供哪些线索

12. NCCL/RDMA 性能线索

在 RoCE 或高速以太网训练集群里，ethtool 的价值是快速发现主机侧明显异常，并为 NCCL/RDMA 排障提供方向。它不能替代 rdma、ibv_devinfo、ib_write_bw、mlxlink 或交换机遥测。

# 训练任务慢时，先采集 NIC 快照
iface=ens5f0
mkdir -p /tmp/net-snapshot
ethtool "$iface"       > /tmp/net-snapshot/$iface.link.txt
ethtool -i "$iface"    > /tmp/net-snapshot/$iface.driver.txt
ethtool -g "$iface"    > /tmp/net-snapshot/$iface.ring.txt
ethtool -k "$iface"    > /tmp/net-snapshot/$iface.offload.txt
ethtool -l "$iface"    > /tmp/net-snapshot/$iface.channels.txt
ethtool -S "$iface"    > /tmp/net-snapshot/$iface.stats.before.txt

# 跑一次可复现的 nccl-tests / ib_write_bw / iperf3 后再采集
ethtool -S "$iface"    > /tmp/net-snapshot/$iface.stats.after.txt
diff -u /tmp/net-snapshot/$iface.stats.before.txt /tmp/net-snapshot/$iface.stats.after.txt
应用现象ethtool 重点下一层工具
NCCL 吞吐低但 CPU 不高速率是否降级、-S 是否有错误、pause/PFC 是否异常NCCL_DEBUG=INFO、nccl-tests、交换机端口计数
iperf3 多流也跑不满channels、IRQ、ring、offload、链路速率mpstat、sar -n DEV、perf
RoCE 抖动或重传PFC/ECN/pause 相关计数、丢包错误rdma statistic、mlxlink、交换机 buffer/ECN
某些节点显著慢驱动固件版本、PCI/NUMA、队列配置是否偏离集群基线lstopo、nvidia-smi topo -m、资产系统
排障思路： 对比“快节点”和“慢节点”的 ethtool 快照，经常比单看慢节点更快发现固件、速率、队列或 offload 差异。

选择图：ethtool vs ip/ss/rdma/mlxlink

ethtool 负责 NIC 层证据，其他工具负责路由、socket、RDMA 和交换侧证据。

13. ethtool vs ip/ss/rdma/mlxlink

工具主要视角典型问题不能替代什么

14. 安全变更流程与回滚

ethtool 的修改类命令经常立即生效，部分会导致链路抖动、驱动重配、流量短暂中断或性能回退。生产环境要把它当成基础设施变更，而不是普通查询命令。

推荐流程

  1. 明确目标：降低 drop、提升吞吐、降低 CPU、降低尾延迟，不能只说“优化网卡”。
  2. 保存基线：ethtool、-i、-g、-k、-l、-c、-S。
  3. 选单台或少量节点灰度，避开训练高峰，记录维护窗口。
  4. 一次只改一类参数，例如只改 ring 或只改 channels。
  5. 跑同一套验证：iperf3、nccl-tests、业务压测、CPU、-S 计数。
  6. 准备回滚命令，并确认重启、NetworkManager、systemd-networkd 或厂商工具是否会覆盖配置。
# 采集基线
iface=ens5f0
out=/tmp/ethtool-$iface-$(date +%Y%m%d-%H%M%S)
mkdir -p "$out"
ethtool "$iface"    > "$out/link.txt"
ethtool -i "$iface" > "$out/driver.txt"
ethtool -g "$iface" > "$out/ring.txt"
ethtool -k "$iface" > "$out/offload.txt"
ethtool -l "$iface" > "$out/channels.txt"
ethtool -c "$iface" > "$out/coalesce.txt"
ethtool -S "$iface" > "$out/stats.before.txt"

# 示例灰度：只改 ring
sudo ethtool -G "$iface" rx 4096 tx 4096

# 验证后采集
ethtool -S "$iface" > "$out/stats.after.txt"
diff -u "$out/stats.before.txt" "$out/stats.after.txt"

# 回滚使用基线中的原始值，不要照抄示例数字
sudo ethtool -G "$iface" rx 1024 tx 1024
不要这样做： 不要在所有 GPU 节点上直接循环执行 sudo ethtool -K $iface gro off 或 sudo ethtool -L $iface combined 64，除非已有灰度数据和回滚策略。

15. 常见故障场景与排障

场景 1：100G 网卡只协商到 25G
查 ethtool DEV 的 Speed、advertised modes、link partner advertised；继续查模块、线缆、交换机端口 profile、分叉模式和 FEC。
场景 2：iperf3 多流跑不满
查 -l 队列数、/proc/interrupts、CPU softirq、RSS、offload 和 -S drop。
场景 3：NCCL 某些节点慢
对比快慢节点的 -i、-g、-k、-l、-S，再看 GPU/NIC NUMA 拓扑。
场景 4：抓包显示 checksum 错误
先查 checksum offload。发送侧抓包看到 checksum “bad” 可能只是硬件尚未填充校验和。
场景 5：突发时丢包
用测试前后 -S diff 找 rx_missed/no_buffer/drop，结合 ring、channels、coalesce 和交换机队列。
场景 6：低延迟推理尾延迟升高
检查 GRO/LRO、coalesce、ring 深度和 CPU 争用；吞吐优化参数可能不适合低延迟服务。

排障模板

iface=ens5f0
peer=10.20.30.40

echo "== route =="
ip route get "$peer"

echo "== link =="
ethtool "$iface" | egrep 'Speed|Duplex|Auto-negotiation|Link detected'

echo "== driver =="
ethtool -i "$iface"

echo "== queues =="
ethtool -g "$iface"
ethtool -l "$iface"

echo "== offload =="
ethtool -k "$iface" | egrep 'tcp-segmentation|generic-segmentation|generic-receive|large-receive|checksum'

echo "== suspicious stats =="
ethtool -S "$iface" | egrep -i 'drop|discard|error|crc|miss|pause|pfc|ecn|timeout|reset'

16. 自动化基线采集

对 AI 集群来说，ethtool 最有价值的用法之一是周期性或验收时采集基线。出现性能异常时，用快慢节点、变更前后、不同机架之间的基线 diff 快速定位偏差。

#!/usr/bin/env bash
set -euo pipefail

out=${1:-/tmp/ethtool-baseline-$(hostname)-$(date +%Y%m%d-%H%M%S)}
mkdir -p "$out"

# 只采集物理接口示例：按需调整过滤规则
for iface in $(ls /sys/class/net | grep -Ev '^(lo|docker|veth|cni|flannel|br-|virbr)'); do
  echo "collect $iface"
  {
    echo "### ip addr"
    ip -br addr show dev "$iface" || true
    echo "### ethtool link"
    ethtool "$iface" || true
    echo "### driver"
    ethtool -i "$iface" || true
    echo "### ring"
    ethtool -g "$iface" || true
    echo "### offload"
    ethtool -k "$iface" || true
    echo "### channels"
    ethtool -l "$iface" || true
    echo "### coalesce"
    ethtool -c "$iface" || true
    echo "### stats"
    ethtool -S "$iface" || true
  } > "$out/$iface.txt"
done

echo "saved to $out"
基线字段建议： 至少保留接口名、MAC、PCI bus-info、driver、firmware-version、Speed、ring、channels、offload、coalesce 和关键 -S 计数。
脚本提醒： 采集脚本可以宽容失败；变更脚本不能宽容失败。不要把只读采集脚本改成批量调参脚本后直接跑全量节点。

17. 学习路线与练习任务

第一阶段：会读状态

  • 用 ip route get 找到访问目标节点的实际出口接口。
  • 用 ethtool DEV 判断链路是否 up、速率是否符合预期。
  • 用 ethtool -i DEV 记录驱动、固件和 PCI bus-info。

第二阶段：会定位性能线索

  • 用 -g、-l、-k 理解 ring、channels、offload 当前配置。
  • 用 -S 做测试前后 diff，找增长的 drop/error/pause 计数。
  • 把 ethtool 输出和 iperf3、NCCL 日志、CPU softirq 对齐。

第三阶段：会安全变更

  • 每次只改一个变量，例如只改 ring 或只改 coalesce。
  • 写下变更假设、验证指标和回滚命令。
  • 先在单节点或小流量窗口灰度，再考虑集群推广。

练习

  1. 找出一台机器上所有物理接口，并记录每个接口的 speed、driver、firmware-version。
  2. 对某个接口执行 ethtool -S，过滤 drop/error/pause 相关计数。
  3. 跑一次 iperf3 前后分别采集 -S，用 diff -u 观察哪些计数增长。
  4. 比较两台同型号节点的 ethtool -i 和 -l 输出，找出差异。
  5. 在非生产测试接口上修改 ring，并用基线值回滚。
  6. 关闭再恢复 gro，观察抓包和 CPU 使用变化；不要在生产接口长期关闭。
