/proc/<pid>/status、smaps、stack 深度教程

这份教程面向 AI Infra 和 Linux 生产排障：用 /proc/<pid>/status 快速读进程身份、线程数、内存高水位、CPU/NUMA 亲和性；用 smaps 与 smaps_rollup 拆解匿名页、文件映射、共享库、PSS/RSS；用 stack 观察线程在内核态卡在哪里。重点不是背字段，而是建立“单进程内省 → 训练任务症状 → 容器/cgroup/NUMA/线程根因”的诊断路径。

一句话理解： /proc/<pid>/status 是进程健康摘要，smaps 是内存映射账本，stack 是内核态调用栈快照；三者合起来能解释“这个训练进程到底占了多少内存、被限制在哪些 CPU/NUMA 节点、线程是否异常、是否卡在内核 I/O 或 futex”。
生产原则： 这些文件主要是只读观察，但仍要控制频率和权限范围；smaps 对超大进程读取成本较高，线上优先用 smaps_rollup 做汇总，只有需要定位具体映射时再读完整 smaps。

1. /proc/<pid> 是什么

/proc 是 Linux 内核暴露运行时状态的伪文件系统。/proc/<pid> 不是磁盘上的真实目录，而是内核按需生成的单个进程视图。AI Infra 排障中，它常用于回答四类问题：进程是谁、吃了多少内存、被调度在哪些 CPU/NUMA 节点、是否卡在内核态。

身份
Name、Pid、PPid、Uid、Gid、NStgid 帮你确认看到的是不是目标 worker。
内存
VmRSS、VmHWM、RssAnon、RssFile、smaps 帮你区分当前驻留、历史峰值和映射来源。
调度
Threads、Cpus_allowed_list、Mems_allowed_list 暴露线程数、CPU 绑定和 NUMA 限制。
卡顿
stack、wchan、stat 可辅助判断线程是否阻塞在 futex、I/O、内存回收或驱动路径。
# 当前 shell 的 proc 视图
cat /proc/$$/status
head -40 /proc/$$/smaps
cat /proc/$$/smaps_rollup 2>/dev/null || echo "kernel does not expose smaps_rollup"

# 对目标 PID 读取摘要
pid=12345
grep -E '^(Name|State|Pid|PPid|Uid|Threads|VmRSS|VmHWM|RssAnon|RssFile|Cpus_allowed_list|Mems_allowed_list):' /proc/$pid/status
动态性提醒： /proc/<pid> 是瞬时快照。训练进程、DataLoader worker、NCCL helper 线程都可能在你读取时变化；做结论前最好连续采样。

信息图：status、smaps、stack 的整体分工

心智模型：status 快速判定方向，smaps 定量拆账，stack 在进程“看起来没动”时提供内核态线索。

2. 安全找到目标 PID

不要只凭进程名猜 PID。AI 训练任务里可能同时存在 launcher、rank 进程、DataLoader worker、torch elastic agent、NCCL helper、Python 子进程和容器 shim。先确认命令行、父子关系、容器和用户，再读取 proc 文件。

# 按命令行查找，避免只看到 python 这个泛名
pgrep -af 'torchrun|deepspeed|train.py|python'

# 展示父子关系，确认 launcher 与 rank 进程
ps -eo pid,ppid,user,stat,comm,args --forest | grep -E 'torchrun|deepspeed|train.py|python' | grep -v grep

# 选择一个 PID 后，确认身份和命令行
pid=12345
tr '\0' ' ' < /proc/$pid/cmdline; echo
grep -E '^(Name|State|Pid|PPid|Uid|Gid|NStgid|Threads):' /proc/$pid/status
字段/文件用途排障价值
/proc/<pid>/cmdlineNUL 分隔的启动参数确认具体 rank、脚本、配置文件和环境传参。
/proc/<pid>/environNUL 分隔的环境变量可查 OMP_NUM_THREADS、CUDA_VISIBLE_DEVICES、NCCL_*，但权限更敏感。
/proc/<pid>/status身份、状态、内存、亲和性摘要最适合第一眼快速检查。
/proc/<pid>/task/线程目录逐线程看 status、stack、wchan。
权限提醒： cmdline 和 status 通常较容易读；environ、stack、跨用户进程和开启 hidepid/ptrace_scope 的系统可能需要同 UID、root 或额外 capability。不要为了排障扩大权限后忘记恢复安全基线。

3. status：进程摘要与身份

/proc/<pid>/status 是面向人读的摘要文件，字段比 stat 稳定易读。它很适合在训练任务异常时先扫一遍：进程状态是否可运行、线程数是否膨胀、内存是否接近限制、CPU/NUMA 是否被错误绑定。

pid=12345
awk '
/^(Name|State|Tgid|Pid|PPid|TracerPid|Uid|Gid|FDSize|Threads|VmPeak|VmSize|VmHWM|VmRSS|RssAnon|RssFile|RssShmem|VmSwap|HugetlbPages|Cpus_allowed_list|Mems_allowed_list):/ {
  print
}' /proc/$pid/status
字段含义AI Infra 读法
State运行、睡眠、僵尸、停止等状态D 常提示不可中断 I/O 或内核等待；R 多但吞吐低要看 CPU 绑定和调度竞争。
TracerPid是否被调试器/追踪器附加非 0 时，strace、profiler 或安全代理可能改变行为。
FDSize文件描述符表容量数据集、日志、socket 泄漏可导致 fd 增长；需要结合 /proc/<pid>/fd。
voluntary_ctxt_switches、nonvoluntary_ctxt_switches上下文切换计数线程过多或锁竞争时计数增长快，需结合 pidstat -w。
读法建议： 先用 grep -E 抽字段，不要把完整 status 粘到告警里；稳定字段加上时间戳，连续采样更有价值。

4. VmRSS、VmHWM 与内存高水位

VmRSS 是当前驻留在物理内存中的页总量；VmHWM 是历史驻留高水位。训练任务出现 OOM、被 kubelet 驱逐或 cgroup 接近上限时，这两个字段能快速判断“现在高”还是“曾经高”。

VmRSS
当前 resident set size。包括匿名页、文件页和共享内存驻留部分，但共享页会被每个进程重复计入。
VmHWM
RSS 历史峰值。训练 warmup、模型加载、checkpoint、dataset cache 可能让峰值远高于当前值。
VmSize
虚拟地址空间大小。CUDA、mmap、allocator arena 可能让它很大，不等于真实物理内存占用。
# 连续观察 RSS 与高水位，适合训练启动和 checkpoint 阶段
pid=12345
while sleep 2; do
  date '+%F %T'
  grep -E '^(VmRSS|VmHWM|RssAnon|RssFile|RssShmem|VmSwap|HugetlbPages):' /proc/$pid/status
  echo
done
现象可能解释下一步
VmHWM 高，VmRSS 已回落阶段性峰值，例如加载权重、构建索引、checkpoint 临时 buffer。对齐日志时间点；看 cgroup OOM 记录和训练阶段。
VmRSS 持续上升缓存无界、DataLoader prefetch、Python 对象增长、C++ allocator 未释放。用 smaps_rollup 判断匿名页还是文件页增长。
VmSize 极大但 VmRSS 不高虚拟预留、mmap、CUDA 或 malloc arena 地址空间。不要仅凭 VIRT/VmSize 报警。
口径提醒： VmRSS 对共享页重复计数，多个 rank 加总可能虚高。跨进程归因优先看 PSS，它来自 smaps/smaps_rollup。

5. Threads 与 AI 训练线程膨胀

Threads 是进程内线程数量。AI 任务线程数异常常来自 OpenMP/MKL/OpenBLAS、DataLoader worker、数据解码库、gRPC/HTTP clients、日志/监控 agent 或 native runtime。线程过多会造成上下文切换、内存栈开销、CPU 抢占和 NUMA 迁移。

pid=12345
grep '^Threads:' /proc/$pid/status
ls /proc/$pid/task | wc -l

# 找出每个线程名和状态
for tid in /proc/$pid/task/*; do
  awk '/^(Name|State|Tgid|Pid):/ {printf "%s ", $0} END {print ""}' "$tid/status"
done | head -30
检查点命令解释
线程总数grep '^Threads:' /proc/$pid/status和预期的 rank、DataLoader、BLAS 线程配置对比。
线程状态grep '^State:' /proc/$pid/task/*/status大量 D 看 I/O；大量 sleeping 不一定异常，要看栈和吞吐。
CPU 亲和性grep Cpus_allowed_list /proc/$pid/task/*/status线程级亲和性可能不同于进程主线程。
运行开销pidstat -t -p $pid 1看线程级 CPU、上下文切换和调度。
实践建议： 训练入口脚本中显式记录 OMP_NUM_THREADS、MKL_NUM_THREADS、OPENBLAS_NUM_THREADS、DataLoader num_workers 和 CPU 绑定策略，排障时能少猜很多。

6. Cpus_allowed 与 CPU 亲和性

Cpus_allowed 是十六进制位图，Cpus_allowed_list 是更好读的 CPU 列表。AI 节点上它常由 taskset、Kubernetes CPU Manager、cpuset cgroup、systemd 或作业调度器设置。错误绑定会导致 GPU 供数不足、NCCL helper 线程竞争、NUMA 远端访问增多。

pid=12345
grep -E '^Cpus_allowed|^Mems_allowed' /proc/$pid/status

# 主线程与子线程可能不同，抽样检查线程级 CPU mask
for tid in /proc/$pid/task/*; do
  printf '%s ' "${tid##*/}"
  grep '^Cpus_allowed_list:' "$tid/status"
done | head -20

# 与 lscpu/numactl 对照
lscpu -e=CPU,NODE,SOCKET,CORE | head
numactl --hardware
绑定太窄
DataLoader 和通信线程抢少量 CPU，GPU 利用率呈锯齿，top -H 看到少数核打满。
绑定跨 NUMA
CPU 列表跨 socket，但内存或 GPU 亲和在另一侧，可能增加远端内存访问和 PCIe/NVLink 路径成本。
线程级差异
某些 runtime 会在线程创建后设置 affinity，排障不能只看主进程一行。
读法： Cpus_allowed_list: 0-31 说明该线程可在 0 到 31 号 CPU 上运行；这不代表它当前正在这些 CPU 上平均运行，实际调度还要看 ps -L -o psr 或 pidstat -t。

7. Mems_allowed 与 NUMA 节点

Mems_allowed/Mems_allowed_list 表示进程允许在哪些 NUMA memory node 分配内存。AI 训练通常同时关心 GPU locality、CPU locality、host memory、page cache 和 pinned memory。若 CPU 可跨节点运行但内存只允许某个节点，或容器 cpuset 与 NUMA 策略不匹配，就可能出现远端访问、局部 OOM 或吞吐抖动。

pid=12345
grep -E '^Mems_allowed|^Cpus_allowed' /proc/$pid/status
numactl --show
numastat -p $pid 2>/dev/null || true

# 如果在容器中，主机侧也要看 cpuset cgroup
cat /proc/$pid/cgroup
grep -R . /sys/fs/cgroup/* 2>/dev/null | grep -E 'cpuset.cpus|cpuset.mems' | head
信号风险排查动作
Mems_allowed_list 只有一个节点该节点内存压力高时容易局部回收或 OOM。对照 numactl -H、cgroup cpuset 和作业调度策略。
CPU 允许多个 socket，mems 只允许一个 node跨 socket 线程可能远端访问内存。检查 CPU/GPU topology，必要时统一绑定。
容器内看到的 CPU/mem 与主机不一致namespace/cgroup 视图造成误判。在主机 PID namespace 读取目标进程 proc。
NUMA 提醒： Mems_allowed 说明“允许在哪里分配”，不直接说明“已经分配在哪里”。已经分布在哪里要看 numastat -p、/proc/<pid>/numa_maps 或 perf/PMU。

流程图：从 status 到 smaps 的内存诊断路径

内存排障先看摘要，再决定是否读取较重的 smaps。不要上来就把几十万行 smaps 扔进日志。

8. smaps：逐映射内存账本

/proc/<pid>/smaps 以 VMA（virtual memory area）为单位列出映射区间，每个区间后面跟一组内存统计。它能回答：RSS 来自堆、匿名 mmap、共享库、文件 mmap、tmpfs/shmem、线程栈，还是大页。

pid=12345
head -80 /proc/$pid/smaps

# 只看映射头，快速了解地址空间组成
grep -E '^[0-9a-f]+-[0-9a-f]+' /proc/$pid/smaps | head -40

# 按字段粗略汇总 KiB
awk '
/^Rss:/ {rss += $2}
/^Pss:/ {pss += $2}
/^Private_Dirty:/ {pd += $2}
/^Shared_Clean:/ {sc += $2}
END {printf "Rss=%d MiB Pss=%d MiB Private_Dirty=%d MiB Shared_Clean=%d MiB\n", rss/1024, pss/1024, pd/1024, sc/1024}
' /proc/$pid/smaps
smaps 字段含义常见 AI 场景
Size映射虚拟大小不等于已驻留；大 mmap 可能只触碰一部分。
Rss该映射驻留物理页判断哪个 VMA 正在占 RAM。
Pss按共享比例分摊后的 RSS多个 rank 共享库和文件页时，PSS 更适合加总。
Private_Dirty进程独占且被修改的页Python 对象、模型 CPU 副本、allocator 堆增长常体现在这里。
Shared_Clean共享且干净的页共享库、只读 mmap 数据集、page cache 映射。
Anonymous匿名内存堆、匿名 mmap、运行时 buffer；通常和 CPU RAM 压力相关。
Lockedmlock 锁定页pinned memory、RDMA 或特定 runtime 可能导致不可回收内存。
成本提醒： 读取 smaps 需要内核遍历映射和页表统计，超大进程上可能有可感知开销。监控系统不要高频全量抓取。

9. smaps_rollup：快速总览

/proc/<pid>/smaps_rollup 提供整个进程的汇总统计，适合告警、采样和第一轮判断。它不告诉你具体哪个映射异常，但能快速区分 RSS、PSS、匿名页、共享页和 swap 的大方向。

pid=12345
cat /proc/$pid/smaps_rollup

# 连续记录 rollup，观察增长来自哪里
while sleep 5; do
  printf '\n== %s ==\n' "$(date '+%F %T')"
  awk '/^(Rss|Pss|Private_Clean|Private_Dirty|Shared_Clean|Shared_Dirty|Anonymous|Swap|Locked):/ {print}' /proc/$pid/smaps_rollup
done
适合
低频采样、趋势判断、PSS 口径、告警现场快速摘要。
不适合
定位具体 VMA、找哪个文件 mmap、区分 heap 与某段匿名 mmap。
兼容性
较老内核可能没有 smaps_rollup；脚本要有 fallback。
# 带 fallback 的读取方式
pid=12345
if [ -r /proc/$pid/smaps_rollup ]; then
  awk '/^(Rss|Pss|Anonymous|Swap|Locked):/ {print}' /proc/$pid/smaps_rollup
else
  awk '/^Rss:/ {rss += $2} /^Pss:/ {pss += $2} /^Anonymous:/ {anon += $2} END {print "Rss:", rss, "kB\nPss:", pss, "kB\nAnonymous:", anon, "kB"}' /proc/$pid/smaps
fi

10. RSS、PSS、Private 与 Shared

AI 节点上常见误判是把多个进程的 RSS 直接相加，得出“内存不够”的错误结论。共享库、只读文件 mmap、fork 后共享页会在每个进程 RSS 中重复出现。PSS 把共享页按共享者数量分摊，更适合跨 rank 或 worker 加总。

口径含义什么时候用风险
RSS进程可见的驻留页总和，共享页重复计入看单进程当前驻留压力多进程加总会虚高
PSS共享页按比例分摊估算一组进程对物理内存的公平占用读取成本比 status 高
Private_Clean/Dirty只有该进程使用的页定位不可共享的真实增长clean 页仍可能被回收，dirty 页回收成本更高
Shared_Clean/Dirty多个进程共享的页判断共享库、mmap 数据集、tmpfsshared dirty 可能与 shmem、IPC、fork 写时复制相关
# 汇总同一用户下训练进程的 PSS，避免 RSS 简单相加
for pid in $(pgrep -u "$USER" -f 'train.py|torchrun|deepspeed'); do
  awk -v pid="$pid" '
    /^Name:/ {name=$2}
    /^Pss:/ {pss += $2}
    END {printf "pid=%s name=%s pss=%.1f MiB\n", pid, name, pss/1024}
  ' /proc/$pid/smaps 2>/dev/null
done
判断经验： Private_Dirty 持续增长更像进程独占内存增长；Shared_Clean 高常见于共享库和只读 mmap；Anonymous 高通常比 RssFile 更值得关注训练进程自身。

对比图：proc 文件、ps、free、pmap 的观测口径

11. AI 训练内存诊断流程

训练任务内存问题通常不是一个数字能解释。模型加载、CPU offload、dataset cache、DataLoader prefetch、tokenizer、checkpoint、通信 buffer、pinned memory 和 mmap 数据集都可能改变宿主机内存曲线。下面是一个低风险诊断顺序。

  1. 用 free -h 或 /proc/meminfo 确认节点是否真的有内存压力。
  2. 用 ps 或 pgrep -af 找到训练主进程、rank 进程和 worker。
  3. 读取每个进程 status，记录 VmRSS、VmHWM、Threads、VmSwap。
  4. 读取 smaps_rollup，比较 Pss、Anonymous、Shared_Clean、Private_Dirty。
  5. 只有在需要归因具体映射时，才读取完整 smaps 并按映射名聚合。
  6. 把采样时间和训练日志阶段对齐：init、load checkpoint、first batch、eval、save checkpoint。
# 轻量采样模板：每 10 秒记录 status + smaps_rollup 核心字段
pid=12345
out=/tmp/proc-memory-$pid.log
while sleep 10; do
  {
    echo "== $(date '+%F %T') pid=$pid =="
    grep -E '^(State|Threads|VmRSS|VmHWM|RssAnon|RssFile|RssShmem|VmSwap):' /proc/$pid/status
    awk '/^(Rss|Pss|Anonymous|Private_Dirty|Shared_Clean|Swap|Locked):/ {print}' /proc/$pid/smaps_rollup 2>/dev/null
  } >> "$out"
done
报告模板： “节点 available memory 从 A 到 B；rank 0 VmRSS 从 X 到 Y，VmHWM 为 Z；smaps_rollup 显示 Anonymous/Private_Dirty 增长；增长发生在 first batch 后 3 分钟。” 这比“内存爆了”可行动得多。

12. stack：内核调用栈快照

/proc/<pid>/stack 显示目标任务当前在内核态的调用栈。更常用的是逐线程读取 /proc/<pid>/task/<tid>/stack，因为一个训练进程可能有上百个线程，只有少数线程真正卡住。它不能显示 Python 栈或用户态 C++ 栈；如果线程在用户态运行，可能看到空或非常短的内核栈。

pid=12345

# 主线程内核栈
sudo cat /proc/$pid/stack

# 逐线程查看 wchan 与 kernel stack，适合进程吞吐停滞时抽样
for tid in /proc/$pid/task/*; do
  tid=${tid##*/}
  printf '\n== tid=%s wchan=' "$tid"
  cat /proc/$pid/task/$tid/wchan 2>/dev/null || true
  echo
  sudo cat /proc/$pid/task/$tid/stack 2>/dev/null | head -20
done
常见线索可能含义下一步
futex_wait、do_futex锁、条件变量、线程池等待；不一定异常。结合用户态 profiler、py-spy、gdb 或应用日志。
io_schedule、块设备路径磁盘或网络文件系统 I/O 等待。看 iostat、pidstat -d、存储日志。
page_fault、内存回收路径缺页、mmap 数据集、内存压力或 page cache 行为。结合 perf、vmstat、numastat。
驱动相关符号GPU、RDMA、文件系统或网络驱动路径。保留现场，结合驱动日志和厂商工具。
边界提醒： stack 是内核态视角，不是 Python traceback。想看 Python 代码停在哪里，用 py-spy、faulthandler、gdb py-bt 或框架 profiler；想看系统调用，用 strace -p，但附加追踪本身会影响进程。

13. 权限、安全与生产影响

读取 proc 文件看起来简单，但在多租户训练平台上属于安全边界的一部分。跨用户读取进程细节可能泄露命令行、路径、环境变量、模型名、数据集位置或密钥。生产平台需要明确谁能读、从哪里读、采样频率是多少。

机制影响排障动作
/proc 挂载参数 hidepid限制普通用户查看其他用户进程。如果看不到目标 PID，先查 mount | grep ' /proc '。
kernel.yama.ptrace_scope限制 ptrace 相关访问，可能影响 stack、调试器和 profiler。确认安全策略，避免临时改完不恢复。
容器 capability缺少 SYS_PTRACE 或主机 PID 视图时无法深入观察。优先从节点侧或受控 debug 容器观察。
高频读取 smaps对大进程有额外遍历成本。用 smaps_rollup 低频采样，完整 smaps 留给人工定位。
# 检查 proc 挂载参数和 ptrace 策略
mount | grep ' /proc '
cat /proc/sys/kernel/yama/ptrace_scope 2>/dev/null || true

# 检查当前用户是否能读目标文件
pid=12345
for f in status smaps smaps_rollup stack; do
  [ -r /proc/$pid/$f ] && echo "readable: $f" || echo "not readable: $f"
done
生产习惯： 排障脚本默认只读，不自动 sudo，不采集 environ，不把完整 cmdline 和路径上传到公共日志，除非有明确脱敏策略。

14. 容器、PID namespace 与 cgroup

容器里看到的 PID 和主机 PID 可能不同；容器内 /proc/1/status 可能是容器 init，而主机上同一进程有另一个 PID。status 中的 NStgid/NSpid 可以帮助跨 namespace 对齐。内存限制、CPU 限制和 NUMA 限制则主要来自 cgroup。

# 在主机上查看一个容器进程的 namespace PID 映射
pid=12345
grep -E '^(Pid|Tgid|NStgid|NSpid|NSpgid|NSsid):' /proc/$pid/status
cat /proc/$pid/cgroup

# cgroup v2 常见文件
cg=$(awk -F: '$1=="0"{print $3}' /proc/$pid/cgroup)
base=/sys/fs/cgroup$cg
cat "$base/memory.current" 2>/dev/null
cat "$base/memory.max" 2>/dev/null
cat "$base/cpuset.cpus.effective" 2>/dev/null
cat "$base/cpuset.mems.effective" 2>/dev/null
容器内读 proc
方便、权限较小，但只看到容器 namespace 和挂载视图；有些 host 信息不可见。
节点侧读 proc
能看到真实主机 PID、cgroup 路径和完整 topology，但需要平台授权和审计。
cgroup memory
容器 OOM 由 cgroup 限制决定，不是只看整机 free。
cpuset
Cpus_allowed_list 通常反映 cpuset 结果，但线程级亲和性仍可能进一步收窄。
Kubernetes 读法： Pod 内 ps 看到的 PID 不一定能在节点侧直接用；用容器 runtime、crictl inspect 或 NSpid 做映射，再读主机 /proc/<host-pid>。

15. proc 文件 vs ps/free/pmap

ps、free、pmap 很多信息本质上来自 proc，但它们做了汇总、格式化或口径选择。理解底层 proc 文件，可以避免把不同工具的字段混用。

工具/文件层次优势常见误区
/proc/<pid>/status单进程摘要轻量、字段清楚、脚本友好VmRSS 不是 PSS，多进程加总可能虚高。
/proc/<pid>/smaps单进程逐映射归因最细，有 PSS 和 private/shared读取较重，不适合高频全量监控。
ps进程列表排序、扫描方便VSZ 常被误认为真实内存占用。
free//proc/meminfo整机判断节点总压力和 page cache不能说明哪个进程负责。
pmap -x进程映射展示比手读 smaps 更易扫不同实现字段口径有差异，仍需回到 smaps 确认。
# 三种视角并排看
pid=12345
ps -o pid,ppid,stat,threads,vsz,rss,comm,args -p $pid
grep -E '^(VmSize|VmRSS|VmHWM|Threads):' /proc/$pid/status
pmap -x $pid | tail -20
推荐表达： 报告里写“/proc/$pid/smaps_rollup 的 PSS 为 18.4 GiB”，不要只写“进程占 18G”，否则别人不知道是 RSS、PSS、VIRT、cgroup current 还是整机 used。

排障图：训练慢、内存高、线程多、NUMA 异常怎么分流

排障不要从“读哪个文件”开始，而要从症状分流：慢、涨、卡、错绑分别对应不同 proc 证据。

16. 排障场景与命令模板

场景 A：GPU 空转但进程还在

pid=12345
grep -E '^(State|Threads|Cpus_allowed_list|Mems_allowed_list):' /proc/$pid/status
pidstat -t -p $pid 1 5
for tid in /proc/$pid/task/*; do
  tid=${tid##*/}
  printf '%s ' "$tid"
  cat /proc/$pid/task/$tid/wchan 2>/dev/null
done | sort | uniq -c | sort -nr | head

如果大量线程在 futex，可能是等待数据、锁或线程池；如果在 I/O 路径，转向存储；如果 CPU 亲和性很窄，检查 cpuset 和 DataLoader 配置。

场景 B：容器被 OOMKilled，但进程 RSS 看起来不夸张

pid=12345
cat /proc/$pid/cgroup
grep -E '^(VmRSS|VmHWM|RssAnon|RssFile|RssShmem):' /proc/$pid/status
awk '/^(Rss|Pss|Anonymous|Private_Dirty|Shared_Clean|Swap):/ {print}' /proc/$pid/smaps_rollup

# cgroup v2，节点侧执行
cg=$(awk -F: '$1=="0"{print $3}' /proc/$pid/cgroup)
cat /sys/fs/cgroup$cg/memory.current /sys/fs/cgroup$cg/memory.max 2>/dev/null

容器 OOM 看的是 cgroup 账本，可能包含多个进程和 page cache；单个进程 VmRSS 不是完整答案。

场景 C：只在多卡训练时 host 内存飙升

# 对所有 rank 汇总 PSS 与线程数
for pid in $(pgrep -f 'train.py|torchrun|deepspeed'); do
  threads=$(awk '/^Threads:/ {print $2}' /proc/$pid/status)
  pss=$(awk '/^Pss:/ {s+=$2} END {printf "%.1f", s/1024}' /proc/$pid/smaps 2>/dev/null)
  cmd=$(tr '\0' ' ' < /proc/$pid/cmdline | cut -c1-100)
  printf 'pid=%s threads=%s pss=%sMiB cmd=%s\n' "$pid" "$threads" "$pss" "$cmd"
done

对比各 rank 的 PSS 和线程数，能发现 rank 0 额外加载验证集、checkpoint 或日志组件的问题。

17. 限制、陷阱与检查清单

陷阱 1：把 VIRT 当内存占用
VmSize/VSZ 是虚拟地址空间，不等于物理内存压力。
陷阱 2：RSS 多进程相加
共享页重复计入，多个 rank 应优先用 PSS。
陷阱 3：只看主线程
线程级 status、wchan、stack 更适合定位卡顿。
陷阱 4：容器 PID 混淆
容器内 PID 和主机 PID 不同，注意 NSpid。
陷阱 5：高频读 smaps
大进程上有成本，自动化采样优先 smaps_rollup。
陷阱 6：stack 当用户态栈
stack 是内核栈，不是 Python traceback。

生产检查清单

  • 确认 PID、用户、容器、rank 和命令行，不对泛名 python 下结论。
  • 记录时间戳，至少连续采样 3 到 5 次，避免把瞬时抖动当趋势。
  • 内存报告区分 VmRSS、VmHWM、PSS、cgroup memory 和整机 available。
  • CPU/NUMA 报告同时写 Cpus_allowed_list、Mems_allowed_list、节点拓扑和容器 cpuset。
  • 卡顿报告同时给出 State、wchan、关键线程 stack 和应用日志阶段。
  • 采集脚本默认只读、低频、脱敏，不把环境变量和敏感路径发到公共系统。
# 最小只读现场包，按需执行，不采集 environ
pid=12345
dir=/tmp/proc-snapshot-$pid-$(date +%Y%m%d-%H%M%S)
mkdir -p "$dir"
cp /proc/$pid/status "$dir/status"
tr '\0' ' ' < /proc/$pid/cmdline > "$dir/cmdline.txt"
cat /proc/$pid/cgroup > "$dir/cgroup.txt"
cat /proc/$pid/smaps_rollup > "$dir/smaps_rollup.txt" 2>/dev/null || true
find /proc/$pid/task -maxdepth 2 -name status -print -exec sh -c 'echo "== $1 =="; grep -E "^(Name|State|Pid|Threads|Cpus_allowed_list|Mems_allowed_list):" "$1"' _ {} \; > "$dir/task-status.txt" 2>/dev/null
echo "$dir"

18. 学习路线与练习任务

第一阶段：会读摘要

  • 用自己的 shell PID 练习 /proc/$$/status，理解 Pid、PPid、State、Threads。
  • 观察一个长期运行进程的 VmRSS、VmHWM，理解当前值与峰值差异。
  • 用 Cpus_allowed_list 对照 taskset -pc $$。

第二阶段：会做内存归因

  • 读取 smaps_rollup，区分 Rss、Pss、Anonymous、Private_Dirty。
  • 用 awk 汇总 smaps，确认 rollup 与手工汇总的大致一致。
  • 找出 [heap]、[stack]、共享库和文件 mmap 的映射头。

第三阶段：结合 AI Infra 现场

  • 在测试训练任务中对齐 first batch、eval、checkpoint 与 proc 内存曲线。
  • 比较不同 num_workers、OMP_NUM_THREADS 下 Threads 和吞吐。
  • 在容器内外分别读取同一进程，理解 NSpid 和 cgroup 限制。
# 本机无风险练习：只读取当前 shell 和 sleep 进程
sleep 300 &
pid=$!
grep -E '^(Name|State|Pid|PPid|Threads|VmRSS|VmHWM|Cpus_allowed_list|Mems_allowed_list):' /proc/$pid/status
cat /proc/$pid/smaps_rollup 2>/dev/null | awk '/^(Rss|Pss|Anonymous):/ {print}'
kill "$pid"
练习提醒： 最后一行 kill "$pid" 只终止你刚启动的 sleep 练习进程；不要把模板直接套到生产训练 PID 上。
