1. mpstat 是什么

mpstat 的名字来自 multi-processor statistics。它读取 Linux 内核暴露的 CPU 时间计数，按采样间隔计算百分比，并可以把结果拆到每个逻辑 CPU。对 AI Infra 来说，它的价值在于快速回答三个问题：CPU 是否足够忙、忙在哪一类内核时间、忙得是否均匀。

它擅长什么
低开销观察总体 CPU、每核 CPU、软中断、iowait、steal、guest 等时间占比，适合训练/推理节点的第一轮体检。
它不擅长什么
不能告诉你具体函数热点、具体线程栈、具体磁盘队列、具体网络包路径。需要继续用 perf、pidstat、iostat、ss 等工具。
它的本质
时间窗口里的 CPU 时间分账：逻辑 CPU 在这一秒里把时间花在 user、system、iowait、softirq、idle 等桶里的比例。
# 每 1 秒输出一次所有 CPU 的利用率
mpstat -P ALL 1

# 采样 5 次后退出，适合保存证据
mpstat -P ALL 1 5

# 只看总体 CPU
mpstat 1

# 显示时间戳，保存到排障记录
mpstat -P ALL 1 10 | tee mpstat.$(date +%F-%H%M%S).log
关键边界： mpstat 展示的是 CPU 时间分布，不是 GPU 利用率，也不是进程级根因。看到异常后要继续向进程、线程、NUMA、I/O 或网络层下钻。

信息图：mpstat 的整体心智模型

mpstat 不看瞬时“当前正在跑什么”，而是看一个采样窗口内每个 CPU 的时间分账。

3. 基本语法与输出字段

mpstat [options] [interval [count]]

# interval：采样间隔，单位秒
# count：采样次数；省略时持续输出
# -P：选择 CPU，ALL 表示每个逻辑 CPU 都输出
字段含义AI Infra 解读
%usr用户态普通进程占用 CPU 时间Python dataloader、预处理、tokenizer、推理服务业务逻辑常体现在这里。
%nicenice 调整过优先级的用户态进程如果批处理任务被 nice 降权，可能在这里看到消耗。
%sys内核态执行时间系统调用、内核网络栈、文件系统、驱动路径增加时会升高。
%iowaitCPU 空闲且系统有未完成 I/O 请求的时间数据集读取、网络存储、checkpoint 写入、日志刷盘可能让它抬高。
%irq硬中断处理时间高包量网卡或设备中断异常时关注。
%soft软中断处理时间网络收发、存储、内核 softirq 压力常见信号。
%steal虚拟机等待宿主机调度 CPU 的时间云上实例被邻居或宿主机超卖影响时会升高。
%guest/%gnice运行虚拟 CPU 的时间嵌套虚拟化或宿主机场景才常见。
%idle空闲时间GPU 低利用且 CPU 大量 idle，常说明瓶颈不在 CPU 算力本身。

4. per-CPU 视角：-P ALL

AI 训练节点通常有几十到上百个逻辑 CPU。总体利用率只能说明平均情况，无法揭示单核打满、软中断集中、NUMA 局部热点、进程亲和性配置错误等问题。排障时应默认使用 -P ALL。

# 每秒采样，显示每个逻辑 CPU
mpstat -P ALL 1

# 只观察 CPU 0、1、32、33，适合验证特定 NUMA 节点或亲和性
mpstat -P 0,1,32,33 1

# 保存 60 秒证据，避免凭感觉判断
mpstat -P ALL 1 60 > /tmp/mpstat.percpu.log
现象常见原因下一步
单个 CPU %usr 接近 100%单线程 Python、tokenizer、压缩/解压、日志格式化、全局锁pidstat -t -u 1 找线程；py-spy 或 perf top 看热点。
少数 CPU %soft 高网卡 RX 队列、RPS/RFS、存储中断、NCCL 网络流量集中看 /proc/softirqs、ethtool -l/-x、IRQ 亲和性。
一个 socket 的 CPU 忙，另一个 socket 闲NUMA 绑定、数据线程集中、内存远端访问numactl -H、numastat -p PID、进程 CPU affinity。
所有 CPU %idle 很高但 GPU 低网络、存储、分布式同步、GPU kernel 小且碎、数据管道外部等待结合 nvidia-smi dmon、iostat、训练日志 step time。

5. AI Infra 快速巡检命令

下面是一组生产上常用的“低侵入观察”命令。它们不会修改系统状态，适合在故障现场先收集证据。

# 1. 总体 + 每核 CPU，持续观察
mpstat -P ALL 1

# 2. 固定 30 秒证据，便于贴到 incident
mpstat -P ALL 1 30 | tee /tmp/mpstat.$(hostname).$(date +%F-%H%M%S).log

# 3. 同时看进程/线程级 CPU，关联到 dataloader worker 或服务线程
pidstat -t -u 1

# 4. 同时看磁盘 I/O
iostat -xz 1

# 5. 同时看 GPU 利用与 PCIe/显存趋势
nvidia-smi dmon -s pucm 1
训练慢
先看 GPU 是否饥饿，再用 mpstat -P ALL 判断 CPU/dataloader 是否跟不上。
推理 P99 抖动
看 %soft、%sys、单核热点和 %steal，再关联网卡、线程池和容器限额。
checkpoint 卡顿
看 %iowait 与 iostat -xz，区分本地盘、网络盘、对象存储 FUSE 和元数据瓶颈。
建议： 采样间隔常用 1 秒；如果系统负载很高或日志量太大，可用 2 到 5 秒。不要用单次截图证明长期问题，至少保存 30 到 60 秒。

6. 理解 %usr、%nice、%guest

%usr 表示普通用户态代码消耗的 CPU 时间。AI 工作负载里的 Python 解释器、数据增强、图片解码、tokenization、batch collate、RPC 序列化、推理服务业务逻辑，都可能主要出现在 %usr。

字段高值说明典型 AI 场景
%usr用户态代码正在大量运行PyTorch dataloader worker、CPU 图像增强、文本 tokenizer、CPU fallback op。
%nice被 nice 调整优先级的任务在运行后台离线预处理、低优先级数据整理任务。
%guest宿主机上运行虚拟 CPU 的时间KVM 宿主机或嵌套虚拟化环境，普通训练容器里通常不是重点。
# 观察 user 态是否单核打满
mpstat -P ALL 1 10

# 找到是哪一个线程在跑
pidstat -t -u 1

# 如果怀疑 Python dataloader，列出 worker
ps -eLo pid,tid,psr,pcpu,comm,args | grep -E 'python|DataLoader' | head -40
不要误读： %usr 高不一定是坏事。训练时 CPU 数据预处理充分并行可能会让多个 CPU 忙起来；只有当 GPU 等待、step time 变慢或延迟抖动时，它才是瓶颈线索。

7. 理解 %sys、%irq、%soft

%sys 是内核态时间，%irq 是硬中断，%soft 是软中断。对高吞吐 AI 系统而言，网络、存储、IPC、容器网络、NCCL 通信和日志写入都可能把时间推到这些桶里。

字段可能原因验证方向
%sys 高系统调用密集、文件系统路径、页缓存、内核锁、容器/网络栈strace -c -p PID、perf top、pidstat -w。
%irq 高硬件中断处理集中cat /proc/interrupts，检查 IRQ affinity 和设备队列。
%soft 高网络包处理、softirq backlog、存储完成队列、虚拟网络cat /proc/softirqs、sar -n DEV 1、ethtool -S。
# 软中断是否集中在少数 CPU
mpstat -P ALL 1
cat /proc/softirqs | sed -n '1,12p'

# 网卡队列和 IRQ 分布
grep -E 'CPU|eth|mlx|ens|eno' /proc/interrupts
for f in /proc/irq/*/smp_affinity_list; do printf '%s ' "$f"; cat "$f"; done 2>/dev/null | head

# 内核热点，低侵入先短采样
sudo perf top
安全注意： 修改 IRQ affinity、RPS/XPS、网卡队列数会改变系统行为，可能影响线上流量。先收集 mpstat、/proc/interrupts、/proc/softirqs 证据，再在维护窗口或灰度节点调整。

8. 理解 %iowait：存储瓶颈还是等待假象

%iowait 表示 CPU 空闲且系统存在未完成 I/O 请求的时间。它常被误解为“磁盘忙的百分比”，但它本质仍是 CPU 时间桶。高 iowait 是线索，不是最终结论。

可能是真瓶颈
数据集在网络盘、对象存储挂载、冷缓存随机读、checkpoint 同步写、日志刷盘、元数据操作过多。
也可能是等待假象
CPU 没有其他可运行任务，所以 I/O 等待被显著显示；如果 GPU、网络或分布式同步也在等待，需要多工具交叉验证。
# 同时观察 CPU iowait 与块设备
mpstat -P ALL 1
iostat -xz 1

# 观察具体进程 I/O
pidstat -d 1

# 查看数据集目录所在文件系统
df -hT /data
findmnt /data
mpstat 现象iostat 现象可能判断
%iowait 高%util 高、await 高块设备或网络盘可能成为瓶颈。
%iowait 高磁盘不忙可能是远端存储、FUSE、网络、元数据服务或采样窗口问题。
%iowait 低GPU 仍低利用瓶颈可能在 CPU user、分布式同步、数据队列、GPU kernel 调度或外部服务。
AI 训练经验： dataloader 读小文件、图片随机增强和远程数据集组合时，%iowait 与 %usr 可能交替升高。只看一个字段很容易误判。

9. 理解 %steal：虚拟化与云上噪声

%steal 表示虚拟机想运行但宿主机没有给它 CPU 的时间。云上训练、共享开发机、CI runner、虚拟化推理环境都要关注它。裸金属上通常接近 0。

# 云上实例 CPU 性能抖动时先看 steal
mpstat -P ALL 1 30

# 同时记录负载和运行队列
vmstat 1 30

# 容器里也可以观察，但要理解看到的是宿主机或容器命名空间暴露的视图
cat /proc/stat | sed -n '1,5p'
%steal解释行动
长期 0没有明显宿主机抢占继续看 user/sys/iowait/softirq。
偶发 1% 到 5%可能有轻微邻居噪声对延迟敏感服务要记录与 P99 的相关性。
持续高于 5%虚拟化调度可能影响性能更换实例、申请独占宿主机、联系云厂商或避开共享资源池。
排障重点： %steal 高时，应用层优化通常收效有限，因为 CPU 时间没有真正分配给虚拟机。

对比图：NUMA 不均衡如何出现在 mpstat 里

当 per-CPU 热点按 socket 聚集时，优先怀疑 NUMA 绑定、GPU 亲和性、内存分配位置、IRQ/队列分布。

10. NUMA 不均衡线索

多 socket AI 服务器里，CPU、内存、PCIe Root Complex、GPU/NIC 之间有拓扑距离。mpstat 不能直接显示 NUMA 远端访问，但它能暴露“某一组 CPU 过忙、另一组 CPU 过闲”的形态，这是继续检查 NUMA 的强线索。

# 查看 CPU 到 NUMA 节点的映射
lscpu -e=CPU,NODE,SOCKET,CORE,ONLINE
numactl -H

# 观察每个 CPU
mpstat -P ALL 1

# 查看进程在哪些 CPU 上跑
ps -eLo pid,tid,psr,pcpu,comm,args | sort -k4 -nr | head -30

# 查看进程内存 NUMA 分布
numastat -p <PID>
线索可能原因修复方向
某个 NUMA 节点 CPU 长期高 %usrdataloader worker 只在一个 socket 上运行检查 taskset、Kubernetes CPU manager、进程 affinity。
靠近某张 NIC/GPU 的 CPU %soft 高IRQ 或网络队列集中调整 IRQ affinity、网卡队列、NCCL 网卡选择。
CPU 利用高但 GPU 仍饥饿远端内存访问、跨 socket 拷贝、数据队列锁竞争按 GPU 拓扑绑定 worker 和内存，验证 numactl --cpunodebind --membind。
不要只凭 mpstat 下结论： NUMA 问题需要拓扑、进程亲和性、内存分布和业务流向共同确认。mpstat 的作用是快速指出“哪里不均匀”。

11. dataloader 饱和与 GPU 饥饿

训练 step time 抖动、GPU 利用率周期性掉到 0、显存占用稳定但 SM 利用低，常常与数据加载有关。mpstat 可以把数据加载瓶颈拆成 CPU 算力不够、I/O 等待、单线程瓶颈、软中断/网络问题几类。

mpstat 形态dataloader 解释验证与行动
多核 %usr 高、%idle 低CPU 预处理真的吃满了减少增强成本、增加缓存、预处理离线化、调 num_workers 与 batch size。
单核 %usr 近 100%主进程 collate、Python GIL、单线程 tokenizer 或解码看 pidstat -t；把热点移到多进程、native 扩展或预计算。
%iowait 高读取数据或 checkpoint I/O 等待看 iostat、缓存命中、数据格式、小文件数量、远程存储。
%soft 高远程数据集、分布式通信或网络栈压力看网卡吞吐、softirq 分布、NCCL 日志、对象存储网关。
CPU 很 idle瓶颈可能不在 CPU 数据预处理看 GPU kernel、分布式同步、数据队列阻塞、外部服务。
# PyTorch 训练现场常用组合
mpstat -P ALL 1 60 > /tmp/mpstat.log &
pidstat -t -u -d 1 60 > /tmp/pidstat.log &
nvidia-smi dmon -s pucm 1 -c 60 > /tmp/gpu.log &
wait

# 查 dataloader worker 是否集中在少数 CPU
ps -eLo pid,tid,psr,pcpu,comm,args | grep python | sort -k4 -nr | head -50
优化顺序： 先用证据判断是哪类瓶颈，再优化。盲目增大 num_workers 可能加重上下文切换、内存压力和远程存储压力。

12. sysstat 历史与 sar 回放

mpstat 和 sar 同属 sysstat。mpstat 适合现场实时观察，sar 适合回放历史。很多线上事故在发生后才被发现，此时历史采集是否开启非常关键。

# 查看 sysstat 是否开启历史采集
systemctl status sysstat 2>/dev/null || true
ls -lh /var/log/sa/ 2>/dev/null

# 回放今天的 CPU 历史
sar -u -f /var/log/sa/sa$(date +%d)

# 回放每 CPU 历史，不同版本 sar 选项可能略有差异
sar -P ALL -f /var/log/sa/sa$(date +%d)

# 回放指定时间窗口
sar -u -s 10:00:00 -e 10:30:00
需求用 mpstat用 sar
事故正在发生直接 mpstat -P ALL 1可同时开，但不是第一观察入口。
事故已经过去无法回到过去，除非当时保存了日志如果 sysstat 采集开启，可回放历史。
自动化日报不适合作为长期存储更适合周期采集、归档和报表。
生产建议： 训练集群基础镜像或节点初始化脚本应开启 sysstat 历史采集，并明确保留周期。否则很多“昨天晚上训练变慢”的问题只能靠业务日志间接推断。

mpstat 是入口，不是终点。它告诉你往 user、kernel、I/O、softirq、steal 还是 NUMA 方向下钻。

13. mpstat vs top/perf/sar/pidstat

工具最佳问题不适合和 mpstat 的关系
mpstat每 CPU 时间花在哪里，是否不均衡找具体函数、具体线程栈第一层分流工具。
top/htop当前哪个进程看起来忙准确分解 CPU 时间桶和历史保存辅助看进程，但容易被瞬时视图误导。
pidstat哪个进程/线程消耗 CPU、I/O、上下文切换系统整体每核分布mpstat 发现异常后用它定位线程。
perf函数级热点、内核/用户栈初学者快速巡检、长期低开销常驻mpstat 指向 user/sys 后用 perf 深挖。
sar历史回放、趋势报表实时交互排障的第一入口同属 sysstat，弥补 mpstat 无历史的问题。
iostat块设备吞吐、延迟、队列CPU per-core 不均衡mpstat %iowait 高时必须配合使用。
# 一个常见下钻链路
mpstat -P ALL 1       # 发现 CPU7 %usr 100%
pidstat -t -u 1       # 找到某个 python 线程
perf top -p <PID>     # 看热点函数
py-spy top --pid <PID> # 如果是 Python，进一步看 Python 栈

14. 故障模式速查表

单核 %usr 100%
常见于单线程瓶颈、GIL、tokenizer、collate、压缩解压。下一步：pidstat -t -u 1。
多核 %usr 高且 GPU 低
CPU 预处理可能跟不上。下一步：减少增强、缓存、离线预处理、调整 worker。
%sys 高
系统调用、文件系统、网络栈或内核锁。下一步：perf top、strace -c。
%soft 高且集中
网络/存储 softirq 或 IRQ 亲和性问题。下一步：/proc/softirqs、网卡队列。
%iowait 高
数据读取或写盘等待，但要用 iostat 验证。下一步：看 await、util、文件系统。
%steal 高
云上宿主机抢占或超卖。下一步：换实例/独占宿主机/联系云厂商。
socket 间冷热不均
NUMA、affinity、IRQ/GPU/NIC 拓扑。下一步：lscpu -e、numastat。
CPU idle 高但服务慢
瓶颈可能在 GPU、网络、锁、外部依赖或排队模型。下一步：关联业务指标。

排障流程图：从 GPU 低利用到 CPU 根因

安全排障的核心是先观察，再定位，再小步验证；不要看到 CPU 高就直接改生产亲和性或 worker 数。

第一步：保存现场

第二步：分类判断

先看判断下钻
all 行总体 CPU 是否忙忙则看字段；不忙则看 GPU/通信/外部等待。
每个 CPU是否单核或 socket 集中看 affinity、NUMA、IRQ、线程分布。
字段构成user/sys/iowait/soft/steal 哪个高分别走进程、内核、I/O、网络、云宿主机路径。

第三步：小步验证

# 示例：怀疑 dataloader worker 不够，先只在一轮实验中调整
# 记录 baseline: step time、GPU 利用率、mpstat、pidstat

16. 采样、容器与可观测性注意事项

在容器、Kubernetes、虚拟机和裸金属混合环境中，mpstat 的输出需要结合边界理解。它通常反映内核暴露的 CPU 视图，而不一定等同于某个容器的 CPU quota 或 cpuset。

场景注意事项建议
容器有 CPU quotampstat 可能看到宿主机全部 CPU，而业务只能用部分配额同时看 cgroup：cpu.max、cpuset.cpus、容器监控。
Kubernetes cpusetGuaranteed Pod 可能绑定特定 CPU用 cat /sys/fs/cgroup/.../cpuset.cpus 与 mpstat -P 对齐。
超短 spike1 秒采样可能平均掉毫秒级尖峰配合应用日志、eBPF、perf 或更细粒度 profiler。
超大 CPU 数-P ALL 输出很长保存日志后用脚本聚合，或先按 NUMA 选择 CPU 列表。
# cgroup v2 常见检查
cat /sys/fs/cgroup/cpu.max 2>/dev/null || true
cat /sys/fs/cgroup/cpuset.cpus.effective 2>/dev/null || true

# 如果只想看 cpuset 内 CPU，可手工指定
mpstat -P 0,1,2,3 1

# 大机器上提取高利用 CPU 行
mpstat -P ALL 1 5 | awk '$3 ~ /^[0-9]+$/ && ($4+$6+$8) > 80 {print}'
监控集成： 长期监控更适合 node exporter、sysstat、eBPF agent 或云监控；mpstat 更适合人类在现场快速建立假设。

17. 练习任务与学习路线

第一阶段：会读表

  1. 运行 mpstat 1 5，解释 all 行里每个字段。
  2. 运行 mpstat -P ALL 1 5，找出最忙的逻辑 CPU。

  2. 改变 dataloader num_workers，比较 CPU 字段构成和 GPU 利用率变化。
  3. 在多 socket 机器上尝试不同 CPU/内存绑定，观察 per-CPU 和吞吐变化。
