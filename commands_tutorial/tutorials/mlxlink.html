1. mlxlink 是什么

mlxlink 属于 NVIDIA/Mellanox Firmware Tools（MFT）工具集，面向 Mellanox/NVIDIA 设备的低层链路查询和诊断。它常用于 ConnectX 网卡、BlueField DPU、InfiniBand/Ethernet 交换设备的端口健康检查，读取链路状态、速率、FEC、物理计数器、模块信息和 PCIe 相关信息。

它擅长什么
定位物理链路问题：端口 down、协商失败、降速、FEC 不匹配、模块异常、BER/误码、lane 级线索。
它不替代什么
不替代 ip/ethtool 的 Linux netdev 视角，不替代 ibstat/ibv_devinfo 的 RDMA/IB 视角，也不替代真实带宽压测。
AI Infra 价值
当 NCCL、RDMA、RoCE 或多节点训练出现掉速、超时、重传时，mlxlink 能把问题下钻到物理端口和线缆模块层。
# 典型只读查询：设备路径按现场替换
mlxlink -d /dev/mst/mt4129_pciconf0
mlxlink -d /dev/mst/mt4129_pciconf0 -p 1
mlxlink -d 0000:41:00.0 -c
mlxlink -d 0000:41:00.0 -m
mlxlink -d 0000:41:00.0 --show_fec
命名提醒： mlxlink 操作的是 Mellanox/NVIDIA 设备或端口，不是普通 Linux 网卡名本身。ens5f0np0、ib0、mlx5_0、PCI BDF、/dev/mst/* 之间需要先建立映射。

信息图：AI Infra 中 mlxlink 的位置

mlxlink 位于 OS/RDMA 和物理介质之间，适合把“训练通信慢”拆成可验证的链路事实。

2. 安装、权限与设备路径

mlxlink 通常随 NVIDIA/Mellanox MFT 安装。不同发行版、OFED/MLNX_OFED、DOCA、厂商镜像和云平台镜像的打包方式不同；生产节点上应以团队基线镜像和变更流程为准。

# 确认工具是否存在
command -v mlxlink
mlxlink --help | head -40

# MFT 常见设备发现流程
sudo mst start
mst status -v
ls -l /dev/mst/ 2>/dev/null

# 不使用 mst 时，也常见直接按 PCI BDF 查询
lspci -D | grep -Ei 'Mellanox|NVIDIA|ConnectX|BlueField'
mlxlink -d 0000:41:00.0
对象例子用途
MST 设备/dev/mst/mt4129_pciconf0MFT 传统路径，适合稳定定位设备和交换机/适配器诊断。
PCI BDF0000:41:00.0和 lspci、ethtool -i、nvidia-smi topo 交叉映射。
Linux netdevens5f0np0mlxlink 通常不直接以它为核心对象，但可用它反查 PCI 设备。
RDMA 设备mlx5_0用 ibdev2netdev、rdma link 映射到端口和 netdev。
权限现实： 读取硬件链路信息通常需要 root 或具备相应设备节点权限。容器内排障要确认是否暴露 /dev/mst、PCI 设备、RDMA 设备和必要 capabilities。

3. 第一条安全命令

刚接触 mlxlink 时，先做只读快照。不要一开始就改 FEC、跑 PRBS、写寄存器或 disable port。你的第一目标是收集“当前事实”，而不是立即修复。

# 单端口适配器或默认端口查询
sudo mlxlink -d /dev/mst/mt4129_pciconf0

# 多端口设备显式指定端口
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 2

# 一次收集更多只读线索：链路、计数器、模块、FEC 能力
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1 -c -m --show_fec
先看状态
Link State、Physical State、Speed、Width、FEC、Loopback、Auto Negotiation。
再看质量
Physical Counters、BER、corrected/uncorrected 相关计数、link down 计数。
最后看介质
Cable/module 类型、长度、温度、电压、TX/RX 光功率、vendor 线索。
采集建议： 把输出保存到工单或 incident 目录，并记录时间、主机、端口、对端交换机端口、作业 ID、NCCL 日志片段。单条命令输出脱离时间线，诊断价值会下降。

4. 输出字段怎么读

不同 MFT 版本、设备代际和端口类型会让输出字段略有差异。读输出时不要机械匹配某个字段名，而要按“状态、协商、质量、模块、上下文”五类整理。

字段类别常见含义异常解读
Link/Physical State链路是否 up、物理层是否训练成功。Down/Polling/Disabled 说明要查线缆、模块、对端、端口配置或硬件。
Speed/Rate/Width协商后的速率、lane 宽度、端口模式。低于预期可能是模块不支持、对端配置、分叉口、FEC/AN 或线缆质量问题。
FEC当前使用的 Forward Error Correction 模式和能力。两端 FEC 能力/策略不匹配会导致 link down、降速或大量 corrected error。
Counters/BER物理层错误、BER 估计、link down 计数等。持续增长比单次非零更重要；要间隔采样看趋势。
Module/Cable模块类型、vendor、长度、温度、电压、光功率。unknown、unsupported、温度异常、RX power 异常常指向介质或对端。
# 用时间戳保存快照，便于比较
host=$(hostname -s)
dev=/dev/mst/mt4129_pciconf0
port=1
ts=$(date +%Y%m%d-%H%M%S)
sudo mlxlink -d "$dev" -p "$port" -c -m --show_fec | tee "mlxlink-${host}-p${port}-${ts}.txt"
不要过度解读单点： 某些 corrected error 或历史 link down 可能来自上线、维护或链路训练阶段。判断线上问题时，更重视“作业运行窗口内是否持续增长”。

流程图：从设备到端口、lane、对端

AI 集群排障中，端口映射错误非常常见。先证明自己读的是正确 HCA、正确物理端口、正确对端。

5. 端口、lane 与分叉口

高速端口常由多条 lane 组成，交换机侧还可能做 breakout/split，例如一个 400G 端口拆成多个 100G/200G 逻辑端口。mlxlink 输出中的端口号、label port、split port 和 lane 需要结合设备型号与交换机配置解释。

# 适配器常见：逐个端口读
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 2

# 交换机或复杂端口场景：通常必须显式 -p
sudo mlxlink -d /dev/mst/mt53100_pciconf0 -p 17

# 用系统工具辅助映射
ibdev2netdev
rdma link show
ethtool -i ens5f0np0
readlink -f /sys/class/net/ens5f0np0/device
概念解释排障意义
Physical port设备上的物理端口。决定你查询哪根线、哪个对端口。
Lane高速端口内部的电/光通道。单 lane 异常可能导致高 BER、FEC 压力或降速。
Split/breakout一个高速端口拆成多个逻辑端口。端口编号和线缆标签容易错配。
Label port设备面板或系统展示的端口标签。交换机侧定位对端时很关键。
经验法则： 排障记录中同时写下 Linux netdev、RDMA device、PCI BDF、MST device、mlxlink port、交换机端口和线缆标签，后续协作成本会低很多。

6. 速率、宽度与降速

链路 up 不等于达到了期望能力。AI 训练集群中，单个端口从 400G 降到 200G、100G 或 lane 数不足，可能只在大规模 all-reduce 时体现为吞吐降低、tail latency 增大或 NCCL timeout。

# 本端物理速率
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1

# Linux netdev 视角交叉验证
ethtool ens5f0np0 | egrep 'Speed|Duplex|Auto-negotiation|Link detected|FEC'

# RDMA/IB 视角交叉验证
ibstat
ibv_devinfo -v | egrep 'hca_id|port:|state:|phys_state:|rate:|link_layer:|active_mtu'
rdma link show
现象常见原因下一步
Link up 但速率低模块不支持目标速率、对端端口配置低、breakout 配置错误、线缆质量不足。查模块能力、对端配置、交换机端口状态、FEC 能力。
链路反复 flap线缆/模块不稳定、对端端口重启、温度、电源、FEC/AN 不匹配。间隔采样 link down counter，查交换机日志和模块温度/功率。
单方向吞吐异常某 lane 质量差、RX/TX 光功率异常、PFC/ECN/队列问题。结合 mlxlink -c -m、ethtool -S、交换机计数器。
速率解读： 不同端口模式下“速率”和“lane 宽度”的显示方式可能不同。不要只看一个数字，要确认目标拓扑设计、设备能力和对端配置。

7. FEC：模式、能力与风险

FEC（Forward Error Correction）用于在高速链路上纠正一定范围内的误码。越高速、越长距离、越复杂的介质，FEC 越关键。mlxlink 可以显示 FEC 状态和能力，也支持配置 FEC，但配置属于变更操作，生产默认不应直接执行。

# 只读：查看 FEC 能力/状态
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1 --show_fec
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1

# 只读：和 Linux 侧对照
ethtool --show-fec ens5f0np0 2>/dev/null || ethtool ens5f0np0 | grep -i fec
FEC 模式常见含义使用提醒
Auto由设备和对端协商或按策略选择。默认最安全，但两端实现/策略不一致时仍需核对。
No-FEC不使用 FEC。高速链路上风险高；误码环境下可能导致业务不稳定。
FireCode / BASER较早或特定速率下常见的 FEC 类型。是否可用取决于端口速率、设备代际和对端。
RS-FEC / LL-RS-FEC高速以太网常见强纠错模式及低延迟变体。要结合交换机、模块和目标速率统一规划。
# 变更示例：不要在生产链路上直接运行
# 仅在维护窗口、已确认对端策略、具备回滚方案时考虑
# sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1 --fec RS
# sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1 --fec AU
变更警告： FEC 配置不匹配可能导致链路 down 或业务抖动。AI 训练集群里，一条链路抖动可能放大为整个 job 失败；不要把 FEC 变更当成普通查询命令。

诊断图：Counters 与 BER 的判断顺序

误码诊断要看趋势：T0/T1 delta、业务窗口、对端计数器和日志时间线，比单次快照更可靠。

8. Counters、BER 与误码趋势

-c 或 --show_counters 用于显示物理计数器和 BER 相关信息。不同设备代际展示项不同，但排障方法一致：保存基线、等待有流量的窗口、再次采样、比较变化。

# 只读采样
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1 -c

# 间隔采样示例：不要只看一次
dev=/dev/mst/mt4129_pciconf0
port=1
sudo mlxlink -d "$dev" -p "$port" -c | tee mlxlink-counters-t0.txt
sleep 300
sudo mlxlink -d "$dev" -p "$port" -c | tee mlxlink-counters-t1.txt
diff -u mlxlink-counters-t0.txt mlxlink-counters-t1.txt || true
线索可能含义处理方向
BER 偏高或恶化介质质量、光功率、端口硬件、对端或环境问题。换线/模块、查对端、降低速率验证、检查温度和弯折半径。
Corrected 增长FEC 正在纠错，短期业务可能未失败但有隐患。看增长速率和是否集中在某端口/lane。
Uncorrected 增长错误超过纠错能力，业务风险明显。建议隔离、维护窗口更换介质或切换路径。
Link down counter 增长链路 flap 或被重置。对齐交换机日志、主机 dmesg、作业失败时间。
基线管理： 大规模集群可以把关键端口的 mlxlink -c 输出纳入节点验收和故障前后对比，但长期监控更适合交给交换机遥测、DCGM/Prometheus、ethtool exporter 或自研采集器。

9. 线缆与光模块线索

-m 或模块相关查询可以显示线缆/模块信息。对 AI 集群而言，模块信息经常能解释“为什么只有某一排机柜、某一批节点、某一类端口异常”。

# 只读查看模块/线缆信息
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1 -m

# Linux 侧补充模块 EEPROM 信息
ethtool -m ens5f0np0 2>/dev/null | head -80

# 对端交换机侧也要查看同一根线的模块读数
# 示例伪命令，按交换机 NOS 替换
# show interfaces ethernet 1/17 transceiver details
模块线索关注点解释
Vendor/Part/Revision是否在兼容清单中。非认证模块不一定不能用，但排障时要提高怀疑权重。
Cable type/LengthDAC/AOC/光模块、长度。超过设计距离或混用规格会造成训练失败或误码。
Temperature/Voltage是否接近告警阈值。高温会放大误码，尤其在高密度机柜中。
TX/RX power双端光功率是否合理。一端低通常指向光纤、模块、清洁度或对端发射问题。
介质排障原则： 换线/换模块是有效验证手段，但要记录原始位置、序列号、对端和更换时间；否则容易把可复现问题变成无法追踪的漂移问题。

10. PCIe 链路诊断

NCCL 或 RDMA 性能异常不总是网络线缆问题。网卡/DPU 到主机的 PCIe 链路如果降速、降宽、错误重试或 NUMA 放置不合理，也会表现为吞吐不足。mlxlink 在部分设备和版本中支持通过 PCIe port type 查看 PCIe counters；同时应结合 lspci 和拓扑工具。

# mlxlink PCIe counters：具体支持取决于设备和 MFT 版本
sudo mlxlink -d /dev/mst/mt4129_pciconf0 --port_type PCIE -c

# PCIe 链路宽度/速率
lspci -s 41:00.0 -vv | egrep 'LnkCap|LnkSta|AER|UESta|CESta'

# 设备到 NUMA/GPU 的拓扑
lstopo --no-io 2>/dev/null | head
nvidia-smi topo -m 2>/dev/null || true
cat /sys/bus/pci/devices/0000:41:00.0/numa_node
现象可能原因验证
NIC 速率正常但吞吐低PCIe x16 变 x8/x4、Gen5 变 Gen4/Gen3、NUMA 跨 socket。lspci -vv、BIOS、插槽布局、nvidia-smi topo -m。
偶发 DMA/RDMA 错误PCIe AER、固件/驱动、主板或 riser 问题。dmesg、AER counters、BMC SEL、厂商诊断。
多卡训练某几张 GPU 慢GPU-NIC 不在同一 NUMA/PCIe root complex。拓扑矩阵、rank placement、NCCL topology dump。
边界： mlxlink 能提供设备侧 PCIe 线索，但完整 PCIe 排障还需要 BIOS、主板、riser、BMC、内核日志和厂商硬件支持一起参与。

11. IB、RoCE 与 Ethernet 场景

mlxlink 更接近物理链路层；InfiniBand、RoCE 和普通 Ethernet 的上层配置仍要用对应工具验证。AI Infra 中常见错误是“mlxlink 正常”就认定网络正常，忽略了 GID index、P_Key、MTU、PFC/ECN、路由或防火墙。

# InfiniBand/RDMA 侧
ibstat
ibv_devinfo -v
rdma link show
rdma resource show

# RoCE/Ethernet 侧
ip -br link
ip -br addr
ethtool ens5f0np0
ethtool -S ens5f0np0 | egrep -i 'err|drop|crc|fec|timeout|pause|pfc|ecn|discard'

# GID 与 NCCL/RDMA 常见交叉点
show_gids 2>/dev/null || true
cat /sys/class/infiniband/mlx5_0/ports/1/gid_attrs/types/* 2>/dev/null
场景mlxlink 负责还必须验证
InfiniBand物理端口、速率、FEC、误码、模块。SM/LID、P_Key、IB rate、fabric 路由、ibdiagnet。
RoCE v2以太物理链路质量。IP、VLAN、MTU、PFC/ECN、GID index、DSCP/TC、交换机 QoS。
普通 Ethernet链路训练、模块、FEC、物理错误。netdev up、队列、offload、bond/LACP、路由和 ACL。
工具组合： 物理层用 mlxlink，Linux netdev 用 ip/ethtool，RDMA verbs 用 ibv_devinfo/rdma，IB fabric 用 ibstat/ibdiagnet，真实性能用 perftest、qperf、iperf3 或 nccl-tests。

12. NCCL fabric 问题定位

NCCL 报错或 all-reduce 掉速时，不要只盯 GPU。多节点训练通信路径通常跨越 GPU、PCIe、NIC、线缆、交换机、RoCE/IB 配置和进程绑核。mlxlink 在这个链条中负责物理层证据。

# 训练作业侧：打开必要日志
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH

# 记录 NCCL 选择了哪些 HCA/接口
env | grep -E 'NCCL|CUDA_VISIBLE_DEVICES|SLURM|OMPI' | sort

# 节点侧：把 NCCL 时间窗口内的链路状态保存下来
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1 -c -m --show_fec
ethtool -S ens5f0np0 | egrep -i 'err|drop|crc|fec|pause|pfc|ecn'
ibv_devinfo -v | egrep 'hca_id|port:|state:|rate:|link_layer|active_mtu'
NCCL 现象mlxlink 关注点非 mlxlink 关注点
NET/IB 初始化慢或失败端口是否 up、速率是否符合、是否 link flap。GID index、HCA 选择、权限、容器 RDMA 设备暴露。
大规模时才 timeout误码/FEC 计数是否在作业窗口增长。PFC/ECN、拥塞、交换机 buffer、路由 ECMP、CPU 绑核。
单节点/单机柜慢该范围端口是否降速、模块批次是否相同。拓扑放置、作业 rank 映射、GPU-NIC locality。
证据链模板： “NCCL 日志 14:03:21 timeout” + “同窗口端口 17 corrected/uncorrected 增长” + “交换机对端 CRC/FEC 增长” + “模块 RX power 低” 比“mlxlink 有一些 error”更能支撑处置决策。

对比图：mlxlink、ethtool、ibstat、rdma 怎么选

mlxlink 是物理链路专家，但不是完整网络栈诊断的替代品。

13. mlxlink vs ethtool/ibstat/rdma

问题优先工具为什么
Linux 网卡是否 up、驱动/固件版本、队列/offloadip、ethtool它们是 netdev 和驱动视角。
IB 端口 state、phys state、rate 快速检查ibstat输出简洁，适合 IB/RDMA 巡检。
RDMA link/resource、netns 相关视角rdma来自内核 RDMA netlink。
FEC、BER、模块、lane、物理计数器mlxlink更接近 NVIDIA/Mellanox 设备物理层。
端到端真实性能ib_write_bw、qperf、iperf3、nccl-tests链路健康不等于业务吞吐达标。
# 一组常用交叉验证命令
ip -br link
ethtool ens5f0np0
ethtool -S ens5f0np0 | egrep -i 'err|drop|crc|fec|pause|pfc|discard'
ibstat
rdma link show
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1 -c -m --show_fec
分层原则： 如果 mlxlink 显示物理层异常，优先处理物理链路；如果 mlxlink 干净但 NCCL 仍异常，继续查 RoCE QoS、IB fabric、路由、NUMA、CPU 绑核、容器和作业拓扑。

14. 安全只读生产工作流

生产环境中，mlxlink 的默认姿势应该是只读采集和交叉验证。需要改配置时，把它纳入网络变更流程，而不是 incident 中的即兴命令。

# 4. 有流量时重复采样，比较 delta
sleep 300
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1 -c
只读白名单
mlxlink -d ...、-c、-m、--show_fec、帮助和版本查询通常适合先跑。
变更红区
--fec 覆盖、PRBS/test mode、disable port、写寄存器、模块写操作应走维护窗口。
证据保存
输出要带时间戳、主机名、端口、对端、作业 ID，方便后续 RCA。

15. 典型故障剧本

剧本 A：端口 Down 或一直 Polling

sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1
sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1 -m --show_fec
ethtool ens5f0np0
dmesg -T | egrep -i 'mlx5|link|module|firmware|pcie' | tail -80

优先查线缆是否插对、模块是否识别、对端端口是否启用、端口模式是否匹配、FEC/auto-negotiation 是否一致、breakout 配置是否正确。

剧本 B：Link Up 但 NCCL 掉速

sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p 1 -c -m --show_fec
ethtool -S ens5f0np0 | egrep -i 'err|drop|crc|fec|pause|pfc|ecn|discard'
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH ./your_nccl_test

如果物理计数器不增长，继续查 RoCE QoS、拥塞、GPU-NIC 拓扑、CPU 绑核、容器 device mapping 和 NCCL HCA 选择。

剧本 C：某一批节点频繁 flap

# 每台节点保存相同格式输出，便于横向比较
for p in 1 2; do
  sudo mlxlink -d /dev/mst/mt4129_pciconf0 -p "$p" -c -m --show_fec \
    | tee "mlxlink-$(hostname -s)-p${p}.txt"
done

按机柜、线缆批次、模块 PN、交换机端口组、温度和布线半径聚类。批量问题通常不是单个命令能解释的，而是供应链、布线或交换机策略一致性问题。

16. 常见坑与安全边界

坑 1：查错端口
没有建立 netdev、RDMA device、PCI、MST、交换机端口映射，导致读到无关端口。
坑 2：把历史 error 当现行故障
没有 T0/T1 delta 和业务时间线，单次非零计数不能直接归因。
坑 3：只看本端
链路是双端系统，本端正常不代表对端交换机、模块和光功率正常。
坑 4：忽略 FEC
速率 up 但 FEC 不合理，可能在高流量下变成 corrected error 风暴。
坑 5：容器内视角不完整
容器可能没有 /dev/mst、RDMA device、内核日志或真实 PCI 拓扑。
坑 6：把 mlxlink 当性能测试
它提供链路证据，不证明应用端到端吞吐达标。
坑 7：排障时改配置
强制 FEC、test mode、disable port 都可能造成业务中断。
坑 8：忽略版本差异
MFT、固件、驱动、设备代际不同，字段和能力会变化。
高风险命令边界： PRBS/test mode、port disable、FEC override、寄存器写入、模块写入、固件更新都不属于“看一眼”的诊断动作。没有维护窗口和回滚方案时，不应执行。

17. 练习与上线清单

练习任务

  1. 在测试节点上用 lspci、mst status -v、ibdev2netdev 建立一张端口映射表。
  2. 对同一端口分别运行 mlxlink、ethtool、ibstat、rdma link，比较它们的视角差异。
  3. 用 mlxlink -c 做 T0/T1 采样，理解哪些字段会随流量变化。
  4. 用 mlxlink -m 和 ethtool -m 对比模块信息，并记录 vendor、PN、长度、温度、光功率。
  5. 在 nccl-tests 或 perftest 前后采集链路输出，把业务性能和物理计数器放到同一时间线。

上线/验收清单

检查项通过标准证据
端口映射主机、PCI、MST、netdev、RDMA、交换机端口一致。映射表、布线表、命令输出。
链路速率达到设计速率和宽度，无异常降速。mlxlink、ethtool、ibstat。
FEC两端策略符合设计，未出现不匹配。--show_fec、交换机配置。
物理计数器压测窗口内无异常增长。T0/T1 mlxlink -c、交换机计数器。
模块与布线模块被识别，温度/功率合理，型号符合基线。mlxlink -m、ethtool -m、资产记录。
业务压测perftest/nccl-tests 达到集群基线。压测结果和日志。
