1. nerdctl 是什么

nerdctl 是 containerd 生态中的命令行工具，目标是提供接近 Docker CLI 的体验，同时直接操作 containerd 管理的镜像、容器、网络和卷。对 AI Infra 来说，它最常见的价值是在不安装 Docker daemon 的节点上，用熟悉的命令调试 containerd 和 Kubernetes 使用的镜像/容器。

它擅长什么
用 Docker 风格命令操作 containerd：run、ps、images、logs、exec、build、compose。
它不是 CRI 专用工具
crictl 面向 kubelet CRI；nerdctl 面向 containerd 本身。两者能看到的对象和字段并不完全一致。
AI Infra 价值
排查节点镜像缓存、训练容器启动、GPU runtime、私有 registry、rootless 沙箱、compose 复现实验环境。
# 查看版本与 containerd 连接情况
nerdctl version

# 默认 namespace 下的镜像和容器
nerdctl images
nerdctl ps -a

# Kubernetes 节点通常要看 k8s.io namespace
nerdctl -n k8s.io images
nerdctl -n k8s.io ps -a
关键区别： docker ps 面向 Docker daemon，nerdctl ps 面向 containerd namespace；在 Kubernetes 节点上忘记 -n k8s.io 是最常见误判。

2. 整体模型：CLI 到 containerd

nerdctl 的语法像 Docker，但对象边界是 containerd namespace。Kubernetes 节点排障时，namespace 是第一关键维度。

3. 安装与环境确认

很多发行版或 Kubernetes 节点已经安装 containerd，但不一定带 nerdctl。安装后先确认版本、socket、rootless/rootful 模式、CNI/BuildKit 组件是否存在。

检查项命令说明
nerdctl 版本nerdctl version确认客户端和 server 连接。
containerd 服务systemctl status containerdrootful 模式通常依赖系统服务。
socket 路径nerdctl --address /run/containerd/containerd.sock version多 containerd 实例或非默认路径时显式指定。
帮助信息nerdctl --help不同版本的 flags 可能不同，脚本前先确认。
# rootful 常见检查
nerdctl version
sudo nerdctl info
sudo nerdctl --namespace k8s.io images

# 查看 containerd namespace
sudo ctr namespaces list

# 如果 socket 不在默认位置
nerdctl --address /run/containerd/containerd.sock --namespace k8s.io ps
权限模型： rootful containerd 通常需要 root 权限或特定 socket 权限；rootless nerdctl 则连接用户级 containerd，不会直接看到系统 Kubernetes 使用的 k8s.io 对象。

4. 命名空间：default 与 k8s.io

Kubernetes 节点上大多数 Pod 镜像和容器在 k8s.io namespace；默认 namespace 空并不代表节点没容器。

5. 镜像：pull、tag、save、load

nerdctl 的镜像命令基本沿用 Docker 风格，但镜像存储在 containerd content store 中，并受 namespace 隔离。AI Infra 常见场景包括预拉训练镜像、检查 digest、导入离线镜像、清理失败的镜像缓存。

# 拉取镜像到默认 namespace
sudo nerdctl pull docker.io/library/ubuntu:22.04

# 拉取到 Kubernetes 使用的 k8s.io namespace
sudo nerdctl -n k8s.io pull nvcr.io/nvidia/pytorch:24.03-py3

# 查看 digest、大小、平台
sudo nerdctl -n k8s.io images --digests

# 打标签并推送到私有 registry
sudo nerdctl tag ubuntu:22.04 registry.example.com/base/ubuntu:22.04
sudo nerdctl push registry.example.com/base/ubuntu:22.04

# 离线导出/导入
sudo nerdctl save -o image.tar registry.example.com/train/app:v1
sudo nerdctl -n k8s.io load -i image.tar
任务推荐命令注意点
查看 Kubernetes 节点镜像nerdctl -n k8s.io images --digests和 kubectl describe pod 中 image ID 对齐。
预拉大模型镜像nerdctl -n k8s.io pull ...要和 kubelet 使用的 registry、凭据、平台一致。
确认多架构nerdctl image inspectarm64/amd64 混合集群尤其重要。
清理镜像nerdctl image prune先 dry-run 式列出候选，避免删除即将复用的大镜像。
镜像清理提醒： 删除 image record 不一定立刻释放所有 content/snapshot 空间；containerd GC、正在运行的容器、其他 namespace 引用都会影响实际释放效果。

6. 容器生命周期

nerdctl 用 run 创建并启动容器，用 stop、rm、restart 管理生命周期。生产节点上对 Kubernetes 创建的容器执行这些命令前要格外谨慎，因为 kubelet 可能会重建它们，或者你的操作会影响业务 Pod。

# 运行一个交互式调试容器，退出后自动删除
sudo nerdctl run --rm -it ubuntu:22.04 bash

# 后台运行并命名
sudo nerdctl run -d --name web -p 8080:80 nginx:alpine

# 查看、停止、删除
sudo nerdctl ps
sudo nerdctl stop web
sudo nerdctl rm web

# Kubernetes namespace 下只读查看更安全
sudo nerdctl -n k8s.io ps -a
sudo nerdctl -n k8s.io inspect <container-id>
节点操作警告： 不要把 nerdctl -n k8s.io stop/rm 当成常规发布手段。业务生命周期应通过 Kubernetes API 管理，例如 kubectl delete pod、drain、cordon 或控制器回滚。

7. logs、exec 与 inspect

排障时最常用的只读路径是 ps 找容器、logs 看 stdout/stderr、inspect 看 runtime 配置、exec 进入容器确认文件和设备。对 AI 容器，重点确认环境变量、挂载、GPU 设备文件、NCCL/网络参数和启动命令。

# 查看容器列表和名称
sudo nerdctl -n k8s.io ps -a

# 看日志，先限制尾部，避免刷屏
sudo nerdctl -n k8s.io logs --tail 200 <container-id-or-name>
sudo nerdctl -n k8s.io logs -f --tail 50 <container-id-or-name>

# 进入容器
sudo nerdctl -n k8s.io exec -it <container-id> sh

# 看启动参数、挂载、环境变量、runtime
sudo nerdctl -n k8s.io inspect <container-id>
问题nerdctl 入口继续确认
容器启动后立即退出logs --tail 200, inspect入口命令、镜像 tag、缺少配置/secret、权限。
GPU 不可见exec nvidia-smi, inspectruntime、device plugin、NVIDIA_VISIBLE_DEVICES、/dev/nvidia*。
找不到模型文件inspect mounts, exec lshostPath/PVC、只读挂载、UID/GID。
NCCL 初始化失败logs, exec env网络、IB/RDMA 设备、NCCL env、容器权限。
日志提醒： Kubernetes 场景优先用 kubectl logs 获取业务语义；nerdctl logs 更适合节点级 CRI/containerd 排障或 kubectl 不可用时的兜底。

8. Kubernetes 节点镜像排障

镜像拉取失败、节点磁盘爆满、私有 registry 认证异常、digest 不一致，是 AI 训练集群最常见的节点问题。nerdctl -n k8s.io 可以直接观察 kubelet 使用的镜像缓存。

# 1. 从 Pod 事件得到镜像名
kubectl describe pod <pod> -n <ns>

# 2. 到对应节点上确认镜像是否存在
sudo nerdctl -n k8s.io images --digests | grep 'train-app'

# 3. 手工验证 registry 拉取路径
sudo nerdctl -n k8s.io pull registry.example.com/ai/train-app:v20260425

# 4. 查看镜像详情
sudo nerdctl -n k8s.io image inspect registry.example.com/ai/train-app:v20260425
ImagePullBackOff
先看 kubectl describe pod 事件，再在节点用 nerdctl -n k8s.io pull 复现。认证问题、DNS、代理、证书、registry 限流都可能导致失败。
磁盘占用异常
镜像层、snapshot、日志都可能占空间。先用 df -h、du、nerdctl images 定位，不要直接粗暴删除 containerd 目录。
推荐顺序： Pod 事件 → 节点镜像列表 → 手工 pull → containerd/kubelet 日志 → registry/网络/证书排查。

9. Kubernetes 容器排障

在 k8s.io namespace 中，nerdctl 可以看到 Pod sandbox 和业务容器，但名称可能较长且包含 Kubernetes 元数据。更适合把 kubectl 与 nerdctl 联合使用：kubectl 提供 Pod 语义，nerdctl 提供节点 containerd 视角。

# 用 kubectl 找节点和容器状态
kubectl get pod <pod> -n <ns> -o wide
kubectl describe pod <pod> -n <ns>

# 在该节点上列出 k8s.io 容器
sudo nerdctl -n k8s.io ps -a | grep '<pod-name-fragment>'

# 查看具体容器配置
sudo nerdctl -n k8s.io inspect <container-id>

# 只在确认影响范围后进入容器
sudo nerdctl -n k8s.io exec -it <container-id> sh
优先工具适用场景为什么
kubectl业务 Pod 状态、事件、控制器、调度、重启。语义最完整，避免绕过 Kubernetes。
crictlCRI 层 sandbox/container/image 诊断。和 kubelet CRI 接口对齐。
nerdctl -n k8s.iocontainerd 原生对象、Docker 风格 inspect/logs/exec、镜像缓存。更接近 containerd 实际存储和 runtime 视角。
ctr -n k8s.io底层 containerd 调试。更原生但不够友好，适合专家兜底。
不要混淆： nerdctl ps 看不到 Kubernetes 容器时，先加 -n k8s.io；如果仍看不到，再检查 containerd socket、权限、节点是否正确。

10. GPU runtime caveats

nerdctl 支持通过 GPU 相关 flag 或 OCI runtime 配置运行 GPU 容器，但是否可用取决于宿主机 NVIDIA 驱动、NVIDIA Container Toolkit、containerd runtime 配置、设备文件、cgroup、rootless 限制以及 Kubernetes device plugin。命令本身不是 GPU 可见性的全部。

# 宿主机先确认 GPU 和驱动
nvidia-smi

# rootful 手工运行 GPU 容器，具体 flag 以本机 nerdctl 版本为准
sudo nerdctl run --rm --gpus all nvcr.io/nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 如果集群使用 NVIDIA runtime class，Kubernetes 中还要确认 RuntimeClass / device plugin
kubectl get runtimeclass
kubectl -n kube-system get pods | grep -i nvidia

# 在已运行训练容器中确认可见性
sudo nerdctl -n k8s.io exec <container-id> nvidia-smi
驱动不在镜像内
CUDA 用户态库可在镜像中，内核驱动来自宿主机。宿主机 nvidia-smi 失败时，容器内通常也不会正常。
runtime 配置是关键
需要 NVIDIA Container Toolkit 将设备、库和 hooks 注入容器。不同发行版和 containerd 配置路径不同。
rootless 有限制
GPU、RDMA、高性能网络设备和 cgroup 访问在 rootless 下常有额外限制，不能默认等同 rootful。
GPU 排障安全线： 不要在生产训练节点随意重启 containerd、nvidia-persistenced 或修改 runtime 配置；这可能影响同节点全部 Pod。先 cordon/drain 或在维护窗口验证。

11. rootless 模式

rootless nerdctl 让普通用户运行用户级 containerd，适合开发机、CI 沙箱和低权限实验环境。它的隔离和安全收益很明显，但网络、端口、cgroup、overlay、设备直通、GPU 和性能行为都可能和 rootful 不同。

# 常见 rootless 安装后会有用户级 containerd
nerdctl info
nerdctl run --rm hello-world

# rootless 端口映射通常依赖 rootlesskit/slirp4netns 等组件
nerdctl run --rm -p 8080:80 nginx:alpine

# 确认当前连接的不是系统级 containerd
nerdctl version
nerdctl namespace ls 2>/dev/null || true
维度rootfulrootless
权限通常 root 或 socket 权限。普通用户级 daemon，更适合开发隔离。
Kubernetes 节点对象可查看系统 containerd 的 k8s.io。默认看不到系统 kubelet 使用的对象。
GPU/RDMA 设备按 runtime 和设备权限配置。限制更多，需单独验证，不适合作为生产假设。
网络性能CNI/bridge/host 等能力完整。用户态网络可能带来功能和性能差异。
选择建议： 开发和 CI 可优先 rootless；节点级 AI Infra 排障通常使用 rootful 视角，因为 kubelet 管理的是系统 containerd。

12. compose 支持

nerdctl compose 提供 Docker Compose 风格体验，适合在 containerd 环境中本地复现实验服务、模型服务依赖、registry/mock 服务和监控组件。它不是 Kubernetes 编排替代品，更适合单机或开发验证。

# docker-compose.yml / compose.yaml 所在目录
sudo nerdctl compose up -d
sudo nerdctl compose ps
sudo nerdctl compose logs --tail 100
sudo nerdctl compose down

# 指定项目名，避免不同目录冲突
sudo nerdctl compose -p llm-demo up -d
# 最小 compose 示例
services:
  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
  worker:
    image: registry.example.com/ai/worker:dev
    environment:
      REDIS_URL: redis://redis:6379/0
兼容提醒： Compose 生态功能很多，nerdctl compose 和 Docker Compose 的边缘行为不一定完全一致。生产前要验证网络、卷、健康检查、profiles、build 和 GPU 相关配置。

13. build 与 BuildKit

nerdctl 的构建通常依赖 BuildKit。AI 镜像往往层很大，构建时要关注缓存、基础镜像 digest、pip/apt 源、私有 registry、跨架构和构建机磁盘空间。

# 构建镜像
sudo nerdctl build -t registry.example.com/ai/train-app:dev .

# 指定 Dockerfile
sudo nerdctl build -f docker/Dockerfile.train -t train-app:dev .

# 构建并推送
sudo nerdctl build -t registry.example.com/ai/train-app:v1 .
sudo nerdctl push registry.example.com/ai/train-app:v1

# 查看 builder/buildkitd 状态，具体服务名视安装方式而定
systemctl status buildkit 2>/dev/null || systemctl status buildkitd 2>/dev/null
可复现构建
基础镜像尽量 pin digest；训练镜像中 CUDA、cuDNN、框架版本要和驱动兼容矩阵匹配。
缓存与磁盘
大模型镜像构建容易耗尽 /var/lib。先监控磁盘，再清理无用 build cache 和镜像。
CI 建议： 将构建、扫描、推送放在 CI 专用 builder 上，不要把生产 Kubernetes 训练节点当作常规镜像构建机。

14. 网络、端口与 CNI

nerdctl 网络行为取决于安装的 CNI 插件和配置。默认 bridge 网络适合本地调试；Kubernetes Pod 网络由 CNI 插件管理，不建议用 nerdctl 直接改动 Pod 网络对象。

# 查看网络
sudo nerdctl network ls
sudo nerdctl network inspect bridge

# 端口映射
sudo nerdctl run --rm -d --name demo -p 8080:80 nginx:alpine
curl http://127.0.0.1:8080/

# 创建自定义网络
sudo nerdctl network create ai-debug-net
sudo nerdctl run --rm --network ai-debug-net alpine ip addr
场景重点排障命令
本地调试服务端口映射、防火墙、监听地址。ss -lntp, nerdctl port, curl
Kubernetes Pod 网络CNI 插件、Pod IP、NetworkPolicy。kubectl get pod -o wide, CNI 日志。
NCCL/RDMAhostNetwork、IB 设备、路由、MTU、NCCL env。ip addr, ibstat, nccl-tests
AI 网络提醒： 容器能 ping 通不代表 NCCL 性能正常。训练通信还受 NUMA、PCIe、IB/RDMA、RoCE、MTU、QoS 和进程绑定影响。

15. 卷、挂载与文件权限

AI 任务常挂载数据集、模型缓存、checkpoint 目录、共享内存和高速本地盘。nerdctl 的 -v、--mount 与 Docker 风格接近，但权限、SELinux/AppArmor、只读挂载、UID/GID 和 rootless 映射会影响实际读写。

# bind mount 数据目录
sudo nerdctl run --rm -it \
  -v /data/datasets:/datasets:ro \
  -v /local/checkpoints:/checkpoints \
  ubuntu:22.04 bash

# 更明确的 --mount 写法
sudo nerdctl run --rm \
  --mount type=bind,src=/models,dst=/models,readonly \
  ubuntu:22.04 ls -lah /models

# 共享内存对 PyTorch DataLoader/多进程可能重要
sudo nerdctl run --rm --shm-size 16g registry.example.com/ai/train:dev python train.py
症状可能原因检查
容器内目录为空宿主机路径写错、挂载点被覆盖、K8s 挂载未生效。inspect mounts, ls -lah
Permission deniedUID/GID 不匹配、只读挂载、SELinux、rootless 映射。id, stat, mount
训练进程 Bus error/dev/shm 太小。df -h /dev/shm, 调整 --shm-size
数据安全： 调试时不要给容器随意挂载宿主机根目录或敏感凭据目录。只挂载最小必要路径，读多写少，能只读就只读。

16. nerdctl vs docker/crictl/podman

工具不是互相替代，而是面向不同控制面：Docker daemon、CRI、containerd、OCI/rootless。
工具主要面向AI Infra 常用场景限制
nerdctlcontainerd，Docker 风格。K8s 节点镜像缓存、containerd 容器、GPU runtime 快速验证。不是 Kubernetes API；部分 compose/build/GPU 行为依赖组件版本。
dockerDocker daemon。开发机、传统 Docker 环境、镜像构建与调试。Kubernetes containerd 节点通常没有 Docker daemon。
crictlCRI runtime API。kubelet 视角的 pod/container/image 排障。不追求 Docker CLI 体验，构建/compose 不是重点。
podmandaemonless OCI 容器。rootless、本地安全沙箱、系统服务集成。不直接操作 Kubernetes 节点的 containerd 对象。
ctrcontainerd 原生命令。底层兜底调试。命令不友好，生产使用要谨慎。

17. 安全清理与变更流程

AI 节点镜像大、checkpoint 多、日志多，清理需求很常见。但在 containerd 中，镜像、snapshot、content、正在运行的容器和不同 namespace 之间存在引用关系。清理前必须先列出、确认、再执行。

# 先只读观察
df -h
sudo nerdctl -n k8s.io images
sudo nerdctl -n k8s.io ps -a
sudo du -sh /var/lib/containerd 2>/dev/null

# 列出 dangling/unused 候选，先人工确认
sudo nerdctl -n k8s.io image ls

# 只在维护窗口或确认无业务依赖后清理
sudo nerdctl -n k8s.io image prune

# 删除单个明确不用的镜像
sudo nerdctl -n k8s.io rmi registry.example.com/ai/old-train:v1
禁止动作： 不要直接 rm -rf /var/lib/containerd、不要在业务高峰重启 containerd、不要批量删除 k8s.io 镜像而不确认 Pod 依赖。
安全流程： cordon 节点 → 确认无关键 Pod → 记录镜像/容器/磁盘状态 → 清理单个明确对象 → 验证 kubelet/containerd 正常 → 解除 cordon。

18. 常见故障排查

排障顺序是：确认 Kubernetes 语义 → 切到正确 namespace → 区分镜像/启动/GPU/网络/存储问题 → 再决定是否变更。

训练容器启动失败

  1. 用 kubectl describe pod 判断是调度、拉镜像、启动、探针还是运行期问题。
  2. 到 Pod 所在节点，用 sudo nerdctl -n k8s.io ps -a 找容器。
  3. 用 logs --tail 200 和 inspect 检查入口命令、环境变量、挂载、runtime。
  4. GPU 相关问题先验证宿主机 nvidia-smi，再验证容器内 nvidia-smi。
  5. 涉及停止、删除、清理时，回到 Kubernetes 控制面操作，避免绕过控制器。

大镜像预热

# 在维护脚本中对目标节点预拉镜像，注意 registry 凭据和 namespace

最终心法： nerdctl 是 containerd 视角的显微镜；Kubernetes 集群里还必须同时保留 kubectl/crictl 的控制面视角，二者结合才能减少误判。
