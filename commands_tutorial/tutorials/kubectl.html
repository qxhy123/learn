kubectl 深度教程：面向 AI Infra 的集群操作、GPU 调度与训练任务排障

这份教程按 AI Infra 日常值班和训练平台运维来讲 kubectl：先建立“本地客户端把声明式意图发送到 Kubernetes API Server，再由控制器、调度器和 kubelet 收敛状态”的心智模型，然后覆盖 Pods、Jobs、Nodes、GPU 资源、describe/logs/exec/events、requests/limits、nodeSelector、taints、JSONPath、安全 apply/delete、kubectl 与 crictl/k9s 的边界，以及卡住的训练任务如何系统排障。

一句话理解： kubectl 不是直接登录节点改进程，而是通过 API Server 读取或提交 Kubernetes 对象，让控制器和节点代理把“期望状态”收敛成“实际状态”。

1. kubectl 是什么

kubectl 是 Kubernetes 的命令行客户端。它负责把你的读取、创建、更新、删除请求发给 API Server，并把返回的对象、状态、事件和日志展示出来。AI Infra 场景下，它通常用于查看 GPU 节点、定位训练 Pod 为什么没被调度、跟踪 Job 是否重试、确认资源请求是否合理，以及在不破坏运行中的训练任务前提下做诊断。

它擅长什么
对象查询、状态解释、声明式变更、日志查看、进入容器、端口转发、rollout 观察。
它不擅长什么
直接调试节点容器运行时、长期监控、交互式集群浏览、深度 GPU 驱动诊断。
核心边界
kubectl 面向 Kubernetes API；如果 kubelet、containerd 或 GPU 驱动坏在节点本地，可能要配合 crictl、SSH、DCGM 或节点日志。
# 查看当前集群和 namespace
kubectl config current-context
kubectl config view --minify --output 'jsonpath={..namespace}{"\n"}'

# 查看训练命名空间下的核心对象
kubectl get pods,jobs,nodes -n ml-training -o wide

# 查看 GPU 节点标签和可分配资源
kubectl get nodes -L accelerator,nvidia.com/gpu.product
kubectl describe node gpu-node-01
值班习惯： 每次操作前先确认 current-context 和 namespace。误在生产集群执行删除，比命令写错本身更常见。

3. 上下文、命名空间与权限边界

多数事故不是因为 kubectl get，而是因为在错误的集群、错误的 namespace、错误的 selector 上执行了变更。AI 平台通常同时有 dev、staging、prod、多租户训练 namespace 和系统 namespace；操作前要把边界显式打出来。

目标命令说明
确认当前上下文kubectl config current-context检查是否连到生产集群。
列出上下文kubectl config get-contexts查看 cluster/user/namespace 映射。
临时指定 namespacekubectl get pod -n ml-training推荐在脚本中显式写 -n。
检查权限kubectl auth can-i delete jobs -n ml-training先确认 RBAC，而不是等命令失败。
# 值班开场三件事
kubectl config current-context
kubectl get ns
kubectl auth can-i get pods -n ml-training

# 不切全局配置，单次命令显式指定上下文和 namespace
kubectl --context prod-gpu-a -n ml-training get pods -o wide
避免全局副作用： kubectl config set-context --current --namespace=... 会影响后续命令。脚本和 runbook 中优先显式传 --context、-n。

4. AI Infra 常见对象地图

训练平台通常把用户提交的训练任务包装成 Job、Pod、自定义资源或工作流对象。无论上层框架是 Kubeflow、Volcano、Kueue、Argo 还是自研平台，落到 Kubernetes 后，排障仍会回到对象关系：谁创建了谁、Pod 被调度到哪个节点、容器为什么启动或退出。

Pod
容器运行的最小调度单元。训练任务通常至少包含 trainer 容器，可能还有 sidecar。
Job
一次性任务控制器，负责重试、并行度和完成状态。
Node
承载 Pod 的机器，AI 场景重点看 GPU、驱动、allocatable、taints。
PVC / PV
数据集、checkpoint、模型输出的持久化存储。
# 从 Job 追到 Pod
kubectl get job -n ml-training train-resnet -o wide
kubectl get pods -n ml-training -l job-name=train-resnet -o wide

# 从 Pod 追到创建者和所在节点
kubectl get pod -n ml-training train-resnet-abcde -o jsonpath='{.metadata.ownerReferences[0].kind}/{.metadata.ownerReferences[0].name}{"\n"}'
kubectl get pod -n ml-training train-resnet-abcde -o jsonpath='{.spec.nodeName}{"\n"}'

5. get：快速盘点 Pods、Jobs、Nodes

get 是所有排障的第一步：先缩小范围，再进入 describe、logs 或节点诊断。AI Infra 的常用观察维度是 namespace、label、node、phase、restart、age、GPU 节点标签和可分配资源。

场景命令
查看训练 Pod 分布kubectl get pods -n ml-training -o wide
按用户或队列筛选kubectl get pods -n ml-training -l user=alice,queue=gpu-a
查看 Job 完成/失败kubectl get jobs -n ml-training
查看 GPU 节点kubectl get nodes -L nvidia.com/gpu.product,accelerator
排序查看重启kubectl get pods -A --sort-by='.status.containerStatuses[0].restartCount'
# 列出非 Running/Succeeded 的训练 Pod
kubectl get pods -n ml-training \
  --field-selector=status.phase!=Running,status.phase!=Succeeded

# 查看所有 Pending Pod 被卡在哪些节点选择条件上
kubectl get pods -n ml-training --field-selector=status.phase=Pending -o wide

# 查看节点 allocatable 中的 GPU
kubectl get nodes -o custom-columns=NODE:.metadata.name,GPU:.status.allocatable.'nvidia\.com/gpu',CPU:.status.allocatable.cpu,MEM:.status.allocatable.memory
输出选择： -o wide 适合值班快速看节点；-o yaml/json 适合查完整字段；custom-columns 和 jsonpath 适合写 runbook。

6. describe：读懂调度失败与事件

describe 是面向人的诊断视图，会把对象摘要、状态、容器、挂载、资源请求、调度条件和最近事件拼在一起。训练 Pod 卡住时，先看 describe pod 末尾的 Events；GPU 不够、节点选择不匹配、污点未容忍、PVC 未绑定、镜像拉取失败都会出现在这里。

# Pod 为什么 Pending、CrashLoopBackOff 或 ImagePullBackOff
kubectl describe pod -n ml-training train-resnet-abcde

# Job 为什么重试、失败或未完成
kubectl describe job -n ml-training train-resnet

# 节点是否 NotReady、GPU 是否可分配、是否有污点
kubectl describe node gpu-node-01
Events 关键词常见含义下一步
FailedScheduling调度器找不到合适节点。看 GPU/CPU/memory requests、nodeSelector、affinity、taints。
FailedMount数据集或 checkpoint PVC 挂载失败。查 PVC/PV、CSI、存储配额和权限。
ErrImagePull镜像无法拉取。查镜像名、tag、registry secret、节点网络。
BackOff容器重复崩溃或拉取重试。看 logs --previous 和容器 exit code。

7. logs：训练日志、崩溃日志与多容器

kubectl logs 从 kubelet 暴露的容器日志读取 stdout/stderr。AI 训练中常见需求是跟踪当前 trainer 输出、查看上一次崩溃日志、只看最近几分钟、同时看 Job 下所有 Pod，或在多容器 Pod 中指定主容器。

# 跟踪单个训练 Pod 日志
kubectl logs -n ml-training pod/train-resnet-abcde -f --tail=200

# 多容器 Pod 指定容器
kubectl logs -n ml-training train-resnet-abcde -c trainer --tail=200

# 容器重启后查看上一次崩溃日志
kubectl logs -n ml-training train-resnet-abcde -c trainer --previous

# 查看 Job 关联 Pod 日志，适合小规模任务
kubectl logs -n ml-training job/train-resnet --all-containers=true --tail=300

# 限制时间窗口，避免刷屏
kubectl logs -n ml-training train-resnet-abcde --since=15m --timestamps
日志边界： kubectl logs 不是长期日志系统。Pod 被删除、节点日志轮转或容器运行时清理后，日志可能不可用；生产训练应接入集中日志或把关键 checkpoint/metrics 写到持久化系统。

8. exec：进入容器做最小侵入诊断

exec 适合做短时诊断：查看进程、环境变量、挂载路径、NCCL 配置、GPU 可见性、数据集路径是否存在。它不适合把运行容器当服务器长期手工修复；容器内临时改动不会被声明式配置记录，重启后也可能消失。

# 进入 trainer 容器
kubectl exec -n ml-training -it train-resnet-abcde -c trainer -- bash

# 无交互检查 GPU 是否可见
kubectl exec -n ml-training train-resnet-abcde -c trainer -- nvidia-smi

# 检查数据挂载、环境变量和进程
kubectl exec -n ml-training train-resnet-abcde -c trainer -- sh -lc 'pwd; df -h /data; env | grep -E "CUDA|NCCL|RANK|WORLD"; ps aux'
生产警告： 不要在训练容器里手工安装包、覆盖代码或删除 checkpoint 来“修复”问题。正确做法是更新镜像、配置或 Job 模板，然后通过可审计的变更重新提交。

9. events：按时间线排查集群行为

events 能把调度、拉镜像、挂载、启动、重启等行为按时间线展示出来。相比 describe 的对象视图，事件视图更适合回答“刚才发生了什么”和“是不是多个任务同时被同一种原因卡住”。

# Kubernetes 新版本可用 events 子命令
kubectl events -n ml-training --for pod/train-resnet-abcde --watch

# 兼容写法：按时间排序查看 namespace 事件
kubectl get events -n ml-training --sort-by='.lastTimestamp'

# 看全局近期调度失败
kubectl get events -A --field-selector reason=FailedScheduling --sort-by='.lastTimestamp'
事件会过期： Events 有 TTL，不是审计日志。重大生产事故要结合 API audit log、调度器日志、节点日志和平台提交记录。

信息图：GPU 训练 Pod 的调度链路

GPU 不是普通整数资源那么简单：Kubernetes 只负责调度扩展资源，真正设备发现和注入依赖节点插件、驱动与运行时配置。

10. 资源请求、限制与 GPU 资源

调度器主要根据 requests 判断节点是否能承载 Pod。CPU 和内存的 request 太小会导致训练任务互相挤压；GPU request 写错会导致 Pending；内存 limit 太低会导致 OOMKilled；ephemeral-storage 忽略后可能在解压数据集或写缓存时把节点磁盘打满。

资源AI 训练关注点典型症状
cpuDataLoader、预处理、通信线程需要足够 CPU。GPU 利用率低，训练吞吐波动。
memory数据缓存、模型加载、worker 进程会吃内存。OOMKilled、节点内存压力。
nvidia.com/gpu必须通过 limits/request 请求扩展资源，通常 request=limit。Insufficient nvidia.com/gpu。
ephemeral-storage本地缓存、临时数据、日志和解压目录。Pod 被驱逐、节点 DiskPressure。
# 查看 Pod 实际声明的资源
kubectl get pod -n ml-training train-resnet-abcde -o jsonpath='{range .spec.containers[*]}{.name}{" requests="}{.resources.requests}{" limits="}{.resources.limits}{"\n"}{end}'

# 查看节点可分配 GPU
kubectl describe node gpu-node-01 | sed -n '/Allocatable:/,/Events:/p'

# Job YAML 片段：GPU 训练容器资源
resources:
  requests:
    cpu: "16"
    memory: "128Gi"
    ephemeral-storage: "200Gi"
    nvidia.com/gpu: "8"
  limits:
    memory: "128Gi"
    nvidia.com/gpu: "8"
GPU 配额提醒： nvidia.com/gpu 这类扩展资源不能像 CPU 一样超卖。Pending 时先查 namespace ResourceQuota、队列配额、节点 allocatable 和是否启用了 MIG。

11. 调度约束：nodeSelector、亲和性、污点容忍

AI 集群经常按 GPU 型号、网络拓扑、存储靠近性和租户隔离做节点分层。nodeSelector 简单直接；node affinity 表达更强；taints/tolerations 用于“默认不让普通 Pod 上 GPU 节点”或隔离故障节点。

nodeSelector
精确匹配节点标签。适合指定 A100、H100、高速盘池。
affinity
支持 In、NotIn、Exists、权重和软硬约束。适合复杂平台调度。
taints/tolerations
节点打污点，Pod 必须容忍才能调度。适合 GPU 池隔离和故障排空。
# 查看节点标签和污点
kubectl get node gpu-node-01 --show-labels
kubectl describe node gpu-node-01 | grep -i taints

# 给节点打标签：先确认目标节点，再执行
kubectl get node gpu-node-01 --show-labels
kubectl label node gpu-node-01 accelerator=nvidia-a100 --dry-run=server -o yaml
kubectl label node gpu-node-01 accelerator=nvidia-a100

# 训练 Pod 片段
nodeSelector:
  accelerator: nvidia-a100
tolerations:
- key: "gpu"
  operator: "Equal"
  value: "true"
  effect: "NoSchedule"
节点变更警告： 给节点加删 label/taint 会影响后续调度，甚至触发平台级任务倾斜。生产环境应先确认调度策略和自动化系统是否会覆盖这些字段。

流程图：训练 Job 从提交到完成

Job 失败不等于 Pod 还在。排障时先保存 YAML、describe、events 和 previous logs，再决定是否清理对象。

12. Jobs、CronJobs 与训练任务生命周期

训练任务通常比 Web 服务更接近 Job：它运行到完成或失败，而不是长期滚动更新。关键字段包括 parallelism、completions、backoffLimit、activeDeadlineSeconds 和 ttlSecondsAfterFinished。

# 查看 Job 的完成数、失败数和持续时间
kubectl get jobs -n ml-training
kubectl describe job -n ml-training train-resnet

# 暂停 CronJob，先 dry-run 预览
kubectl patch cronjob -n ml-training nightly-eval \
  -p '{"spec":{"suspend":true}}' --type=merge --dry-run=server -o yaml

# 确认后再执行
kubectl patch cronjob -n ml-training nightly-eval \
  -p '{"spec":{"suspend":true}}' --type=merge
字段作用AI 训练建议
backoffLimit失败后最多重试次数。数据或代码错误时过高会浪费 GPU。
activeDeadlineSeconds总运行时长上限。防止训练挂死长期占 GPU。
ttlSecondsAfterFinished完成后自动清理 Job/Pod。不要短到日志和排障证据来不及采集。
parallelism同时运行 Pod 数。分布式训练需配合 rendezvous、rank、网络策略。

13. 调试卡住的训练任务

卡住的训练任务不要一上来就删除。先判断它卡在哪一层：尚未调度、镜像或存储未准备、容器启动后崩溃、进程运行但训练无吞吐、分布式通信互等，还是节点/GPU 层异常。

排障顺序

# 1. 找到 Pod 和节点
kubectl get pods -n ml-training -l job-name=train-resnet -o wide

# 2. 看 Pod 事件：Pending、Mount、Image、OOM、BackOff
kubectl describe pod -n ml-training train-resnet-abcde

# 3. 看当前日志和上一次崩溃日志
kubectl logs -n ml-training train-resnet-abcde -c trainer --tail=200
kubectl logs -n ml-training train-resnet-abcde -c trainer --previous --tail=200

# 4. 检查资源声明和节点资源
kubectl get pod -n ml-training train-resnet-abcde -o yaml | sed -n '/resources:/,/volumeMounts:/p'
kubectl describe node gpu-node-01 | sed -n '/Allocated resources:/,/Events:/p'

# 5. 只做只读 exec 诊断
kubectl exec -n ml-training train-resnet-abcde -c trainer -- nvidia-smi
Pending
看 FailedScheduling，重点查 GPU 不足、label 不匹配、taint 未容忍、PVC 未绑定、ResourceQuota。
CrashLoopBackOff
看 logs --previous，重点查启动命令、依赖、CUDA/NCCL、数据路径、内存 OOM。
Running 但无进展
看训练日志、GPU 利用率、DataLoader CPU、存储吞吐、分布式 rank 是否互等。
Node 异常
看 Node Conditions、device plugin Pod、kubelet/containerd 日志、DCGM/驱动健康。
保留证据： 删除前保存 get -o yaml、describe、events、当前/previous logs 和平台提交参数，避免清理后无法复盘。

14. JSONPath 与自定义输出

当你需要把 kubectl 放进 runbook 或脚本时，不要靠人眼解析表格。-o jsonpath、-o custom-columns 和 -o name 可以把对象字段稳定输出出来。

# 输出 Pod -> Node 映射
kubectl get pods -n ml-training -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.nodeName}{"\n"}{end}'

# 输出每个 Pod 的容器重启次数
kubectl get pods -n ml-training -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .status.containerStatuses[*]}{.name}:{.restartCount}{" "}{end}{"\n"}{end}'

# 输出所有节点 GPU allocatable
kubectl get nodes -o custom-columns=NODE:.metadata.name,GPU:.status.allocatable.'nvidia\.com/gpu'

# 只取对象名，适合继续 xargs
kubectl get pods -n ml-training -l job-name=train-resnet -o name
输出格式适合场景注意
-o wide人工快速查看。字段有限，不适合脚本强依赖。
-o yaml/json完整对象、备份证据。输出大，包含 managedFields。
-o jsonpath抽取字段、脚本化。语法转义较多，复杂时考虑 jq。
-o custom-columns生成表格。只适合字段路径较简单的场景。

15. 安全 apply、diff、rollout 与 delete

声明式管理的基本流程是：本地 YAML 先服务端 dry-run，通过准入和 schema 校验；再 diff 看真实变化；最后 apply。删除和批量 patch 必须先验证 selector 和影响对象。

# 服务端 dry-run：让 API Server 做校验和准入
kubectl apply -f train-job.yaml --dry-run=server -o yaml

# 查看将要改变什么
kubectl diff -f train-job.yaml

# 确认后提交
kubectl apply -f train-job.yaml

# 观察 Deployment 类对象发布
kubectl rollout status deployment/training-api -n platform
kubectl rollout history deployment/training-api -n platform

删除前的安全模板

# 先列出将被删除的对象
kubectl get pods -n ml-training -l job-name=train-resnet -o wide
kubectl get pods -n ml-training -l job-name=train-resnet -o name

# dry-run 预览 delete 请求
kubectl delete pod -n ml-training -l job-name=train-resnet --dry-run=server -o yaml

# 确认不需要保留运行现场后再删除
kubectl delete pod -n ml-training -l job-name=train-resnet
高危命令： 避免 kubectl delete pod --all -A、宽泛 label selector、--force --grace-period=0。强删可能绕过优雅退出，导致 checkpoint 损坏或分布式任务集体失败。

安全图：apply/delete 的变更护栏

安全不是不操作，而是每次操作都能提前证明范围、影响和回滚路径。

16. kubectl vs crictl vs k9s

这三个工具的层级不同。kubectl 是 API 级工具，适合绝大多数对象和状态操作；crictl 是节点容器运行时诊断工具，通常需要登录节点；k9s 是交互式 TUI，适合浏览和观察，但生产变更仍应回到可复制、可审计的命令或 YAML。

工具层级适合不适合
kubectlKubernetes API对象查询、声明式变更、日志、exec、rollout。节点本地 containerd 深度故障。
crictlCRI / 节点运行时kubelet 或 API 不通时，在节点上查容器、镜像、Pod sandbox。跨集群对象管理和声明式变更。
k9s交互式 Kubernetes 客户端快速浏览对象、日志、事件。作为 runbook 的唯一依据；难以审计批量操作。
# kubectl：从 API 看 Pod
kubectl get pod -n ml-training train-resnet-abcde -o wide

# crictl：登录对应节点后，从运行时看容器
sudo crictl ps -a | grep train-resnet
sudo crictl logs CONTAINER_ID

# k9s：适合交互浏览，但关键结论要落回命令记录
k9s -n ml-training

17. 常见故障速查表

症状优先命令常见根因处理方向
Pod Pendingdescribe pod、get eventsGPU 不足、label 不匹配、taint 未容忍、PVC 未绑定。调整 requests、调度约束、配额或存储。
ImagePullBackOffdescribe pod镜像不存在、secret 错误、节点网络或 registry 故障。校验镜像 tag、imagePullSecrets、registry 访问。
CrashLoopBackOfflogs --previous入口命令错误、依赖缺失、配置错误、代码异常。修镜像/命令/配置，重提 Job。
OOMKilleddescribe pod、logs --previous内存 limit 过低、batch size 过大、DataLoader 过多。调内存、batch、worker、模型加载方式。
GPU 不可见exec -- nvidia-smi、describe node未请求 GPU、device plugin/驱动/runtime 异常。查资源声明、NVIDIA plugin、节点驱动。
训练 Running 但不动logs、exec、节点监控数据读取慢、NCCL 互等、网络/存储瓶颈。查吞吐、rank、NCCL env、存储和网络。
