1. lscpu 是什么

lscpu 来自 util-linux，主要汇总 /proc/cpuinfo、/sys/devices/system/cpu/ 等内核接口暴露的 CPU 架构、在线状态、拓扑关系、缓存、NUMA 与虚拟化信息。它适合在登录节点、训练节点、推理服务器、CI runner、容器镜像里快速确认 CPU 资源画像。

它能回答
CPU 架构是什么？逻辑 CPU 有多少？每个 socket 有多少 core？每个 core 有几个 thread？NUMA 节点如何划分？
它不能单独回答
GPU 与 NUMA 的完整距离、实际内存带宽、运行时线程是否真的绑定、容器被 cgroup 限制后的有效 CPU 配额。
AI Infra 用法
给 dataloader、CPU inference、RDMA/NIC 中断、GPU worker、MPI rank、Kubernetes CPU requests/limits 提供拓扑依据。
# 最常用：查看汇总拓扑
lscpu

# 查看每个逻辑 CPU 的归属关系
lscpu -e

# 明确显示在线/离线 CPU
lscpu -a -e=CPU,ONLINE,SOCKET,CORE,NODE

# JSON 输出，便于采集系统解析
lscpu --json
边界提醒： lscpu 显示的是操作系统看到的 CPU 拓扑。BIOS 设置、超线程开关、虚拟机暴露方式、容器 cpuset/cgroup、CPU hotplug 都可能让它与硬件铭牌不一致。

信息图：AI Infra 里 lscpu 的位置

把 lscpu 当成“CPU 侧地图”：它不能替代性能测试，但能解释很多放置错误为什么会慢。

2. 快速上手与常用选项

lscpu 的默认输出适合人读；-e 和 -p 适合看每个逻辑 CPU 的关系；--json 适合被采集器或巡检脚本消费。

命令用途AI Infra 场景
lscpu汇总视图确认节点规格、socket/core/thread/NUMA 数量
lscpu -e扩展表格，逐 CPU 展示给 taskset、numactl、进程绑定准备 CPU 列表
lscpu -p可解析格式，注释以 # 开头脚本生成 CPU 到 NUMA/socket/core 映射
lscpu --jsonJSON 格式资产采集、CI 验证、节点巡检
lscpu -C缓存详情理解 L1/L2/L3 共享边界和 CPU worker 干扰
# 人读汇总
lscpu | sed -n '1,25p'

# 只看和拓扑最相关的字段
lscpu | grep -E '^(Architecture|CPU\\(s\\)|Thread|Core|Socket|NUMA|Model name|Flags)'

# 每个逻辑 CPU 的 socket/core/node 归属
lscpu -e=CPU,ONLINE,SOCKET,CORE,NODE

# 可解析格式，去掉注释
lscpu -p=CPU,SOCKET,CORE,NODE | awk -F, '!/^#/ {print}'
版本差异： 不同 util-linux 版本支持的列名略有差异。脚本里固定列名比解析默认输出更稳；跨发行版巡检要先在目标 OS 上验证。

3. 读懂 sockets、cores、threads

AI 任务调参时最容易混淆的是“逻辑 CPU 数”和“物理核心数”。CPU(s) 通常是逻辑 CPU 数；Socket(s) 是物理 CPU 插槽；Core(s) per socket 是每个 socket 的物理核心；Thread(s) per core 是每个物理核心暴露的硬件线程数。

字段含义计算关系实践意义
CPU(s)在线或可见逻辑 CPU 数Socket(s) * Core(s) per socket * Thread(s) per core，但容器/热插拔可能改变可见值线程池上限、容器 cpuset、监控基线
Thread(s) per core每个物理核心的硬件线程常见为 1 或 2CPU-bound 任务通常不要把 SMT 当成等价物理核
Core(s) per socket单 socket 物理核心数乘 socket 得到物理核心总数推理 worker、dataloader worker、OpenMP 线程估算
Socket(s)物理 CPU 插槽数多 socket 往往对应多个 NUMA 域跨 socket 调度可能带来远端内存访问
# 从默认输出快速计算物理核心数
lscpu | awk -F: '
  /Socket\\(s\\)/ {gsub(/ /,"",$2); sockets=$2}
  /Core\\(s\\) per socket/ {gsub(/ /,"",$2); cores=$2}
  END {print "physical_cores=" sockets * cores}'

# 找出同一个物理 core 对应的逻辑 CPU 兄弟线程
lscpu -e=CPU,SOCKET,CORE,NODE | awk 'NR>1 {k=$2":"$3; a[k]=a[k] " " $1} END {for (k in a) print k ":" a[k]}'
调参提醒： PyTorch dataloader、OpenMP、MKL、oneDNN、tokenizer 线程池都可能吃 CPU。不要只看 GPU 利用率；CPU worker 过多会争抢 cache 和内存带宽，过少会饿死 GPU。

结构图：socket、core、thread 与 NUMA 节点

同一个物理核心上的兄弟逻辑 CPU 共享执行资源；同一个 NUMA 节点里的 CPU 访问本地内存更近。

4. NUMA 节点与内存距离

NUMA 是多 socket 服务器的核心性能边界。训练或推理作业的 CPU 线程如果跑在 NUMA node 0，却频繁访问 node 1 的内存或驱动 node 1 旁边的 GPU，就可能出现吞吐抖动、GPU 利用率周期性下降、CPU system time 升高。

# lscpu 默认输出中的典型 NUMA 字段
lscpu | grep -E '^NUMA|^CPU\\(s\\)'

# 逐 CPU 看 NUMA node
lscpu -e=CPU,NODE,SOCKET,CORE,ONLINE

# 和 numactl 对照看节点内存与距离矩阵
numactl --hardware
现象可能解释下一步
NUMA node(s): 1单 NUMA 或 BIOS 关闭/合并 NUMA继续关注 core/thread/cache，不必做跨 NUMA 绑定
NUMA node0 CPU(s): 0-31
NUMA node1 CPU(s): 32-63		两个 NUMA 节点GPU worker、dataloader、NIC IRQ 尽量按节点分组
CPU 列表交错BIOS 枚举或平台拓扑特殊用 lscpu -e 和 numactl -H 建立真实映射，不要凭编号猜
放置经验： 对单机多 GPU 训练，通常先按 GPU 的 PCIe/NUMA 归属把进程分组，再把每组 dataloader worker 绑定到相邻 NUMA 的 CPU 集合。

5. 缓存层级与 AI 数据管道

lscpu 会显示 L1d、L1i、L2、L3 cache 信息。现代 CPU 的 L3 常按 socket 或芯片小片共享，L2 常按核心私有或小范围共享。对 AI Infra 来说，cache 影响 tokenization、image decode、feature preprocessing、CPU inference、embedding 检索前处理等 CPU-heavy 阶段。

# 查看缓存汇总
lscpu | grep -E 'cache|L1|L2|L3'

# 新版本 util-linux 可显示缓存表
lscpu -C

# 如果 -C 不可用，可从 sysfs 查看
find /sys/devices/system/cpu/cpu0/cache -maxdepth 2 -type f -name size -o -name level -o -name type
缓存通常特点AI Infra 关注点
L1d/L1i最小最快，通常核心私有紧密循环、解码、tokenizer 热路径
L2比 L1 大，延迟较低CPU 推理算子、小 batch 预处理
L3较大，常被多个核心共享多 worker 是否互相挤占，跨 socket 是否命中远端缓存/内存
不要过度解读： cache 大小不等于性能。真实吞吐还受内存带宽、频率、指令集、NUMA、数据格式和软件库调度影响。

6. CPU flags 与指令集能力

Flags 字段非常长，但它直接影响 AI 框架能否使用 AVX2、AVX-512、AMX、BF16、VNNI、AES、虚拟化扩展等能力。CPU-only inference、embedding 服务、量化推理、数据压缩/加密、特征工程都可能受它影响。

Flag大致含义常见影响
avx2256-bit SIMD 扩展通用 CPU 向量化、oneDNN/MKL 路径
avx512f、avx512_vnniAVX-512 基础与 VNNIINT8/BF16 推理、矩阵乘路径，注意频率降档
amx_bf16、amx_int8Intel AMX tile 能力新一代 CPU 推理/训练加速，需要内核与库支持
sve、asimdArm SIMD/SVE 能力Arm 服务器上的向量化后端
vmx、svm硬件虚拟化扩展KVM/嵌套虚拟化线索，不代表当前一定可用
# 检查关键指令集是否存在
lscpu | grep -oE 'avx512[^ ]*|avx2|amx_[^ ]+|vnni|sve|asimd' | sort -u

# 用 awk 把 Flags 拆成一行一个，便于审计
lscpu | awk -F: '/^Flags/ {gsub(/^ /,"",$2); n=split($2,a," "); for(i=1;i<=n;i++) print a[i]}' | sort

# Python 中记录运行环境
python3 - <<'PY'
import subprocess
print(subprocess.check_output(["lscpu"], text=True).splitlines()[0:12])
PY
验证原则： 有 flag 不代表框架一定启用该路径。还要看内核、微码、编译选项、运行库版本、环境变量和实际 benchmark。

7. 虚拟化与容器线索

lscpu 常显示 Hypervisor vendor、Virtualization type、Virtualization 等字段。它们能提示你当前是在裸金属、虚拟机还是被 hypervisor 抽象过的环境里运行。AI Infra 中，这会影响性能可预测性、PMU/性能计数器、NUMA 暴露、CPU pinning 和嵌套虚拟化。

# 查看虚拟化相关字段
lscpu | grep -E 'Virtualization|Hypervisor|Vendor ID|Model name'

# 容器里再看 cgroup 约束，不要只信 lscpu CPU(s)
grep -H . /sys/fs/cgroup/cpu.max 2>/dev/null || true
grep -H . /sys/fs/cgroup/cpuset.cpus.effective 2>/dev/null || true

# systemd 环境也可查看
systemd-detect-virt 2>/dev/null || true
裸金属常见特征
没有 Hypervisor vendor；NUMA 和 cache 信息较完整；可结合 BIOS/firmware、dmidecode、BMC 资产信息确认。
虚拟机常见特征
Hypervisor vendor 可能是 KVM、VMware、Microsoft、Xen；CPU flags 可能被屏蔽；拓扑可能由云厂商策略决定。
容器常见特征
lscpu 可能看到宿主机拓扑，但进程被 cpuset 或 cpu quota 限制；调度上限要看 cgroup。
CI runner 常见特征
CPU 数、型号、flags 可能随机器池变化；不要把一次 lscpu 输出写死为长期假设。

关联图：CPU NUMA 与 GPU locality

GPU locality 是跨 CPU、内存、PCIe、NIC 的问题。lscpu 提供 CPU/NUMA 坐标系，GPU 距离还需要专用拓扑工具确认。

8. GPU locality 上下文

在多 GPU 节点上，CPU 的 NUMA 拓扑决定了 host-side worker 的最佳位置。虽然 lscpu 不显示 GPU，但它告诉你“哪些 CPU 属于哪个 NUMA 节点”，再与 GPU topo 输出对齐，就能规划进程和线程。

# CPU/NUMA 侧地图
lscpu -e=CPU,NODE,SOCKET,CORE | column -t
numactl --hardware

# NVIDIA GPU 拓扑和 CPU affinity 示例
nvidia-smi topo -m
nvidia-smi topo -m | grep -E 'GPU|CPU Affinity|NUMA'

# AMD/ROCm 环境可结合 rocm-smi 或 hwloc
rocm-smi --showtoponuma 2>/dev/null || true
lstopo-no-graphics 2>/dev/null | sed -n '1,80p'
目标做法验证
让 GPU0 的 dataloader 靠近本地 CPU从 GPU topo 找 CPU affinity，再用 lscpu -e 转成 CPU 列表看 GPU 利用率、H2D 拷贝时间、dataloader wait
减少 NIC 到 GPU 的跨 socket 路径将通信进程、IRQ、GPU rank 放在相邻 NUMA看 NCCL/RCCL 日志、RDMA counters、吞吐抖动
避免所有 worker 堆在 node0按 GPU/NUMA 分片 CPU worker 池看 pidstat -t、numastat -p、perf top

9. 可解析输出与脚本化

生产巡检不要解析默认人读输出，因为字段名、缩进、locale、版本差异都可能破坏脚本。优先使用 --json、--parse/-p 或明确列名的 -e=...。

# JSON 输出：适合 jq 或 Python 解析
lscpu --json

# 解析 JSON 中的字段名和值
lscpu --json | jq -r '.lscpu[] | "\(.field)\t\(.data)"'

# CSV-like parse 输出：注释行以 # 开头
lscpu -p=CPU,SOCKET,CORE,NODE | awk -F, '!/^#/ {print "cpu="$1,"socket="$2,"core="$3,"node="$4}'

# 生成每个 NUMA 节点的 CPU 列表
lscpu -p=CPU,NODE | awk -F, '!/^#/ {a[$2]=a[$2]","$1} END {for (n in a) {sub(/^,/,"",a[n]); print "node" n "=" a[n]}}'
脚本建议： 采集脚本里同时记录 lscpu --version、内核版本、容器 cgroup 约束和命令原始输出；只保存派生结果会丢失排障上下文。

10. lscpu vs numactl vs lstopo

这三个工具经常一起出现，但关注层级不同。lscpu 快速、轻量、适合 CPU 汇总；numactl --hardware 更直接展示 NUMA 内存和距离；lstopo 来自 hwloc，能把 CPU、cache、NUMA、PCIe 设备放进同一张拓扑图。

工具优势不足何时使用
lscpu默认系统常见；输出清晰；可看 CPU flags、cache、拓扑GPU/NIC/PCIe 关系有限节点登录后的第一步巡检
numactl --hardwareNUMA CPU 列表、节点内存、距离矩阵直接不展示 CPU flags/cache 细节调优内存绑定、排查远端 NUMA
lstopo全系统拓扑，包含 PCI/OS device，适合 locality可能需要额外安装；输出较复杂多 GPU、多 NIC、复杂 NUMA 机器
# 推荐组合巡检
echo "== lscpu =="; lscpu
echo "== per-cpu topology =="; lscpu -e=CPU,ONLINE,NODE,SOCKET,CORE
echo "== numactl =="; numactl --hardware
echo "== hwloc =="; lstopo-no-graphics 2>/dev/null | sed -n '1,120p'

流程图：性能放置排障路径

拓扑只能提出假设；最终要用真实 workload 的吞吐、延迟、CPU 利用率、NUMA 统计和 GPU 指标验证。

11. 线程放置与亲和性排障

当 GPU 等 CPU 数据、CPU 推理延迟抖动、或者训练吞吐不稳定时，先确认线程实际跑在哪里。lscpu 给出可选 CPU 集合，taskset、numactl、ps、pidstat 用来验证和调整。

# 查看当前 shell 可运行在哪些 CPU 上
taskset -pc $$

# 只读检查某进程亲和性
taskset -pc <PID>

# dry-run 思路：先打印计划使用的 CPU 列表
lscpu -p=CPU,NODE | awk -F, '!/^#/ && $2==0 {print $1}' | paste -sd, -

# 小规模验证：绑定一个 benchmark 到 NUMA node 0 的 CPU
numactl --cpunodebind=0 --membind=0 python train_or_infer_smoke.py
生产警告： 不要直接把在线服务进程强行迁移到新 CPU 集合。先在 canary、副本、离线 benchmark 或低流量窗口验证；错误绑定可能让服务只剩少量 CPU、跨 NUMA 访问变多或与系统中断争抢。

12. 容器、Kubernetes 与 cgroup 限制

容器里运行 lscpu 时，最危险的误判是：命令显示宿主机有 128 个 CPU，但当前容器只被允许使用 8 个 CPU 或 4 个 CPU quota。AI 服务如果按 lscpu 的逻辑 CPU 数自动开线程，可能严重超卖。

# cgroup v2：CPU quota，max 表示不限制
cat /sys/fs/cgroup/cpu.max 2>/dev/null || true

# cgroup v2：实际 cpuset
cat /sys/fs/cgroup/cpuset.cpus.effective 2>/dev/null || true

# cgroup v1 兼容路径
cat /sys/fs/cgroup/cpuset/cpuset.cpus 2>/dev/null || true
cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us 2>/dev/null || true
cat /sys/fs/cgroup/cpu/cpu.cfs_period_us 2>/dev/null || true
环境变量/参数常见用途为什么与 lscpu 有关
OMP_NUM_THREADS控制 OpenMP 线程数默认可能按可见 CPU 过度开线程
MKL_NUM_THREADS控制 MKL 线程数CPU 算子可能与 dataloader 争抢核心
torch.set_num_threads()PyTorch CPU intra-op 线程CPU 前处理/推理需要按配额调小
Kubernetes resources.limits.cpu容器 CPU quota不等价于拓扑亲和，可能导致 throttling
容器原则： 拓扑用 lscpu，有效上限看 cgroup，调度归属看 Kubernetes CPU manager / cpuset，性能结果看实际 benchmark。

13. AI 训练/推理场景清单

单机多 GPU 训练
为每个 rank 分配靠近对应 GPU 的 CPU worker；避免所有 rank 的 dataloader 默认挤在同一 NUMA 节点。
在线推理服务
按 CPU quota 和物理核心设置线程池；对 CPU-heavy tokenizer、reranker、embedding 前处理做独立亲和性验证。
CPU-only 推理
检查 AVX2/AVX-512/AMX/VNNI；评估 SMT 是否增益，很多低延迟场景更看重物理核心和 cache 隔离。
数据预处理集群
压缩、解码、特征转换通常受内存带宽和 cache 影响；用 NUMA 分片减少跨 socket 访问。
NCCL/RCCL 通信
通信线程、NIC IRQ、GPU 进程尽量在相邻拓扑域；跨 socket 会放大尾延迟。
Benchmark 对比
记录 lscpu、内核、微码、BIOS NUMA/SMT 设置、容器限制，避免机器差异污染结论。
# 训练脚本前记录环境快照
mkdir -p run-env
lscpu > run-env/lscpu.txt
lscpu -e=CPU,ONLINE,NODE,SOCKET,CORE > run-env/lscpu-extended.txt
numactl --hardware > run-env/numactl-hardware.txt 2>&1 || true
nvidia-smi topo -m > run-env/nvidia-topo.txt 2>&1 || true

14. 常见坑与排障流程

坑 1：把逻辑 CPU 当物理核心
CPU(s) 包含 SMT 线程；CPU-bound 线程池通常先按物理核心估算。
坑 2：凭 CPU 编号猜 NUMA
编号可能交错或被容器裁剪；用 lscpu -e=CPU,NODE 验证。
坑 3：忽略 cgroup
容器里 lscpu 可能看见宿主机，但 quota/cpuset 才是当前进程可用资源。
坑 4：看到 AVX-512 就认为更快
频率降档、库实现、batch size、内存带宽都可能改变结果。
坑 5：只看 CPU 不看 GPU/NIC
多 GPU 节点需要把 NUMA 与 PCIe、NIC、GPU topo 一起看。
坑 6：绑定后不验证
错误亲和性可能让性能更差；必须用真实 workload 或代表性 benchmark 验证。

排障命令模板

# 1. 拓扑快照
lscpu
lscpu -e=CPU,ONLINE,NODE,SOCKET,CORE

# 2. NUMA 与 GPU/NIC 关系

15. 生产巡检模板与练习

节点巡检模板

#!/usr/bin/env bash
set -euo pipefail

out="${1:-cpu-topology-report}"
mkdir -p "$out"

lscpu > "$out/lscpu.txt"
lscpu -e=CPU,ONLINE,NODE,SOCKET,CORE > "$out/lscpu-extended.txt"
lscpu -p=CPU,SOCKET,CORE,NODE > "$out/lscpu-parse.csv"
lscpu --json > "$out/lscpu.json" 2>/dev/null || true
numactl --hardware > "$out/numactl-hardware.txt" 2>&1 || true
nvidia-smi topo -m > "$out/nvidia-topo.txt" 2>&1 || true
cat /sys/fs/cgroup/cpu.max > "$out/cgroup-cpu-max.txt" 2>/dev/null || true
cat /sys/fs/cgroup/cpuset.cpus.effective > "$out/cgroup-cpuset-effective.txt" 2>/dev/null || true

echo "report written to $out"

练习任务

  1. 用 lscpu 计算当前机器的物理核心数，并与 nproc 对比。
  2. 用 lscpu -e 找出每个 NUMA 节点包含哪些逻辑 CPU。
  3. 检查当前环境是否暴露 avx2、avx512、amx 或 Arm SIMD flags。
  4. 在容器中比较 lscpu 的 CPU 数与 cgroup quota/cpuset。
  5. 为一个 GPU worker 设计 CPU 绑定方案，并说明需要哪些额外工具验证 GPU locality。
  6. 运行一次小 benchmark，对比绑定前后吞吐或延迟，不要只凭拓扑判断。
上线前检查： 记录基线、只改一个变量、保留回滚方案、用真实指标验证。CPU 拓扑优化通常是“测量驱动”的工程，不是一次命令就能永久解决。
