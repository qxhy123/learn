crictl 深度教程：AI Infra 场景下的 CRI 与 Kubernetes 节点调试

这份教程面向 AI Infra、Kubernetes 平台和 GPU 集群运维场景，系统讲清楚 crictl 如何直接连接节点上的 CRI 运行时，查看 Pod sandbox、容器、镜像、日志、exec、inspect、stats、runtime 配置和 GPU 运行时线索。它不是替代 kubectl 的通用管理工具，而是在 API Server 不可用、kubelet 异常、GPU Pod 启动失败、镜像拉取慢、containerd/CRI-O 需要现场排障时，绕过控制面直接读节点事实的工具。

一句话理解： crictl 是 CRI 客户端。它不通过 Kubernetes API Server，而是连接本机 containerd、CRI-O 或其他 CRI endpoint，查看 kubelet 交给运行时之后的真实 Pod/容器/镜像状态。

1. crictl 是什么

crictl 是 Kubernetes SIG Node 维护的 CRI 工具，面向实现了 Container Runtime Interface 的运行时。Kubernetes 节点上的 kubelet 通过 CRI 调用运行时创建 Pod sandbox、容器和镜像；crictl 使用同一类接口读取或操作这些对象。

它擅长什么
在节点本地查看 Pod sandbox、容器、镜像、日志、inspect、stats 和 runtime info，尤其适合控制面不可用时排障。
它不擅长什么
不负责 Deployment/Job/Service 等 Kubernetes API 资源编排，也不理解调度、控制器期望状态和 RBAC 审计上下文。
它的定位
节点现场工具。它看的是运行时事实，不是 Kubernetes API Server 里的期望状态。
# 查看节点上 CRI 运行时看到的容器
sudo crictl ps -a

# 查看 Pod sandbox，通常能看到 Kubernetes Pod 名称、namespace、attempt
sudo crictl pods

# 查看容器日志，不需要 kubectl 连接 API Server
sudo crictl logs <container-id>

# 查看容器详细配置、状态、挂载、环境变量、标签
sudo crictl inspect <container-id>
权限提醒： CRI socket 通常属于 root 或特定运行时用户组。生产节点上使用 sudo 等同于本机高权限操作，应遵守变更窗口和审计要求。

2. 整体模型：kubectl、kubelet、CRI 与运行时

调试 Kubernetes Pod 时，最容易混淆的是“API 里显示什么”和“节点运行时实际做了什么”。kubectl 主要看 API Server；crictl 直接看节点 runtime。两者经常互补，而不是互相替代。

信息图：crictl 位于 Kubernetes 控制面之外

当 API Server、kubectl 或控制器路径不可用时，crictl 仍可在节点本机读取 runtime 状态。
层级主要工具你能确认什么
Kubernetes APIkubectlPod 期望状态、调度结果、事件、控制器、Service、Secret、ConfigMap 等。
kubeletjournalctl -u kubelet节点代理是否能注册、拉镜像、创建 sandbox、调用 CNI/CSI/Device Plugin。
CRI 运行时crictlruntime 实际创建了哪些 sandbox/container，容器退出码、日志、镜像和资源统计。
底层系统systemctl、journalctl、nvidia-smicontainerd/CRI-O、CNI、GPU 驱动、内核、磁盘、网络是否正常。

3. 安装、版本与兼容性

生产环境中建议让 cri-tools 与 Kubernetes 小版本保持一致或接近。CRI 会随 Kubernetes 演进，版本差距过大可能导致新字段、新命令或行为不完全匹配。

# 查看 crictl 版本
crictl --version

# 查看运行时版本和 CRI 服务响应
sudo crictl version

# 查看帮助和子命令
crictl --help
crictl ps --help
检查项命令判断
二进制存在command -v crictl没有输出说明未安装或 PATH 不包含。
版本匹配crictl --version优先与节点 Kubernetes 小版本一致。
能连 runtimesudo crictl info能返回 runtime 配置和状态，说明 endpoint 可用。
权限正常sudo crictl ps普通用户失败但 sudo 成功，通常是 socket 权限问题。
版本心智模型： crictl 是客户端，containerd/CRI-O 是服务端，kubelet 也是客户端。排障时同时记录三者版本，避免把协议不匹配误判成业务故障。

4. 连接 containerd 与 CRI-O endpoint

crictl 必须知道 runtime endpoint 和 image endpoint。常见配置文件是 /etc/crictl.yaml，也可以使用环境变量或命令行参数。AI 集群节点大多使用 containerd，也可能使用 CRI-O 或 cri-dockerd。

信息图：endpoint 选择路径

endpoint 配错时，crictl 的错误通常是连接失败、超时或看不到预期容器。

containerd 常见配置

# /etc/crictl.yaml
runtime-endpoint: unix:///run/containerd/containerd.sock
image-endpoint: unix:///run/containerd/containerd.sock
timeout: 10
debug: false

CRI-O 常见配置

# /etc/crictl.yaml
runtime-endpoint: unix:///run/crio/crio.sock
image-endpoint: unix:///run/crio/crio.sock
timeout: 10
debug: false

临时指定 endpoint

# containerd
sudo crictl \
  --runtime-endpoint unix:///run/containerd/containerd.sock \
  --image-endpoint unix:///run/containerd/containerd.sock \
  ps -a

# CRI-O
sudo crictl \
  --runtime-endpoint unix:///run/crio/crio.sock \
  --image-endpoint unix:///run/crio/crio.sock \
  pods
运行时常见 socket确认方式
containerdunix:///run/containerd/containerd.socksystemctl status containerd、ls -l /run/containerd/containerd.sock
CRI-Ounix:///run/crio/crio.socksystemctl status crio、ls -l /run/crio/crio.sock
cri-dockerdunix:///var/run/cri-dockerd.sock旧 Docker 兼容路径，现代 Kubernetes 集群较少见。
不要盲扫 endpoint： 连接到错误 socket 可能看到空结果或旧运行时对象。先从 kubelet 参数 --container-runtime-endpoint、systemd unit 或节点基线配置确认。

5. 基础命令速览

先建立对象关系：Pod sandbox 是 Pod 的运行时外壳，容器运行在 sandbox 里，镜像由 image service 管理。大多数排障从 pods 和 ps -a 开始。

目标常用命令用途
运行时健康crictl info、crictl version确认 CRI 服务可用、版本和 runtime 配置。
Pod sandboxcrictl pods、crictl inspectp定位 Kubernetes Pod 对应的 sandbox。
容器crictl ps -a、crictl inspect查看容器状态、退出码、镜像、标签、挂载。
日志和交互crictl logs、crictl exec控制面异常时直接读取容器日志或进入容器。
镜像crictl images、crictl pull、crictl rmi排查镜像缓存、拉取失败、磁盘占用。
统计crictl stats、crictl statsp查看容器和 Pod sandbox 的 CPU、内存、文件系统指标。
# 排障起手式：确认 endpoint、Pod、容器、最近失败容器
sudo crictl info
sudo crictl pods
sudo crictl ps -a

# 只看非 running 的容器，快速找 CrashLoop / Exited
sudo crictl ps -a | grep -v Running

# 查看某个容器的日志和 inspect
sudo crictl logs <container-id> | tail -100
sudo crictl inspect <container-id>
ID 使用习惯： crictl 多数命令支持短 ID，但事故排查记录建议保留完整 ID、节点名、时间和 endpoint。

6. Pod sandbox 调试

CRI 里 Pod 通常先表现为 sandbox。网络命名空间、Pod IP、labels、annotations、attempt 等信息常能从 inspectp 看到。GPU 训练任务排障时，sandbox 能帮你确认 Pod 是否已经在目标节点创建，还是停留在调度/API 层。

# 列出所有 Pod sandbox
sudo crictl pods

# 按名称或 namespace 粗筛
sudo crictl pods | grep training
sudo crictl pods | grep kube-system

# 查看 sandbox 详情
sudo crictl inspectp <pod-sandbox-id>

# 查看 Pod sandbox 统计
sudo crictl statsp <pod-sandbox-id>
字段或现象排障意义
metadata.name / namespace确认对应 Kubernetes Pod，而不是同名旧对象。
state确认 sandbox 是否 Ready。sandbox 不 Ready 时容器通常无法正常创建。
attempt重建次数。频繁增加可能对应网络、镜像、runtime 或 kubelet 重试。
labels / annotations可映射 Kubernetes UID、容器名、runtime handler、sandbox 配置。
Pod IP判断 CNI 是否成功分配网络，以及日志服务或训练通信是否有地址。
sandbox 删除风险： crictl rmp 会移除 Pod sandbox。除非确认它已停止、孤儿化或 kubelet 无法清理，否则应优先让 kubelet 自己回收。

7. 容器列表、状态与退出码

crictl ps 默认只显示运行中容器；排障必须加 -a，否则会漏掉刚退出的 init 容器、失败任务容器和 CrashLoop 中间态。

# 运行中容器
sudo crictl ps

# 所有容器，包括 Exited 和 Unknown
sudo crictl ps -a

# 根据 Pod sandbox 查询容器
sudo crictl ps -a --pod <pod-sandbox-id>

# 根据名称粗筛 AI 任务容器
sudo crictl ps -a | grep -E 'train|worker|launcher|nccl'
状态常见含义下一步
Running容器进程仍在运行。看 logs、exec、stats 和 GPU 使用情况。
Exited进程已退出，可能成功也可能失败。看 inspect 里的 exitCode、reason、finishedAt，再看日志。
Created已创建但未运行，可能等待 runtime 启动或 kubelet 动作。看 kubelet/containerd 日志和 inspect。
Unknownruntime 状态异常或查询失败。检查 runtime 服务、节点压力、shim 进程和系统日志。
# 从 inspect 中定位退出信息，适合没有 jq 的节点
sudo crictl inspect <container-id> | grep -E 'exitCode|reason|message|startedAt|finishedAt' -A2 -B2

# 保存现场，便于事故复盘
sudo crictl inspect <container-id> > /tmp/crictl-inspect-<container-id>.json
sudo crictl logs <container-id> > /tmp/crictl-logs-<container-id>.log
AI 训练任务提示： 多 worker 任务里，launcher 退出和 worker 退出含义不同。先用 Pod sandbox 或容器名确认你看的容器角色。

8. 日志、exec 与现场确认

当 kubectl logs 因 API Server、kubelet 代理或网络问题不可用时，crictl logs 常能直接读取节点本地日志。crictl exec 则适合确认容器内环境变量、挂载、GPU 设备文件和训练进程。

# 查看最后 200 行日志
sudo crictl logs --tail=200 <container-id>

# 跟随日志
sudo crictl logs -f <container-id>

# 带时间戳查看
sudo crictl logs --timestamps <container-id>

# 进入容器执行命令
sudo crictl exec -it <container-id> /bin/sh

AI Infra 现场检查

# 容器内确认 GPU 设备和环境变量
sudo crictl exec -it <container-id> /bin/sh -c 'ls -l /dev/nvidia* 2>/dev/null; env | grep -E "CUDA|NVIDIA|ROCR|HSA|GPU"'

# 容器内确认训练进程
sudo crictl exec -it <container-id> /bin/sh -c 'ps -ef | grep -E "python|torchrun|deepspeed|mpirun|ray" | grep -v grep'

# 容器内确认共享内存大小，NCCL/数据加载常受影响
sudo crictl exec -it <container-id> /bin/sh -c 'df -h /dev/shm; mount | grep shm'
exec 边界： crictl exec 是节点高权限调试入口。不要在生产训练容器内修改模型文件、依赖或运行时配置，除非这是明确批准的临时处置。

9. inspect 与字段定位

inspect、inspectp 和 inspecti 输出 JSON。它们能回答很多 ps 看不到的问题：容器是哪个 Pod 创建的、使用什么镜像、挂载了哪些路径、环境变量是什么、runtime handler 是什么、退出码和失败消息是什么。

命令对象常查内容
crictl inspect CONTAINER容器状态、exitCode、env、mounts、labels、annotations、image、pid。
crictl inspectp PODPod sandboxPod metadata、namespace、network、labels、attempt、sandbox 状态。
crictl inspecti IMAGE镜像镜像 ID、repoTags、repoDigests、size、image spec。
# 没有 jq 时，用 grep 定位关键字段
sudo crictl inspect <container-id> | grep -E 'name|image|state|exitCode|reason|message|runtime|mounts|env' -A3 -B2

# 如果节点有 jq，可以更精确地取字段
sudo crictl inspect <container-id> | jq '.status'
sudo crictl inspectp <pod-id> | jq '.status.metadata, .status.network'

# 查看容器标签，映射回 Kubernetes Pod
sudo crictl inspect <container-id> | grep -E 'io.kubernetes.pod.name|io.kubernetes.pod.namespace|io.kubernetes.container.name' -A1
复盘建议： 事故现场先保存 inspect 原始 JSON，不要只贴终端截图。JSON 能保留时间戳、exitCode、labels、annotations 和 runtime 字段。

10. 镜像与拉取排障

AI 镜像通常体积大、层数多、依赖私有 registry、跨地域镜像缓存和凭证。crictl images 与 pull 能帮助确认“节点 runtime 能否拉到镜像”，这比只看 Pod 事件更接近真实问题。

# 列出镜像缓存
sudo crictl images

# 按仓库名筛选
sudo crictl images | grep -E 'cuda|pytorch|training|registry.example.com'

# 手动拉取镜像，复现 ImagePullBackOff
sudo crictl pull registry.example.com/ai/pytorch:cuda12.4

# 查看镜像详情
sudo crictl inspecti registry.example.com/ai/pytorch:cuda12.4
现象常见原因crictl 侧检查
拉取超时registry 网络、代理、DNS、跨地域带宽。crictl pull 复现，配合 journalctl -u containerd。
认证失败imagePullSecret、credential provider、节点凭证配置错误。pull 错误消息和 kubelet 日志一起看。
磁盘不足镜像层和容器 writable layer 占满。crictl images、crictl stats、节点磁盘工具。
架构不匹配arm64/amd64 镜像或 manifest 配置错误。inspecti 查看镜像 spec，结合节点架构。
清理提醒： 大镜像不能随手删。先确认没有运行中容器使用，再删除未使用或过期镜像；否则 kubelet 可能立即重新拉取，造成更大网络压力。

11. Kubernetes 节点故障工作流

节点故障时，按层次排查能避免误判：先确认 kubelet 和 runtime 服务，再确认 CRI endpoint，再看 sandbox、容器、日志、镜像和系统资源。

流程图：节点现场排障路径

排障顺序越稳定，越不容易在高压现场执行危险操作。
# 1. 节点上确认服务
systemctl status kubelet --no-pager
systemctl status containerd --no-pager   # 或 systemctl status crio

# 2. 看 kubelet 和 runtime 日志
journalctl -u kubelet -n 200 --no-pager
journalctl -u containerd -n 200 --no-pager

# 3. 确认 CRI 可用
sudo crictl info
sudo crictl version

# 4. 查 Pod 和容器
sudo crictl pods
sudo crictl ps -a
sudo crictl logs --tail=200 <container-id>
控制面不可用时： 如果 kubectl 完全不可用，crictl 仍可以帮助确认关键组件容器，例如 kube-apiserver、etcd、coredns、device-plugin 是否在节点上运行。

12. GPU Pod 与 AI 训练任务线索

crictl 不能替代 nvidia-smi、dcgmi、rocm-smi 或 device plugin 日志，但它能确认 GPU 容器在 CRI 层是否拿到了正确的环境、挂载、runtime handler 和启动错误信息。

容器层线索
看 inspect 中的 env、mounts、annotations、labels、logPath、pid、image 和 runtime 相关字段。
节点层线索
结合 nvidia-smi、ls -l /dev/nvidia*、device plugin 日志、containerd/CRI-O 日志判断。
# 筛选 GPU 相关 Pod/容器
sudo crictl pods | grep -E 'gpu|train|worker|llm|nccl'
sudo crictl ps -a | grep -E 'gpu|train|worker|llm|nccl|device-plugin'

# 查看 NVIDIA device plugin 日志
sudo crictl ps -a | grep nvidia-device-plugin
sudo crictl logs <nvidia-device-plugin-container-id> | tail -200

# 查看容器内 GPU 可见性
sudo crictl exec -it <container-id> /bin/sh -c 'ls -l /dev/nvidia* 2>/dev/null; nvidia-smi 2>/dev/null || true'

# 查 runtime handler、NVIDIA 环境变量和设备挂载线索
sudo crictl inspect <container-id> | grep -E 'runtime|NVIDIA|CUDA|ROCR|HSA|/dev/nvidia|/dev/dri|mounts' -A4 -B2
现象可能位置检查路径
Pod Pending，节点没有容器调度、配额、资源声明、taint/toleration。kubectl describe pod，crictl pods 看不到目标是正常的。
容器创建失败runtime handler、OCI hook、NVIDIA Container Toolkit、CDI 配置。crictl inspect、kubelet/containerd 日志、device plugin 日志。
容器运行但无 GPU设备文件、环境变量、MIG/CDI、驱动容器、权限。crictl exec 检查 /dev/nvidia* 和 NVIDIA_VISIBLE_DEVICES。
NCCL 初始化失败网络、IB/RDMA、共享内存、GPU 拓扑。容器日志、/dev/shm、主机网络/RDMA/GPU 工具一起看。
GPU 排障边界： crictl 只能说明 runtime 层给了什么，不保证驱动、CUDA、NCCL、RDMA 或训练框架可用。不要只凭 crictl ps 的 Running 判定训练健康。

13. stats、info 与运行时健康

crictl stats 能给出 CRI 视角的资源使用，但它不是完整性能分析工具。AI 任务排障时，应把它作为“容器是否明显耗尽资源”的快速信号，再结合 nvidia-smi、pidstat、iostat、sar、cgroup 和 runtime 日志。

# 所有容器统计
sudo crictl stats

# 指定容器统计
sudo crictl stats <container-id>

# Pod sandbox 统计
sudo crictl statsp <pod-sandbox-id>

# runtime 配置和状态
sudo crictl info
信号解读补充工具
CPU 很高训练进程、数据加载、压缩解压、日志输出可能占满 CPU。pidstat、top、perf。
内存接近 limit可能 OOMKilled 或进入内存压力。crictl inspect、dmesg、journalctl -u kubelet。
文件系统占用增长日志、checkpoint、缓存或容器 writable layer 膨胀。du、iotop、runtime 存储目录。
runtime info 异常runtime 配置、CNI、snapshotter 或 plugin 状态异常。containerd/CRI-O 日志和配置文件。

14. crictl vs kubectl/nerdctl/docker

这些工具常在同一节点出现，但服务对象不同。排障时先选对接口，否则会出现“kubectl 看不到但 crictl 看得到”或“nerdctl namespace 不对所以看不到容器”的混乱。

对比图：选工具先选控制面

工具不是越底层越好。先确定你要看 Kubernetes API、CRI、containerd 还是 Docker Engine。
工具接口优点风险或限制
kubectlKubernetes API理解控制器、事件、调度、权限和资源对象。依赖 API Server 和 kubelet 代理路径。
crictlCRI直接看 kubelet 调用 runtime 后的事实。缺少 Kubernetes 期望状态语义，误删风险高。
nerdctlcontainerd适合 containerd namespace、镜像和类似 Docker 的操作。Kubernetes 容器通常在 k8s.io namespace，直接操作需谨慎。
dockerDocker Engine适合 Docker 主机。现代 Kubernetes 已不通过 dockershim 使用 Docker Engine 管理 Pod。

15. 安全清理与回收空间

空间告警时最危险的动作是直接删除容器、Pod sandbox 或镜像。正确流程是先确认对象状态、归属、是否由 kubelet 管理、是否仍被运行中容器引用，再执行最小范围清理。

只读确认

# 看磁盘压力和 runtime 缓存大致情况
df -h
sudo crictl images
sudo crictl ps -a
sudo crictl stats

# 列出已退出容器，先人工确认
sudo crictl ps -a | grep Exited

# 列出可能很大的 AI 镜像
sudo crictl images | grep -E 'cuda|pytorch|tensorflow|training|llm'

谨慎清理容器

# 先列出候选容器，不删除
sudo crictl ps -a | grep Exited

# 对单个已退出容器，先保存日志和 inspect
sudo crictl logs <container-id> > /tmp/<container-id>.log 2>&1
sudo crictl inspect <container-id> > /tmp/<container-id>.inspect.json

# 确认不再需要后，删除单个容器
sudo crictl rm <container-id>

谨慎清理镜像

# 先确认没有运行中容器使用目标镜像
sudo crictl ps -a | grep 'registry.example.com/ai/pytorch:old'

# 确认可删除后，再删除指定镜像
sudo crictl rmi registry.example.com/ai/pytorch:old
危险命令边界： 不要在不了解节点状态时批量执行 crictl rm、crictl rmp、crictl rmi --prune。这些动作会改变 runtime 事实，可能触发 kubelet 重建、镜像重新拉取、训练任务中断或现场证据丢失。

16. 常见错误与排障树

crictl 报错通常集中在 endpoint、权限、runtime 服务、版本兼容、对象 ID 和镜像认证。先判断错误发生在“连接 CRI”还是“操作对象”。

排障图：crictl 命令失败时怎么查

crictl 排障先解决连接和权限，再看对象和运行时错误；不要用删除动作验证猜想。
错误/现象可能原因处理
connection refused 或 deadline exceededruntime 未运行、endpoint 错误、socket 不存在、服务卡死。检查 /etc/crictl.yaml、systemctl status、ls -l socket 和 runtime 日志。
permission denied当前用户无权访问 CRI socket。使用 sudo 或按组织规范加入受控用户组。
not foundID 写错、对象已被 kubelet 回收、endpoint 指向另一运行时。重新执行 ps -a 或 pods 获取当前 ID。
ImagePull 失败认证、DNS、代理、registry、磁盘或架构问题。crictl pull 复现并结合 kubelet/runtime 日志。
看不到 PodPod 尚未调度到该节点、endpoint 错误或已被清理。先用 kubectl get pod -o wide 确认节点；控制面不可用时查 kubelet 日志。

17. AI Infra 实战剧本

剧本 A：训练 Pod CrashLoopBackOff

# API 侧确认节点和事件
kubectl get pod -n train -o wide | grep job-a
kubectl describe pod -n train job-a-worker-0

# 节点侧确认容器和日志
sudo crictl pods | grep job-a
sudo crictl ps -a | grep job-a
sudo crictl logs --tail=300 <container-id>
sudo crictl inspect <container-id> | grep -E 'exitCode|reason|message|OOM|finishedAt' -A3 -B2

剧本 B：GPU Pod Running 但训练看不到 GPU

# 看 device plugin 是否健康
sudo crictl ps -a | grep -E 'nvidia-device-plugin|amd-gpu|device-plugin'
sudo crictl logs <device-plugin-container-id> | tail -200

# 看业务容器的设备和环境
sudo crictl exec -it <container-id> /bin/sh -c 'ls -l /dev/nvidia* 2>/dev/null; env | grep -E "NVIDIA|CUDA"'
sudo crictl inspect <container-id> | grep -E 'NVIDIA|CUDA|runtime|/dev/nvidia|mounts' -A4 -B2

剧本 C：大镜像拉取慢或失败

# 节点上直接复现拉取
time sudo crictl pull registry.example.com/ai/llm-train:cuda12.4

# 看 runtime 日志中的 registry、认证、代理、解压错误
journalctl -u containerd -n 300 --no-pager

# 查看镜像是否已缓存
sudo crictl images | grep 'llm-train'

剧本 D：API Server 不可用但要确认控制面容器

# 控制平面节点上直接看静态 Pod 容器
sudo crictl ps -a | grep -E 'kube-apiserver|etcd|kube-controller|kube-scheduler'
sudo crictl logs --tail=200 <kube-apiserver-container-id>
sudo crictl logs --tail=200 <etcd-container-id>
记录模板： 每次现场排障至少记录节点名、时间、crictl 版本、endpoint、Pod UID/名称、container ID、exitCode、日志片段、inspect JSON 路径和你执行过的变更命令。

18. 命令清单与练习路线

常用命令清单

类别命令说明
健康crictl info、crictl version确认 CRI endpoint 和 runtime 状态。
Podcrictl pods、crictl inspectp、crictl statsp查看 Pod sandbox、网络和统计。
容器crictl ps -a、crictl inspect、crictl stats查看容器状态、资源和详细配置。
交互crictl logs、crictl exec、crictl attach读取日志、进入容器、附加进程输出。
镜像crictl images、crictl pull、crictl inspecti、crictl rmi排查镜像缓存和拉取。
清理crictl rm、crictl rmp删除容器或 sandbox，必须谨慎。

练习路线

  1. 在测试节点上配置 /etc/crictl.yaml，分别用 crictl info 和 crictl version 验证 endpoint。
  2. 创建一个测试 Pod，用 kubectl get pod -o wide 找到节点，再登录节点用 crictl pods 和 ps -a 映射它。
  3. 让测试容器主动退出，观察 crictl ps -a、logs 和 inspect 中的退出码。
  4. 拉取一个大镜像，比较 kubectl describe pod 事件和 crictl pull 的错误信息。
  5. 在 GPU 测试 Pod 中用 crictl exec 查看 /dev/nvidia*、环境变量和 nvidia-smi。
  6. 模拟磁盘压力时，只做只读确认，写出清理计划后再删除单个已退出容器。
