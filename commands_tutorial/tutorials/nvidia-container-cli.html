1. nvidia-container-cli 是什么

nvidia-container-cli 来自 libnvidia-container。它不是训练程序，也不是 Docker 命令的替代品，而是 NVIDIA 容器工具链里的低层执行器和诊断入口。高层的 Docker、containerd、CRI、Kubernetes device plugin、NVIDIA runtime wrapper 最终都需要解决同一个问题：普通 Linux 容器默认看不到宿主机 GPU 驱动栈，必须在启动前显式注入设备节点、驱动库和权限。

它擅长什么
诊断宿主机驱动、枚举 GPU、检查可见设备、列出运行时将注入的库和设备、生成详细 debug 日志。
它不负责什么
不负责训练框架性能调优，不直接管理 Kubernetes 调度策略，也不建议作为日常配置 Docker/containerd 的首选入口。
AI Infra 价值
当 docker run --gpus all、nerdctl --gpus 或 Pod 内 nvidia-smi 失败时，它能把问题拆回“宿主机驱动、设备可见性、库注入、runtime 配置、容器镜像”几个层次。
# 查看命令是否存在
command -v nvidia-container-cli
nvidia-container-cli --version

# 只读诊断宿主机驱动与 GPU
sudo nvidia-container-cli --load-kmods info

# 输出更详细的诊断日志到终端或文件
sudo nvidia-container-cli --debug=/dev/stderr --load-kmods info
sudo nvidia-container-cli --debug=/tmp/nvidia-container-cli.log --load-kmods info
权限提醒： info 多数情况下只读，但加载内核模块、访问设备节点、读取某些驱动状态可能需要 root。生产节点上优先以只读方式收集证据，不要直接修改 runtime 配置。

2. 整体模型：OCI 启动前的 GPU 注入器

心智模型：容器启动不是“把 GPU 传进去”这么简单，而是一次受 env、capabilities、cgroups、驱动版本和 rootfs 共同影响的注入过程。

3. 安装位置与版本确认

在排障前先确认三件事：宿主机 NVIDIA 驱动正常、NVIDIA Container Toolkit 组件存在、容器运行时确实配置了 NVIDIA runtime 或 CDI。nvidia-container-cli 通常位于 /usr/bin 或发行版包安装路径中。

检查项命令判断
宿主机驱动nvidia-smi能列出 GPU、Driver Version、CUDA Version，是容器 GPU 成功的前提。
低层 CLInvidia-container-cli --version确认 libnvidia-container 包已安装。
运行时工具nvidia-ctk --version用于配置 Docker/containerd、生成 CDI spec、查看 runtime 配置。
Docker GPUdocker info | grep -i runtime确认 NVIDIA runtime 是否被注册；现代 Docker 也可通过 --gpus 请求设备。
containerd GPUgrep -R "nvidia" /etc/containerd /etc/nvidia-container-runtime 2>/dev/null确认是否配置 NVIDIA runtime class 或 CDI。
# 最小巡检：不修改系统
nvidia-smi
command -v nvidia-container-cli && nvidia-container-cli --version
command -v nvidia-ctk && nvidia-ctk --version

# 查看 NVIDIA Container Runtime 配置文件是否存在
ls -l /etc/nvidia-container-runtime/config.toml 2>/dev/null || true
版本关系： 容器镜像里的 CUDA toolkit 版本、宿主机驱动版本、NVIDIA Container Toolkit 版本是三条不同线。多数“容器里看不到 GPU”的问题不是 CUDA 包没装，而是宿主机驱动、runtime 配置或设备注入失败。

4. info：宿主机 GPU 与驱动诊断

info 是最常用的低层只读诊断命令。它会尝试初始化 NVIDIA 驱动接口，输出 NVRM 版本、CUDA driver 能力、GPU 列表、UUID、架构、PCI Bus ID 等信息。若这里失败，Docker 或 Kubernetes 里的 GPU 容器通常也会失败。

# 推荐的宿主机低层诊断入口
sudo nvidia-container-cli --load-kmods info

# 常见输出重点
# NVRM version:   ...
# CUDA version:   ...
# Device Index:   0
# Device Minor:   0
# Model:          NVIDIA ...
# GPU UUID:       GPU-...
# Bus Location:   00000000:xx:00.0
# Architecture:   ...
现象含义下一步
info 正常，容器失败宿主机驱动大概率正常，问题转向 runtime 配置、env、cgroups、镜像或权限。看 nvidia-container-cli --debug、Docker/containerd 配置、容器内 /dev/nvidia*。
info 找不到设备驱动未加载、设备节点不存在、权限或内核模块问题。检查 nvidia-smi、lsmod | grep nvidia、ls -l /dev/nvidia*、dmesg。
info 报 driver/library mismatch宿主机 NVIDIA 内核模块与用户态库版本不一致。重启进入新驱动，或重新安装同版本驱动包。
info 权限失败当前用户无法访问设备或 cgroups 信息。用 root 复现，或检查 udev、容器 runtime 权限配置。
排障基线： 把 nvidia-smi 与 sudo nvidia-container-cli --load-kmods info 的输出一起保存，能快速区分“驱动层坏了”还是“容器注入层坏了”。

5. debug 日志：看到它真正做了什么

默认错误信息经常很短，debug 日志会显示 CLI 如何加载配置、解析环境变量、发现驱动库、处理 cgroups、选择设备、执行 mount 和生成 ld cache。遇到容器启动失败时，debug 日志通常比 Docker 的最终错误更接近根因。

# 直接输出到 stderr，适合临时排障
sudo nvidia-container-cli --debug=/dev/stderr --load-kmods info

# 写入文件，便于归档或附到工单
sudo rm -f /tmp/nvidia-container-cli.log
sudo nvidia-container-cli --debug=/tmp/nvidia-container-cli.log --load-kmods info
sed -n '1,160p' /tmp/nvidia-container-cli.log

# 查看是否出现库、设备、cgroup、约束相关错误
grep -Ei 'error|warn|failed|library|cgroup|device|require|cuda' /tmp/nvidia-container-cli.log
日志里重点找什么
配置文件路径、ldconfig 路径、driver capabilities、可见设备、库解析结果、mount 失败、cgroup 失败、CUDA requirement 失败。
日志怎么交给平台团队
同时提供宿主机驱动版本、toolkit 版本、容器运行命令、镜像 tag、debug 日志、容器 runtime 配置片段和是否启用 MIG。
隐私提醒： debug 日志可能包含路径、镜像名、环境变量和节点信息。外发前先脱敏集群名、用户路径、镜像仓库地址和业务参数。

6. list：查看将注入的库、设备和二进制

list 用来观察某组 driver capabilities 下，运行时会暴露哪些宿主机文件。不同版本的 libnvidia-container 支持的选项可能略有差异，所以脚本化前应以本机 nvidia-container-cli list --help 为准。

# 查看本机支持的 list 选项
nvidia-container-cli list --help

# 常见排障：列出 compute + utility 能力涉及的文件
sudo nvidia-container-cli --load-kmods --compute --utility list

# 如果本机版本支持细分输出，可分别检查库和设备
sudo nvidia-container-cli --load-kmods --compute --utility list --libraries
sudo nvidia-container-cli --load-kmods --compute --utility list --devices
sudo nvidia-container-cli --load-kmods --compute --utility list --binaries
输出类别典型内容为什么重要
设备节点/dev/nvidia0、/dev/nvidiactl、/dev/nvidia-uvmCUDA 进程需要访问 GPU、控制设备和 UVM；缺一个都可能失败。
驱动库libcuda.so、libnvidia-ml.so、NCCL 相关底层依赖容器应使用宿主机匹配的 NVIDIA driver libraries，而不是镜像里过期的拷贝。
二进制nvidia-smi、调试辅助工具utility capability 常用于在容器里运行 nvidia-smi。
配置/缓存ld cache、egl/vendor config 等决定动态链接器是否能找到被注入的库。
实用判断： 如果 list 能看到 libcuda.so 和 /dev/nvidia*，但容器内看不到，问题更可能在 Docker/containerd runtime 挂载、cgroup 或 rootless 配置。

configure 子命令的边界

configure 是运行时 hook 在容器启动路径里调用的低层动作，会面向某个 OCI rootfs 准备设备、mount 和库视图。它适合由 runtime 自动调用，不适合人工直接对生产容器 rootfs 试错。

# 只读查看本机版本支持的 configure 参数
nvidia-container-cli configure --help

# 生产排障优先使用 info/list/debug，而不是手工 configure
sudo nvidia-container-cli --debug=/tmp/nvc.log --load-kmods info
sudo nvidia-container-cli --load-kmods --compute --utility list
安全边界： 如果确实要实验 configure，只在临时 rootfs 或测试节点上做，并保存 debug 日志；不要把它当作修复 Docker/containerd 配置的替代品。

这张图也是排障顺序：先证实宿主机与 CLI 正常，再看 runtime 注入，最后看应用框架和 CUDA 兼容性。

8. GPU 可见性：NVIDIA_VISIBLE_DEVICES

NVIDIA_VISIBLE_DEVICES 决定容器启动时哪些 GPU 或 MIG 实例对容器可见。Docker 的 --gpus、Kubernetes device plugin、containerd runtime 最终都会映射到类似的可见设备选择。

值含义场景
all暴露所有可用 GPU。单租户节点、测试环境。
none不暴露 GPU 设备，但仍可注入 utility 能力下的部分驱动库。只需要查询驱动能力或构建镜像中的工具链。
void 或未设置按普通容器处理，不启用 NVIDIA 注入。排除 runtime 影响，或运行非 GPU 容器。
0,2按 GPU index 选择。人工测试方便，但 index 不是长期稳定标识。
GPU-...按 GPU UUID 选择。平台调度、资产绑定、长期脚本更推荐。
MIG-... 或 MIG-GPU-...按 MIG 实例标识选择，具体格式以 nvidia-smi -L 输出为准。A100/H100 等启用 MIG 的多租户环境。
# Docker 推荐入口：由 Docker 传递 GPU 请求
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 指定某张 GPU，注意 shell 引号
docker run --rm --gpus '"device=0"' nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 低层环境变量方式，适合理解机制或排障
docker run --rm --runtime=nvidia \
  -e NVIDIA_VISIBLE_DEVICES=GPU-aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee \
  -e NVIDIA_DRIVER_CAPABILITIES=compute,utility \
  nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
稳定性提醒： GPU index 会受可见设备过滤影响。在容器内看到的 GPU 0 不一定是宿主机的 GPU 0。平台层记录和调度应使用 UUID 或 MIG UUID。

9. driver capabilities：只注入需要的能力

NVIDIA_DRIVER_CAPABILITIES 控制注入哪些类型的驱动库和工具。AI 训练最常见是 compute,utility：前者提供 CUDA 计算所需库，后者让容器内能运行 nvidia-smi 和 NVML 相关工具。

能力用途AI Infra 建议
computeCUDA、OpenCL 等计算能力相关驱动库。训练/推理容器通常必须。
utilityNVML、nvidia-smi 等运维工具。生产排障强烈建议保留。
videoNVENC/NVDEC 视频编解码。视频推理、转码工作负载需要。
graphicsOpenGL/Vulkan/图形栈。普通训练不需要，图形/仿真/可视化需要。
display显示相关能力。服务器训练一般不需要。
all注入全部能力。排障可用，生产多租户应按最小能力暴露。
# 训练容器的常见最小能力
docker run --rm --gpus all \
  -e NVIDIA_DRIVER_CAPABILITIES=compute,utility \
  nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 视频推理额外需要 video
docker run --rm --gpus all \
  -e NVIDIA_DRIVER_CAPABILITIES=compute,utility,video \
  nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 排查 capabilities 影响：对比 list 输出
sudo nvidia-container-cli --load-kmods --compute --utility list
sudo nvidia-container-cli --load-kmods --compute --utility --video list
最小暴露原则： 多租户 GPU 平台不要默认给 all。训练作业一般从 compute,utility 开始，按业务需要逐项增加。

10. 设备节点与 cgroups

CUDA 容器能否真正访问 GPU，除了文件被挂载进去，还取决于 device cgroup 是否允许访问对应 major/minor 设备。rootless Docker、systemd cgroup v2、Kubernetes runtime class、LXC/Podman 等环境中，cgroup 和权限问题很常见。

# 宿主机设备节点
ls -l /dev/nvidia* 2>/dev/null

# 容器内检查设备节点是否存在
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 \
  sh -lc 'ls -l /dev/nvidia* && nvidia-smi'

# 查看 NVIDIA runtime 配置中的 cgroup 相关项
grep -nE 'no-cgroups|cgroup|ldconfig|debug' /etc/nvidia-container-runtime/config.toml 2>/dev/null || true
场景常见症状处理方向
rootful Docker设备存在但访问失败较少见。确认 runtime 注册、--gpus 请求和 toolkit 版本。
rootless Docker/Podmancgroup 或设备权限失败。按官方 rootless 指南配置，谨慎调整 no-cgroups；不要影响 rootful 节点。
containerd + KubernetesPod pending、容器创建失败或 device plugin 分配后不可用。检查 RuntimeClass、containerd handler、device plugin 日志、kubelet 日志。
cgroup v2老版本 toolkit 行为异常。升级 NVIDIA Container Toolkit，确认发行版和 container runtime 支持矩阵。
配置风险： no-cgroups = true 不是万能修复。它可能让 rootless 场景可用，也可能破坏 rootful/Kubernetes 的设备隔离语义。修改前备份配置并在单节点演练。

11. 驱动库注入与 ldconfig

NVIDIA 容器的关键设计是：容器镜像提供 CUDA runtime、cuDNN、训练框架等用户空间依赖，宿主机提供与内核驱动匹配的 NVIDIA driver libraries，例如 libcuda.so 和 libnvidia-ml.so。如果容器错误地加载了镜像里陈旧的 libcuda.so，就可能出现 NVML 初始化失败或 CUDA driver version 不足。

# 宿主机查看驱动和用户态库线索
nvidia-smi --query-gpu=driver_version,name --format=csv
ldconfig -p | grep -E 'libcuda.so|libnvidia-ml.so' || true
cat /proc/driver/nvidia/version 2>/dev/null || true

# 容器内查看动态链接解析
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 \
  sh -lc 'ldconfig -p | grep -E "libcuda.so|libnvidia-ml.so"; nvidia-smi'

# 用 nvidia-container-cli 看注入候选
sudo nvidia-container-cli --load-kmods --compute --utility list --libraries 2>/dev/null || \
sudo nvidia-container-cli --load-kmods --compute --utility list
正确方向
容器内 libcuda.so 应来自宿主机驱动注入路径；CUDA runtime 版本应被宿主机 driver 支持。
危险方向
在镜像里手工安装完整 NVIDIA driver，或把宿主机 /usr/lib 粗暴 bind mount 进容器，容易制造更隐蔽的不匹配。
兼容提醒： CUDA toolkit 版本不是驱动版本。nvidia-smi 显示的 CUDA Version 是该驱动最高支持的 CUDA driver API 能力，不代表容器镜像里安装的 toolkit 版本。

12. 对比图：nvidia-container-cli vs nvidia-ctk

平台工程里常见错误是用 nvidia-container-cli 手工“修配置”。更稳妥的方式是让 nvidia-ctk 管配置，把 CLI 用作证据收集。

13. Docker 集成与验证

Docker 场景的目标很简单：docker run --gpus all ... nvidia-smi 能成功。若失败，不要马上重装驱动，先分别验证宿主机、低层 CLI、Docker runtime 配置和容器内设备。

# 1. 宿主机基线
nvidia-smi
sudo nvidia-container-cli --load-kmods info

# 2. Docker GPU 最小验证
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 3. 指定 capability 复现
docker run --rm --gpus all \
  -e NVIDIA_DRIVER_CAPABILITIES=compute,utility \
  nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 4. 只读预览 Docker runtime 配置变更
sudo nvidia-ctk runtime configure --runtime=docker --dry-run

需要修改 Docker 配置时的安全流程

# 先备份，避免覆盖其他团队写入的 daemon.json
sudo test -f /etc/docker/daemon.json && \
  sudo cp /etc/docker/daemon.json /etc/docker/daemon.json.bak.$(date +%F-%H%M%S)

# 预览变更，确认不会删除已有 registry、log-driver、proxy 等配置
sudo nvidia-ctk runtime configure --runtime=docker --dry-run

# 确认维护窗口后再执行并重启 Docker
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

# 重启后验证
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
生产警告： 重启 Docker 会影响该节点上的容器。GPU 训练节点上必须先 drain/cordon 或确认没有业务容器，再执行 runtime 配置和服务重启。

14. containerd / nerdctl / Kubernetes 集成

containerd 场景比 Docker 多一层：CRI runtime handler、RuntimeClass、Kubernetes device plugin、CDI spec 都可能参与。nvidia-container-cli 能证明低层注入能力，但 Pod 能不能拿到 GPU 还取决于 kubelet 和 device plugin。

# 宿主机低层仍然先跑
sudo nvidia-container-cli --load-kmods info

# containerd 配置预览，先 dry-run
sudo nvidia-ctk runtime configure --runtime=containerd --dry-run

# 确认维护窗口后才配置并重启 containerd
sudo test -f /etc/containerd/config.toml && \
  sudo cp /etc/containerd/config.toml /etc/containerd/config.toml.bak.$(date +%F-%H%M%S)
sudo nvidia-ctk runtime configure --runtime=containerd
sudo systemctl restart containerd

# nerdctl 环境可用时做最小验证
nerdctl run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

Kubernetes 排障视角

# 看节点是否上报 GPU 资源
kubectl describe node <node> | grep -A5 -i 'nvidia.com/gpu'

# 看 device plugin 日志
kubectl -n kube-system logs -l name=nvidia-device-plugin-ds --tail=200

# 看 Pod 是否使用正确 RuntimeClass
kubectl get pod <pod> -o yaml | grep -E 'runtimeClassName|nvidia.com/gpu|NVIDIA_VISIBLE_DEVICES'

# Pod 内验证
kubectl exec -it <pod> -- nvidia-smi
层次证明命令失败时看哪里
宿主机驱动nvidia-smi驱动、内核、硬件、XID。
低层注入nvidia-container-cli info/listtoolkit、库、设备、cgroups。
containerdnerdctl --gpus all 或 CRI 测试 Podruntime handler、config.toml、CDI。
Kuberneteskubectl describe node/poddevice plugin、RuntimeClass、调度资源、Pod security。
边界提醒： nvidia-container-cli info 正常只能证明节点低层可用，不能证明 Kubernetes 已正确分配 GPU 给某个 Pod。

15. MIG：实例可见性与容器调度

MIG 把一张物理 GPU 切成多个 GPU Instance / Compute Instance。对容器运行时来说，关键是：可见设备不再只是物理 GPU UUID，还可能是 MIG 实例 UUID；调度层要保证 Pod 请求的资源类型和实例策略一致。

# 宿主机查看 MIG 状态和实例标识
nvidia-smi -L
nvidia-smi mig -lgi
nvidia-smi mig -lci

# nvidia-container-cli 基线诊断
sudo nvidia-container-cli --load-kmods info

# Docker 指定 MIG 设备时，以 nvidia-smi -L 输出的 MIG 标识为准
docker run --rm --runtime=nvidia \
  -e NVIDIA_VISIBLE_DEVICES=MIG-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx \
  -e NVIDIA_DRIVER_CAPABILITIES=compute,utility \
  nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi -L
MIG 问题典型症状排障方向
实例未创建宿主机 nvidia-smi -L 只显示整卡。确认 GPU 型号支持 MIG、驱动版本、MIG mode 和实例创建状态。
UUID 写错容器启动失败或容器内看不到设备。从 nvidia-smi -L 复制完整 MIG 标识，不要手写。
Kubernetes 资源策略不一致节点上报资源与 Pod request 不匹配。检查 device plugin MIG strategy、资源名和调度请求。
监控误判物理 GPU 与 MIG 实例指标混淆。监控标签中保留 GPU UUID、MIG UUID、GI/CI 信息。
操作警告： 启用/禁用 MIG、创建/销毁 MIG 实例会影响该 GPU 上已有作业。不要在有训练任务运行时直接执行 nvidia-smi -mig 或实例重配命令。

16. 驱动/库/CUDA 版本不匹配

AI Infra 中最常见的误判之一是“容器 CUDA 版本不对”。实际要区分三层：宿主机内核驱动、宿主机 NVIDIA driver libraries、容器镜像里的 CUDA runtime/toolkit。nvidia-container-cli 的价值在于帮你确认宿主机 driver libraries 是否能被正确注入。

错误信息更可能的含义处理方向
Failed to initialize NVML: Driver/library version mismatch宿主机 NVIDIA 内核模块和用户态库版本不一致，常见于驱动升级后未重启。确认 /proc/driver/nvidia/version、ldconfig、包版本；重启或统一驱动包。
CUDA driver version is insufficient for CUDA runtime version容器 CUDA runtime 需要的最低驱动版本高于宿主机驱动。升级宿主机驱动，或换更低 CUDA 版本的镜像。
unsatisfied condition: cuda>=...镜像或环境声明了 NVIDIA_REQUIRE_CUDA 约束，当前驱动不满足。升级驱动、换镜像，临时排障才考虑禁用 require。
libcuda.so.1: cannot open shared object filedriver library 没注入或动态链接路径不对。检查 capabilities、runtime 配置、ldconfig、容器内 ldconfig -p。
# 宿主机证据
nvidia-smi
cat /proc/driver/nvidia/version 2>/dev/null || true
ldconfig -p | grep -E 'libcuda.so|libnvidia-ml.so' || true

# 低层证据
sudo nvidia-container-cli --debug=/tmp/nvc.log --load-kmods info
grep -Ei 'nvrm|cuda|library|require|mismatch|failed' /tmp/nvc.log

# 容器证据
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 \
  sh -lc 'nvidia-smi; ldconfig -p | grep -E "libcuda.so|libnvidia-ml.so"'
不要这样修： 不要在运行中的 GPU 节点上混装多个来源的 NVIDIA driver 包，也不要把容器镜像里的 driver library 复制到宿主机。驱动层修复应走节点维护流程。

17. 常见错误与处理表

症状快速定位建议处理
docker: could not select device driver "" with capabilities: [[gpu]]Docker 不知道 NVIDIA runtime 或 toolkit 未配置。运行 nvidia-ctk runtime configure --runtime=docker --dry-run 预览，备份后配置并重启 Docker。
容器内没有 /dev/nvidia0未请求 GPU、runtime 未启用、可见设备为空。检查 --gpus、NVIDIA_VISIBLE_DEVICES、Docker/containerd runtime。
容器内有设备但 nvidia-smi 不存在utility capability 未注入，或镜像没有工具。设置 NVIDIA_DRIVER_CAPABILITIES=compute,utility，使用 CUDA base 镜像验证。

18. 排障流程图

排障不要跳层：宿主机驱动不通时不要看 Kubernetes；低层 CLI 不通时不要怪 PyTorch；容器内 nvidia-smi 正常后再看框架和通信库。

19. 安全操作清单与演练脚本

GPU 节点往往承载长时间训练任务。任何会重启 Docker/containerd、改 runtime 配置、切 MIG、升级驱动的操作，都应按维护流程执行。下面的命令以“先读、先备份、先 dry-run”为原则。

只读安全命令
nvidia-smi、nvidia-container-cli info、nvidia-container-cli list、docker run --rm --gpus all ... nvidia-smi。
需要维护窗口
重启 Docker/containerd、修改 daemon.json 或 config.toml、驱动升级、MIG 重配、节点重启。
# 一次标准只读巡检
set -eu
echo "== host =="
hostname
nvidia-smi
echo "== toolkit =="
nvidia-container-cli --version
sudo nvidia-container-cli --load-kmods info
echo "== list compute+utility =="
sudo nvidia-container-cli --load-kmods --compute --utility list | sed -n '1,80p'
echo "== docker smoke test =="
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 配置变更前的最低保护
sudo nvidia-ctk runtime configure --runtime=docker --dry-run
sudo nvidia-ctk runtime configure --runtime=containerd --dry-run
systemctl is-active docker containerd 2>/dev/null || true

变更前检查表

  • 确认节点已从调度中摘除，或确认没有业务容器和训练任务。
  • 保存 nvidia-smi、nvidia-container-cli info、runtime 配置文件和容器烟测输出。
  • 对 /etc/docker/daemon.json、/etc/containerd/config.toml、/etc/nvidia-container-runtime/config.toml 做带时间戳备份。
  • 优先运行 nvidia-ctk ... --dry-run，确认不会覆盖已有 registry、proxy、日志、镜像加速和 runtime handler 配置。
  • 变更后执行 Docker/containerd 烟测、Kubernetes Pod 烟测和一条最小 CUDA 程序。
收敛原则： 一次只改一个层次。先修宿主机，再修 toolkit，再修 Docker/containerd，再修 Kubernetes，最后修框架镜像。
