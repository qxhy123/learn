1. nvidia-debugdump 是什么

nvidia-debugdump 是 NVIDIA Linux 图形/数据中心驱动包里的调试工具，用于收集 GPU 内部状态。NVIDIA 官方说明中明确提到，它通常由 /usr/bin/nvidia-bug-report.sh 调用；少数情况下，在 NVIDIA 技术支持代表指示下，也可作为独立诊断程序运行。

它输出什么
通常是二进制 dump/blob，面向 NVIDIA 工程分析。平台团队一般不能直接解释其中寄存器、引擎或微控制器状态。
它解决什么
为 GPU hang、XID、驱动崩溃、疑似硬件异常、供应商升级提供“发生当时”的低层状态证据。
它不是什么
不是性能 profiler，不是健康检查，不是替代 DCGM 的自动化诊断，也不是能直接给出根因的命令。
# 查找命令是否随驱动安装
command -v nvidia-debugdump || echo "未找到 nvidia-debugdump"

# 查看帮助，不采集 dump，适合作为安全 dry-run
nvidia-debugdump --help

# 查看 NVIDIA 驱动与 GPU 基本状态
nvidia-smi
nvidia-smi -L
边界提醒： 如果你只是想确认 GPU 是否在线、温度是否异常、ECC 是否增加、作业是否占用显存，先用 nvidia-smi、DCGM 或调度系统；不要把 nvidia-debugdump 当成日常巡检命令。

信息图：nvidia-debugdump 在 AI Infra 故障证据链中的位置

AI 集群排障时，最有价值的是“同一时间线上的证据包”：XID、内核日志、驱动状态、作业信息、拓扑、健康检查和 debug dump。

2. 什么时候应该使用

使用 nvidia-debugdump 的判断标准不是“GPU 有点慢”，而是“需要保留足够低层的现场状态，供驱动/硬件支持团队分析”。常见触发条件如下。

场景是否适合原因优先动作
节点出现 XID 79、GPU fallen off bus、持续不可恢复适合可能涉及 PCIe、硬件、驱动或平台问题，需要完整证据记录 XID、BDF、GPU UUID，先跑 bug report，再按支持要求 dump
训练任务 OOM、吞吐下降但无 XID通常不适合更像容量、调度、框架或性能问题用 nvidia-smi、DCGM、profiling、作业日志
GPU hang、CUDA 调用卡死、驱动堆栈异常适合hang 现场可能很快丢失，低层状态有升级价值先保存进程、dmesg、nvidia-smi，再采集
多节点 NCCL 失败视情况多数是网络、拓扑、容器或配置；只有伴随 XID/驱动错误时才需要先查 NCCL 日志、拓扑、IB/RDMA、DCGM
NVIDIA/OEM/CSP 支持要求提供 debug dump适合这是最明确的使用理由严格按工单说明执行并保留校验和
AI Infra 经验： 真正能加速供应商响应的不是单个 dump 文件，而是“dump + bug report + XID 时间点 + 节点硬件身份 + 业务影响 + 复现步骤”。

3. 安装来源、版本与帮助

nvidia-debugdump 随 NVIDIA Linux 驱动安装。不同驱动版本的选项可能不同，所以教程不假设固定参数名；生产 runbook 应以目标节点上的 --help 输出为准。

# 定位二进制
command -v nvidia-debugdump
ls -l "$(command -v nvidia-debugdump)"

# 读取本机支持的参数
nvidia-debugdump --help

# 保存版本和环境，便于后续复盘
{
  date -Is
  uname -a
  nvidia-smi --query-gpu=index,uuid,pci.bus_id,name,driver_version --format=csv
  nvidia-debugdump --help
} > precheck-nvidia-debugdump.txt
版本提醒： 不要从另一台机器复制 nvidia-debugdump 到当前节点凑合运行。调试工具、内核模块、驱动版本应保持一致，否则采集结果和支持流程都可能失真。

4. 权限、影响面与采集窗口

GPU 低层状态采集通常需要访问 NVIDIA 设备文件、内核驱动接口和系统日志。实际权限取决于驱动、发行版和节点安全策略；生产环境一般由 root 或受控的值班账号执行。

权限
优先使用节点运维权限执行；避免把调试二进制暴露给普通租户。
窗口
尽量在故障刚发生、GPU 未 reset、节点未重启前采集。
影响
采集可能读取大量状态或短暂增加驱动压力；不要在健康节点上批量无差别运行。
隔离
多租户场景先冻结调度、标记节点不可调度，避免新作业覆盖现场。
# 采集前建议先从调度侧隔离节点，示例：Kubernetes
kubectl cordon NODE_NAME

# 记录当前作业和进程，避免后续无法关联
nvidia-smi pmon -c 1
nvidia-smi --query-compute-apps=gpu_uuid,pid,process_name,used_memory --format=csv
ps -eo pid,user,ppid,cmd --sort=pid | grep -E 'python|torchrun|deepspeed|ray|nvidia' || true
生产警告： 不要为了采集 dump 立即重启节点。重启会清掉大量现场证据；除非业务恢复优先级高于根因分析，或 runbook 明确要求先恢复。

5. 基础命令与安全 dry-run

由于 nvidia-debugdump 的参数随驱动版本可能变化，最安全的起点是先查看帮助并保存帮助文本。若帮助里显示需要指定输出文件或 GPU 选择参数，再按本机帮助执行。

# 安全 dry-run：只看帮助，不生成 dump
nvidia-debugdump --help

# 常见采集骨架：以本机 --help 为准替换参数
sudo nvidia-debugdump [本机帮助中显示的 GPU 选择参数] [本机帮助中显示的输出参数] ./nvdebugdump-GPU0.bin

# 如果没有把握，优先运行官方聚合脚本
sudo nvidia-bug-report.sh

# 记录产物元数据，不直接打开或尝试解析二进制 blob
ls -lh ./nvdebugdump-*.bin 2>/dev/null || true
shasum -a 256 ./nvdebugdump-*.bin 2>/dev/null || sha256sum ./nvdebugdump-*.bin
命令策略： 教程中的独立采集命令故意写成骨架形式，因为可靠做法是以目标驱动版本的 --help 为准；硬编码过期参数会比没有命令更危险。

6. 采集前上下文清单

单独的 dump 文件缺少上下文时，供应商通常很难判断影响范围和触发路径。下面这组命令用于构建同一时间点的最小证据包。

# 建议每次故障建一个目录，避免工件混杂
case_id="gpu-incident-$(hostname)-$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "$case_id"
cd "$case_id"

# 时间、内核、驱动、GPU 身份
date -u +%FT%TZ | tee time.txt
uname -a > uname.txt
nvidia-smi -q > nvidia-smi-q.txt
nvidia-smi -L > nvidia-smi-L.txt
nvidia-smi topo -m > nvidia-smi-topo.txt

# XID 和内核日志，按发行版选择可用命令
dmesg -T | grep -iE 'NVRM|Xid|nvidia|pcie|aer' > dmesg-gpu.txt || true
journalctl -k --since "-2 hours" | grep -iE 'NVRM|Xid|nvidia|pcie|aer' > journal-gpu.txt || true

# 作业和进程上下文
nvidia-smi pmon -c 1 > nvidia-smi-pmon.txt
ps -eo pid,user,ppid,stat,etime,cmd --sort=pid > ps.txt
字段为什么重要建议来源
GPU UUID / PCI BDF把 XID、进程、物理槽位、支持工单关联到同一张卡nvidia-smi -L、nvidia-smi --query-gpu
UTC 时间跨时区、跨系统日志对齐date -u、调度系统事件
驱动/内核/CUDA判断已知问题、兼容性和升级建议nvidia-smi、uname -a、镜像标签
作业 ID / 租户区分应用 bug、资源争用和节点硬件问题Slurm/K8s/Ray/内部调度系统

7. XID 与 crash triage

XID 是 NVIDIA 驱动写入内核日志的 GPU 错误报告。它可能指向用户程序错误、驱动问题、硬件问题、PCIe/NVLink 问题或“伴随其他错误出现的二次错误”。nvidia-debugdump 的价值在于补足 XID 之外的低层状态。

# 提取最近的 XID
dmesg -T | grep -i 'NVRM: Xid' | tail -50

# systemd 系统上按时间过滤
journalctl -k --since "2026-04-25 10:00:00" | grep -i 'Xid'

# 把 XID 和 GPU 身份放到同一个文件
{
  echo "## GPU inventory"
  nvidia-smi --query-gpu=index,uuid,pci.bus_id,name,serial --format=csv
  echo
  echo "## Recent XID"
  dmesg -T | grep -i 'NVRM: Xid' | tail -50
} > xid-summary.txt
应用侧优先
XID 13、31 等常见类型可能与非法内存访问、CUDA 程序错误有关，应结合 Compute Sanitizer、cuda-gdb 或框架日志。
硬件/链路优先
GPU fallen off bus、重复 ECC/PCIe/AER、同一槽位重复故障，更需要节点硬件、固件、线缆、主板和散热证据。
升级优先
同版本驱动多节点重复、升级后消失/出现、支持方要求复现包时，dump 与 bug report 的时序完整性最关键。
不要过度解读： XID 编号本身不是完整根因。NVIDIA 的 XID 文档给的是分类和建议动作，最终仍要结合具体 GPU、驱动版本、平台、负载和复现条件。

流程图：从告警到 nvidia-debugdump 的安全采集路径

关键决策点是“是否需要低层 dump”。多数性能、调度和应用问题不需要；严重 XID、hang、支持升级才进入 debugdump 路径。

8. 与 nvidia-bug-report.sh 的关系

nvidia-bug-report.sh 是更常用的聚合采集入口，会收集系统和 NVIDIA 驱动相关信息并生成压缩日志。NVIDIA 官方说明里，nvidia-debugdump 大多数情况下由它调用。因此实际 runbook 应优先把 bug report 作为基础证据。

工具定位输出适用方式
nvidia-bug-report.sh完整环境与驱动问题采集通常为 nvidia-bug-report.log.gz绝大多数 NVIDIA 工单的第一证据
nvidia-debugdumpGPU 内部状态 dump二进制 blob 或工具指定格式支持要求、严重现场、补充低层证据
nvidia-smi -q可读的 GPU 状态快照文本值班人员初筛、健康状态、ECC/时钟/温度
DCGM数据中心监控、健康、诊断指标、诊断结果、日志自动化巡检、节点验收、故障后诊断
# 推荐：先收集完整 bug report
sudo nvidia-bug-report.sh
ls -lh nvidia-bug-report.log.gz
shasum -a 256 nvidia-bug-report.log.gz || sha256sum nvidia-bug-report.log.gz

# 若 bug report 卡住，再查看脚本帮助或安全模式选项
nvidia-bug-report.sh --help 2>&1 | tee nvidia-bug-report-help.txt
优先级建议： 没有特殊指示时，提交 nvidia-bug-report.log.gz、XID 摘要、nvidia-smi -q、DCGM 结果和复现信息；只有支持方要求时再补独立 debug dump。

9. 与 DCGM / nvidia-smi 的关系

DCGM 和 nvidia-smi 更适合平台侧日常自动化；nvidia-debugdump 更像事故现场的低层取证。把三者分清楚，能避免在生产集群里做过度采集。

nvidia-smi
低成本、可读、随处可用。适合查看 GPU 是否在线、进程、显存、ECC、时钟、拓扑、持久化模式。
DCGM / dcgmi
面向数据中心的监控和诊断。适合节点准入、健康检查、压力诊断、故障后验证。
nvidia-debugdump
低层调试状态采集。适合工单升级和 NVIDIA 工程分析，不适合日常循环巡检。
# DCGM 诊断示例：先确认 dcgmi 可用和目标 GPU
dcgmi discovery -l

# 按 runbook 运行诊断级别，具体级别和时长需结合生产窗口
sudo dcgmi diag -r 1
sudo dcgmi diag -r 3 -p diagnostic.test_duration=300.0

# nvidia-smi 快照：适合在 debugdump 前后都保存
nvidia-smi --query-gpu=index,uuid,pci.bus_id,name,temperature.gpu,power.draw,ecc.errors.uncorrected.volatile.total --format=csv
运行顺序： 如果 GPU 正处于 hang 或刚出现 XID，先保存静态现场和 bug report；耗时或施压型 DCGM 诊断可能改变现场状态，应放在取证之后或在备用窗口执行。

对比图：四类 NVIDIA 诊断工具的使用边界

越靠近右下角，越不适合无条件自动化批量运行，越需要明确故障上下文和访问控制。

10. 容器与 Kubernetes 节点采集

在 Kubernetes、Slurm on Kubernetes、Ray 或容器化训练平台中，nvidia-debugdump 通常应在宿主机侧采集，而不是在普通业务容器里采集。原因是容器可能缺少完整设备节点、驱动工具、内核日志和主机硬件上下文。

# Kubernetes：先隔离节点，避免新 Pod 调度进来
kubectl cordon NODE_NAME

# 标记故障，便于平台和调度侧追踪
kubectl label node NODE_NAME gpu-incident=true --overwrite

# 找到该节点上的 GPU Pod
kubectl get pods -A -o wide --field-selector spec.nodeName=NODE_NAME

# 进入节点侧运维通道后采集，而不是在租户容器内直接采集
ssh NODE_NAME
sudo nvidia-bug-report.sh
sudo nvidia-debugdump --help
位置优点风险建议
宿主机日志和设备完整，便于关联 BDF、内核、驱动需要严格运维权限首选
特权 debug 容器可审计、可模板化容易权限过大，仍可能缺日志仅平台团队维护
普通训练容器接近应用缺权限、缺工具、跨租户风险不建议
多租户安全： 不要把 dump 工具和宿主机日志读取权限交给租户容器。debug dump、进程列表和 bug report 可能暴露其他租户的路径、用户名、命令行参数或拓扑信息。

11. 安全工件处理与隐私保护

debug dump 虽然不是普通文本，但仍应按敏感工件处理；它与 bug report、系统日志、进程列表一起打包时，往往包含主机名、用户名、路径、命令行参数、集群拓扑、驱动版本和潜在客户数据痕迹。

# 设置保守权限
umask 077
mkdir -p "$case_id"/private

# 生成清单和校验和
find "$case_id" -type f -maxdepth 2 -print0 | xargs -0 ls -lh > "$case_id"/MANIFEST.txt
find "$case_id" -type f -maxdepth 2 -print0 | xargs -0 shasum -a 256 > "$case_id"/SHA256SUMS.txt

# 打包前先查看文件列表，不要误打包大规模训练数据或密钥
tar -tzf "$case_id".tar.gz 2>/dev/null || true
find "$case_id" -type f -maxdepth 2 -print

# 加密传输示例：按公司密钥管理规范替换收件人
tar -czf "$case_id".tar.gz "$case_id"
gpg --encrypt --recipient infra-support@example.com "$case_id".tar.gz
保留
XID、时间线、驱动版本、GPU 身份、拓扑、dump、bug report、DCGM 结果。
审查
命令行参数、环境变量、路径、主机名、用户信息、内部 IP、作业配置。
避免
私钥、token、训练数据样本、模型权重、客户数据、无关日志全集。
脱敏原则： 不要修改二进制 dump 本体，否则可能破坏可分析性。需要脱敏时，通常对外围文本日志做最小替换，并在工单中说明替换规则。

安全图：debug dump 工件的保护边界

最安全的做法是：工件目录独立、权限收紧、生成校验和、受控传输、按工单生命周期清理。

12. 供应商升级包怎么组织

升级给 NVIDIA、服务器 OEM、云厂商或集群硬件团队时，按“可复现、可定位、可验证”的结构组织材料。不要只发一句“GPU 挂了”和一个 dump。

README 项示例
影响范围host123 GPU0，A100 80GB，训练作业 84721 失败，节点已 cordon
首次发生时间2026-04-25T02:15:30Z
错误摘要NVRM: Xid (PCI:0000:81:00): 79, GPU has fallen off the bus
复现条件同一模型启动 15-30 分钟后概率出现；其他节点未复现
已做动作已隔离节点，未重启，已采集 bug report 和 debugdump
希望支持方判断是否建议 RMA、驱动升级、BIOS/固件升级、槽位/主板排查
升级技巧： 如果多个节点出现同类 XID，分别保留每个节点的证据包，并额外提供聚合表：节点、GPU UUID、BDF、驱动版本、XID、时间、机型、槽位、作业类型。

13. 常见问题与排障矩阵

现象可能原因处理方式
nvidia-debugdump: command not found驱动包未安装完整、路径不在 PATH、容器内缺工具在宿主机检查驱动安装；用 command -v、包管理器或驱动安装目录定位
普通用户权限不足设备文件或驱动接口需要管理员权限使用受控 sudo/runbook，不要放宽设备文件给所有租户
采集卡住GPU/驱动已 hang、内核接口无响应、bug report 同步等待保留终端输出和时间；尝试官方脚本安全模式或支持方建议；不要反复施压
dump 文件很小或为空参数错误、目标 GPU 不存在、采集时状态已丢失核对 --help、GPU index/UUID/BDF、XID 时间，重新收集上下文
支持方说不能分析驱动版本不匹配、dump 损坏、缺少上下文、文件被改写提交校验和、bug report、原始文件、完整 README
节点恢复后无法复现一次性硬件/链路事件、现场已被重置保留证据，观察同卡/同槽位重复率，配置告警和后续 DCGM 验证
# 采集卡住时，另开窗口记录状态，不要先 kill
date -u +%FT%TZ
ps -ef | grep -E 'nvidia-debugdump|nvidia-bug-report' | grep -v grep
dmesg -T | tail -200

# 若必须终止，记录原因和时间
echo "terminated debug collection at $(date -u +%FT%TZ), reason: business recovery window" >> incident-notes.txt

14. 不要做什么

nvidia-debugdump 的风险主要来自误用：错误时间采集、错误对象采集、权限过度开放、工件泄漏，以及用它替代更合适的诊断工具。

不要批量扫全集群
这不是健康巡检。全量运行可能制造噪声、影响节点，并产生大量敏感工件。
不要在无上下文时单发 dump
没有 XID、时间、驱动、GPU 身份和作业背景，dump 很难被有效分析。
不要直接公开上传
不要把 bug report、dump、日志贴到公开 issue、论坛或未授权对象存储。
不要修改 dump 本体
二进制 blob 需要保持原样；需要脱敏时处理外围文本并说明。
恢复与取证冲突： 如果业务恢复必须优先，可以重启或摘除节点；但必须在事故记录里写清楚“未采集 dump 的原因”，避免后续复盘误判为证据缺失。

15. 团队 runbook 模板

下面模板适合放进值班手册。按本地驱动版本补齐 nvidia-debugdump --help 中的实际参数，并把工件传输目标替换成公司内部安全渠道。

#!/usr/bin/env bash
set -euo pipefail

node="$(hostname -s)"
case_id="gpu-incident-${node}-$(date -u +%Y%m%dT%H%M%SZ)"
umask 077
mkdir -p "$case_id"
cd "$case_id"

echo "case_id=$case_id" | tee README.md
date -u +%FT%TZ | tee time.txt
uname -a > uname.txt
nvidia-smi --query-gpu=index,uuid,pci.bus_id,name,driver_version --format=csv > gpu-inventory.csv
nvidia-smi -q > nvidia-smi-q.txt || true
nvidia-smi topo -m > nvidia-smi-topo.txt || true
dmesg -T | grep -iE 'NVRM|Xid|nvidia|pcie|aer' > dmesg-gpu.txt || true
journalctl -k --since "-2 hours" | grep -iE 'NVRM|Xid|nvidia|pcie|aer' > journal-gpu.txt || true
ps -eo pid,user,ppid,stat,etime,cmd --sort=pid > ps.txt

sudo nvidia-bug-report.sh || echo "nvidia-bug-report failed: $?" >> README.md
nvidia-debugdump --help > nvidia-debugdump-help.txt 2>&1 || true

# 如果支持方要求独立 dump，在这里按本机 help 增加明确参数：
# sudo nvidia-debugdump ... ./nvdebugdump-GPU0.bin

find . -type f -print0 | xargs -0 ls -lh > MANIFEST.txt
find . -type f -print0 | xargs -0 shasum -a 256 > SHA256SUMS.txt
cd ..
tar -czf "${case_id}.tar.gz" "$case_id"
shasum -a 256 "${case_id}.tar.gz"
模板策略： 默认只保存 nvidia-debugdump --help，不自动执行独立 dump；这样可以安全纳入通用 runbook。真正执行 dump 的参数应由支持工单或本机帮助确认。

16. 快速决策卡片

先看 XID
没有 XID 也可能有 GPU 问题，但 XID 是最重要的第一分类信号。先保存最近两小时内核日志。
先聚合再深入
nvidia-bug-report.sh 是默认入口，nvidia-debugdump 是支持要求下的深入补充。
先保现场再恢复
如果 SLA 允许，采集完关键证据再 reset/reboot；如果不允许，记录跳过原因。
按 GPU 身份组织
始终记录 GPU index、UUID、PCI BDF、序列号或资产号，避免 index 重排造成混淆。
按敏感工件处理
最小权限、校验和、加密传输、受控存储、到期删除。
不要代替诊断
性能慢、OOM、NCCL 配置错，通常先走 profiler、DCGM、网络和作业日志。
