1. nvme 是什么

nvme 通常指 nvme-cli 命令行工具。它通过 Linux NVMe 驱动向 NVMe 控制器发送管理命令，读取设备列表、控制器标识、命名空间标识、SMART/Health 信息、错误日志、固件日志和其他日志页。

它擅长什么
回答“这块盘是谁、能力是什么、健康如何、错误计数是否增长、固件是什么、命名空间怎么暴露”。
它不擅长什么
不能直接告诉你某个训练进程的实时吞吐，也不能替代 iostat、fio、文件系统日志或厂商诊断工具。
它的本质
设备控制面工具：比 lsblk 更懂 NVMe，比 iostat 更接近硬件内部日志。
# 列出 NVMe 控制器和命名空间
nvme list

# 查看控制器能力和序列号
sudo nvme id-ctrl /dev/nvme0

# 查看命名空间容量、格式、LBA 大小
sudo nvme id-ns /dev/nvme0n1

# 查看健康状态
sudo nvme smart-log /dev/nvme0
sudo nvme error-log /dev/nvme0
关键区别： /dev/nvme0 是控制器字符设备，/dev/nvme0n1 是命名空间块设备。很多查询两者都能工作，但诊断时要明确自己是在问控制器还是某个 namespace。

2. AI Infra 为什么关心 NVMe

AI 训练和推理经常把问题描述成 GPU 利用率低、dataloader 慢、checkpoint 卡顿、节点偶发掉盘。NVMe 是本地数据集缓存、模型权重、容器镜像层、临时特征缓存、spill 文件和 checkpoint 的关键路径。nvme 能把“存储好像有问题”转化成设备级证据。

AI 场景nvme 关注点典型解释
dataloader 读慢smart-log 温度、介质错误、可用备用空间、读错误计数；id-ns 容量和 LBA 格式可能是盘健康退化、热降频、命名空间配置不符合预期，或只是上层小文件随机读导致。
checkpoint 写入突然变慢温度、控制器忙时、错误日志、PCIe 链路宽度/速率盘可能热保护、链路降速、后端固件错误，或被其他任务写满队列。
节点偶发 I/O errorerror-log、内核 dmesg、AER/PCIe 错误、控制器 reset要区分介质错误、链路问题、驱动 reset、掉电保护事件和文件系统损坏。
批量节点验收序列号、型号、固件版本、容量、温度、SMART 阈值同一训练池中混入不同盘型或不同固件，会导致性能分布长尾。
AI Infra 心法： nvme 看健康和身份，iostat 看实时负载，fio 做受控压测，三者合起来才接近完整答案。

3. 整体心智模型

信息图：从 AI 任务到 NVMe 控制器

NVMe 排障的核心不是背字段，而是把业务路径、块设备、控制器、PCIe 和日志页对齐到同一个时间线。

4. 安装、权限与设备命名

nvme-cli 通常需要 root 权限读取部分控制器信息或日志页。普通用户可能能运行 nvme list，但生产诊断建议明确使用 sudo 并记录命令输出。

系统安装命令说明
Ubuntu / Debiansudo apt-get update && sudo apt-get install -y nvme-cli云镜像和容器镜像不一定默认安装。
RHEL / Rocky / Almasudo dnf install -y nvme-cli旧系统可能使用 yum install nvme-cli。
SUSEsudo zypper install nvme-cli企业环境要确认发行版支持的 nvme-cli 版本。
# 查看工具版本
nvme version

# 常见设备名
ls -l /dev/nvme*

# 控制器与命名空间映射
lsblk -o NAME,KNAME,TYPE,SIZE,MODEL,SERIAL,MOUNTPOINT,FSTYPE
readlink -f /sys/block/nvme0n1/device

# NVMe 控制器在 sysfs 中的 PCI 地址线索
basename "$(readlink -f /sys/class/nvme/nvme0/device)"
/dev/nvme0
控制器设备。常用于 id-ctrl、smart-log、fw-log、error-log。
/dev/nvme0n1
第 0 个控制器暴露的第 1 个命名空间。常用于挂载、文件系统和 iostat。
/dev/nvme0n1p1
namespace 上的分区。业务目录通常挂在这里或其上层 LVM/dm 设备。
权限提醒： 不要为了方便给容器长期挂载整个 /dev 和高权限。采集节点硬件证据时，优先用临时 debug 容器或宿主机运维通道。

5. 快速上手：nvme list

nvme list 是最安全、最高频的入口。它列出 NVMe 设备、序列号、型号、命名空间、容量、格式和固件版本。批量验收、故障节点比对和资产盘点都从这里开始。

# 人类可读列表
sudo nvme list

# JSON 输出更适合脚本和证据归档
sudo nvme list -o json

# 和挂载点对应起来
lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,MOUNTPOINT,FSTYPE
findmnt -no SOURCE,TARGET,FSTYPE,OPTIONS /data
字段含义排障价值
Node设备路径，例如 /dev/nvme0n1后续 iostat、fio、文件系统命令的锚点。
SN序列号资产追踪、RMA、同型号批次问题定位。
Model设备型号识别混盘、消费级盘误用、不同性能等级混入训练池。
Namespace命名空间 ID确认单控制器多 namespace 或 NVMe-oF 暴露关系。
FormatLBA 大小和元数据格式确认 512B/4K 扇区、格式化参数是否符合平台规范。
FW Rev固件版本批量节点一致性、已知固件缺陷排查。
验收建议： 新节点入池前保存 nvme list -o json、id-ctrl、id-ns、smart-log 的基线。后续性能或可靠性问题可以和基线做 diff。

6. 控制器与命名空间：identify

identify 类命令读取 NVMe Identify 数据结构。控制器回答“我是什么硬件、支持什么能力”，命名空间回答“这个块设备有多大、用什么 LBA 格式、属于哪个 namespace”。

# 控制器身份和能力
sudo nvme id-ctrl /dev/nvme0

# 命名空间身份、容量、LBA 格式
sudo nvme id-ns /dev/nvme0n1

# JSON 便于留档和 diff
sudo nvme id-ctrl /dev/nvme0 -o json > nvme0.id-ctrl.json
sudo nvme id-ns /dev/nvme0n1 -o json > nvme0n1.id-ns.json
观察点在哪看为什么重要
型号、序列号、固件id-ctrl确认资产、批次和固件一致性。
支持的日志和能力id-ctrl不同设备支持的 telemetry、sanitize、namespace 管理能力不同。
容量与使用容量id-ns确认 namespace 是否被切分、是否符合平台容量规划。
LBA 格式id-ns4K LBA、元数据和保护信息会影响兼容性与性能。
读字段方式： 不要只看单个字段名。不同 nvme-cli 版本的展示细节会变化，但 JSON 输出通常更稳定，适合平台自动采集。

7. SMART 健康：smart-log

smart-log 是生产中最常用的只读健康命令。它提供温度、可用备用空间、寿命消耗、数据读写量、控制器忙时、断电次数、介质错误和错误日志项数量等信号。

# 控制器级 SMART / Health 信息
sudo nvme smart-log /dev/nvme0

# 某些环境也可对 namespace 调用
sudo nvme smart-log /dev/nvme0n1

# JSON 输出用于监控采集
sudo nvme smart-log /dev/nvme0 -o json
字段正常读法AI Infra 风险信号
critical_warning位图告警，0 通常表示没有控制器声明的严重告警非 0 必须升级处理，尤其是备用空间、温度、可靠性、只读模式告警。
temperature当前温度高温可能触发热降频，表现为 checkpoint 或 dataloader 吞吐周期性下降。
available_spare可用备用空间百分比低于阈值说明介质可靠性风险上升，应结合厂商策略换盘。
percentage_used厂商估算寿命消耗大规模训练缓存盘写放大明显时，该值可用于寿命容量规划。
media_errors介质和数据完整性错误持续增长是强烈风险信号，必须结合 dmesg、文件系统日志和备份状态处理。
num_err_log_entries错误日志项数量增长不一定等于当前故障，但需要和 error-log 时间线对应。
不要误判： percentage_used 大于 100 不一定表示立刻坏盘，它是厂商寿命估算；但在生产池中应视为容量规划和更换策略信号，而不是忽略。

8. 错误证据：error-log

error-log 展示控制器记录的 NVMe 错误日志项，包括命令 ID、状态字段、参数错误位置、LBA、namespace 和 vendor 信息。它适合和内核日志中的 I/O error、reset、timeout 对齐。

# 查看最近错误日志，默认条目数由工具/设备决定
sudo nvme error-log /dev/nvme0

# 指定条目数，避免输出过少
sudo nvme error-log /dev/nvme0 --log-entries=64

# 保存 JSON 证据
sudo nvme error-log /dev/nvme0 --log-entries=64 -o json > nvme0.error-log.json

# 同时抓内核日志中的 NVMe/PCIe 线索
dmesg -T | egrep -i 'nvme|pcie|aer|i/o error|timeout|reset' | tail -200
看到什么可能含义下一步
错误项数量稳定，不再增长历史错误或一次性事件和事故时间对齐；继续观察 smart-log 与 dmesg。
错误项持续增长介质、固件、链路或上层命令持续失败下线节点、保留证据、检查备份，联系硬件/云厂商。
LBA 相关错误可能涉及特定区域读写失败避免继续压测破坏证据；检查文件系统和数据完整性。
timeout/reset 同时出现控制器无响应、链路抖动或电源/散热问题查 PCIe AER、温度、固件版本、主板槽位和供电。
证据保全： 错误发生后不要立刻重启或格式化。先抓 smart-log、error-log、dmesg、lsblk、lspci -vv 和业务时间线。

9. 日志页与 JSON 输出

NVMe 设备提供多类日志页。常用命令已经封装了部分日志，如 SMART、错误、固件。更高级的 telemetry、persistent event log、vendor log 取决于设备和 nvme-cli 版本，不应在不了解厂商语义时盲目解读。

# 固件槽位与当前激活固件
sudo nvme fw-log /dev/nvme0

# 支持时获取 telemetry 日志，输出为二进制文件，给厂商或内部工具分析
sudo nvme telemetry-log /dev/nvme0 --output-file=nvme0.telemetry.bin

# 以 JSON 留档，便于脚本解析和对比
sudo nvme smart-log /dev/nvme0 -o json | jq .
sudo nvme fw-log /dev/nvme0 -o json | jq .
标准日志
smart-log、error-log、fw-log 是日常排障首选，语义相对稳定。
Telemetry
更适合厂商支持或深度硬件分析。文件可能较大，采集时记录时间和设备序列号。
JSON
面向平台自动化。避免从人类文本里 grep 字段名导致版本兼容问题。
无 jq 也能用： 本教程页面不依赖外部库；命令示例中的 jq 只是现场可选的 JSON 查看工具，不是 nvme 的运行要求。

10. PCIe 拓扑与带宽线索

信息图：从 namespace 追到 PCIe 链路

NVMe 性能异常不一定是盘坏。链路降速、插槽共享、PCIe AER、NUMA 远端访问和散热都会影响 AI 数据路径。

PCIe 追踪命令

# 从挂载点找到源设备
findmnt -no SOURCE,TARGET,FSTYPE,OPTIONS /data
lsblk -o NAME,KNAME,TYPE,SIZE,MODEL,SERIAL,MOUNTPOINT

# 从 namespace 追到控制器和 PCI BDF
readlink -f /sys/block/nvme0n1/device
basename "$(readlink -f /sys/block/nvme0n1/device)"

# 查看链路能力和当前链路状态
sudo lspci -vv -s 0000:65:00.0 | egrep -i 'LnkCap|LnkSta|NUMA|AER|UESta|CESta'

# 查看 NUMA 归属，GPU/NVMe 跨 NUMA 可能拖慢数据路径
cat /sys/class/nvme/nvme0/device/numa_node
nvidia-smi topo -m
线索读法处理方向
LnkCap 高、LnkSta 低硬件支持更高速度/宽度，但当前协商较低检查插槽、转接卡、BIOS、线缆、主板限制和重插。
AER 错误增长PCIe 可纠正或不可纠正错误保留 dmesg 和 lspci 证据，排查链路质量和固件。
NUMA 远端GPU 和 NVMe 不在同一 NUMA 侧调整数据缓存位置、进程绑核、GPU 分配或节点硬件拓扑策略。
多块盘共享上游同一 PCIe switch/root port 下争用吞吐压测要按拓扑解释，避免把上游瓶颈误判为单盘问题。

11. Namespace 与多路径

NVMe namespace 是控制器暴露给系统的逻辑块设备。大多数本地 SSD 只有一个 namespace，但企业盘、NVMe-oF、云平台或特殊分区策略可能有多个 namespace 或多路径关系。

# 查看控制器下的 namespace
sudo nvme list-ns /dev/nvme0

# 查看某个 namespace 的详细信息
sudo nvme id-ns /dev/nvme0n1

# 查看 subsystem 和路径信息
sudo nvme list-subsys

# Linux 多路径设备关系
lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,WWN,MOUNTPOINT
multipath -ll 2>/dev/null || true
本地单盘
常见形态是 /dev/nvme0 + /dev/nvme0n1，排障相对直接。
多 namespace
同一个控制器暴露多个逻辑块设备，容量、格式和隔离策略要分别确认。
NVMe-oF/多路径
命名空间可能经网络或多路径暴露。nvme 能看到 subsystem，但性能还受网络和 target 影响。
危险边界： namespace 管理命令可能创建、删除或重格式化块设备。除非你正在执行明确的存储变更，否则不要运行 create-ns、delete-ns、attach-ns、detach-ns。

12. 固件、格式化和危险操作安全

流程图：危险操作的生产闸门

nvme-cli 里既有安全查询，也有会清盘或改变固件状态的命令。生产事故往往来自把两者当成同一风险级别。

危险命令清单与安全写法

命令族风险安全策略
nvme format可能清除数据、改变 LBA 格式或保护信息必须离线、备份、确认序列号；先只运行 id-ns 和 list 验证目标。
fw-download / fw-activate固件升级失败可能导致设备不可用，激活可能需要 reset/reboot使用厂商固件包和流程，确认兼容矩阵，不在业务高峰执行。
delete-ns / detach-ns删除或解绑 namespace，导致块设备消失仅在明确的存储重配置窗口执行。
sanitize介质擦除，通常不可恢复只在退役、RMA 或合规销毁流程中执行。
reset短时中断 I/O，可能触发文件系统错误只在下线节点或厂商指导下执行。
# 安全：先确认目标身份，不修改任何状态
sudo nvme list
sudo nvme id-ctrl /dev/nvme0 | egrep 'sn|mn|fr'
sudo nvme smart-log /dev/nvme0

# 危险：以下命令仅作为识别示例，不要在生产节点直接复制执行
# sudo nvme format /dev/nvme0n1
# sudo nvme fw-download /dev/nvme0 --fw=vendor-fw.bin
# sudo nvme fw-activate /dev/nvme0 --slot=1 --action=1
# sudo nvme sanitize /dev/nvme0 --sanact=1
复制保护： 本教程对危险命令全部注释展示。执行前必须把注释去掉，这本身就是一次人为确认，但它不能替代变更审批和备份验证。

13. AI dataloader 存储健康排查

当训练吞吐下降时，nvme 的角色是确认“本地 NVMe 是否健康、是否降速、是否报错”。它不直接测吞吐；吞吐用 iostat 和 fio 看，进程责任用 pidstat、iotop 或应用日志看。

# 1. 找到数据目录对应设备
findmnt -no SOURCE,TARGET,FSTYPE,OPTIONS /data
lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,MOUNTPOINT

# 2. 实时看设备是否饱和
iostat -xz 1 60

# 3. 看 NVMe 健康和错误
sudo nvme smart-log /dev/nvme0
sudo nvme error-log /dev/nvme0 --log-entries=64

# 4. 查内核是否有 reset、timeout、AER、I/O error
dmesg -T | egrep -i 'nvme|pcie|aer|i/o error|timeout|reset' | tail -200
症状组合更可能的问题下一步
iostat await 高，smart-log 正常上层访问模式、队列争用、文件系统或缓存问题看 dataloader worker、文件大小分布、页缓存命中、并发和预取。
温度高且吞吐周期性下降热降频或机箱风道问题采集温度时间线，检查风扇、散热片、盘位和相邻 GPU 热源。
media_errors 或错误日志增长设备可靠性风险停止写入、迁移数据、下线节点、按硬件流程处理。
PCIe 链路低于预期链路降速、插槽/转接卡限制查 lspci -vv、重插、换槽、BIOS 设置和主板规格。
排障闭环： 只有当 nvme 健康正常、dmesg 无硬件错误、PCIe 链路正常时，才更有把握把注意力转向数据格式、文件系统、并发或应用层 dataloader 设计。

14. nvme vs smartctl/lsblk/iostat

对比图：四类工具各看一层

工具边界清楚，排障才不会绕圈。nvme 是设备内部事实，不是运行时吞吐仪表盘。

工具对照表

工具最佳问题典型命令局限
nvmeNVMe 设备身份、健康、日志、固件、namespacenvme list、nvme smart-log、nvme error-log不直接给进程责任，不等于性能压测。
smartctl跨 SATA/SAS/NVMe 的统一 SMART 采集smartctl -a /dev/nvme0NVMe 专有能力不如 nvme-cli 直接。
lsblk块设备层级、分区、挂载点、文件系统lsblk -o NAME,TYPE,SIZE,MODEL,MOUNTPOINT看不到控制器内部健康细节。
iostat实时 IOPS、吞吐、延迟、队列和忙碌度iostat -xz 1设备级统计，不说明哪个进程或文件导致。
fio受控读写压测和基线fio --name=read --rw=read ...写测试可能破坏数据；生产必须使用安全文件路径和只读策略。

16. 采集脚本与证据包

事故现场最怕信息丢失。下面脚本只做只读采集，适合在下线前或复现窗口内保存 NVMe 证据。它不会修改设备状态。

#!/usr/bin/env bash
set -euo pipefail

out="${1:-/tmp/nvme-evidence.$(date +%Y%m%d-%H%M%S)}"
mkdir -p "$out"

uname -a > "$out/uname.txt"
date -Is > "$out/collected_at.txt"

nvme list > "$out/nvme-list.txt" 2>&1 || true
nvme list -o json > "$out/nvme-list.json" 2>&1 || true
lsblk -o NAME,KNAME,TYPE,SIZE,MODEL,SERIAL,WWN,MOUNTPOINT,FSTYPE > "$out/lsblk.txt" 2>&1 || true

for ctrl in /dev/nvme[0-9]*; do
  [ -e "$ctrl" ] || continue
  case "$ctrl" in
    *n*) continue ;;
  esac
  base="$(basename "$ctrl")"
  nvme id-ctrl "$ctrl" -o json > "$out/$base.id-ctrl.json" 2>&1 || true
  nvme smart-log "$ctrl" -o json > "$out/$base.smart-log.json" 2>&1 || true
  nvme error-log "$ctrl" --log-entries=64 -o json > "$out/$base.error-log.json" 2>&1 || true
  nvme fw-log "$ctrl" -o json > "$out/$base.fw-log.json" 2>&1 || true
done

for ns in /dev/nvme*n*; do
  [ -e "$ns" ] || continue
  base="$(basename "$ns")"
  nvme id-ns "$ns" -o json > "$out/$base.id-ns.json" 2>&1 || true
done

dmesg -T | egrep -i 'nvme|pcie|aer|i/o error|timeout|reset' > "$out/dmesg-nvme.txt" 2>&1 || true
echo "saved to $out"
证据包内容： 至少包含时间、内核版本、设备列表、序列号、固件、SMART、错误日志、挂载关系和 dmesg。若涉及性能，还应追加 iostat -xz 1 60 和业务日志时间戳。

17. 容器、云盘与虚拟化边界

在容器、云主机和虚拟化环境里，nvme 看到的未必是物理本地 SSD。很多云盘以 NVMe 设备名暴露，但后端是网络块存储；一些容器只看到宿主机映射出的块设备或根本没有权限访问控制器日志。

环境常见现象解读方式
云盘以 NVMe 暴露/dev/nvme1n1 不是本地盘，而是 EBS/云块存储同时查云厂商卷 ID、限流指标、burst credit、IOPS/吞吐规格。
Kubernetes 容器容器内没有 /dev/nvme0 或权限不足用节点级 debug 工具采集；不要给业务 Pod 长期开高权限。
虚拟机看到虚拟 NVMe 控制器SMART/错误日志可能被 hypervisor 抽象，硬件结论要回到宿主机或云平台。
NVMe-oF设备名像 NVMe，但路径经过 RDMA/TCP还要查网络、target、multipath、队列深度和远端存储日志。
# 云环境常见：把块设备映射到云盘 ID，需要用厂商工具或 metadata
nvme list
lsblk -o NAME,SERIAL,MODEL,SIZE,MOUNTPOINT

# NVMe subsystem 信息
sudo nvme list-subsys

# 容器内先判断是否真的有权限
test -e /dev/nvme0 && sudo nvme smart-log /dev/nvme0 || echo "no controller access"
云上原则： 设备名叫 NVMe 不等于本地 SSD。AI 训练池排障要把节点内证据和云监控/存储服务指标合并看。

18. 参考资料与练习

练习任务

  1. 在一台测试节点上运行 nvme list、id-ctrl、id-ns、smart-log，把设备型号、序列号、固件、namespace 容量和温度整理成表格。
  2. 用 findmnt 和 lsblk 找到 /data 对应的块设备，再用 readlink -f /sys/block/.../device 找到 PCI BDF。
  3. 同时采集 iostat -xz 1 30 和 nvme smart-log，解释“实时负载”和“设备健康”分别来自哪一层证据。
  4. 阅读一份厂商固件升级说明，列出升级前必须确认的备份、业务下线、兼容版本和回滚条件。
