I
Chapter One · 序章

为何需要异步

在咖啡店里，一个店员可以同时招呼五位顾客 —— 但 CPU 一次只能做一件事。如果两者都正确，那么"并发"究竟意味着什么？

想象一家咖啡店只有一位店员。顾客 A 点了一杯需要研磨豆子、煮水、冲泡的手冲咖啡。如果店员是一个 同步 的程序，他会站在咖啡机前盯着水沸腾，然后盯着滴滤完成，整整三分钟，期间排队的顾客 B、C、D 只能干等。咖啡店在三分钟内只服务了一位客户。

但真实世界的店员显然不会这么做。他启动咖啡机后，会立刻转身招呼下一位顾客；当第二杯也开始萃取时，他可能去补充牛奶；只有当某一台机器"叮"一声，他才回头处理。这就是 异步：用一个工作者，通过让出"等待时间"，把多份工作交错完成。

asyncio 是 Python 内置的异步并发库。它解决的不是 CPU 密集问题（那需要多进程），而是 I/O 密集 问题 —— 网络请求、磁盘读写、数据库查询，这些任务里 CPU 大部分时间都在"等待"。asyncio 的本质，就是把这些等待的间隙重新填满。

三种并发模型，三种代价

在我们深入 asyncio 之前，需要先把它在并发版图上的位置说清楚。Python 提供三种主要的并发手段，每一种都有截然不同的适用场景：

模型调度者适合代价
多进程
multiprocessing		 操作系统 CPU 密集（图像处理、数值计算） 进程切换重，内存独立，IPC 复杂
多线程
threading		 操作系统 I/O 密集，遗留 API 集成 受 GIL 限制，竞态条件难调试
异步
asyncio		 程序自己（事件循环） 大量 I/O、高并发连接、网络服务 "病毒式"传染，需全栈异步生态

线程让操作系统替你切换；asyncio 让你自己决定何时切换。前者公平但昂贵，后者高效但需要写得对。

asyncio 的最大优势在于：单线程内可以维持 数万个并发"任务"，每个任务的内存开销只有几 KB，而一个操作系统线程通常需要 MB 级栈空间。这就是为什么现代高并发服务器（FastAPI、aiohttp、Starlette）几乎清一色基于 asyncio。

Chapter Two · 核心概念

协程、事件循环、任务

三个名词，三种身份。理解了它们的区别，asyncio 就只剩下机械的 API 了。

asyncio 的整个世界由四种基本对象构成：协程（Coroutine）、事件循环（Event Loop）、任务（Task） 和 未来对象（Future）。它们之间的关系常常被初学者混淆，所以我们先用一张图把整体格局画出来。

协程 ≠ 协程函数

这是初学者最常踩的概念坑。async def f(): 定义的是一个 协程函数（coroutine function）。调用它，f()，并不会执行函数体，而是返回一个 协程对象（coroutine object）。这个对象就像一份未拆封的菜谱 —— 它需要被"播放"才有效果。

import asyncio

async def greet():
    print("hello")
    await asyncio.sleep(1)
    print("world")

# 1) 调用协程函数，得到的是协程对象 —— 没有任何输出
coro = greet()
print(type(coro))   # <class 'coroutine'>

# 2) 必须交给事件循环驱动
asyncio.run(coro)        # hello → (1秒后) → world
⚠ Common Pitfall 如果你忘记 await 或 asyncio.run()，Python 会发出 RuntimeWarning: coroutine was never awaited。这是 asyncio 最常见的告警。

协程的生命周期

每个协程对象都是一台微型状态机。它从"待启动"开始，被事件循环驱动后进入"运行中"，在 await 处让出控制权变为"挂起"，等待对应的 I/O 或定时器就绪后被"唤醒"，最后到达 return 进入"完成"状态。如果途中抛出未捕获的异常，则进入"出错"状态。

事件循环 — 唯一的真神

事件循环是 asyncio 的发动机。它做的事极其简单 —— 一遍又一遍地：

  1. 检查"就绪队列"中是否有任务可以立即运行；
  2. 取出一个任务，让它运行到下一个 await 或结束；
  3. 如果任务挂起了，记录它在等什么（定时器、文件描述符、Future）；
  4. 询问操作系统："有什么 I/O 完成了吗？"（通过 epoll / kqueue / IOCP）；
  5. 把就绪的回调放回就绪队列；
  6. 循环。

整个过程是 单线程 的。这意味着在任意时刻，你写的 Python 代码里只有一行正在执行 —— 不存在线程级别的竞态。这极大简化了代码，但也带来了著名的代价：任何阻塞调用都会冻住整个程序。

⚠ 致命陷阱 在协程里使用 time.sleep(5) 会让事件循环停摆 5 秒，所有其他任务都被冻结。必须用 await asyncio.sleep(5)。同理：requests.get() 会阻塞，应该用 aiohttp。

任务 — 协程的"在跑"形态

协程本身只是一份配方，要让它真正在事件循环里"跑起来"，需要把它包装成 Task。包装方式有三种：

# 方式 1：asyncio.run() — 顶层入口，自动创建并管理事件循环
asyncio.run(main())

# 方式 2：asyncio.create_task() — 在协程内部派生新任务
async def main():
    task = asyncio.create_task(work())   # 立刻开始调度
    result = await task                  # 等待完成

# 方式 3：asyncio.gather() — 一次启动多个并等待
results = await asyncio.gather(work1(), work2(), work3())

"协程"和"任务"的差别看似微妙却至关重要：把协程对象传给 await，它从此刻开始顺序执行；把它包装为 task 后，它立刻开始调度，可以与当前协程并发。

Chapter Three · 语法

async / await 的语法解剖

两个关键字撑起整个生态。它们看似简单，但每一个的语义都需要精确把握。

Python 在 3.5 引入了原生的 async/await 关键字，让异步代码读起来几乎和同步代码一样自然。但"看起来一样"恰恰是最危险的：你需要清楚每一个 await 背后发生了什么。

async 的三种形态

async 关键字可以出现在三处，分别定义三种不同的可等待结构：

# 1. 协程函数（最常见）
async def fetch(url):
    return await http_get(url)

# 2. 异步生成器（async iterator）
async def stream_lines(url):
    async with session.get(url) as resp:
        async for chunk in resp.content:
            yield chunk

# 3. 异步上下文管理器（通过 __aenter__ / __aexit__）
class DBConnection:
    async def __aenter__(self):
        self.conn = await connect()
        return self.conn
    async def __aexit__(self, *exc):
        await self.conn.close()

await 究竟在等什么？

await <expr> 要求 <expr> 是一个 awaitable 对象。Python 中只有三种东西是 awaitable：

类型来源典型例子
Coroutineasync def 函数被调用await fetch(url)
Taskasyncio.create_task()await task
Future底层 I/O 桥接、loop.run_in_executor()await future

对一个普通函数返回的值（比如 1 + 1 或 "hello"）使用 await，会立刻报 TypeError: object int can't be used in 'await' expression。

下面这张时序图，展示 await asyncio.sleep(1) 这一行代码背后，在协程、事件循环、定时器调度器三方之间发生的完整通信。这是理解 asyncio 的关键时刻 —— 一旦掌握了这张图，你就掌握了所有 await 的本质。

同步 vs 异步：同一段逻辑的两种写法

把上面的概念落到代码上。下面是从一个 URL 列表抓取数据的同步与异步对照实现：

同步版本

import requests
import time

def fetch(url):
    r = requests.get(url)
    return r.text

def main():
    urls = ["https://a.com",
            "https://b.com",
            "https://c.com"]
    start = time.time()
    results = [fetch(u) for u in urls]
    print(f"耗时 {time.time()-start:.2f}s")
    return results

main()  # ≈ 3 × 单次请求时长

异步版本

import aiohttp
import asyncio
import time

async def fetch(session, url):
    async with session.get(url) as r:
        return await r.text()

async def main():
    urls = ["https://a.com",
            "https://b.com",
            "https://c.com"]
    start = time.time()
    async with aiohttp.ClientSession() as s:
        results = await asyncio.gather(
            *(fetch(s, u) for u in urls))
    print(f"耗时 {time.time()-start:.2f}s")
    return results

asyncio.run(main())  # ≈ 最慢的那个请求时长

注意三个变化：(1) 函数前加 async；(2) I/O 调用前加 await；(3) 用 asyncio.gather 把多个协程并发起来。底层从 requests 换成 aiohttp —— 这就是 asyncio "病毒式传染"的体现：你的整个 I/O 栈都需要异步原生支持。

Chapter Four · 引擎

事件循环 — 一台永不停息的机器

如果你能理解事件循环的一次"心跳"，你就理解了 asyncio 的全部底层。

很多教程把事件循环比作"魔法盒子"，这种描述对于深入使用 asyncio 是不够的。事实上，事件循环的实现非常机械 —— 它就是一个 while 循环，每一轮称为一次 tick。下面这张流程图，逐步展开了 CPython 内置的 BaseEventLoop._run_once() 在每个 tick 里实际做的事情。

从代码看事件循环

对应到 Python 源码（简化版），这就是事件循环的核心 4 行：

# asyncio/base_events.py 的简化版本
def _run_once(self):
    timeout = self._compute_timeout()              # step 1
    event_list = self._selector.select(timeout)    # step 2 (核心阻塞点)
    self._process_events(event_list)
    self._process_scheduled()                       # step 3
    while self._ready:                          # step 4
        handle = self._ready.popleft()
        handle._run()                              # step 5: 真正运行用户协程

事件循环本身不"等" I/O —— 它把"等"这件事委托给了操作系统的多路复用器（epoll/kqueue/IOCP）。

启动事件循环的三种姿势

1. asyncio.run()（推荐）

Python 3.7+ 引入的高层 API。它做了三件事：创建新事件循环、运行你给的协程、清理所有未完成任务并关闭循环。

async def main():
    await do_things()

asyncio.run(main())   # ✓ 标准入口

2. 手动管理（不推荐）

loop = asyncio.new_event_loop()
asyncio.set_event_loop(loop)
try:
    loop.run_until_complete(main())
finally:
    loop.close()

3. asyncio.Runner（Python 3.11+）

用于需要复用同一个事件循环跑多个独立协程的场景：

with asyncio.Runner() as runner:
    runner.run(main1())
    runner.run(main2())   # 共享同一个事件循环
✦ Tip 除非你写底层框架（如 web 服务器），永远只用 asyncio.run()。它是经过最多检查的、最不容易出错的入口。

Chapter Five · 编排

任务编排 — gather, wait, as_completed

让多个协程并发不是难事 —— 难的是按你想要的方式收集结果、处理失败、决定何时停止。

asyncio 提供了多种并发编排原语。它们看似相似，但对失败处理、结果收集、取消行为的语义截然不同。错用一个，可能导致协程泄漏或异常被吞掉。我们一个一个看。

asyncio.gather — 一锅端

最常见的并发模式：启动 N 个协程，等所有都完成，按顺序拿到结果列表。

results = await asyncio.gather(
    fetch("a"), fetch("b"), fetch("c")
)
# results = [a 的结果, b 的结果, c 的结果]

关键参数 return_exceptions：默认是 False，意味着任一子协程抛异常就立即把异常传到 gather 的 await 处，但其他任务不会被自动取消（这是个常见误区）。改成 True 后，异常对象会作为"结果"出现在列表中：

results = await asyncio.gather(
    fetch("a"), fetch("b"), fetch("c"),
    return_exceptions=True
)
# results = [<data>, <TimeoutError>, <data>]

asyncio.TaskGroup（Python 3.11+，推荐）

这是 gather 的现代替代品，借鉴自 Trio 的"结构化并发"思想。它正确地处理了"一个失败就取消其他"的语义：

async with asyncio.TaskGroup() as tg:
    t1 = tg.create_task(fetch("a"))
    t2 = tg.create_task(fetch("b"))
    t3 = tg.create_task(fetch("c"))
# 退出 with 时所有任务保证完成或被取消
# 异常以 ExceptionGroup 形式抛出

asyncio.wait — 更灵活的控制

wait 不会自动解包结果，而是返回 (done, pending) 两个集合。它支持四种 return_when 策略：

策略语义
ALL_COMPLETED等所有任务完成（默认）
FIRST_COMPLETED第一个任务完成就返回
FIRST_EXCEPTION第一个抛异常或全部完成时返回

asyncio.as_completed — 流式获取

当你不关心顺序、想"先完成的先处理"时使用：

for coro in asyncio.as_completed([fetch(u) for u in urls]):
    result = await coro       # 谁先好谁先来
    process(result)

选择决策表

需求首选备注

Chapter Six · 协调

同步原语 — 锁、信号量、事件

单线程也需要同步原语？是的 —— 因为协程会在 await 处让出控制权，"原子操作"的边界从此变得微妙。

新手常以为：既然 asyncio 是单线程的，就不会有并发问题。这只对了一半。在两次 await 之间，代码确实是原子的；但只要跨过一个 await，其他协程就可能修改共享状态。所以 asyncio 提供了与 threading 同名的一组同步原语，但实现完全不同 —— 它们不阻塞线程，只阻塞协程。

四个核心原语速览

原语用途关键方法
Lock互斥访问临界区async with lock:
Semaphore限流（最多 N 个并发）async with sem:
Event一对多通知set() / wait()
Condition条件变量（带锁的 Event）wait_for(predicate)

Lock — 跨 await 的临界区

balance = 100
lock = asyncio.Lock()

async def withdraw(amount):
    global balance
    async with lock:                # 同一时刻只有一个协程进入
        if balance >= amount:
            await asyncio.sleep(0.1)  # 模拟 I/O
            balance -= amount

没有 Lock，balance >= amount 检查通过后、balance -= amount 执行前，await asyncio.sleep 会让出控制；其他协程可能在此期间提走钱，导致透支。这是典型的 TOCTOU（check-then-act）问题，单线程异步代码同样会遇到。

Semaphore — 优雅的限流

这是 asyncio 最实用的原语之一。当你要并发访问外部 API 但不想触发其速率限制，Semaphore 几乎是唯一答案：

sem = asyncio.Semaphore(10)   # 最多 10 个并发

async def limited_fetch(url):
    async with sem:
        return await fetch(url)

# 即使你 gather 1000 个，也只有 10 个真正并发
results = await asyncio.gather(*[limited_fetch(u) for u in urls])

Event — 广播信号

started = asyncio.Event()

async def worker(name):
    await started.wait()         # 阻塞直到事件被 set
    print(f"{name} 开工")

async def main():
    workers = [asyncio.create_task(worker(f"W{i}")) for i in range(5)]
    await asyncio.sleep(2)
    started.set()                  # 5 个 worker 同时被唤醒
    await asyncio.gather(*workers)
⚠ 切勿混用 asyncio.Lock 和 threading.Lock 是完全不同的对象。在协程里使用 threading.Lock 不会报错，但它会阻塞整个事件循环 —— 这是隐蔽的性能杀手。

Chapter Seven · 通信

异步队列 — 生产者与消费者

当任务之间需要解耦，asyncio.Queue 就是它们的邮局。

当一组协程负责"产生数据"，另一组负责"处理数据"，把它们直接耦合是糟糕的设计：生产快慢被消费拖累，反之亦然。asyncio.Queue 是经典的解决方案，它在协程之间提供有界 FIFO 缓冲，自动处理"满了就让生产者等"和"空了就让消费者等"两种情况。

三种队列变体

类型语义
asyncio.Queue(maxsize)FIFO，先进先出（最常用）
asyncio.LifoQueueLIFO，后进先出（栈）
asyncio.PriorityQueue按优先级出队

下面这张图展示了一个典型的生产者-消费者拓扑：M 个生产者把数据塞进队列，N 个消费者并发取出处理。

完整代码：网页爬虫管线

import asyncio, aiohttp

async def producer(queue, urls):
    for url in urls:
        await queue.put(url)
        print(f"[Producer] enqueued {url}")
    # 投递结束哨兵
    for _ in range(N_WORKERS):
        await queue.put(None)

async def consumer(queue, session, name):
    while True:
        url = await queue.get()
        if url is None:           # 收到哨兵，退出
            queue.task_done()
            break
        try:
            async with session.get(url) as r:
                data = await r.text()
                print(f"[{name}] {url} -> {len(data)} bytes")
        finally:
            queue.task_done()         # 必须配对，否则 join() 永不返回

N_WORKERS = 5

async def main(urls):
    queue = asyncio.Queue(maxsize=10)
    async with aiohttp.ClientSession() as session:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(producer(queue, urls))
            for i in range(N_WORKERS):
                tg.create_task(consumer(queue, session, f"W{i}"))
✦ 设计要点 哨兵模式：通过 put None 的方式通知消费者退出，是 asyncio 中标准做法。task_done() 必须与 get() 配对，queue.join() 才能正确判断队列已被处理完毕。

Chapter Eight · 失败处理

超时、取消与异常

真实世界里，网络会断、用户会取消、服务会挂。优秀的异步代码不是没有失败，而是优雅地承受失败。

超时控制 — 永远不要无限等待

asyncio 提供两种超时方式。asyncio.wait_for 是经典 API，asyncio.timeout（3.11+）是新的上下文管理器形式，更灵活也更推荐：

# 写法 1：wait_for —— 包裹单个协程
try:
    result = await asyncio.wait_for(slow_op(), timeout=5.0)
except asyncio.TimeoutError:
    print("超时了")

# 写法 2：timeout —— 包裹一段代码（推荐）
try:
    async with asyncio.timeout(5.0):
        result = await step1()
        result = await step2(result)
        result = await step3(result)
except TimeoutError:
    print("整个流程必须 5 秒内完成")

取消 — 协作式停止

asyncio 的取消机制是协作式的：task.cancel() 仅仅是请求取消，它会在目标协程的下一个 await 点抛出 CancelledError。如果协程从不 await，它永远不会被取消。

async def long_running():
    try:
        while True:
            await asyncio.sleep(1)
            print("working...")
    except asyncio.CancelledError:
        print("清理资源")
        raise                  # 必须重新抛出，否则任务状态不正确

task = asyncio.create_task(long_running())
await asyncio.sleep(3)
task.cancel()
try:
    await task
except asyncio.CancelledError:
    pass
⚠ 黄金法则 捕获 CancelledError 后，除非你有意吞掉取消请求（极少数场景），都应该 raise 重新抛出。否则调用方以为任务被取消，实际上它继续运行，造成幽灵任务。

异常处理流程图

下面这张图总结了 asyncio 中异常的传播路径，包括 TaskGroup 引入的 ExceptionGroup 概念：

ExceptionGroup 实战

async def main():
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(may_fail_with_value_error())
            tg.create_task(may_fail_with_runtime_error())
            tg.create_task(succeed())
    except* ValueError as eg:        # Python 3.11+: except* 语法
        for e in eg.exceptions:
            print(f"值错误: {e}")
    except* RuntimeError as eg:
        for e in eg.exceptions:
            print(f"运行时错误: {e}")

在异步世界里，"忽略异常"几乎总是 bug 的源头。Python 3.11 的 TaskGroup + ExceptionGroup 终于让异步异常处理像同步代码一样可靠。

shield — 保护协程不被取消

当一段操作必须完成（哪怕外层请求被取消）时，使用 asyncio.shield：

async def save_critical_data():
    # 即使外面 timeout 了，这个 await 也会跑完
    await asyncio.shield(write_to_disk())

Chapter Nine · 实战

用例图与三个真实场景

理论到此为止。让我们看看 asyncio 在实际系统中负责的角色 —— 它擅长什么，以及它如何与其他组件协作。

在动手之前，先用一张用例图（Use Case Diagram）来俯瞰 asyncio 的"势力范围"。这种图原本来自 UML，用于展示系统的不同参与者（actors）如何与系统交互、利用哪些功能。我们用它来回答："一个项目里，谁会在什么场景下选择 asyncio？"

场景一：批量并发 HTTP 请求（带限流与重试）

这是 asyncio 最经典的应用。比如你需要从 1000 个 URL 抓取数据，但目标服务限制每秒最多 50 并发，且偶尔会返回 503：

import asyncio, aiohttp, random
from dataclasses import dataclass

@dataclass
class Result:
    url: str
    status: int
    body: str | None
    error: str | None

async def fetch_with_retry(session, sem, url, max_tries=3):
    async with sem:                              # 限流
        for attempt in range(1, max_tries + 1):
            try:
                async with asyncio.timeout(10):
                    async with session.get(url) as r:
                        if r.status >= 500:
                            raise RuntimeError(f"server {r.status}")
                        body = await r.text()
                        return Result(url, r.status, body, None)
            except Exception as e:
                if attempt == max_tries:
                    return Result(url, 0, None, str(e))
                # 指数退避 + 抖动
                await asyncio.sleep(2 ** attempt + random.random())

async def fetch_all(urls, concurrency=50):
    sem = asyncio.Semaphore(concurrency)
    timeout = aiohttp.ClientTimeout(total=60)
    async with aiohttp.ClientSession(timeout=timeout) as s:
        return await asyncio.gather(
            *(fetch_with_retry(s, sem, u) for u in urls)
        )

场景二：异步 WebSocket 聊天室

展示 TaskGroup 在双向通信中的优雅。一个连接里有"读取"和"广播"两条独立的协程，任何一方失败应立即关闭整个连接：

import asyncio, websockets

CLIENTS: set[websockets.WebSocketServerProtocol] = set()

async def handler(ws):
    CLIENTS.add(ws)
    try:
        async for msg in ws:
            # 广播给所有人，每个发送独立超时
            async with asyncio.TaskGroup() as tg:
                for client in CLIENTS:
                    if client is not ws:
                        tg.create_task(safe_send(client, msg))
    finally:
        CLIENTS.discard(ws)

async def safe_send(client, msg):
    try:
        async with asyncio.timeout(5):
            await client.send(msg)
    except Exception:
        CLIENTS.discard(client)

async def main():
    async with websockets.serve(handler, "localhost", 8765):
        await asyncio.Future()         # 永远运行

asyncio.run(main())

场景三：把同步阻塞代码"包装"成异步

真实项目里你常常被迫使用某些只有同步 API 的库（比如某个 SDK）。如果直接调用，会阻塞事件循环。解决方案是用 run_in_executor 把它丢到线程池里：

import asyncio
from concurrent.futures import ThreadPoolExecutor

def blocking_db_call(query):
    # 假设这是一个阻塞 5 秒的同步 ORM 调用
    import time; time.sleep(5)
    return f"result of {query}"

async def async_query(query):
    loop = asyncio.get_running_loop()
    # Python 3.9+: asyncio.to_thread 是更短的写法
    return await asyncio.to_thread(blocking_db_call, query)

async def main():
    # 三个查询真的并发了，因为线程池里是 OS 线程
    results = await asyncio.gather(
        async_query("SELECT 1"),
        async_query("SELECT 2"),
        async_query("SELECT 3"),
    )
✦ 关键技巧 asyncio.to_thread（3.9+）是 run_in_executor(None, ...) 的简写，是包装阻塞 I/O 的标准答案。但不要用它来跑 CPU 密集代码 —— 那需要 ProcessPoolExecutor。

Chapter Ten · 终章

陷阱与最佳实践

异步代码 90% 的 bug 都来自同样的几个错误。把这一章当作清单收下。

十大常见陷阱

① 忘记 await 协程

# ✗ 错误：协程对象被丢弃，永远不执行
asyncio.sleep(1)

# ✓ 正确
await asyncio.sleep(1)

② 在协程里用阻塞调用

# ✗ 错误：冻结整个事件循环
async def bad():
    time.sleep(5)
    requests.get(url)

# ✓ 正确
async def good():
    await asyncio.sleep(5)
    async with aiohttp.ClientSession() as s:
        async with s.get(url) as r:
            await r.text()

③ create_task 创建后丢失引用

# ✗ 错误：任务可能被 GC 提前回收
async def spawn():
    asyncio.create_task(work())   # 没人持有，可能被回收

# ✓ 正确：保留强引用
background_tasks = set()
async def spawn():
    task = asyncio.create_task(work())
    background_tasks.add(task)
    task.add_done_callback(background_tasks.discard)

④ 误用 gather 处理失败

# ✗ 在 3.11+ 应该用 TaskGroup
results = await asyncio.gather(t1, t2, t3)

# ✓ 推荐
async with asyncio.TaskGroup() as tg:
    r1 = tg.create_task(t1)
    r2 = tg.create_task(t2)
    r3 = tg.create_task(t3)

⑤ 吞掉 CancelledError

# ✗ 错误：取消信号被吞，调用方以为成功
try:
    await work()
except Exception:        # Exception 包含 CancelledError
    pass

# ✓ 正确：单独处理 CancelledError
try:
    await work()
except asyncio.CancelledError:
    cleanup()
    raise
except Exception as e:
    log_error(e)

⑥ 在循环里 await（顺序而非并发）

# ✗ 慢：N 个请求顺序执行
for url in urls:
    result = await fetch(url)

# ✓ 快：并发执行
results = await asyncio.gather(*(fetch(u) for u in urls))

⑦ 混淆 asyncio.Lock 和 threading.Lock

# ✗ 错：threading 锁阻塞整个事件循环
from threading import Lock
lock = Lock()
async def bad():
    with lock:                # 阻塞的 acquire
        ...

# ✓ 对：asyncio 锁让出协程而非阻塞线程
lock = asyncio.Lock()
async def good():
    async with lock:
        ...

⑧ 不限制并发量

一次性 gather 1 万个 HTTP 请求，会立刻把客户端、目标服务器、本地文件描述符全部打爆。永远用 Semaphore 限流。

⑨ asyncio.run 嵌套调用

# ✗ 在已运行的事件循环里再次调用 asyncio.run() 会抛异常
async def outer():
    asyncio.run(inner())   # RuntimeError

# ✓ 直接 await
async def outer():
    await inner()

⑩ Jupyter / IPython 中误用

Jupyter 已经在背景运行了一个事件循环。在 cell 里直接写 await coro() 即可，不需要 asyncio.run。后者会抛出 "asyncio.run() cannot be called from a running event loop"。

九条最佳实践

  1. 始终设置超时。生产环境的每一次 I/O 都应该被 asyncio.timeout 包裹。
  2. 限制并发数。Semaphore 是你的朋友，连接池也是。永远不要让客户端"全速"轰击下游服务。
  3. 使用 TaskGroup（3.11+）。它处理异常和取消的方式比 gather 正确得多。
  4. 异步函数染色保持一致。一旦决定异步，整条路径都要异步；混用同步阻塞调用是性能反模式。
  5. 启用调试模式。asyncio.run(main(), debug=True) 或环境变量 PYTHONASYNCIODEBUG=1，会在协程被错误使用时大声告警。
  6. 合理使用 to_thread。把无法异步化的库丢进线程池，但只用于 I/O 密集；CPU 密集请走多进程。
  7. 给后台任务留引用。把 create_task 返回的 Task 加入一个集合，避免被 GC。
  8. 优雅停机。监听 SIGTERM，给所有任务发 cancel，等待 asyncio.gather(..., return_exceptions=True) 收尾。
  9. 测量再优化。aiomonitor、aiodebug、Python 3.12+ 的 asyncio.taskgroups 任务名机制能帮你看到事件循环里到底在跑什么。

异步不是更快的同步，而是另一种编程范式。一旦你在脑中建立了"事件循环"这个心智模型，所有问题都会变得简单。
