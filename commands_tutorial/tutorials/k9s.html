k9s 深度教程：面向 AI Infra 的 Kubernetes 终端控制台

这份教程面向 AI Infra、平台工程和训练集群值班场景。它不是“快捷键背诵表”，而是把 k9s 当作 Kubernetes API 的实时终端 UI 来理解：从 context/namespace 安全边界开始，进入 pods、logs、exec、describe、events、nodes、resource views，再落到 GPU 训练任务排障、资源配额、OOM、镜像拉取、调度失败和安全删除流程。

一句话理解： k9s 是 kubectl get/watch/describe/logs/exec/delete 的交互式控制台，它把 Kubernetes 资源关系、状态变化和常用动作聚合到一个可搜索、可过滤、可钻取的终端界面里。
生产原则： 默认用只读或低权限账号观察集群；任何 delete、kill、scale、edit、cordon、drain、node shell、exec 之前，都先确认 context、namespace、资源名、owner、影响面和回滚路径。

1. k9s 是什么，解决什么问题

k9s 是一个运行在终端里的 Kubernetes TUI。它读取你的 kubeconfig，与当前 context 指向的 API Server 通信，并用 watch/list/get/logs/exec 等 Kubernetes API 把资源实时展示出来。它尤其适合值班排障：不用反复复制 Pod 名、Namespace、Label，也不用在多个 kubectl 命令之间来回拼参数。

它擅长
快速发现异常 Pod、跟踪日志、查看事件、进入容器、浏览 Deployment/Job/Node/PVC/Service 等相关资源。
它不替代
声明式变更、GitOps、CI/CD、复杂 JSONPath 查询、批量审计脚本和需要精确复现的自动化流程。
对 AI Infra 的价值
把 GPU 训练任务的 Pod 状态、Node 资源、调度事件、日志和重启历史放在同一个操作面板里。
# 查看版本、配置路径、日志路径
k9s version
k9s info

# 使用默认 kubeconfig 和当前 context 启动
k9s

# 指定 context / namespace / 只读模式
k9s --context prod-gpu
k9s --context prod-gpu -n training
k9s --context prod-gpu -n training --readonly
边界提醒： k9s 的权限来自 kubeconfig 当前身份。它不是安全沙箱；如果你的 RBAC 允许删除 Pod，k9s 也能触发删除。

2. AI Infra 心智模型

信息图：k9s 在 AI Infra 中的位置

k9s 的核心价值是缩短“发现异常资源 → 查看上下文 → 定位根因 → 做最小动作”的路径；它的核心风险是把强权限变成一键动作。

3. 安装、版本与启动方式

在集群运维机、堡垒机或个人工作站上使用 k9s 前，先确认本机 kubectl 能访问目标集群。k9s 读取同一套 kubeconfig，因此 context、证书、token、OIDC 登录状态都会影响它。

目标命令说明
确认 kubectl 当前目标kubectl config current-context先知道自己会连到哪个集群。
查看 k9s 版本k9s version排查快捷键或配置差异时很重要。
查看配置和日志路径k9s info定位 config.yaml、日志、插件、热键文件。
指定命名空间启动k9s -n training避免打开后落在错误 namespace。
只读启动k9s --readonly禁用集群修改类动作，适合观察和培训。
# 推荐给生产观察者的启动习惯
kubectl config current-context
kubectl auth can-i delete pods -n training
k9s --context prod-gpu -n training --readonly

# 临时排障需要写权限时，仍先确认身份和权限
kubectl auth can-i get pods -n training
kubectl auth can-i exec pods -n training
kubectl auth can-i delete pods -n training
实践建议： 把生产 context 的名字做得非常醒目，例如 prod-gpu-us-east；不要让 prod 和 dev 在终端提示符或 k9s header 中难以区分。

4. 界面结构与导航语法

k9s 界面通常由 header、资源表格、详情/状态栏、命令提示区组成。你选择一行资源后，快捷键会作用在当前资源上；输入 : 进入命令模式，可以跳到不同资源视图。

Header
显示 context、namespace、cluster、用户、K9s 状态。
Table
资源列表，如 Pod、Node、Job、PVC、Event。
Command
: 后输入资源别名，如 po、deploy、jobs。
Help
? 查看当前视图可用快捷键。
# 在 k9s 中输入，不是在 shell 中输入
:po          # Pods
:deploy      # Deployments
:jobs        # Jobs
:no          # Nodes
:ns          # Namespaces
:ev          # Events
:pvc         # PersistentVolumeClaims
:ctx         # Contexts
:q           # 退出
语法差异： shell 命令是 k9s --context prod -n training；k9s 内部命令模式是 :po、:ns、:ctx。不要把两者混在一起。

5. Context 与 Namespace 安全边界

大多数生产事故不是因为 k9s 难用，而是因为操作者在错误 context 或 namespace 里做了正确动作。AI 集群通常有 dev、staging、prod、training、inference、platform 多个边界，k9s 的第一件事就是确认边界。

检查点k9s 操作等价 kubectl 思路
当前集群看 header，或进入 :ctxkubectl config current-context
当前 namespace看 header，或进入 :ns 选择kubectl config view --minify --output 'jsonpath={..namespace}'
观察全部 namespace使用 k9s 的 all namespace 模式或显式切换kubectl get po -A
权限边界写动作前先退出到 shell 验证kubectl auth can-i ...
# 进入 k9s 前的三步确认
kubectl config current-context
kubectl get ns | grep -E 'training|inference|gpu'
kubectl auth can-i delete pods -n training

# 启动时直接固定目标，减少误操作
k9s --context prod-gpu -n training --readonly
生产警告： 如果你需要临时切换到生产写权限，建议重新开一个终端窗口，显式执行 k9s --context prod-gpu -n training，不要在长时间打开的 k9s 会话里反复切换 context。

6. Resource Alias 与命令模式

Kubernetes 资源很多，k9s 用别名和命令模式降低跳转成本。命令模式支持资源名、复数、短名和部分别名；不同版本和配置可能略有差异，以 ? 和 Ctrl-A 展示的当前帮助为准。

视图常见输入AI Infra 场景
Pods:po / :pods训练 Worker、推理实例、CrashLoop、OOMKilled。
Jobs:jobsKubernetes Job、批处理训练、数据预处理。
Deployments:deploy推理服务、控制面组件、operator。
Nodes:no / :nodesGPU 节点、污点、容量、压力状态。
Events:ev / :events调度失败、拉镜像失败、卷挂载失败。
PVC:pvc数据集、checkpoint、模型权重挂载。
Services:svc推理入口、Ray head、指标服务。
# k9s 内部常用跳转
:po training            # 查看 training namespace 的 Pods
:jobs training          # 查看 training namespace 的 Jobs
:ev                     # 查看 Events
:no                     # 查看 Nodes
/gpu                    # 在当前表格中过滤包含 gpu 的行
Esc                     # 返回上一级或退出过滤/命令模式
记忆法： 先用 :po 找工作负载，再用 d/l/s 钻取；资源找不到时用 Ctrl-A 看别名列表。

流程图：Pod 排障主路径

不要一上来 exec。AI 训练任务的多数失败可以先由 Pod 状态、Describe Events 和日志定位，exec 应作为确认环境的后手。

7. Pod 排障主路径

Pod 是 k9s 中最常用的入口。训练 Job、Ray worker、vLLM 推理副本、数据预处理任务最终都会落成 Pod。先看状态，再看事件，再看日志，最后才进入容器。

现象优先看什么常见原因
Pendingd describe + eventsGPU 不足、nodeSelector 不匹配、taint 未容忍、PVC 未绑定、镜像拉取慢。
ImagePullBackOffevents + image 字段镜像名错误、registry 权限、tag 不存在、节点无法访问 registry。
CrashLoopBackOffl 当前日志 + previous logs入口脚本失败、环境变量缺失、模型路径错误、CUDA/NCCL 初始化失败。
OOMKilleddescribe 中 Last State 和 limits内存 limit 太低、DataLoader worker 过多、checkpoint 加载峰值过高。
Running 但无进度logs + node/top + GPU 指标侧工具数据 IO、NCCL hang、网络、分布式 rendezvous、CPU 预处理瓶颈。
# k9s 内部操作序列
:po
/train-20260425
d          # describe 当前 Pod
l          # logs 当前 Pod
s          # shell/exec，确认容器内环境
Esc        # 返回

# shell 中可复现的 kubectl 等价流程
kubectl -n training get pod train-0 -o wide
kubectl -n training describe pod train-0
kubectl -n training logs train-0 --all-containers=true --tail=200
kubectl -n training logs train-0 --previous --tail=200
排障顺序： 状态列告诉你“发生了什么”，events 告诉你“控制面为什么这么做”，logs 告诉你“容器内程序为什么失败”。

8. Logs：训练日志、前后容器与多容器 Pod

k9s 的日志视图适合持续观察训练输出、错误栈、NCCL 初始化、模型加载进度和推理服务请求。多容器 Pod 会提示选择容器；CrashLoop 场景要特别关注 previous logs，因为当前容器可能刚重启。

当前日志
选中 Pod 后按 l，查看当前容器输出。
多容器
选择 init、sidecar、main container，避免只看错容器。
历史失败
容器重启后，用 previous logs 或 kubectl 补充确认。
# k9s 中：选中 Pod 后按 l，按 ? 查看日志视图快捷键

# kubectl 等价命令，便于复制到事故记录
kubectl -n training logs train-0 -c trainer --tail=300
kubectl -n training logs train-0 -c trainer --previous --tail=300
kubectl -n training logs -f job/train-job --all-containers=true

# 常见 AI 训练日志过滤
kubectl -n training logs train-0 -c trainer --tail=1000 | grep -E 'CUDA|NCCL|OOM|Traceback|RuntimeError|Address already in use'
日志关键词可能方向下一步
CUDA out of memory显存不足看 request/limit、batch size、模型并行参数、MIG 切分。
NCCL WARN网络或 RDMA/NIC 配置看节点、网卡、环境变量、跨节点连通性。
No such file模型或数据路径错误检查 PVC、mountPath、启动参数。
Permission denied文件权限或安全上下文检查 fsGroup、runAsUser、PVC 权限。
日志限制： k9s 是排障界面，不是日志平台。长期检索、跨 Pod 聚合、审计归档应使用 Loki、Elastic、Cloud Logging、Stern 或集中式日志系统。

9. Describe 与 Events：定位调度和运行失败

Describe 是控制面解释资源状态的入口。对于 GPU 训练任务，Events 通常比应用日志更早暴露问题，例如调度失败、镜像拉取失败、卷挂载失败、配额不足。

# k9s 中
:po
/train
d          # describe 选中 Pod

:ev
/train     # 在 Events 中过滤任务名或 Pod 名

# kubectl 等价命令
kubectl -n training describe pod train-0
kubectl -n training get events --sort-by=.lastTimestamp
kubectl -n training get events --field-selector involvedObject.name=train-0
Event Reason含义AI Infra 排查方向
FailedScheduling调度器无法放置 PodGPU request、nodeSelector、affinity、taints/tolerations、quota。
FailedMount卷挂载失败PVC 绑定、存储后端、权限、节点插件。
BackOff容器反复失败previous logs、入口命令、环境变量、依赖服务。
Pulling/Failed镜像拉取异常registry token、镜像 tag、网络、节点磁盘。
Preempted被抢占PriorityClass、队列策略、训练任务可恢复性。
观察重点： Describe 里的 Requests、Limits、Node、QoS Class、Conditions、Events 是训练任务排障高频字段。

10. Exec、Shell 与临时调试边界

在 Pod 上按 shell/exec 快捷键能进入容器执行命令。它适合确认运行时环境，例如 CUDA 库、NCCL 环境变量、模型文件是否存在、DNS 是否可解析。但它也是高风险动作：你进入的是线上容器，不是本地沙盒。

# k9s 中：选中 Pod，按 s 进入 shell/exec；多容器时选择目标容器

# 容器内安全检查示例，只读为主
pwd
id
env | grep -E 'CUDA|NCCL|RANK|WORLD|MASTER|OMP'
ls -lah /models
df -h
cat /proc/meminfo | head

# kubectl 等价命令
kubectl -n training exec -it train-0 -c trainer -- bash
kubectl -n training exec train-0 -c trainer -- nvidia-smi
不要在生产容器内做这些事： 不要手工修改模型文件、删除 checkpoint、安装临时包覆盖依赖、kill 主训练进程、写入共享数据集目录。临时观察可以，修复应回到镜像、配置、Job 或 GitOps 流程。
安全 exec 习惯： 先执行只读命令；如果必须写入，记录命令、目标路径、原因和回滚方法，并优先在非生产副本复现。

11. GPU Workloads 观察法

k9s 不直接替代 nvidia-smi、DCGM、Prometheus 或厂商 GPU 工具，但它能帮你把 Kubernetes 层的调度与容器层的失败联系起来。关键是先确认 Pod 是否请求 GPU、落到哪个节点、是否被配额或节点标签限制。

问题k9s 视角补充命令
是否请求 GPUPod describe 中看 Requests/Limitskubectl -n training get pod train-0 -o yaml | grep -A5 nvidia.com/gpu
落在哪台节点Pod 列表 NODE 列或 describekubectl get node gpu-node-1 -o wide
节点是否 Ready:no 查看状态和压力kubectl describe node gpu-node-1
是否 GPU 不足Events 中 Insufficient nvidia.com/gpukubectl describe node | grep -A8 Allocatable
是否程序用到 GPU日志 + exec 中只读检查nvidia-smi、DCGM、Prometheus GPU 指标。
# 常见 GPU Pod 片段，排障时核对 request/limit
resources:
  limits:
    nvidia.com/gpu: "8"
  requests:
    cpu: "32"
    memory: "256Gi"

# 调度失败常见事件
0/24 nodes are available: 8 Insufficient nvidia.com/gpu, 4 node(s) had untolerated taint, 12 node(s) didn't match Pod's node affinity.
AI 集群特殊点： 一个 Pod Running 不代表训练健康。GPU 利用率为 0、NCCL hang、数据读取慢、rank 掉线都可能让任务“活着但不前进”。k9s 负责找到容器和节点，深度性能判断要结合 GPU/网络/存储指标。

13. 常用快捷键与操作表

快捷键会随视图和版本变化，当前视图可按 ? 查看。下面列的是高频心智模型，不建议在生产中盲按不熟悉的组合键。

键常见作用安全级别说明
?帮助安全查看当前视图支持哪些动作。
:命令模式安全跳转资源视图，如 :po、:ev。
/过滤安全按名字、状态、节点名等过滤当前表格。
dDescribe安全只读查看资源详情。
lLogs安全查看 Pod/容器日志。
sShell/Scale，取决于视图谨慎Pod 中常为 shell；Deployment 中可能是 scale。
eEdit高风险会修改线上对象，优先走 GitOps。
Ctrl-D / 删除键位Delete高风险不同版本/视图可能有确认；仍按破坏性动作处理。
Esc返回/退出模式安全退出过滤、详情或返回上级。
Ctrl-A资源别名列表安全查看可跳转资源。
快捷键陷阱： 同一个键在不同资源视图含义可能不同。例如 s 在 Pod 视图可能进入 shell，在 Deployment 视图可能是 scale。按键前看底部提示或 ?。

14. 安全处理破坏性动作

k9s 的破坏性动作包括 delete、kill、edit、scale、cordon/drain、node shell、port-forward 到敏感服务等。安全做法不是“永远不用”，而是给它们建立明确的确认流程。

动作风险安全流程
删除 Pod中断训练、触发重建、丢失本地临时状态确认 owner、checkpoint、重启策略、是否可重跑。
Kill/强制删除跳过优雅退出，可能破坏 checkpoint只在卡死且已确认可恢复时使用。
Edit 资源绕过 GitOps，造成漂移优先改仓库；临时热修必须记录 diff 和恢复方案。
Scale影响服务容量或训练并行度先看 HPA、队列、上游流量和预算。
Node Shell节点级权限风险只给平台值班人员，操作留痕。
# 删除前的 shell dry-run 思路：先确认选中对象的 owner 和影响面
kubectl -n training get pod train-0 -o wide
kubectl -n training get pod train-0 -o jsonpath='{.metadata.ownerReferences[*].kind}{" "}{.metadata.ownerReferences[*].name}{"\n"}'
kubectl -n training describe pod train-0 | sed -n '/Controlled By:/,/Events:/p'

# 如果必须删除，优先使用可记录、可复审的 kubectl 命令
kubectl -n training delete pod train-0 --wait=false

# 对 Job/Deployment 等上层资源更要谨慎
kubectl -n training get job train-job -o yaml > /tmp/train-job.before.yaml
事故防线： 删除 Pod 不等于删除训练任务本身，但可能导致 rank 重组、checkpoint 损坏、队列重试、GPU 资源被其他任务抢占。删除前问清楚“谁会重建它、重建后是否还能接上”。

对比图：k9s 与 kubectl 的协作边界

交互式探索用 k9s 很快；需要写入、复盘、自动化和审计时，把关键结论落到 kubectl 命令、YAML diff 或工单记录中。

15. k9s vs kubectl：什么时候用谁

任务更适合 k9s更适合 kubectl
快速找异常 Pod按状态排序、过滤、钻取脚本化扫描多个集群。
查看单个 Pod 上下文列表 → describe → logs 很快把命令输出贴到事故记录。
批量变更不推荐明确命令、dry-run、review、apply。
训练任务值班实时观察和切换资源复现检查、导出 YAML、采集证据。
GitOps 环境修复定位差异修改仓库、PR、CI、同步。
# 推荐的协作方式
# 1. k9s 中发现 train-0 CrashLoopBackOff
# 2. kubectl 采证

17. 配置、只读模式、热键与插件

k9s 支持配置文件、皮肤、别名、热键和插件。生产环境建议先把“安全默认值”做好：只读 context、清晰 skin、日志尾行数、禁用不必要的高危插件。

# 查看 k9s 会读取哪些路径
k9s info

# 只读启动，适合新同事培训或生产观察
k9s --context prod-gpu -n training --readonly

# 示例：通过配置调小日志默认窗口，避免终端卡顿
# $XDG_CONFIG_HOME/k9s/config.yaml
k9s:
  refreshRate: 2
  readOnly: false
  logger:
    tail: 200
    buffer: 1000
    sinceSeconds: 300
能力用途安全建议
Aliases给资源定义短名只做跳转，不隐藏危险动作。
HotKeys快速进入常用视图避免把删除/修改动作绑定成热键。
Plugins调用外部命令扩展功能审查命令、参数、confirm、dangerous 标记和作用域。
Skins改变视觉主题给生产 context 使用醒目的颜色。
插件风险： 插件本质上可以执行外部命令。不要从聊天记录或网页复制未审查的插件到生产运维机，尤其是包含 shell、curl、kubectl delete、node shell 的插件。

18. 常见坑与恢复方法

问题现象处理
看不到资源列表为空或 forbidden确认 context/namespace/RBAC；用 kubectl auth can-i list pods -n ns 验证。
Top 没数据CPU/Memory 列为空检查 metrics-server、RBAC、APIService 状态。
界面卡顿日志或资源列表刷新慢指定 namespace 启动、过滤资源、调小日志 buffer、避免全 namespace 观察巨大集群。
快捷键不符合预期按键动作和教程不同按 ? 看当前版本/视图帮助；检查自定义 hotkeys/plugins。
OIDC/token 过期连接失败或 unauthorized先用 kubectl get ns 触发登录或刷新 token，再重开 k9s。
误进入错误 contextHeader 显示非目标集群立即退出；用显式 k9s --context ... -n ... 重启。
# 排查 k9s 自身问题
k9s info
k9s -l debug

# 查看 k9s 日志路径后 tail
# 路径以 k9s info 输出为准
tail -f ~/.local/state/k9s/k9s.log

# 验证不是 k9s 问题，而是 API/RBAC 问题
kubectl --context prod-gpu -n training get pods
kubectl auth can-i get pods --context prod-gpu -n training
恢复策略： k9s 出问题时先回到 kubectl，因为 kubectl 输出更适合定位 kubeconfig、认证、RBAC 和 API Server 问题。
