1. ulimit 解决什么问题

ulimit 控制当前 shell 及其子进程能使用的某些资源上限，例如最多打开多少文件、最多创建多少进程/线程、栈大小、core dump 大小、锁页内存大小。它不是性能优化开关，而是防止单个用户或服务把节点资源耗尽的保护栏。

它擅长什么
快速查看和临时调整当前 shell 的资源限制，适合复现实验、诊断“Too many open files”“fork: Resource temporarily unavailable”“cannot allocate locked memory”等问题。
它不擅长什么
不能替代 cgroup、systemd、Kubernetes resource requests/limits；不能改变已经运行进程的 limits；也不能自动让所有登录方式、服务和容器都继承同一配置。
AI Infra 视角
训练框架、数据加载器、NCCL/RDMA、Web 推理服务、日志采集器、sidecar 都可能撞到 limits。排障必须确认“应用进程实际 limits”，而不是只看当前终端。
# 当前 shell 的全部资源限制
ulimit -a

# 单项查看：open files / user processes / locked memory
ulimit -n
ulimit -u
ulimit -l

# 查看已经运行进程实际继承到的 limits
cat /proc/$(pidof python | awk '{print $1}')/limits
关键区别： ulimit 是 shell 内建命令，不是普通二进制程序；不同 shell 输出略有差异，脚本中要明确使用 bash -lc、sh -lc 或目标运行时。

信息图：Linux limits 从哪里来、到哪里去

同一个用户从 SSH、systemd、Docker、Kubernetes、Slurm 启动的进程，limits 可能完全不同。

2. 快速巡检：ulimit -a 与 /proc

排障第一步是建立事实：当前 shell 的 soft/hard limits 是多少，目标进程实际继承到多少，单位是什么。ulimit -a 常用人类可读单位；/proc/<pid>/limits 则更接近最终真相。

# 当前 shell：软限制
ulimit -Sa

# 当前 shell：硬限制
ulimit -Ha

# 只看关键项
printf 'nofile soft=%s hard=%s\n' "$(ulimit -Sn)" "$(ulimit -Hn)"
printf 'nproc  soft=%s hard=%s\n' "$(ulimit -Su)" "$(ulimit -Hu)"
printf 'memlock soft=%s KB hard=%s KB\n' "$(ulimit -Sl)" "$(ulimit -Hl)"

# 目标进程：最可靠的排障入口
pid=12345
cat /proc/$pid/limits
grep -E 'Max open files|Max processes|Max locked memory|Max stack size|Max core file size' /proc/$pid/limits
检查对象说明适用场景
ulimit -Sa当前 shell 软限制临时运行命令前确认
ulimit -Ha当前 shell 硬限制判断普通用户还能否升高软限制
/proc/<pid>/limits某个运行中进程实际限制服务、容器、训练任务排障
prlimit --pid PID读取或调整运行进程限制需要 root/权限，适合临时救火和确认
单位提醒： ulimit -l 通常以 KB 显示 locked memory，/proc/<pid>/limits 的 Max locked memory 通常显示 bytes。对 memlock 排障时不要把 KB 和 bytes 混在一起。

流程图：soft limit 与 hard limit 的关系

生产配置通常同时设置 soft 和 hard：soft 给应用即时可用值，hard 给受控调高空间。

3. soft 与 hard：谁能改什么

每个限制项都有 soft 和 hard 两个值。内核实际判定多数情况下看 soft；hard 是普通用户能把 soft 调高到的最大值。普通用户可以降低 hard，但通常不能再升回去；root 或具备 CAP_SYS_RESOURCE 的进程才能升高 hard。

# 查看 nofile 的 soft/hard
ulimit -Sn
ulimit -Hn

# 临时把当前 shell 的 soft nofile 提高到硬限制内
ulimit -Sn 65535

# 同时设置 soft/hard，通常需要当前 hard 足够高或 root
ulimit -n 1048576

# 使用 prlimit 查看某个进程
prlimit --pid 12345

# root 临时调整运行进程，救火前先记录原值
prlimit --pid 12345 --nofile
sudo prlimit --pid 12345 --nofile=65535:65535
救火警告： prlimit 可以改变运行进程限制，但不是持久配置。事故处理时先保存 prlimit --pid PID 输出，修复后把配置固化到真正的启动路径，例如 systemd unit、容器 runtime 或 PAM limits。

4. 常见限制项速查

ulimit 选项limits.conf 项/proc 名称AI Infra 常见影响
-nnofileMax open files高并发推理服务、日志 tail、数据集小文件、socket 连接
-unprocMax processesPyTorch DataLoader、Ray、Jupyter、fork/clone 失败
-lmemlockMax locked memoryRDMA verbs、NCCL、DPDK、低延迟网络、部分 GPU/IPC 场景
-sstackMax stack size深递归、OpenMP/线程库、C/C++ 扩展栈溢出
-ccoreMax core file size崩溃后是否生成 core dump，调试训练/推理崩溃
-ffsizeMax file sizecheckpoint、日志、dump 文件被截断或写入失败
-vasMax address space限制虚拟地址空间，可能干扰大模型 mmap/allocator
-tcpuMax cpu time批处理任务 CPU 时间限制，通常 AI 节点不靠它做隔离
配置口径： limits.conf 的字段名不总等于 ulimit 选项名。例如 ulimit -n 对应 nofile，ulimit -l 对应 memlock。

5. nofile：文件描述符与高并发

nofile 限制进程最多能打开多少文件描述符。Linux 中 socket、pipe、eventfd、epoll、普通文件、日志文件都消耗 FD。高并发推理服务、分布式训练控制面、数据加载器、对象存储客户端很容易撞到它。

# 当前 shell 查看和临时设置
ulimit -Sn
ulimit -Hn
ulimit -Sn 65535

# 目标进程已经打开多少 FD
pid=12345
ls /proc/$pid/fd | wc -l
grep 'Max open files' /proc/$pid/limits

# 按进程查看 FD 数，定位泄漏嫌疑
for p in /proc/[0-9]*; do
  pid=${p##*/}
  count=$(ls "$p/fd" 2>/dev/null | wc -l | tr -d ' ')
  comm=$(cat "$p/comm" 2>/dev/null || true)
  printf '%8s %8s %s\n' "$count" "$pid" "$comm"
done | sort -n | tail
症状常见日志下一步
打开文件失败Too many open files看 /proc/PID/fd 数量和 Max open files
服务 accept 失败EMFILE、连接突然失败检查进程 FD 泄漏、连接池、日志轮转和 nofile
训练数据读取异常worker 读取小文件失败检查 DataLoader worker 数、预取、文件句柄关闭
不是越大越好： 把 nofile 提高只能避免过早撞限，不能修复 FD 泄漏。若 FD 数持续增长，先定位泄漏，否则节点会被内存、socket buffer 或后端服务拖垮。

6. nproc：线程、进程与 fork 失败

nproc 名字像“进程数”，实际和 Linux task 计数关系紧密，线程也可能计入。AI 训练中常见的 PyTorch DataLoader、OpenMP、Ray worker、Jupyter 多用户环境都可能触发 fork: Resource temporarily unavailable。

# 查看当前用户限制
ulimit -Su
ulimit -Hu

# 查看目标进程能用多少
grep 'Max processes' /proc/12345/limits

# 当前用户大致 task 数
ps -u "$USER" -o pid= | wc -l
ps -eLf | awk -v u="$USER" '$3==u {count++} END {print count+0}'

# 观察线程多的进程
ps -eLo pid,ppid,user,nlwp,comm --sort=-nlwp | head
训练节点常见触发点
每个 rank 多个 DataLoader worker，每个 worker 又使用 OpenMP/BLAS 线程，叠加日志/监控/sidecar 后超过用户级 task 限制。
修复顺序
先降低不必要 worker/线程数，再提高 nproc；不要只把 nproc 改大掩盖进程风暴。
# 常见降噪变量：按作业实际调小
export OMP_NUM_THREADS=8
export MKL_NUM_THREADS=8

# PyTorch 示例：减少 DataLoader worker
# DataLoader(..., num_workers=4, persistent_workers=True)
多租户警告： 对共享登录节点和 JupyterHub 节点，盲目给所有用户 nproc unlimited 会削弱防护；更推荐按组设置合理 hard limit，并用 cgroup/作业调度器隔离。

7. stack、core、fsize 与虚拟内存

不是所有 limits 都应该在生产中放开。stack 影响线程栈；core 控制 core dump 大小；fsize 限制单文件大小；as/v 限制虚拟地址空间。AI Infra 中它们通常用于调试、安全和故障隔离。

限制项常见建议注意事项
stack默认通常够用；C/C++ 深递归或复杂线程栈再评估线程多时过大 stack 会增加虚拟地址空间消耗
core调试崩溃时临时启用或由 systemd-coredump 管理core 可能包含模型权重、输入、密钥和用户数据
fsize通常不人为限制训练/推理服务输出低 fsize 会让 checkpoint、日志、dump 写失败
asAI 节点通常不靠它限制内存大模型 mmap、CUDA、allocator 可能依赖大虚拟地址空间
# 临时允许当前 shell 下程序生成 core，适合测试环境
ulimit -c unlimited

# 查看 core 配置与目标进程限制
cat /proc/sys/kernel/core_pattern
grep 'Max core file size' /proc/12345/limits

# 查看 stack
ulimit -s
grep 'Max stack size' /proc/12345/limits
安全提醒： core dump 是调试利器，也是敏感数据泄漏源。生产启用前要确认落盘路径、权限、清理策略和合规要求。

对照图：AI Infra 中最常撞限的资源

最常见的撞限项是 nofile、nproc、memlock；core/stack 常在调试和 C/C++ 扩展场景出现。

8. memlock：RDMA、CUDA IPC 与锁页内存

memlock 限制进程可锁定在物理内存中的大小。RDMA verbs 注册内存区域时需要把内存页 pin/lock，许多 InfiniBand/RoCE、DPDK、低延迟网络场景会受它影响。NCCL 或 UCX 报内存注册失败时，memlock 是必须检查的第一批项目之一。

# 查看 memlock，ulimit 通常以 KB 显示
ulimit -Sl
ulimit -Hl

# 目标训练进程实际值，/proc 通常显示 bytes
grep 'Max locked memory' /proc/12345/limits

# RDMA 相关基础确认
ls -l /dev/infiniband 2>/dev/null || true
ibv_devinfo 2>/dev/null | head -40 || true
rdma link 2>/dev/null || true
典型错误可能含义检查
Cannot allocate memory内存注册失败，可能是 memlock 或真实内存压力Max locked memory、dmesg、RDMA 驱动日志
ibv_reg_mr failedverbs 注册 MR 失败memlock、设备权限、HCA 状态、容器设备透传
NCCL/UCX fallback通信没有走预期 RDMA 路径NCCL/UCX 日志、/proc/PID/limits、容器配置
实践建议： 对专用训练节点，常见做法是给训练用户或训练服务设置较高 memlock，很多 RDMA 场景会设置为 unlimited；但要限定在可信用户/服务/容器运行时范围内，不要无差别放开共享节点。

9. limits.conf 语法与 PAM 生效路径

/etc/security/limits.conf 和 /etc/security/limits.d/*.conf 通过 PAM 的 pam_limits.so 在登录会话建立时设置限制。它主要影响 SSH、login、su 等 PAM 会话，不自动影响已经运行的进程，也通常不影响 systemd 启动的服务。

# 查看 PAM 是否加载 pam_limits
grep -R 'pam_limits.so' /etc/pam.d 2>/dev/null

# 推荐把自定义配置放到 limits.d，便于审计和回滚
sudo install -m 0644 /dev/null /etc/security/limits.d/90-ai-infra.conf

# 先编辑测试文件，不要直接覆盖系统文件
sudoedit /etc/security/limits.d/90-ai-infra.conf
字段示例含义
domainaiuser、@trainers、*用户、组或全局匹配。组名前加 @
typesoft、hard、-设置软限制、硬限制，或同时设置
itemnofile、nproc、memlock资源限制项
value65535、1048576、unlimited限制值，单位按 item 语义解释
# /etc/security/limits.d/90-ai-infra.conf
# 面向训练用户组的示例，按节点容量和租户策略调整
@trainers soft nofile 1048576
@trainers hard nofile 1048576
@trainers soft nproc  262144
@trainers hard nproc  262144
@trainers soft memlock unlimited
@trainers hard memlock unlimited

# 推理服务用户：高 nofile，但不一定需要 unlimited memlock
infer soft nofile 262144
infer hard nofile 262144
infer soft nproc  65535
infer hard nproc  65535
生效提醒： 修改 limits.conf 后，已有 shell 和已有进程不会变化。退出并重新登录，或重新启动由 PAM 创建的会话后再检查 ulimit -Sa/-Ha。

10. 安全变更流程

limits 变更看似简单，但错误范围很大：可能让服务仍不生效，也可能让共享节点失去保护。推荐用“备份、最小范围、重登/重启、验证目标进程”的流程。

# 1. 记录现状
date
ulimit -Sa
ulimit -Ha
cat /proc/$$/limits
sudo test -f /etc/security/limits.conf && sudo cp -a /etc/security/limits.conf /etc/security/limits.conf.$(date +%Y%m%d%H%M%S).bak

# 2. 新增独立 drop-in，不直接大改主文件
sudo tee /etc/security/limits.d/90-ai-infra.conf >/dev/null <<'EOF'
@trainers soft nofile 1048576
@trainers hard nofile 1048576
@trainers soft memlock unlimited
@trainers hard memlock unlimited
EOF

# 3. 重新登录后验证，不要在旧 shell 里判断
ssh "$USER@$(hostname)" 'ulimit -Sn; ulimit -Hn; ulimit -Sl; ulimit -Hl'

# 4. 启动真实应用后看目标进程
pid=12345
cat /proc/$pid/limits
先确认影响面
优先按用户或组配置，避免直接用 * 放开全系统。
先验证启动路径
登录 shell、systemd 服务、容器 Pod 分别验证，不要互相推断。
保留回滚路径
drop-in 文件更容易删除和审计；主配置改坏时影响更难定位。
不要这样做： 不要在生产共享节点上无差别写入 * - nofile unlimited、* - nproc unlimited。这会削弱防护，并可能让故障从“单作业失败”扩大成“整节点耗尽”。

11. systemd 服务 caveat

systemd 启动的服务通常不通过交互式 PAM 登录会话，因此 /etc/security/limits.conf 往往不会影响它们。服务要用 unit 文件里的 LimitNOFILE、LimitNPROC、LimitMEMLOCK 等配置，或者通过 drop-in 覆盖。

# 查看服务主进程实际 limits
svc=training-worker.service
systemctl show "$svc" -p MainPID -p LimitNOFILE -p LimitNPROC -p LimitMEMLOCK
pid=$(systemctl show "$svc" -p MainPID --value)
cat /proc/$pid/limits

# 创建 drop-in，推荐不要直接编辑 vendor unit
sudo systemctl edit training-worker.service
# /etc/systemd/system/training-worker.service.d/override.conf
[Service]
LimitNOFILE=1048576
LimitNPROC=262144
LimitMEMLOCK=infinity

# 生效
sudo systemctl daemon-reload
sudo systemctl restart training-worker.service
systemctl show training-worker.service -p LimitNOFILE -p LimitNPROC -p LimitMEMLOCK
systemd 字段对应限制常见值
LimitNOFILEnofile65535、1048576
LimitNPROCnproc按服务线程/worker 模型设置
LimitMEMLOCKmemlockinfinity 或明确字节大小
LimitCOREcore调试时启用，结合 core 策略
验证标准： 对 systemd 服务，最终以 /proc/MainPID/limits 为准；ulimit -a 只说明当前终端，不说明服务。

12. 容器与 Kubernetes caveat

容器里的 limits 由宿主机内核执行，但启动时可能被 OCI runtime、Docker/containerd、Kubernetes、systemd 和 cgroup 共同影响。宿主机 limits.conf 不等于 Pod 内进程 limits；必须进入容器看 /proc/1/limits 或目标进程 limits。

# Docker：启动时显式设置 ulimits
docker run --rm \
  --ulimit nofile=1048576:1048576 \
  --ulimit memlock=-1:-1 \
  --cap-add IPC_LOCK \
  ubuntu:24.04 bash -lc 'ulimit -a; cat /proc/$$/limits'

# Docker：查看容器 1 号进程实际 limits
docker exec CONTAINER bash -lc 'cat /proc/1/limits'

# Kubernetes：进入 Pod 验证
kubectl exec -n train pod/name -- sh -lc 'ulimit -a; cat /proc/1/limits'
nofile caveat
Kubernetes 原生 Pod spec 长期没有像 Docker CLI 一样直接的 per-container ulimit 字段；很多集群需要通过 container runtime 默认配置、CRI 配置、节点 systemd/containerd 配置或准入控制统一设置。
memlock caveat
即使 memlock 足够，容器也可能缺少 CAP_IPC_LOCK、/dev/infiniband 设备、RDMA device plugin、IPC/hostNetwork/驱动挂载等条件。
# containerd / CRI 场景：从节点侧确认运行时和 shim
ps -ef | egrep 'containerd|runc|crun' | grep -v grep
systemctl show containerd -p LimitNOFILE -p LimitNPROC -p LimitMEMLOCK

# Pod 内确认 RDMA 设备与 limits
kubectl exec -n train pod/name -- sh -lc '
  cat /proc/1/limits
  ls -l /dev/infiniband 2>/dev/null || true
  grep Cap /proc/1/status
'
结论边界： 容器内 ulimit -a 正常，只说明 limits 这一层正常；RDMA/NCCL 仍可能被设备插件、网络、GID、PFC/ECN、NCCL 参数或驱动版本阻塞。

13. 调度器、SSH 与非交互 shell

AI 集群常见启动路径包括 SSH 登录、JupyterHub、Slurm/PBS 作业、systemd timers、cron、Kubernetes Job、CI runner。不同路径是否走 PAM、是否读取用户 shell profile、是否继承提交端 limits，都不一样。

启动路径limits 来源验证方式
SSH 交互登录PAM pam_limits.so + shellssh node 'ulimit -Sa; ulimit -Ha'
systemd serviceunit Limit*、manager 默认值systemctl show + /proc/MainPID/limits
cronPAM/cron 服务配置与 daemon limits在任务里输出 ulimit -a
Slurm/PBS调度器 daemon、作业 prolog、PAM/插件配置作业脚本内 cat /proc/$$/limits
Kubernetesruntime、CRI、cgroup、镜像入口Pod 内看 /proc/1/limits
# 把 limits 打进作业日志，避免猜测
cat > check-limits.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
hostname
id
ulimit -Sa
ulimit -Ha
cat /proc/$$/limits
EOF
chmod +x check-limits.sh

# Slurm 示例
srun -N1 ./check-limits.sh
平台化建议： 把 limits 巡检写入节点验收、镜像验收、作业 prolog 或训练启动器，避免每次 NCCL/FD/fork 失败后再人工猜启动路径。

14. 故障症状映射

limits 类故障通常表现为系统调用失败，上层框架错误信息可能很绕。排障时把错误消息翻译回资源项，再用 /proc/PID/limits 和实际使用量确认。

15. 排障流程与命令模板

下面是一套可直接复制到事故现场的只读采集模板。它不修改系统，只把 limits、FD、线程、cgroup、systemd/container 线索集中保存，便于判断下一步该改哪里。

#!/usr/bin/env bash
set -euo pipefail
pid="${1:?usage: $0 PID}"
out="limits-triage-${pid}-$(date +%Y%m%d%H%M%S).txt"
{
  echo "== host =="; hostname; date; uname -a
  echo "== process =="; ps -p "$pid" -o pid,ppid,user,comm,args
  echo "== limits =="; cat "/proc/$pid/limits"
  echo "== fd count =="; ls "/proc/$pid/fd" 2>/dev/null | wc -l
  echo "== threads =="; grep -E '^Threads:|^NStgid:|^NSpid:' "/proc/$pid/status" || true
  echo "== cgroup =="; cat "/proc/$pid/cgroup" || true
  echo "== caps =="; grep '^Cap' "/proc/$pid/status" || true
  echo "== parent limits =="; ppid=$(awk '/^PPid:/ {print $2}' "/proc/$pid/status"); cat "/proc/$ppid/limits" 2>/dev/null || true
} | tee "$out"
echo "saved: $out"
判断方法： 如果目标进程 limits 已经足够高，但错误仍在，继续查应用泄漏、cgroup pids/memory、容器 capability、RDMA 设备权限、内核参数或后端服务瓶颈。

17. 练习路线与检查清单

第一阶段：看懂当前限制

  • 运行 ulimit -Sa 和 ulimit -Ha，解释 nofile、nproc、memlock 的 soft/hard。
  • 启动一个 sleep 300，读取 /proc/PID/limits，确认它继承当前 shell。
  • 比较 ulimit -l 与 /proc/PID/limits 的单位。

第二阶段：安全修改

  • 只在测试用户上新增 /etc/security/limits.d/90-lab.conf，重新登录后验证。
  • 为一个测试 systemd 服务添加 LimitNOFILE drop-in，重启服务后看 /proc/MainPID/limits。
  • 用 Docker --ulimit 启动容器，并在容器内看 /proc/1/limits。

第三阶段：AI Infra 排障

  • 模拟打开大量文件，观察 Too many open files 与 nofile 的关系。
  • 检查训练进程的 FD 数、线程数、memlock，并把结果保存到排障报告。
  • 把 limits 检查加入训练启动脚本或作业 prolog。

18. 常见误区

误区 1：改了 limits.conf 服务就会生效
systemd 服务通常要设置 Limit* 并重启服务。
误区 2：当前终端正常，Pod 就正常
Pod 由容器运行时启动，必须在容器内看目标进程。
误区 3：unlimited 是万能修复
它可能绕过保护栏，并掩盖 FD 泄漏、线程风暴或权限问题。
误区 4：只看 soft，不看 hard
普通用户只能在 hard 内调 soft；hard 太低时临时 ulimit 会失败。
误区 5：只查 limits，不查 cgroup
Kubernetes 和 systemd 还会用 cgroup 限制 pids、memory、CPU 和设备访问。
误区 6：RDMA 报错都归因于 memlock
memlock 很重要，但设备、GID、路由、PFC/ECN、NCCL/UCX 配置也同样关键。
