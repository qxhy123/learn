iperf3 深度教程：AI Infra 网络带宽测试与 NCCL 排障

这份教程围绕 Linux 命令 iperf3 展开，面向训练集群、推理集群、存储网络和 GPU 节点互联场景。它不是单纯罗列参数，而是从“一个节点开 server，另一个节点开 client，生成受控流量并观察吞吐、重传、抖动、丢包、CPU 利用”的心智模型出发，系统讲清 TCP/UDP、并发流 -P、反向测试 -R、MTU 线索、CPU 瓶颈、NCCL 网络三角定位，以及 iperf3 与 qperf、ib_write_bw 的边界。

AI InfraTCP/UDPServer/Client并发流 -P反向 -RMTU 线索CPU 瓶颈NCCL 排障生产安全
一句话理解： iperf3 是可控网络流量发生器和测量器：server 负责监听，client 负责发起测试，输出告诉你链路在指定方向、协议、并发度和时长下能跑到多少。
最重要原则： 在共享训练集群里先约定窗口、端口、节点和目标速率；先小流量短测，再扩大并发和时长，避免把生产网络、存储网络或正在训练的 NCCL 作业打满。

1. iperf3 是什么

iperf3 用来在两台主机之间生成 TCP、UDP 或 SCTP 测试流，并报告吞吐、重传、丢包、抖动等指标。AI Infra 中，它常用于回答一个基础问题：节点 A 到节点 B 的 IP 网络能力是否符合预期，是否足以支撑数据加载、参数同步、NCCL fallback、对象存储访问或推理流量。

它擅长什么
快速验证主机到主机的 IP 层带宽、方向差异、并发连接扩展性、UDP 丢包、TCP 重传和粗粒度网络健康。
它不擅长什么
不能直接证明 RDMA verbs、GPUDirect RDMA、NCCL collective 算法或应用层协议一定正常。
它的本质
一个受控流量实验：固定协议、方向、并发、时长和目标速率，然后把结果与网卡、交换机、CPU、MTU、NCCL 现象对照。
# 节点 B 上监听
iperf3 -s

# 节点 A 上发起 TCP 测试，默认端口 5201
iperf3 -c node-b

# 指定 30 秒、每 1 秒输出一次
iperf3 -c node-b -t 30 -i 1
边界提醒： iperf3 跑满不代表训练一定快；iperf3 跑不满则通常说明 IP 网络、CPU、内核参数、路由、MTU 或交换路径需要继续排查。

信息图：iperf3 的整体心智模型

iperf3 的测试结果只有在协议、方向、并发、时长、网卡接口和节点角色明确时才有工程意义。

2. 安装与版本确认

多数 Linux 发行版仓库都提供 iperf3。AI 集群里更重要的是确认所有节点版本大致一致，并确认测试用的是预期网络接口，而不是管理网或容器 NAT 路径。

# Debian / Ubuntu
sudo apt-get update
sudo apt-get install -y iperf3

# RHEL / CentOS / Rocky / Alma
sudo dnf install -y iperf3

# 确认版本和路径
iperf3 --version
command -v iperf3

# 确认路由会走哪张网卡
ip route get 10.10.20.12
ip -br addr
检查项为什么重要常见问题
版本不同版本支持的参数、JSON 字段和 bug 修复不同脚本在一台机器可用，另一台不识别参数
IP 与接口AI 节点常有管理网、业务网、存储网、RoCE 网误测 1/10Gb 管理网，误以为训练网慢
防火墙server 默认监听 TCP 5201client 报连接超时或 refused
权限普通带宽测试通常不需要 root抓包、调 sysctl、查 ethtool 可能需要 sudo
容器提示： 在 Kubernetes 或 Docker 内测试时，要明确测的是 Pod 网络、hostNetwork、宿主机网卡还是 Service 路径；这些结论不可混用。

3. 第一组 TCP 带宽测试

TCP 是 iperf3 默认协议。建议先做短时间单流测试确认连通性，再增加时长和并发，最后记录两端命令、节点名、IP、网卡、时间窗口和输出摘要。

# node-b：启动 server，默认监听 5201
iperf3 -s

# node-a：连到 node-b，跑 10 秒 TCP 测试
iperf3 -c 10.10.20.12

# 更适合基线记录：30 秒、每秒报告一次
iperf3 -c 10.10.20.12 -t 30 -i 1

# server 只服务一次后退出，适合自动化任务
iperf3 -s -1 -p 5201
先通后快
先确认能连接、端口通、方向对，再讨论是否达到 25G/100G/200G/400G 预期。
先单流后并发
单 TCP 流可能受拥塞窗口、CPU、内核队列影响；不能仅凭单流否定链路能力。
先短测后长测
短测适合连通性，长测更能暴露热 throttling、队列丢包、交换机拥塞和 CPU 饱和。
生产警告： 不要在未知共享网络上直接长时间高并发跑满。先和集群管理员确认测试窗口，避免影响正在训练或在线推理服务。

4. 读懂输出：sender、receiver、retransmits

iperf3 TCP 输出通常包含每个时间段和最终汇总。重点看 sender、receiver、Retr、带宽单位，以及测试是否完整结束。

[ ID] Interval           Transfer     Bitrate         Retr
[  5]   0.00-1.00   sec  10.9 GBytes  93.7 Gbits/sec  0
[  5]   1.00-2.00   sec  10.8 GBytes  92.9 Gbits/sec  1
- - - - - - - - - - - - - - - - - - - - - - - - -
[  5]   0.00-30.00  sec   326 GBytes  93.3 Gbits/sec  4 sender
[  5]   0.00-30.04  sec   326 GBytes  93.1 Gbits/sec    receiver
字段含义AI Infra 解读
Bitrate当前时间窗或总周期吞吐与网卡速率、交换机端口、预期拓扑对比
RetrTCP 重传数量高重传常见于拥塞、丢包、队列溢出、错误 MTU、网卡/交换机问题
sender发送端视角看发送侧是否被 CPU 或窗口限制
receiver接收端视角更接近对端实际收到的数据量
测试时长输出中的实际秒数短测波动大；30 到 120 秒更适合基线
判断原则： 高吞吐、低重传、两端结果接近，通常说明 IP 网络基本健康；吞吐低但重传也低，则更像窗口、CPU、单流限制、限速或路径选错。

5. TCP 调优：时长、间隔、窗口、零拷贝

iperf3 不只是 -c。在高速网卡上，合理设置测试时长、报告间隔、窗口、CPU 亲和和零拷贝，能减少误判。

参数用途例子
-t测试时长，默认 10 秒-t 60
-i报告间隔-i 1
-O忽略前 N 秒，避开 TCP 慢启动或热身-O 3
-wTCP socket buffer/window-w 16M
-ZLinux 零拷贝发送，降低 CPU 开销-Z
-ACPU 亲和，减少调度漂移-A 8
-B绑定本地地址，确保走目标接口-B 10.10.20.11
# 高速链路常用基线：忽略前 3 秒，持续 60 秒，绑定源 IP
iperf3 -c 10.10.20.12 -B 10.10.20.11 -t 60 -i 1 -O 3

# 尝试更大的 socket buffer
iperf3 -c 10.10.20.12 -t 60 -w 16M

# Linux 上降低发送端 CPU 压力
iperf3 -c 10.10.20.12 -t 60 -Z
不要把调参当修复： 如果只有极端窗口或特殊 CPU 绑定才能跑满，仍要检查内核参数、NUMA、IRQ、网卡 offload、交换机队列和实际应用行为。

流程图：并行流 -P 如何帮助识别瓶颈

并行流不是“作弊”，而是用多个 TCP 连接验证链路聚合能力；但它也可能掩盖单连接应用的真实瓶颈。

6. 并行流 -P：为什么单流跑不满

在 100G/200G/400G 网络上，单个 TCP 连接可能因为拥塞窗口、单核 CPU、socket buffer、RSS/队列映射或路径策略跑不满。-P 会开启多个并行 TCP 连接，观察总吞吐是否随并发提高。

# 逐步扩大，不要一上来就打满共享网络
iperf3 -c 10.10.20.12 -t 30 -P 1
iperf3 -c 10.10.20.12 -t 30 -P 4
iperf3 -c 10.10.20.12 -t 30 -P 8
iperf3 -c 10.10.20.12 -t 30 -P 16

# 配合忽略热身期和绑定源 IP
iperf3 -c 10.10.20.12 -B 10.10.20.11 -t 60 -O 3 -P 8
现象可能含义下一步
-P 1 低，-P 8 高单连接受限，但链路总能力可能正常看应用是否也是多连接；调窗口、CPU、队列
-P 增加后仍低路径、限速、CPU、MTU、丢包或物理链路异常查接口速率、错误包、交换机、retrans
吞吐高但 retrans 高可能靠重传堆出吞吐，网络质量不稳检查拥塞、PFC/ECN、队列、MTU
某些流明显慢ECMP/RSS/队列或链路哈希不均换端口、换 IP、看交换机链路利用率
结论写法： 不要只写“iperf3 93G”。应写“TCP，A 到 B，-P 8，60 秒，receiver 93G，retrans 低”。

7. 反向与双向：-R、--bidir

默认情况下，client 向 server 发送数据。-R 会反向：client 仍发起控制连接，但由 server 向 client 发送数据。双向测试则同时测两个方向，更容易暴露全双工、队列和 CPU 瓶颈。

# 默认方向：node-a client 发送到 node-b server
iperf3 -c 10.10.20.12 -t 30 -P 8

# 反向：node-b server 发送到 node-a client
iperf3 -c 10.10.20.12 -t 30 -P 8 -R

# 双向：两个方向同时发送，适合观察全双工压力
iperf3 -c 10.10.20.12 -t 30 -P 4 --bidir
为什么方向重要
AI 集群的路由、QoS、ACL、队列、源 IP 选择、容器路径可能方向不对称。A 到 B 正常，不代表 B 到 A 正常。
什么时候用双向
需要模拟参数交换、双向 RPC、存储读写混合或 NCCL 通信时，用双向测试观察是否出现明显吞吐塌陷。
兼容提醒： --bidir 需要较新的 iperf3。脚本化前先用 iperf3 --version 确认目标环境支持。

8. UDP：目标码率、抖动与丢包

UDP 测试不会像 TCP 那样自动拥塞控制。使用 -u 时必须设置合理目标码率 -b，否则很容易制造丢包或误伤共享网络。UDP 的价值在于观察路径在指定速率下的 jitter、lost datagrams 和是否存在限速。

# 从 1G 开始，不要直接打满
iperf3 -c 10.10.20.12 -u -b 1G -t 30 -i 1

# 逐步提高到目标链路的一部分
iperf3 -c 10.10.20.12 -u -b 10G -t 30 -i 1

# 指定 UDP datagram 长度，辅助观察 MTU/分片线索
iperf3 -c 10.10.20.12 -u -b 10G -l 1200 -t 30
iperf3 -c 10.10.20.12 -u -b 10G -l 8972 -t 30
指标含义常见解读
Jitter包到达间隔抖动实时推理、RPC 和存储 tail latency 可能受影响
Lost/Total Datagrams丢包数量与比例RoCE 网络尤其需要关注丢包、PFC/ECN 与队列配置
-b目标发送码率不要超过当前测试窗口允许的安全上限
-lUDP payload 长度大包丢、小包不丢时，考虑 MTU、分片或设备 offload
UDP 安全警告： UDP 没有 TCP 的退让机制。高 -b UDP 测试可能让交换机队列、存储流量和训练任务受到明显影响。

9. AI Infra 测试基线设计

AI Infra 的网络测试要从“随机跑一下”升级为“可复现基线”。每次记录节点角色、机架、网卡、驱动、交换路径、命令、时间和负载背景，才能和 NCCL、存储、数据加载或推理延迟关联。

场景建议测试重点指标
GPU 节点间训练网TCP -P 8 双方向，必要时 UDP 分级速率吞吐、retrans、方向差异、CPU
数据加载到训练节点存储网到计算节点多对一、多对多聚合带宽、接收端 CPU、交换机拥塞
推理服务东西向流量短时低并发和高并发都测稳定性、抖动、反向路径、CPU
新节点验收同机架、跨机架、跨交换域矩阵是否达到端口速率合理比例
NCCL fallback 到 TCP绑定 NCCL 使用的 IP 接口测 iperf3路径是否选对，TCP 性能是否健康
# 建议的最小基线矩阵
# 1. 同机架 A -> B
iperf3 -c 10.10.20.12 -B 10.10.20.11 -t 60 -O 3 -P 8

# 2. 同机架 B -> A
iperf3 -c 10.10.20.12 -B 10.10.20.11 -t 60 -O 3 -P 8 -R

# 3. 跨机架 A -> C
iperf3 -c 10.10.40.21 -B 10.10.20.11 -t 60 -O 3 -P 8

# 4. JSON 保存，便于和巡检系统对接
iperf3 -c 10.10.20.12 -t 60 -O 3 -P 8 -J > iperf3-node-a-node-b.json
基线建议： 对高速网络，单次结果不如趋势重要。保留同一参数、同一时间窗口、同一拓扑的历史 JSON，才能看出退化。

信息图：MTU、分片与吞吐异常线索

iperf3 能提供 MTU 线索，但不能替代端到端 MTU 验证、接口统计和交换机侧检查。

10. MTU 与分片线索

MTU 错配在 AI 集群里很常见：物理网卡设了 9000，bond、VLAN、容器 overlay、交换机端口或中间路径却没有统一。iperf3 不是 MTU 探测工具，但能通过 TCP 重传、UDP 大包丢包和吞吐平台期提供线索。

# 查看接口 MTU
ip -br link
ip link show dev ens5f0

# IPv4 下用 DF 位探测，不允许分片
ping -M do -s 1472 10.10.20.12   # 对应常见 1500 MTU
ping -M do -s 8972 10.10.20.12   # 对应常见 9000 MTU

# UDP 用不同 payload 长度对比
iperf3 -c 10.10.20.12 -u -b 5G -l 1200 -t 20
iperf3 -c 10.10.20.12 -u -b 5G -l 8972 -t 20

# 查看网卡错误、丢包、offload 相关统计
ethtool -S ens5f0 | egrep -i 'err|drop|crc|timeout|discard'
ethtool -k ens5f0
现象可能方向不要忽略
小包 ping 通，大包 DF ping 不通端到端 MTU 不一致VLAN、bond、overlay、交换机端口
TCP 有明显重传，UDP 大包丢分片、队列、MTU 或硬件错误同时看 ethtool -S 和交换机 counters
只有容器内异常CNI/overlay MTU 与宿主机不一致Pod、veth、tunl/vxlan、Service 路径
计算提醒： ping -s 是 ICMP payload，不等于链路 MTU；常见 IPv4 1500 MTU 对应 -s 1472，9000 MTU 对应 -s 8972。

11. CPU、NUMA 与中断瓶颈

高速网络不是只看线缆和交换机。100G 以上 TCP 测试经常被 CPU、NUMA、IRQ 亲和、RSS 队列、内存带宽或 copy 开销限制。AI 节点上 GPU、数据加载、解压、加密和日志也会抢 CPU。

发送端 CPU 瓶颈
表现为吞吐上不去、单核接近 100%、-Z 有明显改善、-P 增加后有所改善。
接收端 CPU 瓶颈
表现为 receiver 低、软中断高、某些 RX 队列过热、丢包或 socket buffer 压力。
NUMA 错位
网卡在 NUMA 0，进程或中断跑到 NUMA 1，内存跨 socket，吞吐和稳定性都可能下降。
队列不均
RSS/IRQ 分布不均，单队列被打满；多流可能改善，也可能暴露哈希不均。
# 测试时同时观察 CPU 和网络
mpstat -P ALL 1
sar -n DEV,TCP,ETCP 1
pidstat -t -p $(pgrep -n iperf3) 1

# 查看网卡所在 NUMA 节点和 PCI 信息
cat /sys/class/net/ens5f0/device/numa_node
readlink /sys/class/net/ens5f0/device

# 绑定 iperf3 到特定 CPU，降低调度漂移
iperf3 -c 10.10.20.12 -t 60 -P 8 -A 8

# Linux zero copy，降低发送端 copy 开销
iperf3 -c 10.10.20.12 -t 60 -P 8 -Z
经验判断： 如果 iperf3 进程或软中断已经把 CPU 顶满，继续调交换机意义不大；先处理 CPU/NUMA/IRQ/RSS，再看链路。

三角图：NCCL 网络排障如何使用 iperf3

iperf3 是 NCCL 排障的 IP 层切片；RDMA、GPU 拓扑、NCCL 算法和环境变量还需要其他工具共同验证。

12. NCCL 网络三角定位

NCCL 慢可能来自 IP 路径、RDMA 路径、GPU 拓扑、NUMA、PCIe、驱动、PFC/ECN、NCCL 环境变量或算法选择。iperf3 的作用是先把“普通 IP 网络是否健康”切出来，避免在 NCCL 日志里盲猜。

# 1. 明确 NCCL 可能使用的接口
ip -br addr
ip route get 10.10.20.12

# 2. 绑定同一张业务网卡做 iperf3
iperf3 -c 10.10.20.12 -B 10.10.20.11 -t 60 -O 3 -P 8
iperf3 -c 10.10.20.12 -B 10.10.20.11 -t 60 -O 3 -P 8 -R

# 3. NCCL 侧打开日志，确认接口选择和网络插件
NCCL_DEBUG=INFO NCCL_SOCKET_IFNAME=ens5f0 ./build/all_reduce_perf -b 8M -e 4G -f 2 -g 8

# 4. 临时禁用 IB 只看 TCP fallback，不作为最终性能目标
NCCL_DEBUG=INFO NCCL_IB_DISABLE=1 NCCL_SOCKET_IFNAME=ens5f0 ./build/all_reduce_perf -b 8M -e 4G -f 2 -g 8
组合结果解释倾向下一步
iperf3 慢，NCCL 也慢IP 路径、CPU、MTU、丢包、路由或限速先有问题修 IP 网络，再回到 NCCL
iperf3 正常，NCCL 慢RDMA、NCCL 配置、GPU/PCIe/NUMA、拓扑或算法问题看 NCCL 日志、nvidia-smi topo -m、RDMA perftest
TCP fallback 正常，IB/RoCE 慢RDMA 路径、PFC/ECN、GID、RoCE 参数或 HCA 问题用 ib_write_bw、端口 counters、交换机 counters
单方向异常路由/ACL/QoS/队列/CPU 方向不对称用 -R、交换源目的、抓 counters
NCCL 提醒： 不要把 NCCL_IB_DISABLE=1 当成长期修复；它只适合定位 TCP fallback。高性能训练通常需要正确的 RDMA/RoCE 路径。

13. iperf3 vs qperf vs ib_write_bw

这些工具解决不同层面的问题。AI Infra 排障时，最常见误区是用 iperf3 证明 RDMA 正常，或用 ib_write_bw 证明 TCP 应用正常。正确做法是按层切片。

工具测量层面优势局限适合问题
iperf3IP/TCP/UDP/SCTP易用、输出清晰、适合主机间带宽基线不直接测 RDMA verbs 或 NCCL collective普通网络吞吐、重传、UDP 丢包、方向差异
qperfTCP/UDP/RDMA 等多种测试可测延迟和带宽，覆盖面比 iperf3 更广环境和参数更依赖发行版/组件快速比较 tcp_lat、tcp_bw、rdma 相关指标
ib_write_bwRDMA verbs接近 HCA/RDMA 数据面，常用于 RoCE/IB 验收不代表应用协议，也不走普通 TCP 栈验证 HCA、GID、PFC/ECN、RDMA 带宽
nccl-testsNCCL collective最接近训练通信行为受 GPU、拓扑、算法、消息大小影响大最终确认 all-reduce/all-gather 性能
# iperf3：IP 层 TCP 带宽
iperf3 -c 10.10.20.12 -t 60 -P 8

# qperf：示例，按环境支持情况调整测试项
qperf 10.10.20.12 tcp_bw tcp_lat

# ib_write_bw：RDMA 写带宽，参数依赖 HCA/GID/设备环境
ib_write_bw -d mlx5_0 -F

# nccl-tests：NCCL collective 端到端
./build/all_reduce_perf -b 8M -e 4G -f 2 -g 8
分层结论： iperf3 正常只能说明 IP 网络切片健康；RDMA 和 NCCL 仍需 qperf/perftest/nccl-tests 继续验证。

14. 自动化采集与 JSON 输出

-J 输出 JSON，适合做节点验收、日常巡检和回归比较。不要只保存一行最终带宽；保存完整 JSON 可以回看 CPU 信息、端点、时间段、丢包和每流数据。

# server 端只跑一次，方便被调度系统启动
iperf3 -s -1 -p 5201

# client 保存 JSON
ts=$(date +%Y%m%d-%H%M%S)
iperf3 -c 10.10.20.12 -t 60 -O 3 -P 8 -J \
  > "iperf3-node-a-to-node-b-${ts}.json"

# 如果安装了 jq，可以抽取最终 receiver 吞吐
jq '.end.sum_received.bits_per_second' iperf3-node-a-to-node-b-${ts}.json
字段/元数据建议记录
节点源节点、目标节点、机架、机型、网卡型号
网络源 IP、目标 IP、接口名、MTU、端口速率、交换域
命令完整 iperf3 命令、版本、测试时长、并发度、方向
环境是否有训练作业、是否有存储流量、CPU 负载、时间窗口
结果sender/receiver 吞吐、retrans、UDP lost/jitter、异常日志
自动化建议： 用固定参数做趋势，用临时参数做诊断。不要把一次临时加大 -P 的结果混进基线趋势。

15. 安全边界与生产演练

iperf3 的危险不在于会修改文件，而在于它能制造真实网络压力。AI Infra 网络经常承载训练同步、checkpoint、对象存储、日志、监控和推理流量，错误的压测会造成级联影响。

测试前
确认窗口、节点、端口、接口、协议、目标速率和回滚动作；通知相关训练/平台团队。
测试中
先短测，逐步扩大；同步观察交换机、主机 CPU、网卡 counters、NCCL 作业和存储延迟。
测试后
停止 server，归档命令和 JSON，记录是否影响其他业务；不要留下长期监听进程。
共享环境
优先测隔离节点、维护窗口或低峰期；UDP 高码率要格外谨慎。
# 查是否已有 iperf3 server
pgrep -a iperf3
ss -ltnp | grep 5201

# 使用非默认端口，避免和他人冲突
iperf3 -s -p 15201
iperf3 -c 10.10.20.12 -p 15201 -t 30 -P 4

# 测完清理自己启动的进程
pkill -f 'iperf3 -s -p 15201'
清理提醒： pkill 前先用 pgrep -a 确认命令行，避免误杀他人的测试进程。

16. 常见故障与排障流程

Connection refused
server 没启动、端口不对、server 已被 -1 测完退出。用 ss -ltnp | grep 5201 确认。
Connection timed out
路由、防火墙、安全组、ACL 或跨网段不可达。先 ip route get，再用 nc -vz 或 telnet 验端口。
单流很低，多流正常
拥塞窗口、单核 CPU、RSS/队列或应用连接模型问题。继续测 -P 阶梯和 CPU。
多流也低
检查是否走错管理网、端口速率是否降级、MTU 是否错配、交换机是否限速。
重传高
关注拥塞、丢包、PFC/ECN、队列、物理错误、CRC、MTU、交换机 counters。
UDP 丢包高
先降低 -b，再看丢包阈值；不要把超速打爆队列误判为链路故障。
只在容器里慢
检查 CNI、overlay MTU、hostNetwork、CPU limit、Pod 路由和 Service 路径。
NCCL 慢但 iperf3 正常
继续查 RDMA、NCCL 环境变量、GPU/PCIe/NUMA 拓扑和 collective 消息大小。

排障模板

# 1. 确认 server 和端口
ssh node-b 'pgrep -a iperf3; ss -ltnp | grep 5201 || true'

# 2. 确认路由和接口
ip route get 10.10.20.12
ip -br addr

# 3. 单流、并发、反向依次测
iperf3 -c 10.10.20.12 -t 20 -P 1
iperf3 -c 10.10.20.12 -t 20 -P 8
iperf3 -c 10.10.20.12 -t 20 -P 8 -R

# 4. 同步看主机指标
sar -n DEV,TCP,ETCP 1
mpstat -P ALL 1
ethtool -S ens5f0 | egrep -i 'err|drop|crc|discard'

17. 练习任务与学习路线

第一阶段：会安全运行

  • 在两台测试节点上启动 server/client，完成 10 秒 TCP 测试。
  • 分别记录默认方向和 -R 反向结果。
  • 使用非默认端口 -p，避免和他人测试冲突。

第二阶段：会解释结果

  • 比较 -P 1、-P 4、-P 8 的吞吐和 retrans。
  • 用 -O 3 忽略热身期，观察最终汇总变化。
  • 同步观察 mpstat 和 sar -n TCP,ETCP，判断 CPU 和重传是否异常。

第三阶段：AI Infra 排障

  • 绑定 NCCL 可能使用的源 IP，用 -B 测同一接口。
  • 对比 iperf3、ib_write_bw 和 all_reduce_perf，写出分层结论。
  • 对跨机架节点做矩阵测试，保留 JSON，建立历史基线。
# 练习环境建议：两台空闲测试节点
# node-b
iperf3 -s -p 15201

# node-a
iperf3 -c node-b -p 15201 -t 20 -P 1
iperf3 -c node-b -p 15201 -t 20 -P 4
iperf3 -c node-b -p 15201 -t 20 -P 4 -R
iperf3 -c node-b -p 15201 -u -b 1G -t 20
iperf3 -c node-b -p 15201 -t 30 -P 4 -J > iperf3-practice.json
