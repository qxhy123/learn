1. perf 是什么，适合解决什么问题

perf 是 Linux 内核自带的性能分析工具族，核心能力来自 perf_events 子系统。它能读取 CPU 硬件计数器、内核软件事件和 tracepoint，并把这些事件按进程、线程、CPU、函数、调用栈维度聚合。

它擅长
CPU 热点、低 IPC、cache miss、分支预测失败、上下文切换、内核/用户态栈、native 库瓶颈。
它不擅长
直接解释业务语义、GPU kernel 细节、Python 对象级内存、分布式链路和数据库内部等待。
AI Infra 价值
定位 dataloader、tokenizer、pre/postprocess、RPC、压缩、日志、内核网络栈、BLAS/oneDNN/native 扩展热点。
# 查看 perf 是否可用
perf --version

# 看一个命令的整体 CPU 事件
perf stat -- python train.py --steps 100

# 对正在运行的服务观察 10 秒
perf stat -p 12345 -- sleep 10

# 采样并离线查看热点
perf record -F 99 -g -p 12345 -- sleep 30
perf report
边界提醒： perf 看到的是机器级事实，不是完整因果。低 IPC 可能来自内存等待、分支失败、锁竞争、虚拟化噪声或 CPU 降频，需要结合指标和业务上下文解释。

2. AI Infra 中的典型 perf 场景

AI 系统不只是 GPU。很多吞吐问题发生在 CPU 侧：样本解码、特征处理、tokenization、batch 拼接、压缩、网络收发、日志、RPC 编解码、模型服务前后处理、native 扩展和内核调度。

现象perf 观察重点常见解释
GPU 利用率低但 CPU 忙cycles、instructions、热点函数、context switchesdataloader/tokenizer/预处理拖慢供给，或线程过多调度抖动。
推理 p99 抖动CPU migrations、context-switches、cache misses、内核栈线程迁移、NUMA、锁、日志或网络栈导致尾延迟。
CPU 使用率高但吞吐不涨IPC、branch-misses、cache-missesCPU 花时间等待内存、错误分支或执行低效代码。
Python 服务看不到 native 瓶颈perf record -g + 符号热点在 C/C++ 扩展、OpenMP、BLAS、protobuf、zlib、jemalloc。
# 训练进程短窗口总览
PID=$(pgrep -n -f 'python.*train.py')
perf stat -d -d -d -p "$PID" -- sleep 15

# 推理服务查看线程级热点，先找线程 ID
ps -L -p 12345 -o pid,tid,psr,pcpu,comm
perf top -t 12378

3. 安装、版本和权限

perf 通常随 Linux kernel tools 安装，版本最好与运行内核匹配。权限由 /proc/sys/kernel/perf_event_paranoid、kptr_restrict、capability、容器安全策略共同决定。

发行版安装示例备注
Ubuntu/Debiansudo apt install linux-tools-common linux-tools-$(uname -r)内核升级后可能需要安装对应版本。
RHEL/CentOS/Rockysudo dnf install perf旧系统可能是 yum install perf。
Archsudo pacman -S perf包名和内核包相关。
# 检查权限
cat /proc/sys/kernel/perf_event_paranoid
cat /proc/sys/kernel/kptr_restrict

# 临时降低限制：只在受控测试机或明确授权环境使用
sudo sysctl kernel.perf_event_paranoid=1

# 更高权限需求的场景可用 capability，但要由平台安全策略批准
sudo setcap cap_perfmon,cap_sys_ptrace,cap_syslog=ep "$(command -v perf)"
安全注意： 不要在共享生产主机随意把 perf_event_paranoid 调到 -1。perf 采样可能暴露进程名、路径、符号、调用栈和部分内核地址信息。

4. 核心心智模型：事件、计数、采样、符号

使用 perf 前先区分两种模式：计数回答“发生了多少次”，采样回答“这些事件大多发生在哪里”。stat 主要计数，top/record/report 主要采样。

信息图：perf 从 CPU 事件到热点函数

先用计数确认问题类型，再用采样定位代码位置，这是 perf 的主流程。
概念解释常见命令
事件CPU cycles、instructions、cache misses、context switches 等。perf list
计数统计窗口内事件总数和派生指标。perf stat -e cycles,instructions
采样事件每发生一段时间或次数后记录一次执行位置。perf record -F 99 -g
符号把地址翻译成函数名、库名、源码行。perf report --stdio

5. perf stat：先判断系统状态

perf stat 是生产排障的第一站。它开销低，输出是统计窗口内的整体事实，可以快速判断 CPU 是否忙于执行、等待内存、频繁调度或大量缺页。

# 对命令做一次完整统计
perf stat -- python preprocess.py --input data.jsonl

# 对进程做 10 秒观测
perf stat -p 12345 -- sleep 10

# 更详细的通用指标，-d 可重复
perf stat -d -d -d -p 12345 -- sleep 15

# 指定事件，便于稳定对比
perf stat -e cycles,instructions,cache-references,cache-misses,context-switches,cpu-migrations,page-faults -p 12345 -- sleep 10
输出项怎么看AI Infra 解释示例
task-clock进程实际获得的 CPU 时间，除以墙钟时间约等于平均 CPU 核数。10 秒窗口里 task-clock 80s，说明平均使用约 8 个 CPU 核。
cyclesCPU 周期数，受频率、停顿和调度影响。CPU 忙但吞吐低，需要结合 IPC 和 miss。
instructions退休指令数。同样请求量下指令数变多，可能引入低效代码路径。
context-switches上下文切换次数。线程池过大、锁等待、I/O 等待或 cgroup 限制。
对比技巧： 固定输入、固定窗口、固定 CPU 亲和性或隔离噪声后，对比优化前后的 instructions、IPC、cache miss ratio 和吞吐，避免只看 CPU 使用率。

6. 读懂 cycles、instructions、IPC

IPC 是 instructions per cycle，即每个 CPU 周期退休多少条指令。它不是越高越好，也不能跨不同 CPU 微架构直接比较，但在同机同负载对比时非常有价值。

信息图：IPC 的直觉

低 IPC 常意味着 CPU 并没有有效执行指令，而是在等待某些资源。
# 只看 cycles / instructions / IPC
perf stat -e cycles,instructions -p 12345 -- sleep 10

# 每秒输出一次，观察抖动
perf stat -I 1000 -e cycles,instructions -p 12345 -- sleep 10
现象可能含义下一步
IPC 明显降低，cache-misses 升高内存访问局部性差，可能随机读、hash、解压、对象遍历。看热点函数和数据结构，尝试批处理、缓存、向量化。
IPC 低，context-switches 高调度/锁/I/O 等待噪声。按线程看，检查线程池、cgroup、锁和阻塞 I/O。
instructions 增加但 IPC 稳定代码路径变长，算法或序列化逻辑变重。对比热点和调用次数，做 A/B perf record。

7. 缓存、分支、内存停顿指标

AI 前后处理常包含大量字符串、JSON、protobuf、图像解码、稀疏特征和随机索引访问。此类代码即使 CPU 使用率高，也可能被缓存缺失拖慢。

# 通用缓存和分支事件
perf stat -e cache-references,cache-misses,branches,branch-misses -p 12345 -- sleep 10

# 进一步查看当前机器支持哪些事件
perf list | grep -E 'cache|branch|stalled|mem-load' | head -80

# 某些 CPU 支持更细的 top-down 指标
perf stat -M TopdownL1 -p 12345 -- sleep 10
指标解读优化方向
cache-misses缓存未命中。比例高时 CPU 等内存。提升局部性、减少对象分散、批量处理、避免随机访问。
branch-misses分支预测失败。复杂分支、数据相关分支会触发。减少热路径条件分支，拆分冷热路径，表驱动或向量化。
stalled-cycles-frontend前端取指/解码停顿。检查代码膨胀、i-cache、间接跳转和符号解释。
stalled-cycles-backend后端执行/内存等待停顿。检查内存、依赖链、缓存 miss 和锁。
平台差异： PMU 事件名、支持矩阵和派生指标随 CPU、内核、虚拟化环境变化。脚本里要检测 perf list，不要假设所有机器都有同名事件。

8. 上下文切换、迁移和调度噪声

AI 服务常使用多线程库：OpenMP、oneDNN、MKL、tokenizer 线程池、RPC worker、Python dataloader worker。线程过多或亲和性不当会造成频繁切换和 CPU 迁移，进而伤害 cache locality 和 p99。

# 看调度相关事件
perf stat -e context-switches,cpu-migrations,page-faults -p 12345 -- sleep 10

# 线程级 CPU 使用和所在 CPU
ps -L -p 12345 -o pid,tid,psr,pcpu,stat,comm

# 记录调度事件，适合短窗口
sudo perf sched record -p 12345 -- sleep 5
sudo perf sched latency
现象可能原因处理思路
context-switches 很高线程池过大、锁竞争、阻塞 I/O、频繁 sleep/wakeup。减少线程数、合并任务、检查锁和队列。
cpu-migrations 很高线程在 CPU 间移动，缓存热数据丢失。CPU 亲和性、NUMA 绑定、合理 cgroup cpuset。
page-faults 异常内存映射、数据加载、缺页或内存压力。预热、减少 mmap 抖动、检查内存和 swap。
AI 运行时提示： 同时设置 OMP_NUM_THREADS、MKL_NUM_THREADS、推理框架 intra/inter op 线程数时，要用实际吞吐和 perf 指标验证，默认值不一定适合容器 CPU 配额。

9. perf top：线上实时热点观察

perf top 类似“函数级 top”。它实时采样并显示最热符号，适合在故障现场快速判断热点是在业务代码、Python 解释器、native 库、内核网络栈还是内存分配器。

# 系统级观察，通常需要权限
sudo perf top

# 限定进程，降低噪声
sudo perf top -p 12345

# 降低采样频率，减少生产开销
sudo perf top -F 49 -p 12345

# 只看某个线程
sudo perf top -t 12378
热点样子可能解释下一步
PyEval_EvalFrame...Python 字节码执行占主导。考虑 py-spy、cProfile、算法优化或迁移热路径。
memcpy/memmove大量拷贝。检查 batch 拼接、序列化、tensor/array 复制。
malloc/free/jemalloc分配频繁或碎片。对象复用、池化、批处理、检查 allocator。
tcp_*/skb_*内核网络栈开销。结合 bpftrace、网络指标、批量发送和连接复用。
使用建议： perf top 是现场观察工具，不适合长期跑。需要留证据、对比或离线分析时，用 perf record。

10. perf record/report：离线采样定位

perf record 把样本写入 perf.data，perf report 离线查看聚合结果。这是定位 CPU 热点的主力流程。

流程图：从安全采样到可行动结论

record/report 的关键是受控采样：限定对象、限定频率、限定时长、保留可复现实验条件。
# 对进程采样 30 秒，记录调用栈
sudo perf record -F 99 -g -p 12345 -- sleep 30
sudo perf report

# 生成文本报告，适合保存到工单
sudo perf report --stdio --no-children | head -120

# 对一个命令采样
perf record -F 99 -g -- python preprocess.py --input data.jsonl
perf report --stdio

# 指定输出文件，避免覆盖
sudo perf record -o perf.train.data -F 99 -g -p 12345 -- sleep 30
sudo perf report -i perf.train.data
生产警告： 不要直接用很高频率长时间采样，例如 -F 9999 跑数小时。先用 -F 49 或 -F 99、10 到 60 秒窗口验证开销和样本质量。

11. 调用栈、火焰图和符号化

没有调用栈时，你只能知道“哪个函数热”；有调用栈时，才能知道“它从哪条路径被调用”。AI Infra 中很多热点来自通用库，调用路径比单个符号更重要。

选项含义适用场景
-g记录调用图，默认 unwind 方式由系统决定。常规采样。
--call-graph fp使用 frame pointer 回溯。二进制保留 frame pointer 时开销低、质量好。
--call-graph dwarf使用 DWARF 信息回溯。frame pointer 缺失时尝试，但开销更高。
--children把子调用成本汇总到父节点。看调用路径总成本。
# frame pointer 栈，通常更稳
sudo perf record -F 99 --call-graph fp -p 12345 -- sleep 30
sudo perf report --stdio

# 如果二进制省略 frame pointer，可尝试 DWARF，但要更短窗口
sudo perf record -F 49 --call-graph dwarf,4096 -p 12345 -- sleep 15

# 导出脚本格式，可交给火焰图工具链
sudo perf script -i perf.data > out.perf
符号 caveat： stripped 二进制、JIT、容器内路径不一致、缺少 debuginfo、未保留 frame pointer 都会让报告出现十六进制地址或错误调用栈。优化前先确认样本能被正确解释。

12. Python 与 native 栈的 caveats

perf 采样的是机器执行位置。对 Python 来说，它天然擅长看到解释器和 C/C++ 扩展，却不一定直接显示 Python 源码函数。AI 项目里热点常在 NumPy、PyTorch、tokenizers、protobuf、OpenCV、Pillow、zlib、jemalloc 或自定义 extension。

# Python 进程 native 视角
sudo perf record -F 99 -g -p "$(pgrep -n -f 'python.*serve.py')" -- sleep 30
sudo perf report --stdio

# Python 3.12+ 可关注系统是否启用 perf map 支持
python -X perf -c 'import time; time.sleep(1)'

# 对纯 Python 热点，py-spy 往往更直接
py-spy top --pid 12345
py-spy record -o profile.svg --pid 12345 --duration 30
报告看到含义怎么继续
PyEval_EvalFrameDefault大量时间在 Python 解释器执行。用 py-spy/cProfile 定位 Python 函数，再考虑批量化或 native 化。
libtorch_cpu.so/libmkl时间在 native 数值库。检查线程数、输入形状、算子选择、NUMA 和 BLAS 配置。
tokenizers/regex文本处理或正则热点。批量 tokenize、缓存、减少重复 normalize。
大量 [unknown]符号或 unwind 信息缺失。补 debuginfo、perf map、frame pointer，缩小采样对象。
实战规则： Python 业务逻辑用 py-spy 更快；native CPU 瓶颈、内核、cache/IPC 用 perf 更强。两者经常要一起用。

13. 容器和 Kubernetes 中使用 perf

容器不是独立内核，perf 仍然依赖宿主机内核权限和 perf_events。最稳妥的方式通常是在宿主机或特权 debug 容器中对目标 PID 采样，同时处理 namespace、符号路径和 securityContext。

# 宿主机上找容器进程
ps aux | grep 'python.*serve.py'
sudo perf stat -p 12345 -- sleep 10

# 容器内可能需要挂载 perf_event 和放开能力，具体由平台策略控制
docker run --rm -it --privileged --pid=host ubuntu:24.04 bash

# Kubernetes 临时 debug 容器示意：是否可用取决于集群策略
kubectl debug node/NODE_NAME -it --image=ubuntu:24.04 --privileged
问题症状处理
权限不足Operation not permitted检查 perf_event_paranoid、capability、seccomp、privileged。
PID namespace容器内 PID 与宿主机 PID 不一致。用宿主机 PID，或 --pid=host debug。
符号路径报告只有地址或找不到库。保存容器镜像、rootfs、debuginfo，使用同版本二进制分析。
cgroup CPU 配额CPU 利用率和 task-clock 难解释。结合 cgroup quota、cpuset 和 throttling 指标。
平台安全： --privileged、hostPID、放开 seccomp 都是高权限操作。生产集群应通过标准 debug 流程申请，并采样最小时间窗口。

14. AI 训练/推理服务案例

下面是一个可复用的定位路径：先确认 GPU 等 CPU，接着用 perf stat 判断 CPU 效率，再用 record/report 找具体函数。

训练 dataloader 吞吐低
现象：GPU 利用率周期性掉到 30%，CPU 有几个 worker 很忙。perf 显示 jpeg 解码、memcpy 和 Python pickle 热。处理：增加预解码缓存、减少进程间拷贝、调 batch 拼接逻辑。
推理 p99 抖动
现象：平均延迟正常，尾延迟高。perf stat 显示 migrations 和 context switches 高，report 显示日志格式化和内核网络栈热点。处理：线程绑定、降低日志热路径、批量发送。
# 案例模板：固定窗口收集
PID=$(pgrep -n -f 'python.*serve.py')
date
perf stat -d -d -d -p "$PID" -- sleep 20
sudo perf record -o perf.$PID.data -F 99 --call-graph fp -p "$PID" -- sleep 30
sudo perf report -i perf.$PID.data --stdio --no-children | head -160

# 对比优化前后，至少记录业务吞吐和 perf 指标
printf 'qps=%s p50=%s p99=%s\n' "$QPS" "$P50" "$P99"
优化假设perf 证据成功标准
减少 tokenizer 重复工作tokenizer 符号样本占比下降，instructions/request 下降。同输入下 QPS 上升，CPU 核数不增加。
降低线程池过度并发context-switches 和 migrations 下降。p99 改善，吞吐不下降。
减少数据拷贝memcpy 样本占比下降。CPU 时间下降，端到端延迟下降。

15. perf vs py-spy vs bpftrace

这些工具不是互相替代，而是观测层次不同。选择工具时先问：我要看 Python 函数、native CPU 热点，还是内核事件和动态追踪？

对比图：三类工具的最佳使用区间

AI Infra 排障经常需要组合工具，而不是期待单个工具给出完整答案。
工具强项弱项优先场景
perfCPU 硬件事件、native 栈、内核栈、低层热点。Python 源码函数不总是直观，权限和符号复杂。CPU 高、IPC 低、cache miss、native 扩展。
py-spyPython 函数采样，使用简单，火焰图直观。看不到完整 PMU 指标，native 细节有限。Python 业务逻辑慢、GIL/线程状态观察。
bpftrace动态追踪内核/用户事件，按条件聚合。脚本能力要求高，生产安全策略更严格。系统调用、网络、I/O、锁、调度等待。

16. 生产安全、开销和数据治理

perf 是强观测工具，也有成本和数据风险。生产使用要遵循最小权限、最小范围、最短时间、可审计留痕。

安全图：生产 perf 的四道闸

生产 perf 的目标是回答一个具体问题，而不是“先抓一堆数据再说”。
# 推荐：先计数，再短采样
perf stat -p 12345 -- sleep 10
sudo perf record -F 49 --call-graph fp -p 12345 -- sleep 30

# 限定输出并记录元信息
uname -a > perf.context.txt
perf --version >> perf.context.txt
sudo perf report --stdio -i perf.data > perf.report.txt
不要做： 不要在多租户机器系统级高频采样；不要采不相关租户进程；不要把包含内部路径、函数名、用户参数的报告公开粘贴到外部系统。

17. 常见错误与排障清单

错误/现象可能原因解决办法
No permission to enable cycles eventperf_event_paranoid 或 capability 限制。查看 sysctl，按平台流程申请权限，或先采自身进程/命令。
perf.data 很大采样频率高、窗口长、DWARF 栈大。降低 -F、缩短时间、限定 PID/TID、用 frame pointer。
大量 [unknown]符号缺失、JIT、容器路径不一致、stripped 二进制。安装 debuginfo，保留镜像 rootfs，启用 perf map/frame pointer。
报告热点全是 perf 或系统噪声没有限定目标，系统级采样混入其他负载。使用 -p、-t、-C 限定对象。
IPC 解释不一致不同 CPU、频率、输入、容器 quota 或虚拟化影响。同机同条件对比，记录上下文，结合业务指标。
cycles 事件不可用虚拟机未暴露 PMU，云厂商限制。尝试软件事件，换宿主机/实例规格，或使用云平台 profiling。
# 常用排障命令
perf list | head
cat /proc/sys/kernel/perf_event_paranoid
cat /proc/sys/kernel/kptr_restrict
ldd /proc/12345/exe 2>/dev/null || true
readelf -Ws /path/to/lib.so | head

# 检查机器和负载上下文
uname -a
lscpu
numactl --hardware 2>/dev/null || true
cat /sys/fs/cgroup/cpu.max 2>/dev/null || true
排障顺序： 先解决权限，再解决目标范围，再解决符号，最后解释指标。顺序反了很容易把噪声当结论。

18. 参考命令速查与学习路线

第一阶段：会看整体
perf stat、task-clock、IPC、context switches、cache misses。
第二阶段：会找热点
perf top、perf record -g、perf report、符号和调用栈。
第三阶段：会解释系统
PMU 事件、调度、NUMA、容器、Python/native 栈、与 eBPF 工具组合。
目标命令
列出事件perf list
统计命令perf stat -- CMD
统计进程perf stat -p PID -- sleep 10
实时热点sudo perf top -p PID
采样热点sudo perf record -F 99 -g -p PID -- sleep 30
查看报告sudo perf report --stdio
导出脚本sudo perf script -i perf.data > out.perf
# 一个保守、可复用的 AI 服务 CPU 排障模板
PID=$(pgrep -n -f 'python.*serve.py')
perf stat -d -d -d -p "$PID" -- sleep 15
sudo perf record -o perf.$PID.data -F 99 --call-graph fp -p "$PID" -- sleep 30
sudo perf report -i perf.$PID.data --stdio --no-children | head -160
