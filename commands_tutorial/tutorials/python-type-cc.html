Chapter I · 第一章 Why Types

为什么 需要
类型注解

Python 因动态而生。它的类型系统不是来取代这一点 — 而是要让你在保留它的灵活性的同时，把那些只有运行才发现的错误，挪到键盘还没离开手时就显形。

Python 的动态本质，是它从一开始就吸引人的原因之一。变量不必预先声明，函数可以接受任何对象，只要后者"长得对"就行。这种自由让 Python 在脚本、原型与数据探索领域几乎不可替代。但当一个脚本长成了二十万行的服务、当它由二十个人共同维护、当它需要在凌晨三点也不出错时，这份自由就开始有了代价。

那个代价，常常以一段相同的剧本上演：某位同事改了某个函数的返回值，从返回 dict 改成返回一个对象；测试覆盖到了主要路径，CI 通过；上线两小时后，某个边缘分支调用了 result["name"]，于是 TypeError: 'User' object is not subscriptable 出现在生产日志里。问题本身不复杂；问题在于它本来 应该 在写代码的那一刻就被发现。

类型注解（type hints）就是为这种场景而生的。它的核心承诺很朴素：让 Python 代码在保留动态性的前提下，能被一个外部工具静态地审视一遍 — 在文件保存的瞬间，在 git commit 之前，在 CI 流水线开始时，把那些 "对象不是它以为的形状" 类的错误，从生产环境里挪到开发者的屏幕上。

§ 1.1类型注解不改变运行时

这是理解整个体系最重要的一句话。当你写下：

annotation_runtime.pyPython
def greet(name: str) -> str:
    return f"Hello, {name}"

# 解释器并不会拒绝下面这一行
greet(42)  # 运行时正常返回 "Hello, 42"

解释器看到 : str 与 -> str，只是把它们存进了 greet.__annotations__ 字典 — 它不会做任何类型检查。这与 Java、TypeScript（编译期）甚至是 C 的行为都不同。Python 的类型注解是 纯粹的元数据，它的检查由外部工具完成：mypy、pyright、Pyre、pytype 等。运行时几乎无成本，但也意味着如果你不运行检查器，注解只是写给人看的注释。

Note · 注
这个 "运行时不参与" 的设计是 PEP 484 (2014) 的关键妥协 — 它让 Python 既可以拥抱类型系统，又不会让现有数十亿行无类型代码崩溃。但近年来 dataclasses、pydantic、typer 等库开始在运行时 读取 这些注解，把它们用作业务逻辑的一部分。这是一种巧妙的复用，但也偶尔带来歧义 — 我们会在第 8 章讨论。

§ 1.2类型注解能抓什么 bug

不是所有 bug 都是类型 bug。注解擅长的是 形状错位类的错误 — 这类错误占典型 Python 项目缺陷的相当大一部分。具体而言：

  • AttributeError 类：调用了对象上不存在的方法或属性。None.split() 是其中最经典的一例。
  • TypeError 类：把字符串传给了期望整数的函数；把列表当字典用；把异步函数当成普通函数调用却忘了 await。
  • None 处理疏漏：返回 Optional[X] 的函数被当作返回 X 来用 — 这是生产环境 NoneType 报错的最大单一来源。
  • 重构遗漏：改了某个函数签名，调用方却没有同步更新。注解让所有受影响的位置在静态检查阶段全部亮红。
  • API 误用：调用第三方库时参数顺序、关键字、容器形状错误。

它 不 擅长的，则是逻辑错误：你计算了均值但本应计算中位数；你的循环边界少了 1。这些错误的类型是对的，只是值错了 — 这仍然要靠测试来抓。把类型注解和单元测试视作互补的两层网，是最务实的态度。

§ 1.3注解的代价

诚实地说，类型注解不是免费午餐。它的成本主要在三处：

第一是 书写成本。最简单的函数原本一行就能写完，加了注解之后变成两行甚至三行。这在写脚本和 notebook 时尤其令人心烦。这也是 Python 生态选择 "渐进式类型" 的原因 — 你可以只给关键的公共接口加注解，私有函数依然裸奔。

第二是 学习曲线。typing 模块本身比看上去丰富得多 — TypeVar、Protocol、Generic、ParamSpec、TypeGuard、Annotated、Self、Final、NewType、TypeAlias… 它们各自解决一类问题，但要把它们全部理解透彻，确实需要一本像本册这样的读本。

第三是 边角案例。当你需要表达 "返回一个和入参同类型的容器" 或 "装饰器保留被装饰函数的签名" 时，事情会迅速变得抽象。这里需要的不是放弃，而是知道哪些武器可用 — 这正是后续章节要回答的。

Heuristic · 经验法则
"项目越大、团队越大、代码越长寿，类型注解的回报越高。" — 二十行的脚本不必注解。两万行、五个人维护、要上线五年的服务，几乎一定要注解。中间地带，凭经验。
类型不是束缚 — 它是把"我以为它是什么"
变成"它就是什么"的契约。

Chapter II · 第二章 Mental Model

核心概念
与 心智模型

在写下第一个 TypeVar 之前，先在脑中放好几张正确的图：注解是什么、谁在读它、它如何在 Python 这门语言的现有结构里安身。

把类型注解放进 Python 这门动态语言，PEP 484 的作者们走的是一条非常克制的路线 — 他们没有发明一门新语言，也没有要求运行时合作。注解只是 语法上 被解析、被存进 __annotations__ 字典；剩下的全交给外部工具。要熟练使用这套系统，先把几个心智模型搭起来。

§ 2.1四个角色，一份契约

注解一旦写下，就有四个不同的角色会读它，每一个都看到了同一份代码的不同切片：

  • 开发者（你和你的同事）：把注解当文档读，理解函数期待什么、返回什么。这是注解最古老、也最重要的用途。
  • 静态检查器（mypy / pyright / pyre）：把整份代码当作一张类型图，验证每一处调用的形状是否对得上签名。
  • 编辑器与 IDE（VS Code、PyCharm）：基于 pyright 或自带的引擎，在你打字的瞬间提供补全、跳转、悬浮文档、重命名。
  • 运行时（dataclass、pydantic、FastAPI、typer）：通过 typing.get_type_hints() 反射读取注解，把它们当作业务规则用 — 比如自动校验 HTTP 请求体。

同一份注解服务于这四个角色，是 Python 类型系统在工程上最有杠杆的地方。一处书写，多处受益。

§ 2.2注解的语法位置

语法上，类型注解能出现在这几个位置 — 没有第五个：

where_to_annotate.pyPython
# 1. 函数参数与返回值（最常见）
def add(x: int, y: int) -> int:
    return x + y

# 2. 变量注解（PEP 526）
count: int = 0
names: list[str] = []
result: str  # 声明但暂不赋值，合法

# 3. 类属性
class User:
    name: str           # 实例属性的类型声明
    age: int = 0       # 带默认值
    visits: ClassVar[int] = 0  # 类级（详见第 8 章）

# 4. 类型别名（type alias）
type UserId = int      # Python 3.12+
JsonDict: TypeAlias = dict[str, Any]  # 旧式

注意：你 不能 在表达式中间写注解。(x: int) + 1 是语法错误。注解只属于绑定（binding）位置 — 形参、变量赋值左侧、类体顶层。

§ 2.3类型对象与值对象

这是新人最容易卡壳的地方。int 既是一个类（继承自 type 的对象），也可以作为类型注解使用。Python 没有为类型设立单独的命名空间 — 它们就是普通的对象，只是在注解位置被特殊解释。

type_vs_value.pyPython
x: int = 42          # int 在这里是"类型"
cls = int            # int 在这里是"值"，被赋给 cls
print(cls("3"))     # 调用 int 类，输出 3

# 因此你可以这样：
def make(cls: type[int]) -> int:
    return cls(0)

make(int)             # OK，传入"类型对象"本身

把这一点想清楚后，type[X]、Type[X]、Callable[..., X] 之类构造就不再玄乎 — 它们只是在注解位置告诉检查器："这里期待的是一个类对象，能被调用并返回 X。"

§ 2.4前向引用与字符串注解

注解默认是 立即求值 的 — 当 Python 解析函数定义时，注解里的名字会被立刻查找。这带来一个经典问题：

forward_ref_problem.pyPython
class Tree:
    def add_child(self, child: Tree) -> None:  # NameError!
        ...                                  # Tree 此时还没定义完

解决方案有两种。第一种是把注解写成字符串（"前向引用"）：

forward_ref_string.pyPython
class Tree:
    def add_child(self, child: "Tree") -> None:
        ...

第二种、也是现代实践推荐的，是在文件顶部写：

future_annotations.pyPython
from __future__ import annotations  # 文件顶部

class Tree:
    def add_child(self, child: Tree) -> None:
        ...                                  # 不再立即求值，问题消失

这个 future 导入让 整个文件 的注解都变成字符串保存（PEP 563）— 解析器只在你显式调用 typing.get_type_hints() 时才解析它们。代价是：依赖运行时反射注解的库（如 pydantic v1）会受影响，要小心兼容性。

PEP Status · 标准状态
PEP 563 曾计划在 Python 3.10 成为默认，但被推迟。PEP 649（lazy annotations）已被接受并在 Python 3.14（2025 年 10 月）取代 PEP 563 — 它兼顾了 "无需立即求值" 与 "运行时仍能读到真实类型" 两个目标。当下最稳妥的做法仍是写 from __future__ import annotations，并在需要反射注解时用 typing.get_type_hints()。

§ 2.5类型 vs 注解 vs 提示 — 词汇澄清

社区常常混用这几个词，但它们其实指不同的东西：

术语含义例
类型 (type)一组值的集合及它们支持的操作int、list[str]、User | None
注解 (annotation)语法上写在 : 或 -> 后的表达式def f(x: int) -> str: 中的 int 与 str
类型提示 (type hint)用作类型语义的注解；与"注解"几乎同义但侧重静态语义同上
类型系统 (type system)一组规则，定义类型间如何兼容"X 是 Y 的子类型 ⇔ ..."
检查器 (checker)实现类型系统的工具mypy、pyright、pyre

记住一个简单的对应：注解是你写下的 文本；类型是这段文本所指向的 语义；检查器是把文本翻译成语义、并在调用点上验证一致性的 程序。

Python 没有类型系统 — 它有
注解，外加一个用注解工作的工具生态。

Chapter III · 第三章 Built-ins & Containers

基础类型
与 容器

从 int、str 这些最朴素的内建类型开始，到 list[T]、dict[K, V] 这些参数化容器，再到 Callable 与 Tuple — 这一章是你日后写所有注解的字母表。

类型系统的字母表，是那些你在每一行 Python 都会用到的内建类型。它们看起来朴实无华，但要把它们的注解形式写对、用得地道，需要弄清几条不那么明显的规则 — 尤其是 PEP 585 之后，List 和 list 的关系发生了根本变化。

§ 3.1原始类型清单

下面这张表是一切的起点。所有这些都直接作为类型注解使用，无需 import：

类型含义示例值
int任意精度整数0, -1, 10**100
float双精度浮点3.14, 1e-9
complex复数1+2j
bool布尔，是 int 的子类True, False
str不可变 Unicode 字符串"hello"
bytes不可变字节序列b"\\x00\\x01"
bytearray可变字节序列bytearray(b"...")
None"无值"，类型也写作 NoneNone
Trap · 陷阱
bool 是 int 的子类 — 这意味着接受 int 的函数也接受 True 和 False，且检查器不会报错。这通常是设计意图，但偶尔会让你写出 list[bool] 却被无声地接受为 list[int] 的位置。

§ 3.2容器：PEP 585 之后

历史上你需要写 List[int]、Dict[str, User]，并从 typing 模块导入。Python 3.9 (PEP 585) 之后，所有内建容器自身就支持下标索引，typing.List 等成为遗留写法：

Legacy · 遗留
from typing import List, Dict, Set, Tuple

names: List[str] = []
ages: Dict[str, int] = {}
flags: Set[str] = set()
point: Tuple[int, int] = (0, 0)
Modern · 现代
// Python 3.9+

names: list[str] = []
ages: dict[str, int] = {}
flags: set[str] = set()
point: tuple[int, int] = (0, 0)

新代码一律使用小写的内建形式。typing 模块里的大写版本只为了向后兼容存在 — 它们 PEP 585 之后被标记为 deprecated，但目前不会移除。

§ 3.3Tuple — 两种截然不同的形式

Tuple 与其他容器有一个关键差异：它的注解可以表达两种不同的结构。

tuple_forms.pyPython
# 形式 1：定长、异质 — 把 tuple 当成"轻量级 record"
point: tuple[int, int] = (3, 4)
record: tuple[str, int, bool] = ("alice", 30, True)

# 形式 2：变长、同质 — 用省略号表示
ints: tuple[int, ...] = (1, 2, 3, 4)  # 任意多个 int

# 空 tuple 的类型
empty: tuple[()] = ()

这两种形式的语义完全不同：tuple[int, int] 的元素永远恰好是两个 int；tuple[int, ...] 是任意长度的纯 int 序列。前者用于固定结构（点、坐标、版本号），后者用于"我就想要个不可变 list"。

§ 3.4Callable — 函数的类型

函数也是值。要给它们写类型，用 Callable：

callable_types.pyPython
from collections.abc import Callable

# Callable[[ArgType, ...], ReturnType]
cb: Callable[[int, int], int] = lambda a, b: a + b

# 接受任意参数
handler: Callable[..., None]

# 高阶函数
def apply(f: Callable[[int], int], x: int) -> int:
    return f(x)

apply(lambda n: n * 2, 5)  # 10
Import Source · 导入位置
推荐从 collections.abc 导入 Callable、Iterable、Iterator、Mapping、Sequence 等抽象基类，而不是从 typing。后者在 Python 3.9 之后是同一对象的别名，前者更"原生"。

§ 3.5Iterable / Iterator / Sequence / Mapping

实际工程里，函数参数应该尽量用最 宽松 的容器类型 — 这是 Python 类型系统中最重要的一条经验法则之一。它让你的函数能接受更多种调用方。

类型能力典型使用场景
Iterable[T]能 for x in函数 参数 — 接受最宽
Iterator[T]有 __next__消费一次的流
Sequence[T]能索引、有 len需要随机访问但不修改
Mapping[K, V]只读字典视图函数参数（替代 dict）
MutableMapping[K, V]可写字典视图需要修改时
list[T] / dict[K, V]具体类函数 返回值 — 给出最具体的

口诀：参数宽松，返回具体。下面这两个签名都合法，但右边的能服务更多调用方：

Too Narrow · 过窄
def total(nums: list[int]) -> int:
    return sum(nums)

# 不接受 tuple、生成器、set
total((1, 2, 3))  # ✗ checker 报错
Just Right · 恰当
def total(nums: Iterable[int]) -> int:
    return sum(nums)

# 三种调用都被接受
total([1, 2])
total((1, 2, 3))
total(x for x in data)

§ 3.6Any 与 object 的区别

新人常把 Any 和 object 混为一谈，但它们对类型检查器是完全不同的两个概念：

  • object 是所有类的根。x: object 意味着"任何对象都行，但你只能调用 object 上有的方法"（即几乎什么都不能做）。要使用 x 上的具体方法，必须先 isinstance 收窄。
  • Any 是类型检查器的"逃生舱口"。x: Any 意味着"放弃检查"。你可以对 x 做任何事，检查器都不会报错；同时 Any 也兼容任何其他类型，意味着 Any 可以传给期待 int 的位置（这种"传染性"是它最危险的地方）。
Don't · 不要
把 Any 当作"我不想想类型"的捷径用。它会污染所有它流过的代码路径。如果你确实需要"任何对象"，几乎总是 object 更安全；只有在与无类型库交互、或在做反射 / 动态分派时，才用 Any。

Chapter IV · 第四章 Union, Optional, Literal

联合、可选
与 类型收窄

真实世界里，函数的参数和返回值往往不是一种类型。Union 让你描述这种"或"关系，而类型守卫则让检查器在你写下 isinstance 的瞬间，就知道分支里的类型变窄了。

单一类型描述世界的能力是有限的 — 一个解析函数可能返回 整数或字符串，一个查询可能 找到 User 或没找到。Union 类型让你优雅地表达这种"多选一"，而类型收窄（type narrowing）让代码在控制流的每个分支里都拥有具体、可用的类型。

§ 4.1Union 与新语法 X | Y

历史上 Union 写作 Union[X, Y]。Python 3.10 (PEP 604) 引入了 X | Y 语法，新代码一律推荐后者：

union_basics.pyPython
# 老写法（仍可用）
from typing import Union
def parse(s: str) -> Union[int, float]: ...

# 现代写法（推荐）
def parse(s: str) -> int | float: ...

# 多元 Union
def handle(x: int | str | bytes | None) -> str: ...

Union 是 对称且 幂等的：int | str 与 str | int 是同一个类型；int | int 简化为 int。它表达的是数学意义上的并集（disjoint union 的近亲）。

§ 4.2Optional[T] 就是 T | None

代码里最常见的 Union 是与 None 的并集 — 表示"也许没有值"。这有专门的别名 Optional[T]，但现代写法直接写 T | None：

optional.pyPython
def find_user(user_id: int) -> User | None:
    user = db.query(user_id)
    return user  # 可能是 User，也可能是 None

# 调用方现在被强制处理 None 情况
u = find_user(42)
print(u.name)        # ✗ checker：u 可能是 None，不能直接 .name

if u is not None:
    print(u.name)    # ✓ 这个分支里 u 被收窄为 User
Habit · 习惯
不要在签名里既写默认值 = None 又不把类型写成 T | None。def f(x: int = None) 在最严格模式下会被拒绝 — 必须是 def f(x: int | None = None)。这一点 mypy 默认就检查。

§ 4.3Literal — 当值本身就是类型

有时你希望某个参数只接受几个具体的值，而不是整个 str 或整个 int。Literal 让你把"值"提升为"类型"：

literal.pyPython
from typing import Literal

Method = Literal["GET", "POST", "PUT", "DELETE"]

def request(method: Method, url: str) -> Response: ...

request("GET", "/api")        # ✓
request("PATCH", "/api")      # ✗ checker：不是合法字面量

# 也可用于数字、布尔、None、枚举成员
HttpStatus = Literal[200, 301, 404, 500]
Direction = Literal["left", "right"] | Literal["up", "down"]

Literal 在 API 设计里非常顺手 — 它让"魔法字符串"既保留人读时的简单性，又获得编译期的安全检查。配合 IDE 的自动补全，调用方甚至不需要查文档。

§ 4.4类型收窄 — 流敏感分析

当函数参数是 X | Y | Z，函数体内你显然不能对它做仅 X 才支持的操作。类型检查器会跟随控制流，在每个分支里把类型收窄到具体的子集。这套机制叫 flow-sensitive analysis，是现代 Python 类型工具最强大的能力之一。

narrowing.pyPython
def describe(x: int | str | None) -> str:
    if x is None:
        return "nothing"           # 这里 x: None

    if isinstance(x, int):
        return f"number {x + 1}"     # 这里 x: int，可以 + 1

    # 走到这里，x 必然是 str
    return x.upper()                  # 这里 x: str

检查器跟随的"线索"包括：

  • is None / is not None — 把 T | None 切成两半。
  • isinstance(x, T) — 把 Union 切到具体子类。
  • type(x) is T — 类似 isinstance，但要求精确等于（不允许子类）。
  • x in {"a", "b"} — 把 str 收窄到 Literal["a", "b"]。
  • 真值检查：if x: 在某些情况下能去掉空字符串、空容器、None。
  • match 语句的每个 case。
  • 调用 类型守卫函数（TypeGuard / TypeIs，第 9 章）。

§ 4.5match 与穷尽性检查

match 语句（PEP 634，Python 3.10+）配合类型系统能做一件特别有用的事：让检查器在你 漏掉某个分支时报错。这叫 exhaustiveness check：

exhaustive_match.pyPython
from typing import assert_never

Shape = Circle | Square | Triangle

def area(s: Shape) -> float:
    match s:
        case Circle(r):
            return 3.14 * r * r
        case Square(side):
            return side * side
        # 漏掉了 Triangle
        case _:
            assert_never(s)  # ✗ checker：Triangle 还能到达这里

assert_never 接受 Never 类型 — 一个不可能存在值的类型。如果检查器能证明此处类型确实是 Never（即所有可能性都被覆盖），代码合法；否则报错。这让 Union 的扩展（增加一个新成员）能立刻在所有 match 处显形，是大型代码库重构时的护身符。

Union 描述世界，
收窄回到具体 — 这是控制流与类型的对舞。

Chapter V · 第五章 Generics

泛型
与 变型

写一个能同时服务于 list[int]、list[str]、list[User] 的函数 — 这是泛型存在的理由。但要把它写正确，你还需要理解一件事：协变、逆变、不变。

考虑一个最朴素的需求：写一个 first(seq) 函数返回序列的第一个元素。如果用具体类型，你必须给 list[int]、list[str]、list[User] 各写一份。如果用 Any，返回值就失去了类型信息 — 调用方拿到的只是 Any，不知道它能做什么。泛型解决的就是这个问题：把类型本身作为参数，让一个签名同时描述无穷多种具体形状。

§ 5.1TypeVar — 类型变量

TypeVar 是声明"这里有一个未知但确定的类型"的工具：

typevar_basics.pyPython
from typing import TypeVar
from collections.abc import Sequence

T = TypeVar("T")

def first(seq: Sequence[T]) -> T:
    return seq[0]

a: int = first([1, 2, 3])           # ✓ T 被推断为 int
b: str = first(["a", "b"])             # ✓ T 被推断为 str
c: str = first([1, 2])               # ✗ T 是 int，不能赋给 str

关键点是：同一个 T 在签名中出现多次时，必须解析为同一个具体类型。这是泛型的力量来源 — 它让"参数类型与返回类型相关"这种约束被表达出来。

§ 5.2PEP 695：新一代泛型语法

Python 3.12 (2023) 引入了一种更简洁的语法（PEP 695），让你不必显式声明 TypeVar：

Pre-3.12 · 旧式
from typing import TypeVar

T = TypeVar("T")

def first(seq: Sequence[T]) -> T:
    return seq[0]

class Box(Generic[T]):
    def __init__(self, x: T):
        self.x = x
3.12+ · 新式
# 不再需要 import 与显式声明




def first[T](seq: Sequence[T]) -> T:
    return seq[0]

class Box[T]:
    def __init__(self, x: T):
        self.x = x

新语法把 TypeVar 的声明放在了它真正起作用的地方：紧跟在 def 或 class 之后的方括号里。这与 TypeScript、Rust、Swift 的写法一致，也让作用域更清晰。如果你的目标 Python ≥ 3.12，全部用新语法。本册后续示例混合两种写法以照顾兼容性。

§ 5.3泛型类

除了泛型函数，泛型还能用在类上 — 这是写自己容器、栈、缓存、Result 类型时的标准做法：

generic_class.pyPython
class Stack[T]:
    def __init__(self) -> None:
        self._items: list[T] = []

    def push(self, item: T) -> None:
        self._items.append(item)

    def pop(self) -> T:
        return self._items.pop()

    def peek(self) -> T | None:
        return self._items[-1] if self._items else None

stack: Stack[int] = Stack()
stack.push(1)
stack.push("hi")         # ✗ checker：T 已是 int
n: int = stack.pop()  # ✓

§ 5.4Bounded 与 Constrained TypeVar

有时你不希望 T 是"任何类型"，而是"任何 X 的子类"。这叫 bounded TypeVar：

bounded.pyPython
class Animal: ...
class Dog(Animal): ...
class Cat(Animal): ...

# 旧语法
A = TypeVar("A", bound=Animal)
def name_of(a: A) -> str: ...

# 新语法 (PEP 695)
def name_of[A: Animal](a: A) -> str: ...

name_of(Dog())   # ✓
name_of("hi")    # ✗ str 不是 Animal 的子类

另一种约束是 constrained — T 只能是几种具体类型之一（不是子类，是精确等于）：

constrained.pyPython
# 旧语法
S = TypeVar("S", str, bytes)
def strip(x: S) -> S: ...

# 新语法
def strip[S: (str, bytes)](x: S) -> S: ...

strip("  hi ")         # ✓ S = str
strip(b"  hi ")        # ✓ S = bytes
strip(123)             # ✗

bounded 与 constrained 的差异：bounded 接受所有子类（你拿到的可能是 Animal 的任何后代）；constrained 是几个固定选项中的精确一个。日常 90% 用 bounded，constrained 留给字符串/字节这种非继承关系的特殊场景。

§ 5.5变型 — 协变、逆变、不变

这一节是泛型最深、也最容易让人放弃的部分。它的核心问题是：如果 Dog 是 Animal 的子类，那 list[Dog] 是不是 list[Animal] 的子类？

直觉会说"是" — 但这个答案在大多数情况下是错的。考虑：

variance_problem.pyPython
def add_cat(animals: list[Animal]) -> None:
    animals.append(Cat())

dogs: list[Dog] = [Dog()]
add_cat(dogs)              # 如果允许 list[Dog] 当 list[Animal] 用...
dogs[1].bark()             # 💥 这只 Cat 不会 bark

因此 list[T] 是 不变（invariant） 的 — list[Dog] 与 list[Animal] 没有任何子类型关系。这是为了类型安全而做的牺牲。

三种变型的口诀：

变型规则典型例子
协变 (covariant)子类型关系 同向传播：Dog <: Animal ⇒ C[Dog] <: C[Animal]只读容器：tuple, frozenset, Sequence 的输出位置
逆变 (contravariant)子类型关系 反向传播：Dog <: Animal ⇒ C[Animal] <: C[Dog]消费者：Callable 的参数位置
不变 (invariant)子类型关系 不传播可读可写容器：list, dict, set

记忆要点：能写入的位置必须不变或逆变（否则就出现上面 add_cat 的灾难）；只读的位置可以协变。这就是为什么 list 是不变的，而 tuple（不可变）是协变的；为什么 Callable[[Animal], None] 可以当 Callable[[Dog], None] 用（接受更宽的参数总是安全的）。

§ 5.6ParamSpec — 装饰器的福音

装饰器是 Python 类型系统里历史上最难表达的对象之一。问题在于：装饰器接受任何函数、返回某种"包装"，要求保留原函数的全部参数签名。Python 3.10 (PEP 612) 引入的 ParamSpec 解决了这个问题：

paramspec.pyPython
from typing import ParamSpec, TypeVar
from collections.abc import Callable
import functools, time

P = ParamSpec("P")
R = TypeVar("R")

def timed(fn: Callable[P, R]) -> Callable[P, R]:
    @functools.wraps(fn)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        t = time.time()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__}: {time.time() - t:.3f}s")
    return wrapper

@timed
def greet(name: str, *, loud: bool = False) -> str:
    return name.upper() if loud else name

greet("alice", loud=True)   # ✓ 签名完全保留
greet(42)                  # ✗ checker 报错：name 应是 str

P.args 和 P.kwargs 这两个语法只能在 *args, **kwargs 注解里出现 — 它们是把"那个参数序列"完整地传递下去的语法糖。3.12 之后用新语法写就是 def timed[**P, R](fn: Callable[P, R]) -> Callable[P, R]。

§ 5.7TypeVarTuple — 变长泛型

NumPy / TensorFlow 之类库长期渴望表达"形状"的类型（一个 3D 张量与一个 4D 张量类型不同）。Python 3.11 (PEP 646) 的 TypeVarTuple 让这成为可能：

typevartuple.pyPython
class Tensor[*Shape]:                  # PEP 695 + 646
    def __init__(self, shape: tuple[*Shape]):
        self.shape = shape

x: Tensor[int, int] = Tensor((3, 4))      # 2D
y: Tensor[int, int, int] = Tensor((3,4,5))  # 3D

这是当代类型系统中最先进的特性之一。日常业务代码极少需要它，但如果你写数值计算库，它会让 API 安全很多。

Chapter VI · 第六章 Protocols

Protocol
与 结构化子类型

"如果它走起来像鸭子，叫起来像鸭子，那它就是鸭子。" — Python 用了三十年的鸭子类型，终于在 PEP 544 里有了对应的静态语义。

Java 的接口、C# 的接口、Go 的 interface — 它们都靠 名义 子类型工作：你必须显式地写 class MyClass implements MyInterface，编译器才会承认。Python 的传统则与众不同：只要一个对象有 read() 方法，所有期待"file-like"的代码就会接受它，不管它叫什么、继承自谁。这种"形状即身份"的哲学叫 结构化子类型，也就是著名的鸭子类型。

PEP 544 (Python 3.8) 的 Protocol 把这套哲学带进了静态类型系统 — 你可以定义一个"形状"，任何具有那个形状的类（无论是否声明）都自动被视为它的子类型。

§ 6.1名义 vs 结构化子类型

先看两种范式的对比：

名义 (nominal)结构 (structural)
判定标准显式继承或声明实现是否具备所需方法/属性
典型代表Java interface, ABC, dataclass 间的 isinstanceGo interface, TypeScript interface, Python Protocol
耦合度使用方需感知接口使用方与定义方可解耦
第三方类适配需写 wrapper开箱即用

两者在 Python 里并存。class X(SomeABC) 是名义的；class X 加上 Protocol 检查是结构的。

§ 6.2定义一个 Protocol

protocol_basics.pyPython
from typing import Protocol

class Named(Protocol):
    name: str            # 要求一个 name 属性

    def greet(self) -> str: ...

# User 没有 inherit Named，但形状对得上
class User:
    def __init__(self, name: str) -> None:
        self.name = name
    def greet(self) -> str:
        return f"Hi, I'm {self.name}"

def welcome(person: Named) -> None:
    print(person.greet())

welcome(User("Alice"))    # ✓ User 满足 Named 的形状

注意 User 没有继承 Named — 它只是恰好有同样的属性和方法。检查器在调用 welcome(User("Alice")) 时验证形状匹配，编译通过。这与 Go 的 interface 完全一致。

§ 6.3runtime_checkable

默认情况下，Protocol 只用于 静态检查 — isinstance(x, MyProtocol) 在运行时会抛 TypeError。如果你确实需要运行时也能检查，加 @runtime_checkable：

runtime_protocol.pyPython
from typing import Protocol, runtime_checkable

@runtime_checkable
class Closeable(Protocol):
    def close(self) -> None: ...

def close_if_can(obj: object) -> None:
    if isinstance(obj, Closeable):
        obj.close()
Caveat · 警告
@runtime_checkable 只验证 方法名是否存在，不验证签名是否匹配。isinstance(x, Named) 看到 x 有 greet 这个名字就通过 — 即便 x.greet 是个不接受任何参数的属性而非方法。运行时检查永远是名字级别的，要细致的形状检查只能靠静态检查器。

§ 6.4Protocol vs ABC — 该用哪个

这两个工具都能定义"接口"，但侧重点不同：

  • 用 ABC 当你 拥有 所有实现，且想强制它们承认这层关系。例如内部领域模型的层级。
  • 用 Protocol 当你 不拥有 实现 — 比如你想接受第三方库的对象、内置类型、或调用方提供的 duck-typed 类。也用于解耦两个模块（依赖于形状而非名字）。
  • 遗留代码用 ABC 就保持 ABC；新代码若没有强烈的"继承图"需求，倾向 Protocol。

§ 6.5常见的内置 Protocol

标准库里 collections.abc 模块的所有抽象基类，从 Python 3.12 起都被注册为 Protocol（同时仍是 ABC）。这意味着：

builtin_protocols.pyPython
from collections.abc import Iterable, Sized, Hashable

# 你写的类不需要 inherit Iterable，
# 只要有 __iter__ 就被检查器视作 Iterable
class Range:
    def __init__(self, n: int):
        self.n = n
    def __iter__(self):
        yield from range(self.n)

def to_list(it: Iterable[int]) -> list[int]:
    return [x for x in it]

to_list(Range(5))  # ✓
Protocol 是给 Python 的鸭子
颁发的"形状护照" — 没有继承的负担，却有了静态保障。

Chapter VII · 第七章 Structured Data

数据类、TypedDict
与 NamedTuple

真实代码处理的，绝大多数是结构化数据。Python 给了你四种描述"一组带类型字段"的工具 — 它们分别擅长不同的场景，知道何时用哪个，是工程能力的一部分。

把一份 JSON 配置塞进 dict，把一个用户记录拆成几个独立变量，把一个返回多个值的函数硬塞进 tuple — 这些做法 Python 都允许，但都让代码失去类型可读性。当数据有"形状"时，最好把这个形状显式写出来。Python 给了你四种工具：dataclass、TypedDict、NamedTuple，加上第三方的 pydantic。它们看似相近，实则各有用武之地。

§ 7.1dataclass — 类的轻量化

dataclasses 是 PEP 557 (Python 3.7) 给"数据类"提供的官方语法糖。它读取你的注解，自动生成 __init__、__repr__、__eq__：

dataclass_basics.pyPython
from dataclasses import dataclass, field

@dataclass
class User:
    name: str
    age: int
    email: str | None = None
    tags: list[str] = field(default_factory=list)

u = User(name="alice", age=30)
print(u)               # User(name='alice', age=30, email=None, tags=[])
u.email = "a@x.com"     # 默认可变

常用的 @dataclass 装饰器选项：

选项作用
frozen=True实例不可变；得到 __hash__，可作为 dict key
slots=True启用 __slots__，省内存、禁止动态加属性 (3.10+)
kw_only=True所有字段必须以关键字传入，避免位置参数歧义 (3.10+)
order=True生成 __lt__ 等比较方法

务实建议：新代码默认写 @dataclass(frozen=True, slots=True, kw_only=True) — 不可变、省内存、清晰的构造调用。可变性留给真正需要的字段。

§ 7.2TypedDict — 给 dict 加上骨架

很多时候你拿到的 就是 一个 dict — 来自 JSON、来自 HTTP body、来自配置文件。你不希望把它转成对象，但你想让检查器知道它的键是什么、对应什么类型。这就是 TypedDict (PEP 589)：

typeddict.pyPython
from typing import TypedDict, NotRequired, Required

class UserDict(TypedDict):
    name: str
    age: int
    email: NotRequired[str]   # 可选键 (3.11+)

def save(u: UserDict) -> None:
    db.insert(u["name"], u["age"])

save({"name": "alice", "age": 30})           # ✓
save({"name": "alice"})                   # ✗ 缺 age
save({"name": "alice", "age": "thirty"})      # ✗ age 类型错
Runtime · 运行时
TypedDict 在运行时 就是普通的 dict — 它没有 schema 验证，没有强制结构，只是给检查器提供形状信息。这与 dataclass 创建一个真正的类不同。如果你需要运行时验证，用 pydantic。

另外两种语法形式：

typeddict_alt.pyPython
# 函数式语法（动态键名）
Config = TypedDict("Config", {"db-host": str, "db-port": int})

# total=False：所有键都是可选的
class Patch(TypedDict, total=False):
    name: str
    age: int
    # 全部 NotRequired，适合 PATCH 请求

§ 7.3NamedTuple — 类型化的元组

当你需要一个 不可变、可索引、带字段名 的小记录时，NamedTuple 是最轻量的选择：

namedtuple.pyPython
from typing import NamedTuple

class Point(NamedTuple):
    x: float
    y: float

p = Point(1.0, 2.0)
print(p.x, p[0])    # 同一个值，两种访问
x, y = p             # 解包仍工作

# 不可变：
p.x = 3.0            # ✗ AttributeError

NamedTuple 的杀手锏是 它仍然是 tuple — 所有期待 tuple 的代码（解包、模式匹配、序列化）都能直接消费它。代价是它无法新增方法（实际可以，但通常不该这么做）、不支持默认值的灵活组合、字段不可变。

Chapter VIII · 第八章 Advanced Features

高级特性
速览

Self、Final、ClassVar、NewType、TypeAlias、Annotated、@overload — 这些是类型系统的"高阶器械"。每一个解决一类小而精的问题，把它们放进工具箱，会让你的注解能力跃升一档。

这一章是工具的展览。每件工具都不大，但缺了它们某一类问题就只能用 Any 凑合 — 而 Any 是类型系统里最锋利的钝刀。把它们一个个学会，看到合适场景就抽出来用。

§ 8.1Self — 让方法返回"自身类型"

建造者模式最让人头疼的地方是它的链式调用：每个方法都 return self，但子类继承后类型该如何标注？Python 3.11 (PEP 673) 的 Self 直接解决：

self_type.pyPython
from typing import Self

class Builder:
    def step(self) -> Self:
        return self

class SqlBuilder(Builder):
    def where(self, cond: str) -> Self:
        return self

q = SqlBuilder().step()  # 返回类型是 SqlBuilder，不是 Builder！
q.where("id=1")         # ✓ 链式仍然能调到子类方法

没有 Self 时，你必须手动写 TypeVar 来表达这层关系，繁琐而易错。Self 让最常见的"返回自身类型"成为单字注解。

§ 8.2Final — 一次性绑定

Final 标记某个变量或属性"绑定一次后不应再改"：

final.pyPython
from typing import Final

MAX_RETRIES: Final = 3          # 不允许再赋值
DB_HOST: Final[str] = "localhost"  # 也可显式带类型

MAX_RETRIES = 5                  # ✗ checker 报错

# 在类中：标记不应被子类覆盖的方法
class Logger:
    @final
    def close(self) -> None: ...

Final 是纯静态约束，运行时不会阻止赋值 — 但检查器会拦下。它最有用的位置是模块级常量与不允许覆写的方法。

§ 8.3ClassVar — 类级而非实例级

类体内的注解默认描述 实例属性。如果你想表达"这是属于类的状态"，用 ClassVar：

classvar.pyPython
from typing import ClassVar

class Counter:
    instances: ClassVar[int] = 0   # 类共享
    name: str                       # 实例独有

    def __init__(self, name: str) -> None:
        self.name = name
        Counter.instances += 1

@dataclass 看到 ClassVar 时不会把它当成字段处理 — 这是它在 dataclass 体内最常见的用途。

§ 8.4NewType — 强类型化的别名

"用户 ID" 和 "订单 ID" 在运行时都是 int，但你绝不希望把一个传到期待另一个的位置。NewType 让你创建零运行时开销的"语义类型"：

newtype.pyPython
from typing import NewType

UserId = NewType("UserId", int)
OrderId = NewType("OrderId", int)

def cancel_order(oid: OrderId) -> None: ...

uid = UserId(42)
oid = OrderId(99)

cancel_order(oid)        # ✓
cancel_order(uid)        # ✗ checker：UserId ≠ OrderId
cancel_order(99)         # ✗ 裸 int 也不接受

运行时 UserId(42) 等价于 int(42)，几乎没有开销。但在静态层面，UserId 与 int 是不同的类型，相互不可替代。这是减少 ID 混淆类 bug 的最简方案。

§ 8.5类型别名 — 三代写法

给复杂的类型起个名字让代码更可读。Python 的别名语法演化了三代：

type_aliases.pyPython
# 第一代：纯赋值（仍可用，但检查器只能"猜"它是别名）
JsonDict = dict[str, Any]

# 第二代：显式 TypeAlias（PEP 613, 3.10+）
from typing import TypeAlias
JsonDict: TypeAlias = dict[str, Any]

# 第三代：type 语句（PEP 695, 3.12+）— 推荐
type JsonDict = dict[str, Any]
type Result[T] = T | Exception     # 还能带泛型参数

新代码若目标是 3.12+，全部用 type 语句 — 它在语法上最清晰，并且支持 惰性求值（避免循环引用问题）。

§ 8.6Annotated — 给类型挂上元数据

Annotated[T, metadata] 在保留 T 作为类型的同时，附带任意运行时可读的元数据。它是 FastAPI、pydantic v2、typer 等现代库的核心机制：

annotated.pyPython
from typing import Annotated
from dataclasses import dataclass

# 类型仍是 int，但带上"必须 > 0"的元数据
@dataclass
class Order:
    quantity: Annotated[int, "must be positive"]

# FastAPI 风格
from fastapi import Query

def search(q: Annotated[str, Query(min_length=3)]):
    ...

对静态检查器来说，Annotated[int, anything] 就是 int；元数据被忽略。但运行时反射能拿到那段元数据，这是它能"双重身份"工作的原理。

§ 8.7@overload — 多签名同名函数

有些函数的输出类型 取决于 输入类型：传 int 回 int，传 str 回 str。Union 表达不出这种相关性，但 @overload 可以：

overload.pyPython
from typing import overload

@overload
def double(x: int) -> int: ...
@overload
def double(x: str) -> str: ...

def double(x):                  # 真正的实现
    return x * 2

a: int = double(5)         # ✓ 检查器知道是 int
b: str = double("hi")      # ✓ 检查器知道是 str
c = double(3.14)            # ✗ 没有匹配的 overload

规则：@overload 装饰的函数体永远是 ...，它们只是给检查器看的"签名清单"；最后必须有一个真实实现（不带 @overload），它的签名要兼容所有 overload。运行时只调用最后一个真实实现 — overload 本身不会被执行。

When · 何时使用
@overload 不便宜 — 三五条以上的 overload 会让 API 变得令人却步。如果你发现一个函数有 8 条 overload，先问问自己是不是该拆成多个函数。它最适合两到三条规则的场景，比如 get(key) vs get(key, default) 这种。

Chapter IX · 第九章 Type Guards

类型守卫
与 流分析

第四章我们见过 isinstance 收窄。但现实代码里有大量"判断"无法用 isinstance 表达 — 比如"这个 dict 是不是合法的 UserDict"。TypeGuard 与 TypeIs 让你把任意判断函数升级为类型收窄器。

类型收窄的核心，是检查器跟着控制流走、在每个分支里推断出更具体的类型。isinstance 是最常用的触发器，但它只能检查"是不是某个类的实例"。当你想检查更复杂的形状 — 一个列表是不是全是 int，一个 dict 是不是符合某个 TypedDict — 你需要写一个 判定函数，并把它的返回值升级为类型谓词。这就是 TypeGuard 与 TypeIs 的工作。

§ 9.1问题陈述：自定义判定函数

看一段直觉但错误的代码：

naive_predicate.pyPython
def all_ints(xs: list[object]) -> bool:
    return all(isinstance(x, int) for x in xs)

def total(xs: list[object]) -> int:
    if all_ints(xs):
        return sum(xs)   # ✗ checker：xs 仍是 list[object]，sum 不行
    return 0

问题在于：从检查器的视角看，all_ints 只是"返回 bool"。它返回 True 时 xs 的类型不会被收窄。TypeGuard 让我们把这层语义告诉检查器。

§ 9.2TypeGuard — 单向收窄

typeguard.pyPython
from typing import TypeGuard

def all_ints(xs: list[object]) -> TypeGuard[list[int]]:
    return all(isinstance(x, int) for x in xs)

def total(xs: list[object]) -> int:
    if all_ints(xs):
        return sum(xs)   # ✓ 此分支 xs: list[int]
    return 0

TypeGuard[T] 在运行时就是 bool；在静态层面则告诉检查器："如果这个函数返回 True，第一个参数（或被检查的表达式）的类型可以被假定为 T。"

注意 "单向"：TypeGuard 只在 True 分支收窄。False 分支里 xs 仍然是原来的类型 — 因为返回 False 不一定意味着不是 T，可能函数本身判断逻辑就有 bug。这是 PEP 647 (3.10) 的设计。

§ 9.3TypeIs — PEP 742 的双向版本

Python 3.13 (2024) 引入了 TypeIs，它是 TypeGuard 的更强版本：当判定函数符合 "返回 True 当且仅当类型为 T" 时，使用 TypeIs 让检查器同时利用两个分支：

typeis.pyPython
from typing import TypeIs

def is_str(x: object) -> TypeIs[str]:
    return isinstance(x, str)

def handle(x: int | str) -> None:
    if is_str(x):
        print(x.upper())  # ✓ x: str
    else:
        print(x + 1)      # ✓ x: int  ← TypeIs 也收窄了 else 分支！

选择规则：

  • 判定函数 "T 的子集"（返回 True 时一定是 T，但 False 不保证不是 T 的某种相关形式）→ TypeGuard。
  • 判定函数是 "完全等价"（返回 True ⇔ 类型是 T）→ TypeIs。

实务中绝大多数自定义判定都是 "完全等价"（你写 isinstance 链），用 TypeIs 几乎总是更好。TypeGuard 留给那些 "判断了一个相关但不等价的形状" 的特殊场景。

§ 9.4match 语句的类型收窄

match 不仅做模式匹配，它的每个 case 都会让被匹配的变量在分支内被收窄到具体形状：

match_narrowing.pyPython
def describe(x: int | str | list[int] | None) -> str:
    match x:
        case None:
            return "empty"
        case int() as n:
            return f"int {n + 1}"           # n: int
        case str() as s if s.startswith("_"):
            return "private name"           # s: str
        case [first, *rest]:
            return f"list of {len(rest)+1}"   # first/rest: int
        case _:
            return "unknown"

§ 9.5assert 与 cast — 最后的逃生路

有些时候你比检查器更了解情况 — 也许是动态加载、也许是某个第三方库的注解不全。这时有两个工具：

assert_cast.pyPython
from typing import cast

# 1. assert：运行时 + 静态都收窄
def unwrap(x: int | None) -> int:
    assert x is not None     # 运行时检查 + 类型收窄
    return x                  # ✓ x: int

# 2. cast：仅静态收窄，无运行时检查
def load_user(data: Any) -> User:
    return cast(User, data)  # 信任你 — 不验证

cast 是纯静态的：它什么都不做，只是告诉检查器"把这个表达式当作 T 看"。它本质上是一个标注的强制类型转换，运行时零成本。滥用 cast 等于关掉类型检查 — 用它的时候要确信你掌握了检查器看不到的信息。

Don't · 慎用
把 assert isinstance(x, T) 当作 cast 用 — 在 Python 用 -O 标志运行时（生产环境常见），assert 整句被剥离。要做运行时检查，写显式的 if not isinstance(...): raise TypeError(...)。
检查器跟着你的代码走 —
类型守卫，是你给它递的一张张地图。

Chapter X · 第十章 Tooling & Practice

工具链
与 实战策略

写注解只是开始。把它们交给一个检查器、把检查器塞进 CI、为既有代码库制定渐进式策略 — 这是让类型系统真正发挥作用的工程动作。

前面九章描述了 Python 类型系统能 表达 什么。但表达本身只解决一半问题 — 另一半是 谁来检查、什么时候检查、如何把它平滑地引入既有代码。这一章是工程层面的指南：工具的选择，CI 的接入，遗留代码的策略，以及那些最常见、最让人困惑的陷阱。

§ 10.1两位主角：mypy 与 pyright

Python 静态检查领域有两位事实上的主角：

mypypyright
开发方Python 软件基金会Microsoft
语言Python 自身TypeScript
速度较慢，但有缓存非常快，增量分析
编辑器集成需配合插件Pylance（VS Code）即基于它
严格度历史上较宽松，可逐项收紧默认就较严
PEP 兼容参考实现参考实现

务实策略：在 IDE 里靠 pyright（通过 Pylance）实时反馈；在 CI 里跑 mypy 作为门禁。两者偶尔在边缘案例上行为不一致 — 通常是 mypy 更宽容，pyright 更严格。修代码以 mypy 通过为准，pyright 的红线作为参考。

§ 10.2mypy 配置：从宽松到严格

mypy 的默认配置非常宽松 — 这是为了不让旧代码库立即满屏报错。但宽松也意味着大量 bug 漏过。健康的策略是把它逐步收紧：

pyproject.tomlTOML
[tool.mypy]
python_version = "3.12"

# Stage 1：基础
warn_return_any = true
warn_unused_configs = true
warn_redundant_casts = true
warn_unused_ignores = true

# Stage 2：处理 None
strict_optional = true
no_implicit_optional = true

# Stage 3：禁止 Any 渗透
disallow_any_generics = true
disallow_subclassing_any = true
warn_no_return = true

# Stage 4：要求所有函数被注解
disallow_untyped_defs = true
disallow_incomplete_defs = true

# 终极：开 strict（包含上面所有）
strict = true

对新代码库直接开 strict = true，让所有问题在第一天就被发现。对老代码库，逐 stage 推进，每升级一档解决一波问题再继续。

§ 10.3渐进式类型化策略

把一个十万行无注解代码库变成全注解，靠"我有空就写一点"的策略基本不会成功 — 因为类型注解的价值是 系统性 的。一两个文件被注解、其他都是 Any，注解就被 Any 污染回去。务实路径如下：

  1. 从边界开始：先注解所有 对外暴露 的接口 — 公共 API、HTTP 路由、消息处理器、CLI 入口。这些位置最容易因类型错误造成生产事故。
  2. 按模块整体推进：完成一个模块就在 mypy 配置里把它列入严格白名单，之后不允许 Any 污染回来。
  3. 使用 monkeytype / pyannotate：让工具运行你的测试套件，记录实际类型，再把记录写回源码。这是最快的"撒种"方式。
  4. 第三方库的 stubs：缺类型的库通过 types-xxx 包补全，或写自己的 .pyi 文件放在 stubs/ 目录。
  5. 把检查放进 CI 门禁：再多注解也抵不过下次合并时被一行 Any 戳破。

§ 10.4.pyi 文件 — 类型存根

有时你不想 / 不能改源码（第三方库、C 扩展、性能敏感模块），但又想给它加注解。.pyi 文件存的就是 "纯注解"：

fastlib.pyiPython Stub
# 这个文件只在静态检查时被读，运行时被忽略
from typing import overload

@overload
def parse(s: str) -> int: ...
@overload
def parse(s: bytes) -> int: ...

class Connection:
    host: str
    port: int
    def close(self) -> None: ...

函数体一律是 ... — stub 只描述形状，不含逻辑。检查器优先读 fastlib.pyi，找不到才回退到 fastlib.py。Python 标准库的所有类型信息都来自 typeshed 仓库的 .pyi 文件。

§ 10.5常见陷阱清单

以下是我（与你）在生产代码里反复犯过的错。把它们记住，能让你省下大量调试时间：

  • 可变默认值 + 注解：def f(x: list[int] = []) — 注解对了，但默认列表在所有调用间共享。永远用 None 配合 if x is None: x = []。
  • list 写成 List 的旧代码：仍然合法但被弃用；用工具 pyupgrade 自动迁移。
  • 把 Optional[X] 当 "可以省略"：Optional 仅意味着 "可以是 None"，不意味着 "可以传也可以不传"。后者要靠默认值。
  • 过早泛化：还没有第二个使用场景就抽象出 TypeVar — 通常会变得难以阅读。先具体，再泛化。
  • 用 isinstance 检查 Protocol 而忘了 @runtime_checkable：直接 TypeError，没有缓冲。
  • 注解和文档脱节：注解告诉 "类型是什么"，docstring 解释 "意义是什么"。两者都要写。
  • 过度依赖 cast：每一个 cast 都是绕过检查器。用它前问自己，能不能用 isinstance 或 TypeIs 替代？

§ 10.6风格小结：六条最重要的经验

  1. 参数宽，返回窄：函数参数用 Iterable、Mapping、Sequence；返回值给具体的 list、dict。
  2. 不要害怕 None，要惧怕 Any：T | None 强制调用方处理；Any 让一切检查作废。
  3. 新代码用现代语法：list[int] 而非 List[int]；X | Y 而非 Union[X, Y]；def f[T]() 而非 TypeVar('T')。
  4. 边界处用 pydantic / dataclass，内部用 dataclass / NamedTuple。
  5. 能用 Protocol 就别用 ABC，除非你确实拥有继承图。
  6. 把检查器放进 CI — 没有强制执行的注解会快速腐烂。
类型不是一种约束，
是一种约定 — 它让你和未来的自己
有一份可以兑现的契约。

本册写到此为止。Python 的类型系统已经是一座完整的工程城邦 — 它有自己的语法、自己的工具、自己的演化节奏（每个 Python 版本都有 PEP 在丰富它）。但你不必一次掌握所有 — 把这本读本当作地图，按图索骥，把每一处工具用到了真实的项目里。下一次当你看到生产环境的 NoneType 报错时，记得问自己：能不能让这个 bug 在编辑器的红线里就显形？
