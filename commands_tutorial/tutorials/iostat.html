1. iostat 是什么

iostat 属于 sysstat 套件，用来报告 CPU 摘要和块设备 I/O 统计。日常排障时最常用的是扩展设备模式：iostat -xz 1。它读取内核块层累计计数器，按两次采样之间的差值计算每秒请求数、吞吐、平均等待、平均队列和设备忙碌比例。

它擅长什么
快速判断某块盘、云盘、LVM/dm 设备、RAID、NVMe 命名空间是否出现吞吐、延迟或队列异常。
它不擅长什么
不能直接告诉你哪个 Python worker、哪个文件、哪个 SQL 查询或哪个数据样本造成了 I/O。
它的定位
设备级实时观测入口：先看设备是否异常，再用进程级、文件级和存储侧工具下钻。
# 最常用：扩展字段、隐藏空闲设备、每秒刷新
iostat -xz 1

# 采样 30 秒并保存证据
iostat -xz 1 30 | tee iostat.$(date +%Y%m%d-%H%M%S).log

# 显示设备分区；某些发行版支持 -p ALL
iostat -xzp 1
iostat -x -p ALL 1 10
边界提醒： iostat 是设备视角，不是进程视角。看到 nvme0n1 的 await 高，只说明块设备路径慢；责任可能在 dataloader、文件系统、页缓存、RAID、云盘限流、网络存储或另一个租户。

2. AI Infra 为什么需要 iostat

AI 训练和推理的卡顿经常被表述为“GPU 利用率低”或“step time 变长”，但 GPU 可能只是在等待输入数据、权重加载、checkpoint 写入、远端存储或容器镜像层。iostat 把这些主机侧 I/O 问题转化成可观察的设备指标。

AI 场景iostat 重点典型解释
训练吞吐周期性下降r/s、rkB/s、await、aqu-szdataloader 读数据跟不上，可能是小文件随机读、冷页缓存、压缩解码前置或共享存储抖动。
保存 checkpoint 卡住w/s、wkB/s、w_await、%util写入吞吐达到上限、后台刷脏页、对象存储 FUSE 或网络盘写确认慢。
多租户节点互相影响多设备 await 同时升高共享宿主机、共享 SAN/NFS、云盘 burst credit 或同 RAID 组争用。
GPU 全部低利用但 CPU 空闲await 高、aqu-sz 高、rkB/s 不高不是 CPU 算不动，而是 I/O 延迟高或请求模式太碎。
AI Infra 心法： iostat 不直接解释模型性能，它解释“存储路径是否把 GPU 喂饱”。

4. 安装、版本与权限

iostat 来自 sysstat。普通用户通常可以运行它，因为它读取的是内核公开统计；但容器镜像可能没有安装，或者看到的是宿主机设备名而不是业务熟悉的挂载路径。

系统安装命令说明
Ubuntu / Debiansudo apt-get update && sudo apt-get install -y sysstat安装后即可使用 iostat；历史 sar 采集是否启用是另一回事。
RHEL / CentOS / Rockysudo dnf install -y sysstat旧系统可能使用 yum install sysstat。
容器/调试镜像apt-get install sysstat 或平台提供 debug image生产应用镜像不一定要内置，临时诊断容器更合适。
# 确认版本；不同 sysstat 版本字段名会有差异
iostat -V

# 找到块设备、挂载点、LVM/dm 关系
lsblk -o NAME,TYPE,SIZE,MODEL,MOUNTPOINT,FSTYPE
findmnt

# 查看内核块设备统计原始入口
cat /proc/diskstats | head
版本注意： 老版本可能显示 avgqu-sz、avgrq-sz、svctm；新版本更常见 aqu-sz、rareq-sz、wareq-sz，并可能不再显示 svctm。教程重点按现代 sysstat 解释，同时说明兼容字段。

5. 快速上手：iostat -xz 1

-x 打开扩展统计，-z 隐藏采样期间无活动的设备，1 表示每秒刷新。这个组合是 AI Infra 现场排障的默认入口。

# 现场观察：每秒刷新，持续到 Ctrl-C
iostat -xz 1

# 记录固定窗口，适合贴到 issue 或事故复盘
iostat -xz 1 60 > /tmp/iostat.train.log

# 和 GPU 利用率、CPU 队列一起采样
ts=$(date +%Y%m%d-%H%M%S)
mkdir -p /tmp/ai-io-debug
iostat -xz 1 120 > /tmp/ai-io-debug/iostat.$ts.log &
vmstat -w 1 120 > /tmp/ai-io-debug/vmstat.$ts.log &
nvidia-smi dmon -s pucvmet -d 1 -c 120 > /tmp/ai-io-debug/gpu.$ts.log &
选项含义为什么常用
-x扩展设备字段没有 await、aqu-sz、%util 很难诊断饱和。
-z隐藏无活动设备AI 节点常有很多 loop、dm、分区；隐藏空闲项减少噪音。
-d只显示设备报告不关心 iostat 自带 CPU 摘要时可用。
-k/-m以 KB/s 或 MB/s 显示吞吐报告给人看时，MB/s 更直观；脚本分析时保持默认也可以。
-p ALL显示所有块设备和分区排查某个挂载点或分区时有用。
现场读法： 先找业务挂载点对应设备，再盯 10 到 60 秒趋势。训练性能问题通常不是单秒尖刺，而是和 step 边界、checkpoint 周期同步的模式。

6. 采样窗口与首行陷阱

不带 -y 时，iostat interval 的第一组报告通常是“自系统启动以来”的平均值，后续才是每个采样间隔的统计。排障实时问题时，不要用首行下结论。

# 首行可能是开机以来平均值，后面才是 1 秒窗口
iostat -xz 1 5

# 如果版本支持 -y，可跳过首份统计，只显示间隔报告
iostat -xzy 1 5

# 对齐训练阶段：先启动采样，再触发一次训练/推理请求
iostat -xzy 1 60 | tee io.window.log
首行
常是系统启动以来平均值，可能把峰值完全抹平，也可能混入旧任务。
后续行
两次采样之间的真实窗口，最适合和 step time、GPU 利用率、日志时间戳对齐。
采样间隔
1 秒适合现场观察；5 到 10 秒适合长期记录；太长会抹掉 batch 边界尖刺。
报告习惯： 给别人发 iostat 证据时，至少保留 20 到 60 行，并说明采样间隔、业务阶段、设备对应的挂载点和是否跳过首行。

rkB/s、wkB/s每秒读/写吞吐判断数据集顺序读、权重加载、checkpoint 写带宽。

%util设备有 I/O 在处理的时间比例单队列设备接近 100% 常提示忙；NVMe/云盘必须结合延迟和吞吐。

8. 吞吐字段：r/s、w/s、rkB/s、wkB/s

r/s 和 w/s 是完成请求数，反映 IOPS；rkB/s 和 wkB/s 是数据量，反映带宽。AI 数据管道可能 IOPS 不高但吞吐很大，也可能吞吐不大但 IOPS 很高且延迟很差。

模式iostat 表现常见 AI 根因
大文件顺序读rkB/s 高、r/s 中等、平均请求较大WebDataset、tar shard、mmap 权重、连续样本读取。
小文件随机读r/s 高、rkB/s 不高、await 容易升高图片小文件、metadata 查询、过多 worker 并发打开文件。
checkpoint 写入wkB/s 周期性冲高、w_await 升高保存模型、optimizer state、日志或 tensorboard 事件。
页缓存命中GPU 低等待但 rkB/s 不高数据已经在内存中，瓶颈可能转向 CPU 解码、增强或 Python 调度。
# 粗略估算平均读请求大小：rkB/s / r/s
# 如果 r/s=1000 且 rkB/s=8000，平均约 8 KB/请求，偏小且容易受延迟影响。

# 查看数据集文件形态
find /data/imagenet/train -type f | head
find /data/imagenet/train -type f -printf '%s\n' 2>/dev/null | awk '{n++; s+=$1} END {print n, s/n/1024 " KiB avg"}'
优化方向： 小文件随机读瓶颈通常优先考虑数据打包、预取、本地缓存、增加页缓存命中率、减少 worker 抢同一个共享存储，而不是单纯把 batch size 调小。

9. 延迟字段：await、r_await、w_await

await 是每个 I/O 请求从进入块层队列到完成的平均时间，通常包含排队时间和设备服务时间。现代 sysstat 常拆成 r_await、w_await，便于区分读慢还是写慢。

现象可能含义下一步
r_await 高，rkB/s 不高随机小读、远端存储延迟、metadata 路径慢、队列并发不足或后端抖动。看数据文件大小、pidstat -d、NFS/对象存储监控、缓存命中。
w_await 高，wkB/s 周期冲高checkpoint、日志、刷脏页、云盘写带宽或 IOPS 限制。错峰 checkpoint、分片写入、用本地 NVMe 缓存、调整保存频率。
await 高且 aqu-sz 高队列堆积，设备或后端已被压住。减少并发、换更高 IOPS/吞吐存储、拆分数据集或本地化。
await 高但 %util 不高可能是稀疏慢请求、网络存储尾延迟、设备映射或采样窗口稀释。延长采样、看 p99 存储指标、用应用日志对齐。
延迟不是 SLA： await 是完成请求的平均值，不是 p95/p99。尾延迟问题可能被平均值掩盖；共享存储和对象存储尤其要结合服务端延迟分位数。

流程图：从 iostat 字段判断读写瓶颈

诊断顺序：先看延迟，再看队列，再看吞吐/IOPS 是否接近设备或共享后端规格；不要只看 %util。

10. 队列字段：aqu-sz 与请求堆积

aqu-sz 是平均队列长度，老版本可能叫 avgqu-sz。它反映采样窗口里平均有多少 I/O 请求在队列或服务中等待。对 AI 任务来说，aqu-sz 的意义是“应用并发提交的 I/O 是否超过设备/后端消化能力”。

组合解读处理方向
aqu-sz 高 + await 高请求堆积并带来体感延迟，常见于设备饱和或共享后端变慢。降低 dataloader 并发、错峰 checkpoint、迁移到本地 NVMe、扩容存储。
aqu-sz 高 + await 可接受高并发设备能吞下队列，多队列 NVMe 可能正常。结合吞吐、GPU 利用率和应用延迟，不必盲目优化。
aqu-sz 低 + await 高稀疏慢 I/O 或尾延迟，平均队列不高但单次慢。查远端存储 p99、文件系统 metadata、网络路径、设备错误。
# 对齐数据加载 worker 数量观察队列变化
for workers in 2 4 8 16; do
  echo "Run benchmark with num_workers=$workers, observe iostat in another terminal"
done

# 观察单设备队列和延迟趋势
iostat -xz 1 30 | awk 'NR<=3 || /nvme0n1|dm-0/'
经验判断： aqu-sz 没有跨设备通用阈值。SATA SSD、单块 HDD、本地 NVMe、云盘、多路径 SAN 的健康队列深度完全不同，必须结合设备规格和应用延迟。

11. 忙碌字段：%util 的正确读法

%util 表示采样窗口内设备至少有一个 I/O 在处理的时间比例。对单队列、低并发设备，接近 100% 常意味着设备忙满；对 NVMe、多队列 SSD、云盘或 dm/md 聚合设备，%util 可能接近 100% 但仍有吞吐余量，也可能不高但尾延迟很差。

现象不要误读为更稳妥的判断
%util 100%，await 低，吞吐接近预期一定有问题设备很忙但服务正常，可能是高效顺序 I/O。
%util 40%，await 高设备一定不忙可能有远端后端慢请求、采样稀释、云盘限流或队列模型复杂。
%util 高，aqu-sz 高，await 高只需要换命令看这是强饱和信号，优先减少压力或提高存储能力。
核心警告： %util 不是“磁盘性能使用百分比”。它是忙碌时间比例，不等价于带宽利用率、IOPS 利用率或 NVMe 内部并行度利用率。

12. svctm caveats：为什么不要迷信它

老版本 iostat 可能显示 svctm，表面含义是平均服务时间。但在现代 Linux 块层、多队列设备、请求合并、设备内部并行和虚拟化/云盘场景下，这个字段很容易误导。很多新版 sysstat 已经不再显示它，或文档明确提示不要信任它。

字段看起来像什么实际 caveat
svctm设备处理单个请求的平均服务时间并行 I/O、队列合并和采样算法会让它不代表真实设备服务时间。
await平均等待时间更贴近应用体感，但仍是平均值，不是尾延迟。
aqu-sz平均队列长度需要结合设备队列深度、NVMe 多队列和业务并发解释。
替代读法： 看到 svctm 时，把它降级为参考；核心判断使用 await/r_await/w_await、aqu-sz、吞吐/IOPS、%util、设备错误日志和存储侧监控。

13. NVMe、多队列与云盘/共享存储

AI 节点常见本地 NVMe、RAID0 临时盘、云盘、NFS、Lustre、BeeGFS、对象存储 FUSE、SAN 多路径和 dm-crypt/LVM 叠加。iostat 的设备名只是块层入口，后面可能是完全不同的后端。

本地 NVMe
多队列、高并发、低延迟。%util 接近 100% 不一定代表完全饱和，重点看吞吐是否接近规格、await 是否恶化。
云盘/EBS/PD
常有 IOPS、吞吐、burst credit、实例带宽上限。iostat 只能看到客户端表现，必须结合云监控。
NFS/并行文件系统
数据可能走网络而非本地块设备。iostat 对客户端缓存盘有用，但不能完整替代服务端和网络指标。
dm/md/LVM/RAID
上层设备和底层物理盘可能同时显示活动。避免把同一 I/O 在 dm 和 nvme 层重复计算成两份吞吐。
# 把业务路径映射到块设备
df -hT /data
findmnt /data
lsblk -o NAME,TYPE,SIZE,MODEL,MOUNTPOINT,FSTYPE

# 查看 NVMe 设备；需要 nvme-cli 时另装
nvme list 2>/dev/null || true

# dm/LVM 关系
lsblk -f
dmsetup ls --tree 2>/dev/null
共享存储提醒： 如果多个节点同时读同一数据集，单节点 iostat 只能证明“这个客户端慢”。要判断是否后端饱和，需要看存储系统吞吐、元数据服务、网络、服务端 CPU 和其他租户。

14. dataloader 读瓶颈排查

dataloader 读瓶颈常见于小文件数据集、远端共享目录、压缩格式、过多 worker、页缓存冷启动、容器 overlayfs 或数据增强与 I/O 混合瓶颈。iostat 可以判断设备侧是否在拖慢输入流水线。

iostat 现象训练现象可能根因下一步
r/s 高、rkB/s 低、r_await 高GPU 周期性空转小文件随机读或 metadata 压力数据打包、缓存到本地、减少随机打开、看 NFS metadata。
rkB/s 高、await 低吞吐正常但 CPU 高存储没问题，瓶颈可能是解码/增强/Pythonpidstat -u -t、mpstat -P ALL、profiler。
await 高、aqu-sz 高，多个节点同时出现所有训练 job 变慢共享存储后端或网络拥塞查存储服务端、交换机、NFS/Lustre 指标。
首轮慢，第二轮快epoch 1 慢，后续快页缓存预热效果预热缓存、本地缓存、调整数据布局。
# 训练时并行采集：设备 + 进程 I/O + CPU
iostat -xzy 1 120 | tee iostat.dataloader.log
pidstat -dru -h 1 120 | tee pidstat.dataloader.log
mpstat -P ALL 1 120 | tee mpstat.dataloader.log

# 查看文件数量和平均大小，小文件数据集尤其危险
find /data/train -type f | wc -l
find /data/train -type f -printf '%s\n' 2>/dev/null | awk '{n++; s+=$1} END {print "files=" n, "avg_kib=" s/n/1024}'
典型优化： 把海量小文件转换成 shard/tar/LMDB/Parquet/WebDataset，或者在每个训练节点使用本地 NVMe 缓存，通常比盲目增加 num_workers 更有效。

15. checkpoint 与写放大排查

大模型 checkpoint 往往包含模型权重、optimizer state、scheduler、随机状态和分布式分片。写入可能在短时间内制造巨大 wkB/s 和 w_await，同时影响 dataloader 读和其他租户。

现象解释应对
wkB/s 周期性冲高，GPU 同步停顿保存 checkpoint 阻塞训练主循环或共享存储写入慢。异步保存、降低保存频率、分片 checkpoint、本地落盘后后台上传。
w_await 高，aqu-sz 高写队列堆积，设备或后端写能力不足。换高写吞吐盘、错峰保存、控制同时保存任务数。
写入后读延迟变差刷脏页、页缓存污染或共享后端争用。隔离 checkpoint 盘和数据盘，控制 dirty ratio，使用独立路径。
dm-* 忙但底层盘也忙LVM/加密/RAID 层叠加显示。避免重复计算，按拓扑看上层逻辑设备和底层物理设备。
# 对齐 checkpoint 时间点
date
iostat -xzy 1 180 | tee iostat.ckpt.log

# 查当前写入进程
pidstat -d 1 20
lsof +D /checkpoints 2>/dev/null | head

# 检查挂载和设备隔离
df -hT /data /checkpoints
lsblk -o NAME,TYPE,SIZE,MOUNTPOINT,MODEL
生产提醒： checkpoint 路径最好和训练数据路径隔离。把高峰写入和高峰读取放到同一共享后端，最容易制造“所有 GPU 都在等存储”的集群级抖动。

16. iostat vs fio/iotop/pidstat/sar

iostat 回答“设备发生了什么”，但完整排障还需要回答“谁造成的”“容量上限是多少”“历史什么时候开始异常”。这些问题需要组合工具。

工具核心价值典型命令注意事项
iostat设备级吞吐、延迟、队列、忙碌度iostat -xz 1不能定位到进程或文件。
pidstat -d进程级读写速率和延迟线索pidstat -dru -h 1对线程、短命进程和缓存命中要谨慎。
iotop交互式进程 I/O 排名sudo iotop -oPa常需要 root；容器环境可能受限。
fio合成基准，测设备/路径容量fio --name=read --rw=randread ...可能破坏数据或影响生产，必须安全配置。
sar -d历史磁盘指标回放sar -d -f /var/log/sa/sa24依赖 sysstat 事先采集。
eBPF/blktrace深入块层延迟分布和调用路径biolatency、biosnoop需要权限和内核支持，适合疑难问题。
fio 安全警告： 不要在生产挂载点上随手运行写测试。需要基准时，先确认测试文件路径、大小、--direct、--readonly 或 --rw=read，避免覆盖真实数据，并告知可能产生的负载。
# 相对安全的只读 fio 示例：读取一个已存在的大测试文件
fio --name=seqread --filename=/data/testfile.bin --rw=read --bs=1M --iodepth=32 --numjobs=1 --direct=1 --runtime=60 --time_based --group_reporting --readonly

# 进程级 I/O
pidstat -dru -h 1 30

# 交互式查看正在产生 I/O 的进程
sudo iotop -oPa

排障图：从 GPU 低利用到存储根因

存储只是 GPU 低利用的常见原因之一。iostat 正常时，不要继续强行归因到磁盘。

17. 故障模式速查

读延迟高
r_await 高，GPU 空转。查小文件、远端存储、页缓存冷启动、metadata 服务和网络。
写延迟高
w_await 高，checkpoint 卡顿。查保存频率、写路径隔离、云盘写限额、后台上传。
队列堆积
aqu-sz 高且 await 高。说明并发压力超过设备或后端消化能力。
IOPS 高吞吐低
r/s 高但 rkB/s 低。常见于小文件随机读和 metadata 风暴。
吞吐高延迟低
rkB/s/wkB/s 高但 await 可接受。可能是健康的大块顺序 I/O。
%util 高但没症状
对 NVMe/多队列设备不必立即恐慌；结合应用延迟、吞吐规格和队列判断。
dm 设备和 nvme 都忙
同一 I/O 可能在多层显示。用 lsblk 看拓扑，避免重复归因。
iostat 正常但训练慢
转查 CPU 解码、Python GIL/worker、网络、NCCL 同步、数据增强、GPU kernel 和框架 profiler。

排障模板

# 1. 确认业务路径对应设备
df -hT /data /checkpoints
findmnt /data /checkpoints
lsblk -o NAME,TYPE,SIZE,MODEL,MOUNTPOINT

# 2. 采集窗口，跳过首行
iostat -xzy 1 60 | tee iostat.issue.log

# 3. 同时抓进程和 CPU
pidstat -dru -h 1 60 | tee pidstat.issue.log
vmstat -w 1 60 | tee vmstat.issue.log

# 4. 对齐应用日志：step time、dataloader time、checkpoint time
grep -E 'step|data|checkpoint|save' train.log | tail -100

18. 安全采集、脚本化与参考资料

iostat 本身是只读低开销工具，适合生产采集；真正需要谨慎的是后续压测、清缓存、迁移数据或调整 checkpoint 策略。任何会增加 I/O 压力或修改数据的动作都要先确认范围。

动作风险安全做法
运行 iostat -xz 1很低只读采样，可在生产使用。
运行 fio 写测试高使用专用测试路径，确认不会覆盖数据，避开生产高峰。
清理页缓存高会影响整机缓存和其他租户，生产上通常不要做。
调整 dataloader worker中小步实验，记录吞吐、CPU、iostat 和 GPU 利用率。
迁移 checkpoint 路径中先验证恢复流程和权限，再改训练配置。
# 轻量采集脚本：只读，不改系统状态
#!/usr/bin/env bash
set -euo pipefail
out=${1:-/tmp/iostat-capture}
mkdir -p "$out"
ts=$(date +%Y%m%d-%H%M%S)
{
  date
  hostname
  iostat -V
  lsblk -o NAME,TYPE,SIZE,MODEL,MOUNTPOINT
  echo "---- iostat ----"
  iostat -xzy 1 60
} | tee "$out/iostat.$ts.log"
不要做： 不要为了“验证是不是缓存问题”就在共享训练节点上执行 echo 3 > /proc/sys/vm/drop_caches；这会影响同机任务，并可能制造比原问题更大的抖动。
