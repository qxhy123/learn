lstopo 深度教程：AI Infra 的 hwloc 拓扑、NUMA、PCIe 与 GPU 亲和性

lstopo 是 hwloc 项目提供的硬件拓扑查看工具。它把 Linux 机器里的 socket、NUMA node、cache、core、PU、PCIe bridge、NIC、NVMe、GPU 等对象组织成一棵拓扑树，帮助 AI Infra 工程师判断“这个进程、这张 GPU、这块网卡、这段内存到底离谁更近”。本教程面向训练/推理服务器、容器和 Kubernetes 节点，重点讲 GPU locality、绑定决策、文本/图形输出、与 lscpu、numactl、nvidia-smi topo 的边界。

hwlocNUMASocketCachePCIeGPU localityContainersCPU bindingAI InfraTroubleshooting
一句话理解： lstopo 不是“CPU 信息命令”，而是“本机硬件亲和性地图”：它告诉你 CPU、内存、I/O 设备之间的层级、距离和可绑定对象。
实践原则： 先用 lstopo --of console 建立拓扑心智，再把 numactl、taskset、容器 CPU set、GPU/NIC 选择映射到同一张图上；不要只凭 CPU 编号或 GPU 编号做绑定。

1. lstopo 是什么

lstopo 来自 Portable Hardware Locality（hwloc）项目。它读取内核、固件和设备枚举信息，把硬件层级展示为可读拓扑：从整机 Machine 到 Package、NUMANode、cache、Core、PU，再到 PCIe 总线上的 GPU、网卡、NVMe 等 I/O 设备。

它回答什么
CPU 核属于哪个 socket？某张 GPU 挂在哪个 PCIe root complex 下？GPU 旁边最近的 NUMA node 是哪一个？容器看到的 CPU set 是否连续且同源？
它不回答什么
GPU 间 NVLink 实时带宽、PCIe 当前链路降速原因、进程真实吞吐瓶颈。那些要结合 nvidia-smi topo、dcgmi、perf、numastat、应用日志继续判断。
AI Infra 价值
减少跨 NUMA 访问、CPU 与 GPU 错配、网卡与 GPU 不同根复合体、容器 cpuset 被切碎等问题，提升训练和推理的稳定性。
# 最常用：在终端中输出拓扑树
lstopo --of console

# 生成可分享的拓扑图
lstopo topology.svg

# 查看进程所在可见拓扑和绑定情况
lstopo --pid "$PID" --of console
权限提醒： 普通用户通常能查看 CPU/NUMA 拓扑，但 I/O 设备、PCI 域名、进程绑定或容器外完整视图可能受权限、namespace、cgroup 和 hwloc 构建选项影响。

信息图：AI 服务器上的 lstopo 心智模型

在 AI 节点上，最重要的不是“有多少核”，而是“线程、内存、GPU、NIC 是否在同一个 locality 域里”。

2. 安装与环境确认

不同发行版的包名通常是 hwloc，命令名是 lstopo；某些环境还提供 lstopo-no-graphics，适合没有图形库的服务器。

系统安装示例说明
Debian / Ubuntusudo apt-get install hwloc服务器上常见，可能包含 console 与图形输出支持。
RHEL / CentOS / Rockysudo dnf install hwloc老系统可能使用 yum install hwloc。
Archsudo pacman -S hwloc包较新，适合开发机验证。
容器镜像apt-get update && apt-get install -y hwloc容器内视图受 cgroup/cpuset 限制，不能默认代表宿主机全貌。
# 确认命令和版本
command -v lstopo
lstopo --version

# 如果无图形依赖，尝试纯文本版本
command -v lstopo-no-graphics || true
lstopo-no-graphics --of console 2>/dev/null || lstopo --of console
版本意识： hwloc 会随版本增加对象类型和输出能力。做集群巡检时，最好记录 lstopo --version，避免把版本差异误判为硬件差异。

3. 最快上手命令

先不要急着记所有选项。AI Infra 排查时，通常从三个视图开始：终端树、带 I/O 设备的图、可机器处理的 XML。

# 1. 终端可读拓扑树
lstopo --of console

# 2. ASCII 树，适合日志和工单粘贴
lstopo --of ascii

# 3. 生成 SVG，适合发给同事或贴到故障复盘
lstopo node-topology.svg

# 4. 保留可解析拓扑，适合归档和离线比较
lstopo --of xml node-topology.xml

# 5. 更关注 I/O 设备时，保留 PCI/OS 设备信息
lstopo --of console | sed -n '/PCI/,/PU/p'
目标建议命令为什么
快速读层级lstopo --of console最稳定、无图形依赖、能复制到工单。
分享拓扑图lstopo topo.svgSVG 可缩放，适合浏览器查看。
离线分析lstopo --of xml topo.xmlXML 可被 hwloc 工具重新读取或比较。
减少噪声lstopo --no-io --of console只看 CPU/NUMA/cache 层级。
输出提醒： topology.png、topology.pdf 等图形格式依赖 hwloc 编译时图形后端；生产脚本优先用 --of console 或 --of xml。

4. 拓扑对象层级

lstopo 的输出是一棵树。不同机器的名称略有差异，但常见层级如下：

对象含义AI Infra 关注点
Machine整台主机或当前 namespace 可见的机器。容器内可能只看到受限拓扑。
Package物理 CPU 封装，常被叫 socket。跨 socket 内存访问和 I/O 访问更贵。
NUMANode内存 locality 域。DataLoader、CPU offload、参数服务器线程应靠近本地内存。
L3/L2/L1cache 层级。线程池、推理 batch、数据预处理可能受 cache 共享影响。
Core物理核心。避免把重线程都绑到同一个 core 的 SMT sibling。
PUProcessing Unit，通常是逻辑 CPU。taskset、cgroup cpuset、K8s CPUManager 实际绑定单位。
PCI BridgePCIe 桥或 root complex 下的层级。判断 GPU、NIC、NVMe 是否共享路径。
OSDev操作系统设备，如 cuda0、mlx5_0、eth0。把硬件拓扑映射到应用可见设备名。
# 只看处理器相关对象，降低 I/O 噪声
lstopo --no-io --of console

# 只看 PCI 相关对象，不同版本支持的过滤粒度可能略有差异
lstopo --only pci --of console 2>/dev/null || lstopo --of console | grep -E 'PCI|OSDev|GPU|mlx|NVMe'
读图顺序： 从 Machine 向下看 socket/NUMA，再看每个 NUMA 下的 core/PU，最后看 PCIe 设备挂在哪个分支。

5. Socket、NUMA 与 Cache

AI 训练节点常见瓶颈之一是跨 NUMA 访问：线程在 NUMA 0 上跑，却频繁访问 NUMA 1 的内存，或给 NUMA 1 下的 GPU 喂数据。lstopo 能把这种结构问题提前暴露出来。

Socket / Package
通常对应一颗物理 CPU。双路机器上跨 socket 通常意味着额外互连跳数。
NUMA Node
内存靠近某组核心。CPU 线程访问本地 NUMA 内存延迟更低、带宽更稳定。
Cache
L3 共享范围影响线程放置。推理预处理、解码线程和通信线程可能争用 cache。
# 对照 lstopo 与 numactl 的 NUMA 视图
lstopo --no-io --of console
numactl --hardware

# 观察进程当前 NUMA 内存分布
numastat -p "$PID" 2>/dev/null || true
现象可能拓扑原因下一步
GPU 利用率周期性掉零数据加载线程跨 NUMA 喂 GPU。用 lstopo 找 GPU 近端 NUMA，再绑定 DataLoader。
NCCL all-reduce 抖动GPU 与 RDMA NIC 不在同一 PCIe/NUMA 分支。对照 GPU、NIC 和 NUMA 位置，调整 rank/NIC 选择。
推理 P99 延迟高线程池跨 socket 调度，cache 和内存 locality 不稳定。缩小 cpuset，固定 worker 到同一 NUMA 域。

6. PU、Core、逻辑编号与物理编号

PU 是 hwloc 的可调度处理单元，通常对应 Linux 里的逻辑 CPU。开启超线程/SMT 时，一个物理 core 可能有两个或更多 PU。绑定时要区分“逻辑编号”和“物理编号”。

# 默认常显示逻辑编号 L#，便于与 hwloc 内部对象一致
lstopo --of console

# 显示物理/OS 编号 P#，更容易对照 /proc/cpuinfo、taskset、cgroup
lstopo --physical --of console

# 同时关注 cpuset，便于复制到 taskset/numactl 前再核对
lstopo --cpuset --of console

# 以 taskset 风格显示 CPU mask
lstopo --taskset --of console
L#
hwloc 的逻辑索引，按拓扑顺序组织，适合在 hwloc 工具链中理解层级。
P#
操作系统或硬件暴露的编号，更适合对照 taskset -cp、/sys/fs/cgroup、Kubernetes CPUManager 分配结果。
绑定提醒： 不要看到 PU L#0 就直接写 taskset -c 0。先确认输出是否是 --physical，并核对 P# 或 cpuset mask。

7. PCIe、OSDev 与 I/O 设备

AI 节点的 GPU、RDMA 网卡、NVMe 本质上都是 I/O 设备。lstopo 会把它们放在 PCIe 层级下，并尽量附上操作系统设备名，帮助你判断设备间是否“近”。

对象示例怎么看
PCI0000:41:00.0PCI domain:bus:device.function，可与 lspci、nvidia-smi -q 对照。
OSDevcuda0、mlx5_0、eth0应用层或内核看到的设备名。
BridgePCI bridge/root port判断设备是否共享上游链路或跨 root complex。
Blocknvme0n1数据集本地盘与 GPU/CPU locality 的线索。
# lstopo 侧：查看 I/O 拓扑
lstopo --of console

# lspci 侧：把 PCI 地址映射到具体设备
lspci -nn | grep -E 'NVIDIA|Mellanox|Ethernet|Non-Volatile'

# NVIDIA 侧：把 GPU index 映射到 PCI bus id
nvidia-smi --query-gpu=index,name,pci.bus_id --format=csv,noheader 2>/dev/null || true
读 I/O 图的技巧： 优先看 GPU 与 NIC 是否在同一 socket/NUMA 附近，再看是否共享同一 PCIe bridge；同一 bridge 不一定总是好，也可能代表共享带宽，需要结合链路和业务流量判断。

8. GPU locality 判断

在训练和推理中，GPU locality 通常包括三层：GPU 到 CPU/NUMA 的近远、GPU 到 NIC 的近远、GPU 到 GPU 的互连关系。lstopo 很适合前两层，第三层要结合厂商工具。

# 1. 找 GPU 对应的 PCI/OSDev 位置
lstopo --of console | grep -Ei 'cuda|gpu|nvidia|pci'

# 2. 对照 GPU 编号与 PCI bus id
nvidia-smi --query-gpu=index,pci.bus_id,name --format=csv,noheader

# 3. 看 GPU-GPU / GPU-NIC 近似关系
nvidia-smi topo -m

# 4. 看 NUMA 节点和 CPU 列表
numactl --hardware
问题lstopo 能帮什么还要补什么
哪个 CPU 喂 GPU0 更合适？找到 GPU0 所在 PCIe 分支附近的 NUMA node 和 PU。用应用 benchmark 验证 DataLoader、H2D copy、推理吞吐。
哪个 NIC 应该给 GPU rank 使用？看 GPU 和 mlx5_* 是否靠近同一 socket/root complex。用 NCCL 拓扑日志、ib_write_bw、nccl-tests 验证。
GPU0 和 GPU1 是否有 NVLink？lstopo 只能展示 PCIe/OSDev 层级。使用 nvidia-smi topo -m 或 NVML/DCGM。
MIG 提醒： MIG 实例是 GPU 内部划分，lstopo 主要看到物理 GPU/PCI 设备；MIG 实例映射要结合 nvidia-smi -L、容器运行时和调度层。

9. 输出格式：console、ASCII、SVG、XML

lstopo 的输出格式决定了使用场景：人读、工单沟通、归档、自动化分析要分开选择。

格式命令适合场景注意
Consolelstopo --of consoleSSH、日志、CI 采集。最推荐作为脚本默认输出。
ASCIIlstopo --of ascii纯文本拓扑图。宽机器上可能很宽。
SVGlstopo topo.svg浏览器查看、复盘文档。可能包含较多设备细节，分享前注意脱敏。
XMLlstopo --of xml topo.xml归档、离线读取、集群拓扑基线。适合做变更前后比较。
Syntheticlstopo --of synthetic测试和模拟拓扑。不代表真实设备 I/O 结构。
# 生成巡检目录
host="$(hostname -s)"
mkdir -p "topology-$host"
lstopo --version > "topology-$host/version.txt"
lstopo --of console > "topology-$host/lstopo.console.txt"
lstopo --of xml > "topology-$host/lstopo.xml"
lstopo "topology-$host/lstopo.svg" 2>/dev/null || true
信息泄露提醒： 拓扑文件可能暴露主机型号、PCI 设备、网卡、磁盘、GPU 型号和集群硬件布局。发到外部 issue 或供应商前先评估脱敏需求。

10. 容器与 Kubernetes 场景

容器内运行 lstopo 时，看到的是当前 namespace、cgroup 和设备挂载共同塑造的视图。它可能是“容器可见拓扑”，不一定是宿主机完整拓扑。

# 容器内：看当前可见 CPU 和拓扑
lstopo --of console
cat /proc/self/status | grep -E 'Cpus_allowed|Mems_allowed'

# cgroup v2 常见位置，具体路径因运行时和发行版而异
cat /sys/fs/cgroup/cpuset.cpus.effective 2>/dev/null || true
cat /sys/fs/cgroup/cpuset.mems.effective 2>/dev/null || true

# Kubernetes Pod 中对照资源限制和可见 GPU
nvidia-smi -L 2>/dev/null || true
grep Cpus_allowed_list /proc/self/status
场景风险建议
Docker 手动指定 --cpuset-cpusCPU 列表可能横跨 NUMA，导致内存和 GPU locality 差。先用宿主机 lstopo --physical --cpuset 选连续近端 CPU。
K8s CPUManager static独占 CPU 可能仍不靠近分配到的 GPU。结合 Topology Manager、设备插件策略和节点拓扑检查。
只挂载部分 GPU容器内 GPU index 可能重排。用 PCI bus id 而不是容器内 index 做跨工具映射。
无特权容器PCI/OSDev 信息可能不完整。在宿主机采集基线，容器内只核对可见 cpuset 和设备。
调度提醒： 不要在容器内看到 PU 0-15 就认为它们是宿主机物理 0-15；容器可见编号可能被限制或重映射，绑定前要对照宿主机 P#、cgroup 和 GPU PCI bus id。

11. 绑定决策：CPU、内存、GPU、NIC

lstopo 本身不负责绑定，它负责告诉你“应该绑定到哪里”。真正执行绑定通常由 numactl、taskset、cgroup、Kubernetes CPUManager、MPI/NCCL 启动器或应用自己的线程池完成。

# 示例：把进程绑定到 NUMA 0 的 CPU 和内存，仅作为模板，先替换为你的实际节点
numactl --cpunodebind=0 --membind=0 python train.py

# 示例：绑定到明确 CPU 列表，先用 lstopo --physical 核对这些 CPU 属于哪个 NUMA
taskset -c 0-15 python inference_server.py

# 查看已有进程的 CPU 亲和性
taskset -cp "$PID"

# 查看进程内存策略，系统支持时可用
numactl --show
决策拓扑依据验证指标
DataLoader CPU 放哪里靠近目标 GPU 的 NUMA node 和 core。GPU 利用率、H2D 拷贝时间、batch 准备耗时。
NCCL 用哪个 NICNIC 与 GPU rank 的 PCIe/NUMA 近远。nccl-tests、NCCL 日志、RDMA 吞吐。
推理 worker 数量同一 L3/NUMA 内可用 core 与 SMT 分布。P50/P99、CPU run queue、cache miss。
NVMe 数据盘选择数据盘是否靠近训练 GPU 所在 socket。读取吞吐、CPU iowait、训练 step time。
不要过度绑定： 拓扑绑定能减少抖动，但过窄的 cpuset 可能让数据加载、通信线程或运行时后台线程饿死。每次绑定都要配套压测和回滚。

12. 与 lscpu、numactl、nvidia-smi topo 对比

工具强项短板AI Infra 用法
lstopo统一展示 CPU、cache、NUMA、PCIe 和 OS 设备层级。不直接给出 GPU NVLink 细节，也不代表实时性能。建立硬件 locality 地图，指导绑定和调度。
lscpuCPU 型号、线程数、NUMA CPU 列表非常快。I/O、PCIe、GPU/NIC 关系弱。快速盘点 CPU 和 NUMA 编号。
numactl --hardwareNUMA node、CPU 列表、node distance 清楚。不展示 PCIe 设备层级。验证内存绑定和 node distance。
nvidia-smi topo -mNVIDIA GPU 间连接、GPU-NIC 近似关系。NVIDIA 专用，不解释完整 CPU/cache 拓扑。决定 rank 排布、NCCL 路径和 GPU 互连。
hwloc-bind按 hwloc 对象执行绑定。团队熟悉度通常低于 numactl/taskset。需要精确按 hwloc 对象绑定时使用。
# 一次性采集四类证据
lstopo --of console > lstopo.txt
lscpu > lscpu.txt
numactl --hardware > numactl-hardware.txt
nvidia-smi topo -m > nvidia-topo.txt 2>/dev/null || true

13. 常见问题与排障

问题 1：看不到 GPU 或 NIC
可能是 hwloc 构建缺少 PCI 支持、容器未暴露设备、权限不足或系统没有对应设备。对照 lspci 和宿主机输出。
问题 2：容器内 CPU 编号和宿主机不一致
检查 /proc/self/status 的 Cpus_allowed_list，并用宿主机 lstopo --physical 重新映射。
问题 3：GPU index 对不上
容器、CUDA_VISIBLE_DEVICES、MIG 都可能重排 index。跨工具映射优先用 PCI bus id。
问题 4：SVG 生成失败
服务器版 hwloc 可能没有图形后端。改用 --of console 或 --of xml。
问题 5：NUMA node 距离看起来奇怪
检查 BIOS NPS/SNC、ACPI SRAT、内核启动参数和 numactl --hardware。
问题 6：绑定后性能更差
可能 cpuset 太窄、SMT sibling 争用、内存策略错误或通信线程被挤压。回滚并逐项压测。
问题 7：lstopo 与 nvidia-smi topo 结论不同
它们视角不同。lstopo 偏硬件层级，nvidia-smi topo 偏 NVIDIA GPU 互连和驱动视图。
问题 8：双路机器只有一个 NUMA
可能 BIOS 关闭 NUMA 或虚拟机隐藏拓扑。检查 BIOS、虚拟化配置和 lscpu。

排障模板

# 1. 采集原始证据
date
hostname -f
lstopo --version
lstopo --of console

# 2. 对照 CPU/NUMA
lscpu

# 3. 对照 PCI/GPU/NIC
lspci -nn | grep -E 'NVIDIA|Mellanox|Ethernet|NVMe'
nvidia-smi topo -m 2>/dev/null || true

# 4. 对照当前进程限制
grep -E 'Cpus_allowed|Mems_allowed' /proc/self/status

CPU/NUMA 视图一致lstopo --no-io、lscpu、numactl --hardwaresocket、NUMA、CPU 列表能互相对照。
GPU/NIC 映射明确lstopo、lspci、nvidia-smiGPU index、PCI bus id、OSDev 名称可关联。
容器边界明确/proc/self/status、cgroup cpuset知道当前视图是宿主机还是容器受限视图。
绑定有回滚启动脚本、调度配置、灰度策略任何绑定变更都能快速撤销。
收益有量化业务 benchmark、nccl-tests、延迟/吞吐指标不是“看起来更近”，而是指标更稳定。
上线建议： 把拓扑采集纳入节点验收和变更复盘。AI 集群里更换主板、BIOS 设置、GPU 拓扑、网卡槽位后，旧绑定策略可能立即失效。

15. AI Infra 常用配方

配方 A：为单 GPU 推理服务选择 CPU

# 找 GPU PCI bus id
nvidia-smi --query-gpu=index,pci.bus_id,name --format=csv,noheader

# 在 lstopo 中定位同一 PCI bus id 附近的 NUMA/PU
lstopo --physical --cpuset --of console

# 试运行：把服务绑到近端 CPU 和内存
numactl --cpunodebind=0 --membind=0 python serve.py

配方 B：为多卡训练检查 GPU 与 NIC

# 采集硬件拓扑
lstopo --of console > lstopo.txt
nvidia-smi topo -m > nvidia-topo.txt

# 找 RDMA 设备与网卡名
ibv_devinfo -l 2>/dev/null || true
ls /sys/class/infiniband 2>/dev/null || true

# NCCL 压测前记录环境
env | grep -E 'NCCL|CUDA|UCX' | sort

配方 C：检查 Kubernetes Pod 是否拿到合理 CPU set

# Pod 内
grep Cpus_allowed_list /proc/self/status
lstopo --physical --of console
nvidia-smi --query-gpu=index,pci.bus_id --format=csv,noheader 2>/dev/null || true

# 宿主机上对照同一 Pod 的 cgroup 和设备分配
lstopo --physical --cpuset --of console

配方 D：归档节点拓扑基线

out="topology-$(hostname -s)-$(date +%Y%m%d)"
mkdir -p "$out"
lstopo --version > "$out/hwloc-version.txt"
lstopo --of console > "$out/lstopo.console.txt"
lstopo --of xml > "$out/lstopo.xml"
lscpu > "$out/lscpu.txt"
numactl --hardware > "$out/numactl-hardware.txt"
nvidia-smi topo -m > "$out/nvidia-topo.txt" 2>/dev/null || true
配方使用边界： 示例里的 NUMA node、CPU 列表和 GPU index 都必须替换为你的真实拓扑。不要把教程中的编号直接复制到生产启动脚本。

16. 练习路线

  1. 在一台普通 Linux 主机上运行 lstopo --of console，标出 Machine、Package、Core、PU。
  2. 对比 lstopo --physical --of console 与 lscpu -e，确认逻辑 CPU 编号如何映射。
  3. 在双 NUMA 机器上对照 lstopo --no-io 和 numactl --hardware。
  4. 在 GPU 节点上用 PCI bus id 把 nvidia-smi 的 GPU index 映射到 lstopo 输出。
  5. 在容器里运行 lstopo，再到宿主机运行一次，比较可见 CPU 和设备差异。
  6. 生成 lstopo.svg 和 lstopo.xml，思考哪一个适合人读、哪一个适合归档。
  7. 设计一个绑定实验：不绑定、绑定近端 NUMA、绑定远端 NUMA，比较业务指标。
学习重点： 能把拓扑图翻译成“应该让哪些线程靠近哪些设备”，才算真正掌握 lstopo。
