1. asyncio 解决什么问题

如果你的服务大部分时间在等待网络、磁盘、数据库、消息队列、远程模型推理接口响应，那么 CPU 其实没有忙，卡住的是 I/O。传统同步代码会让线程阻塞；asyncio 允许你在等待期间切到别的任务，在单线程里把大量 I/O 等待“摊平”。

适合
API 网关、抓取器、异步 worker、代理层、消息泵、批量 RPC、流式转发、长连接服务。
不适合
纯 CPU 密集运算、大量 NumPy/GPU 前后处理中的同步热点、需要真实并行 CPU 的场景。
典型收益
更少线程、更稳定内存、更明确的超时与取消语义，以及更易表达的并发控制。
# 同步版本：每次请求都阻塞当前线程
def sync_handler():
    data = requests.get("https://api.internal/models").json()
    return transform(data)

# 异步版本：等待网络时，事件循环可切换到其他任务
async def async_handler():
    data = await fetch_json("https://api.internal/models")
    return transform(data)
现实判断： 把同步代码表面改成 async def 不会自动提速。只有底层 I/O 真正异步，或者阻塞步骤被隔离到线程/进程，事件循环才能受益。

信息图：事件循环如何推进任务

事件循环不会“抢占”你的 Python 代码；只有你 await 某个可等待对象，或者回到循环边界时，调度才会发生。

2. 事件循环的核心心智模型

可以把事件循环想成一个调度器：它维护一个“就绪任务队列”和一个“等待 I/O/定时器/Future 完成的集合”。任务运行到 await 时暂停；底层资源就绪后，循环再把它放回可运行队列。

概念含义你该怎么理解
事件循环负责调度任务、监控 I/O、触发回调类似单线程操作系统调度器
await挂起当前协程，等待某个可等待对象主动让出执行权，不是睡死线程
可等待对象协程、Task、Future 等调度器知道何时恢复它们
回调/定时器当 Future 完成或超时触发事件循环的另一种输入
关键限制： 一个事件循环线程同一时刻只能执行一段 Python 字节码。asyncio 擅长隐藏等待时间，不擅长突破 GIL 做 CPU 并行。

3. 协程、Task、Future 的关系

这是初学者最容易混淆的三件事。协程对象是“可被调度的函数调用结果”；Task 是“被事件循环实际调度执行的协程包装”；Future 是“稍后会完成的占位结果”，Task 本身就是 Future 的子类。

协程对象
coro = fetch()
只是对象，尚未运行。
Task
task = asyncio.create_task(fetch())
注册进事件循环，开始并发推进。
Future
底层桥接回调式 API 与 await 语义，通常框架或库内部更常见。
import asyncio

async def fetch():
    await asyncio.sleep(0.1)
    return "ok"

async def main():
    coro = fetch()                       # 只是协程对象
    task = asyncio.create_task(coro)    # 变成可调度任务
    result = await task                 # Task 可被 await
    print(result)

asyncio.run(main())
常见错误： 创建协程对象但没有 await 或没有包装成 Task，会触发 “coroutine was never awaited” 警告，而且逻辑根本没执行。

流程图：协程到 Task 的生命周期

协程对象本身不会自动开始，Task 才是事件循环的并发单元；取消、异常和结果都通过 Task/Future 语义传播。

4. asyncio.run() 的边界

asyncio.run(main()) 是标准入口。它会创建事件循环、运行顶层协程、等待所有内部任务收尾，然后关闭循环。脚本、CLI、单次批处理通常都应该从这里进入。

import asyncio

async def main():
    print("boot")
    await asyncio.sleep(0.1)
    print("done")

if __name__ == "__main__":
    asyncio.run(main())
场景建议原因
普通脚本直接用 asyncio.run()最简单、最安全
Jupyter / 已有事件循环环境不要嵌套调用会报 “cannot be called from a running event loop”
ASGI 框架让框架管理循环生命周期和连接管理由服务器统一接管
不要做： 在已经运行事件循环的上下文里再调用 asyncio.run()。这不是“再开一层异步”，而是错误的循环嵌套。

5. create_task() 与后台并发

如果你想“启动一个协程，同时继续做别的事”，就要用 asyncio.create_task()。否则单纯 await 会串行等待当前步骤完成。

import asyncio

async def fetch_profile(user_id):
    await asyncio.sleep(0.2)
    return {"user_id": user_id}

async def fetch_quota(user_id):
    await asyncio.sleep(0.2)
    return {"quota": 128}

async def main():
    profile_task = asyncio.create_task(fetch_profile("u-42"))
    quota_task = asyncio.create_task(fetch_quota("u-42"))

    profile = await profile_task
    quota = await quota_task
    print(profile, quota)

asyncio.run(main())
工程约束： 被创建的 Task 要么被 await，要么被集中管理；“fire-and-forget” 任务如果悄悄异常，默认只会在日志里报 “Task exception was never retrieved”。
推荐模式： 对后台任务建立注册表，退出时统一取消并 await 收尾，而不是把 Task 对象丢掉。

6. gather() 与 TaskGroup

asyncio.gather() 用来并发等待多个可等待对象；TaskGroup 是 Python 3.11 引入的结构化并发工具，更适合生产代码，因为它能把任务生命周期和错误传播收束在一个作用域里。

能力gather()TaskGroup
返回值聚合直接返回结果列表通常自己从 task.result() 取
结构化生命周期较弱强，退出上下文前确保子任务收束
错误传播默认首个异常抛出，其他任务状态需理解清楚子任务异常会取消同组其他任务并统一抛出
推荐场景简单扇出/聚合服务端生产代码、需要严格边界的并发
import asyncio

async def query_model(name, delay):
    await asyncio.sleep(delay)
    return f"{name}:ok"

async def with_gather():
    results = await asyncio.gather(
        query_model("embed", 0.2),
        query_model("rank", 0.1),
    )
    print(results)

async def with_taskgroup():
    async with asyncio.TaskGroup() as tg:
        t1 = tg.create_task(query_model("embed", 0.2))
        t2 = tg.create_task(query_model("rank", 0.1))
    print(t1.result(), t2.result())

asyncio.run(with_gather())
asyncio.run(with_taskgroup())
建议： 新项目若 Python 版本允许，优先用 TaskGroup 管理有父子关系的并发任务；它更接近“这个作用域里的所有子任务，要么一起成功，要么一起失败”。

7. 取消、超时与背压

生产异步程序的稳定性，往往不是由“能跑多快”决定，而是由“失败时能否及时停下来”决定。外部 RPC、批量任务、队列消费者，都应该显式设置取消和超时。

import asyncio

async def slow_rpc():
    await asyncio.sleep(3)
    return "late"

async def main():
    try:
        async with asyncio.timeout(1.0):   # Python 3.11+
            result = await slow_rpc()
            print(result)
    except TimeoutError:
        print("rpc timed out")

asyncio.run(main())
# Python 3.10 及更早可用 wait_for
result = await asyncio.wait_for(slow_rpc(), timeout=1.0)
async def worker():
    try:
        while True:
            await asyncio.sleep(1)
    except asyncio.CancelledError:
        # 做清理动作，然后必须继续抛出
        await flush_metrics()
        raise
取消语义： 不要吞掉 CancelledError 后当成正常成功返回，否则上层会误以为任务干净完成，导致关闭流程、重试逻辑或资源回收全部失真。
背压来源： 超时保证“别无限等”，并发上限保证“别把对端打爆”，队列容量保证“别把自己内存打爆”。三者要同时设计。

信息图：队列、信号量与背压

真正可上线的异步程序，不是“无限开 Task”，而是让请求流量、内部缓冲和外部依赖能力形成稳定闭环。

8. Queue、Semaphore、Lock、Event

这些原语不是为了“模仿多线程写法”，而是为了在单线程事件循环里表达排队、限流、互斥和通知。

原语用途AI/后端例子
asyncio.Queue生产者-消费者、背压推理任务排队、日志/指标批处理
asyncio.Semaphore限制并发量限制并发访问模型服务、数据库或对象存储
asyncio.Lock保护共享状态刷新本地缓存、轮换令牌、批量刷盘
asyncio.Event一对多通知配置已加载、预热完成、系统进入 draining
import asyncio

async def producer(queue):
    for i in range(10):
        await queue.put(i)
    await queue.put(None)

async def consumer(queue):
    while True:
        item = await queue.get()
        if item is None:
            queue.task_done()
            break
        await asyncio.sleep(0.05)
        print(f"processed {item}")
        queue.task_done()

async def main():
    queue = asyncio.Queue(maxsize=4)
    async with asyncio.TaskGroup() as tg:
        tg.create_task(producer(queue))
        tg.create_task(consumer(queue))
    await queue.join()

asyncio.run(main())
sem = asyncio.Semaphore(8)

async def bounded_call(payload):
    async with sem:
        async with asyncio.timeout(2.5):
            return await call_inference_gateway(payload)

9. 网络 I/O 与流式处理

asyncio 内建流接口，足以演示 TCP 客户端/服务端、代理和简单流式协议。生产里很多框架会基于它封装，但底层思想一样：读写都要 await，并且显式处理 EOF、超时和半关闭。

import asyncio

async def echo_client():
    reader, writer = await asyncio.open_connection("127.0.0.1", 9000)
    writer.write(b"ping\n")
    await writer.drain()

    line = await reader.readline()
    print(line.decode().strip())

    writer.close()
    await writer.wait_closed()

asyncio.run(echo_client())
import asyncio

async def handle_conn(reader, writer):
    addr = writer.get_extra_info("peername")
    try:
        while data := await reader.readline():
            writer.write(b"echo:" + data)
            await writer.drain()
    finally:
        writer.close()
        await writer.wait_closed()
        print("closed", addr)

async def main():
    server = await asyncio.start_server(handle_conn, "127.0.0.1", 9000)
    async with server:
        await server.serve_forever()

asyncio.run(main())
流式响应注意： 对 SSE、token stream、日志转发这类长连接，忘记 drain() 或忽略客户端断开，都会让缓冲悄悄堆积。

10. 子进程与外部命令

AI/平台侧任务经常需要调用 ffmpeg、nvidia-smi、自研推理 CLI 或 shell 工具。同步 subprocess.run() 会卡住事件循环；异步版本可以边等子进程边服务其他任务。

import asyncio

async def run_cmd():
    proc = await asyncio.create_subprocess_exec(
        "python3", "-c", "print('ready')",
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE,
    )
    stdout, stderr = await proc.communicate()
    print(proc.returncode, stdout.decode().strip(), stderr.decode().strip())

asyncio.run(run_cmd())
async def stream_subprocess():
    proc = await asyncio.create_subprocess_shell(
        "ping -c 3 127.0.0.1",
        stdout=asyncio.subprocess.PIPE,
    )
    async for raw in proc.stdout:
        print(raw.decode().rstrip())
    await proc.wait()
安全提醒： 只要参数来自用户输入，就优先用 create_subprocess_exec() 传分离参数；create_subprocess_shell() 只有在你明确需要 shell 语法时才用。

11. 阻塞陷阱与隔离策略

最容易把异步程序写坏的，不是不会写 await，而是把同步阻塞函数偷偷塞进协程里。time.sleep()、同步 HTTP 客户端、慢磁盘读取、压缩、JSON 大对象编码、PIL/OpenCV 某些调用，都可能卡住整个事件循环。

坏味道后果替代方式
time.sleep()整个循环冻结await asyncio.sleep()
同步网络请求所有 Task 一起卡住异步客户端或 to_thread()
慢文件/压缩操作尾延迟变大asyncio.to_thread()
CPU 重计算吞吐骤降进程池、任务下沉、原生扩展
import asyncio
import time

def blocking_io():
    time.sleep(1.5)
    return "done"

async def main():
    result = await asyncio.to_thread(blocking_io)
    print(result)

asyncio.run(main())
原则：to_thread() 适合隔离阻塞 I/O；如果是纯 CPU 密集任务，线程通常救不了吞吐，应该考虑进程池、任务切分或服务拆分。

12. AI / 后端基础设施生产模式

下面这些模式在模型网关、批量 embedding 服务、拉取器、代理层里很常见，关键都不是“能并发”，而是“并发边界清晰”。

扇出聚合
一次请求并发访问多个模型或多个后端，最后聚合结果。适合 rerank + features + quota 三路并发。
有界 worker pool
入口任务进入队列，固定数量 worker 消费，防止瞬时峰值把下游压垮。
令牌刷新单飞
共享凭证快过期时，只允许一个协程刷新，其他协程等待同一结果，避免惊群。
优雅降级
主依赖超时后快速 fallback，不把排队压力继续放大到内部。
import asyncio

class EmbedGateway:
    def __init__(self, concurrency=16):
        self.sem = asyncio.Semaphore(concurrency)

    async def infer_one(self, text):
        async with self.sem:
            async with asyncio.timeout(1.5):
                await asyncio.sleep(0.05)  # 模拟远程推理调用
                return {"text": text, "dim": 1024}

    async def infer_batch(self, texts):
        async with asyncio.TaskGroup() as tg:
            tasks = [tg.create_task(self.infer_one(t)) for t in texts]
        return [task.result() for task in tasks]

async def main():
    gateway = EmbedGateway(concurrency=8)
    rows = await gateway.infer_batch(["a", "b", "c"])
    print(rows)

asyncio.run(main())
生产建议： 把“超时、重试、并发上限、熔断、指标”视为一个整体。只做其中一项，系统通常仍然会在峰值或依赖抖动时失稳。

用例图：如何选择 asyncio、线程、进程或 Trio

不要把并发模型变成信仰问题。标准做法通常是：I/O 主干用 asyncio，局部阻塞点用线程隔离，CPU 重活交给进程或外部服务。

13. 调试、监控与排障

异步问题常见为“没有报错但吞吐掉了”“偶尔卡住”“任务泄漏”“退出不干净”。所以你需要的不只是日志，还包括任务可见性、超时指标、队列长度和慢回调观测。

# 打开 asyncio 调试模式
PYTHONASYNCIODEBUG=1 python app.py
import asyncio
import logging

logging.basicConfig(level=logging.INFO)

async def dump_tasks():
    for task in asyncio.all_tasks():
        logging.info("task=%s done=%s coro=%s", task.get_name(), task.done(), task.get_coro())
症状可能原因排查手段
吞吐突然下降事件循环被同步阻塞抓慢栈、检查 to_thread() 缺失点
退出卡住后台 Task 未取消或未结束asyncio.all_tasks() 枚举存活任务
内存上涨队列无限增长、结果未消费观测 Queue size、Task 数量、缓冲区
偶发超时并发过高或下游抖动记录超时分布、并发数、重试次数
日志实践： 给关键 Task 命名，例如 create_task(job(), name="embed-worker-3")，出故障时你会感谢自己。

14. 优雅退出与错误传播

服务接到退出信号时，理想流程不是“立刻杀死”，而是停止接新活、取消后台任务、等待关键中的任务在超时窗口内收尾、最后关闭连接和写出最后指标。

import asyncio
import signal

async def worker(stop_event):
    while not stop_event.is_set():
        await asyncio.sleep(0.2)

async def main():
    stop_event = asyncio.Event()
    loop = asyncio.get_running_loop()
    loop.add_signal_handler(signal.SIGTERM, stop_event.set)
    loop.add_signal_handler(signal.SIGINT, stop_event.set)

    async with asyncio.TaskGroup() as tg:
        tg.create_task(worker(stop_event), name="worker-1")
        tg.create_task(worker(stop_event), name="worker-2")
        await stop_event.wait()

asyncio.run(main())
错误处理原则： 不要在底层把所有异常都吃掉再返回默认值。只有你确定该错误已被转换成业务上可接受的降级结果时，才应该屏蔽异常。
Unix 限制： add_signal_handler() 在某些平台和运行环境受限，跨平台守护进程要根据部署方式调整退出逻辑。

15. asyncio vs 线程 / 进程 / Trio

没有哪种并发模型能统治所有场景。选型时看你的主瓶颈、依赖生态和运维复杂度。

方案优点代价何时选
asyncio标准库、I/O 并发效率高、资源更省需要异步生态，阻塞点要显式治理API、代理、worker、流式服务
线程兼容同步库，迁移门槛低线程成本更高，取消和生命周期更散同步 SDK 很多、改造成本高
进程CPU 真并行序列化和进程管理成本高CPU 密集、模型前后处理重计算
Trio / AnyIO结构化并发设计更强直接标准库迁移路径不同新框架、追求更严格并发语义
工程现实： 很多成熟系统不是单选题，而是“asyncio 主干 + 少量线程池 + 进程/外部服务处理 CPU 重活”的混合结构。

排障图：异步服务上线前的四类风险

异步服务的大多数事故并不神秘：不是事件循环被卡住，就是边界没收住，或者退出、取消、异常语义被写乱了。

16. 上线前检查清单

  • 所有外部 I/O 是否都配置了合理的超时？
  • 是否对下游依赖设置了并发上限，而不是无限制创建 Task？
  • 是否存在同步阻塞代码混入协程，且没有用 to_thread() 或其他隔离手段？
  • 队列是否设置了 maxsize，并且消费者能真正跟上？
  • 取消时是否会正确传播 CancelledError，而不是吞掉？
  • 后台任务是否都可追踪、可取消、可等待，退出时不会悬挂？
  • 是否暴露了关键指标：超时率、队列长度、活动任务数、慢请求、重试次数？
  • 如果依赖抖动，系统是快速失败/降级，还是把压力放大成级联故障？
最后建议： 学 asyncio 不要从 API 名字开始背，而要从“哪些地方在等待、等待时谁能继续、何时该停止、系统如何收束”这四个问题出发。只要这四件事想清楚，API 细节反而很容易记住。
