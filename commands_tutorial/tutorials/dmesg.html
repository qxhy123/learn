1. dmesg 是什么

dmesg 是读取和控制 kernel ring buffer 的工具。它最常见的用途是看内核启动、硬件枚举、驱动加载和运行时错误。对 AI Infra 来说，它经常是排查“节点为什么挂了、GPU 为什么掉了、训练为什么被杀、NVMe 为什么抖动”的第一现场。

它擅长什么
发现内核级事件：OOM kill、GPU XID、PCIe AER、NVMe timeout、I/O error、驱动 probe 失败、固件加载失败。
它不擅长什么
不能替代应用日志、训练框架日志、Kubernetes 事件或持久化审计日志。ring buffer 容量有限，旧消息会被覆盖。
它的本质
读取内核维护的循环日志缓冲区；输出可以来自当前缓冲区，也可以通过 -w 持续等待新消息。
# 查看内核消息，使用人类可读时间
dmesg -T | less

# 只看最新 100 行
dmesg -T | tail -100

# 实时追踪新内核消息，常用于复现故障时观察
sudo dmesg -T -w

# 只看错误及以上级别
sudo dmesg -T --level=err,crit,alert,emerg
重要限制： dmesg -T 的墙钟时间是根据当前系统时间换算的，系统 suspend/resume 或时间被调整时可能不完全精确；需要严格时间线时同时看 journalctl -k --since ...。

信息图：从硬件/内核事件到 dmesg 输出

内核消息先进入 ring buffer；dmesg 只是读取这个缓冲区。缓冲区会循环覆盖，因此事故发生后应尽快采集。

2. 基本语法与常用选项

dmesg [options]

# 推荐起步组合
dmesg -T | less
dmesg -T | grep -Ei 'oom|killed process|xid|nvrm|aer|pcie|nvme|i/o error|timeout'
sudo dmesg -T --level=err,warn
sudo dmesg -T -w
选项用途AI Infra 典型场景
-T显示人类可读时间把 XID/OOM 与训练日志时间对齐
-w等待并持续输出新消息复现 GPU reset、NVMe timeout、驱动加载失败
--level=...按日志级别过滤先缩小到 err,warn,crit
-H增强可读输出，通常会分页交互式查看长日志
-k显示内核消息现代 util-linux 下默认通常就是内核消息
-c读取后清空 ring buffer不建议生产随手使用
-C仅清空 ring buffer会破坏现场，除非实验环境明确需要
不要把 -c/-C 当成普通查看命令： 它们会清空当前缓冲区，可能让后续取证丢失现场。

3. 时间戳：-T、-w 与 --time-format

原始 dmesg 时间通常是“从内核启动以来的秒数”，例如 [12345.678901]。-T 会把它换算成墙钟时间，便于与训练框架、调度器和监控系统对齐。

# 墙钟时间，适合人工排障
dmesg -T | tail -50

# ISO 风格时间，适合粘贴到工单或机器处理
dmesg --time-format=iso | tail -50

# 实时追踪：复现故障时另开一个终端
sudo dmesg -T -w

# 只追踪新错误，减少噪声
sudo dmesg -T -w --level=err,warn,crit,alert,emerg
-T 适合人读
快速判断“XID 是否发生在训练 loss 爆炸之前”“OOM 是否对应某次 batch size 调整”。
--time-format=iso 适合证据
输出更容易被日志系统、工单系统和脚本解析。
时间线建议： 对重大故障同时保存 date -Is、uptime -s、dmesg --time-format=iso、journalctl -k --since，避免只依赖单一时间源。

流程图：用 dmesg -T -w 复现并捕获故障

dmesg -T -w 的价值在于“事件发生时正在看”。复现窗口内的新消息比事后翻全量日志更容易定位因果。

4. 日志级别、设施与筛选

内核消息有级别，例如 emerg、alert、crit、err、warn、notice、info、debug。AI Infra 排障通常先看 err 和 warn，再回到完整上下文。

# 先看严重问题
sudo dmesg -T --level=err,crit,alert,emerg

# 包含 warn，能看到 AER corrected error、驱动警告等
sudo dmesg -T --level=warn,err,crit,alert,emerg

# grep 常见 AI Infra 关键词
dmesg -T | grep -Ei 'oom|out of memory|killed process|xid|nvrm|gpu|pcie|aer|nvme|blk_update_request|i/o error|timeout|reset|firmware'

# 保留前后文，避免只看单行误判
dmesg -T | grep -Ei -C 5 'xid|oom|nvme|aer'
关键词常见含义下一步
Out of memory, Killed process内核 OOM killer 介入查 cgroup、进程 RSS、作业资源限制
NVRM, XidNVIDIA 驱动报告 GPU 异常查 XID 编号、GPU 拓扑、温度、电源、驱动版本
AER, PCIe Bus ErrorPCIe 高级错误报告查槽位、链路速率、可纠正/不可纠正错误
nvme, I/O error, timeoutNVMe 或块层异常查 SMART、错误日志、固件、温度和队列超时

5. 权限：dmesg_restrict 与 sudo

很多生产发行版会限制普通用户读取 dmesg，因为内核日志可能包含地址、设备拓扑、命令行参数、硬件序列号等敏感信息。限制通常由 kernel.dmesg_restrict 控制。

# 查看当前限制，1 表示普通用户通常不能读 dmesg
sysctl kernel.dmesg_restrict
cat /proc/sys/kernel/dmesg_restrict

# 如果普通用户失败，使用 sudo 读取
sudo dmesg -T | tail -100

# 仅在临时实验环境中、经过授权后才考虑放宽；默认不要执行
# sudo sysctl kernel.dmesg_restrict=0

# 生产上更建议通过 sudoers、日志采集或 journalctl 权限分组控制访问
权限安全： 不要为了让训练用户方便排障而永久关闭 dmesg_restrict。更稳妥的做法是给 SRE/平台组受控读取权限，或把内核日志采集到受权限保护的日志系统。

6. dmesg 与 journald 的关系

dmesg 读取当前内核 ring buffer；systemd-journald 通常会从内核日志源收集消息并持久化或半持久化保存。两者经常内容相似，但语义不同。

dmesg
直接、快速、当前缓冲区视角。适合事故现场、复现时实时跟随、无 systemd 的环境。
journalctl -k
日志数据库视角。适合跨时间范围检索、按 boot 过滤、关联 unit、导出和持久化审计。
# 当前 boot 的内核日志
journalctl -k -b

# 上一次 boot 的内核日志，适合查重启前 panic、硬件错误
journalctl -k -b -1

# 从指定时间开始看内核日志
journalctl -k --since "2026-04-25 10:00:00"

# 实时跟随内核日志，类似 dmesg -w 但走 journal
journalctl -k -f
定位顺序： 新鲜现场用 dmesg -T 快速看；需要历史、上一次启动、严格时间范围或持久证据时用 journalctl -k。

对比图：dmesg vs journalctl -k

不要把 dmesg 和 journalctl -k 对立起来。它们是同一类内核事件的两个观测面。

7. dmesg vs journalctl 怎么选

问题优先命令原因
刚复现 GPU XID，想实时看新消息sudo dmesg -T -w延迟低，直接观察 ring buffer 新增内容
节点昨晚自动重启，想查重启前内核错误journalctl -k -b -1dmesg 只看当前 boot，历史要靠 journal 或集中日志
需要按时间窗口对齐训练失败journalctl -k --since ... --until ...时间过滤更可靠，可和系统日志统一查询
救援环境、极简系统或 journald 不可用dmesg依赖少，内核缓冲区可直接读
要把内核日志附到工单两者都取当前现场和持久日志互相校验
# 重大故障建议一次性采集
hostnamectl
uname -a
date -Is
uptime -s
sudo dmesg --time-format=iso > dmesg.iso.txt
journalctl -k -b --no-pager > journal-k-current-boot.txt
journalctl -k -b -1 --no-pager > journal-k-previous-boot.txt 2>/dev/null || true

8. AI Infra 排障总览

AI 节点上的问题经常跨越应用、容器、驱动、内核和硬件。dmesg 负责回答：“内核是否在同一时间报告了异常？”

内存
OOM kill、page allocation failure、NUMA/THP 相关告警。
GPU
NVRM XID、GPU fallen off the bus、驱动 probe/reset。
PCIe
AER corrected/uncorrected、链路降速、设备消失。
存储
NVMe timeout、I/O error、reset controller、filesystem error。
# 一条高信噪比的 AI Infra 初筛命令
sudo dmesg -T | grep -Ei \
'oom|out of memory|killed process|nvrm|xid|gpu has fallen off|pcie|aer|nvme|i/o error|blk|timeout|reset|firmware|segfault'

# 结合设备和驱动状态
nvidia-smi -q -x > nvidia-smi-q.xml
lspci -tv
lsmod | grep -E 'nvidia|nvme|mlx|ib_'
uname -a
判断原则： 如果应用日志只说 “CUDA error” 或 “NCCL timeout”，而 dmesg 同时出现 XID/AER/NVMe timeout，排障重心应上移到节点和硬件链路。

9. OOM 与内存压力

当系统或 cgroup 内存不足时，内核可能触发 OOM killer，选择一个进程杀掉。训练任务表现为进程突然退出、容器被杀、Python 只看到 Killed，而 dmesg 里能看到更完整的原因。

# 查 OOM 相关内核消息
sudo dmesg -T | grep -Ei 'out of memory|oom-killer|killed process|memory cgroup'

# systemd/journal 视角
journalctl -k -b | grep -Ei 'out of memory|oom-killer|killed process|memory cgroup'

# Kubernetes 节点上再关联容器状态
kubectl describe pod <pod> -n <ns> | grep -Ei 'oom|killed|reason|exit code' -C 3
kubectl top pod -n <ns>
dmesg 线索可能含义下一步
invoked oom-killer内核开始 OOM 选择流程看触发进程、gfp mask、节点内存状态
Killed process 12345 (python)某训练进程被杀关联作业 ID、容器 ID、GPU 使用和 batch size
Memory cgroup out of memory容器/cgroup 达到限制调整 pod limit/request 或应用内存策略
page allocation failure内核分配高阶页失败，不一定是总内存耗尽查碎片、驱动分配、hugepage/THP 设置
不要只看 free 内存： OOM 可能来自 cgroup limit、NUMA 局部压力、不可回收内核内存或高阶连续页分配失败。

10. GPU XID 与 NVRM 错误

NVIDIA 驱动常用 NVRM: Xid 报告 GPU 异常。XID 是错误编号，不同编号含义不同，可能涉及应用非法访问、驱动问题、ECC、PCIe、供电、温度或硬件故障。dmesg 能告诉你 XID 发生时间、GPU PCI 地址和上下文。

# 查 NVIDIA 内核驱动消息
sudo dmesg -T | grep -Ei 'nvrm|xid|gpu has fallen off|rm_init_adapter|nvidia'

# 实时观察 XID
sudo dmesg -T -w | grep --line-buffered -Ei 'nvrm|xid|gpu'

# 关联 GPU 状态
nvidia-smi
nvidia-smi -q -d ERROR,ECC,TEMPERATURE,POWER,CLOCK,PCIE
nvidia-smi topo -m
现象dmesg 线索排查方向
训练报 CUDA unknown errorNVRM: Xid ...查 XID 编号、驱动/CUDA 版本、应用栈和复现输入
GPU 从系统消失GPU has fallen off the bus重点看 PCIe/AER、供电、温度、主板槽位
驱动加载失败RmInitAdapter failed查 Secure Boot、内核模块版本、固件、设备权限
多卡通信失败XID 与 NCCL timeout 同时出现先处理底层 GPU/PCIe 错误，再看 NCCL 参数
证据链： XID 不能只贴一行。至少保留 XID 前后 50 行、nvidia-smi -q、驱动版本、内核版本、GPU 型号、PCI 地址和作业时间线。

用例图：AI 节点 dmesg 关键词到排查路径

在 AI Infra 中，dmesg 常负责指路：它指出内核看到的故障类型，再由设备工具和调度器日志补全因果链。

11. PCIe/AER 与链路错误

PCIe AER（Advanced Error Reporting）会报告链路层、事务层等错误。可纠正错误不一定立刻导致业务失败，但如果数量持续上升，可能预示槽位、线缆、retimer、主板、供电或设备稳定性问题。不可纠正错误更需要立刻关注。

# 查 PCIe/AER 相关内核消息
sudo dmesg -T | grep -Ei 'pcie|aer|pci bus error|uncorrected|corrected|fatal|non-fatal'

# 查看设备拓扑和具体 BDF
lspci -tv
lspci -vv -s 0000:65:00.0

# 关联 GPU BDF
nvidia-smi --query-gpu=index,pci.bus_id,name --format=csv
AER 线索风险解释建议动作
Corrected error硬件纠错成功，短期可能无感观察频率；与 GPU/NVMe timeout 关联判断
Uncorrected (Non-Fatal)事务失败但系统可继续检查链路、固件、驱动，考虑迁移作业
Uncorrected (Fatal)可能导致设备不可用或系统崩溃隔离节点，保留日志，硬件介入
BadTLP, BadDLLP链路层传输异常重点看链路质量、槽位、线缆、retimer
不要孤立解读 AER： 少量 corrected error 可能由平台噪声导致；如果同时出现 GPU XID、NVMe reset、链路降速或业务 timeout，优先按硬件链路问题处理。

12. NVMe 与块设备错误

训练数据读取、checkpoint 写入和本地缓存高度依赖 NVMe。dmesg 中的 nvme timeout、I/O error、reset controller、文件系统错误，通常比上层框架的 “DataLoader hang” 更接近根因。

# 查 NVMe 和块层错误
sudo dmesg -T | grep -Ei 'nvme|blk_update_request|buffer i/o error|i/o error|ext4|xfs|reset controller|timeout'

# 设备健康信息
sudo nvme list
sudo nvme smart-log /dev/nvme0
sudo nvme error-log /dev/nvme0

# 关联块设备和挂载点
lsblk -o NAME,MODEL,SERIAL,SIZE,TYPE,MOUNTPOINTS
findmnt
dmesg 线索常见影响下一步
nvme timeoutI/O 延迟飙升，训练读取卡住查温度、固件、队列深度、PCIe/AER
reset controller控制器重置，短时 I/O 中断确认是否和业务错误同一时间
I/O error读写失败，可能损坏文件或 checkpoint迁移作业，检查 SMART/error-log，考虑下线设备
EXT4-fs error, XFS文件系统层检测异常只读保护、备份、维护窗口内 fsck/修复
数据安全： 文件系统错误出现后不要盲目继续压测或修复。先保留证据、确认备份和业务影响，再在维护窗口执行破坏性修复命令。

13. 驱动加载、模块与固件

AI 节点常依赖 NVIDIA、RDMA、NVMe、BPF、文件系统等内核模块。驱动加载失败时，应用层通常只看到设备不可见或初始化失败；dmesg 会显示模块签名、符号不匹配、固件缺失、probe 失败等线索。

# 查看最近驱动/固件相关消息
sudo dmesg -T | grep -Ei 'module|firmware|nvidia|mlx|ib_|nvme|probe|failed|taint|secure boot'

# 模块是否加载
lsmod | grep -E 'nvidia|nvme|mlx5|ib_core'

# 模块元信息
modinfo nvidia 2>/dev/null | head -40
modinfo mlx5_core 2>/dev/null | head -40

# 仅查看，不执行加载/卸载
modprobe --show-depends nvidia 2>/dev/null | head
线索可能原因处理方向
firmware: failed to load固件文件缺失或版本不匹配确认发行版固件包、驱动版本、initramfs
module verification failed模块签名或 Secure Boot 问题确认 Secure Boot 策略和 DKMS 签名
Unknown symbol模块与当前内核 ABI 不匹配重装匹配版本驱动，检查 DKMS 构建日志
probe failed设备初始化失败结合 PCI BDF、固件、IOMMU、资源冲突排查

14. 容器与 Kubernetes 节点视角

dmesg 是节点级视角，不是容器内部日志。容器中的进程触发 OOM、GPU fault 或 I/O 错误时，内核消息仍发生在宿主机。Kubernetes 中排障要把 pod、container、node、kernel 四层对齐。

# 先定位 pod 所在节点
kubectl get pod <pod> -n <ns> -o wide

# 在对应节点上查看内核日志
sudo dmesg -T | grep -Ei 'oom|killed process|nvrm|xid|nvme|aer'

# K8s 事件和容器退出原因
kubectl describe pod <pod> -n <ns>
kubectl get events -n <ns> --sort-by=.lastTimestamp

# 如果运行时可用，关联容器
sudo crictl ps -a | grep <pod-name>
sudo crictl inspect <container-id> | grep -Ei 'pid|oom|exitCode' -C 3
常见误区： 在容器里执行 dmesg 可能没有权限，也可能不是你想要的完整节点视角。生产排障应到宿主机或节点日志系统查看。

15. 实时观察与事件复现

当故障可复现时，dmesg -T -w 是最高效的观察方式。建议把实时内核日志、应用日志和设备状态分三个终端并排观察。

# 终端 1：内核事件
sudo dmesg -T -w

# 终端 2：只看高风险关键词
sudo dmesg -T -w | grep --line-buffered -Ei 'oom|killed process|xid|nvrm|aer|nvme|i/o error|timeout|reset'

# 终端 3：GPU 状态采样
watch -n 1 nvidia-smi

# 记录到文件，便于复盘
sudo sh -c 'dmesg --time-format=iso -w >> /var/tmp/dmesg-watch.log'
记录文件注意： 长时间 -w 可能产生大文件。生产上应设置轮转或使用日志采集系统，不要无限写满根分区。

16. 安全取证与脱敏

内核日志可能包含主机名、内核命令行、设备序列号、PCI 拓扑、MAC 地址、IP、容器 ID、路径和进程参数。给厂商或外部团队前应先确认共享范围。

# 只读采集，适合附到内部工单
mkdir -p /tmp/node-evidence
date -Is > /tmp/node-evidence/collected-at.txt
hostnamectl > /tmp/node-evidence/hostnamectl.txt
uname -a > /tmp/node-evidence/uname.txt
sudo dmesg --time-format=iso > /tmp/node-evidence/dmesg.iso.txt
journalctl -k -b --no-pager > /tmp/node-evidence/journal-k.txt

# 粗略脱敏示例：先输出到新文件，不覆盖原始证据
sed -E 's/([0-9a-f]{2}:){5}[0-9a-f]{2}/<MAC>/Ig; s/([0-9]{1,3}\.){3}[0-9]{1,3}/<IP>/g' \
  /tmp/node-evidence/dmesg.iso.txt > /tmp/node-evidence/dmesg.redacted.txt
证据原则： 保留一份原始日志在受控位置，再生成脱敏副本对外共享。不要直接修改原始证据文件。

安全图：排障时哪些 dmesg 操作该避免

大多数 dmesg 排障都是只读的；危险主要来自清空缓冲区、无限制写日志、随意放宽权限和未脱敏共享。

17. 排障 Playbook 与速查表

推荐排障顺序

  1. 记录节点、时间和上下文：hostnamectl、date -Is、uptime -s、作业 ID、pod 名称、GPU 编号。
  2. 快速看最近内核错误：sudo dmesg -T | tail -200 和关键词 grep。
  3. 如果故障可复现，开启 sudo dmesg -T -w 后再触发动作。
  4. 按类型分流：OOM 查 cgroup/内存；XID 查 GPU/驱动；AER 查 PCIe；NVMe 查盘和文件系统。
  5. 用 journalctl -k 补历史，用设备工具补状态，用应用日志补业务影响。
  6. 保留原始证据；对外共享只给脱敏副本。

18. 常见误判与经验规则

误判 1：只看到应用 CUDA error 就重启训练
先查同一时间是否有 XID、AER 或 GPU fallen off bus。否则会把硬件/驱动问题误判成应用偶发。
误判 2：OOM 一定是整机内存不足
很多训练失败来自 cgroup limit 或容器内存限制，整机 free 可能仍有余量。
误判 3：AER corrected error 完全无害
单次 corrected 不一定危险，持续增长且伴随 timeout/XID 时应按链路稳定性问题处理。
误判 4：dmesg 没有日志就说明内核没问题
ring buffer 可能已覆盖，或者 journald 中仍有历史；还要查 journalctl -k -b -1 和集中日志。
误判 5：普通用户读不了 dmesg 是系统坏了
这通常是安全策略。用授权方式读取，而不是永久关闭限制。
误判 6：清空 dmesg 后更干净
事故现场清空缓冲区会破坏证据。实验环境也应明确记录清空时间。
经验规则： 如果 dmesg 在业务失败时间点有硬件/驱动级错误，先解决内核和设备层；如果没有，再深入应用、网络、存储服务和调度层。
