1. ip 是什么：替代 ifconfig/route/arp

ip 来自 iproute2 工具集，是现代 Linux 管理网络配置的标准命令。老命令 ifconfig、route、arp 仍可能存在，但在多网卡、IPv6、策略路由、网络命名空间、容器网络等场景下，ip 的表达更完整。

查看状态
ip -br addr 看接口和地址，ip link 看链路状态，ip route 看路由表。
定位路径
ip route get 10.0.0.8 能回答“到这个目标会走哪张卡、哪个源地址、哪个网关”。
隔离视角
ip netns exec 能进入容器/命名空间的网络视角，看见和宿主机不同的路由与接口。
旧命令现代替代说明
ifconfig -aip addr show / ip -br addr查看地址、状态、作用域，支持 IPv4/IPv6。
route -nip route show查看主路由表，支持多路由表和策略路由。
arp -nip neigh show查看 IPv4 ARP 与 IPv6 Neighbor Discovery 缓存。
netstat -rnip route / ss路由用 ip，连接/socket 用 ss。
# 常用只读体检
ip -br link
ip -br addr
ip route show
ip rule show
ip neigh show

# 解释到某个目标的实际出接口和源地址
ip route get 10.42.0.23
注意： ip 直接操作内核运行时配置。很多发行版重启网络服务或机器后会从 NetworkManager、systemd-networkd、netplan、ifcfg、CNI 等持久化配置重新生成网络状态。

信息图：ip 看到的 Linux 网络栈

排查网络不要只看 IP 地址。完整路径至少包含接口状态、地址、路由、邻居解析和命名空间视角。

2. 基本语法与输出风格

ip 的语法通常是 ip [全局选项] 对象 动作 [参数]。对象包括 addr、link、route、rule、neigh、netns、tunnel 等。很多对象名和动作可以缩写，但生产脚本建议写完整，降低误读。

写法含义适合场景
ip addr show完整地址输出需要 flags、scope、valid_lft 等细节。
ip -br addrbrief 简洁输出快速扫所有接口和地址。
ip -d link showdetails 详细链路信息看 veth、bond、vlan、vxlan、队列等细节。
ip -j addrJSON 输出脚本采集，配合 jq。
ip -4 route / ip -6 route限定协议族区分 IPv4/IPv6 路由。
# 推荐日常别名：一眼看接口和地址
ip -br addr

# 显示更详细 link 信息，包括接口类型
ip -d link show dev eth0

# 机器可读输出
ip -j -br addr

# 只看 IPv4 或 IPv6
ip -4 addr show
ip -6 route show
输出阅读顺序： 先看接口名和状态，再看地址和 prefix，再看路由是否指向正确接口，最后看邻居缓存能否解析下一跳。

3. ip addr：地址、作用域与临时配置

ip addr 管理接口上的 IP 地址。AI 训练节点常有管理网、存储网、RDMA/IB 网、容器网、Docker bridge 等多类地址。排查时要区分“接口 up 了”和“接口有可用地址”是两件事。

字段含义排查价值
inet 10.10.1.23/24IPv4 地址和前缀长度判断网段是否和目标/网关匹配。
inet6 fe80::... scope link链路本地 IPv6正常存在，不代表有全局 IPv6 连通性。
scope global全局可路由地址服务监听和出站通信通常需要它。
scope host本机回环范围常见于 lo 和 VIP/本机地址。
secondary同接口上的附加地址多 IP、VIP、迁移中容易出现。
# 查看所有地址，brief 适合巡检
ip -br addr

# 查看指定接口
ip addr show dev ens5f0

# 临时添加一个地址：重启或网络服务重载后可能消失
sudo ip addr add 10.20.30.40/24 dev ens5f0

# 删除前先确认存在
ip addr show dev ens5f0 | grep '10.20.30.40/24'
sudo ip addr del 10.20.30.40/24 dev ens5f0
不要远程盲删地址： 如果你当前 SSH 就走这张卡或这个地址，ip addr del 会直接断开连接。先用 ip route get 你的客户端IP 判断回包路径。

4. ip link：网卡状态、MTU、MAC 与队列

ip link 查看和修改二层接口属性。它回答的是“接口是否存在、是否 administratively up、链路是否 lower up、MTU 是多少、MAC 是什么、它是什么类型”。GPU 集群里常见的 ens*、enp*、ib*、bond*、vlan*、docker0、cni0、veth* 都从这里开始看。

状态/字段说明常见解释
UP接口被配置为启用管理员层面启用，不等于物理链路通。
LOWER_UP底层链路已连通物理网卡通常表示网线/交换机侧正常。
NO-CARRIER无载波可能是线缆、交换机端口、光模块、bond slave 状态问题。
mtu 9000最大传输单元Jumbo Frame 必须路径两端和交换设备一致。
qdisc队列调度器一般不是第一排查项，但拥塞/限速时有价值。
# 快速看所有接口状态
ip -br link

# 查看详细 link，尤其是 veth/vlan/bond/vxlan 类型
ip -d link show dev ens5f0

# 临时启用/停用接口
sudo ip link set dev ens5f0 up
sudo ip link set dev ens5f0 down

# 临时修改 MTU：先确认对端和交换机也支持
ip link show dev ens5f0
sudo ip link set dev ens5f0 mtu 9000
MTU 修改风险： MTU 不一致可能导致小包通、大包卡、NCCL 初始化后吞吐异常。生产上先用一对测试节点验证，再批量改。

流程图：从目标 IP 到出接口的选择

ip route get 是排查路由选择的核心命令，因为它让内核直接告诉你实际选择结果。

5. ip route：默认路由、源地址选择与 route get

ip route 管理路由表。不要只看 default，还要看更具体的网段路由、metric、协议来源、指定源地址 src。多 NIC AI 节点经常因为默认路由、源地址、metric 或策略路由不符合预期，导致训练流量走管理网而不是高速网络。

路由片段含义例子
default via 10.0.0.1 dev eth0没有更具体匹配时走默认网关公网、管理网常见。
10.42.0.0/16 dev ens5f0 src 10.42.1.23到训练网段直连，从 ens5f0 出GPU 节点互联常见。
metric 100同等前缀下优先级数值越小越优先。
proto dhcp路由来源可能由 DHCP/NetworkManager 生成。
# 查看主路由表
ip route show

# 查看所有表，排查策略路由时很有用
ip route show table all

# 让内核解释到目标的实际路径
ip route get 10.42.8.12
# 典型输出：
# 10.42.8.12 dev ens5f0 src 10.42.1.23 uid 1000

# 临时添加更具体路由
sudo ip route add 10.42.0.0/16 dev ens5f0 src 10.42.1.23

# 安全替换默认路由前先记录当前状态
ip route show default
sudo ip route replace default via 10.0.0.1 dev eth0 metric 100
远程操作默认路由要极谨慎： 改错默认路由可能立刻失联。先用 ip route get 你的SSH客户端IP 确认回程路径，最好在带外控制台或 tmux 中操作，并准备恢复命令。

6. ip neigh：ARP/ND 邻居缓存

路由表决定“下一跳 IP 是谁、从哪张卡出去”，但以太网真正发送前还要解析下一跳 MAC。ip neigh 显示 IPv4 ARP 与 IPv6 Neighbor Discovery 状态。GPU 集群里如果同网段节点偶发不通、迁移后 MAC 变化、网关漂移、容器 veth 异常，邻居表经常能给线索。

状态含义行动建议
REACHABLE近期确认可达正常状态。
STALE缓存存在但需要重新确认不一定是故障，通信时会刷新。
DELAY/PROBE正在验证邻居如果长期停留，检查链路/网关/交换机。
FAILED解析失败重点检查同网段、VLAN、网关、ARP 抑制、安全组。
permanent静态邻居项变更 MAC 时容易留下错误配置。
# 查看所有邻居
ip neigh show

# 看指定接口上的邻居缓存
ip neigh show dev ens5f0

# 查看某个下一跳是否能解析
ip neigh get 10.42.1.1 dev ens5f0

# 谨慎刷新邻居缓存：会触发重新解析
sudo ip neigh flush dev ens5f0
刷新不是修复： ip neigh flush 只能清缓存。如果根因是 VLAN、交换机、网关、CNI 或安全策略，刷新后还会再次失败。

7. ip netns：容器和隔离网络视角

网络命名空间让不同进程拥有不同的接口、地址、路由表和邻居表。容器网络排障的核心问题是：你是在宿主机视角看，还是在容器 netns 里看？ip netns 可以创建、查看、进入命名空间；容器运行时也会把进程放进自己的 netns。

# 查看由 ip netns 管理的命名空间
ip netns list

# 在指定命名空间里看地址和路由
sudo ip netns exec training-ns ip -br addr
sudo ip netns exec training-ns ip route

# 通过进程 PID 进入它所在的网络命名空间观察
sudo nsenter -t <PID> -n ip -br addr
sudo nsenter -t <PID> -n ip route get 10.42.8.12

veth pair 的典型形态

宿主机侧容器/netns 侧说明
vethabc@if42eth0@if17一对虚拟网线两端，ifindex 可辅助对应。
cni0/docker0eth0桥接型容器网络常见。
calico*/flannel*Pod 内 eth0CNI 插件会生成路由、隧道或策略。
删除命名空间前确认归属： ip netns delete 会移除该命名空间的网络视图和其中接口。不要删除容器运行时、Kubernetes 或 CNI 正在管理的命名空间。

用例图：多 NIC AI 节点的路由视角

多网卡节点的核心问题不是“有没有 IP”，而是“不同业务流量是否走了正确的接口和源地址”。

8. 多 NIC 路由与源地址问题

AI Infra 节点经常同时连接管理网、训练网、存储网、容器网。如果路由没有明确指向，Linux 可能选择默认路由或错误源地址，表现为：单机能 ping，跨节点训练慢；SSH 正常但 NCCL 超时；服务监听在一个地址，回包却从另一张卡出去。

# 先列出每张卡的地址
ip -br addr

# 检查到训练 peer 的路径
ip route get 10.42.8.12

# 检查到存储服务的路径
ip route get 172.16.8.10

# 如果到训练网 peer 走了 eth0，说明路由选择不符合预期
# 可添加更具体路由，先在单节点验证
sudo ip route add 10.42.0.0/16 dev ens5f0 src 10.42.1.23 metric 50
症状常见原因检查命令
NCCL 连接到管理网地址DNS/hosts 解析到 eth0，或路由默认走 eth0getent hosts peer、ip route get peer_ip
同网段节点偶发不可达源地址选错、ARP 异常、VLAN 不通ip route get、ip neigh show dev
存储 IO 慢存储流量走管理网或 MTU 不匹配ip route get storage_ip、ip link show
服务只在容器内通宿主机和容器 netns 路由不同nsenter -t PID -n ip route
稳定做法： 给训练网、存储网配置明确网段路由和源地址；不要依赖接口枚举顺序或“看起来默认会走高速网”的猜测。

9. 策略路由：ip rule + 多路由表

普通路由表主要按目标地址选择路径。策略路由可以按源地址、fwmark、入接口、用户等条件选择不同路由表。多网卡服务器、容器网关、云主机多弹性网卡、存储/训练网络隔离时经常需要它。

# 查看策略规则，priority 数值越小越先匹配
ip rule show

# 查看某个表
ip route show table 100

# 示例：来自训练网地址的包查 table 100
sudo ip rule add from 10.42.1.23/32 table 100 priority 1000
sudo ip route add default via 10.42.1.1 dev ens5f0 src 10.42.1.23 table 100

# 验证选择结果
ip route get 8.8.8.8 from 10.42.1.23

# 回滚
sudo ip rule del from 10.42.1.23/32 table 100 priority 1000
sudo ip route flush table 100
组件作用风险
ip rule决定查哪张路由表优先级错会覆盖系统规则。
table main默认主路由表多数命令默认只看它，容易漏查其他表。
table local本地地址和广播路由不要随意修改。
/etc/iproute2/rt_tables路由表数字和名字映射名字只是映射，真正生效的是内核表号。
排查策略路由一定看全局： ip route 默认只看 main 表。遇到多网卡回包异常时，必须同时看 ip rule 和 ip route show table all。

10. MTU、Jumbo Frame 与路径 MTU

MTU 决定单个二层帧能承载多大的 IP 包。AI 训练网络常启用 9000 MTU 的 Jumbo Frame 来降低协议开销，但必须端到端一致：发送端、接收端、bond/vlan/veth、交换机端口、隧道开销都要考虑。MTU 不一致的典型现象是小 ping 通，大流量卡顿或吞吐远低于预期。

# 查看接口 MTU
ip -br link
ip link show dev ens5f0

# 临时修改 MTU
sudo ip link set dev ens5f0 mtu 9000

# 用不分片 ping 验证路径 MTU，IPv4 下 8972 + 28 字节头约等于 9000
ping -M do -s 8972 10.42.8.12

# 如果走 VXLAN/Geneve/IPIP 等隧道，要扣除封装开销
ip -d link show type vxlan
场景建议
裸机训练网两端网卡和交换机端口统一 MTU，验证大包。
bond/vlan底层 slave、bond、vlan 子接口 MTU 要一致或可承载。
容器网络veth、bridge、CNI overlay 可能降低有效 MTU。
跨云/VPN路径中隧道开销大，优先验证 PMTU 和 MSS clamp。
不要只改一端： 单端 MTU 变大不能提升吞吐，反而可能制造黑洞。先抽样验证，再通过配置管理持久化。

11. AI/NCCL 网络选择线索

NCCL、Gloo、MPI、Parameter Server 或自研通信库最终都要走 Linux 网络栈或 RDMA 栈。ip 不能替代 NCCL 日志和 RDMA 工具，但能回答“这台机器有哪些接口、到 peer 走哪里、源地址是什么、容器里看到什么”。这常常是定位训练卡住的第一步。

关键问题

通信库选择了哪张卡？
查看 NCCL 日志中的接口名/IP，再用 ip addr 对照。
到 peer 的路由是否正确？
对每个 peer IP 执行 ip route get，确认 dev 和 src。
容器视角是否不同？
在容器进程 netns 内执行 ip -br addr 和 ip route。
MTU 是否匹配？
训练网大包和 overlay 网络都要验证，不能只看管理网。
# 对照 NCCL 可见接口
ip -br addr

# 容器内视角，PID 换成训练进程或容器 init 进程
sudo nsenter -t <PID> -n ip -br addr
sudo nsenter -t <PID> -n ip route get 10.42.8.12

# 如果需要限制 NCCL 使用接口，先用 ip 确认接口名和地址
export NCCL_SOCKET_IFNAME=ens5f0
export NCCL_DEBUG=INFO

# 批量检查 peer 路由
for peer in 10.42.8.12 10.42.8.13 10.42.8.14; do
  echo "== $peer =="
  ip route get "$peer"
done
NCCL 提醒： NCCL_SOCKET_IFNAME 是选择线索，不是修复网络的万能开关。路由、MTU、DNS/hosts、容器 netns、RDMA 设备状态仍要分别验证。

12. ip vs ethtool/ss/tcpdump

ip 是网络配置和路由视角的入口，但不是唯一工具。排障时要按层次切换工具：接口存在和地址路由看 ip，网卡驱动和速率看 ethtool，socket 监听和连接看 ss，真实包有没有进出看 tcpdump。

问题首选工具示例
接口是否 up、有无地址、路由走哪张卡ipip -br addr、ip route get 10.42.8.12
链路速率、双工、驱动、offloadethtoolethtool ens5f0、ethtool -k ens5f0
端口是否监听、连接状态ssss -lntp、ss -tan state established
包是否真的到达/发出tcpdumptcpdump -ni ens5f0 host 10.42.8.12
RDMA/IB 设备状态ibstat/rdma/perfquery结合具体 IB/RoCE 环境。
# 一条 TCP 服务不通的分层检查
ip route get 10.42.8.12
ip neigh show to 10.42.8.12
ss -lntp | grep ':23456'
sudo tcpdump -ni ens5f0 host 10.42.8.12 and port 23456
ethtool ens5f0
组合思路： ip route get 证明内核想从哪里走；tcpdump 证明包实际上有没有走；ss 证明应用有没有监听或建立连接。

运行时 ip 命令适合快速验证；长期配置应落到系统网络管理器或自动化配置中。

13. 安全变更流程与回滚

网络命令的危险点在于“立即生效”。安全流程要把观察、变更、验证、回滚拆开。特别是远程 SSH、生产训练节点、Kubernetes 宿主机、带有默认路由的机器，不要直接复制未知命令。

变更前快照

# 保存运行时网络状态，便于回滚和审计
mkdir -p /tmp/net-snapshot
ip -br addr > /tmp/net-snapshot/addr.brief
ip addr show > /tmp/net-snapshot/addr.full
ip -d link show > /tmp/net-snapshot/link.detail
ip route show table all > /tmp/net-snapshot/routes.all
ip rule show > /tmp/net-snapshot/rules
ip neigh show > /tmp/net-snapshot/neigh

示例：临时加训练网路由

# 1. 验证当前路径
ip route get 10.42.8.12

# 2. 准备回滚命令
echo 'sudo ip route del 10.42.0.0/16 dev ens5f0'

# 3. 执行最小变更
sudo ip route add 10.42.0.0/16 dev ens5f0 src 10.42.1.23 metric 50

# 4. 立即验证
ip route get 10.42.8.12
ping -c 3 10.42.8.12

# 5. 如异常，回滚
sudo ip route del 10.42.0.0/16 dev ens5f0
持久化不是 ip 命令本身： ip route add 只改运行时。不同系统持久化位置不同，不要在不了解 NetworkManager、netplan、systemd-networkd、Kubernetes CNI 的情况下手工覆盖配置。

14. 排障手册：从症状到命令

网络问题要按层次缩小范围：接口是否存在、地址是否正确、路由是否正确、邻居是否解析、应用是否监听、包是否到达。下面的命令组合适合 AI Infra 值班时快速取证。

症状先运行判断点
节点完全不通ip -br link、ip -br addr接口是否 UP/LOWER_UP，地址是否消失。
只到某个网段不通ip route get 目标IP出接口、源地址、网关是否正确。
同网段不通ip neigh show dev 接口是否 FAILED/INCOMPLETE，VLAN 或二层问题。
容器内通宿主机不通nsenter -t PID -n ip route命名空间内外路由不同。
NCCL hang 或慢ip route get peer、ip link show接口选择、源地址、MTU 是否符合预期。
默认路由被改坏ip route show default、ip rulemetric、via、dev、策略规则是否异常。

15. 常见坑与生产习惯

坑 1：只看 ip addr
有地址不代表路由正确。一定用 ip route get 目标IP 验证实际选择。
坑 2：忽略 netns
容器内看到的接口和路由可能完全不同。用 nsenter -t PID -n 进入同一视角。
坑 3：把 UP 当成链路通
还要看 LOWER_UP，必要时结合 ethtool。
坑 4：只改运行时不持久化
ip 变更重启后可能消失。验证通过后写入正确网络管理器。
坑 5：默认路由抢流量
多 NIC 下默认路由可能让训练流量走管理网。
坑 6：MTU 单点修改
Jumbo Frame 必须端到端一致，包括容器和隧道。
坑 7：策略路由漏查
ip route 看不到全部真相。要看 ip rule 和 table all。
坑 8：用 flush 当修复
刷新邻居或地址只是清状态，不解决根因。

建议养成的习惯

  • 排障报告里同时记录 ip -br addr、ip route get 目标、ip rule、ip neigh。
  • 远程改路由前确认回程路径，保留带外控制台或自动回滚窗口。
  • 容器问题必须在容器进程 netns 内运行同样的 ip 命令。
  • 多网卡节点用明确路由和源地址，不依赖默认路由碰运气。
  • 临时修复验证后，及时转成 NetworkManager、netplan、systemd-networkd、CNI 或配置管理的持久化变更。

16. 练习实验：命名空间搭一个小网络

下面实验用两个 network namespace 和一对 veth 模拟容器网络。所有修改都在本机临时创建的命名空间中进行，适合学习 ip link、ip addr、ip route 和 ip netns exec 的关系。

# 创建两个命名空间
sudo ip netns add ns-a
sudo ip netns add ns-b

# 创建一对 veth，像一根虚拟网线
sudo ip link add veth-a type veth peer name veth-b
sudo ip link set veth-a netns ns-a
sudo ip link set veth-b netns ns-b

# 在各自命名空间内配置地址并启用
sudo ip netns exec ns-a ip addr add 192.0.2.1/24 dev veth-a
sudo ip netns exec ns-b ip addr add 192.0.2.2/24 dev veth-b
sudo ip netns exec ns-a ip link set lo up
sudo ip netns exec ns-b ip link set lo up
sudo ip netns exec ns-a ip link set veth-a up
sudo ip netns exec ns-b ip link set veth-b up

# 验证
sudo ip netns exec ns-a ip -br addr
sudo ip netns exec ns-a ip route get 192.0.2.2
sudo ip netns exec ns-a ping -c 3 192.0.2.2

# 清理
sudo ip netns delete ns-a
sudo ip netns delete ns-b
实验理解： veth 两端分别放进不同 netns 后，每个命名空间都有自己的接口、地址和路由表。这正是容器网络的基础模型之一。
