1. nvidia-smi 是什么

nvidia-smi 是 NVIDIA System Management Interface 的命令行工具，随 NVIDIA 驱动安装。它通过底层 NVML 能力读取和管理 GPU 状态，常用于训练节点巡检、作业排障、监控采样、拓扑确认和设备维护。

它擅长什么
快速查看 GPU 是否被识别、谁在占用显存、利用率是否上来、是否降频、拓扑是否合理、是否有 ECC/XID 错误。
它不等于什么
它不是深度性能剖析器。kernel 级瓶颈、通信算子耗时、CPU dataloader 阻塞仍需 Nsight、PyTorch profiler、NCCL 日志、perf 等工具。
AI Infra 价值
它是训练排障的第一跳：先确认设备、驱动、进程、显存、功耗、温度、拓扑和错误日志，再决定是否深入应用或硬件层。
# 最常见：查看所有 GPU 当前状态和进程
nvidia-smi

# 查看驱动、GPU 型号和 PCI Bus ID
nvidia-smi --query-gpu=index,name,driver_version,pci.bus_id --format=csv

# 只看第 0 张卡的关键指标
nvidia-smi -i 0 --query-gpu=timestamp,name,utilization.gpu,memory.used,memory.total,power.draw,temperature.gpu --format=csv
兼容提醒： nvidia-smi 输出格式并不保证跨驱动版本完全稳定。脚本采集请优先使用 --query-gpu=... 加 --format=csv,noheader,nounits，不要脆弱地解析默认大表格。

2. 整体心智模型

排障时先判断你需要哪种视图：当前快照、连续采样、进程归因、拓扑矩阵，还是硬件错误证据链。

3. 默认输出怎么读

直接运行 nvidia-smi 会显示两大块：上半部分是每张 GPU 的状态，下半部分是占用 GPU 上下文的进程。AI 训练排障时，先看 GPU 是否存在，再看显存、利用率、功耗/温度、性能状态和进程。

字段怎么理解排障提示
GPU-Util采样窗口内 GPU 计算单元忙碌比例。训练慢但长期接近 0%，常见原因是数据加载、CPU、I/O、分布式同步或进程没真正跑到 GPU。
Memory-Usage已分配显存 / 总显存，不等于正在计算。显存高但利用率低，可能是模型已加载、缓存占用、进程挂起或等待数据。
Power当前功耗 / 功耗上限。利用率高但功耗低，可能是 memory-bound、小 batch、降频或测量窗口未捕获峰值。
Pwr:Usage/Cap功耗与上限。长期贴近上限且性能受限，需要结合 clocks/perf cap 查看是否被功耗限制。
TempGPU 温度。温度接近阈值时可能 thermal throttle，检查风道、风扇和机房环境。
PerfP-state，常见 P0 高性能、P8 空闲。空闲在 P8 正常；训练中长期低性能状态需继续看时钟和功耗限制。
MIG M.MIG 模式状态。数据中心卡上若启用 MIG，默认 GPU 视图和进程显示会改变。
# 默认快照
nvidia-smi

# 查看完整设备详情，输出很长
nvidia-smi -q

# 只看利用率、显存、功耗、温度
nvidia-smi --query-gpu=index,name,utilization.gpu,utilization.memory,memory.used,memory.total,power.draw,power.limit,temperature.gpu --format=csv
判断顺序： “GPU 是否被识别” → “进程是否存在” → “显存是否符合预期” → “GPU-Util 是否有波动” → “功耗/时钟/温度是否限制” → “是否有 XID/ECC”。

4. 设备选择与稳定标识

-i 可以选择设备。单机临时操作用 index 很方便；自动化、长期配置和作业绑定应优先使用 UUID，因为 GPU index 可能随重启、拓扑变化、驱动枚举或容器可见性变化。

标识例子适用场景
Index-i 0人工巡检、临时排障，最短但不稳定。
UUID-i GPU-aaaaaaaa-bbbb-...脚本、调度、资产映射，稳定性更好。
PCI Bus ID00000000:3B:00.0和 lspci、NUMA、硬件槽位、拓扑排障联动。
MIG UUIDMIG-...MIG 实例被调度给容器或作业时的稳定标识。
# 建立 index、UUID、PCI Bus ID 的映射
nvidia-smi --query-gpu=index,uuid,pci.bus_id,name --format=csv

# 只查询某张卡
nvidia-smi -i 0 --query-gpu=index,uuid,name,memory.total --format=csv

# 按 UUID 查询，适合脚本
nvidia-smi -i GPU-aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee --query-gpu=uuid,name,temperature.gpu --format=csv
容器提醒： 容器内看到的 GPU index 可能是重映射后的局部编号，不一定等于宿主机 index。跨宿主机/容器定位问题时，同时记录 UUID 和 PCI Bus ID。

5. query-gpu 与 CSV 输出

生产脚本不要解析默认大表格，应明确列出字段并输出 CSV。nounits 便于数值比较，noheader 便于追加日志或被 shell/awk 读取。

# 机器可读：无表头、无单位
nvidia-smi --query-gpu=timestamp,index,uuid,utilization.gpu,memory.used,memory.total,power.draw,temperature.gpu --format=csv,noheader,nounits

# 带表头：适合人工查看和保存
nvidia-smi --query-gpu=timestamp,index,name,driver_version,memory.used,memory.total --format=csv

# 查看可用字段通常可从帮助与文档确认
nvidia-smi --help-query-gpu
常用字段含义AI Infra 用法
utilization.gpuGPU 计算利用率。判断训练是否真正压到 GPU。
utilization.memory显存读写相关利用率。辅助判断 memory-bound 或访存压力。
memory.used, memory.free, memory.total显存占用。容量规划、OOM 排查、空闲卡检测。
power.draw, power.limit当前功耗和上限。降频、功耗封顶、机柜功耗预算。
clocks.current.sm, clocks.current.memorySM 与显存时钟。确认性能状态和锁时钟效果。
pcie.link.gen.current, pcie.link.width.currentPCIe 当前链路。定位插槽、BIOS、链路降级问题。
采集建议： 日志字段固定后不要频繁调整，否则后续分析脚本会复杂化。新增字段时另开版本或追加到末尾。

6. 利用率、显存与瓶颈判断

显存是“是否分配资源”的线索，利用率是“采样窗口内是否忙”的线索；二者必须和进程、功耗、时钟、应用日志一起看。
# 每秒刷新一次默认界面，适合人工观察波动
nvidia-smi -l 1

# 更适合脚本的利用率和显存采样
nvidia-smi --query-gpu=timestamp,index,utilization.gpu,utilization.memory,memory.used,power.draw --format=csv,noheader,nounits -l 1
采样窗口提醒： 利用率是采样窗口内的近似值。短 kernel、突发式推理、强同步训练可能出现“业务确实在跑，但某一秒看起来不高”的情况。

7. 进程表与显存归因

默认输出底部会列出拥有 GPU compute/graphics context 的进程。训练节点上最常用的问题是：谁占了显存、PID 属于哪个用户、容器里哪个任务、是否有僵尸作业残留。

# 查看 GPU 进程，默认大表格底部已有
nvidia-smi

# 更详细的进程查询
nvidia-smi --query-compute-apps=gpu_uuid,pid,process_name,used_memory --format=csv

# 结合宿主机进程信息
ps -o user,pid,ppid,stat,etime,cmd -p 12345

# 查进程打开的 nvidia 设备文件
lsof -p 12345 | grep -E '/dev/nvidia|libcuda|libnvidia'
现象可能原因下一步
显存被占但进程表为空驱动状态异常、MIG/MPS 场景显示受限、权限/容器视图不完整、进程刚退出但资源未释放。宿主机执行、查 dmesg、重查 PID、必要时维护窗口内重置 GPU。
进程存在但 GPU-Util 长期 0%模型加载后等待数据、断点停住、分布式同步阻塞、CPU/I/O 慢。查应用日志、CPU、磁盘、网络、NCCL、pmon。
多个作业共享一张卡调度隔离失败、手工启动、MPS 或容器可见性配置不当。核对调度器分配、CUDA_VISIBLE_DEVICES、容器 runtime。
不要盲杀： 在共享训练节点上，不要只凭显存占用就 kill -9。先确认用户、作业 ID、容器 ID、调度器状态和是否允许抢占。

8. dmon：设备级时间序列

nvidia-smi dmon 用紧凑列输出设备级监控，适合交互观察和轻量采样。它比不断刷新默认表格更适合看趋势，例如 SM 利用率、显存利用率、编码/解码、功耗、温度等。

# 每 1 秒采样一次，显示默认指标
nvidia-smi dmon -d 1

# 只监控第 0、1 张卡
nvidia-smi dmon -i 0,1 -d 1

# 选择指标组：p=power/temp, u=util, c=clocks, v=power/thermal violations, m=fb/bar1/ecc 等
nvidia-smi dmon -s pucvmt -d 1

# 采样 60 次后退出，方便保存日志
nvidia-smi dmon -s pucvmt -d 1 -c 60 > gpu-dmon.log
列/指标组常见含义怎么用
pwr, gtemp功耗、温度。判断是否接近功耗墙或热墙。
sm, memSM 利用率、显存利用率。判断 compute-bound、memory-bound 或空等。
mclk, pclk显存时钟、图形/SM 时钟。确认是否降频或锁频。
rxpci, txpciPCIe 收发吞吐。辅助排查数据搬运或 PCIe 瓶颈。
dmon 定位法： 如果训练吞吐抖动，保存 dmon 日志并对齐应用时间戳，观察抖动时是否伴随功耗、温度、SM 利用率或 PCIe 流量变化。

9. pmon：进程级时间序列

pmon 关注每个 GPU 上的进程活动，适合定位“哪一个 PID 在用 GPU”“哪个进程显存高但不算”“多进程是否公平共享”等问题。

# 每秒显示进程级利用率
nvidia-smi pmon -d 1

# 只看第 0 张 GPU
nvidia-smi pmon -i 0 -d 1

# 选择利用率和显存字段，常用于训练排障
nvidia-smi pmon -i 0 -s um -d 1

# 采样 120 次
nvidia-smi pmon -i 0 -s um -d 1 -c 120 > gpu-pmon.log
看到 PID
继续用 ps、调度器和容器元数据归因。
看到 -
可能没有进程、指标不支持，或该周期没有可报告数据。
MPS/MIG 场景
进程归因可能不如裸卡直观，需结合 MPS server、MIG UUID 和容器运行时。
限制提醒： 进程级利用率并非所有 GPU、驱动、虚拟化或 MIG 场景都完整支持。看到空值时不要立即判定没有负载。

10. 监控循环与日志采样

-l 和 -lms 可循环输出。对于短期排障，用 CSV 追加到日志；对于长期生产监控，应使用 DCGM exporter、Prometheus 或已有监控系统，而不是让每个节点跑一堆临时脚本。

# 每 5 秒采样一次关键字段
nvidia-smi --query-gpu=timestamp,index,uuid,utilization.gpu,memory.used,power.draw,temperature.gpu --format=csv -l 5

# 追加到日志，适合临时排障
nvidia-smi --query-gpu=timestamp,index,uuid,utilization.gpu,memory.used,power.draw,temperature.gpu --format=csv,noheader,nounits -l 5 >> gpu-sample.csv

# shell 控制采样次数，避免忘记停止
for i in $(seq 1 60); do
  nvidia-smi --query-gpu=timestamp,index,utilization.gpu,memory.used,power.draw --format=csv,noheader,nounits
  sleep 5
done > gpu-5min.csv
采样方式适合场景风险
nvidia-smi -l 1人工实时观察。默认大表格不适合机器解析。
--query-gpu ... -l N短期保存关键字段。长时间运行需要日志轮转。
dmon/pmon设备级/进程级趋势。字段和支持度受硬件/驱动影响。
DCGM exporter集群长期监控。需要统一部署和告警策略。
日志习惯： 每次采样都带上 timestamp、GPU UUID、host、job id。否则跨节点和跨容器定位时会丢失上下文。

11. 拓扑 topo -m 与 NUMA

多 GPU 训练不是只看“有几张卡”。GPU 之间、GPU 到 NIC、GPU 到 CPU/内存的距离，会影响 NCCL、RDMA、数据加载和 CPU 绑核策略。
# 查看 GPU/NIC/CPU affinity 拓扑矩阵
nvidia-smi topo -m

# 只看 PCIe 路径，排除 NVLink 影响
nvidia-smi topo -mp

# 和 PCI 设备映射结合
nvidia-smi --query-gpu=index,uuid,pci.bus_id,name --format=csv
lspci -nn | grep -i nvidia
常见矩阵符号： X 表示自身，NV# 表示经过若干条 NVLink，PIX/PXB/PHB 表示不同 PCIe 路径，SYS 通常表示跨 NUMA/CPU 互联。

12. NVLink 与互联健康

NVLink 对多 GPU 训练通信非常关键。topo -m 能看到是否存在 NVLink 路径，部分环境还可以用 nvidia-smi nvlink 子命令查看链路状态和计数器。

# 查看拓扑中是否出现 NV# 标记
nvidia-smi topo -m

# 查看 NVLink 帮助和支持的查询方式
nvidia-smi nvlink -h

# 常见思路：查看链路状态或错误计数，具体参数以当前驱动帮助为准
nvidia-smi nvlink --status
nvidia-smi nvlink --errorcounters
关注点线索下一步
拓扑缺失 NVLinktopo -m 没有预期的 NV#。核对机型、桥接、BIOS、驱动、GPU 插槽和硬件装配。
通信慢NCCL 日志显示走低速路径，或跨 NUMA。对齐 topo -m、NCCL_TOPO_DUMP_FILE、进程 GPU 分配。
链路错误NVLink error counter 增加。升级/回退驱动验证，检查硬件链路，必要时厂商支持。
版本提醒： nvlink 子命令能力与 GPU/驱动相关。写自动化脚本前先用 nvidia-smi nvlink -h 在目标环境确认可用参数。

13. MIG：切分、可见性与排障

MIG（Multi-Instance GPU）把支持的 NVIDIA 数据中心 GPU 切分为多个隔离的 GPU 实例/计算实例。它对多租户推理、小模型训练和资源碎片利用很有价值，但会改变监控视图、进程归因和调度语义。

# 查看 GPU 是否启用 MIG
nvidia-smi --query-gpu=index,name,mig.mode.current,mig.mode.pending --format=csv

# 查看 MIG 设备
nvidia-smi -L

# 查看 MIG 子命令帮助
nvidia-smi mig -h

# 查看详细信息，常用于确认 GI/CI、profile、UUID
nvidia-smi -q -d MIG
MIG 概念含义排障影响
GPU Instance (GI)GPU 资源切片。决定可用 SM、显存等资源边界。
Compute Instance (CI)GI 内的计算实例。容器/作业可能拿到的是 MIG 设备而非整卡。
MIG UUIDMIG 设备稳定标识。用于容器、调度器和日志归因。
Profile如 1g.10gb、2g.20gb 等。容量不足或性能不符时先核对 profile。
MIG 状态变更警告： 启用/禁用 MIG、创建/销毁实例会影响正在运行的业务，通常需要管理员权限和维护窗口。不要在有训练/推理任务的 GPU 上直接操作。

14. 功耗、时钟与性能状态

AI 训练性能不仅由利用率决定，还受功耗上限、SM/显存时钟、P-state、应用时钟、温度和电源策略影响。nvidia-smi 能查询，也能在有权限时修改部分状态。

# 查询功耗、时钟、P-state
nvidia-smi --query-gpu=index,pstate,power.draw,power.limit,clocks.current.sm,clocks.current.memory,clocks.current.graphics,clocks_throttle_reasons.active --format=csv

# 查看支持的应用时钟
nvidia-smi -q -d SUPPORTED_CLOCKS

# 查看功耗限制范围
nvidia-smi -q -d POWER

# 只演示：修改前先读范围和当前值，不要直接在生产训练中执行
nvidia-smi -i 0 -q -d POWER
# sudo nvidia-smi -i 0 -pl 300
字段/命令用途注意
power.draw/power.limit当前功耗与上限。长期贴近上限可能被功耗限制。
clocks.current.sm/clocks.current.memorySM/显存时钟。吞吐异常时与基线对比。
pstate性能状态。P0 常见于高负载，P8 常见于空闲。
-pl设置功耗上限。需要权限；过低会影响性能，过高受硬件/机柜限制。
锁时钟相关命令稳定 benchmark 或受控环境。不同驱动/卡型支持不同，错误配置会影响共享节点。
Benchmark 提醒： 做性能基线时记录驱动版本、功耗上限、时钟、温度、P-state、GPU 型号和拓扑，否则结果不可复现。

15. 温度、风扇与降频线索

温度问题常表现为吞吐下降、时钟降低、功耗异常、节点间性能差异。数据中心 GPU 未必都暴露风扇信息，服务器风扇还可能由 BMC 控制，因此需要结合硬件平台工具。

# 查询温度、功耗、时钟和 throttle 原因
nvidia-smi --query-gpu=index,temperature.gpu,power.draw,clocks.current.sm,clocks.current.memory,clocks_throttle_reasons.active --format=csv

# 详细温度信息
nvidia-smi -q -d TEMPERATURE

# 如果平台支持，查看风扇
nvidia-smi --query-gpu=index,fan.speed,temperature.gpu --format=csv
热降频
温度接近阈值，时钟下降，吞吐变差。检查风道、散热片、机房温度和邻近高功耗设备。
功耗限制
温度正常但功耗贴上限，时钟上不去。检查 power.limit、机柜预算和应用负载形态。
采样错觉
短期峰值没被捕获，或 batch 间空闲。用 dmon -d 1 或更细采样对齐应用日志。
集群视角： 同型号同任务，如果某台节点长期更热或更慢，优先对比拓扑、功耗上限、风扇策略、PCIe 链路和 XID/ECC 记录。

16. ECC、XID 与硬件错误证据链

AI Infra 排障要避免“看到一个 XID 就换卡”或“只看应用日志不看硬件”。证据链越完整，处置越稳。
# ECC 当前和累计计数
nvidia-smi -q -d ECC

# 页退休、行重映射等硬件健康线索，字段支持取决于 GPU/驱动
nvidia-smi -q -d PAGE_RETIREMENT,ROW_REMAPPER

# Linux 内核日志中的 NVIDIA/XID 线索
dmesg -T | grep -iE 'nvrm|xid|nvidia'
journalctl -k --since "1 hour ago" | grep -iE 'nvrm|xid|nvidia'
线索含义行动
Correctable ECC 增加硬件纠正了错误，未必立即影响结果。观察趋势，和同型号卡对比，记录节点/作业。
Uncorrectable ECC不可纠正错误，风险更高。驱逐节点、保留日志、安排维护和硬件检查。
XID 事件驱动报告 GPU/硬件/软件相关异常。结合 XID 编号、应用错误、驱动版本、复现频率判断。
GPU lost / fallen off bus设备从总线消失或通信失败。检查 PCIe、电源、硬件槽位、温度、BMC SEL，通常需要维护窗口。
安全处置： nvidia-smi --gpu-reset 可能影响同一板卡、同一 NVLink 组或正在运行的进程。只在确认无业务或已驱逐作业后执行，并保留事前日志。

17. 容器、Kubernetes 与可见性

在 Docker、containerd、Kubernetes 中，nvidia-smi 是否可用取决于宿主机驱动、NVIDIA container runtime/toolkit、设备文件挂载、环境变量和调度器资源分配。

# 宿主机先确认驱动可用
nvidia-smi

# Docker 临时验证容器可见 GPU，镜像名称按你的环境替换
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 容器内常见环境变量
env | grep -E 'NVIDIA_VISIBLE_DEVICES|CUDA_VISIBLE_DEVICES'

# Kubernetes 中查看分配和容器日志
kubectl describe pod <pod>
kubectl logs <pod> -c <container>
现象可能原因检查项
宿主机可用，容器内没有 nvidia-smi镜像未包含工具，或 runtime 未挂载。换 CUDA base 镜像验证；检查 NVIDIA container toolkit。
容器内 No devices were found没有分配 GPU，或可见设备为空。NVIDIA_VISIBLE_DEVICES、K8s resource limits、device plugin。
容器 index 与宿主机不一致运行时重映射设备编号。记录 UUID，不要只记录 index。
MIG 容器看不到整卡调度的是 MIG 实例。nvidia-smi -L、MIG UUID、resource name。
驱动/运行时边界： 容器通常使用宿主机 NVIDIA 驱动，镜像内 CUDA 用户态版本需要和驱动兼容。不要只升级镜像而忽略宿主机驱动基线。

18. 常见故障排查路径

排障路线从“工具能否读到设备”开始，而不是直接猜框架、驱动或硬件。

故障 1：NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver

# 驱动模块是否加载
lsmod | grep nvidia

# 设备是否在 PCIe 上
lspci | grep -i nvidia

# 内核日志
dmesg -T | grep -iE 'nvrm|nvidia|xid'

# 驱动版本文件
cat /proc/driver/nvidia/version

故障 2：训练慢但 GPU 利用率低

# 先看进程级 GPU 活动
nvidia-smi pmon -d 1

# 再看设备级功耗、SM、显存、PCIe
nvidia-smi dmon -s pucvmt -d 1

# 看 CPU 和 I/O 是否瓶颈
top
iostat -xz 1
pidstat -dru -p <pid> 1

故障 3：多机多卡通信慢或 NCCL hang

# 拓扑和 GPU/NIC 亲和性
nvidia-smi topo -m

# GPU UUID 和 PCI Bus ID
nvidia-smi --query-gpu=index,uuid,pci.bus_id,name --format=csv

# 查内核日志和 XID
journalctl -k --since "30 minutes ago" | grep -iE 'nvrm|xid|nvidia'

19. 安全操作清单

nvidia-smi 不只是读命令，也包含会改变设备状态的管理命令。共享训练集群中，所有修改型操作都应该经过确认和记录。

操作风险安全做法
--gpu-reset中断进程，影响同组 GPU/NVLink，可能失败或需要无进程。先驱逐作业、保存日志、确认无进程、维护窗口执行。
-pl 设置功耗上限影响性能和节点功耗策略。先查询范围和当前值，记录变更，逐台灰度。
锁时钟/应用时钟影响共享节点性能、功耗和温度。只在 benchmark 或专用节点使用，完成后恢复默认。
启用/禁用 MIG改变设备形态，中断作业。维护窗口、调度器下线节点、重建资源并验证。
启用/禁用 ECC可能需要重启或重置 GPU，影响可用显存和性能。遵循集群标准，不对在线业务临时修改。
# 修改前的最小确认包
hostname
date -Is
nvidia-smi --query-gpu=index,uuid,name,persistence_mode,mig.mode.current,power.limit --format=csv
nvidia-smi

# 示例：只查询，不修改
nvidia-smi -i 0 -q -d POWER,CLOCK,TEMPERATURE
变更红线： 没有确认作业归属和维护窗口时，不要执行 reset、MIG 变更、ECC 变更、功耗/时钟策略变更。读命令可以大胆，改命令必须保守。
