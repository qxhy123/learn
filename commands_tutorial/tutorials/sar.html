sar 深度教程：AI Infra 的历史性能指标与事故复盘

这份教程面向 AI Infra、GPU 集群运维、训练平台 SRE 和性能排障工程师。它不是简单罗列 sar 参数，而是从 sysstat 的“后台采样 + 历史二进制档案 + 事后按维度回放”模型出发，讲清楚 CPU、内存、网络、磁盘模式，sar -u/-r/-n/-d 的读法，如何读取 sa 文件，如何还原事故时间线，以及如何理解采样开销、保留周期和 sar 与 vmstat/mpstat/iostat 的边界。

AI Infrasysstat历史指标CPU内存网络磁盘事故复盘低开销采样
一句话理解： sar 是 sysstat 套件里的历史性能回放器：后台 sadc 周期性采样系统指标，写入每日 saXX 文件，排障时再用 sar 按 CPU、内存、网络、磁盘等维度回放某段时间。
生产实践： 对 AI 训练节点，提前启用 sysstat 比事故后临时装工具更重要；sar 不是实时追踪器，而是“低成本黑匣子”，适合回答“昨天 02:13 到底发生了什么”。

1. sar 是什么：历史性能黑匣子

sar 是 sysstat 项目中的系统活动报告工具。它可以实时按间隔打印指标，也可以读取历史采样文件。对 AI Infra 来说，后者更关键：训练任务失败、吞吐突然下降、数据加载变慢、RDMA 或 TCP 抖动、磁盘卡顿，很多问题发生时没有人在终端里盯着 top，但如果 sysstat 已经启用，sar 能帮你事后回放。

实时视角
sar -u 1 5 这类命令像轻量监控，每 1 秒打印一次当前 CPU 指标，共 5 次。
历史视角
sar -f /var/log/sa/sa24 从历史二进制文件读取某天的采样，适合复盘。
AI Infra 价值
把 GPU 监控、训练日志、NCCL 日志、节点事件和主机指标对齐，定位瓶颈在 CPU、内存、网络还是磁盘。
# 立刻观察 CPU，1 秒一次，共 5 次
sar -u 1 5

# 观察内存，2 秒一次，共 10 次
sar -r 2 10

# 回放今天 sysstat 采集的所有默认报告
sar

# 回放指定历史文件
sar -f /var/log/sa/sa24
边界提醒： sar 采样粒度通常是分钟级，不适合分析微秒级延迟尖刺或内核函数热点；那类问题应结合 perf、eBPF、应用 tracing 或设备侧遥测。

2. 安装与启用 sysstat 采集

很多发行版安装 sysstat 后不会自动启用历史采集，或者采集频率由 systemd timer / cron 控制。先确认采集链路是否存在，再谈复盘。

发行版安装常见启用方式历史文件位置
RHEL / CentOS / Rocky / Almadnf install sysstat 或 yum install sysstatsystemctl enable --now sysstat；旧系统可能使用 /etc/cron.d/sysstat/var/log/sa/saDD
Ubuntu / Debianapt install sysstat配置 /etc/default/sysstat 的 ENABLED="true"，再启用 timer 或 cron/var/log/sysstat/saDD
SUSEzypper install sysstatsystemd timer 或 cron，路径随版本略有差异/var/log/sa/saDD 或发行版约定路径
# 查看是否安装
sar -V

# systemd 环境：查看采集 timer/service
systemctl list-timers | grep -E 'sysstat|sa'
systemctl status sysstat 2>/dev/null

# cron 环境：查看采集配置
grep -R "sa1\\|sadc\\|sa2" /etc/cron.d /etc/cron* 2>/dev/null

# 查看历史文件是否在增长
ls -lh /var/log/sa /var/log/sysstat 2>/dev/null
命名习惯： saDD 通常是二进制采样文件，例如 sa24 表示当月 24 日；有些系统还会生成 sarDD 文本报表。

信息图：sar 的整体心智模型

理解 sar 的关键是“先采集，后回放”。事故发生后才安装 sysstat，无法补回历史。

3. 核心模型：sadc 采样、sa 文件、sar 回放

sysstat 通常由三层组成：sadc 从系统计数器读取原始数据；sa1 由 cron 或 systemd timer 调用 sadc 写入每日文件；sar 读取当前或历史文件并格式化输出。sa2 则常用于生成每日文本摘要。

组件角色你通常怎么接触它
sadc系统活动数据采集器，写二进制记录很少直接运行，多由 sa1 调用
sa1采集脚本包装器在 cron/timer 配置里看到
sa2日报脚本包装器生成 sarDD 文本摘要
sar查询和格式化工具日常排障主要入口
# 查看 sysstat 版本和功能
sar -V

# 查看当天默认历史报告
sar

# 指定间隔实时采样：interval count
sar -u 1 3

# 指定历史文件回放 CPU
sar -u -f /var/log/sa/sa24
心智模型： sar 输出多数是“两个采样点之间的平均速率或比例”，不是瞬时值。不要把 10 分钟采样间隔里的平均值误读成尖刺峰值。

4. 快速上手：实时采样与历史查询

sar 命令基本结构是：选择报告类型，选择实时采样间隔或历史文件，再选择时间窗口。

# CPU：每 1 秒输出一次，共 5 次
sar -u 1 5

# 内存：每 2 秒输出一次，共 6 次
sar -r 2 6

# 网络设备：每 1 秒输出一次，共 5 次
sar -n DEV 1 5

# 磁盘设备：每 1 秒输出一次，共 5 次
sar -d 1 5

# 历史文件 + 时间窗口
sar -u -f /var/log/sa/sa24 -s 02:00:00 -e 03:00:00
维度常用命令适合回答的问题
CPUsar -u、sar -P ALL用户态、系统态、iowait、steal、空闲比例是否异常
内存sar -r、sar -B、sar -S可用内存、缓存、分页、交换是否造成训练抖动
网络sar -n DEV、sar -n TCP,ETCP吞吐、包率、重传、连接错误是否与 NCCL 或数据读取异常同窗
磁盘sar -d、sar -b块设备繁忙度、队列、等待时间是否拖慢 dataloader 或 checkpoint

5. CPU 模式：sar -u 与饱和判断

sar -u 汇总 CPU 利用率，适合快速判断节点是否被用户态计算、内核态开销、I/O 等待或虚拟化 steal 拖住。AI 节点上，CPU 不只是“辅助资源”：数据解码、增强、压缩、Python dataloader、多进程调度、网络协议栈都可能让 GPU 饥饿。

# 汇总 CPU 历史
sar -u -f /var/log/sa/sa24 -s 01:30:00 -e 02:30:00

# 每个 CPU 核心
sar -P ALL -f /var/log/sa/sa24 -s 01:30:00 -e 02:30:00

# 实时看 CPU
sar -u 1 10
字段含义AI Infra 解读
%user用户态 CPU 时间训练前处理、Python workers、数据增强、压缩解压可能升高
%system内核态 CPU 时间网络、文件系统、驱动、容器层、页回收可能导致升高
%iowaitCPU 等待块 I/O 的时间数据盘、NFS、对象存储缓存、checkpoint 写入可能相关
%steal虚拟化环境被宿主机抢占的时间云上训练节点若出现 steal，可能不是应用自身问题
%idle空闲比例GPU 低利用且 CPU 很空闲时，瓶颈可能在网络、远端存储、框架同步或任务调度
读数陷阱： %iowait 高说明 CPU 在等待 I/O，但不等于磁盘一定满；网络文件系统、远端存储、块层队列、驱动问题都可能表现为等待。

6. 内存模式：sar -r 与缓存/回收压力

sar -r 报告内存和缓存状态。AI 训练常见问题包括 dataloader worker 过多、页缓存被 checkpoint 或数据预取冲刷、容器内存限制触发回收、NUMA 不均衡导致局部内存压力。sar -r 可以给出主机级线索。

# 内存历史窗口
sar -r -f /var/log/sa/sa24 -s 02:00:00 -e 03:00:00

# 分页活动：判断回收和 page fault 压力
sar -B -f /var/log/sa/sa24 -s 02:00:00 -e 03:00:00

# swap 使用
sar -S -f /var/log/sa/sa24 -s 02:00:00 -e 03:00:00
字段含义排障信号
kbmemfree空闲内存Linux 会用内存做缓存，低空闲不一定是问题
kbavail估算可用内存比 kbmemfree 更适合作为“还能不能分配”的信号
kbcommit / %commit承诺分配量过高时关注 OOM、overcommit、容器限制
kbcached页缓存数据集读取、checkpoint、日志写入会影响缓存行为
pgpgin/s、pgpgout/s分页输入/输出大幅升高可能对应数据加载或写 checkpoint 阶段
容器注意： sar 多数指标来自主机视角。Kubernetes/容器内的 cgroup 限额、OOMKilled、memory.high 等需要结合 kubectl describe pod、cgroup 文件或平台监控确认。

7. 网络模式：sar -n DEV/TCP/ETCP

网络是分布式训练最常见的外部瓶颈之一。sar -n DEV 看网卡吞吐和包率；sar -n TCP,ETCP 看 TCP 连接、重传和错误。RDMA/IB 指标不完全由 sar 覆盖，但 sar 仍能帮助判断主机侧网络是否同时间异常。

# 网卡吞吐与包率
sar -n DEV -f /var/log/sa/sa24 -s 10:00:00 -e 11:00:00

# TCP 连接与段统计
sar -n TCP -f /var/log/sa/sa24 -s 10:00:00 -e 11:00:00

# TCP 错误、重传、reset 等扩展统计
sar -n ETCP -f /var/log/sa/sa24 -s 10:00:00 -e 11:00:00

# 同时看多个网络类别
sar -n DEV,TCP,ETCP 1 5
报告重点字段AI Infra 解读
DEVrxkB/s、txkB/s、rxpck/s、txpck/s、%ifutil数据集拉取、参数同步、checkpoint 上传是否接近网卡瓶颈
TCPactive/s、passive/s、iseg/s、oseg/s连接建立和 TCP 段收发是否出现突变
ETCPretrans/s、isegerr/s、orsts/s重传升高常与吞吐下降、训练同步变慢、存储读取抖动相关
RDMA 提醒： sar -n DEV 可能能看到接口吞吐，但不能替代 ibstat、ibv_devinfo、交换机计数器、NCCL 日志和厂商工具。RoCE 场景还要关注 PFC/ECN/丢包与重传。

8. 磁盘模式：sar -d 与 I/O 队列

sar -d 查看块设备活动，常用于定位数据加载、日志写入、checkpoint、容器镜像层和本地缓存盘问题。它与 iostat -x 关注点相近，但 sar 的优势在于能读历史。

# 历史磁盘报告
sar -d -f /var/log/sa/sa24 -s 18:00:00 -e 19:00:00

# 以设备名显示，部分版本支持 -p
sar -d -p -f /var/log/sa/sa24 -s 18:00:00 -e 19:00:00

# 块 I/O 总览
sar -b -f /var/log/sa/sa24 -s 18:00:00 -e 19:00:00
字段含义如何使用
tps每秒 I/O 请求数小文件数据集或日志风暴会让 tps 升高
rkB/s、wkB/s读写吞吐判断是否接近本地盘、网络盘或缓存层吞吐上限
await平均 I/O 等待时间升高通常比单看吞吐更能反映用户感知卡顿
aqu-sz平均队列长度队列堆积时关注盘、文件系统、远端存储或请求模式
%util设备忙碌比例接近 100% 可能表示设备饱和，但多队列 NVMe 上需结合 await 和吞吐解读
AI 训练典型模式： GPU 利用率周期性掉零，同时 sar -d 的 await 和 aqu-sz 在 batch 边界升高，通常提示 dataloader 或存储层正在拖慢输入流水线。

9. 读取 sa 文件与时间窗口

历史分析的核心命令是 sar -f FILE。生产上先确认系统的 sysstat 路径和保留周期，然后用 -s、-e 切出事故窗口。不同发行版路径不同，脚本要写得保守。

# 常见历史目录
ls -lh /var/log/sa/sa* /var/log/sysstat/sa* 2>/dev/null

# 读取指定日期文件：RHEL 系常见
sar -u -f /var/log/sa/sa24

# 读取指定日期文件：Debian/Ubuntu 常见
sar -u -f /var/log/sysstat/sa24

# 切时间窗口
sar -u -f /var/log/sa/sa24 -s 02:10:00 -e 02:40:00

# 只看某个报告的平均值，适合快速扫尾
sar -r -f /var/log/sa/sa24 -s 02:10:00 -e 02:40:00 | tail -5
参数含义示例
-f FILE读取历史二进制文件sar -n DEV -f /var/log/sa/sa24
-s HH:MM:SS开始时间-s 01:00:00
-e HH:MM:SS结束时间-e 02:00:00
-o FILE实时采样时写出二进制文件sar -u -o /tmp/cpu.sa 1 60
不要手工编辑 saDD： 它是二进制采样文件。需要归档就复制，不能用文本编辑器改；跨版本读取失败时优先用同版本 sysstat 或导出文本。

流程图：用 sar 重建事故时间线

复盘时先固定时间窗口，再扫维度；不要先挑一个喜欢的指标去解释所有现象。

10. 事故时间线重建方法

用 sar 做事故复盘，最重要的是时间对齐。先从训练日志、调度系统、告警系统、GPU 指标里确定异常窗口，再把 CPU、内存、网络、磁盘的 sar 输出切到同一段，最后按因果链组织结论。

# 假设训练日志显示 02:13-02:26 step time 上升
DAY=/var/log/sa/sa24
START=02:05:00
END=02:35:00

sar -u -f "$DAY" -s "$START" -e "$END"
sar -r -f "$DAY" -s "$START" -e "$END"
sar -n DEV,TCP,ETCP -f "$DAY" -s "$START" -e "$END"
sar -d -p -f "$DAY" -s "$START" -e "$END"
复盘问题sar 证据下一步
GPU 利用率掉零，step time 增大sar -u 显示 CPU %iowait 同窗升高查看 sar -d、训练 checkpoint、数据盘/网络盘事件
多机训练 all-reduce 卡顿sar -n ETCP 重传升高，DEV 吞吐下降对齐 NCCL 日志、交换机端口、RoCE/IB 计数器
dataloader worker 异常慢sar -u 用户态接近饱和或 sar -r/-B 回收压力升高检查 worker 数、CPU affinity、NUMA、文件缓存
节点短暂不可用sar 出现采样缺口或全部指标异常跳变结合 journalctl、BMC、内核日志、平台事件
报告格式建议： 用“时间段 + 指标变化 + 关联事件 + 可排除项”写结论，例如：02:12-02:18，nvme0n1 await 从 2ms 升至 95ms，GPU 利用率同步下降；CPU idle 仍高，暂不支持 CPU 饱和假设。

11. AI 训练场景的典型读法

AI Infra 的 sar 分析通常围绕“GPU 为什么没吃满”展开。sar 不能直接告诉你 GPU 原因，但能快速排除或确认主机侧资源瓶颈。

数据加载慢
看 sar -d 的 await/aqu-sz/%util，看 sar -n DEV 的入站吞吐，再看 sar -u 是否 CPU 用户态饱和。
分布式同步慢
看 sar -n DEV,TCP,ETCP 是否吞吐下降或重传升高；RDMA 场景再查 IB/RoCE 专用计数器。
checkpoint 卡顿
看写盘 wkB/s、await、网络上传吞吐，以及是否与日志、对象存储、NFS 同窗。
CPU worker 抢占
看 %user、%system、每核 sar -P ALL 是否热点明显，再结合 pidstat 或 profiler 定位进程。
# 一段常用的 AI 节点主机侧排障快照
sar -u 1 5
sar -P ALL 1 3
sar -r 1 5
sar -n DEV,TCP,ETCP 1 5
sar -d -p 1 5
不要单指标归因： GPU 利用率低 + sar -u 空闲高，不等于主机没问题；可能是网络阻塞、远端存储慢、进程同步等待、锁竞争或调度暂停。

12. 保留周期、采样频率与开销

sysstat 的优势是低开销，但采样频率和保留周期仍要有策略。频率太低会错过短故障；频率太高会增加磁盘写入和文件体积。AI 集群可以按节点角色分层配置：训练节点保留更长，控制节点和存储网关保留更细。

策略优点代价适合场景
10 分钟采样，7-14 天保留开销极低，默认常见短尖刺容易被平均掉普通业务节点、基础趋势
1 分钟采样，14-31 天保留复盘能力明显增强文件更大，指标更多训练节点、存储网关、网络敏感节点
临时 1 秒采样写 -o短期细粒度分析需要主动启动，文件增长快压测、复现、变更验证
# 临时采集 CPU 到独立文件：每 1 秒，共 300 秒
sar -u -o /tmp/cpu-5min.sa 1 300

# 回放临时文件
sar -u -f /tmp/cpu-5min.sa

# 查看 sysstat 保留配置，路径因发行版不同
grep -R "HISTORY\\|COMPRESSAFTER\\|SADC_OPTIONS" /etc/sysconfig /etc/default 2>/dev/null

# 查看 sa 文件体积
du -sh /var/log/sa /var/log/sysstat 2>/dev/null
开销判断： 对大多数服务器，分钟级 sysstat 采样开销很低；真正要评估的是保留天数、指标类别、磁盘写入策略和是否压缩归档。

对比图：sar、vmstat、mpstat、iostat 怎么选

sar 是历史入口，不是替代所有实时工具；它常用于确定“哪段时间、哪个维度值得深入”。

13. sar vs vmstat/mpstat/iostat

工具核心价值历史能力典型命令
sar多维系统活动报告和历史回放强，依赖 sysstat 已启用采集sar -u/-r/-n DEV/-d -f saDD
vmstat系统整体压力快照：运行队列、内存、swap、I/O、CPU弱，通常实时vmstat 1
mpstat每 CPU 利用率、软中断、核心不均衡可实时；与 sysstat 同源但常用于当前观察mpstat -P ALL 1
iostat磁盘和块设备扩展统计弱，通常实时iostat -xz 1
pidstat进程级 CPU、内存、I/O可实时或采集到文件，取决于用法pidstat -durh 1
组合方式： 事故后用 sar -f 找历史异常窗口；复现时用 vmstat 看总压，用 mpstat 看 CPU 分布，用 iostat 看磁盘细节，用 pidstat 把压力归到进程。

14. 脚本化导出与报表

sar 输出是文本，适合快速管道处理。做正式报表时建议保留原始 sa 文件和命令行，避免只留下二次处理后的片段。部分版本支持 -o 写二进制、-f 读二进制；新版本 sysstat 还可能提供 sadf 用于 CSV/JSON 等格式导出。

# 导出某天 CPU/内存/网络/磁盘关键窗口到文本
DAY=/var/log/sa/sa24
START=02:00:00
END=03:00:00
OUT=/tmp/sar-incident-$(date +%Y%m%d%H%M%S)
mkdir -p "$OUT"

sar -u -f "$DAY" -s "$START" -e "$END" > "$OUT/cpu.txt"
sar -r -f "$DAY" -s "$START" -e "$END" > "$OUT/mem.txt"
sar -n DEV,TCP,ETCP -f "$DAY" -s "$START" -e "$END" > "$OUT/net.txt"
sar -d -p -f "$DAY" -s "$START" -e "$END" > "$OUT/disk.txt"

# 如 sadf 可用，可查看它支持的格式
sadf -h 2>/dev/null | head
报表纪律： 不要只贴 Average: 行。平均值会掩盖短窗口尖刺；事故复盘至少保留异常前、异常中、恢复后三段原始时间序列。

15. 安全注意事项与权限边界

sar 本身以读取和报告为主，风险通常不在“破坏系统”，而在误配置采集、误解指标、暴露主机信息和在高压节点上临时开过细采样。

权限
普通用户通常可以运行实时 sar，但读取 /var/log/sa 可能受文件权限限制；生产环境按最小权限授权。
信息泄露
sar 输出可能暴露网卡名、磁盘名、吞吐模式、业务高峰时间；分享到外部前要脱敏。
采样配置
调整 cron/timer 会影响全机采集频率。先在少量节点验证，再批量 rollout。
磁盘占用
长保留 + 高频采样会增加日志目录体积。要配置保留周期、压缩和监控。
# 修改 sysstat 采样策略前先备份配置
sudo cp -a /etc/sysconfig/sysstat /etc/sysconfig/sysstat.bak 2>/dev/null || true
sudo cp -a /etc/default/sysstat /etc/default/sysstat.bak 2>/dev/null || true

# 查看当前日志目录大小，避免盲目加频率
du -sh /var/log/sa /var/log/sysstat 2>/dev/null

# 变更后确认 timer/cron 状态
systemctl list-timers | grep -E 'sysstat|sa'
生产警告： 不要在全量训练集群上直接把采样从 10 分钟改成 1 秒。需要细粒度时优先对目标节点临时采样，或通过监控系统做受控采集。

16. 常见问题与排障

问题 1：没有历史文件
多半是 sysstat 未启用、timer/cron 未运行，或路径不是你以为的 /var/log/sa。先查 systemctl list-timers 和 /var/log/sysstat。
问题 2：命令输出列名和教程不同
sysstat 版本、内核版本和发行版会影响字段。以本机 man sar 和输出表头为准。
问题 3：时间窗口没有数据
检查日期文件是否正确、时区是否一致、采样间隔是否覆盖该窗口、节点是否重启。
问题 4：Average: 看起来正常
平均值可能掩盖短峰值。查看原始时间行，并缩小 -s/-e 窗口。
问题 5：容器内 sar 与平台监控不同
sar 多为主机视角；容器限制、cgroup 内存、pod 网络命名空间需要单独核对。
问题 6：设备名看不懂
尝试 sar -d -p 显示持久设备名；再用 lsblk、udevadm 或云盘映射关系确认。

排障模板

# 1. 找历史文件
find /var/log/sa /var/log/sysstat -maxdepth 1 -type f -name 'sa[0-9][0-9]' -ls 2>/dev/null

# 2. 确认文件能读
sar -f /var/log/sa/sa24 | head

# 3. 用同一时间窗口查四大维度
sar -u -f /var/log/sa/sa24 -s 12:00:00 -e 12:30:00
sar -r -f /var/log/sa/sa24 -s 12:00:00 -e 12:30:00
sar -n DEV,TCP,ETCP -f /var/log/sa/sa24 -s 12:00:00 -e 12:30:00
sar -d -p -f /var/log/sa/sa24 -s 12:00:00 -e 12:30:00

# 4. 如果历史粒度太粗，复现时临时细采样
sar -A -o /tmp/repro.sa 1 300

17. 学习路线与练习任务

第一阶段：会查

  • 掌握 sar -u 1 5、sar -r 1 5、sar -n DEV 1 5、sar -d 1 5。
  • 知道 interval count 是实时采样，-f saDD 是历史回放。
  • 能解释 %user、%system、%iowait、kbavail、rxkB/s、await。

第二阶段：会复盘

  • 能用 -s 和 -e 切出事故窗口。
  • 能把训练日志、GPU 指标、NCCL 日志、Kubernetes 事件和 sar 输出按时间对齐。
  • 能写出包含证据和反证的事故结论。

第三阶段：会运营

  • 能确认 sysstat 是否在目标节点启用。
  • 能评估采样频率、保留周期和日志目录空间。
  • 能在高价值节点上设置合理的历史保留策略，并在复现时临时加细采样。

练习

  1. 在测试节点运行 sar -u 1 5，解释每一列。
  2. 找到本机历史 saDD 文件，读取今天 10 分钟窗口的 CPU、内存、网络和磁盘报告。
  3. 运行一个磁盘读写压测或复制大文件，用 sar -d 1 20 观察 await 和吞吐变化。
  4. 下载或复制大文件，用 sar -n DEV 1 20 观察网卡吞吐。
  5. 把四个维度导出到文本目录，写一段 5 行以内的事故摘要。
# 练习目录：只写 /tmp，不影响业务文件
mkdir -p /tmp/sar-demo

# 采集一个 60 秒 CPU 文件并回放
sar -u -o /tmp/sar-demo/cpu.sa 1 60
sar -u -f /tmp/sar-demo/cpu.sa

# 安全清理练习文件
rm -f /tmp/sar-demo/cpu.sa
