journalctl 深度教程：从 systemd 日志模型到生产排障

这份教程系统讲解 journalctl：它不是传统文本日志查看器，而是 systemd journal 的结构化查询入口。你将学会 journal 的存储与字段模型、按 unit/进程/字段过滤、时间窗口、优先级、实时跟随、按启动轮次查看、JSON 输出、磁盘占用与安全清理、与 tail/grep 的边界，以及服务启动失败、日志缺失、权限不足、磁盘爆满等真实排障路径。

systemd journal结构化字段unit 过滤时间窗口优先级实时跟随启动轮次JSON 输出磁盘清理生产排障
一句话理解： journalctl 是“带索引的系统日志查询器”：日志不是只按行存在文件里，而是带有 _SYSTEMD_UNIT、_PID、PRIORITY、_BOOT_ID、时间戳等字段的 journal entry。
安全原则： 查询命令默认只读；但 --vacuum-* 会删除已归档 journal 文件。清理前先运行 journalctl --disk-usage 和 journalctl --list-boots，确认你不会删掉仍需排障的历史启动日志。

1. journalctl 是什么

journalctl 用来读取 systemd-journald 收集的日志。它可以显示内核、系统服务、用户服务、stdout/stderr、syslog 兼容消息以及其他写入 journal 的结构化日志。

它擅长什么
按服务、启动轮次、时间、优先级、进程、用户、字段快速定位日志，并保留比纯文本更多的上下文。
它不只是 tail
tail -f /var/log/app.log 只跟一个文本文件；journalctl -fu nginx.service 按 systemd unit 跟随日志，自动合并该 unit 相关来源。
它的本质
查询 journal entry：每条日志包含消息正文和元数据字段，journalctl 根据字段索引筛选、排序、格式化输出。
# 查看当前用户可见的全部 journal，从最早记录开始
journalctl

# 查看当前启动以来的错误及更严重日志
journalctl -b -p err

# 查看某个服务最近 100 行并实时跟随
journalctl -u nginx.service -n 100 -f

# 查看今天的 SSH 服务日志
journalctl -u ssh.service --since today
环境前提： journalctl 主要存在于使用 systemd 的 Linux 发行版。macOS、传统 SysV init 系统或容器最小镜像中可能没有完整 journal。

2. systemd journal 模型

核心心智模型：journalctl 不是在某个日志文件里 grep，而是在结构化 journal 中查询字段。

3. 快速上手与输出控制

默认运行 journalctl 会显示调用用户可见的日志，并通常交给分页器查看。实际排障时更常用“限定范围”的查询：限定启动轮次、unit、时间、优先级和行数。

命令作用常见场景
journalctl -b当前启动以来的日志排查本次启动问题
journalctl -n 50最后 50 条快速查看最近事件
journalctl -r倒序显示，最新在前从最近错误开始看
journalctl --no-pager不进入分页器脚本、复制输出、CI 日志
journalctl -o short-isoISO 风格时间跨时区协作时减少歧义
# 当前启动以来的最近 80 条日志
journalctl -b -n 80

# 最新日志在前，并禁用分页器
journalctl -r -n 40 --no-pager

# 显示精确时间，便于和监控告警对齐
journalctl -b -o short-iso

# 显示 UTC 时间，适合跨地域排障
journalctl -b --utc -o short-iso
实用习惯： 排障不要先裸跑 journalctl 翻海量日志；先问“哪个服务、哪个时间、哪个启动轮次、什么严重程度”。

4. 权限、系统日志与用户日志

journal 的可见范围受权限控制。普通用户通常只能看自己的用户服务和部分系统日志；查看完整系统日志通常需要 root、sudo，或加入发行版配置的日志读取组。

命令含义注意点
journalctl --system查看系统服务和内核日志可能需要权限
journalctl --user查看当前用户的 user manager 日志依赖用户 journal 可用
sudo journalctl以管理员权限查看生产环境注意审计和最小权限
groups查看当前用户组某些发行版使用 adm 或 systemd-journal 组授权
# 查看自己能看到的范围
journalctl -n 20

# 查看系统日志，权限不足时再使用 sudo
journalctl --system -n 20
sudo journalctl --system -n 20

# 查看当前用户的 systemd 用户服务日志
journalctl --user -n 50
journalctl --user -u pipewire.service -n 50
权限现象： “没有日志”不一定代表服务没写日志，可能只是当前用户看不到。先对比 journalctl -n 5 与 sudo journalctl -n 5 的结果范围。

流程图：journalctl 如何叠加过滤条件

过滤思路：启动轮次和时间先缩小范围，unit/字段定位来源，优先级突出异常，最后再决定输出格式。

5. 字段匹配与过滤语义

journal entry 是字段集合。journalctl FIELD=VALUE 可以直接按字段匹配，例如 _PID=1234、_SYSTEMD_UNIT=nginx.service、SYSLOG_IDENTIFIER=sshd。

字段含义示例
MESSAGE人类可读的日志正文MESSAGE=Started OpenSSH server daemon
_SYSTEMD_UNITsystemd 系统 unit_SYSTEMD_UNIT=nginx.service
_SYSTEMD_USER_UNIT用户级 systemd unit_SYSTEMD_USER_UNIT=pipewire.service
PRIORITYsyslog 严重等级数字PRIORITY=3
_PID/_UID进程 ID / 用户 ID_PID=1234
_COMM/_EXE进程名 / 可执行文件路径_COMM=sshd
_BOOT_ID启动轮次 ID通常由 -b 间接使用

AND 与 OR 语义

不同字段的多个匹配通常是 AND；同一个字段的多个匹配通常是 OR。这个规则非常重要。

# unit 是 nginx.service 且优先级字段为 3
journalctl _SYSTEMD_UNIT=nginx.service PRIORITY=3

# 同一字段多个值：匹配 nginx.service 或 php-fpm.service
journalctl _SYSTEMD_UNIT=nginx.service _SYSTEMD_UNIT=php-fpm.service

# 查看当前 journal 中出现过哪些字段名
journalctl -N

# 查看某字段出现过的值，例如有哪些 systemd unit
journalctl -F _SYSTEMD_UNIT
字段查询建议： 不确定字段名时先用 journalctl -o verbose -n 1 看一条完整 entry，再用 -N 和 -F FIELD 探索可用字段。

6. 按 unit 和服务排查

服务排障时，-u/--unit 是最常用入口。它按 systemd unit 过滤，比 grep 服务名更可靠，因为它使用 journal 元数据，而不是文本包含关系。

命令含义
journalctl -u nginx.service查看 nginx systemd unit 日志
journalctl -u nginx很多系统会补全为 nginx.service，脚本中建议写完整 unit
journalctl -u nginx.service -b只看当前启动以来该服务日志
journalctl -u nginx.service -u php-fpm.service同时看多个相关服务
journalctl --user -u pipewire.service查看用户级 unit 日志
# 服务启动失败：先看状态，再看该 unit 当前启动日志
systemctl status nginx.service
journalctl -b -u nginx.service --no-pager

# 只看最近一次尝试附近的日志
journalctl -u nginx.service --since "15 min ago" -o short-iso

# 多服务联排：反向代理与后端一起看
journalctl -b -u nginx.service -u php-fpm.service -p notice

# 如果服务模板带实例名，完整写出实例
journalctl -u 'getty@tty1.service' -b
排障顺序： 对 systemd 服务，优先 systemctl status unit 看状态摘要，再 journalctl -u unit -b 看完整日志。不要先去猜日志文件路径。

7. 时间过滤

--since/--until 用来限定时间窗口。它们支持具体时间，也支持相对表达式。生产排障通常从告警时间点向前后扩展窗口。

写法含义示例
--since today今天零点以来journalctl --since today
--since yesterday昨天零点以来journalctl --since yesterday -p err
--since "2026-04-25 09:00"指定本地时间journalctl -S "2026-04-25 09:00"
--since "30 min ago"最近 30 分钟journalctl -S "30 min ago"
--until "2026-04-25 10:00"结束时间journalctl -S "09:00" -U "10:00"
# 告警发生在 14:03，先看前后 10 分钟
journalctl --since "2026-04-25 13:53" --until "2026-04-25 14:13" -o short-iso

# 当前启动中最近 20 分钟的 nginx warning 以上日志
journalctl -b -u nginx.service --since "20 min ago" -p warning

# 今天所有认证相关日志
journalctl --since today SYSLOG_IDENTIFIER=sshd

# 使用短选项：-S 等价于 --since，-U 等价于 --until
journalctl -S "1 hour ago" -U now
时间注意： 默认按本地时区解释和显示时间。多人跨时区协作时，建议统一使用 --utc -o short-iso 或在记录中明确时区。

8. 优先级与严重程度

journal 兼容 syslog 优先级，数字越小越严重。-p 可以按严重级别过滤，常用于从海量正常日志中突出异常。

数字名称含义常用程度
0emerg系统不可用极少但最高优先级
1alert必须立即处理严重告警
2crit严重条件关键服务失败
3err错误最常用异常入口
4warning警告排查隐患
5notice重要但正常服务状态变化
6info普通信息默认常见日志
7debug调试信息通常很吵
# 当前启动以来所有错误及更严重日志
journalctl -b -p err

# warning 到 emerg，即 0..4
journalctl -b -p warning

# 只看 nginx 的错误
journalctl -b -u nginx.service -p err

# 指定范围：info 到 warning 这种写法用于排除 debug
journalctl -p info..warning
解释细节： -p err 通常表示显示 err 及更严重级别，而不是只显示数字 3。需要精确字段匹配时可用 PRIORITY=3。

9. 实时跟随与最近日志

-f/--follow 类似 tail -f，但它跟随的是 journal 查询结果。配合 -u、-p、--since 可以把实时流限制在需要的范围。

# 跟随某服务，先显示最近 50 条
journalctl -u nginx.service -n 50 -f

# 只跟随当前启动以来该服务 warning 以上日志
journalctl -b -u nginx.service -p warning -f

# 跟随所有系统日志，适合刚复现问题时观察
sudo journalctl -f

# 不想先刷历史，只看新日志
journalctl -u nginx.service -n 0 -f
-n
先显示最近 N 条，默认值通常足够但生产中建议显式写出。
-f
持续等待新 entry；用 Ctrl + C 退出。
--no-tail
和 -f 配合时可从查询开头显示，而不是只显示尾部。
实时排障提示： journalctl -f 在繁忙机器上可能非常吵。优先加 -u、SYSLOG_IDENTIFIER=、_PID= 或 -p 限制范围。

信息图：启动轮次与时间线

启动轮次让“上次为什么宕机/重启失败”这类问题可查询，而不是只能看当前运行状态。

10. 按启动轮次查看

-b/--boot 用来查看某次系统启动中的日志。当前启动是 -b 或 -b 0；上一次启动是 -b -1。这对排查重启、内核 panic、服务启动失败尤其关键。

# 列出可查询的启动轮次
journalctl --list-boots

# 当前启动
journalctl -b
journalctl -b 0

# 上一次启动
journalctl -b -1

# 上一次启动中的错误
journalctl -b -1 -p err

# 当前启动的内核日志
journalctl -k -b
问题建议命令原因
机器刚刚异常重启journalctl -b -1 -p warning当前启动可能看不到重启前错误
服务开机启动失败journalctl -b -u app.service限定当前启动的该 unit
内核或驱动异常journalctl -k -b -1只看上次启动内核消息
历史日志风险： 如果 journalctl --list-boots 只显示当前启动，可能是 journal 未持久化、已被清理，或权限不足。不要在未确认前执行 vacuum。

11. 内核、进程、用户与字段查询

除了 unit，journalctl 还可以按内核日志、进程名、PID、可执行路径、用户 ID、syslog 标识符等维度查询。字段查询让你能从“服务视角”切换到“进程视角”。

目标命令说明
内核日志journalctl -k类似 dmesg，但可结合时间、boot、priority
某 PIDjournalctl _PID=1234进程退出后也可查历史
某进程名journalctl _COMM=sshd按 comm 字段，不等于全文搜索
syslog 标识符journalctl -t sshd-t 等价于按 SYSLOG_IDENTIFIER 过滤
某用户 IDjournalctl _UID=1000常用于用户服务或会话问题
# 查看当前启动内核 warning 以上日志
journalctl -k -b -p warning

# 查看 sshd 最近一小时日志
journalctl -t sshd --since "1 hour ago"

# 查看某个 PID 的完整字段，便于理解它来自哪里
journalctl _PID=1234 -o verbose

# 查看 UID 1000 的用户相关日志
journalctl _UID=1000 --since today
字段与 grep 的区别： journalctl _COMM=sshd 只匹配进程名字段；journalctl | grep sshd 是文本包含，可能漏掉或误中。

12. 输出格式与 JSON

-o/--output 决定 journalctl 如何展示 entry。日常阅读用短格式，字段分析用 verbose，机器处理用 JSON 或 export。

格式用途示例
short默认短文本journalctl -o short
short-isoISO 风格时间journalctl -o short-iso
short-precise微秒级时间journalctl -o short-precise
cat只输出消息正文journalctl -o cat -u app.service
verbose显示完整字段journalctl -o verbose -n 1
json每条一行 JSONjournalctl -o json
json-pretty便于人读的 JSONjournalctl -o json-pretty -n 1
exportJournal Export Format迁移、取证、专用工具处理
# 看一条完整 entry 的所有字段
journalctl -u nginx.service -n 1 -o verbose

# 机器处理：每条日志一行 JSON，限制数量避免输出过大
journalctl -u nginx.service --since "10 min ago" -o json --no-pager

# 人类阅读 JSON
journalctl -u nginx.service -n 2 -o json-pretty

# 只输出 MESSAGE，适合和传统文本管道配合
journalctl -u nginx.service -o cat --since today
JSON 注意： journal 字段值可能包含二进制或数组式字段；严肃自动化建议用 jq 或 systemd 的 sd-journal API，而不是脆弱的正则解析。

13. 光标、分页与自动化脚本

journal entry 有 cursor，可以标识“读到哪里”。脚本需要增量消费日志时，cursor 比“最后一行文本”可靠得多。交互查看时则要理解分页器和输出数量。

选项作用使用场景
--show-cursor显示最后 entry 的 cursor记录增量位置
--after-cursor=...从某 cursor 之后读取日志采集脚本
--cursor-file=PATH读取并更新 cursor 文件周期性任务
--no-pager不使用分页器脚本和重定向
--no-hostname隐藏 hostname本机调试时减少噪声
# 显示最近 20 条并打印 cursor
journalctl -u app.service -n 20 --show-cursor

# 周期性增量读取示例：cursor 文件由 journalctl 维护
journalctl -u app.service \
  --cursor-file=/var/lib/mycollector/app.cursor \
  --since "1 hour ago" \
  -o json --no-pager

# 脚本中避免进入 less
journalctl -b -p err --no-pager > boot-errors.log
脚本建议： 自动化任务务必限制范围，例如 -u、--since、-n 或 cursor；避免每次全量扫 journal。

安全图：journal 存储与 vacuum 决策

vacuum 是删除操作，不是查看操作。先确认占用和保留需求，再清理归档文件，最后用配置建立长期上限。

14. 磁盘占用、持久化与 vacuum

journal 可以存在内存型路径 /run/log/journal，也可以存在持久化路径 /var/log/journal。是否保留跨重启日志取决于系统配置和目录状态。

主题命令或路径说明
查看占用journalctl --disk-usage显示 active 和 archived journal 文件占用总量
运行时日志/run/log/journal通常位于内存或临时文件系统，重启后消失
持久化日志/var/log/journal用于跨重启保留历史
配置/etc/systemd/journald.conf 与 journald.conf.d建议用 drop-in 管理本地策略
临时清理--vacuum-size/--vacuum-time/--vacuum-files清理已归档 journal 文件

安全清理流程

# 1. 只读检查：当前占用多少
journalctl --disk-usage

# 2. 只读检查：有哪些启动轮次，确认历史是否仍要保留
journalctl --list-boots

# 3. 如需保存关键窗口，先导出文本或 JSON
journalctl -b -1 -p warning --no-pager > previous-boot-warnings.log

# 4. 让当前活跃 journal 文件轮转为归档文件
sudo journalctl --rotate

# 5. 删除 14 天以前的归档 journal 文件
sudo journalctl --vacuum-time=14d

# 或者限制归档 journal 总量到 1G 左右
sudo journalctl --vacuum-size=1G

# 6. 再次确认
journalctl --disk-usage

长期保留策略示例

# 查看现有配置，不修改
systemd-analyze cat-config systemd/journald.conf

# 创建 drop-in 前先决定策略；以下只是示例
sudo mkdir -p /etc/systemd/journald.conf.d
sudo tee /etc/systemd/journald.conf.d/10-retention.conf <<'EOF'
[Journal]
SystemMaxUse=2G
MaxRetentionSec=30day
EOF

# 重启 journald 使配置生效
sudo systemctl restart systemd-journald.service
删除边界： --vacuum-* 主要清理归档 journal 文件；它不会按“某条日志内容”精确删除。合规或取证场景不要临时 vacuum，先走组织保留策略。

对比图：journalctl、tail、grep 怎么选

不要把 journalctl 当成 tail 的替代品，也不要把 grep 当成结构化查询器。三者各有边界。

15. journalctl vs tail/grep

维度journalctltailgrep/rg
数据源systemd journal具体文本文件文本文件或命令输出
过滤方式字段、unit、boot、时间、优先级行数和实时末尾文本正则匹配
上下文包含 PID、UID、unit、boot、精确时间等元数据取决于文件内容只知道文本匹配
实时-f-f通常配管道或文件扫描
机器输出JSON、export、verbose原始文本原始匹配行
# 错误示范：先全量输出再 grep，可能慢且丢失字段语义
journalctl | grep nginx

# 更好：先按 unit/时间/优先级过滤，再必要时文本搜索
journalctl -b -u nginx.service --since "1 hour ago" -p warning
journalctl -b -u nginx.service --since "1 hour ago" -o cat | grep 'upstream'

# 应用明确写到文件时，tail 仍然直接有效
tail -n 100 -f /var/log/myapp/app.log
实践结论： 对 systemd 管理的服务，先用 journalctl 结构化缩小范围；对应用私有文本日志，再用 tail/grep。

16. 常见排障场景

服务启动失败

# 看服务摘要
systemctl status app.service

# 看当前启动该服务的完整日志
journalctl -b -u app.service --no-pager

# 只看 warning 以上，减少噪声
journalctl -b -u app.service -p warning

机器异常重启或上次启动失败

# 有哪些历史启动
journalctl --list-boots

# 上一次启动末尾 200 条
journalctl -b -1 -n 200 -o short-iso

# 上一次启动的内核错误
journalctl -k -b -1 -p warning

登录失败、SSH 问题

# 不同发行版 unit 名可能是 ssh.service 或 sshd.service
journalctl -u ssh.service -u sshd.service --since today

# 按 syslog identifier 查询
journalctl -t sshd --since "2 hours ago"

# 只看认证失败文本，先结构化过滤再 grep
journalctl -t sshd --since today -o cat | grep -i 'failed'

日志太多、想定位错误尖峰

# 先看时间窗口内 warning 以上
journalctl --since "30 min ago" -p warning -o short-iso

# 再按 unit 或进程字段收窄
journalctl --since "30 min ago" -p warning -o verbose -n 5

为什么没有日志

服务没经过 systemd？
容器内进程、手工启动进程或应用私有日志可能不进 journal。
权限不够？
对比普通用户与 sudo journalctl。
时间/boot 查错？
加 --list-boots、-b、--since 重新限定。
journal 未持久化？
重启后历史可能在 /run 中消失，检查 /var/log/journal 和 journald 配置。

可复用的排障套路：时间、对象、启动轮次三件事先定下来，再组合查询。

17. 安全清理与运维清单

journalctl 的查询大多安全，但磁盘清理、服务重启、配置变更会影响系统行为。把查看、导出、删除、配置分开执行，能降低误操作风险。

只读检查清单

# 当前可见日志范围
journalctl -n 20

# 当前启动错误
journalctl -b -p err --no-pager

# 历史启动是否存在
journalctl --list-boots

# journal 占用
journalctl --disk-usage

# journald 配置合成结果
systemd-analyze cat-config systemd/journald.conf

清理前确认清单

  • 确认是否有事故取证、审计、合规或回溯需求。
  • 确认 --list-boots 中哪些历史启动还需要保留。
  • 先导出关键窗口日志，再执行 vacuum。
  • 清理后用 journalctl --disk-usage 验证结果。
  • 频繁磁盘压力应通过 journald.conf.d 保留策略解决，而不是人工反复删除。
不要这样做： 不要直接删除 /var/log/journal 下的文件来“清空间”。优先使用 journalctl --vacuum-* 和 journald 配置，让 systemd 按 journal 文件状态处理。

18. 学习路线与练习任务

第一阶段：会查

  • 理解 journal entry 是字段化日志。
  • 掌握 -b、-u、--since、-p、-n、-f。
  • 能用 --no-pager、-o short-iso 输出便于复制的日志。

第二阶段：会定位

  • 会用 --list-boots 查上次启动日志。
  • 会用 -o verbose 找字段，再用 FIELD=VALUE 查询。
  • 能区分 unit 过滤、进程字段过滤、文本 grep 的不同语义。

第三阶段：会运维

  • 知道持久化 journal 与运行时 journal 的区别。
  • 会安全执行 --disk-usage、--rotate、--vacuum-time/--vacuum-size。
  • 能用 journald.conf.d 建立长期保留策略。

练习

  1. 运行 journalctl -b -n 50 -o short-iso，识别最近日志的时间和来源。
  2. 选择一个正在运行的服务，执行 journalctl -u 服务名 -b -n 100。
  3. 用 journalctl -o verbose -n 1 找出一条日志的 _SYSTEMD_UNIT、_PID、PRIORITY。
  4. 用 journalctl --since "1 hour ago" -p warning 查看最近异常。
  5. 用 journalctl --list-boots 判断系统是否保留历史启动。
  6. 只读运行 journalctl --disk-usage，不要清理，先估算保留策略。
  7. 在测试机上练习 journalctl -f -n 0，同时重启一个无害服务观察日志。
# 一个完整练习：排查 cron 或 ssh 服务最近问题
journalctl --list-boots
journalctl -b -u cron.service -u crond.service --since today --no-pager
journalctl -b -u ssh.service -u sshd.service --since "2 hours ago" -p notice
journalctl -t sshd -n 20 -o verbose
