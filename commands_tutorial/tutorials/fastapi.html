FastAPI 中文教程：从 ASGI 心智模型到 AI 基础设施生产部署

这份教程面向后端工程、平台工程和 AI 基础设施场景，不把 FastAPI 当成“会自动生成 Swagger 的 Python Web 框架”，而是把它放回正确位置：它运行在 ASGI 服务器之上，依靠 Python 类型标注、依赖注入和 Pydantic 验证，把路由、请求解析、响应过滤、文档生成、生命周期管理和流式输出整合成一套高效率 API 开发模型。你会看到的不只是 CRUD，而是模型服务、检索网关、批处理任务入口、文件上传和流式推送等真实工程用法。

ASGI类型驱动DependsPydanticasync/syncStreamingUploadFileOpenAPI部署与观测
一句话心智模型： FastAPI = ASGI 应用壳 + 声明式参数解析 + Pydantic 输入/输出约束 + 依赖注入，本质上是在每次请求到来时，把“连接上下文、请求数据、共享资源、业务函数、响应格式”自动拼装起来。
工程实践原则： 先把接口契约、阻塞点、生命周期和部署边界想清楚，再写路由。很多 FastAPI 线上问题并不是“框架慢”，而是把阻塞 I/O、CPU 重任务、错误的 worker 策略或未受控的大文件流量塞进了错误位置。

1. FastAPI 适合什么场景

FastAPI 的强项不是“语法新潮”，而是非常适合把 Python 类型系统、异步 I/O、自动文档、请求校验和服务装配结合在一起。对 AI 基础设施来说，这很重要，因为模型网关、向量检索服务、推理任务编排、文件接入层、流式推送接口和内部运维 API 往往共享一套模式：大量 I/O、明确契约、快速演化、对性能和可观测性敏感。

很适合
模型推理 API、RAG 检索网关、内部平台 API、数据接入服务、异步编排入口、文件上传中转层。
中等适合
传统后台管理 API、移动端后端、Webhook 聚合器、需要 OpenAPI 驱动 SDK 的服务。
不建议直接硬扛
长时间 CPU 密集计算、超重离线任务、复杂事务型单体后台。此时需要队列、worker、专用计算服务或更完整的业务框架配合。
诉求FastAPI 的优势你仍需自己负责的部分
接口迭代快类型标注直连验证与文档版本管理、兼容性策略
高并发 I/OASGI + async 适合等待型负载数据库/外部 API 自身吞吐
AI 服务接入适合封装 embedding、rerank、LLM gateway模型加载、资源隔离、限流
多团队协作OpenAPI 与 schema 约束降低接口歧义统一错误码、日志、鉴权、SLO
边界意识： FastAPI 让“服务壳”写得很快，但不会替你解决架构问题。CPU 重推理、模型预热、对象存储回写、消息队列和 tracing 采集，仍然要按系统设计处理。

2. ASGI 心智模型

官方 ASGI 文档和 Uvicorn 文档强调：应用暴露的是一个 async callable，核心交互对象是 scope、receive、send。FastAPI 是在这个协议之上做“声明式 API 组装”。
工程翻译： 如果你理解 ASGI，就不会把 FastAPI 误当成“只能处理 JSON 的 Flask 替代品”。它本质上更接近一个协议感知、类型驱动的服务装配层。

4. 路由、路径参数、查询参数

FastAPI 的参数解析核心是：看函数签名。路径参数、查询参数、Header、Cookie、Body、Form、File 都能通过类型标注和辅助声明自动解析。

from typing import Annotated
from fastapi import FastAPI, Path, Query, Header

app = FastAPI()

@app.get("/models/{model_id}/search")
async def search(
    model_id: Annotated[str, Path(pattern="^[a-z0-9-]+$")],
    q: Annotated[str, Query(min_length=2, max_length=200)],
    top_k: Annotated[int, Query(ge=1, le=50)] = 5,
    x_trace_id: Annotated[str | None, Header()] = None,
):
    return {
        "model_id": model_id,
        "query": q,
        "top_k": top_k,
        "trace_id": x_trace_id,
    }
路径参数
决定资源定位，例如 /models/{model_id}。
查询参数
决定筛选与行为，例如 ?top_k=10。
Header
适合 trace id、认证 token、租户信息等横切上下文。
实务提醒： 不要把所有参数都塞进 JSON body。检索、分页、过滤、排序、调试开关等最好清晰地区分在 path/query/header/body 中，否则契约会很快失控。

5. Pydantic、验证与 response_model

FastAPI 的体验很大一部分来自 Pydantic。输入模型定义请求结构，输出模型定义返回契约。它不仅校验数据，也帮你防止“内部字段误泄露”。

from typing import Annotated
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()

class EmbedRequest(BaseModel):
    texts: list[str] = Field(min_length=1, max_length=32)
    normalize: bool = True

class EmbedResponse(BaseModel):
    model: str
    dimension: int
    vectors: list[list[float]]

class InternalVectorRecord(BaseModel):
    model: str
    dimension: int
    vectors: list[list[float]]
    raw_latency_ms: float
    backend_host: str

@app.post("/embed", response_model=EmbedResponse)
async def embed(req: EmbedRequest) -> InternalVectorRecord:
    return InternalVectorRecord(
        model="bge-small",
        dimension=384,
        vectors=[[0.1, 0.2, 0.3]],
        raw_latency_ms=12.4,
        backend_host="embed-worker-03",
    )
能力价值
请求体验证坏数据在进入业务代码前被挡住
响应过滤response_model 只暴露你允许暴露的字段
OpenAPI 联动schema 自动体现在 /docs 和生成客户端中
类型驱动开发编辑器、类型检查器、评审都更容易对齐
安全提醒： 如果你直接返回 ORM 对象、内部 DTO 或调试字典，而没有用 response_model 过滤，很容易把内部字段、调试信息、基础设施地址、评分细节直接暴露给调用方。

6. Depends 依赖注入

官方依赖文档强调：依赖和子依赖会被 FastAPI 自动求值，它们的参数声明也会整合进 OpenAPI。依赖注入在 FastAPI 里不是装饰品，而是“资源装配协议”。
from typing import Annotated
from fastapi import Depends, FastAPI, Header, HTTPException, Request

app = FastAPI()

class RequestContext(dict):
    pass

async def get_request_context(
    x_trace_id: Annotated[str | None, Header()] = None,
    x_tenant_id: Annotated[str | None, Header()] = None,
) -> RequestContext:
    if not x_tenant_id:
        raise HTTPException(status_code=400, detail="missing tenant id")
    return RequestContext(trace_id=x_trace_id, tenant_id=x_tenant_id)

def get_embed_client(request: Request):
    return request.app.state.embed_client

Ctx = Annotated[RequestContext, Depends(get_request_context)]

@app.get("/v1/query")
async def query(ctx: Ctx, embed_client=Depends(get_embed_client)):
    return {"tenant": ctx["tenant_id"], "backend": str(embed_client)}
推荐用法： 把鉴权、租户上下文、数据库 session、外部客户端、限流信息都收敛进依赖，handler 只关心业务变量。

7. async vs sync 端点

FastAPI 官方文档给的判断标准非常实用：如果第三方库要求你 await，就写 async def；如果是阻塞式库，就写普通 def；两者可以混用，FastAPI 会处理好调用方式。

场景建议原因
调用异步 HTTP / 异步数据库客户端async def能把等待时间让给事件循环
调用阻塞式 SDKdefFastAPI 会在线程池中处理，不阻塞主事件循环
CPU 密集推理或压缩都不该直接做应转移到进程池、任务队列、独立推理服务
import httpx
from fastapi import FastAPI

app = FastAPI()

@app.get("/async-rerank")
async def async_rerank():
    async with httpx.AsyncClient(timeout=5.0) as client:
        r = await client.post("http://rerank.internal/score", json={"q": "gpu"})
    return r.json()

@app.get("/sync-legacy")
def sync_legacy():
    # 假设 legacy_sdk 只有阻塞接口
    result = legacy_sdk.lookup("gpu")
    return {"result": result}
最常见误区： 在 async def 里直接调用阻塞数据库驱动、阻塞文件 I/O、time.sleep()、大模型本地推理。这会让事件循环假装“异步”，实际上吞吐急剧下降。

8. lifespan 生命周期：把共享资源放到应用启动/关闭边界

FastAPI 当前推荐用 lifespan 参数管理启动和关闭逻辑。官方文档明确说明：如果你提供了 lifespan，旧式 startup/shutdown 事件处理器将不再被调用。

from contextlib import asynccontextmanager
from fastapi import FastAPI
import httpx

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http = httpx.AsyncClient(timeout=10.0)
    app.state.model_registry = {
        "embed-small": {"dim": 384},
        "rerank-v1": {"max_batch": 16},
    }
    yield
    await app.state.http.aclose()
    app.state.model_registry.clear()

app = FastAPI(lifespan=lifespan)

@app.get("/models")
async def list_models():
    return app.state.model_registry
适合放进 lifespan 的资源
异步 HTTP 客户端、数据库连接池、模型元信息缓存、向量库客户端、配置快照、指标导出器。
不适合放进 lifespan 的内容
按请求变化的用户态数据、会持续无限增长的大缓存、必须随 tenant 动态隔离的对象。
AI infra 提醒： 预热大模型或 tokenizer 时，要非常明确启动时长与失败策略。启动前加载能减少首请求抖动，但也可能拖慢发布和探针通过时间。

9. BackgroundTasks：轻量收尾，不是离线计算平台

FastAPI 的 BackgroundTasks 很适合“响应已经可以先返回，但还要顺手做一点轻量工作”的场景，例如写审计日志、发通知、记录回执、提交一个短小的对象存储回写。官方文档也明确提醒：如果是重计算或需要跨进程/跨机器执行的任务，应考虑 Celery 一类队列系统。

from fastapi import BackgroundTasks, FastAPI, status

app = FastAPI()

def write_audit(job_id: str, tenant: str) -> None:
    with open("audit.log", "a", encoding="utf-8") as f:
        f.write(f"{job_id},{tenant}\n")

@app.post("/ingest", status_code=status.HTTP_202_ACCEPTED)
async def ingest(tenant: str, background_tasks: BackgroundTasks):
    job_id = "job-20260426-001"
    background_tasks.add_task(write_audit, job_id, tenant)
    return {"job_id": job_id, "status": "accepted"}
判断标准： 如果任务失败你希望立刻在本进程日志中看到，且任务与当前请求同生共死，可以用 BackgroundTasks。如果任务很重、很慢、必须重试、必须跨 worker 保证，那就上消息队列。

10. StreamingResponse：流式输出、SSE 风格接口与大响应

FastAPI 支持直接返回 StreamingResponse。官方文档说明它可以接收 async generator 或普通 generator，并特别提醒：对 async 生成器来说，要让取消生效，生成器需要有 await 机会。

import anyio
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

async def token_stream():
    for token in ["你", "好", "，", "世", "界"]:
        yield f"data: {token}\n\n".encode("utf-8")
        await anyio.sleep(0.05)

@app.get("/stream")
async def stream():
    return StreamingResponse(
        token_stream(),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache"},
    )
场景典型 media type说明
LLM token 流text/event-stream前端或 agent 逐段接收 token
JSONL 数据导出application/jsonl边算边吐，减少内存峰值
文件下载FileResponse直接走文件响应更合适
流式接口常见坑： 代理层缓冲、客户端超时、生成器里没有 await、异常被吞掉后连接悬挂、日志里只看到 200 却看不到中途断流。

11. 文件上传与大文件策略

FastAPI 官方文档区分得很清楚：bytes = File() 会把整个文件内容读入内存；UploadFile 则基于 spooled file，更适合较大文件，因为超过阈值后会落盘，并带有文件对象接口与元数据。

from typing import Annotated
from fastapi import FastAPI, File, Form, HTTPException, UploadFile

app = FastAPI()

@app.post("/datasets/upload")
async def upload_dataset(
    tenant: Annotated[str, Form()],
    file: Annotated[UploadFile, File(description="训练样本或评测集")],
):
    if file.content_type not in {"text/csv", "application/json"}:
        raise HTTPException(status_code=415, detail="unsupported content type")

    target = f"/tmp/{tenant}-{file.filename}"
    with open(target, "wb") as out:
        while chunk := await file.read(1024 * 1024):
            out.write(chunk)

    await file.close()
    return {"stored_at": target, "filename": file.filename}
小文件
bytes 简单直接，但会占用整块内存。
大文件
UploadFile 更稳，适合图片、压缩包、模型片段、日志归档。
混合表单
文件上传走 multipart/form-data，不能同时把同一请求体当作 JSON body 解析。
安全与容量提醒： 限制 MIME、扩展名、大小、租户配额，并在反向代理和应用两层都配置上传限制。不要把对象存储落地路径直接暴露给未授权调用方。

12. 认证与授权基础

FastAPI 自带一套安全工具，能把认证参数与 OpenAPI 文档整合起来。最基础的 mental model 是：认证负责“你是谁”，授权负责“你能做什么”。不要把能在 /docs 点 Authorize 当成安全方案本身，那只是文档 UI 对接。

from typing import Annotated
from fastapi import Depends, FastAPI, HTTPException, status
from fastapi.security import OAuth2PasswordBearer

app = FastAPI()
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")

def decode_token(token: str) -> dict:
    if token != "demo-token":
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="invalid token",
            headers={"WWW-Authenticate": "Bearer"},
        )
    return {"sub": "alice", "roles": ["reader"], "tenant": "acme"}

@app.get("/me")
async def me(token: Annotated[str, Depends(oauth2_scheme)]):
    return decode_token(token)

@app.get("/admin/jobs")
async def admin_jobs(token: Annotated[str, Depends(oauth2_scheme)]):
    claims = decode_token(token)
    if "admin" not in claims["roles"]:
        raise HTTPException(status_code=403, detail="forbidden")
    return {"jobs": []}
层次应该校验什么
认证token 是否有效、是否过期、签名是否合法
授权角色、租户、资源范围、操作类型
审计谁在何时对哪个资源执行了什么操作
实战提醒： 只做“有 token 就过”远远不够。AI infra 常见越权问题是：A tenant 能调用 B tenant 的数据集、模型、索引、异步任务或日志下载接口。

13. OpenAPI、/docs 与契约先行

FastAPI 的 OpenAPI 能力不是附赠品，而是协作效率核心。依赖参数、请求模型、响应模型、错误码和安全方案都可以进契约。内部平台、Agent SDK、前端、测试平台都能直接消费它。

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI(
    title="Inference Gateway",
    version="2026.04",
    summary="统一接入 embedding / rerank / generation",
)

class GenerateRequest(BaseModel):
    prompt: str
    max_tokens: int = 256

class GenerateResponse(BaseModel):
    output: str
    trace_id: str

@app.post(
    "/v1/generate",
    response_model=GenerateResponse,
    tags=["generation"],
    summary="调用生成模型",
)
async def generate(req: GenerateRequest) -> GenerateResponse:
    return GenerateResponse(output="hello", trace_id="tr-001")
为什么这对 AI infra 尤其重要： 你通常会有多种消费者：前端控制台、批处理作业、Agent、SDK、回归测试脚本。契约不稳定时，发布成本会放大得很快。

14. 错误处理、HTTPException 与 422 验证失败

FastAPI 内置了常见异常处理。最常见的两类错误是业务侧主动抛出的 HTTPException，以及请求数据不合法时框架触发的 RequestValidationError。后者默认表现为 422。

from fastapi import FastAPI, HTTPException, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse

app = FastAPI()

@app.get("/jobs/{job_id}")
async def get_job(job_id: str):
    if job_id != "job-1":
        raise HTTPException(status_code=404, detail="job not found")
    return {"job_id": job_id}

@app.exception_handler(RequestValidationError)
async def handle_validation_error(request: Request, exc: RequestValidationError):
    return JSONResponse(
        status_code=422,
        content={
            "code": "INVALID_REQUEST",
            "detail": exc.errors(),
            "path": str(request.url.path),
        },
    )
状态码典型含义
400请求格式对，但业务上缺必要条件
401未认证或认证失败
403已认证但无权限
404资源不存在
409状态冲突，如重复任务提交
422请求参数/Body 验证不通过
503下游模型、向量库、依赖服务不可用
不要把所有错误都包成 500： 这会让调用方无法区分“请求错了”和“服务坏了”，也会让重试、告警、SLO 统计全部失真。

15. 性能优化：先找阻塞点，再谈框架快慢

FastAPI 通常不是系统的首要瓶颈。真正影响吞吐和尾延迟的，多半是阻塞 I/O、序列化成本、无上限并发、数据库连接池、错误的 worker 数和过大的响应体。官方响应文档还特别提到：如果追求默认 JSON 路径上的最好性能，优先使用 response model 和正常返回值，而不是到处手写 JSONResponse。

事件循环
避免在 async def 中做阻塞调用。
连接池
HTTP/DB/Redis 客户端应复用，而不是每请求创建。
批量化
embedding / rerank 请求常能通过 batch 降低总开销。
响应大小
能流式就流式，能裁剪字段就裁剪字段。
问题常见表现处理方向
阻塞 I/OQPS 一高整体卡顿改 async 客户端或移到线程池/队列
CPU 重任务单 worker 打满 CPU，尾延迟飙升单独推理服务、进程池、GPU worker
序列化大 JSON返回耗时异常高减少字段、用流式或文件输出
连接池不足请求等待下游连接调池大小并做压测
过度 worker内存翻倍、上下文切换多基于 CPU/内存/依赖负载压测决策

uvicorn main:app --workers 1
uvicorn main:app --workers 4
性能反模式： 用一个 FastAPI 进程既做 HTTP 接入，又在同进程里跑大型本地推理、Pandas 大聚合、ZIP 解压和对象存储上传。这样压测结果几乎无法解释。

16. 生产部署：uvicorn、gunicorn、反向代理与 worker 策略

Uvicorn 官方部署文档给出的通用建议是：开发用 uvicorn --reload，生产可用 gunicorn -k uvicorn.workers.UvicornWorker，自托管场景通常在前面再放 Nginx。
# 本地开发
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000

# 直接多 worker 运行
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4

# 经典生产方式
gunicorn -k uvicorn.workers.UvicornWorker -w 4 app.main:app

# 代码内启动时，若使用 reload 或 workers，放进 __main__ 守卫
if __name__ == "__main__":
    import uvicorn
    uvicorn.run("app.main:app", host="0.0.0.0", port=8000)
部署判断： 选择 worker 数时，不看“别人都配 4”，而看你的负载是 I/O 密集还是 CPU 密集、单进程内存多大、是否持有大型模型、是否要和 GPU/数据库连接池竞争资源。

17. 可观测性：日志、指标、trace、健康检查

FastAPI 代码写得再优雅，如果没有请求级日志、错误聚合、核心指标和可验证的健康端点，线上排障仍然会很痛苦。对 AI 服务来说，还要特别记录模型名、租户、batch size、下游耗时、缓存命中率和超时来源。

import time
from fastapi import FastAPI, Request

app = FastAPI()

@app.middleware("http")
async def timing_middleware(request: Request, call_next):
    started = time.perf_counter()
    response = await call_next(request)
    elapsed = time.perf_counter() - started
    response.headers["X-Process-Time"] = f"{elapsed:.6f}"
    return response

@app.get("/healthz")
async def healthz():
    return {"status": "ok"}

@app.get("/readyz")
async def readyz(request: Request):
    http = getattr(request.app.state, "http", None)
    return {"ready": http is not None}
日志
至少记录 trace id、tenant、route、status、latency、downstream error。
指标
QPS、P95/P99、422/5xx 比例、下游超时、队列堆积、worker 内存。
追踪
跨网关、向量库、模型服务时，没有 trace 基本很难定位尾延迟来源。
经验判断： /healthz 只回答“进程活着”，/readyz 回答“依赖已就绪，可以接流量”。两者不要混为一谈。

18. FastAPI vs Flask vs Django

这不是绝对优劣，而是匹配问题：FastAPI 更像“现代 Python API 平台层”，Flask 更像“轻框架拼装底座”，Django 更像“业务系统全家桶”。
维度FastAPIFlaskDjango
自动 schema / 文档强通常靠扩展API 方向需额外组件
异步能力强可做但不是核心心智逐步增强，但整体更重
后台管理与 ORM需自行组合需自行组合原生强项
AI infra API 壳很合适能做但要补很多约束多数场景偏重

19. 常见故障排查

排查顺序建议：先看请求契约，再看阻塞点，再看生命周期资源和部署层超时/缓冲。不要一上来就怪 FastAPI。
症状：/docs 正常但业务慢
通常不是路由表问题，而是下游依赖、连接池、CPU、锁竞争或大响应序列化。
症状：上线后首请求慢
多半与模型预热、连接初始化、懒加载 tokenizer、DNS、TLS 建链有关。
症状：上传大文件 413/502
检查反向代理体积限制、超时、应用端分块写入与对象存储回写路径。
症状：流式接口看似 200 但客户端没收到全量
检查代理缓冲、客户端读取方式、生成器取消点、日志是否按 chunk 记录。
症状：422 意外增多
一般是 schema 变更、字段位置改了、query/body/form 混淆、客户端未升级。
症状：多 worker 内存爆炸
每个 worker 各自加载模型或大缓存；应分离推理层或缩小进程内常驻对象。

最小排障动作

# 1. 先看契约是否按预期
curl -s http://127.0.0.1:8000/openapi.json | jq '.paths | keys'

# 2. 看服务是否只是“活着”还是“准备好”
curl -s http://127.0.0.1:8000/healthz
curl -s http://127.0.0.1:8000/readyz

# 3. 本地单 worker 重现，再比较多 worker
uvicorn main:app --workers 1
uvicorn main:app --workers 4

# 4. 针对流式接口，直接看原始输出
curl -N http://127.0.0.1:8000/stream
