1. gpustat 是什么

gpustat 是一个面向 NVIDIA GPU 的命令行状态查看工具。它通常通过 Python 包安装，底层读取 NVIDIA 管理库（NVML）或相关 Python binding，再把每张 GPU 的状态压缩成一行，显示主机名、GPU 索引、型号、温度、利用率、显存占用和使用进程。

它擅长什么
训练前看哪些卡空闲、训练启动时盯显存增长、定位占卡用户、快速发现 util 为 0 但显存被占满的异常。
它不擅长什么
驱动安装诊断、GPU 拓扑、MIG 全量管理、ECC 细节、复杂性能剖析、长期时序监控和告警。
它的定位
人眼扫视优先，脚本集成次之；它不是 Prometheus exporter，也不是 CUDA profiler。
# 最常用：查看当前节点全部 GPU 的紧凑状态
gpustat

# 显示更多进程字段，例如 PID、用户、命令、功耗等
gpustat -cpuP

# 每 2 秒刷新一次，适合观察训练启动和显存释放
gpustat -i 2

# 输出 JSON，适合集成脚本
gpustat --json
版本提醒： gpustat 不同版本的短选项组合可能略有差异。生产脚本应优先使用长选项并在目标镜像里执行 gpustat --help 固化行为。

信息图：gpustat 在 AI Infra 中的位置

gpustat 的价值在“压缩认知成本”：你不需要每次展开完整 nvidia-smi 表格，就能判断节点是否适合跑任务。

2. 安装与环境检查

gpustat 依赖 NVIDIA 驱动和 Python 环境。安装本身通常很简单，但在 AI 平台里更重要的是确认它运行在正确的 Python 环境、容器能看到 GPU、NVML 可访问。

步骤命令判断标准
确认驱动可用nvidia-smi能列出 GPU、驱动版本、CUDA runtime 兼容信息。
安装 gpustatpython -m pip install gpustatgpustat --help 可执行。
确认命令位置command -v gpustat路径来自预期 venv、conda env 或系统环境。
确认容器权限gpustat容器内能看到被分配的 GPU，而不是报 NVML 初始化失败。
# 推荐：在明确的 Python 环境中安装
python -m pip install --upgrade gpustat

# 检查版本和帮助
gpustat --version
gpustat --help

# 如果命令找不到，先确认安装位置
python -m pip show gpustat
python -m site --user-base
command -v gpustat
镜像建议： 训练镜像里可以预装 gpustat，但不要把它当作 GPU 驱动依赖的替代品。驱动和 NVML 来自主机或 NVIDIA container runtime 暴露。

3. 基本输出如何读

一次普通输出通常包含主机名、查询时间、GPU 索引、型号、温度、利用率、显存占用和进程列表。不同版本和选项的字段会变化，但读法一致：先看卡号，再看显存和 util，最后看进程归属。

$ gpustat
node-a  Sat Apr 25 18:20:11 2026
[0] NVIDIA A100-SXM4-80GB | 41'C,  92 % | 61440 / 81920 MB | alice(60210, 59800M)
[1] NVIDIA A100-SXM4-80GB | 38'C,   0 % |   512 / 81920 MB |
[2] NVIDIA A100-SXM4-80GB | 67'C,  98 % | 79012 / 81920 MB | bob(7412, 78500M)
[3] NVIDIA A100-SXM4-80GB | 36'C,   0 % |     0 / 81920 MB |
字段含义AI Infra 判断
[0]GPU index和 CUDA_VISIBLE_DEVICES、调度器分配、容器内可见编号一起核对。
41'CGPU 温度训练中升温正常；长期高温且 util 高可能是散热压力，util 低但高温要查风道或残留进程。
92 %GPU compute util训练主循环中高 util 通常正常；长期 0% 但显存大说明进程 idle、卡住或只占显存。
61440 / 81920 MB已用显存 / 总显存判断是否能放下新任务；注意框架缓存和碎片化不等于真实张量占用。
alice(60210, 59800M)用户、PID、进程显存定位谁占卡，下一步用 ps、pstree 或调度器命令确认任务归属。
不要只看显存： GPU 已占显存但 util 为 0% 不一定是“坏任务”，可能是数据加载、checkpoint 保存、评估阶段或等待分布式同步。判断异常要结合时间窗口和任务日志。

4. 常用选项速查

日常使用中，gpustat 的关键选项可以分成四类：展示更多字段、定时刷新、机器可读输出、颜色控制。下面的表按用途组织，具体短选项以 gpustat --help 为准。

用途常见写法说明
显示用户gpustat -u 或 gpustat --show-user显示占用 GPU 的用户名，适合共享节点。
显示 PIDgpustat -p 或 gpustat --show-pid定位进程后可接 ps -fp PID。
显示命令gpustat -c 或 gpustat --show-cmd区分 python train.py、vllm、torchrun 等。
显示功耗gpustat -P 或 gpustat --show-power辅助判断是否真的在计算，或是否被 power cap 限制。
定时刷新gpustat -i 2每 2 秒刷新，类似轻量 watch。
JSON 输出gpustat --json适合 jq、Python、巡检脚本。
关闭颜色gpustat --no-color日志、CI、文本解析中避免 ANSI 转义字符。
# 人眼巡检：尽量显示进程归属
gpustat -cpuP

# 日志或脚本：关闭颜色，避免解析混乱
gpustat --no-color

# 机器可读：JSON
gpustat --json
脚本建议： 能用 --json 就不要解析彩色文本；必须解析文本时加 --no-color，并把 gpustat 版本纳入镜像或部署约束。

流程图：watch 模式观察训练启动

watch 模式用于观察“变化趋势”，不是只看某一秒的截图。训练启动、模型加载、dataloader warmup、评估阶段的曲线都不同。

5. watch 模式与训练启动观察

gpustat -i 会按固定间隔刷新输出，适合在另一个终端里观察任务启动、显存释放、推理服务热加载和分布式任务是否均匀占卡。

# 每 1 秒刷新，适合观察启动瞬间
gpustat -i 1

# 每 5 秒刷新，适合长时间低频观察
gpustat -i 5

# 如果版本不支持 -i，也可以使用 watch
watch -n 2 --color gpustat

# 日志里记录快照，不要用彩色输出
while true; do
  date '+%F %T'
  gpustat --no-color
  sleep 30
done >> gpu-snapshot.log
观察形态常见原因下一步
显存快速上涨，util 稳定高位训练主循环正常运行继续看 loss、吞吐、step time。
显存上涨后 util 长期 0%等待数据、分布式同步、死锁、断点加载、评估或进程卡住查任务日志、CPU/IO、网络、nvidia-smi pmon、ps。
某些卡占用明显低rank 未启动、CUDA_VISIBLE_DEVICES 映射错、负载不均核对调度器分配、rank 日志、容器 GPU 可见性。
显存一直不释放进程仍存活、父子进程残留、服务常驻、框架缓存先确认 PID 和任务归属，不要直接 kill 别人的进程。
共享节点警告： 看到空闲卡不等于可以直接占用。生产集群必须以调度器分配为准，gpustat 只是观察工具，不是资源授权工具。

6. JSON 输出与脚本集成

--json 是把 gpustat 用进自动化的关键。文本输出适合人读，但列宽、颜色、进程格式、版本差异都不适合稳定解析。JSON 输出通常包含主机名、查询时间、GPU 列表、显存、利用率、功耗和进程信息。

$ gpustat --json
{
  "hostname": "node-a",
  "query_time": "2026-04-25T18:20:11",
  "gpus": [
    {
      "index": 0,
      "uuid": "GPU-...",
      "name": "NVIDIA A100-SXM4-80GB",
      "temperature.gpu": 41,
      "utilization.gpu": 92,
      "memory.used": 61440,
      "memory.total": 81920,
      "power.draw": 310,
      "enforced.power.limit": 400,
      "processes": [
        {"username": "alice", "pid": 60210, "command": "python", "gpu_memory_usage": 59800}
      ]
    }
  ]
}

用 jq 选出空闲卡

# 筛选显存低于 1GB 且 util 为 0 的 GPU index
gpustat --json | jq -r '
  .gpus[]
  | select(."memory.used" < 1024 and ."utilization.gpu" == 0)
  | .index
'

用 Python 做巡检摘要

#!/usr/bin/env python3
import json
import subprocess

raw = subprocess.check_output(["gpustat", "--json"], text=True)
data = json.loads(raw)

for gpu in data["gpus"]:
    used = gpu.get("memory.used", 0)
    total = gpu.get("memory.total", 0)
    util = gpu.get("utilization.gpu")
    procs = gpu.get("processes") or []
    owners = ",".join(sorted({p.get("username", "?") for p in procs})) or "-"
    print(f'{data["hostname"]} gpu={gpu["index"]} mem={used}/{total}MiB util={util}% owners={owners}')
JSON 兼容提醒： 字段名称来自 gpustat/NVML 暴露能力和版本实现。脚本应使用 dict.get()、处理 null，并在 CI 或镜像构建阶段固定 gpustat --version。

7. 进程、用户与命令映射

AI Infra 排障最常见的问题不是“GPU 忙不忙”，而是“谁让它忙、这个 PID 属于哪个任务、能不能安全处理”。gpustat 能给出第一层线索，但完整归因通常还要结合 ps、容器、调度器和作业日志。

# 显示用户、PID、命令、功耗
gpustat -cpuP

# 对某个 PID 展开系统进程信息
ps -fp 60210
pstree -sap 60210 2>/dev/null || ps -o pid,ppid,user,stat,etime,cmd -p 60210

# 看进程打开的工作目录和命令行
readlink -f /proc/60210/cwd
tr '\0' ' ' < /proc/60210/cmdline; echo
你看到的现象可能解释确认方法
同一用户多个 PID 占一张卡DataLoader worker、torchrun rank、推理服务 worker看父子进程、启动命令、端口、日志。
PID 显示为 python 但不知道任务训练脚本、notebook、服务入口都可能是 python看 /proc/PID/cmdline、cwd、环境变量、调度器 job id。
进程属于 root容器内 root、系统服务、驱动相关进程映射容器 ID、Kubernetes pod、Slurm job。
gpustat 有显存但 ps 找不到 PID进程刚退出、权限不足、NVML 状态延迟、容器命名空间差异重复查询，使用 sudo nvidia-smi 或节点管理员权限确认。
不要直接 kill： 在共享训练节点上，处理 GPU 进程前先确认用户、作业 ID、业务影响和调度器状态。错误 kill 可能导致长时间训练损失 checkpoint 或破坏线上推理服务。

信息图：显存、利用率、功耗的组合解读

GPU 指标是组合判断题。显存、util、温度、功耗、进程、时间窗口缺一不可。

8. 显存、利用率、温度、功耗解释

AI 训练和推理中的 GPU 指标经常被误读。gpustat 的优势是把关键指标放在同一行，但你仍然需要理解每个指标的含义和边界。

指标它说明什么它不说明什么
显存已用当前进程在 GPU 上保留或使用的内存规模。不等于模型真实参数量，也不等于下一步不会 OOM。
GPU util采样窗口内 GPU 计算单元忙碌比例。不直接等于训练吞吐、kernel 效率或端到端性能。
温度当前热状态。不能单独判断性能问题，需结合功耗、频率和散热策略。
功耗当前板卡功耗或相对 power limit 的负载状态。不能解释所有性能瓶颈，通信等待时功耗可能下降。
进程显存每个进程对 GPU memory 的占用估计。容器、MIG、驱动版本可能影响可见性和精度。
# 组合查看：gpustat 看总览，nvidia-smi 看更细字段
gpustat -cpuP
nvidia-smi

# 周期性输出 nvidia-smi 的利用率和显存，便于和 gpustat 对照
nvidia-smi --query-gpu=index,name,utilization.gpu,memory.used,memory.total,power.draw,temperature.gpu \
  --format=csv -l 2
训练阶段差异： 模型加载时显存先涨，数据预处理时 util 可能低，反向传播时 util 和功耗上升，checkpoint 保存时 GPU 可能短暂 idle。不要用单点快照判定任务健康。

9. 集群节点快速巡检

在多节点训练平台中，gpustat 常被用于 SSH 批量巡检：快速知道哪些节点繁忙、哪些卡空闲、是否有异常残留进程。巡检脚本应只读、低频、可超时，避免给登录节点或 GPU 节点造成额外压力。

# nodes.txt 每行一个节点名
cat nodes.txt
gpu-a01
gpu-a02
gpu-a03

# 串行巡检，简单可靠
while read -r node; do
  echo "===== $node ====="
  ssh -o BatchMode=yes -o ConnectTimeout=3 "$node" 'gpustat --no-color' || echo "failed"
done < nodes.txt

# 并发巡检：限制并发，避免压垮登录节点
xargs -a nodes.txt -P 8 -I{} sh -c '
  echo "===== {} ====="
  ssh -o BatchMode=yes -o ConnectTimeout=3 "{}" "gpustat --no-color" || true
'

JSON 汇总节点空闲卡

#!/usr/bin/env bash
set -euo pipefail

while read -r node; do
  ssh -o BatchMode=yes -o ConnectTimeout=3 "$node" 'gpustat --json' |
    jq -r --arg node "$node" '
      .gpus[]
      | select(."memory.used" < 1024 and ."utilization.gpu" == 0)
      | "\($node) gpu=\(.index) free_mem=\(."memory.total" - ."memory.used")MiB"
    ' || true
done < nodes.txt
巡检边界： 空闲卡巡检结果只能作为观察，不应绕过 Slurm、Kubernetes、Ray、队列系统或内部资源平台直接抢占。

10. 调度器和容器场景

在容器和调度器环境里，GPU 编号和进程归属会多一层映射。你在容器内看到的 GPU [0] 可能不是宿主机物理 GPU 0；CUDA_VISIBLE_DEVICES、NVIDIA container runtime、MIG、调度器资源插件都会影响可见性。

环境gpustat 读数注意点建议确认命令
Docker / Kubernetes容器内只应看到分配给容器的 GPU；用户可能显示为 root。echo $CUDA_VISIBLE_DEVICES、Pod spec、容器运行参数。
Slurm作业内 GPU 编号可能被重映射；节点上可见所有作业进程。squeue、scontrol show job、SLURM_JOB_GPUS。
Ray / 多进程服务多个 worker 共享一张卡或多卡，进程名可能相似。Ray dashboard、worker 日志、端口、父子进程。
MIG显存和实例可见性依赖 NVML 暴露和 gpustat 版本。nvidia-smi -L、nvidia-smi mig -lgi。
# 容器内确认 GPU 可见性
echo "CUDA_VISIBLE_DEVICES=${CUDA_VISIBLE_DEVICES:-unset}"
gpustat
nvidia-smi -L

# Slurm 作业内确认资源
echo "SLURM_JOB_ID=${SLURM_JOB_ID:-unset}"
echo "SLURM_JOB_GPUS=${SLURM_JOB_GPUS:-unset}"
gpustat -cpu
编号规则： 面向用户的 GPU index 是上下文相关的。跨容器、跨节点、跨调度器沟通时，优先同时记录 hostname、GPU UUID、物理 index、容器内 index 和 job id。

11. 自动化脚本模式

把 gpustat 用进脚本时，优先按“只读、超时、JSON、容错、低频”的原则设计。脚本不应因为某个节点驱动异常就整体失败，也不应把瞬时空闲误判成可调度资源。

只读
gpustat 本身只读；脚本也应避免自动 kill、自动抢卡等副作用。
超时
SSH、容器 exec、节点命令都要设置超时，避免巡检挂死。
容错
NVML 初始化失败、节点离线、JSON 字段为空都要可降级。
#!/usr/bin/env bash
# gpu-health.sh：生成单节点 GPU 摘要，失败时返回非零但输出清晰错误
set -euo pipefail

if ! command -v gpustat >/dev/null 2>&1; then
  echo "ERROR: gpustat not found" >&2
  exit 2
fi

if ! json=$(timeout 5 gpustat --json 2>gpustat.err); then
  echo "ERROR: gpustat failed: $(cat gpustat.err)" >&2
  exit 3
fi

printf '%s\n' "$json" | jq -r '
  .hostname as $host
  | .gpus[]
  | [$host, .index, .name, ."memory.used", ."memory.total", ."utilization.gpu", ((.processes // []) | length)]
  | @tsv
'
工程化建议： 如果你需要长期监控、告警、历史曲线和多租户审计，应该使用 DCGM exporter、Prometheus、Grafana、调度器事件和日志系统；gpustat 更适合即时诊断和轻量巡检。

三者不是替代关系，而是不同层级的工具：快照、权威细节、交互视图。

12. gpustat vs nvidia-smi vs nvtop

工具优势劣势典型场景
gpustat输出紧凑；进程归属直观；JSON 简单；适合 SSH 批量。指标不如官方工具全；版本字段可能变化；不适合深度诊断。节点巡检、训练启动观察、共享 GPU 沟通。
nvidia-smiNVIDIA 官方；字段丰富；驱动、MIG、ECC、功耗、query 支持强。默认表格较宽；人眼快速扫多卡不如 gpustat。权威确认、脚本精确 query、驱动和设备排障。
nvtop交互式 TUI；实时曲线；进程视图更适合盯屏。不适合非交互脚本；集群批量巡检不方便。登录节点后人工观察负载变化。
DCGM exporter适合生产监控、Prometheus、长期时序和告警。部署成本更高，不是临时 one-liner。平台级监控和 SLO。
# gpustat 快速扫
gpustat -cpuP

# nvidia-smi 精确 query
nvidia-smi --query-gpu=index,uuid,name,utilization.gpu,memory.used,memory.total,power.draw \
  --format=csv

# nvtop 交互观察
nvtop
选择原则： 人看一眼用 gpustat；要权威字段或管理能力用 nvidia-smi；要实时交互曲线用 nvtop；要平台监控用 DCGM/Prometheus。

13. 排障流程

当 gpustat 输出看起来“不对”时，先分清是工具不可用、读数异常、任务异常还是调度冲突。不要把所有问题都归因到 GPU 本身。

gpustat 报 NVML 初始化失败

# 先用官方工具确认驱动可用
nvidia-smi

# 容器里确认是否挂载了 NVIDIA runtime
ls -l /dev/nvidia* 2>/dev/null || true
echo "${NVIDIA_VISIBLE_DEVICES:-unset}"

# Python 包问题时重装 gpustat
python -m pip install --upgrade --force-reinstall gpustat

显存占满但找不到进程

# 多查几次，排除进程刚退出和采样延迟
gpustat -cpu
sleep 2
gpustat -cpu

# 用 nvidia-smi 复核完整进程视图
nvidia-smi

# 有权限时查所有用户进程
ps aux | grep -E 'python|torchrun|vllm|triton|ray' | grep -v grep

util 长期低但任务说在跑

# 同时观察 CPU、IO、网络和日志推进
gpustat -i 2
top -H -p PID
iostat -xz 2 5 2>/dev/null || true
tail -f train.log
排障纪律： gpustat 快照只能证明“某一刻看到的状态”。要判断卡住、泄漏、性能下降，至少观察一段时间并关联任务日志。

14. 安全与协作规范

GPU 节点通常是昂贵共享资源，gpustat 会让资源占用变得透明，但透明不等于可以随意处置。平台团队应把它纳入协作规范，而不是靠口头约定。

查卡前
确认自己在正确节点、正确容器、正确调度上下文，不要把容器内 index 和宿主机 index 混用。
用卡前
以调度器分配为准；即使 gpustat 显示空闲，也不要绕过队列直接占卡。
处置前
确认 owner、job id、业务优先级、checkpoint 状态和是否有线上服务影响。
记录时
保留 hostname、时间、GPU index/UUID、PID、用户名、命令、调度器 job id。
# 安全地生成排障快照，便于发给 owner 或平台团队
{
  date '+%F %T %Z'
  hostname
  gpustat --no-color || true
  nvidia-smi --query-gpu=index,uuid,name,utilization.gpu,memory.used,memory.total,power.draw,temperature.gpu \
    --format=csv || true
} > gpu-incident-snapshot.txt
高风险操作： kill、nvidia-smi --gpu-reset、重启容器、驱逐 Pod、取消 Slurm job 都可能影响他人任务或线上服务。必须走平台权限和变更流程。

15. 常见坑与边界

坑 1：把空闲读数当成调度授权
空闲只是现象，资源归属必须看调度器。
坑 2：解析彩色文本
脚本里使用 --json；退而求其次也要加 --no-color。
坑 3：混淆 GPU 编号
容器内 [0] 不一定是宿主机物理 GPU 0，跨上下文请记录 UUID。
坑 4：只看 util 判断性能
高 util 不等于高吞吐，低 util 不一定异常。
坑 5：忽略进程阶段
加载、预处理、checkpoint、评估和分布式同步都会改变 GPU 曲线。
坑 6：忽略权限差异
普通用户、容器 root、宿主机 root 看到的进程信息可能不同。
坑 7：用 gpustat 做长期监控
长期监控应接 DCGM exporter、Prometheus 和告警系统。
坑 8：忘记版本差异
不同镜像里的 gpustat 字段和选项可能不同，生产脚本要固定版本。

最小排障模板

# 1. 先确认工具和驱动
gpustat --version
nvidia-smi

# 2. 看一段时间，不只看一帧
gpustat -i 2

# 3. 定位进程
gpustat -cpuP
ps -fp PID

# 4. 结合任务系统
squeue -u "$USER" 2>/dev/null || true
kubectl get pods -A -o wide 2>/dev/null | grep "$(hostname)" || true

16. 学习路线与练习任务

第一阶段：会读

  • 能解释 GPU index、显存、util、温度、进程列表分别代表什么。
  • 能用 gpustat -cpuP 找到占卡用户、PID 和命令。
  • 能说明为什么“显存高 util 低”不一定等于异常。

第二阶段：会查

  • 用 gpustat -i 2 观察训练启动，并记录显存和 util 的阶段变化。
  • 用 ps、/proc/PID/cmdline、调度器命令把 PID 映射到任务。
  • 用 nvidia-smi 复核 gpustat 看到的异常。

第三阶段：会集成

  • 用 gpustat --json 写一个只读巡检脚本。
  • 为 SSH 批量巡检加超时、并发限制和错误容忍。
  • 把 gpustat 快照纳入 GPU incident 模板，但不替代正式监控。

练习

  1. 运行 gpustat 和 nvidia-smi，对照每个字段。
  2. 用 gpustat -i 1 观察一个小模型脚本启动时显存变化。
  3. 用 gpustat --json | jq 输出每张卡的 index、memory.used、utilization.gpu。
  4. 写一个脚本，筛选显存低于 1GB 且 util 为 0 的 GPU。
  5. 在容器内外分别运行 gpustat，比较 GPU 编号和可见设备。
  6. 模拟节点列表，写一个 SSH 串行巡检脚本，并处理连接失败。
  7. 把一次异常快照保存成文件，包含时间、hostname、gpustat 和 nvidia-smi query。
# 练习：输出简洁 TSV 摘要
gpustat --json | jq -r '
  .hostname as $host
  | .gpus[]
  | [$host, .index, .name, ."memory.used", ."memory.total", ."utilization.gpu"]
  | @tsv
'
