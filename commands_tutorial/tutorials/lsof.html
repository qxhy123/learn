lsof 深度教程：AI Infra 中的文件、端口、库与资源占用排障

lsof 的名字来自 “list open files”。在 Linux/Unix 里，普通文件、目录、TCP/UDP socket、Unix socket、设备、共享库、被删除但仍占用磁盘的文件、内存映射对象都可以表现为“打开的文件”。这份教程面向 AI Infra 场景：训练进程、推理服务、数据加载器、NCCL/RDMA 网络、GPU 运行时库、checkpoint、日志与容器权限排障。

AI Infra打开文件端口排障lsof -pdeleted 文件GPU/runtime 库dataset/checkpoint权限边界ss/fuser/strace 对比
一句话理解： lsof 是“从进程视角看资源引用”的工具：只要某个进程还握着文件描述符或映射关系，lsof 就能把它暴露出来。
生产实践： 先用无副作用查询定位 PID、FD、端口和路径；需要结束进程、清理文件或卸载挂载点时，先确认影响面，再执行 kill、重启服务或运维变更。

1. lsof 是什么

在 Linux 中，“文件”不只指磁盘上的普通文件。进程打开的 TCP 连接、监听端口、Unix socket、设备节点、共享库、工作目录、根目录、内存映射文件、管道和匿名 inode，都可能以文件描述符或文件引用的形式存在。lsof 把这些引用按进程列出来。

它回答的问题
谁在占用这个端口？谁打开了这个 checkpoint？哪个进程还握着 deleted 日志？训练进程加载了哪个 CUDA/NCCL 库？
它不回答的问题
它不会告诉你系统调用发生的完整时间线，也不是高性能网络统计器；需要时应配合 strace、ss、perf、日志和应用指标。
AI Infra 价值
训练/推理服务通常同时持有数据集文件、checkpoint、端口、GPU 设备、运行时库和日志。lsof 能快速建立“PID 到资源”的地图。
# 查看某个进程打开了什么
lsof -p 12345

# 谁监听 8080 端口
lsof -nP -iTCP:8080 -sTCP:LISTEN

# 谁还占着已删除文件
lsof +L1

# 谁正在访问某个数据目录
lsof +D /mnt/datasets/imagenet
心智边界： lsof 是快照工具。它看到的是查询瞬间的打开状态；高频打开又立即关闭的文件，可能需要 strace、eBPF 或应用日志补充。

信息图：lsof 的整体心智模型

不要把 lsof 当成“列文件”的工具；它更像“进程资源引用表”。

2. 安装、权限与输出列

多数发行版可以从系统包安装 lsof。容器镜像为了精简经常不带它，排障镜像或宿主机工具箱通常需要单独准备。

# Debian/Ubuntu
sudo apt-get update && sudo apt-get install -y lsof

# RHEL/CentOS/Rocky/Alma
sudo yum install -y lsof
# 或
sudo dnf install -y lsof

# macOS
sudo lsof -iTCP:8080 -sTCP:LISTEN
列名含义AI Infra 解读
COMMAND进程名python、torchrun、tritonserver、ray、java
PID/USER进程 ID 与用户用于定位 worker、launcher、sidecar 或服务账户
FD文件描述符或特殊引用cwd 工作目录，txt 可执行文件，mem 映射库，12u 可读写 FD
TYPE对象类型REG 普通文件，DIR 目录，IPv4/IPv6 网络，CHR 字符设备，unix Unix socket
DEVICE/SIZE/OFF/NODE设备、大小、偏移或 inode定位磁盘、挂载点、deleted 文件和 inode 级占用
NAME路径或连接描述最常用字段：路径、端口、连接两端、(deleted) 标记
权限提醒： 普通用户通常只能完整看到自己的进程。生产排障经常需要 sudo lsof ...，否则结果可能缺失而不是报错。

3. 基础查询与常用选项

默认 lsof 输出可能非常大。生产上应尽量用 PID、端口、路径、用户或协议缩小范围，并用 -nP 避免 DNS 和服务名解析造成延迟。

命令用途说明
lsof -p PID按进程查询最适合定位训练/推理进程资源引用
lsof -nP -i列网络连接-n 不解析主机名，-P 不解析端口名
lsof /path/file谁打开了文件适合 checkpoint、日志、模型权重
lsof +D /dir递归查目录可能很慢，谨慎用于大数据集目录
lsof -u user按用户查询定位某个训练用户或服务账户
lsof -c name按命令前缀查询lsof -c python 可快速看 Python 进程
lsof -a ...AND 条件多个条件默认常有 OR 语义，-a 用于交集过滤
# 避免网络解析，生产上推荐默认带上
sudo lsof -nP -iTCP

# 某用户的 Python 进程打开了什么
sudo lsof -a -u train -c python

# 某个模型文件是否仍被服务持有
sudo lsof /models/llama/checkpoint.safetensors

# 某个目录是否被进程占用
sudo lsof +D /mnt/checkpoints/exp-042
性能习惯： +D 会递归遍历目录树；在包含百万级小文件的数据集目录上可能很重。能用具体文件、PID 或挂载点时，不要先上 +D。

4. 按 PID 排查：lsof -p

AI 任务排障最常用入口是先从 ps、nvidia-smi、调度系统或服务管理器拿到 PID，再用 lsof -p 还原它的资源占用。

# 从 nvidia-smi 找到占用 GPU 的 PID 后
sudo lsof -p 12345

# 只看这个 PID 的网络连接
sudo lsof -nP -a -p 12345 -i

# 只看普通文件、目录、库映射等非网络资源
sudo lsof -a -p 12345 | grep -E ' REG | DIR | mem '

# 多个 worker PID
sudo lsof -p 12345,12346,12347
FD 示例含义排障价值
cwd当前工作目录目录无法卸载或删除时，检查进程是否还在里面
txt可执行文件确认实际启动的是哪个 Python、server 或二进制
mem内存映射文件/共享库确认加载的 CUDA、cuDNN、NCCL、libtorch 路径
1w/2wstdout/stderr 写入目标找训练日志、容器日志或被删除日志占用
23r/24u普通 FD 及访问模式定位 dataset shard、checkpoint、socket、pipe
实战建议： 对长时间训练进程，先保存一份 sudo lsof -nP -p PID > lsof.PID.txt，后续再和异常时快照对比。

流程图：从端口异常到责任进程

端口排障优先使用 -nP，避免 DNS/服务名解析拖慢判断。

5. 端口与网络 socket

训练集群和推理服务常见端口问题包括：服务启动时报 Address already in use、NCCL worker 互联异常、Ray/etcd/Redis/Prometheus 端口冲突、Ingress 或 sidecar 监听预期不一致。

# 谁在监听 8080
sudo lsof -nP -iTCP:8080 -sTCP:LISTEN

# 查看所有监听中的 TCP 端口
sudo lsof -nP -iTCP -sTCP:LISTEN

# 查看某个进程的 TCP/UDP 连接
sudo lsof -nP -a -p 12345 -i

# 查看和某远端 IP 的连接
sudo lsof -nP -i@10.20.30.40

# UDP 端口，例如某些服务发现、监控或自定义通信
sudo lsof -nP -iUDP:8125
场景命令解释
推理服务端口冲突lsof -nP -iTCP:8000 -sTCP:LISTEN找到旧服务、残留 worker 或本地测试进程
多机训练连接异常lsof -nP -a -p PID -iTCP确认 worker 是否建立到 master/peer 的连接
端口看起来没占用但仍失败ss -ltnp 与 namespace 检查可能是容器网络命名空间、权限或协议族差异
lsof 与 ss： lsof 更擅长“端口对应哪个进程和 FD”；ss 更擅长大规模、高性能地看 socket 状态、队列和 TCP 细节。

6. deleted 文件占用磁盘

Linux 上删除文件只是移除目录项。如果进程仍打开该文件，磁盘空间不会释放，直到最后一个引用关闭。AI 训练中大日志、临时 shard、失败 checkpoint、tensor dump 被删除后仍占空间，是非常常见的磁盘告警原因。

# 找所有 link count 小于 1 的打开文件，常用于 deleted 排查
sudo lsof +L1

# 只看某个挂载点相关的 deleted 文件
sudo lsof +L1 /mnt/train

# 结合 grep 看 deleted 标记
sudo lsof -nP | grep '(deleted)'

# 定位某个 PID 的 deleted 文件
sudo lsof -p 12345 | grep deleted
现象lsof 线索处理方式
df -h 显示满，du -sh 找不到大文件lsof +L1 看到大文件 (deleted)让进程关闭文件、滚动日志、重启服务或优雅停止任务
训练日志被 rm 后空间不释放FD 可能是 1w、2w 或普通写 FD重启/重定向日志进程，修正 logrotate 策略
checkpoint 清理后仍占空间训练 worker 仍打开旧 checkpoint 或临时文件确认无恢复需求后停止对应 worker
不要盲目清空 FD： 网上常见 > /proc/PID/fd/N 可能破坏进程语义或正在写入的数据。生产上优先让应用关闭文件、触发日志 reopen、或按服务流程重启。

7. 数据集、checkpoint 与日志描述符

数据加载器通常有多个 worker 并行读取 shard；训练任务会周期性写 checkpoint；推理服务会 mmap 模型权重。lsof 能帮助判断“文件是否真的正在被使用”。

# 谁正在读某个数据 shard
sudo lsof /mnt/datasets/c4/train-000123.jsonl.zst

# 谁打开了某个 checkpoint 目录中的文件
sudo lsof +D /mnt/checkpoints/run-2026-04-25

# 查看训练进程 stdout/stderr 去向
sudo lsof -p 12345 | awk '$4 ~ /^[12]/ {print}'

# 查 safetensors/pt/bin 模型文件是否被推理服务持有
sudo lsof -p 23456 | grep -E '\.(safetensors|pt|bin|onnx)$'
数据集
关注 REG 文件、读取 FD、挂载路径和是否大量 worker 同时打开同一 shard。
checkpoint
关注写入中的临时文件、.tmp、.part、latest 链接和 deleted 状态。
日志
关注 1w、2w、应用日志文件与 logrotate 后的 (deleted)。
大目录提醒： 对对象存储挂载、NFS 或 FUSE 数据集目录执行 lsof +D 可能很慢，并给元数据服务制造压力。先缩小到具体文件或 PID。

8. GPU、驱动与运行时库

lsof 不能直接告诉你 GPU 显存占用；那是 nvidia-smi、rocm-smi、DCGM 等工具的职责。但它能回答另一些关键问题：进程打开了哪些 GPU 设备节点？加载了哪个 CUDA/cuDNN/NCCL/libtorch 库？是否仍引用旧版本库或被删除库？

# 查看进程打开的 NVIDIA 设备节点
sudo lsof -p 12345 | grep -E '/dev/nvidia|/dev/dri'

# 查看 CUDA/NCCL/cuDNN/libtorch 等运行时库映射
sudo lsof -p 12345 | grep -E 'libcuda|libcudart|libcudnn|libnccl|libtorch'

# 系统中谁打开了 GPU 设备
sudo lsof /dev/nvidia0 /dev/nvidiactl /dev/nvidia-uvm 2>/dev/null

# 库文件已升级或删除但进程仍映射旧 inode
sudo lsof -p 12345 | grep -E 'deleted|libcuda|libnccl'
线索可能含义下一步
/dev/nvidia0、/dev/nvidiactl进程和 NVIDIA 驱动设备有引用用 nvidia-smi 交叉确认 GPU/PID/显存
mem ... libnccl.so进程映射了 NCCL 库确认路径是否来自预期 conda/env/container image
mem ... (deleted)库文件更新或删除后，进程仍用旧 inode计划滚动重启，避免混用旧运行时
未看到设备节点权限不足、容器隔离或进程未实际触发 GPU 初始化检查容器设备挂载、runtime、权限和应用日志
库版本判断： ldd 看“新进程可能加载什么”，lsof -p 看“这个运行中的进程已经加载了什么”。二者在滚动升级和热修场景下可能不同。

9. Unix socket、共享内存与 IPC

分布式训练和推理栈里，进程间通信不仅是 TCP。Python multiprocessing、PyTorch DataLoader、Ray、Docker/containerd、systemd、Prometheus exporter、Unix domain socket、匿名 pipe 和共享内存都可能出现在 lsof 输出里。

# 查看某个 PID 的 Unix socket、pipe、共享内存线索
sudo lsof -nP -p 12345 | grep -E 'unix|FIFO|PIPE|memfd|/dev/shm|anon_inode'

# 谁打开了 /dev/shm 中的对象
sudo lsof +D /dev/shm

# 查看 Docker/containerd 相关 socket
sudo lsof -nP | grep -E 'docker.sock|containerd.sock'

# Ray 或本地控制面 socket
sudo lsof -nP | grep -E '/tmp/ray|raylet|plasma'
对象常见来源排查意义
/dev/shmPyTorch multiprocessing、NCCL、DataLoader、共享缓存判断共享内存是否被持有，是否与容器 --shm-size 不足相关
unix本机进程通信、runtime socket、sidecar定位服务控制面、agent 和本地代理连接
FIFO/PIPEshell 管道、日志收集、进程间流式传输判断进程是否阻塞在管道或日志链路
memfd/anon_inode现代 runtime、eventfd、epoll、匿名内存对象提示资源类型，但需要 strace/perf/日志进一步确认行为
解释边界： lsof 能列出 IPC 对象，但不能完整解释协议语义。看到 Unix socket 后，通常还要结合进程命令行、日志和服务拓扑。

用例图：按 AI Infra 问题选择 lsof 查询入口

如果你已经知道 PID，lsof -p 通常比全局扫描更快、更安全。

10. 容器、namespace 与权限

容器环境会改变 lsof 的观察视角。你在容器内看到的是容器命名空间内的进程和路径；在宿主机看到的是宿主机 PID、挂载路径和网络 namespace。两边结果可能都正确，但语义不同。

# 宿主机上查看容器进程打开文件
sudo lsof -p HOST_PID

# 在容器内查看当前命名空间视角
docker exec -it CONTAINER sh -lc 'lsof -nP -p 1'

# Kubernetes 中进入 Pod 排查
kubectl exec -it POD -- sh -lc 'lsof -nP -iTCP'

# 普通用户看不到完整结果时
sudo lsof -nP -p 12345
问题典型原因处理思路
容器内看不到宿主机上的 PIDPID namespace 隔离用宿主机 PID 查询，或进入目标 namespace
路径不一致bind mount、overlayfs、容器 rootfs同时记录容器内路径和宿主机 mountinfo
端口宿主机可见但容器内不可见网络 namespace、hostNetwork、端口映射分别在宿主机和容器内用 lsof/ss 查询
结果缺失权限不足或内核安全策略使用 sudo、debug container 或节点级排障工具
Kubernetes 提醒： 对 GPU 训练 Pod，最好同时记录 Pod 名、容器 ID、宿主机 PID、GPU UUID 和 lsof -p 快照，避免多层映射混淆。

11. 文件描述符上限与泄漏

长跑训练、数据服务和推理网关可能因为 FD 泄漏逐渐接近 ulimit -n，表现为 “Too many open files”、新连接失败、DataLoader worker 异常或 checkpoint 写入失败。

# 查看某个 PID 当前打开 FD 数量
sudo lsof -p 12345 | wc -l

# 更接近 FD 数量的内核视角
sudo ls /proc/12345/fd | wc -l

# 查看进程限制
cat /proc/12345/limits | grep -i 'open files'

# 简单观察 FD 数量变化
while true; do date; sudo ls /proc/12345/fd | wc -l; sleep 10; done
线索解释下一步
FD 数量单调增长可能存在文件/socket 泄漏按时间保存 lsof -p，比较新增路径或连接
大量 dataset shard FDDataLoader、缓存策略或文件句柄未关闭检查 worker 生命周期、prefetch、IterableDataset 实现
大量 TCP ESTABLISHED/CLOSE_WAIT连接管理异常配合 ss -tanp 和服务端日志定位
大量日志或临时文件 FD日志轮转或临时文件清理问题检查 logrotate、应用 reopen 机制、临时目录策略
修复顺序： 提高 ulimit -n 只能缓解容量问题，不能替代修复泄漏。先判断是正常高并发还是异常增长。

12. 挂载点、NFS、对象存储网关与 “busy”

AI 集群常用 NFS、Lustre、BeeGFS、CephFS、JuiceFS、S3 FUSE 或本地 NVMe RAID。卸载失败、目录删除失败、滚动升级卡住时，lsof 能定位仍在使用挂载点的进程。

# 谁正在使用某个挂载点下的文件
sudo lsof +f -- /mnt/datasets

# 递归目录查询，适合范围较小的目录
sudo lsof +D /mnt/datasets/project-a

# 当前工作目录在挂载点内的进程
sudo lsof | awk '$4 == "cwd" && $9 ~ "^/mnt/datasets" {print}'

# 卸载前先确认影响面
sudo lsof +f -- /mnt/checkpoints
mount | grep /mnt/checkpoints
卸载安全： 不要在未确认进程归属时强制卸载或杀进程。训练任务可能正在写 checkpoint；强制中断可能导致恢复点损坏或长时间重训。
网络文件系统提醒： lsof 查询本身也可能触发元数据访问。大规模目录优先按 PID、具体文件或挂载点查询，避免递归扫描全量数据集。

13. lsof vs ss/fuser/strace

这些工具经常一起出现，但用途不同。正确选择工具可以减少误判。

工具核心问题优势不足
lsof哪个进程打开了哪些资源？统一查看文件、端口、库、设备、deleted 文件快照型；高频事件可能错过
sssocket 当前状态如何？网络状态、队列、连接规模更强更快不覆盖普通文件、库、日志等资源
fuser谁正在使用这个文件/端口/挂载点？输出简洁，适合脚本和卸载前检查上下文少；不如 lsof 表达丰富
strace进程正在做哪些系统调用？时间线和失败 errno 清楚侵入性更高，输出大，生产需谨慎
nvidia-smi/rocm-smiGPU 设备和显存状态如何？GPU 专用信息准确不告诉你进程打开了哪些文件和库
# 端口归属：lsof 或 ss 都能看
sudo lsof -nP -iTCP:8080 -sTCP:LISTEN
sudo ss -ltnp 'sport = :8080'

# 挂载点 busy：lsof 给详细列表，fuser 给简洁 PID
sudo lsof +f -- /mnt/datasets
sudo fuser -vm /mnt/datasets

# 高频打开/失败：lsof 看不到时间线，用 strace 追踪
sudo strace -f -e trace=openat,close,connect -p 12345
组合原则： 先用 lsof 建立“谁持有什么”的资源图；网络深挖用 ss；文件/系统调用失败深挖用 strace；GPU 深挖用厂商工具。

排障图：AI Infra 中 lsof 的安全工作流

lsof 查询本身通常安全；真正有风险的是查询之后的 kill、清理、卸载和服务重启。

14. AI Infra 排障工作流

下面是可以直接用于值班排障的分支式流程。它假设你已经知道异常类型，但还不知道责任进程或资源引用。

端口冲突

PORT=8080
sudo lsof -nP -iTCP:${PORT} -sTCP:LISTEN
sudo ss -ltnp "sport = :${PORT}"

GPU 进程异常

PID=12345
nvidia-smi
sudo lsof -nP -p ${PID} | tee lsof.${PID}.txt
grep -E '/dev/nvidia|libcuda|libcudnn|libnccl|libtorch' lsof.${PID}.txt

磁盘满但找不到文件

df -h
sudo lsof +L1
sudo lsof +L1 /mnt/train

数据目录无法卸载或清理

MNT=/mnt/datasets
sudo lsof +f -- ${MNT}
sudo fuser -vm ${MNT}
记录模板： 每次线上排障建议保存：时间、节点名、PID、用户、命令行、lsof 查询命令、关键输出、后续操作和回滚方式。

15. 安全注意事项

不要把查询结果等同于权限授权
看到某进程占用端口或文件，不代表可以直接杀掉。先确认 owner、调度系统和服务影响面。
谨慎使用递归目录查询
+D 在大数据集、NFS、FUSE、对象存储挂载上可能很慢，并增加元数据压力。
小心输出中的敏感路径
lsof 可能暴露模型路径、用户目录、临时 token 文件、Unix socket 路径和内部 IP。
不要盲目修补 deleted 文件
对 /proc/PID/fd/N 写入或截断可能破坏应用状态。优先优雅关闭或重启。
权限不足会导致假阴性
没有 sudo 时，结果缺失很常见。排障报告中要写明查询权限。
容器视角要标清
同一个进程在宿主机和容器里 PID、路径、网络 namespace 可能不同。
# 安全 dry-run 风格：先观察，不改变系统状态
sudo lsof -nP -iTCP:8080 -sTCP:LISTEN
ps -fp PID
systemctl status SERVICE 2>/dev/null || true

# 需要停止进程时，先确认命令行和归属
ps -o pid,ppid,user,stat,lstart,cmd -p PID
危险操作必须确认： kill -9、强制卸载、删除 checkpoint、清空 FD、重启训练服务都可能造成数据损坏或任务失败。lsof 只负责提供证据，不替你做变更决策。

16. 常见坑与排障清单

坑表现处理
忘记 -nP查询网络连接很慢生产默认使用 lsof -nP ...
没有 sudo看不到其他用户进程或输出不完整用 root/debug 权限重查，并记录权限差异
误解 +D大目录查询卡住或压力大先按 PID、具体文件、挂载点查询
容器路径混淆宿主机路径和容器路径对不上同时记录 container ID、mount、host PID
把快照当时间线短暂打开的文件没被看到用 strace、eBPF、应用日志或循环采样补充
只看端口不看协议TCP/UDP 或 IPv4/IPv6 判断错明确 -iTCP、-iUDP、-sTCP:LISTEN
库升级后未重启进程仍映射旧库或 (deleted) 库计划滚动重启，确认新进程加载路径

排障清单

# 1. 明确入口
PID=12345
PORT=8080
PATH_TO_CHECK=/mnt/checkpoints/run-001

# 2. 保存快照
sudo lsof -nP -p ${PID} > lsof.${PID}.$(date +%Y%m%d-%H%M%S).txt

# 3. 查网络
sudo lsof -nP -a -p ${PID} -i

# 4. 查 deleted
sudo lsof -p ${PID} | grep deleted || true

# 5. 查运行时库
sudo lsof -p ${PID} | grep -E 'libcuda|libcudnn|libnccl|libtorch' || true

# 6. 查路径占用
sudo lsof +f -- ${PATH_TO_CHECK}

17. 练习任务

以下练习都以观察为主，不要求破坏系统状态。可以在测试机或本地容器中完成。

  1. 启动一个简单 HTTP 服务，用 lsof -nP -iTCP:PORT -sTCP:LISTEN 找到 PID。
  2. 打开一个日志文件持续写入，删除文件后用 lsof +L1 观察 (deleted)。
  3. 对一个 Python 进程执行 lsof -p，区分 cwd、txt、mem、普通数字 FD。
  4. 在容器内外分别查看同一服务端口，记录 PID 和路径差异。
  5. 找一个加载 CUDA/NCCL 的训练进程，确认运行中进程实际映射的库路径。
  6. 比较 lsof -nP -iTCP 与 ss -tanp 的输出差异。
# 本地端口练习
python3 -m http.server 18080 &
SERVER_PID=$!
sudo lsof -nP -iTCP:18080 -sTCP:LISTEN
kill ${SERVER_PID}

# deleted 文件练习：只在 /tmp 中做
mkdir -p /tmp/lsof-demo
sh -c 'while true; do date >> /tmp/lsof-demo/live.log; sleep 1; done' &
WRITER_PID=$!
rm /tmp/lsof-demo/live.log
sudo lsof -p ${WRITER_PID} | grep deleted
kill ${WRITER_PID}
练习安全： 上述练习只应在测试环境运行。不要对生产训练进程做删除文件、强制停止或压力型递归查询。

参考资料与延伸阅读

  • lsof(8) manual：选项、输出列、文件类型、网络选择器、+L、+D、+f 等说明。
  • Linux man-pages：proc(5)、socket(7)、unix(7)、capabilities(7)，用于理解 /proc/PID/fd、socket 和权限模型。
  • iproute2 文档与 ss(8) manual：用于网络 socket 状态、监听队列和连接细节排查。
  • fuser(1) 与 strace(1) manual：分别用于资源使用者快速定位和系统调用时间线追踪。
  • NVIDIA/DCGM 或 ROCm 官方工具文档：用于 GPU 设备、显存、驱动和运行时状态的专用排查。

建议阅读顺序：先理解“一切皆文件”和 FD 模型，再掌握 -p、-i、路径查询、+L1，最后学习容器 namespace、GPU 库映射和跨工具组合。
