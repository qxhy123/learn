1. smartctl 是什么

smartctl 来自 smartmontools，用于查询和控制磁盘的 SMART、SCSI/SAS log sense、NVMe health log、自检和错误日志。它常被用在节点巡检、故障盘定位、RMA 证据收集、性能异常 triage 和数据迁移前检查。

它能回答
设备是否报告健康异常？是否有重映射扇区、不可纠正错误、介质错误、温度过高、寿命耗尽或自检失败？
它不能保证
SMART 显示 PASSED 不代表一定安全；很多故障来自线缆、背板、控制器、固件、文件系统或上层服务。
它的定位
底层设备证据采集工具，通常和 dmesg、journalctl、lsblk、nvme、RAID 工具、监控系统一起使用。
# 查看某块盘的完整健康与日志摘要
sudo smartctl -a /dev/sda

# NVMe 设备也可以用 smartctl 读取健康日志
sudo smartctl -a /dev/nvme0n1

# 更详细输出，包含更多日志页和厂商信息
sudo smartctl -x /dev/sda
重要心智模型： smartctl 读到的是设备和控制器暴露出来的信号；不同厂商、协议、固件版本的字段含义和阈值不完全相同。

2. AI Infra 为什么必须关注磁盘健康

AI 基础设施里的磁盘故障不只是“坏一块盘”。它可能表现为 checkpoint 写入抖动、数据集读取长尾、训练作业挂起、分布式存储恢复风暴、GPU 空转、节点被调度器误判健康，甚至导致多副本系统在 rebalance 时进一步放大 IO。

训练节点
本地 NVMe 常用于数据缓存、临时 shard、checkpoint staging；低层介质错误会变成 GPU 利用率下降。
存储节点
HDD/SSD 盘组承载对象存储、Ceph、Lustre、BeeGFS 或 NFS；坏盘误判会触发恢复和副本迁移。
日志节点
高写入量导致 SSD 磨损、温度上升、写放大和延迟抖动。
调度系统
SMART 信号可用于 cordon/drain、自动报修、节点健康评分和容量规划。
# AI 节点 triage 常用组合：硬件健康 + 内核 IO 错误 + 块设备拓扑
sudo smartctl -a /dev/nvme0n1
journalctl -k -p warning..alert --since "2 hours ago"
lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,ROTA,MOUNTPOINTS
实践建议： 把 SMART 异常当作“需要操作的证据”，而不是“仪表盘上的红点”：结合业务延迟、错误率、恢复状态和副本安全性决定是否下线。

信息图：smartctl 在 AI Infra 存储排障中的位置

业务层只看到“慢”和“错”；smartctl 负责把问题落到磁盘健康证据，但最后决策仍要结合系统和集群状态。

3. 安装与权限

大多数发行版通过 smartmontools 包提供 smartctl。读取底层设备通常需要 root 权限，因为命令会向块设备发送 ATA/SCSI/NVMe 管理命令。

# Debian / Ubuntu
sudo apt-get update
sudo apt-get install smartmontools

# RHEL / CentOS / Rocky / Alma
sudo dnf install smartmontools

# 验证版本与基础可用性
smartctl --version
sudo smartctl --scan
命令作用备注
smartctl --scan列出可能支持 SMART 的设备比盲猜 /dev/sdX 更安全
smartctl --scan-open尝试打开设备并给出推荐参数适合排查 USB、RAID、HBA
smartctl -i DEV只看设备身份信息确认型号、序列号、协议
权限建议： 自动化采集可以通过 root 运行的 exporter 或受控 sudoers 规则实现；不要给普通用户开放任意块设备写入权限。

4. 发现磁盘与设备名

AI 集群节点里常同时存在系统盘、数据盘、本地 NVMe、RAID 虚拟盘和容器挂载。先识别真实物理设备，再运行 SMART 查询。

# 查看块设备拓扑、型号、序列号、是否旋转盘
lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,ROTA,TRAN,MOUNTPOINTS

# 查看 smartctl 认为可检测的设备
sudo smartctl --scan-open

# 按稳定路径查看，避免 /dev/sdX 重排
ls -l /dev/disk/by-id/ | sed -n '1,20p'
设备名常见含义smartctl 示例
/dev/sdaSATA/SAS/SCSI 磁盘或 RAID 暴露的逻辑盘sudo smartctl -a /dev/sda
/dev/nvme0n1NVMe 第 0 个控制器的第 1 个 namespacesudo smartctl -a /dev/nvme0n1
/dev/disk/by-id/...按序列号/WWN 的稳定路径sudo smartctl -a /dev/disk/by-id/nvme-...
/dev/sgXSCSI generic 设备常用于 RAID/HBA 或老式 SAS 场景
定位提醒： 在有热插拔、RAID、容器和多路径的环境中，不要只凭 /dev/sdb 更换硬盘；必须核对序列号、槽位、控制器工具输出和机房资产信息。

5. 第一次健康检查

第一次检查不要从复杂字段开始。先回答四个问题：设备身份对不对、SMART 是否可用、总体健康是否异常、有没有明显错误日志或自检失败。

# 设备身份：型号、序列号、固件、容量、协议
sudo smartctl -i /dev/sda

# 总体健康：快速判断，但不要作为唯一证据
sudo smartctl -H /dev/sda

# 常用完整摘要：身份、属性、错误日志、自检日志
sudo smartctl -a /dev/sda

# 扩展信息：更多日志页，适合故障证据收集
sudo smartctl -x /dev/sda
PASSED 的含义
表示设备当前没有触发厂商定义的 SMART 总体失败阈值；不代表没有坏块、没有历史错误、没有性能风险。
FAILED 的含义
通常应视为高优先级硬件风险：先确认副本安全和业务影响，再安排下线、备份、替换或 RMA。
不要误判： 很多正在恶化的盘仍会显示 SMART overall-health self-assessment test result: PASSED，必须继续看属性、错误日志和自检。

对比图：SATA/SAS SMART 与 NVMe Health Log

SATA/SAS 常见输出是属性表；NVMe 更偏向标准化健康日志。smartctl 统一入口，但解释逻辑不同。

6. SATA/SAS 与 NVMe 差异

smartctl 能统一读取多种协议，但输出结构不是一回事。SATA HDD 的 Reallocated_Sector_Ct、Current_Pending_Sector 与 NVMe 的 Media and Data Integrity Errors、Available Spare、Percentage Used 不能机械对照。

维度SATA/SAS 常见输出NVMe 常见输出AI Infra 解读
总体健康SMART overall-health...SMART overall-health... + Critical Warning只做入口判断，不能替代详细日志
介质错误重映射、待重映射、离线不可纠正Media and Data Integrity Errors任何增长趋势都应高优先级关注
磨损厂商属性如 177/202/233 等Percentage Used用于寿命规划，阈值依 SLA 和副本策略决定
温度194 或厂商属性Temperature 与传感器字段关注峰值、热降速和机箱风道
错误日志SMART Error Log、SCT Error Recovery ControlError Information Log Entries结合时间、LBA、内核错误判断
# SATA/HDD 常见完整输出
sudo smartctl -a /dev/sda

# NVMe 常见完整输出
sudo smartctl -a /dev/nvme0n1

# 如果需要 NVMe 专用更细日志，可再用 nvme-cli 补充
sudo nvme smart-log /dev/nvme0n1
字段解释原则： 先看协议，再看厂商文档，再看趋势；不要只看某个 RAW_VALUE 的单次绝对值。

7. 关键属性与指标解释

SMART 属性表里通常有 VALUE、WORST、THRESH、TYPE、UPDATED、WHEN_FAILED、RAW_VALUE。AI Infra 排障最关心的是错误类、温度类、磨损类和接口类指标。

指标常见于关注点处置倾向
Reallocated_Sector_CtSATA HDD/SSD已重映射扇区；增长说明介质退化增长趋势明显时准备更换
Current_Pending_SectorSATA HDD等待重读/重映射的不稳定扇区高风险，尽快备份/迁移/长测
Offline_UncorrectableSATA HDD离线扫描发现不可纠正错误结合自检失败和日志决定下线
UDMA_CRC_Error_CountSATA链路传输错误，常见于线缆/背板/接口若只增长 CRC，优先查线缆和背板
Media and Data Integrity ErrorsNVMe控制器报告介质或数据完整性错误生产集群中通常应高优先级处置
Percentage UsedNVMe厂商估算寿命消耗百分比用于容量和寿命规划，接近/超过 100% 要评估替换
Available SpareNVMe可用备用块余量低于阈值或 Critical Warning 时应下线评估
Temperature_CelsiusSATA/NVMe当前温度、历史温度、传感器温度高温会导致降速和寿命风险
# 只抽取常见高价值字段，适合人工快速看
sudo smartctl -a /dev/sda | egrep -i \
  'overall|reallocated|pending|uncorrect|crc|temperature|power_on|error|self-test'

sudo smartctl -a /dev/nvme0n1 | egrep -i \
  'critical|temperature|available spare|percentage used|media|error|unsafe|power cycles'
厂商差异： SATA SSD 的磨损属性编号高度厂商化；同一个属性名的 RAW 值单位也可能不同。自动化告警要按型号白名单校准。

8. 错误日志与介质错误

错误日志比总体健康更接近故障现场。HDD 上的 LBA 读写失败、NVMe 的 media/data integrity error、内核里的 I/O error，都可能指向同一块盘或同一条链路。

# SATA/SAS：查看完整输出中的 Error Log 和 Self-test Log
sudo smartctl -a /dev/sda

# 扩展日志，有些设备会输出更多细节
sudo smartctl -x /dev/sda

# 同时查看内核日志中的块设备错误
journalctl -k --since "24 hours ago" | egrep -i \
  'I/O error|medium error|blk_update_request|nvme|ata|reset|timeout'
现象可能原因验证方向
介质错误增长盘面/闪存介质退化看自检、LBA、增长趋势，准备迁移
CRC/链路错误增长线缆、背板、HBA、连接器问题换槽/换线/查控制器日志
大量 timeout/reset设备卡死、固件、供电、控制器问题看 dmesg 时间线和同控制器其他盘
NVMe unsafe shutdown 增长断电、热重启、PCIe 复位查节点电源、BMC、内核 PCIe/AER 日志
数据安全优先： 对已经出现不可纠正读错误的盘，不要先跑重负载压力测试；先确认副本、备份、恢复窗口和上层存储健康。

流程图：smartctl 自检与故障判断

自检不是第一步，也不是唯一证据。先确认副本和业务风险，再选择合适自检窗口。

9. 自检：short、long、conveyance

SMART 自检由设备固件执行，通常不会破坏数据，但会占用设备资源，可能让已经不稳定的盘暴露更多错误。在生产集群中，先确保副本安全和维护窗口，再运行长自检。

自检类型命令特点适合场景
shortsmartctl -t short DEV几分钟，覆盖有限快速验证可疑盘
longsmartctl -t long DEV全盘扫描，耗时长维护窗口、RMA 证据、深度排查
conveyancesmartctl -t conveyance DEV运输损伤相关，部分 ATA 盘支持新盘上架验收
abortsmartctl -X DEV终止正在运行的自检业务受影响时停止
# 启动短自检
sudo smartctl -t short /dev/sda

# 查看预计完成时间和当前状态
sudo smartctl -c /dev/sda

# 等待完成后查看自检日志
sudo smartctl -l selftest /dev/sda

# 长自检通常要在维护窗口执行
sudo smartctl -t long /dev/sda
生产提醒： 不要在恢复风暴、训练高峰、RAID rebuild 或 Ceph backfill 正忙时批量跑 long test；它可能放大尾延迟。

10. 温度与热降速

NVMe 和高密度 HDD/SSD 在 AI 服务器里很容易受 GPU 热排、风道、PCIe 插槽位置影响。温度异常常表现为吞吐下降、延迟长尾、NVMe thermal throttling、错误率上升或寿命缩短。

# SATA/HDD/SSD 温度通常在 194 或 Temperature 字段
sudo smartctl -a /dev/sda | egrep -i 'temperature|airflow'

# NVMe 温度和温度传感器
sudo smartctl -a /dev/nvme0n1 | egrep -i 'temperature|sensor|thermal'

# 同时看内核是否记录 nvme reset/timeout
journalctl -k --since "6 hours ago" | egrep -i 'nvme|thermal|timeout|reset'
观察项为什么重要排查方向
当前温度持续高温影响寿命和性能风扇策略、灰尘、风道、环境温度
温度历史/峰值峰值可能解释偶发降速BMC 传感器、机箱事件、作业时间线
NVMe thermal throttling直接造成 IO 延迟和吞吐下降散热片、插槽位置、固件、气流遮挡
同节点多盘温度区分单盘问题和机箱问题同一背板/同一风道批量比较
AI 节点经验： 如果所有 NVMe 同时升温，优先查机箱气流和 GPU 风扇策略；如果单盘异常热，优先查该盘、插槽或散热接触。

11. 磨损、寿命与写入量

训练缓存、特征落盘、日志、checkpoint 和数据预处理会造成大量写入。SSD/NVMe 的寿命管理要看写入量、磨损百分比、备用块、错误趋势和业务 SLA。

# NVMe 寿命和写入量
sudo smartctl -a /dev/nvme0n1 | egrep -i \
  'percentage used|data units written|host writes|available spare|media'

# SATA SSD 厂商字段差异大，先查看完整属性表
sudo smartctl -A /dev/sda
字段解释注意事项
Percentage UsedNVMe 估算寿命消耗可能超过 100；不是精确剩余寿命
Data Units WrittenNVMe 写入单位计数需要换算，适合趋势监控
Total_LBAs_Written部分 SATA SSD 写入量单位依厂商而定
Available Spare可用备用容量余量低于阈值通常触发 Critical Warning
厂商磨损属性如 wear leveling、media wearout 等必须按型号确认含义
容量规划： 对本地 NVMe 缓存盘，应按实际写入速率估算寿命，并把“接近寿命阈值”的盘提前纳入滚动替换计划。

12. 预测性故障判断

预测性故障不是看一个字段，而是看证据组合：错误是否增长、是否影响读写、是否有自检失败、是否与内核日志一致、是否发生在关键业务路径上、是否有副本或恢复风险。

强烈建议下线/替换
总体健康 FAILED、NVMe Critical Warning、介质/完整性错误增长、自检读失败、pending/uncorrectable 增长、同 LBA 反复读失败。
先排查链路/环境
只有 CRC 增长、timeout/reset 集中在同控制器、所有盘同时高温、unsafe shutdown 与节点掉电一致。
继续观察趋势
历史老错误不增长、温度短时峰值但无降速、磨损高但仍在可接受替换窗口内。
立即保护数据
副本不足、RAID degraded、Ceph PG 不干净、训练 checkpoint 唯一副本在可疑盘上。
# 建立同一块盘的时间线：SMART + 内核日志 + 挂载点
DEV=/dev/nvme0n1
sudo smartctl -a "$DEV" | tee smart.$(basename "$DEV").txt
journalctl -k --since "24 hours ago" | egrep -i 'nvme|I/O error|timeout|reset'
lsblk -o NAME,SIZE,MODEL,SERIAL,MOUNTPOINTS "$DEV"
决策优先级： 如果已经有不可纠正错误且上层冗余不足，先迁移/备份/隔离，后做诊断；不要为了“证明坏盘”增加数据风险。

安全图：存储集群故障 triage

集群处置的第一原则是保护冗余和业务，再定位硬件。smartctl 是关键证据，不是唯一决策器。

13. 存储集群 triage 流程

当一个节点出现磁盘告警，不要直接拔盘。先看上层系统是否还有足够副本、是否正在 rebalance/rebuild、是否影响训练或推理任务，再决定 drain、cordon、停止写入、替换或继续观察。

# 单机证据收集模板
HOST=$(hostname)
OUT=/tmp/disk-triage-$HOST-$(date +%Y%m%d%H%M)
mkdir -p "$OUT"
lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,ROTA,TRAN,MOUNTPOINTS > "$OUT/lsblk.txt"
sudo smartctl --scan-open > "$OUT/smart-scan.txt"
journalctl -k --since "24 hours ago" > "$OUT/kernel-24h.txt"

# 对扫描到的设备逐个采集，先人工审查 smart-scan.txt 再执行
sudo smartctl -x /dev/sda > "$OUT/sda.smart.txt"
sudo smartctl -x /dev/nvme0n1 > "$OUT/nvme0n1.smart.txt"
阶段问题证据动作
入口是业务慢还是硬件告警？监控、训练日志、内核日志确定影响范围
冗余副本是否安全？Ceph PG、RAID 状态、备份状态必要时先停止新写入
设备哪块盘异常？序列号、槽位、smartctl 输出锁定物理盘
处置换盘还是修链路？介质错误、自检、CRC、控制器日志drain、replace、RMA 或修复环境
集群警告： 多盘同时告警时，优先怀疑背板、控制器、供电、散热或批次问题；不要并发下线过多 OSD/磁盘导致副本不足。

14. smartctl vs nvme vs lsblk

这三个工具解决的问题不同。lsblk 负责“有哪些块设备以及挂到哪里”，smartctl 负责“设备健康和自检证据”，nvme 负责“NVMe 协议专用管理与日志”。

工具最擅长不擅长典型命令
lsblk拓扑、挂载点、容量、传输类型、序列号深度健康日志lsblk -o NAME,SIZE,MODEL,SERIAL,MOUNTPOINTS
smartctlSMART、健康、自检、错误日志、跨协议统一入口NVMe 高级管理和厂商专用操作smartctl -a /dev/nvme0n1
nvmeNVMe identify、smart-log、error-log、firmware-logSATA/HDD/SAS 通用健康nvme smart-log /dev/nvme0n1
RAID 工具控制器、虚拟盘、物理槽位、rebuild 状态通用跨厂商一致性storcli /c0 /eall /sall show all
# 推荐顺序：先定位，再看健康，再补协议专用信息
lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,TRAN,MOUNTPOINTS
sudo smartctl --scan-open
sudo smartctl -a /dev/nvme0n1
sudo nvme smart-log /dev/nvme0n1
选择原则： 不是三选一；AI Infra 排障常常需要组合使用，避免只看一个工具导致证据断层。

15. RAID、HBA、USB 和虚拟化场景

当磁盘不直接暴露给操作系统时，smartctl -a /dev/sdX 可能只能看到逻辑盘，甚至看不到 SMART。需要通过 -d 指定设备类型或使用控制器厂商工具。

# 让 smartctl 尝试识别可用设备类型
sudo smartctl --scan-open

# USB-SATA 桥接常见写法，具体取决于桥接芯片
sudo smartctl -a -d sat /dev/sdb

# MegaRAID 示例：N 是物理盘索引，必须结合控制器工具确认
sudo smartctl -a -d megaraid,0 /dev/sda

# 有些 HBA/SAS 场景可能需要 /dev/sgX
sudo smartctl -a /dev/sg2
场景症状处理
硬 RAID只能看到虚拟盘使用 -d megaraid,N 或 storcli/perccli/arcconf
HBA 直通通常能直接读到物理盘优先按 by-id 和序列号定位
USB/SATA 桥SMART unsupported 或字段缺失尝试 -d sat，必要时更换桥接盒
虚拟机看到的是虚拟磁盘在宿主机或存储后端采集真实 SMART
容器没有块设备权限使用宿主机 agent，不建议把整块设备随意暴露给容器
槽位风险： RAID 下的编号、Linux 设备名和机箱槽位不是天然一致的；换盘前必须通过控制器工具点灯/定位并核对序列号。

16. 自动化采集与监控

生产环境不应靠人工 SSH 到节点看 SMART。更合理的方式是周期性采集关键指标、保存趋势、将强信号接入告警，并在工单里附上完整 smartctl -x 输出。

# 简单巡检脚本：只读采集，不做处置
#!/usr/bin/env bash
set -euo pipefail
out="/var/log/smart-snapshots/$(hostname)-$(date +%Y%m%d%H%M%S)"
mkdir -p "$out"
sudo smartctl --scan-open > "$out/scan.txt"
awk '{print $1}' "$out/scan.txt" | while read -r dev; do
  safe=$(basename "$dev" | tr '/' '_')
  sudo smartctl -x "$dev" > "$out/$safe.txt" 2>&1 || true
done

# 人工快速检查高风险关键词
grep -RniE 'FAILED|Critical Warning|Media and Data Integrity Errors|Current_Pending|Offline_Uncorrectable' "$out"
告警类型建议级别说明
总体健康 FAILED严重立即进入下线/替换评估
NVMe Critical Warning 非 0严重检查 spare、温度、可靠性、只读模式等原因
介质错误增长严重趋势比单次值更重要
CRC 增长警告通常先查链路，持续增长需处理
温度持续过高警告/严重按设备规格和业务影响定级
磨损接近阈值计划进入容量和备件计划
自动化边界： 自动采集可以很激进，自动处置要保守；下线盘/节点前应检查副本、恢复状态和当前业务负载。

smartctl 排障先从设备身份、协议、控制器和权限开始；字段解释要建立在“目标盘正确”的基础上。

17. 常见排障清单

问题 1：SMART support is Unavailable
可能是虚拟磁盘、RAID 控制器遮挡、USB 桥不透传或权限不足。先运行 smartctl --scan-open。
问题 2：PASSED 但业务仍然报 IO 错
继续看错误日志、自检日志、内核日志和上层存储；PASSED 不是无故障证明。
问题 3：CRC 错误增长但介质字段正常
优先查 SATA 线缆、背板、接口、电源和控制器，不要立刻定性为盘面坏。
问题 4：NVMe Media Errors 增长
高风险，结合 Error Information Log、内核日志和副本状态，准备下线/替换。
问题 5：自检一直中断
可能是掉电、设备 reset、负载、控制器问题或不支持相关测试。看 journalctl -k 时间线。
问题 6：盘符变化导致查错盘
使用 /dev/disk/by-id、序列号、WWN、控制器槽位映射，不依赖 /dev/sdX。
问题 7：容器里看不到设备
SMART 应在宿主机采集；不要为了方便把所有块设备暴露给业务容器。
问题 8：多盘同时异常
优先考虑背板、HBA、供电、散热、固件批次或机房事件，而不是多个盘同时自然损坏。

最小排障模板

# 1. 确认目标盘身份
lsblk -o NAME,TYPE,SIZE,MODEL,SERIAL,TRAN,MOUNTPOINTS
sudo smartctl -i /dev/sdX

# 2. 收集完整 smartctl 输出
sudo smartctl -x /dev/sdX | tee /tmp/sdX.smart.txt

# 3. 对齐系统错误时间线
journalctl -k --since "24 hours ago" | egrep -i 'sdX|ata|scsi|I/O error|timeout|reset'

# 4. 如果是 NVMe，补充 NVMe 专用日志
sudo nvme smart-log /dev/nvme0n1
sudo nvme error-log /dev/nvme0n1

18. 安全边界与参考资料

安全边界

  • smartctl -a、-x、-i、-H 主要是只读查询，适合生产排障采集。
  • smartctl -t short/long 通常不破坏数据，但会占用设备资源，并可能让不稳定盘暴露更多错误。
  • smartctl -X 会终止自检，适合业务受影响时使用。
  • 不要把 smartctl 与破坏性写测试混淆；介质已异常时，先保护数据，再考虑压力测试。
  • 换盘前必须核对序列号、槽位、控制器映射和上层副本状态。
