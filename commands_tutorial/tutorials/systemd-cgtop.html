1. systemd-cgtop 是什么

systemd-cgtop 是 systemd 提供的 cgroup 资源观察工具。它把本机 cgroup 层级中的控制组按 CPU、内存或 I/O 使用量排序，并像 top 一样周期刷新。对 AI Infra 来说，它的价值是把“一个训练作业、一个 Pod、一个 systemd 服务、一批用户进程”的资源使用先聚合起来，而不是在上千个 Python、DataLoader、NCCL helper、runtime shim 和 kernel thread 里逐个猜。

它能回答
哪个 cgroup 正在吃 CPU？哪个服务或容器内存最高？I/O 峰值是否集中在某个训练作业？
它不能回答
不能直接给出 GPU 显存、网络 RDMA 计数器、Python 对象泄漏栈、每个 Pod 的语义标签。
AI Infra 用法
先用它按 cgroup 找“责任边界”，再用 systemd-cgls、pidstat、iotop、kubectl 或业务日志下钻。
# 交互式查看本机 cgroup 资源排行
systemd-cgtop

# 只看前 2 层，适合先看 slice 级别
systemd-cgtop --depth=2

# 按内存排序
systemd-cgtop --order=memory

# 按 I/O 排序，1 秒刷新
systemd-cgtop --order=io --delay=1s
边界提醒： systemd-cgtop 的内存和 I/O 列依赖 cgroup 控制器与 systemd accounting。空白或 0 不一定代表没有消耗，可能是记账没开启或当前层级不可见。

2. 整体模型：进程到 cgroup 再到资源列

核心不是“看一个 PID”，而是看系统把一批进程放在哪个资源控制边界里，并把这个边界上的资源账本显示出来。

3. 安装、权限与运行环境

systemd-cgtop 随 systemd 工具集提供，常见 systemd 发行版默认安装。它需要本机使用 systemd 管理 cgroup；在 macOS、非 systemd 容器、极简镜像或旧式 init 环境中通常不可用。

检查项命令说明
命令是否存在command -v systemd-cgtop不存在时安装 systemd 相关包，或改用节点侧工具。
systemd 是否为 PID 1ps -p 1 -o comm=容器内 PID 1 可能不是 systemd，此时 cgroup 视图可能受限。
cgroup 版本stat -fc %T /sys/fs/cgroupcgroup2fs 表示统一层级 cgroup v2。
版本systemd-cgtop --version不同 systemd 版本的列、选项和默认行为可能略有差异。
# Debian/Ubuntu 常见检查
command -v systemd-cgtop || dpkg -S systemd-cgtop

# RHEL/CentOS/Rocky 常见检查
rpm -qf "$(command -v systemd-cgtop)"

# 确认当前环境是不是容器内受限视角
cat /proc/1/cgroup
cat /proc/self/cgroup
权限模型： 普通用户通常可以运行它看到部分或全部 cgroup 统计；但某些发行版、容器、rootless 环境或安全策略会限制对其他用户/服务 cgroup 的可见性。

4. 输出列：Path、Tasks、CPU、Memory、Input、Output

表格列是 systemd-cgtop 的核心。排障时不要只看最大数字，要把列和 cgroup 层级、记账开关、采样窗口一起解读。

列含义AI Infra 解读常见陷阱
Pathcgroup 路径可映射到 service、scope、user slice、pod、container、Slurm 作业。路径不是业务名；需要再映射 owner。
Tasks任务/线程或进程计数DataLoader worker、线程池、runtime shim、kernel thread 会推高计数。默认按 task 计数，和 ps 进程数不一定一致。
%CPU该 cgroup CPU 使用率多核机器上可超过 100%，例如 64 核可接近 6400%。不能按单核百分比理解。
Memorycgroup 内存用量适合判断 Pod/服务/作业是否接近 limit 或异常增长。需要 memory controller 和 accounting 支持。
Input/s读 I/O 速率数据加载、checkpoint 读取、缓存未命中会体现。需要 IOAccounting；page cache 命中不一定体现为磁盘读。
Output/s写 I/O 速率checkpoint、日志风暴、临时文件写入会体现。overlayfs、网络盘和缓存会影响归因。
# 示例输出形态，不同版本列名可能略有差异
Control Group                         Tasks   %CPU   Memory  Input/s Output/s
/                                      1842  750.0    92.1G   90.2M   410.0M
/system.slice/containerd.service        91   12.0     1.4G    2.0M     4.1M
/kubepods.slice/podabc...              320  610.0    44.8G   74.0M   380.0M
/user.slice/user-1000.slice             52   18.0     2.2G      0B   120.0K
读表原则： Path 是归因入口，数值列是症状强度。不要在未确认路径归属前直接杀进程或重启服务。

5. 交互按键与排序

交互模式适合现场排障。你可以先按 CPU 排序找算力争抢，再按内存或 I/O 切换视角，最后按路径排序观察层级位置。

按键/选项作用典型用途
c / --order=cpu按 CPU 使用排序找 DataLoader 过量、CPU inference、压缩/解压、日志处理风暴。
m / --order=memory按内存排序找接近 cgroup limit 的训练、推理服务或用户会话。
i / --order=io按 I/O 排序找 checkpoint 写入、数据集扫描、日志风暴、缓存 miss。
t / --order=tasks按任务数排序发现 worker 爆炸、线程池失控、fork storm。
p / --order=path按路径排序按层级看 slice/scope/service 结构。
% / --cpu=timeCPU 百分比和累计时间切换区分瞬时热点和长期累计消耗。
Space立即刷新观察操作前后变化。
q退出结束现场观察。
# 从命令行直接指定排序和刷新间隔
systemd-cgtop --order=cpu --delay=500ms
systemd-cgtop --order=memory --delay=2s
systemd-cgtop --order=io --depth=5

6. 常用命令模板

先用浅层视图判断是系统服务、用户会话、容器还是某个 pod slice；再加深层级或指定路径下钻。

先看大类
--depth=2 能快速看 /system.slice、/user.slice、/kubepods.slice 哪一类最重。
再看细节
对可疑路径加参数，只显示该 cgroup 子树，减少噪声。
# 大盘：前 2 层，快速看系统/用户/kube 作业哪类最重
systemd-cgtop --depth=2

# 只看 system.slice 下的服务
systemd-cgtop /system.slice

# 只看用户会话
systemd-cgtop /user.slice

# 只跑一次，适合留证或脚本
systemd-cgtop --batch --iterations=1 --depth=4

# 每 5 秒采样一次，共 12 次，约 1 分钟
systemd-cgtop --batch --iterations=12 --delay=5s --depth=5
脚本提醒： 非 TTY 输出时默认通常只运行一轮；需要持续采样时显式加 --batch、--iterations= 和 --delay=。

7. slice、scope、service 怎么读

slice 是层级分组，service 是 systemd 管理的长期服务，scope 常表示由外部进程创建并交给 systemd 记账的进程组，例如登录会话、容器、临时作业。
名称含义AI Infra 例子
*.slice资源层级分组，不一定直接包含主进程。system.slice、user.slice、kubepods.slice。
*.servicesystemd 管理的服务 unit。containerd.service、kubelet.service、nvidia-fabricmanager.service。
*.scope外部创建的进程组，由 systemd 追踪。SSH 会话、容器 scope、systemd-run --scope 启动的训练。

8. AI 训练节点的 noisy job 定位流程

训练节点上的噪声通常来自 CPU 数据加载、checkpoint I/O、日志爆炸、容器内存接近上限、解压/预处理、推理 sidecar 或相邻用户会话。systemd-cgtop 适合先把噪声定位到 cgroup，再用更细工具确认具体进程和业务。

# 1. 先看节点级 cgroup 大类
systemd-cgtop --depth=2 --delay=1s

# 2. CPU 维度找 CPU noisy neighbor
systemd-cgtop --order=cpu --depth=5

# 3. 内存维度找大 cgroup
systemd-cgtop --order=memory --depth=5

# 4. I/O 维度找 checkpoint 或数据扫描
systemd-cgtop --order=io --depth=6
观察常见原因下一步
某 pod cgroup CPU 很高，GPU 利用率低DataLoader worker 太多、CPU 预处理瓶颈、解压/增强耗 CPU。pidstat -t -p PID 1、框架 dataloader 配置、CPU affinity。
Output/s 周期性冲高checkpoint 保存、tensorboard/logging、临时文件写入。iotop、lsof、训练日志时间点、存储监控。
Memory 持续增长batch 缓存、worker 泄漏、数据集预加载、推理 KV cache。cgroup memory.current/events、smaps_rollup、OOM 事件。
Tasks 异常多fork storm、线程池爆炸、DataLoader 多进程未回收。systemd-cgls 展开、pstree、业务启动参数。
定位模板： “在 60 秒窗口内，/kubepods.slice/.../podX 持续占用约 2800% CPU，Tasks 约 420，GPU util 同期只有 35%；初步判断是 Pod X 的 CPU 数据管线瓶颈，而不是 GPU 计算饱和。”

9. 容器与 Kubernetes cgroup 映射

Kubernetes 节点上，systemd-cgtop 看到的是宿主机 cgroup 路径，不一定直接显示 namespace/name。你需要把路径中的 pod UID、container ID、scope 名称映射回 Kubernetes 对象。

# 从可疑 PID 反查 cgroup
cat /proc/12345/cgroup

# 展开 cgroup 树，找到里面的 PID
systemd-cgls /kubepods.slice

# containerd/CRI 场景：列出容器与 Pod
crictl ps
crictl inspect <container-id> | grep -E 'podSandboxId|pid|name|namespace'

# Kubernetes 侧映射 Pod UID
kubectl get pod -A -o wide
kubectl get pod -A -o jsonpath='{range .items[*]}{.metadata.namespace}{" "}{.metadata.name}{" "}{.metadata.uid}{"\n"}{end}'
路径片段可能含义映射方法
kubepods.sliceKubelet 管理的 Pod cgroup 根看子路径中的 QoS class、pod UID。
kubepods-burstable.sliceBurstable QoS Pod对照 requests/limits，检查是否资源争抢。
pod<uid>.slice某个 Pod 的 cgroup把 _ 或转义还原为 UID 后查 Kubernetes。
cri-containerd-<id>.scope某个 containerd 容器 scope用 crictl inspect 或运行时元数据映射。
libpod-<id>.scopePodman 容器 scope用 podman inspect 映射。
容器视角提醒： 在 Pod 内运行 systemd-cgtop 往往没有完整宿主机视图。AI 平台排障通常应在节点调试容器、宿主机、运维 bastion 或受控诊断 DaemonSet 中执行。

10. cgroup v2 与记账 caveats

systemd-cgtop 的可靠性依赖内核 cgroup 控制器和 systemd accounting 设置。CPU 在统一 cgroup v2 上通常更容易看到；内存和 I/O 需要对应控制器、unit 配置和系统默认策略支持。

项目检查命令解释
cgroup 文件系统类型stat -fc %T /sys/fs/cgroupcgroup2fs 是 cgroup v2；旧系统可能是 hybrid/v1。
可用控制器cat /sys/fs/cgroup/cgroup.controllers应关注 cpu、memory、io、pids。
子树启用情况cat /sys/fs/cgroup/cgroup.subtree_control控制器未启用时，下层 cgroup 可能无法记账或控制。
systemd 默认记账systemctl show -p DefaultMemoryAccounting -p DefaultIOAccounting不同发行版默认值可能不同。
单个 unit 记账systemctl show foo.service -p MemoryAccounting -p IOAccounting内存/I/O 为空时先查这里。
# 临时为服务开启资源记账，先确认影响范围
systemctl show my-trainer.service -p MemoryAccounting -p IOAccounting
sudo systemctl set-property my-trainer.service MemoryAccounting=yes IOAccounting=yes

# 持久配置示例：/etc/systemd/system/my-trainer.service.d/accounting.conf
[Service]
MemoryAccounting=yes
IOAccounting=yes
配置变更警告： systemctl set-property 会修改 unit 运行时属性并可能落盘成 drop-in。生产集群要先确认平台策略，不要在共享节点上绕过配置管理。

11. CPU 列的正确解读

%CPU 是 cgroup 在采样窗口内消耗 CPU 的百分比，范围可到 100 × CPU 数。例如 8 核机器上 800% 代表近似用满 8 个 CPU；128 核 AI 节点上 3200% 可能只是 25% 整机 CPU。

# 看机器 CPU 数
nproc
lscpu | sed -n '1,20p'

# 对照 cgroup CPU quota/cpuset
cat /sys/fs/cgroup/cpu.max 2>/dev/null || true
cat /sys/fs/cgroup/cpuset.cpus.effective 2>/dev/null || true

# 进程/线程级下钻
pidstat -u -t -p 12345 1
ps -L -p 12345 -o pid,tid,psr,pcpu,comm
现象解读下钻
Pod CPU 高、GPU 低CPU 数据管线可能成为瓶颈。看 worker 数、预处理、解码、CPU affinity、NUMA。
Tasks 多但 CPU 不高大量线程阻塞、sleep 或 I/O 等待。pidstat -w、strace -p、锁等待、I/O。
CPU 高但吞吐没涨可能是 busy loop、日志格式化、压缩、重试风暴。perf top、py-spy、业务日志。
配额提醒： 容器限 8 核时，cgroup 内 800% 可能已经满载；宿主机有 128 核不代表该 Pod 可用 128 核。

12. 内存列与 OOMKilled 排查

内存列适合快速找大 cgroup，但它不是完整内存诊断。AI 任务里，page cache、tmpfs、共享内存、pinned host memory、DataLoader worker 复制、推理 KV cache 都可能影响 cgroup 内存。

# 对可疑 cgroup 读取 cgroup v2 内存文件
CG=/sys/fs/cgroup/kubepods.slice/...
cat "$CG/memory.current" 2>/dev/null
cat "$CG/memory.max" 2>/dev/null
cat "$CG/memory.high" 2>/dev/null
cat "$CG/memory.events" 2>/dev/null
grep -E 'anon|file|kernel|slab|shmem|pgfault|pgmajfault' "$CG/memory.stat" 2>/dev/null

# 进程级内存下钻
cat /proc/12345/status | egrep 'VmRSS|VmHWM|VmSwap|Threads'
cat /proc/12345/smaps_rollup 2>/dev/null
信号可能原因建议
memory.current 接近 memory.maxPod limit 将触发 OOMKilled。降 batch、worker、prefetch，或调整 limit。
memory.events 中 oom/oom_kill 增加cgroup 内发生 OOM。结合 kube events、dmesg、应用日志确认。
file 很高page cache、mmap 数据集、checkpoint 文件缓存。看是否可回收，不要简单等同泄漏。
anon 持续增长进程堆、Python 对象、KV cache、worker 复制。用 profiler 或进程级 smaps 下钻。
GPU 显存边界： systemd-cgtop 不显示 GPU 显存。GPU OOM 要看 nvidia-smi、DCGM、框架分配器和训练日志；cgroup 内存只解释 CPU/主机内存侧压力。

13. I/O 列与数据加载瓶颈

I/O 列能帮助判断一个 cgroup 是否在读数据、写 checkpoint 或刷日志，但它不是完整存储诊断。page cache、网络文件系统、overlayfs、块设备队列和对象存储客户端都会影响你看到的读写速率。

# 按 I/O 排序观察 cgroup
systemd-cgtop --order=io --delay=1s --depth=6

# 对照设备级压力
iostat -xz 1

# 进程级 I/O
pidstat -d -p 12345 1
iotop -oPa

# 从 PID 找具体打开文件
lsof -p 12345 | head -50
现象解释下钻工具
Input/s 高，GPU idle数据集扫描或缓存 miss，训练在等 I/O。iostat、pidstat -d、数据管线日志。
Output/s 周期性高checkpoint、日志、指标写入。lsof、训练保存间隔、存储监控。
cgtop I/O 不高但应用慢可能是 page cache、网络、元数据锁、对象存储延迟。strace、NFS/并行文件系统指标、应用 tracing。
多个 Pod 同时 I/O 高共享存储或本地 NVMe 被邻居任务争抢。按 Pod cgroup 分摊，结合设备队列和平台调度。
AI 数据管线建议： 如果 I/O 噪声频繁出现，把 systemd-cgtop --batch、iostat、pidstat -d 和 Pod 映射做成统一采样包，事故后才能还原时间线。

14. systemd-cgtop vs top/systemd-cgls/cadvisor

四类工具不是互相替代：systemd-cgtop 最适合“现场谁最重”的 cgroup 聚合视角。
工具最佳问题不适合的问题
systemd-cgtop哪个 cgroup 当前最耗 CPU/内存/I/O？长期趋势、业务标签、函数级热点。
systemd-cgls某个 cgroup 下有哪些进程？层级怎样？资源速率排行。
top/htop哪个 PID 或线程当前最耗 CPU/内存？把多个进程聚合成 Pod/服务/作业。
cadvisor/Prometheus容器历史曲线、标签化告警、容量报告。临时 SSH 到节点后的快速层级下钻。

15. 批处理采样与留证

事故排查需要证据。--batch、--iterations、--delay、--raw 适合把 cgroup 资源快照保存成文本，便于和日志、训练 step、Kubernetes event 对齐。

# 创建一次性采样目录
out=/tmp/cgtop-debug-$(date +%Y%m%d-%H%M%S)
mkdir -p "$out"

# 记录版本与环境
systemd-cgtop --version > "$out/version.txt" 2>&1
uname -a > "$out/uname.txt"
stat -fc %T /sys/fs/cgroup > "$out/cgroup-fstype.txt" 2>&1

# 1 分钟 cgroup 资源采样
systemd-cgtop --batch --iterations=12 --delay=5s --depth=6 > "$out/cgtop.txt"

# 同步保存 cgroup 树和进程快照
systemd-cgls --no-pager > "$out/cgls.txt" 2>&1
ps -eo pid,ppid,user,stat,pcpu,pmem,comm,args --sort=-pcpu | head -80 > "$out/ps-cpu.txt"
ps -eo pid,ppid,user,stat,pcpu,pmem,comm,args --sort=-pmem | head -80 > "$out/ps-mem.txt"
隐私提醒： ps args、容器名称、路径、环境变量和日志可能包含用户名、项目名、token 或数据集路径。共享采样包前要脱敏。
参数作用建议
--batch非交互输出，适合重定向。脚本中显式使用。
--iterations=N运行 N 轮。现场短采样用 12×5s 或 60×1s。
--delay=刷新间隔。CPU 抖动看 1s；长期趋势看 5s/10s。
--raw输出原始数值。便于后续脚本解析。
--depth=限制展开深度。先浅后深，避免输出过大。

16. 故障排查决策树

不要停在“某个 cgroup 很高”。合格结论必须包含列、路径、时间窗口、owner、影响面和下一步验证。
输出为空或列全是横线
检查是否在 systemd 主机上运行、cgroup 控制器是否启用、unit 是否开启 Memory/IOAccounting。
路径看不懂
用 systemd-cgls 展开，再从 PID 查 /proc/PID/cgroup，最后映射到容器或 Kubernetes 对象。
CPU 百分比离谱
先看 CPU 数和 quota。多核机器超过 100% 是正常现象。
容器内结果不可信
切到宿主机或节点调试视角，容器内权限和 namespace 可能隐藏其他 cgroup。

17. 生产安全与操作边界

systemd-cgtop 本身是只读低风险工具，但它常引出高风险动作：杀进程、重启服务、调整 cgroup 限额、迁移训练作业、删除 checkpoint、改 Kubernetes limit。排障流程必须把“观察”和“处置”分开。

动作风险安全做法
杀掉最大 CPU PID可能杀错容器 runtime、共享服务或系统组件。先确认 cgroup owner、业务影响和回滚方案。
重启 containerd/kubelet影响整节点 Pod 生命周期。先 cordon/drain 或按平台应急手册执行。
调整 MemoryMax/CPUQuota可能改变调度公平性或触发 OOM。通过配置管理和变更流程落地，不在现场随手改。
降低训练 worker/batch影响吞吐和实验可复现性。记录配置、对比指标、通知 owner。
清理缓存或临时文件可能破坏数据集缓存或 checkpoint。确认路径归属和保留策略，避免自动递归删除。
# 只读确认链路示例：观察 → 展开 → 映射 → 再决定
systemd-cgtop --batch --iterations=1 --depth=6
systemd-cgls /kubepods.slice --no-pager
cat /proc/12345/cgroup
crictl inspect <container-id>
kubectl describe pod -n <ns> <pod>
红线： 不要只凭 systemd-cgtop 一屏输出直接 kill -9、重启 runtime 或修改限额。它负责发现嫌疑 cgroup，不负责完成业务归因和变更审批。

18. 练习任务与检查清单

  1. 在一台 systemd Linux 机器上运行 systemd-cgtop --depth=2，解释 system.slice、user.slice、容器相关 slice 的资源占比。
  2. 用 systemd-cgtop --order=cpu 找一个 CPU 高的 cgroup，再用 systemd-cgls 找到其中的 PID。
  3. 从一个 PID 的 /proc/PID/cgroup 反查它属于哪个 service、scope、Pod 或容器。
  4. 比较 systemd-cgtop 与 top 的视角差异：哪个按 cgroup 聚合，哪个按进程排序。
  5. 在测试服务上开启 MemoryAccounting=yes 与 IOAccounting=yes，观察内存/I/O 列变化。
  6. 模拟 checkpoint 写入，观察 Output/s 是否出现周期性峰值，并用 iostat 对照设备压力。
现场结论必须有路径
例如 /kubepods.slice/.../podX，不要只说“CPU 高”。
必须有时间窗口
瞬时峰值、1 分钟持续高、训练 step 周期性峰值的处理不同。
必须能映射 owner
服务名、Pod、namespace、job id、用户或队列至少要确认一个。
必须交叉验证
CPU 用 pidstat/perf，内存用 cgroup 文件，I/O 用 iostat/iotop。
必须说明 caveat
记账未开启、容器内视角、cgroup v1/v2、GPU 显存不在列里。
必须记录处置边界
只读采样可以直接做；杀进程、重启、改限额需要变更流程。

19. 常见误区与 FAQ

误区 1：CPU 2500% 一定异常
不一定。先看节点 CPU 数和该 cgroup 的 quota；在 64 核机器上 2500% 只是约 25 个 CPU 的使用量。
误区 2：Memory 为空就是没有内存占用
不一定。可能是 memory accounting 未开启、控制器不可用、权限受限或当前层级没有直接记账。
误区 3：Path 就是 Kubernetes 名称
不是。Path 是 cgroup 路径，Pod 名、namespace、owner 要通过 UID、container ID、CRI 或 Kubernetes API 映射。
误区 4：I/O 高就一定是磁盘坏
高 I/O 可能来自 checkpoint、数据预取、日志、缓存 miss、元数据风暴或共享存储争抢，需要结合 iostat 和应用时间线。
误区 5：cgtop 能解释 GPU OOM
不能直接解释。GPU 显存不属于 cgroup Memory 列，必须看 nvidia-smi、DCGM 和框架日志。
误区 6：容器内结果等于宿主机结果
通常不等。容器内可能缺 systemd、缺权限或只看到自身 cgroup；节点级排障应尽量用宿主机或受控 node debug 视角。
问题快速回答更可靠的验证
能不能替代 kubectl top？不能。它没有 Kubernetes 标签和历史聚合。用它做节点现场下钻，用 metrics server/Prometheus 做平台视角。
能不能只看第一行根 cgroup？只能看全机合计，不能归因。用 --depth=2 到 --depth=6 逐层展开。
为什么和 Prometheus 数字不同？采样窗口、口径、cgroup 路径、容器重启和 rate 计算都可能不同。对齐时间窗口、Pod UID、container ID 和节点。
为什么 Tasks 比进程数多？Tasks 可能包含线程。用 ps -L 或 pidstat -t 对照。
