1. systemd-cgls 是什么

systemd-cgls 的全称可以理解为 “systemd control group list”。它递归显示 Linux control group 层级中的 cgroup 和成员进程。和 ps aux 不同，systemd-cgls 关注“进程被谁管理、被放进哪个资源边界”，这对 AI 训练平台尤其重要。

它回答的问题
这个 python train.py 是登录会话、systemd service、Slurm step、Docker 容器、Kubernetes pod，还是某个 transient scope 启动的？
它不直接回答的问题
CPU/GPU/内存当前消耗是多少、谁在 OOM、哪个 GPU kernel 卡住。那些要用 systemd-cgtop、ps、nvidia-smi、journalctl 和 cgroup 文件继续查。
AI Infra 价值
训练任务经常通过 launcher、容器 runtime、kubelet、systemd-run 或 job scheduler 间接启动；cgroup 树能把“谁创建谁、谁隔离谁”重新串起来。
# 查看整棵 systemd cgroup 树
systemd-cgls

# 输出完整命令行，避免长命令被省略
systemd-cgls --full --no-pager

# 只看某个 systemd unit 的 cgroup 子树
systemd-cgls --unit kubelet.service

# 只看当前用户的 user unit 子树
systemd-cgls --user-unit my-training.scope
边界提醒： systemd-cgls 显示的是 cgroup 归属和树形结构，不是实时性能采样器。看到某个训练进程在 pod cgroup 下，只说明归属；要判断是否被限流、OOM 或资源争抢，还需要继续读限制文件和指标。

信息图：AI 节点上的 cgroup 树心智模型

普通进程树回答父子关系；cgroup 树回答资源边界和管理归属。训练任务、容器 runtime 和 kubelet 往往在 cgroup 树里更容易定位。

2. 语法、选项与权限

基本语法是 systemd-cgls [OPTIONS...] [CGROUP...]，也可以通过 --unit 或 --user-unit 查看指定 unit 的 cgroup 子树。没有参数时，一般显示完整 systemd cgroup 层级；如果当前目录位于 /sys/fs/cgroup/ 下，则可能显示当前目录对应的 cgroup。

选项含义AI Infra 用法
--all显示空 cgroup确认某个 service/scope 是否存在但没有进程
-l, --full不省略过长进程命令行查看 torchrun、launcher 参数、容器 entrypoint
-u, --unit显示指定 system unit 子树kubelet.service、containerd.service、自建 trainer service
--user-unit显示指定 user unit 子树定位用户态 systemd-run --user --scope 启动的训练任务
-k包含 kernel threads排查节点底层线程归属时使用，默认多数训练排障不需要
-M, --machine=限制到某个 machine/containersystemd-nspawn 或 machined 管理的容器/VM 场景
--xattr=显示 cgroup 扩展属性信息少见，通常用于深入 systemd/cgroup 元数据排障
--cgroup-id=显示 cgroup 数字 ID与 eBPF、内核事件或审计日志按 cgroup id 关联时有用
--no-pager不进入 pager脚本、远程命令、工单粘贴时必备
# 推荐排障默认组合：完整命令行 + 不进 pager
sudo systemd-cgls --full --no-pager

# 查看空 cgroup，适合确认 unit 是否只剩目录没有进程
sudo systemd-cgls --all --no-pager --unit kubelet.service

# 指定 cgroup 路径
sudo systemd-cgls /sys/fs/cgroup/system.slice/containerd.service

# 查看命令是否支持某个新选项
systemd-cgls --help
systemd-cgls --version
权限模型： 普通用户通常能看到不少进程和 cgroup 名称，但命令行、其他用户进程、容器细节可能受权限或内核 hidepid 设置影响。生产排障建议使用具备授权的 root/sudo 只读观察。

3. 读懂输出：树、PID、命令行

systemd-cgls 输出由 cgroup 节点和进程叶子组成。cgroup 节点一般以路径片段、unit 名、slice 名或 scope 名出现；叶子进程通常显示 PID 和命令行。树缩进表达 cgroup 层级，不等价于进程父子关系。

输出片段解释排障动作
system.slice系统服务集合查 kubelet/containerd/docker/slurm 等守护进程
user-1000.sliceUID 1000 的用户资源树关联登录会话、Jupyter、用户级训练任务
session-12.scope一次登录会话或 PAM 创建的 scope判断训练是否从 SSH/tmux/screen 手动启动

读树提醒： 同一 cgroup 下的多个进程是同一个资源控制边界内的成员，不表示它们互为父子。父子关系请用 pstree -ap 或 ps -o pid,ppid,cmd 查看。

4. system.slice、user.slice、machine.slice

systemd 把资源管理抽象为 slice。对 AI 节点来说，最常见的是系统服务所在的 system.slice、用户会话所在的 user.slice，以及某些虚拟机/容器场景下的 machine.slice。Kubernetes pod cgroup 也经常以 slice 形式出现，具体取决于 kubelet cgroup driver 和 cgroup 版本。

system.slice
kubelet、containerd、docker、slurmd、node exporter、DCGM exporter 等守护进程通常在这里。平台级故障先看这里。
user.slice
SSH、Jupyter、tmux、用户级 systemd service/scope 常在这里。手动训练、Notebook 训练和开发机排障先看这里。
machine.slice
systemd-machined 管理的 machine、nspawn 容器或某些 VM 方案可能在这里。普通 Kubernetes 节点不一定明显使用它。
# 只看系统服务层
sudo systemd-cgls /sys/fs/cgroup/system.slice --full --no-pager

# 只看某个用户资源层，UID 1000 只是示例
sudo systemd-cgls /sys/fs/cgroup/user.slice/user-1000.slice --full --no-pager

# 观察 machine 相关 cgroup，若不存在则说明当前节点未使用这类管理方式
sudo systemd-cgls /sys/fs/cgroup/machine.slice --full --no-pager
定位技巧： 如果一个训练进程在 user.slice/session-*.scope 下，通常说明它来自登录会话；如果在 kubepods.slice 或 cri-containerd-*.scope 下，通常说明它来自容器编排；如果在自定义 *.service 下，说明它被 systemd unit 托管。

5. service、scope、slice 的关系

systemd-cgls 输出里的 *.service、*.scope、*.slice 不是装饰字符串，而是 systemd 管理资源边界的关键线索。

类型含义AI Infra 示例常用交叉验证
service由 systemd 按 unit 文件启动和监督的服务kubelet.service、containerd.service、slurmd.servicesystemctl status kubelet、systemctl show kubelet
scope外部创建、systemd 只负责归组和资源控制的一组进程session-12.scope、cri-containerd-*.scope、run-*.scopesystemctl status run-xxx.scope、loginctl session-status
slice资源层级分组，不直接代表一个进程kubepods-burstable.slice、user-1000.slicesystemctl show user-1000.slice、读 cgroup 文件
# 查看 unit 的资源属性，常用于确认是否设置了 CPU/Memory 限制
systemctl show kubelet.service -p Slice -p ControlGroup -p CPUWeight -p MemoryMax -p TasksMax

# 查看登录会话对应 scope
loginctl list-sessions
loginctl session-status 12

# 用 systemd-run 创建一个可控 scope，适合做资源隔离实验
systemd-run --user --scope -p MemoryMax=8G -p CPUWeight=200 python train.py
实验边界： systemd-run 会真正启动进程；生产节点不要为了演示随意创建训练进程或调整资源属性。先在测试机验证。

6. 定位 AI 训练进程

AI 训练节点常见问题是“GPU 被占用，但平台看不到任务”或“训练进程还在，调度器认为任务结束”。systemd-cgls 能帮助判断这个进程来自容器、登录会话、服务，还是被遗留在某个 scope 中。

# 1. 从 GPU 侧拿 PID
nvidia-smi --query-compute-apps=pid,process_name,used_gpu_memory --format=csv

# 2. 查看 PID 的基础信息
ps -o pid,ppid,user,stat,etime,cmd -p 31772

# 3. 反查 cgroup 归属
cat /proc/31772/cgroup

# 4. 用 systemd-cgls 展开相关 cgroup 或整棵树中过滤 PID
sudo systemd-cgls --full --no-pager | grep -C 8 '31772'

# 5. 如果知道路径，直接看子树
sudo systemd-cgls /sys/fs/cgroup/kubepods.slice/kubepods-burstable.slice/pod-example.slice --full --no-pager

训练进程常见形态

torchrun + 多个 worker
通常会看到一个 launcher 和多个 Python worker；如果在同一个 cgroup 下，说明资源限制对整组进程生效。
DataLoader worker
大量短命 Python 子进程可能和主训练进程同属一个容器 cgroup；CPU 飙升时要结合 ps -L、pidstat 查线程和子进程。
NCCL/通信辅助进程
通常仍在训练 cgroup 下，但网络和 RDMA 问题要继续用 ss、rdma、ibstat、nvidia-smi topo 交叉验证。
Jupyter 启动训练
常见于 user.slice 或 notebook 容器 cgroup 下；要分清 notebook server、kernel 和真实训练 worker。
操作警告： kill、systemctl stop、crictl stop、kubectl delete pod 都是破坏性操作。先截图/保存 systemd-cgls、ps、/proc/PID/cgroup、平台任务 ID，再按组织流程处理。

7. 从 PID 反查 cgroup

systemd-cgls 适合从树找进程；/proc/PID/cgroup 适合从进程找树。AI Infra 排障中，两者通常一起使用。

# cgroup v2 常见输出：0:: 后面是统一层级路径
cat /proc/31772/cgroup
0::/kubepods.slice/kubepods-burstable.slice/kubepods-burstable-pod9d4a.slice/cri-containerd-7f0.scope

# 拼成实际 cgroup 文件路径
CG=$(awk -F: '$1=="0"{print $3}' /proc/31772/cgroup)
echo "/sys/fs/cgroup$CG"

# 查看该 cgroup 的进程列表和线程列表
sudo cat "/sys/fs/cgroup$CG/cgroup.procs"
sudo cat "/sys/fs/cgroup$CG/cgroup.threads"

# 直接展开这个 cgroup
sudo systemd-cgls "/sys/fs/cgroup$CG" --full --no-pager
文件用途注意
/proc/PID/cgroup查看 PID 所属 cgroup 路径v1 会按 controller 多行显示，v2 通常是 0::/path
cgroup.procs该 cgroup 及其直接成员进程不同层级读取结果可能不同，注意是否在叶子 cgroup
cgroup.threads线程级成员排查多线程 CPU 问题时有用
cgroup.controllersv2 可用 controller确认 CPU、memory、io、pids 等 controller 是否启用
实用习惯： 在工单里同时贴 PID、/proc/PID/cgroup、systemd-cgls --full 相关子树，后续关联 pod/container/job 会快很多。

8. Kubernetes 与 containerd cgroup

Kubernetes 节点上，训练容器的 cgroup 名称取决于 kubelet 的 cgroup driver、runtime 和 cgroup 版本。systemd driver 下经常能看到 kubepods.slice、QoS slice、pod UID slice、cri-containerd-<container-id>.scope。这正是从 Linux 视角映射回 Kubernetes 对象的入口。

# 查看 kubelet cgroup driver 和运行参数线索
ps -o pid,cmd -C kubelet
systemctl show kubelet.service -p ControlGroup -p ExecStart

# containerd 进程和 shim 通常在 system.slice 下
sudo systemd-cgls --unit containerd.service --full --no-pager

# 在整棵树中寻找某个容器 ID 前缀
sudo systemd-cgls --full --no-pager | grep -C 5 '7f0a1b2c3d4e'

# 用 crictl 从容器 ID 反查 pod/container 元数据
sudo crictl ps -a | grep '7f0a1b2c3d4e'
sudo crictl inspect 7f0a1b2c3d4e | grep -E '"name"|"podSandboxId"|"pid"'

常见 Kubernetes cgroup 形态

形态常见含义排障动作
kubepods.slice/kubepods-besteffort.slice/...BestEffort pod，没有显式 request/limit资源争抢风险高，优先查调度规格和节点压力
kubepods-burstable-pod<uid>.sliceBurstable pod，部分容器设置 request/limit检查 CPU quota、memory.max、OOM 事件
kubepods-pod<uid>.sliceGuaranteed pod 或不同发行版命名按 pod UID 反查 Kubernetes 对象
cri-containerd-<id>.scopecontainerd 创建的具体容器 scope取容器 ID 前缀，用 crictl inspect 关联
# 从 pod UID 反查集群对象，注意 Kubernetes UID 中的 '-' 在 cgroup 名里可能被转义或改写
kubectl get pod -A -o wide | grep 'train'
kubectl get pod -A -o jsonpath='{range .items[*]}{.metadata.namespace}{"\t"}{.metadata.name}{"\t"}{.metadata.uid}{"\n"}{end}' | grep '9d4a'

# 查看 pod 资源规格和 QoS
kubectl describe pod -n ml train-job-0 | sed -n '/Containers:/,/Conditions:/p'
kubectl get pod -n ml train-job-0 -o jsonpath='{.status.qosClass}{"\n"}'
路径 caveat： 不同 Kubernetes 版本、发行版、runtime、cgroup driver 会导致路径差异。不要把示例路径写死到自动化脚本中；脚本应从 /proc/PID/cgroup 或 runtime API 动态获取。

9. Docker、Podman、nerdctl 场景

非 Kubernetes 场景中，容器可能由 Docker、Podman、nerdctl 或直接由 containerd 管理。systemd-cgls 的作用仍然是回答“容器进程在哪个 cgroup/scope 里”。

# Docker 守护进程归属
sudo systemd-cgls --unit docker.service --full --no-pager

# containerd 归属，Docker 和 nerdctl 都可能间接使用它
sudo systemd-cgls --unit containerd.service --full --no-pager

# 用 Docker 反查容器主进程 PID
docker ps --no-trunc
docker inspect -f '{{.State.Pid}} {{.Name}} {{.Id}}' CONTAINER_ID
cat /proc/$(docker inspect -f '{{.State.Pid}}' CONTAINER_ID)/cgroup

# Podman rootless 常在 user.slice 下，先从整棵树中过滤线索
systemd-cgls --full --no-pager | grep -C 8 -E 'podman|libpod|conmon'
rootful Docker
守护进程在 system.slice/docker.service，容器进程路径可能体现 docker/containerd scope，具体取决于 cgroup driver。
rootless Podman
经常落在用户 cgroup 树下，排障时不要只看 system.slice。
nerdctl/containerd
容器 shim 常由 containerd 管理；容器 ID 前缀是关联 runtime 元数据的重要线索。
AI 镜像训练
训练进程可能是容器 entrypoint、launcher 子进程或 notebook kernel；要结合容器内外 PID 映射判断。
容器内外 PID： 容器内看到的 PID 1 不一定是宿主机 PID 1。systemd-cgls 在宿主机上显示的是宿主机 PID；关联容器内进程时要通过 runtime inspect 或 nsenter 进一步确认。

10. 资源隔离线索

systemd-cgls 本身不会显示所有资源限制，但它给出 cgroup 路径。拿到路径后，就可以读取 CPU、memory、io、pids 等控制文件，判断训练是否被 quota、cpuset、内存上限或 pids 上限影响。

# 假设 CG 是从 /proc/PID/cgroup 得到的 v2 路径
CG=$(awk -F: '$1=="0"{print $3}' /proc/31772/cgroup)
CGDIR="/sys/fs/cgroup$CG"

# CPU 限制和权重
cat "$CGDIR/cpu.max"        # max 100000 表示不设 quota；50000 100000 表示 50% 一个 CPU
cat "$CGDIR/cpu.weight"     # v2 权重，范围通常 1..10000

# 内存限制、当前值、事件
cat "$CGDIR/memory.max"
cat "$CGDIR/memory.current"
cat "$CGDIR/memory.events"

# pids 限制
cat "$CGDIR/pids.max"
cat "$CGDIR/pids.current"

# cpuset，排查 CPU 绑核/NUMA 约束
cat "$CGDIR/cpuset.cpus.effective"
cat "$CGDIR/cpuset.mems.effective"
线索可能现象下一步
cpu.max 很低DataLoader 慢、CPU 预处理跟不上 GPU检查 pod CPU limit、systemd CPUQuota、调度规格
memory.events 中 oom/oom_kill 增加训练 worker 被杀、进程消失、容器重启查 journalctl -k、kubectl describe pod、应用日志
pids.current 接近 pids.max无法 fork、DataLoader worker 创建失败检查 pids limit、线程/进程泄漏
cpuset.cpus.effective 很窄多卡训练 CPU 侧瓶颈、NUMA 不匹配结合 numactl -H、lscpu、pod CPU manager 策略
关键连接： systemd-cgls 给你 cgroup 位置；cgroup 文件告诉你资源规则和事件；指标工具告诉你当前消耗。三者合起来才是完整判断。

11. cgroup v1/v2 caveats

现代发行版越来越多默认使用 cgroup v2 unified hierarchy，但老节点、容器宿主机或特殊内核参数可能仍是 v1 或 hybrid。systemd-cgls 会尽量展示 systemd 管理的层级，但你读取限制文件和解析 /proc/PID/cgroup 时必须区分版本。

# 判断 cgroup v2 是否启用
stat -fc %T /sys/fs/cgroup
# cgroup2fs 表示 unified cgroup v2

# v2 常见：/proc/PID/cgroup 只有 0::/path
cat /proc/31772/cgroup
0::/user.slice/user-1000.slice/session-12.scope

# v1 常见：每个 controller 一行，路径可能不完全相同
cat /proc/31772/cgroup
11:memory:/kubepods/burstable/pod9d4a/7f0...
10:cpu,cpuacct:/kubepods/burstable/pod9d4a/7f0...
9:pids:/kubepods/burstable/pod9d4a/7f0...
主题cgroup v1cgroup v2排障建议
层级每个 controller 可有不同层级统一层级v1 不要假设 memory/cpu 路径完全一致
CPU quota 文件cpu.cfs_quota_us、cpu.cfs_period_uscpu.max脚本按版本分支读取
内存限制文件memory.limit_in_bytesmemory.max注意 v1 可能出现很大的“无限制”数值
事件文件分散在 controller 文件中memory.events 等更统一OOM 排障优先确认版本
systemd driver路径可能较旧式slice/scope 命名更常见不要写死 Kubernetes 路径模板
兼容性提醒： --xattr 和 --cgroup-id 是较新的 systemd 选项；在旧发行版上可能不可用。自动化脚本应先检测 systemd-cgls --help。

对比图：systemd-cgls、systemd-cgtop、ps、/proc 怎么分工

不要把 systemd-cgls 当成万能性能工具；它最强的是结构归属，其他信息要靠配套工具补齐。

12. systemd-cgls vs cgtop/proc/ps

工具最适合回答不适合回答典型命令
systemd-cgls进程属于哪个 cgroup/unit/slice/scope实时 CPU/GPU 利用率systemd-cgls --full --no-pager
systemd-cgtop哪个 cgroup 当前消耗 CPU/内存/IO/任务数完整命令行和平台对象映射systemd-cgtop --depth=4

13. AI Infra 排障工作流

下面是一个生产可用的排障框架：先确认现象，再定位归属，再验证资源限制，最后决定操作路径。

场景 A：GPU 被占用但平台无任务

# 取 GPU PID
nvidia-smi --query-compute-apps=pid,process_name,used_gpu_memory --format=csv

# 查 PID 属于哪个 cgroup
PID=31772
ps -o pid,ppid,user,stat,etime,cmd -p "$PID"
cat "/proc/$PID/cgroup"
sudo systemd-cgls --full --no-pager | grep -C 10 "$PID"

# 判断是否是 Kubernetes 容器
cat "/proc/$PID/cgroup" | grep -E 'kubepods|cri-containerd|docker|libpod' || true

场景 B：训练很慢，怀疑 CPU 被限

PID=31772
CG=$(awk -F: '$1=="0"{print $3}' "/proc/$PID/cgroup")
CGDIR="/sys/fs/cgroup$CG"

cat "$CGDIR/cpu.max"
cat "$CGDIR/cpuset.cpus.effective"
ps -o pid,psr,pcpu,stat,cmd -p "$PID"
pidstat -p "$PID" 1 5

场景 C：容器重启或 worker 消失

PID=31772
CG=$(awk -F: '$1=="0"{print $3}' "/proc/$PID/cgroup")
CGDIR="/sys/fs/cgroup$CG"

cat "$CGDIR/memory.events"
journalctl -k --since '30 min ago' | grep -Ei 'oom|killed process|memory'
kubectl describe pod -n ml train-job-0 | grep -A8 -Ei 'State:|Last State:|OOM|Reason'
推理纪律： 看到 memory.events 有 oom_kill 只能说明该 cgroup 发生过 OOM kill；要判断是不是当前训练导致，还要看时间、容器 restart count、内核日志和应用日志。

14. 常见问题与陷阱

陷阱 1：把 cgroup 树当进程树
缩进表示资源层级，不表示 PPID。父子关系请用 ps 或 pstree。
陷阱 2：忘记 --full
训练命令行很长，默认输出可能省略关键参数；排障取证优先加 --full --no-pager。
陷阱 3：只看 system.slice
Jupyter、rootless Podman、用户级 scope 可能在 user.slice。
陷阱 4：Kubernetes 路径写死
cgroup driver、runtime、版本不同会改变路径；自动化应从 /proc/PID/cgroup 动态取。
陷阱 5：空 cgroup 默认隐藏
怀疑 unit 存在但没进程时，用 --all。
陷阱 6：权限导致信息缺失
普通用户可能看不到完整命令行或其他用户进程；用授权的 sudo 只读查看。
陷阱 7：混淆 v1/v2 文件名
cpu.max 是 v2；v1 要读 cpu.cfs_quota_us 等 controller 文件。
陷阱 8：只靠单一工具下结论
cgroup 归属、资源限制、实际消耗、业务对象必须交叉验证。

排障模板

# 最小取证包：不修改系统状态

systemd-cgls --version
sudo systemd-cgls --full --no-pager | sed -n '1,220p'

# 针对某个 PID 的取证包

ps -o pid,ppid,user,stat,etime,cmd -p "$PID"
cat "/proc/$PID/cgroup"
cat "/proc/$PID/status" | sed -n '1,80p'

15. 安全与生产取证

在共享 GPU 集群或训练平台上，排障的目标不是“最快杀掉可疑进程”，而是先把归属和影响面查清楚，避免误杀长期训练、在线推理服务或其他团队作业。

建议保存的证据

# 建议把输出重定向到工单附件目录，路径按现场规范选择
mkdir -p /tmp/cgls-evidence
date -Is | tee /tmp/cgls-evidence/time.txt
hostname -f | tee /tmp/cgls-evidence/host.txt

sudo systemd-cgls --full --no-pager > /tmp/cgls-evidence/systemd-cgls.full.txt
ps -eo pid,ppid,user,stat,etime,pcpu,pmem,cmd > /tmp/cgls-evidence/ps.txt
nvidia-smi > /tmp/cgls-evidence/nvidia-smi.txt 2>&1

# 针对目标 PID
PID=31772
cat "/proc/$PID/cgroup" > "/tmp/cgls-evidence/$PID.cgroup.txt"
cat "/proc/$PID/status" > "/tmp/cgls-evidence/$PID.status.txt"
处置红线： 未确认 owner、平台对象和影响面前，不要直接执行 kill -9、systemctl stop、kubectl delete pod 或清理容器 runtime 目录。尤其不要删除 /sys/fs/cgroup 下文件来“清理”进程。

何时升级

  • 同一 cgroup 下有在线推理服务和训练进程混跑，资源隔离边界不清楚。
  • memory.events、内核日志、容器状态三者互相矛盾。
  • PID 属于 kubelet/containerd/dockerd 等关键服务本身，而不是普通工作负载。
  • 怀疑 runtime 泄漏、shim 残留、pod 已删除但 cgroup 未回收。

常用命令速查

目标命令
查看完整 cgroup 树sudo systemd-cgls --full --no-pager
包含空 cgroupsudo systemd-cgls --all --full --no-pager

练习任务

  1. 在一台测试 Linux 机器上运行 systemd-cgls --full --no-pager，找出 system.slice、user.slice 和你的登录 session-*.scope。
  2. 启动一个普通 sleep 600，用 ps 找 PID，再用 /proc/PID/cgroup 和 systemd-cgls 定位它在哪个 scope。
  3. 如果有容器环境，启动一个测试容器，比较 docker inspect/crictl inspect 的 PID 与宿主机 systemd-cgls 输出。
  4. 在 cgroup v2 节点上读取 cpu.max、memory.max、memory.events，理解无限制和有限制的表示方式。
  5. 比较 systemd-cgls 和 systemd-cgtop 对同一训练或测试进程给出的不同信息。
# 安全练习：只启动 sleep，不占用 GPU
sleep 600 &
PID=$!
echo "PID=$PID"
ps -o pid,ppid,user,stat,etime,cmd -p "$PID"
cat "/proc/$PID/cgroup"
systemd-cgls --full --no-pager | grep -C 5 "$PID"
kill "$PID"
练习说明： 最后一行 kill "$PID" 只清理你刚刚创建的 sleep 练习进程；在真实训练排障中不要套用到未知 PID。
