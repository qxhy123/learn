1. fio 是什么：不是 dd 的加强版

fio 的全称是 Flexible I/O Tester。它可以模拟不同 IO 引擎、块大小、读写比例、队列深度、线程/进程数量、文件布局、运行时长和延迟目标。与 dd 相比，fio 更适合做可解释、可复现、可对比的存储基准。

它能回答
单盘顺序读能跑多高？随机 4K 读 P99 多大？数据加载 64K 随机读是否被 metadata 或队列深度卡住？checkpoint 写入会不会拖慢训练 step？
它不能直接回答
真实训练端到端性能一定提升多少。fio 是底层 IO 负载近似，仍需结合 dataloader、文件格式、缓存、网络和训练 profiler。
正确定位
fio 是“显微镜”和“压测器”：先把存储子系统看清楚，再把结果映射到 AI workload。
# 最小非破坏性随机读测试：在 /tmp 创建测试文件，不碰裸设备
fio --name=smoke-randread \
    --directory=/tmp \
    --size=256M \
    --rw=randread \
    --bs=4k \
    --iodepth=16 \
    --numjobs=1 \
    --time_based --runtime=20s \
    --direct=1 \
    --group_reporting
先理解再跑： 同一个设备用 bs=4k rw=randread 和 bs=1m rw=read 得到的不是“谁更真实”，而是两个完全不同的问题。

2. AI Infra 的存储问题模型

先从 AI 场景抽象出 IO 形状，再用 fio 参数表达。这样结果才有工程含义。

3. 安装、版本与最小安全测试

不同发行版的 fio 版本可能不同，输出字段和引擎支持也会有差异。团队内做对比时，应记录 fio 版本、内核版本、文件系统、设备型号、挂载参数和测试命令。

# 查看版本
fio --version

# Debian/Ubuntu
sudo apt-get update
sudo apt-get install fio

# RHEL/CentOS/Rocky/Alma
sudo dnf install fio

# macOS 可用于学习参数，但不要把结果等同于 Linux 生产环境
brew install fio

最小 smoke test

# 非破坏性：在当前目录生成一个 128M 文件，做 10 秒读测试
mkdir -p fio-lab
fio --name=smoke \
    --directory=fio-lab \
    --size=128M \
    --rw=read \
    --bs=1m \
    --time_based --runtime=10s \
    --direct=1 \
    --group_reporting

# 清理测试文件前先确认目录
ls -lh fio-lab
rm -f fio-lab/smoke.*
不要把教程命令直接指向生产目录： 对共享训练数据、checkpoint 目录、数据库目录和裸设备测试前，必须明确谁拥有目录、是否可覆盖、是否影响其他作业。

4. fio 的核心参数心智模型

fio 命令看起来参数很多，但核心只有四类：数据在哪里、怎么访问、并发多大、跑多久并如何汇总。

where
测试对象
directory、filename、size、filesize、nrfiles
shape
访问形状
rw、rwmixread、bs、random_distribution
load
负载强度
numjobs、iodepth、ioengine、direct
time
运行与报告
runtime、time_based、ramp_time、group_reporting
参数含义AI Infra 常用判断
--rw=randread随机读小样本、多 shard、shuffle 后读取
--bs=4k单次 IO 大小4K/16K 看元数据与小块，256K/1M 看大样本流
--iodepth=32单 job 队列深度模拟异步预取、并发 dataloader 请求
--numjobs=8并发 job 数模拟多个 worker、多个训练进程或多租户
--direct=1尽量绕过页缓存避免把内存缓存误当成磁盘性能
经验公式： 总并发约等于 numjobs × iodepth。但真实效果还受 IO 引擎、文件系统、设备队列、网络、服务端限流影响。

对照图：顺序/随机 × 读/写/混合

AI 存储瓶颈常出现在随机读和混合读写，而不是顺序吞吐峰值。

5. 顺序、随机、读、写、混合负载

rw 决定 IO 方向和访问顺序。AI 场景中，数据预处理和 checkpoint 更像顺序大块，dataloader shuffle 更像随机小块，多任务共享缓存则更像混合读写。

rw含义典型场景风险
read顺序读连续读取大 tar/webdataset shard、模型权重加载容易掩盖随机访问问题
randread随机读小文件样本、shuffle 后分散读取、metadata 压力对共享文件系统可能造成明显影响
write顺序写checkpoint、日志、转换后数据集落盘会覆盖测试文件内容
randwrite随机写缓存更新、KV/索引写入近似破坏性强，容易触发 SSD 写放大
randrw随机混合读写训练读数据同时写缓存/checkpoint读写互相干扰，结果解释更复杂
# 顺序读：看大块吞吐
fio --name=seq-read --directory=fio-lab --size=4G \
    --rw=read --bs=1m --iodepth=16 --numjobs=1 \
    --time_based --runtime=60s --direct=1 --group_reporting

# 随机读：看 IOPS 与尾延迟
fio --name=rand-read --directory=fio-lab --size=4G \
    --rw=randread --bs=4k --iodepth=32 --numjobs=4 \
    --time_based --runtime=60s --direct=1 --group_reporting

# 混合随机：70% 读、30% 写。仅在测试目录执行
fio --name=mixed --directory=fio-lab --size=4G \
    --rw=randrw --rwmixread=70 --bs=16k \
    --iodepth=32 --numjobs=4 --time_based --runtime=60s \
    --direct=1 --group_reporting
写测试会改变文件： 在生产数据目录运行 write、randwrite、rw、randrw 前必须确认路径是专用测试文件或专用测试盘。

6. 块大小：从 4K 元数据到 1M 样本流

bs 是单次 IO 的大小。它直接决定 fio 测的是 IOPS、吞吐还是两者之间的折中。AI Infra 中不要只测一个 bs，至少覆盖 4K、16K、64K、256K、1M。

小块：4K/16K
适合观察随机元数据、小文件、索引、碎片化访问。瓶颈通常是 IOPS、队列调度和 P99。
中块：64K/256K
常用于数据加载、压缩块、对象缓存和预取。既看吞吐，也看并发下的延迟。
大块：1M/4M
适合顺序流式读取、checkpoint 写入、模型权重加载。瓶颈通常是带宽、网络和写入 flush。
# 用一个循环扫块大小，结果输出 JSON 方便后续解析
for bs in 4k 16k 64k 256k 1m; do
  fio --name=bs-${bs} --directory=fio-lab --size=2G \
      --rw=randread --bs=${bs} --iodepth=32 --numjobs=4 \
      --time_based --runtime=45s --direct=1 \
      --group_reporting --output-format=json \
      --output=fio-randread-${bs}.json
done
读结果方式： 小块结果重点看 IOPS 和延迟百分位；大块结果重点看带宽和稳定性。不要把 4K IOPS 和 1M GB/s 混成一个“性能分”。

7. 并发、numjobs 与 iodepth

numjobs 表示启动多少个 job 副本，iodepth 表示每个 job 的异步队列深度。对于 libaio 或 io_uring，较高的 iodepth 能让设备队列保持忙碌；对于同步引擎，iodepth 可能没有预期效果。

组合近似含义适合场景
numjobs=1 iodepth=1单请求串行 IO最小延迟、基线、排除并发影响
numjobs=1 iodepth=32单进程异步预取一个 dataloader worker 有深预取队列
numjobs=8 iodepth=8多 worker 中等队列8 个 worker 并发加载样本
numjobs=32 iodepth=32高压多租户共享存储极限压测，需隔离窗口
# 并发扫描：找出吞吐上升、延迟爆炸的拐点
for depth in 1 2 4 8 16 32 64; do
  fio --name=depth-${depth} --directory=fio-lab --size=4G \
      --rw=randread --bs=16k --ioengine=libaio \
      --iodepth=${depth} --numjobs=4 \
      --time_based --runtime=45s --ramp_time=10s \
      --direct=1 --group_reporting
done
拐点比峰值更重要： AI 训练通常需要稳定 step time。若 iodepth=64 让平均吞吐更高但 P99 延迟翻倍，未必是更好的生产配置。

8. direct IO 与页缓存陷阱

direct=1 尝试绕过 Linux 页缓存，让 fio 更接近设备或文件系统本身的性能。没有 direct=1 时，第二次读测试可能主要命中内存缓存，从而把内存带宽误当作磁盘性能。

模式优点风险适合问题
direct=1减少页缓存干扰不同 FS/设备支持不同；对齐要求更严格设备能力、共享 FS 后端能力
direct=0接近普通应用 buffered IO缓存命中会显著美化结果应用是否受 Linux cache 保护
冷缓存读接近首次加载清缓存是全机影响操作数据集首次读取、作业冷启动
热缓存读接近重复 epoch不能代表存储后端能力页缓存、节点本地缓存效果
# 对比 direct 与 buffered，观察是否被页缓存影响
fio --name=direct-read --directory=fio-lab --size=2G \
    --rw=read --bs=1m --iodepth=16 --direct=1 \
    --time_based --runtime=30s --group_reporting

fio --name=buffered-read --directory=fio-lab --size=2G \
    --rw=read --bs=1m --iodepth=16 --direct=0 \
    --time_based --runtime=30s --group_reporting
谨慎清缓存： echo 3 > /proc/sys/vm/drop_caches 会影响整机所有进程，生产机器上不要为了一次 fio 测试随意执行。

流程图：从问题到 job file 的可复现流程

团队内的 fio 结果如果不能复现，就很难用于容量规划和故障复盘。

9. job file：把测试变成可复现资产

命令行适合探索，job file 适合复现、评审和归档。对 AI Infra 团队，建议把常用场景固化成 job file：随机读、顺序读、混合读写、checkpoint 写、共享 FS 多客户端。

# ai-randread.fio
[global]
ioengine=libaio
direct=1
time_based=1
runtime=120s
ramp_time=20s
group_reporting=1
directory=fio-lab
size=8G
thread=1

[dataset-small-random-read]
rw=randread
bs=16k
iodepth=32
numjobs=8
# 运行 job file，并输出机器可读 JSON
mkdir -p fio-lab results
fio ai-randread.fio \
    --output-format=json \
    --output=results/ai-randread-$(hostname)-$(date +%Y%m%d-%H%M%S).json
job file 字段建议
[global]放公共设置：direct、runtime、ramp_time、group_reporting、directory
独立 job 段每个场景一个段，名字表达问题，不要叫 test1
输出优先保留 JSON；人读摘要可以后处理生成 Markdown

10. 读懂输出：IOPS、BW、lat、clat

fio 输出很多，先抓住四个指标：IOPS、带宽、完成延迟、延迟百分位。对异步 IO，clat 通常比 lat 更常用于观察设备完成请求的耗时；报告时说明采用哪个字段。

read: IOPS=184k, BW=718MiB/s (753MB/s)(42.1GiB/60001msec)
  slat (nsec): min=1200, max=98200, avg=4100
  clat (usec): min=85, max=12800, avg=692.31
   lat (usec): min=88, max=12805, avg=696.50
  clat percentiles (usec):
   |  1.00th=[  190], 50.00th=[  620], 95.00th=[ 1205],
   | 99.00th=[ 2409], 99.90th=[ 5538], 99.99th=[10159]
字段怎么读常见误读
IOPS每秒完成多少次 IO只对固定块大小有意义；不同 bs 不能直接比
BW吞吐量，常用 MiB/s 或 GB/s高吞吐不代表低尾延迟
slat提交延迟，fio 提交请求耗时过高可能是 fio 端 CPU/调度问题，不一定是盘慢
clat完成延迟，设备/系统完成请求耗时平均值会掩盖 P99/P999
lat总延迟，通常包含提交与完成不同 ioengine 下解释要谨慎
AI 视角： step time 更怕“偶发慢请求”。平均延迟很漂亮但 P99 很差时，dataloader worker 可能周期性拖住 GPU。

11. 延迟百分位：P50/P95/P99/P999

平均值回答“通常多快”，百分位回答“尾部有多糟”。AI 训练中，尾部延迟会表现为 GPU utilization 抖动、step time 长尾、checkpoint 停顿或多机同步等待。

P50
中位数，代表常规体验。适合比较常态性能。
P95
轻度尾部，常用于观察稳定性开始变差的点。
P99
生产常用尾延迟指标。对 dataloader 和服务化推理很关键。
P999/P9999
极端尾部。共享文件系统、多租户和网络存储尤其要看。
# 显式关注延迟分布，并减少启动阶段干扰
fio --name=p99-randread --directory=fio-lab --size=8G \
    --rw=randread --bs=16k --ioengine=libaio \
    --iodepth=32 --numjobs=8 \
    --time_based --runtime=180s --ramp_time=30s \
    --direct=1 --group_reporting \
    --percentile_list=50:90:95:99:99.9:99.99
现象可能解释下一步
P50 低、P99 高偶发排队、GC、网络抖动、共享后端拥塞同时看 iostat -x、服务端日志、网络重传
P50/P99 都高负载超过设备能力或参数过激降低 iodepth、分离读写、改数据布局
IOPS 低但延迟也低fio 端没有压满，可能并发不足增加 numjobs 或 iodepth
IOPS 高但训练仍慢瓶颈不在块设备，可能是解码、Python、网络或文件格式结合 profiler、strace、dataloader 指标

12. AI 数据集加载基准

数据集加载不是单一 IO 形状。小图片散文件、WebDataset shard、Parquet、LMDB、mmap token 文件，对存储提出的压力完全不同。fio 的价值在于把这些形状拆开测。

数据形态近似 fio 负载重点指标
百万级小文件图片randread bs=4k/16k numjobs=worker数IOPS、metadata、P99
tar/webdataset shardread bs=256k/1m顺序带宽、预取稳定性
mmap token 文件randread bs=4k/64k随机读延迟、页缓存效果
远端共享 FSrandread/randrw 多客户端尾延迟、公平性、服务端瓶颈
# 模拟 8 个 dataloader worker 的随机小块读取
fio --name=dataloader-8w \
    --directory=/mnt/ai-test/fio-lab \
    --size=16G \
    --rw=randread \
    --bs=16k \
    --ioengine=libaio \
    --iodepth=16 \
    --numjobs=8 \
    --time_based --runtime=180s --ramp_time=30s \
    --direct=1 --group_reporting

# 模拟 shard 顺序读取
fio --name=shard-stream \
    --directory=/mnt/ai-test/fio-lab \
    --size=64G \
    --rw=read \
    --bs=1m \
    --iodepth=32 \
    --numjobs=4 \
    --time_based --runtime=180s --ramp_time=30s \
    --direct=1 --group_reporting
落地建议： 先用 fio 找底层上限和尾延迟，再用真实 dataloader benchmark 验证端到端。两者结论不一致时，优先怀疑文件格式、解码、Python 进程和缓存策略。

13. checkpoint 与写入路径基准

checkpoint 写入通常是大块顺序写，但真实系统中还包含临时文件、rename、fsync、分布式 rank 并发写和共享后端刷盘。fio 可以分别测试顺序写吞吐、混合读写干扰和同步落盘成本。

# 安全准备：使用专用测试目录，不使用真实 checkpoint 目录
mkdir -p /mnt/ai-test/fio-checkpoint-lab
df -h /mnt/ai-test/fio-checkpoint-lab

# 顺序写：近似单机 checkpoint 大文件写入
fio --name=ckpt-write \
    --directory=/mnt/ai-test/fio-checkpoint-lab \
    --size=32G \
    --rw=write \
    --bs=1m \
    --iodepth=16 \
    --numjobs=2 \
    --time_based --runtime=120s --ramp_time=20s \
    --direct=1 --group_reporting

# 读写混合：训练读数据时写 checkpoint
fio --name=ckpt-mixed \
    --directory=/mnt/ai-test/fio-checkpoint-lab \
    --size=32G \
    --rw=randrw --rwmixread=80 \
    --bs=256k \
    --iodepth=16 \
    --numjobs=4 \
    --time_based --runtime=120s --ramp_time=20s \
    --direct=1 --group_reporting
写入测试要看持续性： 很多 SSD 或缓存层前几十秒很快，缓存耗尽后掉速。使用 runtime=300s 或更久才能看出稳态写入。

14. 共享文件系统与多客户端测试

NFS、Lustre、BeeGFS、CephFS、GPFS 等共享文件系统的性能不只由客户端单机决定。单客户端 fio 只能回答局部问题；多客户端同时跑同一个 job file，才能观察后端服务、网络和公平性。

多客户端基本策略

策略做法目的
每客户端独立目录/mnt/fs/fio/$HOSTNAME避免互相覆盖，减少锁竞争干扰
统一 job file所有节点使用同一份参数保证可比性
统一时间窗口用调度器或脚本同时启动观察真实并发拥塞
收集服务端指标元数据服务、对象服务、网卡、磁盘定位瓶颈在客户端还是后端
# 每个客户端只写自己的测试目录
export FIO_ROOT=/mnt/shared/fio-lab/$(hostname)
mkdir -p "$FIO_ROOT"

fio --name=shared-randread \
    --directory="$FIO_ROOT" \
    --size=8G \
    --rw=randread \
    --bs=64k \
    --iodepth=16 \
    --numjobs=8 \
    --time_based --runtime=300s --ramp_time=30s \
    --direct=1 --group_reporting \
    --output-format=json \
    --output="shared-randread-$(hostname).json"
共享 FS 压测要预约窗口： 高并发随机 IO 可能影响同集群训练任务。生产集群上必须设定测试窗口、限速范围和回滚方案。

安全图：fio 破坏性风险分级

fio 最大的风险不是参数写错报错，而是参数写对了、目标路径写错了。

15. 破坏性安全与测试隔离

fio 可以直接对裸块设备发起写入，这在实验室很有用，在生产上也极危险。安全策略要写进命令模板，而不是靠临场记忆。

危险操作为什么危险安全替代
--filename=/dev/nvme0n1 --rw=write可能覆盖整个块设备数据只在已下线、已确认、可重建的测试盘执行
--directory=/mnt/train-data --rw=randwrite会在生产数据目录创建/改写文件使用 /mnt/ai-test/fio-lab 等隔离目录
--size=90%可能占满共享文件系统固定小规模起步，逐步增加并监控 df
生产时段高并发压测影响训练作业和其他租户预约维护窗口，设置 runtime 和限流
# 安全启动清单：先确认路径、容量和目标文件
export FIO_DIR=/mnt/ai-test/fio-lab
mkdir -p "$FIO_DIR"
pwd
df -h "$FIO_DIR"
find "$FIO_DIR" -maxdepth 1 -type f -ls | head

# 先跑只读或小 size，再扩大
fio --name=safety-first --directory="$FIO_DIR" --size=512M \
    --rw=read --bs=1m --runtime=10s --time_based --direct=1

# 如果必须清理，只清理专用前缀
find "$FIO_DIR" -maxdepth 1 -type f -name 'safety-first.*' -print
find "$FIO_DIR" -maxdepth 1 -type f -name 'safety-first.*' -delete
裸设备规则： 只有在设备已从业务摘除、已确认盘符、已备份或可重建，并且团队接受数据丢失风险时，才考虑 filename=/dev/... 写测试。

16. fio vs dd、iostat、iotop、nvme

这些工具不是互相替代，而是分工不同。fio 负责制造负载，iostat/nvme 负责观察系统侧证据，dd 适合极简烟测，iotop/pidstat 适合看进程维度。

工具定位适合不适合
fio可控 IO 负载发生器基准测试、容量规划、尾延迟分析直接解释应用层全部瓶颈
dd简单顺序读写快速烟测、验证路径可写随机 IO、并发、延迟百分位
iostat -x块设备监控看利用率、await、队列、设备饱和制造负载或区分应用逻辑
iotop进程 IO 观察找哪个进程在读写精确块设备性能分析
nvmeNVMe 管理与健康信息SMART、温度、错误、设备特性文件系统/共享 FS 层分析
# fio 压测时并行观察块设备
iostat -x 1

# NVMe 健康信息
sudo nvme smart-log /dev/nvme0

# 极简 dd 烟测：只用于粗略观察，不替代 fio
dd if=/dev/zero of=/mnt/ai-test/dd-smoke.bin bs=1M count=1024 oflag=direct status=progress
rm -f /mnt/ai-test/dd-smoke.bin
组合证据： 如果 fio 显示延迟很高，同时 iostat 的 util 接近 100%、await 升高，瓶颈更可能在块设备或下层；如果设备不忙，继续查网络、文件系统、权限、CPU 或 fio 参数。

排障图：fio 结果不可信时怎么拆

不可信结果通常来自缓存、并发不足、目标路径错误、fio 端 CPU 瓶颈或共享后端干扰。

17. Troubleshooting：结果不可信怎么办

症状常见原因处理方法
吞吐高得离谱命中页缓存；测试文件小于内存；没有 direct=1扩大 size、使用 direct=1、区分热缓存和冷缓存
iodepth 增加但性能不变ioengine 不支持异步；设备或 FS 限制；fio 端 CPU 瓶颈尝试 ioengine=libaio 或 io_uring，看 CPU 与 iostat
P99 周期性尖刺后台 flush、SSD GC、共享后端拥塞、网络抖动延长 runtime，记录时间序列，结合服务端与网络指标
写入一开始快后面慢缓存耗尽、SLC cache 退化、后端限速增加 runtime 和测试数据量，关注稳态而非开头峰值
多次结果差异大共享负载、温度、CPU 调度、文件布局不同固定窗口、重复 3 次以上、记录背景负载与温度
共享 FS 单客户端快，多客户端慢metadata server、object server、网络或锁竞争瓶颈每客户端独立目录，收集服务端指标，调整数据布局
# 压测时的并行观察命令
uname -a
fio --version
df -hT /mnt/ai-test/fio-lab
mount | grep /mnt/ai-test
iostat -x 1
pidstat -d 1
sar -n DEV,TCP,ETCP 1
排障原则： 不要只保存 fio 的最后一行。完整命令、完整输出、环境信息和同时段系统指标，才足以支撑结论。
