1. tcpdump 是什么

tcpdump 是基于 libpcap 的命令行抓包工具。它从指定网络接口读取数据包，使用 BPF 表达式在内核侧尽量早过滤，再把匹配包打印到终端或写入 pcap 文件。

它擅长什么
验证某台机器是否发包/收包、确认 SYN/SYN-ACK/RST、保存小样本 pcap、用 host/port/protocol 快速缩小问题面。
它不擅长什么
长时间全量流量审计、应用层协议深度解析、大规模可视化分析、RDMA 数据路径完整观测。
AI Infra 价值
在分布式训练、参数服务器、对象存储、推理网关和 NCCL 初始化阶段，快速判断问题在应用、内核、路由、防火墙还是对端。
# 最小抓包：在指定接口上抓 10 个包，不解析 DNS，不解析端口名
sudo tcpdump -i eth0 -nn -c 10

# 抓某个训练节点之间的 TCP 控制面流量
sudo tcpdump -i eth0 -nn 'host 10.0.3.21 and tcp'

# 把小样本写入 pcap，后续用 tcpdump/tshark/Wireshark 分析
sudo tcpdump -i eth0 -nn -s 128 -c 500 -w /tmp/train-node.pcap 'host 10.0.3.21'
边界提醒： tcpdump 看到的是“经过该接口且能被捕获的数据包”。如果流量走了另一个网卡、被 offload 改写、在内核旁路/RDMA 数据路径中传输，tcpdump 看到的内容可能不完整。

信息图：packet capture 心智模型

tcpdump 通常在内核网络栈和接口附近观察包副本。抓不到包不一定代表应用没发，也可能是接口、命名空间、offload、隧道或 RDMA 数据路径选择错误。

2. 安装、权限与版本

tcpdump 需要抓取原始包，通常要求 root 权限或 CAP_NET_RAW/CAP_NET_ADMIN 能力。生产环境不要为了方便给普通用户永久开放抓包权限，应通过受控 sudo、堡垒机或应急流程执行。

任务命令说明
查看版本tcpdump --version确认 tcpdump 与 libpcap 版本，排查过滤语法兼容性。
Debian/Ubuntu 安装sudo apt-get install tcpdump容器镜像中常被裁剪，需要临时安装或用 debug 镜像。
RHEL/CentOS 安装sudo yum install tcpdump新系统也可能使用 dnf。
列接口sudo tcpdump -D比只看 ip link 更接近 tcpdump 可捕获接口列表。
# 容器里检查权限和命名空间
id
capsh --print 2>/dev/null | grep -E 'cap_net_raw|cap_net_admin' || true
ip netns identify $$ 2>/dev/null || true

# 在 Kubernetes 节点上抓 Pod 流量时，先确认流量在哪个命名空间/接口
ip addr
ip route
sudo tcpdump -D
权限提醒： pcap 文件可能包含 token、Cookie、请求体、内部 IP 和模型服务路径。保存、传输、上传前必须脱敏或确认安全边界。

3. 接口选择与方向

抓包第一步不是写复杂过滤器，而是选对接口。AI 服务器常见多网卡：管理网、业务网、IB/RoCE 网、bond、VLAN、容器 veth、CNI bridge。接口选错时，过滤器再正确也看不到包。

选项作用适合场景
-i eth0指定接口最推荐，范围可控。
-i any抓所有可见接口的合并视图快速判断包是否经过本机，但链路层信息可能简化。
-Q in/-Q out限制方向排查只发不收、只收不回时有用，支持情况依平台而异。
-e打印二层头观察 MAC、VLAN、bond/交换侧线索。
# 看路由决定流量可能走哪张网卡
ip route get 10.0.3.21

# 在候选接口上抓少量 ICMP/TCP 样本
sudo tcpdump -i eth0 -nn -c 20 'host 10.0.3.21'
sudo tcpdump -i bond0 -nn -c 20 'host 10.0.3.21'

# 快速确认本机是否看到相关流量
sudo tcpdump -i any -nn -c 50 'host 10.0.3.21 and (tcp or udp)'
容器场景： Pod 内抓包看到的是 Pod 网络命名空间；节点上可能要看 veth*、CNI bridge、overlay 接口或物理 NIC。先用 ip route get、ss -tnp、CNI 工具定位路径。

4. 输出字段怎么读

tcpdump 默认输出是“每个包一行”的摘要。理解时间戳、五元组、flags、seq/ack、窗口和长度，能快速看出 TCP 是否建立、谁先关闭、是否出现 RST 或重传迹象。

12:01:03.123456 IP 10.0.1.10.45678 > 10.0.1.20.443: Flags [S], seq 100, win 64240, options [mss 1460,sackOK,TS val 1 ecr 0], length 0
12:01:03.124010 IP 10.0.1.20.443 > 10.0.1.10.45678: Flags [S.], seq 900, ack 101, win 65160, options [mss 1460,sackOK,TS val 2 ecr 1], length 0
12:01:03.124060 IP 10.0.1.10.45678 > 10.0.1.20.443: Flags [.], ack 901, win 502, length 0
字段含义排障价值
12:01:03.123456抓包主机时间戳和应用日志、NCCL 日志、内核日志对齐。
IP/IP6三层协议确认 IPv4/IPv6 是否和配置一致。
src.port > dst.port源和目的地址端口确认实际连接方向、NAT 后地址、端口是否符合预期。
Flags [S]TCP 标志位SYN、SYN-ACK、ACK、FIN、RST 是连接生命周期线索。
lengthTCP 负载长度区分控制包和有载荷数据包。
# 常用输出控制：不做名称解析，打印绝对 seq，时间戳更详细
sudo tcpdump -i eth0 -nn -tttt -S -c 20 'tcp and host 10.0.1.20'

# 打印链路层头，观察 VLAN/MAC
sudo tcpdump -i eth0 -nn -e -c 20 'host 10.0.1.20'

5. BPF 过滤器基础

BPF 过滤器是 tcpdump 的核心能力。表达式越精确，内核复制给用户态的包越少，对生产节点越安全。基本结构是：限定类型、限定方向、限定地址/端口、用布尔逻辑组合。

过滤器含义例子
host源或目的主机host 10.0.1.20
src host/dst host源/目的主机src host 10.0.1.10
port源或目的端口port 443
tcp/udp/icmp协议tcp and port 443
net网段net 10.0.0.0/8
and/or/not布尔组合host A and not port 22
# 注意 shell 里的括号要加引号
sudo tcpdump -i eth0 -nn 'host 10.0.1.20 and (tcp port 443 or tcp port 8443)'

# 排除 SSH，避免自己的远程登录刷屏
sudo tcpdump -i eth0 -nn 'host 10.0.1.20 and not port 22'

# 只看 SYN 包，定位连接发起和是否被回应
sudo tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-syn != 0 and host 10.0.1.20'
语法提醒： BPF 表达式建议整体用单引号包起来，避免 shell 把括号、&、|、! 提前解释。

流程图：从问题到 BPF 过滤器

过滤器不是越复杂越好，而是越贴近问题越好。先用小包数验证，再扩大样本。

6. host、port、protocol 组合

AI Infra 排障常围绕“训练节点 A 到节点 B 的某个端口是否通”“对象存储/参数服务/调度器有没有响应”“连接被谁 RST”。下面是常用组合。

# 单 host 的所有 TCP/UDP
sudo tcpdump -i eth0 -nn 'host 10.0.1.20 and (tcp or udp)'

# 两个训练节点之间的流量
sudo tcpdump -i eth0 -nn 'host 10.0.1.10 and host 10.0.1.20'

# 只看访问对象存储或推理网关的 HTTPS
sudo tcpdump -i eth0 -nn 'dst host 10.0.2.15 and tcp dst port 443'

# 端口范围，例如服务动态端口或分布式训练 rendezvous 范围
sudo tcpdump -i eth0 -nn 'tcp and portrange 20000-20100'

# DNS 解析问题
sudo tcpdump -i eth0 -nn 'udp port 53 or tcp port 53'
排障问题推荐过滤器看什么
节点 A 连接 B 超时host A and host B and tcpA 是否发 SYN，B 是否回 SYN-ACK/RST。
服务端没收到请求dst host server and dst port P包是否到达服务端网卡。
怀疑本机回包走错路src host server and dst host client回包接口和源地址是否符合预期。
DNS 慢或失败port 53查询发往哪个 resolver，是否有响应。

7. 安全采样与性能控制

高吞吐训练节点上，全量抓包可能消耗 CPU、内存、磁盘和 I/O，甚至改变被观测系统的时延。生产抓包要把“观察成本”当成排障风险的一部分。

控制项命令作用
限制包数-c 1000达到包数自动退出。
限制时长timeout 30 tcpdump ...避免忘记停止。
限制 snaplen-s 96/-s 128只保存包头和少量载荷，降低敏感数据和磁盘压力。
不解析名称-nn避免 DNS/服务名解析带来延迟和噪声。
行缓冲-l管道实时处理时减少缓冲等待。
丢弃统计结束输出关注 captured/received/dropped by kernel。
# 生产推荐起步：短时、小包数、小 snaplen、精确过滤
sudo timeout 20 tcpdump -i eth0 -nn -s 128 -c 1000 \
  -w /tmp/sample.pcap 'host 10.0.1.20 and tcp and not port 22'

# 只看摘要，不保存载荷
sudo timeout 10 tcpdump -i eth0 -nn -q -c 100 'host 10.0.1.20'

# 抓包结束后关注 dropped by kernel；如果非零，样本可能不完整
sudo tcpdump -i eth0 -nn -c 1000 'tcp port 443'
生产红线： 不要在忙碌的 100G/200G/400G 训练网卡上长时间 -s 0 全包保存；不要把 pcap 发到外部工单系统前不脱敏；不要在 SSH 会话里抓 port 22 导致输出刷屏。

8. pcap 写入、轮转与读取

终端输出适合快速判断，pcap 适合离线分析和共享证据。写 pcap 时优先保存最小可复现样本：明确接口、过滤器、时长、snaplen、机器名和时间窗口。

# 写入 pcap：-w 后 tcpdump 不再打印逐包摘要
sudo tcpdump -i eth0 -nn -s 128 -c 5000 \
  -w /tmp/$(hostname)-api-$(date +%Y%m%d-%H%M%S).pcap \
  'host 10.0.2.15 and tcp port 443'

# 读取 pcap 并用新过滤器二次筛选
tcpdump -nn -r /tmp/sample.pcap 'tcp[tcpflags] & tcp-rst != 0'

# 轮转：每 60 秒一个文件，最多保留 5 个
sudo tcpdump -i eth0 -nn -s 128 -G 60 -W 5 \
  -w '/tmp/api-%Y%m%d-%H%M%S.pcap' \
  'host 10.0.2.15 and tcp port 443'
选项含义建议
-w file.pcap写 pcap适合证据留存和离线分析。
-r file.pcap读 pcap可继续加 BPF 过滤器。
-s 0保存完整包仅在低流量、安全授权、确需应用载荷时使用。
-C size按文件大小轮转，单位 MB防止磁盘被打满。
-G sec按时间轮转适合等待偶发问题。
证据命名： pcap 文件名建议包含主机、接口、目标、时间和过滤条件摘要；排障记录中写清楚抓包主机时钟是否和集群 NTP 同步。

信息图：TCP 握手、失败与关闭线索

三次握手是定位连接问题的第一张地图：SYN 有没有出去，SYN-ACK 有没有回来，是否被 RST，决定下一步查路由、防火墙、监听还是应用。

9. TCP 握手与连接失败

连接超时、连接拒绝、偶发初始化失败，是分布式训练和推理服务中最常见的网络症状。tcpdump 能把应用报错拆成具体包序列。

抓包现象常见含义下一步
只看到客户端 SYN 重复服务端没收到、回包丢失、防火墙丢弃、路由不通在服务端同时抓；查安全组、iptables、路由、ToR。
SYN 后立即 RST目标端口未监听或被中间设备拒绝服务端查 ss -ltnp、应用日志、端口配置。
SYN/SYN-ACK/ACK 完成但应用超时TCP 通了，问题可能在 TLS、协议、应用处理或队列结合 ss -ti、应用指标、服务端 pcap。
握手方向地址不符合预期NAT、容器网络、源地址选择或多网卡路由问题查 ip route get、policy routing、CNI。
# 只抓 TCP 握手和 RST/FIN 类控制包
sudo tcpdump -i eth0 -nn -tttt \
  'host 10.0.1.20 and tcp and (tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0)'

# 服务端确认某端口是否有 SYN 到达
sudo tcpdump -i eth0 -nn 'dst host 10.0.1.20 and tcp dst port 29500'

# 客户端确认是否收到 SYN-ACK/RST
sudo tcpdump -i eth0 -nn 'src host 10.0.1.20 and tcp src port 29500'
双端抓包： 单端抓包只能说明“这台机器看到什么”。连接问题最好在客户端和服务端同一时间窗口各抓一份，对齐时间戳后比较包是否在中途消失。

10. 重传、乱序与零窗口线索

tcpdump 不像 Wireshark 那样直接标注 “TCP Retransmission”，但可以从重复 seq、重复 SYN、重复 ACK、窗口变化和时间间隔中找线索。对性能问题，tcpdump 更适合提供方向性证据，而不是单独完成定量归因。

# 用绝对序列号更容易比较重复 seq
sudo tcpdump -i eth0 -nn -S -tttt 'host 10.0.1.20 and tcp port 443'

# 抓窗口和 ACK 变化，配合 ss -ti 看拥塞/重传计数
ss -ti dst 10.0.1.20
sudo tcpdump -i eth0 -nn -tttt 'host 10.0.1.20 and tcp'

# 只看 ACK 包和小包时，可以降低样本量
sudo tcpdump -i eth0 -nn -c 2000 'host 10.0.1.20 and tcp and less 128'
线索可能原因辅助工具
相同 seq 的数据包重复出现丢包、ACK 丢失、重传ss -ti、网卡计数、交换机端口错误。
大量 duplicate ACK乱序或丢包Wireshark/tshark 专业分析。
窗口变小或零窗口接收端应用读不动、内核缓冲受限ss -m、进程 CPU、GC/阻塞日志。
周期性 SYN 重传连接建立阶段无响应双端抓包、路由和防火墙。
精度提醒： TSO/GSO/GRO/LRO 等 offload 会改变主机侧看到的包形态。需要精细分析包大小和分段时，要同时查看 ethtool -k，必要时在镜像口或对端抓包验证。

11. AI 训练流量画像

AI Infra 的网络流量通常分为控制面、数据面、存储面和观测面。tcpdump 对控制面最有用，对高吞吐数据面要谨慎采样。

控制面
rendezvous、scheduler、etcd、API、SSH、DNS。适合 tcpdump 精确定位。
训练数据面
NCCL、Gloo、parameter server、RPC。吞吐高，抓包必须限量。
存储面
S3/OSS、NFS、Lustre、Ceph、镜像拉取。关注连接、TLS、重试和 DNS。
观测面
Prometheus、日志、trace、metrics。可确认采集是否到达和响应。
# PyTorch rendezvous 常见端口示例，按实际 MASTER_PORT 修改
sudo tcpdump -i eth0 -nn 'host 10.0.1.10 and tcp port 29500'

# 观察对象存储访问是否建立 TCP/TLS 连接
sudo tcpdump -i eth0 -nn -s 128 -c 1000 \
  '(tcp port 443 or tcp port 80) and host 10.0.2.15'

# DNS 对训练启动时间影响很大
sudo tcpdump -i eth0 -nn -tttt 'port 53'
排障顺序建议： 训练任务启动失败先抓控制面端口和 DNS；训练中吞吐抖动再结合 NCCL 日志、网卡计数、交换机遥测、ss、ethtool 和 pcap 小样本。

12. NCCL/RDMA Caveats

NCCL 与 RDMA/RoCE 场景要特别小心 tcpdump 的观察边界。RoCEv2 使用 UDP/IP 封装，可能能在以太网接口看到部分包；InfiniBand verbs 或内核旁路路径上，tcpdump 可能看不到实际数据流，只能看到控制面或相关 IP 流量。

场景tcpdump 能帮什么不能替代什么
NCCL 初始化失败确认 bootstrap/rendezvous TCP 连接、DNS、错误网卡选择。不能解释所有 NCCL 内部拓扑和算法选择。
RoCEv2可能观察 UDP 4791、ECN/DSCP、源目的 IP。不能完整评估 PFC、ECN、交换机队列和 NIC 拥塞控制。
InfiniBand可辅助看 IPoIB 或控制面。不能完整抓 verbs 数据路径。
GPUDirect RDMA可确认控制连接和主机网络配置。不能直接证明 GPU-NIC DMA 路径健康。
# NCCL 常见第一步：确认它选了哪张网卡
env | grep -E 'NCCL_SOCKET_IFNAME|NCCL_IB_HCA|NCCL_DEBUG'
ip addr
ip route get 10.0.1.20

# RoCEv2 常见 UDP 端口，是否适用取决于网卡/驱动/网络
sudo tcpdump -i eth0 -nn -s 128 -c 1000 'udp port 4791'

# NCCL bootstrap TCP 连接按实际 peer 和端口过滤
sudo tcpdump -i eth0 -nn 'host 10.0.1.20 and tcp'
RDMA 注意： RDMA 性能问题不要只看 pcap。必须结合 ibstat/ibv_devinfo、rdma link、NIC counters、DCGM、交换机 telemetry、PFC/ECN 配置和 NCCL_DEBUG 日志。

用例图：tcpdump、tshark、ss、ethtool 怎么分工

tcpdump 是现场取证入口，不是唯一答案。复杂问题要把 pcap、socket 状态、网卡计数和应用日志放在同一条时间线上。

13. tcpdump vs tshark/ss

工具优势限制AI Infra 用法
tcpdump轻量、几乎随处可用、BPF 精确过滤、能写 pcap。协议解析有限，重传等高级标注不如 Wireshark。线上短时抓包、证据采集、验证是否发/收。
tshark解码强、字段过滤强、适合离线批处理 pcap。安装较重，线上直接跑需谨慎。对 pcap 做重传、TLS、HTTP/2、DNS 细分析。
ss读取内核 socket 状态，能看进程、队列、拥塞信息。不显示逐包路径。确认连接状态、Send-Q/Recv-Q、重传计数。
ethtool看 NIC counters、offload、速率和错误。不告诉你具体哪条连接受影响。定位丢包、CRC、pause、offload 干扰。
# tcpdump 取证
sudo tcpdump -i eth0 -nn -s 128 -c 5000 -w /tmp/evidence.pcap 'host 10.0.1.20 and tcp'

# ss 看同一连接的内核状态
ss -ti dst 10.0.1.20

# tshark 离线统计协议层信息
tshark -r /tmp/evidence.pcap -q -z conv,tcp 2>/dev/null

# ethtool 看网卡计数
ethtool -S eth0 | egrep -i 'drop|err|timeout|crc|pause|discard'

14. 故障排查流程

tcpdump 排障应遵循“先定位路径，再抓最小样本，再双端对齐，再扩大证据”的顺序。不要一开始就全接口、全包、长时间抓取。

  1. 明确问题：连接失败、吞吐低、DNS 慢、偶发 RST、某 rank 掉线。
  2. 定位路径：ip route get、ss -tnp、服务端监听、容器命名空间。
  3. 写最小过滤器：host + protocol + port + not port 22。
  4. 短时验证：-c 20 或 timeout 10 看是否抓到预期包。
  5. 保存证据：-s 128 -w file.pcap，必要时双端同时抓。
  6. 关联证据：应用日志、NCCL 日志、ss、ethtool、交换机计数。
# 一个可复用的最小排障模板
PEER=10.0.1.20
PORT=29500
IFACE=eth0

ip route get "$PEER"
ss -tnp "dst $PEER" 2>/dev/null || true
sudo timeout 15 tcpdump -i "$IFACE" -nn -s 128 -c 1000 \
  -w "/tmp/$(hostname)-${PEER}-${PORT}.pcap" \
  "host $PEER and tcp port $PORT and not port 22"
结论写法： 好的抓包结论应描述“在哪台机器、哪个接口、什么时间窗口、用什么过滤器、看到了什么包序列、没有看到什么预期包”。

安全排障图：线上抓包的风险控制

线上 tcpdump 的第一目标是得到足够证据，第二目标是尽量少打扰业务，第三目标是避免敏感数据扩散。

15. 常见命令手册

快速看包
sudo tcpdump -i eth0 -nn -c 20
指定主机
sudo tcpdump -i eth0 -nn 'host 10.0.1.20'
指定端口
sudo tcpdump -i eth0 -nn 'tcp port 443'
排除 SSH
sudo tcpdump -i eth0 -nn 'not port 22'
写 pcap
sudo tcpdump -i eth0 -nn -s 128 -w /tmp/a.pcap 'host 10.0.1.20'
读 pcap
tcpdump -nn -r /tmp/a.pcap 'tcp'
看 SYN/RST/FIN
sudo tcpdump -i eth0 -nn 'tcp[tcpflags] & (tcp-syn|tcp-rst|tcp-fin) != 0'
短时安全采样
sudo timeout 15 tcpdump -i eth0 -nn -s 128 -c 1000 'host 10.0.1.20'
默认组合： 新手建议把 -i、-nn、-c、精确 BPF 当成固定模板；需要保存时再加 -s 128 -w。

16. 常见坑与练习

坑 1：接口选错
先用 ip route get PEER 和 tcpdump -D 定位接口。
坑 2：忘记 -nn
名称解析会引入 DNS 噪声，也会让输出不稳定。
坑 3：过滤器没加引号
&、括号、or 可能被 shell 解释。
坑 4：抓到自己的 SSH
远程排障时通常加 and not port 22。
坑 5：把无包误判为无流量
也可能是命名空间、接口、offload、隧道或 RDMA 路径问题。
坑 6：pcap 泄露敏感数据
限制 -s，控制权限，必要时脱敏。
坑 7：忽略 dropped by kernel
抓包丢弃意味着样本不完整，不能据此做精确统计。
坑 8：单端抓包下结论过重
网络路径问题需要双端或中间设备证据。

练习任务

  1. 用 tcpdump -D 找出可抓包接口，并解释每个接口可能对应的网络。
  2. 对一个可访问的 HTTPS 服务抓 20 个 TCP 包，识别 SYN、SYN-ACK、ACK。
  3. 写一个过滤器：只抓某 peer 的 TCP 443，排除 SSH。
  4. 把 500 个包写入 pcap，再用 tcpdump -r 只筛选 RST 包。
  5. 在客户端和服务端同时抓同一连接，对齐时间戳判断包是否中途丢失。
  6. 查看 ethtool -k 和 ethtool -S，说明 offload/counter 对 pcap 解释的影响。
# 本机安全练习：抓 loopback 上的 HTTP 请求
python3 -m http.server 18080 >/tmp/tcpdump-demo.log 2>&1 &
PID=$!
sudo timeout 10 tcpdump -i lo -nn -c 20 'tcp port 18080' &
curl -s http://127.0.0.1:18080/ >/dev/null
wait
kill "$PID" 2>/dev/null || true
