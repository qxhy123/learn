1. hl-smi 是什么

hl-smi 是 Intel Gaudi 软件栈提供的 System Management Interface 工具，用来获取和监控 Intel Gaudi AI 加速器的信息。它通常安装在带 Habana/Gaudi 驱动、固件和运行时的 Linux 节点上，是排查 HPU/AIP 是否正常工作的入口命令。

它擅长什么
设备列表、PCIe 地址、驱动/固件版本、温度、功耗、显存、利用率、ECC/row replacement、进程、拓扑、Gaudi NIC 状态。
它不等于什么
它不是性能 profiler，不能替代 Habana profiler、框架日志、HCCL/NIC 诊断、训练吞吐统计或应用层 trace。
它的定位
节点现场“第一轮分诊”：先判定硬件是否可见、是否被占用、是否处于异常健康状态，再决定深入哪条链路。
# 查看所有已识别的 Gaudi 加速器摘要
hl-smi

# 列出 Gaudi AIP 设备
hl-smi -L

# 查看完整查询信息
hl-smi -q

# 查看帮助和本机支持的选项
hl-smi -h
权限提醒： 在非 root 或容器内运行时，某些字段可能显示 N/A，尤其是其他用户的进程信息。需要完整进程视图时，在宿主机上用 sudo hl-smi。

信息图：hl-smi 的整体心智模型

把 hl-smi 当成“节点级事实来源”：先用它确认硬件和驱动层，再逐步上钻到容器、框架、通信库和训练脚本。

2. 安装来源与运行环境

hl-smi 随 Intel Gaudi / Habana 软件包安装，通常在 Gaudi 服务器镜像、驱动包或厂商提供的容器/宿主机环境中可用。它依赖内核驱动、固件、设备节点和管理库；只有二进制存在不代表节点健康。

检查项命令判断
命令是否存在command -v hl-smi找不到说明软件包或 PATH 不完整。
版本信息hl-smi -v记录 hl-smi/驱动栈版本，便于和集群基线对比。
设备是否可见hl-smi -L无设备时先查驱动、PCIe 枚举、容器透传。
完整权限视图sudo hl-smi宿主机 root 更容易看到所有用户进程和管理字段。
# 基础自检脚本片段
set -eu
command -v hl-smi
hl-smi -v
hl-smi -L
hl-smi -q | sed -n '1,80p'
容器 caveat： 容器内能否看到 Gaudi 设备取决于设备节点、驱动库、运行时和调度器注入方式。容器内 hl-smi 异常时，要同时在宿主机运行一次作对照。

3. 设备发现与身份映射

AI Infra 排障最怕“看错卡”。Gaudi 输出里常见多个标识：index、AIP/accelN、bus_id、module_id、serial、uuid。其中 index 是 OS 分配的编号，可能在重启或驱动重载后变化；module_id 更偏物理位置，bus_id 适合和 PCIe、NUMA、容器设备映射关联。

# 列出设备
hl-smi -L

# 用 CSV 方式拿到稳定排障字段
hl-smi -Q index,module_id,bus_id,serial,uuid,name,driver_version -f csv

# 定位某个 PCIe 设备
hl-smi -i 0000:08:00.0 -q
字段适合用途注意点
index快速命令输出和本机短时定位可能随 OS 枚举变化，不建议写入长期资产表。
bus_id绑定 PCIe、NUMA、容器和 lspci 信息格式通常类似 0000:08:00.0。
module_id对应板上/OAM 物理位置更适合和机型槽位图、报修流程关联。
serial/uuid资产、RMA、跨重启追踪记录时避免混入用户日志中的敏感环境信息。
值班习惯： 报障单里同时写 hostname、bus_id、module_id、serial 和作业 ID，比只写“卡 3 坏了”更可复现。

4. 默认摘要表怎么看

直接运行 hl-smi 会显示检测到的 Gaudi 设备摘要。不同软件版本和硬件代际的列名可能略有不同，但读法类似：先看设备是否齐，再看温度/功耗/显存/利用率/进程是否符合预期。

# 最常用的一眼检查
hl-smi

# 如果怀疑权限导致进程看不全
sudo hl-smi
数量
机器应有 8 张却只显示 7 张，先查 PCIe 枚举、驱动和硬件状态。
显存
任务结束后 memory.used 长期不降，可能有残留进程、框架上下文或异常 fd。
温度/功耗
高温、功耗异常、violation 计数增加，优先看散热、限功耗、机房环境。
进程
有 PID 却无人认领时，结合 ps、systemd-cgls、容器 runtime 查归属。
不要只看利用率： 训练卡住时，利用率可能为 0%，也可能周期性抖动。要把利用率和显存、进程、网络、CPU wait、框架日志一起判断。

5. 查询模式：-q、-d、-Q

hl-smi 有三类常用查询方式：默认摘要用于人工快速看；-q 适合完整报告；-d 适合只看某类信息；-Q 配合 -f csv 适合脚本采集和监控。

方式示例适合场景
摘要hl-smi登录节点后第一眼检查。
完整查询hl-smi -q收集 issue、工单、RMA 现场信息。
分类显示hl-smi -q -d MEMORY只关注 PRODUCT、POWER、CLOCK、TEMPERATURE、FAN、BUS、MEMORY、NET、ROW_REPLACEMENT 等一类信息。
字段查询hl-smi -Q timestamp,bus_id,memory.used -f csv脚本解析、定时采样、写入日志。
# 只看显存相关报告
hl-smi -q -d MEMORY

# 只看温度相关报告
hl-smi -q -d TEMPERATURE

# 采集常用指标，去掉单位便于后续处理
hl-smi -Q timestamp,index,bus_id,utilization.aip,memory.used,memory.total,temperature.aip,power.draw \
  -f csv,nounits
字段 caveat： 官方支持的 -Q 字段随版本扩展。脚本里应先在目标镜像上运行 hl-smi -h 或小样本命令，确认字段名和单位。

流程图：从“训练变慢”到 hl-smi 分诊

值班时不要从 profiler 开始。先用 hl-smi 判断问题在节点基础栈、资源占用、热/电/链路，还是上层应用。

6. 利用率与“空闲假象”

utilization.aip 表示采样窗口内硬件组件是否繁忙的简化利用率视图，适合发现“卡根本没跑起来”或“负载周期性断档”。但它不是模型吞吐、MFU 或 kernel 级 profiler 指标。

# 单次查询利用率
hl-smi -Q timestamp,index,bus_id,utilization.aip -f csv

# 每 5 秒循环输出，观察是否周期性掉到 0
hl-smi -Q timestamp,index,bus_id,utilization.aip,memory.used -f csv,nounits -l 5
现象可能原因下一步
util 长期 0，显存也低任务未拿到设备、容器未透传、框架 fallback、数据加载卡住查容器设备、框架设备枚举、CPU/dataloader、作业日志。
util 长期 0，显存很高进程占显存但未计算、死锁、通信等待、断点调试定位 PID，查栈、日志、HCCL/NIC、分布式 barrier。
util 周期性尖峰输入 pipeline 不稳、host 到 device 拷贝/编译/同步开销看 dataloader、CPU wait、框架 profiler、recipe cache。
单卡 util 明显低rank 偏斜、NUMA/PCIe/NIC 问题、某卡降频对比 bus_id、温度、功耗、拓扑、通信测试。
解释边界： 利用率为 90% 不等于训练效率高；利用率为 0% 也不一定是硬件坏。它是分诊指标，不是最终性能结论。

7. 显存、HBM 与进程定位

Gaudi 训练/推理问题里，显存是最常见线索之一。memory.total、memory.used、memory.free 可以帮助区分 OOM、残留上下文、模型碎片化、进程泄漏和调度误分配。

# 显存快照
hl-smi -Q timestamp,index,bus_id,memory.total,memory.used,memory.free -f csv

# 观察任务结束后显存是否释放
hl-smi -Q timestamp,index,bus_id,memory.used,memory.free -f csv,nounits -l 10

# 用 root 查看完整进程归属，再用 ps 展开命令行
sudo hl-smi
ps -fp 123456
ps -o pid,ppid,user,stat,etime,cmd -p 123456
训练前就有显存占用
先查是否有残留 Python、服务化推理进程、Jupyter、IDE 后台、系统健康检查或上一个作业未退出。
任务结束后显存不释放
不要直接 reset。先确认 PID、容器、作业调度状态和用户；必要时让调度器终止作业，避免破坏别人的运行中任务。
生产警告： kill -9 和设备 reset 都可能导致框架、通信库和调度器留下不一致状态。优先通过作业系统取消任务；手工清理前记录证据。

8. 温度、功耗与降频线索

温度和功耗是判断硬件健康、散热、限速的重要线索。temperature.aip 通常表示 SoC 多个传感器中的最高温；power.draw 在 -Q 中有版本/硬件语义差异，Gaudi 2/3 上它可能只反映 54V power rail，而默认摘要中的功耗可能是 54V 与 12V 合并视图。

# 温度、功耗和限速线索
hl-smi -Q timestamp,index,bus_id,temperature.aip,power.draw,stats.violation.power,stats.violation.thermal \
  -f csv

# 分类查看温度/功耗细节
hl-smi -q -d TEMPERATURE
hl-smi -q -d POWER
信号含义处理方向
某卡温度显著高风道、散热器、局部负载、机箱位置可能异常对比相邻卡、风扇、BMC、机房温度。
thermal violation 增长存在热相关限速事件降低负载只是缓解；根因多在散热/环境/固件策略。
power violation 增长功耗限制相关事件检查功耗上限、供电、机型推荐配置。
功耗低但 util 高指标口径、采样时序或 workload 类型差异用更长采样窗口和框架吞吐一起判断。
设置功耗上限： hl-smi -p/--power-max 是管理动作。只有在平台支持、维护窗口明确、目标设备确认后才执行。

对数据加载、host staging、通信和 CPU 绑核敏感的任务，拓扑信息会直接影响性能解释。

9. PCIe 与设备定位

bus_id 是把 hl-smi 和 Linux 设备树连接起来的关键字段。PCIe 链路降速、宽度异常、AER 错误或重训练问题，可能表现为单卡吞吐差、H2D/D2H 拷贝慢、训练 rank 偏斜。

# 查询 PCIe 字段
hl-smi -Q index,bus_id,pcie.link.gen.current,pcie.link.gen.max,pcie.link.width.current,pcie.link.width.max,pcie.link.speed.current,pcie.link.speed.max \
  -f csv

# 和 Linux PCIe 视图交叉验证
lspci -s 0000:08:00.0 -vv | sed -n '/LnkCap:/,/LnkSta:/p'

# 查内核是否有 PCIe/AER/驱动错误
dmesg -T | grep -Ei 'habana|gaudi|aer|pcie|habanalabs' | tail -100
排障问题hl-smi 线索Linux 侧补充
设备不见了hl-smi -L 数量不足lspci、dmesg、BMC、重插/硬件报修。
吞吐异常PCIe gen/width 低于预期BIOS、槽位、线缆/背板、链路重训练。
间歇性失败设备仍可见但错误计数或日志异常AER、驱动 reset、框架异常时间线。
定位策略： 先用 bus_id 锁定设备，再把 hl-smi、lspci、dmesg 和机型槽位图串起来。

10. Gaudi NIC 与链路状态

Gaudi 服务器的 scale-out 通信经常依赖设备侧网络能力。hl-smi -n 可以查询 Gaudi NIC 端口、链路和统计信息；这对 HCCL、分布式训练、跨节点吞吐异常尤其重要。

# 查看某个设备的 NIC 端口类型
hl-smi -n ports -i 0000:08:00.0

# 查看指定端口 link up/down
hl-smi --nic=link -i 0000:08:00.0 -P 0,1,2,3

# 查看统计，常用于错误包、丢包、重传线索
hl-smi --nic=stats -i 0000:08:00.0 -P 0
link DOWN
查线缆、交换机端口、端口配置、NIC mask、作业实际使用的 fabric。
stats 错误增长
结合交换机计数、RDMA/HCCL 日志、链路 flap 时间点判断。
单 rank 慢
把 rank → bus_id → NIC port → switch port 映射出来，找局部异常。
边界提醒： hl-smi 能显示 Gaudi 侧 NIC 状态，但完整网络排障还需要交换机、路由、RDMA 工具和集群拓扑信息。

11. CSV、循环采样与日志化

人工查看适合分诊，脚本采样适合复盘。-Q 选择字段，-f csv 输出 CSV，nounits 便于后处理，-l 可以按间隔循环采样。

# 每 5 秒采样一次，直接追加到日志
hl-smi -Q timestamp,index,bus_id,utilization.aip,memory.used,memory.free,temperature.aip,power.draw \
  -f csv,nounits -l 5 | tee -a /tmp/hl-smi-$(hostname)-$(date +%Y%m%d-%H%M%S).csv

# 只采样 12 次，避免无限运行
timeout 60s hl-smi -Q timestamp,index,bus_id,utilization.aip,memory.used,temperature.aip \
  -f csv,nounits -l 5 > /tmp/hl-smi-sample.csv

# 找出显存占用最高的行，示例假设 memory.used 是第 5 列
awk -F, 'NR>1 {print $0}' /tmp/hl-smi-sample.csv | sort -t, -k5,5nr | head
采样建议原因
采样命令写入工单避免“当时看着是 0%”这种不可复现描述。
带 hostname 和时间戳多节点训练必须能按节点对齐时间线。
限制采样时长防止值班脚本无限跑，占满终端或日志目录。
保留单位或明确 nounits不同版本字段单位可能影响后处理脚本。
实用做法： 对集群故障，优先采集所有节点同一字段集，再用 bus_id 和作业 rank 映射做横向比较。

12. 驱动、固件与运行时 caveats

很多 hl-smi 异常不是命令本身问题，而是驱动、固件、HLML、容器库、框架运行时或内核模块状态不一致。尤其在升级、回滚、混合镜像和裸机/容器切换后，要先核对版本矩阵。

# 版本和固件信息
hl-smi -v
hl-smi --fw-versions
hl-smi -Q index,bus_id,driver_version,name -f csv

# 内核模块和日志
lsmod | grep -Ei 'habana|habanalabs'
dmesg -T | grep -Ei 'habana|gaudi|habanalabs' | tail -200

# 容器内外对比
hl-smi -L
sudo nsenter -t 1 -m -u -i -n -p -- hl-smi -L 2>/dev/null || true
版本不匹配
表现为设备可见但框架初始化失败、字段 N/A、固件报告异常或运行时随机错误。按平台发布说明恢复到受支持组合。
容器库错配
容器内 hl-smi 正常不代表 PyTorch/Habana runtime 正常；还要验证框架能枚举 HPU 并运行最小计算。
升级纪律： 不要只升级用户态包或只替换容器镜像。Gaudi 栈通常需要驱动、固件、runtime、框架插件和容器注入方式一起验证。

13. hl-smi vs nvidia-smi/rocm-smi

hl-smi、nvidia-smi、rocm-smi 都是厂商 SMI 工具，但字段、设备模型、进程可见性、网络能力和管理动作不同。迁移脚本时不要机械替换命令名。

维度hl-sminvidia-smirocm-smi
主要硬件Intel Habana / Intel Gaudi AIP/HPUNVIDIA GPUAMD GPU / ROCm 平台
脚本查询-Q ... -f csv--query-gpu=... --format=csv多为显示选项和 JSON/CSV 相关能力，版本差异较大
设备选择-i <pci-addr> 常用 PCIe 地址-i <index/uuid>-d/--device 等版本相关形式
网络/拓扑包含 Gaudi NIC 与 topo -c -N有 topo、NVLink、PCIe 等生态字段有 PCIe、拓扑和 ROCm 相关工具链
迁移风险Gaudi 利用率、功耗 rail、AIP/index 语义需要单独理解GPU utilization/SM/memory 语义不能直接套到 Gaudi字段名和单位不能直接套到 Gaudi
# NVIDIA 脚本迁移前，先写出你真正需要的指标语义
# 例如：设备身份、利用率、显存、温度、功耗、PCIe、进程
hl-smi -Q timestamp,index,bus_id,utilization.aip,memory.used,memory.total,temperature.aip,power.draw \
  -f csv,nounits
迁移原则： 监控面板应该抽象“指标语义”，不是硬编码某厂商字段。不同 SMI 的同名指标也可能采样窗口、单位和统计口径不同。

15. 生产安全清单

hl-smi 的只读查询很适合自动化，但管理动作必须纳入变更纪律。下面这份清单适合贴到值班 Runbook。

只读命令可直接执行
hl-smi、hl-smi -L、hl-smi -q、hl-smi -Q ... -f csv、hl-smi topo -c -N、hl-smi -n link。
影响性命令需审批
hl-smi -r -i <bus_id>、hl-smi -p ...、重载驱动、重启节点、手工杀业务进程。

执行 reset 前的最低确认

# 1. 确认目标设备
hl-smi -Q index,module_id,bus_id,serial,uuid -f csv

# 2. 确认是否有进程占用
sudo hl-smi

# 3. 确认节点已从调度中摘除，且维护窗口允许
# 下面是示例，不同集群用不同调度器命令
scontrol show node "$HOSTNAME" 2>/dev/null || true
kubectl get node "$HOSTNAME" 2>/dev/null || true

# 4. 最后才执行 reset，且必须指定 PCIe 设备
sudo hl-smi -r -i 0000:08:00.0
红线： 不要在共享训练节点上看到显存高就 reset；不要凭 index 做长期自动化 reset；不要在不知道 bus_id 对应哪张物理卡时执行管理动作。
