1. gdb 与 gcore 解决什么问题

在 AI Infra 中，训练 job、推理 worker、embedding 服务、NCCL 通信进程、Python C++/CUDA extension 都可能表现为“还活着但不动”“偶发 crash”“GPU 利用率为 0 但进程占卡”“服务不返回且日志停住”。这类问题只看日志通常不够，需要看到 native 线程栈和崩溃现场。

gdb 适合
附加到活进程、暂停线程、打印 backtrace、切换线程、查看共享库、打开 core、检查 native 变量和寄存器。
gcore 适合
在进程仍运行时生成 core 文件，方便离线分析和交给开发者，不必一直占用线上节点。
AI Infra 价值
定位 C++ operator、CUDA runtime、PyTorch/TensorFlow extension、NCCL、glibc malloc、线程池、锁等待和驱动调用栈。
# 查看某个进程的所有线程栈，适合卡住现场
sudo gdb -q -p 12345
(gdb) set pagination off
(gdb) thread apply all bt
(gdb) detach
(gdb) quit

# 生成在线 core，之后离线分析
sudo gcore -o /var/tmp/core.infer-worker 12345
gdb /proc/12345/exe /var/tmp/core.infer-worker.12345
不要把 gdb 当成第一反应： 先看监控、日志、ps、top -H、nvidia-smi、strace -p 的风险是否更低；需要 native 栈或 core 证据时再 attach。

信息图：gdb/gcore 的整体心智模型

核心模型：先安全地拿到现场，再用匹配的二进制和符号把地址还原成可读的函数栈。

2. 安装、版本与环境准备

同一份 core 的可读性高度依赖工具版本、二进制、共享库和 debuginfo。最稳妥的做法是在同一台机器或同一镜像里分析，至少保存 /proc/PID/exe、/proc/PID/maps、容器镜像 digest、包版本和符号包来源。

项目命令说明
确认 gdbgdb --version建议与发行版配套，过旧版本可能识别不了新 DWARF 格式。
确认 gcorecommand -v gcore || rpm -q gdb多数 Linux 发行版的 gcore 随 gdb 包提供。
进程路径readlink -f /proc/$PID/exe离线打开 core 时通常需要这个可执行文件。
共享库映射cat /proc/$PID/maps用于确认加载了哪些 Python/CUDA/C++ .so。
限制信息cat /proc/$PID/limits看 core size、open files、memlock 等限制。
# Debian/Ubuntu
sudo apt-get update
sudo apt-get install -y gdb libc6-dbg

# RHEL/CentOS/Rocky
sudo yum install -y gdb
sudo debuginfo-install glibc libstdc++

# 记录现场元信息，便于离线复现
PID=12345
mkdir -p /var/tmp/gdb-case-$PID
readlink -f /proc/$PID/exe > /var/tmp/gdb-case-$PID/exe.path
cat /proc/$PID/maps > /var/tmp/gdb-case-$PID/maps.txt
cat /proc/$PID/status > /var/tmp/gdb-case-$PID/status.txt
cat /proc/$PID/limits > /var/tmp/gdb-case-$PID/limits.txt
AI Infra 建议： 构建自研 C++/CUDA extension 时保留未 strip 的构建产物或单独的 debug symbol 文件，否则 core 里只能看到地址和少量导出符号。

3. 生产安全检查清单

gdb -p 和 gcore 本质上都需要通过 ptrace 暂停并读取目标进程。对延迟敏感的推理服务、分布式训练 rank、参数服务器或网关进程，错误时机的一次 attach 可能触发超时、重试风暴或 job 失败。

业务影响
确认进程是否在请求路径上、是否有副本、是否可从负载均衡摘除、是否处于训练关键 barrier。
停顿窗口
普通 backtrace 常是秒级内；gcore 可能随 RSS 增大而明显变慢，TB 级虚拟映射更要谨慎。
数据敏感性
core 可能包含 prompt、token、密钥、用户数据、模型权重片段、环境变量和明文缓存。
落盘风险
core 文件大小通常接近进程可转储内存，先检查 df -h 和目标目录配额。
# attach 前的低风险检查
PID=12345
ps -p $PID -o pid,ppid,user,stat,etime,rss,vsz,cmd
top -H -p $PID
df -h /var/tmp
sudo cat /proc/$PID/status | egrep 'Name|State|Threads|VmRSS|VmSize|CoreDumping|TracerPid'

# 如果是服务进程，先在调度/网关层摘流量，再采集
# 示例伪命令：根据你的平台替换
# kubectl cordon NODE
# kubectl scale deployment/infer-worker --replicas=N-1
# lbctl drain --instance INSTANCE_ID
生产红线： 不要在未知影响、未知磁盘空间、未知数据分级的情况下对核心生产进程运行 gcore。如果只能在线采集，优先做短暂停顿的 thread apply all bt，再决定是否生成 core。

流程图：从告警到是否 attach

决策顺序：先低侵入证据，再业务影响，再采集 native 现场；不要把 attach 作为无脑默认动作。

4. 找到目标进程并判断是否适合 attach

定位 PID 时要避免误伤父进程、sidecar、shell wrapper 或同机其他租户的进程。AI 训练任务常有多个 rank、data loader、NCCL helper thread 和 Python 子进程，先确认你要看的到底是哪一个。

# 按命令关键字找进程
pgrep -af 'python|torchrun|vllm|triton|infer'

# 看线程级 CPU，找到忙等或卡住的线程
top -H -p 12345
ps -L -p 12345 -o pid,tid,psr,stat,pcpu,comm,wchan:32

# 看 GPU 进程映射
nvidia-smi
nvidia-smi pmon -c 1

# 确认是否已有调试器附加
grep -E 'TracerPid|State|Threads|VmRSS|CoreDumping' /proc/12345/status
现象优先检查是否适合 gdb/gcore
CPU 单线程 100%top -H、perf top适合 gdb 看 busy loop 栈，也适合 perf 低侵入采样。
所有线程睡眠，服务无响应wchan、strace -p、backtrace适合看锁等待、futex、IO、驱动调用。
GPU 占用但利用率 0nvidia-smi、线程栈、CUDA runtime适合看是否卡在同步、拷贝、allocator 或 NCCL。
进程刚 crash系统 core、日志、退出码优先找已有 core；活进程已不存在则不能 gcore。
线程 ID 转换： Linux 的 TID 可在 gdb 中对应 LWP。ps -L 看到的 TID，在 info threads 里通常显示为 LWP TID。

5. gdb attach 到卡住的进程

最小安全 attach 流程是：关闭分页、采集所有线程栈、记录共享库、detach。不要在生产进程里随意 continue、修改变量、调用函数或设置断点长期停住。

# 交互方式：适合现场探索
sudo gdb -q -p 12345
(gdb) set pagination off
(gdb) set print thread-events off
(gdb) info threads
(gdb) thread apply all bt
(gdb) info sharedlibrary
(gdb) detach
(gdb) quit

# 非交互方式：适合快速采集文本证据
sudo gdb -q -p 12345 \
  -ex 'set pagination off' \
  -ex 'set print thread-events off' \
  -ex 'info threads' \
  -ex 'thread apply all bt' \
  -ex 'info sharedlibrary' \
  -ex 'detach' \
  -ex 'quit' \
  > /var/tmp/gdb-bt.12345.txt 2>&1
gdb 命令用途常见解读
info threads列出线程与 LWP找当前线程、线程数量、线程名。
thread apply all bt所有线程 backtrace卡死和死锁最常用。
thread apply all bt full带局部变量的栈信息更多，也可能输出敏感数据。
info sharedlibrary列出加载的共享库确认 Python extension、CUDA/NCCL 库版本。
detach脱离目标进程生产现场必须明确执行。
输出敏感性： bt full 可能打印请求内容、路径、token、模型输入片段。生产交接通常先采 bt，需要变量时再按最小范围采集。

6. 用 gcore 生成在线 core

gcore 会附加目标进程并把可转储内存写成 core 文件。它对“偶现卡住但不能长时间占用现场”的问题很有用：在线只做一次快照，后续在隔离环境离线分析。

# 先做空间和影响检查
PID=12345
ps -p $PID -o pid,user,stat,etime,rss,vsz,cmd
df -h /var/tmp
grep -E 'VmRSS|VmSize|Threads|TracerPid' /proc/$PID/status

# 生成 core，文件名通常为 /var/tmp/core.infer.12345
sudo gcore -o /var/tmp/core.infer $PID
ls -lh /var/tmp/core.infer.$PID

# 采集二进制路径和 maps，便于离线分析
readlink -f /proc/$PID/exe | sudo tee /var/tmp/core.infer.$PID.exe.path
sudo cp /proc/$PID/maps /var/tmp/core.infer.$PID.maps
优点
离线可重复查看栈、内存映射、线程状态；便于交给 runtime、kernel、framework 或业务开发者。
成本
进程会暂停；大内存进程写 core 很慢；文件可能极大且敏感。
适合时机
可摘流量、有副本、问题现场稀缺、需要保留证据、不能长时间在线调试。
安全提示： core 文件不是普通日志。它可能包含模型权重、用户输入、环境变量、访问凭据和堆上缓存，必须按敏感数据处理、加密传输、限制留存。

7. 离线打开 core 并读 backtrace

离线分析 core 的基本形式是 gdb 可执行文件 core文件。如果使用了容器，最好在同一镜像或同版本 rootfs 中打开，否则共享库路径和符号可能对不上。

# 使用原始可执行文件打开 core
EXE=$(cat /var/tmp/core.infer.12345.exe.path)
gdb -q "$EXE" /var/tmp/core.infer.12345

# gdb 中常用命令
(gdb) set pagination off
(gdb) info threads
(gdb) thread apply all bt
(gdb) thread 17
(gdb) bt
(gdb) frame 3
(gdb) info sharedlibrary
(gdb) quit

backtrace 怎么读

栈帧特征可能含义下一步
pthread_cond_wait、futex线程在等条件变量或锁看其他线程是否持锁、是否有死锁或线程池耗尽。
cudaDeviceSynchronize、cuStreamSynchronizeCPU 线程等待 GPU 工作完成结合 GPU 错误、kernel 超时、CUDA stream、NCCL 状态。
malloc、free、jemalloc内存分配器路径排查内存碎片、OOM、分配器锁竞争。
PyEval_EvalFrame、pybind11Python 与 native 扩展混合调用安装 Python gdb helpers 或看扩展符号。
?? 或裸地址缺符号或栈损坏补 debuginfo，确认二进制和 core 是否匹配。
先看所有线程： 只看当前线程容易误判。卡住问题通常要在所有线程中找“持锁者”“等待者”“唯一忙线程”或“全部卡在同一系统调用”。

图解：线程栈如何指向卡点

读栈时不要只找报错线程，要在所有线程之间建立资源等待关系。

8. 线程分析：all bt、锁、死锁与线程池

AI 服务常见线程模型包括主线程、RPC/HTTP worker、Python data loader、OpenMP/MKL 线程池、CUDA runtime helper、NCCL 通信线程和后台缓存刷新线程。卡住时要识别哪些线程正常睡眠，哪些线程异常等待，哪些线程在持有关键资源。

# 在 gdb 中快速聚合线程现场
(gdb) set pagination off
(gdb) info threads
(gdb) thread apply all bt 8

# 如果输出太长，可以限制栈深度
sudo gdb -q -p 12345 \
  -ex 'set pagination off' \
  -ex 'thread apply all bt 12' \
  -ex 'detach' -ex 'quit' \
  > /var/tmp/bt-depth12.txt 2>&1
线程栈模式可能解释AI Infra 排查方向
大量线程在 pthread_cond_wait线程池空闲或等待任务看是否入口线程被卡住，队列是否不再投递。
大量线程在 futex/pthread_mutex_lock锁竞争或死锁找持锁线程，结合业务锁、allocator 锁、Python GIL。
线程在 epoll_wait/poll事件循环等待 IO可能正常；看连接数、上游下游、网络状态。
线程在 CUDA/NCCL 同步等待 GPU 或通信完成查 GPU Xid、NCCL 日志、rank 一致性、网络/RDMA。
线程在 dlopen/ld.so动态加载库或符号解析排查 lazy import、自定义 op 加载、NFS/镜像层 IO。
死锁判断要谨慎： backtrace 只能显示等待位置，不一定显示“谁持锁”。需要结合代码、日志、锁实现、bt full 局部变量或额外 instrumentation。

9. Python、C++ 与 CUDA 扩展混合栈

AI Infra 的崩溃栈经常跨越 Python 解释器、pybind11、自研 C++ op、CUDA runtime、cuDNN/NCCL 和驱动库。只看 Python traceback 会漏掉 native 层；只看 gdb backtrace 又可能看不到 Python 帧，需要两边对齐。

Python 进程 native 栈

# 先采 native 栈
sudo gdb -q -p 12345 \
  -ex 'set pagination off' \
  -ex 'thread apply all bt' \
  -ex 'detach' -ex 'quit' \
  > /var/tmp/python-native-bt.txt 2>&1

# 如果发行版提供 Python gdb helpers，可在 gdb 中尝试
(gdb) py-bt
(gdb) py-list
(gdb) py-locals

C++/CUDA extension 栈的常见样子

# 示例：缺符号时只能看到 .so 和地址
#0  0x00007f... in cudaStreamSynchronize () from /usr/local/cuda/lib64/libcudart.so
#1  0x00007f... in my_ops::attention_forward(...) from /opt/app/my_ops_cuda.so
#2  0x00007f... in pybind11::cpp_function::dispatcher(...) from /opt/app/my_ops_cuda.so
#3  0x00007f... in cfunction_call () from /usr/lib/libpython3.10.so

# 查看扩展库是否加载
(gdb) info sharedlibrary my_ops
(gdb) info files
(gdb) maintenance info sections
PyTorch/TensorFlow 扩展
重点看自研 .so、ATen/TensorFlow runtime、allocator、CUDA stream 同步、kernel launch 前后的 C++ 栈。
NCCL/分布式训练
单个 rank 的栈不够，通常要对多个 rank 同时采样，比较是否都卡在同一 collective 或某个 rank 先异常。
实用判断： 如果所有 Python worker 都在等待 native op 返回，而某个 native 线程卡在 CUDA/NCCL/allocator，根因通常不在 Python 业务循环本身。

10. symbols、debuginfo 与 stripped 二进制

gdb 能否把地址显示成函数名、文件名和行号，取决于符号信息。生产二进制常被 strip，容器镜像也常只带运行时库，这会让 backtrace 充满 ??。解决办法不是盲猜，而是补齐完全匹配的 debuginfo。

现象原因处理
??、只有地址无符号或栈损坏安装 debuginfo，确认 build-id 与二进制匹配。
函数名有，行号无只有动态符号，无 DWARF debug info使用未 strip 文件或 .debug 符号文件。
显示错误源码路径构建路径和分析环境不同用 set substitute-path 映射源码路径。
共享库找不到容器/rootfs 不一致在同镜像分析，或设置 set solib-search-path。
# 查看二进制是否 stripped
file /proc/12345/exe
readelf -n /proc/12345/exe | grep -A3 'Build ID'

# gdb 中查看符号加载情况
(gdb) info sharedlibrary
(gdb) info sources
(gdb) set debug-file-directory /usr/lib/debug:/opt/debug
(gdb) set solib-search-path /opt/app/lib:/usr/local/cuda/lib64
(gdb) set substitute-path /build/workspace /src
工程化建议： CI 构建 C++/CUDA extension 时，把 runtime wheel/so 与 debug symbols 同时归档，并记录 build-id、git commit、编译参数、CUDA/cuDNN/NCCL 版本。

11. core pattern、ulimit 与 systemd-coredump

自动 crash core 由内核 core dump 设置控制；gcore 是主动生成 core。两者经常混淆。想让崩溃自动落盘，需要设置 core size、kernel.core_pattern、systemd 或容器运行时策略。

# 当前 shell 是否允许 crash core
ulimit -c
ulimit -c unlimited

# 查看系统 core pattern
cat /proc/sys/kernel/core_pattern

# systemd-coredump 环境中查看 core
coredumpctl list
coredumpctl info PID
coredumpctl gdb PID

# 临时设置 core pattern 示例：谨慎，只在测试环境
sudo sysctl -w kernel.core_pattern='/var/tmp/core.%e.%p.%t'
机制触发方式适用场景注意
gcore人为对活进程采样卡住、慢、现场稀缺会暂停进程并读取内存。
内核 crash core进程异常退出segfault、abort、非法指令受 ulimit、core pattern、权限影响。
systemd-coredumpsystemd 管理 core发行版默认集成core 可能在 journal 或专用目录中。
容器 runtime继承宿主策略Kubernetes crash 诊断路径、权限、PID namespace 可能让定位变复杂。
不要在生产随意改全局 core_pattern： 它影响整台机器所有进程。需要变更时应走节点级配置和回滚流程。

12. 容器、Kubernetes 与权限边界

容器里 attach 进程时，常见障碍不是 gdb 命令本身，而是 PID namespace、ptrace 权限、seccomp、只读文件系统、缺少 gdb 包和宿主 core pattern。生产集群还要考虑多租户隔离和敏感数据边界。

# 容器内看 PID namespace 中的进程
ps -ef
cat /proc/sys/kernel/yama/ptrace_scope 2>/dev/null || true

# Kubernetes：进入目标容器
kubectl exec -it POD -c CONTAINER -- sh

# 如果镜像没有 gdb，优先用临时 debug 容器或同镜像复现
kubectl debug -it POD --image=debug-tools:latest --target=CONTAINER

# 宿主机按 namespace 进入，需平台授权
sudo nsenter -t HOST_PID -p -m -u -i -n -- gdb -q -p CONTAINER_PID
问题症状处理方向
ptrace 被限制Operation not permitted检查用户、capability、Yama、seccomp、容器安全策略。
PID 不一致宿主看到的 PID 和容器内不同明确使用哪个 namespace，记录宿主 PID 与容器 PID。
缺少工具容器内无 gdb/gcore用 debug image、ephemeral container 或在同镜像离线分析。
core 无处落盘目录只读或空间不足使用专用 emptyDir/hostPath，确认配额和加密策略。
权限边界： 不要为了调试永久给业务容器加 SYS_PTRACE 或特权模式。更好的做法是按需启用 debug 容器、节点隔离和审计。

用例图：gdb/gcore、py-spy、perf、strace 怎么选

调试目标是用最小代价获得足够证据，而不是固定使用某一个工具。

13. gdb/gcore vs py-spy/perf/strace

工具优势局限AI Infra 典型用法
gdb精确 native 栈、线程、core、变量、共享库attach 会暂停；使用不当影响生产查 C++/CUDA extension、锁等待、崩溃栈。
gcore保存完整离线现场文件大、敏感、生成慢稀缺现场归档，跨团队交接。
py-spyPython 采样低侵入，不需改代码native 细节有限找 Python 层热点、GIL 等待、调用路径。
perfCPU 采样强，可火焰图符号和权限要求高，不适合所有容器查 busy loop、kernel/user CPU 热点。
strace系统调用可见，定位 IO/网络/futex高频 syscall 可能开销大，只看到 syscall 边界查卡在读写、connect、futex、文件系统。
# 低侵入 Python 采样
py-spy top --pid 12345
py-spy dump --pid 12345

# CPU 热点采样
sudo perf top -p 12345
sudo perf record -g -p 12345 -- sleep 30

# 系统调用观察：先短时间、小范围
sudo strace -tt -T -p 12345 -o /var/tmp/strace.12345.txt
组合策略： 先用 py-spy/perf/strace 缩小方向，再用 gdb 或 gcore 获取最终 native 证据，通常比直接 core dump 更安全。

15. 自动化采集脚本模板

生产采集应尽量标准化：记录元信息、限制输出、明确 detach、文件命名带时间和 PID。下面模板只采 backtrace，不生成 core，适合作为低风险第一步。

#!/usr/bin/env bash
set -euo pipefail

PID="${1:?usage: $0 PID}"
OUT_DIR="${2:-/var/tmp/gdb-snapshot-$PID-$(date +%Y%m%d-%H%M%S)}"
mkdir -p "$OUT_DIR"

ps -p "$PID" -o pid,ppid,user,stat,etime,rss,vsz,cmd > "$OUT_DIR/ps.txt"
ps -L -p "$PID" -o pid,tid,psr,stat,pcpu,wchan:32,comm > "$OUT_DIR/threads.txt"
cat "/proc/$PID/status" > "$OUT_DIR/status.txt"
cat "/proc/$PID/limits" > "$OUT_DIR/limits.txt"
cat "/proc/$PID/maps" > "$OUT_DIR/maps.txt"
readlink -f "/proc/$PID/exe" > "$OUT_DIR/exe.path"

sudo gdb -q -p "$PID" \
  -ex 'set pagination off' \
  -ex 'set print thread-events off' \
  -ex 'info threads' \
  -ex 'thread apply all bt 16' \
  -ex 'info sharedlibrary' \
  -ex 'detach' \
  -ex 'quit' \
  > "$OUT_DIR/gdb-bt.txt" 2>&1

tar -C "$(dirname "$OUT_DIR")" -czf "$OUT_DIR.tar.gz" "$(basename "$OUT_DIR")"
echo "$OUT_DIR.tar.gz"
生成 core 的自动化不要默认开启： 如果要脚本化 gcore，必须加磁盘空间检查、目标进程白名单、敏感数据标记、最大并发限制和审批/审计记录。

排障图：gdb/gcore 失败时怎么查

失败时优先区分权限、进程生命周期、磁盘空间和符号问题，避免在生产现场反复试错。

16. 常见故障与排障路径

问题 1：ptrace 权限不足
确认是否同用户、是否 root、/proc/sys/kernel/yama/ptrace_scope、容器 capability 和 seccomp 策略。
问题 2：attach 后服务抖动
说明停顿窗口不可忽略。下次先摘流量、缩短命令、限制 backtrace 深度或改用采样工具。
问题 3：gcore 文件过大
检查 RSS、映射、磁盘；必要时只采 backtrace，或调整 /proc/PID/coredump_filter 后再评估。
问题 4：core 打不开
确认架构、gdb 版本、core 是否完整、二进制是否匹配、是否在同容器/rootfs 分析。
问题 5：栈全是 ??
安装 debuginfo，加载未 strip 的 extension，设置 debug-file-directory 和 solib-search-path。
问题 6：看不到 Python 帧
安装匹配 Python 的 gdb helper，或结合 py-spy dump 与 native backtrace 对齐。
问题 7：NCCL 栈无法判断根因
同时采多个 rank，结合 NCCL 日志、网络/RDMA 指标、GPU Xid 和最早异常 rank。
问题 8：core 包含敏感数据
限制访问、加密传输、缩短留存，必要时在隔离环境脱敏或只分享 backtrace 摘要。

最小排障命令

# 权限与状态
PID=12345
id
ls -l /proc/$PID/exe
grep -E 'TracerPid|Uid|Gid|State|Threads|CoreDumping' /proc/$PID/status
cat /proc/sys/kernel/yama/ptrace_scope 2>/dev/null || true

# 符号与二进制匹配
file /proc/$PID/exe
readelf -n /proc/$PID/exe | grep -A3 'Build ID' || true

# 空间与大小
df -h /var/tmp
grep -E 'VmRSS|VmSize' /proc/$PID/status

17. 学习路线、练习与交接格式

第一阶段：会安全采集

  • 理解 attach 会暂停进程，core 可能很大且敏感。
  • 会用 gdb -p PID -ex 'thread apply all bt' 采集所有线程栈。
  • 会执行 detach，不会在生产进程中随意修改状态。

第二阶段：会离线分析

  • 掌握 gdb EXE core、info threads、bt、frame、info sharedlibrary。
  • 能识别 futex、pthread、CUDA/NCCL、Python/native extension 的典型栈。
  • 知道如何补齐 debuginfo、共享库搜索路径和源码路径映射。

第三阶段：工程化治理

  • 为 AI Infra 服务设计可审计的 debug 容器和采集脚本。
  • CI 归档 debug symbols、build-id、镜像 digest 和源码 commit。
  • 建立 core 文件敏感数据策略：访问控制、加密、留存、销毁。

交接格式

事件：infer-worker 卡住，P99 超时
时间：2026-04-25 14:32:10 +0800
节点/容器：node-a / pod-x / image sha256:...
PID：12345
采集动作：gdb thread apply all bt 16，未生成 core
影响控制：先摘除流量，采集耗时约 3 秒
关键发现：线程 27 卡在 cudaStreamSynchronize；线程 31 持有 ModelCache::reload 路径
附件：ps.txt、threads.txt、status.txt、maps.txt、gdb-bt.txt
风险：未采 bt full，缺少局部变量；my_ops_cuda.so 需要补 debuginfo
最终目标： 不是“跑过 gdb 命令”，而是形成可复盘证据：哪个进程、哪个线程、哪个栈帧、哪个库版本、什么业务上下文、采集有什么风险和缺口。
