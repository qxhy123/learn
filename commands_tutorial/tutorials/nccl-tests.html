nccl-tests 深度教程：AI Infra GPU 通信压测与拓扑排障

nccl-tests 是 AI 集群里验证 GPU 集合通信能力的基础工具。它不训练模型，也不代表完整业务吞吐，但能把 all_reduce、all_gather、reduce_scatter 等通信模式拆出来，帮助你判断单机 NVLink/PCIe、跨机 RDMA、NCCL 环境变量、MPI 启动方式和拓扑绑定是否正确。

AI InfraNCCLall_reduce_perfalgbw / busbwNVLinkRDMAMPItorchrun 对照拓扑排障生产安全
一句话理解： nccl-tests 用固定张量大小和固定 collective 算法负载，测出 GPU 之间“做一次通信操作”的耗时、算法带宽与总线带宽，是集群上线前验证 GPU 通信面的标尺。
实践原则： 先单机、再双机、再扩到目标规模；每次只改一个变量，例如网卡、NCCL 环境变量、进程布局或容器挂载。不要一上来跑全量节点，否则失败信号会被拓扑、调度和网络噪声淹没。

1. nccl-tests 是什么

nccl-tests 是 NVIDIA NCCL 的配套测试集，核心目标是测量多 GPU、多进程、多节点之间的 collective 通信性能与正确性。AI Infra 场景里，它常用于新机器验收、驱动/CUDA/NCCL 升级回归、网络变更验证、容器镜像验证，以及训练慢、挂起、跨节点不通时的最小复现。

它能回答
单机 8 卡通信是否走 NVLink？跨节点是否走 RDMA？NCCL 是否选对网卡？all_reduce 在大消息时是否达到预期带宽？
它不能回答
模型端到端吞吐、数据加载瓶颈、优化器开销、框架图编译、checkpoint I/O 或业务代码 bug。
它的位置
介于硬件裸测和训练框架之间：比 nvidia-smi 更接近训练通信，比完整训练更容易定位。
# 常见二进制名称
all_reduce_perf
all_gather_perf
reduce_scatter_perf
broadcast_perf
reduce_perf
sendrecv_perf
基准语义： nccl-tests 结果是通信微基准，不是训练性能承诺。它适合做“通信面是否健康”的证据，而不是单独作为模型吞吐 SLA。

信息图：nccl-tests 在 AI Infra 验证链路中的位置

nccl-tests 最适合作为“通信面健康”的证据：上游看硬件和网络，下游再看框架与业务。

2. 构建与二进制

构建时要让 CUDA、NCCL、MPI 与运行环境一致。单机不一定需要 MPI；多机测试通常需要 MPI 支持，或使用集群已有的 MPI launcher 启动多个进程。

# 获取源码后构建。实际 CUDA_HOME/NCCL_HOME 按环境调整。
git clone https://github.com/NVIDIA/nccl-tests.git
cd nccl-tests

# 单机构建：适合先验证同机多 GPU
make -j

# 多节点 MPI 构建：需要 MPI 编译器和运行时
make MPI=1 MPI_HOME=/usr/local/mpi -j

# 查看生成的测试程序
ls build/*_perf
构建项检查点常见问题
CUDAnvcc --version、驱动支持的 CUDA 版本容器 CUDA 与宿主驱动不兼容，运行时报库错误
NCCLlibnccl.so 路径、版本一致性编译链接一个版本，运行时加载另一个版本
MPImpirun --version、mpicc、SSH/PMIMPI 没把环境变量传到远端，或容器内外 MPI 不匹配
最小原则： 如果只是排查训练通信，优先使用和训练容器相同的 CUDA/NCCL/MPI 镜像构建并运行，避免“裸机能跑、容器不能跑”的双环境问题。

3. 单机 all_reduce_perf 快速开始

all_reduce_perf 是最常用的入口，因为数据并行训练里的梯度同步主要就是 all-reduce 语义。先用小规模命令确认能跑，再扩大消息大小与 GPU 数量。

# 1 张 GPU，功能冒烟
./build/all_reduce_perf -b 8 -e 128M -f 2 -g 1

# 单机 8 张 GPU，大消息通信性能
./build/all_reduce_perf -b 8 -e 8G -f 2 -g 8

# 增加迭代，降低短测抖动；-w 是 warmup，-n 是正式迭代次数
./build/all_reduce_perf -b 1M -e 8G -f 2 -g 8 -w 20 -n 100
参数含义AI Infra 使用建议
-b起始消息大小从 8B 或 1K 开始看小包延迟，从 1M 开始看稳定带宽
-e结束消息大小单机常到 1G 或 8G；大规模集群先别直接拉满显存
-f消息大小增长倍数2 最常用，便于画趋势
-g每个进程使用的 GPU 数单进程单机常用 -g 8；多进程模式需按 rank 布局设计
-w / -n预热/正式迭代次数做基准记录时增加迭代，排除首次初始化噪声
推荐路径： 先 -g 1 验证二进制，再 -g 2 验证点对点拓扑，再 -g 8 验证整机通信面。

4. 输出列：time、algbw、busbw、wrong

多数 *_perf 输出会按消息大小打印耗时和带宽。做排障时，不要只看最后一行；小消息、中等消息、大消息分别代表延迟、协议切换和链路吞吐。

# 输出示意，数值仅用于说明列含义
# size         count    type   redop   root   time(us)  algbw(GB/s)  busbw(GB/s)  #wrong
# 1048576      262144   float  sum     -1     83.20     12.60        22.05        0
# 8388608      2097152  float  sum     -1     225.30    37.24        65.17        0
# 67108864     16777216 float  sum     -1     980.40    68.45        119.78       0
列怎么看异常信号
time单次 collective 平均耗时，通常单位为微秒小消息耗时异常高，多为初始化、CPU 绑定、PCIe/NUMA 或网络握手问题
algbw按算法处理的数据量除以耗时得到的算法带宽大消息上不去，说明通信路径、协议或链路存在瓶颈
busbw按 collective 实际总线流量折算的链路压力指标和预期拓扑差距大，常见于没走 NVLink/RDMA 或 rank 布局错误
#wrong正确性检查错误数非 0 要先停下排查，不要继续解读性能数据
硬规则： #wrong 非 0 时，性能数值没有可信意义。先查驱动、NCCL/CUDA 版本、GPU ECC/Xid、超频/温度、电源和硬件稳定性。

对比图：三类常用 Collective 的数据流

选择哪个测试程序取决于你要模拟的训练通信：数据并行优先 all_reduce，分片策略还要看 all_gather 和 reduce_scatter。

5. all_reduce、all_gather、reduce_scatter 怎么选

不同训练并行策略对应的通信热点不同。只跑 all_reduce_perf 不足以覆盖所有 AI Infra 场景，尤其是 FSDP、ZeRO、张量并行和 MoE 场景。

测试程序最接近的训练通信重点观察
all_reduce_perf数据并行梯度同步、部分张量并行规约大消息带宽、跨节点扩展、#wrong
all_gather_perfFSDP 参数 gather、张量并行拼接跨节点全量聚合开销，是否受网卡选择影响
reduce_scatter_perfZeRO/FSDP 梯度分片、分布式优化器分片通信带宽和 rank 布局敏感度
sendrecv_perf流水并行、点对点通信、链路局部验证单链路延迟/带宽，定位坏链路很有用
# 同一环境下横向跑三类 collective，避免只看 all_reduce
for t in all_reduce_perf all_gather_perf reduce_scatter_perf; do
  ./build/$t -b 1M -e 4G -f 2 -g 8 -w 20 -n 100 | tee ${t}.single-node.log
done
对照思维： 如果训练使用 FSDP/ZeRO，只证明 all_reduce_perf 正常是不够的；还要验证 all_gather_perf 与 reduce_scatter_perf。

6. 单节点 GPU 拓扑验证

单机先确认 GPU 可见性、拓扑、NVLink 状态和 NUMA 关系。通信测试慢不一定是 NCCL bug，常见原因是 GPU 没走预期链路、进程 CPU 绑错 NUMA、容器没暴露 NVLink/NVML 信息，或机器处于降频/错误状态。

# 查看 GPU 与 CPU/网卡拓扑
nvidia-smi topo -m

# 查看 NVLink 链路状态和吞吐计数
nvidia-smi nvlink --status

# 单机分步测试：1 卡、2 卡、4 卡、8 卡
for g in 1 2 4 8; do
  ./build/all_reduce_perf -b 1M -e 8G -f 2 -g $g -w 20 -n 100 | tee ar_g${g}.log
done
现象可能原因下一步
2 卡就很慢GPU 间是 PCIe PHB/SYS，或 NVLink 链路不可用对照 nvidia-smi topo -m，换 GPU pair 测试
小包延迟高CPU 绑核/NUMA 不佳，进程被调度打断用 numactl 或调度器 CPU binding 固定
大包带宽低没走 NVLink、PCIe 降速、GPU 温度/功耗限制查 nvidia-smi -q、链路宽度、功耗和 Xid
单机基线： 单节点结果是多节点排障的地基。单机都不稳定时，不要继续调 RDMA 或 MPI。

7. 多节点 MPI 启动模式

多节点通常用 MPI 启动每台机器上的 rank。两种常见布局是“每节点 1 个 rank，rank 内用 -g 8 管理 8 卡”和“每 GPU 1 个 rank，-g 1”。前者简单，后者更贴近部分框架布局。排障时先选择一种并固定下来。

# hosts.txt 示例，每行一个节点，可带 slots
node-a slots=1
node-b slots=1

# 两节点，每节点一个进程，每进程 8 张 GPU
mpirun -np 2 --hostfile hosts.txt \
  -x NCCL_DEBUG=INFO \
  -x NCCL_SOCKET_IFNAME=eth0 \
  -x NCCL_IB_HCA=mlx5_0,mlx5_1 \
  ./build/all_reduce_perf -b 1M -e 8G -f 2 -g 8 -w 20 -n 100

# 两节点，每 GPU 一个进程。此时 hostfile slots 通常应等于每节点 GPU 数。
mpirun -np 16 --host node-a:8,node-b:8 \
  -x NCCL_DEBUG=INFO \
  -x NCCL_SOCKET_IFNAME=eth0 \
  ./build/all_reduce_perf -b 1M -e 2G -f 2 -g 1 -w 20 -n 100
MPI 环境变量： 不同 MPI 实现传参方式不同。Open MPI 常用 -x VAR=value，MPICH/Intel MPI 可能使用不同语法。确认远端 rank 真的拿到了 NCCL 环境变量。
布局优点风险
每节点 1 rank，-g 8命令短，适合节点级验收不完全等同每 GPU 一个训练进程
每 GPU 1 rank，-g 1更接近 PyTorch DDP/FSDP 常见进程布局MPI、CPU binding、rank-GPU 映射更容易错

8. torchrun 与训练链路对照

nccl-tests 本身不由 torchrun 启动，但 AI Infra 排障经常需要把它和 PyTorch 分布式最小脚本对照：如果 nccl-tests 正常而 torchrun 失败，问题更可能在框架、容器环境、 rendezvous、rank 映射或训练代码；如果二者都失败，先查 NCCL/网络/权限。

# torchrun 对照脚本：只做一次 all_reduce，验证框架链路
cat > torch_nccl_smoke.py <<'PY'
import os
import torch
import torch.distributed as dist

dist.init_process_group("nccl")
rank = dist.get_rank()
local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)
x = torch.ones(1024 * 1024, device="cuda") * (rank + 1)
dist.all_reduce(x)
if rank == 0:
    print("ok", x[0].item(), "world", dist.get_world_size())
dist.destroy_process_group()
PY

# 单机 8 进程
NCCL_DEBUG=INFO torchrun --standalone --nproc_per_node=8 torch_nccl_smoke.py

# 多机示意：两台都执行，node_rank 分别为 0 和 1
NCCL_DEBUG=INFO torchrun \
  --nnodes=2 --nproc_per_node=8 \
  --node_rank=0 --master_addr=node-a --master_port=29500 \
  torch_nccl_smoke.py
对照技巧： 让 torchrun 使用和 mpirun nccl-tests 相同的 NCCL_SOCKET_IFNAME、NCCL_IB_HCA、NCCL_DEBUG，否则对比没有意义。

9. NCCL 环境变量速查

NCCL 环境变量是定位通信路径的核心工具。排障时应显式记录变量，而不是依赖默认选择。默认选择可能随 NCCL 版本、网卡命名、容器网络和 PCIe 拓扑变化。

变量用途示例
NCCL_DEBUG输出 NCCL 日志级别NCCL_DEBUG=INFO
NCCL_DEBUG_SUBSYS限制日志子系统，便于看网络/拓扑NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH
NCCL_SOCKET_IFNAME选择 TCP bootstrap 或 socket 网络接口NCCL_SOCKET_IFNAME=eth0
NCCL_IB_HCA选择 RDMA HCANCCL_IB_HCA=mlx5_0,mlx5_1
NCCL_IB_DISABLE禁用 InfiniBand/RDMA 路径做 A/B 对照NCCL_IB_DISABLE=1
NCCL_P2P_DISABLE禁用 GPU P2P 做对照NCCL_P2P_DISABLE=1
NCCL_TOPO_FILE指定拓扑文件，复现实验路径NCCL_TOPO_FILE=/tmp/topo.xml
NCCL_ALGO / NCCL_PROTO限制算法/协议做定位NCCL_ALGO=Ring NCCL_PROTO=Simple
# 推荐的排障日志组合
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,NET,GRAPH
export NCCL_SOCKET_IFNAME=eth0
export NCCL_IB_HCA=mlx5_0,mlx5_1

mpirun -np 2 --host node-a,node-b \
  -x NCCL_DEBUG -x NCCL_DEBUG_SUBSYS -x NCCL_SOCKET_IFNAME -x NCCL_IB_HCA \
  ./build/all_reduce_perf -b 1M -e 4G -f 2 -g 8
不要永久化排障变量： NCCL_IB_DISABLE=1、NCCL_P2P_DISABLE=1、强制 NCCL_ALGO 适合 A/B 定位，不应不经验证写进生产训练环境。

10. algbw 与 busbw 的解释

algbw 是算法视角的有效带宽，busbw 是按 collective 在链路上产生的数据流量折算后的总线带宽。不同 collective 的 busbw 公式不同，所以跨程序比较时要谨慎。

什么时候看 algbw
评估某个 collective 对训练步骤的有效吞吐，例如大梯度 all-reduce 的整体完成速度。
什么时候看 busbw
判断底层链路是否接近预期，例如 NVLink、PCIe、IB/RoCE 的可用带宽是否被打满。
判断解释行动
algbw 和 busbw 都低链路或进程布局可能有明显瓶颈从拓扑、网卡选择、CPU binding 开始
小消息低，大消息正常延迟敏感，可能是启动、协议、CPU 调度影响增加迭代，固定 CPU，观察 p50/p99 外的整体趋势
单机正常，多机低跨节点网络、RDMA、路由或交换机侧问题对照 ib_write_bw、iperf3、NCCL NET 日志
多次结果抖动大共享集群干扰、温度/功耗、后台任务或拥塞隔离节点，记录时间段，查交换机/作业负载
不要机械套公式： busbw 是 nccl-tests 为不同 collective 做的折算指标，适合同类同规模对比；跨版本、跨拓扑、跨 collective 时，应结合 NCCL 日志和硬件理论值解释。

拓扑图：从 GPU 到跨节点网络的三段链路

定位不要直接跳到“网络慢”：先拆成同机 GPU 链路、跨节点网络链路、NCCL 实际选择路径三层。

11. 拓扑、NVLink、PCIe 与 RDMA 三角定位

通信慢通常不是单点问题，而是拓扑、网络和 NCCL 选择共同作用。最有效的方法是 A/B：禁用某条路径或固定某张网卡，观察结果是否按预期变化。

# A/B 1：禁用 RDMA，强制走 TCP，验证 RDMA 是否真的带来提升
NCCL_IB_DISABLE=1 \
mpirun -np 2 --host node-a,node-b \
  ./build/all_reduce_perf -b 1M -e 4G -f 2 -g 8

# A/B 2：禁用 GPU P2P，观察单机是否明显下降
NCCL_P2P_DISABLE=1 ./build/all_reduce_perf -b 1M -e 4G -f 2 -g 8

# A/B 3：固定 HCA，逐个测试网卡
for hca in mlx5_0 mlx5_1 mlx5_2 mlx5_3; do
  NCCL_IB_HCA=$hca mpirun -np 2 --host node-a,node-b \
    ./build/all_reduce_perf -b 1M -e 2G -f 2 -g 8 | tee ar_${hca}.log
done
对照结果含义后续
禁用 RDMA 后几乎不变原本可能就没走 RDMA，或 RDMA 路径异常查 NCCL NET 日志、HCA、GID、RoCE PFC/ECN、IB link
禁用 P2P 后单机大幅下降NVLink/P2P 路径有效单机拓扑基本健康，再看跨机
某个 HCA 明显慢网卡、线缆、交换机端口或 NUMA 关系可能异常用 ib_write_bw 点测，再查交换机计数

12. nccl-tests vs nvidia-smi / iperf3 / ib_write_bw

这几个工具不是互相替代，而是从不同层面观察同一个系统。排障时先用低层工具确认硬件和网络，再用 nccl-tests 验证 NCCL collective。

工具测什么不能说明什么和 nccl-tests 的关系
nvidia-smiGPU 可见性、温度、功耗、进程、拓扑、NVLink 状态不能证明 NCCL collective 带宽正常先验健康检查
iperf3TCP/IP 网络吞吐不能证明 RDMA 或 GPU Direct RDMA 正常排除基础 IP 网络问题
ib_write_bwRDMA verbs 层点对点带宽/延迟不能证明 NCCL rank 拓扑和算法选择正确验证 HCA/链路/交换机
nccl-testsGPU collective 的端到端通信表现不能单独解释底层哪一段坏AI 训练通信面的主基准
# 一个合理的跨节点排障顺序
nvidia-smi topo -m
ibstat
ib_write_bw node-b
iperf3 -c node-b -P 8
mpirun -np 2 --host node-a,node-b ./build/all_reduce_perf -b 1M -e 4G -f 2 -g 8
判断边界： ib_write_bw 好而 nccl-tests 差，重点查 NCCL 环境、GPU-HCA 亲和性和 GDR；nccl-tests 好而训练差，重点转向框架和模型。

13. 容器、调度器与权限注意事项

AI 集群通常在容器和调度器中运行，很多问题来自“容器里看见的世界”和宿主机不一致。做验收时应记录镜像、驱动、NCCL 版本、挂载设备、网络模式和调度器资源绑定。

# Docker 示例：需要按集群安全策略调整，不要照搬到生产共享节点
docker run --rm --gpus all --ipc=host --network=host \
  --ulimit memlock=-1 --cap-add IPC_LOCK \
  -v /dev/infiniband:/dev/infiniband \
  nccl-test-image:cuda12 \
  ./build/all_reduce_perf -b 1M -e 4G -f 2 -g 8

# Slurm 示例：每节点 8 GPU，两节点运行
srun -N 2 --ntasks-per-node=1 --gres=gpu:8 \
  --mpi=pmix \
  bash -lc 'NCCL_DEBUG=INFO ./build/all_reduce_perf -b 1M -e 4G -f 2 -g 8'
检查项为什么重要
/dev/infiniband容器内缺失时通常无法使用 RDMA verbs
--network=host 或 CNI 配置NCCL bootstrap 需要可达的节点间地址
memlock / IPC lockRDMA 注册内存可能受限制
GPU 与 CPU 绑定NUMA 不匹配会造成小包延迟和 host staging 开销
镜像内 NCCL 版本不同版本可能选择不同算法/协议，日志和性能都变
生产注意： 提权参数、host network 和设备挂载要符合平台策略。教程中的容器命令是诊断模板，不是默认生产安全基线。

14. 安全压测与生产影响控制

nccl-tests 会占用 GPU、显存、PCIe/NVLink、RDMA 网络和交换机缓冲。共享训练集群里，盲目跑大规模测试可能影响其他作业。

隔离节点
优先在维护窗口或独占节点运行。
逐步放大
1 节点 → 2 节点 → 1 个机架 → 目标规模。
限制消息
先用 -e 1G，确认稳定后再扩大。
记录环境
保存命令、变量、NCCL 日志和节点列表。
# 安全 dry-run 思路：先确认节点、GPU、命令，不直接跑大规模

nvidia-smi --query-gpu=index,name,uuid,pci.bus_id --format=csv
env | grep -E '^(NCCL|CUDA|UCX|OMPI|PMI)_' | sort

# 小流量冒烟
./build/all_reduce_perf -b 8 -e 16M -f 2 -g 8 -w 5 -n 20

# 通过后再跑正式基准
./build/all_reduce_perf -b 1M -e 8G -f 2 -g 8 -w 20 -n 100
避免事故： 不要在业务高峰对整集群运行全量 all_reduce；不要在未知 RoCE 配置上直接打满网络；不要把排障变量写入全局 profile 影响其他训练作业。

排障要先收敛层次：本机不正常先别看网络，基础网络不正常先别调 NCCL 算法。
