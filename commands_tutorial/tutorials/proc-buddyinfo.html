/proc/buddyinfo 深度教程：AI Infra 中的 Buddy Allocator、内存碎片与大页排障

这份教程围绕 Linux 伪文件 /proc/buddyinfo 展开。它不是普通“剩余内存”表，而是 buddy allocator 按 NUMA node、zone 和 order 暴露的空闲物理页块分布。通过它可以判断：系统是否还有连续物理内存、2MiB huge page 为什么分配失败、内存碎片是否正在恶化、GPU pinned memory 是否让 compaction 失效，以及应该如何把它和 /proc/meminfo、/proc/vmstat、NUMA 拓扑、THP/hugetlb 指标一起读。

一句话理解： /proc/buddyinfo 告诉你“每个 NUMA zone 里还有多少个 2order 连续页块”；高 order 空了，就算总内存还很多，也可能分不出大页、DMA 连续块或需要高阶页的内核对象。
实践原则： 读取 /proc/buddyinfo 是安全的；但主动 compact、调整 huge page、清 page cache 或重启 GPU/训练任务都可能影响业务。先采样、对齐故障时间线，再做低风险缓解。

1. /proc/buddyinfo 是什么

/proc/buddyinfo 是 Linux 内核通过 procfs 暴露的只读伪文件，用来展示 buddy allocator 当前的空闲块数量。buddy allocator 管理物理页框，它把连续页按 2 的幂次组织成不同 order：order 0 是 1 个页，order 1 是 2 个连续页，order 9 在 4KiB 页系统上就是 512 个连续页，也就是 2MiB。

它能回答
每个 NUMA node / zone 还有多少连续物理页块，尤其是高 order 是否枯竭。
它不能回答
哪个进程直接导致碎片、每页属于谁、未来 compaction 一定能否成功。
它的定位
不是容量指标，而是连续性指标；它解释“为什么还有空闲内存却分配不到大块”。
# 只读查看，安全
cat /proc/buddyinfo

# 每秒观察高阶块是否下降
watch -n 1 'cat /proc/buddyinfo'

# 保存排障现场
ts=$(date +%Y%m%d-%H%M%S)
cat /proc/buddyinfo > buddyinfo.$ts.txt
cat /proc/meminfo > meminfo.$ts.txt
cat /proc/vmstat > vmstat.$ts.txt
关键区别： free -h 或 MemAvailable 说明“容量还够不够”；/proc/buddyinfo 说明“够不够连续”。AI 节点上这两个问题经常不是同一个答案。

2. AI Infra 为什么要看它

训练和推理节点通常同时承载大模型权重加载、page cache、dataloader worker、checkpoint、GPU host pinned buffer、RDMA、NCCL、IPC shared memory 和容器调度。总内存看起来还够时，连续物理内存可能已经被长期运行的混合负载切碎，导致 THP 回退、hugetlb 分配失败、DMA 映射压力变大或 compaction 把 CPU 打满。

AI Infra 现象buddyinfo 关注点常见解释
2MiB huge page 分配失败目标 node/zone 的 order 9 是否接近 0高阶连续块不足，或 compaction 无法迁移被 pin / unmovable 页。
训练跑久后吞吐下降高 order 持续下降，compaction 计数上升长生命周期对象、pinned memory、page cache 与匿名页混合造成碎片。
GPU H2D copy 抖动Normal zone 高阶块、NUMA 本地 zone 分布host buffer 分配跨 NUMA 或触发 direct compaction。
推理服务 p99 尾延迟尖刺分配失败、compact stall 与高阶块恢复情况请求路径或后台线程触发内核回收/压缩。
节点空闲内存多但重启 job 才恢复高阶块长期枯竭碎片来自不可迁移页，单纯释放 page cache 不一定有效。
AI Infra 心法： 当 GPU 利用率低但 CPU、IO、网络都解释不清时，检查内存连续性和 compaction 事件，能发现一类“容量足够但形状不对”的问题。

3. 整体心智模型

信息图：从物理页到 /proc/buddyinfo

每一行代表一个 NUMA node 的一个 zone；行尾数字从 order 0 开始，越往右代表越大的连续物理页块。

4. 读取方式与输出样例

/proc/buddyinfo 是伪文件，内容由内核实时生成。读取不需要 root，不会修改系统状态。不同机器的 zone 名称和 order 列数可能不同，常见输出如下：

$ cat /proc/buddyinfo
Node 0, zone      DMA      1      1      1      0      2      1      1      0      1      1      3
Node 0, zone    DMA32    870    401    198     78     34     15      7      3      1      0      0
Node 0, zone   Normal  12543   6420   2201    913    245     71     19      4      1      0      0
Node 1, zone   Normal   9401   3880   1900    702    180     50     12      3      0      0      0
片段含义
Node 0NUMA 节点编号。多路服务器或多 NUMA 域机器会有多个 Node。
zone Normal内存 zone。常见有 DMA、DMA32、Normal、Movable，具体取决于架构和内核配置。
后续数字按 order 从 0 到最大 order 排列的空闲块数量。
# 给每一列标注 order，便于读样例
awk '
/Node/ {
  printf "%s %s %s ", $1, $2, $3
  for (i=5; i<=NF; i++) printf "order%-2d=%s ", i-5, $i
  print ""
}' /proc/buddyinfo
解析提醒： 不要假设永远有 11 个 order，也不要假设 zone 名称固定。脚本应从行结构动态解析数字列。

5. 列解释：Node、zone、order

读 /proc/buddyinfo 时要同时看三个维度：NUMA node 决定本地性，zone 决定分配约束，order 决定连续块大小。只看全机总和会掩盖“目标 GPU 所在 node 已碎片化”的问题。

维度为什么重要AI Infra 示例
Node内存分配通常优先本地 node；跨 node 访问可能更慢。GPU0 靠近 Node 0，但 Node 0 order 9 为空，H2D host buffer 或 THP 行为可能不同于 GPU1。
Zone不同 zone 服务不同分配约束；很多普通内核/用户页来自 Normal。Normal 高阶块枯竭，比 DMA zone 中还有高阶块更值得关注。
Orderorder 越高，需要越大的连续物理内存，越容易被碎片影响。4KiB 页系统上 order 9 对应 2MiB，是 THP 和 2MiB hugetlb 的关键。
order 0
单页分配。数量大说明小块还多，但不代表能分大页。
order 1-4
小到中等连续块。内核对象、网络和文件系统路径可能使用。
order 5-8
碎片趋势观察区。持续归零通常说明合并能力下降。
order 9+
大页与高阶分配关键区。AI 节点上尤其值得采样。
# 按 node/zone 汇总 order 9 及以上块数
awk '
/Node/ {
  high=0
  for (i=14; i<=NF; i++) high += $i
  printf "%s %s %-8s high_order_blocks=%d\n", $1, $2, $4, high
}' /proc/buddyinfo
定位原则： 对 GPU 相关问题，先用 nvidia-smi topo -m、lscpu -e 或 numactl --hardware 建立 GPU 到 NUMA node 的映射，再看对应 node 的高阶块。

6. Buddy allocator 工作流

流程图：分裂、分配、释放与合并

高阶块可以通过释放后合并恢复，也可以通过 compaction 迁移可移动页后创造；被长期 pin 或不可迁移的页会阻断合并。

7. order 与页块大小换算

buddy allocator 的 order 使用公式：block_size = PAGE_SIZE * 2^order。大多数 x86_64 Linux 使用 4KiB 基础页，因此 order 9 是 2MiB，order 10 是 4MiB。ARM 或特殊内核可能使用 16KiB/64KiB 页，换算必须以实际 getconf PAGE_SIZE 为准。

order4KiB 页系统块大小典型意义
04KiB普通单页分配。
18KiB两个连续页。
464KiB中等连续块，常用于内核路径。
81MiB接近大页规模，碎片敏感。
92MiBx86_64 THP/2MiB hugetlb 关键 order。
104MiB默认 MAX_ORDER=11 时常见最大 buddy 块。
# 查看基础页大小
getconf PAGE_SIZE

# 打印当前系统每个 order 对应大小
pagesize=$(getconf PAGE_SIZE)
awk -v ps="$pagesize" 'BEGIN {
  for (o=0; o<=10; o++) {
    bytes = ps * (2 ^ o)
    if (bytes >= 1048576) printf "order %-2d = %.0f MiB\n", o, bytes/1048576
    else printf "order %-2d = %.0f KiB\n", o, bytes/1024
  }
}'
大页提醒： 1GiB huge page 通常属于 gigantic page 路径，不是简单看默认 buddyinfo 最右列就能判断。2MiB huge page 才通常对应 4KiB 页系统上的 order 9。

8. 如何判断内存碎片

碎片判断不是看低阶块数量，而是看高阶块是否长期缺失、是否集中在非目标 node/zone、是否伴随 compaction stall 或 THP fallback。一个典型碎片化状态是：order 0 到 order 3 很多，order 8 到 order 10 接近 0，系统还有不少 MemAvailable，但大页分配失败。

健康倾向
各 node 的 Normal zone 中高阶块仍有余量，短期分配后能通过释放/compaction 恢复。
碎片倾向
低阶块很多，高阶块长期为 0；compaction 扫描多但成功少；THP fault fallback 增长。
局部碎片
全机看起来还行，但靠近目标 GPU 的 node 高阶块枯竭。
不可迁移碎片
pinned pages、内核不可迁移页、长期 mlock、RDMA 注册内存让 compaction 难以合并。
# 快速看每行低阶和高阶块分布
awk '
/Node/ {
  low=0; high=0
  for (i=5; i<=8 && i<=NF; i++) low += $i
  for (i=13; i<=NF; i++) high += $i
  printf "%s %s %-8s low_order=%8d high_order=%6d\n", $1, $2, $4, low, high
}' /proc/buddyinfo

# 看 compaction 和 THP 相关 vmstat 计数
grep -E 'compact|thp|allocstall|pgscan|pgsteal' /proc/vmstat
趋势比快照重要： 单次 buddyinfo 只能说明当前状态。排障要采样故障前后，看高阶块是否在某个训练阶段、模型加载、checkpoint 或 GPU buffer 注册后明显下降。

对比图：容量足够但 2MiB 连续块不足

buddyinfo 适合解释“为什么还有内存但没有合适形状的内存”。对 4KiB 页系统，2MiB huge page 通常要关注 order 9。

9. Huge page 分配失败

AI 运行时可能使用 Transparent Huge Pages、显式 hugetlbfs、JVM/数据库式大页、共享内存或某些 DMA/驱动路径。2MiB huge page 分配失败时，常见表现是性能下降、fallback 计数增加，或者预留 hugetlb 页面时失败。

机制关注指标说明
Transparent Huge Pages/sys/kernel/mm/transparent_hugepage/enabled、/proc/vmstat 中 thp_fault_fallbackTHP 失败通常回退到 4KiB 页，应用不一定报错，但 TLB miss 和 CPU 开销可能上升。
2MiB hugetlb/proc/meminfo 中 HugePages_*、order 9 块运行时动态增加 hugepages 需要连续内存，碎片化后更容易失败。
1GiB huge page启动参数、专用 hugepage 配置常需要更早预留，不能只靠 buddyinfo 末列判断。
# 查看 THP 配置与统计
cat /sys/kernel/mm/transparent_hugepage/enabled
grep -E 'thp_fault_alloc|thp_fault_fallback|thp_collapse_alloc|thp_collapse_alloc_failed' /proc/vmstat

# 查看 hugetlb 状态
grep -E 'Huge|AnonHugePages|ShmemHugePages' /proc/meminfo

# 动态申请 hugepages 前先 dry-run 采样，不要直接改生产节点
cat /proc/buddyinfo
grep -E 'HugePages_Total|HugePages_Free|HugePages_Rsvd|Hugepagesize' /proc/meminfo
安全警告： 不要在繁忙生产节点上直接大幅增加 vm.nr_hugepages。这可能触发 compaction、回收和延迟尖刺，也可能失败。先在维护窗口或隔离节点验证。

10. NUMA zones 与本地性

多 NUMA 节点服务器上，buddyinfo 的每个 node 都要单独读。全机高阶块足够，不代表目标 GPU 附近的 node 足够。训练进程若绑定在 Node 0 CPU 且 GPU 也靠近 Node 0，但内存策略把大量页分配到 Node 1，可能引入远端内存访问和 PCIe copy 抖动。

# 查看 NUMA 拓扑
numactl --hardware
lscpu -e=CPU,CORE,SOCKET,NODE,ONLINE

# 查看 GPU 与 CPU/NUMA 的拓扑关系
nvidia-smi topo -m 2>/dev/null || true
rocm-smi --showtoponuma 2>/dev/null || true

# 观察每个 node 的 buddyinfo
cat /proc/buddyinfo
zone典型含义排障侧重点
DMA传统低地址 DMA 区，现代大内存服务器通常很小。除非驱动或老设备路径需要，一般不是 AI 应用主关注区。
DMA3232 位 DMA 可访问区域，x86_64 上常见。某些设备约束可能相关，但容量有限。
Normal常规内核和用户页主要来源。AI 节点碎片、大页、pinned memory 的核心观察区。
Movable主要放可迁移页，便于内存热插拔或隔离。有助于 compaction，但并非所有机器都有。
NUMA 原则： 排查 GPU0 的 host memory 问题时，优先看 GPU0 本地 node 的 Normal zone 高阶块，而不是所有 node 加总。

11. compaction 与迁移限制

内存 compaction 会把可移动页迁走，试图把零散空闲页合并成高阶连续块。它能缓解碎片，但不是魔法：被 mlock、GUP pin、RDMA 注册、GPU pinned、内核不可迁移对象占用的页，可能无法移动。此时 compaction 扫描很多页但成功率低，高阶块仍恢复不了。

指标来源如何读
compact_stall/proc/vmstat分配路径因 compaction 阻塞的次数，增长可能对应延迟尖刺。
compact_success/compact_fail/proc/vmstat成功/失败趋势。失败持续增长说明碎片或不可迁移页严重。
compact_migrate_scanned/proc/vmstat扫描可迁移页的工作量，增长快会消耗 CPU。
compact_free_scanned/proc/vmstat扫描空闲页的工作量。
# 对比 compaction 前后计数
grep '^compact' /proc/vmstat > compact.before
sleep 60
grep '^compact' /proc/vmstat > compact.after
diff -u compact.before compact.after || true

# 手动触发 compaction 前先记录状态；生产节点慎用
cat /proc/buddyinfo > buddy.before
grep '^compact' /proc/vmstat > compact.before
# 维护窗口内才考虑：
# echo 1 | sudo tee /proc/sys/vm/compact_memory
cat /proc/buddyinfo > buddy.after
生产警告： echo 1 > /proc/sys/vm/compact_memory 可能造成 CPU 开销和延迟抖动。它适合诊断或维护窗口，不适合作为高频 cron “修复器”。

12. 和 meminfo/vmstat 的关系

/proc/buddyinfo 只告诉你空闲块分布。要解释原因和影响，必须关联 /proc/meminfo 的容量、大页和 slab 信息，以及 /proc/vmstat 的分配、回收、THP、compaction 计数。

文件看什么用途
/proc/buddyinfo按 node/zone/order 的空闲块数量判断连续物理内存形状。
/proc/meminfoMemAvailable、HugePages_*、AnonHugePages、SReclaimable、Unevictable判断容量、大页使用、slab、不可回收/不可迁移压力。
/proc/vmstatcompact*、thp*、allocstall*、pgscan*判断是否发生 compaction、THP fallback、内存回收。
vmstat 1si/so、free/cache、wa、r/b看系统级压力和时间趋势。
# 一次性采集内存碎片相关现场
out="memfrag.$(hostname).$(date +%Y%m%d-%H%M%S)"
mkdir -p "$out"
cat /proc/buddyinfo > "$out/buddyinfo.txt"
cat /proc/meminfo > "$out/meminfo.txt"
cat /proc/vmstat > "$out/vmstat.txt"
numactl --hardware > "$out/numactl-hardware.txt" 2>&1 || true
vmstat -w 1 10 > "$out/vmstat-sample.txt"
组合读法： MemAvailable 高 + order 9 为 0 + thp_fault_fallback 增长，指向连续大块不足；compact_fail 增长则说明内核尝试过但没有成功制造足够连续块。

13. GPU pinned memory 压力

PyTorch pin_memory=True、CUDA pinned allocation、NCCL/RDMA、GPUDirect RDMA、数据加载共享内存和用户态驱动注册页，都可能让部分页变得难以迁移。少量短生命周期 pinned buffer 通常没问题；过量、长期、跨 NUMA 或泄漏式 pinned memory 才会让高阶块恢复困难。

线索可能含义验证方向
Unevictable 或 Mlocked 偏高有大量不可回收/锁定页。grep -E 'Unevictable|Mlocked' /proc/meminfo。
某 job 启动后 order 9 快速下降模型加载、pinned buffer 池或通信库注册内存改变了空闲块形状。对齐 job 时间线，采样 buddyinfo。
compaction 扫描多但失败多可移动页不足或被不可迁移页阻断。grep '^compact' /proc/vmstat 前后 diff。
只在某几张 GPU 上复现NUMA 本地 node 碎片化或 CPU/GPU 拓扑不匹配。nvidia-smi topo -m + per-node buddyinfo。
# PyTorch 场景：先降低 pin 与 worker 做对照实验
# 原配置可能是 pin_memory=True, num_workers=16, prefetch_factor=4
# 对照：pin_memory=False 或 num_workers 减半，观察 buddyinfo 和吞吐变化

# 采集不可迁移/锁定内存线索
grep -E 'Unevictable|Mlocked|AnonHugePages|HugePages' /proc/meminfo

# 按进程看锁定内存字段 VmLck
grep -H '^VmLck:' /proc/[0-9]*/status 2>/dev/null | sort -k2 -nr | head
实验原则： 不要直接把 pin_memory 永久关掉作为结论。它可能降低 H2D 传输效率。正确做法是缩小 worker、prefetch、batch、buffer 池大小，并验证吞吐、p99 和碎片趋势。

14. 采样、解析与可视化

buddyinfo 最有价值的用法是按时间采样，和 job 生命周期、GPU 利用率、THP fallback、compaction 计数对齐。下面的脚本只读采样，不改变系统状态，适合作为工单附件或节点健康巡检的一部分。

# 每 5 秒采样一次，持续 10 分钟
mkdir -p buddy-samples
for i in $(seq 1 120); do
  ts=$(date +%s)
  cat /proc/buddyinfo > "buddy-samples/buddyinfo.$ts"
  grep -E 'compact|thp|allocstall' /proc/vmstat > "buddy-samples/vmstat.$ts"
  sleep 5
done

# 把 buddyinfo 转成 CSV：timestamp,node,zone,order,count
for f in buddy-samples/buddyinfo.*; do
  ts=${f##*.}
  awk -v ts="$ts" '
  /Node/ {
    node=$2; gsub(",", "", node)
    zone=$4
    for (i=5; i<=NF; i++) {
      printf "%s,%s,%s,%d,%s\n", ts, node, zone, i-5, $i
    }
  }' "$f"
done > buddyinfo.csv
采样字段用途
node,zone,order,count画每个 node 的高阶块趋势。
compact_success/fail/stall判断是否用 compaction 试图恢复高阶块。
thp_fault_fallback判断 THP 是否回退。
GPU 利用率/H2D copy/p99把内存形状变化和业务症状对齐。
巡检建议： 记录每个 node 的 order 9+ 块数、compaction fail/success 比例、THP fallback 增量，比只保存一张 free -h 截图有用得多。

安全流程图：从症状到缓解

排障顺序要从只读证据开始，避免把 compaction、drop caches 或 hugepage 调整当成无成本操作。

15. 故障排查流程

下面是一套适合 AI 节点的排障模板。目标是先确认“是否真的是连续内存问题”，再判断“影响哪个 NUMA node / zone”，最后选择低风险缓解。

  1. 确认症状：THP fallback、hugetlb 申请失败、训练吞吐下降、p99 尖刺、GPU copy 抖动。
  2. 采集只读现场：/proc/buddyinfo、/proc/meminfo、/proc/vmstat、NUMA/GPU 拓扑。
  3. 看目标 node/zone：不要只看全机总量。
  4. 对齐时间线：模型加载、dataloader 启动、checkpoint、通信库初始化、容器迁移。
  5. 判断是否伴随 compaction/THP fallback：看 vmstat 计数增量。
  6. 先做低风险对照实验：降低 worker、pin buffer、prefetch、batch，或调整 NUMA 绑定。
  7. 维护窗口内再考虑主动 compaction、重启 job、重新预留 hugepages 或节点 drain。
# 1. 快速确认高阶块
cat /proc/buddyinfo

# 2. 关联 THP/compaction
grep -E 'thp|compact|allocstall' /proc/vmstat

# 3. 关联大页和不可迁移线索
grep -E 'Huge|Unevictable|Mlocked|Slab|SReclaimable|SUnreclaim' /proc/meminfo

# 4. 关联 NUMA/GPU 拓扑
numactl --hardware
nvidia-smi topo -m 2>/dev/null || true
判断标准： 如果目标 node 的 order 9 长期为 0，同时 thp_fault_fallback 或 compact_fail 在故障窗口增长，才有较强证据说明大页/碎片参与了问题。

16. 生产缓解与安全边界

内存碎片问题的缓解分为三类：减少碎片来源、改善分配位置、在合适时机恢复高阶块。优先选择低风险策略；高风险操作必须在维护窗口或可回滚条件下执行。

动作风险适用场景
降低 dataloader num_workers、prefetch_factor、pinned buffer 池低到中pinned memory 过量、worker 过多导致碎片或内存压力。
绑定 CPU/内存到 GPU 本地 NUMA node中跨 NUMA 分配导致 copy 抖动或本地 node 压力不均。
提前预留 hugepages中服务明确依赖 hugetlb，且启动期有足够连续内存。
手动触发 compaction中到高诊断或维护窗口尝试恢复高阶块。
drop caches中到高只影响 page cache，不保证解决碎片，还会让后续 IO 变冷。
重启 job / drain 节点 / 重启节点高长期不可迁移碎片无法在线恢复，业务允许迁移。
# 安全：只读检查
cat /proc/buddyinfo
grep -E 'compact|thp' /proc/vmstat

# 谨慎：维护窗口内才考虑手动 compaction
cat /proc/buddyinfo > before.buddyinfo
# echo 1 | sudo tee /proc/sys/vm/compact_memory
cat /proc/buddyinfo > after.buddyinfo
diff -u before.buddyinfo after.buddyinfo || true

# 高风险：drop caches 不是碎片万能药，且会影响 IO 性能
# sync
# echo 3 | sudo tee /proc/sys/vm/drop_caches
不要这样做： 不要用 cron 高频执行 compact 或 drop caches；不要在没有业务对照的情况下关闭 THP、关闭 pinned memory 或重启节点；不要把全机 buddyinfo 总和当作 NUMA 本地健康度。

17. 容器、Kubernetes 与 Slurm

容器内读取 /proc/buddyinfo 时要小心视角问题。procfs 可能来自宿主机，容器的 cgroup 限制又只允许使用部分 CPU/内存；因此容器内看到的 buddyinfo 不一定等于该容器可分配的连续内存。HPC/Slurm 或 Kubernetes 节点上，最好同时采集作业分配的 CPU/NUMA/GPU 信息。

环境注意点建议
Docker/Containerd容器可能没有 numactl，procfs 视角可能偏宿主。在宿主机或 privileged debug pod 中采集。
KubernetesCPU Manager、Topology Manager、hugepages resource 会影响 NUMA 本地性。看 Pod spec、QoS、资源限制、节点拓扑策略。
Slurm--mem-bind、--cpu-bind、GPU 绑定策略影响分配位置。保存 scontrol show job、numactl --show、拓扑信息。
多租户 AI 节点其他 job 的 pinned memory 或 page cache 会影响同一 node。按节点采样，结合调度系统时间线定位邻居干扰。
# 容器内确认 cgroup 与 CPU 集合
cat /proc/self/status | grep -E 'Cpus_allowed_list|Mems_allowed_list'
cat /proc/self/cgroup

# Kubernetes hugepages 资源示例排查
kubectl describe node "$NODE" | grep -A5 -i huge
kubectl describe pod "$POD" | grep -A20 -i resources

# Slurm 作业中记录绑定策略
numactl --show
env | grep -E 'SLURM|CUDA_VISIBLE_DEVICES|NVIDIA_VISIBLE_DEVICES' | sort
视角提醒： 如果容器内 buddyinfo 和宿主机采样不一致，优先以宿主机节点级采样为准，再结合 cgroup/调度器解释容器可见资源。

速查表

你看到的现象优先检查可能结论
MemAvailable 高，但 hugepage 失败目标 node/zone 的 order 9连续 2MiB 块不足。
order 0 很多，order 9/10 为 0compact_fail、thp_fault_fallback碎片化，容量不是主要矛盾。
某 GPU 相关任务更慢GPU-NUMA 映射 + per-node buddyinfo本地 node 压力或碎片不均。
compaction 后高阶块仍不恢复Unevictable、VmLck、pinned buffer 配置不可迁移页可能阻断合并。
训练启动后高阶块骤降模型加载、DataLoader、NCCL/RDMA 初始化阶段大块分配、pinned memory 或 page cache 改变空闲块形状。

练习任务

  1. 在一台 Linux 机器上运行 cat /proc/buddyinfo，标注每一列对应的 order。
  2. 用 getconf PAGE_SIZE 计算 order 9 在当前系统上的大小。
  3. 写脚本每 5 秒采样一次 order 9+ 块数，并观察一个训练 job 启动前后的变化。
  4. 把 /proc/buddyinfo、/proc/meminfo、/proc/vmstat 放在一起解释一次 THP fallback 增长。
  5. 用 numactl --hardware 和 GPU 拓扑命令判断目标 GPU 的本地 NUMA node。
# 小练习：输出每个 node/zone 的 order9 块数和约等价 2MiB 容量
awk '
/Node/ {
  node=$2; gsub(",", "", node)
  zone=$4
  order9 = (NF >= 14 ? $14 : 0)
  printf "node=%s zone=%s order9_blocks=%d approx_2MiB_capacity=%dMiB\n",
    node, zone, order9, order9 * 2
}' /proc/buddyinfo
