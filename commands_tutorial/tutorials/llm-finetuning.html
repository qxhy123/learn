§ 01 · Foundation什么是模型调优

模型调优 (Fine-Tuning) 是指在已经预训练好的模型基础上，使用相对少量的、特定领域的数据继续训练，让模型适应具体下游任务的过程。它的核心理念可以用一个朴素的比喻来理解：

预训练教给模型语言与世界的常识；调优则告诉它，在你的工作场景里该如何说话、如何决策。 — 调优的本质

预训练的模型就像一个博览群书的研究生——它读过几乎所有公开的网络文本，掌握了语法、逻辑、常识，乃至大量的世界知识。但这位"通才"在面对特定行业（比如法律文书审查、医学影像诊断、客服对话）时，往往不知道你公司内部的术语、流程、偏好。调优就是让它"在岗培训"的过程。

¶为什么要调优而不是从头训练

从零训练一个 70B 的大模型需要数千张 H100 GPU、数月时间、上千万美元——这是绝大多数团队负担不起的。而调优只需要其中的百分之一甚至千分之一的资源，就能让模型在你的具体任务上达到甚至超过通用模型的表现。这是一种典型的"站在巨人肩膀上"的工程思路。

¶调优 vs Prompt Engineering vs RAG

很多团队在面对"模型不够好用"时，第一反应是调优。但实际上还有两个更轻量的选择：提示工程 (Prompt Engineering) 和 检索增强生成 (RAG)。三者各有适用场景：

方法解决什么问题启动成本知识更新典型场景
Prompt Engineering 调整模型输出风格 / 格式 低 实时 简单分类、格式约束
RAG 注入外部 / 私有知识 中 随检索库更新 问答、文档查询
Fine-Tuning 改变模型行为模式 / 风格 高 需重新训练 领域语言、复杂格式、风格

经验法则：先 Prompt，再 RAG，最后才考虑 Fine-Tuning。只有当前两者都无法满足需求时，才投入调优的成本。如果你的目标是"让模型记住我的私有文档"——那是 RAG 的领域，不是调优。

§ 02 · Taxonomy调优方法的图谱

调优并不是一个单一的算法，而是一族技术的总称。按照"更新哪些参数"和"如何更新"，可以分为四大类。理解它们的差异，是选择合适方法的前提。

i.Full Fine-Tuning · 全参数调优

最直接的做法：把整个模型的所有参数都纳入梯度更新。这是上下界最高的方案——理论上能逼近最佳性能，但代价是显存占用约为模型权重的 4–6 倍（权重 + 梯度 + 优化器状态），对于 7B 模型至少需要单张 80GB GPU 配合优化技巧。

ii.LoRA · 低秩适配

2021 年提出的 LoRA (Low-Rank Adaptation) 是目前最流行的方法。它的核心洞察是：调优过程中权重的更新矩阵 ΔW 通常具有较低的"内在秩"，因此可以分解为两个小矩阵的乘积 ΔW = B·A，其中 A ∈ ℝ^(r×d)、B ∈ ℝ^(d×r)，秩 r 通常取 8 到 64。

# 原始前向：
h = W·x

# LoRA 前向（W 冻结，A·B 可训练）：
h = W·x + (B·A)·x · (α/r)

# 训练参数量从 d·d 降到 2·r·d
# 当 d=4096, r=8 时：缩减 256 倍

训练完成后，可以选择把 B·A 合并回 W（推理零开销），也可以保留为独立的"适配器"——这意味着同一个基模型可以挂载多个 LoRA，按需切换不同任务。

LoRA 的另一个隐藏优势是正则化效应：低秩约束本身限制了模型的"过拟合空间"，在小数据场景下往往比全参数调优更稳健。

iii.QLoRA · 量化 + 低秩

QLoRA 在 LoRA 基础上更进一步：把基模型权重量化为 4-bit（NF4 编码），仅在前向传播时反量化为 bf16 计算。这让单张 24GB 消费级显卡也能调优 33B 模型。代价是反量化的额外开销，训练速度比 LoRA 慢 30–40%，但显存节省可达 75%。

iv.Prompt / Prefix / P-Tuning · 软提示家族

这一族方法的思路截然不同：完全冻结模型参数，只在输入端学习一段"软提示"（连续的 embedding 向量）。它的可训练参数最少（通常少于 1%），但能力上限也较低，更适合分类、抽取这类相对简单的任务。

v.对齐类调优 · SFT、DPO、RLHF

当目标不仅是"会做任务"，还要"按人类偏好做"时，需要更复杂的训练范式：

  • SFT (Supervised Fine-Tuning) — 用 (指令, 回复) 对进行有监督训练，是所有对齐工作的起点。
  • DPO (Direct Preference Optimization) — 用 (chosen, rejected) 偏好对直接优化，绕过了 RLHF 的奖励模型。
  • RLHF (Reinforcement Learning from Human Feedback) — 经典三步法：SFT → 奖励模型 → PPO 强化学习。效果最好但最复杂。
方法可训参数比显存需求性能上限推荐场景
Full FT100%极高★★★★★资源充足、追求极致
LoRA0.1–1%中★★★★大多数场景的默认选择
QLoRA0.1–1%低★★★★单卡训练大模型
Prompt Tuning< 0.1%极低★★分类、抽取等简单任务
DPO≈ LoRA中★★★★偏好对齐、安全调优

选型建议：2026 年的工业实践中，QLoRA + DPO 已经成为中小团队最常见的组合——既能用单卡跑大模型，又能直接做偏好对齐。除非你有极强的资源储备和明确的性能要求，否则没必要从全参数调优开始。

¶关键决策点的判断

流程图上的两个决策点是整个流水线的"关卡"。第一个决策——资源是否满足——通常在跑了一个小规模 dry-run 后才能确定：你需要先估算实际的显存占用、单步时长，反推训练总时长是否在可接受范围。第二个决策——指标是否达标——则需要预先定义清晰的"通过标准"，否则容易陷入"再训一会儿可能就好了"的无止境循环。

常见陷阱：很多团队在流程的第 1 步就走错了——没有清晰定义"成功长什么样"。如果你说不出"模型在 X 测试集上的 Y 指标达到 Z 才算成功"，那么你后面的所有训练都将是漫无目的的。

01

ML 工程师

主导调优策略选择、超参配置、训练执行、模型评估。是整个项目的技术核心，需要同时懂算法、工程、数据。

负责数据管道：从生产系统采集、脱敏、清洗，到训练 / 验证 / 测试集的科学切分。

§ 05 · Sequence训练步骤的时序

在最微观的层面上，调优训练的核心是一个循环：取一批数据 → 前向计算 → 反向传播 → 更新参数 → 记录指标。看似简单，但这个循环里发生的事件之间的时序关系，决定了训练是否高效、稳定。

¶容易被忽视的细节

这张图里有两个值得停下来思考的细节：

第一，第 12 步 zero_grad() 必须在下一步开始前执行。PyTorch 的梯度默认是累加的，如果忘记清零，本次的梯度会和上次的叠加，造成训练发散。这是新手最常踩的坑之一。

第二，第 9 步 optimizer.step() 内部其实远比"减去梯度"复杂——以 AdamW 为例，它需要维护每个参数的一阶动量、二阶动量、偏差修正项，这些状态加起来通常是模型权重的 2 倍。这就是为什么 Adam 系列优化器的显存占用如此之大。

for step, batch in enumerate(dataloader):           # 1, 2
    inputs, targets = batch["input"], batch["label"]

    logits = model(inputs)                              # 3
    loss   = loss_fn(logits, targets)                   # 4, 5, 6

    loss.backward()                                     # 7, 8

    if (step + 1) % grad_accum_steps == 0:
        torch.nn.utils.clip_grad_norm_(
            model.parameters(), max_norm=1.0          # 防爆梯度
        )
        optimizer.step()                                # 9, 10
        scheduler.step()                                # 学习率调度
        optimizer.zero_grad()                           # 12

    logger.log({                                        # 11
        "loss": loss.item(),
        "lr": scheduler.get_last_lr()[0],
        "grad_norm": total_norm,
    })

梯度累积 (Gradient Accumulation)：当显存不足以容纳目标 batch size 时，可以让多个小 batch 累计梯度，再一次性更新——效果等价于大 batch，但显存只需一份。代码上就是把 optimizer.step() 放进 if 条件里。

§ 06 · Data数据准备的艺术

有一个在工程师圈子里流传甚广的格言：Garbage in, garbage out。在调优领域，这句话甚至要更狠——数据质量直接决定了模型的能力上限。算力可以买，超参数可以搜，但数据是不可替代的核心资产。

¶数据的三大维度

01

规模 · Quantity

对于 LoRA / SFT，500–10,000 高质量样本通常已经足够。规模并非越大越好——脏数据多了反而是负担。

02

质量 · Quality

每条样本都应当是你希望模型输出的"理想答案"。一条糟糕的样本可能抵消一百条好样本。

03

多样性 · Diversity

覆盖任务的不同子场景、不同输入风格、不同长度。单调的数据让模型学到捷径而非泛化。

¶数据格式：以指令调优为例

当前主流的对话 / 指令调优使用的格式相对统一，每条样本是一个多轮对话，包含 system / user / assistant 三种角色：

{
  "messages": [
    {"role": "system",
     "content": "你是一名资深法律顾问，回答应当严谨、引用法条。"},
    {"role": "user",
     "content": "二手房买卖中，卖方违约不交房应如何处理？"},
    {"role": "assistant",
     "content": "根据《民法典》第 577 条，卖方违约应承担继续履行..."}
  ]
}

训练时，框架会把这些消息按模型的 chat template 拼接成一段长文本，并通过 loss mask 让模型只在 assistant 部分计算损失——你不希望模型学着去"模仿用户提问"，只希望它学会怎么"回答"。

这个 loss mask 的细节经常被忽略。如果你直接用普通的 causal LM loss 不做掩码，模型会同时学习"提问"和"回答"的分布——结果就是它会自言自语、问自己问题。

¶数据切分的科学

训练集 / 验证集 / 测试集的切分听起来是基础知识，但在实践中很多团队都会在这里出错。常见的反模式：

错误做法问题正确做法
随机切分 同一个用户 / 文档可能同时出现在训练和测试集 按用户 / 文档 ID 切分，保证零重叠
测试集只有 50 条 评估指标方差太大，无法可靠对比 测试集至少 500 条，分层覆盖各子任务
训练时偷看测试集 调优过程中反复用测试集选模型 = 数据泄漏 用验证集选模型，测试集只在最终评估时打开
只用历史数据 无法发现模型对新分布的泛化能力 测试集中至少留 20% 来自最近时间段

关于"数据污染"：如果你用某个公开基准 (如 MMLU、GSM8K) 来评估调优效果，请先确认你的训练数据中没有这些基准的题目——否则你测出来的会是"模型记住了多少"，而不是"模型学会了什么"。

§ 07 · Hyperparams超参数调优

超参数是调优过程中你能直接控制的"旋钮"。它们不在训练中被学习，而是由你预先设定。在所有旋钮里，有几个对结果影响最大的核心参数，值得花最多精力去调。

¶核心超参数概览

参数典型范围影响调节优先级
Learning Rate 1e-5 ~ 5e-4 最关键。过大不收敛，过小学不到 最高
Batch Size 1 ~ 64 影响梯度噪声、吞吐量 高
Epochs 1 ~ 5 过多易过拟合，特别是小数据 高
LoRA Rank (r) 4 ~ 64 控制 LoRA 容量 高
LoRA Alpha (α) 16 ~ 32 缩放因子，常设 r 的 2 倍 低
Weight Decay 0 ~ 0.1 正则化强度 低
Warmup Ratio 0.03 ~ 0.1 前期线性升温，缓解早期不稳定 中

¶学习率：最重要的旋钮

如果你只能调一个超参，那一定是学习率。Full Fine-Tuning 的常见取值是 1e-5 到 5e-5，而 LoRA 因为只更新很小一部分参数，可以用大得多的 1e-4 到 3e-4。一个稳健的起点：

config = {
    "learning_rate":    2e-4,    # LoRA 的甜点区
    "lr_scheduler":     "cosine", # 余弦退火
    "warmup_ratio":     0.05,
    "num_train_epochs": 3,
    "per_device_batch": 4,
    "grad_accum_steps": 8,    # 等价 batch=32
    "weight_decay":     0.0,    # LoRA 通常关掉
    "lora_r":           16,
    "lora_alpha":       32,
    "lora_dropout":     0.05,
    "target_modules":   ["q_proj", "k_proj", "v_proj", "o_proj"],
}

¶学习率寻找：LR Range Test

对于一个新数据集，找最佳学习率的高效方法是学习率范围测试——让 lr 从极小值（如 1e-7）线性增长到极大值（如 1e-2），观察 loss 曲线。最佳学习率位于"loss 下降最陡"的那个区间，通常比 loss 最低点的 lr 小一个数量级。

"loss 不降三件套"：当你发现 loss 完全不动时，按这个顺序排查：(1) 学习率是不是太小了，量级提一档；(2) 数据 mask 是不是写错了，loss 一直在算 padding；(3) 梯度是不是被 clip 到接近零了，把 max_norm 从 0.5 调到 1.0。

¶Epochs 与过拟合

大模型调优一个反直觉的现象是：epochs 通常不需要很多。1–3 个 epoch 是绝大多数场景的合理范围。如果你的数据是几千条样本，跑到 5+ epochs 几乎肯定会过拟合——表现是训练 loss 持续下降，但验证 loss 开始反弹。

判断是否过拟合的最佳方法不是看 loss，而是看实际生成质量：让模型在验证集上生成回复，亲自读 20 条。如果开始出现训练集里的固定句式、重复模板、过度自信的错误，就是过拟合的信号。

在 LoRA 调优中，调小 rank (从 16 到 8) 比加大 weight decay 更能有效抑制过拟合——因为低秩本身就是一种容量约束。

§ 08 · Evaluation评估与监控

"它训完了，效果怎么样？"——这是调优中最难回答的问题。损失函数下降只能说明模型在拟合训练数据，说明不了任何关于真实任务表现的事情。建立一套可信的评估体系，是调优工程师的核心能力。

¶评估的三个层次

不同层次的评估各有用途，互不替代：

L1

训练侧指标

train loss、val loss、grad norm、token accuracy。实时监控用，能发现训练异常，但不能判断质量。

L2

自动化指标

BLEU、ROUGE、Exact Match、自定义业务指标。大规模回归用，便宜、快、可重复。

L3

人工 / LLM 评测

人工打分 / GPT-4 作为评委。最终把关用，最贵但最贴近真实质量。

¶构造一个好的评测集

一个好的评测集应当满足这几个条件：

  • ① 分层覆盖：不只是平均表现，要分别覆盖简单 / 中等 / 困难三档样本。
  • ② 包含负例：要有"模型应当拒绝回答"的样本，否则你测不出过度自信。
  • ③ 包含历史 bad case：把基线模型曾经犯过的错误都加进去，做回归测试。
  • ④ 足够大：500 条是底线。指标差异 < 1% 在 100 条样本上没有统计意义。

¶LLM-as-Judge：成本与陷阱

用更强的模型作为"裁判"来打分（如 GPT-4 评判调优后的小模型）已经是标准实践，但要警惕几个陷阱：

陷阱表现缓解
位置偏见 裁判更倾向于打分给前面那个回答 每对样本测两次，交换顺序取平均
长度偏见 裁判更喜欢长回答，即使内容空洞 评分维度中显式考虑"简洁性"
风格同源偏见 裁判更喜欢和自己风格一致的回答 用至少两个不同家族的裁判模型
规则模糊 不同次评分波动很大 给裁判清晰的 rubric，要求按维度打分

把评估代码当成产品代码来对待——纳入版本控制，写单元测试，确保每次能复现。当三个月后老板问"为什么这个模型上线后变差了"，你的评估系统是唯一能回答的工具。

§ 09 · Troubleshooting疑难杂症与对策

真实的调优工作中，绝大多数时间不是在写训练代码，而是在排查问题。这一节列出最常见的 6 种症状及其诊断思路。

⚠症状一 · Loss 完全不下降

训练几十上百步，loss 在初始值附近震荡，纹丝不动。诊断顺序：

  1. 检查学习率是否过小——把 lr 调大 10 倍试试，loss 应当至少有变化。
  2. 检查数据掩码——把一个 batch 的输入和 label 打印出来，确认 label 不是全 -100 (PyTorch 中 -100 表示忽略)。
  3. 检查梯度是否在反向——打印 model.parameters() 里某个权重的 .grad.norm()，应当非零。
  4. 对于 LoRA，确认 requires_grad=True 设置正确，基模型确实被冻结但 LoRA 层确实可训练。

⚠症状二 · Loss 飞了 / 出现 NaN

loss 突然从 2.x 飙升到 1e6，或者直接变成 NaN。最常见原因：

  • 学习率太大——降一个数量级。
  • 没做梯度裁剪——加上 clip_grad_norm_(parameters, max_norm=1.0)。
  • 混合精度溢出——bf16 比 fp16 稳定得多，能用 bf16 优先用 bf16。
  • 有脏数据样本——几条超长或包含特殊字符的样本可能导致计算图爆炸。

⚠症状三 · 训练 loss 降了，但生成质量变差

这是过拟合的典型症状，也是初学者最难察觉的问题——因为指标看起来都在改善。处理方法：

  • 减少 epochs，从 3 降到 1。
  • 降低 LoRA rank，从 16 降到 8 或 4。
  • 增加数据多样性，而不是数据数量。
  • 引入定期人工质检——每 N 步生成一些样本人工读读，比看曲线靠谱。

⚠症状四 · 模型"忘了"通用能力

调优后的模型在你的任务上很厉害，但回答日常问题反而变笨了——这叫灾难性遗忘 (Catastrophic Forgetting)。对策：

  • 在训练数据中混入 10–20% 的通用对话样本（"经验回放"）。
  • 使用 LoRA 而非全参数调优——LoRA 天然只动一小块参数，遗忘程度最小。
  • 降低学习率、减少 epochs。
  • 训练后做"通用能力回归测试"，发现退化就回滚。

⚠症状五 · 显存 OOM

报错 CUDA out of memory。优化清单（按收益从大到小）：

  1. 开启 gradient checkpointing（用算力换显存，约 50% 节省）。
  2. 降低 per_device_batch_size，配合 grad_accum_steps 维持等效大小。
  3. 从 LoRA 切到 QLoRA（4-bit 量化基模型）。
  4. 降低序列长度 max_length——很多场景 1024 token 已经足够。
  5. 用 DeepSpeed ZeRO 或 FSDP 做模型分片（多卡）。

⚠症状六 · 训练慢得反常

显卡占用很满，但每一步耗时远超预期。可能的瓶颈：

  • 数据加载——num_workers 设为 4–8，避免 dataloader 阻塞 GPU。
  • 序列长度不均——很多 padding 在做无效计算，启用 group_by_length。
  • CPU-GPU 数据搬运——确认数据在 pin_memory，non_blocking=True。
  • 同步等待——用 PyTorch Profiler 看一下时间都花在哪里。
调优工程师的 80% 时间不在调模型，而在调那些本不该出问题的地方。 — 一条朴素的真理

§ 10 · Practices最佳实践清单

把这一节当作一份给"未来的自己"的清单——每次启动新调优项目前过一遍。它浓缩了前面所有章节的要点，按时间顺序排列。

①项目启动前

  • 写一份 1 页的调优需求文档：任务定义、目标指标、最低可接受值、deadline、资源预算。
  • 评估调优是否真的必要——能 Prompt 解决就不用 RAG，能 RAG 就不用调优。
  • 对齐评估方法。在写代码之前就要想好"怎么算成功"。
  • 选定基模型。许可证、上下文长度、社区生态、可获得性都是考量。

②数据阶段

  • 构造一个 200 条的评测集 v0，先于训练数据存在。
  • 训练数据先做 100 条原型集，用它跑通流程，再扩量。
  • 每条样本在入库前必须经过自动校验（格式、长度、语种、空字段）。
  • 切分按"实体"切，不按"行"切（按用户、按文档、按日期）。

③训练阶段

  • 第一次训练用 100 条数据 + 全部超参默认值，目标只是"跑起来不报错"。
  • 每个实验都有唯一 run ID，所有产物（配置、日志、checkpoint、评测结果）按 ID 归档。
  • 用 W&B / TensorBoard 记录指标，不要只看终端日志。
  • 每隔 N 步在验证集上生成 5 条样本，附在日志里。曲线骗人，样本不骗人。
  • 所有调超参的实验都遵循"一次只动一个变量"原则。

④评估阶段

  • 评估前先冻结评测集，不要因为某些指标差就修改评测集。
  • 对比基线必须是没有调优的同一基模型，而不是另一个产品。
  • 报告时同时给出 mean ± std（多次评估的均值标准差），单点数字没有说服力。
  • 留 50 条困难样本专门人工读，找系统性错误。

⑤部署阶段

  • 先做影子流量 (shadow traffic)，新模型只输出不返回，对比与线上模型的差异。
  • 再做灰度 (1% → 10% → 50% → 100%)，每一档都监控核心业务指标。
  • 准备一键回滚脚本。模型上线后业务指标恶化，立刻回滚再排查。
  • 建立反馈回路——bad case 自动收集到训练数据池中，为下一轮调优积累。

调优是一项系统工程，不是一次性技术活。一个能稳定迭代的调优 pipeline，比任何一个特别精彩的"单次实验"都有价值得多。先建工厂，再造产品。

¶延伸阅读

本教程是一份地图，不是一本百科全书。当你完成第一个调优项目后，建议从这些方向深入：

  • 对齐技术：DPO、KTO、ORPO、SimPO——后 RLHF 时代的偏好优化方法族。
  • 高效推理：把调优好的模型部署到生产，涉及 vLLM、TensorRT-LLM、量化推理等。
  • 持续学习：如何让模型在不遗忘的前提下持续吸收新知识，这是开放问题。
  • 多模态调优：当输入不只是文本，还有图像、音频、视频时的调优范式。
