/proc/meminfo 深度教程：AI Infra 视角的 Linux 内存账本

这份教程讲的是 Linux 伪文件 /proc/meminfo，而不是一个普通命令。它是内核暴露的系统级内存快照，AI Infra 工程师常用它判断训练/推理节点是否真的缺内存、页缓存是否可回收、匿名页是否异常膨胀、Slab 是否泄漏、HugePages 是否配置正确、容器里看到的内存为什么和宿主机/cgroup 不一致，以及 free、smaps、cgroup 指标之间如何互相校验。

1. /proc/meminfo 是什么

/proc/meminfo 是 Linux procfs 中的只读伪文件。读取它时，内核实时生成一份当前系统内存状态摘要；它不是磁盘上的普通文本文件，也不会因为你 cat 它而保存历史。

它回答什么
全机物理内存、可用内存、页缓存、匿名页、Slab、HugePages、Swap、提交量、mlock 等“系统级账目”。
它不回答什么
某个容器真实可用额度、单个进程每个映射的 PSS/RSS、GPU 显存、DMA pinned host memory 的完整归因。
AI Infra 价值
判断 CPU 内存是否限制吞吐、DataLoader 是否撑爆页缓存、模型服务是否匿名页泄漏、内核对象是否异常增长。
# 最直接的读取方式
cat /proc/meminfo

# 只看关键字段
egrep 'MemTotal|MemAvailable|MemFree|Buffers|Cached|AnonPages|Slab|SReclaimable|SUnreclaim|Huge|Mlocked|Unevictable|Swap|Commit' /proc/meminfo

# 连续观察，每秒一帧
watch -n 1 "egrep 'MemAvailable|AnonPages|Cached|Slab|SUnreclaim|Huge|Mlocked|Unevictable' /proc/meminfo"
读数边界： /proc/meminfo 是宿主机视角。容器内读取时，经常仍然看到宿主机总内存，而不是容器限制；容器容量判断必须再读 cgroup。

2. 整体模型：内存账本如何分层

AI 节点上，“空闲很少”通常不是问题；关键是哪些内存可回收，哪些被进程、内核或特殊页长期占住。

3. 快速读取与单位换算

/proc/meminfo 大多数字段以 kB 为单位；字段集合会随内核版本、配置和架构变化。脚本解析时不要假设每个字段都存在，也不要依赖固定行号。

# 查看前几行
head -20 /proc/meminfo

# 以 GiB 展示关键字段
awk '
  /^(MemTotal|MemAvailable|MemFree|Cached|Buffers|AnonPages|Slab|SUnreclaim):/ {
    printf "%-16s %10.2f GiB\n", $1, $2/1024/1024
  }
' /proc/meminfo

# 生成一行 Prometheus textfile collector 风格样例
awk '/^[A-Za-z_()]+:/ {gsub(":","",$1); print "node_meminfo_" $1 "_bytes " $2*1024}' /proc/meminfo
实践原因
按字段名解析不同内核的字段顺序、字段数量可能不同。
统一换算为 bytes 或 GiB避免 kB、KiB、GB 混用导致容量判断误差。
记录时间序列单点快照只能说明当前状态，不能证明泄漏或趋势。
和 cgroup/进程指标交叉验证meminfo 是全机账本，不负责容器或单进程归因。
单位提示： meminfo 标注的 kB 在 Linux 语境中通常按 1024 bytes 计算；容量报表最好显式写 KiB/GiB 或 bytes。

4. 核心字段速查表

字段AI Infra 解读常见关联动作
MemTotal宿主机可管理物理内存总量。容量规划、NUMA 节点核对、容器误读排查。
MemFree完全未使用的内存页，通常很低也正常。不要单独用作告警。
MemAvailable内核估算可安全分配的内存，包含部分可回收 cache/slab。主告警信号之一。
Buffers块设备元数据等缓冲。I/O 密集任务辅助观察。
Cached文件页缓存，不含部分 tmpfs/shmem 语义细节。数据集读取、checkpoint、镜像拉取后观察。
SwapCached曾被换出又换入、仍在 swap 有副本的页。判断是否发生过 swap 压力。
Active/InactiveLRU 上较活跃/不活跃的页。缓存回收与工作集分析。
AnonPages匿名页：进程堆、栈、匿名 mmap 等。训练/推理进程 CPU 内存增长的核心线索。
Mapped映射到进程地址空间的文件页。模型文件 mmap、共享库、数据文件映射观察。
Shmemtmpfs、POSIX shared memory 等。DataLoader 共享内存、/dev/shm、Ray plasma 等。
Slab内核对象缓存总量。文件系统元数据、网络、驱动对象排查。
SReclaimable理论上可回收的 Slab。目录项/inode cache 多时不一定是泄漏。
SUnreclaim不可轻易回收的 Slab。内核/驱动问题或对象泄漏重点关注。
Unevictable/Mlocked不可驱逐页、被 mlock 锁住的页。RDMA、数据库、框架 pinned memory 线索之一。
HugePages_Total 等显式 HugeTLB 池状态。大页预留、NUMA 与应用配置核对。
AnonHugePages透明大页中匿名页部分。THP 对延迟、碎片、回收的影响。
Committed_AS/CommitLimit虚拟内存提交量与限制。overcommit、fork、mmap、OOM 前兆判断。

5. MemTotal、MemFree 与 MemAvailable

MemFree 是完全空闲页；Linux 会主动把闲置内存用于页缓存和内核缓存，所以它低并不等于内存不足。MemAvailable 是更接近“现在还能分配多少”的估算，考虑了低水位和可回收页。

MemTotal
宿主机全局值。容器中看到它时，不要误以为容器也有这么多可用内存。
MemFree
裸空闲页。只适合解释“为什么 free 很少”，不适合直接告警。
MemAvailable
容量与告警核心字段。低于工作负载峰值缓冲时，OOM/直接回收/延迟抖动风险升高。
# 计算 available 百分比
awk '
  /MemTotal:/ {total=$2}
  /MemAvailable:/ {avail=$2}
  END {printf "MemAvailable: %.1f%%\n", avail/total*100}
' /proc/meminfo

# 简单告警示例：低于 8 GiB 或 8%
awk '
  /MemTotal:/ {total=$2}
  /MemAvailable:/ {avail=$2}
  END {
    if (avail < 8*1024*1024 || avail/total < 0.08) print "WARN low MemAvailable"
    else print "OK"
  }
' /proc/meminfo
告警不要机械化： 512 GiB 训练节点和 16 GiB 边缘推理机的阈值不同；应结合批大小、并发、预取队列、checkpoint 峰值、容器 limit 和历史水位设阈值。

6. Buffers、Cached 与页缓存

AI 训练常见场景是数据集、tokenized shards、checkpoint、容器镜像层反复读写。Linux 会用空闲内存缓存文件页，以提升后续读取吞吐。Cached 高通常是好事，只有当 MemAvailable 同时低、回收频繁、I/O 延迟上升时才需要进一步排查。

现象可能原因验证方式
Cached 很高，MemAvailable 也高页缓存正常利用空闲内存。无需处理，观察吞吐是否稳定。
Cached 高但 MemAvailable 低部分 cache 不易回收，或匿名页/Slab 同时很高。看 AnonPages、Shmem、SUnreclaim。
训练启动后 cache 快速增长DataLoader 顺序扫描数据集。观察 pgscan/pgsteal、I/O、样本吞吐。
Buffers 波动块设备元数据或写入路径变化。结合 iostat、文件系统、checkpoint 周期。
# 观察 cache 与匿名页的相对变化
watch -n 2 "awk '/^(MemAvailable|Cached|Buffers|AnonPages|Shmem|Slab):/ {printf \"%-14s %9.2f GiB\\n\", \$1, \$2/1024/1024}' /proc/meminfo"

# 谨慎演示：drop_caches 会影响全机性能，生产不要随意执行
sync
echo 3 | sudo tee /proc/sys/vm/drop_caches
安全提示： drop_caches 是全机副作用操作，会破坏缓存热度并影响其他任务。排障时优先观察，不要把“清缓存”当作常规修复。

流程图：AI 任务如何改变 meminfo

AI 任务的内存变化不是单一路径：数据、模型、预取、通信和驱动都会在 meminfo 中留下不同线索。

7. AnonPages：训练进程真正吃掉的内存

AnonPages 通常代表没有文件后备的进程内存，例如 Python heap、C++ allocator arena、匿名 mmap、复制后的 COW 页。AI 工作负载里，它常对应 batch buffer、token cache、CPU offload、特征缓存、推理 KV cache 的 CPU 部分、数据增强中间对象等。

# 同时看全机匿名页和进程 RSS 排名
awk '/^AnonPages:/ {printf "AnonPages %.2f GiB\n", $2/1024/1024}' /proc/meminfo
ps -eo pid,ppid,rss,comm,args --sort=-rss | head -20

# 对单个进程看 smaps_rollup，Pss/Rss/Anonymous 更适合归因
pid=12345
cat /proc/$pid/smaps_rollup

# Python/torch 场景可同时记录 batch size、num_workers、prefetch_factor
date
egrep 'MemAvailable|AnonPages|Shmem|Cached' /proc/meminfo
持续增长
如果 AnonPages 随 step 单调增长，而 Cached 不足以解释下降，优先怀疑进程侧泄漏、缓存未释放、队列积压或 allocator 碎片。
平台期
训练启动期增长后稳定，通常是正常工作集形成。要结合吞吐、step 时间、OOM 事件和容器 limit 判断。
归因原则： meminfo 只能告诉你“匿名页总量变化”；要知道是谁占用，必须去 ps、smaps_rollup、应用指标或 profiler。

8. Slab、SReclaimable、SUnreclaim

Slab 是内核对象缓存。AI 节点上，数据集包含海量小文件、容器镜像层很多、网络连接/存储客户端繁忙时，目录项、inode、网络对象和文件系统对象可能大量增长。

字段含义排障重点
Slab内核对象缓存总量。先看它占总内存比例和增长趋势。
SReclaimable可回收 slab，例如部分 dentry/inode cache。高但可回收时未必是故障。
SUnreclaim不可回收或难回收 slab。持续增长更值得警惕，可能涉及内核、驱动、网络或文件系统问题。
KReclaimable较新内核中更广义可回收内核分配。和 SReclaimable 一起看。
# meminfo 层面观察
egrep 'Slab|SReclaimable|SUnreclaim|KReclaimable' /proc/meminfo

# slabtop 需要交互或 root 权限，适合进一步归因
sudo slabtop -o | head -30

# 非交互观察 slab cache
sudo cat /proc/slabinfo | awk 'NR>2 {printf "%-32s %12d %12d\n", $1, $3, $4}' | sort -k2,2nr | head
不要误判： 小文件数据集被扫描后，dentry/inode cache 高很常见；如果 MemAvailable 仍充足，且 SReclaimable 占主导，通常不是内存泄漏。

9. HugePages 与 THP

meminfo 同时暴露显式 HugeTLB 大页池和透明大页相关计数。AI 场景里，显式 HugePages 更多见于特定数据库、低延迟服务、虚拟化或通信栈配置；透明大页（THP）可能影响匿名页分配、碎片、延迟尖刺和 NUMA 行为。

字段解释典型问题
HugePages_Total预留的显式 HugeTLB 页总数。预留过多会减少普通内存可用量。
HugePages_Free尚未使用的显式 huge pages。配置了但应用没用上。
HugePages_Rsvd已承诺但尚未实际分配。应用启动后可能继续消耗。
Hugepagesize单个 huge page 大小。通常是 2 MiB，也可能有 1 GiB 页配置。
AnonHugePages透明大页中的匿名页。THP 导致回收/压缩开销或延迟抖动。
# 查看 huge page 相关字段
egrep 'Huge|AnonHugePages|ShmemHugePages|FileHugePages' /proc/meminfo

# 查看 THP 当前策略
cat /sys/kernel/mm/transparent_hugepage/enabled 2>/dev/null
cat /sys/kernel/mm/transparent_hugepage/defrag 2>/dev/null

# NUMA 维度显式 huge pages
find /sys/devices/system/node -name 'free_hugepages' -o -name 'nr_hugepages' 2>/dev/null | sort | xargs -r -n1 sh -c 'printf "%s " "$1"; cat "$1"' sh
配置风险： 修改 huge pages 或 THP 策略会影响全机内存行为和延迟特征；生产变更应先在同类节点灰度，并记录吞吐、P99、OOM 与内存碎片指标。

10. mlocked 与 pinned memory 线索

AI Infra 常提到 pinned memory：PyTorch DataLoader 的 pin_memory=True、CUDA host pinned buffer、RDMA/NCCL/InfiniBand 注册内存、数据库或低延迟组件的 mlock。但 meminfo 不能完整归因所有 pinned host memory，只能提供若干线索。

Mlocked
被 mlock 锁住的内存。它不一定覆盖所有驱动注册页，但能说明用户态锁页压力。
Unevictable
不可驱逐页集合，通常包含 mlocked 页，也可能包含其他不可回收页。
SUnreclaim
驱动或内核对象导致的不可回收内存压力可能在这里留下痕迹。
# meminfo 线索
egrep 'Mlocked|Unevictable|SUnreclaim|VmallocUsed' /proc/meminfo

# 进程级 locked memory 线索
pid=12345
grep -E 'VmLck|VmPin|VmRSS|VmData' /proc/$pid/status

# 查看进程 limits，RLIMIT_MEMLOCK 太低会导致 RDMA/CUDA/DPDK 类应用失败
grep -i 'Max locked memory' /proc/$pid/limits
关键 caveat： GPU 显存不在 /proc/meminfo 中；CUDA pinned host memory 也不总能被某一个 meminfo 字段完整解释。需要结合 nvidia-smi、框架日志、进程 status/smaps、驱动指标和 cgroup 事件。

11. Swap、Commit 与 overcommit

AI 训练节点通常希望避免 swap 造成长尾延迟或吞吐崩塌，但 swap 指标仍有排障价值。CommitLimit 与 Committed_AS 则描述虚拟内存承诺，不等同于实际 RSS。

字段含义怎么用
SwapTotal/SwapFreeswap 总量与剩余。确认是否启用 swap、是否被耗尽。
SwapCached仍有 swap 副本的内存页。判断曾经发生过换入换出。
Committed_AS进程已承诺虚拟内存总量。大规模 mmap/fork 后可快速膨胀。
CommitLimit根据 overcommit 策略计算的提交上限。解释虚拟内存申请失败。
# 查看 commit 与 swap
egrep 'SwapTotal|SwapFree|SwapCached|CommitLimit|Committed_AS' /proc/meminfo
cat /proc/sys/vm/overcommit_memory
cat /proc/sys/vm/overcommit_ratio

# 结合 vmstat 看 si/so，持续非零通常意味着 swap 活动
vmstat 1 5
AI 节点建议： 是否禁用 swap 取决于平台策略；无论如何，训练/推理服务的 SLO 告警应关注 swap in/out、major fault、direct reclaim 和 OOM 事件，而不仅是 swap 使用量。

12. 容器和 cgroup 陷阱

在容器中读取 /proc/meminfo，常见结果仍是宿主机视角。因此，一个容器可能看到 MemTotal: 512 GiB，但 cgroup limit 只有 32 GiB。AI 平台排障时，必须把 meminfo 和 cgroup v1/v2 指标配对。

# cgroup v2 常见路径：容器内直接读当前 cgroup
cat /sys/fs/cgroup/memory.max 2>/dev/null
cat /sys/fs/cgroup/memory.current 2>/dev/null
cat /sys/fs/cgroup/memory.events 2>/dev/null
cat /sys/fs/cgroup/memory.stat 2>/dev/null | egrep 'anon|file|kernel|slab|shmem|pgfault|pgmajfault'

# cgroup v1 常见路径
cat /sys/fs/cgroup/memory/memory.limit_in_bytes 2>/dev/null
cat /sys/fs/cgroup/memory/memory.usage_in_bytes 2>/dev/null
cat /sys/fs/cgroup/memory/memory.stat 2>/dev/null | egrep 'rss|cache|mapped_file|pgfault|pgmajfault'
问题正确做法
容器内 MemAvailable 很高但进程 OOMKilled看 cgroup memory.max/memory.current/memory.events，不是宿主机 meminfo。
Pod 内 free -h 显示 512 GiB这是宿主机视角；调度和限额以 Kubernetes requests/limits/cgroup 为准。
file cache 被算进容器 usagecgroup 会记账 file cache，回收行为和宿主机全局 meminfo 不完全一致。
多容器共享节点互相影响同时看宿主机 MemAvailable 和每个 cgroup 的 memory.current/events。
容量判断红线： 容器里的 /proc/meminfo 不能单独用于判断“我还能申请多少内存”。必须读取 cgroup limit 和 current，否则会低估 OOMKilled 风险。

13. 解析 meminfo 的脚本方法

生产脚本要容错：字段可能缺失，单位可能固定为 kB 但仍应校验，读取时是快照但不保证和其他文件同一时刻。解析目标应是稳定输出，而不是依赖 head 行号。

Shell/AWK：快速巡检

awk '
  /^[A-Za-z_()]+:/ {
    key=$1; gsub(":","",key); mem[key]=$2
  }
  END {
    printf "total_gib      %.2f\n", mem["MemTotal"]/1024/1024
    printf "available_gib  %.2f\n", mem["MemAvailable"]/1024/1024
    printf "anon_gib       %.2f\n", mem["AnonPages"]/1024/1024
    printf "cache_gib      %.2f\n", mem["Cached"]/1024/1024
    printf "slab_gib       %.2f\n", mem["Slab"]/1024/1024
    printf "available_pct  %.1f\n", mem["MemAvailable"]/mem["MemTotal"]*100
  }
' /proc/meminfo

Python：稳定集成

#!/usr/bin/env python3
from pathlib import Path

def read_meminfo(path="/proc/meminfo"):
    out = {}
    for line in Path(path).read_text().splitlines():
        key, rest = line.split(":", 1)
        parts = rest.split()
        if not parts:
            continue
        value = int(parts[0])
        unit = parts[1] if len(parts) > 1 else ""
        out[key] = value * 1024 if unit == "kB" else value
    return out

mem = read_meminfo()
total = mem.get("MemTotal", 0)
available = mem.get("MemAvailable", 0)
print(f"available_gib={available / 2**30:.2f}")
print(f"available_pct={available / total * 100:.1f}" if total else "available_pct=unknown")
脚本建议： 把 meminfo 原始行和解析后数值都写入日志。事故复盘时，原始快照能避免解析脚本 bug 或字段兼容问题误导结论。

14. meminfo vs free/smaps/cgroups

free 的数据主要来自 meminfo，是人类可读摘要；/proc/<pid>/smaps 和 smaps_rollup 是进程级映射视角；cgroup 文件是容器/服务限额视角。AI Infra 排障要用它们互相补齐。

问题首选工具补充工具
节点是否快没内存了？/proc/meminfo 的 MemAvailablevmstat、dmesg、node exporter。
某个训练进程占多少？/proc/<pid>/smaps_rollupps、应用 profiler、allocator 指标。
Pod 为什么 OOMKilled？cgroup memory.events 与 memory.currentKubernetes events、container logs、meminfo。
缓存是否可回收？Cached、SReclaimable、MemAvailablevmtouch、slabtop、I/O 指标。
是不是 GPU 显存问题？不是 meminfonvidia-smi、DCGM、框架 CUDA memory summary。
# free 摘要
free -h

# meminfo 原始依据
cat /proc/meminfo | head

# 单进程汇总，更适合找“谁占了内存”
pid=12345
egrep 'Rss|Pss|Anonymous|Shared|Private|Locked' /proc/$pid/smaps_rollup

# 容器视角

15. AI Infra 排障工作流

内存事故排障不要从“清缓存”开始，而要先确定边界：是宿主机压力、容器 limit、单进程泄漏、内核不可回收增长、swap/reclaim 抖动，还是 GPU/驱动问题被误认为 CPU 内存问题。

判断路径

MemAvailable 低，AnonPages 高
优先查训练/推理进程、DataLoader、CPU offload、队列积压、内存泄漏、batch/concurrency。
MemAvailable 低，Cached 高
看是否能回收、是否有 shmem/tmpfs、是否发生 direct reclaim 和 I/O 抖动。
Slab/SUnreclaim 高
查 slabtop、文件系统/网络/驱动对象，注意内核版本和节点负载历史。
容器 OOM，但宿主机充足
看 cgroup limit、memory.events、应用峰值和 Kubernetes requests/limits。

16. 采集、告警与容量规划

meminfo 最适合进入节点级监控。单次 cat 只能帮助现场排查；长期时间序列才能回答“是否泄漏”“哪个版本引入增长”“高峰期 buffer 是否足够”。

指标推荐告警方向AI Infra 解释
MemAvailable / MemTotal低水位持续 N 分钟节点级 OOM、回收和延迟风险。
AnonPages 增速任务稳定后仍持续上升泄漏、缓存策略、队列堆积、allocator 碎片。
SUnreclaim 增速持续上升且不可解释内核/驱动/文件系统对象问题。
Shmem接近 tmpfs 或容器限制/dev/shm、Ray、DataLoader、共享缓存。
HugePages_Free长期大量空闲或不足预留浪费或应用无法获得大页。
Mlocked/Unevictable异常增长锁页、RDMA、pinned buffer 或特殊驱动行为。
# 每 10 秒采样一次关键字段，写 CSV
while sleep 10; do
  awk -v ts="$(date +%s)" '
    BEGIN {printf "%s", ts}
    /^(MemAvailable|AnonPages|Cached|Shmem|Slab|SUnreclaim|Mlocked|Unevictable):/ {
      printf ",%s=%s", $1, $2
    }
    END {print ""}
  ' /proc/meminfo
done > meminfo-sample.csv
容量规划建议： 对训练平台，记录任务启动期峰值、稳定期平台值、checkpoint 峰值、DataLoader worker 数和 batch size；用 P95/P99 峰值而不是平均值设节点余量。

17. 常见误区与检查清单

误区 1：MemFree 低就是缺内存
Linux 会积极使用内存做缓存；优先看 MemAvailable。
误区 2：Cached 高就是浪费
页缓存通常提升数据读取吞吐，是可回收资源的一部分。
误区 3：容器内 meminfo 等于容器可用内存
容器必须看 cgroup limit/current/events。
误区 4：meminfo 能解释 GPU 显存
GPU 显存看 DCGM/nvidia-smi，meminfo 是 CPU/内核内存视角。
误区 5：AnonPages 高一定是泄漏
也可能是正常工作集、CPU offload、缓存或预取队列。
误区 6：Slab 高一定要清理
先分清 SReclaimable 和 SUnreclaim，再用 slabtop 归因。
误区 7：drop_caches 是修复手段
它更像诊断手段，有全机副作用，不应自动化常规执行。
误区 8：单次快照能证明泄漏
泄漏需要时间序列和工作负载阶段信息。

上线前检查清单

  1. 节点监控是否采集 MemAvailable、AnonPages、Cached、Shmem、Slab、SUnreclaim、HugePages 和 cgroup 指标。
  2. 容器告警是否使用 cgroup，而不是容器内 free 或 /proc/meminfo 的宿主机总量。
  3. 训练任务是否记录 batch size、worker 数、prefetch、checkpoint 周期和内存峰值。
  4. 推理服务是否记录并发、模型版本、KV cache、CPU offload、pinned buffer 和 P99 延迟。
  5. OOM 事件是否保存 meminfo、cgroup events、进程 RSS 排名、dmesg 和应用日志。
