1. bpftrace 是什么

bpftrace 是 Linux 动态追踪工具，语法类似 awk：probe /filter/ { action }。它让你无需改业务代码、无需重启服务，就能观察内核路径和部分用户态函数的真实行为。

它擅长什么
临时诊断系统调用、I/O、网络、调度、锁等待、函数参数、延迟分布、调用栈和异常频率。
它不擅长什么
长期可观测平台、复杂控制流、大量字符串处理、稳定产品化 agent。此时更适合 bcc/libbpf/CO-RE 或专用监控系统。
AI Infra 价值
定位训练吞吐下降到底是数据读取、远端存储、网络、CPU 调度、NUMA、页缓存还是服务端依赖导致。
# 查看可用 tracepoint
sudo bpftrace -l 'tracepoint:syscalls:sys_enter_*' | head

# 每秒统计 openat 系统调用次数，按进程名聚合
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); } interval:s:1 { print(@); clear(@); }'

# 采样 CPU 栈，快速观察热点路径
sudo bpftrace -e 'profile:hz:99 { @[kstack] = count(); }'
边界提醒： bpftrace 是“现场显微镜”，不是默认长期常驻的监控 agent。先短时间、低频、窄范围运行，确认开销和输出量后再扩大。

信息图：bpftrace 的 eBPF 追踪心智模型

bpftrace 不是先验猜测工具，而是把“怀疑点”转化成可观测事件和聚合结果。

2. 安装、权限与内核支持

bpftrace 依赖内核 eBPF 能力、BPF 文件系统、调试符号或 BTF 类型信息。不同发行版和内核版本支持程度不同，生产机器尤其要先确认能力边界。

检查项命令说明
版本bpftrace --version记录工具版本，便于和线上问题绑定。
内核uname -a较新的内核通常提供更好的 BPF、BTF 和 tracepoint 支持。
BTFls -l /sys/kernel/btf/vmlinuxBTF 可让 args、结构体字段和 fentry 等体验更好。
tracefsmount | grep -E 'tracefs|debugfs'探针枚举和事件元数据常依赖 tracefs/debugfs。
权限sudo bpftrace -l 'tracepoint:syscalls:*' | head多数环境需要 root 或特定 BPF/perf capability。
# Ubuntu/Debian 常见安装
sudo apt-get update
sudo apt-get install -y bpftrace

# RHEL/CentOS/Fedora 常见安装
sudo dnf install -y bpftrace

# 快速自检：能否列出探针
sudo bpftrace -l 'tracepoint:sched:*' | head
权限警告： 不要为了方便给普通用户长期开放无限 BPF 能力。bpftrace 可观察内核与进程行为，权限模型应按运维边界、审计要求和主机隔离策略设计。

3. 基本语法与运行方式

bpftrace 脚本的基本形式是：匹配某个探针事件，满足过滤条件时执行动作。动作通常不是逐行打印，而是写入 map 做聚合，然后定时输出。

# 基本形式
probe /predicate/ { action }

# 直接执行一段脚本
sudo bpftrace -e 'BEGIN { printf("start\n"); } interval:s:1 { printf("tick\n"); }'

# 使用脚本文件
cat > io.bt <<'BT'
tracepoint:syscalls:sys_enter_read
{
  @[comm] = count();
}
interval:s:5
{
  print(@);
  clear(@);
}
BT
sudo bpftrace io.bt
语法元素含义例子
probe事件来源tracepoint:syscalls:sys_enter_read
/predicate/过滤条件/pid == 1234/
@map跨事件聚合状态@[comm] = count()
interval定时输出interval:s:1 { print(@); }
写法建议： 交互诊断用 -e，可复用诊断脚本写成 .bt 文件，并把采样窗口、过滤条件和退出条件写清楚。

4. 探针类型：kprobe、tracepoint、uprobe、profile

选择探针就是选择观察边界。稳定性优先时用 tracepoint；需要函数级细节时用 kprobe/uprobe；看 CPU 热点时用 profile；看周期性状态时用 interval。

探针观察对象稳定性典型用途
tracepoint内核预定义事件较稳定系统调用、调度、块 I/O、网络事件。
kprobe/kretprobe内核函数入口/返回受内核版本影响函数参数、返回值、精细路径。
uprobe/uretprobe用户态二进制或库函数受符号和版本影响libc、Python/C++ 扩展、服务进程函数。
profile固定频率采样适合低侵入热点分析CPU 火焰图前的粗看、热点栈聚合。
interval时间定时器稳定周期输出、清空 map、限时退出。
# 列出某类探针
sudo bpftrace -l 'tracepoint:block:*'
sudo bpftrace -l 'kprobe:vfs_*'
sudo bpftrace -l 'uprobe:/usr/bin/python3:*PyEval*'

# tracepoint 参数通常可用 args 查看
sudo bpftrace -lv 'tracepoint:syscalls:sys_enter_openat'
选择顺序： 能用 tracepoint 就先用 tracepoint；需要更深内部细节再上 kprobe；需要业务库函数才用 uprobe；需要全局热点先用 profile。

流程图：从症状选择 bpftrace 探针

探针选择从问题边界开始，不从“我会哪个 one-liner”开始。

5. 内置变量、参数与过滤条件

bpftrace 的常用内置变量能帮助你把事件归属到进程、线程、CPU、时间和栈。过滤条件越早越窄，输出越可控，生产风险越低。

变量/函数用途例子
pid/tid进程 ID / 线程 ID/pid == 4242/
comm进程名/comm == "python"/
cpu当前 CPU@[cpu] = count()
nsecs单调纳秒时间计算开始到返回的延迟。
argstracepoint/fentry 参数args->fd、args->filename
arg0 等kprobe/uprobe 原始参数依 ABI 和函数签名解读。
kstack/ustack内核/用户调用栈热点或阻塞路径聚合。
# 只观察某个训练进程
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_read /pid == 4242/ { @[comm] = count(); }'

# 只观察 python 进程的 openat 文件名
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat /comm == "python"/ { printf("%s\n", str(args->filename)); }'

# 用环境变量传入目标 PID，便于脚本化
TARGET=4242
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_write /pid == '$TARGET'/ { @writes = count(); } interval:s:1 { print(@writes); clear(@writes); }'
字符串提醒： 打印字符串、路径和调用栈通常比计数更贵；先用 count()、hist() 看趋势，再按需打印少量样本。

6. maps、聚合、直方图与 interval 输出

bpftrace 的核心不是不停 printf，而是把高频事件汇总进 map，然后按时间窗口输出。AI Infra 诊断通常需要 p50/p95/p99 级别的延迟分布，而不是几行日志。

聚合含义适用场景
count()次数按进程统计系统调用频率。
sum(x)求和累计字节数、累计耗时。
avg(x)平均值低频事件的粗略均值。
min(x)/max(x)极值快速发现异常上界。
hist(x)2 的幂桶直方图I/O、网络、调度延迟分布。
lhist(x,min,max,step)线性桶直方图固定范围内的细粒度延迟。
# read 系统调用返回延迟直方图，单位微秒
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_read
{
  @start[tid] = nsecs;
}
tracepoint:syscalls:sys_exit_read
/@start[tid]/
{
  @read_us[comm] = hist((nsecs - @start[tid]) / 1000);
  delete(@start[tid]);
}
interval:s:10
{
  print(@read_us);
  clear(@read_us);
}'
聚合优先： 在线上机器上，@latency = hist(...) 通常比每次事件 printf 安全得多。

7. 常用 one-liners

one-liner 适合快速确认方向。真正复杂的诊断应升级为 .bt 脚本，添加过滤、输出窗口和退出条件。

按进程统计 syscall
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); } interval:s:5 { print(@); clear(@); }'
观察打开文件
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat /comm == "python"/ { printf("%s %s\n", comm, str(args->filename)); }'
CPU 采样热点
sudo bpftrace -e 'profile:hz:99 { @[comm, kstack] = count(); }'
按进程统计 read 字节
sudo bpftrace -e 'tracepoint:syscalls:sys_exit_read /args->ret > 0/ { @[comm] = sum(args->ret); } interval:s:5 { print(@); clear(@); }'
# 限时运行 30 秒后自动退出
sudo bpftrace -e 'BEGIN { printf("sampling 30s\n"); } tracepoint:sched:sched_switch { @ = count(); } interval:s:30 { print(@); exit(); }'
复制前先改过滤条件： 任何包含 printf、ustack、kstack 或高频探针的 one-liner，都应先加 /pid == .../ 或 /comm == "..."/。

8. 系统调用追踪

系统调用是用户态进入内核的边界。AI 训练中，频繁的 openat、read、pread64、statx、futex、sendto、recvfrom 往往能解释 dataloader、远端存储或 RPC 客户端瓶颈。

# 按进程名统计 openat 次数
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_openat
{
  @[comm] = count();
}
interval:s:5 { print(@); clear(@); }'

# 观察某 PID 的失败 openat
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_openat /pid == 4242/
{
  @file[tid] = str(args->filename);
}
tracepoint:syscalls:sys_exit_openat /@file[tid]/
{
  if (args->ret < 0) {
    printf("%s ret=%d file=%s\n", comm, args->ret, @file[tid]);
  }
  delete(@file[tid]);
}'
现象优先观察可能解释
GPU 空转，CPU 不高read/pread64 延迟直方图数据读取慢、页缓存未命中、远端存储抖动。
worker 数量增加但吞吐不升futex、sched_switch锁竞争、队列阻塞、Python 多进程协调开销。
启动慢openat、statx、mmap小文件过多、模型权重加载路径慢。
方法： 用 enter 事件记录 nsecs，用 exit 事件计算延迟，用 tid 做关联键，结束后 delete() 防止 map 膨胀。

9. 块设备与文件 I/O 延迟

训练数据读取慢可能发生在 Python、文件系统、页缓存、块层、网络文件系统或对象存储网关。bpftrace 可以从 syscall 和 block tracepoint 两端夹逼定位。

# 块 I/O 请求耗时分布，单位毫秒
sudo bpftrace -e '
tracepoint:block:block_rq_issue
{
  @start[args->dev, args->sector] = nsecs;
}
tracepoint:block:block_rq_complete
/@start[args->dev, args->sector]/
{
  @block_ms[args->dev] = hist((nsecs - @start[args->dev, args->sector]) / 1000000);
  delete(@start[args->dev, args->sector]);
}
interval:s:10
{
  print(@block_ms);
  clear(@block_ms);
}'
syscall 慢，block 不慢
可能卡在文件系统、锁、页缓存、网络 FS 客户端或用户态解码。
block 慢
优先看设备队列、云盘抖动、并发读写、IO 调度和容器共享。
open/stat 很多
数据集小文件过多，dataloader metadata 开销可能高于实际读取。
# 按进程统计 read/pread64 字节量，判断是否真的在读数据
sudo bpftrace -e '
tracepoint:syscalls:sys_exit_read /args->ret > 0/ { @[comm] = sum(args->ret); }
tracepoint:syscalls:sys_exit_pread64 /args->ret > 0/ { @[comm] = sum(args->ret); }
interval:s:5 { print(@); clear(@); }'
设备字段提醒： 不同内核的 block tracepoint 参数可能有差异，先用 bpftrace -lv 'tracepoint:block:block_rq_complete' 查看本机字段。

10. 网络延迟与连接诊断

AI Infra 中网络瓶颈可能来自数据服务、对象存储、参数服务器、Ray/分布式训练控制面、NCCL 周边服务或远端文件系统。bpftrace 可用于快速观察连接、重传、收发调用和内核 TCP 路径。

# 统计 connect 系统调用返回延迟，单位毫秒
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_connect
{
  @start[tid] = nsecs;
}
tracepoint:syscalls:sys_exit_connect
/@start[tid]/
{
  @connect_ms[comm] = hist((nsecs - @start[tid]) / 1000000);
  delete(@start[tid]);
}
interval:s:10 { print(@connect_ms); clear(@connect_ms); }'

# TCP 重传事件计数，事件名依内核而异，先 bpftrace -l 查询
sudo bpftrace -e 'tracepoint:tcp:tcp_retransmit_skb { @[comm] = count(); } interval:s:5 { print(@); clear(@); }'
问题观察点下一步
远端数据服务慢connect、sendto、recvfrom 延迟按目标服务端口、PID、进程名缩小。
吞吐偶发下降TCP 重传、拥塞窗口相关 tracepoint/kprobe结合 ss -ti、网卡错误、交换机侧指标。
多机训练 hang系统调用阻塞、futex、网络发送接收频率确认卡在通信库、数据源还是进程同步。
网络诊断原则： bpftrace 给你主机侧证据；跨机问题还要和服务端日志、流量指标、队列长度、DNS、LB 和安全组配置一起看。

用例图：AI dataloader/IO/网络延迟定位路径

AI 训练“慢”经常是多层叠加。bpftrace 的价值是快速确定下一步应该找存储、网络、调度还是应用代码。

11. AI dataloader 与训练吞吐诊断

训练吞吐下降时，先把目标进程或 worker PID 找出来，再观察数据路径。常见目标包括 torchrun 主进程、PyTorch dataloader worker、预处理服务、缓存代理和远端存储客户端。

# 找出 python/torchrun 进程
pgrep -af 'python|torchrun'

# 针对单个 PID 观察 read 延迟，单位微秒
TARGET=4242
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_read /pid == '$TARGET'/ { @s[tid] = nsecs; }
tracepoint:syscalls:sys_exit_read /@s[tid]/ {
  @read_us = hist((nsecs - @s[tid]) / 1000);
  delete(@s[tid]);
}
interval:s:10 { print(@read_us); clear(@read_us); }'

# 观察是否频繁访问小文件元数据
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat /comm == "python"/ { @[str(args->filename)] = count(); } interval:s:10 { print(@, 20); clear(@); }'
诊断问题bpftrace 证据可能改进
小文件数据集拖慢openat/statx 高频，单次读很小打包样本、缓存 metadata、增加预取、减少随机小文件。
远端存储抖动read p99 高但 CPU 低，网络重传或 connect 慢本地缓存、并发限制、服务端扩容、网络排障。
worker 被调度延迟sched_switch 或 off-CPU 栈显示等待CPU 亲和、worker 数量、容器 CPU quota、NUMA 策略。
预处理 CPU 热点profile:hz 用户栈集中在解码/增强函数更快编解码、离线预处理、向量化、增大缓存。
路径打印风险： 按文件名聚合可能产生大量 map key，并暴露敏感路径。生产中优先按进程、扩展名、目录前缀抽样，或只在短窗口内打印 top N。

12. CPU 调度、off-CPU 与锁等待

当 GPU 等数据、服务吞吐不稳定或多进程 pipeline 卡住时，问题未必在 I/O。CPU 调度延迟、锁等待、futex、线程池耗尽也很常见。

# 按进程统计上下文切换次数
sudo bpftrace -e 'tracepoint:sched:sched_switch { @[args->prev_comm, args->next_comm] = count(); } interval:s:5 { print(@, 20); clear(@); }'

# futex 调用延迟，常用于观察锁/条件变量等待
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_futex /comm == "python"/ { @s[tid] = nsecs; }
tracepoint:syscalls:sys_exit_futex /@s[tid]/ {
  @futex_us = hist((nsecs - @s[tid]) / 1000);
  delete(@s[tid]);
}
interval:s:10 { print(@futex_us); clear(@futex_us); }'
run queue 延迟
进程可运行但迟迟没有上 CPU，常见于 CPU quota、过度超卖或绑核不当。
futex 等待
常见于队列空、锁竞争、Python worker 同步或 C++ 线程池阻塞。
off-CPU 栈
用于判断线程睡在哪里；开销更高，应短时间并按 PID 限制。
实践建议： 不要只看 CPU 利用率。训练慢但 CPU 不高，可能是线程睡眠；CPU 高但吞吐低，可能是解码、压缩、数据增强或锁竞争。

13. 用户态追踪：Python、libc 与 CUDA 周边

uprobe 可以挂到用户态 ELF 符号，例如 libc、Python 解释器、C++ 服务或本地扩展库。它适合观察库函数边界，但依赖符号、路径、编译方式和版本。

# 找 libc 路径
ldd /usr/bin/python3 | grep libc

# 列出某二进制/库的可用符号，实际数量可能很大
sudo bpftrace -l 'uprobe:/usr/bin/python3:*Py*' | head

# 观察 libc malloc 调用次数，先限制目标进程
TARGET=4242
LIBC=/usr/lib/x86_64-linux-gnu/libc.so.6
sudo bpftrace -e 'uprobe:'$LIBC':malloc /pid == '$TARGET'/ { @malloc = count(); } interval:s:5 { print(@malloc); clear(@malloc); }'
场景用法注意
Python 解释器边界挂 python 符号或用 USDT（如果程序暴露）不同 Python 构建符号差异大。
C/C++ 扩展挂扩展 .so 的函数符号函数可能被内联或去符号。
CUDA/NCCL 周边观察用户态库函数入口/返回符号、动态加载和版本路径要先确认；GPU 内部事件不等同于内核 eBPF 事件。
用户栈提醒： ustack 需要合适的符号和 unwind 条件。容器、JIT、帧指针省略、 stripped binary 都可能导致栈不完整。

14. 生产安全、开销与降级策略

bpftrace 虽然受内核验证器约束，但不是零成本。高频探针、字符串读取、调用栈采集、未清理 map、无界输出都会影响生产机器。

风险危险写法安全替代
输出风暴在高频事件中 printf用 count()/hist() 聚合后 interval 输出。
范围过大全系统追踪所有 syscall按 pid、comm、cgroup、端口或设备过滤。
map 膨胀以完整路径、请求 ID、随机字符串做 key限制窗口、top N 输出、及时 clear()/delete()。
符号不稳定生产长期依赖 kprobe 内核函数名优先 tracepoint；长期化用 bcc/libbpf 并做版本适配。
栈采集开销高频事件全量 ustack/kstack降低频率，短窗口，先 profile，再按 PID 深挖。
# 推荐：限时、窄范围、聚合输出
TARGET=4242
sudo timeout 30s bpftrace -e '
tracepoint:syscalls:sys_enter_read /pid == '$TARGET'/ { @s[tid] = nsecs; }
tracepoint:syscalls:sys_exit_read /@s[tid]/ {
  @lat = hist((nsecs - @s[tid]) / 1000);
  delete(@s[tid]);
}
interval:s:10 { print(@lat); clear(@lat); }'
生产底线： 首次在关键机器运行脚本前，先在同内核测试机验证；线上使用 timeout、过滤条件和聚合；不要把探索脚本直接做成守护进程。

安全图：生产运行 bpftrace 的控制面

安全不是一句“bpftrace 很轻量”，而是每个脚本都要有可控范围、可控输出和明确退出。

15. bpftrace vs bcc vs perf vs strace

这些工具不是替代关系，而是不同层级的诊断入口。选错工具会浪费时间，也可能带来不必要开销。

工具优势劣势适合场景
bpftrace脚本短、动态追踪快、聚合表达力强复杂程序化能力弱，长期化不如 libbpf/bcc现场假设验证、延迟直方图、函数/事件聚合。
bccPython/C++ 生态，工具丰富，可写更复杂逻辑部署依赖更重，脚本开发成本更高更复杂的 eBPF 工具、长期诊断脚本。
perfCPU 性能分析强，采样、硬件事件、火焰图生态成熟对任意参数和事件聚合不如 bpftrace 灵活CPU 热点、硬件计数器、性能剖析。
strace系统调用语义直观，容易上手ptrace 开销高，可能明显扰动进程低频进程、功能排错、快速确认 syscall 行为。
ftrace内核自带，函数追踪能力强交互和聚合便利性较弱内核函数路径、低层追踪。
先用 bpftrace
当你要回答“这个事件多久一次、慢在哪里、按谁聚合”时，bpftrace 通常最快。
切到 perf
当问题变成 CPU 指令级热点、PMU 事件、火焰图剖析时，perf 更合适。
切到 strace
当你只需要看一个低频命令具体调用了哪些 syscall，strace 更直观。
切到 bcc/libbpf
当脚本要长期运行、产品化、跨内核版本稳定交付时，bpftrace 只是原型。

16. 常见错误与排障

错误 1：找不到探针
先用 bpftrace -l 查本机名称；tracepoint、内核函数和库符号都可能因版本不同而变化。
错误 2：字段不存在
用 bpftrace -lv 'tracepoint:...' 查看 args 字段，不要复制其他内核上的字段名。
错误 3：permission denied
确认 root/capability、lockdown、安全模块、容器特权和 tracefs/debugfs 挂载。
错误 4：BTF 不可用
安装内核调试包或调整脚本，避免依赖本机缺失的类型信息。
错误 5：输出太多
立即中断，增加过滤条件，改成 map 聚合和 interval 输出。
错误 6：栈不完整
检查符号、帧指针、JIT、容器路径映射和二进制是否 stripped。
错误 7：脚本编译失败
简化为最小脚本，逐步加字段、过滤和 map；先验证 probe 是否可用。
错误 8：线上开销异常
停止脚本，改用低频采样、短窗口、聚合输出或在测试机复现。

排障模板

# 1. 先确认探针存在
sudo bpftrace -l 'tracepoint:syscalls:sys_enter_openat'

# 2. 查看字段
sudo bpftrace -lv 'tracepoint:syscalls:sys_enter_openat'

# 3. 最小脚本验证事件是否触发
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @ = count(); } interval:s:1 { print(@); clear(@); }'

# 4. 再加过滤条件和字段
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat /comm == "python"/ { @[comm] = count(); }'

# 5. 最后加延迟计算、直方图或栈

排障流程图：bpftrace 脚本不工作时怎么查

排障顺序固定：探针名 → 字段 → 权限 → 事件是否触发 → 过滤条件 → 聚合逻辑。

17. 练习路线与可复用脚本

第一阶段：会观察

  • 会用 bpftrace -l 和 -lv 找 probe 与字段。
  • 会写 probe { @[comm] = count(); } 统计事件频率。
  • 会用 interval 周期输出并 clear() map。

第二阶段：会定位

  • 掌握 enter/exit 事件用 tid 关联并计算延迟。
  • 掌握 hist() 和 lhist() 看延迟分布。
  • 能按 PID、进程名、设备、端口把观察范围收窄。

第三阶段：会生产化

  • 所有脚本都有采样窗口、过滤条件和输出上限。
  • 优先 tracepoint，谨慎使用高频 kprobe/uprobe 和栈采集。
  • 把有效的一次性脚本沉淀为可审计、可回滚、可版本化的诊断工具。
# 练习：在测试机上制造少量 I/O，再用 bpftrace 观察
dd if=/dev/zero of=/tmp/bpftrace-demo.bin bs=1M count=128 oflag=direct

# 另一个终端运行：按进程观察 read/write
sudo bpftrace -e '
tracepoint:syscalls:sys_exit_read /args->ret > 0/ { @[comm, "read"] = sum(args->ret); }
tracepoint:syscalls:sys_exit_write /args->ret > 0/ { @[comm, "write"] = sum(args->ret); }
interval:s:2 { print(@); clear(@); }'
练习安全： I/O 练习放在测试机或临时目录，不要对生产数据盘制造压力；需要直接 I/O 时确认文件系统和权限。
