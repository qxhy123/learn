dcgmi 深度教程：AI Infra 中的 NVIDIA DCGM 运维、诊断与观测

这份教程面向 GPU 集群、训练平台、推理平台和 HPC/AI Infra 运维人员。它从 dcgmi 的心智模型讲起：dcgmi 是 NVIDIA DCGM 的命令行客户端，通过 nv-hostengine 管理 GPU 分组、发现、健康检查、诊断、字段采样、作业统计和与 Prometheus/dcgm-exporter 的观测链路。重点覆盖发现 GPU、健康巡检、诊断等级、field group、profiling 指标、ECC/XID 诊断、集群 burn-in、生产安全、与 nvidia-smi 的边界以及排障流程。

一句话理解： dcgmi 不是另一个简单版 nvidia-smi；它是 DCGM 控制面的 CLI，适合把 GPU 生命周期管理、诊断、健康状态和集群观测纳入自动化流程。

1. dcgmi 是什么

dcgmi 是 NVIDIA Data Center GPU Manager（DCGM）的命令行接口。它面向“节点和集群运维”，而不是单次人工查看 GPU。AI Infra 中常见的使用场景包括：节点上线前验收、GPU 异常定位、训练作业资源统计、Prometheus 指标校验、MIG 设备观测、ECC/XID 告警复盘，以及故障 GPU 的隔离决策。

控制对象
GPU、MIG 实体、GPU group、field group、健康监控、诊断任务、作业统计窗口。
运行方式
dcgmi 通常连接本机或远端的 nv-hostengine，由 hostengine 与驱动/NVML/DCGM 库交互。
运维价值
把“看一眼 GPU”升级为“可脚本化、可分组、可观测、可验收、可排障”的 GPU 管理流程。
# 看 dcgmi 是否可用
dcgmi --help
dcgmi version

# 最小只读巡检：不改变 GPU 状态
dcgmi discovery -l
dcgmi group -l
dcgmi health -c
边界提醒： 诊断、压力测试、策略修改、配置修改都可能影响运行中的训练或推理。本文所有涉及高侵入操作的例子都先给出只读检查或窗口化建议。

信息图：dcgmi 在 AI Infra 观测链路中的位置

同一个 DCGM 后端可以服务 dcgmi 命令和 dcgm-exporter。生产中要注意版本兼容和 hostengine 的单实例/远端连接方式。

2. 安装、权限与服务检查

不同发行版、DGX 镜像、GPU Operator 和容器环境安装方式不同，但排障入口基本一致：确认驱动、确认 DCGM 包、确认 nv-hostengine 服务、确认当前用户是否有足够权限访问 GPU。

检查项命令判断
驱动可见nvidia-smi能列出 GPU、驱动版本、CUDA 版本。
dcgmi 可见command -v dcgmi && dcgmi version能输出 DCGM 组件版本。
hostenginesystemctl status nvidia-dcgm服务运行，或由 dcgmi/exporter 按需启动。
容器权限docker run --gpus all ...容器内能看到 GPU，并有必要的 capability/挂载。
# 主机上常用检查
nvidia-smi
dcgmi version
systemctl status nvidia-dcgm --no-pager
ps -ef | grep -E 'nv-hostengine|dcgm' | grep -v grep

# 若服务未启动，生产环境先确认节点是否正在服务业务
sudo systemctl start nvidia-dcgm
dcgmi discovery -l
容器提示： dcgm-exporter 容器可能内置 DCGM client library 并连接主机或独立容器中的 nv-hostengine。版本不匹配时会出现“hostengine 可达但指标异常”的灰色故障。

3. 第一批安全只读命令

刚接触一台 GPU 节点时，先跑只读命令。不要一上来做压力诊断、重置、配置变更或清空计数器。

节点入口巡检 
hostname
nvidia-smi -L
dcgmi discovery -l
dcgmi health -c
dcgmi fieldgroup -l
轻量采样 5 次 
# 字段 ID 会随需求选择；这里演示温度、功耗、XID 等常见观测
dcgmi dmon -e 150,155,156,230,319 -c 5

# 如果版本支持按间隔控制，可先看帮助
dcgmi dmon --help
命令风险用途
dcgmi discovery -l低列出 active GPU 的 ID、名称、PCI Bus ID、UUID。
dcgmi discovery -l -a低同时显示 inactive、detached、lost、inaccessible 设备。
dcgmi health -c低查看已启用 watch 的健康状态。
dcgmi dmon ...低到中流式读取指标；高频采样会增加少量管理面压力。
dcgmi diag -r 2/3/4高会运行诊断/压力任务，通常需要独占 GPU。
团队约定： 在 runbook 里把命令分成“只读安全”“需变更窗口”“需下线节点”三类，避免值班人员误伤在线业务。

4. GPU 发现：active、all、MIG 与实体

dcgmi discovery 是进入 DCGM 世界的第一步。AI 集群中，“GPU 不在 active 列表里”本身就是重要信号：可能是驱动故障、设备丢失、MIG 配置变化、权限问题或硬件不可达。

# 只显示 active GPU
dcgmi discovery -l

# 显示所有 GPU，包括 inactive/detached/lost/inaccessible
dcgmi discovery -l -a

# 查看 CPU/GPU/MIG 等实体枚举能力，具体输出取决于 DCGM 版本和硬件
dcgmi discovery -c

# 查询 workload power profile 支持情况，若硬件/版本支持
dcgmi discovery -i w
观察项为什么重要下一步
GPU ID后续 group、diag、dmon 常用的本地编号。记录到节点资产信息，不要跨节点假设 ID 稳定。
PCI Bus ID定位拓扑、NUMA、NVLink、故障槽位。和 nvidia-smi topo -m、BMC/资产系统交叉验证。
UUID跨重启和跨调度系统更稳定。Kubernetes/Slurm 事件中优先保存 UUID。
inactive 状态DETACHED/LOST/INACCESSIBLE 往往需要下线排查。查内核日志、XID、驱动、硬件链路。
MIG 注意： MIG 设备会引入 GPU Instance/Compute Instance 粒度。监控和调度系统需要明确看的是整卡指标还是 MIG 实例指标，否则利用率解释会偏差。

5. Group：把 GPU 变成可管理对象

DCGM 的很多操作围绕 group 展开。group 可以代表整机、一个训练作业占用的 GPU 集合、某个机架的测试对象，或 MIG 实体集合。把 group 建好，后续 health、diag、stats、dmon 就能复用同一组目标。

# 创建一个 GPU group
dcgmi group -c train-node-gpus

# 查看 group
dcgmi group -l

# 把 GPU 0,1 加入 group 1
dcgmi group -g 1 -a 0,1

# 查看 group 详情
dcgmi group -g 1 -i

# 删除临时 group：先确认 ID，再删除
dcgmi group -l
dcgmi group -d 1
全节点 group
适合节点健康巡检、burn-in、整机验收。
作业 group
适合 Slurm prologue/epilogue 记录作业级 GPU 统计。
MIG group
适合隔离不同 GPU Instance 的指标解释与告警。
删除提醒： 删除 group 前先确认没有自动化脚本依赖该 group ID。更稳妥的做法是在脚本里按名称创建临时 group，结束后清理。

流程图：健康检查与诊断的安全决策

后台健康 watch 可用于持续发现风险；主动诊断会运行真实 workload 或压力测试，必须考虑业务影响。

6. Health：后台健康 watch 与快速巡检

dcgmi health 用来设置和查询 DCGM 的后台健康监控。常见 watch 包括 PCIe、Memory、InfoROM、Thermal/Power、NVLink，以及 all。健康检查适合纳入节点日检、作业前检查和告警回看。

Watch flag关注范围典型风险
pPCIePCIe replay、链路质量、插槽/主板/线缆问题。
mMemoryECC、显存错误、不可纠正错误。
iInfoROMInfoROM 损坏或不可读。
tThermal/Power温度、功耗、降频、散热问题。
nNVLinkNVLink 链路错误、拓扑异常。
aAll启用全部健康 watch。
# 对 group 1 启用 PCIe + Memory + InfoROM watch
dcgmi health -g 1 -s pmi

# 查询 group 1 当前健康
dcgmi health -g 1 -c

# 启用全量 watch，适合测试/验收窗口
dcgmi health -g 1 -s a
dcgmi health -g 1 -c
结果解释： Health 的 Warning 不等于马上宕机，但它给出“需要调查”的方向。Fatal/Error 类结果通常应触发作业终止、节点隔离或 GPU 深入诊断。

7. Diagnostics：从 quick 到 extended 的诊断等级

dcgmi diag 是 DCGM Diagnostics 的入口。NVIDIA 文档将 NVVS 能力整合到 dcgmi 中。诊断等级越高，覆盖越深、耗时越长、侵入性越强。生产中应把它放进维护窗口、节点上线验收、故障复现和 RMA 证据采集流程。

命令形态用途建议场景
dcgmi diag -r 1快速部署/软件类检查。作业前轻量检查、新节点基础验证。
dcgmi diag -r 2中等诊断，通常更适合短维护窗口。疑似问题复核、上线前抽检。
dcgmi diag -r 3更长的系统验证。节点验收、故障节点下线后检查。
dcgmi diag -r 4扩展诊断，可能包含更长压力项。burn-in、硬件验收、深度故障定位。
dcgmi diag -r pcie,diagnostic按测试名运行指定项。已知方向明确时减少不必要压力。
# 先确认 GPU 和业务状态
dcgmi discovery -l
nvidia-smi

# 只对 GPU 0,1 运行 quick 级别诊断
dcgmi diag -r 1 -i 0,1

# 对 group 1 运行中等诊断，建议在维护窗口
dcgmi diag -r 2 -g 1 -v

# 指定测试名，聚焦 PCIe/diagnostic
dcgmi diag -r pcie,diagnostic -i 0

# 查看当前版本支持哪些参数和测试
dcgmi diag --help
高侵入警告： diag 可能需要 GPU 独占并运行真实 workload。在线推理、训练、共享 HPC 节点上先迁移/停止业务，再运行高等级诊断。

8. Field 与 Field Group：DCGM 指标字典

DCGM 把大量 GPU 状态抽象为 field，例如温度、功耗、显存、XID、PCIe replay、SM 活跃度、Tensor Core 活跃度等。field group 是一组字段的集合，便于统一 watch 和查询。dcgmi fieldgroup -l 可以查看系统已有 field group。

# 查看已有 field group
dcgmi fieldgroup -l

# 查看 field 相关帮助，确认本版本支持的创建/删除/查看语法
dcgmi fieldgroup --help
dcgmi dmon --help
指标类别例子AI Infra 用途
设备状态温度、功耗、显存使用、时钟容量、散热、功耗墙、资源利用率。
RAS/错误ECC、XID、PCIe replay、NVLink error故障预警、节点隔离、硬件质量复盘。
ProfilingGraphics/SM activity、Tensor active、DRAM active、PCIe bytes判断训练瓶颈：算力、显存带宽、通信或数据输入。
作业统计能耗、最大显存、平均功耗、平均利用率成本核算、队列公平性、模型优化反馈。
字段 ID 提醒： 线上脚本不要盲目复制不明来源的 field ID。优先用当前 DCGM 版本的帮助、官方字段说明和 exporter metrics CSV 校验字段含义。

信息图：从 DCGM Field 到 Prometheus 指标

同一个 field 可以在 dcgmi dmon 中临时查看，也可以由 dcgm-exporter 暴露为 Prometheus 指标。

9. dmon：流式采样与 profiling 指标

dcgmi dmon 适合排障现场临时观察。和 watch nvidia-smi 相比，它能按 DCGM field 精确采样，也能查看 profiling 指标，例如 SM/Graphics 活跃度、Tensor Core 活跃度、DRAM 活跃度、PCIe 收发字节等。

# 查看当前版本 dmon 支持的参数
dcgmi dmon --help

# 采样指定字段，输出 10 次后退出
dcgmi dmon -e 1001,1004,1005 -c 10

# 只观察 group 1
dcgmi dmon -g 1 -e 1001,1004,1005

# MIG/实体场景：按当前版本帮助使用 --entity-id
dcgmi dmon --entity-id gpu:0 -e 1001,1004 -c 5
观测现象可能解释下一步
SM 活跃高，DRAM 活跃高训练计算与显存带宽都忙。结合 batch size、kernel、通信指标分析。
SM 活跃低，显存占用高作业占卡但没算，可能卡在数据加载/通信/同步。查 dataloader、NCCL、CPU、网络、存储。
Tensor active 低未充分使用 Tensor Core 或模型/精度不匹配。检查 AMP/BF16/FP16、算子融合、框架配置。
PCIe/NVLink 错误增加链路质量或拓扑问题。转入硬件/拓扑/XID 排查。
采样频率： NVIDIA 文档说明 DCGM profiling 指标默认可按 1Hz 采样，部分场景可配置更高频率。高频采样应限制在排障窗口，避免把观测本身变成噪声。

10. ECC、PCIe、NVLink 与 XID 诊断

AI 集群中最常见的 GPU 硬件/驱动类告警通常围绕 ECC、XID、PCIe replay、NVLink error、温度/功耗降频展开。dcgmi 的价值是把这些信号放到健康检查、字段采样和诊断流程里，而不是只看一条孤立日志。

现场证据采集 
date -Is
hostname
nvidia-smi -q -x > nvidia-smi-query.xml
dcgmi discovery -l -a
dcgmi health -c
dcgmi dmon -e 230,319 -c 5
dmesg -T | grep -i xid | tail -50
隔离后深入诊断 
# 先确认没有作业
nvidia-smi

# 针对异常 GPU 做诊断
dcgmi diag -r 2 -i 0 -v
dcgmi diag -r pcie,diagnostic -i 0 -v
信号含义处置倾向
XIDNVIDIA 驱动报告的 GPU 错误事件。结合 XID 码、作业、内核日志、DCGM health 判断是否隔离。
ECC correctable可纠正显存错误。少量可观察；持续增长需隔离、复测、供应商支持。
ECC uncorrectable不可纠正显存错误。通常高严重度，优先保护作业正确性并下线诊断。
PCIe replayPCIe 传输重试。持续高值可能是链路/插槽/主板/线缆风险。
NVLink errorGPU 间高速链路错误。影响多卡训练通信稳定性，需结合拓扑和 NCCL 错误。
正确性优先： 对训练平台而言，不可纠正 ECC、反复 XID、GPU reset、NCCL 异常后的继续训练可能污染 checkpoint 或浪费大量算力。自动化应优先隔离并保留证据。

11. 作业统计：训练平台的 prologue/epilogue

dcgmi stats 可以在作业级别记录 GPU 使用情况。调度系统可以在 prologue 开始记录，在 epilogue 停止并导出统计，为计费、资源画像、异常作业识别和容量规划提供依据。

# 初始化：对 group 1 启用 process watches
dcgmi stats -g 1 --enable

# 作业开始：用调度系统的 job id 开始记录
JOB_ID="train-20260425-001"
dcgmi stats -g 1 -s "$JOB_ID"

# 作业结束：停止记录
dcgmi stats -x "$JOB_ID"

# 查询统计，-v 输出更多细节
dcgmi stats -j "$JOB_ID" -v
统计项平台价值
执行时长、最大显存识别 over-request/under-request，优化队列配额。
平均/峰值功耗、能耗成本核算、PUE/能耗优化、机房功率规划。
SM/Memory utilization判断作业是否有效使用 GPU，发现数据加载瓶颈。
冲突进程发现共享节点隔离问题或残留进程。
时序要求： 可靠统计需要在目标 workload 启动前启用记录，并在结束后由 epilogue 拉取。只在事后运行命令通常无法重建完整窗口。

12. Prometheus 与 dcgm-exporter 的关系

dcgmi 是面向人和脚本的 CLI；dcgm-exporter 是面向监控系统的常驻 exporter。它基于 DCGM API 收集 GPU 指标，并通过 HTTP /metrics 暴露给 Prometheus。生产中常见架构是每个 GPU 节点运行 dcgm-exporter，Prometheus 按节点抓取，Grafana 展示，Alertmanager 告警。

# 临时确认 exporter 是否暴露指标
curl -s http://127.0.0.1:9400/metrics | grep -E 'DCGM_FI_DEV_GPU_TEMP|DCGM_FI_DEV_XID_ERRORS' | head

# dcgmi 与 exporter 交叉验证
dcgmi discovery -l
dcgmi dmon -e 150,155,230,319 -c 3

# Kubernetes 中查看 daemonset/pod，名称取决于部署方式
kubectl -n gpu-operator get pods -o wide | grep -i dcgm
kubectl -n gpu-operator logs ds/dcgm-exporter --tail=100
问题常见原因排查
dcgmi 正常，exporter 无指标exporter 容器权限、端口、metrics CSV、连接 hostengine 失败。看 exporter logs、容器 --gpus all、-r host:5555、版本。
exporter 正常，Prometheus 无数据ServiceMonitor/target 配置错误、网络策略、label 不匹配。查 Prometheus targets、抓取错误、K8s service endpoints。
MIG 指标不完整DCGM/exporter 版本、MIG label、设备枚举方式。确认 host DCGM 与 exporter 版本兼容，并查看 dcgmi discovery -c。
版本兼容： NVIDIA 官方文档强调 exporter 内的 DCGM client library 与 hostengine 之间存在内部协议，建议 exporter 基于的 DCGM 版本不低于被连接的 host DCGM 版本。

信息图：集群 burn-in 验收漏斗

burn-in 的目标不是“跑一次没挂”，而是证明节点在目标功率、散热、拓扑和业务压力下稳定。

13. 集群 burn-in 与验收流程

新 GPU 节点、返修节点、驱动升级后节点都应经过 burn-in。dcgmi 负责健康和诊断证据，业务 benchmark 负责验证真实训练/推理路径。

#!/usr/bin/env bash
set -euo pipefail

LOG_DIR="burnin-$(hostname)-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$LOG_DIR"

{
  date -Is
  hostname
  nvidia-smi
  dcgmi version
  dcgmi discovery -l -a
  dcgmi group -l
} | tee "$LOG_DIR/00-inventory.txt"

# 创建临时 group，实际脚本应解析 group id
dcgmi group -c burnin-all | tee "$LOG_DIR/01-group.txt"
dcgmi health -s a | tee "$LOG_DIR/02-health-set.txt"
dcgmi health -c | tee "$LOG_DIR/03-health-before.txt"

# 维护窗口内运行；根据硬件规模和窗口选择等级
dcgmi diag -r 2 -v | tee "$LOG_DIR/04-diag-r2.txt"

# 采样一段时间，和业务压测并行运行
dcgmi dmon -e 1001,1004,1005,150,155,230,319 -c 60 | tee "$LOG_DIR/05-dmon.txt"
dcgmi health -c | tee "$LOG_DIR/06-health-after.txt"
验收门槛建议
枚举一致GPU 数量、UUID、PCI Bus ID、MIG 配置与资产系统一致。
健康无错误health 无 Error/Fatal；Warning 必须有处置说明。
诊断通过所选等级和测试项通过，日志归档。
业务稳定目标训练/推理 benchmark 长跑无 XID、无不可纠正 ECC、吞吐无异常抖动。
验收产物： 保留 DCGM 版本、驱动版本、固件/BIOS、拓扑、诊断日志、业务压测结果。没有证据的“已验收”很难支撑后续故障复盘。

14. 生产安全与变更窗口

GPU 诊断和观测命令在生产环境的风险差异很大。SRE runbook 应把命令分级，并把“是否独占 GPU”“是否可能施加压力”“是否改变状态”写清楚。

类别命令例子生产策略
只读低风险dcgmi discovery -l、dcgmi group -l、dcgmi health -c可在值班排障中使用，仍需避免高频循环刷屏。
只读中风险dcgmi dmon 高频采样、长时间采样限制采样频率和时长，避免影响 hostengine/exporter。
状态变更dcgmi group -c/-d、dcgmi health -s脚本必须可重入，记录变更，避免误删共享 group。
高侵入dcgmi diag -r 2/3/4、压力测试维护窗口、独占 GPU、迁移业务、保留证据。
# 安全模式：先确认有没有业务
nvidia-smi --query-compute-apps=pid,process_name,gpu_uuid,used_memory --format=csv

# 如果有业务，先停止在这里：不要继续跑高侵入诊断
dcgmi discovery -l
dcgmi health -c

# 维护窗口内才运行
dcgmi diag -r 3 -v
不要这样做： 不要在所有 GPU 节点上无差别并发运行长诊断；不要在在线推理节点运行压力测试；不要把临时排障命令直接放进高频 cron。

15. dcgmi vs nvidia-smi

nvidia-smi 更像“驱动和设备状态入口”，适合快速查看、配置部分驱动/设备属性；dcgmi 更像“数据中心 GPU 管理与健康诊断入口”，适合分组、健康 watch、诊断、field/profiling、作业统计和 exporter 交叉验证。

维度dcgminvidia-smi
主要定位DCGM 管理、诊断、健康、观测。驱动/NVML 层设备状态与部分配置。
分组能力原生 group 和 field group。通常按 GPU ID/UUID 查询，无 DCGM group 抽象。
诊断能力dcgmi diag 分级诊断和指定测试。更多是状态查看，不是完整 DCGM Diagnostics。
持续监控与 dcgm-exporter/Prometheus 同源。可脚本采样，但不如 exporter 适合集群监控。
作业统计dcgmi stats 支持作业窗口。需要外部系统自行聚合。
日常入口平台/SRE 自动化。用户和运维快速查看。
# 两者经常配合，而不是互斥
nvidia-smi -L
nvidia-smi topo -m
dcgmi discovery -l -a
dcgmi health -c
dcgmi dmon -e 1001,1004,1005 -c 5
选型建议： 用户问“我的卡有没有被占用”时先用 nvidia-smi；平台问“这个节点是否应进入训练池、这类错误是否可自动隔离”时用 dcgmi。

排障时不要跳步：连二进制/hostengine 都没确认，就直接分析 ECC/XID，容易浪费时间。

16. 故障排查剧本

场景 A：dcgmi discovery -l 看不到 GPU

command -v dcgmi
dcgmi version
nvidia-smi -L
dcgmi discovery -l -a
systemctl status nvidia-dcgm --no-pager
dmesg -T | grep -Ei 'NVRM|Xid|nvidia' | tail -100

如果 nvidia-smi 也看不到 GPU，优先查驱动、内核模块、设备文件、PCIe 枚举、BMC/硬件；如果 nvidia-smi 正常但 DCGM 异常，重点查 nv-hostengine、DCGM 版本、权限和容器连接方式。

场景 B：health Warning / Error

dcgmi health -c
dcgmi discovery -l -a
dcgmi dmon -e 150,155,156,230,319 -c 10
dmesg -T | grep -i xid | tail -50

Warning 先分流到对应方向：PCIe、Memory、InfoROM、Thermal/Power、NVLink。Error/Fatal 或不可纠正 ECC 应倾向于停止受影响作业、下线节点或至少从调度池摘除。

场景 C：diag 失败

# 先确认没有业务和其他监控/分析工具冲突
nvidia-smi
ps -ef | grep -E 'dcgmi|nv-hostengine|dcgm|nsys|ncu' | grep -v grep

# 用更小范围复现
dcgmi diag -r 1 -i 0 -v
dcgmi diag -r 2 -i 0 -v

如果低等级通过、高等级失败，可能是压力下的硬件/散热/功耗/链路问题；如果所有等级都失败，先看软件依赖、权限、hostengine 工作目录、日志路径和 DCGM 版本。

17. 自动化脚本模板

下面是一个保守的节点巡检脚本，只运行只读或低风险命令，适合纳入值班工具箱。它不会运行高等级 diag，也不会修改 group 或 health watch。

#!/usr/bin/env bash
set -euo pipefail

OUT="${1:-dcgmi-check-$(hostname)-$(date +%Y%m%d-%H%M%S).log}"

{
  echo "## basic"
  date -Is
  hostname
  uname -a

  echo
  echo "## nvidia-smi"
  nvidia-smi || true

  echo
  echo "## dcgmi version"
  dcgmi version || true

  echo
  echo "## discovery active"
  dcgmi discovery -l || true

  echo
  echo "## discovery all"
  dcgmi discovery -l -a || true

  echo
  echo "## groups"
  dcgmi group -l || true

  echo
  echo "## health"
  dcgmi health -c || true

  echo
  echo "## short dmon"
  dcgmi dmon -e 150,155,230,319 -c 5 || true

  echo
  echo "## recent xid"
  dmesg -T | grep -i xid | tail -50 || true
} | tee "$OUT"

echo "wrote $OUT"
自动化建议： 巡检脚本只采证；处置脚本要单独设计审批、幂等、回滚和调度系统联动，避免“检测到异常就立刻重启 GPU/节点”的粗暴策略。

18. 常见坑与 FAQ

Q：dcgmi 能替代 nvidia-smi 吗？
A：不能简单替代。日常人工看卡仍然常用 nvidia-smi；平台健康、诊断、field/profiling 和 exporter 校验更适合 dcgmi。
Q：为什么 exporter 有数据但 dcgmi diag 失败？
A：采集指标和主动诊断是不同路径。diag 可能需要独占 GPU、可写日志目录、测试依赖和更高权限。
Q：为什么 XID 指标是 0，但 dmesg 有 XID？
A：检查采样窗口、字段选择、hostengine 状态、GPU reset 后计数、driver/DCGM 版本，以及是否看错 GPU/MIG 实体。
Q：所有节点都要跑 diag -r 4 吗？
A：不建议作为日常频繁操作。它更适合 burn-in、返修验收和深度排障，且需要维护窗口。
Q：MIG 环境怎么解释利用率？
A：确认指标粒度是整卡还是 GPU Instance/Compute Instance；MIG profile 的资源比例会影响整卡指标解释。
Q：脚本里可以固定 field ID 吗？
A：可以，但要把 DCGM 版本、字段含义和测试样例写入仓库；升级 DCGM/exporter 前做兼容性验证。
最容易误判： 把“单次健康 Warning”当成硬件必坏，或把“短时间无错误”当成节点完全健康。正确做法是结合时间序列、作业事件、XID/ECC、诊断结果和复现性。
