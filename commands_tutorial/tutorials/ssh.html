ssh 深度教程：从安全登录到跳板机、端口转发与排障

这份教程按常用命令 ssh 讲解。它不是“怎么连上服务器”的速查表，而是从 SSH 的连接模型、主机身份校验、用户认证、密钥文件、配置文件、known_hosts、agent、端口转发、ProxyJump、安全加固和 -v 排障路径出发，帮助你把日常远程登录变成可解释、可审计、可维护的工程能力。

信息图加密通道主机指纹密钥登录ssh_configssh-agent端口转发ProxyJump安全加固-v 排障
一句话理解： ssh 是“在不可信网络上建立可信远程会话”的工具：先验证服务器身份，再认证用户身份，最后在加密通道里传输终端、命令、文件或端口流量。
最重要原则： 不要盲目接受主机指纹，不要共享私钥，不要把生产服务器暴露成弱口令入口；先理解 known_hosts、authorized_keys 和 ssh -v，再做自动化批量登录。

1. ssh 是什么

ssh 是 Secure Shell 的客户端命令，常见实现是 OpenSSH。它最常见的用途是远程登录 Linux/Unix 服务器，但本质上它提供的是一条经过认证和加密的传输通道。终端登录、执行远程命令、转发端口、通过跳板机访问内网、给 scp/sftp 提供底层连接，都是这个通道的不同用法。

它解决什么
在公网、办公网、云厂商网络等不可信链路上，安全地访问远程主机。
它不解决什么
不会替你确认“这台服务器是否本该被你访问”，也不会修复服务器侧账号权限、审计、补丁和防火墙问题。
它的核心对象
客户端配置 ~/.ssh/config、私钥、公钥、known_hosts、服务端 sshd 和 authorized_keys。
# 最常见：登录远程服务器
ssh user@example.com

# 指定端口和私钥
ssh -p 2222 -i ~/.ssh/id_ed25519 user@example.com

# 只执行一条远程命令，不进入交互 shell
ssh deploy@app01.example.com 'systemctl status nginx --no-pager'
不要把 ssh 当成“远程万能钥匙”： 能连上不代表权限设计合理；能用密钥登录不代表私钥管理安全。

2. 连接模型：客户端、服务端与加密通道

一次 SSH 连接可以拆成四个阶段：建立 TCP 连接、协商加密参数、验证服务器主机身份、认证用户身份。前两个阶段解决“通道是否保密”，后两个阶段解决“我连的是谁”和“谁在登录”。

TCP 连通
DNS、路由、防火墙和端口必须先通。
密钥交换
双方协商会话密钥，后续流量加密传输。
主机校验
客户端用 known_hosts 判断服务端身份。
用户认证
服务端用密码、公钥或证书判断用户身份。

信息图：ssh 连接模型

SSH 不是先输入密码这么简单；真正的顺序是协商加密参数、验证服务器、认证用户，然后才进入远程会话。

3. 基本语法与第一批例子

ssh [options] [user@]host [command]

# 常用形式
ssh user@host
ssh -p PORT user@host
ssh -i KEY_FILE user@host
ssh HOST_ALIAS
命令作用适合场景
ssh user@server使用默认端口 22 登录日常登录
ssh -p 2222 user@server连接非默认端口云主机、堡垒机或端口映射
ssh -i ~/.ssh/id_ed25519 user@server指定私钥文件多套密钥、多环境隔离
ssh -o ConnectTimeout=5 user@server临时指定配置项脚本中避免长时间卡住
ssh -vv user@server输出更详细调试日志定位认证和网络问题

最小安全习惯

# 第一次连接前，尽量从可信渠道核对服务器指纹
ssh-keygen -l -f /etc/ssh/ssh_host_ed25519_key.pub

# 连接时只执行只读检查命令
ssh user@server 'hostname; whoami; pwd'
命令行选项和 config 等价： 大多数 -o Name=value 都可以写进 ~/.ssh/config，长期使用的服务器应优先配置别名。

4. 认证模型：密码、密钥与证书

SSH 里有两类身份要验证：服务器向客户端证明“我就是你要连的那台主机”，用户向服务器证明“我有权以这个账号登录”。这两件事不要混在一起。

认证类型验证对象优点风险
密码认证用户身份容易理解，不需要分发公钥弱口令、撞库、暴力破解、共享密码难审计
公钥认证用户身份无需传输密码，可加 passphrase，可逐个撤销公钥私钥泄露会造成横向移动风险
主机密钥服务器身份防止中间人攻击用户盲目输入 yes 会绕过保护
SSH 证书用户或主机身份集中签发、可设置有效期和主体需要额外 CA 流程和运维规范
关键安全点： 用户公钥放在服务端 ~/.ssh/authorized_keys；服务器主机指纹记录在客户端 ~/.ssh/known_hosts。文件名字相似，但职责完全不同。

流程图：密钥登录发生了什么

密钥登录不是“把私钥发给服务器”；服务器只验证客户端能否用私钥完成签名。

5. 生成和保护密钥

现代通用选择是 Ed25519 密钥。密钥应该按用途隔离：个人 Git、生产运维、测试环境、CI 部署最好不要共用同一把私钥。

# 生成 Ed25519 密钥，并添加清晰注释
ssh-keygen -t ed25519 -a 100 -C "yang@example laptop 2026" -f ~/.ssh/id_ed25519_prod

# 查看公钥指纹，不泄露私钥
ssh-keygen -l -f ~/.ssh/id_ed25519_prod.pub

# 修改私钥 passphrase
ssh-keygen -p -f ~/.ssh/id_ed25519_prod

# 修正本地权限
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519_prod
chmod 644 ~/.ssh/id_ed25519_prod.pub
文件放在哪里权限建议说明
私钥客户端600绝不能上传到服务器、仓库或聊天工具
公钥可复制到服务端644公开不等于可乱发；仍应可追踪用途
authorized_keys服务端用户家目录600每行一个允许登录的公钥
known_hosts客户端644记录服务器主机身份
私钥泄露处理： 不要只改 passphrase。应立即从所有服务器的 authorized_keys 中删除对应公钥，审计登录记录，并重新签发新密钥。

6. 部署公钥与 authorized_keys

公钥登录的服务端入口是目标用户家目录下的 ~/.ssh/authorized_keys。你可以用 ssh-copy-id，也可以手动追加。生产环境更推荐通过配置管理、镜像或身份系统统一下发。

# 自动追加公钥，目标服务器仍会要求你完成一次现有认证
ssh-copy-id -i ~/.ssh/id_ed25519_prod.pub user@server

# 手动方式：先确认要追加的公钥内容
cat ~/.ssh/id_ed25519_prod.pub

# 手动追加，注意只追加公钥，不要复制私钥
ssh user@server 'mkdir -p ~/.ssh && chmod 700 ~/.ssh'
cat ~/.ssh/id_ed25519_prod.pub | ssh user@server 'cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys'

authorized_keys 的限制选项

# 限制某个部署 key 只能从指定来源执行指定命令
from="203.0.113.10",command="/usr/local/bin/deploy-readonly",no-pty,no-agent-forwarding,no-X11-forwarding ssh-ed25519 AAAA... deploy-key
排查权限： 很多“公钥明明在却不能登录”的问题，来自服务端 ~/.ssh 或 authorized_keys 权限过宽，被 sshd 拒绝。

7. known_hosts 与主机指纹

第一次连接新主机时，SSH 会显示服务器主机密钥指纹，并询问是否信任。你输入 yes 后，指纹会写入客户端的 ~/.ssh/known_hosts。以后如果同一地址的主机密钥变化，SSH 会报警。

# 查看某台主机在 known_hosts 中的记录
ssh-keygen -F server.example.com

# 删除旧记录。适合确认服务器重装或更换 host key 后使用
ssh-keygen -R server.example.com

# 从网络扫描主机公钥。只适合采集，不等于可信验证
ssh-keyscan -t ed25519 server.example.com

# 查看服务器本地 host key 指纹，需要登录服务器或通过可信渠道获取
ssh-keygen -l -f /etc/ssh/ssh_host_ed25519_key.pub
中间人风险： 如果你没有核对指纹就输入 yes，等于告诉 SSH“信任当前网络上回答我的那台机器”。在不可信 Wi-Fi、VPN、跳板链路和供应链迁移中尤其危险。
现象可能原因正确处理
REMOTE HOST IDENTIFICATION HAS CHANGED服务器重装、DNS 指向变化、负载均衡后端变化，或中间人攻击先通过可信渠道确认新指纹，再用 ssh-keygen -R 删除旧记录
Host key verification failed主机指纹不匹配或策略禁止自动接受核对 known_hosts 和目标地址，不要直接关闭校验
同一 IP 多台主机冲突NAT、端口映射、测试机复用 IP使用 [host]:port 记录，或给不同入口配置不同别名

8. ssh_config：把复杂命令变成别名

长期使用的连接不要靠记忆一长串参数，应该写进客户端配置 ~/.ssh/config。配置文件能减少误连、漏参数和脚本复制错误。

# ~/.ssh/config
Host prod-app01
    HostName 203.0.113.21
    User deploy
    Port 2222
    IdentityFile ~/.ssh/id_ed25519_prod
    IdentitiesOnly yes
    ServerAliveInterval 30
    ServerAliveCountMax 3

Host *.corp
    User yang
    IdentityFile ~/.ssh/id_ed25519_corp
    AddKeysToAgent yes
# 使用别名后，命令更短也更稳定
ssh prod-app01
ssh prod-app01 'uptime'

# 查看某个 Host 最终展开后的配置
ssh -G prod-app01 | sed -n '1,80p'
配置项用途建议
Host匹配别名或通配符用环境和角色命名，例如 prod-app01
HostName真实域名或 IP避免把 IP 散落在脚本里
IdentityFile指定私钥不同环境使用不同密钥
IdentitiesOnly yes只尝试指定密钥避免 agent 里太多 key 导致认证失败
StrictHostKeyChecking控制主机指纹策略生产环境不要设为 no

9. ssh-agent 与密钥解锁

ssh-agent 是本地进程，用来缓存已解锁的私钥。它不应该被理解成“把私钥交给所有服务器”，而是客户端本地替你完成签名。Agent forwarding 则会把本地 agent 暴露给远端会话，风险更高。

# 查看 agent 中已有的 key
ssh-add -l

# 加载一把私钥，输入一次 passphrase 后缓存
ssh-add ~/.ssh/id_ed25519_prod

# 从 agent 中移除指定 key
ssh-add -d ~/.ssh/id_ed25519_prod

# 清空 agent 中所有 key
ssh-add -D
推荐用法
本机日常登录时用 agent 缓存 passphrase，配合 IdentityFile 和 IdentitiesOnly 控制尝试范围。
谨慎用法
ssh -A 或 ForwardAgent yes 会让远端能请求你的本地 agent 签名。只对高度可信的跳板机短时使用。
# 临时开启 agent forwarding，不建议写成全局默认
ssh -A bastion.example.com

# 更安全的替代方案通常是 ProxyJump，而不是先登录跳板机再从跳板机 ssh
ssh -J bastion.example.com internal-app
安全提醒： 如果跳板机被攻陷，开启 agent forwarding 的会话可能被滥用来访问你有权访问的其他主机。优先使用 ProxyJump。

10. 执行远程命令与非交互脚本

SSH 不只用于交互登录。给 ssh 追加命令时，它会在远端执行该命令并返回退出码。脚本里要注意超时、主机密钥策略、标准输入和引用。

# 执行单条命令
ssh app01 'hostname; uptime; df -h /'

# 本地变量在本地展开，远程变量在远程展开：注意引号
service=nginx
ssh app01 "systemctl is-active $service"
ssh app01 'echo "remote home is $HOME"'

# 把本地脚本通过 stdin 传给远端 bash
ssh app01 'bash -s' < ./health-check.sh

# 脚本中避免无限等待
ssh -o BatchMode=yes -o ConnectTimeout=5 app01 'true'
选项含义脚本建议
BatchMode=yes禁止交互式密码/口令提示CI 和批量任务应开启，失败就失败
ConnectTimeout=5连接超时秒数避免网络异常时卡住整批任务
LogLevel=ERROR降低普通日志噪声只在脚本输出需要干净时使用
RequestTTY=no不申请伪终端非交互命令默认即可
脚本安全： 不要把未转义的用户输入拼进远程 shell 命令；跨机器执行时，引用错误会变成远程命令注入。

信息图：本地端口转发 -L

-L 常用于“我本机想访问远端内网服务”：把本机端口映射到 SSH 服务器视角可访问的目标。

11. 本地端口转发 -L

本地转发的方向是：在本机监听一个端口，连接进来的流量通过 SSH 隧道送到远端网络里的目标。它常用于访问内网数据库、只监听 localhost 的管理界面、或临时调试服务。

# 通过 bastion 访问内网 PostgreSQL
ssh -N -L 15432:db.internal:5432 user@bastion.example.com

# 另一个终端中访问本机端口，实际到达 db.internal:5432
psql -h 127.0.0.1 -p 15432 -U app appdb

# 只绑定本机回环地址，避免局域网其他机器访问你的转发端口
ssh -N -L 127.0.0.1:18080:127.0.0.1:8080 user@app01
选项作用
-L [bind_address:]local_port:host:host_port建立本地端口转发
-N不执行远程命令，只建立隧道
-f认证后转入后台，脚本中要谨慎使用
ExitOnForwardFailure=yes转发失败时让 ssh 直接失败，适合脚本
绑定地址提醒： -L 0.0.0.0:8080:... 会把本机转发端口暴露给其他机器，除非你明确知道需要这样做，否则使用 127.0.0.1。

12. 远程端口转发 -R 与动态转发 -D

-R 和 -D 解决的是不同问题。-R 是让远端开放一个入口转回本机或本机可达服务；-D 是在本机开一个 SOCKS 代理，把浏览器或工具流量动态送进 SSH 通道。

# 远程转发：让远端 server 的 19000 转回本机 3000
ssh -N -R 19000:127.0.0.1:3000 user@server

# 动态转发：本机开 SOCKS5 代理
ssh -N -D 127.0.0.1:1080 user@bastion.example.com

# 使用 SOCKS 代理发起请求
curl --socks5-hostname 127.0.0.1:1080 https://example.com
模式入口在哪里目标怎么确定典型用途
-L本机命令中固定本机访问远端内网服务
-R远端命令中固定临时回连本机开发服务
-D本机由 SOCKS 客户端动态决定浏览器或工具走跳板访问
生产限制： 远程转发可能被服务器配置 AllowTcpForwarding、GatewayPorts 限制。不要用转发绕过组织网络边界和审计要求。

13. ProxyJump 与跳板机

跳板机场景里，推荐使用 ProxyJump 或 -J。它让本机 SSH 客户端直接和最终目标完成认证，跳板机只负责转发连接，通常比“先 ssh 到跳板机，再在跳板机上 ssh 内网机器”更安全、更可审计。

# 临时命令：通过 bastion 连接内网机器
ssh -J user@bastion.example.com appuser@10.0.1.25

# 多级跳转
ssh -J bastion1.example.com,bastion2.internal app01.internal

# ~/.ssh/config 写法
Host bastion
    HostName bastion.example.com
    User yang
    IdentityFile ~/.ssh/id_ed25519_corp

Host app-*.internal
    User deploy
    ProxyJump bastion
    IdentityFile ~/.ssh/id_ed25519_prod
    IdentitiesOnly yes
ProxyJump 的好处
私钥留在本机；最终目标认证由本机完成；命令、scp、sftp、端口转发都能复用同一 Host 别名。
传统跳板登录的问题
容易在跳板机落地私钥；命令历史和临时文件更难管；agent forwarding 风险更高。

14. 安全加固清单

SSH 安全不是一个选项，而是一组互相配合的控制：账号权限、密钥生命周期、服务端策略、网络边界、日志审计和应急撤销。

位置配置/动作建议
客户端私钥 passphrase重要密钥必须设置，配合 agent 使用
客户端StrictHostKeyChecking生产保持校验，不要全局关闭
服务端PasswordAuthentication no确认公钥和应急通道可用后再关闭密码
服务端PermitRootLogin no禁止直接 root 登录，使用普通账号 + sudo 审计
服务端AllowUsers/AllowGroups限制可登录账号范围
服务端MaxAuthTries降低暴力尝试空间，配合日志告警
网络防火墙/安全组只对可信来源开放 22 或自定义端口
运维密钥轮换和离职撤权把公钥当权限凭证管理，而不是个人小工具

修改服务端 sshd 前的安全流程

# 1. 在当前连接之外，保留一个已登录的应急会话

# 2. 检查配置语法，不要直接重启
sudo sshd -t

# 3. 重载而不是立刻重启
sudo systemctl reload sshd

# 4. 新开一个终端验证新连接
ssh -v user@server 'echo ok'
防锁死原则： 修改 /etc/ssh/sshd_config 前，先保留现有会话，语法检查通过后重载，再用新终端验证。不要在唯一连接里边改边重启。

排障流程图：从 ssh -v 日志定位问题

ssh -v 的日志很多，但排障顺序很固定：先连通性，再主机身份，再认证方式，最后看远端 shell 和权限。

15. 调试：ssh -v / -vv / -vvv

-v 是 SSH 排障的入口。它会显示配置匹配、密钥尝试、主机密钥校验、认证方式协商等关键线索。-vv 和 -vvv 更详细，但也更嘈杂。

# 基础调试
ssh -v user@server

# 更详细：认证失败或跳板机问题时使用
ssh -vvv -J bastion user@app01.internal

# 把日志保存下来，便于比较
ssh -vv user@server true 2> ssh-debug.log
日志片段含义下一步
Connection timed out网络或防火墙无法到达检查 DNS、端口、安全组、路由
No route to host本地路由或目标网络不可达检查 VPN、子网、网关
Host key verification failed主机身份校验失败核对指纹，不要直接关闭校验
Offering public key客户端正在尝试某把 key确认是否是预期私钥
Permission denied (publickey)服务端拒绝所有可用认证检查用户名、公钥、权限、sshd_config
Too many authentication failuresagent 尝试了太多 key配置 IdentitiesOnly yes 和指定 IdentityFile
快速定位技巧： 先运行 ssh -G alias 看最终配置，再运行 ssh -vv alias 看实际认证过程。

16. ssh vs scp/sftp/mosh

这些工具经常一起出现，但目标不同。选错工具会让问题变复杂。

工具主要用途依赖关系适合
ssh远程登录、远程命令、端口转发基础协议和客户端终端管理、跳板、隧道
scp复制文件通常基于 SSH 传输简单的一次性文件拷贝
sftp交互式文件传输基于 SSH 子系统浏览目录、批量上传下载、权限管理
rsync -e ssh增量同步用 SSH 作为远程 shell大目录、重复同步、备份
mosh移动网络下的远程终端启动阶段用 SSH，数据阶段用 UDP网络抖动、IP 变化、长时间终端
# scp：简单复制
scp ./app.tar.gz user@server:/tmp/

# sftp：交互式文件管理
sftp user@server

# rsync：增量同步，保留属性并可删除目标多余文件
rsync -av --delete -e ssh ./site/ user@server:/var/www/site/

# mosh：适合不稳定网络，但需要服务端安装 mosh 并放通 UDP
mosh user@server
选择建议： 少量文件用 scp 或 sftp；目录同步用 rsync -e ssh；弱网交互终端用 mosh；端口和跳板还是直接掌握 ssh。

17. 常见故障与处理

故障 1：Permission denied (publickey)
检查用户名是否正确、公钥是否在目标用户的 authorized_keys、服务端权限是否过宽、客户端是否用了预期私钥。
故障 2：Too many authentication failures
agent 里 key 太多。为该 Host 设置 IdentityFile 和 IdentitiesOnly yes。
故障 3：REMOTE HOST IDENTIFICATION HAS CHANGED
先核对新主机指纹。确认是重装或迁移后，再执行 ssh-keygen -R host。
故障 4：Connection timed out
目标端口不可达。检查安全组、防火墙、VPN、端口、DNS 和跳板链路。
故障 5：端口转发连不上
区分本机监听是否成功、SSH 是否建立、远端视角能否访问目标服务。
故障 6：登录后马上断开
远端 shell、.bashrc、账号状态、磁盘满、强制命令或 PAM 策略可能异常。
故障 7：密钥权限报错
本地私钥一般 600，服务端 ~/.ssh 一般 700，authorized_keys 一般 600。
故障 8：配置没生效
用 ssh -G alias 查看最终配置；注意 Host 匹配是从上到下应用。

排障模板

# 1. 看最终配置
ssh -G prod-app01 | sed -n '1,120p'

# 2. 检查 TCP 连通性
nc -vz prod-app01 22

# 3. 单独指定 key，排除 agent 干扰
ssh -vv -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519_prod deploy@prod-app01

# 4. 检查主机记录
ssh-keygen -F prod-app01

# 5. 验证远程命令退出码
ssh prod-app01 'whoami && hostname'
echo "$?"

18. 练习路线与参考资料

第一阶段：会连

  • 理解 user@host、-p、-i、远程命令的基本语法。
  • 用 ssh-keygen 生成一把带 passphrase 的 Ed25519 密钥。
  • 用 ssh-copy-id 或手动方式部署公钥。

第二阶段：安全

  • 能解释 authorized_keys 和 known_hosts 的区别。
  • 会核对主机指纹，并谨慎处理 host key changed 报警。
  • 会用 ~/.ssh/config 为不同环境隔离私钥。

第三阶段：工程化

  • 掌握 ProxyJump，替代在跳板机落地私钥。
  • 掌握 -L、-R、-D 的方向和边界。
  • 会用 ssh -G、ssh -v、ssh-add -l 系统排障。

练习

  1. 为一台测试机写 Host lab 配置，并用 ssh -G lab 验证展开结果。
  2. 生成一把专用测试密钥，部署到测试用户，确认不输入密码也能登录。
  3. 故意指定错误用户，用 ssh -vv 找到认证失败位置。
  4. 建立 -L 18080:127.0.0.1:80 转发，确认本机只绑定 127.0.0.1。
  5. 使用 ProxyJump 连接内网测试机，不在跳板机复制私钥。
  6. 模拟服务器重装后的 known_hosts 冲突，练习先核对再 ssh-keygen -R。
