readelf 深度教程：面向 AI Infra 的 ELF 二进制诊断

这份教程按 AI Infra 生产排障视角讲解 readelf：如何不用执行目标程序就读取 ELF 文件的头、节、段、动态链接信息、符号、版本、NOTE、RPATH/RUNPATH 和 ABI 线索，并把这些信息用于 PyTorch/CUDA/C++ 扩展、容器镜像、glibc 兼容性和动态库依赖问题诊断。

ELFAI InfraCUDA 扩展GLIBC 版本RPATH/RUNPATH动态链接符号诊断容器排障无执行检查
一句话理解： readelf 是 ELF 文件的“只读体检仪”：它直接解析二进制元数据，不运行程序、不触发动态加载器，适合在不可信制品、跨镜像 ABI 兼容性和线上依赖问题里先做静态判断。
实践原则： 先用 readelf -h/-l/-S/-d/-s/-V/-n 建立事实，再决定是否用 ldd、objdump、nm 或运行时日志继续验证；不要对来源不明的二进制直接执行。

1. readelf 是什么，为什么 AI Infra 需要它

readelf 来自 GNU Binutils，用于显示 ELF（Executable and Linkable Format）文件内部结构。AI Infra 常见对象包括：Python C/C++ 扩展 .so、CUDA 扩展、推理引擎插件、NCCL/CUDNN/TensorRT 动态库、容器内二进制工具、模型服务进程和 core dump 辅助文件。

它解决什么
确认二进制架构、动态依赖、符号、版本需求、加载段、调试信息、构建 ID 和 ABI 线索。
它不会做什么
不会解析所有机器指令语义，不会真正加载依赖，也不会告诉你运行时最终选中了哪个库。
它为什么安全
它读取文件元数据而不是执行目标程序；面对未知 .so 时通常比 ldd 更适合作为第一步。
# 最常用的只读检查组合
readelf -h libtorch_cuda.so       # ELF 头：架构、类型、入口点
readelf -d my_extension.so        # 动态段：NEEDED、RPATH、RUNPATH、SONAME
readelf -Ws my_extension.so       # 符号表：导入/导出符号
readelf -V my_extension.so        # 版本需求：GLIBC、GLIBCXX、CXXABI
readelf -n my_extension.so        # NOTE：Build ID、ABI tag 等
边界提醒： readelf 告诉你“文件声明了什么”。动态加载失败还可能来自文件不存在、权限、LD_LIBRARY_PATH、容器挂载、驱动版本或加载器实际搜索顺序。

信息图：ELF 从文件到进程的心智模型

节表更像“链接和分析目录”；程序头更像“加载说明书”。动态段、符号表和版本表是 AI Infra 排查依赖与 ABI 问题的核心入口。

2. 快速命令速查

目标命令看什么
文件基本身份readelf -h fileClass、Machine、Type、入口点
节表readelf -S file.dynsym、.debug_*、.note.*、.gnu.version*
段表readelf -l fileINTERP、LOAD、DYNAMIC、GNU_RELRO
动态依赖readelf -d fileNEEDED、SONAME、RUNPATH、RPATH
符号readelf -Ws fileUND 未定义导入、GLOBAL 导出、C++ mangled name
版本需求readelf -V fileGLIBC_*、GLIBCXX_*、CXXABI_*
NOTEreadelf -n fileBuild ID、ABI tag、属性说明
重定位readelf -r filePLT/GOT 重定位、外部符号引用
# 推荐排障起手式：一屏看完关键事实
target=build/lib.linux-x86_64-cpython-311/my_ext.so
readelf -h "$target"
readelf -d "$target" | egrep 'NEEDED|RPATH|RUNPATH|SONAME'
readelf -V "$target" | egrep 'GLIBC|GLIBCXX|CXXABI' | sort -u
readelf -Ws "$target" | egrep ' UND |cuda|cudart|c10|torch|GLIBCXX' | head -80
选项习惯： -W 表示宽输出，避免长符号被截断；排查 C++/CUDA 扩展时建议常配 -Ws。

3. 识别文件类型、架构与入口点

AI Infra 经常在 x86_64、aarch64、manylinux、不同 CUDA 基础镜像之间移动制品。第一步不是看源码，而是确认二进制本身是什么。

readelf -h my_service
readelf -h my_extension.so

# 关注字段示例
# Class:                             ELF64
# Data:                              2's complement, little endian
# Type:                              DYN (Position-Independent Executable file)
# Machine:                           Advanced Micro Devices X86-64
# Entry point address:               0x1090
字段含义AI Infra 排查价值
ClassELF32 或 ELF64避免 32/64 位不匹配
Data大小端交叉编译、嵌入式推理设备排查
TypeEXEC、DYN、REL、CORE判断可执行、共享库、目标文件、core 文件
Machine目标 ISAx86_64 镜像误放 aarch64 wheel 时快速定位
Entry point程序入口地址共享库通常不靠入口点运行；可执行文件才更关键
常见现象： 现代 PIE 可执行文件在 Type 中也可能显示为 DYN，不要仅凭 DYN 就断定它是普通共享库。

4. ELF Header：ABI 与平台基本事实

-h 输出是所有判断的根。它能回答“这个文件是否能在当前机器和加载器语义下被理解”。在 AI 平台中，错误 wheel、错误容器架构、错误交叉编译产物常在这里暴露。

# 对比宿主架构与 ELF 架构
uname -m
readelf -h ./venv/lib/python3.11/site-packages/pkg/_core.so | grep Machine

# 查找目录中非 x86-64 的 ELF
find . -type f -name '*.so*' -print0 |
  xargs -0 -I{} sh -c 'readelf -h "$1" 2>/dev/null | grep -q "X86-64" || echo "$1"' sh {}
可执行与共享对象
EXEC 是传统固定地址可执行文件；DYN 可表示共享库，也可表示 PIE 可执行文件。
目标文件
REL 是尚未完全链接的目标文件，常出现在编译缓存或构建中间产物中。
生产建议： CI 中可对构建产物统一运行 readelf -h，防止错误架构的二进制混入镜像或 Python wheel。

5. Section Headers：节表与调试线索

readelf -S 展示节表。节是链接器和分析工具的组织单位，包含代码、只读数据、符号表、字符串表、调试信息、动态链接信息等。被 strip 后，某些节可能消失，但加载段仍可存在。

readelf -S my_extension.so
readelf -SW my_extension.so | egrep '\.(text|dynsym|symtab|debug|note|gnu.version|nv_fatbin)'
节名用途排查价值
.text机器代码确认文件包含可执行代码
.dynsym/.dynstr动态符号与字符串动态链接器解析导入/导出符号
.symtab/.strtab完整符号表未 strip 时更利于调试
.debug_*DWARF 调试信息符号化栈、源码定位、性能分析
.gnu.version*符号版本信息定位 GLIBC/GLIBCXX/CXXABI 版本需求
.nv_fatbinNVIDIA CUDA fatbin判断 CUDA kernel 代码是否嵌入扩展
节表不是加载必需： 运行时加载器主要看程序头。极端情况下节表可被剥离，但程序仍可运行；因此排查加载问题时要同时看 -l 和 -d。

6. Program Headers：加载视角与运行内存布局

readelf -l 展示程序头，也叫段表。动态加载器按段表把文件映射到内存，并寻找解释器、动态段、只读重定位保护等运行时信息。

readelf -l my_service
readelf -lW my_extension.so | egrep 'INTERP|LOAD|DYNAMIC|GNU_STACK|GNU_RELRO'
段类型含义关注点
INTERP动态加载器路径，如 /lib64/ld-linux-x86-64.so.2容器基础镜像中加载器是否存在
LOAD需要映射进内存的文件区域权限 R/E/W 是否异常
DYNAMIC动态链接元数据位置readelf -d 的来源
GNU_STACK栈权限声明是否意外要求可执行栈
GNU_RELRO重定位后只读区域安全加固信号
# 检查可执行文件使用的动态加载器
readelf -l ./server | sed -n '/Requesting program interpreter/p'

# 检查栈是否可执行，RWE 中的 E 值得关注
readelf -lW ./server | grep GNU_STACK
安全习惯： 看到 GNU_STACK 带执行权限时要进一步调查构建参数或汇编对象文件来源，尤其是对外运行的推理服务。

流程图：从加载失败到 readelf 证据链

动态库问题通常不是单点故障：先分解成“库名是否声明、路径是否能找到、版本是否满足、符号是否由正确库提供”。

7. Dynamic Section：依赖库、SONAME、RPATH/RUNPATH

readelf -d 是排查共享库加载失败的核心命令。它读取 .dynamic，展示动态链接器需要处理的条目。

readelf -d my_extension.so
readelf -dW my_extension.so | egrep 'NEEDED|SONAME|RPATH|RUNPATH|TEXTREL|BIND_NOW'
条目含义典型问题
NEEDED运行时需要的共享库名缺 libcudart.so、libtorch_cpu.so、libnccl.so
SONAME该库对外声明的名字软链接或打包命名混乱
RUNPATH新式运行时搜索路径$ORIGIN 写错导致旁路库找不到
RPATH旧式搜索路径优先级语义与 RUNPATH 不同，易造成环境覆盖困惑
TEXTREL代码段重定位安全与性能风险
BIND_NOW启动时立即解析符号让缺符号更早暴露，也可能增加启动成本
# 找出 Python site-packages 中依赖 CUDA/NCCL/Torch 的扩展
find "$VIRTUAL_ENV/lib" -type f -name '*.so' -print0 |
  xargs -0 -I{} sh -c 'readelf -d "$1" 2>/dev/null | egrep -q "libcuda|libcudart|libtorch|libnccl" && echo "$1"' sh {}
关键点： NEEDED 只记录库名，不记录最终文件路径；最终路径由动态加载器按搜索规则决定。

8. 符号表：导入、导出、弱符号与 C++ 符号

符号是链接和加载的名字契约。readelf -Ws 能展示动态符号与普通符号，尤其适合检查扩展是否导出 Python 初始化函数、是否引用未定义 CUDA/Torch 符号。

# 宽输出查看符号，避免长 C++ 名字被截断
readelf -Ws my_extension.so | head

# 查看未定义符号：这些需要由依赖库或主进程提供
readelf -Ws my_extension.so | awk '$7 == "UND" {print}'

# Python 扩展必须有 PyInit_模块名
readelf -Ws my_extension.so | grep ' PyInit_'
字段含义排查方法
Ndx = UND未定义符号，等待运行时解析确认哪个 NEEDED 库应提供它
Bind = GLOBAL全局可见常见导出/导入符号
Bind = WEAK弱符号可被覆盖，缺失不一定失败
Type = FUNC函数符号C/C++ 函数入口
Type = OBJECT对象符号全局变量、表、运行时对象
# C++ 符号可用 c++filt 还原，readelf 自身偏向原始事实
readelf -Ws my_extension.so | grep _ZN | head -20 | c++filt

# 观察是否引用 torch/c10 符号
readelf -Ws my_extension.so | c++filt | egrep 'torch::|c10::|at::' | head -50
C++ ABI 提醒： 同名源码函数在不同编译器、标准库 ABI、命名空间和签名下会形成不同 mangled name。未定义符号错误经常来自 PyTorch 版本、编译参数或 _GLIBCXX_USE_CXX11_ABI 不一致。

9. 版本信息：GLIBC、GLIBCXX、CXXABI 线索

readelf -V 显示符号版本需求。它是定位“本机 libstdc++ 太旧”“基础镜像 glibc 太旧”“wheel 不符合部署基线”的关键工具。

readelf -V my_extension.so
readelf -V my_extension.so | egrep 'GLIBC_|GLIBCXX_|CXXABI_' | sort -u
版本前缀来源常见错误
GLIBC_*GNU C Libraryversion `GLIBC_2.xx' not found
GLIBCXX_*GNU libstdc++version `GLIBCXX_3.4.xx' not found
CXXABI_*C++ ABI 支持库version `CXXABI_1.x' not found
CUDA/NCCL 自身版本通常不走 GNU 符号版本体系更多依赖 SONAME、驱动/runtime 兼容矩阵和实际库文件
# 对比目标文件需求和容器内 libstdc++ 能提供的版本
readelf -V my_extension.so | grep -o 'GLIBCXX_[0-9.]*' | sort -Vu | tail
strings /usr/lib/x86_64-linux-gnu/libstdc++.so.6 | grep '^GLIBCXX_' | sort -Vu | tail

# 对比 glibc 版本需求
readelf -V my_extension.so | grep -o 'GLIBC_[0-9.]*' | sort -Vu | tail
ldd --version | head -1
兼容性原则： 编译环境版本高于部署环境时，常会引入更高的 GLIBC_* 或 GLIBCXX_* 需求。生产 wheel 应在符合最低部署基线的构建镜像中生成。

10. NOTE 与 Build ID：发行版、ABI、调试包关联

readelf -n 显示 NOTE 段内容。常见信息包括 GNU Build ID、ABI tag、属性说明。Build ID 对 core dump、符号服务器、debuginfo 包匹配非常有用。

readelf -n ./server

# 只看 Build ID
readelf -n ./server | sed -n '/Build ID/p'
NOTE意义使用场景
NT_GNU_BUILD_ID构建产物唯一标识关联 debug symbols、crash dump、制品仓库
NT_GNU_ABI_TAG目标 OS/ABI 信息判断构建目标系统线索
.note.gnu.property平台属性，如 CET 等安全特性和 CPU 属性排查
# 在崩溃机器上记录 Build ID，便于找到对应符号文件
for f in ./server ./plugins/*.so; do
  printf '%s ' "$f"
  readelf -n "$f" 2>/dev/null | sed -n 's/.*Build ID: //p' | head -1
done
工程建议： 发布二进制时记录文件 SHA256、Build ID、编译镜像、编译器版本和依赖版本；排障时这些比“看起来是同一个包”可靠得多。

11. RPATH/RUNPATH 与动态库搜索路径

AI 应用常把自带库放在 wheel、插件目录或容器特定路径下。RPATH/RUNPATH 决定二进制是否能从相对路径找到这些库。$ORIGIN 表示当前 ELF 文件所在目录，是打包共享库最常用的锚点。

readelf -dW my_extension.so | egrep 'RPATH|RUNPATH'

# 常见输出
# 0x000000000000001d (RUNPATH) Library runpath: [$ORIGIN:$ORIGIN/lib]
写法含义典型用途
$ORIGIN当前 ELF 文件所在目录wheel 内相邻 .so 查找
$ORIGIN/../lib相对上级目录的 lib服务目录下 bin/ 与 lib/ 分离
绝对路径固定机器路径生产中不推荐，容易跨镜像失效
无 RUNPATH依赖系统路径或环境变量更依赖 LD_LIBRARY_PATH 和镜像布局
RUNPATH 更常见
现代链接器默认倾向 RUNPATH。它对间接依赖的传播语义不同于旧 RPATH，排查时要看真实加载链。
readelf 只读不修改
如果需要修改路径，常用 patchelf 或重新链接；本教程只用 readelf 建立证据。
# 验证 wheel 中每个扩展是否使用相对 RUNPATH
find dist_unpacked -type f -name '*.so' -print0 |
  xargs -0 -I{} sh -c 'printf "%s\n" "$1"; readelf -dW "$1" 2>/dev/null | egrep "RPATH|RUNPATH" || true' sh {}
安全提醒： 不要把可被低权限用户写入的目录放进 RPATH/RUNPATH，否则可能造成库劫持。

对比图：AI 扩展加载链上的 readelf 观察点

扩展加载失败时，不要只看 Python 报错。把扩展本体、PyTorch 库、CUDA runtime、驱动库和容器路径拆开验证。

12. CUDA 与 PyTorch 扩展依赖诊断

自定义 CUDA/C++ 扩展常见错误包括：缺 libcudart.so、PyTorch ABI 不匹配、编译器基线过高、未导出 PyInit_*、符号由错误版本库提供。

检查依赖声明

ext=build/lib.linux-x86_64-cpython-311/my_kernel.so
readelf -dW "$ext" | egrep 'NEEDED|RUNPATH|RPATH'

# 期望可能看到
# Shared library: [libc10.so]
# Shared library: [libtorch_cpu.so]
# Shared library: [libcudart.so.12]
# Library runpath: [$ORIGIN:$ORIGIN/../../torch/lib]

检查 Python 初始化函数

# 模块名为 my_kernel 时，CPython 扩展通常需要 PyInit_my_kernel
readelf -Ws "$ext" | grep ' PyInit_'

检查 CUDA fatbin 和未定义符号

# 是否包含 CUDA fatbin 节
readelf -SW "$ext" | grep -E '\.nv_fatbin|\.nvFatBinSegment'

# 未定义符号中是否引用 CUDA/Torch
readelf -Ws "$ext" | c++filt | awk '$7 == "UND" {print}' |
  egrep 'cuda|cudart|torch|c10|at::|nccl' | head -80
驱动库特殊性： libcuda.so.1 通常来自宿主 NVIDIA driver，通过容器运行时挂载进容器；它不一定应该被打进 wheel。readelf 能看到是否声明依赖，但不能替你验证宿主驱动是否兼容。

13. readelf vs ldd/nm/objdump

这些工具有重叠，但观察层级不同。排查时先用低风险、静态的 readelf 建立事实，再按需要补充运行时或反汇编信息。

工具核心视角优点风险/限制
readelf直接解析 ELF 元数据不执行目标程序；ELF 结构覆盖完整不告诉你运行时最终路径和真实加载结果
ldd动态加载器解析依赖能看到解析出的路径对不可信程序有风险；受当前环境影响
nm符号表符号查看简洁，可配 -D对版本、段、动态项覆盖不如 readelf
objdump反汇编与对象信息适合看指令、PLT、反汇编输出更重，排依赖时不是第一选择
patchelf修改 ELF 动态属性可改 RUNPATH/INTERP/NEEDED会修改文件，需备份和验证
# 推荐顺序：先静态事实，再运行时验证
readelf -dW my_extension.so | grep NEEDED
readelf -V my_extension.so | grep GLIBCXX

# 在可信文件和受控环境中再用 ldd 看解析路径
ldd my_extension.so

# 需要指令级分析时再用 objdump
objdump -d my_extension.so | head
安全注意： 不要对不可信二进制直接运行 ldd 或执行文件。先用 file、readelf、隔离容器或沙箱做静态检查。

14. 容器镜像与多架构排障

容器让依赖更可控，也让“构建镜像”和“运行镜像”不一致的问题更隐蔽。readelf 能帮你把制品需求和镜像能力对齐。

# 进入运行镜像后检查服务二进制和扩展
readelf -h /app/server | egrep 'Class|Machine|Type'
readelf -l /app/server | sed -n '/interpreter/p'
readelf -dW /app/plugins/my_backend.so | egrep 'NEEDED|RUNPATH'
readelf -V /app/plugins/my_backend.so | egrep 'GLIBC_|GLIBCXX_|CXXABI_' | sort -u
架构错配
arm64 节点上部署 x86_64 wheel，通常在 Machine 字段直接暴露。
基础镜像过旧
构建机 GCC/libstdc++ 新，运行镜像旧，常表现为 GLIBCXX_* 找不到。
路径错配
多阶段构建漏复制 lib/，NEEDED 存在但最终文件不存在。
# 批量列出镜像目录中所有 ELF 的最高 GLIBCXX 需求
find /app -type f -print0 |
  xargs -0 -I{} sh -c '
    readelf -h "$1" >/dev/null 2>&1 || exit 0
    max=$(readelf -V "$1" 2>/dev/null | grep -o "GLIBCXX_[0-9.]*" | sort -Vu | tail -1)
    [ -n "$max" ] && printf "%-50s %s\n" "$1" "$max"
  ' sh {}
CI 建议： 对发布镜像运行一次 readelf 扫描并保存报告，后续线上错误可直接与报告比对。

安全图：不可信 ELF 的检查边界

readelf 的价值之一是降低第一步检查的攻击面：你可以先知道它想加载什么、要求什么 ABI，再决定是否进入沙箱动态验证。

15. 安全检查与供应链扫描

AI 平台常从外部拿模型插件、推理后端、第三方 wheel 或厂商库。readelf 可作为准入检查的一部分，发现异常加载路径、可执行栈、过高 ABI 需求和奇怪依赖。

# 只读扫描：列出可疑 RPATH/RUNPATH
find artifacts -type f -name '*.so*' -print0 |
  xargs -0 -I{} sh -c '
    paths=$(readelf -dW "$1" 2>/dev/null | egrep "RPATH|RUNPATH" || true)
    echo "$paths" | egrep -q "/tmp|/home|/var/tmp|\\." && printf "%s\n%s\n" "$1" "$paths"
  ' sh {}

# 检查可执行栈
find artifacts -type f -print0 |
  xargs -0 -I{} sh -c '
    readelf -lW "$1" 2>/dev/null | grep GNU_STACK | grep -q "RWE" && echo "$1"
  ' sh {}
检查项信号处理建议
不安全路径RUNPATH 指向 /tmp、用户目录、相对可写目录拒绝或重新打包
可执行栈GNU_STACK 权限含 E追查对象文件和构建参数
异常依赖依赖陌生库或系统外路径核验来源、签名和许可证
ABI 需求过高要求部署基线不存在的版本降低构建基线或升级运行镜像
不要误判： readelf 不是恶意代码检测器。它只能提供结构证据；供应链安全还需要签名、哈希、来源、沙箱、SBOM 和运行时策略。

16. 常见故障排查手册

故障 1：ImportError: libxxx.so: cannot open shared object file

readelf -dW my_extension.so | grep NEEDED
readelf -dW my_extension.so | egrep 'RPATH|RUNPATH'
find /usr /opt /app -name 'libxxx.so*' 2>/dev/null | head

如果 NEEDED 中有库名，但镜像里找不到文件，修复镜像或打包规则；如果文件存在但路径不在搜索范围，检查 RUNPATH、LD_LIBRARY_PATH 和加载器缓存。

故障 2：version `GLIBCXX_3.4.xx' not found

readelf -V my_extension.so | grep -o 'GLIBCXX_[0-9.]*' | sort -Vu | tail
strings /usr/lib/x86_64-linux-gnu/libstdc++.so.6 | grep '^GLIBCXX_' | sort -Vu | tail

如果扩展要求版本高于运行镜像提供能力，需使用更老构建基线重新编译，或升级运行镜像的 libstdc++，但后者要评估系统兼容性。

故障 3：undefined symbol: _ZN...

readelf -Ws my_extension.so | grep '_ZN' | c++filt | head -50
readelf -dW my_extension.so | grep NEEDED

先 demangle 符号，判断它属于 PyTorch、C10、ATen、CUDA、NCCL 还是自研库。然后确认对应库是否在 NEEDED 中、运行时是否加载了兼容版本。

故障 4：wrong ELF class 或 Exec format error

uname -m
readelf -h my_extension.so | egrep 'Class|Machine'

这通常是 32/64 位或 CPU 架构错配，常见于 arm64/x86_64 混合构建、错误 wheel 下载和多架构镜像 manifest 配置问题。

17. 自动化脚本与 CI 检查

把 readelf 纳入 CI 可以提前发现二进制制品不符合部署基线。下面脚本只读扫描，不修改文件，适合作为发布前报告。

#!/usr/bin/env bash
set -euo pipefail

root="${1:-dist}"
baseline_glibcxx="${BASELINE_GLIBCXX:-GLIBCXX_3.4.29}"

find "$root" -type f -print0 |
while IFS= read -r -d '' f; do
  readelf -h "$f" >/dev/null 2>&1 || continue
  echo "== $f =="
  readelf -h "$f" | egrep 'Class:|Machine:|Type:'
  readelf -dW "$f" 2>/dev/null | egrep 'NEEDED|RPATH|RUNPATH' || true
  readelf -V "$f" 2>/dev/null | egrep 'GLIBC_|GLIBCXX_|CXXABI_' | sort -u || true
done
准入规则示例
禁止绝对 RPATH、禁止可执行栈、限制最高 GLIBCXX、要求扩展包含 PyInit_、要求 Build ID 存在。
报告归档
把扫描结果随镜像 tag、Git SHA、构建镜像 digest 一起保存，线上排障时能快速确认制品是否漂移。
脚本风格： 使用 readelf -h 判断文件是否是 ELF，错误输出丢弃；这比按扩展名猜测更可靠。

18. 学习路线与练习任务

  1. 找一个系统命令，例如 /bin/ls，分别运行 readelf -h、-l、-d、-s、-V，把每类输出对应到本教程的概念。
  2. 找一个 Python 包中的 .so，检查它的 PyInit_ 符号、NEEDED 依赖和 GLIBCXX 需求。
  3. 在构建镜像和运行镜像中对同一个扩展执行 readelf -V 与 strings libstdc++.so.6，理解 ABI 基线。
  4. 对 CUDA 扩展检查 .nv_fatbin、libcudart 依赖和 RUNPATH，再对照实际容器中库文件位置。
  5. 把第 17 节脚本接入 CI，先只生成报告，不阻断构建；稳定后再逐步加入准入规则。
最终目标： 看到一个加载错误时，不再盲目改 LD_LIBRARY_PATH，而是能用 readelf 先回答：这个文件是什么、需要什么、声明去哪找、要求什么 ABI、哪些符号还没被满足。
