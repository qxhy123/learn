1. numactl 解决什么问题

现代双路或多路服务器通常不是“所有 CPU 访问所有内存都一样快”。每个 CPU socket 附近有本地内存控制器，访问本地内存快，跨 socket 访问远端内存慢。GPU 也通常挂在某个 PCIe root complex 下，离某些 CPU/NUMA 节点更近。

它能控制
进程可运行在哪些 NUMA 节点或 CPU 核上，以及内存分配优先来自哪些 NUMA 节点。
它不能控制
GPU kernel 调度、CUDA stream、NVLink 路由、PCIe 带宽上限、应用内部线程池策略。
AI Infra 价值
减少远端内存访问、降低 DataLoader 抖动、让 CPU 预处理靠近目标 GPU、让基准测试更可复现。
# 查看机器 NUMA 拓扑
numactl --hardware

# 在 NUMA node 0 的 CPU 上运行，并尽量从 node 0 分配内存
numactl --cpunodebind=0 --membind=0 python train.py

# 只查看当前 shell 的默认 NUMA 策略
numactl --show
边界提醒： numactl 是启动时施加策略的工具。它不能把已经启动的复杂服务“完全无损地重新 NUMA 绑定”，也不能绕过容器或作业系统已经限制的 cpuset。

3. 安装、版本与基本命令

numactl 通常由 Linux 发行版的 numactl 包提供。生产镜像里如果没有它，先确认基础镜像是否允许安装诊断工具，或者在宿主机侧完成拓扑探测。

系统安装命令说明
Ubuntu / Debiansudo apt-get install numactl包含 numactl 与常用 NUMA 库工具。
RHEL / Rocky / Almasudo dnf install numactl老系统可能使用 yum。
SUSEsudo zypper install numactlHPC 环境常已预装。
容器在镜像内安装或从宿主机探测容器内看到的 CPU/内存集合可能已被 cgroup 限制。
# 查看版本与帮助
numactl --version
numactl --help

# 查看 NUMA 拓扑
numactl --hardware

# 查看当前 shell 的策略
numactl --show

# 为一个命令设置策略
numactl --cpunodebind=0 --membind=0 command arg1 arg2
读法提醒： numactl 的节点编号是 NUMA node 编号，不是 GPU 编号，也不是 socket 物理标签；必须通过拓扑命令建立映射。

4. 用 --hardware 读取拓扑

numactl --hardware 是第一条应该运行的命令。它展示可用 NUMA 节点、每个节点包含哪些 CPU、节点内存大小、空闲内存，以及节点间距离矩阵。

$ numactl --hardware
available: 2 nodes (0-1)
node 0 cpus: 0 1 2 3 ... 31
node 0 size: 257652 MB
node 0 free: 188430 MB
node 1 cpus: 32 33 34 35 ... 63
node 1 size: 257914 MB
node 1 free: 201002 MB
node distances:
node   0   1
  0:  10  21
  1:  21  10
字段含义AI Infra 解读
available当前可见 NUMA 节点集合容器或作业系统可能只暴露子集。
node N cpus该节点包含的逻辑 CPU用于选择 DataLoader worker、CPU 预处理线程和服务进程亲和性。
node N size/free该节点总内存与空闲内存--membind 前要确认容量，否则容易分配失败或 OOM。
distances节点间访问成本，数值越小越近本地通常为 10，跨 socket 更高；不是绝对延迟，只是相对距离。
# 结合 lscpu 看 socket、core、thread 映射
lscpu -e=CPU,CORE,SOCKET,NODE,ONLINE

# 更详细的拓扑可用 hwloc/lstopo，但不是 numactl 必需项
lstopo-no-graphics 2>/dev/null | head
常见误读： node 0 free 只是当前空闲量，不等于应用运行期间一直可用；训练作业启动时，缓存、其他容器和 page cache 都可能改变局部内存压力。

5. 用 --show 验证当前策略

numactl --show 显示当前进程的 NUMA 策略、CPU 绑定和内存绑定。它适合在脚本开头打印一次，作为实验记录的一部分。

$ numactl --show
policy: default
preferred node: current
physcpubind: 0 1 2 3 4 5 6 7
cpubind: 0
nodebind: 0
membind: 0 1
# 在绑定环境中检查策略
numactl --cpunodebind=0 --membind=0 bash -lc '
  echo "NUMA policy:"
  numactl --show
  echo "Python sees CPUs:"
  python -c "import os; print(len(os.sched_getaffinity(0)), sorted(os.sched_getaffinity(0))[:8])"
'
验证习惯： 不要只看启动命令。用 numactl --show、taskset -pc $$、/proc/$$/status 和应用日志一起确认最终生效的 CPU 集合。

6. CPU 绑定：--cpunodebind 与 --physcpubind

CPU 绑定有两种常见粒度：按 NUMA 节点绑定，或按具体逻辑 CPU 绑定。AI Infra 通常先按节点绑定，只有在需要精细隔离 worker、网络线程、推理实例时再按 CPU 列表绑定。

选项粒度适合场景示例
--cpunodebind=0NUMA 节点让进程只在 node 0 的 CPU 上运行。numactl -N 0 python serve.py
--physcpubind=0-15逻辑 CPU 列表精确隔离核心、保留部分核心给系统或其他服务。numactl -C 0-15 python worker.py
--localalloc内存策略内存跟随运行 CPU 的本地节点分配。numactl -N 0 -l command
# 让推理服务只跑在 NUMA node 0 的 CPU 上
numactl --cpunodebind=0 python serve.py --model /models/llm

# 更精细：只允许逻辑 CPU 0-15
numactl --physcpubind=0-15 python preprocess.py

# 结合环境变量限制线程库，避免绑定 16 核却开 64 个线程
OMP_NUM_THREADS=16 MKL_NUM_THREADS=16 \
numactl --physcpubind=0-15 --membind=0 python benchmark.py
超线程提醒： 逻辑 CPU 不等于物理核心。绑定前用 lscpu -e 看清 CORE、SOCKET、NODE，否则可能把两个繁忙线程放到同一个物理核心的 sibling 上。

流程图：选择 CPU 与内存策略

策略选择不是“永远 membind”。严格本地能减少远端访问，但也会降低内存弹性，内存不足时更容易失败。

7. 内存策略：--membind、--preferred、--interleave

CPU 亲和性决定线程在哪里运行，内存策略决定匿名页和 mmap 页面倾向从哪里分配。AI 任务中，模型权重加载、tokenizer/feature cache、DataLoader pinned memory 和 CPU 侧 batch buffer 都可能受影响。

策略含义优点风险
--membind=0只允许从 node 0 分配内存局部性强，结果清晰。node 0 内存不足时容易分配失败或触发 OOM。
--preferred=0优先从 node 0 分配，不足时可退到其他节点比 strict bind 更弹性。实际远端比例需要监控确认。
--interleave=0,1在多个节点间交错分配页适合跨节点均摊带宽或避免单节点内存热点。降低本地性，不适合强 GPU 本地输入路径。
--localalloc按当前运行 CPU 所在节点分配适合多线程跟随调度。如果线程迁移，局部性可能变复杂。
# 严格绑定：CPU 和内存都在 node 0
numactl --cpunodebind=0 --membind=0 python train.py

# 更弹性的本地优先策略
numactl --cpunodebind=0 --preferred=0 python infer.py

# 大内存 CPU-only 预处理，跨两个节点交错分配
numactl --cpunodebind=0,1 --interleave=0,1 python build_dataset_cache.py

# 内存跟随本地 CPU
numactl --cpunodebind=0 --localalloc python dataloader_bench.py
--membind 警告： 不要把它当作默认优化开关。先确认目标节点内存容量、page cache、容器 memory limit 和模型加载峰值；否则“优化”可能变成 OOM 或加载失败。

8. AI 训练与推理的启动流程

实用流程是先探测拓扑，再选择 GPU，再绑定靠近该 GPU 的 CPU/内存节点，最后记录策略和性能指标。以下例子假设 GPU0/GPU1 靠近 node 0，GPU2/GPU3 靠近 node 1。

# 1. 记录拓扑
numactl --hardware
nvidia-smi topo -m
lscpu -e=CPU,CORE,SOCKET,NODE,ONLINE

# 2. 单 GPU 推理：让 CPU 预处理靠近 GPU0
CUDA_VISIBLE_DEVICES=0 \
OMP_NUM_THREADS=16 MKL_NUM_THREADS=16 \
numactl --cpunodebind=0 --preferred=0 \
python serve.py --model /models/resnet50 --batch-size 64

# 3. 单机多进程：每个进程靠近自己的 GPU
CUDA_VISIBLE_DEVICES=0 numactl -N 0 -m 0 python worker.py --rank 0 &
CUDA_VISIBLE_DEVICES=1 numactl -N 0 -m 0 python worker.py --rank 1 &
CUDA_VISIBLE_DEVICES=2 numactl -N 1 -m 1 python worker.py --rank 2 &
CUDA_VISIBLE_DEVICES=3 numactl -N 1 -m 1 python worker.py --rank 3 &
wait
训练
关注 DataLoader、CPU augmentation、host-to-device copy、分布式进程与 GPU 映射是否一致。
推理
关注尾延迟、tokenizer 线程、batcher、网络线程、CPU fallback op、KV cache 预处理与服务进程隔离。
记录建议： 每次 benchmark 日志里保留 numactl --hardware、numactl --show、nvidia-smi topo -m、线程环境变量和容器 CPU/memory limit。

用例图：GPU locality 绑定策略

GPU locality 的目标不是让 GPU “属于”某个 NUMA node，而是让 CPU 侧数据生产和 host memory 尽量靠近 GPU 的 PCIe/NVLink 入口。

9. GPU locality：CPU、内存与 GPU 的距离

numactl 不认识 CUDA 设备编号。你需要用 GPU 拓扑工具把 GPU 编号映射到 CPU/NUMA 节点，然后再选择 --cpunodebind 和内存策略。

# NVIDIA GPU 拓扑：看 GPU 之间、GPU 与 CPU affinity 的关系
nvidia-smi topo -m

# 常见输出中可能有 CPU Affinity / NUMA Affinity 列
# GPU0    X    NV4  SYS  SYS  0-31   0
# GPU1   NV4    X   SYS  SYS  0-31   0
# GPU2   SYS  SYS    X   NV4  32-63  1
# GPU3   SYS  SYS   NV4   X   32-63  1

# 从 PCI 设备查看 NUMA 节点，0000:81:00.0 需替换成真实 GPU bus id
cat /sys/bus/pci/devices/0000:81:00.0/numa_node
现象可能原因处理方式
GPU 利用率周期性掉到很低DataLoader 或 CPU 预处理跨 NUMA，数据供给不稳。绑定 worker 到靠近 GPU 的节点，检查 num_workers 与线程数。
H2D copy 时间抖动host buffer 来自远端节点或 page cache 压力不均。尝试 --preferred 或 --membind，并记录 pinned memory 设置。
多 GPU 单机性能不均rank 到 GPU 到 NUMA 节点映射错位。固定 CUDA_VISIBLE_DEVICES、rank、numactl 策略，逐 rank 打印。
MIG 提醒： MIG 实例共享同一物理 GPU 的 PCIe/NUMA 位置。不要把 MIG 设备编号误解成新的物理 locality。

10. DataLoader、worker 与线程库

PyTorch、TensorFlow、JAX 等框架会启动多进程或多线程数据加载、CPU kernel、BLAS/OpenMP 线程。numactl 只限制进程可见的 CPU/内存策略，应用内部还需要合理设置 worker 数、线程数和进程布局。

# PyTorch 单 GPU 训练示例：绑定 CPU/内存并控制线程库
CUDA_VISIBLE_DEVICES=0 \
OMP_NUM_THREADS=8 MKL_NUM_THREADS=8 NUMEXPR_NUM_THREADS=8 \
numactl --cpunodebind=0 --preferred=0 \
python train.py \
  --num-workers 8 \
  --pin-memory true \
  --prefetch-factor 2

# 在程序中打印每个 DataLoader worker 的 CPU affinity，便于确认继承关系
python - <<'PY'
import os
print("main affinity:", sorted(os.sched_getaffinity(0))[:16], "count=", len(os.sched_getaffinity(0)))
PY
num_workers
不是越大越好。过多 worker 会争抢 CPU、内存带宽和文件系统。
pin_memory
可加速 H2D copy，但 pinned host memory 仍来自 NUMA 内存策略影响的节点。
OpenMP/MKL
绑定 8 核却开 64 线程会造成上下文切换和 cache 抖动。
经验顺序： 先固定 GPU 与 NUMA node，再调 num_workers，最后调 OMP_NUM_THREADS、batch size 和 prefetch。不要同时改所有变量。

11. benchmarking 常见陷阱

NUMA 优化经常被误判，因为 benchmark 本身不稳定。必须控制冷启动、page cache、数据路径、线程数、GPU warmup 和并发干扰。

陷阱为什么会误导建议
只跑一次首次加载模型、JIT、page fault 和缓存状态不同。区分 warmup 与测量段，报告均值、P95、P99。
只看吞吐推理服务更关心尾延迟和抖动。同时记录 latency histogram、CPU usage、GPU utilization。
没固定线程数线程库自动选择可能每次不同，且不尊重预期核心数。固定 OMP_NUM_THREADS、MKL_NUM_THREADS。
忽略容器 cpuset容器内 node 编号可见，但 CPU 实际被限制。记录 /sys/fs/cgroup CPU 与 memory 限制。
把 --membind 当万能优化严格绑定可能导致局部 OOM 或更频繁 reclaim。对比 default、preferred、membind、interleave。
# 一个可复现实验骨架
for policy in default preferred membind interleave; do
  echo "== $policy =="
  case "$policy" in
    default)    cmd="python bench.py" ;;
    preferred)  cmd="numactl -N 0 --preferred=0 python bench.py" ;;
    membind)    cmd="numactl -N 0 -m 0 python bench.py" ;;
    interleave) cmd="numactl -N 0,1 -i 0,1 python bench.py" ;;
  esac
  OMP_NUM_THREADS=16 MKL_NUM_THREADS=16 bash -lc "$cmd"
done
判断标准： 好的 NUMA 策略应该在多次运行中稳定改善目标指标，而不是只在某一次 benchmark 中提高平均吞吐。

12. containers、cpuset 与 cgroups

在容器里使用 numactl 时，先理解两层约束：容器运行时或 Kubernetes/Slurm 可能已经通过 cgroup 限制了可用 CPU 和内存节点；numactl 只能在这个集合内再施加策略。

# Docker：显式给 CPU 和内存节点
docker run --rm --gpus '"device=0"' \
  --cpuset-cpus=0-31 \
  --cpuset-mems=0 \
  image:tag \
  numactl --show

# 容器内查看可用 CPU
grep Cpus_allowed_list /proc/self/status
grep Mems_allowed_list /proc/self/status

# cgroup v2 常见位置，具体路径随运行时不同
cat /sys/fs/cgroup/cpuset.cpus.effective 2>/dev/null
cat /sys/fs/cgroup/cpuset.mems.effective 2>/dev/null
场景numactl 表现解释
容器只允许 CPU 0-15--cpunodebind=1 可能失败或没有预期效果node 1 的 CPU 不在 cpuset 中。
只允许 mem node 0--membind=1 不可用cgroup 的 mems_allowed 更高优先级。
Kubernetes CPU request/limit 未绑核进程可能在更多 CPU 间迁移需要 CPU Manager static policy 或运行时 cpuset 配置。
容器警告： 不要只在容器内看 numactl --hardware 就下结论。必须同时看 Cpus_allowed_list、Mems_allowed_list 和调度系统分配。

13. numactl vs taskset

taskset 控制 CPU affinity，numactl 控制 CPU affinity 与 NUMA 内存策略。两者有重叠，但不是等价工具。

维度tasksetnumactl
CPU 绑定强项，按 CPU mask/list。支持按 NUMA node 或物理 CPU 列表。
内存策略不支持。支持 membind、preferred、interleave、localalloc。
NUMA 拓扑查看不支持。--hardware 可查看节点、内存和距离。
适合场景简单 CPU pinning、调试单进程。AI/HPC 中 CPU 与内存本地性一起控制。
# taskset：只限制 CPU，不改变内存策略
taskset -c 0-15 python infer.py

# numactl：限制 CPU，同时设置内存偏好
numactl --physcpubind=0-15 --preferred=0 python infer.py

# 两者不建议混着写，除非你明确知道最终 affinity 的覆盖关系
taskset -c 0-15 numactl --show
选择规则： 只想临时限制 CPU 用 taskset；只要讨论远端内存、GPU locality 或 NUMA node，就用 numactl。

14. systemd、Slurm 与 Kubernetes 场景

生产环境里，numactl 常不是唯一的资源控制层。systemd、Slurm、Kubernetes、Docker 和云平台都可能先限制资源，再由 numactl 细化策略。

systemd 服务

# /etc/systemd/system/infer-node0.service
[Service]
Environment=CUDA_VISIBLE_DEVICES=0
Environment=OMP_NUM_THREADS=16
ExecStart=/usr/bin/numactl --cpunodebind=0 --preferred=0 /opt/venv/bin/python /srv/infer.py
Restart=always

Slurm 作业

# 让 Slurm 分配资源，再在每个 rank 内做清晰映射
srun --gres=gpu:1 --cpus-per-task=16 \
  bash -lc 'numactl --show; numactl -N 0 --preferred=0 python train.py'

Kubernetes

# Kubernetes 中更推荐通过 CPU Manager / Topology Manager 获得拓扑一致分配
# 容器 entrypoint 再使用 numactl 做进程级策略：
numactl --cpunodebind=0 --preferred=0 python serve.py
优先级提醒： 调度系统的资源分配是外层约束。numactl 不能申请调度器没有给你的 CPU、memory node 或 GPU。

15. 排障：性能变慢、OOM、绑定失效

问题 1：--membind 后 OOM
目标节点内存不足、容器 memory limit 太小、模型加载峰值超过单节点容量。改用 --preferred 或扩大 mem node 集合。
问题 2：绑定后 CPU 仍跨节点
外层 cpuset、systemd/Slurm 配置、应用子进程重新设置 affinity。检查 /proc/PID/status。
问题 3：性能没有改善
瓶颈可能在 GPU kernel、网络、存储、Python GIL、batching 或线程过量，不在 NUMA。
问题 4：容器里 node 编号困惑
容器可见节点和宿主拓扑可能被过滤。以 Cpus_allowed_list 与 Mems_allowed_list 为准。
问题 5：DataLoader worker 抖动
worker 数太大、线程库抢核、远端内存、数据集 I/O 路径慢都会造成 GPU 饥饿。
问题 6：rank/GPU 映射错
CUDA_VISIBLE_DEVICES 改变了进程内 GPU 编号。日志里打印 bus id、rank 和 NUMA node。

排障命令模板

# 查看进程 CPU 和内存允许集合
pid=12345
grep -E 'Cpus_allowed_list|Mems_allowed_list' /proc/$pid/status

# 查看进程内存实际分布
numastat -p $pid

# 查看线程在哪些 CPU 上跑
ps -L -o pid,tid,psr,comm -p $pid | head -30

# 看 CPU 迁移和利用率
pidstat -t -p $pid 1

# 在进程内部确认 Python 看到的 affinity
python -c 'import os; print(sorted(os.sched_getaffinity(0)))'
解释 numastat -p： 如果进程大部分内存在远端节点，说明内存策略、初始化时机、线程迁移或 page cache 路径需要继续检查。

16. 生产配方与反模式

配方 A：单 GPU 推理服务

# GPU0 靠近 node 0；使用 preferred 保留内存弹性
CUDA_VISIBLE_DEVICES=0 \
OMP_NUM_THREADS=16 MKL_NUM_THREADS=16 \
numactl --cpunodebind=0 --preferred=0 \
python serve.py --host 0.0.0.0 --port 8000

配方 B：双 socket 四 GPU 单机训练

# 按 GPU locality 启动四个 rank
CUDA_VISIBLE_DEVICES=0 numactl -N 0 --preferred=0 python train.py --rank 0 &
CUDA_VISIBLE_DEVICES=1 numactl -N 0 --preferred=0 python train.py --rank 1 &
CUDA_VISIBLE_DEVICES=2 numactl -N 1 --preferred=1 python train.py --rank 2 &
CUDA_VISIBLE_DEVICES=3 numactl -N 1 --preferred=1 python train.py --rank 3 &
wait

配方 C：CPU-only 特征预处理

# 大内存、吞吐优先，可对比 interleave 与 localalloc
numactl --interleave=0,1 python build_features.py
numactl --cpunodebind=0,1 --localalloc python build_features.py

反模式

  • 在所有命令前机械添加 numactl -m 0 -N 0，不看拓扑和内存容量。
  • 绑定了 8 个 CPU，却让 DataLoader、OpenMP、MKL 总共开出几十到上百线程。
  • 只绑定 CPU，不确认 host memory 和 GPU PCIe locality。
  • 在 Kubernetes 中忽略 CPU Manager / Topology Manager，只靠容器 entrypoint 里的 numactl。
  • 拿一次冷启动 benchmark 结果证明 NUMA 优化有效。

17. 速查表与学习路线

目标命令说明
看拓扑numactl --hardware节点、CPU、内存、距离矩阵。
看当前策略numactl --show适合写入 benchmark 日志。
按节点绑 CPUnumactl --cpunodebind=0 command短写 -N 0。
按 CPU 绑核numactl --physcpubind=0-15 command短写 -C 0-15。
严格内存绑定numactl --membind=0 command短写 -m 0，容量不足风险高。
本地优先numactl --preferred=0 command更弹性，适合生产初始策略。
交错分配numactl --interleave=0,1 command短写 -i 0,1，适合对比实验。
看进程分布numastat -p PID确认内存实际落在哪些节点。

学习路线

  1. 先在一台双路机器上运行 numactl --hardware，读懂 CPU 列表和距离矩阵。
  2. 用 lscpu -e 建立 CPU、core、socket、node 的映射。
  3. 用 nvidia-smi topo -m 建立 GPU 到 NUMA node 的映射。
  4. 对同一 benchmark 对比 default、--preferred、--membind、--interleave。
  5. 在真实训练或推理服务中同时记录吞吐、P99、GPU 利用率、CPU 利用率和 numastat -p。
最终心智模型： NUMA 优化是“让计算、数据和设备更近”的工程手段，不是单个命令开关。先画清拓扑，再做可复现实验。
