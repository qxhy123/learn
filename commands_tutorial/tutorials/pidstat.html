pidstat 深度教程：AI Infra 的进程级 CPU、内存、I/O 与线程排障

这份教程围绕 Linux pidstat 展开，面向训练、推理、数据加载、checkpoint、日志写入和多进程服务排障。它不是参数清单，而是从“按采样窗口读取每个进程/线程的内核计数器差值”这个心智模型出发，讲清楚 -u、-r、-d、-t、-p、-C、采样间隔、进程和线程归因、dataloader 与 checkpoint 瓶颈、sysstat 历史边界、以及与 top、iotop、perf、sar 的配合。

一句话理解： pidstat 是 sysstat 套件里的进程采样器：它按时间间隔读取进程和线程的 CPU、内存、I/O、上下文切换等计数器，并把“系统压力”归因到具体 PID、命令名或 TID。
生产实践： GPU 利用率下降时，不要只看 top 总览。先用 pidstat -urd -h 1 找出哪个训练进程、dataloader worker、解压进程、日志进程或 checkpoint 写入进程在消耗 CPU、内存或 I/O，再用 -t、iostat、perf、strace 下钻。

1. pidstat 是什么

pidstat 的价值是把全机资源压力映射到进程。mpstat 能告诉你 CPU 是否忙，iostat 能告诉你磁盘是否忙，pidstat 则回答“是谁在忙”。在 AI Infra 场景中，这个“谁”可能是主训练进程、PyTorch DataLoader worker、tokenizer、图片解码进程、checkpoint 保存进程、推理 worker、日志 sidecar 或压缩归档进程。

它擅长什么
按 PID 或线程观察 CPU、内存、I/O、上下文切换、页错误等增量指标，适合低开销持续采样和现场归因。
它不擅长什么
不能直接给出函数级热点、SQL/HTTP 语义、GPU kernel 细节或块设备队列深度。需要和 perf、strace、iostat、GPU 工具组合。
它的本质
进程级时间序列：在每个采样窗口内，把 CPU 时间、RSS、读写字节、上下文切换等变化归到 PID/TID。
# 每 1 秒显示进程 CPU、内存、I/O，横向紧凑输出
pidstat -urd -h 1

# 对某个训练进程采样 10 次
pidstat -urd -p 12345 1 10

# 查看所有线程，定位单线程热点
pidstat -ut -p 12345 1

# 按命令名过滤 Python / torchrun / vllm 相关进程
pidstat -urd -C 'python|torchrun|vllm' 1
关键边界： pidstat 是采样工具，不是追踪器。它能告诉你“某 PID 在写很多字节”，但不能直接告诉你“写的是哪个文件”；后者需要 lsof、strace、应用日志或 eBPF 工具。

信息图：pidstat 的整体心智模型

pidstat 的核心不是“当前截图”，而是连续采样窗口里的 PID/TID 变化趋势。

2. 安装、版本与权限

pidstat 通常由 sysstat 包提供。大多数指标普通用户即可查看自己有权限读取的进程；读取其他用户进程、容器宿主机进程或完整命令行时，可能受 /proc 挂载选项、系统安全策略和容器命名空间限制。

环境安装命令确认方式
Ubuntu / Debiansudo apt-get install sysstatpidstat -V
RHEL / CentOS / Rockysudo dnf install sysstat 或 sudo yum install sysstatrpm -q sysstat
SUSEsudo zypper install sysstatpidstat -V
容器调试镜像建议放在 debug 镜像，不强行塞进业务镜像which pidstat
# 查看版本和帮助，确认当前发行版支持的选项
pidstat -V
pidstat --help 2>&1 | sed -n '1,120p'

# 检查 /proc 是否能读取目标进程
ls -ld /proc/12345
test -r /proc/12345/stat && echo readable
版本提醒： sysstat 不同版本的字段、-h、JSON 输出和帮助文本可能略有差异。生产脚本不要硬编码列号，至少要保存表头，并在目标镜像验证。

3. 基本语法与第一批命令

pidstat [options] [interval [count]]

# interval：采样间隔，单位秒
# count：采样次数；省略时持续输出
# -p：指定 PID，ALL 表示所有进程
# -u/-r/-d/-w/-t：选择 CPU、内存、I/O、上下文切换、线程视角
目标命令适用场景
全局巡检pidstat -urd -h 1训练或推理异常时先找“谁”在消耗资源。
指定 PIDpidstat -urd -p 12345 1 30跟踪一个训练进程或推理 worker。
所有线程pidstat -ut -p 12345 1定位单线程热点、线程池不均衡、GIL 或 C++ worker 异常。
只看 I/Opidstat -d -p ALL 1checkpoint、日志、数据集读取、解压、缓存回填。
按命令过滤pidstat -urd -C 'python|java|vllm' 1多租户节点上只看相关进程。
第一条原则： 不带 interval 的一次性输出通常是自进程启动以来的平均值或瞬时汇总，排障价值有限；现场定位优先使用 1 30、5 60 这类连续采样。

4. 输出字段速读

不同选项会显示不同字段。看 pidstat 时要先确认你正在看的是 CPU、内存、I/O 还是线程级表格，不要把不同表的字段混在一起解释。

字段常见来源含义AI Infra 解读
UID所有视图进程所属用户多租户节点上用于区分训练用户、平台服务和 root 进程。
PID/TID进程/线程视图进程 ID / 线程 ID-t 下看到具体线程，方便映射线程池或 DataLoader worker。
%usr/%system-u用户态/内核态 CPU 占比预处理、tokenizer 多在用户态；文件系统、网络和驱动路径多体现为系统态。
%guest/%wait-u虚拟化或等待 CPU 相关字段，视版本而定云上或 CPU 争用场景需要关注；以本机表头为准。
%CPU-u进程在采样窗口内消耗的 CPU 百分比多核进程可超过 100%，线程视图通常更容易看单核热点。
minflt/s/majflt/s-r次要/主要页错误速率majflt/s 高常提示缺页读盘、mmap 数据集或内存压力。
VSZ/RSS/%MEM-r虚拟内存、常驻内存、内存占比看 dataloader 缓存、模型权重、副本、内存泄漏和 OOM 风险。
kB_rd/s/kB_wr/s-d每秒读写字节数据读取、checkpoint、日志、缓存回填的第一归因字段。
kB_ccwr/s-d被取消的写入速率频繁覆盖临时文件或 page cache 写回被取消时可能出现。
cswch/s/nvcswch/s-w自愿/非自愿上下文切换锁竞争、线程过多、调度争用、阻塞 I/O 会改变它们的形态。
# 一次采 CPU、内存、I/O 和上下文切换，保存表头
pidstat -urdw -h 1 10 | tee /tmp/pidstat.$(date +%F-%H%M%S).log
读表纪律： 每次贴证据都保留命令、采样间隔、表头、时间戳、节点名和目标 PID。没有采样窗口的单行截图很难复盘。

5. CPU 视角：pidstat -u

-u 用来观察进程 CPU 时间分布。AI 训练中，GPU idle 但 pidstat -u 显示某些 dataloader worker 或 tokenizer CPU 打满，通常说明输入管线跟不上；如果主进程系统态很高，可能是频繁系统调用、I/O、网络或驱动路径。

# 看所有进程 CPU，按持续采样观察趋势
pidstat -u -p ALL 1

# 看某个训练进程及其线程 CPU
pidstat -ut -p 12345 1

# 只保留 Python 相关进程
pidstat -u -C 'python|torchrun' 1 30
现象常见解释下一步
单个 PID %CPU 接近 100%单线程瓶颈、Python GIL、串行预处理、单 worker 忙加 -t 看线程；用 py-spy/perf 看热点。
多个 dataloader worker 用户态高CPU 预处理重、解码/增强重、tokenizer 重调 num_workers、缓存、预处理离线化、检查 NUMA 亲和性。
系统态高大量系统调用、文件系统、网络、page cache、驱动路径联合 strace -c、iostat、perf top。
平均 CPU 不高但 GPU 等待瓶颈可能是 I/O、锁、RPC、队列或单线程看 -d、-w、-t 和应用日志。
多核解释： 进程 %CPU 可能超过 100%，表示它在多个 CPU 上并行消耗时间。不要把 400% 误读为错误；它可能只是 4 个核被充分使用。

核心流程图：从 GPU 低利用到 PID 归因

GPU 低利用不能直接归因到 CPU 或磁盘；pidstat 的作用是先把压力落到具体 PID/TID。

6. 内存视角：pidstat -r

-r 展示页错误、虚拟内存、RSS 和内存占比。AI 任务里，RSS 持续上升可能来自 dataloader 缓存、batch 队列过深、模型副本、token 缓存、内存泄漏或没有释放的 mmap；majflt/s 升高则经常说明进程在等待磁盘把页面调入内存。

# 按进程观察内存、页错误和 RSS
pidstat -r -p ALL 1

# 观察目标训练进程 5 分钟
pidstat -r -p 12345 5 60

# 和 free/vmstat 联合判断全机内存压力
free -h
vmstat 1 10
指标怎么看下一步
RSS 持续增长常驻内存越来越大检查缓存、prefetch、worker 数、对象生命周期和 batch 队列。
majflt/s 升高需要从磁盘加载页面看 pidstat -d、iostat -xz 1、数据集 mmap 行为。
minflt/s 高但 majflt/s 低大量内存映射或匿名页分配，不一定是磁盘瓶颈结合 RSS、应用阶段和分配器指标判断。
多个 worker RSS 相似且高每个进程复制了数据或模型状态检查 fork/spawn 策略、共享内存、数据缓存和对象复制。
OOM 风险： 看到 RSS 斜率持续上升时，不要等到 OOM Killer 触发才采证。立即保存 pidstat -r、free -h、dmesg -T | tail、应用配置和 batch/prefetch 参数。

7. I/O 视角：pidstat -d

-d 是定位“谁在读写磁盘”的入口。它按进程显示读写速率，但不显示具体文件和设备队列。因此它适合先归因到 PID，再用 lsof、strace、iostat 或应用日志确认文件路径和块设备瓶颈。

# 全进程 I/O 采样
pidstat -d -p ALL 1

# 只看训练相关进程
pidstat -d -C 'python|torchrun|deepspeed' 1

# 找到高写入 PID 后查看它打开的文件
lsof -p 12345 | sed -n '1,80p'

# 同时看设备层是否拥塞
iostat -xz 1
现象可能原因验证动作
kB_rd/s 高且 GPU 等待在线读取数据集、解压、远端挂载慢、缓存未命中看 iostat、数据集路径、page cache、网络存储指标。
kB_wr/s 周期性尖刺checkpoint 保存、日志 flush、tensorboard、缓存回填对齐训练 step 时间；用 lsof 查写入文件。
某平台进程 I/O 高日志采集、备份、镜像层、监控 sidecar 干扰按 UID/CMD 区分业务和平台进程，必要时隔离节点。
pidstat 写入不高但磁盘忙内核写回、其他命名空间、短生命周期进程或设备层拥塞提高采样频率，联合 iotop、iostat、eBPF。
字段边界： pidstat -d 的读写字节来自进程 I/O 计数器，可能与块设备真实物理 I/O 不完全相同，因为 page cache、写回合并、压缩、网络文件系统和容器层都会改变路径。

8. 线程视角：pidstat -t

-t 把进程拆到线程。AI 任务经常表现为“进程平均看不高，但一个线程卡住或打满”：例如 Python 主线程、单个 tokenizer 线程、OpenMP 线程池不均、DataLoader worker 内部单线程解码、推理服务事件循环被阻塞。

# 查看某个进程的线程级 CPU
pidstat -ut -p 12345 1

# 查看线程级上下文切换
pidstat -wt -p 12345 1

# 把 TID 映射到线程名
ps -T -p 12345 -o pid,tid,psr,pcpu,comm,wchan:24
线程现象常见解释后续工具
单个 TID 长期接近 100%串行热点、GIL、事件循环、单 workerperf top -p PID、py-spy top --pid PID。
很多 TID CPU 低但 cswch/s 高频繁阻塞、队列等待、锁竞争、I/O 等待pidstat -w、strace -f -p PID、应用队列指标。
线程集中在少数 CPU亲和性、cgroup cpuset、NUMA 绑定或调度限制taskset -pc PID、numactl -H、ps -o psr。
OpenMP/MKL 线程过多CPU 过订阅，调度开销大检查 OMP_NUM_THREADS、MKL_NUM_THREADS、worker 数。
线程定位技巧： 先用 pidstat -ut -p PID 1 找 TID，再用 ps -T 看线程名和 CPU，最后用采样 profiler 看函数热点。不要一上来就跑重型 tracing。

9. 过滤目标：-p、-C 与命令名

生产节点上进程很多，必须先缩小观察目标。-p 精确指定 PID，-p ALL 展示所有进程，-C 按命令名正则匹配。长命令行、参数、容器内外 PID 映射可能影响过滤结果，必要时先用 ps 确认。

# 找到训练相关 PID
pgrep -af 'torchrun|deepspeed|python.*train'

# 精确观察 PID
pidstat -urd -p 12345 1 30

# 观察所有进程，但可能输出很多
pidstat -urd -p ALL 1 5

# 按命令名过滤，适合快速找 Python/vLLM/Ray worker
pidstat -urd -C 'python|vllm|ray|torchrun' 1
-p PID
最精确，适合已知目标。训练脚本、推理 worker、日志进程都建议先定位 PID。
-p ALL
最全面，但输出噪声大。适合未知现场第一轮扫面。
-C pattern
按命令名过滤，适合快速聚焦，但可能漏掉命令名不含关键词的子进程。
-l
部分版本支持显示命令行参数。对区分多个训练任务有帮助，但注意敏感参数脱敏。
隐私提醒： -l 或 ps -ef 可能暴露 token、数据路径、租户名和模型名。排障记录外发前要脱敏。

10. 采样策略与证据保存

性能问题往往是时间相关的。采样太短会错过 checkpoint 尖刺，采样太粗会抹平 dataloader 抖动。经验上，交互排障用 1 秒采样，复盘证据用 5 到 10 秒采样并持续覆盖一个完整训练 step 或 checkpoint 周期。

场景建议采样理由
现场交互定位pidstat -urd -h 1快速看到尖刺和进程切换。
训练 step 抖动pidstat -urdw -h 1 300覆盖多个 step，能和训练日志对齐。
checkpoint 周期pidstat -urd -h 5 240覆盖 20 分钟，避免输出过大。
低频内存增长pidstat -r -h 30 120看 RSS 趋势，不需要秒级。
归档证据tee /tmp/pidstat.$(date +%F-%H%M%S).log保留原始文本和时间线。
# 推荐证据包：只写 /tmp，不修改业务文件
OUT=/tmp/pidstat-case-$(hostname)-$(date +%F-%H%M%S)
mkdir -p "$OUT"
pidstat -urdw -h 1 300 | tee "$OUT/pidstat-urdw.txt"
mpstat -P ALL 1 300 | tee "$OUT/mpstat.txt"
iostat -xz 1 300 | tee "$OUT/iostat.txt"
ps -eo pid,ppid,uid,psr,pcpu,pmem,comm,args --sort=-pcpu | head -80 > "$OUT/ps-top.txt"
证据对齐： pidstat 输出必须和训练日志、GPU 利用率、checkpoint 时间、Kubernetes 事件、存储监控处在同一时区和同一时间窗口，否则很容易错配根因。

11. AI 训练：dataloader 瓶颈

dataloader 瓶颈通常表现为 GPU 周期性等待、step time 抖动、CPU worker 忙或读盘抖动。pidstat 能把这些现象拆成 CPU、I/O、内存和线程几个方向。

# 观察训练进程和 DataLoader worker
pgrep -af 'python.*train|torchrun|deepspeed'
pidstat -urdwt -C 'python|torchrun|deepspeed' 1

# 如果 worker 是独立 PID，查看每个 worker 的 I/O 和 RSS
pidstat -rd -p ALL 1 | grep -E 'python|DataLoader|PID'
pidstat 现象dataloader 解释优化方向
worker %usr 高，kB_rd/s 不高CPU 预处理、图片解码、tokenization 或数据增强重离线预处理、增加/减少 worker、优化 tokenizer、检查 SIMD/库版本。
worker kB_rd/s 高且 majflt/s 高数据集读取或 mmap 缺页导致等待本地缓存、预热 page cache、优化 shard、检查网络存储。
worker RSS 持续增长缓存失控、prefetch 过深、对象复制调低 prefetch_factor、检查 persistent_workers 和数据缓存。
线程上下文切换高worker 过多、队列/锁竞争、CPU 过订阅减少 worker 或线程数，设置 OMP_NUM_THREADS，绑定 NUMA。
调参不是越大越好： num_workers 增加可能提升吞吐，也可能引入 CPU 过订阅、内存复制、磁盘随机读放大和上下文切换。用 pidstat 看趋势后再调。

12. AI 训练：checkpoint 与日志写入

checkpoint 问题通常不是持续高写入，而是周期性尖刺。pidstat -d 可以把写入尖刺归到主训练进程、异步保存线程、日志进程、对象存储客户端或压缩进程。再把尖刺时间与训练 step、GPU 利用率和存储指标对齐，才能判断是否影响训练。

# 采样覆盖完整 checkpoint 周期
pidstat -d -C 'python|torchrun|deepspeed|wandb|tensorboard' 1 900 | tee /tmp/pidstat-ckpt.log

# 找到高写入 PID 后确认打开文件
lsof -p 12345 | grep -E 'ckpt|checkpoint|pt|safetensors|log|event'

# 对齐块设备层
iostat -xz 1 900 | tee /tmp/iostat-ckpt.log
主进程写入高
同步 checkpoint 可能阻塞训练 loop。考虑异步保存、降低保存频率、分片保存或使用更快本地盘。
日志进程写入高
TensorBoard、wandb、结构化日志或 debug dump 可能放大写入。检查 flush 频率和日志级别。
压缩/上传进程 CPU 高
checkpoint 后处理可能抢 CPU 或网络。用 pidstat -u 和 sar -n DEV 验证。
设备忙但 PID 写入不高
可能是内核写回、文件系统 journal、其他容器或存储层拥塞。继续看 iostat 和宿主机视角。
不要盲目删除 checkpoint： 清理旧 checkpoint 属于破坏性操作。排障时只做观察和证据保存；是否删除、移动或改保存策略，应按任务恢复策略和用户要求执行。

13. 推理服务与多进程服务

推理服务常由主进程、worker、tokenizer、HTTP/gRPC 线程、KV cache 管理、日志 sidecar 和监控进程组成。pidstat 适合用来区分“请求慢是业务 worker 忙、tokenizer 忙、I/O 忙，还是平台进程干扰”。

# vLLM / Triton / Python 推理服务巡检
pidstat -urdwt -C 'vllm|python|triton|uvicorn|gunicorn|ray' 1

# 按 CPU 使用率辅助排序
ps -eo pid,ppid,psr,pcpu,pmem,comm,args --sort=-pcpu | head -30

# 查看线程在哪些 CPU 上运行
ps -T -p 12345 -o pid,tid,psr,pcpu,comm,wchan:24 | sort -k4 -nr | head
服务现象pidstat 线索解释
P99 延迟升高少数 worker %CPU 高请求分布不均、单 worker 阻塞、batching 策略不均衡。
吞吐下降tokenizer 进程 CPU 高前处理成为瓶颈，GPU 侧并未饱和。
周期性卡顿日志或指标进程 kB_wr/s 尖刺同步写日志、指标 flush、采样过细。
worker RSS 接近限制RSS 增长或 majflt/s 增加KV cache、batch 队列、内存碎片或 cgroup 压力。

14. sysstat 历史与 pidstat 的边界

pidstat 属于 sysstat 套件，但这不等于系统默认会长期保存进程级历史。很多发行版启用的 sysstat 历史主要由 sadc/sar 采集系统级 CPU、内存、磁盘、网络等指标；它通常不能在事故后凭空还原某个 PID 在昨晚的 CPU/I/O 时间序列。若需要进程级历史，要在事故前主动采集 pidstat 或接入监控/eBPF/agent。

问题答案实践建议
pidstat 能直接读 /var/log/sa/saDD 还原 PID 历史吗？通常不能。sar 历史多是系统级，不是完整 PID 历史。事故复盘先用 sar 找窗口，再看是否有单独保存的 pidstat 日志。
sysstat 历史还有价值吗？有。它能告诉你事故窗口 CPU、I/O、内存、网络是否异常。用 sar -u/-d/-r/-n 定位时间和资源维度，再复现时用 pidstat 归因到进程。
如何保存进程级历史？定时运行 pidstat、业务监控、eBPF agent 或平台可观测性。保存表头、采样间隔、节点名和时间戳，控制数据量和隐私。
# sar 找系统级事故窗口
sar -u -f /var/log/sa/sa24 -s 02:00:00 -e 03:00:00
sar -d -p -f /var/log/sa/sa24 -s 02:00:00 -e 03:00:00

# 复现期间主动保存进程级证据
pidstat -urdw -h 1 1800 > /var/log/pidstat-repro.$(date +%F-%H%M%S).log
历史边界： 如果事故已经过去且没有 pidstat/agent 进程级采样，不能仅凭 sar 精确断言“某个 PID 是根因”。最多能说系统级某维度异常，并列出仍需复现验证的候选进程。

15. pidstat vs top/iotop/perf/sar

工具核心价值不适合典型命令
pidstat进程/线程级 CPU、内存、I/O、上下文切换时间序列函数级热点、具体文件路径、历史回放pidstat -urdwt -h 1
top/htop交互式排序和即时观察严谨证据保存、细分 I/O 和线程历史top -H -p PID
iotop交互式 I/O 排名无权限环境、长期归档、系统级设备队列解释sudo iotop -oPa
perf函数级 CPU 热点、内核/用户态采样初筛进程、内存 RSS 趋势、I/O 字节归因perf top -p PID
sar系统级历史和多维指标回放事故后精确还原每个进程sar -u/-d/-r/-n -f saDD
iostat块设备吞吐、await、util、队列归因到进程iostat -xz 1
组合套路： sar 找历史窗口，mpstat 看 CPU 分布，pidstat 找 PID/TID，iostat 验证设备，perf/strace 解释函数或系统调用。

16. 容器、cgroup 与 PID 命名空间

容器里运行 pidstat 时，看到的 PID、进程集合和资源限制可能与宿主机不同。AI 平台常有 Kubernetes pod、sidecar、runtime shim、GPU operator、日志 agent、存储 CSI 组件；若只在容器内看，很容易漏掉宿主机或同节点其他容器的干扰。

# 容器内查看自己的 PID 命名空间视角
pidstat -urd -p ALL 1
cat /proc/1/cgroup

# 宿主机上按容器相关命令粗筛
ps -eo pid,ppid,uid,pcpu,pmem,comm,args | grep -E 'containerd|python|vllm|kubelet'

# Kubernetes 场景：先从平台命令拿 pod 和容器，再进宿主机确认 PID
kubectl top pod -A
kubectl describe pod POD -n NAMESPACE
PID 映射
容器内 PID 123 不一定是宿主机 PID 123。需要通过 runtime、crictl inspect、nsenter 或平台工具映射。
CPU 限制
进程 %CPU 要结合 cgroup CPU limit/cpuset 解读。容器限 4 核时，400% 可能已经满载。
内存限制
RSS 接近容器限制比接近宿主机内存更危险。容器 OOM 可能不体现在全机 free 里。
I/O 归因
容器内进程 I/O 与宿主机块设备 I/O 之间可能隔着 overlayfs、网络盘、CSI 和 page cache。
视角声明： 排障报告里明确写“pidstat 在容器内运行”还是“在宿主机运行”。两个视角输出不一致并不罕见。

17. 常见故障模式速查

GPU 空但 CPU 单进程 100%
常见于串行预处理、Python GIL、单 tokenizer、数据增强瓶颈。用 pidstat -ut -p PID 1 拆线程。
GPU 周期性掉到 0，写入尖刺
常见于同步 checkpoint 或日志 flush。用 pidstat -d 对齐 step 时间。
RSS 缓慢上升
常见于 dataloader 缓存、prefetch、队列积压、内存泄漏。用 pidstat -r 30 看斜率。
majflt/s 高
常见于 mmap 数据集、内存压力或冷 page cache。联合 iostat 和 vmstat。
上下文切换很高
常见于线程过多、锁竞争、短任务切换、过度并行。看 pidstat -w -t。
pidstat 看不到明显高 PID
可能是采样太粗、短生命周期进程、内核线程、宿主机其他容器或设备层瓶颈。提高频率并换宿主机视角。
系统态高但用户态不高
常见于系统调用、网络栈、文件系统、驱动路径。下一步用 strace -c 或 perf。
多 worker 都低但训练慢
瓶颈可能在远端服务、队列、GPU 同步、分布式通信或应用锁。结合日志、NCCL、网络指标。

18. 生产排障工作流

下面是一套保守、可复盘、低风险的 pidstat 工作流。它只采集和保存证据，不修改业务配置，不杀进程，不清理文件，适合先在事故现场执行。

第一步：确认目标和时间

# 记录节点、时间、负载和目标进程
date -Is
hostname -f 2>/dev/null || hostname
uptime
pgrep -af 'torchrun|deepspeed|python|vllm|triton'

第二步：采集并行证据

OUT=/tmp/ai-infra-pidstat-$(hostname)-$(date +%F-%H%M%S)
mkdir -p "$OUT"

pidstat -urdwt -h 1 300 | tee "$OUT/pidstat.txt" &
PIDSTAT_PID=$!
mpstat -P ALL 1 300 | tee "$OUT/mpstat.txt" &
MPSTAT_PID=$!
iostat -xz 1 300 | tee "$OUT/iostat.txt" &
IOSTAT_PID=$!

wait "$PIDSTAT_PID" "$MPSTAT_PID" "$IOSTAT_PID"

第三步：形成证据链

问题证据不能跳过的反证
谁消耗 CPU？pidstat -u/-t 中持续高的 PID/TIDmpstat -P ALL 是否显示 CPU 不均衡或全机饱和。
谁消耗内存？pidstat -r 的 RSS 斜率和 majflt/sfree、cgroup limit、OOM 日志是否支持。
谁在读写？pidstat -d 的读写尖刺iostat 是否显示设备层拥塞；lsof 是否确认文件。
是否线程/调度问题？pidstat -t/-w、ps -Tcpuset、线程数、OpenMP/MKL 环境变量是否一致。
安全边界： 排障命令可以采集证据；杀进程、删数据、改 checkpoint 目录、改 worker 数、调系统参数都属于行为变更。除非任务明确要求，否则先形成证据链再改。

19. 学习路线与练习任务

第一阶段：会看

  • 掌握 pidstat -u 1、pidstat -r 1、pidstat -d 1、pidstat -w 1。
  • 知道 interval count 是采样窗口，不是简单刷新频率。
  • 能解释 %usr、%system、RSS、majflt/s、kB_rd/s、kB_wr/s。

第二阶段：会归因

  • 能用 -p、-C 找目标进程。
  • 能用 -t 把进程拆到线程。
  • 能把 pidstat 输出和训练 step、checkpoint、GPU 指标对齐。

第三阶段：会联动

  • CPU 根因用 perf 或语言 profiler 下钻。
  • I/O 根因用 iostat、lsof、strace 验证。
  • 历史问题用 sar 定窗口，复现时用 pidstat 定进程。

练习

  1. 启动一个 CPU 密集任务，用 pidstat -u -p PID 1 10 观察。
  2. 复制一个大文件到 /tmp，用 pidstat -d -p ALL 1 找写入进程。
  3. 运行一个 Python 多线程/多进程小程序，用 pidstat -t 对比 PID 和 TID。
  4. 用 pidstat -r 观察一个逐步分配内存的进程 RSS 变化。
  5. 把 pidstat、mpstat、iostat 同时保存 60 秒，并写 5 行以内的结论。
# 练习环境：只使用 /tmp
mkdir -p /tmp/pidstat-demo

# CPU 练习：启动后台 CPU 消耗进程
python3 - <<'PY' &
import time
end = time.time() + 60
x = 0
while time.time() < end:
    x = (x * 3 + 1) % 1000003
PY
DEMO_PID=$!
pidstat -u -p "$DEMO_PID" 1 5
wait "$DEMO_PID"

# I/O 练习：写一个临时文件，然后清理
dd if=/dev/zero of=/tmp/pidstat-demo/blob bs=1M count=256 status=progress
rm -f /tmp/pidstat-demo/blob
