mlnx_qos 深度教程：AI Infra RoCE 无损网络的主机 QoS 配置

这份教程面向 AI Infra、GPU 集群、RoCEv2、NCCL 和 RDMA 运维场景，讲清楚 mlnx_qos 如何在 Mellanox/NVIDIA 网卡本地主机侧查看和配置 QoS：PFC、ETS、DSCP/PCP trust、DSCP 到 priority、UP 到 TC、rate limit、DCBX 控制模式，以及它与 ethtool、mlxlink、dcb、tc 的边界。重点不是背选项，而是建立“应用标记 → 主机映射 → 网卡队列 → 交换机队列 → 无损/拥塞行为”的生产心智模型。

一句话理解： mlnx_qos 是 NVIDIA/Mellanox 网卡本地主机侧的 QoS 观察和配置入口；它把 “priority 0-7” 映射到硬件 TC，并为 TC 设置 PFC、调度算法、带宽保证和速率限制。

1. mlnx_qos 是什么

mlnx_qos 是 MLNX_OFED/MLNX_EN 环境中用于 Mellanox/NVIDIA 网卡 QoS 的集中式工具。它直接和驱动交互，用来查看当前 QoS 映射，也可以设置本地主机侧的 PFC、UP-to-TC、TC 调度算法、ETS 带宽保证、TC rate limit、DCBX 模式、trust state 和 DSCP 到 priority 映射。

它解决的问题
主机侧“流量标记如何进入硬件队列、哪个队列暂停、哪个队列有带宽保证”。
它不解决的问题
交换机端口 QoS、ECN/WRED 策略、布线错误、链路 FEC 错误、NCCL 算法选择。
它的风险点
错误 PFC 会造成 head-of-line blocking，错误 ETS 会饿死业务队列，错误 trust 会让 DSCP 标记完全失效。
# 查看指定网口的 QoS 状态，默认是读操作
sudo mlnx_qos -i ens1f0

# 查看所有接口的 TC/QoS 信息
sudo mlnx_qos -i ens1f0 -a

# 查看帮助，确认当前 OFED/EN 版本支持的选项
mlnx_qos --help
版本提醒： 不同驱动、固件、网卡代际、发行版打包路径可能不同。生产脚本不要假设输出格式永久稳定，至少要记录 mlnx_qos --version、驱动版本和固件版本。

信息图：AI Infra RoCE QoS 的端到端模型

RoCE 无损不是单个命令的结果，而是应用标记、主机映射、网卡队列、交换机队列和拥塞控制共同一致的结果。

3. 环境、权限与适用范围

mlnx_qos 通常来自 NVIDIA/Mellanox OFED 或 MLNX_EN 的工具包。它面向 Mellanox/NVIDIA 以太网/RoCE 网卡；如果机器只装了内核 inbox 驱动或发行版裁剪包，命令可能不存在或能力受限。

检查项命令说明
命令是否存在command -v mlnx_qos有些系统路径可能在 /usr/sbin 或 OFED 脚本目录。
网卡与驱动ethtool -i ens1f0确认驱动、固件、bus-info；常见驱动名为 mlx5_core。
链路状态ethtool ens1f0QoS 调整前先确认速率、双工、link detected。
RDMA 设备rdma link show确认 RoCE 设备和 netdev 绑定关系。
权限sudo mlnx_qos -i ens1f0读取通常也建议用 root，写入必须 root。
# 最小环境快照：变更前必须留存
date -Is
hostname -f
uname -r
command -v mlnx_qos
mlnx_qos --version || true
ethtool -i ens1f0
sudo mlnx_qos -i ens1f0
BlueField/DPU 提醒： 在嵌入式主机模式等 DPU 场景中，不要在 host 和 Arm 侧同时用 mlnx_qos 管同一对象；官方文档提示这类双边配置可能导致未定义行为。

4. 只读读取：先看清当前状态

最安全的第一步永远是读取，不是修改。mlnx_qos -i <iface> 会显示 DCBX mode、priority trust state、DSCP 映射、PFC 开关、每个 TC 的 rate limit、TSA 和绑定的 priority。

# 读取当前 QoS 配置
sudo mlnx_qos -i ens1f0

# 输出保存成变更前基线
sudo mlnx_qos -i ens1f0 | tee /var/tmp/ens1f0.mlnx_qos.before.txt

# 同时抓取邻接和链路证据
ip -br link show dev ens1f0
ethtool -S ens1f0 | egrep -i 'pause|pfc|prio|disc|drop|ecn|rx_disc|tx_disc' || true
rdma link show | grep ens1f0 || true
读输出时的顺序： 先看 Priority trust state，再看 dscp2prio mapping 或 PCP 路径，再看 PFC 哪些 priority enabled，最后看 TC 的 tsa、bw、ratelimit 和 priority 归属。

5. 字段解读：trust、PFC、TC、TSA

不同版本输出略有差异，但核心字段相对稳定。生产排障时要把它翻译成一句话：“哪些包会进哪个 priority，哪些 priority 会 pause，哪些 TC 会按 ETS 或 strict 出队”。

字段含义AI Infra 关注点
DCBX modeQoS/ETS/PFC 由 OS 还是固件/协商控制。如果被 firmware 或 LLDP/DCBX 控制，本地手改可能不生效或被覆盖。
Priority trust state主机按 PCP 还是 DSCP 推导 priority。RoCEv2 常见做法是 trust DSCP；VLAN/PCP 方案则要 trust PCP 并保证 tag 存在。
dscp2prio mappingDSCP 0-63 到 priority 0-7 的映射。NCCL/RDMA 使用的 DSCP 必须落到启用 PFC 的 priority。
PFC configurationpriority 0-7 是否启用 Priority Flow Control。RoCE lossless 通常只给 RDMA priority 开 PFC，不建议所有 priority 全开。
tc硬件 Traffic Class，承载实际调度、带宽保证、限速。UP-to-TC 错了会让 RDMA 进普通队列，或普通流量挤入无损队列。
tsaTransmission Selection Algorithm，常见 ets、strict、vendor。strict 用错会产生饥饿；ETS 用来做最小带宽保证。
ratelimitTC 最大速率限制，单位常为 Gbps。误设会让 NCCL 带宽固定掉坑；无限制通常显示 unlimited 或配置 0。
# 快速抽取重点行，便于巡检日志阅读
sudo mlnx_qos -i ens1f0 | egrep -i 'DCBX|trust|dscp|PFC|enabled|tc:|priority:|ratelimit|tsa|bw'

流程图：DSCP/PCP/UP/TC 映射链

PFC 的开关粒度是 priority，而 ETS/ratelimit 的调度粒度是 TC；mlnx_qos 的核心价值就是把两者显式连起来。

6. DSCP/PCP/UP/TC 映射链

RoCEv2 运行在 IP/UDP 上，数据包可以携带 DSCP；传统二层 QoS 也可以依赖 VLAN PCP。主机侧到底信谁，由 --trust=dscp 或 --trust=pcp 决定。

DSCP 路线
适合 L3 fabric、跨三层 ECMP 的 AI 集群。需要应用或 RDMA 栈打 DSCP，主机 trust DSCP，交换机 trust DSCP 并映射到同一无损队列。
PCP 路线
适合明确使用 VLAN tag 的二层设计。需要 VLAN PCP 标记存在，主机 trust PCP，交换机 trust L2/PCP。
# 读取 trust state 和 dscp2prio
sudo mlnx_qos -i ens1f0 | sed -n '/Priority trust state/,$p' | head -40

# 设置主机信任 DSCP；变更前务必保存当前输出
sudo mlnx_qos -i ens1f0 --trust=dscp

# 将 DSCP 26 映射到 priority 3
sudo mlnx_qos -i ens1f0 --dscp2prio=set,26,3

# 删除 DSCP 26 的自定义映射，回到默认映射
sudo mlnx_qos -i ens1f0 --dscp2prio=del,26,3
SR-IOV 提醒： trust state 需要在启用 VF 前规划好，很多环境要求先设置再创建/暴露 VF，否则 VF 继承行为可能不符合预期。

7. PFC：RoCE 无损的暂停语义

PFC（Priority Flow Control）是按 priority 暂停发送的二层机制。它常用于 RoCE lossless 队列，让 RDMA 包在短时拥塞时不被直接丢弃。但 PFC 不是免费的：配置错误会导致 pause 扩散、队头阻塞，甚至让整个 fabric 抖动。

做法为什么
只给 RDMA priority 开 PFC避免普通 TCP、管理流量、存储流量都进入无损暂停域。
主机和交换机同一 priority 开 PFC单边开启没有端到端意义，甚至会误导排障。
配合 ECN/拥塞控制现代 RoCE fabric 通常用 ECN/CNP 缓解持续拥塞，PFC 只兜底短时突发。
关注 pause/PFC 计数少量 pause 可接受，持续增长通常意味着拥塞、buffer 或流量分类有问题。
# 只读：查看当前 PFC bitmap
sudo mlnx_qos -i ens1f0 | sed -n '/PFC configuration/,+3p'

# 示例：只在 priority 3 开 PFC
# 列表从 priority 0 到 7，1 表示启用，0 表示关闭
sudo mlnx_qos -i ens1f0 --pfc=0,0,0,1,0,0,0,0

# 变更后读取确认
sudo mlnx_qos -i ens1f0 | sed -n '/PFC configuration/,+3p'
不要盲目全开： --pfc=1,1,1,1,1,1,1,1 看起来“更无损”，实际可能把所有流量放进暂停域，是 AI 集群网络抖动的常见事故来源。

8. ETS、strict 与 rate limit

TC 承载实际出队调度。--tsa 设置每个 TC 的传输选择算法，--tcbw 给 ETS TC 设置最小带宽保证，--ratelimit 给 TC 设置最大速率限制。NVIDIA 文档说明 rate limit 为 0 表示不限制。

机制用途风险
ets给多个 TC 分配最小带宽保证；空闲份额可被其他 TC 使用。ETS 百分比对 ETS TC 求和必须合理，和交换机端调度要一致。
strict低带宽、低延迟控制流量可用严格优先级。高优先级 strict 队列流量过大时会饿死低优先级队列。
vendor由厂商/固件策略处理。含义依赖设备和驱动，不适合写死为跨集群标准。
ratelimit限制某个 TC 最大 Gbps。误设会让 NCCL all-reduce 吞吐固定下降。
# 示例：UP 0-7 分别映射到 TC 0-7，保持一一对应，便于排障
sudo mlnx_qos -i ens1f0 --prio_tc=0,1,2,3,4,5,6,7

# 示例：TC0-6 用 ETS，TC7 strict；ETS TC 的带宽保证合计 100
sudo mlnx_qos -i ens1f0 \
  --tsa=ets,ets,ets,ets,ets,ets,ets,strict \
  --tcbw=10,10,10,40,10,10,10,0

# 示例：所有 TC 不限速；0 表示 unlimited
sudo mlnx_qos -i ens1f0 --ratelimit=0,0,0,0,0,0,0,0
AI 集群常见策略： 给 RDMA 数据队列一个明确 TC 和 ETS 份额，给控制/管理流量保留可用带宽，避免把所有资源都交给单一无损队列。

9. RoCE 与 NCCL 性能路径

NCCL/RDMA 性能问题经常被误判为“GPU 慢”或“NCCL 参数错”。实际上，RoCE lossless 链路上的队列映射、PFC、ECN、buffer 和交换机队列不一致，会直接表现为 all-reduce 带宽下降、尾延迟尖刺、训练 job 偶发 timeout。

吞吐掉坑
检查 RDMA DSCP 是否进了预期 priority/TC，是否误设 TC rate limit，是否存在 FEC/PCS 错误。
尾延迟抖动
检查 PFC pause 是否持续增长，交换机队列是否拥塞，ECN/CNP 是否过多或过少。
NCCL timeout
检查链路 flap、RDMA CM 路径、MTU、路由、PFC storm，以及多 rail 配置是否一致。
# 结合 NCCL/RDMA 排查时的主机侧证据
sudo mlnx_qos -i ens1f0
ethtool -S ens1f0 | egrep -i 'pfc|pause|ecn|cnp|drop|disc|err|crc|fec'
rdma link show
ibv_devinfo -v | egrep -i 'hca_id|transport|link_layer|active_mtu|phys_port_cnt'

# 跑压测前后抓两次计数，用 diff 看 PFC/drop 是否增长
ethtool -S ens1f0 > /var/tmp/ens1f0.stats.before
# run nccl-tests / ib_write_bw / application workload here
ethtool -S ens1f0 > /var/tmp/ens1f0.stats.after
diff -u /var/tmp/ens1f0.stats.before /var/tmp/ens1f0.stats.after | egrep -i 'pfc|pause|drop|disc|ecn|cnp|err' || true
不要只看主机： RoCE 训练流量是双向、多路径、跨交换机的。主机 mlnx_qos 正确只能证明本端分类和队列策略正确，不能证明交换机 buffer/ECN/PFC 完整正确。

10. 读操作与改操作的边界

mlnx_qos -i 是读操作；带 --pfc、--trust、--dscp2prio、--prio_tc、--tsa、--tcbw、--ratelimit、--dcbx、--cable_len 等通常是改操作。AI 集群里应把两类命令严格分开。

类别示例生产处理方式
读取mlnx_qos -i ens1f0可以纳入巡检，建议保存到日志。
映射变更--trust、--dscp2prio、--prio_tc必须和应用标记、交换机 trust/map 一起评审。
无损变更--pfc必须确认交换机同 priority PFC、buffer、ECN。
调度变更--tsa、--tcbw、--ratelimit必须评估普通流量、存储流量、管理流量的带宽影响。
控制权变更--dcbx=os 或 --dcbx=fw会改变谁拥有 QoS 控制权，需避免和 lldpad/lldptool/dcb 工具并行抢配置。
# 推荐：把只读命令和写命令分成不同脚本
sudo mlnx_qos -i ens1f0 > /var/tmp/qos.readonly.txt

# 写命令必须带有工单、预期、回滚、验证
# sudo mlnx_qos -i ens1f0 --trust=dscp --dscp2prio=set,26,3

流程图：安全变更工作流

QoS 变更具有跨主机、跨交换机的系统性影响；必须像网络变更一样管理，而不是像本机 sysctl 一样随手改。

11. 安全变更工作流

推荐步骤

  1. 保存主机侧基线：mlnx_qos、ethtool -i、ethtool -S、rdma link。
  2. 保存交换机侧基线：端口 trust、PFC、buffer、ECN、队列调度、PFC/drop counters。
  3. 明确目标链路：例如 “DSCP 26 → priority 3 → TC 3 → PFC on → ETS 40%”。
  4. 单机或单 rack 灰度，跑固定的 NCCL/RDMA 压测和真实作业。
  5. 对比变更前后吞吐、尾延迟、drop、pause、CNP/ECN 计数。
  6. 通过后再扩大范围；失败时立即按保存的基线回滚。
# 变更前基线目录
IF=ens1f0
TS=$(date +%Y%m%d-%H%M%S)
DIR=/var/tmp/qos-${IF}-${TS}
sudo mkdir -p "$DIR"

sudo mlnx_qos -i "$IF" | sudo tee "$DIR/mlnx_qos.before.txt"
ethtool -i "$IF" | sudo tee "$DIR/ethtool-i.txt"
ethtool -S "$IF" | sudo tee "$DIR/ethtool-S.before.txt"
rdma link show | sudo tee "$DIR/rdma-link.txt"

# 变更后再次采集，必须能 diff
sudo mlnx_qos -i "$IF" | sudo tee "$DIR/mlnx_qos.after.txt"
ethtool -S "$IF" | sudo tee "$DIR/ethtool-S.after.txt"
diff -u "$DIR/mlnx_qos.before.txt" "$DIR/mlnx_qos.after.txt" || true
禁止无回滚变更： 如果你无法把 mlnx_qos 当前状态翻译成可执行的回滚命令，不要在生产批量执行写操作。

12. 主机与交换机对齐

RoCE QoS 最常见失败点不是主机命令写错，而是主机和交换机对“同一个字段”的解释不一致。主机 trust DSCP，交换机 trust PCP；主机 DSCP 26 到 priority 3，交换机 DSCP 26 到 queue 4；主机 priority 3 开 PFC，交换机 priority 4 开 PFC，都会造成隐蔽故障。

对齐项主机侧证据交换机侧证据
trust 模式Priority trust state: dscp/pcp端口 QoS trust L3/DSCP 或 L2/PCP。
DSCP/PCP 到 priority/queuedscp2prio mapping、VLAN egress map。DSCP-to-traffic-class、PCP-to-priority 或 QoS map。
PFC priorityPFC configuration enabled接口 PFC enabled priorities、PFC Rx/Tx counters。
调度/ETStc: ... tsa: ets, bw队列 scheduler、ETS bandwidth、strict priority。
拥塞控制CNP/ECN 相关网卡计数。ECN marking、WRED/threshold、buffer occupancy。
# 主机侧：确认 DSCP 26 是否映射到目标 priority
sudo mlnx_qos -i ens1f0 | sed -n '/dscp2prio mapping:/,/Cable len:/p'

# 主机侧：确认 PFC priority 和 TC 归属
sudo mlnx_qos -i ens1f0 | sed -n '/PFC configuration:/,$p'

# 交换机侧命令因厂商不同而不同，至少要能回答：
# 1. 端口 trust DSCP 还是 PCP？
# 2. DSCP 26/PCP 3 映射到哪个 queue？
# 3. 该 queue/priority 是否启用 PFC？
# 4. 该 queue 的 ECN/PFC/drop counter 是否增长？
最佳实践： 把主机侧和交换机侧配置写成同一张“QoS 意图表”，例如 DSCP 26、priority 3、TC 3、lossless queue、ETS 40%，而不是分散在不同团队的命令片段里。

对照图：主机和交换机必须同语义

对齐不是“都开了 PFC”，而是同一个业务流在两端都被分类到同一类 lossless priority/queue。

13. 常用命令模板

下面模板用于理解参数形态，不应不经评审直接套用到生产。实际 DSCP、priority、TC、ETS 百分比应来自集群网络设计。

读取与审计

# 查看单接口
sudo mlnx_qos -i ens1f0

# 查看所有 TC 信息
sudo mlnx_qos -i ens1f0 -a

# 输出适合贴进工单的摘要
sudo mlnx_qos -i ens1f0 | egrep -i 'DCBX|trust|PFC|enabled|tc:|priority:|dscp'

DSCP 路线示例

# 目标意图：DSCP 26 → priority 3 → TC 3；priority 3 开 PFC
sudo mlnx_qos -i ens1f0 --trust=dscp
sudo mlnx_qos -i ens1f0 --dscp2prio=set,26,3
sudo mlnx_qos -i ens1f0 --prio_tc=0,1,2,3,4,5,6,7
sudo mlnx_qos -i ens1f0 --pfc=0,0,0,1,0,0,0,0
sudo mlnx_qos -i ens1f0

ETS 与限速示例

# TC3 作为 RDMA 队列拿到 40% 最小保证，其余 ETS TC 合理分配
sudo mlnx_qos -i ens1f0 \
  --tsa=ets,ets,ets,ets,ets,ets,ets,strict \
  --tcbw=10,10,10,40,10,10,10,0

# 确认没有误限速
sudo mlnx_qos -i ens1f0 --ratelimit=0,0,0,0,0,0,0,0

DCBX 控制权

# 查看当前 DCBX mode
sudo mlnx_qos -i ens1f0 | grep -i 'DCBX mode'

# OS 控制示例：不要与 lldpad/lldptool 并行抢配置
sudo mlnx_qos -i ens1f0 --dcbx=os

# firmware 控制示例：通常意味着本地软件不再直接控制部分 QoS 项
sudo mlnx_qos -i ens1f0 --dcbx=fw
参数长度： --pfc 是 8 个 priority 的 0/1 列表；--prio_tc 是 8 个 UP 对应 TC 的列表；--tsa、--tcbw、--ratelimit 要和当前支持的 TC 数量及工具要求匹配。

14. mlnx_qos vs ethtool/mlxlink/dcb/tc

AI Infra 排障需要多个工具互补。mlnx_qos 负责“主机 QoS 意图和网卡 TC 配置”，但链路物理层、驱动统计、标准 DCB 接口、Linux 队列规则分别由其他工具覆盖。

工具主要看什么和 mlnx_qos 的关系
mlnx_qosPFC、UP-to-TC、TSA/ETS、rate limit、trust、DSCP map、DCBX。主机侧 Mellanox/NVIDIA QoS 的核心工具。
ethtool驱动/固件版本、link、offload、网卡统计计数。验证 PFC/pause/drop/error 是否真实发生。
mlxlink物理链路、FEC、模块、误码、SerDes 相关信息。排除“QoS 看似错误，其实物理链路有错”的情况。
dcb/lldptoolLinux 标准 DCB/LLDP/DCBX 配置和协商。如果 DCBX 由 OS/LLDP 管，需避免和 mlnx_qos 抢控制权。
tcLinux qdisc、mqprio、skb priority 映射、过滤器。影响 sk_prio/UP 路径，尤其是 RoCE 或容器流量分类。
rdma/ibv_devinfoRDMA link、GID、RoCE、MTU、HCA 信息。确认业务确实走 RDMA/RoCE 设备和预期 netdev。
# 常用组合：QoS + 统计 + 物理链路
sudo mlnx_qos -i ens1f0
ethtool -i ens1f0
ethtool -S ens1f0 | egrep -i 'pfc|pause|drop|disc|err|fec|ecn|cnp'
mlxlink -d /dev/mst/mt4129_pciconf0 -p 1 -c 2>/dev/null || true
rdma link show
边界判断： 如果 mlnx_qos 显示分类正确，但 ethtool -S 有 CRC/FEC/PCS 错误，优先查光模块、线缆、速率、FEC，而不是继续改 PFC。

排障图：NCCL/RDMA 慢或超时从哪里开始

先排除物理层和分类链，再看 PFC/ECN/buffer，最后才把问题归因到通信库参数。

15. 排障决策树

症状 1：mlnx_qos 设置后看起来没生效

  • 检查 DCBX mode，如果由 firmware 或 DCBX/LLDP 控制，本地软件配置可能被拒绝或覆盖。
  • 检查是否有 lldpad、lldptool、NetworkManager dispatcher、集群初始化脚本在重写配置。
  • 确认接口名正确，Bond、VLAN、VF、representor 场景不要把命令打到错误 netdev。
  • 确认驱动/固件支持对应能力，老卡或 inbox 驱动可能缺少部分选项。

症状 2：PFC 开了但 RDMA 仍然丢包

  • 确认应用 DSCP/PCP 真的打在包上，可用抓包或交换机 telemetry 验证。
  • 确认 --trust 路线与实际标记一致，DSCP 标记不能被 trust PCP 的端口识别。
  • 确认 dscp2prio 和 prio_tc 把流量导入启用 PFC 的 priority/TC。
  • 确认交换机同 priority 开启 PFC，并有正确 buffer/ECN 阈值。

症状 3：NCCL 带宽稳定低于预期

  • 检查 TC ratelimit 是否不是 unlimited。
  • 检查 ETS 百分比是否给 RDMA 队列过低，或 strict 高优先级队列长期占用。
  • 检查链路速率、FEC 错误、PCIe 带宽、NUMA 亲和性、多 rail 选择。
  • 对比单流 ib_write_bw、多流 NCCL、真实训练，分清网络瓶颈和应用瓶颈。
# 一个实用排障摘要
IF=ens1f0
sudo mlnx_qos -i "$IF"
ethtool "$IF"
ethtool -i "$IF"
ethtool -S "$IF" | egrep -i 'pfc|pause|drop|disc|err|crc|fec|ecn|cnp|timeout'
rdma link show | grep "$IF" || true
ip -d link show dev "$IF"

16. 回滚与持久化

mlnx_qos 写入的是当前系统/驱动状态，具体是否跨重启持久化取决于发行版、驱动、固件、初始化脚本和集群配置管理。生产环境不要依赖“我手工敲过一次”这种隐式状态。

回滚原则

  • 回滚不是“猜一个默认值”，而是恢复变更前保存的 mlnx_qos 输出所表达的配置。
  • 每条写命令都应有对应反向命令，例如 trust、PFC bitmap、DSCP mapping、UP-to-TC、ETS、rate limit。
  • 回滚后要重新读取并跑最小验证，不要只看命令 exit code。
# 示例：变更前保存
sudo mlnx_qos -i ens1f0 | tee /var/tmp/ens1f0.qos.before

# 示例：回滚到常见默认/安全模板时，必须以你的 before 文件为准
sudo mlnx_qos -i ens1f0 --trust=pcp
sudo mlnx_qos -i ens1f0 --pfc=0,0,0,0,0,0,0,0
sudo mlnx_qos -i ens1f0 --prio_tc=0,1,2,3,4,5,6,7
sudo mlnx_qos -i ens1f0 --ratelimit=0,0,0,0,0,0,0,0
sudo mlnx_qos -i ens1f0
持久化建议： 用 Ansible、systemd oneshot、cloud-init、镜像初始化或集群节点 agent 统一下发；脚本里先读取当前状态，输出 diff，再执行写入，并将结果落盘。

17. 自动化巡检脚本

QoS 巡检的目标不是“输出越多越好”，而是把关键意图和反常信号变成可比较的文本。下面脚本只读，不修改配置，适合作为故障现场采集模板。

#!/usr/bin/env bash
set -euo pipefail

IF="${1:-ens1f0}"
OUT="${2:-/var/tmp/qos-audit-${IF}-$(date +%Y%m%d-%H%M%S)}"
mkdir -p "$OUT"

{
  date -Is
  hostname -f || hostname
  uname -a
  echo "interface=$IF"
} | tee "$OUT/00-host.txt"

command -v mlnx_qos | tee "$OUT/01-mlnx_qos-path.txt"
mlnx_qos --version > "$OUT/02-mlnx_qos-version.txt" 2>&1 || true
sudo mlnx_qos -i "$IF" > "$OUT/10-mlnx_qos.txt"
ethtool -i "$IF" > "$OUT/20-ethtool-i.txt"
ethtool "$IF" > "$OUT/21-ethtool-link.txt"
ethtool -S "$IF" > "$OUT/22-ethtool-stats.txt"
rdma link show > "$OUT/30-rdma-link.txt" 2>&1 || true
ip -d link show dev "$IF" > "$OUT/40-ip-link.txt"

egrep -i 'DCBX|trust|PFC|enabled|tc:|priority:|dscp|ratelimit|tsa|bw' "$OUT/10-mlnx_qos.txt" \
  > "$OUT/summary-qos.txt" || true
egrep -i 'pfc|pause|drop|disc|err|crc|fec|ecn|cnp' "$OUT/22-ethtool-stats.txt" \
  > "$OUT/summary-counters.txt" || true

echo "Wrote $OUT"
自动化建议： 将巡检输出和交换机 telemetry 以同一时间窗口关联，才能判断 pause/drop 是谁先发生、在哪条链路发生。

18. 生产检查清单

变更前
有基线、有工单、有交换机配置、有回滚命令、有压测方法、有影响范围。
变更中
单机灰度，逐项修改；每次修改后读取 mlnx_qos，不要把 trust、PFC、ETS、DCBX 混在一个不可分辨的大命令里。
变更后
确认主机和交换机对齐，NCCL/RDMA 指标达标，drop 不增长，PFC pause 没有异常持续增长。
长期维护
将 DSCP/priority/TC/queue 设计文档化；纳入节点初始化和漂移检测；驱动/固件升级后重新验证。
检查问题合格标准
RoCE 流量使用哪个 DSCP 或 PCP？应用、主机、交换机三方答案一致。
该标记进入哪个 priority？dscp2prio 或 PCP map 明确可见。
该 priority 是否启用 PFC？主机和交换机都只在目标 priority 启用。
该 priority 映射到哪个 TC/queue？主机 TC 和交换机 queue 的调度/ETS 语义一致。
是否有限速或 strict 饥饿风险？TC rate limit、strict、ETS 份额经过压测验证。
失败时如何恢复？有从基线生成的回滚命令，且回滚后有验证步骤。
最终安全线： 在多租户 GPU 集群中，QoS 变更可能影响非目标作业。没有灰度和观测，不要在整集群执行 mlnx_qos 写操作。
