1. rdma 是什么

rdma 是 iproute2 套件的一部分，地位类似 ip、ss、tc。它不是 RDMA 性能压测工具，也不是交换机配置工具；它的核心价值是把 Linux 内核 RDMA 子系统中的对象以命令行形式展示出来。

它擅长什么
查看 RDMA 设备、端口 link、netdev 绑定、资源对象、统计计数器、设备事件，以及与进程、PID、QP 类型相关的资源分布。
它不擅长什么
不能替代 ib_write_bw、qperf、nccl-tests 做性能结论；不能直接读取交换机 PFC/ECN 配置；不能保证 GPU Direct RDMA 已经可用。
AI Infra 心智模型
rdma 回答“内核 RDMA 栈看到什么”；压测工具回答“这条路径跑得怎样”；NCCL 日志回答“应用实际选择了哪条通信路径”。
# 快速确认系统是否看见 RDMA 设备和端口
rdma dev
rdma link

# 详细输出，适合现场记录
rdma -d dev show
rdma -d link show

# JSON 输出，适合自动化采集
rdma -j -p link show
rdma -j -p resource show
排障边界： 如果 rdma dev 为空，优先检查驱动、内核模块、PCIe 设备和容器设备透传；如果 rdma dev 正常但应用失败，再继续查 link、GID、QP、CM ID、路由、PFC/ECN、NCCL 参数和进程权限。

信息图：rdma 命令看到的内核 RDMA netlink 视图

把 rdma 当成“内核 RDMA 对象浏览器”：它非常适合定位设备、端口、资源和统计，但最终性能还要用应用与压测工具闭环。

2. 安装、版本与权限

rdma 通常由 iproute2 包提供；RDMA 用户态库、驱动和诊断命令通常来自 rdma-core、厂商 OFED 或发行版内核包。多数 show 操作普通用户可读，但详细资源、统计绑定、netns 迁移、设备创建删除等操作可能需要 root 或额外 capability。

# Debian / Ubuntu
sudo apt-get update
sudo apt-get install -y iproute2 rdma-core

# RHEL / Rocky / Alma / CentOS
sudo dnf install -y iproute rdma-core

# 版本与帮助
rdma -V
rdma help
rdma dev help
rdma link help
rdma resource help
rdma statistic help

# 同时确认内核与用户态 RDMA 组件
uname -r
lsmod | egrep 'ib_core|ib_uverbs|rdma_cm|mlx5_ib|irdma|bnxt_re|rxe' || true
ls -l /dev/infiniband 2>/dev/null || true
组件作用排障意义
iproute2提供 rdma 命令版本决定支持哪些对象、过滤器和 JSON 字段
rdma-core提供 libibverbs、librdmacm、ibv 工具应用和工具访问 verbs 的基础
内核驱动例如 mlx5_ib、irdma、bnxt_rerdma dev 是否能看到硬件设备
/dev/infiniband用户态 verbs 设备节点容器、权限、cgroup、device plugin 问题常在这里暴露
版本现实： rdma 的对象模型来自 iproute2 与内核能力组合。不同发行版、内核、厂商驱动可能输出字段不同，自动化脚本应优先解析 JSON 并容忍缺字段。

3. 命令对象与输出模式

rdma 的顶层语法是 rdma [OPTIONS] OBJECT { COMMAND | help }。AI Infra 排障中最常用对象是 dev、link、resource、statistic 和 monitor。

对象看什么典型命令
devRDMA 设备级信息，类似 HCA inventoryrdma -d dev show
link端口、state、physical state、netdev 映射rdma -d link show
resourceQP、CQ、MR、PD、SRQ、CM ID、context 等资源rdma -d resource show
statistic默认硬件计数器、对象计数器、QP/MR counterrdma statistic show link mlx5_0/1
monitor设备注册、注销、netdev attach/detach 等事件rdma monitor
# 输出模式
rdma dev show              # 人类可读
rdma -d dev show           # details，更多字段
rdma -o link show          # oneline，便于 grep
rdma -j link show          # JSON，便于 jq
rdma -j -p link show       # pretty JSON，便于人工审阅

# 只看某个设备或端口
rdma dev show mlx5_0
rdma link show mlx5_0/1
rdma resource show mlx5_0/1
采集建议： 事故现场优先采 rdma -j -p dev/link/resource/statistic，再用 ip -j addr/link/route、ethtool、devlink、厂商工具补齐上下文。

4. rdma dev：设备视图

rdma dev 展示系统内 RDMA 设备。对 Mellanox/NVIDIA ConnectX 常见名字是 mlx5_0、mlx5_1；软 RoCE 可能是 rxe0；不同厂商会有自己的设备名。设备名不是 Linux 网卡名，必须通过 rdma link 或 sysfs 关联到 netdev。

# 列出所有 RDMA 设备
rdma dev
rdma -d dev show

# 查看单个设备
rdma -d dev show mlx5_0

# 用 JSON 保存 inventory
rdma -j -p dev show > rdma-dev.$(hostname).json
你关心的字段含义AI Infra 判断
dev / 设备名内核 RDMA 设备标识后续 mlx5_0/1、rdma resource、qperf 绑定都会用到
node type / transport设备类型与传输能力区分 IB、RoCE、iWARP、soft-RoCE 的第一层线索
fw / driver 信息详细输出中可能出现固件或驱动字段用于和节点基线、厂商兼容矩阵对比
netns设备所在网络命名空间容器/租户隔离场景中非常关键
不要混淆： mlx5_0 是 RDMA device，ens5f0np0 是 netdev，0000:ca:00.0 是 PCI BDF。三者要通过 rdma link、ethtool -i、readlink /sys/class/infiniband/mlx5_0/device 串起来。

5. rdma link：端口与 netdev 映射

rdma link 是 AI Infra 排障中最常用的入口。它把 RDMA 设备端口与 Linux netdev、link state、physical state 关联起来。RoCE 场景中，netdev 映射尤其重要，因为 NCCL、UCX、MPI、存储客户端常要同时满足 IP 路由和 RDMA verbs。

# 全部 RDMA link
rdma link
rdma -d link show

# 查看指定设备端口
rdma -d link show mlx5_0/1

# 配合 IP 路由确认会走哪张网卡
ip route get 10.32.8.17
ip -br addr show dev ens5f0np0
ethtool ens5f0np0 | egrep 'Speed|Duplex|Link detected'
字段含义常见问题
link mlx5_0/1RDMA 设备的端口索引多端口卡、双 rail 集群容易选错端口
state ACTIVERDMA 端口逻辑可用不是 ACTIVE 时，应用 verbs 通常不可用
physical_state LINK_UP物理链路层状态link up 但 state down 常见于 IB 管理、GID 或配置问题
netdev ens5f0np0关联 Linux 网络接口RoCE/NCCL 常因 IP 路由选错 netdev 而慢或失败
实战判断： 对 RoCE，rdma link 正常只是第一步；还要确认 ip addr、ip route get、MTU、PFC/ECN、DSCP/PCP、交换机端口和 GID index 是否一致。

流程图：从设备到 RoCE/IB 可用状态的判读

设备存在、端口 ACTIVE、物理链路 LINK_UP 是 RDMA readiness 的前置条件；RoCE 还必须证明 IP/队列/无损配置走的是同一条训练网路径。

6. RoCE 与 InfiniBand 状态判读

同样是 RDMA，InfiniBand 与 RoCE 的排障侧重点不同。InfiniBand 依赖 IB fabric、Subnet Manager、LID、PKey 等；RoCE 依赖以太网 netdev、IP 路由、VLAN、MTU、PFC/ECN、DSCP/PCP、GID index 等。rdma 不会替你解释全部网络设计，但它能给出内核端口和资源是否成立的证据。

维度InfiniBandRoCE v2
链路基础IB fabric，通常有 Subnet ManagerEthernet/IP fabric，通常跨三层网络
关键状态state ACTIVE、LID、SM、PKeystate ACTIVE、netdev、IP、GID、MTU、QoS
常见验证ibstat、ibv_devinfo、ib_write_bwrdma link、ip route get、show_gids、qperf
AI 集群故障SM/fabric、端口降速、分区、线缆/光模块选错网卡、PFC pause storm、ECN 不一致、GID index 错、交换机队列拥塞

rdma -d link show
ip -br addr
ip route get 10.42.7.19
cat /sys/class/infiniband/mlx5_0/ports/1/gid_attrs/types/* 2>/dev/null
cat /sys/class/infiniband/mlx5_0/ports/1/gids/* 2>/dev/null

# IB：通常还需要 IB 专用工具补充 LID/SM/fabric 信息
ibstat
ibv_devinfo -v
ib_write_bw -d mlx5_0 -i 1 peer-host
RoCE 误区： ping 通、TCP 带宽高，并不等于 RoCE 无损队列、GID 和 NCCL RDMA 都正确；rdma link ACTIVE 也不等于交换机 PFC/ECN 没有问题。

7. rdma resource：QP/CQ/MR/PD/CM ID

rdma resource 展示内核追踪到的 RDMA 资源。它非常适合回答：“哪个进程打开了多少 RDMA context？”“是否存在大量 QP/CQ/MR 泄漏？”“某个端口上有没有应用实际创建 RDMA 连接？”

# 总览：所有设备上的资源摘要
rdma resource show
rdma -d resource show

# 只看某个设备或端口
rdma resource show mlx5_0
rdma resource show mlx5_0/1

# 细分对象
rdma res show ctx
rdma res show qp
rdma res show cq
rdma res show mr
rdma res show pd
rdma res show cm_id

# 过滤某个 link 或 PID，具体支持随版本变化
rdma res show qp link mlx5_0/1
rdma res show qp pid 12345
rdma res show cm_id link mlx5_0/1
资源表示什么排障价值
ctx用户态进程打开的 RDMA device context判断作业是否真的进入 verbs 路径
qpQueue Pair，RDMA 通信的核心对象看 QP 类型、状态、所属 PID、端口，定位连接是否建立
cqCompletion Queue大量 CQ 可能对应高并发连接或资源泄漏
mrMemory Region，注册内存区域训练作业内存注册异常、ODP/pinning 问题可从数量变化找线索
pdProtection Domain资源归属与隔离线索
cm_idRDMA CM 连接管理对象librdmacm、RoCE 连接建立问题的重要证据
AI Infra 用法： 运行 NCCL、UCX、MPI 或存储客户端前后各采一次 rdma -j -p res show，对比 QP/CQ/MR/CM ID 数量和 PID 归属，能快速判断应用是否触达 RDMA 子系统。

信息图：从进程到 RDMA 连接对象的排障链

资源视图把“应用现象”连接到“内核对象”。NCCL 慢时，先证明它是否创建了 RDMA context/QP，再讨论网络性能。

8. 连接与进程诊断

RDMA 连接问题经常表现为应用层超时、NCCL hang、UCX endpoint error、NVMe-oF connect 失败或存储客户端断连。rdma resource 能从 PID 和对象角度补齐证据。

# 找到训练或测试进程
pgrep -af 'nccl|all_reduce|ucx|mpi|ib_write|qperf'

# 看该 PID 是否持有 RDMA 资源
PID=12345
rdma res show ctx pid "$PID"
rdma res show qp pid "$PID"
rdma res show cq pid "$PID"
rdma res show mr pid "$PID"
rdma res show cm_id pid "$PID"

# 看特定端口上是否有连接资源
rdma res show qp link mlx5_0/1
rdma res show cm_id link mlx5_0/1

# 结合进程文件描述符与设备节点
ls -l /proc/"$PID"/fd 2>/dev/null | grep infiniband || true
cat /proc/"$PID"/status | egrep 'Name|State|Pid|Cpus_allowed_list|Mems_allowed_list'
现象rdma resource 线索下一步
应用声称使用 RDMA，但性能像 TCP没有 ctx/QP，或只看到控制面少量对象查 NCCL/UCX 环境变量、容器设备、权限、fallback 日志
连接建立阶段 hangcm_id 有变化但 QP 未进入预期状态查 GID index、IP 路由、防火墙、ARP/ND、交换机 ACL
运行一段时间后失败QP/CQ/MR 数量异常增长或频繁重建查应用重试、HCA syndrome、dmesg、端口 counters
单节点异常同一作业 PID 在坏节点资源分布不同对比好/坏节点的 dev/link/resource/statistic 快照
权限提示： 某些发行版需要 root 才能看完整 PID、进程名和对象详情。容器内看到的 PID/netns 也可能和宿主机不同，必要时从宿主机同一时间采集。

9. rdma statistic 与计数器

rdma statistic 用于查询 RDMA 和驱动暴露的计数器。不同驱动支持的计数器差异很大；它适合做趋势和对比，不适合脱离基线孤立解读。

# 默认硬件计数器
rdma statistic show
rdma statistic show link mlx5_0/1

# QP 计数器，具体模式和过滤器依赖内核/驱动
rdma statistic qp show
rdma statistic qp show link mlx5_0/1
rdma statistic qp show link mlx5_0/1 pid 12345
rdma statistic qp show link mlx5_0/1 qp-type RC

# 查看支持的统计模式
rdma statistic qp mode
rdma statistic mode supported link mlx5_0/1
计数器用法适合回答注意事项
跑测试前后采样某段测试是否让特定端口计数增长不要只采一次；需要差值
好坏节点对比坏节点是否有异常错误或重试趋势字段名可能随驱动变化，先建立基线
按 PID/QP 类型过滤某个进程或 RC/UD QP 是否异常过滤器支持取决于版本和硬件
结合 ethtool/devlink把 RDMA 计数与以太网链路错误、pause、丢包对齐RoCE 排障不能只看 RDMA 计数
基线方法： 对每类节点建立空闲、单流压测、多机 NCCL、生产作业四类计数器快照。没有基线时，很多“非零计数器”无法判断是正常噪声还是故障。

10. rdma monitor：事件流

rdma monitor 监听 RDMA netlink 事件，适合排查设备热插拔、驱动重载、netdev attach/detach、容器或命名空间操作导致的瞬态变化。它不是性能 profiler，而是事件时间线。

# 终端 1：监听事件
sudo rdma monitor

# 终端 2：执行只读操作或观察作业启动
rdma link
rdma dev

# 事故期间可以带时间戳保存
sudo sh -c 'rdma monitor | ts "%Y-%m-%d %H:%M:%S" >> /var/log/rdma-monitor.log'
适合场景
节点上报偶发 RDMA device disappeared、Pod 启动后设备不可见、驱动重载、网卡 reset、容器 netns 切换。
不适合场景
分析微秒级延迟、交换机队列拥塞、NCCL collective 算法选择。
结合工具
dmesg -Tw、journalctl -k -f、udevadm monitor、devlink monitor、厂商 health reporter。
现场技巧： 对偶发问题，先把 rdma monitor、dmesg -Tw、journalctl -k -f 同时带时间戳记录，再复现应用错误。没有时间线很难判断是应用先失败还是设备先掉线。

11. 命名空间与容器

RDMA 与普通网卡一样会遇到命名空间问题，但更容易被忽略：容器可能能看到 IP 接口，却看不到 /dev/infiniband；也可能看到设备节点，但 RDMA device 仍在宿主机 netns；或者 Kubernetes RDMA device plugin 只分配了部分设备。

# 宿主机：查看 RDMA 设备和 netns 线索
rdma -d dev show
rdma -d link show
ip netns list

# 将 RDMA 设备迁移到已存在的 netns，属于变更操作，先确认无人使用
ip netns add rdma-test
rdma dev set mlx5_0 netns rdma-test
ip netns exec rdma-test rdma dev
ip netns exec rdma-test rdma link

# 容器内：确认设备节点、rdma 视图和 IP 路径
ls -l /dev/infiniband
rdma dev
rdma link
ip route get 10.32.8.17
容器现象可能原因验证命令
/dev/infiniband 不存在device plugin、runtime、cgroup device 未暴露ls -l /dev/infiniband
rdma dev 为空RDMA device 未进入该 netns 或权限不足rdma -d dev show
RDMA 可见但连接失败Pod IP/CNI 路由与 RoCE netdev 不一致ip route get peer、rdma link
NCCL fallback 到 socket环境变量、netdev 选择、插件分配、GID index 错误NCCL 日志 + rdma res show qp pid
生产警告： rdma dev set ... netns ... 会改变设备可见位置，可能影响宿主机或其他容器中的作业。共享 GPU 节点上不要临时手工迁移生产 HCA，除非你明确知道调度器和 device plugin 的期望状态。

对照图：NCCL/RDMA readiness 的分层检查

NCCL/RDMA readiness 必须同时覆盖设备、端口、应用资源和性能闭环。缺一层证据，结论都容易误导。

12. NCCL/RDMA readiness 清单

分布式训练排障中，rdma 最适合放在 readiness 和故障现场采集脚本中。下面是一套保守、只读、可复制的检查流程。

# 1. 节点 RDMA inventory
hostname -f
rdma -j -p dev show
rdma -j -p link show
ls -l /dev/infiniband

# 2. RoCE 路由与 netdev 选择
PEER=10.32.8.17
ip route get "$PEER"
ip -br addr
rdma -d link show

# 3. 启动 NCCL 测试时打开日志
export NCCL_DEBUG=INFO
export NCCL_DEBUG_SUBSYS=INIT,NET
# 按实际训练网接口填写，避免误选管理网
export NCCL_SOCKET_IFNAME=ens5f0np0

# 4. 测试期间观察该 PID 的 RDMA 对象
PID=$(pgrep -n all_reduce_perf)
sudo rdma res show ctx pid "$PID"
sudo rdma res show qp pid "$PID"
sudo rdma res show mr pid "$PID"

# 5. 测试前后采集统计差值
rdma -j -p statistic show link mlx5_0/1 > before.json
# run nccl-tests ...
rdma -j -p statistic show link mlx5_0/1 > after.json
设备
rdma dev 非空，驱动/固件与基线一致。
端口
rdma link 显示目标端口 ACTIVE，netdev 对应训练网。
应用
进程有 ctx/QP/MR 资源，日志显示 RDMA/IB plugin 路径。
性能
端口计数增长、压测达标、真实 step time 与预期一致。
环境变量提醒： NCCL 的可用变量会随版本和插件变化。不要只靠变量名判断是否生效；以 NCCL 日志、rdma resource、压测和 counters 作为证据链。

13. rdma vs ibstat/ibv_devinfo/mlxlink

RDMA 排障没有单一万能命令。rdma 的优势是内核 netlink 对象和 JSON 自动化；IB verbs 和厂商工具则提供更底层或更硬件相关的信息。

工具主要视角适合问题不能替代
rdmaLinux 内核 RDMA netlink：dev/link/resource/statistic/monitor设备、端口、资源、PID、netns、JSON 采集交换机配置、线缆眼图、真实 NCCL 性能
ibstatIB 设备/端口状态，常用于 IB fabricIB link state、physical state、rate、LID 等进程资源、QP/MR/PID 归属
ibv_devinfoverbs 设备能力与端口属性HCA capability、max_qp、max_mr、port attrnetdev/IP 路由、资源实时归属
mlxlinkNVIDIA/Mellanox 链路物理层与模块信息速率、FEC、lane、模块、物理错误非 mlx 设备、内核资源对象
ib_write_bwverbs 性能压测点到点 RDMA 带宽/延迟验证设备 inventory、应用是否使用 RDMA
qperfTCP/UDP/RDMA 主机间快速探针IP 与 RDMA 分层性能对比交换机/设备底层 counters
# 建议的组合采集
rdma -d link show
rdma -d resource show
ibstat

ethtool ens5f0np0

工具选择： 先用 rdma 建立内核对象证据，再根据问题方向选择 ibv_devinfo 看能力、mlxlink 看物理层、qperf/ib_write_bw/nccl-tests 看数据面。

14. 自动化采集与 JSON

-j -p 是 rdma 在生产排障中的关键能力。相比解析人类可读输出，JSON 更适合写巡检、基线对比和事故快照。

#!/usr/bin/env bash
set -euo pipefail

out="rdma-snapshot.$(hostname -s).$(date +%Y%m%d-%H%M%S)"
mkdir -p "$out"

rdma -j -p dev show > "$out/rdma-dev.json"
rdma -j -p link show > "$out/rdma-link.json"
rdma -j -p resource show > "$out/rdma-resource.json"
rdma -j -p statistic show > "$out/rdma-statistic.json" || true
ip -j addr show > "$out/ip-addr.json"
ip -j route show table all > "$out/ip-route.json"
ls -l /dev/infiniband > "$out/dev-infiniband.txt" 2>&1 || true
uname -a > "$out/uname.txt"

tar -czf "$out.tar.gz" "$out"
自动化目标建议做法避免什么
巡检只读采集 dev/link/statistic，和黄金节点对比字段与数量巡检脚本自动修复设备状态
事故快照在应用启动前、运行中、失败后各采一次只保留失败后的单点输出
CI/准入检查设备数量、端口 ACTIVE、netdev 匹配、容器设备可见把压测跑满训练网作为每次准入
对比分析按 host/slot/rail/port 命名，和拓扑数据库关联只记录 mlx5_0，不记录 PCI BDF 和 netdev
脚本鲁棒性： JSON 字段随版本变化，脚本应校验“必要事实”而不是依赖完整结构。例如：设备数、link ACTIVE、netdev 名、端口索引、资源是否增长。

15. 安全边界与变更操作

大多数教程只展示 show，但 rdma 也能执行变更，例如设备改名、迁移 netns、添加/删除软 RDMA 设备、统计 counter 绑定等。这些操作可能影响运行中的应用，AI 集群中应按变更处理。

# 安全：只读确认
rdma -d dev show mlx5_0
rdma -d link show mlx5_0/1
rdma -d resource show mlx5_0/1

# 变更前：确认没有生产进程持有资源
rdma res show qp link mlx5_0/1
rdma res show ctx
fuser -v /dev/infiniband/uverbs0 2>/dev/null || true

# 变更示例：迁移 netns，仅在测试节点或维护窗口执行
ip netns add rdma-lab
rdma dev set mlx5_0 netns rdma-lab

# 变更示例：修改设备名，可能影响脚本和服务配置
rdma dev set mlx5_0 name train_rail0
不要在生产作业中途做： 改名、netns 迁移、删除软 RDMA 设备、重载驱动、修改 QoS、关闭端口、更新固件。这些都可能导致 NCCL、NVMe-oF、NFS/RDMA、存储客户端或推理服务连接中断。
变更守则： 先保存 rdma -j -p dev/link/resource/statistic、ip -j、ethtool、dmesg 快照；确认无资源持有；在维护窗口执行；变更后跑最小 smoke test，再恢复生产调度。

排障图：RDMA/NCCL 常见问题的安全诊断路径

从最便宜、最安全、最确定的只读证据开始：设备、端口、路径、进程资源、计数器，再进入压测和网络设备侧排查。

17. 练习任务与学习路线

练习 1：建立节点 inventory
在两台训练节点上采集 rdma -j -p dev/link、ip -j addr/route，画出 RDMA device、netdev、PCI BDF、NUMA node、训练网 IP 的对应关系。
练习 2：观察应用资源
运行 ib_write_bw、qperf rc_bw 或 nccl-tests，在运行前后对比 rdma res show ctx/qp/mr，确认资源增长与 PID 对应。
练习 3：构造只读 readiness 脚本
写一个不改变系统状态的脚本，输出设备数量、ACTIVE 端口、netdev 映射、训练网路由和 /dev/infiniband 权限。
练习 4：好坏节点对比
选择一台性能正常节点和一台异常节点，采集相同命令，找出设备、端口、资源、统计、IP 路由、驱动版本中的差异。

推荐学习顺序

  1. 先掌握 rdma dev 与 rdma link，能把 RDMA 设备映射到 netdev、PCIe 和物理端口。
  2. 再学习 rdma resource，理解 QP、CQ、MR、PD、CM ID 如何证明应用进入 RDMA 路径。
  3. 随后引入 rdma statistic 与前后差值，建立好坏节点和空闲/压测/生产基线。
  4. 最后把 rdma 与 ibv_devinfo、ibstat、mlxlink、qperf、ib_write_bw、nccl-tests 串成完整证据链。
