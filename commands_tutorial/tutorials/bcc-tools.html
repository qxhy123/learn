1. bcc-tools 是什么，适合解决什么问题

bcc-tools 是 BCC 项目附带的一组命令行工具。它们通常是 Python 脚本，运行时编译一小段 C 风格 eBPF 程序，挂载到内核 kprobe、tracepoint、uprobes 或 perf event 上，再把事件通过 perf buffer/ring buffer 传回用户态打印。

它擅长
短窗口、事件驱动、低侵入地观察内核边界：进程 exec、文件 open、块 I/O、TCP 连接、调度延迟、系统调用、VFS、网络栈。
它不擅长
长期全量审计、复杂业务语义、GPU kernel 内部、Python 对象级分析、跨节点链路追踪、需要稳定 ABI 的长期 agent。
AI Infra 价值
训练任务突然重启、worker 频繁拉起、模型文件 miss、NFS/本地盘 I/O 抖动、推理服务连接风暴、数据加载慢但不想用高开销 tracing。
# 查看系统里有哪些 BCC 工具
ls /usr/share/bcc/tools 2>/dev/null | head
compgen -c | grep -E '^(execsnoop|opensnoop|biosnoop|tcplife)(-bpfcc)?$'

# 用短窗口观察进程启动事件
sudo timeout 10s execsnoop-bpfcc

# 只观察某个 PID 的文件打开
sudo timeout 15s opensnoop-bpfcc -p 12345
边界提醒： eBPF 工具看到的是内核事件，不自动解释业务因果。比如 opensnoop 看到大量 ENOENT 只说明程序在尝试查找路径，是否异常要结合框架、缓存和部署结构判断。

2. AI Infra 中的典型场景

AI 训练和推理问题经常跨越 Python、C++ runtime、文件系统、网络、容器和内核调度。bcc-tools 的价值是快速把“猜测”变成事件证据，尤其适合 strace 过重、perf 太偏 CPU、日志又不够细的场景。

现象优先工具看什么常见解释
训练 worker 或 dataloader 频繁重启execsnoop命令行、父进程、返回码相关线索launcher 重试、健康检查拉起、shell wrapper 循环、OOM 后 supervisor 重启。
模型加载偶发慢或失败opensnoop模型/权重/配置路径、ENOENT/EACCES路径查找风暴、挂载不一致、权限、缓存 miss、动态库搜索。
GPU 利用率周期性掉到 0biosnoopI/O 延迟、设备、进程名、读写大小数据集读盘、checkpoint、日志 fsync、本地盘/NFS 抖动。
推理服务 p99 抖动或连接暴涨tcplife连接持续时间、收发字节、端口、远端地址客户端重试、负载均衡重连、短连接风暴、服务端主动关闭。
# 一个安全的 AI Infra 快速巡检窗口
sudo timeout 10s execsnoop-bpfcc -T
sudo timeout 10s opensnoop-bpfcc -T -p 12345
sudo timeout 15s biosnoop-bpfcc
sudo timeout 15s tcplife-bpfcc -p 12345

3. 核心模型：eBPF 程序、探针、事件流

信息图：BCC 工具从内核事件到终端输出

心智模型：BCC 工具不是轮询日志，而是在内核事件发生时运行一小段受 verifier 限制的程序，把少量关键字段返回用户态。

4. 安装、命名和版本检查

BCC 工具的包名和命令名在发行版间差异很大。Ubuntu/Debian 常见命令后缀是 -bpfcc，RHEL/CentOS/Rocky/Fedora 常见无后缀命令，工具文件也可能放在 /usr/share/bcc/tools。

环境安装示例常见命令名备注
Ubuntu/Debiansudo apt install bpfcc-tools linux-headers-$(uname -r)execsnoop-bpfcc、opensnoop-bpfcc需要匹配内核头文件；容器内可能缺 headers。
RHEL/CentOS/Rockysudo dnf install bcc-tools bccexecsnoop、opensnoop旧系统可能用 yum；内核较旧时工具能力受限。
Fedorasudo dnf install bcc-toolsexecsnoop、tcplife通常 BPF 支持较新。
源码/自建环境BCC + LLVM/Clang + kernel headers取决于安装路径适合调试 BCC 本身，不是生产节点首选。
# 找到工具真实名称：Ubuntu 上常带 -bpfcc 后缀
command -v execsnoop || command -v execsnoop-bpfcc
command -v opensnoop || command -v opensnoop-bpfcc
command -v biosnoop || command -v biosnoop-bpfcc
command -v tcplife || command -v tcplife-bpfcc

# 常用兼容写法：先设置变量
EXECSNOOP=$(command -v execsnoop || command -v execsnoop-bpfcc)
OPENSNOOP=$(command -v opensnoop || command -v opensnoop-bpfcc)

# 检查内核、BPF 文件系统和工具目录
uname -a
mount | grep bpf || true
ls /sys/fs/bpf 2>/dev/null || true
ls /usr/share/bcc/tools 2>/dev/null | head
命名提醒： 文档里写 execsnoop 时，实际命令可能是 execsnoop-bpfcc。如果命令不存在，先查包名和安装路径，不要立刻判断内核不支持 eBPF。

5. 内核能力、权限与安全边界

运行 BCC 工具通常需要 root，或具备加载 BPF、附加 perf event、读取内核符号所需的 capability。限制来自内核配置、kernel.unprivileged_bpf_disabled、perf_event_paranoid、kptr_restrict、LSM、安全基线和容器 seccomp/capability。

检查项命令解释
内核版本uname -r新内核 BPF 能力更完整，旧内核可能缺 tracepoint 或 helper。
BPF 是否禁用cat /proc/sys/kernel/unprivileged_bpf_disabled即使禁用非特权 BPF，root 通常仍可运行；以平台策略为准。
perf 权限cat /proc/sys/kernel/perf_event_paranoid影响 perf event 和部分 BPF attach 能力。
内核符号cat /proc/sys/kernel/kptr_restrict影响地址/符号可见性，排障时会影响可读性。
BTFls /sys/kernel/btf/vmlinuxBCC 不强依赖 CO-RE BTF，但新工具和 bpftrace 常受益。
# 只读检查，不改变系统策略
uname -r
grep BPF /boot/config-$(uname -r) 2>/dev/null | head || true
cat /proc/sys/kernel/unprivileged_bpf_disabled 2>/dev/null || true
cat /proc/sys/kernel/perf_event_paranoid
cat /proc/sys/kernel/kptr_restrict

# 受控测试环境可临时调整；生产环境必须走平台流程
sudo sysctl kernel.perf_event_paranoid=1
安全注意： 不要为了跑一个工具就在共享生产节点长期放宽 BPF/perf/syslog 限制。BCC 输出可能包含命令行参数、文件路径、租户目录、IP、端口、容器 ID 和业务数据痕迹。

6. 快速开局：先用短窗口观察

BCC 工具的正确打开方式不是“开着一直跑”，而是基于一个具体问题做短窗口证据采集。先确认工具能运行，再对目标进程、端口或事件类型加过滤，最后把输出保存到文件供后处理。

# 1. 验证工具能启动：5 秒窗口
sudo timeout 5s execsnoop-bpfcc

# 2. 对目标服务短窗口观察
PID=$(pgrep -n -f 'python.*serve.py')
sudo timeout 15s opensnoop-bpfcc -T -p "$PID" > /tmp/opensnoop.$PID.log

# 3. 对输出做后处理，而不是肉眼滚屏
grep -E 'ENOENT|EACCES|model|tokenizer|safetensors|pt$' /tmp/opensnoop.$PID.log | head -50
短窗口
timeout 10s 是默认起点，异常复现慢时再延长。
窄过滤
优先按 PID、进程名、端口、设备或路径关键词缩小范围。
写文件
线上不要让高频输出刷终端；保存后用 grep/awk 汇总。
对照指标
和 iostat、ss、pidstat、应用日志、GPU 利用率一起解释。
输出风险： execsnoop 可能打印完整命令行参数；如果参数里有 token、路径或用户输入，保存和分享 trace 前要脱敏。

7. execsnoop：追踪进程启动和命令行

execsnoop 追踪 execve 相关事件，能看到系统中新进程启动的时间、PID、父 PID、命令名和参数。它非常适合定位“谁在反复拉起进程”“worker 是否真的启动”“shell wrapper 到底执行了什么”。

关注字段含义AI Infra 解读
TIME/TIME(s)事件时间和 GPU 利用率掉点、服务 p99 抖动、日志时间线对齐。
PCOMM/COMM父进程或当前命令名识别 launcher、supervisor、worker、shell、python。
PID/PPID进程和父进程追踪进程树，判断是谁拉起谁。
ARGS命令行参数确认训练脚本、模型路径、rank、worker 参数是否符合预期。
# 看所有 exec，带时间戳，10 秒后退出
sudo timeout 10s execsnoop-bpfcc -T

# 常见过滤：只看命令名包含 python 的进程
sudo timeout 30s execsnoop-bpfcc -T | grep -E 'python|torchrun|deepspeed|ray'

# 如果工具支持 -n，可按命令名过滤；不同版本参数略有差异，先看 -h
execsnoop-bpfcc -h
sudo timeout 30s execsnoop-bpfcc -n python
实战判断： 如果 GPU 利用率每隔 60 秒下降，同时 execsnoop 显示有健康检查脚本、日志压缩、checkpoint helper 或 worker 重启，就能把“GPU 问题”转化为 CPU/进程编排问题继续追。
隐私提醒： 命令行参数可能包含访问密钥、数据路径、用户 ID、实验名和内部地址。不要把原始 execsnoop 输出直接贴到工单或公开聊天。

8. opensnoop：追踪文件打开和路径问题

opensnoop 追踪文件打开相关调用，常用于定位模型加载、数据读取、动态库搜索、配置文件查找、权限拒绝和路径不存在。它比 strace -e trace=file 对目标进程的干扰通常更小，也能全局观察。

场景观察重点下一步
模型文件找不到ENOENT、路径拼接、容器内路径确认挂载、工作目录、版本化路径和 symlink。
权限拒绝EACCES、UID、路径权限检查容器用户、fsGroup、SELinux/AppArmor、只读挂载。
启动慢大量动态库或 Python 模块 open检查镜像层、site-packages、冷缓存、网络文件系统。
dataloader 慢样本文件路径、频率、失败重试结合 biosnoop 看底层 I/O 延迟。
# 只追踪某个训练/推理进程
PID=$(pgrep -n -f 'python.*train.py')
sudo timeout 20s opensnoop-bpfcc -T -p "$PID" > /tmp/opensnoop.$PID.log

# 查找模型、tokenizer、权重、配置路径
grep -E 'safetensors|\.pt|\.bin|tokenizer|config\.json|ENOENT|EACCES' /tmp/opensnoop.$PID.log | head -80

# 全局观察打开失败事件，适合启动阶段
sudo timeout 15s opensnoop-bpfcc -T | grep -E 'ENOENT|EACCES|EPERM'
解释技巧： 看到大量 ENOENT 不一定是故障。动态链接器、Python import、配置查找常会尝试多个路径。异常通常表现为“同一路径高频失败”“最终没有成功路径”“失败时间和用户请求抖动对齐”。

工作流图：从 GPU 掉利用率到块 I/O 证据

biosnoop 的核心价值是把“可能是磁盘/存储问题”变成“某进程、某设备、某大小、某延迟”的事件证据。

9. biosnoop：追踪块设备 I/O 延迟

biosnoop 追踪块层 I/O，输出进程、磁盘、I/O 类型、大小和延迟。它适合回答“是不是块设备 I/O 慢”“哪个进程触发慢 I/O”“慢 I/O 是否和训练/推理抖动同一时间发生”。

字段含义解释方式
COMM/PID触发 I/O 的进程可能是 python、dataloader worker、checkpoint 线程、日志进程或后台 daemon。
DISK块设备区分本地 NVMe、云盘、映射设备、容器 overlay 后端。
R/W读或写读慢常影响数据加载；写慢常出现在 checkpoint、日志、缓存落盘。
LAT(ms)I/O 延迟看尾部延迟和异常尖峰，不只看平均值。
# 全局观察 20 秒块 I/O
sudo timeout 20s biosnoop-bpfcc > /tmp/biosnoop.log

# 看尾部事件；字段位置会随版本略有差异，先保留原始日志
tail -50 /tmp/biosnoop.log

# 同时记录 iostat 作为上下文
iostat -xz 1 20 > /tmp/iostat.log &
sudo timeout 20s biosnoop-bpfcc > /tmp/biosnoop.log
wait
解释限制： biosnoop 在块层看不到所有文件路径语义。要知道打开了哪些文件，用 opensnoop；要知道存储设备整体饱和度，用 iostat/nvme/smartctl；要压测，用 fio。

10. tcplife：追踪 TCP 连接生命周期

tcplife 在 TCP 连接结束时输出连接生命周期摘要，包括进程、PID、本地/远端地址端口、连接持续时间、收发字节数。它适合定位短连接风暴、客户端重试、推理服务连接抖动、数据服务吞吐异常。

问题tcplife 线索进一步验证
p99 延迟抖动连接持续时间大量变短或集中超时结合服务日志、LB 指标、ss -ti、重试配置。
短连接风暴同一远端大量短生命周期连接检查 keepalive、连接池、HTTP/gRPC 客户端配置。
数据服务慢连接长但字节少，或字节多但持续时间异常结合 tcpdump、tshark、应用请求 ID。
端口归属不清进程名/PID/端口对应关系对照 ss -tulpn、Kubernetes pod/container 信息。
# 观察某个服务进程的 TCP 生命周期
PID=$(pgrep -n -f 'python.*serve.py')
sudo timeout 30s tcplife-bpfcc -p "$PID" > /tmp/tcplife.$PID.log

# 全局观察短连接，后处理关注本地服务端口
sudo timeout 30s tcplife-bpfcc > /tmp/tcplife.log
awk '$0 ~ /:8000|:8080|:50051/ {print}' /tmp/tcplife.log | head -100

# 版本参数差异较多，先查看帮助
tcplife-bpfcc -h
和 tcpdump 的区别： tcplife 给连接级摘要，开销低、易读；tcpdump 给包级细节，适合协议和重传分析，但数据量和敏感性更高。

11. 进程、线程、容器和 cgroup 过滤

多数 BCC 工具支持部分过滤参数，但不同发行版版本不完全一致。生产排障时要先看 -h，再选择 PID、UID、进程名、端口、设备或 cgroup 过滤。容器环境中，主机 PID 与容器内 PID 可能不同。

# 先确认工具支持哪些参数
execsnoop-bpfcc -h
opensnoop-bpfcc -h
tcplife-bpfcc -h

# 找目标进程：主机视角
ps -eo pid,ppid,user,comm,args | grep -E 'torchrun|deepspeed|serve.py' | grep -v grep

# 容器内 PID 到宿主机 PID 的常见排查思路
docker inspect --format '{{.State.Pid}}' CONTAINER_ID
nsenter -t HOST_PID -p -m -- ps -ef | head

# Kubernetes 节点上先定位 Pod/容器，再到节点命名空间运行工具
crictl ps | grep model-server
crictl inspect CONTAINER_ID | grep -E 'pid|podSandboxId' | head
PID 过滤
适合已知单个服务进程，噪声最低。
命令名过滤
适合进程反复启动，PID 变化快的场景。
端口/地址过滤
适合网络连接问题，具体支持取决于工具版本。
容器提醒： 在容器里直接运行 BCC 往往缺 CAP_BPF/CAP_SYS_ADMIN/CAP_PERFMON、内核头、/sys/kernel/debug 或 /lib/modules。更稳妥的方式通常是在宿主节点或受控 debug 容器中运行。

选择图：症状应该先用哪个 BCC 工具

工具选择先从症状出发。不要一上来打开所有 BCC 工具；事件越多，噪声、开销和敏感数据风险越高。

12. 低开销诊断方法：从症状到证据

低开销不是“不产生开销”，而是把观测成本控制在问题需要的最小范围内。BCC 的优势来自事件驱动和内核侧过滤，但高频事件、全局追踪、复杂字符串采集仍然可能造成影响。

  1. 先写清楚问题：例如“每分钟 p99 抖动 2 秒”或“模型加载偶发多 30 秒”。
  2. 选择单一工具：进程用 execsnoop，文件用 opensnoop，块 I/O 用 biosnoop，连接生命周期用 tcplife。
  3. 限制范围：优先 PID/进程名/端口/短时间窗口。
  4. 保存原始输出：带时间戳，和应用日志、GPU 指标、节点指标对齐。
  5. 验证假设：用第二个工具或指标确认，不靠单条事件下结论。
# 例：推理 p99 抖动，怀疑连接风暴
PID=$(pgrep -n -f 'python.*serve.py')
date -Is
sudo timeout 30s tcplife-bpfcc -p "$PID" > /tmp/tcplife.$PID.$(date +%s).log
date -Is

# 例：模型加载慢，怀疑文件路径/权限
sudo timeout 20s opensnoop-bpfcc -T -p "$PID" > /tmp/open.$PID.log
grep -E 'ENOENT|EACCES|safetensors|tokenizer|config' /tmp/open.$PID.log | head -100
判断标准： 好的 BCC 诊断输出应该能回答“事件发生在异常窗口吗？是哪个进程/连接/设备？结果成功还是失败？有没有足够样本支持结论？”

13. 生产安全：窗口、过滤、采样、数据治理

BCC 工具常被认为比 strace 更适合生产，但这不等于可以无约束使用。它仍然会加载内核程序、读取敏感元数据、增加事件路径工作量，并可能因为内核版本、BTF/headers、verifier 或安全策略失败。

风险表现控制手段
事件过高频CPU 开销、输出暴涨、丢事件缩短窗口、按 PID/端口过滤、避免追踪 read/write 这类极高频路径。
敏感数据泄露命令行、路径、IP、端口、租户目录只采必要字段，保存到受控目录，分享前脱敏。
权限放宽修改 sysctl、加 capability走变更流程，临时调整后恢复，记录审计。
错误解释把正常 ENOENT 或短连接误判为故障和基线、日志、指标对照；关注异常窗口和频率变化。
# 推荐生产模板：短窗口 + 保存文件 + 明确目标
OUT=/var/tmp/bcc.$(hostname).$(date +%Y%m%d-%H%M%S)
mkdir -p "$OUT"
PID=$(pgrep -n -f 'python.*serve.py')
sudo timeout 15s opensnoop-bpfcc -T -p "$PID" > "$OUT/opensnoop.$PID.log"
sudo timeout 15s tcplife-bpfcc -p "$PID" > "$OUT/tcplife.$PID.log"

# 分享前先粗略脱敏示例：按需调整，不要覆盖原始文件
sed -E 's#/[A-Za-z0-9._/-]*(token|secret|key)[A-Za-z0-9._/-]*#/REDACTED_PATH#g' "$OUT/opensnoop.$PID.log" > "$OUT/opensnoop.redacted.log"
生产警告： 不要把 BCC 工具作为长期后台 daemon 临时拼出来。如果需要长期 eBPF 观测，应使用经过压测、限流、权限审计、版本兼容和数据治理设计的 agent。

14. bcc vs bpftrace vs perf vs strace

这些工具不是互相替代，而是观察层级不同。选择工具时先问：我要看 CPU 采样、系统调用逐条记录、内核事件摘要，还是快速写一段临时 BPF 脚本？

工具优势劣势适合场景
bcc-tools现成工具多，事件语义清楚，适合生产短窗口诊断。依赖 Python/LLVM/headers，版本和发行版命名差异明显。进程、文件、I/O、网络等低开销事件追踪。
bpftrace一行脚本快速表达自定义探针，探索性强。复杂脚本可维护性一般；生产长期使用需谨慎。临时回答“某个内核函数/tracepoint 发生了什么”。
perfCPU 采样、PMU、调用栈和性能计数强。不直接给文件路径/TCP 生命周期这类业务近似字段。CPU 热点、IPC、cache miss、上下文切换。
strace系统调用参数和返回值极详细，学习和单进程调试直观。ptrace 开销高，会显著影响 syscall 密集进程。单进程启动失败、权限、系统调用级精确诊断。
# 选择示例
# CPU 热点：先 perf
perf top -p 12345

# 单进程文件打开失败且可接受较高开销：strace
timeout 10s strace -f -e trace=file -p 12345 -o /tmp/file.strace

# 全局观察谁在启动进程：bcc-tools
sudo timeout 10s execsnoop-bpfcc -T

# 临时统计某 tracepoint：bpftrace
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_execve { @[comm] = count(); }'

15. Kubernetes 和容器环境实践

Kubernetes 中的 BCC 排障通常在节点层完成，因为 eBPF 程序加载到宿主内核，目标进程也以宿主 PID 存在。关键是把 Pod/容器映射到节点、宿主 PID、cgroup 和进程名。

# 1. 找到 Pod 所在节点
kubectl get pod -n ai model-server-0 -o wide

# 2. 到节点上定位容器
sudo crictl ps | grep model-server
sudo crictl inspect CONTAINER_ID | grep -E '"pid"|podSandboxId' | head

# 3. 用宿主 PID 或进程名运行 BCC 工具
HOST_PID=12345
sudo timeout 20s opensnoop-bpfcc -T -p "$HOST_PID" > /var/tmp/open.$HOST_PID.log
sudo timeout 20s tcplife-bpfcc -p "$HOST_PID" > /var/tmp/tcp.$HOST_PID.log
部署方式优点风险/限制
SSH 到节点运行最接近真实主机环境，依赖少。需要节点权限；操作审计和变更流程要清楚。
特权 debug Pod便于平台化，能挂载必要路径。权限高；需要严格 RBAC、镜像治理和生命周期控制。
业务容器内运行路径和进程视角直观。通常缺 capability、headers、debugfs、工具包，不推荐作为默认方案。
Kubernetes 提醒： Pod 内看到的 PID 可能不是宿主 PID，网络命名空间也可能不同。排障报告里要写清楚“工具运行位置”和“PID/端口视角”，否则很容易对错对象下结论。

排障流程图：BCC 工具跑不起来或输出不可信

BCC 排障要分层：命令发现、编译加载、权限、目标选择、事件解释。不要跳过前面几层直接分析业务。

16. 常见错误与 troubleshooting

错误 1：command not found
检查发行版命名：Ubuntu/Debian 可能是 execsnoop-bpfcc，工具也可能在 /usr/share/bcc/tools。
错误 2：找不到内核头文件
安装 linux-headers-$(uname -r) 或发行版对应 kernel-devel；容器内缺宿主内核 headers 很常见。
错误 3：Operation not permitted
检查是否 root、capability、perf_event_paranoid、seccomp、AppArmor/SELinux、Kubernetes 安全上下文。
错误 4：verifier 拒绝加载
可能是内核过旧、BCC 版本不匹配、工具使用了当前内核不支持的 helper 或探针字段。
错误 5：无输出
可能目标 PID 错、容器 PID 映射错、事件没有发生、过滤过窄，或工具挂在了当前内核不存在的探针。
错误 6：输出太多
缩短窗口、加 PID/命令/端口过滤、保存文件后汇总，不要把终端滚屏当分析。
错误 7：字段解释错
不同版本输出列可能变化，先看表头和 -h；不要盲目套用旧 awk 列号。
错误 8：误判正常失败
程序查找路径时常有正常 ENOENT；要看最终是否成功、频率是否异常、是否和故障窗口对齐。

最小排障模板

# 1. 找命令
for t in execsnoop opensnoop biosnoop tcplife; do
  command -v "$t" || command -v "$t-bpfcc" || true
done

# 2. 看帮助和版本差异
execsnoop-bpfcc -h 2>&1 | head -40

# 3. 用短窗口验证工具链
sudo timeout 5s execsnoop-bpfcc -T

# 4. 如果失败，收集只读诊断
uname -a
cat /proc/sys/kernel/perf_event_paranoid
cat /proc/sys/kernel/unprivileged_bpf_disabled 2>/dev/null || true
mount | grep -E 'debugfs|bpf' || true

17. AI Infra 排障 playbook

案例 A：模型服务启动慢

# 目标：确认是路径查找、权限、动态库还是 I/O
PID=$(pgrep -n -f 'python.*serve.py')
sudo timeout 30s opensnoop-bpfcc -T -p "$PID" > /tmp/open.$PID.log
grep -E 'ENOENT|EACCES|\.so|safetensors|tokenizer|config' /tmp/open.$PID.log | head -120

# 如果打开成功但仍然慢，再看块 I/O
sudo timeout 20s biosnoop-bpfcc > /tmp/bio.startup.log

案例 B：训练 GPU 利用率周期性下降

# 目标：确认是否有进程启动、checkpoint 写入或数据读取尖峰
sudo timeout 60s execsnoop-bpfcc -T > /tmp/exec.train.log &
sudo timeout 60s biosnoop-bpfcc > /tmp/bio.train.log &
wait

grep -E 'python|torchrun|deepspeed|rsync|tar|gzip|checkpoint' /tmp/exec.train.log | head -80
tail -80 /tmp/bio.train.log

案例 C：推理 p99 突然升高

# 目标：确认是否连接短生命周期、重试、远端异常
PID=$(pgrep -n -f 'model.*server|serve.py|uvicorn|gunicorn')
sudo timeout 45s tcplife-bpfcc -p "$PID" > /tmp/tcp.$PID.log

# 按远端或端口聚合需要根据实际列调整；先看表头
head -5 /tmp/tcp.$PID.log
grep -E ':80|:443|:50051|:8000|:8080' /tmp/tcp.$PID.log | head -100
报告模板： 写清楚采集时间、节点、命令、目标 PID/Pod、工具版本/命令名、原始日志位置、观察到的事件模式、和业务指标对齐的证据，以及没有覆盖的范围。

18. 速查、练习和学习路线

常用命令速查

目标命令模板
找工具名command -v execsnoop || command -v execsnoop-bpfcc
看进程启动sudo timeout 10s execsnoop-bpfcc -T
看某进程文件打开sudo timeout 20s opensnoop-bpfcc -T -p PID
看块 I/O 延迟sudo timeout 20s biosnoop-bpfcc
看 TCP 生命周期sudo timeout 30s tcplife-bpfcc -p PID
查权限相关 sysctlcat /proc/sys/kernel/perf_event_paranoid

学习路线

  1. 先理解 eBPF 的事件驱动模型：探针触发、内核侧过滤、用户态输出。
  2. 从四个工具开始：execsnoop、opensnoop、biosnoop、tcplife。
  3. 每次练习只问一个问题，例如“这个命令启动了什么子进程”或“这个服务打开了哪些模型文件”。
  4. 学会和 perf、strace、iostat、ss、tcpdump 组合验证。
  5. 最后再学习 bpftrace 或自写 BCC 脚本，避免一开始就陷入内核细节。

安全练习

# 在非生产 Linux 机器上练习
mkdir -p /tmp/bcc-demo

# 终端 A：观察 exec
sudo timeout 20s execsnoop-bpfcc -T

# 终端 B：触发 exec
python3 -c 'import subprocess; subprocess.run(["/bin/echo", "hello-bcc"])'

# 终端 A：观察 open
sudo timeout 20s opensnoop-bpfcc -T | grep bcc-demo

# 终端 B：触发 open
echo data > /tmp/bcc-demo/input.txt
python3 -c 'open("/tmp/bcc-demo/input.txt").read()'
练习原则： 在测试机上先熟悉字段和输出节奏，再到生产短窗口使用。不要第一次运行 BCC 就对高 QPS 服务做全局无过滤追踪。
