1. ib_write_bw / ib_read_bw 是什么

ib_write_bw 与 ib_read_bw 属于 perftest 工具集，用于测试 RDMA verbs 层的带宽。它们绕过 TCP/IP socket 数据路径，直接使用 RDMA queue pair、memory registration、completion queue 等机制，把数据搬运压力放到 HCA/NIC、PCIe、内存子系统和网络 fabric 上。

ib_write_bw
测试 RDMA Write。发起端把本地 buffer 写到对端注册内存，常用于观察单向推送带宽上限。
ib_read_bw
测试 RDMA Read。发起端从对端注册内存读取数据，更依赖 read request/response 路径，部分平台上更容易暴露读带宽限制。
perftest 的价值
比 NCCL 更底层，比 iperf3 更贴近 RDMA；适合把“网络链路问题”和“训练框架/集合通信问题”拆开。
# 常见包名，按发行版选择
sudo apt-get install perftest rdma-core ibverbs-utils
sudo dnf install perftest rdma-core infiniband-diags

# 看工具是否存在
command -v ib_write_bw
command -v ib_read_bw

# 看本机 RDMA 设备
ibv_devinfo -l
ibv_devices
命名提醒： 工具名以 ib_ 开头，但并不只用于 InfiniBand；在 RoCE 网卡上也常用，只是需要正确选择以太网接口、GID index、PFC/ECN 等网络配置。

2. AI Infra 中的 RDMA 带宽心智模型

AI 集群排障时，perftest 是底层链路体检；NCCL 是真实集合通信基准；训练吞吐则还包含框架、数据、计算和调度因素。

3. 安装、版本与环境预检

不要上来就跑带宽。先确认网卡、端口状态、链路层、速率、IP/GID、驱动和固件信息。很多“带宽差”其实是端口没起来、跑在错误端口、RoCE GID 选错、MTU 不一致或 PCIe 降速。

# 设备和端口
ibv_devinfo -v
ibstat
rdma link show

# mlx5 常见命名示例：mlx5_0 端口 1
ibv_devinfo -d mlx5_0 -i 1

# 网卡/IP/MTU，RoCE 场景尤其重要
ip -br addr
ip link show
ethtool ens5f0np0

# PCIe 和 NUMA 关系
lspci | grep -i -E 'mellanox|nvidia|connectx|bluefield'
lspci -vv -s 0000:81:00.0 | grep -E 'LnkCap|LnkSta'
cat /sys/class/infiniband/mlx5_0/device/numa_node
检查项期望异常信号
端口状态ACTIVE / PORT_ACTIVEDown、Init、端口号选错
链路层IB 或 Ethernet 与预期一致RoCE 环境按 IB 假设排查，或反过来
速率与网卡和交换机规格匹配400G 卡只协商到 100G/200G
MTU端到端一致主机 MTU、交换机 MTU、RoCE path MTU 不一致
NUMA测试进程靠近 NIC 所在 NUMA跨 socket 读写导致吞吐下降、CPU 占用异常
版本记录： 每次正式测试都记录 ib_write_bw --version 或包版本、ofed_info -s、内核版本、NIC 固件版本和交换机配置摘要，避免不同批次结果不可比。

4. server/client 最小工作流

两台机器分别执行 server 和 client。server 先启动并等待；client 带上 server 地址发起连接。以下命令故意使用较保守的参数，适合作为连通性 smoke test。

节点 A：server

# 节点 A：监听，等待 client
ib_write_bw -d mlx5_0 -i 1 -F --report_gbits

# RoCE 常见写法：显式指定 GID index
ib_write_bw -d mlx5_0 -i 1 -x 3 -F --report_gbits

节点 B：client

# 节点 B：连接节点 A 的 RDMA/RoCE 可达 IP
ib_write_bw -d mlx5_0 -i 1 -F --report_gbits 192.168.100.11

# RoCE：client 和 server 端的 -x 需要匹配可达的 GID 类型
ib_write_bw -d mlx5_0 -i 1 -x 3 -F --report_gbits 192.168.100.11
参数作用备注
-d mlx5_0选择 RDMA device避免多卡机器跑错 HCA
-i 1选择端口双口卡尤其要明确
-x 3选择 GID indexRoCE 常用；实际索引以本机为准
-F避免 CPU frequency 检查中断测试不代表可以忽略 CPU/NUMA 影响
--report_gbits以 Gbit/s 报告更容易和 100G/200G/400G 链路对齐
不要盲跑： 如果在共享 RoCE fabric 上测试，先确认测试链路、限速策略和维护窗口。满速 RDMA 压测可能影响训练作业、存储流量或同机其他租户。

5. ib_write_bw：RDMA Write 带宽测试

ib_write_bw 测的是 RDMA Write：发起端把数据直接写入远端已注册内存。AI 集群中它常用于确认主机到主机的单向 RDMA 推送能力是否达到网卡规格的合理比例。

# server
ib_write_bw -d mlx5_0 -i 1 -F --report_gbits

# client：跑 64 KiB message，持续 10 秒，便于观察稳定带宽
ib_write_bw -d mlx5_0 -i 1 -F --report_gbits -s 65536 -D 10 192.168.100.11

# RoCE：显式 GID index
ib_write_bw -d mlx5_0 -i 1 -x 3 -F --report_gbits -s 65536 -D 10 192.168.100.11
小消息
-s 64、-s 256 更关注消息率、CQ 处理、CPU 与队列效率。
中大消息
-s 65536、-s 1048576 更容易接近链路吞吐上限。
长时间
-D 30 或更长可观察 ECN/PFC、热稳定性和短时抖动。

常用变体

# 双向测试：两端同时发起流量，观察全双工能力
ib_write_bw -d mlx5_0 -i 1 -F --report_gbits -b -s 65536 -D 10 SERVER_IP

# 扫 message size，观察拐点
for s in 64 256 1024 4096 16384 65536 1048576; do
  ib_write_bw -d mlx5_0 -i 1 -F --report_gbits -s "$s" -D 5 SERVER_IP
done
解释重点： 单向 write 带宽接近线速不代表 NCCL 一定达标，但如果 write 带宽明显偏低，NCCL 很难表现好。

6. ib_read_bw：RDMA Read 带宽测试

ib_read_bw 测的是 RDMA Read：发起端从远端注册内存读取数据。Read 路径与 Write 不同，受 outstanding read、网卡 read pipeline、PCIe、交换网络和对端内存路径影响，结果经常与 write 不完全一致。

# server
ib_read_bw -d mlx5_0 -i 1 -F --report_gbits

# client
ib_read_bw -d mlx5_0 -i 1 -F --report_gbits -s 65536 -D 10 192.168.100.11

# RoCE with GID index
ib_read_bw -d mlx5_0 -i 1 -x 3 -F --report_gbits -s 65536 -D 10 192.168.100.11
现象可能原因下一步
write 高、read 低read outstanding 不足、NIC read 能力限制、NUMA/PCIe 路径差增加并发 QP、检查 PCIe、绑定 CPU、对比不同 message size
read/write 都低链路速率、GID、MTU、拥塞控制、端口选错先回到预检和最小命令
短测高、长测低PFC pause、ECN/拥塞、热降频、后台流量延长 -D，同步观察交换机计数器
不要混淆： RDMA Read 带宽偏低不一定意味着网络物理链路坏了；它可能是 read 操作本身的 pipeline、队列深度或平台实现限制。

8. GID index：RoCE 测试的第一关键参数

RoCE 使用以太网承载 RDMA，GID 表中可能同时存在 IPv4、IPv6、RoCE v1/v2、不同 VLAN 或不同 IP 对应的条目。-x 选错时，常见表现是连接失败、路由不通、跑到错误网络、或者性能异常。

# 查看 GID 表
show_gids

# 常见 sysfs 路径
for f in /sys/class/infiniband/mlx5_0/ports/1/gids/*; do
  printf '%s ' "$f"
  cat "$f"
done

# 查看 GID 类型，区分 RoCE v1 / RoCE v2
for f in /sys/class/infiniband/mlx5_0/ports/1/gid_attrs/types/*; do
  printf '%s ' "$f"
  cat "$f"
done
检查点说明命令
GID 是否对应目标网卡 IP多 IP、多 VLAN、多 bond 环境容易选错show_gids、ip addr
GID 类型RoCE v2 常见于可路由以太网络gid_attrs/types
两端一致性server/client 都要使用可互通的 GID index两端分别确认 -x
交换网络配置PFC/ECN/DSCP/PCP 不当会影响稳定性交换机计数器与主机 QoS 配置
# 推荐：把 GID index 写入测试记录，不要只写“RoCE 已测试”
SERVER=192.168.100.11
DEV=mlx5_0
PORT=1
GID=3
ib_write_bw -d "$DEV" -i "$PORT" -x "$GID" -F --report_gbits -s 65536 -D 10 "$SERVER"
高频事故： 同一台机器的 mlx5_0、ens*、VLAN、bond、container network namespace 之间不一定一一对应。GID index 必须以实际 show_gids 和 IP 可达性为准。

RoCE 的 RDMA 性能问题经常来自以太网 QoS 和 IP/GID 映射，而不是 perftest 本身。

9. InfiniBand vs RoCE

ib_write_bw 和 ib_read_bw 在 IB 与 RoCE 上命令形态相近，但排障重点不同。IB 更关注 fabric 管理、LID、SM、PKey、端口 active_mtu；RoCE 更关注 GID、IP、VLAN、PFC/ECN、DSCP/PCP、以太网 MTU 和交换机队列。

维度InfiniBandRoCE
寻址LID/GID，依赖 IB fabricGID 与 IP/以太网接口强相关
拥塞/无损IB fabric 机制与 SM 配置PFC/ECN/DCQCN 等以太网 QoS 配置
常见故障SM、端口状态、PKey、链路降速GID index、MTU、VLAN、PFC pause storm、ECN 不生效
测试参数通常 -d、-i 足够开始常需要显式 -x，并确认 IP 可达
# IB 快速检查
ibstat
iblinkinfo 2>/dev/null | head

# RoCE 快速检查
show_gids
ip route get 192.168.100.11
ethtool -S ens5f0np0 | grep -i -E 'pause|pfc|ecn|discard|drop|timeout'
测试命名建议： 报告里明确写成 IB/mlx5_0/port1 或 RoCEv2/ens5f0np0/GID3/VLAN100，否则后续很难复现。

10. MTU、message size 与 inline

MTU 和 perftest 的 message size 不是一回事。MTU 是链路层/路径最大传输单元，message size 是每个 RDMA 操作的数据大小。大消息通常更容易打满链路，小消息更考验消息率、CQ 处理和 CPU 路径。

参数/概念含义建议
-smessage size，单位 byte至少测 64、256、4K、64K、1M
-mperftest path MTU 参数，具体可用值以 --help 为准只在确认端到端支持后指定
网卡 MTULinux netdev MTU，RoCE 场景关键两端和交换机路径一致
inline小消息直接内联到 WQE，减少 DMA 开销适合小消息实验，不应用大消息结论替代
# 查看 RoCE 以太网 MTU
ip link show ens5f0np0

# 查看 IB 端口 active_mtu
ibv_devinfo -d mlx5_0 -i 1 | grep -i mtu

# 扫描不同 message size
for s in 64 256 1024 4096 16384 65536 262144 1048576; do
  echo "### size=$s"
  ib_write_bw -d mlx5_0 -i 1 -x 3 -F --report_gbits -s "$s" -D 5 SERVER_IP
done
解释陷阱： 大消息带宽高，不代表小消息延迟和消息率好；小消息差，也不一定影响大张量 AllReduce。按业务通信形态选择测试矩阵。

11. 多连接、多队列与并发

单 QP 不一定能打满高规格链路，尤其是 400G/800G、多端口、多 rail 或 read 测试。perftest 支持通过多个 QP/连接、双向模式和持续时间来观察并发能力。具体参数名可能随版本变化，先用 ib_write_bw --help 确认本机支持。

# 查看本机 perftest 支持的并发参数
ib_write_bw --help | grep -E 'qp|connection|bidirectional|duplex|post|cq|events'
ib_read_bw --help | grep -E 'qp|connection|bidirectional|duplex|post|cq|events'

# 常见思路：增加 QP 数，观察单流打不满时是否可扩展
ib_write_bw -d mlx5_0 -i 1 -x 3 -F --report_gbits -s 65536 -D 10 -q 4 SERVER_IP

# 双向模式观察全双工
ib_write_bw -d mlx5_0 -i 1 -x 3 -F --report_gbits -s 65536 -D 10 -b SERVER_IP
目标参数方向判断
单连接上限默认 QP，固定大消息评估最小路径是否健康
链路总吞吐增加 QP/连接数，必要时多进程看是否随并发增加接近线速
全双工能力双向模式看两方向同时压测是否互相影响
CQ/CPU 压力小消息 + 多 QP看消息率、CPU 使用率和软中断
AI Infra 视角： NCCL 通常会使用多通道、多 rail 和多 GPU 组合，不要只用一个 QP 的结果否定整机；也不要用多 QP 跑满掩盖单路径异常。

12. NUMA、CPU 亲和与 PCIe 拓扑

高带宽 RDMA 测试不是纯网络测试。CPU 线程、内存分配、PCIe root complex、NIC 所在 NUMA、GPU 所在 NUMA 都会影响结果。400G 以上链路尤其容易被跨 socket 内存访问或 PCIe 降速拖垮。

# 找 NIC 所在 NUMA
cat /sys/class/infiniband/mlx5_0/device/numa_node

# 看 CPU 拓扑
lscpu -e=CPU,NODE,SOCKET,CORE,ONLINE
numactl --hardware

# 绑定到 NIC 所在 NUMA 节点，例如 NUMA 1
numactl --cpunodebind=1 --membind=1 \
  ib_write_bw -d mlx5_0 -i 1 -x 3 -F --report_gbits -s 65536 -D 10 SERVER_IP

# 或用 taskset 绑定核心
taskset -c 32-47 ib_write_bw -d mlx5_0 -i 1 -x 3 -F --report_gbits -s 65536 -D 10 SERVER_IP
检查项命令说明
NIC NUMAcat /sys/class/infiniband/DEV/device/numa_node决定进程和内存优先绑定到哪里
PCIe 链路lspci -vv确认速度和宽度没有降级
GPU/NIC 亲和nvidia-smi topo -mNCCL/GDR 相关，perftest 主机内存测试不等价于 GPU Direct
CPU 频率cpupower frequency-info低频、节能策略可能影响小消息和 CQ 处理
对照实验： 同一命令分别跑“不绑定”和“绑定 NIC NUMA”，如果差异明显，先修正测试方法，再判断网络是否异常。

13. 和 NCCL baseline 对齐

perftest 证明 RDMA 底座，NCCL tests 证明 GPU 集合通信路径。AI 集群验收应同时保留两类数据：ib_write_bw/ib_read_bw 的 host RDMA baseline，以及 all_reduce_perf 的 GPU 通信 baseline。

# perftest host RDMA baseline
ib_write_bw -d mlx5_0 -i 1 -x 3 -F --report_gbits -s 1048576 -D 10 SERVER_IP
ib_read_bw  -d mlx5_0 -i 1 -x 3 -F --report_gbits -s 1048576 -D 10 SERVER_IP

# NCCL tests 示例，按实际环境调整
NCCL_DEBUG=INFO \
NCCL_IB_HCA=mlx5_0 \
NCCL_SOCKET_IFNAME=ens5f0np0 \
./build/all_reduce_perf -b 8M -e 8G -f 2 -g 8
组合结果解释下一步
perftest 低、NCCL 低底层链路或主机路径可能有问题先修 RDMA、NUMA、QoS、链路速率
perftest 高、NCCL 低GPU Direct、NCCL 拓扑、算法、rail 选择或框架配置问题看 NCCL_DEBUG=INFO、拓扑、HCA 选择
perftest 高、NCCL 高网络底座和集合通信都健康训练慢时转向数据管线、计算、调度
perftest 抖、NCCL 抖拥塞、PFC/ECN、共享流量或硬件不稳定长测并同步采集交换机/网卡计数器
不要直接换算： perftest 的 Gbit/s、NCCL algbw/busbw、训练 step time 不是同一个指标。它们用于分层定位，不应简单互相等价。

选择图：ib_write_bw、qperf、iperf3、NCCL tests 怎么选

iperf3 测 socket 网络，perftest 测 RDMA verbs，NCCL tests 测 GPU 集合通信；层次不同，结论不能互相替代。

14. ib_write_bw vs qperf vs iperf3

工具层次优势不适合
ib_write_bw/ib_read_bwRDMA verbs最贴近 HCA/RDMA 数据路径，适合 AI RDMA baseline不能代表 NCCL 算法、GPU Direct 或训练吞吐
qperfTCP、RDMA 等多模式快速测延迟/带宽，命令简单细粒度 RDMA 参数和 perftest 生态不如专用工具
iperf3TCP/UDP socket验证 IP 网络、路由、防火墙、基础吞吐不能证明 RDMA verbs、GID、PFC/ECN 正确
nccl-testsGPU 集合通信最接近训练通信模式底层问题与 NCCL 配置问题混在一起，需配合 perftest 分层
# 分层排障示例
iperf3 -s
iperf3 -c SERVER_IP -P 8

qperf SERVER_IP tcp_bw tcp_lat
qperf SERVER_IP rc_bw rc_lat

ib_write_bw -d mlx5_0 -i 1 -x 3 -F --report_gbits -s 65536 -D 10 SERVER_IP
经验法则： iperf3 通过只能说明 IP 层可用；perftest 通过才说明 RDMA verbs 路径基本可用；NCCL 通过才说明 GPU 通信路径基本可用。

15. 安全压测与生产注意事项

RDMA 带宽测试可能跑满端口、触发 PFC pause、影响共享交换机 buffer，甚至让同租户训练作业出现尾延迟。生产环境必须把测试当成变更操作管理。

先小后大
先 -s 1024 -D 3 验证连通，再扩大到 64K/1M 和 10 到 60 秒。
限定范围
优先选择隔离主机对、隔离 VLAN/队列或维护窗口，避免全网并发扫测。
同步观测
同时采集 ethtool -S、交换机 counters、CPU、NUMA、温度和 dmesg。
记录参数
记录 DEV、PORT、GID、server IP、message size、duration、QP 数、NUMA 绑定。
# 安全的渐进式测试模板
SERVER=192.168.100.11
DEV=mlx5_0
PORT=1
GID=3

# 1. 短测试
ib_write_bw -d "$DEV" -i "$PORT" -x "$GID" -F --report_gbits -s 1024 -D 3 "$SERVER"

# 2. 中等消息
ib_write_bw -d "$DEV" -i "$PORT" -x "$GID" -F --report_gbits -s 65536 -D 10 "$SERVER"

# 3. 长一点的稳定性测试，仅在确认影响范围后执行
ib_write_bw -d "$DEV" -i "$PORT" -x "$GID" -F --report_gbits -s 1048576 -D 60 "$SERVER"
生产红线： 不要在未知 fabric 上并发启动大量 server/client 组合；不要把压测脚本放进自动巡检高频执行；不要在未确认 PFC/ECN 的 RoCE 网络上长时间满速轰炸。

排障图：带宽低或连接失败时的优先级

排障优先级：先确认设备和寻址，再看 MTU/QoS，最后看 NUMA/PCIe 与并发参数；上层 NCCL 放在 perftest 之后。

16. 常见故障与排障流程

连接超时
检查 server 是否先启动、防火墙、IP 路由、GID index、端口和设备名。
Failed to modify QP
常见于 GID/MTU/端口状态不匹配，先回到 ibv_devinfo 和 show_gids。
带宽只有理论值一半
检查端口速率、PCIe 宽度、NUMA 绑定、是否单 QP 不足、是否跑到错误端口。
RoCE 长测抖动
看 PFC pause、ECN mark、交换机 buffer、丢包、拥塞队列映射。
server 无输出或等待
server 正常会等待 client；确认 client 使用的是 server 的正确地址。
NCCL 慢但 perftest 快
转查 GPU/NIC 拓扑、GDR、NCCL HCA 选择、rail 数、NCCL 日志。

排障命令包

# 设备状态
ibv_devinfo -d mlx5_0 -i 1
rdma link show

# RoCE GID 和 IP
show_gids
ip addr show
ip route get SERVER_IP

# 网卡计数器，按驱动字段过滤
ethtool -S ens5f0np0 | grep -i -E 'drop|discard|error|timeout|pause|pfc|ecn|retry|roce'

# 内核日志
dmesg -T | grep -i -E 'mlx5|rdma|infiniband|pci|aer|error|reset'

# PCIe 降速
lspci -vv -s 0000:81:00.0 | grep -E 'LnkCap|LnkSta'
复现策略： 保留一组“已知好”的 server/client 主机对。新节点异常时，分别与已知好节点交叉测试，可以快速判断问题在本机、对端还是 fabric。

17. 可复现实验模板

正式验收需要可复现：同一批机器、同一套参数、同一份环境信息、同一段测试时间。下面模板只写日志，不修改系统配置，适合按需扩展到巡检或交付记录。

#!/usr/bin/env bash
set -euo pipefail

SERVER="${1:?usage: $0 SERVER_IP}"
DEV="${DEV:-mlx5_0}"
PORT="${PORT:-1}"
GID="${GID:-3}"
DURATION="${DURATION:-10}"
OUT="${OUT:-rdma-perftest-$(hostname)-$(date +%Y%m%d-%H%M%S).log}"

{
  echo "## meta"
  date -Is
  hostname
  uname -a
  echo "DEV=$DEV PORT=$PORT GID=$GID SERVER=$SERVER DURATION=$DURATION"

  echo "## devices"
  ibv_devinfo -d "$DEV" -i "$PORT" || true
  rdma link show || true
  show_gids || true

  echo "## numa"
  cat "/sys/class/infiniband/$DEV/device/numa_node" || true
  numactl --hardware || true

  echo "## write bandwidth"
  for s in 1024 4096 65536 1048576; do
    echo "### ib_write_bw size=$s"
    ib_write_bw -d "$DEV" -i "$PORT" -x "$GID" -F --report_gbits -s "$s" -D "$DURATION" "$SERVER"
  done

  echo "## read bandwidth"
  for s in 1024 4096 65536 1048576; do
    echo "### ib_read_bw size=$s"
    ib_read_bw -d "$DEV" -i "$PORT" -x "$GID" -F --report_gbits -s "$s" -D "$DURATION" "$SERVER"
  done
} | tee "$OUT"
记录字段为什么重要
主机名、时间、内核、驱动/OFED、固件支撑跨批次比较和回归定位
DEV/PORT/GID/server IPRDMA 测试最小复现条件
message size 与 duration决定结果关注吞吐、消息率还是稳定性
NUMA/PCIe/端口状态避免把主机拓扑问题误判为网络问题
自动化边界： 自动巡检可以跑短测试；长时间满速压测应保留人工审批或维护窗口，尤其是共享 RoCE fabric。

- write average: xxx Gbit/s
- read average:  xxx Gbit/s
- message rate:  xxx Mpps

- ethtool drops/errors: 0
