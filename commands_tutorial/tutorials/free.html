free 深度教程：AI Infra 场景下的内存、页缓存、Swap 与容器洞察

这份教程按常用 Linux 命令 free 讲解。它不是简单字段翻译，而是从“Linux 把物理内存同时用于进程、内核、页缓存、buffer、slab、tmpfs 和可回收缓存”这个模型出发，系统解释 Mem/Swap、available 与 free、page cache、训练内存压力、pinned memory、swap 风险、cgroups/容器口径、/proc/meminfo/smaps 的边界，以及 AI Infra 排障流程。

AI InfraMem/Swapavailable vs freePage CachePinned Memory训练内存压力容器/cgroup/proc/meminfo排障
一句话理解： free 是 Linux 主机内存总览表：它回答“整机还有多少可用内存、缓存是否可回收、swap 是否被动用”，但不直接回答“哪个进程泄漏了哪一段内存”。
实践原则： AI 训练节点不要只盯 free 列；优先看 available、swap used 与趋势，再结合 ps、smem、pmap、/proc/PID/smaps_rollup、cgroup 统计和 GPU 工具下钻。

1. free 是什么

free 来自 procps/procps-ng 工具集，用来从内核统计中汇总系统内存和 swap 使用情况。它读取的核心来源是 /proc/meminfo，再按人类更容易理解的几列展示。

它擅长什么
快速判断整机内存余量、页缓存规模、swap 是否被使用，以及采样趋势是否恶化。
它不擅长什么
不能直接定位进程级 RSS/PSS、Python 对象泄漏、CUDA 显存、NUMA 分布或某个 cgroup 内部责任方。
它的定位
主机内存入口仪表盘。先判断系统是否有压力，再下钻到进程、容器、NUMA、存储或框架。
# 最常用：人类可读单位
free -h

# 观察趋势：每 1 秒输出一次，共 10 次
free -h -s 1 -c 10

# 宽格式，拆出 buffers 与 cache
free -h -w

# 按 GiB 显示，适合大内存 AI 节点
free -g
边界提醒： free 看的是系统内存，不看 GPU 显存。GPU OOM 要看 nvidia-smi、框架日志和显存分配器统计；CPU 内存 OOM 才主要从 free、cgroup 和 /proc 下钻。

2. AI Infra 为什么需要 free

训练和推理任务的瓶颈不只在 GPU。数据加载、样本解码、augmentation、tokenization、checkpoint、模型权重加载、CPU offload、KV cache 元数据、对象存储客户端缓存，都可能让主机内存成为瓶颈。free 的价值是先回答“主机内存是否足够支撑这条 pipeline”。

AI 场景free 重点字段常见解释
训练吞吐突然下降available 下降、swap used 或 si/so 升高CPU 内存压力导致页回收或 swap，GPU 在等数据。
首次 epoch 慢、后续变快buff/cache 上升，available 仍充足数据集逐步进入 page cache，通常是正常现象。
DataLoader worker 变多后 OOMavailable 快速下降，进程 RSS/PSS 增长worker 复制数据结构、预取队列或 pinned memory 占用扩大。
容器被 OOMKilled宿主机 available 充足但 cgroup memory.current 达限容器内存限制比整机小，free 口径可能误导。
AI Infra 心法： available 告诉你“主机还能给新分配腾出多少内存”，buff/cache 告诉你“数据和文件系统缓存吃了多少”，Swap 告诉你“系统是否已经开始用慢盘当内存”。

3. 安装、版本与基本语法

多数 Linux 发行版默认带 free。极简容器镜像可能没有，需要安装 procps 或 procps-ng。普通用户即可运行；是否能看到其他进程细节取决于后续工具和系统权限。

free [options]

# 常用选项
# -h: human readable
# -b/-k/-m/-g: 固定单位
# -w: wide，拆分 buffers 与 cache
# -s N: 每 N 秒重复
# -c N: 输出 N 次后退出
# -t: 增加 total 汇总行
系统安装命令说明
Ubuntu/Debiansudo apt-get update && sudo apt-get install -y procpsfree 通常已预装。
RHEL/CentOS/Rockysudo dnf install -y procps-ng旧系统可用 yum install procps-ng。
诊断容器apt-get install procps只建议在调试镜像或临时容器中安装。
# 确认路径和版本
command -v free
free --version 2>/dev/null || free -V 2>/dev/null || true

# 查看帮助
free --help
复制建议： 排障记录里优先贴 free -h -w 和 free -h -s 1 -c 10，前者清楚，后者能展示趋势。

4. 输出字段总览

典型输出包含 Mem 和 Swap 两行。不同 procps 版本的列名可能略有差异，但现代 Linux 常见列包括 total、used、free、shared、buff/cache 和 available。

$ free -h
               total        used        free      shared  buff/cache   available
Mem:           503Gi       116Gi        18Gi       2.0Gi       368Gi       380Gi
Swap:          16Gi        0.0Gi        16Gi
列含义AI Infra 读法
total可管理的总内存，扣除了内核保留等不可用部分。节点内存容量基线，不等于 DIMM 标称值。
used已使用内存的汇总口径，通常不包含可回收 cache 的简单“坏用量”。不要单独用它判断 OOM 风险。
free完全未使用的内存。低很正常，Linux 会用空闲内存做缓存。
shared主要来自 tmpfs/shmem 等共享内存。大数据预处理、Ray、容器 /dev/shm 可能推高它。
buff/cache块设备 buffer、page cache、部分可回收内核缓存。数据集读入后增大通常是好事，但也会与进程内存竞争。
available估算无需 swap 就能给新程序使用的内存。最适合快速判断 CPU 内存余量。
列名陷阱： 老版本 free 可能显示 -/+ buffers/cache 行；现代版本用 available 替代了很多手工心算。

5. 整体心智模型

free 的核心不是“空闲内存越多越好”，而是理解哪些内存正在被进程持有，哪些只是可回收缓存。

6. Mem 行：total、used、free

Mem 行描述物理内存的宏观状态。total 是内核可管理内存，used 是已占用汇总，free 是完全未使用内存。对 AI 节点来说，free 低经常只是说明数据集或权重文件被缓存了。

判断更可靠的证据说明
free 很低available 仍高、Swap used 为 0通常不是问题，可能是 page cache 充分利用内存。
used 很高结合 buff/cache 和进程 RSS/PSS需要区分进程真正持有和可回收缓存。
total 低于机器标称dmesg、BIOS、NUMA、内核保留、虚拟机规格内核和设备会保留一部分内存。
# 宽输出能拆开 buffers 与 cache
free -h -w

# 和内核原始口径对照
grep -E '^(MemTotal|MemFree|MemAvailable|Buffers|Cached|SReclaimable|Shmem):' /proc/meminfo
读法： 如果 available 有数百 GiB、swap used 为 0，即使 free 只有几 GiB，通常也不代表训练马上会 OOM。

7. available vs free

available 是现代 free 最重要的列之一。它估算在不发生 swap 的情况下，系统还能给新进程或现有进程增长使用多少内存。它会考虑可回收 page cache、slab、低水位线等因素，因此比 free 更接近“真实余量”。

free
完全没被使用的页。这个值低很常见，因为 Linux 不想让内存闲着。
available
估算可安全分配的内存。排障时更适合判断是否接近 CPU 内存 OOM。
# 只看关键列
free -h | awk 'NR==1 || /^Mem:/ {print}'

# 采样 available 趋势
while true; do
  date '+%F %T'
  free -h | awk '/^Mem:/ {print "available=" $7, "free=" $4, "buff/cache=" $6}'
  sleep 5
done
现象解释下一步
free 低、available 高缓存可回收，通常健康。无需清 cache，继续观察趋势。
available 持续下降进程或不可回收内核内存持续增长。用 ps、smem、slabtop、cgroup 统计下钻。
available 低且 swap 活跃系统已进入内存压力。降低 batch/worker/prefetch，限制任务或扩容。
不要误操作： 为了让 free 变高而盲目 drop_caches 会破坏页缓存，可能让训练和推理更慢；生产上只应在明确实验目的和影响窗口时执行。

8. buff/cache 与 page cache

buff/cache 汇总了文件页缓存、buffer、部分可回收 slab 等。AI 任务读取数据集、模型权重、tokenizer 文件和 checkpoint 时，page cache 会显著增长；这通常提升后续读取速度。

对象在 free 中的表现AI 场景
数据集文件缓存buff/cache 上升第二轮 epoch 可能更快。
模型权重文件缓存buff/cache 上升多 worker 或多进程加载时减少磁盘读取。
tmpfs//dev/shmshared 上升，也占用内存Ray、DataLoader、IPC 队列、容器共享内存。
slab 元数据可能计入可回收缓存大量小文件、网络文件系统、容器层可能推高。
# 查看 page cache 相关原始字段
grep -E '^(Cached|Buffers|SReclaimable|Shmem|Dirty|Writeback):' /proc/meminfo

# 查看文件系统缓存和脏页是否异常
grep -E '^(Dirty|Writeback):' /proc/meminfo

# 大量小文件场景下观察 slab
slabtop -o | head -30
正确态度： 高 page cache 是 Linux 在帮你。如果 available 仍充足，不要把 buff/cache 当成泄漏。

流程图：从 free 判断 AI 训练是否有内存压力

训练排障时先看 available 趋势，再看 swap 是否活跃，最后定位是进程、cgroup、page cache、tmpfs 还是内核缓存造成压力。

9. Swap 行与训练风险

Swap 行显示交换空间总量、已用和空闲。swap 本身不是错误，但 AI 训练/推理节点一旦持续 swap，通常意味着吞吐和尾延迟会明显恶化，因为内存访问退化为磁盘或压缩内存路径。

现象风险建议
Swap used 非零但不增长可能是历史遗留页，未必正在抖动。结合 vmstat 1 看 si/so。
Swap used 持续增长进程工作集超过物理内存。降低 batch size、worker、prefetch、缓存或扩容。
si/so 持续非零正在频繁换入换出，训练极易卡顿。立即定位进程/cgroup，必要时停止低优先级任务。
# free 看总量，vmstat 看是否正在发生 swap I/O
free -h
vmstat 1 20

# 查看系统 swappiness
cat /proc/sys/vm/swappiness

# 查看每个进程的 swap，用于定位责任方
for p in /proc/[0-9]*; do
  awk '/^Name:/{name=$2} /^VmSwap:/{if ($2 > 0) print FILENAME, name, $2 " kB"}' "$p/status" 2>/dev/null
done | sort -k3 -n | tail
生产风险： 不要在不了解业务影响时直接 swapoff -a。如果物理内存不足，关闭 swap 可能立刻触发 OOM kill；先降载、迁移或停止低优先级任务。

10. 单位、采样与趋势观察

单次 free 是快照，排障更需要趋势。内存泄漏、DataLoader 预取、checkpoint 写入、page cache 预热都需要连续采样才能看清。

命令用途
free -h快速人工阅读。
free -m脚本中按 MiB 粗略处理。
free -g大内存节点按 GiB 查看。
free -w宽输出，拆出 buffers 与 cache。
free -s 1 -c 60每秒采样 60 次后退出。
free -t增加 Mem+Swap 汇总，不适合替代真实内存余量判断。
# 带时间戳采样，方便和训练日志对齐
for i in $(seq 1 30); do
  printf '%s ' "$(date '+%F %T')"
  free -m | awk '/^Mem:/ {printf "mem_available_mb=%s buff_cache_mb=%s ", $7, $6} /^Swap:/ {print "swap_used_mb=" $3}'
  sleep 1
done | tee free-trace.log

# watch 适合人工观察，不适合严肃留证
watch -n 1 'free -h -w'
趋势判断： 稳态高 cache 不等于泄漏；available 单调下降、swap 增长、进程 PSS 增长三者同时出现，才更像真实内存压力。

11. 训练内存压力排查

AI 训练的 CPU 内存压力常来自数据管线和框架运行时，而不是模型参数本身。常见来源包括 DataLoader worker 复制父进程对象、预取队列过大、样本解码后常驻、缓存全部数据集、CPU offload、日志/metrics 队列堆积，以及 checkpoint 期间的短时峰值。

DataLoader worker
num_workers 越多，不一定越快；也可能复制数据索引、metadata 和 Python 对象。
预取与缓存
prefetch_factor、队列、数据增强中间结果会推高 CPU 内存。
Checkpoint
保存模型、优化器状态或转换格式可能产生短时双倍内存峰值。
# 先看整机趋势
free -h -s 1 -c 30

# 再看进程 RSS
ps -eo pid,ppid,rss,vsz,comm,args --sort=-rss | head -20

# 如果安装了 smem，用 PSS 更适合多进程共享库场景
smem -tk | sort -nr -k 5 | head -20

# 对单个训练进程查看汇总 smaps
grep -E '^(Rss|Pss|Private_Dirty|Shared_Clean|Swap):' /proc/$PID/smaps_rollup
症状可能原因可尝试动作
每个 epoch 开始内存跳涨缓存样本、索引或预取队列填充。降低 worker/prefetch，检查 dataset 是否把数据全量读入内存。
多 worker 后 RSS 近似倍增fork 后写时复制被破坏，Python 对象被各 worker 私有化。减少父进程大对象，使用 mmap/Arrow/WebDataset 等共享友好格式。
checkpoint 时 OOM序列化和优化器状态造成峰值。分片保存、异步保存、降低并发任务、预留内存水位。
调参原则： num_workers、pin_memory、prefetch_factor 是吞吐和内存的交换。不要只用 GPU 利用率调大它们，必须同步看 available 和进程 PSS。

12. Pinned memory 与 DataLoader

Pinned memory（page-locked memory，页锁定内存）常用于加速 CPU 到 GPU 的 DMA 传输。PyTorch 的 pin_memory=True 能减少 H2D 拷贝等待，但 pinned 内存不能像普通 page cache 那样随意换出，过量会加重主机内存压力。

概念表现排障视角
普通进程内存计入进程 RSS/PSS可被回收或换出，取决于页面类型和压力。
Pinned/page-locked通常仍表现为进程内存消耗锁页过多会降低系统可回收空间，可能触发 OOM 或传输抖动。
Page cache主要表现为 buff/cache一般可回收，不应和 pinned memory 混淆。
# PyTorch 常见相关参数示意
# DataLoader(..., num_workers=8, pin_memory=True, prefetch_factor=2)

# 观察锁页和内存概况
grep -E '^(MemAvailable|Mlocked|Unevictable|SwapTotal|SwapFree):' /proc/meminfo

# 找训练进程及 worker
ps -e -o pid,ppid,rss,comm,args --sort=-rss | grep -E 'python|torchrun|accelerate' | head -30
误区： pinned memory 不是 GPU 显存，也不是免费的加速开关。小 batch 或数据已在 GPU 附近时收益可能有限；大 batch、多 worker、高 prefetch 时主机内存成本会很明显。

对比图：free、/proc/meminfo、smaps、cgroup 各自回答什么

free 是入口，不是终点。真正定位责任方时，需要切到更细粒度的 /proc、smaps 和 cgroup 视角。

13. cgroups 与容器内存口径

在 Kubernetes、Docker、Slurm cgroup 或云平台作业环境里，free 的读数可能让人误判。你可能在容器内看到宿主机总内存，也可能看到受命名空间影响后的视角；但 OOMKilled 的判定通常来自 cgroup 限额，而不是整机 available。

检查项cgroup v2cgroup v1
当前使用cat /sys/fs/cgroup/memory.currentcat /sys/fs/cgroup/memory/memory.usage_in_bytes
内存上限cat /sys/fs/cgroup/memory.maxcat /sys/fs/cgroup/memory/memory.limit_in_bytes
事件cat /sys/fs/cgroup/memory.eventscat /sys/fs/cgroup/memory/memory.oom_control
明细cat /sys/fs/cgroup/memory.statcat /sys/fs/cgroup/memory/memory.stat
# 容器内同时看 free 和 cgroup
free -h
cat /proc/self/cgroup

# cgroup v2 常见检查
test -f /sys/fs/cgroup/memory.current && {
  echo "current=$(cat /sys/fs/cgroup/memory.current)"
  echo "max=$(cat /sys/fs/cgroup/memory.max)"
  cat /sys/fs/cgroup/memory.events
}

# Kubernetes 侧还应查看
kubectl describe pod POD_NAME
kubectl top pod POD_NAME --containers
容器陷阱： 宿主机 free -h 看起来很宽裕，Pod 仍可能因为 limits.memory 达限被 OOMKilled。容器排障必须同时看 cgroup 当前值、上限和事件。

14. free vs /proc/meminfo/smaps

free 是汇总表；/proc/meminfo 是更细的系统字段；/proc/PID/smaps 或 smaps_rollup 是进程内存映射明细。三者回答的问题不同，不能互相替代。

问题优先工具原因
整机还有多少可用内存？free -h快速看 available 和 swap。
为什么 buff/cache 高？/proc/meminfo拆 Cached、SReclaimable、Shmem、Dirty。
哪个进程占用最多？ps、smemRSS/PSS 排序更接近责任方。
某进程内存类型是什么？smaps_rollup、pmap -x看 private/shared/anonymous/file-backed/swap。
容器为什么被杀？cgroup memory.eventsOOM 事件按 cgroup 限额触发。
# meminfo 解释 free
grep -E '^(MemTotal|MemFree|MemAvailable|Buffers|Cached|SReclaimable|Shmem|Mlocked|Unevictable|Dirty|Writeback|SwapTotal|SwapFree):' /proc/meminfo

# 进程汇总，Linux 新内核通常有 smaps_rollup
PID=12345
cat /proc/$PID/smaps_rollup

# pmap 可读性较好，但 PSS 信息通常不如 smaps 完整
pmap -x $PID | tail -20
口径提醒： 多进程共享内存和共享库会让 RSS 简单相加偏大；PSS 会把共享页按比例分摊，更适合估算多 worker 训练任务的真实占用。

15. 故障模式速查

free 低但 available 高
通常是 page cache 正常利用内存。不要清 cache，继续看吞吐和 swap。
available 持续下降
可能是进程泄漏、worker 复制、tmpfs 增长、slab 增长或 cgroup 内部压力。
Swap used 增长
训练节点高风险。看 vmstat si/so 判断是否正在换页。
shared 很高
检查 /dev/shm、Ray object store、IPC 队列、tmpfs 数据。
buff/cache 很高且 available 低
可能 cache 回收受限、dirty/writeback、不可回收 slab 或工作集过大。
容器 OOM 但宿主机充足
看 cgroup 限额和 memory.events，不要只看宿主机 free。
checkpoint 时短时 OOM
保存过程峰值超过水位，需分片、降并发或预留 headroom。
GPU 空但 CPU 内存满
数据加载或 CPU offload 可能堵住训练，结合 ps、vmstat、框架 profiler。

排障命令模板

# 1. 主机概览和趋势
free -h -w
free -h -s 1 -c 30
vmstat 1 30

# 2. 原始内核字段
grep -E '^(MemAvailable|Cached|SReclaimable|Shmem|Mlocked|Unevictable|Dirty|Writeback|SwapFree):' /proc/meminfo

# 3. 进程责任方
ps -eo pid,ppid,rss,vsz,comm,args --sort=-rss | head -30

# 4. 容器/cgroup
cat /proc/self/cgroup
find /sys/fs/cgroup -maxdepth 2 -name 'memory.current' -o -name 'memory.max' -o -name 'memory.events'

16. 生产采集与安全注意事项

free 本身只读、低开销，适合生产现场采集。真正需要谨慎的是后续动作：清 cache、关闭 swap、杀进程、调整 cgroup 限额、重启训练任务都可能影响业务。

推荐采集包

# 建议在问题发生时采集，命令本身只读
mkdir -p /tmp/mem-debug
date '+%F %T' | tee /tmp/mem-debug/time.txt
free -h -w | tee /tmp/mem-debug/free.once.txt
free -h -w -s 1 -c 30 | tee /tmp/mem-debug/free.30s.txt
vmstat 1 30 | tee /tmp/mem-debug/vmstat.30s.txt
grep -E '^(Mem|Swap|Cached|Buffers|SReclaimable|Shmem|Mlocked|Unevictable|Dirty|Writeback)' /proc/meminfo | tee /tmp/mem-debug/meminfo.txt
ps -eo pid,ppid,rss,vsz,comm,args --sort=-rss | head -50 | tee /tmp/mem-debug/top-rss.txt

危险动作清单

动作风险更安全做法
echo 3 > /proc/sys/vm/drop_caches破坏 page cache，造成 IO 风暴或训练变慢。只在隔离实验中使用，先记录前后指标。
swapoff -a物理内存不足时可能立即 OOM。先降载或迁移，再规划 swap 策略。
直接杀最大 RSS 进程可能杀错共享内存大户或系统组件。先确认用户、作业、cgroup 和业务影响。
盲目调大 DataLoader worker吞吐未必升，内存可能爆。逐步调参，并同步记录 free、GPU 利用率和 step time。
最终判断模板： “在 30 秒采样内，available 从 A 降到 B，Swap used 从 C 增到 D，cgroup 当前值接近上限 E，最大 PSS 进程是 F；建议先 G，再 H。” 这样的结论比“free 很低”更可执行。
