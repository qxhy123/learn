1. nvtop 是什么

nvtop 全称常被解释为 Neat Videocard TOP，是一个基于 ncurses 的 GPU/加速器状态查看器。对 AI Infra 来说，它的价值在于把“每张 GPU 的实时状态”和“正在使用 GPU 的进程”放在同一个终端界面里，比单次 nvidia-smi 更适合连续观察。

适合场景
排查训练卡住、推理服务抖动、显存泄漏、错误占卡、MIG/多进程争用、远程节点负载异常。
不适合场景
长期指标留存、集群级告警、跨节点容量规划、账单统计。这些应交给 Prometheus、DCGM Exporter、Grafana 或调度系统。
核心优势
低门槛、实时、交互式、可通过 SSH 使用，能快速把“哪张卡异常”和“哪个 PID 可疑”连接起来。
# 启动交互式 GPU 监控
nvtop

# 查看帮助和版本，先确认本机实际支持的选项
nvtop --help
nvtop --version

# 查看本机手册，发行版打包的选项以本机为准
man nvtop
命名提醒： 虽然名字里有 nv，现代 nvtop 不只看 NVIDIA。上游版本也支持 AMD、Intel 以及一些其他加速器，但各厂商指标完整性不同。

2. 核心模型：设备区、图表区、进程区

nvtop 的价值不是单个数字，而是把设备、趋势和进程放在同屏，让你更快完成归因。

3. 安装与版本确认

不同发行版打包的 nvtop 版本差异很大，支持的厂商、快捷键和命令行参数也可能不同。生产环境先确认“装的是哪个版本、链接了哪些 GPU 后端、当前机器驱动是否满足”。

环境常见安装方式注意点
Ubuntu / Debiansudo apt install nvtop仓库版本可能偏旧；需要新 GPU 或 Intel/AMD 支持时检查 backports、PPA、snap、AppImage 或源码构建。
Fedora / RHEL 系sudo dnf install nvtopRHEL/Rocky/Alma 常通过 EPEL 获取；驱动和权限仍需单独满足。
Arch Linuxsudo pacman -S nvtop通常较新，但仍以 nvtop --version 和 man nvtop 为准。
源码构建cmake .. -DNVIDIA_SUPPORT=ON -DAMDGPU_SUPPORT=ON -DINTEL_SUPPORT=ON适合需要明确启用后端、修复旧包缺陷或部署到定制镜像。
# 确认命令是否存在
command -v nvtop

# 确认版本和本机帮助
nvtop --version
nvtop --help

# NVIDIA 节点先确认驱动/NVML 是否工作
nvidia-smi

# AMD/Intel 节点先确认 DRM 设备和内核驱动
ls -l /dev/dri 2>/dev/null || true
lspci | grep -Ei 'vga|3d|display|amd|intel|nvidia'
经验法则： 如果 nvidia-smi 都不能正常工作，nvtop 在 NVIDIA 节点上通常也无法提供完整信息；如果 AMD/Intel 的 DRM/sysfs/fdinfo 不可读，进程级指标也会缺失。

4. 首次启动与界面阅读

直接运行 nvtop 后，先不要急着按快捷键。值班排障时建议按这个顺序读屏：设备列表、利用率趋势、显存占用、进程表、进程命令行。

GPU 利用率
反映一段刷新周期内计算/图形引擎忙碌程度。训练高吞吐时通常长期较高。
显存
反映已分配或保留的 GPU 内存。显存高不等于正在计算。
温度/功耗
帮助判断散热、功耗墙、降频和硬件异常。
进程表
连接 PID、用户和命令，是定位作业归属的入口。
# 启动默认视图
nvtop

# 常用交互键，实际以 man nvtop 和界面提示为准
# Up/Down       选择进程
# Left/Right    横向滚动进程行
# F6            选择排序字段
# + / -         升序或降序排序
# F2            打开设置窗口
# F12           保存当前界面偏好
# F10 / q / Esc 退出
# F9            对选中进程选择信号，生产环境慎用
版本差异： 部分发行版或新版本还提供搜索/过滤相关交互入口；如果你要依赖某个快捷键写运维手册，请以目标节点上的 man nvtop 和界面帮助为准。

5. 多 GPU 实时监控

AI 训练节点经常有 4、8、16 张 GPU。nvtop 的第一件事是帮助你看到“是否所有 GPU 都被合理使用”，尤其是数据加载瓶颈、单卡掉队、错误绑定设备、负载不均衡等问题。

观察现象可能含义下一步
所有卡显存接近，利用率周期性同步典型 DDP/多卡训练，可能正常结合吞吐日志、网络和 CPU 观察是否有瓶颈。
一张卡显存很高但利用率长期为 0进程占卡但不计算，可能卡死、等待数据或只做缓存看 PID、命令、日志、进程状态和 CPU I/O。
某张卡利用率明显低于其他卡数据并行不均衡、通信等待、绑定错误、硬件/热问题检查 rank 到 GPU 映射、NCCL 日志、温度功耗。
所有卡利用率低但显存高模型已加载但请求少、训练在等待 CPU/存储/网络同时看 top、iostat、iftop、服务 QPS。
# 多卡训练前，先确认哪些 GPU 对当前 shell 可见
echo "$CUDA_VISIBLE_DEVICES"
nvidia-smi --query-gpu=index,name,memory.total --format=csv

# 启动训练后，另一个 SSH/tmux pane 里持续观察
nvtop
AI Infra 视角： 多 GPU 问题通常不是“GPU 数字异常”这么简单，而是 GPU、CPU、数据加载、通信、容器隔离、调度器分配共同作用。nvtop 是入口，不是完整根因分析系统。

流程图：从异常 GPU 到责任进程

进程归因不是只读 PID。生产上还要确认用户、容器、调度器作业、日志和业务影响。

6. 进程归因：PID、用户、命令、容器

nvtop 的进程表通常会展示 PID、用户、命令和 GPU 相关资源。定位到可疑 PID 后，应跳出 nvtop 进一步确认它属于哪个作业、容器或服务。

# 假设 nvtop 中看到可疑 PID=123456，先做只读确认
PID=123456
ps -fp "$PID"
readlink -f "/proc/$PID/cwd" 2>/dev/null
tr '\0' ' ' < "/proc/$PID/cmdline"; echo

# 查看父子关系，定位是训练脚本、torchrun、python worker 还是服务进程
pstree -aps "$PID"

# 容器环境中，尝试从 cgroup 反查容器线索
cat "/proc/$PID/cgroup"

# Slurm 环境常见线索
squeue -u "$(ps -o user= -p "$PID" | awk '{print $1}')" 2>/dev/null || true
PID
进程标识，可能很快复用。记录时同时记录时间、用户、命令和节点。
USER
用户不一定等于责任人。容器、服务账号、调度器账号都需要继续映射。
COMMAND
短命令可能被截断。需要用 /proc/PID/cmdline、日志或作业系统补全。
不要误判： PyTorch、TensorFlow、vLLM、Triton、Jupyter、Ray worker 都可能产生多个子进程；只杀其中一个 worker 可能导致作业反复重启或进入更难排查的半坏状态。

7. 利用率 vs 显存：不要混为一谈

GPU 利用率和显存占用回答的是两个不同问题。利用率更像“当下引擎忙不忙”，显存更像“资源是否被分配或保留”。AI 框架还会使用 caching allocator，进程退出前显存看起来可能长期占用。

现象常见解释排查建议
高利用率 + 高显存训练或推理正在活跃运行关注吞吐、温度、功耗、是否接近功耗墙。
低利用率 + 高显存模型已加载但空闲、进程卡住、等待数据、显存缓存看服务请求量、训练日志、CPU/磁盘/网络。
高利用率 + 低显存小模型、数据预处理 GPU kernel、图形/编解码、短任务观察 ENC/DEC 或进程类型，避免只按显存判断。
显存缓慢上涨可能是泄漏、batch 变化、KV cache 增长或框架缓存结合应用指标、请求模式和重启前后对比。
# NVIDIA 上用 nvidia-smi 补充进程显存视角
nvidia-smi
nvidia-smi pmon -s um -c 5

# Python 服务里常见的 PyTorch 缓存解释，需要从应用内确认
# torch.cuda.memory_allocated()
# torch.cuda.memory_reserved()
判断技巧： 看趋势比看瞬时值更可靠。连续观察 1 到 3 分钟，通常能区分“启动预热”“短时 batch 尖峰”和“持续性异常”。

8. 排序、搜索与过滤思路

排障时不要默认按 PID 看进程。更高效的方式是围绕问题排序：显存不足时按显存相关字段，计算拥塞时按利用率/使用率字段，误占卡时按用户或命令线索。

目标nvtop 内操作终端辅助过滤
找最大显存占用者F6 选择显存字段，再用 +/- 调整方向nvidia-smi --query-compute-apps=pid,used_memory --format=csv
找最活跃计算进程选择 GPU 使用率或进程使用率字段排序nvidia-smi pmon -s u -c 10
找某个用户如果当前版本支持搜索/过滤，可用界面入口；否则通过 PID 跳出查询ps -u alice -o pid,user,stat,cmd
找某个服务横向滚动看命令，必要时用 /proc 补全pgrep -af 'vllm|triton|torchrun'
# 过滤不是必须在 nvtop 内完成。常见做法是 nvtop 负责发现 PID，shell 负责精确查询
PID=123456
ps -o pid,ppid,user,stat,etime,%cpu,%mem,cmd -p "$PID"

# 按用户名快速列出该用户的 GPU 相关 Python 进程
ps -u alice -o pid,etime,stat,cmd | grep -E 'python|torchrun|ray|vllm|triton'
工作方式： nvtop 是交互式观察器，不必把所有过滤都塞进它。与 ps、pgrep、nvidia-smi、调度器命令组合，往往更稳。

9. 刷新间隔、图表和编码解码指标

刷新太快会让短尖峰很显眼，也会增加终端刷新噪声；刷新太慢会漏掉短任务。上游手册中 -d/--delay 的单位是“十分之一秒”，例如 -d 10 表示约 1 秒。

# 约 1 秒刷新一次
nvtop -d 10

# 约 2 秒刷新一次，适合 SSH 慢链路或值班观察
nvtop -d 20

# 单色模式，适合颜色支持差或日志截图
nvtop -C

# 编码/解码指标持续显示，便于排查视频推理、转码或多模态服务
nvtop -E -1

# 简化图表显示，某些版本中 -p/--no-plot 表示只显示单个合并条形图
nvtop -p
训练节点
通常关注 GPU 利用率、显存、温度、功耗和多卡一致性。刷新 1 秒左右足够。
推理节点
除显存和利用率外，还要关注请求流量、KV cache、ENC/DEC、CPU 线程池和网络。
选项提醒： 不同发行版的短选项可能随版本变化。脚本或文档中引用选项前，先在目标机器上运行 nvtop --help。

对比图：NVIDIA、AMD、Intel 支持路径

同一个 nvtop 界面背后可能是 NVML、DRM/sysfs、fdinfo 或厂商库。指标缺失不一定是 nvtop 本身坏了。

10. NVIDIA 支持与 NVML caveats

NVIDIA 节点上，nvtop 主要依赖 NVIDIA Management Library，也就是 NVML。只要驱动、设备文件和权限正常，它通常能提供比较完整的实时指标。

检查项命令解释
驱动/NVML 是否可用nvidia-smi失败时先修驱动，不要先怪 nvtop。
GPU 是否可见nvidia-smi -L容器里可能只暴露部分设备。
进程列表nvidia-smi pmon -c 3用于和 nvtop 的进程视图交叉验证。
MIG 情况nvidia-smi -LMIG 会改变设备和实例可见性，需结合调度器和容器配置。
# NVIDIA 节点排障基本序列
nvidia-smi -L
nvidia-smi
nvidia-smi pmon -s um -c 5
nvtop
硬件 caveat： 上游说明中，NVML 对 Kepler 之前的一些 GPU 查询支持有限；现代 AI 训练卡通常不是这个问题，但旧工作站或混合硬件集群需要注意。

11. AMD/Intel 支持 caveats

AMD 和 Intel 上的进程级 GPU 归因更多依赖 Linux 内核暴露的 DRM/sysfs/fdinfo 信息。很多“看不到进程”或字段 N/A 的问题，本质是内核、驱动或权限不足。

平台依赖常见 caveat建议
AMDamdgpu 驱动、DRM/sysfs、fdinfo上游说明 AMD 进程级信息需要 Linux 5.14+ 的 fdinfo；旧 radeon 驱动不适用。升级内核和 amdgpu，检查 /dev/dri 权限。
Inteli915 或 xe 驱动、fdinfo上游说明 Intel 进程级信息需要 Linux 5.19+；总显存读取可能需要 CAP_PERFMON 或 CAP_SYS_ADMIN。优先授予最小 capability，而不是长期 root 运行。
容器设备挂载和 cgroup 权限宿主可见不代表容器可见，尤其是 /dev/dri、/proc、fdinfo。确认 runtime、device plugin、securityContext。
# AMD/Intel 节点只读检查
uname -r
ls -l /dev/dri
lspci -k | grep -EA3 'VGA|3D|Display'

# Intel 总显存权限问题的一个上游建议，需要按安全策略评审后执行
# sudo setcap cap_perfmon=ep "$(command -v nvtop)"
权限警告： 不要为了让指标完整就随意让所有人 root 运行监控工具。优先理解缺的是什么字段，再按最小权限授予 capability 或调整设备权限。

12. SSH、tmux 与远程值班

nvtop 是 ncurses TUI，最常见运行环境就是 SSH。远程链路慢、终端类型错误、tmux 配色不兼容，都可能导致界面闪烁、乱码或按键异常。

# 推荐：一个 tmux 窗格跑训练，一个窗格跑 nvtop，一个窗格看日志
tmux new -s gpu-debug

# pane 1
watch -n 2 nvidia-smi

# pane 2
nvtop -d 20

# pane 3
tail -f train.log
问题检查处理
界面乱码或边框异常echo $TERM尝试 export TERM=xterm-256color，或使用 nvtop -C 单色模式。
SSH 刷新很卡高延迟链路、刷新过快增大 -d，少开图表，避免在弱网里超高频刷新。
tmux 中功能键无效终端和 tmux 配置用界面提示的替代键，或在本机修正 tmux/terminal 设置。
Putty 兼容问题终端类型报告上游建议让 Putty 不要错误报告 $TERM 能力。
值班习惯： 排障截图或贴日志时，记录节点名、时间、nvtop --version、驱动版本、调度器作业号和可疑 PID，避免只发一张没有上下文的终端截图。

13. 集群节点 triage 工作流

当告警说“GPU 利用率异常”“某队列任务慢”“节点不可调度”时，nvtop 是进入节点后的快速观察工具。它应该和调度器、容器和系统命令一起使用。

# Slurm 示例：先从调度器确认节点和作业，再进入节点
squeue -w gpu-node-07
scontrol show job JOBID
ssh gpu-node-07
hostname
nvtop

# Kubernetes 示例：先定位 pod 和节点，再确认宿主或容器内视图
kubectl get pod -A -o wide | grep gpu-node-07
kubectl describe node gpu-node-07 | grep -i nvidia -A5
ssh gpu-node-07
nvtop

triage 输出模板

时间: 2026-04-25 14:30
节点: gpu-node-07
现象: GPU2 显存 78GiB/80GiB, 利用率 0-5% 持续 10 分钟
进程: PID 123456, user alice, cmd torchrun ...
作业: Slurm JOBID 998877, queue train-long
交叉验证: nvidia-smi pmon 进程活跃度低，训练日志停在 data loader
建议: 通知用户检查数据路径；30 分钟无响应后按队列策略处理
工程化重点： nvtop 给的是现场视图，triage 结论要补充调度器、日志和业务影响，否则很难复盘。

14. nvtop vs nvidia-smi vs gpustat

三者都常用于 GPU 运维，但定位不同。不要把 nvtop 当作所有场景的替代品，也不要在需要交互观察时只反复执行 nvidia-smi。

工具优势短板推荐场景
nvtop交互式、实时图表、多 GPU 同屏、进程选择和排序不适合脚本解析和长期留存；TUI 依赖终端能力SSH 排障、值班观察、快速定位可疑 PID
nvidia-smiNVIDIA 官方、字段丰富、可查询/循环/CSV、适合脚本主要面向 NVIDIA；默认视图不是交互式自动化采样、驱动确认、MIG/拓扑/进程交叉验证
gpustat轻量、单行摘要、适合 watch 和集群概览信息比 nvtop 少，通常依赖 NVIDIA 栈快速看空闲卡、登录提示、简单巡检
DCGM/Grafana长期指标、告警、跨节点视图部署成本更高，不能直接替代现场交互生产监控、容量规划、SLO 和告警
# nvidia-smi 适合机器可读输出
nvidia-smi --query-gpu=index,name,utilization.gpu,memory.used,memory.total,temperature.gpu,power.draw --format=csv

# watch 适合粗略重复刷新，但交互能力不如 nvtop
watch -n 1 nvidia-smi

# 如果安装了 gpustat，可以看紧凑摘要
gpustat -cp
组合建议： 用 nvtop 发现和观察，用 nvidia-smi 精确查询和脚本化，用监控系统做历史与告警。

15. 安全处理 GPU 进程

nvtop 的 F9 可以对选中进程发送信号。这很方便，也很危险。AI 作业可能正在写 checkpoint、更新共享缓存、服务线上请求，直接 kill 可能造成数据损坏、任务重试风暴或业务故障。

先 dry-run 式确认，再执行

# 只读确认，不改变进程
PID=123456
ps -fp "$PID"
pstree -aps "$PID"
readlink -f "/proc/$PID/cwd" 2>/dev/null
tr '\0' ' ' < "/proc/$PID/cmdline"; echo
kill -0 "$PID" && echo "process exists"

# 确认调度器或服务策略后，优先请求应用自停或调度器取消
# Slurm 示例：先查看，再按组织策略取消
scontrol show job JOBID
# scancel JOBID

# 只有确认无误时才发 TERM，避免直接 KILL
# kill -TERM "$PID"
# sleep 10
# kill -KILL "$PID"
生产红线： 不要在共享训练节点上只凭“显存占用高”就 F9 或 kill -9。至少确认用户、作业、命令、运行时长、是否在线服务、是否有 checkpoint 策略。
动作风险更安全替代
直接 kill -9无法清理、无法保存 checkpoint、可能触发调度器重试先 TERM、应用自停、scancel 或平台下线流程。
杀容器内单个 workerSupervisor 反复拉起，故障更隐蔽通过容器/调度器处理整个作业或服务副本。
重启驱动或节点影响同节点所有作业先迁移/排空节点，并保留诊断信息。

16. 常见问题与排障

问题 1：nvtop: command not found
未安装、PATH 不正确，或只装在某个 conda/pixi 环境里。用 command -v nvtop 和包管理器确认。
问题 2：No GPU to monitor
NVIDIA 先跑 nvidia-smi；AMD/Intel 先看 /dev/dri、内核驱动和容器设备暴露。
问题 3：进程列表为空但 GPU 忙
可能是权限、fdinfo 不可读、容器隔离、采样窗口短，或厂商后端不支持该字段。
问题 4：字段显示 N/A
常见于旧 GPU、旧驱动、旧内核、非完整厂商库或权限不足。先看上游支持矩阵。
问题 5：界面花屏
检查 $TERM、tmux、Putty、ncurses wide char 支持，必要时使用 -C。
问题 6：容器里看不到宿主 GPU
检查 runtime、device plugin、--gpus、/dev/nvidia* 或 /dev/dri 挂载。
问题 7：刷新数字和 nvidia-smi 不一致
采样窗口、单位、后端和刷新时刻不同。看趋势，不要纠结单次读数完全一致。
问题 8：F9 无法杀进程
权限不足、snap confinement、容器隔离或进程已退出。优先用调度器取消作业。

最小排障命令组

date
hostname
nvtop --version
nvtop --help | head -40
uname -a
command -v nvidia-smi && nvidia-smi || true
ls -l /dev/nvidia* /dev/dri 2>/dev/null || true
lspci | grep -Ei 'nvidia|amd|intel|vga|3d|display'

练习任务

  1. 在一台有 GPU 的机器上运行 nvtop，指出设备区、图表区和进程区分别回答什么问题。
