py-spy 深度教程：AI Infra 现场 Python 训练任务采样剖析

这份教程面向 AI Infra、训练平台、SRE 和模型工程团队，讲清楚如何用 py-spy 在不修改业务代码、不重启训练任务的情况下观察 Python 进程：实时 top、单次 dump --pid、采样录制 flamegraph、GIL 与线程视角、原生扩展栈、容器和 Kubernetes 权限、开销控制，以及它和 perf、strace、cProfile 的边界。

一句话理解： py-spy 是一个进程外 Python 采样剖析器：它从目标 CPython 进程读取线程和栈信息，按采样频率统计“时间主要花在哪些 Python 调用栈上”。

1. py-spy 是什么，解决什么问题

py-spy 的价值在于“现场观察”：训练任务已经在跑，GPU 利用率突然掉到 20%，DataLoader 卡住，某个 rank 不前进，或者线上推理进程 CPU 飙高，但你不想改代码、不想打开 profiler、不想重启服务。此时 py-spy 可以附着到现有 CPython 进程，采样每个 Python 线程的调用栈，并把样本汇总成实时 top、快照 dump 或 flamegraph。

擅长
Python 层 CPU 热点、训练循环卡顿、DataLoader 队列等待、锁竞争、GIL 线索、推理服务 handler 热点。
不擅长
GPU kernel 内部耗时、NCCL 内部细节、系统调用时序、内核态 CPU 栈、内存泄漏根因。
核心优势
进程外运行，不需要 import，不需要 decorator，通常可以对正在运行的生产 Python 进程使用。
# 三个最常用入口
py-spy top --pid 12345
py-spy dump --pid 12345
py-spy record -o train.svg --pid 12345 --duration 60
AI Infra 视角： py-spy 看到的是 Python 解释器栈和部分原生扩展栈。GPU 忙不忙、kernel 为什么慢，仍需配合 nvidia-smi、Nsight Systems、PyTorch profiler、DCGM 或平台监控。

信息图：py-spy 的进程外采样模型

py-spy 不把 profiler 代码注入训练进程，因此适合现场排查；但它仍受操作系统权限、符号信息和采样误差影响。

2. 安装、版本与基础自检

在训练节点上优先使用平台镜像内预装版本，避免临时安装污染环境。若必须安装，可以用 PyPI、Homebrew、GitHub release 或 Rust/Cargo。构建源码版本在 Linux 上通常需要 libunwind。

# 常见安装方式，按你的平台规范选择一种
python -m pip install --user py-spy
brew install py-spy
cargo install py-spy

# 基础自检
py-spy --version
py-spy --help
py-spy record --help
py-spy top --help
py-spy dump --help
检查项为什么重要命令
版本不同版本的输出格式和选项可能略有差异py-spy --version
平台原生扩展栈、权限模型和符号解析受平台影响uname -a
Python 发行版符号、debug info、容器路径都会影响解析质量python -VV
权限attach 到既有 PID 通常需要 ptrace 权限cat /proc/sys/kernel/yama/ptrace_scope
版本策略： 教程命令使用 record、top、dump 这些稳定入口；细节选项以目标机器上的 py-spy <subcommand> --help 为准。

3. 找到训练进程 PID

AI 训练任务常常由 torchrun、accelerate、Ray、Slurm、Kubernetes 或平台 launcher 启动。先确认你附着的是哪个 rank、哪个 worker、哪个容器内 PID，而不是误抓 scheduler、shell 或日志 sidecar。

# 本机查找 Python 训练进程
pgrep -af 'python|torchrun|accelerate|train.py'
ps -eo pid,ppid,stat,pcpu,pmem,cmd --sort=-pcpu | head -30

# 查看某个 PID 的命令行和父子关系
PID=12345
tr '\0' ' ' < /proc/$PID/cmdline; echo
pstree -aps $PID 2>/dev/null || ps -o pid,ppid,cmd -p $PID

# GPU 视角辅助定位
nvidia-smi pmon -c 1
nvidia-smi --query-compute-apps=pid,process_name,used_gpu_memory --format=csv
单机单进程
通常一个 python train.py PID，直接 py-spy top --pid $PID。
torchrun/DDP
每个 rank 是独立 Python 进程。需要分别观察异常 rank，或用 --subprocesses 从 launcher 跟踪子进程。
DataLoader workers
num_workers>0 时有子进程。卡顿可能发生在 worker，也可能发生在主进程等待队列。
Kubernetes
容器内 PID 与宿主机 PID namespace 可能不同。进入目标容器或使用合适的 debug/ephemeral container。

流程图：AI 训练任务现场排查顺序

不要一上来录长时间 profile。现场先用快照和实时视图判断方向，再决定是否生成火焰图或切换到 GPU/系统级工具。

4. py-spy top 实时观察

top 类似 Unix top：持续刷新函数占比、活动线程、GIL 信息等。它适合回答“当前是不是一直卡在同一段 Python 代码”“CPU 热点是否稳定”“某个 rank 是否在等待队列或锁”。

# 附着到已有进程
PID=12345
sudo py-spy top --pid $PID

# 降低采样频率，减少现场扰动
sudo py-spy top --pid $PID --rate 50

# 显示线程 ID，便于和日志、gdb、/proc 对齐
sudo py-spy top --pid $PID --threads

# 只看持有 GIL 的线程样本
sudo py-spy top --pid $PID --gil

# 从 py-spy 启动目标程序，通常比 attach 现有 PID 权限要求低
py-spy top -- python train.py --config configs/debug.yaml
观察点可能含义下一步
热点在 __getitem__ / transform数据预处理 CPU 成为瓶颈调 DataLoader worker、缓存、向量化、I/O 预取
热点在 logging / json / tokenizer训练 loop 周边逻辑吞噬 CPU降低日志频率，预 tokenize，批处理编码
大部分在 queue/get/wait主进程等待数据、锁或子进程dump 主进程和 worker，检查 worker 是否异常
%GIL 很高且多线程争用Python 多线程没有并行执行 CPU 代码改多进程、释放 GIL 的库、减少 Python 热循环
读数原则： top 是实时采样视图，不是精确计时器。短暂抖动不要过度解读，稳定重复出现的栈才值得优化。

5. dump --pid 快照诊断

dump 打印当前每个 Python 线程的调用栈，特别适合“卡住了但不知道卡在哪里”的场景。它不是统计热点，而是某一瞬间的线程快照。

# 最小快照
sudo py-spy dump --pid 12345

# 带线程 ID，便于对齐平台日志
sudo py-spy dump --pid 12345 --threads

# 打印局部变量。谨慎：可能泄露路径、token、样本内容或密钥
sudo py-spy dump --pid 12345 --locals

# 快速保存现场证据
TS=$(date +%Y%m%d-%H%M%S)
sudo py-spy dump --pid 12345 --threads > pyspy-dump-$TS.txt
--locals 安全警告： 局部变量可能包含训练样本、用户数据、访问 token、路径、环境配置或模型输入。只在受控环境使用，输出文件按敏感日志处理。
看到 threading.Condition.wait
可能是主线程等待 DataLoader、queue、日志 flush 或后台线程。
看到 multiprocessing/queues.py
检查 worker 是否还活着、共享内存是否不足、数据读取是否阻塞。
看到 tokenizer / PIL / json
CPU 预处理热点，常见于 NLP、图像增强或数据解析。
看到训练 step 之外的框架栈
可能是 callback、checkpoint、metric、eval 或 logging 周期触发。

6. record 与 flamegraph

record 会在一段时间内采样并写入文件，默认常用于生成 SVG flamegraph。它适合沉淀证据、做优化前后对比，或发给团队一起阅读。

# 对已有训练进程录制 60 秒火焰图
PID=12345
sudo py-spy record -o train-rank0.svg --pid $PID --duration 60 --rate 100

# 输出 speedscope 格式，便于在 speedscope.app 或内部工具查看
sudo py-spy record -o train-rank0.json --format speedscope --pid $PID --duration 60

# 只记录持有 GIL 的样本
sudo py-spy record -o gil.svg --pid $PID --duration 30 --gil

# 记录线程 ID，分析多线程时更清楚
sudo py-spy record -o threads.svg --pid $PID --duration 60 --threads

# 从 py-spy 启动任务并录制
py-spy record -o startup.svg -- python train.py --epochs 1 --dry-run
参数作用AI Infra 建议
--duration限制录制时长生产先录 30 到 120 秒，避免无界运行
--rate采样频率默认通常够用；现场排查可降到 50 或更低
--format选择输出格式SVG 便于分享，speedscope 便于交互分析
--subprocesses跟踪子 Python 进程适合 launcher、DataLoader、gunicorn、multiprocessing
--native包含 C/C++/Cython 原生栈需要平台支持和符号；结果不完整时不要强行推断
录制边界： flamegraph 展示采样占比，不是 trace timeline。想看 GPU kernel 时间线、CUDA stream、NCCL collective，请用 Nsight Systems 或 PyTorch profiler。

信息图：如何读 py-spy 火焰图

优化优先级通常看“宽且可控”的栈：比如数据预处理、tokenizer、日志、Python 循环；窄而偶发的栈不一定值得改。

7. 读懂火焰图

火焰图不是调用时序图。横向宽度代表采样占比，纵向代表调用关系。一个函数很宽，说明采样时经常看到它在栈上；它可能是自己慢，也可能是它下面的子调用慢。

看到的形态常见解释行动
大块集中在 dataset/transformCPU 预处理压住训练吞吐缓存、并行 worker、减少 Python 逻辑、使用高效库
主线程宽在 queue/wait主训练 loop 等数据或后台任务同时抓 worker；检查 worker 死锁、I/O、共享内存
logging/checkpoint 很宽观测或保存频率过高降低频率、异步化、只在 rank0 执行
Python 栈很薄但 GPU 低瓶颈可能在 native、I/O、系统调用或外部服务切到 --native、strace、perf 或 Nsight
# 优化前后对比建议
sudo py-spy record -o before.svg --pid $PID --duration 60
# 修改配置或发布修复后
sudo py-spy record -o after.svg --pid $PID --duration 60

# 对比时记录上下文
python -VV
py-spy --version
nvidia-smi --query-gpu=index,name,utilization.gpu,memory.used --format=csv

8. GIL、线程与 DataLoader

py-spy top 会展示 GIL 相关信息；--gil 可以只包含持有 GIL 的样本。对 AI 工作负载来说，GIL 视角能帮助区分“Python 线程争用”和“原生库释放 GIL 后在外部运行”。

# 看当前 GIL 相关占比
sudo py-spy top --pid $PID

# 只采持有 GIL 的栈，排查 Python CPU 热循环
sudo py-spy record -o gil-only.svg --pid $PID --duration 45 --gil

# 线程视图，结合 dump 判断哪个线程在等锁或队列
sudo py-spy dump --pid $PID --threads
多线程 CPU 预处理
如果大量 Python 代码争 GIL，多线程不一定提升吞吐。
NumPy/PyTorch 原生算子
很多原生代码会释放 GIL；--gil 可能看不到这部分活跃工作。
DataLoader workers
PyTorch 多 worker 通常是多进程。主进程等待时，要继续看 worker 进程。
GIL caveat： 只看 --gil 可能漏掉释放 GIL 后仍在运行的原生扩展。怀疑 C/C++/Cython、tokenizer、OpenCV、Pillow、NumPy、PyTorch native 时，结合 --native 或系统级 profiler。

9. 多进程、DDP 与 subprocesses

DDP、DataLoader、Ray worker、gunicorn worker 都可能让“一个训练作业”变成多个 Python 进程。不要只 profile launcher；要确认被采样的是实际消耗 CPU 或卡住的 rank/worker。

# 从 torchrun 父进程跟踪子 Python 进程
sudo py-spy record -o ddp.svg --pid $LAUNCHER_PID --subprocesses --duration 60

# 分 rank 分别记录，便于比较异常 rank
for pid in $(pgrep -f 'train.py'); do
  echo "recording $pid"
  sudo py-spy record -o "rank-$pid.svg" --pid "$pid" --duration 30
done

# DataLoader worker 排查：先看进程树，再对可疑 worker dump
pstree -aps $MAIN_PID
sudo py-spy dump --pid $WORKER_PID --threads
场景建议抓谁判断标准
某个 rank step 慢慢 rank 的 Python 进程对比正常 rank 的 flamegraph
全部 rank GPU 利用率低rank0、任一慢 rank、DataLoader worker看是否共同等待数据、日志或 barrier
launcher 卡住launcher + --subprocesses确认子进程是否还在运行或等待
推理服务多 worker高 CPU 或高延迟 worker按 PID 与端口、日志 request id 对齐

10. 原生扩展、CUDA 与符号 caveat

--native 可以尝试把 C/C++/Cython 栈纳入 profile。它对 Python 扩展热点很有价值，比如 tokenizers、OpenCV、Pillow、NumPy、Cython 数据处理、部分 PyTorch native 路径。但原生栈质量高度依赖平台、架构、符号和编译选项。

# 捕获原生扩展栈
sudo py-spy record -o native.svg --pid $PID --duration 60 --native

# top 中查看原生热点
sudo py-spy top --pid $PID --native

# 如果只看到地址或 unknown，检查符号和二进制
readelf -Ws /path/to/extension.so | head
file /path/to/extension.so
CUDA 异步性
Python 发起 CUDA kernel 后可能很快返回；实际 GPU 时间不一定体现在 Python 栈宽度上。
NCCL/通信等待
py-spy 可能只看到 Python 调用或等待点，通信内部 timeline 需要 NCCL 日志或 Nsight。
符号缺失
没有符号时，原生栈可能显示地址、unknown 或过于粗糙的函数名。
Cython 行号
要映射到 .pyx 行号，通常需要生成的 C/C++ 文件和符号配合。
工具组合： Python 热点先用 py-spy；CPU native 热点用 perf；GPU timeline 用 Nsight Systems；PyTorch operator 级别可用 PyTorch profiler。

11. 权限、ptrace、Docker、Kubernetes

py-spy 需要读取另一个进程的内存。Linux 上 attach 到非子进程通常受 ptrace/Yama 限制；Docker 和 Kubernetes 默认也常缺少 SYS_PTRACE 能力。权限问题不是 py-spy 命令写错，而是安全边界在生效。

# Linux 主机：查看 ptrace 策略
cat /proc/sys/kernel/yama/ptrace_scope

# 常见 attach 方式
sudo py-spy top --pid $PID
sudo py-spy dump --pid $PID

# 如果 py-spy 启动目标进程，通常不需要 attach 现有非子进程
py-spy record -o startup.svg -- python train.py
环境症状处理方式
Linux 裸机Permission denied用 sudo，或按安全策略调整 kernel.yama.ptrace_scope
Dockerroot 仍失败启动容器时加入 --cap-add SYS_PTRACE，必要时检查 seccomp profile
KubernetesPod 内无法读取目标进程容器安全上下文增加 SYS_PTRACE，或使用授权的 ephemeral debug container
macOS系统 Python 或受保护进程失败System Integrity Protection 可能阻止读取；使用非系统 Python 或受控环境
# Docker 示例：启动时授予能力
docker run --cap-add SYS_PTRACE --security-opt seccomp=unconfined ...

# docker-compose 片段
services:
  trainer:
    cap_add:
      - SYS_PTRACE

# Kubernetes 容器 securityContext 片段
securityContext:
  capabilities:
    add:
      - SYS_PTRACE
安全提醒： SYS_PTRACE 允许读取进程内存，可能暴露模型输入、密钥、环境变量或用户数据。多租户集群不要随意给业务 Pod 长期开启该能力；优先使用短生命周期调试容器和审批流程。

12. 开销、采样率与生产安全

py-spy 的开销通常很低，因为它在目标进程外运行；但“低开销”不等于“零影响”。采样需要读取目标进程状态，某些模式可能短暂停顿目标进程；高采样率、长时间录制、原生栈解析、子进程跟踪都会增加扰动。

# 保守生产模板：低采样率、短时长、明确输出路径
TS=$(date +%Y%m%d-%H%M%S)
sudo py-spy record \
  --pid $PID \
  --duration 60 \
  --rate 50 \
  -o "/tmp/pyspy-$PID-$TS.svg"

# 尝试避免暂停目标进程，但可能增加采样错误或部分栈
sudo py-spy record --pid $PID --duration 60 --nonblocking -o nonblocking.svg
控制项更安全的选择代价
采样率--rate 50 或更低细粒度热点可能不明显
录制时长--duration 30/60/120不能覆盖很长周期事件
本地变量默认不要 --locals少了变量上下文
原生栈先不加 --native看不到 C/C++/Cython 细节
暂停行为高敏感任务可试 --nonblocking可能出现采样错误或不完整栈
上线窗口建议： 在低峰或单个异常实例先抓；记录 PID、rank、镜像、commit、采样率、时长、GPU 利用率和时间段，避免 profile 文件脱离上下文后无法解释。

选择图：py-spy、perf、strace、cProfile 怎么选

工具不是互斥的。py-spy 常用于第一现场定位方向，再把问题交给更低层或更精确的 profiler。

13. py-spy vs perf/strace/cProfile

工具回答的问题优势局限
py-spyPython 进程现在卡在哪些 Python 栈上进程外、可 attach、适合生产现场不是 GPU timeline，不是 syscall trace
perfCPU 周期、内核/用户态 native 热点系统级强，适合 C/C++/内核Python 符号和解释器栈需额外处理
strace进程在做哪些系统调用I/O、网络、文件、futex 等等待非常直观不是 CPU profiler，可能明显影响高频 syscall 程序
cProfile可控运行中的 Python 函数调用次数和累计耗时精确到函数调用统计，适合本地复现需要代码/启动介入，不适合已经运行的生产任务
PyTorch profilerPyTorch operator、CPU/GPU 活动、timeline训练框架语义最强需要在代码中配置 profile window，开销更高
# 组合排查示例
sudo py-spy dump --pid $PID --threads
sudo py-spy record -o py.svg --pid $PID --duration 60
sudo strace -tt -T -p $PID -f -o strace.txt
sudo perf top -p $PID
不要混淆： py-spy flamegraph 宽，不代表某个 syscall 慢；strace 中某个 futex 等待长，也不代表 Python 热点函数自身 CPU 高。不同工具的语义要分开解释。

排障树：py-spy 报错或结果看不懂时

大多数 py-spy 问题不是“命令不可用”，而是目标 PID、权限、采样窗口或工具层级没有对齐。

14. 常见故障与排障

Permission denied
用 sudo 重试；容器检查 SYS_PTRACE；Kubernetes 检查 securityContext 或 debug container profile。
top 看起来没有变化
确认 PID 是训练 worker 而非 launcher；降低过滤条件，不要一开始就加 --gil。
火焰图只有等待
这可能是真相：主进程在等数据、通信或锁。继续 dump worker/rank，并用 strace 看等待类型。
看不到 GPU 慢在哪里
py-spy 不是 GPU profiler。使用 Nsight Systems、PyTorch profiler、DCGM、NCCL_DEBUG。
native 栈是地址或 unknown
缺少符号、平台不支持或二进制被 strip。不要从 unknown 栈过度推断。
采样结果每次不同
窗口太短或 workload 周期性强。按 step 周期录制，多次对比，并记录训练阶段。
--locals 输出太大或敏感
停止使用，删除或加密处理输出文件，改用不含 locals 的 dump。
attach 导致任务敏感抖动
降低 --rate，缩短 --duration，尝试 --nonblocking，或在副本环境复现。

15. 实战模板与报告格式

一次有价值的 py-spy 排查不只是生成 SVG，而是把证据放进训练上下文：哪个任务、哪个 rank、什么时间、什么症状、采样多久、看到什么、排除了什么、下一步用什么工具验证。

# 生产友好的采样脚本片段
#!/usr/bin/env bash
set -euo pipefail

PID="${1:?usage: $0 PID}"
OUT_DIR="${OUT_DIR:-/tmp/pyspy}"
mkdir -p "$OUT_DIR"

TS="$(date +%Y%m%d-%H%M%S)"
BASE="$OUT_DIR/pyspy-$PID-$TS"

tr '\0' ' ' < "/proc/$PID/cmdline" > "$BASE.cmdline.txt"
ps -o pid,ppid,stat,pcpu,pmem,etime,cmd -p "$PID" > "$BASE.ps.txt"
sudo py-spy dump --pid "$PID" --threads > "$BASE.dump.txt"
sudo py-spy record --pid "$PID" --duration 60 --rate 50 -o "$BASE.svg"

echo "wrote $BASE.*"

16. 学习路线与练习任务

第一阶段：会安全观察

  • 会找到正确 PID，并确认它是目标 Python 进程。
  • 会使用 dump --pid 保存线程快照。
  • 会用 top --pid 观察稳定热点，而不是解读瞬时噪声。

第二阶段：会沉淀证据

  • 会用 record --duration 生成短时 flamegraph。
  • 会比较 rank 之间、优化前后、不同训练阶段的 profile。
  • 会记录采样率、时长、版本、PID、GPU 指标和代码 commit。

第三阶段：会判断边界

  • 知道什么时候加 --gil、--threads、--native、--subprocesses。
  • 知道 py-spy 不能替代 GPU profiler、system call tracer 或框架 profiler。
  • 知道权限能力的安全含义，尤其是 SYS_PTRACE 和 --locals。

练习

  1. 写一个 CPU 忙循环 Python 脚本，用 py-spy top 观察热点函数。
  2. 写一个 time.sleep 或 queue wait 脚本，用 dump 观察等待栈。
  3. 录制 30 秒 flamegraph，解释最宽的 3 个栈。
  4. 用 --threads 对比多线程脚本的输出。
  5. 在测试容器中验证缺少和添加 SYS_PTRACE 时的行为。
  6. 对 PyTorch DataLoader 示例分别 profile 主进程和 worker。
