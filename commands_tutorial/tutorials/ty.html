1. ty 是什么，适合解决什么问题

ty 是 Astral 推出的 Python 类型检查器和语言服务器，官方描述是“一个用 Rust 编写、极快的 Python type checker and language server”。它的目标不是只替代某一个命令，而是把“终端检查 + IDE/LSP 反馈”统一成一套工具链。

它擅长什么
项目级类型检查、编辑器内实时诊断、导航与补全、对部分未注解代码的渐进式接纳，以及较快的增量反馈。
它不承诺什么
不替代测试，不保证运行时正确，也不意味着你可以删除现有 lint、formatter、单元测试或接口契约验证。
最适合的场景
正在做 Python 工程化、希望统一 CLI 和 LSP、对大型仓库反馈速度敏感、又不想一上来全仓库 strict 的团队。
# 最快上手方式：不安装，直接运行
uvx ty check

# 在项目里固定版本
uv add --dev ty
uv run ty check

# 编辑器通常会直接启动 ty server
ty server
工程判断： 如果你的核心诉求是“更快的类型反馈 + 一体化语言服务”，ty 值得试；如果你的核心诉求是“立刻替换所有现有 mypy plugin 工作流”，那就要先做兼容性盘点。

信息图：ty 的整体工作模型

理解 ty 的关键，是把它看成“一套分析核心，两种输出界面”：终端里的检查结果和编辑器里的语言服务并不是两套逻辑。

2. 类型检查的整体心智模型

对 Python 工程师来说，最有用的心智模型不是“工具会不会报错”，而是“工具凭什么得出这个结论”。ty 主要依赖四类证据：源码本身、类型注解、导入可见的第三方/第一方模块、以及项目配置。

输入ty 会做什么你该关注什么
源码与控制流分析赋值、分支、导入、函数调用接口边界是否清晰，是否把动态行为显式化
类型注解用注解约束参数、返回值、属性与泛型关键边界是否写准，而不是“有没有写满”
项目环境从虚拟环境和 site-packages 解析第三方依赖虚拟环境路径、依赖是否已安装
规则配置决定哪些诊断被当作 warn / error / ignore别把所有问题都一刀切成 error
核心判断： 类型检查器最怕“隐式真相”。例如运行时猴子补丁、动态拼属性、依赖未安装、路径布局不标准。你不把这些边界说清楚，任何类型检查器都会变得脆弱。

3. 安装方式与首次运行

官方文档给了多种安装方式。对团队项目，最稳的是把 ty 作为开发依赖加进项目；对个人试用，最轻的是 uvx ty check。

# 方式 1：零安装试用
uvx ty check

# 方式 2：项目内固定版本，推荐给团队
uv add --dev ty
uv run ty check

# 方式 3：全局工具
uv tool install ty@latest
ty version

# 也支持 pip / pipx
pip install ty
pipx install ty

第一次接入建议

# 先在一个小目录跑，别一上来扫全仓库
uv run ty check src/app

# 如果依赖来自虚拟环境，优先用 uv run 让 VIRTUAL_ENV 就位
uv run ty check

# 想看规则文档
uv run ty explain rule unresolved-import
接入提示： 官方文档明确提到，如果你在项目里运行 ty，可能需要使用 uv run 或先激活虚拟环境，否则它可能找不到你的依赖。

4. CLI 主命令：check、watch、server、explain

ty 的 CLI 很克制，主命令不多，但都很直接。

命令用途何时使用
ty check [PATH]...检查项目或指定路径本地、CI、批量治理
ty check --watch监听文件变化并增量重查终端常驻开发流
ty server启动语言服务器通常由编辑器代管，少数情况下手动调试
ty explain rule RULE解释规则含义诊断治理、培训团队
ty version查看版本排查升级与 CI 漂移
# 指定目录
uv run ty check src tests

# watch 模式
uv run ty check --watch

# 对规则提问
uv run ty explain rule invalid-argument-type

# 指定 Python 解释器或虚拟环境
uv run ty check --python .venv
命令设计信号： ty 把重点放在 check 和 server，这也说明它的产品定位并不是“脚本型 lint 命令集合”，而是“类型分析核心 + 工程入口”。

5. 项目配置：规则、环境、路径、终端输出

ty 支持把配置写在 pyproject.toml 的 [tool.ty] 下面，也支持独立的 ty.toml。最常用的几个区块是 rules、analysis、environment、overrides、src 和 terminal。

[tool.ty.rules]
possibly-unresolved-reference = "warn"
unresolved-import = "error"

[tool.ty.analysis]
allowed-unresolved-imports = ["vendor.**"]
replace-imports-with-any = ["legacy_sdk.**"]
respect-type-ignore-comments = true

[tool.ty.environment]
python-version = "3.12"
root = ["./src", "./python"]

[tool.ty.src]
exclude = ["build/**", "dist/**", "generated/**"]
respect-ignore-files = true

[tool.ty.terminal]
output-format = "concise"
error-on-warning = false

[[tool.ty.overrides]]
include = ["tests/**"]

[tool.ty.overrides.rules]
possibly-unresolved-reference = "warn"
[tool.ty.rules]
把具体规则设成 ignore、warn 或 error。
[tool.ty.analysis]
处理 unresolved imports、type: ignore 兼容和 Any 化过渡。
[tool.ty.environment]
处理 Python 版本、平台、解释器路径和第一方源码根。
配置边界： 编辑器设置里可以内联覆盖配置，但官方说明内联设置优先级高于配置文件。团队协作时，尽量把共享策略放在仓库配置里，把个人偏好留在编辑器层。

流程图：本地开发、编辑器和 CI 的推荐链路

理想状态不是“只在 CI 跑 ty”，而是编辑器、终端 watch 和 CI 三层同时工作，但严格度可以分阶段提升。

6. 文件选择、模块发现与 Python 版本推断

ty 默认会检查工作目录或项目目录下的所有 Python 文件。模块发现则依赖项目根、源码根和 Python 环境。

主题官方行为你应如何利用
文件选择默认递归检查工作目录或项目目录下的 Python 文件第一次接入时先传具体路径，逐步扩大范围
环境发现优先看 VIRTUAL_ENV，其次找项目根下的 .venv，再退回 python3/python团队里尽量统一虚拟环境约定
Python 版本优先用 project.requires-python 的最小版本，其次推断环境，再回退默认版本把 requires-python 写准，减少误报
源码根environment.root 支持多个第一方源码目录对非标准布局或 monorepo 很关键
# 限定检查范围
uv run ty check src/service_a tests/service_a

# 指定项目根
uv run ty check --project packages/payment

# 指定解释器或虚拟环境
uv run ty check --python .venv

# 指定 Python 版本和平台
uv run ty check --python-version 3.12 --python-platform linux
实务建议： 很多“类型错了”其实不是类型系统问题，而是路径和环境没有配准。先看导入解析，再看诊断本身，效率更高。

7. 编辑器与语言服务器工作流

官方文档把 ty 定位成“fully-featured language server for Python”。它支持诊断、跳转、补全、代码动作、auto-import、hover、inlay hints 等能力。

VS Code

Astral 维护了官方 VS Code 扩展。官方文档说明，这个扩展默认会把 Python 扩展里的语言服务器设为 "None"，避免同时运行两个 Python 语言服务器。

{
  "python.languageServer": "Pylance",
  "ty.disableLanguageServices": true
}

上面的配置是官方文档给出的“只用 ty 做 type checking，而把 hover / completion 等继续交给别的语言服务器”的做法。

Neovim

vim.lsp.config('ty', {
  settings = {
    ty = {
      diagnosticMode = 'workspace',
    }
  }
})

vim.lsp.enable('ty')

常见编辑器设置

设置默认值作用
ty.disableLanguageServicesfalse只保留类型检查，关闭补全/hover/跳转等语言服务
ty.diagnosticModeopenFilesOnly仅看打开文件，或扩展到整个 workspace
ty.configurationFilenull显式指定一份 ty.toml
ty.configurationnull在编辑器内联覆写配置
不要双开两个语言服务器： 如果你同时跑 ty 和 Pylance / Pyright，又都开启诊断，很容易收到重复或相互冲突的反馈。要么让 ty 全权负责，要么明确让它只做 type checking。

8. 诊断、规则级别与 suppression

ty 的诊断通常会关联到规则。规则可以在项目级别配置成 ignore、warn 或 error，也可以用 suppression comment 局部压制。

[tool.ty.rules]
all = "warn"
unresolved-import = "error"
possibly-unresolved-reference = "warn"

局部忽略

a = 10 + "test"  # ty: ignore[unsupported-operator]

sum_three_numbers("one", 5)  # ty: ignore[missing-argument, invalid-argument-type]

# ty: ignore[invalid-argument-type]
sum_three_numbers(3, 2, "1")

谨慎使用会改文件的命令

# 会直接修改源码，先在小范围路径试点
git switch -c chore/ty-baseline
uv run ty check src/legacy --add-ignore
git diff -- src/legacy

# fix 也会改文件，同样先限制范围并审 diff
uv run ty check src/service --fix
git diff -- src/service
安全提示： --add-ignore 和 --fix 都会写回文件。它们没有“自动替你做正确治理”的魔法。先限定路径、先看 diff、先在分支上做，再决定是否推广。

9. 渐进式类型与 Unknown 心智模型

ty 的一个重要设计点，是它希望在未完全注解的代码上尽量避免过早产生 false positive。官方 FAQ 把这套行为解释为：当类型信息不足时，ty 会引入 Unknown。

class RetryPolicy:
    max_retries = None

policy = RetryPolicy()
policy.max_retries = 1

根据官方类型系统文档，上面这段代码在 ty 中不会因为 max_retries 初始值是 None 就立刻报错；它会把该属性视为 Unknown | None，从而维护一种“渐进式保证”。

好处
旧仓库、第三方未注解代码、半类型化模块更容易接入。
代价
如果你希望更激进的推断，它会显得“没有那么严格”。
工程含义
别把 Unknown 当特性炫技；它本质上是在帮你给旧代码留迁移空间。
# 更严格的做法仍然是显式注解
class RetryPolicy:
    max_retries: int | None = None
结论： ty 适合“先接进来，再逐步加准”的路线。它不是让你永远停留在 Unknown，而是让你不必为了第一天接入就大修全仓库。

用例图：ty、mypy、pyright、Ruff 的分工边界

工程上更常见的不是“谁彻底替代谁”，而是分阶段并行：先确定边界，再决定是否收敛到单一检查器。

10. 团队 adoption：如何从零接入旧仓库

如果仓库已经跑了多年、类型注解稀疏、第三方依赖复杂，不要从“全仓库 error、全员马上修完”开始。建议按下面顺序推进。

  1. 固定版本：把 ty 加入开发依赖，避免每台机器拉到不同 0.0.x 行为。
  2. 选一块边界清晰的目录：例如一个服务包、一个 SDK、或公共工具模块。
  3. 把问题先降级到 warn：先看到反馈，再决定哪些该变成 error。
  4. 对棘手依赖使用 allowed-unresolved-imports 或 replace-imports-with-any 过渡。
  5. 把 suppression 限制在局部，不要把整个模块直接“静音”。
[tool.ty.rules]
all = "warn"
unresolved-import = "warn"

[tool.ty.analysis]
replace-imports-with-any = ["legacy_vendor.**"]

[[tool.ty.overrides]]
include = ["src/new_service/**"]

[tool.ty.overrides.rules]
invalid-argument-type = "error"
治理原则： 先让反馈进入开发流，再提高违例成本。先追求“每天都在跑”，再追求“所有目录都最严”。

11. CI、报告格式与退出码

ty 对 CI 很友好，因为官方把输出格式和退出码定义得比较明确。

退出码含义
0没有 error 级别及以上的诊断
1发现了 error 级别及以上的诊断
2无效 CLI 参数、无效配置或 IO 错误
101内部错误
# 普通 CI
uv run ty check

# 把 warning 也当失败
uv run ty check --error-on-warning

# 生成 GitHub Actions 注释格式
uv run ty check --output-format github

# 生成 JUnit XML
uv run ty check --output-format junit
[tool.ty.terminal]
output-format = "github"
error-on-warning = true
实务建议： 试点期可先用默认行为，只卡 error；等团队已经消化了告警，再考虑 error-on-warning。

12. 和 mypy、pyright、Ruff 怎么分工

四者都跟 Python 代码质量有关，但职责并不相同。

工具核心定位你应关注的差异
ty类型检查器 + 语言服务器官方强调速度、LSP、一体化项目支持、对部分未注解代码的 adoption 友好；但当前仍是 beta。
mypy成熟类型检查器官方文档提供 --strict、dmypy daemon 与 plugin 机制，适合既有 mypy 生态深度用户。
pyright高性能静态类型检查器官方配置支持 typeCheckingMode 的 off/basic/standard/strict；语言服务能力在 README 中与 Pylance 关系更紧。
Rufflinter / formatter不是完整类型检查器；但可以用 ANN* 规则补上“缺少类型注解”的治理。
什么时候选 ty
你想要一个正在快速演进的一体化类型与编辑器平台，且能接受 beta 期版本固定与渐进试点。
什么时候先别急着替换
你的仓库依赖 mypy plugin、已有严格 pyright 基线，或者团队对 beta 兼容性窗口非常敏感。
别把 Ruff 当 type checker： Ruff 的 ANN 规则能帮助你推动“写注解”，但它不等于跨模块类型推理、控制流缩窄和导入环境分析。

13. 性能、watch 模式与 benchmark 解读

官方首页和 README 都突出展示了性能，并给出“10x - 100x faster than mypy and Pyright”的口径，样例基于对 home-assistant 项目的无缓存检查。这个信息有价值，但解读要克制。

可以信什么
官方确实把速度作为核心卖点，且 watch 模式与 fine-grained incrementality 是明确设计目标。
不要直接外推什么
不要把官方 benchmark 当成你仓库的真实收益。仓库规模、依赖结构、缓存冷热、编辑器用法都会影响结果。
正确验证方式
在你自己的 CI 和本地开发流上测冷启动、热启动、单文件修改后的反馈时延。
# 冷启动
time uv run ty check

# 增量开发流
uv run ty check --watch

# 指定目录对比
time uv run ty check src/payment
判断标准： 对开发者最有感的通常不是“单次全量跑快多少”，而是“改完一行代码后编辑器和终端多久给你可信反馈”。

14. beta / 兼容性 caveat 与迁移风险

这是接入 ty 时最不能跳过的一节。根据 Astral 官方 README，截至 2026-04-26 可见的当前说明：

  • ty 当前处于 beta。
  • 版本策略仍是 0.0.x。
  • 官方明确写明：它“尚无稳定 API”，包括诊断在内的 breaking change 可能发生在任意两个版本之间。
  • FAQ 明确写明：ty 目前 还没有 strict mode。
  • FAQ 明确写明：ty 没有 plugin system，而且目前没有计划添加。
风险点含义缓解方式
诊断漂移升级后报错数量和规则解释可能变化锁版本，升级前单独跑验证分支
生态缺口mypy plugin 工作流不能直接照搬先盘点依赖插件的目录，再决定并行期长度
严格度预期错位习惯 strict 的团队可能觉得它“太松”用 Ruff ANN 补充缺注解治理，并逐步补显式注解
编辑器冲突双开语言服务器导致重复反馈明确只保留一套主诊断来源
迁移前置检查： 只要你的生产流程依赖“诊断文本稳定”“plugin 行为稳定”“旧 baseline 长期不动”，就不能把 ty 当作无痛替换。它更适合带着版本固定和验证策略逐步引入。

15. 从 mypy 或 pyright 迁移的策略

迁移时不要把问题表述成“换不换工具”，而要拆成四个具体问题：规则覆盖、编辑器体验、CI 契约、生态依赖。

从 mypy 迁移

  1. 先盘点是否使用了 mypy plugins、dmypy、严格模式和 per-module 配置。
  2. 把“缺注解治理”从 mypy strict 中剥离出来，改由 Ruff ANN 规则承担一部分。
  3. 先并行跑 mypy 与 ty，比较差异，再决定下线时机。

从 pyright 迁移

  1. 先确认团队是否依赖 typeCheckingMode = strict 的行为。
  2. 明确编辑器里是否继续使用 Pylance，还是让 ty 接管语言服务。
  3. 如果只想先试 type checking，可按官方建议把 ty.disableLanguageServices 设为 true。
# 并行验证示例
uv run ty check src > /tmp/ty.out || true
pyright src > /tmp/pyright.out || true
mypy src > /tmp/mypy.out || true
推荐路径： 并行期接受“同一段代码在两个检查器下有不同判断”，重点看这些差异是否影响你的关键契约，而不是追求每条诊断逐字对齐。

16. monorepo、PEP 723、第三方库与特殊场景

官方 FAQ 对一些边界场景给得很直接，下面这些点最值得工程团队提前知道。

场景官方现状实务建议
monorepo支持，但对嵌套项目的自动发现有限优先每个包单独跑 ty check --project ...
多个源码根environment.root 支持多个目录把多包视作单项目时要注意运行时 import 真实性
PEP 723 单脚本单个脚本可借助 uvx --with-requirements script.py ty check script.py多脚本 workspace 目前还不能按各自元数据区分依赖
纯编译扩展库没有 .py 或 .pyi 时类型信息有限尽量补 stubs，或用 replace-imports-with-any 做过渡
# monorepo：按包检查
uv run ty check --project packages/package_a
uv run ty check --project packages/package_b

# 单个 PEP 723 脚本
uvx --with-requirements script.py ty check script.py

# 对顽固依赖做 Any 化过渡
[tool.ty.analysis]
replace-imports-with-any = ["vendor_ext.**"]
monorepo 提醒： 官方 FAQ 也明确指出，把多个包作为一个项目根处理，可能导致 ty 认为某些模块“可导入”，但运行时其实并不成立。

17. 常见问题与排障流程

1. 为什么报 unresolved-import？

官方 FAQ 提示先查四件事：虚拟环境是否可发现、项目结构是否需要配置 environment.root、第三方依赖是否真的安装进环境、依赖是否只有编译扩展而没有 .pyi。

# 看更详细的路径信息
uv run ty check -v

# 显式指定虚拟环境
uv run ty check --python .venv

2. 为什么没有 strict mode？

官方 FAQ 的答案很直接：还没有。如果你想对“缺少类型注解”更严格，可以结合 Ruff 的 ANN* 规则。

3. 为什么某些未注解代码没报错？

因为 ty 对未注解符号会推成 Unknown，目的是在渐进式 adoption 里减少误报。要更严格，就补显式注解。

4. 能用 mypy plugins 吗？

不能。官方 FAQ 明确表示：没有 plugin system，而且目前没有计划添加。

5. CI 突然挂了但代码没改？

先看是否升级了 ty 版本。由于官方明确说明 beta 阶段可能在任意两个版本之间出现 breaking change，版本漂移是第一嫌疑人。

18. 推荐落地路线与命令速查

推荐落地路线

  1. 把 ty 固定到项目依赖里，不要直接跟着 latest 飘。
  2. 先在一个服务或库试点，优先解决导入与环境问题。
  3. 编辑器接入时先决定谁是主语言服务器，避免双开。
  4. CI 第一阶段只卡 error；第二阶段再评估 error-on-warning。
  5. 如果要替代 mypy / pyright，先并行跑一段时间，用数据而不是感觉做决策。

命令速查

# 快速试用
uvx ty check

# 项目内运行
uv run ty check

# 指定目录
uv run ty check src tests

# watch 模式
uv run ty check --watch

# 显式指定环境
uv run ty check --python .venv

# 改输出格式
uv run ty check --output-format github

# warning 也让 CI 失败
uv run ty check --error-on-warning

# 解释规则
uv run ty explain rule unresolved-import

# 查看版本
uv run ty version
最后的工程建议： 把 ty 当成一个正在快速成熟的工程平台，而不是“一次性替换一切”的宗教选择。对大多数团队来说，最稳的路径是先让它创造增量价值，再决定它最终占据多大比重。
