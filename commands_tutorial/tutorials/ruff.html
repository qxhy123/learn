1. Ruff 是什么，适合解决什么问题

Ruff 是一个用 Rust 编写的 Python linter 和 formatter。它把大量原本分散在 flake8、插件生态、isort、black、pyupgrade、autoflake 里的能力收拢到同一套 CLI 与配置模型里。

它擅长什么
快速发现未使用导入、潜在 bug、导入排序问题、可升级语法、风格不一致，以及自动修复一部分安全问题。
它不替代什么
不替代类型检查、测试、业务静态分析，也不保证所有修复都适合你的运行时语义。
最有价值的场景
中大型 Python 仓库、多人协作项目、CI 频繁运行的仓库，以及希望统一 lint/format 入口的团队。
# 最基础的两个入口
ruff check .
ruff format .

# 更适合工程接入的最小安全流程
ruff check . --fix --diff
ruff format . --check
边界提醒： Ruff 的价值不是“把所有规则都打开”，而是让代码质量规则以足够快、足够统一、足够可自动化的方式进入日常开发闭环。

2. 心智模型：linter、formatter、配置与缓存

理解 Ruff 的关键，是把它看成四层协作：文件发现、规则检查、格式统一、结果缓存。check 和 format 共享配置发现与文件发现逻辑，但操作目标不同。

输入
Python 文件、notebook、配置文件、目标 Python 版本。
检查
ruff check 根据规则集给出诊断，并可做部分自动修复。
格式化
ruff format 统一排版，但不负责全部 lint 语义。
缓存
只重算变化文件，适合本地反复执行与 CI 高频运行。
运行顺序建议： 当同时使用 lint 修复、导入排序和格式化时，先跑 ruff check --fix，再跑 ruff format。因为前者可能会改导入和语句结构，后者负责把最终文本整理干净。

信息图：Ruff 的整体工作模型

先把 Ruff 拆成“规则检查”和“文本格式化”两件事，再去理解命令和配置，会清晰很多。

3. 安装、首次运行与退出码

# 官方常见安装方式
uv tool install ruff@latest
# 或
pip install ruff
# 或
pipx install ruff

# 不安装，直接执行
uvx ruff check .
uvx ruff format .

第一次接入建议

# 先看问题长什么样，不改文件
ruff check src tests

# 只检查格式，不改文件
ruff format src tests --check

# 预览自动修复会产生什么 diff
ruff check src tests --fix --diff
命令退出码含义
ruff check0没有违规，或者所有违规都已被自动修复。
ruff check1发现违规。
ruff check2配置错误、CLI 参数错误或内部异常。
ruff format --check0当前文件已经符合格式要求。
ruff format --check1如果不带 --check，将会有文件被重新格式化。
ruff format --check2配置错误、CLI 参数错误或内部异常。
CI 提示： 退出码是最稳的集成接口。流水线里不要靠日志关键字判断是否失败，直接依赖进程退出码。

4. ruff check：规则检查与自动修复

ruff check 是 Ruff 的主入口。它会读取规则集，对文件做静态检查，并在开启 --fix 时修复那些被认为可自动修复的问题。

# 检查当前目录
ruff check .

# 只看导入排序规则
ruff check . --select I

# 按规则类别渐进加严
ruff check . --extend-select B,UP,SIM

# 自动修复安全问题
ruff check . --fix

# 只展示将被修复的内容，不落盘
ruff check . --fix --diff
输出是什么
文件、行列号、规则码、提示文本，以及可选的 fix 提示。
适合什么时候跑
本地保存前、提交前、CI、批量重构后、升级 Python 版本后。
它不会做什么
不会替你决定哪些“不安全修复”应该自动落盘，也不会理解你的业务约束。
实务建议： 新仓库可从默认规则起步；旧仓库不要一把梭全开规则。先保证 check 运行时间短、输出可读、可修复比例高，再扩展规则家族。

5. ruff format：格式统一与运行顺序

ruff format 是 Ruff 的格式化入口，目标是成为 Black 风格的高性能替代。它直接改写文件；带 --check 时只做验证，不写回。

# 直接格式化
ruff format src tests

# 仅检查是否需要格式化
ruff format src tests --check

# 查看格式化后的差异
ruff format src tests --diff
问题回答
它会排序导入吗？不会。导入排序仍由 linter 侧的 I 规则与 isort 配置负责。
它会替代所有风格规则吗？不会。formatter 负责排版，不负责全部语义或风格检查。
它和 line-length 的关系？会尽力遵守，但不是绝对硬上限，某些行仍可能超过长度限制。
推荐顺序： ruff check --fix 先修语义和导入，再 ruff format 清理文本布局。这样可以避免导入排序和自动修复后再留下格式噪音。

流程图：本地与 CI 中的推荐执行链路

把“本地允许自动改代码”和“CI 只做守门”分开，是 Ruff 落地时最稳定的工作流。

6. 规则家族：默认集与常见扩展

Ruff 支持大量规则，并沿用 Flake8 风格的规则码前缀。默认会启用 Pyflakes 的 F 规则和一部分 E 规则，优先覆盖常见错误，而不是一开始就把所有风格意见强塞进来。

前缀来源/倾向典型用途
FPyflakes未使用导入、未绑定变量、明显逻辑错误。
Epycodestyle 子集基础代码风格和明显排版问题。
Iisort导入排序、导入分组。
UPpyupgrade使用更现代的 Python 语法与标准库写法。
Bflake8-bugbear容易引发 bug 的模式。
SIMflake8-simplify冗余条件、可简化表达式。
ARGflake8-unused-arguments未使用参数治理。
Dpydocstyle文档字符串规范。
Sflake8-bandit 风格基础安全规则，适合谨慎接入。
TCflake8-type-checking类型检查导入边界。
RUFRuff 自有规则Ruff 特有优化与清理规则。
[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]
规则选择原则： 不要先开 ALL。它会在升级 Ruff 后隐式带入新规则，造成版本升级时大面积噪音。更稳妥的做法是按家族逐步启用。

7. pyproject.toml 基础配置

Ruff 可以配置在 pyproject.toml、ruff.toml 或 .ruff.toml。多数 Python 工程直接放在 pyproject.toml 最方便，因为依赖、构建、测试工具通常也在那里。

[tool.ruff]
line-length = 100
target-version = "py311"
src = ["src", "tests"]
extend-exclude = ["migrations", "dist"]

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]
ignore = ["E501"]

[tool.ruff.lint.per-file-ignores]
"tests/**/*.py" = ["S101"]

[tool.ruff.format]
quote-style = "double"
indent-style = "space"
docstring-code-format = true
配置块职责
[tool.ruff]通用配置，如 line-length、target-version、src、文件发现。
[tool.ruff.lint]规则集、忽略规则、修复策略、isort 子配置。
[tool.ruff.format]格式化风格，如引号风格、缩进风格、docstring 代码块格式化。
配置优先级： 同目录下如果同时存在 .ruff.toml、ruff.toml 和 pyproject.toml，Ruff 会优先使用前两者，而不是把三份文件合并。

8. 规则选择策略：select、ignore、per-file-ignores

规则治理的核心不在“会不会写规则码”，而在“如何让规则集可解释、可演进、可局部例外”。

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]
ignore = ["B008"]

[tool.ruff.lint.per-file-ignores]
"tests/**/*.py" = ["S101", "ARG001"]
"__init__.py" = ["F401"]
select
明确给出要启用的规则集。最适合团队长期维护，因为升级时行为更可预测。
ignore
在整体规则集里关掉某些不适合当前仓库的规则。
per-file-ignores
把例外控制在局部文件，而不是让整个仓库为少数特殊目录降标。

一条实用建议

如果你的目标是“团队看配置一眼就懂”，优先用完整的 select，不要过度依赖 extend-select 叠加。Ruff 官方也建议更偏向显式规则集。

反模式： 把一切都放到全局 ignore。这样短期很安静，长期会让规则体系变成黑箱，谁也不知道哪些错误本应被拦下来。

9. 修复安全模型：safe、unsafe 与 fix 范围

Ruff 把自动修复分成 safe 和 unsafe。安全修复应尽量保持代码语义；不安全修复可能改变运行时行为，或者删除注释等信息。

# 只应用安全修复
ruff check . --fix

# 显示不安全修复建议
ruff check . --unsafe-fixes

# 应用不安全修复
ruff check . --fix --unsafe-fixes
[tool.ruff.lint]
extend-safe-fixes = ["F601"]
extend-unsafe-fixes = ["UP034"]
unfixable = ["F401"]
配置/参数作用
--fix应用被允许的自动修复。
--unsafe-fixes允许执行被标记为不安全的修复。
lint.extend-safe-fixes把某些原本不安全的修复提升为安全。
lint.extend-unsafe-fixes把某些原本安全的修复降级为不安全。
lint.unfixable即使命中规则，也不允许 Ruff 自动落盘修复。
落地建议： 旧仓库第一次治理时，把 --unsafe-fixes 当成人工审阅模式，而不是默认执行模式。最稳的做法是先 --fix --diff，配合代码评审决定是否落盘。

10. 导入排序与 isort 的关系

Ruff 的 formatter 不负责排序导入；导入排序由 linter 侧的 I 规则和 [tool.ruff.lint.isort] 配置负责。这意味着“想统一 import”，要跑 ruff check --select I --fix 或更常见的 ruff check --fix。

# 只整理导入
ruff check . --select I --fix

# 更常见：统一跑 lint 修复，再格式化
ruff check . --fix
ruff format .
[tool.ruff]
src = ["src"]

[tool.ruff.lint.isort]
known-first-party = ["my_app"]
known-third-party = ["wandb"]
combine-as-imports = true
兼容点
Ruff 的导入排序设计目标与 Black/formatter 兼容，适合替代常规 isort 流程。
冲突点
如果你启用了非默认的 force-single-line、force-wrap-aliases、lines-after-imports、lines-between-types、split-on-trailing-comma 等设置，ruff format 可能会发出警告。
第一方导入识别： Ruff 会用 src 目录和项目根推断 first-party 包。如果目录名和第三方包重名，使用 known-third-party 明确纠正。

11. 局部豁免：noqa、fmt: off、批量加注释

工程里总会有无法立即收敛的边角。Ruff 提供行级、块级、文件级忽略，以及 formatter 的局部关闭机制。

value = 1  # noqa: F841

# ruff: disable[E501]
LONG_SQL = "select id, created_at, updated_at from extremely_long_table_name ..."
# ruff: enable[E501]

# ruff: noqa: F401

# fmt: off
payload={ "name":"demo",    "retry":3 }
# fmt: on
# 给迁移中的旧代码自动加 noqa
ruff check legacy/ --add-noqa

# 找出无效 noqa
ruff check . --extend-select RUF100

# 清理无效 noqa
ruff check . --extend-select RUF100 --fix
line-level
# noqa: F401 只压制单行违规。
block-level
# ruff: disable[...] 到 # ruff: enable[...] 之间整块生效。
format suppression
# fmt: off / # fmt: on / # fmt: skip 只影响 formatter。
治理建议： --add-noqa 适合迁移期生成“临时基线”，但不要把它当永久方案。后续应配合 RUF100 清理无效压制，并逐步把真实问题修掉。

12. 编辑器、pre-commit 与 CI 集成

Ruff 的价值只有进入开发闭环才会放大。本地编辑器负责即时反馈，pre-commit 负责防止明显问题进入提交，CI 负责最终守门。

pre-commit

repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.15.10
    hooks:
      - id: ruff-check
        args: [--fix]
      - id: ruff-format

GitHub Actions

name: Ruff
on: [push, pull_request]
jobs:
  ruff:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/ruff-action@v3
        with:
          args: check --output-format=github
      - uses: astral-sh/ruff-action@v3
        with:
          args: format --check
顺序要求： pre-commit 里如果 ruff-check 带 --fix，它应放在 ruff-format 前面，也应放在其他 formatter 前面。否则修复后还可能残留排版变化。
编辑器心法： 保存时可只做 format，诊断用 check；或者让语言服务器同时提供诊断和代码动作，但仍建议把真正的仓库策略写进配置文件与 CI，而不是藏在个人编辑器设置里。

13. 从 flake8 / black / isort 迁移

Ruff 最常见的接入方式，不是“新增一个工具”，而是“把原来三个到多个工具的职责收拢”。迁移时要分清哪些能力能直接替代，哪些仍需保留。

原工具Ruff 对应能力迁移注意点
flake8ruff check大多数常用插件已有内建替代，但自定义第三方插件体系目前不等价。
blackruff format整体风格高度接近，但边缘格式可能与 Black 有少量差异。
isortruff check --select I --fix要检查 isort 特殊设置是否与 formatter 冲突。
# 一个务实的迁移流程
# 1. 先保持原 black/isort 不动，只引入 ruff check
ruff check . --select E,F,I,UP,B --fix --diff

# 2. 收敛规则噪音后，再试运行 formatter
ruff format . --diff

# 3. 最后替换 CI 和 pre-commit 入口
重要限制： Ruff 当前不支持第三方自定义 lint 插件。如果你的 Flake8 体系严重依赖自研插件，迁移前要先确认这些规则能否改写为 Ruff 已有规则或由别的检查链路承接。

对比图：从分散工具链迁移到 Ruff

把迁移拆成“先接管 lint，再接管 format，最后收敛配置和 CI”，风险最低。

14. monorepo 与多包仓配置策略

Ruff 的配置发现规则对 monorepo 很重要：它对每个文件使用“最近的配置文件”，而不是像 ESLint 那样把父子配置自动合并。父配置如果想被子项目继承，需要显式使用 extend。

# repo/
# ├── pyproject.toml
# ├── services/api/pyproject.toml
# └── libs/common/.ruff.toml

# repo/pyproject.toml
[tool.ruff]
line-length = 100
target-version = "py311"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]
# repo/services/api/pyproject.toml
[tool.ruff]
extend = "../../pyproject.toml"
src = ["src"]

[tool.ruff.lint.per-file-ignores]
"tests/**/*.py" = ["S101"]
不要误解为“会层层 merge”
不会。最近的配置生效，父配置默认被忽略。
用 extend 明确继承
这样子项目的差异是显式的，不靠隐式级联。
路径相对谁计算
配置里的 exclude、src 等路径，按配置文件所在目录解析。
monorepo 实战建议： 在根上定义统一底线，如 line-length、target-version、核心规则集；业务子包只覆写少量差异，不要每个包都发明一套新规则。

15. notebook、脚本、类型桩与生成代码

当前 Ruff 默认会发现并处理 *.py、*.pyi、*.ipynb 以及 pyproject.toml。这对数据科学仓库和平台脚本仓库很方便，但也意味着你需要明确哪些文件应该被排除。

[tool.ruff]
extend-exclude = ["generated", "vendor", "*.min.py"]

[tool.ruff.format]
exclude = ["*.ipynb"]

[tool.ruff.lint.per-file-ignores]
"*.ipynb" = ["T20"]
"scripts/**/*.py" = ["INP001"]
文件类型建议
Jupyter Notebook若团队把 notebook 当正式产物，可纳入 Ruff；如果只是探索笔记，可只 lint 不 format，或直接排除。
.pyi 类型桩保留在 Ruff 范围内，能帮助发现导入与格式问题，但要注意它们有不同的排版习惯。
生成代码多数情况应排除，除非生成器稳定且希望对生成结果做守门。
一次性运维脚本可保留基础规则，如 E、F、I，不必强推过多风格意见。
核心原则： 把 Ruff 覆盖面和“需要长期维护的代码面”对齐。不是所有会执行的 Python 文件，都值得同等强度治理。

16. Python 版本、requires-python 与 preview

target-version 会影响 lint 规则和 formatter 的某些版本相关行为。如果没有显式设置，Ruff 会尝试从附近 pyproject.toml 的 requires-python 推断最低兼容版本。

[project]
requires-python = ">=3.11"

[tool.ruff]
line-length = 100
# 若不显式写 target-version，Ruff 可能从 requires-python 推断
target-version = "py311"
# 临时试验 preview 行为
ruff check . --preview
ruff format . --preview
显式写 target-version
适合多开发机、多 CI 环境的团队，减少“为什么我这里和你那里结果不一样”的推断差异。
--preview
适合先试运行新规则集或格式化变化，但不要在没有评审和基线的情况下直接常态化启用。
升级注意： Ruff 版本升级、新 preview 行为启用、或 Python 基线升级，都会改变结果。把这些动作和普通业务改动分开提交，最利于审查。

17. 常见问题与排障

问题 1：明明有根配置，子目录结果却不同
检查是否被更近的 pyproject.toml / ruff.toml 覆盖；Ruff 默认不合并父子配置。
问题 2：格式化后仍有 E501
这是正常现象。formatter 只做 best-effort，不保证所有长行都被压到阈值内。
问题 3：导入分组不对
检查 src、known-first-party、known-third-party 是否准确。
问题 4：ruff format 提示冲突
检查是否启用了与 formatter 不兼容的引号、缩进、逗号或 isort 特殊设置。
问题 5：一次修太多
按目录、按规则家族或按文件类型拆批次；先 --diff 再落盘。
问题 6：旧仓库噪音太大
先用 --add-noqa 建临时基线，再分阶段清理，并配合 RUF100 清无效抑制。

排障命令模板

# 看 Ruff 认为哪些文件会被处理
ruff check . --show-files

# 看某条规则的说明
ruff rule F401

# 看某个配置键怎么解释
ruff config line-length

# 先只看某一类问题
ruff check src --select I

# 预览修复，不落盘
ruff check src --fix --diff
故障定位顺序： 先看“处理了哪些文件”，再看“用了哪份配置”，然后看“启用了哪些规则”，最后才看“这个修复要不要自动落盘”。很多 Ruff 问题本质都是配置发现问题，而不是规则本身有 bug。

多数“Ruff 不对劲”问题，最终都会落回文件发现、配置发现、规则选择或修复安全等级这四类。

18. 推荐落地路线与命令速查

推荐落地路线

  1. 只接入 ruff check 默认规则或轻量规则集，先让团队看到问题分布。
  2. 对高收益规则开启 --fix，并用 --diff 评审第一批改动。
  3. 稳定后接入 ruff format，把统一格式从 Black 或零散编辑器格式化迁移过来。
  4. 再进入 pre-commit 和 CI，把本地自动修复、CI 只守门的流程固化。
  5. 最后再考虑更多规则家族、notebook 支持、monorepo 细分配置和 preview 试运行。
