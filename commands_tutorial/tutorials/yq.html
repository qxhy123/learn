一句话理解： yq 是结构化配置的命令行编辑器：它把 YAML/JSON 解析成数据树，再用表达式读取节点、筛选数组、更新字段、合并文件或输出成另一种格式。

1. yq 是什么，为什么 AI Infra 常用

yq 用来在命令行读取和编辑 YAML、JSON 等结构化文本。AI Infra 中大量配置都以 YAML 存在：Kubernetes Deployment、Job、Pod、Kueue/Volcano 训练队列、Helm values、Argo Workflow、GPU Operator、PrometheusRule、Ray/Kubeflow 配置等。用纯 sed 修改这些文件容易误伤缩进、数组项和同名字段；yq 的价值是按结构修改，而不是按字符串猜测。

读取
抽取镜像、资源限制、节点选择器、容器环境变量、Service 端口、Ingress 域名。
修改
更新 tag、replicas、GPU limit、storage class、tolerations、affinity、Helm values 覆盖项。
转换
YAML 转 JSON 给 jq、API 或审计系统；JSON 转 YAML 便于人审查和 GitOps 提交。
# 读取 Kubernetes Deployment 的镜像
yq '.spec.template.spec.containers[].image' deployment.yaml

# 更新 Helm values 中的镜像 tag，先输出到 stdout 预览
yq '.image.tag = "v1.8.3"' values.yaml

# YAML 转 JSON，交给 jq 或平台 API
yq -o=json '.' pod.yaml
适用边界： yq 适合结构化配置的局部查询和转换；如果需要复杂业务校验、跨仓库状态管理或 schema-aware 修改，应使用 Python/Go SDK、Kubernetes API 或专门的 IaC 工具。

信息图：yq 的整体心智模型

不要把 yq 当成“会处理缩进的 sed”。它的核心是解析结构，再对结构节点执行表达式。

2. 安装、版本与实现差异

生产脚本里最先要确认的是：你手上的 yq 到底是哪一个。日常 DevOps 中最常见的是 Mike Farah 的 Go 版 yq，表达式风格接近 jq 但有自己的 YAML 能力；另一个常见实现是 Python 包 yq，它通常作为 jq 的 YAML 前端，语法和选项不同。

实现常见识别方式表达式特点脚本建议
Mike Farah Go yqyq --version 显示 mikefarah/yq 或 v4 风格版本常用 yq '.a.b'、yq -i '.x = 1' file.yaml、eval-all本教程默认使用该语法；CI 中固定版本
Python yq/kislyuk yqpip show yq 或帮助里强调 jq wrapper依赖 jq，常见选项与 Go yq 不同不要直接复用 Go yq 脚本；显式写清工具来源
系统包旧版本发行版仓库可能滞后v3/v4 语法差异很大不要假设线上和本机一致
# 先识别版本
yq --version
command -v yq

# 如果团队脚本依赖 Go yq v4，建议在 CI 中打印版本
yq --version || exit 1

# 检查表达式是否符合预期
printf 'image:\n  tag: old\n' | yq '.image.tag = "new"'
版本警告： 网上很多答案没有说明 yq 实现和主版本。看到 yq r、yq w 这类写法时，多半是旧版语法；看到大量 jq 选项时，可能是 Python wrapper。

3. 基本语法与读取路径

Go 版 yq v4 的常用形式是 yq '表达式' 文件。表达式中的 . 表示当前文档根节点，.a.b 访问 map 字段，[] 遍历数组，带特殊字符的 key 用引号。

表达式含义AI Infra 例子
.输出整个文档格式化 values.yaml
.metadata.name读取嵌套字段读取 Kubernetes 资源名
.spec.containers[].image遍历数组字段列出 Pod 所有镜像
.resources.limits."nvidia.com/gpu"读取包含斜杠的 key读取 GPU limit
.env[] | select(.name == "NCCL_DEBUG")筛选数组元素查找指定环境变量
# 示例文件
cat > pod.yaml <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: train-worker-0
spec:
  containers:
    - name: trainer
      image: registry.local/train:v1
      resources:
        limits:
          nvidia.com/gpu: 8
YAML

# 读取字段
yq '.kind' pod.yaml
yq '.metadata.name' pod.yaml
yq '.spec.containers[0].resources.limits."nvidia.com/gpu"' pod.yaml
路径习惯： YAML key 如果包含 .、/、- 或其他容易歧义的字符，使用 ."key-name" 更稳妥。

4. 路径、数组与 select 筛选

Kubernetes 和 Helm values 中最常见的数据结构是 map 嵌套 array。掌握数组遍历、按字段筛选和投影，是使用 yq 的分水岭。

# 列出所有容器名和镜像
yq '.spec.template.spec.containers[] | .name + " => " + .image' deployment.yaml

# 只读取名为 trainer 的容器镜像
yq '.spec.template.spec.containers[] | select(.name == "trainer").image' deployment.yaml

# 查询所有带 GPU limit 的容器
yq '.spec.template.spec.containers[]
  | select(.resources.limits."nvidia.com/gpu" != null)
  | {name: .name, gpu: .resources.limits."nvidia.com/gpu"}' deployment.yaml

# 输出所有 env 的 name
yq '.spec.template.spec.containers[].env[]?.name' deployment.yaml
写法作用避免的问题
[]遍历数组所有元素避免只看第一个容器
[0]取第一个元素适合结构固定的 values
select(...)按条件过滤避免按数组下标误改容器
[]?字段不存在时不报硬错误适合跨多种资源扫描
生产建议： 修改容器字段时优先按 .name 筛选，不要依赖数组下标；Sidecar、initContainer 或 Helm 模板变化都可能改变顺序。

流程图：从路径选择到安全更新

yq 的安全更新流程是：定位结构节点，必要时筛选数组，再 dry-run、diff、原地修改。

5. 更新、赋值与新增字段

= 用于赋值，|= 用于基于旧值更新。更新表达式默认输出修改后的文档，不会改写源文件；加 -i 才会原地修改。

表达式用途例子
.replicaCount = 4设置固定值扩容推理服务
.image.tag = env(TAG)从环境变量读取CI 注入镜像 tag
.args += ["--debug"]数组追加临时增加启动参数
.metadata.labels.team = "ml-platform"新增嵌套字段统一资源归属标签
.resources.requests.cpu |= . + "m"基于旧值更新需要谨慎处理类型
# 设置 replicas
yq '.spec.replicas = 3' deployment.yaml

# 按容器名更新镜像，不依赖数组下标
yq '(.spec.template.spec.containers[] | select(.name == "trainer").image) = "registry.local/train:v2"' deployment.yaml

# 新增或更新 label
yq '.metadata.labels."app.kubernetes.io/managed-by" = "gitops"' deployment.yaml

# 删除字段
yq 'del(.metadata.annotations."kubectl.kubernetes.io/last-applied-configuration")' deployment.yaml

# 从环境变量读取 tag
TAG=v2.1.0 yq '.image.tag = env(TAG)' values.yaml
类型提醒： YAML 中 8、"8"、8Gi、"500m" 是不同语义。Kubernetes 资源量经常是字符串样式的 quantity，不要盲目做数值运算。

6. Kubernetes Manifest 查询

在 AI 集群里，yq 常用于离线审查 manifest：找出资源名、镜像、GPU request/limit、hostPath、privileged、nodeSelector、tolerations、affinity 和 annotations。它适合在提交前检查 YAML，也适合在 CI 里对渲染后的 Helm/Kustomize 输出做静态扫描。

# 从 Deployment 读取常用摘要
yq '{
  kind: .kind,
  name: .metadata.name,
  namespace: .metadata.namespace,
  replicas: .spec.replicas,
  images: [.spec.template.spec.containers[].image]
}' deployment.yaml

# 找出所有容器的资源声明
yq '.spec.template.spec.containers[]
  | {name: .name, requests: .resources.requests, limits: .resources.limits}' deployment.yaml

# 检查是否使用 hostPath
yq '.spec.template.spec.volumes[]? | select(has("hostPath")) | {name, hostPath}' deployment.yaml

# 检查是否有 privileged 容器
yq '.spec.template.spec.containers[]?
  | select(.securityContext.privileged == true)
  | .name' deployment.yaml
离线文件
helm template、kustomize build、Git 中的 YAML 都适合用 yq 扫描。
在线集群
从 API 读取实时对象时，优先使用 kubectl get ... -o yaml/json，再按需接 yq 或 jq。

7. 批量修改镜像、资源与环境变量

AI Infra 中最常见的三类修改是镜像 tag、GPU/CPU/内存资源和训练相关环境变量。关键原则是按容器名筛选，先预览，再原地修改。

# 修改 trainer 容器镜像，先 dry-run
yq '(.spec.template.spec.containers[] | select(.name == "trainer").image) =
  "registry.local/ml/trainer:2026-04-25"' train-job.yaml

# 审查差异
yq '(.spec.template.spec.containers[] | select(.name == "trainer").image) =
  "registry.local/ml/trainer:2026-04-25"' train-job.yaml | diff -u train-job.yaml -

# 确认后再原地修改
yq -i '(.spec.template.spec.containers[] | select(.name == "trainer").image) =
  "registry.local/ml/trainer:2026-04-25"' train-job.yaml

# 修改 GPU limit
yq '(.spec.template.spec.containers[] | select(.name == "trainer").resources.limits."nvidia.com/gpu") = 8' train-job.yaml

# 修改或新增 NCCL_DEBUG 环境变量，适合 env 已存在该项时
yq '(.spec.template.spec.containers[] | select(.name == "trainer").env[]
  | select(.name == "NCCL_DEBUG").value) = "INFO"' train-job.yaml
新增 env 的现实问题： 如果目标 env 不存在，直接筛选赋值不会创建数组元素。生产脚本通常先检查是否存在，再决定追加，或用更完整的表达式处理缺省值。
# 检查 NCCL_DEBUG 是否存在
yq '.spec.template.spec.containers[] | select(.name == "trainer").env[]? | select(.name == "NCCL_DEBUG")' train-job.yaml

# 追加一个 env 项，先 dry-run
yq '(.spec.template.spec.containers[] | select(.name == "trainer").env) +=
  [{"name": "NCCL_DEBUG", "value": "INFO"}]' train-job.yaml

8. 多文档 YAML 处理

Kubernetes 渲染结果经常是多文档 YAML：一个文件中用 --- 分隔 Namespace、ServiceAccount、ConfigMap、Deployment、Service 等资源。yq 默认会逐个文档执行表达式；筛选时要把 kind、metadata.name 和 metadata.namespace 作为定位条件。

# 列出多文档 manifest 中每个资源的 kind/name
yq '.kind + "/" + .metadata.name' rendered.yaml

# 只输出 Deployment
yq 'select(.kind == "Deployment")' rendered.yaml

# 只读取指定 Deployment 的镜像
yq 'select(.kind == "Deployment" and .metadata.name == "trainer")
  | .spec.template.spec.containers[].image' rendered.yaml

# 删除所有 null 文档或空文档
yq 'select(. != null)' rendered.yaml
场景推荐定位条件原因
修改 Deployment 镜像kind + metadata.name + namespace避免误改同文件中的 Job 或 CronJob
扫描 Service 端口kind == "Service"同一渲染文件包含多类资源
删除 last-applied annotation对所有文档执行 del(...)该字段位置相对统一
处理 CRD/CRapiVersion + kind同名 kind 可能来自不同 API group

信息图：多文档 Kubernetes YAML 的筛选路径

多文档文件不是一个“巨大对象”，而是一串文档。先用 select 选中文档，再读取或更新内部字段。

9. YAML 与 JSON 转换

很多 AI Infra 工具链在 YAML 和 JSON 之间来回切换：Kubernetes API 输出 JSON 更稳定，GitOps 配置常用 YAML，审计/报表可能更适合 JSON Lines。yq 可以作为转换边界。

# YAML 转 JSON
yq -o=json '.' deployment.yaml

# JSON 转 YAML
cat pod.json | yq -P '.'

# 输出单个原始字符串，便于 shell 变量接收
IMAGE=$(yq -r '.spec.template.spec.containers[0].image' deployment.yaml)
printf 'image=%s\n' "$IMAGE"

# kubectl JSON 输出转 YAML 摘要
kubectl get pod train-worker-0 -o json | yq -P '{name: .metadata.name, phase: .status.phase}'

# 多文档 YAML 转 JSON，每个文档一个 JSON 对象
yq -o=json '.' rendered.yaml
选项常见用途
-o=json输出 JSON，便于交给 jq、API、日志系统
-Ppretty print YAML，便于人工审查
-r输出 raw string，避免带引号
-I 2控制缩进，适合统一格式
边界提醒： JSON 不保留 YAML 注释；某些 YAML 特性在转换后也会丢失。需要保留注释和格式的人工维护文件，不要把转换当成无损操作。

10. 合并 values 与覆盖配置

训练平台和推理平台常见配置模式是 base values 加环境覆盖：values.base.yaml、values.prod.yaml、values.gpu-a100.yaml。Go yq 的 eval-all 可以一次读取多个文件，并按文件索引合并。

# 查看两个 values 合并后的结果，prod 覆盖 base
yq eval-all 'select(fileIndex == 0) * select(fileIndex == 1)' values.base.yaml values.prod.yaml

# 多层覆盖：base < cluster < release
yq eval-all '
  select(fileIndex == 0) *
  select(fileIndex == 1) *
  select(fileIndex == 2)
' values.base.yaml values.cluster.yaml values.release.yaml

# 只抽取合并后的关键字段
yq eval-all 'select(fileIndex == 0) * select(fileIndex == 1)
  | {image: .image, resources: .resources, nodeSelector: .nodeSelector}' base.yaml prod.yaml
浅层覆盖
适合简单 values，但嵌套 map 需要确认合并语义。
数组合并
数组覆盖、追加、按 name 合并的需求不同，不能混用。
Helm 真实语义
最终以 helm template 渲染结果为准，yq 合并只是一种辅助检查。
合并警告： values 合并很容易在数组上出现误判，例如 tolerations、env、volumes。上线前用 helm template ... | yq ... 检查最终 manifest。

11. 原地修改 -i 的安全流程

-i 会把结果写回文件。它很适合 CI 自动 bump 镜像 tag，也很容易把大批配置改坏。生产流程要把“预览、审查、备份、验证”写成习惯。

# 1. 确认工作区状态
git status --short

# 2. dry-run 输出，不改文件
yq '.image.tag = "v1.8.3"' values.yaml

# 3. 用 diff 审查差异
yq '.image.tag = "v1.8.3"' values.yaml | diff -u values.yaml -

# 4. 确认后原地修改
yq -i '.image.tag = "v1.8.3"' values.yaml

# 5. 再看 git diff
git diff -- values.yaml

# 6. 如果是 Kubernetes manifest，做客户端校验或渲染检查
kubectl apply --dry-run=client -f values-rendered.yaml
不要这样做： 不要在未知文件集合上直接运行 find . -name '*.yaml' -exec yq -i '...' {} \;。先列出文件、抽样 diff、确认表达式只命中目标资源，再批量执行。
# 批量前先列出候选文件
rg -l 'registry.local/ml/trainer' configs/

# 对单个文件审查差异
yq '(.spec.template.spec.containers[] | select(.name == "trainer").image) = "registry.local/ml/trainer:v2"' configs/train.yaml | diff -u configs/train.yaml -

# 批量时保留 git diff 作为最终审查
for f in $(rg -l 'registry.local/ml/trainer' configs/); do
  yq -i '(.spec.template.spec.containers[] | select(.name == "trainer").image) = "registry.local/ml/trainer:v2"' "$f"
done
git diff -- configs/

12. yq 与 jq、kubectl、python 的边界

工具优势限制推荐场景
yq直接读写 YAML，适合 manifest 和 values复杂业务逻辑可读性下降；实现差异明显配置查询、局部更新、YAML/JSON 转换
jqJSON 生态成熟，过滤聚合强不直接处理 YAML 注释和格式Kubernetes JSON 输出、日志 JSON、API 响应
kubectl理解 Kubernetes API，可校验和提交对象不适合离线批量编辑 arbitrary YAML集群实时查询、apply、patch、rollout
Python/Go可测试、可维护、可接 schema/API比 one-liner 重复杂迁移、策略校验、跨文件一致性检查
sed简单文本替换非常快不理解 YAML 结构只处理无结构文本或明确字符串替换
# 离线 YAML：yq
yq '.image.tag = "v2"' values.yaml

# 在线对象：kubectl patch 更直接
kubectl patch deployment trainer -p '{"spec":{"replicas":4}}'

# JSON 深加工：kubectl + jq
kubectl get pods -A -o json | jq '.items[] | {ns: .metadata.namespace, name: .metadata.name}'

# 复杂校验：用 Python 写可测试脚本，而不是堆超长 yq one-liner

13. CI/CD 与 GitOps 使用模式

在 CI 中使用 yq，重点不是“能改”，而是“可重复、可审计、可回滚”。固定 yq 版本、打印版本、限制修改路径、生成 diff，是比炫技表达式更重要的工程实践。

# CI 中 bump Helm values 镜像 tag
yq --version
test -n "$IMAGE_TAG"
yq -i '.image.repository = "registry.local/ml/trainer" | .image.tag = env(IMAGE_TAG)' charts/trainer/values.yaml
git diff -- charts/trainer/values.yaml

# 渲染后做静态检查
helm template trainer charts/trainer -f charts/trainer/values.yaml > /tmp/rendered.yaml
yq 'select(.kind == "Deployment")
  | .spec.template.spec.containers[]
  | select(.resources.limits."nvidia.com/gpu" == null)
  | .name' /tmp/rendered.yaml

# GitOps PR 中输出摘要
yq '{image: .image, resources: .resources, nodeSelector: .nodeSelector}' charts/trainer/values.yaml
CI 建议： 把 yq --version、目标文件路径、关键修改摘要和 git diff --exit-code 或 PR diff 纳入流水线日志，便于审计。

14. 常见 AI Infra 配置任务

镜像审计
列出所有镜像，检查是否来自内部 registry，是否使用 latest。
GPU 配额审计
扫描 nvidia.com/gpu request/limit，避免训练任务漏配或超配。
NCCL/UCX 参数检查
读取 env 中的 NCCL_DEBUG、NCCL_SOCKET_IFNAME、UCX_NET_DEVICES。
节点调度约束
检查 nodeSelector、tolerations、affinity 是否符合 GPU 池规范。
安全上下文
扫描 privileged、hostNetwork、hostPID、hostPath。
Helm values 合规
确认镜像仓库、tag、resources、serviceAccount 和 metrics 开关。
# 找 latest 镜像
yq '.. | select(tag == "!!str") | select(test(":latest$"))' rendered.yaml

# 更常见：从容器字段列出 latest
yq '.spec.template.spec.containers[]?.image | select(test(":latest$"))' deployment.yaml

# 扫描 hostNetwork
yq 'select(.spec.template.spec.hostNetwork == true) | .kind + "/" + .metadata.name' rendered.yaml

# 读取 NCCL 相关环境变量
yq '.spec.template.spec.containers[].env[]?
  | select(.name | test("^NCCL_"))
  | .name + "=" + .value' train-job.yaml

# 列出 GPU limit
yq '.spec.template.spec.containers[]?
  | select(.resources.limits."nvidia.com/gpu" != null)
  | .name + ": " + (.resources.limits."nvidia.com/gpu" | tostring)' train-job.yaml
扫描提醒： .. 递归搜索很方便，但在大文件和复杂 CRD 上可能输出过多。生产审计优先走明确路径，递归搜索作为排障辅助。

15. 排障：表达式、类型、缩进和版本

yq 出问题通常集中在四类：版本不一致、路径没命中、数组筛选为空、类型不符合预期。排障时先构造最小 YAML，再逐步加复杂条件。

问题 1：命令在本机能跑，CI 失败
先看 yq --version。CI 可能是另一个实现或旧版本。
问题 2：输出 null
路径不存在、当前资源 kind 不对、数组下标不对，或 key 含特殊字符未加引号。
问题 3：select 没结果
条件字段不存在、类型不一致，或目标在 initContainers 而不是 containers。
问题 4：Kubernetes 不接受结果
YAML 语法正确不代表 Kubernetes schema 合法；需要 kubectl apply --dry-run=client/server。
问题 5：注释消失
转换、重写或不同实现可能影响注释和格式；不要对需要保留手写注释的文件做无谓格式化。
问题 6：shell 引号破坏表达式
外层用单引号包 yq 表达式；需要环境变量时用 env(NAME)，不要让 shell 提前展开复杂字符串。

排障模板

# 1. 固定最小输入
cat > /tmp/yq-debug.yaml <<'YAML'
spec:
  template:
    spec:
      containers:
        - name: trainer
          image: old
YAML

# 2. 先验证路径
yq '.spec.template.spec.containers[].name' /tmp/yq-debug.yaml

# 3. 再验证筛选
yq '.spec.template.spec.containers[] | select(.name == "trainer")' /tmp/yq-debug.yaml

# 4. 最后验证更新
yq '(.spec.template.spec.containers[] | select(.name == "trainer").image) = "new"' /tmp/yq-debug.yaml

排障顺序：版本 → 输入结构 → 路径 → 类型 → dry-run diff → Kubernetes schema 校验。

检查项命令或动作目标
确认 yq 实现yq --version避免 Go yq/Python yq/旧版语法混用
确认目标文件rg -l 'pattern' configs/限制修改范围
确认表达式命中yq 'path' file.yaml避免路径为 null 或空筛选
预览修改yq 'update' file.yaml | diff -u file.yaml -审查真实差异
原地修改yq -i 'update' file.yaml只在确认后执行

17. 学习路线与练习任务

第一阶段：会读

  • 理解 . 是根节点，.a.b 是路径访问。
  • 掌握数组遍历 [] 和特殊 key 引号写法。
  • 能从 Kubernetes YAML 中读取 kind、name、images、resources。

第二阶段：会改

  • 掌握 =、|=、del()、数组追加。
  • 按容器名筛选后修改镜像、GPU limit、环境变量。
  • 使用 diff -u file - 审查 dry-run 结果。

第三阶段：工程化

  • 处理 Helm 渲染后的多文档 YAML。
  • 用 eval-all 理解 values 覆盖结果。
  • 在 CI 中固定 yq 版本、输出 diff、执行 Kubernetes dry-run。

  1. 创建一个 Pod YAML，读取 metadata.name 和第一个容器镜像。
