1. dd 是什么，为什么 AI Infra 会用到

dd 的定位不是“性能基准测试工具”，而是“可控的字节复制工具”。它常被用来快速生成大文件、观察单线程顺序读写吞吐、制作磁盘镜像、从设备或文件中跳过/截取固定范围，以及验证存储路径是否出现明显异常。

适合
顺序读写粗测、生成训练缓存占位文件、镜像备份、截取固定偏移数据、验证磁盘写入链路。
不适合
随机 IO、并发队列深度、多 job 混合负载、延迟分布、真实训练 dataloader 模拟。
核心风险
参数短、权限高、反馈少；一旦把 of 指向错误磁盘，覆盖会立即发生。
# 生成一个 1 GiB 测试文件
dd if=/dev/zero of=test-1g.bin bs=1M count=1024 status=progress

# 从文件复制前 64 MiB
dd if=dataset.bin of=head-64m.bin bs=1M count=64 status=progress

# 查看 dd 的最终统计：复制字节数、耗时、平均吞吐
dd if=test-1g.bin of=/dev/null bs=4M status=progress
生产提醒： dd 输出的 MB/s 只是本次单进程复制平均值。它不是训练吞吐、不是 P99 延迟、也不是存储系统容量规划结论。

信息图：dd 的整体心智模型

理解 dd 的关键是看清楚字节流：输入从哪里来、每块多大、复制多少块、输出写到哪里。

2. 基本语法：if/of/bs/count

dd if=输入 of=输出 bs=块大小 count=块数量 [选项...]

# 不写 if 时从标准输入读
# 不写 of 时写到标准输出
# bs * count 约等于总复制量
参数含义AI Infra 常见用法
if=input file，输入文件或设备/dev/zero、模型缓存文件、磁盘镜像
of=output file，输出文件或设备测试文件、镜像文件、块设备；最危险参数
bs=一次读写的块大小1M、4M、16M 做顺序 IO 粗测
count=复制多少个输入块控制测试文件大小，避免写满磁盘
skip=输入端跳过多少块从镜像或大文件中截取偏移区域
seek=输出端跳过多少块写稀疏文件或覆盖指定偏移
# 复制 256 MiB：bs=1M count=256
dd if=/dev/zero of=/tmp/dd-demo.bin bs=1M count=256 status=progress

# 读取 256 MiB 丢弃，观察读取吞吐
dd if=/tmp/dd-demo.bin of=/dev/null bs=1M count=256 status=progress

# 从 1 GiB 偏移处截取 128 MiB
dd if=large-cache.bin of=slice.bin bs=1M skip=1024 count=128 status=progress
心算公式： bs=4M count=256 约等于 1 GiB；bs=1M count=10240 约等于 10 GiB。

3. 单位、块大小与完整读

GNU dd 支持多种大小后缀。工程沟通时要区分十进制 MB 与二进制 MiB：M 在 GNU coreutils 中通常表示 1024*1024 字节，适合 Linux 环境下的容量心算。

写法大致含义建议
bs=4K4 KiB 级别块贴近页大小，但对顺序吞吐测试调用次数多
bs=1M1 MiB 级别块简单、常用，适合生成文件与粗测
bs=4M4 MiB 级别块常用于顺序读写粗测，系统调用开销较低
bs=64M大块复制不一定更快，可能增加内存压力和进度颗粒度
# 比较不同 bs 的单进程顺序读差异
for bs in 4K 1M 4M 16M; do
  echo "== bs=$bs =="
  dd if=/tmp/dd-demo.bin of=/dev/null bs="$bs" status=progress
done

# 管道或特殊输入可能出现短读，iflag=fullblock 可要求填满输入块
gzip -dc dataset.bin.gz | dd of=dataset.bin bs=4M iflag=fullblock status=progress
块大小不是魔法旋钮： 如果后端瓶颈是网络、RAID、对象存储网关或文件系统锁，单纯增大 bs 不会把系统变快。

4. 安全演练：只写普通文件

学习 dd 时，应先把所有输出限定在临时目录的普通文件中。确认命令含义后，再讨论块设备。下面的演练不会写磁盘设备，只会在 /tmp 创建和删除测试文件。

set -euo pipefail
mkdir -p /tmp/dd-lab
cd /tmp/dd-lab

# 确认当前目录，避免误删其他路径
pwd

# 生成 128 MiB 文件
dd if=/dev/zero of=sample.bin bs=1M count=128 status=progress

# 看文件大小和磁盘占用
ls -lh sample.bin
du -h sample.bin

# 清理只删除本实验文件
rm -f /tmp/dd-lab/sample.bin
推荐习惯： 把危险命令中的 of= 先写成普通文件，确认大小、耗时和输出后，再考虑是否需要设备级操作。

流程图：用 dd 做简单顺序写测试

写测试必须先确认路径和空间；普通 buffered 写入很容易测到页缓存，不等价于真实设备写入能力。

5. 简单顺序写测试

AI 训练节点常需要快速判断本地 NVMe、共享文件系统或挂载路径是否明显异常。dd 可以做一个低成本 smoke test，但要明确它只测单进程顺序写。

# 先确认测试路径和剩余空间
TEST_DIR=/mnt/nvme0/dd-test
mkdir -p "$TEST_DIR"
df -h "$TEST_DIR"

# buffered 写：可能主要测到 page cache 和回写策略
dd if=/dev/zero of="$TEST_DIR/write-buffered.bin" bs=1M count=4096 status=progress
sync

# 更保守：把数据同步到介质后再结束统计
dd if=/dev/zero of="$TEST_DIR/write-fdatasync.bin" bs=1M count=4096 conv=fdatasync status=progress

# 清理测试文件
rm -f "$TEST_DIR"/write-buffered.bin "$TEST_DIR"/write-fdatasync.bin
写法统计含义风险/ caveat
dd ...写入系统缓存完成即可返回可能高估真实落盘能力
conv=fdatasync结束前同步文件数据仍是单文件、单进程、顺序写
oflag=direct尝试绕过页缓存要求对齐，文件系统和设备行为可能不同
不要写满盘： 训练节点写满本地盘可能导致 kubelet、容器运行时、日志系统和 checkpoint 全部异常。

6. 简单顺序读测试

读测试要先有一个足够大的文件。文件过小会被缓存完全命中，得到的只是内存读速度。建议测试文件至少大于可用内存的一部分，或者使用 direct IO，并清楚记录方法。

TEST_DIR=/mnt/nvme0/dd-test
mkdir -p "$TEST_DIR"

# 先生成 8 GiB 文件，结束时同步数据
dd if=/dev/zero of="$TEST_DIR/read-source.bin" bs=1M count=8192 conv=fdatasync status=progress

# 普通读：第二次通常会因为 page cache 变快
dd if="$TEST_DIR/read-source.bin" of=/dev/null bs=4M status=progress
dd if="$TEST_DIR/read-source.bin" of=/dev/null bs=4M status=progress

# direct 读：减少 page cache 干扰，但仍需理解文件系统和对齐限制
dd if="$TEST_DIR/read-source.bin" of=/dev/null bs=4M iflag=direct status=progress

rm -f "$TEST_DIR/read-source.bin"
读测试解释： 如果第一次慢、第二次极快，多半是页缓存命中；这不是磁盘突然变快，而是数据已经在内存里。

7. page cache 对结果的影响

Linux 会把文件读写缓存到内存中。dd 的默认 buffered IO 会经过 page cache，因此它的结果经常混合了内存缓存、文件系统回写策略、设备吞吐和后台 flush 行为。

写入时
命令可能在数据真正写入设备前返回；后续 sync 或后台回写才承担落盘成本。
读取时
重复读取同一文件可能从内存命中，吞吐远高于设备能力。
清缓存
echo 3 > /proc/sys/vm/drop_caches 需要 root，影响整机，不适合共享生产节点随意执行。
替代方案
使用大于内存的文件、切换测试文件、使用 direct IO，或使用 fio 明确参数。
# 不推荐在共享训练节点随意清缓存；如必须在隔离测试机执行：
sync
echo 3 | sudo tee /proc/sys/vm/drop_caches

# 更安全的做法：记录这是 buffered 测试，并用 direct IO 追加对照
dd if=source.bin of=/dev/null bs=4M status=progress
dd if=source.bin of=/dev/null bs=4M iflag=direct status=progress
平台影响： 在多租户 GPU 节点上清 page cache 可能让其他训练任务瞬间抖动。除非你拥有隔离测试窗口，否则不要把清缓存当成常规步骤。

8. oflag=direct 与对齐限制

oflag=direct 请求使用 direct IO 写输出，iflag=direct 请求 direct IO 读输入。它们可减少 page cache 干扰，但并不等于“真实业务性能”，也不保证所有文件系统、块设备、网络挂载都支持。

选项方向常见用途常见失败
oflag=direct写顺序写粗测时减少缓存影响Invalid argument，块大小或地址未对齐
iflag=direct读顺序读粗测时减少缓存影响文件系统不支持或设备限制
conv=fdatasync写结束结束前同步数据不绕过缓存，只把落盘成本计入尾部
TEST_DIR=/mnt/nvme0/dd-test
mkdir -p "$TEST_DIR"

# direct 写通常使用较大的、对齐友好的 bs
dd if=/dev/zero of="$TEST_DIR/direct-write.bin" bs=4M count=2048 oflag=direct status=progress

# direct 读
dd if="$TEST_DIR/direct-write.bin" of=/dev/null bs=4M iflag=direct status=progress

rm -f "$TEST_DIR/direct-write.bin"
解释 caveat： direct IO 绕过页缓存，但仍会受文件系统、块层调度、RAID、加密、网络存储和虚拟化层影响。结果只能说明“这条路径在这个参数下”的表现。

9. status=progress 与进度观测

GNU coreutils 的 dd 支持 status=progress，会周期性显示已复制字节数、耗时和平均速度。没有该选项时，也可以向运行中的 dd 发送 USR1 信号打印统计。

# 直接显示进度
dd if=/dev/zero of=/tmp/progress-demo.bin bs=1M count=4096 status=progress

# 另一个终端查看进程并打印一次统计
pgrep -af 'dd if=/dev/zero'
kill -USR1 <dd-pid>

# 只输出最终统计，减少日志噪声
dd if=/tmp/progress-demo.bin of=/dev/null bs=4M status=none
rm -f /tmp/progress-demo.bin
status 值作用场景
status=progress显示运行中进度和最终统计长时间复制、生成大文件
status=none不显示统计脚本中只关心退出码
默认结束时显示统计短命令或交互执行
日志建议： 在 CI 或批量巡检中记录完整命令、路径、文件系统、内核版本和最终统计，否则单个 MB/s 数字很难复现。

对比图：dd 与 fio 的边界

dd 是好用的手电筒，不是完整的实验室。性能结论需要 fio 这类可复现实验工具。

10. dd vs fio：何时换工具

问题dd 是否足够推荐工具
这块盘顺序写是不是只有几十 MB/s？通常足够做初筛dd + iostat
训练 dataloader 随机读小文件是否卡？不够fio、业务 profile
NVMe 在 QD=32 随机读 IOPS 如何？不够fio
制作磁盘镜像或截取文件范围适合dd
比较文件系统挂载参数的延迟分布不够fio、blktrace、eBPF 工具
# dd：快速 smoke test
dd if=/dev/zero of=/mnt/nvme0/smoke.bin bs=4M count=1024 conv=fdatasync status=progress

# fio：严肃顺序写基准的起点示例
fio --name=seqwrite --directory=/mnt/nvme0 --size=4G --rw=write \
    --bs=1M --iodepth=16 --numjobs=1 --direct=1 --group_reporting
决策规则： 用 dd 快速定位“路径是否离谱”；只要要比较方案、出报告、做容量规划，就切到 fio。

11. 磁盘镜像与恢复

dd 能把块设备复制成镜像文件，也能把镜像写回设备。这是它最有用也最危险的能力之一。读取设备做镜像通常风险较低；把镜像写回设备则会覆盖目标。

# 只读方向：把设备保存为镜像文件
lsblk -o NAME,SIZE,MODEL,MOUNTPOINTS
sudo dd if=/dev/sdX of=/backup/sdX-$(date +%F).img bs=4M status=progress conv=fsync

# 镜像压缩：节省空间，但恢复前要验证
sudo dd if=/dev/sdX bs=4M status=progress | gzip -1 > /backup/sdX.img.gz

# 查看镜像文件分区，可在隔离环境中使用 loop 设备
sudo losetup --find --show --partscan /backup/sdX-2026-04-25.img
lsblk
写回镜像前必须确认： 目标设备大小、型号、序列号、挂载点都要核对。不要在生产节点上凭 /dev/sdX 的字母猜目标盘。
# 危险示例：写回镜像会覆盖目标设备
lsblk -o NAME,SIZE,MODEL,SERIAL,MOUNTPOINTS
read -rp "确认目标 /dev/sdX 会被覆盖，输入 YES 继续: " ans
[ "$ans" = YES ] || exit 1
sudo dd if=/backup/sdX.img of=/dev/sdX bs=4M status=progress conv=fsync

12. 零填充、擦除与破坏性写入

if=/dev/zero of=... 可以把输出写成全 0。写到普通文件时它只是生成零文件；写到块设备时，它会覆盖磁盘内容。对 SSD/NVMe，零填充也不等于安全擦除，可能增加写放大；安全擦除应优先使用设备支持的 sanitize/secure erase 流程。

# 安全：只在临时目录创建一个零文件
dd if=/dev/zero of=/tmp/zero-file.bin bs=1M count=1024 status=progress
rm -f /tmp/zero-file.bin

# 危险：下面命令会覆盖整块设备，默认不要运行
lsblk -o NAME,SIZE,MODEL,SERIAL,MOUNTPOINTS
read -rp "确认要清零 /dev/sdX，输入 WIPE: " ans
[ "$ans" = WIPE ] || exit 1
sudo dd if=/dev/zero of=/dev/sdX bs=16M status=progress oflag=direct
零填充危险： of=/dev/sda 与 of=/dev/sdb 只差一个字符，但后果可能是系统盘被覆盖。复制粘贴前先把目标设备路径单独核对一遍。
目标更合适的做法说明
释放文件空间rm 或应用级清理不需要 dd 清零文件
安全擦除 SSD/NVMeblkdiscard、NVMe sanitize、厂商工具依设备和合规要求选择
生成占位文件dd 或 fallocatefallocate 更快但可能创建未实际写入的空间

13. AI Infra 常见场景

节点验收 smoke test
在本地 NVMe 上写 4-16 GiB 普通文件，观察吞吐是否和同类机器差几个数量级。
缓存盘预热/占位
快速创建固定大小文件验证 quota、挂载权限、inode 和路径可写性。
镜像备份
对离线盘制作镜像，便于取证或迁移；写回前必须核对设备。
故障隔离
把业务 dataloader 慢的问题拆成：磁盘顺序读、随机读、小文件元数据、网络路径、CPU 解码。
# 节点验收：记录硬件和挂载信息
hostname
uname -a
lsblk -o NAME,SIZE,MODEL,ROTA,MOUNTPOINTS
findmnt /mnt/nvme0

# 单线程顺序写 smoke test
dd if=/dev/zero of=/mnt/nvme0/dd-smoke.bin bs=4M count=4096 conv=fdatasync status=progress

# 单线程顺序读 smoke test
dd if=/mnt/nvme0/dd-smoke.bin of=/dev/null bs=4M iflag=direct status=progress
rm -f /mnt/nvme0/dd-smoke.bin
和训练性能的关系： GPU 利用率低不一定是磁盘慢。可能是小文件过多、解码 CPU 瓶颈、网络抖动、分布式采样、容器限速或数据格式问题。

排障/安全图：dd 结果异常或命令危险时怎么查

dd 排障同时是安全流程：先确认目标，再解释缓存，再复验工具，不要在设备上试错。

14. 故障排查流程

当 dd 速度“看起来不对”时，先判断是命令测法问题，还是存储路径真的异常。下面的流程适合 AI 节点、容器宿主机、裸机和虚拟机。

# 1. 记录路径和挂载
TARGET=/mnt/nvme0
df -h "$TARGET"
findmnt "$TARGET"
lsblk -o NAME,SIZE,MODEL,ROTA,MOUNTPOINTS

# 2. 记录系统压力
iostat -xz 1 5
dmesg | tail -n 80

# 3. buffered 与 direct 对照
dd if=/dev/zero of="$TARGET/dd-check.bin" bs=4M count=1024 conv=fdatasync status=progress
dd if="$TARGET/dd-check.bin" of=/dev/null bs=4M iflag=direct status=progress
rm -f "$TARGET/dd-check.bin"

# 4. 如果要下结论，用 fio 复验并保存参数
fio --name=readcheck --directory="$TARGET" --size=4G --rw=read \
    --bs=1M --iodepth=16 --direct=1 --numjobs=1 --group_reporting
Invalid argument
常见于 direct IO 对齐或文件系统不支持。尝试 bs=4M，或去掉 direct 做对照。
No space left on device
测试文件太大、quota 满、容器 writable layer 满。先 df -h 和 df -i。
速度忽高忽低
可能是 page cache、后台 flush、共享盘争用、热迁移、网络存储抖动。
写入很快但 sync 很慢
前面写入多在缓存，真正落盘成本集中在同步阶段。

15. 练习路线与检查清单

第一阶段：理解复制模型

  • 用 /dev/zero 生成 64 MiB、1 GiB 文件。
  • 改变 bs 和 count，确认总大小如何变化。
  • 用 of=/dev/null 观察读取路径。

第二阶段：理解缓存与 direct IO

  • 连续读取同一个文件两次，观察第二次是否变快。
  • 比较 conv=fdatasync、oflag=direct、普通 buffered 写。
  • 记录测试目录所在文件系统和挂载方式。

第三阶段：生产安全

  • 每次写设备前运行 lsblk -o NAME,SIZE,MODEL,SERIAL,MOUNTPOINTS。
  • 把危险命令先改成普通文件演练。
  • 需要性能结论时写 fio job 或完整命令，避免只贴一个速度数字。
