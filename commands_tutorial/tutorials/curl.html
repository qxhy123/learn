一句话理解： curl 是可脚本化的网络客户端：你用选项精确描述“发什么请求、如何连接、如何认证、如何处理响应”，它把传输过程变成可复制、可调试、可自动化的命令。

1. curl 是什么，适合解决什么问题

curl 是命令行网络传输工具，名字来自“client URL”。它支持 HTTP、HTTPS、FTP、SFTP、SMTP 等协议，但日常最常见用途是调试 HTTP API、下载文件、检查站点连通性、在脚本里调用服务。

它擅长什么
构造精确 HTTP 请求、查看响应头、提交 JSON/表单、带认证访问 API、测试 TLS 与代理、下载/上传文件。
它不擅长什么
复杂交互式浏览器行为、执行 JavaScript、自动解析 HTML 页面、长期爬虫调度。那些场景更适合浏览器自动化或专用爬虫框架。
它的本质
把“URL + 方法 + 头 + 体 + 传输策略”变成一次网络请求，并把响应和诊断信息暴露给你。
# 最小请求：GET 一个 URL，把响应正文输出到 stdout
curl https://example.com

# 只看响应头
curl -I https://example.com

# 调试一次 API 请求
curl -v -H 'Accept: application/json' https://api.example.com/health
边界提醒： curl 默认不会像浏览器一样执行跳转后的页面脚本，也不会自动保存复杂会话状态。你必须显式提供 Cookie、Header、Body、代理和 TLS 选项。

2. HTTP 请求/响应心智模型

信息图：curl 视角下的 HTTP 请求/响应模型

curl 的选项本质上都在控制四类事情：如何连接、发什么请求、如何接收响应、遇到错误时如何处理。

一次 HTTP 调用可以拆成两半：请求由客户端发出，包含方法、路径、请求头和可选请求体；响应由服务器返回，包含状态码、响应头和可选响应体。curl 的价值在于让这些部件都可以显式控制和观察。

# 同时观察请求头、响应头和 TLS/连接信息
curl -v -H 'Accept: application/json' https://api.example.com/health

2. 基本语法、URL 与退出码

curl [options] URL

# 常用结构
curl -H 'Header-Name: value' -X METHOD -d 'body' https://host/path?query=value

没有显式指定方法时，curl 通常使用 GET；使用 -d、--data、-F 等提交数据时，curl 会自动倾向于 POST。URL 里的 shell 特殊字符要正确引用，特别是 &、?、空格、方括号。

部件例子说明
协议https://决定传输协议，HTTPS 会经过 TLS 握手。
主机api.example.com用于 DNS 解析、TLS SNI、Host 头。
路径/v1/users服务器路由通常依赖它。
查询参数?page=1&size=20GET 查询常用；建议整体用引号包住。
# 引号避免 & 被 shell 当成后台执行符
curl 'https://api.example.com/search?q=linux curl&page=1'

# 查看退出码：0 表示 curl 传输层面成功，不一定表示 HTTP 2xx
curl -sS https://example.com/health
echo "$?"
重要区别： 默认情况下，HTTP 404/500 也可能让 curl 返回退出码 0，因为“请求成功完成，只是服务器返回错误状态”。脚本里常用 --fail 或 --fail-with-body 把 HTTP 错误转成非零退出码。

3. 查看响应：正文、头部、状态码

调试 HTTP 时，第一步是分清“响应正文”“响应头”“状态码”“curl 自己的诊断输出”。不同选项输出到 stdout/stderr 的位置不同，写脚本时要有意识地区分。

选项作用典型场景
-i响应头 + 响应体都输出到 stdout临时观察完整响应。
-I发 HEAD 请求，只取响应头检查资源是否存在、缓存头、跳转。
-v输出连接、TLS、请求头、响应头等诊断到 stderr定位协议和网络问题。
-sS静默进度条，但保留错误信息脚本调用 API。
-w / --write-out按模板输出状态码、耗时、大小等指标监控、CI、排障。
# 响应头和正文一起看
curl -i https://example.com

# 只看响应头
curl -I https://example.com

# 只输出状态码
curl -sS -o /dev/null -w '%{http_code}\n' https://example.com

# 输出一行便于日志收集的指标
curl -sS -o /dev/null \
  -w 'code=%{http_code} dns=%{time_namelookup} connect=%{time_connect} total=%{time_total}\n' \
  https://example.com
脚本建议： 使用 -sS 代替单独的 -s。单独 -s 会隐藏错误信息，失败时排障成本更高。

4. HTTP 方法：GET、POST、PUT、PATCH、DELETE

HTTP 方法描述客户端意图。curl 的 -X 可以显式指定方法，但并不自动改变请求体、Content-Type 或语义。生产中要同时确认方法、URL、Header、Body 是否共同表达了正确意图。

方法常见语义curl 示例注意
GET读取资源curl 'https://api.example.com/users/42'参数通常放查询字符串；不应产生副作用。
POST创建、提交动作curl -d 'name=alice' https://api.example.com/users-d 默认触发 POST。
PUT整体替换资源curl -X PUT --json '{"name":"alice"}' URL常要求发送完整资源表示。
PATCH局部更新资源curl -X PATCH --json '{"enabled":true}' URL确认 API 接收的 patch 格式。
DELETE删除资源curl -X DELETE URL危险操作先确认环境和资源 ID。
# GET：读取
curl -H 'Accept: application/json' 'https://api.example.com/v1/users?limit=20'

# POST：提交 JSON
curl --json '{"name":"alice","role":"reader"}' https://api.example.com/v1/users

# PATCH：局部更新
curl -X PATCH --json '{"role":"admin"}' https://api.example.com/v1/users/42

# DELETE：生产中先查，再删
curl -sS https://api.example.com/v1/users/42
curl -X DELETE https://api.example.com/v1/users/42
危险方法提醒： DELETE、修改账务/订单/权限的 POST/PATCH 命令不要直接从聊天记录或文档复制到生产环境执行。先确认 base URL、环境变量、资源 ID、认证身份和 API 是否支持 dry-run。

流程图：从需求到 curl 请求的构造流程

构造 curl 命令不要从选项开始，而要从 API 意图开始：方法、URL、头、体、安全策略缺一不可。

5. 查询参数、表单与 JSON 请求体

请求体的格式决定了服务器如何解析你的数据。curl 不会自动猜业务格式；你需要选对 Content-Type，并使用合适的提交方式。

数据类型选项默认/效果适用场景
查询参数写在 URL 或 --get --data-urlencode拼到 URL 后面搜索、分页、筛选。
普通表单-d 'a=1&b=2'application/x-www-form-urlencoded传统表单、OAuth token 请求。
JSON--json '{...}'设置 JSON 相关头并发送 body现代 REST/HTTP API。
原始二进制--data-binary @file尽量原样发送上传压缩包、签名数据、webhook 回放。
multipart-F 'file=@a.png'multipart/form-data文件上传和混合字段。
# URL 编码查询参数，避免手写转义
curl --get 'https://api.example.com/search' \
  --data-urlencode 'q=linux curl 教程' \
  --data-urlencode 'page=1'

# 普通表单
curl -d 'username=alice&password=secret' https://example.com/login

# JSON：curl 7.82+ 支持 --json
curl --json '{"name":"alice","tags":["linux","api"]}' https://api.example.com/v1/items

# 老版本 curl 可手动写 Header
curl -H 'Content-Type: application/json' \
  -d '{"name":"alice"}' \
  https://api.example.com/v1/items

# 原样发送文件内容作为请求体
curl -H 'Content-Type: application/octet-stream' \
  --data-binary @payload.bin \
  https://api.example.com/upload/raw
JSON 引号提醒： 在 shell 里 JSON 外层常用单引号，避免双引号被 shell 解释。需要变量插值时，不要直接拼接未转义的用户输入，优先用文件或专用 JSON 工具生成。

6. 请求头、内容协商与 User-Agent

HTTP Header 是请求的元数据：告诉服务器你接受什么格式、发送什么格式、如何认证、希望如何缓存或追踪。curl 用 -H 添加或覆盖头。

Header含义示例
Accept客户端希望接收的响应格式Accept: application/json
Content-Type请求体格式Content-Type: application/json
Authorization认证凭据Authorization: Bearer $TOKEN
User-Agent客户端标识User-Agent: ops-check/1.0
X-Request-ID链路追踪 IDX-Request-ID: debug-20260425-001
# 指定 Accept 和 User-Agent
curl -H 'Accept: application/json' \
  -A 'ops-health-check/1.0' \
  https://api.example.com/health

# 添加追踪 ID，便于服务端日志检索
curl -H 'X-Request-ID: debug-20260425-001' \
  https://api.example.com/v1/orders/1001

# 发送空 Header：有时用于移除 curl 默认头
curl -H 'User-Agent:' https://example.com
调试技巧： 用 -v 可以看到 curl 实际发出的请求头；这比“我以为我设置了 Header”可靠得多。

7. 认证：Basic、Bearer、Cookie、mTLS

认证是 curl 最容易泄露敏感信息的部分。命令行参数可能进入 shell 历史、进程列表、CI 日志和监控系统。优先使用环境变量、配置文件权限、stdin 或短期 token，并避免在共享终端直接敲密码。

方式curl 写法说明
Basic Auth-u user:password简单但敏感；HTTPS 下才安全。
Bearer Token-H "Authorization: Bearer $TOKEN"API 常用；注意 token 生命周期。
Cookie-b cookie.txt -c cookie.txt模拟会话；可读写 cookie jar。
客户端证书--cert client.pem --key client.keymTLS 双向认证。
netrc--netrc-file ~/.netrc把凭据放受权限保护的文件。
# Basic：让 curl 提示输入密码，避免写进历史
curl -u alice https://api.example.com/private

# Bearer：从环境变量读取
TOKEN='replace-with-short-lived-token'
curl -H "Authorization: Bearer ${TOKEN}" https://api.example.com/v1/me

# Cookie jar：先登录，再带 cookie 访问
curl -c cookies.txt -d 'user=alice&password=secret' https://example.com/login
curl -b cookies.txt https://example.com/account

# mTLS：客户端证书认证
curl --cert client.crt --key client.key https://mtls.example.com/status
凭据安全： 不要把真实 token、密码、私钥提交到仓库或粘贴到工单。排障截图里也要打码 Authorization、Cookie、Set-Cookie。

8. 重定向、压缩与缓存相关行为

服务器可能返回 301、302、307、308 等重定向，响应头中的 Location 指向新地址。curl 默认不跟随重定向，需要 -L。跟随后要小心方法和认证头在跨域跳转时的行为。

# 查看跳转链
curl -I https://example.com/old-path

# 跟随重定向
curl -L https://example.com/old-path

# 限制最大跳转次数，避免循环
curl -L --max-redirs 5 https://example.com/old-path

# 请求压缩响应并自动解压
curl --compressed https://example.com/api/data
选项/头作用注意
-L跟随重定向排障时配合 -v 看每一跳。
--max-redirs N限制跳转次数防止跳转循环。
--compressed请求压缩内容并解压调试 CDN/网关压缩很有用。
If-None-Match条件请求检查 ETag 缓存行为。
重定向提醒： 对带认证的请求使用 -L 时，确认是否跨主机跳转。不要把敏感 Header 发送给非预期域名。

9. TLS、证书与安全开关

HTTPS 不是“加了 s 的 HTTP”，它会先进行 TLS 握手：验证证书链、主机名、协议版本和加密套件，然后才传输 HTTP。curl 的 TLS 诊断能力很强，但也有危险开关。

选项作用生产建议
-v显示 TLS 握手摘要、证书信息、协商协议推荐用于排障。
--cacert ca.pem指定 CA 证书内网私有 CA 常用。
--cert / --key客户端证书与私钥保护私钥权限。
--tlsv1.2 / --tlsv1.3限制 TLS 版本兼容性测试使用。
-k / --insecure跳过证书校验只用于临时定位，不能写入生产脚本。
# 查看 TLS 握手和证书验证过程
curl -v https://example.com -o /dev/null

# 使用私有 CA
curl --cacert company-root-ca.pem https://internal.example.com/health

# 检查服务是否支持 TLS 1.3
curl --tlsv1.3 -I https://example.com

# 临时验证“是否只是证书问题”，不要固化到脚本
curl -k -I https://staging.example.local
安全底线： -k 会关闭证书校验，使中间人攻击无法被发现。它可以帮助定位“证书链/主机名问题”，但不能作为修复方案。

信息图：连接、超时与重试的时间线

把超时看成预算：连接预算、总耗时预算、重试预算都要明确，否则脚本在故障时最容易失控。

10. 超时、重试、限速与失败策略

生产脚本里调用 curl，不能只写 URL。你还需要定义失败策略：多久算失败、哪些错误重试、重试几次、HTTP 500 是否让脚本失败、下载是否限速。

选项含义建议
--connect-timeout 3连接建立超时避免 DNS/TCP/TLS 阶段长时间卡住。
--max-time 15总耗时上限脚本和 CI 必备。
--retry 3重试次数适合临时网络错误，不适合非幂等写操作。
--retry-delay 2重试间隔避免立即打爆故障服务。
--retry-all-errors更多错误都重试谨慎使用，尤其是写请求。
--fail-with-bodyHTTP 4xx/5xx 返回非零，仍保留响应体现代 curl 推荐；老版本可用 --fail。
# 健康检查：失败要有退出码，也要有诊断信息
curl -sS --fail-with-body \
  --connect-timeout 3 \
  --max-time 10 \
  --retry 2 \
  https://api.example.com/health

# 下载限速，避免压垮小带宽环境
curl --limit-rate 2M -O https://example.com/big.tar.gz
重试语义： 对 GET、HEAD 这类通常幂等的请求，重试风险较低；对创建订单、扣款、发消息等非幂等写请求，自动重试可能造成重复副作用，必须依赖幂等键或服务端去重。

11. 下载文件：保存、断点续传、校验

curl 默认把响应体写到 stdout。下载二进制文件时必须用 -o 或 -O 保存到文件，否则终端可能输出乱码甚至污染屏幕。

选项作用例子
-o file保存为指定文件名curl -o app.tar.gz URL
-O使用远端文件名curl -O https://host/app.tar.gz
-C -自动断点续传curl -C - -O URL
--remote-name-all多个 URL 都使用远端文件名curl --remote-name-all URL1 URL2
# 指定文件名下载
curl -L -o kubectl https://example.com/bin/kubectl

# 使用远端文件名，常配合 -L
curl -L -O https://example.com/releases/app-1.2.3.tar.gz

# 断点续传
curl -C - -O https://example.com/releases/large-image.iso

# 下载后校验哈希
curl -L -O https://example.com/releases/app.tar.gz
curl -L -O https://example.com/releases/app.tar.gz.sha256
sha256sum -c app.tar.gz.sha256
供应链安全： 下载可执行文件、安装脚本或镜像后要校验哈希/签名。不要把 curl URL | sh 当成默认安装方式，除非你已经审查来源、内容和校验机制。

12. 上传文件与 multipart 表单

上传有两种常见模型：把整个文件当作请求体，或使用 multipart 表单字段。前者适合对象存储和原始二进制 API；后者适合 Web 表单和带字段元数据的上传。

# multipart 文件上传
curl -F 'file=@report.pdf' \
  -F 'project=alpha' \
  https://upload.example.com/files

# 指定文件字段的 MIME 类型
curl -F 'avatar=@me.png;type=image/png' https://example.com/profile/avatar

# 原始二进制上传
curl -X PUT \
  -H 'Content-Type: application/octet-stream' \
  --data-binary @backup.tar.gz \
  https://storage.example.com/bucket/backup.tar.gz

# 从 stdin 上传
tar czf - logs/ | curl -X PUT --data-binary @- https://storage.example.com/logs.tgz
写法含义常见坑
-F 'file=@a.txt'上传文件内容漏掉 @ 会上传字面字符串。
-F 'name=value'普通表单字段服务端字段名必须匹配。
--data-binary @file原样发送文件作为 body要确认 Content-Type 和 API 语义。
上传提醒： 大文件上传要设置超时、重试和校验；如果 API 不支持幂等，失败后自动重试可能产生重复对象或脏数据。

13. API 调试工作流

API 调试不要只看“返回了什么”。要分层确认：DNS 是否解析到预期地址、TLS 是否验证通过、请求头/体是否正确、服务端状态码是什么、响应体是否解释了业务错误。

推荐四步

# 1. 连通性和证书
curl -v -I https://api.example.com/health

# 2. 精简到最小可复现请求
curl -sS -i -H 'Accept: application/json' https://api.example.com/v1/users/42

# 3. 加认证和请求体
curl -sS -i --fail-with-body \
  -H "Authorization: Bearer ${TOKEN}" \
  --json '{"enabled":true}' \
  https://api.example.com/v1/users/42/actions/enable

# 4. 输出可观测指标
curl -sS -o response.json \
  -w 'code=%{http_code} remote=%{remote_ip} total=%{time_total}\n' \
  https://api.example.com/v1/users/42
请求侧检查
URL 是否正确、环境是否正确、方法是否正确、Header 是否实际发出、Body 是否符合 API schema、凭据是否属于预期账号。
响应侧检查
状态码、响应头、错误码、trace/request ID、是否经过 CDN/网关、服务端日志是否能按请求 ID 查到。
可复现原则： 把失败请求压缩成最小 curl 命令，通常比“应用里调用失败”更容易让后端、网关、网络团队共同定位。

14. 代理、DNS、IPv4/IPv6 与网络定位

网络问题常出在“请求根本没有到你以为的服务器”。curl 可以显式控制代理、DNS 解析、Host 头、IP 版本和连接目标，从而定位负载均衡、CDN、服务发现、内网代理问题。

选项作用场景
-x / --proxy使用代理公司代理、调试出口网络。
--noproxy绕过代理内网服务不应走代理。
--resolve host:port:ip临时指定 DNS 结果并保留 Host/SNI灰度、排查单台后端、绕过 DNS。
-4 / -6强制 IPv4/IPv6定位双栈问题。
--interface指定网卡/源地址多网卡机器排障。
# 通过 HTTP 代理访问
curl -x http://proxy.example.com:8080 https://api.example.com/health

# 内网站点绕过代理
curl --noproxy '*.internal.example.com' https://svc.internal.example.com/health

# 指定 api.example.com:443 解析到某个 IP，但 TLS SNI 和 Host 仍是 api.example.com
curl --resolve api.example.com:443:203.0.113.10 https://api.example.com/health

# 强制 IPv4 或 IPv6
curl -4 https://example.com
curl -6 https://example.com
定位价值： --resolve 比直接访问 IP 更适合 HTTPS 排障，因为它保留了 Host 头和 TLS SNI，更接近真实请求。

选择图：curl、wget、httpie 怎么选

curl 的优势是控制粒度和普遍可用；wget 的优势是下载任务；httpie 的优势是交互体验。

15. curl vs wget vs httpie

工具强项弱项典型命令
curl精确控制 HTTP 请求、认证、Header、TLS、代理、输出指标；几乎所有 Linux/macOS 环境可用。复杂 JSON 输出不美观；选项多，初学门槛高。curl -sS -H 'Accept: application/json' URL
wget下载文件、递归下载、镜像站点、断点续传体验好。API 调试粒度不如 curl 灵活。wget -c URL
httpie面向人类的 API 调试，JSON 语法和高亮友好。不是基础系统必备工具；脚本可移植性较差。http GET api.example.com/users
选 curl
需要稳定脚本、CI、细粒度 Header、TLS、代理、状态码和耗时指标。
选 wget
核心任务是下载文件、镜像目录、批量抓取静态资源。
选 httpie
本地交互式调 API，想要更自然的参数语法和漂亮 JSON 输出。

16. 常见错误与排障

现象可能原因排查命令
Could not resolve hostURL 拼写错、DNS 故障、shell 把 & 拆开、代理 DNS 策略不同。curl -v 'https://host/path?x=1&y=2'
Connection refused目标端口无服务、负载均衡后端异常、防火墙拒绝。curl -v --connect-timeout 3 URL
Operation timed out网络不通、服务无响应、代理卡住、包被丢弃。curl -v --connect-timeout 3 --max-time 10 URL
SSL certificate problem证书过期、链不完整、私有 CA 未信任、主机名不匹配。curl -vI https://host
HTTP 401/403未认证、token 过期、权限不足、签名错误。curl -i -H "Authorization: Bearer $TOKEN" URL
HTTP 404路径错、环境错、网关路由不匹配、资源不存在。curl -i URL
HTTP 415Content-Type 不匹配。curl -i -H 'Content-Type: application/json' -d '{}' URL
脚本没失败但 API 返回 500没有使用 --fail 或 --fail-with-body。curl --fail-with-body -sS URL
# 通用排障模板：保留正文到文件，指标输出到终端
curl -sS -i \
  --connect-timeout 3 \
  --max-time 10 \
  -o response.txt \
  -w 'code=%{http_code} ip=%{remote_ip} dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} total=%{time_total}\n' \
  https://api.example.com/health
读日志顺序： 先看 curl 退出码和 -v 阶段，再看 HTTP 状态码，最后看业务错误体。顺序反了容易把网络/TLS问题误判成业务问题。

17. 脚本化实践与安全清单

curl 命令进入脚本后，要像生产代码一样处理：显式失败、隐藏敏感信息、设置超时、记录必要指标、避免非幂等重试。

#!/usr/bin/env bash
set -euo pipefail

base_url="${API_BASE_URL:-https://api.example.com}"
token="${API_TOKEN:?API_TOKEN is required}"

tmp_body="$(mktemp)"
trap 'rm -f "$tmp_body"' EXIT

status="$(
  curl -sS --fail-with-body \
    --connect-timeout 3 \
    --max-time 15 \
    --retry 2 \
    -H "Authorization: Bearer ${token}" \
    -H 'Accept: application/json' \
    -o "$tmp_body" \
    -w '%{http_code}' \
    "${base_url}/v1/health"
)"

printf 'status=%s\n' "$status"
cat "$tmp_body"
脚本清单
使用 -sS；设置 --connect-timeout 和 --max-time；对 HTTP 错误使用 --fail-with-body；把响应体和状态码分开处理；为重试设置上限。
安全清单
token 用环境变量或受权限保护文件；日志打码 Header；危险方法先查后改；不要固化 -k；下载可执行内容要校验哈希或签名。
不要这样做： curl -k -s https://unknown.example/install.sh | sudo sh 同时绕过 TLS 校验、隐藏错误、信任未知脚本并提权执行，是多重风险叠加。

18. 练习任务：把 curl 用成可靠调试工具

  1. 用 curl -I 和 curl -L -I 比较一个站点的跳转前后响应头。
  2. 用 --write-out 输出状态码、远端 IP、DNS 耗时、连接耗时、总耗时。
  3. 构造一个 JSON POST 请求，同时设置 Accept、Content-Type 和 X-Request-ID。
  4. 用 --resolve 把一个 HTTPS 域名临时指向指定 IP，观察与直接访问 IP 的区别。
  5. 写一个 Bash 函数封装健康检查：有超时、有失败退出码、有状态码输出、不会泄露 token。
