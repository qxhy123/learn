qperf 深度教程：AI Infra 网络延迟、带宽与 RDMA 排障

这份教程围绕 Linux 命令 qperf 展开，面向 GPU 训练集群、RoCE/InfiniBand 网络、存储网络和推理服务排障。它不是单纯罗列测试名，而是从“一个节点常驻 server，另一个节点按测试项发起 client，分别测 TCP/UDP/RDMA 的 latency 与 bandwidth”这个心智模型出发，系统讲清 server/client 工作流、tcp_lat/tcp_bw、udp_lat/udp_bw、RDMA RC/UD 测试、结果解读、CPU/NUMA caveat、分布式训练网络 triage，以及 qperf 与 iperf3、ib_write_bw 的边界。

AI InfraLatencyBandwidthTCP/UDPRDMAServer/ClientNUMANCCL 排障生产安全
一句话理解： qperf 是主机间性能探针：server 端等待，client 端指定一个或多个测试项，用相同工具同时观察“延迟”和“带宽”，尤其适合在 IP 网络与 RDMA 网络之间做快速分层定位。
最重要原则： 在共享 AI 集群里先短测、低并发、明确接口和维护窗口；RDMA 测试要确认 HCA、端口、GID/路由和 PFC/ECN 配置，避免把 qperf 输出误读成 NCCL 或 GPUDirect RDMA 的最终结论。

1. qperf 是什么

qperf 用于在两台主机之间测量网络延迟和带宽。它最常见的使用方式是：目标节点运行 qperf 作为 server，发起节点运行 qperf <server> <test> ... 作为 client。与只关注吞吐的工具相比，qperf 的优势是延迟测试很方便，并且许多发行版构建会同时支持 TCP、UDP 和 RDMA 相关测试。

它擅长什么
快速比较节点间 tcp_lat、tcp_bw、udp_lat、udp_bw、RDMA RC/UD 相关 latency/bandwidth，适合网络验收和故障切片。
它不擅长什么
不能直接代表 NCCL collective、真实训练 step time、存储协议、RPC 框架或 GPU Direct RDMA 的完整路径。
它的本质
一个可重复的两端实验：固定节点、接口、协议、测试项、时长、CPU/NUMA 条件，再把结果与硬件和应用现象对照。
# node-b：启动 qperf server，默认监听 19765
qperf

# node-a：测 TCP 带宽和延迟
qperf node-b tcp_bw tcp_lat

# 常见 RDMA 快速探针，实际可用测试项取决于构建和硬件
qperf node-b rc_bw rc_lat
qperf node-b rc_rdma_write_bw rc_rdma_write_lat
边界提醒： qperf 结果只对当前参数和路径成立。尤其在多网卡、多路由、多 NUMA、多租户训练集群里，必须写清源/目的 IP、接口、HCA、端口、测试时长和当时负载。

信息图：qperf 的整体心智模型

qperf 是“指定测试项的两端探针”。没有测试项、接口、方向和设备上下文，单个数字没有排障价值。

2. 安装与环境确认

qperf 常见于 RHEL/Rocky/Alma/CentOS、Ubuntu/Debian 的软件仓库，RDMA 测试还依赖 rdma-core、HCA 驱动、内核模块、端口状态和网络配置。AI 集群中先确认你测的是训练网、存储网还是管理网。

# Debian / Ubuntu
sudo apt-get update
sudo apt-get install -y qperf rdma-core

# RHEL / Rocky / Alma / CentOS
sudo dnf install -y qperf rdma-core

# 确认版本、路径和帮助
command -v qperf
qperf --help

# 确认 IP 路由会走哪张网卡
ip route get 10.10.20.12
ip -br addr
ip -br link

# RDMA 环境检查，命令是否存在取决于系统包
rdma link
ibv_devices
ibv_devinfo -v
检查项为什么重要常见误判
qperf 版本与构建不同发行版编译的测试项和输出格式可能不同脚本在一组节点可用，另一组节点没有 RDMA 测试项
IP 路由TCP/UDP 测试走 Linux IP 栈误测 1/10Gb 管理网，却拿来判断训练网
RDMA 设备RC/UD/RDMA 测试依赖 verbs 设备和端口状态IP 网络正常，但 RDMA port down 或 GID 不对
防火墙server 默认监听 19765client 超时，误以为链路性能差
容器提示： 容器内 qperf 可能测的是 Pod 网络或受限 RDMA device plugin 暴露的设备。结论要标注 hostNetwork、CNI、veth/overlay、RDMA device plugin 和安全上下文。

3. 第一组 TCP 测试

TCP 是最容易开始的切片：它不要求 RDMA 正常，能快速回答“这两个节点的 IP 数据面是否健康”。建议先测 tcp_lat 和 tcp_bw，再做方向互换和接口绑定。

# node-b：启动 server，默认监听 19765
qperf

# node-a：一次执行两个测试项
qperf node-b tcp_lat tcp_bw

# 指定测试时长，减少短测波动
qperf -t 60 node-b tcp_lat tcp_bw

# 如果主机名可能解析到管理网，直接用训练网 IP
qperf -t 60 10.10.20.12 tcp_lat tcp_bw
先通后快
先确认 server 端口可达，再讨论带宽是否接近 25G/100G/200G/400G 预期。
延迟和带宽分开看
低延迟不代表高带宽，高带宽也不代表 tail latency 稳定。
双方向都测
A 到 B 正常，不代表 B 到 A 正常；路由、ACL、QoS、CPU 和队列都可能方向不对称。
生产警告： tcp_bw 会生成真实网络压力。共享训练网中先约定窗口、节点、接口和持续时间，避免影响正在运行的 NCCL 作业、checkpoint 或在线推理流量。

4. 读懂 latency 与 bandwidth

qperf 的输出会按测试项列出指标。常见单位包括 microseconds、MB/sec、Gb/sec 等，具体取决于版本、测试项和参数。不要只看数值大小，要同时看方向、链路速率、消息大小、CPU 负载和是否有异常错误。

# 示例输出形态，具体字段会随版本和参数变化
tcp_lat:
    latency  =  38.2 us
tcp_bw:
    bw       =  11.3 GB/sec

# 使用更详细输出，便于看到测试参数
qperf -v -t 60 node-b tcp_lat tcp_bw
指标含义AI Infra 解读
latency一次往返或操作的延迟度量，具体由测试项定义对 RPC、参数同步控制面、metadata、tail latency 敏感场景很重要
bw测试项在给定参数下测得的吞吐与端口速率、PCIe、NUMA、CPU、交换机和链路聚合预期对比
单位qperf 可用不同单位输出GB/sec 与 Gb/sec 差 8 倍，写报告时必须统一
测试时长短测可能被慢启动、缓存、瞬时调度影响基线建议 30 到 120 秒，故障复现可更长
判断原则： 延迟异常先怀疑路径、CPU 调度、C-state、IRQ、NUMA、拥塞和交换机队列；带宽异常还要加查 MTU、链路速率、PFC/ECN、HCA counters 和应用是否单流受限。

5. 常用参数与输出单位

qperf 的参数因版本略有差异，但下面这些在常见发行版中很常用。生产脚本要先用 qperf --help 在目标节点确认可用性，再固定参数。

参数用途例子
-t设置每个测试项运行时间qperf -t 60 node-b tcp_bw
-v详细输出，显示更多测试参数qperf -v node-b tcp_lat
-ub以 bits/sec 体系输出带宽，便于和网卡速率对齐qperf -ub node-b tcp_bw
-i指定 RDMA 设备和端口，常见形式为 Device:Portqperf -i mlx5_0:1 node-b rc_bw
-m设置或限制消息大小，适合做 message size sweepqperf -m 1M node-b tcp_bw
-oo向测试项传递选项，具体支持依赖测试项qperf -oo msg_size:64K node-b tcp_bw
# 用 bit/s 单位输出，更适合和 100G/200G/400G 端口对比
qperf -ub -t 60 node-b tcp_bw

# 详细输出，记录测试参数
qperf -v -ub -t 60 node-b tcp_lat tcp_bw

# RDMA 设备绑定示例
qperf -i mlx5_0:1 -ub -t 60 node-b rc_bw rc_lat
兼容提醒： qperf 版本和发行版补丁会影响参数和测试项。自动化前要在每类节点上执行 qperf --help 和一组 smoke test，不要假设所有镜像完全一致。

流程图：从 TCP 到 UDP/RDMA 的测试推进

不要一上来就跑复杂 RDMA 测试。先用 TCP 排除基础 IP 路径，再按问题进入 UDP/RDMA/NCCL 层。

6. UDP 测试与丢包风险

UDP 测试适合观察无连接路径、丢包倾向和小包延迟，但它不像 TCP 那样有拥塞控制。高码率 UDP 在共享网络上很容易造成队列拥塞和业务抖动，所以必须从短测和小流量开始。

# 基础 UDP latency 和 bandwidth
qperf -t 30 node-b udp_lat udp_bw

# 详细输出，记录消息大小等参数
qperf -v -t 30 node-b udp_lat udp_bw

# 如果需要逐步扫消息大小，先确认当前 qperf 支持的选项写法
qperf -v -m 64K -t 30 node-b udp_bw
观察点可能含义下一步
UDP latency 抖动大调度噪声、队列拥塞、CPU C-state、交换机 buffer 或跨 NUMA同步看 mpstat、sar -n DEV、交换机 counters
UDP bandwidth 明显低限速、丢包、MTU、socket buffer 或 CPU 限制降低消息大小/码率，检查 drops/errors
TCP 正常，UDP 异常队列策略、ACL/QoS 或无拥塞控制下路径不稳检查 QoS、PFC/ECN、端口 buffer 和策略
UDP 安全警告： 在生产 RoCE 网络上，高速 UDP 压测可能触发丢包、PFC pause 或交换机队列异常。没有维护窗口时，不要直接把 UDP 测试推到端口线速。

7. RDMA 测试模式

qperf 的 RDMA 能力取决于系统是否有 verbs 支持、HCA 是否可见、端口是否 active，以及 qperf 包是否启用了对应测试。常见测试名包括可靠连接 RC、非可靠数据报 UD，以及 RDMA read/write/send 相关延迟和带宽测试。

测试项大致层面适合回答的问题
rc_lat / rc_bwReliable Connected Queue PairRC send/receive 路径是否健康，延迟/带宽是否符合预期
ud_lat / ud_bwUnreliable DatagramUD 路径可用性、小包和无连接模式行为
rc_rdma_write_lat / rc_rdma_write_bwRDMA write写数据面是否健康，常用于和 ib_write_bw 对照
rc_rdma_read_lat / rc_rdma_read_bwRDMA read读数据面是否健康，可能受平台和 HCA 行为影响
xrc_* 或其他扩展项依赖构建只有目标版本明确支持时再纳入基线
# node-b：server
qperf

# node-a：RC 基础测试
qperf -i mlx5_0:1 -t 60 node-b rc_lat rc_bw

# RDMA write/read 测试
qperf -i mlx5_0:1 -t 60 node-b rc_rdma_write_lat rc_rdma_write_bw
qperf -i mlx5_0:1 -t 60 node-b rc_rdma_read_lat rc_rdma_read_bw

# 先查当前构建支持哪些测试项
qperf --help | less
RDMA 解释边界： qperf 的 RDMA 测试走 verbs 数据面，但它不等同于 NCCL 实际算法，也不覆盖 GPU 内存、PCIe 拓扑、CUDA 注册缓存、NCCL plugin 和多 rank collective 行为。

8. 绑定 RDMA 设备与端口

AI 节点常有多张 HCA、多端口、多 GID、多网络平面。RDMA 测试如果没有显式绑定设备和端口，可能测到错误的 HCA 或错误网络。qperf 常用 -i Device:Port 指定本地 RDMA 设备端口。

# 查看 RDMA link 与 netdev 对应关系
rdma link
ibv_devices
ibv_devinfo -v

# 找到网卡对应的 PCI 和 NUMA
readlink /sys/class/net/ens5f0/device
cat /sys/class/net/ens5f0/device/numa_node

# 指定 mlx5_0 的 1 号端口测试
qperf -i mlx5_0:1 -v -t 60 node-b rc_lat rc_bw

# 如果同一主机有多张 HCA，分别测试并记录
qperf -i mlx5_0:1 -ub -t 60 node-b rc_bw
qperf -i mlx5_1:1 -ub -t 60 node-b rc_bw
要记录原因
HCA 名称与端口mlx5_0:1 和 mlx5_1:1 可能接到不同交换平面
对应 netdevRoCE 场景下 IP、GID、VLAN、MTU 和 netdev 配置相关
NUMA 节点HCA 与 CPU/GPU 跨 NUMA 会拉高延迟并降低稳定性
端口状态active/down、速率、宽度、link layer 都会影响结果
实践建议： 在验收报告里不要写“RDMA qperf 正常”，而要写“mlx5_0:1 到 mlx5_0:1，rc_rdma_write_bw，60s，bit/s 单位，端口 active，MTU/GID 已确认”。

9. AI Infra 基线矩阵

AI Infra 的网络基线要覆盖同机架、跨机架、同交换平面、跨交换平面、东西向通信和存储访问路径。不要只测一对节点后推断整个集群。

场景建议 qperf 测试重点指标
GPU 节点同机架tcp_lat tcp_bw rc_lat rc_bw低延迟、接近线速、方向一致
GPU 节点跨机架同机架基线加跨交换域矩阵是否存在 spine/leaf 瓶颈或 ECMP 不均
RoCE 验收rc_rdma_write_bw、rc_rdma_read_bw、端口 countersPFC/ECN、丢包、GID、MTU、HCA 错误
存储网络tcp_bw 多对一/一对多，必要时 tcp_lat聚合吞吐、接收端 CPU、交换机拥塞
NCCL fallback绑定 NCCL socket 接口测 tcp_lat tcp_bwTCP 路径是否健康，接口是否选对
# 示例：最小单对节点基线
qperf -v -ub -t 60 10.10.20.12 tcp_lat tcp_bw
qperf -v -ub -t 60 -i mlx5_0:1 10.10.20.12 rc_lat rc_bw
qperf -v -ub -t 60 -i mlx5_0:1 10.10.20.12 rc_rdma_write_lat rc_rdma_write_bw

# 方向互换：到 node-b 上对 node-a 再跑同一组命令
qperf -v -ub -t 60 10.10.20.11 tcp_lat tcp_bw
趋势优先： 单次 qperf 结果只能说明当时状态。更有价值的是同一拓扑、同一参数、同一时间窗口下的历史趋势和离群点。

10. 解释延迟：平均值、尾部与噪声

qperf 的 latency 是重要信号，但不能直接等同于真实业务的 p99/p999。训练框架、RPC、存储客户端、NCCL 和内核调度都有自己的批处理、队列、消息大小和并发行为。qperf latency 更适合做“路径是否异常”的探针。

低平均延迟
说明测试条件下路径短且轻载，但不证明高负载下 tail latency 稳定。
偶发高延迟
可能来自 CPU 调度、软中断、C-state、NUMA 远端访问、交换机拥塞、PFC pause 或后台作业。
RDMA latency 异常
重点看 HCA counters、端口状态、GID、PFC/ECN、NUMA 和 PCIe 拓扑。
TCP latency 异常
重点看路由、队列、iptables/eBPF、CPU、socket buffer、MTU 和中间设备。
# 延迟测试时同步观察系统噪声
qperf -v -t 120 node-b tcp_lat
mpstat -P ALL 1
pidstat -wt 1
sar -n DEV,TCP,ETCP 1

# RDMA 场景同步看 counters
rdma statistic
ethtool -S ens5f0 | egrep -i 'err|drop|timeout|discard|pause|pfc|ecn|crc'
报告提醒： 如果业务抱怨 p99 慢，不要只贴 qperf 平均 latency。应补充业务侧分位数、并发度、消息大小、CPU 负载和网络 counters。

11. CPU、NUMA 与中断 caveat

高速网络测试常被主机侧限制，而不是被线缆或交换机限制。AI 节点的 GPU 训练、数据加载、压缩、日志、监控 agent、容器 runtime 都可能和 qperf 抢 CPU、内存带宽或 PCIe 路径。

现象可能原因验证方式
带宽上不去，单核很高单线程/软中断/协议栈 CPU 限制mpstat -P ALL 1、pidstat -t
延迟偶发尖刺调度、C-state、IRQ 迁移、后台任务cyclictest、perf top、CPU 频率状态
RDMA 带宽低但端口无错NUMA 错位、PCIe 限制、内存带宽瓶颈lstopo、numactl -H、PCIe link status
多队列不均RSS/IRQ affinity/哈希不均/proc/interrupts、ethtool -l/-x
# 找 HCA / NIC 所在 NUMA
cat /sys/class/infiniband/mlx5_0/device/numa_node
cat /sys/class/net/ens5f0/device/numa_node

# 查看中断是否集中在少数 CPU
grep -i mlx5 /proc/interrupts

# 测试时同步观察
mpstat -P ALL 1
sar -n DEV,EDEV,TCP,ETCP 1
numactl -H
经验判断： 如果 qperf 测试期间 CPU、软中断或内存带宽已经饱和，先不要调整交换机。主机侧瓶颈会让健康链路看起来像坏链路。

三角图：分布式训练网络 triage

qperf 是训练网络 triage 的一层证据。最终仍要用 NCCL tests、业务日志、GPU/PCIe/NUMA 拓扑和交换机 counters 交叉验证。

12. 分布式训练网络 triage

当训练 step time 变慢、NCCL timeout、all-reduce 性能下降或 checkpoint 抖动时，qperf 可用来快速判断是 IP 层、RDMA 层还是应用/NCCL 层继续深入。

# 1. 确认应用可能使用的接口
ip -br addr
ip route get 10.10.20.12

# 2. IP 层切片
qperf -v -ub -t 60 10.10.20.12 tcp_lat tcp_bw

# 3. RDMA 层切片
qperf -v -ub -t 60 -i mlx5_0:1 10.10.20.12 rc_lat rc_bw
qperf -v -ub -t 60 -i mlx5_0:1 10.10.20.12 rc_rdma_write_lat rc_rdma_write_bw

# 4. NCCL 对照，确认接口选择和插件行为
NCCL_DEBUG=INFO NCCL_SOCKET_IFNAME=ens5f0 ./build/all_reduce_perf -b 8M -e 4G -f 2 -g 8
NCCL_DEBUG=INFO NCCL_IB_HCA=mlx5_0 ./build/all_reduce_perf -b 8M -e 4G -f 2 -g 8
组合结果解释倾向下一步
TCP qperf 慢，RDMA qperf 也慢主机路径、物理链路、交换机拥塞、MTU 或 CPU 基础问题先修基础网络和主机 counters
TCP 正常，RDMA 慢HCA、GID、PFC/ECN、RoCE、verbs 或 RDMA 端口问题用 perftest、RDMA counters、交换机 counters 深挖
TCP/RDMA 都正常，NCCL 慢NCCL 配置、GPU 拓扑、PCIe、算法、消息大小或 rank 映射看 NCCL log、nvidia-smi topo -m、rank placement
只有跨机架慢spine/leaf、ECMP、QoS 或 oversubscription做矩阵测试并对齐交换机端口利用率
NCCL 提醒： 临时设置 NCCL_IB_DISABLE=1 或 NCCL_SOCKET_IFNAME 只适合定位，不应作为长期性能修复。长期方案要修正确的网络和拓扑。

对比图：qperf、iperf3、ib_write_bw 的边界

qperf 的价值在于横跨 latency/bandwidth 和 TCP/UDP/RDMA，但最终定位仍要使用对应层的专用证据。

13. qperf vs iperf3 vs ib_write_bw

AI Infra 排障最怕“一个工具证明所有层”。正确做法是按网络栈分层：IP 层、RDMA verbs 层、NCCL collective 层、应用层分别验证。

工具测量层面优势局限适合问题
qperfTCP/UDP/RDMA 多测试项同一工具测 latency 和 bandwidth，适合快速分层输出和测试项依赖构建，不如 iperf3 JSON 友好tcp_lat/tcp_bw、rc_lat/rc_bw、RDMA 快速切片
iperf3IP/TCP/UDP/SCTP带宽测试成熟，支持并发流、反向、JSON不直接测 RDMA verbsIP 带宽基线、重传、方向差异、自动化巡检
ib_write_bwRDMA verbs接近 HCA/RDMA 数据面，RoCE/IB 验收常用不代表 TCP 应用，也不代表 NCCL collectiveHCA、GID、PFC/ECN、RDMA 带宽
nccl-testsNCCL collective最接近训练通信模式受 GPU、rank、拓扑、算法、消息大小影响最终确认 all-reduce/all-gather 性能
# qperf：延迟 + 带宽快速切片
qperf -v -ub -t 60 node-b tcp_lat tcp_bw rc_lat rc_bw

# iperf3：IP TCP 带宽、并发流和反向
iperf3 -c node-b -t 60 -O 3 -P 8
iperf3 -c node-b -t 60 -O 3 -P 8 -R

# ib_write_bw：RDMA write 带宽，参数需按 HCA/GID 环境调整
ib_write_bw -d mlx5_0 -F

# NCCL tests：最终 collective 对照
./build/all_reduce_perf -b 8M -e 4G -f 2 -g 8
分层结论： qperf TCP 正常说明 IP 切片健康；qperf RDMA 正常说明 verbs 切片健康；只有 nccl-tests 和真实业务才能证明训练通信路径符合目标。

14. 自动化采集与命名规范

qperf 没有 iperf3 那样统一好用的 JSON 输出习惯，因此自动化时更要保存完整 stdout、命令、版本和环境元数据。对比趋势时，参数必须严格一致。

# server 端建议由调度或 systemd 控制，避免长期遗留
qperf

# client 端保存输出和上下文
ts=$(date +%Y%m%d-%H%M%S)
src=$(hostname -s)
dst=node-b
{
  echo "timestamp=${ts}"
  echo "src=${src}"
  echo "dst=${dst}"
  echo "cmd=qperf -v -ub -t 60 ${dst} tcp_lat tcp_bw"
  qperf --help | sed -n '1,20p'
  qperf -v -ub -t 60 "${dst}" tcp_lat tcp_bw
} > "qperf-${src}-to-${dst}-tcp-${ts}.log"

# RDMA 输出单独命名，记录 HCA
qperf -v -ub -t 60 -i mlx5_0:1 "${dst}" rc_lat rc_bw \
  > "qperf-${src}-to-${dst}-mlx5_0p1-rc-${ts}.log"
字段建议记录
节点与拓扑源/目的主机、机架、交换域、源/目的 IP、接口名
命令完整 qperf 命令、测试项、时长、单位、消息大小、设备端口
环境是否有训练作业、存储流量、CPU 负载、维护窗口
网络MTU、端口速率、RoCE/IB、GID、PFC/ECN 策略
结果latency、bw、错误信息、主机 counters、交换机 counters 链接
自动化建议： 把“验收基线”和“故障临时实验”分开存档。临时调大 message size 或换 HCA 的结果不要混入长期趋势。

15. 安全边界与生产演练

qperf 不会修改文件，但会制造真实网络负载，也可能打开监听端口。共享 AI 集群中的训练网、存储网和推理服务网络经常相互影响，因此测试需要最小化、可追踪、可清理。

测试前
确认窗口、节点、端口、接口、协议、测试项、时长、HCA、预期上限和告警观察人。
测试中
先 tcp_lat 和短时 tcp_bw，再扩展到 RDMA 和更长时长；同步看 CPU、网卡和交换机。
测试后
停止 server，保存命令与输出，记录是否影响业务，归档异常 counters。
共享环境
优先使用隔离节点、低峰期或维护窗口；RDMA/RoCE 压测前确认 PFC/ECN 和交换机 buffer 策略。
# 查是否已有 qperf server
pgrep -a qperf
ss -ltnp | grep 19765

# 如需终止自己启动的 server，先确认命令行和 PID
pgrep -a qperf
kill <pid>

# 测试前后保存 counters 快照
ethtool -S ens5f0 > ethtool-before.txt
qperf -v -ub -t 60 node-b tcp_bw
ethtool -S ens5f0 > ethtool-after.txt
diff -u ethtool-before.txt ethtool-after.txt | sed -n '1,120p'
清理提醒： 不要盲目 pkill qperf。在多人环境里，先用 pgrep -a 和端口确认进程归属，避免中断他人的验收或排障。

17. 练习任务与学习路线

学习 qperf 的目标不是背测试项，而是形成“可复现、可分层、能和业务现象对齐”的网络诊断习惯。下面练习可以在测试集群或维护窗口完成。

  1. 在两台节点上分别运行 qperf node-b tcp_lat tcp_bw 和反方向测试，记录方向差异。
  2. 把输出单位统一为 bit/s，比较 qperf -ub tcp_bw 与 iperf3 -P 8 的差异。
  3. 在同一对节点上测试 tcp_lat、rc_lat、rc_rdma_write_lat，解释三者不是同一层延迟。
  4. 用 rdma link、ibv_devinfo 和 qperf -i mlx5_0:1 绑定 HCA，确认没有误测其他端口。
  5. 人为选择同机架、跨机架两组节点，建立最小延迟/带宽矩阵。
  6. 在 qperf 运行期间同步采集 mpstat、sar、ethtool -S，练习把性能数字和 counters 关联。
  7. 当 NCCL tests 慢时，按 TCP qperf、RDMA qperf、ib_write_bw、all_reduce_perf 的顺序写一份分层诊断报告。
学习路线： 先掌握 server/client 和 tcp_lat tcp_bw，再加 UDP 风险意识，然后学习 RDMA 设备绑定，最后把 qperf 放进 NCCL/存储/推理的完整 triage 流程。
