nm 深度教程：AI Infra 中的符号表、ABI 与链接排障

这份教程面向 AI Infra、GPU 平台和机器学习系统工程中的 nm 使用场景。它不会只罗列选项，而是从“目标文件、静态库、共享库里到底暴露了哪些符号”这个核心问题出发，讲清楚：定义/未定义符号、符号类型字母、C++ 名字修饰与 -C 反混淆、CUDA/C++ 扩展符号冲突、静态库归档、动态库导出、ABI 线索、与 readelf/objdump/ldd 的边界，以及生产排障流程。

AI Infra符号表Undefined SymbolsDemangle -CCUDA ExtensionC++ ABIStatic/Shared LibsPyTorch 扩展链接排障
一句话理解： nm 是“看符号账本”的工具：它告诉你一个 .o、.a、.so 或可执行文件里，哪些函数/变量被定义了，哪些还在等待链接器或动态加载器去解析。
最重要原则： 看到 undefined symbol 不要先猜环境变量；先用 nm -C 确认“谁需要这个符号、谁提供这个符号、名字和 ABI 是否完全一致”，再检查链接顺序、库版本和加载路径。

1. nm 是什么，为什么 AI Infra 常用

nm 读取二进制对象中的符号表，并输出函数、全局变量、弱符号、未定义引用、调试符号等信息。对 AI Infra 来说，它最常用于定位 C++/CUDA/PyTorch 扩展在编译、链接和运行时加载阶段出现的符号问题。

编译阶段
检查 .o 是否真的编出了某个 kernel wrapper、C API 或 C++ 函数。
链接阶段
定位 undefined reference、重复定义、静态库顺序错误和漏链依赖库。
运行时加载
排查 Python import 扩展时报 undefined symbol、ABI 不匹配、加载了错误版本 .so。
# 查看一个目标文件定义了什么
nm -C build/attention.o | less

# 只看未解析引用
nm -C -u build/my_extension.o

# 检查共享库的动态导出符号
nm -D -C build/libflash_attn_ext.so | grep 'flash_attn'

# 检查静态库里哪个成员提供了符号
nm -A -C build/libkernels.a | grep 'fused_layer_norm'
边界提醒： nm 不是性能分析器，也不告诉你库是否会被动态加载器实际找到。它回答的是“符号表里有什么”；加载路径和依赖解析还要结合 ldd、readelf -d、LD_DEBUG=libs。

信息图：nm 在编译/链接/加载链路中的位置

在 AI Infra 中，nm 常用于“从报错反推二进制事实”：符号是否存在、在哪个文件、以什么名字存在、是否被导出。

2. 安装、版本与输入对象

nm 通常来自 GNU binutils；macOS 也有同名工具但输出和选项存在差异。Linux AI 训练/推理环境中，排查 ELF 二进制时通常使用 GNU nm。交叉编译或嵌入式环境会有架构前缀，例如 aarch64-linux-gnu-nm。

输入对象是否适合 nmAI Infra 例子
.o很适合单个 C++/CUDA 编译单元：attention.o、binding.o
.a很适合静态 kernel 库：libcutlass_kernels.a
.so适合，常配 -DPython 扩展：my_op.cpython-311-x86_64-linux-gnu.so
可执行文件适合推理服务二进制、benchmark 程序
被 strip 的文件部分适合普通符号表可能消失，但动态符号表可能仍可用
# 确认工具来源
which nm
nm --version

# 判断文件类型
file build/my_extension.so
readelf -h build/my_extension.so | sed -n '1,12p'

# 交叉编译产物用匹配架构的 nm
aarch64-linux-gnu-nm -C build/libedge_infer.a | head
实用判断： 如果 nm libx.so 输出很少或提示 no symbols，不要立刻认为库没有导出；先试 nm -D libx.so 查看动态符号表。

3. 基本语法与常用选项

nm [options] file...

# 最常用组合
nm -C file.o                 # C++ 符号反混淆
nm -C -u file.o              # 只看未定义符号
nm -C --defined-only file.o  # 只看已定义符号
nm -D -C libx.so             # 查看共享库动态符号表
nm -A -C libx.a              # 每行带文件名/归档成员名
nm -S -C --size-sort file.o  # 显示大小并按大小排序
选项含义什么时候用
-C / --demangle把 C++ 修饰名还原成人类可读签名几乎所有 C++/CUDA/PyTorch 扩展排障都应使用
-u / --undefined-only只显示未定义符号定位缺少哪个库或对象
--defined-only只显示当前文件定义的符号确认库是否提供目标函数
-D / --dynamic显示动态符号表而不是普通符号表检查 .so 对运行时可见的导入/导出
-A / --print-file-name输出来源文件名查多个对象或静态库成员时必须用
-S / --print-size显示符号大小粗略查看大函数/大对象或重复膨胀
--size-sort按大小排序观察 C++ 模板实例化膨胀
-g / --extern-only只显示外部符号忽略局部实现细节，关注链接边界
推荐默认命令： 查 C++/CUDA 问题时先用 nm -A -C；查 .so 的运行时导入导出时用 nm -D -A -C。

4. 输出列与符号类型字母

nm 的典型输出是“地址、类型、符号名”。未定义符号没有地址，常见类型是 U。大写通常代表全局/外部可见，小写通常代表局部符号；具体含义会受目标格式和平台影响。

00000000000012b0 T launch_attention(at::Tensor, at::Tensor)
                 U at::Tensor::data_ptr() const
0000000000004060 B global_workspace
0000000000002030 R kernel_name
0000000000001170 t helper_local(float*)
0000000000000000 W c10::Error::what() const
类型常见含义排障解读
T/t代码段 text 中的函数T 表示库定义了可链接函数；t 常是局部 helper
U未定义符号当前文件需要别人提供；链接或加载失败时优先看它
B/bBSS，未初始化数据全局 buffer、workspace、静态变量可能在这里
D/d已初始化数据全局配置、注册表、非 const 全局对象
R/r只读数据字符串、常量表、kernel name
W/w弱符号可被强符号覆盖；模板、运行库兼容层里常见
V/v弱对象符号C++ ABI、全局对象兼容场景可能出现
i间接函数或平台相关符号通常需要结合 readelf 判断
不要过度解读地址： 对可重定位 .o 来说，地址通常只是段内偏移；最终运行地址由链接器和加载器决定。

流程图：定义、未定义与链接解析

U 不一定是错误：对象文件和共享库可以包含未定义符号。错误发生在链接器或运行时加载器需要解析它却找不到兼容提供者时。

5. 定义符号、未定义符号与重复定义

AI Infra 的链接问题常可以归结为三类：缺定义、定义太多、定义存在但名字不一样。nm 的工作是把这三类问题从猜测变成可见事实。

缺定义
某个对象里有 U foo，但参与链接的对象和库里没有 T foo、W foo 或相关数据符号。
重复定义
多个对象都定义同一个强符号，例如头文件里错误放了非 inline 函数实现。
名字不一致
C++ 参数、命名空间、extern "C"、宏开关或 ABI 配置不同，导致符号名不匹配。
# 谁需要这个符号？
nm -A -C build/*.o | grep ' U .*launch_fused_attention'

# 谁提供这个符号？
nm -A -C --defined-only build/*.o build/*.a | grep 'launch_fused_attention'

# 只看一个库是否存在重复强定义
nm -A -C --defined-only build/*.o | awk '$2 ~ /^[TDBR]$/ {print $3}' | sort | uniq -d

# 查看所有同名定义来源
nm -A -C --defined-only build/*.o | grep ' fused_layer_norm('
重复定义警告： 不要靠随便删除对象文件“修好”链接。先定位为何多个编译单元定义同一强符号，再改为 inline、static、匿名命名空间，或移动实现到唯一 .cc/.cu。

6. C++ 名字修饰与 demangle -C

C++ 支持函数重载、命名空间、模板和类方法，链接器不能只用 foo 这样的短名字。因此编译器会把人类可读签名编码成修饰名，例如 _ZN2at6Tensor8data_ptrEv。nm -C 会把它反混淆成更接近源码的签名。

不加 -C加 -C 后价值
_ZN2at6Tensor8data_ptrIfEEPT_vfloat* at::Tensor::data_ptr<float>()看清模板参数和命名空间
_ZN3c105ErrorC1ENS_14SourceLocationESsc10::Error::Error(c10::SourceLocation, std::string)判断 PyTorch/C++ ABI 相关签名
_Z20launch_fused_softmaxPN2at6TensorES1_launch_fused_softmax(at::Tensor*, at::Tensor*)确认参数是否与声明一致
# 对比原始修饰名与反混淆结果
nm build/my_extension.o | grep '_ZN2at6Tensor'
nm -C build/my_extension.o | grep 'at::Tensor'

# c++filt 可单独反混淆一行符号
echo '_ZN2at6Tensor8data_ptrIfEEPT_v' | c++filt

# 排查 extern "C" 是否生效：C API 通常不应出现 C++ 修饰名
nm -D build/libplugin.so | grep 'create_plugin'
AI Infra 经验： 如果 Python 扩展报的 undefined symbol 是一串 _ZN...，第一步就是用 c++filt 或 nm -C 看它到底对应哪个 C++ 函数。

用例图：CUDA/C++ 扩展符号冲突怎么定位

CUDA kernel 名本身不一定出现在动态符号表中；更常排查的是 host wrapper、注册函数、PyTorch/C10/ATen 相关 C++ 符号和运行库符号。

7. CUDA/C++ 扩展排障

PyTorch、TensorFlow、自研 runtime 插件或 Triton/CUDA 混合扩展失败时，报错常来自 Python 的 import、ctypes.CDLL、dlopen 或推理服务加载插件。nm 能把“库版本可能不对”拆成可验证问题。

典型错误 1：Python import 报 undefined symbol

# 例：导入扩展失败时，先把符号反混淆
python -c 'import my_ext' 2>&1 | tee /tmp/import.err
grep -o '_Z[^ ]*' /tmp/import.err | c++filt

# 这个扩展到底缺什么？
nm -D -C -u build/my_ext*.so | sort | less

# 相关依赖库是否导出了它？
nm -D -C "$(python - <<'PY'
import torch, os
print(os.path.join(os.path.dirname(torch.__file__), "lib", "libtorch_cpu.so"))
PY
)" | grep '目标符号的一部分'

典型错误 2：C++ wrapper 没有被导出

# 检查 Python 扩展是否有 pybind11 初始化符号
nm -D build/my_ext*.so | grep 'PyInit_'

# 检查自研 C API 是否是未修饰的 C 符号
nm -D build/libmy_plugin.so | grep -E 'create_plugin|destroy_plugin'

# 如果看到 _Z...create_plugin...，可能忘了 extern "C"
c++filt _Z13create_pluginv

典型错误 3：CUDA runtime 或 driver API 漏链

# 对象中有 U cudaLaunchKernel，最终 .so 也还缺它
nm -C -u build/kernel.o | grep cuda
nm -D -C -u build/my_ext.so | grep cuda

# 再看动态依赖是否包含 libcudart
readelf -d build/my_ext.so | grep NEEDED
ldd build/my_ext.so | grep -E 'cuda|cudart|torch'
CUDA 注意： nm 主要看 host 侧 ELF 符号；device 侧代码、fatbin、PTX/SASS 细节要用 cuobjdump、nvdisasm 或 readelf -S 辅助判断。

8. 静态库 .a 与链接顺序

静态库本质上是一组 .o 的归档。链接器按命令行从左到右扫描静态库，只在当时需要某个符号时才从库里抽取成员。因此“库里明明有符号，链接却失败”经常是链接顺序问题。

# 查看静态库每个成员的符号，-A 会显示 lib.a(member.o)
nm -A -C build/libkernels.a | grep 'launch_fused_attention'

# 只看这个静态库对外提供什么
nm -A -C --defined-only build/libkernels.a | less

# 只看这个静态库仍然需要哪些外部符号
nm -A -C -u build/libkernels.a | sort -u

# 用 ar 看成员列表
ar t build/libkernels.a | sed -n '1,20p'
现象可能原因排查命令
undefined reference to launch_x-lkernels 放在使用者之前nm -A -C libkernels.a | grep launch_x
两个静态库循环依赖单次扫描无法解析检查双方 U 与 T
库有符号但签名不匹配C++ 重载、命名空间、ABI 宏不同nm -C 对比完整签名
重复定义多个成员包含同一强符号nm -A --defined-only lib.a | sort
# 链接顺序示意：使用者在前，提供者在后
g++ main.o binding.o -Lbuild -lkernels -lcudart -o demo

# 循环依赖可用 group，但不要滥用
g++ main.o -Wl,--start-group -lA -lB -Wl,--end-group -o demo
构建系统提示： CMake 中应优先用 target_link_libraries 表达目标依赖，而不是手写一长串全局 linker flags；否则静态库顺序问题很难维护。

9. 共享库 .so 与动态符号

共享库通常有普通符号表和动态符号表。普通符号表可能被 strip 删除；动态符号表用于动态链接和 dlopen 解析，通常保留。排查运行时加载问题时，应优先使用 nm -D。

# 查看动态导出和导入
nm -D -C build/libinference_plugin.so | less

# 只看动态未定义符号：这些需要运行时依赖库提供
nm -D -C -u build/libinference_plugin.so | sort

# 只看动态导出符号
nm -D -C --defined-only build/libinference_plugin.so | sort

# 对比普通符号表和动态符号表数量
nm -C build/libinference_plugin.so | wc -l
nm -D -C build/libinference_plugin.so | wc -l
问题nm 视角后续工具
库没有导出插件入口nm -D --defined-only 找不到 create_plugin检查 visibility、链接脚本、extern "C"
运行时缺 PyTorch 符号nm -D -u 有 at::/c10:: 未定义ldd、readelf -d、Python 环境路径
本机有多个同名库目标库符号存在但加载了别的库LD_DEBUG=libs、ldd、rpath
符号被隐藏普通表有，动态表没有-fvisibility、导出宏、版本脚本
生产警告： 不要为了“让符号出现”随意关闭所有 visibility 控制。AI 推理插件暴露过多 C++ 符号可能增加 ABI 冲突和 ODR 风险；只导出稳定入口更安全。

10. ABI 线索：GLIBCXX、CXXABI、PyTorch ABI

nm 能看到 C++ 符号的签名线索，但 ABI 问题通常还要结合版本符号、字符串和动态依赖。AI Infra 最常见的是编译器/libstdc++ 版本、_GLIBCXX_USE_CXX11_ABI、PyTorch 编译 ABI、CUDA runtime 版本不一致。

C++11 ABI 宏
同一个接口如果一边用旧 ABI，一边用新 ABI，涉及 std::string/std::list 等类型的符号可能不同。
libstdc++ 版本
扩展可能需要较新的 GLIBCXX_3.4.xx，但运行环境只提供旧版本，最终 import 失败。
PyTorch ABI
自定义 C++ 扩展应与安装的 PyTorch 使用相同编译器约束、C++ 标准库 ABI 和 CUDA 组合。
符号版本
nm 可显示部分带版本的动态符号，但版本需求常用 readelf --version-info 更清楚。
# 查看扩展引用的 C++ 标准库符号版本
strings build/my_ext.so | grep -E 'GLIBCXX_|CXXABI_' | sort -V | tail

# 查看动态符号中是否有 std::__cxx11 线索
nm -D -C build/my_ext.so | grep 'std::__cxx11' | head

# PyTorch 侧 ABI 配置
python - <<'PY'
import torch
print(torch.__version__)
print(torch._C._GLIBCXX_USE_CXX11_ABI)
print(torch.version.cuda)
PY

# 更完整的版本符号检查
readelf --version-info build/my_ext.so | grep -E 'GLIBCXX|CXXABI' | tail
ABI 判断不要只靠一个命令： nm -C 看到 std::__cxx11 是重要线索，但最终要结合 PyTorch ABI 配置、编译参数、运行环境 libstdc++.so.6 和版本符号确认。

11. nm vs readelf vs objdump vs ldd

这些工具经常一起出现，但职责不同。高效排障的关键是先问清楚问题属于“符号表内容”“ELF 元数据”“反汇编/重定位细节”还是“运行时加载路径”。

工具主要回答典型命令AI Infra 用法
nm符号定义、未定义、导出、大小nm -D -C -u libx.so查 undefined symbol、C++ 签名、静态库成员
readelfELF 头、段、节、动态依赖、版本符号readelf -d libx.so查 NEEDED、RPATH、RUNPATH、GLIBCXX 版本
objdump反汇编、重定位、符号表补充objdump -T -C libx.so看 PLT/GOT、版本化动态符号、指令级线索
ldd当前环境会解析到哪些共享库ldd libx.so查加载了哪个 libtorch/libcuda/libstdc++
c++filt单独反混淆 C++ 修饰名echo _ZN... | c++filt把报错中的 _Z... 变成人类可读签名
# 一套常用组合拳
nm -D -C -u build/my_ext.so | sort | sed -n '1,80p'
readelf -d build/my_ext.so | grep -E 'NEEDED|RPATH|RUNPATH'
ldd build/my_ext.so | grep -E 'torch|cuda|stdc\\+\\+|not found'
readelf --version-info build/my_ext.so | grep -E 'GLIBCXX|CXXABI' | tail
选择规则： 先用 nm 确认“符号事实”，再用 readelf/ldd 确认“加载事实”。不要用 ldd 代替符号检查，也不要用 nm 代替加载路径检查。

对比图：四类二进制排障问题该用什么工具

工具边界越清楚，排障越快：nm 看符号表，readelf 看 ELF 元数据，ldd 看当前运行环境解析结果。

12. AI Infra 常见场景清单

下面这些场景都适合先用 nm 建立事实，再决定是否修改构建脚本、环境变量或部署镜像。

PyTorch C++ extension import 失败
nm -D -C -u ext.so 找缺失 ATen/C10 符号；用 c++filt 反混淆报错符号。
TensorRT / 推理插件入口缺失
nm -D --defined-only plugin.so 检查 createInferRuntime_INTERNAL、自研 C API 或插件注册函数。
CUDA runtime 漏链
nm -D -u libx.so | grep cuda 和 readelf -d 联合检查 libcudart 依赖。
静态 kernel 库链接失败
nm -A -C libkernels.a 找归档成员，确认链接顺序和 group。
C++ ABI 与 PyTorch 不一致
nm -C 查 std::__cxx11，再核对 torch._C._GLIBCXX_USE_CXX11_ABI。
多版本库冲突
目标库符号存在但运行仍失败时，用 ldd/LD_DEBUG=libs 看实际加载路径。
# 快速巡检一个扩展的核心信息
so=build/my_ext.so
echo "== undefined dynamic symbols =="
nm -D -C -u "$so" | sort | sed -n '1,80p'
echo "== exported entrypoints =="
nm -D -C --defined-only "$so" | grep -E 'PyInit_|create_|register|launch' || true
echo "== dependencies =="
readelf -d "$so" | grep NEEDED

13. 生产安全与自动化脚本

nm 是只读工具，本身不会修改二进制。但自动化脚本仍要注意输出体积、路径歧义、C++ 符号中的空格、CI 日志泄露和误判。生产巡检建议输出稳定摘要，而不是把几十万行符号完整刷进日志。

安全巡检模板

#!/usr/bin/env bash
set -euo pipefail

so="${1:?usage: check-symbols.sh path/to/lib.so}"

echo "[file]"
file "$so"

echo "[missing dynamic deps]"
ldd "$so" | grep 'not found' && exit 1 || true

echo "[undefined dynamic symbols: first 100]"
nm -D -C -u "$so" | sort | sed -n '1,100p'

echo "[exported entrypoints]"
nm -D -C --defined-only "$so" | grep -E 'PyInit_|create_|destroy_|register' || true

echo "[version requirements]"
strings "$so" | grep -E 'GLIBCXX_|CXXABI_' | sort -V | tail -20 || true

CI 中检查入口符号

# 例：要求 Python 扩展导出 PyInit_my_ext
nm -D build/my_ext*.so | grep -q ' T PyInit_my_ext'

# 例：要求插件导出 C ABI 入口，避免 C++ 名字修饰
nm -D build/libplugin.so | grep -q ' T create_plugin'
if nm -D build/libplugin.so | grep -q '_Z.*create_plugin'; then
  echo "create_plugin appears to be C++ mangled; check extern C" >&2
  exit 1
fi
脚本注意： nm -C 后的 C++ 签名包含空格、逗号、尖括号和括号；不要用简单的 awk '{print $3}' 解析所有情况。需要机器解析时，尽量匹配原始修饰名或使用更明确的规则。

排障流程图：undefined symbol 到最终修复

排障不要跳步：先把报错符号翻译成人话，再证明需求方和提供方，最后才处理路径、版本和部署。

14. 排障流程与常见坑

推荐排障流程

  1. 从报错中提取原始符号，使用 c++filt 反混淆。
  2. 用 nm -D -C -u 确认出错 .so 是否确实需要该符号。
  3. 用 nm -D -C --defined-only 在候选依赖库中确认是否提供完全一致的签名。
  4. 如果提供方不存在，修构建依赖或链接顺序；如果存在但签名不同，查 ABI、宏、头文件版本和命名空间。
  5. 如果提供方存在且签名一致，查 readelf -d、ldd、RPATH/RUNPATH、容器镜像内库路径。
坑 1：忘记 -C
只看 _ZN... 很容易误判；C++ 问题默认加 -C。
坑 2：查 .so 忘记 -D
运行时可见性主要看动态符号表，不是普通符号表。
坑 3：把所有 U 当错误
共享库保留未定义动态符号很常见，只要运行时依赖能提供即可。
坑 4：只 grep 短名字
C++ 重载可能同名不同参；必须看完整签名。
坑 5：忽略 extern "C"
插件入口如果被 C++ 修饰，宿主按 C 名查找会失败。
坑 6：忽略 strip
被 strip 的库普通符号表可能没有，但动态符号表仍可检查。
坑 7：把链接期和加载期混在一起
undefined reference 是链接器；undefined symbol 常是动态加载器。
坑 8：路径里查到的是错库
本地有多个 libtorch/libstdc++ 时，必须看实际加载路径。
# 最小化排障模板
sym='_ZN2at6Tensor8data_ptrIfEEPT_v'
echo "$sym" | c++filt

so=build/my_ext.so
nm -D -C -u "$so" | grep 'data_ptr'

# 假设候选库是 libtorch_cpu.so
nm -D -C --defined-only /path/to/libtorch_cpu.so | grep 'data_ptr'
readelf -d "$so" | grep -E 'NEEDED|RPATH|RUNPATH'
ldd "$so" | grep -E 'torch|stdc\\+\\+|not found'

cat > math_ops.cc <<'CPP'
namespace ai {

extern "C" int c_add(int a, int b) { return add(a, b); }
}
CPP

g++ -c math_ops.cc -o math_ops.o
nm math_ops.o | grep add
nm -C math_ops.o | grep add

常用速查

目标命令
看 C++ 可读符号nm -C file.o
看未定义符号nm -C -u file.o

学习路线

  • 第一阶段：能读懂 U、T、W、D、B、R，知道 -C 和 -D 的区别。
  • 第二阶段：能用 nm -A -C 在 .o/.a/.so 中定位需求方和提供方。
  • 第三阶段：能把 nm 与 readelf、ldd、strings、c++filt 串成完整 ABI/加载排障流程。
