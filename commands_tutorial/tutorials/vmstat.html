vmstat 深度教程：AI Infra 场景下的 CPU、内存、IO 与调度观测

这份教程按常用 Linux 命令 vmstat 讲解。它不是简单字段翻译，而是从“每个采样周期里，内核把调度队列、内存、交换、块 IO、系统中断/上下文切换、CPU 时间切片汇总成一行”这个模型出发，系统解释如何在 AI 训练、推理服务、数据加载、NFS/本地盘 IO、NUMA/CPU 争用和虚拟化环境中快速判断瓶颈。

一句话理解： vmstat 是系统级“生命体征监视器”：它不告诉你哪个进程最慢，但能在一眼内判断机器是否被 CPU 调度、内存回收、swap、磁盘 IO、上下文切换或虚拟化 steal time 拖住。

1. vmstat 是什么

vmstat 来自 procps 工具集，用来周期性展示虚拟内存、进程队列、块设备 IO、系统中断/上下文切换和 CPU 时间分布。它读取内核暴露的统计信息，按固定列输出，非常适合在 SSH 终端里快速判断“整机正在被什么资源限制”。

它擅长什么
低开销、秒级采样、系统级瓶颈判断、长期卡顿现场的第一屏观察。
它不擅长什么
不能直接定位具体 Python 函数、具体文件、具体 GPU kernel 或单个线程的调用栈。
它的定位
先判断瓶颈类别，再切到更专门的工具下钻。
# 每 1 秒采样一次，共 10 次
vmstat 1 10

# 带单位输出，便于阅读内存数字
vmstat -S M 1 10

# 显示内存、磁盘、fork、slab 等摘要
vmstat -s
vmstat -d
vmstat -f
vmstat -m
边界提醒： vmstat 是整机视角。如果同一台节点上有多个训练任务、容器或租户，它只能说明主机层面发生了什么，不能自动替你分摊到某个 job。

2. AI Infra 为什么需要 vmstat

AI 训练和推理的性能问题经常表现为“GPU 利用率掉下去”，但根因可能在 CPU、内存、页缓存、数据集存储、网络文件系统、解压/增强线程、容器 CPU 限额或虚拟机宿主机争用。vmstat 的价值在于：它能快速告诉你 GPU 之前的主机侧流水线是否健康。

AI 场景vmstat 观察重点典型解释
PyTorch/TF 训练吞吐下降r、b、wa、bi、cs数据加载线程 CPU 不够、IO 阻塞、过度进程/线程切换。
GPU 利用率周期性锯齿b 和 wa 周期升高dataloader 或 checkpoint 读写把训练 step 卡住。
推理服务 p99 抖动r、sy、cs、stCPU 调度争用、网络/系统调用开销、虚拟化 steal time。
大模型权重加载慢bi、b、wa、cache冷页缓存、磁盘或远端存储吞吐不足。
AI Infra 心法： GPU 是结果，主机侧 pipeline 是原因之一。看 vmstat 是为了判断“GPU 在等谁”。

vmstat 把多个内核子系统浓缩成一行。对 AI Infra 来说，它是判断“GPU 之前哪段 pipeline 堵住”的入口。

4. 安装、权限与可用性

大多数 Linux 发行版默认提供 vmstat。它通常不需要 root 权限，因为读取的是内核公开统计；但某些容器环境可能因为最小镜像没有安装 procps，或者因为命名空间/cgroup 限制导致看到的是宿主机或容器视角的混合信息。

系统安装命令说明
Ubuntu/Debiansudo apt-get update && sudo apt-get install -y procpsvmstat 属于 procps。
RHEL/CentOS/Rockysudo dnf install -y procps-ng旧系统可能使用 yum。
容器镜像apt-get install procps 或使用基础镜像自带工具只在诊断镜像中安装，生产镜像不必强行加入。
# 确认版本与路径
command -v vmstat
vmstat --version 2>/dev/null || vmstat -V

# 查看帮助
vmstat --help 2>/dev/null || man vmstat
容器注意： 在 Kubernetes Pod 内运行 vmstat 时，CPU/内存限制、宿主机统计和 cgroup 统计可能不完全一致。排障容器资源限制时，同时查看 cat /sys/fs/cgroup/*、kubectl top 或节点级监控。

5. 基本语法与第一批命令

vmstat [options] [delay [count]]

# delay: 两次采样之间的秒数
# count: 输出多少次；不写 count 时持续输出
# 常用方式：vmstat 1 30
命令用途
vmstat输出一行自系统启动以来的平均摘要。
vmstat 1每秒持续输出，适合现场观察。
vmstat 1 30每秒采样 30 次，适合贴到工单或排障记录。
vmstat -S M 1 10内存字段用 MB 显示，降低换算成本。
vmstat -w 1 10宽格式输出，字段不容易挤在一起。
# 训练过程中记录 60 秒主机状态
vmstat -w -S M 1 60 | tee vmstat.$(date +%Y%m%d-%H%M%S).log

# 与 GPU 利用率并排观察，两个终端分别运行
watch -n 1 nvidia-smi
vmstat -w 1
复制建议： 排障时优先使用 vmstat -w 1 30。宽输出更适合截图和粘贴，1 秒采样能看到训练 step 间歇性抖动。

6. 输出字段总览

典型 vmstat 输出按列分组。不同发行版可能略有差异，但核心字段基本一致。

procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 2  0      0  8192M   512M  64.0G    0    0     4    32 1200 3500 28  5 66  1  0
分组字段一句话解释
procsr、b可运行队列和不可中断阻塞队列。
memoryswpd、free、buff、cacheswap 使用量、空闲内存、块设备 buffer、页缓存。
swapsi、so每秒 swap in/out，非零且持续通常危险。
iobi、bo每秒从块设备读入/写出块数。
systemin、cs每秒中断和上下文切换次数。
cpuus、sy、id、wa、st用户态、内核态、空闲、IO 等待、虚拟化被偷走的 CPU 时间。
读表顺序： 先看 r/b 判断队列，再看 us/sy/id/wa/st 判断 CPU 时间流向，最后结合 si/so、bi/bo、in/cs 解释原因。

7. procs：r 与 b 队列

r 是正在运行或等待 CPU 的任务数，近似反映 run queue 压力；b 是不可中断睡眠任务数，常见于等待磁盘、网络文件系统或某些内核 IO。AI 训练中，r 高常指 CPU worker 抢核，b 高常指数据/权重/checkpoint IO 卡住。

现象可能含义下一步
r 长期大于 CPU 逻辑核数CPU 供给不足，线程/进程过多，dataloader worker 过量。mpstat -P ALL 1、pidstat -u -t 1。
b 周期性升高训练 step 等待 IO，可能是数据读取、解压、checkpoint。iostat -xz 1、pidstat -d 1、存储监控。
r 高但 us 不高可能有 CPU 限额、steal time 或锁/调度异常。看 st、cgroup CPU quota、perf top。
# 观察 run queue 是否超过逻辑核数
nproc
vmstat -w 1 20

# 找出 CPU 热线程
pidstat -u -t 1 10
ps -eLo pid,tid,psr,pcpu,comm --sort=-pcpu | head
不要机械套阈值： r 短时间高不一定有问题；关键是它是否持续高于可用 CPU、是否伴随吞吐下降或延迟升高。

8. memory：free、buff、cache

Linux 会积极用空闲内存做页缓存，因此 free 低不等于内存不足。AI 任务读取大数据集时，cache 可能很高，这是正常且有益的；真正危险的是持续 swap、OOM、活跃页回收和训练进程 resident memory 不断上涨。

字段含义AI 场景解释
swpd已使用 swap 总量非零不一定立刻危险，但持续增长要警惕。
free完全空闲内存Linux 正常运行时可能较低。
buff块设备 buffer通常不是主要关注点。
cache页缓存数据集读取越多越可能升高，有助于后续 epoch。
# 更清楚地看可用内存
free -h

# 观察训练进程内存
ps -o pid,ppid,rss,vsz,cmd -p "$PID"
pmap -x "$PID" | tail -n 1

# 看内存压力和 OOM 记录
dmesg -T | grep -Ei 'out of memory|oom|killed process' | tail
判断重点： 页缓存高通常不是坏事。把注意力放在 si/so 是否持续非零、进程 RSS 是否异常增长、系统日志是否出现 OOM。

9. swap：si 与 so

si 表示每秒从 swap 读回内存，so 表示每秒把内存写到 swap。对 AI 训练而言，持续 swap 往往是严重问题：一次 batch 可能拖慢数十倍，GPU 会长期等待 CPU/内存子系统。

si=0 so=0
理想状态，至少没有持续 swap 抖动。
so 持续大于 0
内存正在被挤出，可能是 batch、worker、缓存或模型副本过大。
si 和 so 来回跳
系统进入内存颠簸，训练吞吐会非常差。
# 观察 swap 使用
swapon --show
free -h
vmstat -w 1 30

# 查找高 RSS 进程
ps aux --sort=-rss | head -20
生产警告： 不要在不了解业务影响时直接 swapoff -a。这可能触发 OOM kill。先降低并发、停止非关键任务、减少 dataloader worker 或 batch，再规划迁移/重启。

10. io：bi 与 bo

bi 和 bo 是块设备读写速率。它们能提示“是否有 IO 活动”，但不能告诉你哪块盘、哪个挂载点、哪个进程最慢。因此在看到 b、wa、bi/bo 异常后，通常要切到 iostat、pidstat -d、iotop 或存储系统监控。

现象常见 AI 原因建议验证
bi 高，GPU 低利用数据集冷读、远端存储慢、解压前置。iostat -xz 1 看设备 %util、await。
bo 周期性尖峰checkpoint、日志、tensorboard、缓存落盘。对齐训练 step 时间点和文件写入。
b 高但 bi/bo 不高可能是 NFS/分布式 FS、元数据等待或内核锁。看挂载类型、NFS 客户端统计、存储端指标。
# 与 vmstat 同时运行，确认是不是设备级 IO 等待
iostat -xz 1 30
pidstat -d 1 30

# 粗略观察当前打开数据集文件
lsof -p "$PID" | grep -E 'dataset|checkpoint|\.pt|\.safetensors' | head
单位提醒： 不同系统文档对 block 单位说明可能不同，实战中更重要的是趋势和与 iostat 的交叉验证，而不是只盯绝对数字。

11. system：in 与 cs

in 是每秒中断次数，cs 是每秒上下文切换次数。AI 数据流水线中，过多 worker、小文件读取、网络包、线程池抖动、锁竞争或过度并发都可能让 cs 异常升高，CPU 时间花在调度而不是有效计算上。

字段含义排查方向
in 很高中断频繁，可能来自网络、磁盘、定时器、GPU 驱动相关事件。cat /proc/interrupts、网卡/存储监控。
cs 很高线程/进程频繁切换。pidstat -w -t 1、检查 worker 数、线程池、锁。
sy 与 cs 同升内核态开销明显。系统调用、网络/IO 路径、容器网络、文件系统。
# 找上下文切换高的进程和线程
pidstat -w -t 1 10

# 看中断分布
cat /proc/interrupts | head -40

# 查看每个 CPU 的负载分布
mpstat -P ALL 1 10
dataloader 经验： num_workers 不是越大越好。worker 过多可能让 r、cs、sy 同时升高，反而降低 GPU feed 速度。

12. cpu：us、sy、id、wa、st

CPU 分组告诉你每个采样窗口里的 CPU 时间花在哪里。AI 排障时尤其关注 wa 和 st：前者说明 CPU 在等 IO，后者说明虚拟化宿主机拿走了本该属于当前虚拟机的 CPU 时间。

字段含义AI Infra 解读
us用户态 CPU 时间Python 数据处理、预处理、推理前后处理、业务逻辑。
sy内核态 CPU 时间文件系统、网络、驱动、内存管理、系统调用。
id空闲 CPU 时间高 id 且 GPU 低，瓶颈可能不是 CPU 算力。
waIO waitCPU 等块设备 IO，数据加载和 checkpoint 常见。
ststeal time虚拟化或云主机争用，裸金属通常接近 0。
# 如果 wa 高，马上切到设备层
vmstat -w 1 10
iostat -xz 1 10

# 如果 st 高，记录证据给云平台/虚拟化团队
vmstat -w 1 60 | tee steal-time.log
lscpu | grep -Ei 'hypervisor|virtualization'
快速判断： us 高看应用 CPU；sy 高看内核/IO/网络；wa 高看存储；st 高看虚拟化争用；id 高但业务慢则看锁、远端服务、GPU/网络或应用等待。

13. 采样间隔与首行陷阱

vmstat 1 5 的第一行通常是自系统启动以来的平均值，不代表当前一秒。第二行开始才是每个采样窗口的数据。AI 训练常有明显周期性，例如每 N step 写 checkpoint、每个 epoch 首次冷读数据、每个 batch 数据增强，因此连续采样比单次输出重要得多。

采样方式适合场景注意事项
vmstat 1 30交互式排障，观察训练 step、推理 p99 抖动。忽略第一行，看后续 29 个窗口。
vmstat 5 605 分钟趋势，适合轻量巡检。尖峰会被平滑，不适合看短 step。
vmstat 60长期后台记录。需要 logrotate 或显式结束，避免日志无限增长。
# 带时间戳记录，便于和训练日志对齐
while true; do
  printf '%s ' "$(date '+%F %T')"
  vmstat -n 1 2 | tail -1
done | tee vmstat.timeline.log

# 只收 2 分钟，避免无限运行
timeout 120s vmstat -w 1 | tee vmstat.120s.log
日志实践： 如果需要长时间采样，使用 timeout、systemd timer、监控系统或 logrotate。不要在生产节点上留下无人管理的无限输出任务。

14. 训练 dataloader stall 排查

dataloader stall 的表象通常是 GPU 利用率周期性掉到低位、每个 batch 间隔变长、吞吐不稳定。vmstat 可以帮你先区分是 CPU worker 不够、worker 太多、IO 等待、内存 swap，还是虚拟化争用。

最小排查组合

# 终端 A：GPU
watch -n 1 nvidia-smi

# 终端 B：整机体征
vmstat -w 1 120 | tee vmstat.train.log

# 终端 C：CPU 和 IO 下钻
pidstat -u -d -w -t 1 120 | tee pidstat.train.log
iostat -xz 1 120 | tee iostat.train.log
vmstat 模式可能根因调参方向
r 高、us 高、cs 高worker 过多或 CPU 预处理太重。降低 num_workers、限制线程池、优化 transform、预处理数据。
b 高、wa 高、bi 高数据读取受存储限制。本地 NVMe cache、减少小文件、WebDataset/LMDB、提高预取。
si/so 持续非零内存不足或 worker 复制数据过多。降低 batch、worker、prefetch factor，检查数据集缓存策略。
st 高云主机或虚拟化宿主机争用。换实例、换宿主机、联系云平台，保留证据。
训练经验： 当 GPU 低利用且 id 很高时，不要马上加 worker。先检查是否是远端数据源、锁、队列阻塞、Python 主进程等待或分布式同步。

15. 推理服务与 GPU 利用率排查

在线推理比离线训练更关注延迟和抖动。vmstat 在这里用于判断系统级噪声：CPU run queue、系统调用开销、网络/磁盘中断、上下文切换、IO wait、steal time 是否与 p99/p999 延迟尖峰同时出现。

CPU 前后处理重
r 和 us 高，GPU 有空洞。优化 tokenizer、图像预处理、batcher、线程池和 CPU 亲和性。
系统调用/网络开销高
sy、in、cs 高。检查连接数、TLS、网卡中断、容器网络和日志写入。
权重/缓存冷启动慢
bi、b、wa 高。预热模型、预拉权重、本地缓存、减少启动时远端读取。
虚拟化噪声
st 高。对 GPU 推理节点尤其危险，因为 CPU 抖动会影响请求调度和数据搬运。
# 请求压测期间同步采集
vmstat -w 1 180 | tee vmstat.infer.log
mpstat -P ALL 1 180 | tee mpstat.infer.log
pidstat -u -w -t -p "$PID" 1 180 | tee pidstat.infer.log

# 与服务日志按时间对齐
grep 'p99' service.log | tail -20
在线服务原则： vmstat 只能证明“节点同时出现系统压力”。要定位具体请求路径，还需要服务端 tracing、框架 profiler、请求日志和 GPU runtime 指标。

16. vmstat vs sar/mpstat/iostat

工具最适合回答的问题和 vmstat 的关系
vmstat整机现在是 CPU、内存、swap、IO、调度还是虚拟化问题？第一屏总览。
sar过去一段时间是否出现过同类问题？历史时间序列，适合复盘。
mpstatCPU 压力是否集中在少数核？是否有软中断/每核不均？CPU 下钻。
iostat哪块设备繁忙？延迟、队列、利用率如何？IO 下钻。
pidstat哪个进程/线程在吃 CPU、IO 或上下文切换？责任主体定位。
top/htop当前最热进程是谁？交互观察。现场辅助。
# 一个常用排障组合
vmstat -w 1 30
mpstat -P ALL 1 30
iostat -xz 1 30
pidstat -u -d -w -t 1 30

# 若安装了 sysstat，可看历史
sar -u 1 5
sar -b 1 5
sar -r 1 5
工具链心法： vmstat 定方向，sar 看历史，mpstat 看每核，iostat 看设备，pidstat 找进程，GPU 工具看加速器侧。

排障图：从 vmstat 模式到下一步动作

vmstat 的价值是把复杂系统问题分流到正确的下钻路径，避免盲目调 batch、worker 或重启服务。

17. 故障模式速查

CPU 饱和
r 持续高于可用核数，us 高。检查 dataloader worker、tokenizer、图像增强、OpenMP/MKL 线程数。
IO 阻塞
b、wa、bi 或 bo 同时升高。检查数据集、checkpoint、NFS、对象存储挂载和本地盘。
内存颠簸
si/so 持续非零，吞吐急剧下降。降低 batch/worker，检查缓存和内存泄漏。
上下文切换风暴
cs 异常高，sy 偏高。减少线程/进程，检查锁、队列、日志和小 IO。
虚拟化争用
st 明显升高。云主机/虚拟机被宿主机抢 CPU，需换节点或升级实例。
看似空闲但业务慢
id 高，其他列平稳。查 GPU 同步、分布式通信、远端 RPC、应用锁或限流。

可复制排障模板

# 1. 收集整机 2 分钟
timeout 120s vmstat -w 1 | tee vmstat.$(hostname).log

# 2. 同步收集 CPU、IO、进程
timeout 120s mpstat -P ALL 1 | tee mpstat.$(hostname).log
timeout 120s iostat -xz 1 | tee iostat.$(hostname).log
timeout 120s pidstat -u -d -w -t 1 | tee pidstat.$(hostname).log

# 3. 如果是 GPU 节点，额外收集
nvidia-smi dmon -s pucvmt -d 1 -c 120 | tee nvidia-dmon.$(hostname).log
证据对齐： 记录主机名、时间、训练 step 或请求时间窗口。没有时间对齐的性能证据很难支持根因判断。

18. 安全采集与生产注意事项

vmstat 本身是只读、低开销命令，适合线上运行。但围绕它的排障动作可能有风险：安装工具、长时间采集、清缓存、关闭 swap、重启服务、调整 worker 或迁移任务都可能影响生产。

动作风险安全做法
运行 vmstat 1 30极低可以直接执行并保存输出。
长时间 tee 日志日志占盘使用 timeout、限制路径、采集后压缩归档。
安装 procps/sysstat变更系统包优先在诊断容器或维护窗口执行。
清页缓存会改变真实 workload 表现只在隔离测试节点上做，生产排障通常不要做。
swapoff、重启、迁移可能触发 OOM 或业务中断先降载和备份现场，再走变更流程。
# 安全采集：限制时长，写入明确文件
mkdir -p /tmp/perf-capture
timeout 180s vmstat -w 1 | tee /tmp/perf-capture/vmstat.log

# 不建议在生产排障中随手执行
# sync; echo 3 | sudo tee /proc/sys/vm/drop_caches
# sudo swapoff -a
安全底线： vmstat 观察是安全的，但“为了验证猜想而清缓存/关 swap/重启节点”不是安全默认动作。生产上先收证据，再评估影响。
