nvidia-ctk 深度教程：AI Infra 中的 NVIDIA Container Toolkit 配置与诊断

nvidia-ctk 是 NVIDIA Container Toolkit 的运维入口，用来配置 Docker、containerd、CRI-O 等容器运行时，生成或检查 CDI 设备规范，调整 NVIDIA runtime 模式，并辅助诊断 GPU 容器不可见、MIG 映射错误、Kubernetes 节点配置漂移等问题。本教程面向 AI Infra 场景：训练节点、推理节点、GPU Operator、rootless 容器、MIG、多租户和生产变更流程。

AI InfraNVIDIA Container ToolkitDockercontainerdCDIMIGKubernetes运行时 HookGPU 可见性安全变更
一句话理解： nvidia-ctk 不直接“运行模型”，它负责把宿主机上的 GPU、驱动库、设备节点和运行时配置，以 Docker/containerd/Kubernetes 能理解的方式接入容器生命周期。
生产原则： 修改 /etc/docker/daemon.json、/etc/containerd/config.toml、/etc/nvidia-container-runtime/config.toml 前先备份、在临时副本演练、生成 diff，再重启运行时；不要在训练高峰期盲目重启 Docker 或 containerd。

1. nvidia-ctk 是什么

nvidia-ctk 是 NVIDIA Container Toolkit CLI。它的职责是“配置和检查工具链”，而不是替代 docker、containerd、kubectl 或 nvidia-smi。在 AI Infra 中，它常用于节点初始化、镜像运行验证、GPU Operator 调试、CDI 规范生成，以及从 legacy hook 模式迁移到 CDI 模式。

配置运行时
将 Docker、containerd、CRI-O 配置为可调用 NVIDIA Container Runtime 或 CDI 设备注入链路。
生成 CDI 规范
把 GPU、MIG 实例等设备描述成 nvidia.com/gpu=... 这类运行时可解析的设备名。
调整 toolkit 配置
修改 config.toml 中的 runtime mode、no-cgroups、debug 等选项。
# 查看版本与帮助
nvidia-ctk --version
nvidia-ctk --help

# 查看某个子命令的参数，生产脚本应以目标节点实际输出为准
nvidia-ctk runtime configure --help
nvidia-ctk cdi generate --help
nvidia-ctk config --help
版本提醒： NVIDIA Container Toolkit 的能力随版本演进。脚本中使用某个参数前，先在目标节点执行 nvidia-ctk 子命令 --help，不要假设所有集群节点参数完全一致。

信息图：AI Infra 中的 NVIDIA 容器接入模型

AI 训练或推理容器能否看到 GPU，取决于宿主机驱动、运行时配置、设备选择、容器权限和编排层资源声明共同正确。

2. 安装前置条件与版本确认

在使用 nvidia-ctk 前，先确认三层基础：宿主机驱动正常、容器引擎可用、Toolkit 版本一致。驱动问题不能靠 nvidia-ctk 修复；它只能把已经可用的宿主机 GPU 暴露给容器。

# 1. 宿主机必须能看到 GPU
nvidia-smi
nvidia-smi -L

# 2. 容器引擎正常
docker version
containerd --version
crictl info 2>/dev/null | head

# 3. Toolkit CLI 存在
command -v nvidia-ctk
nvidia-ctk --version

# 4. 相关二进制是否安装
command -v nvidia-container-runtime
command -v nvidia-container-cli
检查项异常信号优先处理
驱动nvidia-smi 失败、NVML 报错修复驱动、内核模块、Secure Boot、驱动版本
Toolkitnvidia-ctk: command not found安装 nvidia-container-toolkit 或对应 base 包
运行时Docker/containerd 无法启动先恢复运行时，再配置 NVIDIA runtime
镜像容器内 CUDA 库缺失选择匹配 CUDA runtime/devel 镜像，不要把宿主机驱动打进镜像

3. 核心子命令速览

nvidia-ctk 的命令族可以按“配置运行时”“管理配置文件”“管理 CDI”三类理解。不同版本的参数略有差异，下面给的是常见生产用法与排障入口。

子命令用途常见场景
runtime configure修改 Docker/containerd/CRI-O 等运行时配置节点初始化、运行时迁移、Kubernetes containerd 接入
config读写 NVIDIA Container Runtime 配置切换 CDI 模式、rootless Docker 设置 no-cgroups
cdi generate生成 CDI YAMLPodman、Docker CDI、CRI-O、rootless、多运行时统一设备声明
cdi list列出已解析 CDI 设备验证 GPU/MIG 设备名、排查 CDI spec 过期
--debug输出更详细日志定位 spec 加载错误、路径权限、设备解析失败
# 只读帮助优先，避免把老版本节点当成新版本使用
nvidia-ctk runtime configure --help
nvidia-ctk cdi list --help

# CDI 设备可见性检查
nvidia-ctk cdi list
nvidia-ctk --debug cdi list

4. Docker 配置流程

官方常见配置命令是 sudo nvidia-ctk runtime configure --runtime=docker，它会更新宿主机 /etc/docker/daemon.json，让 Docker 能使用 NVIDIA Container Runtime。生产环境建议先对临时副本演练，再正式应用。

# 安全演练：不要先改真实 daemon.json
tmp=$(mktemp)
sudo test -f /etc/docker/daemon.json \
  && sudo cp -a /etc/docker/daemon.json "$tmp" \
  || printf '{}\n' > "$tmp"

# 在临时副本上生成目标配置；如本机版本不支持 --config，请先查看 --help
sudo nvidia-ctk runtime configure --runtime=docker --config="$tmp"
sudo diff -u /etc/docker/daemon.json "$tmp" || true

# 确认 diff 后再正式执行
sudo cp -a /etc/docker/daemon.json "/etc/docker/daemon.json.$(date +%Y%m%d-%H%M%S).bak" 2>/dev/null || true
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

# 验证 GPU 容器
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
Rootless Docker： rootless 模式通常要把 Docker 配置写到 $HOME/.config/docker/daemon.json，并按目标版本帮助设置 nvidia-container-cli.no-cgroups。这类节点尤其要记录用户级 systemd 服务和全局 runtime 配置的对应关系。

5. containerd 与 Kubernetes 配置

Kubernetes 节点大多通过 containerd 作为 CRI。nvidia-ctk runtime configure --runtime=containerd 通常会创建 NVIDIA drop-in 配置，并确保 containerd 主配置导入该文件。修改后需要重启或让 containerd 重新加载，变更会影响该节点上的 Pod 生命周期。

# 先保存当前配置
sudo cp -a /etc/containerd/config.toml "/etc/containerd/config.toml.$(date +%Y%m%d-%H%M%S).bak"
sudo test -d /etc/containerd/conf.d && sudo ls -la /etc/containerd/conf.d

# 配置 containerd 运行时
sudo nvidia-ctk runtime configure --runtime=containerd

# 检查 NVIDIA drop-in 与 imports
sudo grep -R "nvidia" /etc/containerd/config.toml /etc/containerd/conf.d 2>/dev/null

# 维护窗口内重启
sudo systemctl restart containerd
sudo systemctl status containerd --no-pager

# Kubernetes 节点验证
kubectl describe node "$(hostname)" | grep -A5 -E "Capacity|Allocatable|nvidia.com/gpu"
环境重点验证
裸 containerddrop-in 路径、runtime handler、config.toml importsctr 或 nerdctl GPU 容器测试
KubernetesDevice Plugin/GPU Operator、RuntimeClass、节点标签kubectl describe node 出现 nvidia.com/gpu
RKE2/MicroK8s发行版自定义 containerd 路径按发行版配置 CONTAINERD_CONFIG 与 socket

6. 运行时 Hook 与 OCI 注入链路

传统 NVIDIA 容器链路的核心是 OCI prestart hook：容器运行时准备好 OCI spec 后，NVIDIA runtime/hook 读取环境变量和配置，把 GPU 设备节点、驱动库、必要 mount 注入容器。nvidia-ctk 负责让 Docker/containerd 知道该调用哪条链路。

OCI spec
容器启动前的配置描述，包括 mount、env、devices、hooks。
runtime wrapper
nvidia-container-runtime 包装底层 runc 并插入 NVIDIA 逻辑。
runtime hook
在 prestart 阶段调用底层注入工具。
libnvidia-container
根据驱动、设备、能力选择生成实际挂载与设备映射。
# 查看 runtime 配置文件
sudo sed -n '1,220p' /etc/nvidia-container-runtime/config.toml

# Docker 检查 runtime 是否注册
docker info | sed -n '/Runtimes:/,/Default Runtime/p'

# 容器内确认注入结果
docker run --rm --gpus '"device=0"' nvidia/cuda:12.4.1-base-ubuntu22.04 \
  bash -lc 'nvidia-smi -L && ls -l /dev/nvidia*'
重要边界： 镜像里的 CUDA runtime 版本可以低于或等于宿主机驱动支持范围；但 GPU 驱动本体在宿主机，不应通过普通应用镜像安装和覆盖。

信息图：legacy hook 与 CDI 的选择

CDI 让设备声明更标准，legacy hook 仍在大量 Docker 生产环境中存在。选择取决于运行时能力、集群版本、rootless 需求和迁移成本。

7. CDI：面向新运行时的设备声明

CDI（Container Device Interface）把 GPU 描述成运行时可消费的设备规范。新版本 Toolkit 可通过 nvidia-cdi-refresh systemd 服务自动生成 /var/run/cdi/nvidia.yaml；MIG 重配、驱动移除等场景可能需要手动刷新。

# 列出运行时能解析的 NVIDIA CDI 设备
nvidia-ctk cdi list
nvidia-ctk --debug cdi list

# 手动生成到临时文件，先审查内容
nvidia-ctk cdi generate > /tmp/nvidia-cdi.yaml
grep "  name:" /tmp/nvidia-cdi.yaml

# 确认后写入标准位置
sudo nvidia-ctk cdi generate --output=/var/run/cdi/nvidia.yaml

# 通过 systemd 刷新服务重新生成
sudo systemctl restart nvidia-cdi-refresh.service
sudo journalctl -u nvidia-cdi-refresh.service --no-pager -n 80
# Podman 使用 CDI 设备名
podman run --rm \
  --device nvidia.com/gpu=all \
  --security-opt=label=disable \
  ubuntu nvidia-smi -L

# Docker 也可以通过 NVIDIA runtime 的 CDI mode 使用 CDI 名称
docker run --rm --runtime=nvidia \
  -e NVIDIA_VISIBLE_DEVICES=nvidia.com/gpu=all \
  ubuntu nvidia-smi -L
冲突提醒： CDI 设备注入与旧的 OCI hook 注入不要随意叠加。如果存在 /usr/share/containers/oci/hooks.d/oci-nvidia-hook.json，同时又用 CDI 设备名，要检查是否造成重复注入或选择逻辑混乱。

8. GPU 可见性与能力控制

GPU 容器可见性通常由三层控制：运行时是否启用 NVIDIA 注入、选择哪些设备、暴露哪些能力。Docker 常见入口是 --gpus，NVIDIA runtime 也支持 NVIDIA_VISIBLE_DEVICES 与 NVIDIA_DRIVER_CAPABILITIES。

控制点例子说明
所有 GPU--gpus all单租户测试方便，生产多租户慎用
指定 GPU--gpus '"device=0,2"'按 Docker 语法选择索引或 UUID
CDI 名称nvidia.com/gpu=0适合 CDI-aware runtime 或 runtime CDI mode
能力NVIDIA_DRIVER_CAPABILITIES=compute,utility训练/推理通常需要 compute 和 utility
# 最小验证：容器内只需要 nvidia-smi
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 训练/推理常见能力
docker run --rm --gpus '"device=0"' \
  -e NVIDIA_DRIVER_CAPABILITIES=compute,utility \
  nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 容器内检查 PyTorch 是否看到 CUDA
docker run --rm --gpus all pytorch/pytorch:2.4.1-cuda12.4-cudnn9-runtime \
  python -c 'import torch; print(torch.cuda.is_available(), torch.cuda.device_count())'
排障顺序： 先在宿主机 nvidia-smi，再跑最小 CUDA 镜像，再跑业务镜像。不要一开始就在完整训练框架里排查。

9. MIG 与多租户隔离

MIG（Multi-Instance GPU）把支持的 GPU 切分成多个硬件隔离实例。nvidia-ctk 不负责规划 MIG 切分策略，但 CDI 规范会包含 MIG 设备引用；重配 MIG 后必须确保 CDI spec 和 Kubernetes 资源视图刷新。

# 宿主机查看 MIG 状态
nvidia-smi -L
nvidia-smi mig -lgi
nvidia-smi mig -lci

# 重配 MIG 后刷新 CDI
sudo systemctl restart nvidia-cdi-refresh.service
nvidia-ctk cdi list | grep -i mig || true

# Podman 请求一个完整 GPU 和一个 MIG 设备的示例形式
podman run --rm \
  --device nvidia.com/gpu=0 \
  --device nvidia.com/gpu=1:0 \
  --security-opt=label=disable \
  ubuntu nvidia-smi -L
场景推荐关注点风险
推理多租户固定 MIG profile、固定调度标签、禁止容器逃逸到全卡spec 过期导致请求到不存在的 MIG 实例
训练共享节点明确是否允许 MPS/MIG/整卡混部资源碎片和性能不可预测
KubernetesDevice Plugin 的 MIG strategy 与节点实际配置一致scheduler 看到的资源与宿主机实际设备不一致
维护窗口： MIG 重配可能影响正在运行的 workload。先 drain 节点或确认业务可中断，再调整 MIG 并刷新 CDI/Kubernetes 视图。

架构图：Kubernetes GPU 节点链路

Kubernetes 中的故障可能发生在驱动、runtime、kubelet、device plugin、pod spec 任意一层，不要只盯着业务容器日志。

10. Kubernetes 集成方式

裸 Kubernetes 可手动安装驱动、Toolkit、Device Plugin；生产集群更常用 NVIDIA GPU Operator 统一管理驱动、Toolkit、Device Plugin、DCGM Exporter、MIG Manager 等组件。nvidia-ctk 在这里常作为 Toolkit 容器或节点脚本的一部分。

# 最小 GPU Pod
cat > cuda-vectoradd.yaml <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: cuda-vectoradd
spec:
  restartPolicy: OnFailure
  containers:
  - name: cuda-vectoradd
    image: nvcr.io/nvidia/k8s/cuda-sample:vectoradd-cuda11.7.1-ubuntu20.04
    resources:
      limits:
        nvidia.com/gpu: 1
YAML

kubectl apply -f cuda-vectoradd.yaml
kubectl logs pod/cuda-vectoradd
kubectl delete -f cuda-vectoradd.yaml
方案何时使用nvidia-ctk 关注点
手动 Toolkit + Device Plugin小集群、实验环境、受控镜像仓库节点上运行 runtime configure，保证 containerd 配置一致
GPU Operator生产集群、节点异构、需要 DCGM/MIG 管理关注 Operator 的 Toolkit 配置、containerd 路径、CDI/NRI 选项
CDI + RuntimeClass新运行时、rootless、降低 hook 耦合确保 CDI spec 自动刷新并被运行时读取
调度层验证： kubectl describe node 看到 nvidia.com/gpu 只说明调度层发现资源；还需要 Pod 内 nvidia-smi 或 CUDA sample 验证 runtime 注入。

11. 安全配置变更流程

GPU 节点上的 runtime 配置是生产基础设施，错误变更会影响所有容器。下面是一套适合 SRE/平台团队的可复制流程。

# 0. 确认当前业务影响
docker ps --format 'table {{.ID}}\t{{.Image}}\t{{.Status}}'
kubectl get pods -A -o wide --field-selector spec.nodeName="$(hostname)" 2>/dev/null

# 1. 备份关键文件
stamp=$(date +%Y%m%d-%H%M%S)
sudo tar -czf "/root/nvidia-container-config-$stamp.tgz" \
  /etc/docker/daemon.json \
  /etc/containerd/config.toml \
  /etc/containerd/conf.d \
  /etc/nvidia-container-runtime/config.toml 2>/dev/null || true

# 2. 在副本上演练并生成 diff
tmp=$(mktemp)
sudo cp -a /etc/docker/daemon.json "$tmp"
sudo nvidia-ctk runtime configure --runtime=docker --config="$tmp"
sudo diff -u /etc/docker/daemon.json "$tmp" || true

# 3. 正式变更前再次确认
printf '确认维护窗口、备份和回滚路径后，再执行正式 nvidia-ctk 配置命令。\n'
不要这样做： 不要在未知节点批量执行 sudo nvidia-ctk runtime configure ... && sudo systemctl restart containerd；先分批、先 canary、先验证 GPU Pod，再滚动到整组节点。

12. 诊断命令与日志采集

排查 GPU 容器问题时，按“宿主机 → toolkit → runtime → 容器 → Kubernetes”分层采集。这样可以避免把驱动问题误判成镜像问题，或把 Kubernetes 调度问题误判成 nvidia-ctk 配置问题。

# 宿主机层
nvidia-smi
nvidia-smi -L
ls -l /dev/nvidia*

# Toolkit 层
nvidia-ctk --version
nvidia-ctk --debug cdi list
sudo sed -n '1,220p' /etc/nvidia-container-runtime/config.toml

# Docker 层
docker info | sed -n '/Runtimes:/,/Default Runtime/p'
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
sudo journalctl -u docker --no-pager -n 120

# containerd/Kubernetes 层
sudo journalctl -u containerd --no-pager -n 120
kubectl describe node "$(hostname)" | grep -A8 -E 'Capacity|Allocatable|nvidia.com/gpu'
kubectl -n gpu-operator logs -l app=nvidia-device-plugin-daemonset --tail=120
症状第一检查点常见原因
容器内无 /dev/nvidia0docker info runtime、--gpus 参数Docker 未注册 NVIDIA runtime 或未请求 GPU
nvidia-smi 容器失败但宿主机成功nvidia-container-cli 日志、runtime config库挂载、权限、cgroup、runtime mode 问题
K8s Pod Pendingkubectl describe pod节点未上报 nvidia.com/gpu 或资源不足
MIG 设备名无效nvidia-ctk cdi listCDI spec 未刷新或 MIG 已重配

13. nvidia-ctk vs nvidia-container-cli

两者经常一起出现，但职责不同。简单说：nvidia-ctk 面向管理员配置和 CDI 生成；nvidia-container-cli 更底层，面向 runtime/hook 实际注入容器所需设备和库。

工具层级典型用户典型用途
nvidia-ctkToolkit 运维 CLISRE、平台工程师、节点初始化脚本配置 Docker/containerd、生成 CDI、修改 Toolkit 配置
nvidia-container-clilibnvidia-container 底层 CLIruntime/hook、深度排障人员根据 GPU 选择、能力、驱动库生成容器注入内容
nvidia-container-runtimeOCI runtime wrapper容器运行时调用包装 runc，注入 NVIDIA hook 或处理 CDI mode
nvidia-smi驱动/NVML 验证工具所有人确认宿主机或容器内 GPU 可见性
排障定位： 如果问题是“Docker 配置没有 NVIDIA runtime”，看 nvidia-ctk 和 daemon 配置；如果问题是“runtime 调用了但库/设备注入失败”，再深入 nvidia-container-cli、hook、libnvidia-container 日志。

排障图：从症状到层级定位

把复杂问题拆成最小复现链路，是 GPU Infra 排障中最节省时间的方法。

14. 常见故障排查

容器启动时报 could not select device driver "" with capabilities: [[gpu]]

docker info | sed -n '/Runtimes:/,/Default Runtime/p'
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

通常是 Docker 未识别 NVIDIA runtime，或 Docker daemon 配置未重启生效。

nvidia-container-cli: initialization error

nvidia-smi
sudo journalctl -u docker --no-pager -n 120
sudo journalctl -u containerd --no-pager -n 120
sudo sed -n '1,220p' /etc/nvidia-container-runtime/config.toml

重点检查驱动库、NVML、cgroup、runtime 配置和 rootless 模式。

CDI 设备列表为空或不含 MIG

nvidia-smi -L
sudo systemctl restart nvidia-cdi-refresh.service
sudo journalctl -u nvidia-cdi-refresh.service --no-pager -n 120
nvidia-ctk --debug cdi list

MIG 重配、驱动更新、服务未运行、CDI YAML 路径权限都可能导致列表不一致。

Kubernetes 能调度但 Pod 内无 GPU

kubectl describe pod <pod> -n <ns>
kubectl describe node <node> | grep -A8 nvidia.com/gpu
kubectl -n gpu-operator get pods -o wide
sudo grep -R "nvidia" /etc/containerd/config.toml /etc/containerd/conf.d 2>/dev/null

调度资源存在不等于 runtime 注入成功。检查 RuntimeClass、containerd 配置、Device Plugin 日志和 Operator Toolkit 配置。

15. 生产最佳实践清单

版本治理
驱动、CUDA 镜像、Toolkit、GPU Operator 版本要有矩阵；升级先 canary，再滚动。
节点不可变
把 nvidia-ctk runtime configure 放进节点镜像、cloud-init、Ansible 或 DaemonSet 管控，避免手工漂移。
最小权限
训练/推理容器只申请需要的 GPU、MIG、driver capabilities；不要默认给所有容器 --privileged。
观测性
配套 DCGM Exporter、runtime 日志采集、节点配置快照，故障时能回放变更。
CDI 策略
明确新集群是否统一走 CDI；不要让 Podman、Docker、Kubernetes 各自使用不同隐式策略。
回滚路径
每次改 Docker/containerd 配置都保留备份和 diff；重启失败时能立即恢复。
# 节点健康巡检脚本片段
set -euo pipefail
nvidia-smi -L
nvidia-ctk --version
nvidia-ctk cdi list || true
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi >/tmp/gpu-container-check.log
tail -n +1 /tmp/gpu-container-check.log

16. 学习路线与练习任务

  1. 在一台测试 GPU 节点上确认 nvidia-smi、nvidia-ctk --version、Docker/containerd 版本。
  2. 对 Docker daemon.json 副本执行 nvidia-ctk runtime configure --runtime=docker --config=...，阅读 diff。
  3. 正式配置 Docker 后运行 CUDA base 镜像，比较宿主机与容器内 nvidia-smi -L 输出。
  4. 生成临时 CDI YAML，找出完整 GPU 与 MIG 设备名的差异。
  5. 在 Kubernetes 测试命名空间运行 CUDA sample Pod，记录从 kubectl describe node 到 Pod 日志的验证链路。
  6. 模拟一次错误配置：把测试节点从调度池摘除，备份、变更、验证失败、回滚，并写下 runbook。
掌握标准： 你能解释“为什么宿主机有 GPU 但容器没有”、能安全修改 runtime 配置、能区分 legacy hook 与 CDI、能在 Kubernetes 中定位故障层，就已经具备 AI Infra 日常维护 nvidia-ctk 的核心能力。
