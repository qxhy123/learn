1. ibv_devinfo 是什么

ibv_devinfo 来自 rdma-core / libibverbs 工具集，用于列出本机 verbs 设备并查询设备属性、端口属性和扩展能力。AI Infra 中它常用于回答三个问题：节点是否暴露了 RDMA HCA；目标端口是否 PORT_ACTIVE；GID、P_Key、MTU、link layer 是否符合 NCCL、MPI、NVMe-oF、分布式存储或自研 RDMA 服务的要求。

它擅长什么
查看 verbs 设备名、node GUID、firmware、vendor、device capability、端口状态、active_mtu、GID 表、P_Key 表、link layer、QP/CQ/MR 等资源上限。
它不擅长什么
不直接显示交换机 ECN/PFC、RoCE UDP 端口、NCCL 选路、GPU Direct RDMA 是否命中、真实吞吐、链路误码或物理光模块细节。
它的本质
用户态 verbs API 的观察窗口：应用能看到什么 RDMA 设备和端口，ibv_devinfo 基本也能看到什么。
# 列出 verbs 设备
ibv_devices
ibv_devinfo -l

# 查看全部设备的常规属性
ibv_devinfo

# 查看详细属性，包含更多能力和表项
ibv_devinfo -v

# 只看指定 HCA 和端口
ibv_devinfo -d mlx5_0 -i 1
边界提醒： ibv_devinfo 显示端口 active 只说明本机 verbs 端口状态可用；跨节点 RDMA 通信还依赖对端、路由、GID index、P_Key、MTU、QoS、PFC/ECN、交换机和防火墙/安全策略。

2. 整体模型：verbs 设备到 AI 作业

ibv_devinfo 的价值在于把“应用不可用/性能差”向下分解成 HCA、端口、MTU、地址表和能力字段。

3. 安装、权限与快速确认

大多数发行版把 ibv_devinfo 放在 rdma-core、libibverbs-utils 或 ibverbs-utils 包中。只读查询通常不需要 root，但容器、Kubernetes、受限 cgroup、设备插件或安全策略可能让用户态看不到 RDMA 设备。

# Debian / Ubuntu
sudo apt-get update
sudo apt-get install -y rdma-core ibverbs-utils

# RHEL / Rocky / Alma / CentOS
sudo dnf install -y rdma-core libibverbs-utils

# 快速确认工具和设备
command -v ibv_devinfo
ibv_devinfo -l
ibv_devices
rdma link

# 常见 Mellanox/NVIDIA mlx5 设备映射
ls -l /sys/class/infiniband
for d in /sys/class/infiniband/*; do echo "== $d =="; cat "$d"/node_guid; done
检查项正常线索异常含义
命令存在command -v ibv_devinfo 有路径工具包未安装，或容器镜像缺少 rdma-core 用户态工具
设备列表mlx5_0、mlx5_1 等可见驱动未加载、VF 未暴露、容器未挂载设备、权限或设备插件问题
端口 activestate: PORT_ACTIVE链路、交换机端口、线缆、RoCE netdev、IB fabric 或固件状态异常
link layerEthernet 或 InfiniBand 符合预期把 RoCE 当 IB，或把 IB 当以太网工具排障，都会走错方向
容器提示： 容器中能运行 ibv_devinfo 不代表 NCCL 能用到所有 HCA；还要检查 /dev/infiniband/*、/sys/class/infiniband、net namespace、RDMA device plugin、NCCL_IB_HCA 和 cgroup device 规则。

4. 常用语法与输出范围

ibv_devinfo 的常用参数很少，但输出字段很多。日常排障建议先列设备，再对单个 HCA/端口采集详细信息，避免多 HCA 节点输出太长导致误读。

命令用途适合场景
ibv_devinfo -l只列出可见 verbs 设备脚本 smoke test、容器设备暴露检查
ibv_devinfo显示所有设备的基础属性与端口属性人工巡检、节点验收
ibv_devinfo -v显示更详细能力、GID/P_Key 等信息排查 GID index、能力字段、资源上限
ibv_devinfo -d mlx5_0只看指定 HCA多 HCA/GPU 节点，减少噪声
ibv_devinfo -d mlx5_0 -i 1只看指定 HCA 的指定端口NCCL 或 RDMA 应用绑定到特定端口时
# 推荐的单端口采集格式
host=$(hostname -s)
dev=mlx5_0
port=1
mkdir -p /tmp/rdma-baseline
ibv_devinfo -v -d "$dev" -i "$port" > "/tmp/rdma-baseline/${host}.${dev}.${port}.ibv_devinfo.txt"
rdma link > "/tmp/rdma-baseline/${host}.rdma-link.txt"
ip -br addr > "/tmp/rdma-baseline/${host}.ip-addr.txt"
好习惯： 报告中不要写“RDMA 正常”这种粗结论，而要写“mlx5_0:1 state=PORT_ACTIVE active_mtu=4096 link_layer=Ethernet gid[3]=RoCEv2 IPv4”。

信息图：ibv_devinfo 输出解剖

输出很多时，阅读顺序比字段数量更重要：设备身份、端口事实、GID/P_Key、资源和能力。

5. HCA 身份与全局能力

HCA 层字段告诉你“这块 RDMA 设备是谁、由什么固件驱动、最大能创建多少资源”。AI 节点常见多 HCA、多端口、多 VF、BlueField DPU、SR-IOV VF 和容器透传，设备名与物理网口/GPU 拓扑不一定一眼对应。

# 示例输出片段，字段名会随设备和 rdma-core 版本略有差异
hca_id: mlx5_0
    transport:                      InfiniBand (0)
    fw_ver:                         28.39.1002
    node_guid:                      248a:0703:00ab:cdef
    sys_image_guid:                 248a:0703:00ab:cdef
    vendor_id:                      0x02c9
    vendor_part_id:                 4129
    hw_ver:                         0x0
    phys_port_cnt:                  1
    max_qp:                         262144
    max_cq:                         16777216
    max_mr:                         16777216
字段含义AI Infra 解读
hca_idverbs 设备名，例如 mlx5_0NCCL 的 NCCL_IB_HCA、MPI provider、RDMA 服务绑定常用它
fw_verHCA 固件版本同一训练池建议基线一致；异常节点先与健康节点对比
node_guid设备全局唯一标识IB fabric、资产映射、跨工具关联时有用
phys_port_cnt物理端口数量双口卡、单口 VF、DPU 环境要特别确认端口编号
max_qp/max_cq/max_mr资源上限大规模多进程、多容器或高连接数 RDMA 服务可能碰到资源耗尽
映射习惯： 把 hca_id、PCI BDF、netdev、NUMA node、GPU PCI 拓扑放在同一张表里，才能解释 NCCL 选哪块 HCA、跨不跨 NUMA、是否经过 PCIe switch。
# mlx5 设备常用映射方法
for dev in /sys/class/infiniband/*; do
  name=$(basename "$dev")
  echo "== $name =="
  readlink -f "$dev/device"
  ls "$dev/device/net" 2>/dev/null || true
  cat "$dev/device/numa_node" 2>/dev/null || true
done

6. 端口状态、物理状态与速率线索

端口是 RDMA 应用真正要用的通信入口。最关键字段是 state、phys_state、active_mtu、link_layer、active_speed/active_width 或等价速率字段。不同设备输出细节会不同，但排障目标一致：端口是否 active，链路是否跑在预期模式。

# 只看端口相关关键字段
ibv_devinfo -d mlx5_0 -i 1 | egrep 'port:|state:|phys_state:|active_mtu|link_layer|active_speed|active_width|rate'

# 和内核 RDMA link 视角交叉验证
rdma link show

# RoCE 场景还要看对应 netdev
ip -br link
ethtool ens5f0 | egrep 'Speed|Link detected'
字段正常线索异常排查方向
statePORT_ACTIVEDOWN/INIT 时查驱动、线缆、交换机端口、netdev、SM 或 fabric
phys_state以设备输出为准，常见是 LinkUp/Polling 等语义物理层未建立时优先查光模块、线缆、FEC、交换机 profile
active_speed/active_width与 100G/200G/400G/IB NDR 等预期匹配降速、降宽、链路 flap 或混插线缆可能导致性能异常
link_layerEthernet 表示 RoCE，InfiniBand 表示 IB决定后续用 IP/RoCE 还是 IB fabric 的排障路径
不要只看 active： 端口 active 但速率降级、MTU 不一致、PFC/ECN 错误、GID index 选错，仍然会让 NCCL 慢、丢包、重传或直接连接失败。

7. MTU、active_mtu 与路径 MTU

active_mtu 是 verbs 端口当前可用 MTU 的重要线索。IB 常见 2048/4096；RoCE 环境中还要同时看 Linux netdev MTU，例如 1500、9000。AI 训练网络里，MTU 不一致会导致 RoCE 性能差、丢包、NCCL 报错或 fallback。

# verbs 视角
ibv_devinfo -d mlx5_0 -i 1 | grep -E 'max_mtu|active_mtu'

# RoCE 对应以太网接口的 MTU
ip link show ens5f0
cat /sys/class/net/ens5f0/mtu

# 非破坏性检查大包路径，按环境选择合适大小
ping -M do -s 8972 10.10.20.12 -c 3
概念说明排障价值
max_mtu端口支持的最大 verbs MTU能力上限，不代表当前正在使用
active_mtu端口当前 active 的 verbs MTUNCCL/RDMA 路径 MTU 判断的基础字段
netdev MTURoCE 对应以太网接口 MTURoCEv2 走 UDP/IP，和 jumbo frame、交换机 MTU 密切相关
路径 MTU从源到目的整条路径可通过的 MTU任一跳不支持都会导致分片、丢包或性能下降
变更警告： 修改 MTU 可能瞬断流量，并且必须端到端一致：主机 netdev、bond/VLAN、交换机端口、fabric profile、对端节点都要匹配。ibv_devinfo 只读，不负责修复 MTU。

8. link_layer：RoCE 与 InfiniBand 线索

link_layer 是排障分叉点。Ethernet 通常表示 RoCE，需要同时考虑 IP 地址、GID、VLAN、MTU、PFC/ECN、交换机 QoS 和 UDP/IP 路径；InfiniBand 则更关注 Subnet Manager、LID、P_Key、IB fabric 路由、SL/VL 和 HCA 端口状态。

RoCE 线索
link_layer: Ethernet；GID 表常包含 IPv4/IPv6 映射或 RoCE v1/v2 类型；需要用 ip、ethtool、rdma link、交换机 ECN/PFC counters 继续验证。
InfiniBand 线索
link_layer: InfiniBand；关注 lid、sm_lid、pkey_tbl_len、P_Key 表；需要用 ibstat、ibnetdiscover、perfquery 等 fabric 工具继续验证。
# 判断当前端口链路类型
ibv_devinfo -d mlx5_0 -i 1 | grep link_layer

# RoCE：把 HCA 关联到 netdev 和 IP
ls /sys/class/infiniband/mlx5_0/device/net
ip addr show ens5f0
rdma link show

# IB：查看 LID/SM/P_Key 线索
ibv_devinfo -v -d mlx5_0 -i 1 | egrep 'lid|sm_lid|pkey|link_layer'
心智模型： RoCE 是“RDMA verbs + 以太网/IP fabric”；InfiniBand 是“RDMA verbs + IB fabric”。同样是 verbs，底层网络排障工具和字段完全不同。

对比图：RoCE 与 InfiniBand 排障分叉

看到 link_layer 后再选择工具链；RoCE 和 InfiniBand 的“同名 RDMA 问题”经常需要完全不同的证据。

9. GID 表与 RoCE 地址选择

GID 是 RDMA 地址选择的核心字段之一。RoCE 环境中，同一端口可能有多个 GID index，对应 IPv6 link-local、IPv4-mapped、VLAN、RoCE v1/v2 或不同地址族。NCCL、MPI、UCX、libfabric 和自研服务选错 GID index 时，症状可能是连接失败、跨网段不通、性能异常或走到错误网卡。

# 查看 GID 表，详细输出更有价值
ibv_devinfo -v -d mlx5_0 -i 1 | sed -n '/GID/p;/gid/p'

# sysfs 中也可观察 GID 与类型，路径随驱动存在差异
ls /sys/class/infiniband/mlx5_0/ports/1/gids
for i in /sys/class/infiniband/mlx5_0/ports/1/gids/*; do
  idx=$(basename "$i")
  printf 'gid[%s]=%s ' "$idx" "$(cat "$i")"
  cat "/sys/class/infiniband/mlx5_0/ports/1/gid_attrs/types/$idx" 2>/dev/null || true
done

# NCCL 常见调试环境变量示例
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET NCCL_IB_HCA=mlx5_0 NCCL_IB_GID_INDEX=3 ./train.sh
现象GID 相关解释下一步
同机房节点可通，跨网段不通选到 link-local 或错误 VLAN 的 GID对照 GID index、IP 地址、路由、VLAN 和 NCCL/UCX 配置
NCCL 日志显示使用 IB/RDMA 但性能差可能选到非预期 HCA、GID 或网段固定 NCCL_IB_HCA、NCCL_IB_GID_INDEX 做 A/B
容器内 GID 表缺失或不一致设备、sysfs 或 net namespace 暴露不完整检查 RDMA device plugin、hostNetwork、CNI 和挂载
RoCEv1/v2 混淆不同 GID type 走不同封装语义以集群标准为准，统一驱动、固件和 NCCL/UCX 配置
GID 提醒： “GID index 3 是正确值”不是普适规则。正确 index 取决于 HCA、驱动、IP/VLAN、RoCE 类型和集群配置，必须在目标节点上采集确认。

10. P_Key 与 InfiniBand 分区

P_Key 是 InfiniBand 分区机制的核心字段，类似 fabric 层访问隔离。RoCE 环境通常不靠 P_Key 做以太网隔离；IB 环境中 P_Key 不匹配可能导致端口 active 但通信失败。ibv_devinfo -v 可展示 P_Key 表长度和表项线索。

# 查看 P_Key 相关字段
ibv_devinfo -v -d mlx5_0 -i 1 | egrep 'pkey|P_Key|pkey_tbl_len'

# sysfs 查看 P_Key 表
ls /sys/class/infiniband/mlx5_0/ports/1/pkeys
for p in /sys/class/infiniband/mlx5_0/ports/1/pkeys/*; do
  echo "$(basename "$p") $(cat "$p")"
done
字段/表项含义排障价值
pkey_tbl_len端口 P_Key 表长度判断 fabric 是否下发了分区表项
0x7fff常见 default limited membership P_Key默认分区可见不代表目标业务分区可用
0xffff常见 default full membership P_Key权限语义要结合 IB fabric 配置确认
自定义 P_Key业务或租户隔离分区对端和本端 P_Key 不匹配会导致连接失败
IB 排障顺序： 先看端口 active 和 SM/LID，再看 P_Key，再看路由、SL/VL 和性能计数。不要只凭 ibv_devinfo 判断整个 fabric 健康。

11. cap_flags、atomics、ODP 与资源上限

详细输出中的能力字段决定应用能否使用某些 verbs 特性。多数 NCCL 基础通信不需要你逐个调这些字段，但当涉及 GPUDirect RDMA、SHARP/collectives、MPI one-sided、原子操作、ODP、内存注册缓存或高连接数服务时，能力差异会变成真实问题。

能力/资源用途异常影响
device_cap_flags设备能力位集合特定 verbs 功能不可用，应用可能 fallback 或启动失败
Atomic capabilitiesRDMA 原子操作支持范围MPI/数据库/自研 RDMA 协议可能依赖原子语义
ODPOn-Demand Paging，减少部分内存注册负担不支持时应用需走传统 MR 注册路径
max_qp_wr/max_sgeQP 工作请求和 scatter-gather 上限高吞吐应用参数过大时创建 QP 或 post WR 失败
max_mr/max_mr_sizeMemory Region 数量和大小大模型训练和 RDMA storage 的内存注册压力可能触顶
# 抽取能力和资源字段做基线对比
ibv_devinfo -v -d mlx5_0 | egrep 'cap_flags|max_qp|max_cq|max_mr|max_sge|max_qp_wr|atomic|ODP|odp'

# 对比两台节点的能力差异
ssh node-a 'ibv_devinfo -v -d mlx5_0' > /tmp/node-a.ibv
ssh node-b 'ibv_devinfo -v -d mlx5_0' > /tmp/node-b.ibv
diff -u /tmp/node-a.ibv /tmp/node-b.ibv
解释提醒： 能力字段名称和展示细节随 rdma-core、驱动和硬件不同而变化。自动化脚本应容忍字段缺失，并保留原始输出用于人工复核。

12. NCCL RDMA readiness 检查

ibv_devinfo 不能证明 NCCL 一定走 RDMA，但它能确认 NCCL 走 RDMA 前的基础条件：HCA 可见、目标端口 active、link layer 符合集群类型、GID/P_Key 可解释、MTU 合理、设备名可用于 NCCL_IB_HCA。之后还要用 NCCL 日志、nccl-tests、GPU 拓扑和 RDMA counters 验证。

最小 readiness 清单

检查命令通过标准
HCA 可见ibv_devinfo -l训练用 HCA 出现在容器/宿主机中
端口 activeibv_devinfo -d mlx5_0 -i 1state: PORT_ACTIVE
RoCE/IB 类型正确grep link_layer与集群设计一致
MTU 合理grep active_mtu + ip link端到端 MTU 符合集群基线
地址/分区可解释ibv_devinfo -vRoCE GID 或 IB P_Key 与应用配置一致
NCCL 实际选择NCCL_DEBUG=INFO日志显示 NET/IB 使用预期 HCA/GID，而非 Socket fallback
# NCCL 排障常用启动前采集
ibv_devinfo -v -d mlx5_0 -i 1
rdma link
ip route get 10.10.20.12
nvidia-smi topo -m

# NCCL 运行时确认网络选择
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET \
NCCL_IB_HCA=mlx5_0 NCCL_SOCKET_IFNAME=ens5f0 \
./build/all_reduce_perf -b 8M -e 8G -f 2 -g 8
不要过度推断： ibv_devinfo 没有 GPU 拓扑、PCIe ACS、IOMMU、GDRCopy、CUDA IPC、NCCL 算法和交换机拥塞信息。NCCL 慢时，它是第一层证据，不是最终判决。

13. ibv_devinfo vs ibstat/rdma/mlxlink

RDMA 排障经常需要多个工具交叉验证。ibv_devinfo 是 verbs 视角；ibstat 更偏 IB/CA 状态摘要；rdma 是内核 RDMA netlink 视角；mlxlink 更接近 Mellanox/NVIDIA 物理链路和模块/FEC 诊断。

工具主要视角适合回答不适合替代
ibv_devinfo用户态 verbs 设备和端口属性应用能看到哪些 HCA/port/GID/P_Key/caps物理误码、交换机 QoS、NCCL 实际选路
ibstatCA/port 状态摘要，IB 语义更强IB 端口 state、LID、SM、rate 简查详细 verbs caps 和 RoCE GID 解释
rdma link内核 RDMA link 与 netdev 关联RDMA 设备、端口和网络接口映射完整 HCA 能力和 GID/P_Key 细节
mlxlinkNVIDIA/Mellanox 物理链路FEC、模块、误码、链路降级、物理层诊断非 mlx 设备或通用 verbs 资源信息
ib_write_bw/qperf主动性能测试实际 RDMA latency/bandwidth 是否达标静态设备能力基线
# 典型分层组合
ibv_devinfo -v -d mlx5_0 -i 1     # verbs 设备和端口
rdma link show                    # RDMA link 与 netdev
ibstat                            # IB/CA 状态摘要
mlxlink -d /dev/mst/mt4129_pciconf0 # mlx 物理链路线索，设备路径按现场调整
ib_write_bw -d mlx5_0 -i 1 peer   # 主动 RDMA 带宽测试
工具选择原则： 静态能力用 ibv_devinfo，内核映射用 rdma，IB fabric 用 IB 工具，物理链路用 mlxlink/ethtool，真实性能用 perftest/qperf/NCCL tests。

14. 自动化基线采集

AI 集群中不要等训练失败才第一次看 RDMA。建议在节点验收、驱动升级、固件升级、交换机变更、Kubernetes 节点加入和大作业上线前采集基线，并保留原始文本。

# 只读采集脚本：不会修改系统状态
#!/usr/bin/env bash
set -euo pipefail
out=${1:-/tmp/rdma-baseline-$(hostname -s)}
mkdir -p "$out"

date -Is > "$out/timestamp.txt"
hostname -f > "$out/hostname.txt"
uname -a > "$out/uname.txt"
ibv_devinfo -l > "$out/ibv-devices.txt" 2>&1 || true
ibv_devinfo -v > "$out/ibv-devinfo-v.txt" 2>&1 || true
rdma link > "$out/rdma-link.txt" 2>&1 || true
ip -br addr > "$out/ip-addr.txt" 2>&1 || true
for dev in /sys/class/infiniband/*; do
  [ -e "$dev" ] || continue
  name=$(basename "$dev")
  mkdir -p "$out/sysfs-$name"
  cp "$dev/node_guid" "$out/sysfs-$name/node_guid" 2>/dev/null || true
  ls "$dev/device/net" > "$out/sysfs-$name/netdevs.txt" 2>/dev/null || true
  cat "$dev/device/numa_node" > "$out/sysfs-$name/numa_node.txt" 2>/dev/null || true
done
采集维度为什么保留对比场景
原始 ibv_devinfo -v字段随版本变化，原文最可靠健康节点 vs 异常节点、升级前 vs 升级后
rdma link 与 ip把 HCA 和 netdev/IP 关联起来RoCE 选错接口、容器网络命名空间问题
NUMA/PCI 映射解释 GPU-HCA 亲和性NCCL 跨 NUMA、PCIe 拓扑异常
时间戳和内核定位变更窗口驱动、固件、内核升级后回归
脚本原则： 自动化解析可以提取少数字段，但必须保存完整原始输出。RDMA 字段命名和展示细节太依赖硬件/驱动，过度结构化容易丢证据。

15. 容器、Kubernetes 与设备暴露

AI 训练大多运行在容器中。宿主机 ibv_devinfo 正常，不代表 Pod 内正常；Pod 内正常，也不代表 NCCL 选到正确 HCA。容器排障要同时看设备节点、sysfs、net namespace、CNI、RDMA device plugin 和环境变量。

# 宿主机：设备节点
ls -l /dev/infiniband
ls -l /sys/class/infiniband

# Pod 内：确认是否看得到同样的 verbs 设备
ibv_devinfo -l
ibv_devinfo -d mlx5_0 -i 1
ls -l /dev/infiniband
ip -br addr

# Kubernetes 侧常见线索
kubectl describe pod train-0 | grep -i -E 'rdma|resource|device|network'
kubectl exec train-0 -- env | grep -E 'NCCL|UCX|FI_'
设备暴露
需要 /dev/infiniband/uverbs*、rdma_cm、对应 sysfs 和合适 cgroup device 权限。SR-IOV VF 场景还要确认 VF 与 netdev/IP 绑定。
网络命名空间
RoCE 依赖 IP/GID/netdev，Pod 网络、hostNetwork、Multus、VLAN 和路由都会影响 GID 与 NCCL socket bootstrap。
NCCL 配置
NCCL_IB_HCA、NCCL_SOCKET_IFNAME、NCCL_IB_GID_INDEX、NCCL_IB_DISABLE 常直接改变选路。
权限与安全
有些集群限制 privileged、capabilities 或设备插件资源名；不要通过放宽权限掩盖设备映射错误。
容器误区： Pod 内 ibv_devinfo -l 能看到设备，只证明 verbs 设备可见；还要确认 Pod IP/路由/GID 与 NCCL 选择一致。

16. 常见故障与排障流程

RDMA 故障最好按层排查：工具可用性、设备可见性、端口状态、link layer、MTU、GID/P_Key、对端一致性、主动性能测试、应用日志。不要从 NCCL 错误直接跳到交换机或驱动结论。

故障 1：No IB devices found
检查驱动、/sys/class/infiniband、/dev/infiniband、容器设备挂载、SR-IOV VF 和 rdma-core 安装。
故障 2：端口不是 PORT_ACTIVE
查 netdev up、光模块/线缆、交换机端口、IB SM、FEC/profile、固件和 link flapping。
故障 3：RoCE 连接失败
重点看 GID index、IP 路由、VLAN、MTU、PFC/ECN、RoCE type、对端是否同网段或可路由。
故障 4：IB 连接失败
重点看 LID、SM、P_Key、fabric 路由、端口 state、partition membership。
故障 5：NCCL fallback 到 Socket
看 NCCL 日志、NCCL_IB_DISABLE、NCCL_IB_HCA、容器设备、libibverbs/provider 是否可用。
故障 6：能连但带宽低
查 MTU、速率、NUMA/GPU 拓扑、PCIe、PFC/ECN、重传/丢包 counters、单流限制和 CPU 绑定。
# 一条保守的只读 triage 路径
ibv_devinfo -l
ibv_devinfo -v -d mlx5_0 -i 1
rdma link show
ip route get <peer_ip>
ip -br addr
ethtool <roce_netdev> | egrep 'Speed|Link detected'
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NET ./run_nccl_test.sh

17. 生产安全与变更边界

ibv_devinfo 本身是只读命令，适合在生产节点上采集。但它常引出后续变更，例如改 MTU、改 PFC/ECN、升级固件、调整 NCCL 环境变量、切换 GID index 或替换线缆。这些变更必须灰度、可回滚，并且避开训练高峰。

动作风险安全做法
采集 ibv_devinfo低，通常只读可批量执行，但注意输出中可能包含资产标识
调整 NCCL 环境变量中，可能改变作业选路单作业 A/B，保留 NCCL 日志和性能曲线
修改 MTU/PFC/ECN高，可能影响整网端到端方案、交换机联动、维护窗口、回滚预案
升级固件/驱动高，可能需要重启或影响兼容性同型号灰度、基线采集、回滚包和节点排空
替换线缆/模块中到高，可能链路中断确认端口映射，维护窗口，替换后复测速率和 counters
生产警告： 不要在只拿到 ibv_devinfo 单一证据时批量改网络。RDMA 故障常是端到端系统问题，主机、交换机、应用和作业调度都可能参与。
# 安全变更前后至少保留这些只读证据
ibv_devinfo -v > before.ibv_devinfo.txt
rdma link > before.rdma-link.txt
ip -br addr > before.ip-addr.txt
ethtool ens5f0 > before.ethtool.txt

# 变更后再采集并 diff
ibv_devinfo -v > after.ibv_devinfo.txt
diff -u before.ibv_devinfo.txt after.ibv_devinfo.txt

18. 练习任务与学习路线

第一阶段：会读字段

  • 在一台节点上运行 ibv_devinfo -l，记录所有 HCA 名称。
  • 对每个 HCA 运行 ibv_devinfo -d DEV -i 1，找出 state、active_mtu、link_layer。
  • 把 hca_id、netdev、IP、NUMA node 写成一张表。

第二阶段：会分 RoCE/IB

  • 看到 link_layer: Ethernet 时，继续查 GID 表、IP、MTU、rdma link 和 ethtool。
  • 看到 link_layer: InfiniBand 时，继续查 LID、SM、P_Key、ibstat 和 fabric 状态。
  • 解释为什么“端口 active”不是“NCCL 一定走 RDMA”。

第三阶段：工程化排障

  • 写一个只读基线采集脚本，保存 ibv_devinfo -v、rdma link、ip -br addr 和 sysfs 映射。
  • 对比一台健康节点和一台异常节点的 active_mtu、GID 表、固件版本和 link layer。
  • 用 NCCL_DEBUG=INFO 验证 NCCL 是否使用预期 HCA/GID。
# 练习：生成一份本机 RDMA 快照
mkdir -p /tmp/ibv-lab
ibv_devinfo -l | tee /tmp/ibv-lab/devices.txt
ibv_devinfo -v | tee /tmp/ibv-lab/ibv-devinfo-v.txt
rdma link | tee /tmp/ibv-lab/rdma-link.txt
ip -br addr | tee /tmp/ibv-lab/ip-addr.txt

# 练习：抽取端口关键字段
awk '/hca_id:|port:|state:|phys_state:|active_mtu|link_layer|gid_tbl_len|pkey_tbl_len/' /tmp/ibv-lab/ibv-devinfo-v.txt
学习目标： 能把 ibv_devinfo 输出翻译成一句可操作结论：哪块 HCA、哪个端口、什么 link layer、什么 MTU、什么 GID/P_Key 线索，以及下一步该用哪个工具验证。
