docker 深度教程：AI Infra 中的镜像、容器、GPU 与训练排障

这份教程面向 AI Infra / Linux 运维和训练平台场景。它不把 docker 当成单纯的“启动容器命令”，而是从镜像层、容器进程、GPU runtime、数据卷、网络、资源隔离、/dev/shm、日志与交互调试出发，讲清楚如何构建、运行、约束、排障和安全管理训练容器。

镜像与容器GPU RuntimeNVIDIA训练任务VolumeNetworkcgroupshm/ipcBuildKit安全基线
一句话理解： Docker 把“用户空间文件系统 + 进程启动参数 + 隔离/限额规则”打包成可重复运行的环境；AI Infra 关注的是这个环境是否能稳定访问 GPU、数据、网络和足够的共享内存。
最重要原则： 训练容器先用只读/最小权限/显式资源参数启动，逐项放开 GPU、volume、IPC、端口和 capability；不要为了省事长期使用 --privileged、宿主机根目录挂载或不受控的 :latest 镜像。

1. Docker 在 AI Infra 中解决什么问题

AI 训练环境通常同时依赖 CUDA、cuDNN、NCCL、Python、PyTorch/TensorFlow、系统库、编译器、网络插件、数据挂载和集群调度参数。Docker 的价值是把这些运行时依赖固化成镜像，把每次训练启动变成可重复的容器进程。

可重复
同一个镜像 digest、同一组启动参数和同一份代码，能显著减少“机器 A 可以、机器 B 不行”的环境差异。
可隔离
用 namespace/cgroup 隔离进程、网络、文件系统和资源限额，避免训练任务污染宿主环境。
可交付
把研发镜像、评测镜像和线上推理镜像以 registry 方式交付，便于 CI/CD、回滚和审计。
# 最小健康检查：确认 docker client/server 可用
docker version
docker info

# 拉取一个 CUDA 基础镜像并验证 GPU 可见性
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
边界提醒： Docker 不会替你解决驱动版本、内核模块、NVIDIA Container Toolkit、RDMA/NCCL 网络和存储性能问题；它只是把用户空间环境变得可控。

信息图：Docker 在训练节点上的整体模型

容器不是虚拟机：它共享宿主机内核。GPU、RDMA、文件系统和网络能力最终都来自宿主机，只是通过 runtime 和参数暴露给容器。

2. 安装、权限与基本健康检查

排查 Docker 问题时先分清三层：Docker CLI 是否能连接 daemon、daemon 是否正常管理容器、宿主机 GPU/网络/存储是否满足训练任务要求。

检查项命令判断重点
Client/Server 版本docker version能看到 Client 和 Server；只有 Client 通常说明 daemon 未连接。
Daemon 配置docker info确认 cgroup driver、storage driver、runtimes、registry mirror、root dir。
当前用户权限groups是否在 docker 组；生产环境不应把 Docker 权限视为普通低权限。
GPU 宿主状态nvidia-smi驱动加载、GPU 可见、无异常 Xid 或掉卡。
# daemon 是否运行
systemctl status docker --no-pager

# 查看 Docker daemon 关键配置
docker info --format 'Runtimes={{json .Runtimes}} Cgroup={{.CgroupDriver}} Storage={{.Driver}}'

# 当前用户如果不能访问 docker.sock，会出现 permission denied
ls -l /var/run/docker.sock
权限警告： 能访问 /var/run/docker.sock 基本等价于可在宿主机获得 root 级控制权。不要把用户加入 docker 组后仍当成低权限账户管理。

3. 镜像基础：pull、tag、inspect、清理

镜像是容器的只读模板。AI 镜像常见问题包括 tag 漂移、基础镜像过大、CUDA 版本与驱动不匹配、pip/apt 缓存膨胀，以及没有记录构建来源。

# 拉取镜像
docker pull nvidia/cuda:12.4.1-cudnn-runtime-ubuntu22.04

# 查看本地镜像
docker image ls

# 查看镜像元数据：入口命令、环境变量、层、架构
docker image inspect nvidia/cuda:12.4.1-cudnn-runtime-ubuntu22.04

# 给内部 registry 打 tag
docker tag train:dev registry.example.com/ai/train:2026-04-25

# 推送镜像
docker push registry.example.com/ai/train:2026-04-25
概念建议原因
tag开发可用语义 tag，生产记录 digest:latest 会漂移，复现实验困难。
runtime 镜像训练运行优先 runtime，编译单独 builder减少体积和攻击面。
清理先 dry-run 式查看，再 prune避免删除仍需回滚的镜像。
# 只查看可清理对象，不马上删除
docker system df
docker image ls --filter dangling=true

# 确认无用后再清理悬空镜像
docker image prune
清理提醒： docker system prune -a 会删除所有未被容器引用的镜像，训练节点上可能影响回滚和离线启动。执行前先看 docker system df 和镜像列表。

4. 容器生命周期：run、ps、stop、rm

docker run 本质上是 create + start：从镜像创建容器可写层，配置 namespace、mount、network、env、resource limit，然后启动进程。

# 一次性容器：退出后自动删除
docker run --rm ubuntu:22.04 cat /etc/os-release

# 后台运行服务容器
docker run -d --name tensorboard -p 6006:6006 -v "$PWD/runs:/runs:ro" \
  python:3.11-slim python -m http.server 6006 -d /runs

# 查看容器
docker ps
docker ps -a

# 优雅停止，确认后删除
docker stop tensorboard
docker rm tensorboard
参数含义AI Infra 用法
--rm退出后删除容器适合短命令验证，不适合需要保留现场的失败训练。
--name固定容器名便于 logs、exec、监控采集定位。
-d后台运行服务、训练 launcher、长任务。
--entrypoint覆盖镜像入口调试镜像启动脚本或进入 shell。
调试习惯： 训练失败时不要马上 rm 容器；先 docker logs、docker inspect、必要时 docker commit 保存现场。

流程图：GPU 容器从宿主机到训练进程

容器内的 CUDA 用户态库来自镜像，GPU 驱动和设备节点来自宿主机；两者必须兼容。

5. GPU 容器运行：NVIDIA runtime 与验证

现代 Docker 通常使用 --gpus 参数请求 GPU。前提是宿主机安装并配置了 NVIDIA Container Toolkit，且 Docker daemon 能识别对应 runtime。

# 宿主机先确认 GPU 正常
nvidia-smi

# Docker 侧确认 runtime 能被识别
docker info --format '{{json .Runtimes}}'

# 容器内验证 GPU
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

# 指定 GPU 0 和 2
docker run --rm --gpus '"device=0,2"' nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

PyTorch 快速验证

docker run --rm --gpus all pytorch/pytorch:2.3.1-cuda12.1-cudnn8-runtime \
  python - <<'PY'
import torch
print("cuda:", torch.cuda.is_available())
print("count:", torch.cuda.device_count())
print("name:", torch.cuda.get_device_name(0) if torch.cuda.is_available() else "none")
PY
版本心智模型： 宿主机 NVIDIA 驱动必须支持容器镜像中的 CUDA 运行时版本；容器通常不安装内核驱动，只带用户态 CUDA/cuDNN/NCCL 等库。
现象优先检查常见原因
容器内没有 nvidia-smi镜像是否包含工具、runtime 是否注入用错镜像或 --gpus 未生效。
CUDA driver version is insufficient宿主驱动版本驱动太旧，不支持镜像 CUDA。
只看到部分 GPU--gpus、NVIDIA_VISIBLE_DEVICES、MIG设备选择或 MIG 分区配置。

6. AI 训练数据与模型目录：volume/bind/tmpfs

训练容器的文件系统分三类：镜像只读层、容器可写层、外部挂载。大型数据集、checkpoint、日志和缓存不要写在容器可写层里，应该显式挂载。

挂载方式命令形式适合场景
bind mount-v /host/data:/data:ro挂载宿主机数据集、代码、checkpoint。
named volume-v pip-cache:/root/.cache/pip跨容器复用缓存或状态。
tmpfs--tmpfs /tmp:rw,size=8g高速临时文件，不需要持久化。
# 只读挂载数据集，读写挂载输出目录
docker run --rm --gpus all \
  -v /datasets/imagenet:/data/imagenet:ro \
  -v /checkpoints/exp42:/out:rw \
  -v "$PWD":/workspace:ro \
  -w /workspace \
  registry.example.com/ai/train:2026-04-25 \
  python train.py --data /data/imagenet --output /out

# 使用 --mount 语法更明确
docker run --rm \
  --mount type=bind,src=/datasets,dst=/data,readonly \
  --mount type=volume,src=pip-cache,dst=/root/.cache/pip \
  ubuntu:22.04 bash -lc 'df -h /data /root/.cache/pip'
数据安全： 不要把 /、/var/run/docker.sock、云厂商凭据目录或宿主机私钥随意挂入训练容器。能写宿主敏感路径的容器可以破坏节点。

7. 网络模式、端口映射与分布式训练

Docker 默认使用 bridge 网络，容器有独立网络 namespace。训练场景要根据需求选择：单机调试通常 bridge 足够，分布式训练常需要 host 网络、固定端口、NCCL 网卡选择和防火墙配合。

# bridge 模式：把容器内 8888 映射到宿主机 18888
docker run --rm -p 18888:8888 jupyter/base-notebook start-notebook.py

# host 网络：容器直接使用宿主机网络 namespace
docker run --rm --network host registry.example.com/ai/train:2026-04-25 \
  python -m torch.distributed.run --nproc_per_node=8 --master_addr=10.0.0.11 \
  --master_port=29500 train.py

# 容器内检查路由、DNS、监听端口
docker exec -it train-0 bash -lc 'ip addr; ip route; ss -lntp; getent hosts registry.example.com'
模式优点风险/限制
bridge隔离好，端口显式映射NCCL 多机通信和服务发现更复杂。
host网络路径最直接，常用于高性能训练端口冲突、隔离弱、容器能看到宿主网络。
自定义 bridge容器间 DNS 名称好用仍有 NAT/路由复杂度。
NCCL 提示： 多网卡节点经常需要显式设置 NCCL_SOCKET_IFNAME，并确认容器内能看到目标网卡名称；host 网络能减少一层变量，但不替代 RDMA/IB 配置。

8. 资源限制：CPU、内存、GPU、ulimit

Docker 使用 cgroup 管理 CPU、内存、pids 等资源。AI 训练容易触发 OOM、文件句柄不足、锁页内存不足、进程数过多、DataLoader worker 争抢 CPU 等问题。

# 限制 CPU 和内存，避免压垮共享节点
docker run --rm --cpus 16 --memory 96g --memory-swap 96g ubuntu:22.04 \
  bash -lc 'nproc; free -h'

# 训练常见 ulimit：memlock 和 stack
docker run --rm --gpus all \
  --ulimit memlock=-1:-1 \
  --ulimit stack=67108864 \
  registry.example.com/ai/train:2026-04-25 python train.py

# 查看容器实时资源
docker stats
参数作用训练影响
--cpus限制 CPU 时间配额影响 DataLoader、预处理、通信线程。
--cpuset-cpus绑定 CPU 核适合 NUMA/GPU 拓扑优化。
--memory限制内存超过可能被 OOM kill。
--pids-limit限制进程/线程数DataLoader worker 太多时可能失败。
观测提醒： 容器内 free、top、Python 看到的资源不一定等于 cgroup 限额。必要时查看 /sys/fs/cgroup 或宿主机监控。

对比图：训练容器关键资源面

AI 训练容器的运行质量取决于 GPU、内存/IPC、存储和网络的组合，而不是单个 --gpus all 参数。

9. 共享内存、IPC 与 PyTorch DataLoader

Docker 默认 /dev/shm 通常很小。PyTorch DataLoader、多进程队列、NCCL、浏览器/Jupyter、Ray 等组件都可能用共享内存，导致 “bus error”、“DataLoader worker exited unexpectedly” 或训练卡死。

# 查看容器内 /dev/shm
docker run --rm ubuntu:22.04 df -h /dev/shm

# 增大共享内存
docker run --rm --gpus all --shm-size 64g registry.example.com/ai/train:2026-04-25 \
  python train.py --num-workers 16

# 如果需要与宿主或同机容器共享 IPC，谨慎使用
docker run --rm --ipc=host --gpus all registry.example.com/ai/train:2026-04-25 python train.py
参数优点风险
--shm-size 64g隔离仍较好，解决多数 DataLoader 共享内存不足需要按节点内存规划。
--ipc=host兼容某些多进程/NCCL/性能场景隔离变弱，可能与宿主/其他容器 IPC 资源互相影响。
--tmpfs /dev/shm:size=64g显式 tmpfs 挂载语法和运行时支持需测试。
实战建议： 单机训练优先尝试 --shm-size；只有明确需要共享 IPC 或框架文档要求时，再使用 --ipc=host。

10. 日志、exec、cp、commit 与现场调试

容器调试要尽量保留现场：先看日志和元数据，再进入容器确认环境，最后再决定是否复制文件或保存临时镜像。

# 查看日志，限制输出量避免刷屏
docker logs --tail 200 train-0
docker logs -f --since 10m train-0

# 进入正在运行的容器
docker exec -it train-0 bash

# 在容器里快速检查训练环境
docker exec train-0 bash -lc 'pwd; id; env | sort | grep -E "CUDA|NCCL|NVIDIA"; df -h; nvidia-smi'

# 从失败容器复制日志和配置
docker cp train-0:/workspace/output/train.log ./train.log
docker cp train-0:/workspace/config.yaml ./config.yaml
命令用途注意
docker inspect查看完整启动参数、mount、network、env、state排障时比口述启动命令可靠。
docker diff查看容器可写层变更定位程序写到了哪里。
docker commit把现场保存成临时镜像只适合救急，不应替代 Dockerfile。
docker events观察 OOM、die、restart 等事件适合定位容器被谁停止。
# 保存失败现场镜像，便于离线分析
docker commit train-0 debug/train-0-failed:2026-04-25
docker run --rm -it --entrypoint bash debug/train-0-failed:2026-04-25
现场纪律： docker exec 进容器手工安装包可以帮助定位问题，但最终修复应回写到 Dockerfile 或启动脚本，否则下一次训练不可复现。

11. 构建镜像：Dockerfile、BuildKit、缓存

AI 镜像构建的关键是可复现、缓存友好、体积可控。把变化频率低的系统依赖放前面，把频繁变化的代码放后面；训练运行镜像不要保留不必要的编译缓存和凭据。

# syntax=docker/dockerfile:1.7
FROM nvidia/cuda:12.4.1-cudnn-runtime-ubuntu22.04

ENV DEBIAN_FRONTEND=noninteractive \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

RUN apt-get update && apt-get install -y --no-install-recommends \
    python3 python3-pip git ca-certificates tini \
  && rm -rf /var/lib/apt/lists/*

WORKDIR /workspace
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    python3 -m pip install --no-cache-dir -r requirements.txt

COPY . .
ENTRYPOINT ["/usr/bin/tini", "--"]
CMD ["python3", "train.py"]
# 开启 BuildKit 构建，并打上明确 tag
DOCKER_BUILDKIT=1 docker build -t registry.example.com/ai/train:2026-04-25 .

# 查看镜像历史，定位大层
docker history registry.example.com/ai/train:2026-04-25
构建策略好处注意
固定基础镜像 tag/digest复现实验需要定期安全更新。
依赖文件先 COPY提高 pip/apt 缓存命中不要过早 COPY 全仓库。
多阶段构建去掉编译工具链CUDA 扩展需要保留运行时库。
BuildKit cache mount加速构建缓存不应成为运行时依赖。

12. Build/Run 生产模式与训练脚本模板

生产训练任务需要把镜像、命令、数据、输出、资源、网络和日志参数显式写清楚。不要依赖交互 shell 里的隐式环境。

#!/usr/bin/env bash
set -euo pipefail

IMAGE="registry.example.com/ai/train:2026-04-25"
NAME="train-$(date +%Y%m%d-%H%M%S)"
DATA="/datasets/imagenet"
OUT="/checkpoints/${NAME}"

mkdir -p "$OUT"

docker run --name "$NAME" --rm \
  --gpus all \
  --network host \
  --shm-size 64g \
  --ulimit memlock=-1:-1 \
  --ulimit stack=67108864 \
  -e NCCL_DEBUG=INFO \
  -e NCCL_SOCKET_IFNAME=eth0 \
  -v "$DATA":/data:ro \
  -v "$OUT":/out:rw \
  "$IMAGE" \
  python3 train.py --data /data --output /out --epochs 90
镜像固定
生产脚本中记录 tag 和 digest，CI 输出 SBOM/扫描报告时更容易追踪。
参数显式
GPU、网络、shm、ulimit、volume、env 都在脚本里声明，便于复现。
输出外置
checkpoint、metrics、日志写到挂载目录，不依赖容器可写层。
调度系统迁移： 这些参数在 Kubernetes、Slurm+Enroot、containerd/nerdctl 中仍有对应概念：设备、挂载、网络、资源、env、entrypoint。

13. 安全：权限、镜像供应链、Secrets

Docker 安全不是一个开关，而是一组边界：镜像来源、容器用户、Linux capability、文件系统权限、设备访问、网络暴露、secret 注入和 socket 挂载。

风险安全做法避免
容器 root 写宿主目录--user $(id -u):$(id -g)、只读挂载训练容器随意写 / 或共享代码库。
权限过大按需添加 --cap-add长期使用 --privileged。
镜像不可追踪固定 tag/digest，记录构建 commit生产拉取 :latest。
凭据泄露运行时挂载 secret，只读且最小范围把 token 写入 Dockerfile 或镜像层。
Docker socket 暴露避免挂载或使用隔离代理-v /var/run/docker.sock:/var/run/docker.sock 给不可信容器。
# 用非 root 用户运行，并把根文件系统设为只读
docker run --rm \
  --user "$(id -u):$(id -g)" \
  --read-only \
  --tmpfs /tmp:rw,size=4g \
  -v "$PWD":/workspace:ro \
  ubuntu:22.04 id

# 查看镜像配置中是否意外写入敏感 env
docker image inspect train:dev --format '{{json .Config.Env}}'
高危参数： --privileged、--pid=host、--network=host、--ipc=host、Docker socket 挂载都可能削弱隔离。训练场景可以按需使用，但必须知道为什么用、谁能用、如何审计。

选择图：docker、podman、nerdctl、crictl 怎么选

这些工具的命令长得相似，但控制对象不同。排障前先确认节点上真正运行的是 Docker Engine、containerd 还是 CRI 管理的 Pod。

14. docker vs podman/nerdctl/crictl

工具控制对象适合场景不适合误用
dockerDocker daemon / Docker Engine本地开发、CI 构建、单机服务、教学和常规镜像流程。把 Docker socket 暴露给不可信租户。
podmanlibpod/OCI runtime，可 rootless多用户 Linux、HPC、希望少依赖常驻 daemon 的场景。假设所有 Docker Compose/插件行为完全一致。
nerdctlcontainerdKubernetes/containerd 节点底层调试，贴近 Docker CLI 的体验。误以为能管理 Docker daemon 里的容器。
crictlKubelet 使用的 CRI runtime排查 Kubernetes Pod、sandbox、容器日志和镜像。日常构建镜像或替代 Dockerfile 工作流。
# 判断当前节点可能有哪些运行时
docker info 2>/dev/null | head
podman info 2>/dev/null | head
nerdctl info 2>/dev/null | head
crictl info 2>/dev/null | head

# K8s/containerd 节点上，docker ps 看不到 kubelet 管理的容器很常见
crictl ps
crictl images
迁移心智： 镜像格式通常是 OCI 兼容的，但 CLI、网络、rootless、volume、GPU 集成和日志路径可能不同。迁移前先验证 GPU、volume、IPC、网络和权限模型。

排障图：训练容器失败时的安全路线

训练容器排障的核心是保留现场、最小复现、一次改变一个变量；不要用大权限掩盖真实根因。

15. 训练容器排障路线图

1. 启动失败

# 看退出码、启动命令、错误日志
docker ps -a --filter name=train-0
docker inspect train-0 --format 'Exit={{.State.ExitCode}} Error={{.State.Error}} Cmd={{json .Config.Cmd}}'
docker logs --tail 200 train-0

# 覆盖 entrypoint 进入 shell
docker run --rm -it --entrypoint bash registry.example.com/ai/train:2026-04-25

2. GPU 不可见或 CUDA 报错

nvidia-smi
docker info --format '{{json .Runtimes}}'
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
docker run --rm --gpus all registry.example.com/ai/train:2026-04-25 \
  python3 -c 'import torch; print(torch.cuda.is_available(), torch.cuda.device_count())'

3. OOM、bus error、DataLoader worker 退出

# 查看是否 OOM killed
docker inspect train-0 --format 'OOMKilled={{.State.OOMKilled}} Exit={{.State.ExitCode}}'
docker events --since 30m --filter container=train-0

# 检查共享内存
docker run --rm --shm-size 64g registry.example.com/ai/train:2026-04-25 df -h /dev/shm

4. 分布式训练卡死

# 容器内检查网络和端口
docker exec train-0 bash -lc 'hostname -I; ip addr; ss -lntp; env | grep -E "NCCL|MASTER|RANK|WORLD"'

# 提高 NCCL 日志粒度
docker run --rm --network host --gpus all \
  -e NCCL_DEBUG=INFO \
  -e NCCL_DEBUG_SUBSYS=INIT,NET \
  -e NCCL_SOCKET_IFNAME=eth0 \
  registry.example.com/ai/train:2026-04-25 python train.py
排障顺序： 先证明宿主机正常，再证明基础 CUDA 镜像正常，再证明你的训练镜像正常，最后才进入数据、网络、shm、ulimit 和业务代码排查。

练习任务

  1. 运行 hello-world 或 ubuntu:22.04，观察 docker ps -a 中的退出状态。
  2. 用 docker run --rm -v "$PWD":/workspace:ro 验证只读挂载。
  3. 用 CUDA 基础镜像执行 nvidia-smi，确认 GPU runtime 是否可用。
  4. 用 --shm-size 对比容器内 df -h /dev/shm。
  5. 构建一个包含 requirements.txt 的最小训练镜像，并用 docker history 查看层大小。
  6. 模拟失败容器，使用 docker logs、inspect、cp 保留现场。
  7. 比较 bridge 与 host 网络下容器内看到的 IP、路由和监听端口。
