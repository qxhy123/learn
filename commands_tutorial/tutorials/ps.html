ps 深度教程：从 Linux 进程模型到生产排障

这份教程围绕 Linux/Unix 命令 ps 展开。它不只列出 ps aux 和 ps -ef 的字段，而是先建立“进程快照”的心智模型，再系统讲清楚 PID/PPID/TTY/STAT、BSD 与 UNIX 选项风格、选择进程、排序、自定义列、进程树、线程、容器视角、与 top/htop/pgrep 的边界，以及生产环境中定位 CPU、内存、僵尸进程和异常父子关系的流程。

信息图进程模型PID/PPIDTTY/STATps auxps -ef排序自定义列进程树生产排障
一句话理解： ps 读取内核暴露的进程信息并输出某一刻的“快照”；它适合回答“现在有哪些进程、由谁启动、状态如何、资源大概占多少”。
实践原则： 先用 ps 观察和缩小范围，再决定是否用 kill、systemctl、strace、top 或日志继续处理；不要把 ps | grep 的一行输出直接当成可安全终止的证据。

1. ps 是什么：进程快照工具

ps 的全称通常理解为 process status。它展示当前系统进程的状态，但“当前”不是持续刷新，而是命令执行瞬间的一次采样。你看到的 CPU、内存、状态、命令行都来自这次采样及内核统计，不等于长期趋势。

它擅长什么
列出进程、确认 PID/PPID、查看启动命令、筛选用户或父进程、排查僵尸和进程树。
它不擅长什么
实时曲线、交互式观察、历史追踪、精确性能分析。那些场景应结合 top、pidstat、sar、日志或 tracing 工具。
它的本质
从内核进程表和 /proc 读取元数据，格式化成一张可筛选、可排序的表。
# 查看当前终端相关进程
ps

# 查看所有用户的所有进程，BSD 风格
ps aux

# 查看所有进程，UNIX 风格
ps -ef

# 按内存从高到低看前 10 个
ps aux --sort=-%mem | head
关键区别： ps 是快照，不会持续刷新；如果一个进程只短暂出现，可能在你执行 ps 时已经结束。

信息图：ps 的整体心智模型

不要把 ps 看作“进程监控器”，而要看作“把内核某一刻的进程信息打印出来的报表工具”。

2. Linux 进程模型：父子关系、生命周期、资源

进程是正在运行或等待运行的程序实例。每个进程有唯一的 PID，通常由另一个进程创建，因此也记录父进程 PPID。进程拥有地址空间、文件描述符、环境变量、当前工作目录、调度状态、凭据和资源统计。

概念含义用 ps 怎么看
PID进程 ID，内核为每个进程分配ps -p 1234
PPID父进程 ID，反映创建或收养关系ps -o pid,ppid,cmd
会话/进程组终端、作业控制和信号传播相关概念ps -o pid,pgid,sid,tty,stat,cmd
资源统计CPU 时间、内存占用、优先级等ps -o pid,pcpu,pmem,rss,vsz,ni,pri,cmd
# 用自定义列看父子关系和调度状态
ps -eo pid,ppid,pgid,sid,tty,stat,comm | head

# 查看某个 PID 的父进程链条起点
ps -o pid,ppid,user,stat,etime,cmd -p 1234
心智模型： 排障时不要只看“进程名”。同一个命令可能被启动多次，真正可靠的定位通常需要 PID、PPID、用户、启动命令、运行时长和进程树一起判断。

3. ps 从哪里读数据：/proc 与快照语义

Linux 上的 ps 通常来自 procps-ng 套件，主要读取 /proc 虚拟文件系统。/proc 不是普通磁盘目录，而是内核把进程和系统状态暴露给用户空间的接口。

# 一个进程在 /proc 下的典型信息
ls /proc/$$
tr '\0' ' ' < /proc/$$/cmdline; echo
grep -E '^(Name|State|Pid|PPid|Threads|VmRSS):' /proc/$$/status

# ps 只是把类似信息整理成列
ps -o pid,ppid,state,stat,nlwp,rss,cmd -p $$
快照性
命令执行时读取，进程可能在读取过程中变化或退出。
权限性
普通用户可以看到很多元数据，但某些命令行、环境或详细信息可能受权限和挂载选项限制。
命名空间
容器内看到的 PID 可能是 PID namespace 里的编号，宿主机看到的 PID 可能不同。
排障提醒： ps 输出中的 CPU 百分比通常不是“这一毫秒的实时占用”，而是基于进程累计 CPU 时间和运行时长计算出的近似指标；要看实时波动请用 top、pidstat 或性能工具。

4. 字段基础：PID、PPID、USER、TTY、TIME、CMD

理解 ps 的第一步是理解列名。不同选项组合会输出不同列，但核心列反复出现。

字段含义排障价值
USER/UID进程属主判断是系统服务、业务用户还是误启动的用户进程
PID进程 ID后续 kill、strace、lsof 都依赖它
PPID父进程 ID定位由谁拉起、是否被 init/systemd 收养
TTY关联终端? 常见于 daemon；pts/N 常见于 SSH 登录会话
STAT/S进程状态及附加标记判断运行、睡眠、僵尸、前台进程组等
TIME累计 CPU 时间不是墙钟运行时间；反映消耗过多少 CPU
CMD/COMMAND命令名或完整命令行确认启动参数、配置文件、工作角色
# 用可读的字段组合看进程身份
ps -eo user,pid,ppid,tty,stat,etime,time,cmd | head -20

# 查看当前 shell 的关键字段
ps -o user,pid,ppid,tty,stat,etime,time,args -p $$
TTY 的直觉： 交互命令通常有 pts/0、pts/1 这类终端；后台服务通常显示 ?，表示没有控制终端。

图解：PID、PPID、TTY 与 STAT 如何连起来

PPID 把进程连接成树；TTY 说明是否挂在终端上；STAT 说明此刻调度状态和作业控制信息。

5. STAT 深解：运行、睡眠、僵尸与附加标记

STAT 是 ps 最容易被忽略、但排障价值很高的字段。它通常由一个主状态字母和若干附加标记组成。

状态含义怎么理解
RRunning 或 runnable正在运行或在运行队列等待 CPU
SInterruptible sleep可被信号唤醒，常见于等待 I/O、socket、定时器
DUninterruptible sleep通常在等待不可中断 I/O；长期 D 状态需要关注磁盘/NFS/内核层问题
TStopped 或 traced被作业控制暂停，或正被调试器跟踪
ZZombie进程已退出但父进程尚未回收退出状态
IIdle kernel thread空闲内核线程，Linux 上常见
附加标记含义例子
ssession leaderSs
+前台进程组R+ 常见于当前终端运行的命令
<高优先级实时或高优先级任务
N低优先级 nice被 nice 降低优先级
l多线程使用 CLONE_THREAD 的进程
# 查看状态、等待通道和命令
ps -eo pid,ppid,stat,wchan:24,cmd | head -30

# 找出僵尸进程
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /Z/ {print}'
僵尸进程提醒： 僵尸进程已经不再执行代码，不能靠 kill -9 杀掉本体；要关注父进程为什么没有 wait，必要时处理父进程或重启对应服务。

6. 选项风格：UNIX、BSD、GNU 长选项

ps 最反直觉的地方是选项风格混用。ps -aux、ps aux、ps -ef 看起来相近，但语义来自不同传统。Linux 的 procps-ng 为兼容保留了多种风格。

风格特点例子说明
UNIX 风格选项前有短横线ps -ef、ps -e -o pid,cmd-e 表示所有进程，-f 表示 full 格式
BSD 风格选项前没有短横线ps aux、ps axjfa 包含其他用户终端进程，x 包含无终端进程，u 用户友好格式
GNU 长选项双短横线ps --sort=-%mem、ps --ppid 1可读性高，适合脚本和教程
# UNIX 风格：所有进程，full 格式
ps -ef

# BSD 风格：常见全量视图
ps aux

# GNU 长选项：按父进程筛选
ps --ppid 1 -o pid,ppid,stat,cmd
不要随手写 ps -aux： 在部分系统里它可能被解释为“用户 x 的所有进程”加上其他兼容行为。Linux 上常常容错，但清晰写法应是 ps aux 或 ps -ef。

7. 常用组合：ps aux 与 ps -ef

ps aux 和 ps -ef 都常用于“看全系统进程”，但输出列不同，适用的直觉也不同。

命令典型列更适合
ps auxUSER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND快速看资源占用、状态、命令行
ps -efUID PID PPID C STIME TTY TIME CMD快速看父进程关系和完整格式
ps -ejH带层级缩进的所有进程看进程树和服务派生关系
ps axjfBSD forest 格式看作业/会话/父子树
# 资源视角
ps aux --sort=-%cpu | head
ps aux --sort=-%mem | head

# 父子关系视角
ps -ef | head
ps -ejH | less

# 指定字段，减少噪音
ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%cpu | head
推荐习惯： 临时排查可用 ps aux/ps -ef，写脚本或分享命令时优先使用 ps -eo ... 明确列名，减少不同平台默认列差异。

8. 选择进程：按用户、PID、父进程、终端、命令

生产排障的关键不是“列出全部”，而是快速缩小范围。ps 支持按用户、PID、PPID、终端、会话等维度筛选。

目标命令说明
指定 PIDps -p 1234 -o pid,ppid,stat,cmd最可靠的单进程查看方式
指定多个 PIDps -p 1234,5678 -o pid,cmd逗号分隔
指定用户ps -u nginx -o pid,stat,cmd看真实用户 ID 相关进程
指定父进程ps --ppid 1024 -o pid,ppid,stat,cmd查看直接子进程
指定终端ps -t pts/0 -o pid,stat,cmd排查 SSH 会话里的进程
按命令名辅助筛选pgrep -a nginxpgrep 常比 ps | grep 更准确
# 当前用户的所有进程
ps -u "$USER" -o pid,ppid,tty,stat,etime,cmd

# 查看当前 shell 的直接子进程
ps --ppid $$ -o pid,ppid,stat,cmd

# 避免 grep 匹配到 grep 自己
pgrep -a sshd
ps -C sshd -o pid,ppid,user,stat,cmd
筛选提醒： ps | grep name 会匹配到 grep name 自己，也可能漏掉命令行被截断或改名的进程。优先用 pgrep -a、ps -C 或明确的 PID。

9. 自定义输出列：-o/--format

-o 是进阶使用 ps 的核心。它让你定义输出列、列顺序、列宽和标题，从“看一大坨默认表格”变成“为当前问题生成报表”。

字段含义常见用途
pid,ppid进程和父进程父子关系
user,uid,euid用户身份权限和启动来源
stat,state状态运行、睡眠、僵尸、停止
pcpu,pmemCPU/内存百分比资源排序和定位
rss,vsz常驻内存/虚拟内存，通常以 KiB 显示内存排障
etime,etimes运行时长，格式化/秒数判断是否刚启动、是否长期异常
args,cmd,comm命令行/命令名确认启动参数
# 为 CPU 排障定制报表
ps -eo pid,ppid,user,stat,pcpu,pmem,etime,args --sort=-pcpu | head -20

# 为内存排障定制报表，rss 单位通常是 KiB
ps -eo pid,ppid,user,stat,rss,vsz,pmem,args --sort=-rss | head -20

# 改标题和列宽
ps -eo pid=PID,ppid=PPID,stat=STATE,args=COMMAND
ps -eo pid,comm:24,etime,stat
脚本建议： 脚本里不要解析 ps aux 的固定列位置。使用 -o pid=,stat=,args= 这类明确格式，必要时去掉标题行。

流程图：从问题到 ps 命令的选择

排障时最重要的是把问题翻译成列：CPU 看 pcpu，内存看 rss/pmem，关系看 ppid，卡顿看 stat/wchan。

10. 排序：按 CPU、内存、时间和 PID

--sort 可以按字段排序，字段名前加 - 表示降序，+ 或不加通常表示升序。排序与自定义列组合后，ps 会变成非常高效的定位工具。

目标命令说明
CPU 高到低ps -eo pid,pcpu,stat,args --sort=-pcpu快速找 CPU 消耗大的进程
RSS 高到低ps -eo pid,rss,pmem,args --sort=-rssRSS 比 VSZ 更接近实际常驻内存
运行时长长到短ps -eo pid,etime,args --sort=etime不同实现对 etime 排序支持可能有差异
按 PIDps -eo pid,ppid,cmd --sort=pid观察启动顺序和 PID 范围
# top 10 CPU
ps -eo pid,ppid,user,stat,pcpu,pmem,etime,args --sort=-pcpu | head -11

# top 10 RSS，并把 KiB 粗略转换为 MiB 可交给 awk
ps -eo pid,rss,args --sort=-rss | awk 'NR==1{print;next}{printf "%s %.1fMiB %s\n",$1,$2/1024,substr($0,index($0,$3))}' | head

# 多字段排序：先按状态，再按 CPU
ps -eo stat,pid,pcpu,args --sort=stat,-pcpu | head -30
解释提醒： %CPU 和 %MEM 是方便排序的信号，不是完整性能结论。确认问题时应结合运行时长、服务指标、日志和实时工具。

11. 进程树与父子排障

很多问题不是单个进程本身，而是“谁拉起了它”“为什么有这么多 worker”“僵尸的父进程是谁”“SSH 断开后为什么任务还在”。这时需要看进程树。

# UNIX 风格进程树
ps -ejH | less

# BSD forest 风格
ps axjf | less

# 只看某个父进程的直接子进程
ps --ppid 1024 -o pid,ppid,stat,etime,cmd

# 逐步向上追父进程
ps -o pid,ppid,user,stat,cmd -p 1024
服务模型
nginx、apache、postgres 等服务常见 master/worker 或 supervisor/child 结构。不要看到多个同名进程就认为异常。
孤儿与收养
父进程退出后，子进程会被 init/systemd 或子收割器收养。PPID 变成 1 不一定是错误，但可能说明原启动会话已结束。
僵尸定位
僵尸的关键不是杀 Z 进程，而是找到 PPID，判断父进程是否卡死或代码没有正确 wait。
终端作业
TTY 和 + 标记能帮助判断当前前台进程组，解释 Ctrl-C、Ctrl-Z 和 SSH 断开的影响。

12. 线程视角：LWP、NLWP 与 -L

Linux 内核把线程也作为 task 管理。普通 ps 常按进程展示；加 -L 可以展示线程级信息。线程排障常用于 Java、数据库、Web 服务等多线程程序。

字段含义用途
LWPLight Weight Process，线程 ID/TID与 top -H、线程 dump、/proc/PID/task 对应
NLWP线程数判断线程泄漏或线程池规模
PSR最近运行 CPU 编号观察 CPU 亲和性或调度分布
PRI/NI优先级/nice 值判断调度优先级
# 查看某进程线程
ps -L -p 1234 -o pid,lwp,psr,stat,pcpu,comm

# 查看线程数较多的进程
ps -eo pid,nlwp,comm --sort=-nlwp | head

# 与 /proc 对照
ls /proc/1234/task | wc -l
Java 场景： 如果 top -H -p PID 看到某个线程 TID CPU 很高，可用 printf '%x\n' TID 转成十六进制，再去 Java thread dump 中找对应 nid。

13. ps vs top/htop/pgrep/pstree

工具优势限制适合场景
ps快照、可脚本化、自定义列强不实时精确列报表、自动化排查、记录证据
top实时刷新、系统总览、几乎默认安装批量脚本不如 ps 直接观察 CPU/内存动态变化
htop交互友好、颜色和树形直观不是所有服务器默认安装人工登录排障
pgrep/pkill按进程名/命令行查找或发信号模式写错可能匹配过宽替代 ps | grep，配合精确确认
pstree树形表达清晰字段不如 ps 丰富理解服务父子结构
# 组合使用示例：先找 PID，再看细节
pgrep -a nginx
ps -o pid,ppid,user,stat,etime,%cpu,%mem,args -p "$(pgrep -n nginx)"

# 实时观察某进程和线程
top -p 1234
top -H -p 1234

14. 生产排障剧本：CPU、内存、僵尸、孤儿进程

CPU 异常

# 先找高 CPU 进程，再看状态和运行时长
ps -eo pid,ppid,user,stat,pcpu,etime,args --sort=-pcpu | head -20

# 如果是多线程程序，展开线程
ps -L -p 1234 -o pid,lwp,psr,stat,pcpu,comm --sort=-pcpu

内存异常

# RSS 更接近常驻物理内存，VSZ 可能包含未实际占用的虚拟地址空间
ps -eo pid,ppid,user,stat,rss,vsz,pmem,etime,args --sort=-rss | head -20

# 看进程是否长期存在
ps -o pid,etime,rss,vsz,cmd -p 1234

僵尸进程

# 找僵尸和父进程
ps -eo pid,ppid,stat,etime,cmd | awk '$3 ~ /Z/ {print}'
ps -o pid,ppid,user,stat,etime,cmd -p PARENT_PID

孤儿或异常父子关系

# 看 PPID=1 的进程，确认哪些是正常服务，哪些是被收养任务
ps --ppid 1 -o pid,user,stat,etime,cmd

# 看整棵树
ps axjf | less
处置前确认： 不要因为一个进程 CPU 高就立刻 kill -9。先确认它是否是正常批任务、是否有 supervisor 会自动拉起、是否能优雅停止、是否需要保留现场。

安全排障的顺序是确认身份、确认关系、确认影响，然后选择最温和且可回滚的处置方式。

15. 安全注意：从观察到处置

ps 本身是只读观察工具，风险通常来自“根据 ps 输出做下一步动作”。特别是批量 kill、自动化脚本和按名称匹配，需要格外保守。

先打印，再执行
批量操作前先输出将被影响的 PID 和完整命令行。
优先 TERM
能优雅退出就不要直接 kill -9；KILL 不给进程清理资源的机会。
使用服务管理器
systemd 管理的服务优先用 systemctl status/stop/restart，避免 supervisor 立即拉起或状态混乱。
保留现场
严重问题先记录 ps、日志、线程 dump、打开文件和网络连接，再重启。
# 安全确认：先列出会匹配的进程
pgrep -a -f 'my-worker --queue critical'

# 再查看详细字段
ps -o pid,ppid,user,stat,etime,pcpu,pmem,args -p "$(pgrep -n -f 'my-worker --queue critical')"

# 如果确需发信号，优先 TERM，并观察是否退出
kill -TERM 1234
ps -p 1234 -o pid,stat,etime,cmd
自动化警告： 不要写 ps aux | grep name | awk '{print $2}' | xargs kill -9 这种无确认流水线。它可能匹配到 grep、自身脚本、无关命令行参数，且没有优雅退出机会。

16. 常见坑、可移植性与练习

常见坑

坑 1：把 ps 当实时监控
它是快照。要看变化请用 top、pidstat 或循环采样。
坑 2：误写 ps -aux
清晰写 ps aux 或 ps -ef，不要依赖兼容解析。
坑 3：grep 匹配到自己
优先 pgrep -a、ps -C 或明确 PID。
坑 4：只看 VSZ
VSZ 是虚拟地址空间，不等于实际物理内存；排查常看 RSS/PSS 等更多指标。
坑 5：看到 Z 就 kill -9
僵尸已退出，关键是父进程是否回收。
坑 6：不同系统字段不同
Linux procps、BSD/macOS ps、BusyBox ps 支持的选项和字段差异很大。

可移植性

本教程以 Linux/procps-ng 为主。macOS、FreeBSD、BusyBox、容器极简镜像里的 ps 可能不支持 --sort、--ppid 或某些 -o 字段。跨平台脚本应在目标环境运行 ps --help、man ps 或改用更保守字段。

# 查看当前 ps 实现
ps --version 2>/dev/null || ps -p $$ -o pid,ppid,stat,comm

# BusyBox/极简环境可能只支持很少选项
ps
ps w

练习任务

  1. 用 ps -o pid,ppid,tty,stat,cmd -p $$ 查看当前 shell。
  2. 比较 ps aux 与 ps -ef 的列差异。
  3. 用 ps -eo pid,ppid,stat,cmd --sort=ppid 观察父子关系。
  4. 用 ps --ppid $$ 查看当前 shell 的直接子进程。
  5. 用 ps -eo pid,rss,pmem,args --sort=-rss | head 找内存占用较高的进程。
  6. 用 ps -L -p PID 展开一个多线程进程。
  7. 故意启动 sleep 300，用 ps 找到它，再用 kill -TERM 优雅结束。
# 练习：启动一个可观察的后台进程
sleep 300 &
demo_pid=$!
ps -o pid,ppid,tty,stat,etime,cmd -p "$demo_pid"
ps --ppid $$ -o pid,ppid,stat,cmd
kill -TERM "$demo_pid"
